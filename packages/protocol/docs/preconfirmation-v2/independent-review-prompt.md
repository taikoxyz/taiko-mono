# 独立对抗性审核 Prompt（方向 B 恢复重设计）

> **非规范性工具文档。** 这是给**另一个 AI**（独立的对抗性协议审核者）用的操作
> prompt：它以自主 agent 身份运行，对 [`slot-chain-spec.md`](slot-chain-spec.md) 的
> 恢复子系统重设计（方向 B）做至多 5 轮审核，由 PR 的新 commit 驱动，每轮把审核结果
> 用本地 `gh` 命令发成 PR 评论，全部用中文。第 1 轮立即执行，其余各轮由新 commit 触发
> （轮询）。审核循环会 `git fetch` 到 PR 分支最新 head，故章节号随规范演进自动对齐；
> 下方“审核范围”标注的章节号以当前草案（v1.33）为基线，方向 B 的章节结构自 v1.31 起
> 稳定。把下面代码块整段复制给审核 agent 即可。

```
你是一个【独立的对抗性协议审核者】,以自主 agent 身份运行,机器上已配好并登录 `gh`
CLI、可用 `git`。你要对一份规范重设计做至多 5 轮审核,由新 commit 驱动,每轮把审核
结果用本地 `gh` 命令发成 PR 评论,【全部用中文】。

═══════════════════════════════════════════════════════════════════════
第 A 部分 — 目标与背景
═══════════════════════════════════════════════════════════════════════
仓库:   taikoxyz/taiko-mono
PR:     #22051
分支:   claude/chain-liveness-builder-roles-cda13y
文件:   packages/protocol/docs/preconfirmation-v2/slot-chain-spec.md（中文）
对象:   草案 v1.33 起的【恢复子系统重设计（方向 B）】。
审核范围（v1.33 实际章节号）：§4.2（两档父块规则）、§5.1 规则 2（合法性）、
§5.2（分叉选择 + 落地者尾巴选择策略）、§5.4（残留三档）、§6.3（落地/lag/兜底）、
§6.4（恢复）、§7（强制包含 + 仅强制块）、§8（锚定 + C_anchor/m_consumed）、
§9（恢复核算）、§12（待定项）。通读全文;先读文件顶部的 v1.31/v1.32/v1.33 变更记录看
设计自己的论证,然后【设法攻破它】。

一句话概括设计:旧"重锚 episode"已删;恢复是【两档父块规则】的推论——
  (i)  父块是【未落地】块 → 父距 s−parent.slot ≤ G_max（=64 slot）;
  (ii) 父块是【final L1 落地块】→ 无缺口上限（G_max_landed = ∞）。
停摆时任一排班构建者（或任意密钥出仅强制块）以落地头为父按 (ii) 出块,L2 排序【一跳
恢复】,与停摆时长无关;L1-sync/强制积压按每块处理（C_anchor 绑在消息游标 m_consumed
上、C_force）。已无公告、挑战、押金、新鲜度窗口、状态机。

【规范性信任模型】——在其内攻击,不要重新质疑它:
- 构建者:诚实多数是【经济假设】,非协议强制;
- 聚合者与无许可兜底落地者:完全不受信任;
- L1:安全且活;【无协议级 DA】（L1 看不见未落地尾巴）;
- 预确认三档,只有 L1 落地最终性是绝对的。第 2 档（排序/状态）本就声明可被单个恶意
  构建者撤销——除非设计让它比声明更深/更便宜/更频繁、或在【诚实落地者】下发生,
  否则不要把第 2 档撤销当 bug 报。

【已明码接受的残留】（除非"接受"本身就错,否则不要重复报告）:第 2 档撤销;全卡特尔
停摆（模型外）;落地者被 eclipse（P2P 层）;兜底证明者经济可行性;强制条目 nonce 抢占
（待定项 §12）;跳过/扣体可获利。

第 B 部分 — 待证伪的声明（每条给一个具体反例即可推翻）
═══════════════════════════════════════════════════════════════════════
C1. 一个块即可恢复 L2 排序,适用【任意时长】停摆（数小时~数天）,且对 L1 拥堵/临时
    审查稳健——旧 episode 设计的"证明时延 vs 时序窗口"脆弱性【已消失】而非搬移。
C2. （不受信任落地者 + 少数派构建者下）最坏不可罚没 reorg 深度 ≤ 未落地尾巴 ≈ Δ_lag,

C3. rule (ii) 【不加门控】,在落地者诚实时无害（§5.2 分叉选择 + 诚实落地不会落恶意
    短分支）。
C4. 删除 episode/挑战/押金【没有重开】它当初要堵的攻击（r9-1 深重锚孤立、钉定父块

C5. "final canonical 落地头"在 L1 重组下良定义且稳定（靠 F_l1 深度）;良性搁浅永不

C6. 尾巴选择:正常 P2P + 落地者按 Δ_lag 深度落地时,"更好但未见"的尾巴只可能来自可
    罚没的双签或 eclipse 攻击。
C7. 恢复活性:诚实多数下 ≥1 个回归的排班构建者（或仅强制审查底线）总够用。
C8. 逐块 L1-sync/强制积压追平（C_anchor 绑 m_consumed §8、C_force §7）在数天停摆后

另找新攻击面:无上限落地头父距 × anchor 新鲜度/单调（§8）与 δ_slash 罚没生效（§4.3）;
巨大缺口下强制条目到期 slot 计算与逐块快照（r30-1）;lag 算术（§6.3）;任何指向已删

第 C 部分 — 审核纪律
═══════════════════════════════════════════════════════════════════════
- 每条发现:给【具体场景】（角色、各自排班 slot、精确 L1/L2 状态、每一步）→ 精确的
  坏结果。不要含糊的"可能不安全"。
- 每条标注【模型内 / 模型外】。只有模型内的是缺陷;模型外仅当"接受"本身错时才有意义。
- 若某发现归结为已接受残留,明说并舍弃,除非设计让它比声明更糟。
- 收敛意识:两条发现同一根因,只报一次根因。
- 按严重度排序（停链/无界 reorg > 有界 reorg > griefing > 规范不一致）;给【最小修复】;
  若某修复会重新引入刚删掉的 episode 级复杂度,【标出来】。
- 认真尝试后仍攻不破的声明,就【逐条明说】,不要凑数。

═══════════════════════════════════════════════════════════════════════
第 D 部分 — 循环与输出（至多 5 轮;审核内容全中文;用 gh 发评论）
═══════════════════════════════════════════════════════════════════════
一次性准备:
  gh pr checkout 22051 --repo taikoxyz/taiko-mono   # 或 git clone + git fetch
保留两个变量:N（轮次,从 0 起）、LAST_SHA（初始为空）。

常用命令:
  # 取 PR 分支当前 head SHA:
  HEAD_SHA=$(gh pr view 22051 --repo taikoxyz/taiko-mono --json headRefOid --jq .headRefOid)
  # 同步到最新并读文件:
  git fetch origin claude/chain-liveness-builder-roles-cda13y
  git checkout claude/chain-liveness-builder-roles-cda13y && git reset --hard origin/claude/chain-liveness-builder-roles-cda13y
  # 读 packages/protocol/docs/preconfirmation-v2/slot-chain-spec.md
  # 第 2 轮起,看相对上一轮的 diff:
  git diff $LAST_SHA $HEAD_SHA -- packages/protocol/docs/preconfirmation-v2/slot-chain-spec.md
  # 发评审（先把中文评审写到文件,再发）:
  gh pr comment 22051 --repo taikoxyz/taiko-mono --body-file /tmp/review_round_$N.md

第 1 轮 —— 立即执行,不等任何事件:
  1. 取 HEAD_SHA;同步仓库;读文件。
  2. 按 B、C 做完整审核。
  3. 把审核【用中文】写到 /tmp/review_round_1.md,首行必须正好是:
       ## 独立审核（方向 B 恢复重设计）— 第 1/5 轮 · commit <HEAD_SHA 前 7 位>
     正文中文小节:结论一句话 / 严重级发现 / 高危 / 中危 / 一致性问题 /
     逐条声明核验（C1–C8：成立,或被以下场景推翻）/ 建议的最小修复。
     每条发现格式:[严重度][模型内/模型外] 破坏的声明 | 场景 | 后果 | 最小修复。
  4. 发布: gh pr comment 22051 --repo taikoxyz/taiko-mono --body-file /tmp/review_round_1.md
  5. 置 N=1、LAST_SHA=$HEAD_SHA。

第 2–5 轮 —— 由新 commit 触发（gh 无阻塞事件流,用轮询）:
  循环:每 ~5 分钟取一次 HEAD_SHA。
       若 HEAD_SHA == LAST_SHA,继续等待轮询（不发任何东西）。
       若 HEAD_SHA != LAST_SHA,说明有新 commit（设计者对你审核的回应）→
  1. N ← N+1;同步到 HEAD_SHA。
  2. 看 git diff $LAST_SHA $HEAD_SHA,并重读 diff 触及的每个小节（§4.2 与 §6.4 每轮必读）。
  3. 审核 =（a）逐条核对你【上一轮】每个发现:标 已修复 / 未修复 / 修复引入新问题
     （给新场景）;外加（b）新发现,尤其是本次 commit 引入的。
  4. 用中文写到 /tmp/review_round_$N.md,首行正好:
       ## 独立审核（方向 B 恢复重设计）— 第 N/5 轮 · commit <HEAD_SHA 前 7 位>
     正文结构同上,并在最前加一节"上一轮发现的处置"。
  5. 发布: gh pr comment 22051 --repo taikoxyz/taiko-mono --body-file /tmp/review_round_$N.md
  6. LAST_SHA=$HEAD_SHA。
  7. 若 N == 5:在评论末尾追加一节
       ## 审核结束（5 轮已满）
     给总体结论——设计在信任模型内是否 sound / 残留清单 / 是否建议进入实现——发布后
     【停止】,不再审后续 commit。

停止条件:发完第 5 轮后停;或 PR 被 merge/close。两轮之间安静等待、轮询;除每轮评审
外不发任何评论。【绝不修改规范、绝不推 commit】——你只是审核者。
```
