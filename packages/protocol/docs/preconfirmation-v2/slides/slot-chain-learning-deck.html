Mental model

A slot is an opportunity, not a finality promise

1 s

L2 slot

A timestamp position measured from genesis. Slot gaps are legal.

+1

L2 block height

Each executed block advances height by one, even if several slots were skipped.

L1

Confirmation depth

Counted in L1 blocks. Beacon slots serve schedule authentication.

Example

Blocks at L2 slots 100 and 104 may have consecutive heights 500 and 501. The four-second gap creates no missing EVM block numbers.

One-second slots do not guarantee one block per second or one-second finality. Timestamp deadlines and L1 block-depth requirements use different clocks.

Builder schedule

Lookahead fixes who may sign each slot

  • Each window contains 384 one-second slots.
  • An authenticated finalized snapshot determines the eligible registry and randomness input.
  • The initial lookahead is 768 L2 slots; new registrations do not rewrite already fixed schedules. Slashing can still make future tickets vacant outside a frozen context.
  • One registry has at most 64 active cells. Entry, exit and retained liability have explicit delays.

How tickets become slots

Bond-weighted, capped D’Hondt allocation repeatedly awards the next ticket to the largest bond / (tickets + 1) score.

Each address receives at most 76 tickets. Deterministic tie-breaking and placement turn those tickets into an exact schedule; shortages become VACANT.

At least six eligible addresses are needed to fill 384 slots. Addresses are not necessarily independent operators: the cap does not prevent Sybils or collusion.

Implemented structure · builder registry

One state owner, two fixed lifecycle facets

BuilderRegistry owns the state and custody

Registry roots, builder generations, window tranches and withdrawal credits stay at the Registry address. Seven explicit wrappers dispatch to constructor-pinned facet targets under a shared operation lock.

Seat facet · 3 selectors

Register a builder, request exit and process maintenance.

Lease facet · 4 selectors

Reserve a window, normalize tranches, release a tranche and reclaim a generation.

Stateless proof verifier

Checks Registry witnesses and equivocation identity through bounded, exact static calls.

The facets have fixed selector sets, code/configuration pins and a common storage-layout hash. They provide no mutable upgrade target or generic fallback dispatch.

The builder “Seat” facet manages registry membership. The separate aggregator service market is still unimplemented. Registry source and tests exist, but the full ScheduleOracle/Router integration remains a release gate.

What users can rely on

Four distinct stages of assurance

1

Observed

A builder has signed a promise. Execution and delivery are not yet proved.

2

Provisionally proved

L1 accepted a normal candidate. A better candidate can still replace it.

3

Canonical

Normal close or recovery commit selects the stored L2 state.

4

L1-final

The underlying L1 finality policy makes that commitment final.

Wallets must keep observed and provisionally proved states visibly provisional. An escape commit revokes omitted promises and returns omitted transactions to the mempool.

A signature establishes authorship and the chosen parent. Same-context equivocation can be slashed; aggregate off-chain promises are neither reserved against the bond nor insured.

Normal settlement

Candidates compete until a fixed deadline

1. Arm

Anyone records the current L1 block number.

2. Activate

A later call authenticates that block and freezes the base, context and deadline.

3. Prove

Valid candidates compete against the same frozen base. Only a strictly better candidate replaces the best.

4. Close

At maturity, a qualifying best becomes canonical. An empty or stale window cancels.

Candidate ordering

More blocks first → later tip slot → smaller tip hash. Replacement does not reset the deadline.

The close still checks freshness

The best must consume the required due queue prefix and retain enough authenticated data lifetime for the reorg margin.

Initial settlement window: 1,200 seconds. Submitting a valid normal proof does not immediately make it canonical.

Data and execution

A commitment binds bytes; it cannot recreate them

What the validity proof checks

  • Parent linkage, slots, the exact context and scheduled signatures for signed tiers.
  • Authenticated blob/body coverage and the frozen queue prefix.
  • Ethereum execution, transaction and receipt roots, and the new canonical state.

What a prover still needs

  • Block bodies and unexpired forced transaction bytes.
  • Canonical state-trie nodes and runtime-bytecode preimages, checked against their commitments.
  • Enough resources to generate the proof and pay for an L1 transaction.

Archives can be untrusted and replaceable

Hash checks establish correctness of supplied data. They do not establish availability after every copy is lost.

The design does not claim recovery from a state root alone after total canonical-data loss, or progress during a permanent proving-system outage.

When normal progress stalls

Recovery uses the first valid proof

Objective activation

Recovery opens when the canonical tip’s lag exceeds 3,600 seconds, when a forced queue head is due, or at an earlier configured aggregator SLA trigger.

A due head cancels an immature normal window. A mature qualifying best may close first; causes are then recomputed.

A frozen round

Each round fixes the canonical base, anchor, queue cutoff, admission rules and deterministic escape slot.

After now > expiresAt, anyone may refresh the expired round. A live proof target cannot be refreshed away.

Signed recovery

Scheduled signatures + validity proof

or

Unsigned escape

Deterministic block + validity proof

→

Canonical commit

First valid candidate wins

A new round keeps the episode and canonical base. Later proofs against an old round or a committed base are stale.

The minimal recovery path

Unsigned means no builder signature

Exactly one deterministic block

  • Extends the L1-final canonical tuple.
  • Contains the protocol anchor and the maximum allowed prefix of the frozen forced queue.
  • Has no discretionary transactions, blob body or beneficiary-chosen coinbase.
  • An SLA-triggered escape can be anchor-only when the queue is empty.

Execution must still be proved

The proof checks the exact block and its state transition. The recovery anchor must reach its required L1 depth; slot and freshness rules still apply.

No builder cartel, empty registry or absent aggregator has a veto over this path, provided the required data, proof system and funded prover remain available.

An escape is not a proof-free empty block. It restores canonical progress and expires every omitted unfinalized promise.

Forced transactions · kind 0

Validate the envelope before it enters the queue

Supported forced inputs

  • Chain-protected legacy transactions (type 0).
  • Access-list transactions (type 1) and dynamic-fee transactions (type 2), where the active fork supports them.
  • Canonical encoding, chain ID, signature, fee fields and creation limits must pass the admission rules.

The forced lane is deliberately bounded

Unprotected legacy, blob type 3, authorization-list type 4, reserved system type 0x7f and unknown types are rejected at admission.

Discretionary transaction support is a separate profile decision.

gasLimit ≥ max(intrinsicGas, calldataFloorGas)

Accounted gas measures queue capacity. It cannot turn an invalid transaction into a valid one. Execution-time state or fork changes still require a complete classifier.

Aggregator service market

The auction buys proving service

  • One primary, up to three standbys, four waiting-offer cells and one stage.
  • Operators offer an ask per second and post the exact SLA bond. Sponsor-funded reserves pay eligible service premiums.
  • Quotes mature in both timestamp and L1 block-number clocks before selection.
  • A healthy primary is competitively replaceable by a strictly cheaper ask, subject to the tenure and handover rules.

Price discovery has distinct rules

Pending offers rank by ask, maturity and deterministic tie-breaks. Replacing the worst standby in a full lineup additionally uses the specified anti-churn threshold.

A lower ask can win service work; it does not win ownership of the L2 slot schedule.

Seat economics are optional for consensus. Missing seats, failed payments or a full duty ring must not block a valid canonical transition.

Slot Chain v2.28 · Economics, slashing and payments18 / 30 · Next →

The recovery tradeoff

A late proof can cure the predecessor’s duty

Progress remains available

A qualifying commit can satisfy an allocated duty through slash equality. After the strict slash threshold it can still advance canonical state, but cannot cure BREACHED.

Cure can close the predecessor and start a selected successor, including before failover. A cured former primary is not restored after removal.

The economic consequence

The successor may have a higher ask. The predecessor can end SATISFIED and ultimately receive its full bond as owner withdrawal credit.

A larger refundable bond creates no guaranteed loss on this path. Capital cost and competitive pressure require separate analysis.

This is an accepted design exposure. New price limits or penalties would be a separate mechanism change; they must not be added as a condition for canonical proof acceptance.

Bridge ingress · kind 1

A forced credit is one step toward delivery

1. Source escrow

A same-L1 DIRECT ETH message escrows value, execution fee and liquidity fee.

2. Queue admission

A preparer supplies the full Message and queue deposit. Source emission alone is not admission.

3. Durable L2 pin

Forced processing applies the kind-1 credit idempotently. It does not call the recipient.

4. LP-funded attempt

A willing liquidity provider funds the L2 ticket and processing. Message bytes and the required execution budget are needed.

DONE

The terminal proof authenticates the LP’s L1 pull credit. Completed settlement may involve a recipient call or, when invocation is prohibited, a destination-owner value pull.

FAILED / cancellation

Absent liquidity or missing Message bytes can prevent delivery. Source cancellation or proved failure creates a user refund credit; actual repayment requires a successful withdrawal.

Forced queue consumption is not recipient delivery, and available source ETH does not create L2 liquidity.

Bridge boundaries

Routes and terminal outcomes remain pinned

  • Launch supports DIRECT ETH from the settlement L1. Cross-L1 kind-1 ingress is outside this version.
  • ERC20, ERC721, ERC1155 and official Vault flows remain V1; they cannot originate a V2 credit.
  • An immutable inbox store pins the destination credit. Later resolver changes cannot retarget it.
  • Append-only terminal commitments authenticate completed settlement or failure and the corresponding source pull.

Bounded deadlines, real dependencies

Strictly after enqueueBy, an unqueued message can be canceled, creating a source-owner refund credit and forbidding later enqueue.

Strictly after processBy, an unterminated credit can enter FAILED without Message bytes. Historical proofs still depend on retained witness data.

The immutable custody kernel is not self-healing. Its compiled code, conservation properties and failure paths must pass the production gates before live value depends on it.

L1 feasibility

A large block limit cannot rescue an oversized call

cap = min(configured L1 block gas limit, 16,777,216)
tokens = zero calldata bytes + 4 × nonzero calldata bytes
required = 21,000 + max(4 × tokens + execution budget, 10 × tokens)
ceil(1.30 × required) ≤ cap

Budget the complete transaction

Include decoding, cold reads, memory, call forwarding, full callee consumption, postreads and the final success or rejection work. Do not rely on refunds.

The calldata floor is a maximum

It is not a second execution charge. This formula covers a direct call with an empty access list and no authorization list; other envelopes add their exact intrinsic charges.

Synthetic model budgets are targets, not compiled gas certificates. Every maximum supported path needs fork-correct measurement and the complete 30% margin.

Version migration · specified timing

A migration arm cannot remain live forever

1

Seven-day notice

The immutable DAO proposer queues the exact operation. Anyone may execute it after the full 604,800-second delay.

2

Seven-day execution window

A migration arm must execute between maturity and maturity + 604,800 seconds, including both endpoints.

3

Seven-day live lease

Successful arming starts a separate, non-extendable lease. Activation requires time strictly before its expiry.

At or after lease expiry, anyone can abort ARMED or READY and restore source ACTIVE. A successful expiry abort invalidates every arm queued at or before that abort timestamp.

A retry must be queued strictly after the abort and serve a fresh seven-day notice. A mature sibling arm cannot immediately reclose admissions.

These are the specified Timelock/PVM/Router rules. The implemented RootMigrationExecutor governs root bootstrap; it does not implement this later-version migration journal.

Version migration · one reverting transaction

Authority changes through one complete journal

  1. Verify and enter ACTIVATING. Freeze the source (MFRZ), adopt the target canonical state (MCAN).
  2. Install inert ingress and source authority. Bind kind 0, activate SourceBridge, update indexes, consume and post-read the route package (BRC1).
  3. Seal the adapter and move the queue. Bind Bridge ingress, execute QMIG, then make the three MAPS consistency reads.
  4. Publish the result. Consume registration, write receipts and indexes, publish ACTIVE; clear the context and return the Router to IDLE.
  5. Finish the lease. VMC1 consumes the lease and returns the version manager to IDLE. The final VML1 static read must return canonical NONE.
VMC1: last mutating external callVML1: final external call

Ingress bindings stay inert until ACTIVE publication. The source, target, queue and version manager still share the same outer transaction’s rollback boundary.

Worked failure case

Even the final lease read can roll activation back

Inject a fault at VML1

The Router has published ACTIVE and returned to IDLE. VMC1 has consumed the lease. The final read returns malformed data or a lease other than canonical NONE.

The entire activation transaction must revert.

State after the revert

Restore READY/IDLE and the prior live lease; old source and queue authority, cursor and payment state; the empty target; prior adapter seals; inactive target SourceBridge; and unused registration with no activation receipt.

What survives

Accounts created by earlier independent SBD1/SAD1 transactions remain deployed. The failed activation does not erase those transactions. Permissionless retry or a mature abort remains possible.

ACTIVE publication inside a transaction is not a partial success. Faults at BRC1, VMC1 or VML1 all remain inside the same revert domain. Genesis has no VMC1 call.

Legacy genesis · specified cutover

Genesis has a bounded campaign and an exit path

Delayed campaign→Forced / proposal cutoffs→Bounded scan→QUIESCENT

If a valid proof lands

Proof verification precedes transaction-local READY, legacy freeze, target adoption and Queue migration. The public gate changes from ACTIVE(legacy) to ACTIVE(target) atomically.

If the campaign expires

At either the block or timestamp bound, activation rejects and permissionless local resume restores legacy ACTIVE. The campaign lasts at most 600 L1 blocks / 7,200 seconds from publication.

Preparation caps: 1,024 proposals + 1,024 forced rows; 4 MiB total. Maximum-progress batches contain up to 16 rows, bounding successful scans to 128 calls.

In-place cutover imports only the last finalized checkpoint. It abandons unfinalized proposals and pending forced records. Lossless treatment or an incompatible legacy deployment requires a separate state migration.

Resume-safe clocks, retained data and the exact legacy profile are prerequisites. Root deployment contracts do not replace the missing legacy cutover implementation or real genesis circuit.
