Implementation snapshot · PR #22139 · v3.0 revision

The design is broader than the code present today

Registry cluster

BuilderRegistry with its two lifecycle facets and stateless proof verifier; one-shot activation by a constructor-pinned activator.

Schedule and history proofs

Schedule SSZ multiproof verification, snapshot evaluation helpers and historical L1 header proofs.

Shared foundations

Types, codecs, fixed trees and MMR, signatures, equivocation evidence, economics, custody accounting and L1 resource arithmetic.

Still specified and modeled

Settlement (a new implementation for the existing Inbox proxy), ForcedQueue, ScheduleOracle, AggregatorSeatMarket, the L2 client fork rules and the validity circuits have no implementation rows yet.

Removed from the design, not merely unimplemented: the root factory, CREATE3 proxy and migration executor, and the fresh V2 bridge with its custody, credits and liquidity pools. The registration MPT verifier and profile library go with them.

Foundry suites, golden vectors and integration checks exist for the partial implementation. A helper or verifier is not the complete protocol path that uses it. See the source and evidence map for the current boundary.

Mental model

A slot is an opportunity, not a finality promise

1 s

L2 slot

Seconds since L2 genesis: timestamp − GENESIS_TIMESTAMP. Slot gaps are legal.

+1

L2 block height

Each executed block advances height by one, even if several slots were skipped.

L1

Confirmation depth

Counted in L1 blocks. Beacon slots serve schedule authentication.

Example

Blocks at L2 slots 100 and 104 may have consecutive heights 500 and 501. The four-second gap creates no missing EVM block numbers.

One-second slots do not guarantee one block per second or one-second finality. Imported V1 blocks and Slot Chain blocks share the one slot clock; timestamp deadlines and L1 block-depth requirements use different clocks.

Builder schedule

Lookahead fixes who may sign each slot

  • Each window contains 384 one-second slots.
  • An authenticated finalized snapshot determines the eligible registry and randomness input.
  • The initial lookahead is 768 L2 slots; new registrations do not rewrite already fixed schedules. Slashing can still make future tickets vacant outside a frozen context.
  • One registry has at most 64 active cells. Entry, exit and retained liability have explicit delays.

How tickets become slots

Bond-weighted, capped D’Hondt allocation repeatedly awards the next ticket to the largest bond / (tickets + 1) score.

Each address receives at most 76 tickets. Deterministic tie-breaking and placement turn those tickets into an exact schedule; shortages become VACANT.

At least six eligible addresses are needed to fill 384 slots. Addresses are not necessarily independent operators: the cap does not prevent Sybils or collusion.

Implemented structure · builder registry

One state owner, two fixed lifecycle facets

BuilderRegistry owns the state and custody

Registry roots, builder generations, window tranches and withdrawal credits stay at the Registry address, a DAO-owned UUPS proxy. Seven explicit wrappers dispatch to constructor-pinned facet targets under a shared operation lock.

Seat facet · 3 selectors

Register a builder, request exit and process maintenance.

Lease facet · 4 selectors

Reserve a window, normalize tranches, release a tranche and reclaim a generation.

Stateless proof verifier

Checks Registry witnesses and equivocation identity through bounded, exact static calls.

Facets and verifier are plain immutable helpers with fixed selector sets, code pins and a common storage-layout hash. Activation is a one-shot call by a constructor-pinned activator; there is no CREATE3 position check.

The builder “Seat” facet manages registry membership. The separate aggregator service market is still unimplemented. Registry source and tests exist, but the ScheduleOracle integration remains a release gate.

What users can rely on

Four distinct stages of assurance

1

Observed

A builder has signed a promise. Execution and delivery are not yet proved.

2

Provisionally proved

L1 accepted a normal candidate. A better candidate can still replace it.

3

Canonical

Normal close or recovery commit selects the stored L2 state and saves its L1 checkpoint.

4

L1-final

The underlying L1 finality policy makes that commitment final.

Wallets must keep observed and provisionally proved states visibly provisional. An escape commit revokes omitted promises and returns omitted transactions to the mempool.

A signature establishes authorship and the chosen parent. Same-context equivocation can be slashed; aggregate off-chain promises are neither reserved against the bond nor insured.

Normal settlement

Candidates compete until a fixed deadline

1. Arm

Anyone records the current L1 block number.

2. Activate

A later call authenticates that block and freezes the base, context and deadline.

3. Prove

Valid candidates compete against the same frozen base. Only a strictly better candidate replaces the best.

4. Close

At maturity, a qualifying best becomes canonical. An empty or stale window cancels.

Candidate ordering

More blocks first → later tip slot → smaller tip hash. Replacement does not reset the deadline.

The close still checks freshness

The best must consume the required due queue prefix and retain enough authenticated data lifetime for the reorg margin.

Initial settlement window: 1,200 seconds. Submitting a valid normal proof does not immediately make it canonical.

Data and execution

A commitment binds bytes; it cannot recreate them

What the validity proof checks

  • Parent linkage, slots, header rules (timestamp, anchor field, extraData, coinbase) and the exact context.
  • Signatures for signed tiers, authenticated blob/body coverage and the frozen queue prefix.
  • Standard execution, transaction and receipt roots, forced classification and the new canonical state.

What a prover still needs

  • Block bodies and unexpired forced transaction bytes.
  • Canonical state-trie nodes and runtime-bytecode preimages, checked against their commitments.
  • Enough resources to generate the proof and pay for an L1 transaction.

Archives can be untrusted and replaceable

Hash checks establish correctness of supplied data. They do not establish availability after every copy is lost.

The design does not claim recovery from a state root alone after total canonical-data loss, or progress during a permanent proving-system outage.

L2 execution · inherited from #22147

One header field replaces the anchor transaction

1. The header carries the anchor

parentBeaconBlockRoot = the candidate’s L1 anchor hash, on every block of every tier. The proof binds it to the statement’s anchorHash.

→

2. EIP-4788 records it

The standard pre-execution call stores the hash in the L2 beacon-roots ring, keyed by the block timestamp. No system transaction runs.

→

3. revealCheckpoint keeps it

Anyone proves the L1 header preimage to the L2 SignalService; Checkpoint{number, hash, stateRoot} becomes permanent.

What a block contains

The header, then the upfront-valid forced transactions of the frozen FIFO prefix, then discretionary transactions. There are no protocol system transactions, no custom transaction type and no reserved senders.

What the header still fixes

timestamp = GENESIS_TIMESTAMP + slot; extraData = base-fee sharing percentage, tier byte (1 normal, 2 recovery, 3 escape) and five zero bytes; the signed coinbase for signed tiers and the protocol sink for escape.

The L2 Anchor contract is treasury-only after #22147: no golden-touch key, no ancestors ring, no anchorV4. Slot Chain adds no L2 contract and no L2 change beyond that fork.

When normal progress stalls

Recovery uses the first valid proof

Objective activation

Recovery opens when the canonical tip’s lag exceeds 3,600 seconds, when a forced queue head is due, or at an earlier configured aggregator SLA trigger.

A due head cancels an immature normal window. A mature qualifying best may close first; causes are then recomputed.

A frozen round

Each round fixes the canonical base, anchor, queue cutoff, admission rules and deterministic escape slot.

After now > expiresAt, anyone may refresh the expired round. A live proof target cannot be refreshed away.

Signed recovery

Scheduled signatures + validity proof

or

Unsigned escape

Deterministic block + validity proof

→

Canonical commit

First valid candidate wins

A new round keeps the episode and canonical base. Later proofs against an old round or a committed base are stale.

The minimal recovery path

Unsigned means no builder signature

Exactly one deterministic block

  • Extends the L1-final canonical tuple.
  • Contains only the maximum allowed prefix of the frozen forced queue, possibly zero transactions.
  • Has no discretionary transactions, blob body or beneficiary-chosen coinbase; tier byte 3 and the protocol coinbase sink.
  • Still carries a fresh L1 anchor hash in its header, so new L1 state reaches L2 even when the block is empty.

Execution must still be proved

The proof checks the exact block and its state transition. The recovery anchor must reach its required L1 depth; slot and freshness rules still apply.

No builder cartel, empty registry or absent aggregator has a veto over this path, provided the required data, proof system and funded prover remain available.

An escape is not a proof-free empty block. It restores canonical progress, publishes an anchor and an L1 checkpoint, and expires every omitted unfinalized promise.

Forced transactions · kind 0

Validate the envelope before it enters the queue

Supported forced inputs

  • Chain-protected legacy transactions (type 0).
  • Access-list transactions (type 1) and dynamic-fee transactions (type 2), where the active fork supports them.
  • Canonical encoding, chain ID, signature, fee fields and creation limits must pass the admission rules.

The forced lane is deliberately bounded

Unprotected legacy, blob type 3, authorization-list type 4 and unknown types are rejected at admission. Kind 0 is the only forced kind; enqueueForcedTransactionV2 lives directly on the ForcedQueue, with no separate ingress adapter.

Discretionary transaction support is a separate profile decision.

gasLimit ≥ max(intrinsicGas, calldataFloorGas)

Accounted gas measures queue capacity. It cannot turn an invalid transaction into a valid one. Execution-time state or fork changes still require a complete classifier.

Consume every item with one exact outcome

Kind-0 classification in evaluation order

An invalid head need not trap valid work behind it

A

Admitted earlier

A transaction passed static admission. Its sender later becomes ineligible under the active execution rules.

6

Prove the rejection

With expiry, nonce, funds and fee checks passing, raw bytes plus authenticated state establish INVALID_NO_TX.

B

Keep processing

The next fitting FIFO item is valid. It is included as an ordinary Ethereum transaction.

If A’s bytes are missing

An unexpired item cannot be called invalid merely because nobody supplies its bytes. After expiry, its durable descriptor suffices for code 0.

At the exact expiry boundary

timestamp == validUntil is still live. Descriptor-only disposal starts strictly afterward.

Every disposition is derived inside the proof using the correct sequential prestate; it is proof-internal, not an L2 or L1 record. A caller-provided flag is not validity evidence.

Aggregator service market

The auction buys proving service

  • One primary, up to three standbys, four waiting-offer cells and one stage.
  • Operators offer an ask per second and post the exact SLA bond. Sponsor-funded reserves pay eligible service premiums.
  • Quotes mature in both timestamp and L1 block-number clocks before selection.
  • A healthy primary is competitively replaceable by a strictly cheaper ask, subject to the tenure and handover rules.

Price discovery has distinct rules

Pending offers rank by ask, maturity and deterministic tie-breaks. Replacing the worst standby in a full lineup additionally uses the specified anti-churn threshold.

A lower ask can win service work; it does not win ownership of the L2 slot schedule.

Seat economics are optional for consensus. Missing seats, failed payments or a full duty ring must not block a valid canonical transition.

Slot Chain v3.0 · Economics, slashing and payments19 / 28 · Next →

The recovery tradeoff

A late proof can cure the predecessor’s duty

Progress remains available

A qualifying commit can satisfy an allocated duty through slash equality. After the strict slash threshold it can still advance canonical state, but cannot cure BREACHED.

Cure can close the predecessor and start a selected successor, including before failover. A cured former primary is not restored after removal.

The economic consequence

The successor may have a higher ask. The predecessor can end SATISFIED and ultimately receive its full bond as owner withdrawal credit.

A larger refundable bond creates no guaranteed loss on this path. Capital cost and competitive pressure require separate analysis.

This is an accepted design exposure. New price limits or penalties would be a separate mechanism change; they must not be added as a condition for canonical proof acceptance.

Bridging · existing contracts, both directions

Bridging uses the existing contracts

Bridge.sendMessage→L1 signal→header anchor→EIP-4788→revealCheckpoint→Bridge.processMessage

L1 → L2

A message becomes a signal in the L1 SignalService. Its anchor reaches L2 in a block header and is revealed as a permanent checkpoint; the existing L2 Bridge.processMessage verifies it with the unchanged HopProof path. No Slot Chain contract is involved.

L2 → L1

In the same transaction as every canonical commit (normal close, recovery or escape), Settlement calls the L1 SignalService.saveCheckpoint with the L2 block number, tip hash and state root. A revert rolls back the commit; the Inbox proxy is already the authorized syncer.

The escape lane is the liveness floor

An escape block needs no builder and no aggregator: a cartel cannot stop fresh L1 state from reaching L2, and every canonical commit publishes an L2 checkpoint on L1.

Censorship-resistant delivery

A user censored on L2 force-includes an ordinary processMessage (or revealCheckpoint then processMessage) through the kind-0 queue. No new mechanism.

Checkpoint availability

Reveal in time; a revealed checkpoint is permanent

8,191 s

Reveal window on L2

Ring index timestamp mod 8191. Relayers reveal a recorded anchor within that wall-clock window.

Every block

A fresh anchor

The newest block’s anchor is at most one settlement window plus inclusion time old, or one recovery round old.

Permanent

Once revealed

Kept by the L2 SignalService. On L1, the SignalService mapping keyed by L2 block number is the historical record.

Existing semantics apply

Exits and deliveries stay subject to the reused Bridge’s guardian pause, QuotaManager and relayer fee model. Slot Chain adds no pause-independent exit path: an explicit non-claim.

What was dropped

No canonical history ring, terminal accumulators, LP tickets or credit registries. The signal, checkpoint and trie-proof paths are the ones deployed today.

A revealable checkpoint exists whenever L2 produces blocks; an anchor nobody reveals in time leaves the ring and the next block carries a newer one.

L1 feasibility

A large block limit cannot rescue an oversized call

cap = min(configured L1 block gas limit, 16,777,216)
tokens = zero calldata bytes + 4 × nonzero calldata bytes
required = 21,000 + max(4 × tokens + execution budget, 10 × tokens)
ceil(1.30 × required) ≤ cap

Budget the complete transaction

Include decoding, cold reads, memory, call forwarding, full callee consumption (the saveCheckpoint call included), postreads and the final success or rejection work. Do not rely on refunds.

The calldata floor is a maximum

It is not a second execution charge. This formula covers a direct call with an empty access list and no authorization list; other envelopes add their exact intrinsic charges.

Synthetic model budgets are targets, not compiled gas certificates. Every maximum supported path needs fork-correct measurement and the complete 30% margin.

Governance and upgrades

DAO-owned proxies, ordinary upgrades

Slot Chain contracts and where they live
ContractWhere it lives
SettlementL1 · a new implementation installed in the existing Inbox proxy.
New L1 proxiesForcedQueue, BuilderRegistry, ScheduleOracle and AggregatorSeatMarket: DAO-owned UUPS proxies in the EssentialContract pattern; lifecycle facets and proof verifiers are plain immutable helpers.
Existing proxiesSignalService, Bridge and token vaults on both chains, unchanged; the treasury-only L2 Anchor and revealCheckpoint come from #22147. No new L2 contracts.

protocolVersion binds signatures

An immutable of each Settlement implementation, part of the EIP-712 signed header and every context ID. Promises and candidates for version N are invalid under N+1.

An upgrade is an ordinary DAO upgrade

A new implementation ships an explicit reinitializer that imports or cancels every live context, round, session and reward, with the specified refunds, after storage-layout review.

No Slot Chain timelock, version manager, router or CREATE3 factory. The DAO is already a safety root able to install code; Slot Chain adds no stronger writer and no weaker one. Permissionless means registering, bidding, proving, landing, recovering and force-enqueueing.

Upgrade from V1 · drain and activate

Upgrading from V1 in place

1. Install

The DAO upgrades the existing Inbox proxy to the Settlement implementation. V1 storage slots stay in place; the proxy starts in DRAINING.

2. Drain

Forced inclusions are rejected. propose runs only while the V1 forced queue drains; prove, checkpoints and bond withdrawals continue. No deadline.

3. Activate

When every proposal is finalized and the V1 queue is empty, anyone calls activateSlotChainV1(headerRlp) to import the last finalized header and enter NORMAL.

L2 needs no deployment

The first Slot Chain block has timestamp ≥ L2_FORK_TIMESTAMP and the next height; clients switch header rules at the fork timestamp. SignalService, treasury Anchor and base-fee sharing continue as under #22147.

Nothing is abandoned

Every V1 proposal is finalized and every V1 forced inclusion consumed first; V1 bonds stay withdrawable. Rollback before activation reinstalls V1 untouched; after activation it is an ordinary governance upgrade with an explicit migration.

Preconditions: V1 has shipped #22147; the L1 SignalService’s authorized syncer is the Inbox proxy. The drain itself is V1 behaviour and is not modeled.
