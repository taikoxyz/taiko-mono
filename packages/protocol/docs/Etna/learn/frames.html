Etna · Accepted C5 specification

Paying for a lost race

Several people may submit a useful action. Frame Transactions can change what the losers pay. They cannot make anyone include the winner.

Source: accepted C5, pinned at 66e3737. This lesson covers the frame construction and L1 dependencies. Landing, confirmations, roles and forced inclusion remain separately reviewed.

Assumed labels a selected rule or premise; proven conditionally an argument under those premises; open an unresolved dependency. Nothing here claims deployment or measured performance.

A failed action can still be a valid transaction

Validity and success answer different questions

Problem. Alice and Bob submit an action depending on the same state. Alice succeeds first; Bob's copy is stale. An ordinary transaction can revert inside its contract call while remaining valid for inclusion. Its effects roll back, but the payer still pays applicable costs.

In the EIP text C5 analyzes, a failing VERIFY frame makes the entire Frame Transaction invalid. A failing SENDER frame alone does not provide that protection.

Do not confuse these outcomes
OutcomeRace consequence
Included transaction; action revertsAction fails; payer pays applicable costs.
Whole transaction invalidIt cannot appear in a valid L1 payload. The construction unwinds payment approval and the nonce increment.

Proven conditionally: this follows from the analyzed frame-processing rules and the inherited exclusion of invalid transactions from valid payloads. It does not mean every public mempool accepts every consensus-valid frame layout. C5-R12 argument and limits.

Approve, attempt the action, then check its status

The direct-to-builder path

Actor P uses its own account nonce. Expiry verification comes first; P then authorizes execution and payment. The inbox action runs, followed by a verification that rejects the whole transaction if the action failed.

The approval step is essential. Expiry and success checks alone never authorize execution or assign its payer. C5 specifies this four-frame shape.

Exact frame indices, C5-R12
IndexOperation
0VERIFY expiry.
1VERIFY targeting P; approval flags 0x3 authorize execution and payment. Default account code reads signature index 0.
2SENDER calls the inbox action land. Its acceptance checks are a prerequisite, not supplied by this lesson.
3Stateless VERIFY requires the preceding SENDER's successful status.

Assumed: P has empty account code and no delegated code; a builder accepts post-payment verification. Open: the final EIP must preserve the layout and invalidation semantics. C5-R12; C5-R17.

Worked example: a gas floor is not a benchmark

With the register's 4,500 bytes of action calldata, this shape has a derived winner's execution-gas floor of 309,372 gas. Actual execution can cost more; blob fees are separate. If Bob's action reverts after Alice wins, Bob's trailing check invalidates his copy. The winner's floor is not charged to his invalid transaction.

Proven conditionally: arithmetic uses the analyzed frame/calldata schedules. Unmeasured: total execution cost and builder behavior. C5-R15.

A public-pool alternative uses a shared nonce

A narrower promise

The public-pool shape uses common gate G as transaction sender. Competitors use the same gate nonce. Its sequence is expiry verification, G's execution approval, payer payment approval, then the inbox call. It has no trailing status check. C5-R12's separate four-frame layout.

Proven conditionally: once a valid transaction consumes the nonce, competing copies using it are invalid. But that included copy may itself contain a reverted inbox call: the payer pays and the nonce is consumed although no protocol work completed. A gate nonce is not a progress counter. C5-R15; C5-R17.

Assumed: pool propagation needs clients implementing the relevant pool rules. Consensus validity alone does not establish propagation.

Worked example: a cheap nonce burn

At 4,500 bytes, a stale public-gate call has a derived floor of 310,752 gas, plus its blob fee. That is not the cheapest attack.

The gate checks a fixed calldata prefix. An attacker can pay for a malformed 68-byte call that passes the prefix checks but fails inbox decoding. Its gas floor is 27,104 gas; actual execution and the minimum tip still matter. No blob is needed under the stated pins unless the open blob-count guardrail is adopted.

This burns a gate nonce, not a protocol action. Honest users may use their own-nonce builder path or ordinary direct transactions. Open: final gate pins, tip value and complete third-party revert inventory. C5-R13; C5-R15; C5-R16.

Keep the ordinary path and identify the real dependencies

Frame support changes the cost of racing

Assumed specification rule: an ordinary direct path remains available without a governance switch. If frame support is absent, incompatible or refused by builders, relevant fallback paths remain. An included reverting ordinary transaction pays applicable costs; private builder protection is not transaction invalidity. C5-R18.

A persistent gate waits until the frame EIP is Final. A changed pinned format may need a new gate version, without removing the ordinary path. C5-R14.

Separate cost protection from safety and inclusion

Attack coverage

Protection depends on the transaction path
AttemptResult or limit
Charge a builder-path loser whose action revertsProven conditionally: trailing VERIFY invalidates it under analyzed semantics.

Check your understanding

Why is expiry → action → status check incomplete?

It never approves execution or payment. The accepted builder layout includes P's approval before the action. C5-R12.

The gate nonce advanced. Did the protocol progress?

Not necessarily: the included action could revert after approval. Read accepted inbox state, not its gate nonce. C5-R17.

No builder accepts trailing verification. What remains?

The ordinary direct path, with paid included reverts. A shared-gate path also needs its deployed gate and implemented pool rules. Neither guarantees inclusion under total L1 censorship. C5-R18.

Challenge this

  • Does the final EIP still let post-payment VERIFY invalidate everything and unwind approval?
  • Will a builder accept this layout, and will a public pool implement its alternative? Consensus validity answers neither.
  • Can a changed gate pin reject honest calldata or leave a cheaper nonce burn? Separate gate usability from inbox safety.
  • Which premise remains if all builders refuse the data? A cost argument cannot supply DA or inclusion.

Open: final pins, builder/client support, measured costs and full inbox composition. C5's open-items register owns closure. No readiness or benchmark claim is made here.
