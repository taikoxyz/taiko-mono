A block must not depend on somebody sending an anchor

Move the context into execution

Problem. If an anchor transaction carries the context needed to execute a block and publish remote state, somebody must supply it. Removing it requires another authenticated source.

Assumed rule, C1-R01/R02. Etna selects an authenticated L1 execution header as the origin. Its execution hash goes into the L2 header field named parentBeaconBlockRoot. Despite that name, this is not an L1 beacon root. C1-R01.

Before ordinary transactions, execution runs the standard EIP-4788 operation, then EIP-2935. The former records the supplied origin word; the latter records the parent L2 execution hash. Their writes affect the state root, but create no synthetic transaction, receipt or ordinary transaction gas charge. A zero-transaction block is permitted; no position is reserved for Anchor.

Assumed dependency. Accepted C2-R04 authenticates and binds origins across the range; D62 merges C7, with genesis, restart, fork choice and encoding obligations still open. Missing context produces UNKNOWN_CONTEXT, not acceptance. C1_PASS means only this component passed. C1-R01.

The old writer must close before ordinary execution

Read the current root to choose the phase

Problem. An old Anchor or router route could still write checkpoints. A voluntary “begin Etna” call could be withheld or ordered after that old writer.

Assumed rule, C1-R04/R07. A legacy writer first verifies the canonical oracle's runtime code hash, then makes the STATICCALL for the currently executing block's timestamp, then requires success and the exact 32-byte return. The caller cannot choose the guard's timestamp.

C4 owns the activation sequence and audit. A partial upgrade is a failed premise. C1-R09 prerequisites.

Turn an authenticated hash into a bridge checkpoint

Reveal the header; pin it when retention matters

Problem. A hash alone does not give SignalService the origin's block number and state root. Those values must come from the same authenticated header bytes.

Assumed rule, C1-R08. Anyone may submit revealCheckpoint(timestamp, headerRlp) as an ordinary paid transaction. The ordered algorithm matters:

  1. Check L2 mode and the current-phase guard.
  2. Require nonempty input and check the raw-header size cap, then hash the exact input bytes.
  3. Parse the complete canonical RLP header and construct (number, hash, stateRoot).
  4. Inspect the existing record without writing: an exact duplicate returns immediately; a conflicting or partial record errors before any remaining timestamp check.
  5. Authenticate a fresh record only through pin membership or the supplied timestamp entry.
  6. Apply the fresh write and return the tuple.

A conflicting existing tuple therefore gives EtnaCheckpointConflict even if the supplied historical timestamp has expired; it does not reach EtnaOracleUnavailable. This is V07’s error precedence, not a new authentication bypass.

A live timestamp entry can authenticate directly. Alternatively, pinCurrentOrigin() remembers membership of the processing block's current origin hash. It accepts no caller-selected origin, stores no header and writes no checkpoint. A later reveal can use that membership. C1-R05.

Assumed rule, C1-R06. Fresh records enter the existing checkpoint map. An identical record is a no-write, no-event success; a conflicting or partial record errors. Authenticated heights may arrive out of order. There is no per-record administrator repair. Record rules.

Proven conditionally. Substituting a different number or state root requires breaking the header hash binding or the premises: authenticated origins, common execution semantics, sound inherited history and cryptographic assumptions. Checkpoint-integrity argument.

The existing SignalService address and ordinary signal-proof path remain. A pin is neither a remote storage proof nor reimbursement. C1-R10 bridge boundary.

Accepted C1-R11: reveal the header inside the signal claim

Authenticate the checkpoint and prove the signal together

Problem. A normal signal claim should not need a separate reveal transaction solely to supply its checkpoint. The previous module explains what authenticates a header; the claim can carry those same bytes alongside its existing storage proof.

Assumed, accepted under D83. D80 retains the execution block hash in the origin field. C1-R11 adds a versioned form of _proof: the timestamp or pin sentinel, the complete header, and one existing HopProof. The public proveSignalReceived and verifySignalReceived signatures and SignalService address remain the same. The historical C1 work order requested this format and its vectors; D83 records technical acceptance.

  1. Assumed rule: authenticate the inline header using C1-R08's current-phase guard, canonical parser, duplicate/conflict precedence and fresh-record timestamp or pin checks. An existing exact checkpoint avoids an expired historical lookup; it does not bypass the current-phase or parser checks.
  2. Assumed rule: require the hop's block number and root to equal the number and state root decoded from that same header. Then verify the remote SignalService account and signal storage proof using the existing remote-address binding. A pin alone is never a signal proof.
  3. Assumed rule: the view call verifies without writing. A successful state-changing prove call saves a fresh checkpoint if needed and records receipt of the signal; any later revert in the enclosing transaction rolls those effects back. It returns 0 cache operations for reimbursement: checkpoint and pin writes earn no Bridge reimbursement. Existing proof, received-cache and stored-checkpoint paths remain available.

Proven arithmetic; example, not a measurement. In C1's byte derivation, a canonical wrapper adds 128 + ceil32(H) bytes over the old proof, where H is the complete header's byte length and ceil32 rounds up to a multiple of 32. For an illustrative H = 600, that is 128 + 608 = 736 extra bytes. At the specified header cap of 1,536, it is 128 + 1,536 = 1,664. This counts encoding bytes, not execution gas; gas remains open and unmeasured.

Assumed recovery boundary. A pin followed by an inline claim is an option only when the entire forced request fits. C3's 4,096-byte CALLDATA cap must accommodate the application call, the proof and the header wrapper, not just the header. The byte calculation does not guarantee that arbitrary claims fit. Standalone forced reveal remains a recovery building block; it does not make an oversized downstream claim executable. See C1's recovery conditions.

Proven conditionally: the same-header comparison rejects pairing a valid origin hash with another hop number or root; remote account/storage verification rejects a header offered without proof of the claimed signal. This rests on the existing authentication and cryptographic premises. Open limits: inline bytes do not solve unavailable headers or proof nodes, reorgs, a pre-signal origin, insufficient funding, or the request-size and gas limits.

Check this format

Can the view verifier publish the newly authenticated checkpoint?

No. C1-R11 keeps verifySignalReceived read-only. Only the successful state-changing path commits the checkpoint and received-signal cache; a transaction revert undoes both.

Does a valid pin let the caller choose another root in HopProof?

No. The pin authenticates the full header hash. The hop's number and root must match that same parsed header, and the remote signal proof must still verify.

Does a 600-byte header prove that a forced signal claim fits?

No. The derived 736-byte overhead must be added to the rest of the encoded request. The complete request must fit the 4,096-byte CALLDATA cap, and its execution gas is unmeasured.

Challenge this format

  • Can malformed wrapper or header bytes reach a different parser or root than the storage proof? Challenge canonical decoding and the same-header comparison.
  • Can a view call write, or a failed claim leave a checkpoint or reimbursement behind? Challenge mutability, transaction rollback and Bridge integration.
  • Can the required proof exceed the request budget or disappear after pinning? Challenge header/proof availability, funding and the conditional recovery path.

Accepted scope: D83 accepts the format and its logical vectors. D85 accepts C8-R12’s interface/error indexing: the selectors stay unchanged, the tagged format uses P-INLINE-TAG, and malformed envelopes use EtnaSignalProofFormat(). Accepted D99 · A fork can change more than the state-root position

A fork can change more than the state-root position

Problem: A reveal parser can reject a newly shaped header even when the state-root field did not move.

Assumed, owner rule accepted by D99: C5’s accepted profile projection names the four C1-R08 type-checked positions: 0, 3, 8 and 11. Both revealCheckpoint and tagged inline claims use that profile. Inserting or moving fields at or before item 11 needs a coordinated L2 SignalService and guest profile upgrade; a moved item 11 also affects the Inbox timestamp decoder.

Worked logical example: A hypothetical fork inserts one field before item 11. Even if item 3 still contains the same state root, the old timestamp-position check is no longer the declared profile. This is a counterexample to treating a state-root position alone as full compatibility, not a prediction of an Ethereum fork.

Defenses and limits: Explicit positions expose parser drift. They do not prove support for an unknown future fork, supply availability, or establish finality. The separate C8 L1 timestamp decoder has its own narrower profile.

Do inline claims avoid the header profile?

No. They use the same C1 type checks.

Does an unchanged state-root index prove compatibility?

No. All four checked positions and canonical RLP constraints matter.

Challenge this

Can a new header shape satisfy one parser while another reads a different number or timestamp? Identify every affected consumer before claiming compatibility.

C5-R07 · Separate L1 decoders

Check your understanding

Can an otherwise empty block close the old Anchor writer?

Yes, conditional on correct execution and migration. The system operation writes the current nonzero origin before ordinary transactions; no pin or reveal is needed. Writer-closure argument.

Does OriginPinned prove its header is available and final?

No. A pin stores hash membership, no header. It can disappear with a reorg. Availability and confirmation guarantees are separate. Pin-label limit.

Do successful forced pin and reveal calls necessarily unblock a particular signal?

No. Under current C1/C3 recovery premises, saving the first request after the persistent signal makes the request-block system pin cover an origin containing that signal. Successful checkpoint recovery still does not establish that the entire later application claim fits the byte and execution limits or has available proof nodes. Recovery premise.

Challenge this

  • Can the importer and proof guest authenticate different origins or execute different system writes? Challenge A-ORIGIN and A-EXEC.
  • Can an inherited or delegated writer bypass the current-root guard? Challenge A-HISTORY.
  • Can forced items advance without successful execution, or only select pre-signal origins? Challenge A-INCLUSION and A-ORIGIN-PROGRESS.
  • Can bytes disappear, funding fail, or permanent state growth exceed its budget? Challenge A-ARCHIVE, A-FUNDING and open resource assumptions.
