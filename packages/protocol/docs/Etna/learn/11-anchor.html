Lesson 11: blocks without an anchor, bridge, migration

Prerequisite: lesson 6. Design page: Anchor, bridge, migration; limitations L17, L21, L22, L-OP.

Goal

State what an Etna L2 header carries and who checks it, how an L1 checkpoint reaches the L2 SignalService, why every shared contract keeps its address and what its upgrade removes, and what a DAO must do, twice on L1, to activate Etna.

The idea

Today every L2 block opens with a golden-touch anchor transaction that forwards an L1 checkpoint to the L2 SignalService; Etna blocks contain no such transaction (anchor-free blocks, issue #22147). What L2 needs from L1 rides in the header: parentBeaconBlockRoot holds the hash of the anchored L1 block, the 7-byte extraData the fee-sharing byte, term, view and kind. The standard EIP-4788 system call stores that hash in L2's beacon-roots contract, keyed by L2 timestamp, so on L2 that contract holds L1 execution block hashes, not beacon roots, and anyone turns a recorded hash into a checkpoint by revealing the matching L1 header to the L2 SignalService. Nothing that needs fresh L1 state or committee keys is verified on L2. Every proxy keeps its address: the Inbox, the Anchor and the L2 SignalService get new behaviour in place, and the shared contracts get compatible implementations that only remove their pause and owner-only powers (after the #22188 review, 2026-10-01).

The rules

  • Header (V5, H1 to H3). parentBeaconBlockRoot is non-zero and equals the hash of the node's own L1 block at the signed anchor number; extraData is exactly 7 bytes, pctg ‖ termId ‖ view ‖ kind, byte 0 equal to BASEFEE_SHARING_PCTG = 100 and (termId, view) matching the signed header; kind is NORMAL (0), FORCED (1, iff view 254), GENESIS_CHILD (2, the first Etna block) or FI (3, a forced-inclusion block). Nodes check these under V6 and the guest asserts them; no L2 contract executes any of these rules.
  • Freshness. The anchored block is at least 48 s and at most 30 min older than the block; the anchor number is monotone, not must-advance.
  • Recording, reveal and pin. L2's EIP-4788 contract keeps each block's anchor hash at that block's L2 timestamp T until the block at T + 8,191 overwrites it: readable for 8,191 s (about 2.3 h) whatever the L1 slot time. revealCheckpoint(l2Timestamp, headerRlp) on the L2 SignalService reads that record (requiring the canonical EIP-4788 runtime, EXPECTED_4788_CODEHASH, and exactly 32 return bytes), requires it non-zero and equal to keccak(headerRlp), strictly decodes the header (at most 1,536 bytes; item 3 the state root, item 8 the number) and stores the checkpoint; an identical repeat is a no-op, a conflicting one reverts. pinCurrentOrigin() pins the processing block's anchor hash, after which revealCheckpoint(0, headerRlp) reveals it with no deadline (adopted from the Astra candidate, PR #22188); queued through forced inclusion, it pins whatever anchor its block carries, so a censoring sequencer delays a durable checkpoint but never prevents one. The sequencer reveals each new anchor by client policy (about 100k gas, assumed); relayers reveal before claiming; a missed reveal is never a fault, since a newer L1 state root proves every signal an older one did.
  • Binding. Guest: every distinct anchored header's RLP hashes to the parentBeaconBlockRoot of each block that anchors it, its number is that block's signed anchor number, and the headers chain by parent hash to the tip (at most 4,096 per landing). Inbox: the tip equals blockhash(n) within 256 blocks or the EIP-2935 record within 8,191; older ranges are refused and replaced. Hence every hash a landed range recorded, and every checkpoint revealed from it, belongs to an L1 block canonical at landing.
  • The L1 checkpoint call. The Inbox makes today's saveCheckpoint call once per landing accepted with two ZK leaves. A one-leaf landing in single-proof mode is provisional and writes none until a second-leaf proof of the same journal or DEGRADED_FINALITY = 24 h without a conflict; a two-leaf landing behind an unfinalized provisional record writes none of its own and is subsumed by that record's finalization checkpoint (after the #22188 review, 2026-10-01; lesson 7).
  • Fork guard. The L2 upgrade bridged before the fork installs a current-root guard (adopted from the Astra candidate, PR #22188): the legacy anchorV4 and the L2 SignalService's saveCheckpoint run only when L2's EIP-4788 contract returns a zero root for the current block, true of every Shasta header and false of every Etna header, so they are closed from the first transaction of the first Etna block with no fork time stored in any contract. After T0 the execution clients drop every golden-touch carve-out, so a golden-touch transaction is an ordinary, fee-paying one that reaches nothing privileged.
  • Shared contracts (R1, R2). Addresses of both SignalServices, the Bridge and the Vaults are unchanged. The L1 SignalService, the Bridge, the Vaults and the quota manager are upgraded in place before T0, independently of the fork, to compatible implementations that remove pause/unpause, remove or freeze every owner-only setter (changeBridgedToken, the quota setters) and keep every storage layout, message format and client-used selector (after the #22188 review, 2026-10-01; A5 revised). After them no address other than the DAO can stop bridging, remap a token or mint a bridged token; the DAO keeps two DAO-only entry points as slow as an upgrade, DefaultResolver.registerAddress and the owner branch of BridgedERC20 mint and burn. The price is the emergency brake: a live exploit is stopped only by a DAO upgrade, the frozen Bridge quota bounding the loss rate (limitation L-OP).
  • Storage. Inbox slots 251-257 keep their types and the additions lie inside the gap; the Shasta proposal-hash mapping becomes the term-record ring after the drain. The Anchor stays at its address as the fee treasury: slots 0 to 257 keep their types, nothing is appended. The L2 SignalService gains only the namespaced pin map and keeps VERSION 1.

The cut-over

  1. Before the fork, in this order (anchor-free blocks, issue #22147): the taiko-geth sealer fix (taiko-geth#601: L2's EIP-4788 system call runs when a block is built as on import) on every geth node, alethia-reth being consistent already; EIP-2935 on L2 (parity-safe; it serves the last 8,191 L2 block hashes); EIP-4788 on L2 only after that (deployed before the sealer fix it would split geth nodes from the chain), recording zero roots harmlessly until the fork; only then the guarded Anchor and L2 SignalService implementations, bridged through the DelegateController, whose guard reverts on a missing oracle and which behave as the Shasta implementations until the fork.
  2. Two upgrade-class L1 transactions (round 4, R4-C5). One at time U deploys the libraries, the verifier and the implementation and calls initEtna(lastFinalizedBlockNumber) without a term grid; a second, armEtna(T0) with T0 ≥ now + MIGRATION_LEAD (7 days), sets the grid once the DAO has read the domain count on chain. The launch condition (8 owners, 72 seats) is a heuristic over a Sybil-able count that no rule enforces; if it fails, launch may begin in no-committee mode. The arming proposal also bridges the guarded L2 upgrades, final after L2's EIP-4788 deployment and before T0; the shared contracts' compatible upgrades are separate transactions before T0; both execution clients and the guests ship the fork time.
  3. Registration opens immediately (effects future-dated). Shasta proposing stops one hour before T0 (FREEZE); Shasta proving continues without its whitelist until every proposal is proven, or until a day after T0 (DRAIN_DEADLINE), when anyone may call abandonShastaTail(unproven) with the full structs of the unproven proposals in id order: each is checked against the ring buffer that holds every unfinalized proposal, the forced-inclusion head moves back by the number of forced sources they contain, and those entries are requeued with fee zero, due at the fork (after the #22188 review, 2026-10-01). The fee Shasta paid its proposer is not recovered, at most 10 entries' fees per abandoned proposal, and the proposals' ordinary content is lost, announced in advance (limitation L17); a proof-backed drain was rejected because a whitelisted prover must not be able to hold the migration (R1).
  4. The drain event fixes the genesis parent (the last Shasta-finalized block) and the first Etna term, whose first block carries kind GENESIS_CHILD; no fallback is armed at that term. It also starts the forced-inclusion stall clock: fiClearTip is set to the drain block's timestamp, treating the queue as clear at the fork (round 6, R6H-1), so entries pending across the cut-over, the requeued ones included, are voided only after four hours of anchored time in which no block catches up with the due prefix. A legacy Shasta entry has no requester and no bond, so a stall that voids it refunds nothing (lesson 10).
  5. Rollback: one upgrade per chain back to Shasta implementations with a verified head. On L2 the current-root guard needs no second gate: the legacy writers reopen exactly when the clients record zero roots again, at the rollback time, so the golden-touch key reaches nothing privileged in between; the reinitializer zeroes the stored ring hash, so the first anchorV4 re-seeds the ring. Landed Etna blocks are final, unlanded ones void, revealed checkpoints stay valid, and the shared contracts' compatible upgrades stay in place.

Self-check

Why is a fake anchor hash harmless to the bridge in the end, and where can it do harm before that?

A block whose parentBeaconBlockRoot is not a canonical L1 block hash can be attested only if Q = 22 attesters skipped V5, and its range can never land, because no witnessed L1 header that chains to the tip hashes to it; it is replaced and its records die with it. Until then a checkpoint can be revealed from the fake hash (its forger knows a preimage) only on that unlanded chain, for at most about an hour; bridge withdrawals should wait for "landed", and the frozen Bridge quota bounds the residual.

Nobody reveals a checkpoint for three hours. What breaks?

Nothing is invalid and nobody is penalized: a missed reveal is never a fault. A record older than 8,191 s may have been overwritten and its reveal by timestamp then fails, but the head block's record always holds the newest anchor and a newer L1 state root proves every signal an older one did, so the next reveal, by the sequencer, a relayer or anyone, restores L1→L2 bridging at once; an origin that was pinned stays revealable with no deadline.

Why must anchorV4 revert from the first Etna block although no Etna block uses it?

Its sender key, the golden touch, is public. In the first anchor-free block the ring value stored by the last Shasta block still matches, so a forged anchorV4 would pass once and save a fake checkpoint through the old syncer path. The current-root guard makes it revert in every block whose header records a non-zero root, that is every Etna block, with no stored fork time to disagree with the clients.

What happens to a forced-inclusion request that a Shasta proposal consumed but that was never proven?

Shasta paid the proposer and advanced the queue head at proposal time but never deleted the entry. After DRAIN_DEADLINE anyone abandons the tail; the ring buffer fixes how many forced sources it held, the head moves back by that number, and the entry is requeued with fee zero, due at the fork, so it is served in the first Etna blocks without a second fee; only if its blob has left retention is it voided by the stall rule, refunding nothing (no requester, no bond). No forced request accepted by Shasta is discarded by the migration except by the stall rule.

Why not deploy a new inbox and point the SignalService at it?

The L1 syncer is an implementation immutable of the contract guarding all bridged value; a new inbox address means a new L1 SignalService implementation, orphans the bond ledger and the forced-inclusion queue, and makes rollback a second SignalService upgrade. Every proxy is upgraded in place instead; the shared contracts' compatible upgrades change no address, storage or client-used selector and only remove the pause and owner powers (limitation L-OP).

What is the expected pause at cut-over?

About one hour (the proposing freeze) if the outgoing provers prove promptly; at most 25 hours otherwise, after which the tail is abandoned. During it nothing can be slashed.

Challenge this

The migration reuses the Shasta proposal-hash mapping as a ring of term records. Find a term id whose slot could collide with an unproven Shasta proposal during the drain, and check whether the "land reverts until drained" rule closes it. Then attack abandonShastaTail: try to requeue an entry twice, and name the check that stops you. Finally try to reveal a checkpoint whose state root differs from the true one for a hash that a landed range recorded.
