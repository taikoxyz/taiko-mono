Keep a checkpoint after its oracle expires

Prerequisites: authenticated origins, ordinary execution and the forced FIFO queue.

The round 08 judge records a historical stopping criterion for the rounds 07–08 anchor-removal snapshot; it does not establish that every current requirement passes. The problem: a temporary hash is not a permanent checkpoint

Proven distinction: standard EIP-4788 stores one word from parentBeaconBlockRoot, keyed by the L2 timestamp. Under the proposed header rule that word is an authenticated L1 execution hash. It does not decode an L1 number or state root, emit CheckpointSaved, or update SignalService. The separate standard EIP-2935 call retains recent L2 parent hashes; neither oracle recreates Anchor's permanent L2 hash history.

Proven oracle limit: 4788 has 8,191 slots indexed by timestamp % 8191, with an exact timestamp check on reads. A later timestamp with the same remainder overwrites the entry. The safe no-collision interval is less than 8,191 seconds of L2 timestamp advancement, not 8,191 arbitrary blocks or a guaranteed 4.5 hours. A permanent bridge checkpoint therefore needs an ordinary contract call.

The mechanism: record, optionally pin, then reveal

Assumed interface: keep the existing L2 SignalService and add permissionless pinCurrentOrigin() and revealCheckpoint(uint64 l2Timestamp, bytes l1HeaderRlp). The canonical oracle is queried with the raw 32-byte timestamp and no function selector; failed calls, malformed return lengths and zero hashes fail. These methods are L2-only and require the processing block's current oracle word to be nonzero.

  1. Assumed recording rule: the unmodified 4788 pre-execution call records the authenticated hash before ordinary transactions. No custom hook calls SignalService, and no anchor, fee exemption, privileged sender or transaction-zero reservation is added.
  2. Assumed pin rule: pinCurrentOrigin() reads at block.timestamp and permanently records that hash in a namespaced map. Its four-byte calldata names no timestamp or old target. The caller pays an ordinary ETH transaction fee; pinning an already pinned hash returns the same hash without another storage entry or event. Neither pin nor reveal has a separate persistence tariff in this candidate.
  3. Assumed reveal rule: a positive timestamp authenticates the full header hash through 4788; timestamp zero uses the permanent pin map instead. Strictly decode at most 1,536 bytes with 12–32 scalar fields, require a nonzero 32-byte state root and a canonical block number fitting uint48 before casting. Save the unchanged number/hash/stateRoot checkpoint and emit CheckpointSaved. An existing identical checkpoint succeeds even after oracle expiry; a conflicting one fails.

Proven conditional result: Keccak equality binds the number and state root to the authenticated L1 hash under A-CRYPTO and correct parsing. The existing checkpoint/cache namespace, Bridge address, HopProof and trie verification remain intact. Any funded caller may enter or stop; no exclusive relayer, new reward, bond or slashing duty is required. A sequencer may voluntarily include a reveal, but omitting one does not invalidate a block.

Worked example: a queue longer than the oracle window

Assumed example: timestamp 10,000 records hash H in slot 1,809. If a block later uses timestamp 18,191, it writes the same slot, and querying 10,000 fails its timestamp check. A forced reveal naming 10,000 can therefore become stale while queued; executing that stale call reverts and still consumes its valid request's FIFO position.

Proven distinction: a pinCurrentOrigin() submitted at time 11,000 but processed at L2 timestamp 20,000 reads that processing block's hash H2. Queue delay cannot stale an argument it never supplied. Once H2 is pinned, a later revealCheckpoint(0, headerOfH2) can authenticate it after any ring overwrite, assuming the full header remains available. The pin selects H2, not the submitter's earlier H.

Proven size bound under the stated envelope: a 1,536-byte header yields at most 1,845 raw bytes for the specified type-2 reveal transaction, below the 2,048-byte FIFO cap. This requires an empty access list, zero value, gas limit at most 1,000,000, a nonce fitting uint64, and chain ID and fee fields fitting uint256. Open: this byte calculation is not a gas benchmark; worst-case parsing, pinning and checkpoint writes must fit the execution/proving limits.

Attacks and limits

Proven conditional defenses: a fake header fails the hash binding; a conflicting number/hash/root fails the checkpoint check. Duplicate or front-run reveals cannot substitute a different checkpoint. A crowded queue cannot expire a forced pin's chosen timestamp because the call chooses at execution. An old timestamp reveal has no such protection. Standard EIP-2935's recent L2 history does not authenticate arbitrary old L1 headers.

Assumed: callers can fund ordinary gas and enqueue fees, keep their transaction nonce and balance usable, recover the exact hash-bound L1 header under A-L1-WITNESS, and rely on continuing proved FIFO progress. Pins and checkpoints roll back with reorged state; permanence is within the accepted history. No designated operator must stay online. Each distinct pinned hash grows permanent storage; bounded calls do not imply bounded lifetime state. Callers pay ordinary gas, but a caller controlling the block's coinbase recovers its own L2 fees under the 100% coinbase rule, so that payment alone is not an irreversible storage price. This persistence path does not guarantee a short queue delay or availability of forgotten header preimages.

Proven accepted-history bound: every block in a segment uses one exact origin. After N accepted post-activation segments, the new origin API therefore admits at most N distinct pin values and at most 2N checkpoint value words. A duplicate creates neither kind again. These are additional raw storage values after a fixed migration baseline; they exclude mapping keys, trie overhead, events, archive history and unrelated SignalService or user-contract state. N itself has no lifetime cap.

Proven worked arithmetic: one distinct origin per 60-second segment for 365 days gives N=525,600. At 32 bytes per value word, pins alone contribute at most 16,819,200 raw bytes; pins plus checkpoint values at most 50,457,600. These are illustrative upper bounds at that schedule, not measured database sizes, a protocol rate cap or proof that the workload is sustainable.

Open storage decision: measure unique-origin growth, fresh-slot costs and synchronization/proving overhead using the state-growth assessment. A pin-only fee would miss direct positive-timestamp reveals, which can create a checkpoint without any pin. A separate nonrecoupable tariff on both operations would require calibrated prices, payment and duplicate rules, force-path funding and fresh review; no such tariff is adopted. Pruning permanent pins would remove the nonexpiring recovery promise and also requires a separately reviewed mechanism.

Open limit: acquiring a checkpoint does not make every bridge proof fit the queue. The existing proof-byte allowance can be 200,000 bytes, far above the 2,048-byte forced transaction cap; separate proof/gas feasibility and ordinary inclusion assumptions still apply. A current origin may support an enduring message signal, but no rule says a newer state root proves every historical storage value. Missing witnesses or a nonpersistent application fact require their own recovery argument.

Check your understanding

A pin waits 20,000 seconds. Which origin does it preserve?

Proven under the proposed rule: its processing block's authenticated origin. It does not promise to recover the origin visible when submitted.

Would charging only pinCurrentOrigin price every new origin checkpoint?

Proven: no. While a positive-timestamp oracle entry remains available, revealCheckpoint can authenticate the header and create its two-word checkpoint directly. Ordinary gas can also return to a caller controlling coinbase. Neither observation authorizes removing the durable path.

Does fitting the reveal in 2,048 bytes guarantee a bridge claim will be forced?

Proven: no. The claim's proof size, gas, funding and inclusion requirements are separate from pinning and reveal.

Challenge this

Assumed: system-call parity, strict parsing, header recovery and funded FIFO progress hold. Try a modulo collision, a malformed raw oracle response, an out-of-range L1 number or a queue delay longer than 8,191 seconds. Identify whether the direct reveal, permanent pin or checkpoint lookup is used. Then remove the only archived header: which assumption fails, and can a hash alone recover it? Finally, distinguish a bound proportional to accepted segments from a fixed lifetime storage cap; the proposed API supplies only the former.
