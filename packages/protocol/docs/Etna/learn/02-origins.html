Etna learning course · lesson 2

Use facts that already exist

Prerequisite: a locally valid candidate is still provisional.

Course mapPrevious: confirmationsNext: exact public bytes
Classification. The mechanism is proposed. Proven identifies its definitions or conditional consequences; Assumed identifies required premises; Open identifies outstanding evidence. No production behavior is asserted.

The problem: the future cannot be an input

Proven/source: today's derivation obtains a proposal timestamp from its L1 landing block and an origin from that block's parent. Those facts are not fixed while a future segment is being built. Copying that dependency into Etna would obstruct proving an exact execution before landing. The baseline summary, section 2 explains the source behavior.

Proven design choice: Etna instead selects an earlier L1 header before building the segment. Call its authenticated number, hash, state root and timestamp the origin. All blocks in that segment use this same tuple.

The mechanism: authenticate, then anchor

Proven rule: a node checks the chosen header in its own authenticated L1 history. Before canonical acceptance, anyone can pin that exact header in HeaderStore. The helper hashes its complete canonical RLP bytes and compares the result with a nonzero BLOCKHASH(number) for an earlier block. It retains the tuple immutably. A supplied RPC state root is insufficient.

Proven rule: transaction zero in every ordinary Etna block is the public system call anchorEtna(checkpoint, originHash, revision). Its checkpoint must exactly equal the origin. The node checks the full transaction and executes it; a successful Solidity call alone does not authenticate L1 history. The existing Anchor passes authenticated checkpoints to the existing SignalService. The first Etna block has a separately specified activation call, taught with migration later.

Proven under A-L1: the pin authenticates an ancestor in that L1 history. A reorg replacing the ancestor also removes the descendant pin and dependent acceptance. Nodes must update their view. No future validator schedule or fixed slot duration supplies these facts.

Worked example: a bounded origin

Assumed example: origin block 200 has timestamp 1000 and authenticated root R. The L2 parent timestamp is 1000. Three candidates use timestamps 1001, 1002 and 1003, each anchoring block 200 and R. The node can check them before a pin transaction lands.

Proven arithmetic: the origin allows L2 timestamps at most 1060; a candidate timestamp 1061 fails even if its transactions execute. Live nodes also allow at most two seconds of future local-clock skew. Origin age at landing is at most 900 seconds, so this origin cannot support acceptance after time 1900. Its number and timestamp cannot regress relative to the parent segment's origin; reuse is allowed.

Defenses and limits

Proven: exact origin equality blocks a publisher from substituting an unrelated L1 state root or changing anchor inputs when landing. It does not make the provisional branch canonical, make an old header recoverable forever, or prevent Ethereum reorgs.

Assumed: A-L1, A-CRYPTO and A-IMPLEMENTATION establish authentication; a correct L1 view and available parent state support local checks. Open: launch-fork header conformance and timely pinning must be validated. Faster L1 blocks shorten BLOCKHASH's wall-clock lookup opportunity; the design does not pretend it lasts a fixed number of seconds.

Check your understanding

Must a node wait for the pin transaction before checking a soft block?

Proven: no. It authenticates the origin in its own L1 view. Canonical acceptance later requires the identical pinned tuple.

An anchor call succeeds with the wrong state root. Is the block valid?

Proven: no. Local validation and the proving relation require exact authenticated origin equality.

Challenge this

Assumed: your node authenticates L1 ancestry and notices reorgs. Try replacing R through a dishonest RPC, or letting the header age out before anyone pins it. Does the client stop at UNKNOWN or rebuild, rather than guess?
