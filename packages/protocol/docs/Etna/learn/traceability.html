The problem: what does a vector name establish?

Ask what evidence the row contains

Assumed, D71's convention: a mapping names a rule's owner, inputs, failure behavior and vector. The owning section is the default owner; a rule placing content in another section explicitly names that owning rule and section. The default does not override a named other owner, whose rule governs any disagreement. A named vector may still be a planned scenario without bytes. Counting convention; owner precedence.

Proven, historical enumeration: D71's snapshot counts 78 of 143 rule rows with all four elements, 46 failure gaps and 40 vector gaps. The two gap categories overlap. These are counts derived from the table, not measured test coverage, performance or a readiness verdict. Definition and enumeration.

The mechanism: separate the case, the fixture and the run

Keep the evidence attached to its claim

Assumed, teaching convention drawn from the source's fixture scope: a logical case specifies a pre-state, call and expected outcome. A full byte fixture supplies concrete inputs, required state/profile and expected bytes and state changes. An executed result records a particular implementation's run against that fixture and the comparison.

Open specification work: full fixture bytes can be specified before production code exists; C1 separates those artifacts from future implementation runs. C8-E01's logical row leaves error selectors and fixture bytes incomplete. Missing artifacts.

Worked example: try to pin an origin on L1

Trace C8-E01 back to C1-R05

PartConcrete logical case
Pre-stateThe SignalService implementation is in deployment mode L1_INBOX.
CallAny caller makes an ordinary, zero-value pinCurrentOrigin() call.
Expected outcomeEtnaWrongMode(); no pin mutation. isOriginPinned remains false for every hash.

Proven conditionally, derived boolean projection: choose any hash h. The view isOriginPinned(h) reports false before and after the rejected call: 0 → 0. This describes the view result, not supplied storage bytes or a measurement.

Proven conditionally: C1-R05 first requires L2_ORIGIN. The stated L1 mode fails that requirement, so this case reaches the named rejection before the pin write. This ordinary call does not test a request block's system pin. Open: concrete fixture state, exact calldata/revert bytes and a recorded execution of those inputs. The expected outcome alone is no claim about deployed behavior or measured gas.

Defenses and limits: challenge the evidence jump

Check what the artifact can support

Proven conditionally: following the owner rule catches a mapping that expects the wrong rejection. A complete byte fixture allows independent implementations to compare against the same expected result. A recorded run can establish agreement for its stated implementation, inputs and environment.

Open limits: a correct mapping does not generate missing bytes, a passing case does not cover every branch, and none of these artifacts alone supplies user acceptance of residual risks or the other D44 requirements. D71 explicitly keeps planned coverage separate from readiness. Acceptance boundary.

Check your understanding

C8-E01 names the right error. Has an implementation passed the case?

Proven conditionally: no such result follows. The row describes an expected outcome; a run needs concrete inputs, an identified implementation and observed outputs.

Does L1 mode with a valid caller let the ordinary pin write succeed?

Proven conditionally: no. C1-R05's mode check rejects with EtnaWrongMode(), regardless of the caller; no pin mutation occurs.

Can the 78 complete rows close D44, or must fixture authors wait for production code?

Assumed, D71's scope: neither follows. “Complete” counts named elements in that snapshot. Open: missing full fixtures can be specified now, with implementation execution and all other readiness checks tracked separately.
