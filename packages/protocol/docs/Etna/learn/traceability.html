The problem: what does a vector name establish?

Ask what evidence the row contains

Assumed, D71's convention: a mapping names a rule's owner, inputs, failure behavior and vector. The owning section is the default owner; a rule placing content in another section explicitly names that owning rule and section. The default does not override a named other owner, whose rule governs any disagreement. A named vector may still be a planned scenario without bytes. Counting convention; owner convention.

Proven, snapshot enumeration: D72’s accepted table counts 132 of 143 rule rows with all four elements, 8 failure gaps and 5 vector gaps across 11 rules. The gap categories overlap: 8 + 5 − 11 = 2 rules have both gaps. These are table counts, not measured test coverage, performance or readiness. Definition and enumeration. D71’s earlier counts remain historical; its owner convention still governs.

The mechanism: separate the case, the fixture and the run

Keep the evidence attached to its claim

Assumed, D72’s three fixture classes: a logical case supplies pre-state, input and expected outcome now. Specification fixtures supply deterministic encodings, state and expected outputs; their owners owe those bytes now, even before production code exists. Only implementation- or proof-dependent artifacts and recorded execution wait for the implementation, prover or harness they need. An undefined S2 or C8 encoding is an open specification dependency, not permission to postpone every fixture until code exists.

Open specification work: C8-E01’s logical row does not supply the complete fixture state, calldata and expected revert bytes. Its author can specify those deterministic artifacts now; execution against a particular implementation remains separate. Owning class distinction. An “after code” marker applies only to implementation- or proof-dependent artifacts, not the whole vector.

Defenses and limits: challenge the evidence jump

Check what the artifact can support

Proven conditionally: following the owner rule catches a mapping that expects the wrong rejection. A complete byte fixture allows independent implementations to compare against the same expected result. A recorded run can establish agreement for its stated implementation, inputs and environment.

Open limits: a correct mapping does not generate missing bytes, a passing case does not cover every branch, and none of these artifacts alone supplies user acceptance of residual risks or the other D44 requirements. D72 explicitly keeps mapped logical coverage separate from completed fixtures and readiness. Acceptance boundary.
