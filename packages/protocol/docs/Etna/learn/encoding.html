Etna · Accepted C8 encoding rules

Agree on the bytes

A node and an L1 contract must identify the same message, even when they receive it in different formats.

Assumed, acceptance record: this lesson follows merged C8, accepted under D49. It teaches one building block: a canonical message identity. Read the landing lesson first. Committee proofs, confirmation rules and complete storage/migration definitions remain outside this lesson and partly open.

Assumed marks an adopted design choice or named premise; proven conditionally marks an argument under those premises; open identifies unfinished work. The lesson is proposed for review; the source section's acceptance does not approve this teaching page or establish implementation readiness.

The problem: equal values can arrive as different bytes

Transport is not the signed identity

The landing lesson used hashes to bind data and proofs. That works only if every participant constructs the same hash input. A byte-order or field-width disagreement can make two honest implementations identify different messages.

Assumed, C8-R04/R16. The peer-to-peer transport uses SSZ with snappy compression. Hashing uses the specified Solidity abi.encode preimage. A preimage is the exact byte string passed to the hash function. Peers decode the transport into typed values, enforce their bounds, and reconstruct that preimage. Neither compressed bytes nor SSZ serialization is the signed representation. C8-R04; C8-R16.

Precise term. PH is the protocol-header field set committed by phHash. It includes the execution block hash and protocol metadata. The execution block hash and phHash are different identities. This lesson fixes the bytes used to identify PH; it does not decide whether that PH is authorized or its execution is valid. Owning field/preimage table.

The mechanism: decode, check, then reconstruct

One canonical preimage from typed fields

Assumed, C8-R02–R04. PH's twelve static fields form a body of twelve ABI words. Each word occupies 32 bytes. Prefix the body with the PH domain tag and chain ID, in their specified order, then apply Keccak-256. The domain tag identifies the message type; it is not chosen by the sender. Domain tags; Static-body construction.

Proven conditionally, C8-R04. Because these fields are static, concatenating the encoded prefix and the 384-byte body gives the specified 448-byte PH preimage. The twelve-field body already includes chainId; the prefix includes it again. Preserve both positions when reconstructing the bytes. L1 does not need an SSZ decoder to recompute them. The sequencer-signature digest has its own domain and wraps phHash; the signature is not simply over arbitrary transport bytes. Construction argument; C8-V03 signature digest.

Worked example: an eight-byte field with a smaller value bound

Check the number before narrowing it

Assumed, C8-R05/R16. SSZ has no uint48 type. The wire carries the L1 anchor number as u64, but the admitted value still cannot exceed 2^48 − 1. A larger transport field does not enlarge the protocol's value range. Width rule; Value-bound register.

Derived fixture, C8-V08. These are test values, not live block numbers or measured performance. Exact source vector.

Check your understanding

Does using u64 on the wire permit an anchor number of 2^48?

No. Wire width and the protocol value bound are separate. C8-V08 rejects that value before conversion.

Why do 384 bytes and 448 bytes both describe PH in this lesson?

The twelve-field body occupies 384 bytes. Its two-word domain/chain prefix adds 64 bytes, giving the 448-byte hash preimage. Neither number is the size of the entire compressed peer message. C8 register.

Two nodes compute the same phHash. Have they proved the block valid?

No. They agree on the committed message, subject to the hash assumption. Authorization, context, execution and availability need their own checks. The landing lesson explains the proof/publication boundary.

Challenge this

  • A-ABI: can two implementations disagree on field order, endianness, padding or bounds while each believes it followed the specified decoder?
  • A-KECCAK: does the identity argument clearly depend on collision resistance, rather than treating a hash as a proof of execution?
  • Open composition: can you point to a signature or hash whose complete preimage remains undefined? Keep that owner item open; a general encoding convention cannot fill it.

C8's named premises and its integration list control these claims. No production conformance or whole-design readiness is asserted.
