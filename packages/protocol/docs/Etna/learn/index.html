Learn Etna, one building block at a time

A research design, not a description of any deployed system. Dated facts cite their sources at the time of writing (2026-09-30 to 2026-10-01).

Etna is a proposed fully permissionless successor to Taiko's based rollup. This site teaches it the way it was designed: as twelve building blocks, each depending on a few earlier ones, ending with a thirteenth module in which you assemble the whole protocol yourself. Every lesson ends with self-check questions (answers hidden until you want them) and a challenge this box that tells you where the design is most attackable and invites you to try.

Who this is for

Engineers, auditors and researchers who know what a rollup is and can read a Solidity signature. No knowledge of Taiko's current code is assumed; lesson 0 gives the minimum. If you already know the current protocol, start at lesson 1.

Lesson 0: start here

The current protocol in a page

Taiko is a based rollup: L1 Ethereum orders its batches, and validity proofs (ZK) finalize its state. Today three contracts matter. The Inbox on L1 accepts propose (blob pointers, one per L1 block) from a whitelisted operator chosen per 384-second epoch, and prove (an aggregated proof, hours later) from a whitelisted prover; prove writes a checkpoint of the L2 state into the L1 SignalService, which the Bridge uses to verify messages. The Anchor on L2 opens every L2 block with a system transaction carrying an L1 checkpoint into the L2 SignalService (Etna removes that transaction; lesson 11). Between propose and prove, users see preconfirmations: blocks the operator signs and gossips every second or two, with no bond behind them and no relation to what L1 will eventually say.

Three things go wrong. Whitelists make liveness depend on admins. Preconfirmations are unaccountable: an operator can withhold blocks, land different ones, and reorg everyone at handoff. And every timing rule assumes 12-second slots and 32-slot epochs. The June 2026 incident, in which forged TEE proofs finalized a false state, added a fourth: only ZK may finalize.

Self-check

Why is "L1 wins" a problem for preconfirmation users today?

Because the block that lands on L1 may differ from the one the user saw preconfirmed, and nothing on L1 references the gossiped block, so the operator can replace it at no cost.

Which contract address must Etna keep, and why is that hard?

The SignalService's authorized syncer is an implementation immutable: the Inbox proxy on L1, the Anchor proxy on L2. Whatever lands batches must keep the Inbox proxy address, or the L1 SignalService implementation must be bumped. Etna upgrades every proxy in place: the L2 SignalService implementation gains the permissionless reveal, since checkpoints there no longer come from a syncer, and the L1 SignalService, the Bridge and the Vaults get compatible implementations that keep addresses and storage and only remove their pause and owner-only powers (lesson 11; after the #22188 review, 2026-10-01).

Challenge this

The brief treats the whitelist as the root problem. Argue the opposite: that a whitelist with a bond and objective removal would satisfy R1's intent. Then check which of R1's words ("no whitelist, no admin in operation") your argument violates. Keep the answer; lesson 2 explains why the design chose bonded seats over a bonded roster.
