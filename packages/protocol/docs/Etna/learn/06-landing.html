Lesson 6: landing with a proof

Prerequisite: lesson 4. Design page: Propose-with-proof §1 to §4, §8.

Goal

Trace one landing from a certified block to a checkpoint in the L1 SignalService, and say which checks are the contract's and which are the proof's.

The idea

Today propose and prove are separate; Etna has one action, land, that carries blobs and a proof and finalizes immediately. Two design choices make it permissionless. First, the blob bytes are a pure function of the certified blocks (signed fields, signatures and the exact compressed transaction bytes, packed in a fixed layout), so two landers produce bit-identical blobs and any prover's proof works for any lander. Second, the inbox verifies the end certificate itself, so the landed range is exactly a certified range: what users saw attested is what lands.

The check list (cheapest first, proof last)

  1. Sequence: the range starts at lastLanded + 1; at most 256 blocks; several landings may sit in one L1 block.
  2. Parent: the parent hash equals lastLanded; the parent state root is read from storage, never from calldata.
  3. View and rights: the range lies in one view; opening a view supplies the view-change chain; the sequencer is the holder (or the term is open, no-committee or in dead mode and the sequencer is bonded).
  4. End certificate: 22 of 32 aggregate signatures over the end header hash; not voided.
  5. Blobs: blobhash(i) matches for each of at most 6 blobs.
  6. Anchor tip: the newest anchored L1 block is verified by blockhash (256 blocks) or EIP-2935 (8,191 blocks).
  7. Forced inclusion: the consumed count meets the floor (lesson 10).
  8. Effects: lastLanded, the term record, rewards, the prevrandao mix, and saveCheckpoint(endHeight, endBlockHash, endStateRoot) into the L1 SignalService, exactly as today.
  9. Proof: two distinct ZK systems accept the journal; a revert rolls everything back.

Contract versus proof

Outside the proof (inbox)Inside the proof (guest)
sequence, rights, certificate, blob hashes, anchor tip, queue state, deadlinesblob decoding, every header's signature and fields, execution to exactly each block hash, the hash chain from the parent to the end, every anchored L1 header chained to the tip, timestamps, the forced-inclusion blocks and their placement

The journal binds: chain id and the published-constants hash; parent hash and root; first and end heights, end hash, root and header hash; the blob-hash root; term, view and leader; the opening object hash; the anchor tip's number, hash and timestamp; the forced-inclusion head before and after and the consumed-entries hash. The verifier keeps two image sets per leaf with a two-hour overlap so a rotation never orphans an in-flight proof.

Self-check

Why is the certificate verified on L1 rather than inside the ZK proof?

So the withholding defence never rests on ZK soundness. If a proof system were unsound, an attacker could at most finalize a false root for a block that was genuinely certified, never land an uncertified one.

Why can any lander use a proof it found in the mempool?

The journal names no lander and the blobs are deterministic; the reward goes to the rewardTo in the winning transaction, and the trailing-VERIFY shape makes losing free, so copying steals nothing.

How does R2 hold?

The Inbox proxy address is unchanged, so it is still the SignalService's authorized syncer; the call is byte-identical to today's; no shared contract changes.

Challenge this

The inbox reads the parent state root from storage. Construct a scenario in which a lander tries to land a range on the wrong parent and show which check stops it and whether the lander pays anything with and without Frame Transactions.
