Change the engine, preserve custody

Install new rules without moving users' assets or forgetting old obligations.

The problem: an address is part of the promise

Proven/source: today's Bridge relies on SignalService checkpoints and persistent message statuses. Vaults hold assets and remember canonical-to-bridged token mappings. Replacing an address or resetting a status map can strand assets or allow a message to be processed twice, even if the new execution engine is correct.

Assumed rule: Etna retains both layers' SignalService, Bridge and ERC20/ERC721/ERC1155 Vault addresses, plus the Anchor proxy. It upgrades implementations compatibly, preserving balances, token mappings, message identifiers, replay protection, checkpoints and proof caches. The exact checkpoint remains (uint48 blockNumber, bytes32 blockHash, bytes32 stateRoot).

The mechanism: finish the old work, then cross one boundary

Assumed rule: the DAO installs a fixed migration manifest and audited upgrades. It removes ordinary pause, remapping, quota, minting, resolver and fee-control powers; ownership authorizes upgrades only. Every wrapper and legacy fallback route must be covered, not just the obvious Inbox entry points.

Proven under the specified transition: old proposal and forced-queue tails are frozen, making the remaining legacy work finite. Anyone can prove that work and construct the prescribed forced-only legacy suffix. New Etna requests and their fees are rejected until ACTIVE. This prevents new escrow from becoming trapped if old data prevents activation; clients must show the temporary intake gap. Legacy blob-slice requests are finished under their original rules rather than reinterpreted as new raw-transaction entries.

Assumed rule: a verified certificate fixes the final legacy L2 number, hash, state root and timestamp. Activation derives every field of the initial Etna head H0 from that certificate and fixed domains. H0 has segment number0, zero consumed cursor, empty force snapshot and a special zero-origin marker. That marker is not an Ethereum header or a publishable checkpoint.

Assumed boundary rule: before sealing the legacy parent, verify builder/importer/prover parity, deploy the exact canonical EIP-4788/2935 contracts and install fail-closed guards at the existing Anchor and SignalService proxies. Their code hashes and retained layouts belong in the authenticated migration manifest. Each legacy Anchor entrypoint and the L2 old saveCheckpoint writer retains its old provenance checks and additionally requires a successful current-timestamp 4788 lookup returning exactly 32 bytes equal to zero. Pin/reveal require the L2 mode and a nonzero current word. The L1 SignalService keeps Inbox authorization and explicitly disables these L2 methods.

Proven conditional boundary: legacy headers keep the zero word. For Etna, the standard pre-execution write puts the authenticated nonzero origin hash into 4788 before the first Etna transaction. Both old writer paths then reject, even if the old ancestors hash would still match. Missing code, failed lookup or malformed returns fail closed. This uses the current word, not a separately writable L2 phase flag. Historic Anchor storage stays frozen and is never reused; consumers replace the live anchor-number getter and Anchored event with the L2 header and authenticated L1 header.

Assumed first-successor rule: the first actual segment extends the stored initialHeadHash, authenticates public L1 context with Inbox ACTIVE and uses a real origin at or after activationL1Number. The existing statement and old-head hash bind that context; local validation uses the same rule and returns UNKNOWN when it is missing. There is no beginEtna or signed activation transaction. The first segment consumes no new forced requests; its origin establishes their first ordinary snapshot. The next segment resumes normal FIFO processing. Activation checks the empty new queue and zero request-fee liabilities; it never erases unexpected records, clears old fees or invents an accepted-segment receipt.

Worked example: nine waiting requests

Assumed example: the certified legacy head is block10,000 at time9980. Activation occurs in L1 block500 at time10,000; requests0–8 enter Etna’s queue later in that block, after activation. H0's cut is0. A minimal first segment has one L2 block with zero transactions, authenticates block510/time10,120 as its real origin under the public ACTIVE context and freezes cut9/time10,120. The standard system calls still write state.

Proven from these numbers: all nine requests are mature because10,000+120≤10,120. Subsequent segments consume0–3,4–7, then8. Request9 arriving after block510 cannot change that frozen snapshot. With a 1,024-byte L2 header, its empty-transaction BodyV1 is at most 1,039 bytes, below the 32,768-byte calldata cap. No activation-witness transaction or anchor gas budget is needed; full execution and system-call parity still require verification.

Attacks and limits

Proven under faithful rules: a caller cannot choose an arbitrary genesis root, reset old message statuses, skip a queued request by changing its namespace, or reactivate a disabled daily admin selector. Preserving addresses alone supplies none of these protections; state and authority compatibility are essential.

Assumed: legacy accepted state is sound, required historical data survives, both proving paths work, and upgrades are honest. Open: authenticate the live address/code/storage manifest and rehearse historical messages, wrappers, bonds and the complete authenticated activation context and first anchor-free block. Before canonical deployment, builders, importers and both guests must agree on the standard system-call writes; code presence alone does not prove parity. Missing legacy data can halt draining indefinitely; there is no timer that fabricates a safe root. A malicious future DAO upgrade remains an explicit trust boundary.

Check your understanding

Does keeping a Vault's address prove migration is safe?

Proven: no. Storage layout, balances, mappings, supply and message replay state must also survive, with correct root authority.

Does the first empty force interval discard the nine requests?

Proven: no. Their records and fees remain, and the first real snapshot makes them mandatory for later successors.

Can the DAO remain inactive after installation?

Proven conditionally: anyone can finish the fixed drain and activate if the required data and proofs exist. DAO inactivity does not replace those prerequisites.

Challenge this

Find one historical message, wrapper privilege or legacy selector that the upgrade inventory misses. Then try to construct two different H0 values from the same valid certificate. Finally, remove a required historical blob: which claimed liveness bound stops applying, and does any rule incorrectly let an administrator assert the missing state?
