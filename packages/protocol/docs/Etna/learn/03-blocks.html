Lesson 3: blocks and validity

Prerequisite: lesson 2. Design pages: Preconfirmation & certificates §1 to §3, Anchor §1.

Goal

Be able to decide, as a node, whether a received 1-second block is valid, using only signed objects and L1 data at least 48 seconds old.

The idea

Today a node rebuilds the block from attributes and never checks that its result matches what the sequencer signed. Etna makes the block self-describing and the check exact. The sequencer signs a header that names the term, the view, the block's execution hash, the hash of the compressed transaction bytes, the certificate it carries and the view change that opened its view. The same fields are the calldata of the block's first transaction, anchorV5, so they sit inside the execution hash and a ZK guest can rebuild the header from blob data alone.

The rules (V1 to V6)

RuleCheckWhat it reads
V1 signerthe header's signature recovers to holder(term, view)a signed object and 20-minute-old L1 state
V2 view entrytimestamp inside the term; the first block of a view carries the view change that opened it and builds on that view change's locksigned objects
V3 parent and carried certificatethe parent was accepted in this view; the carried certificate is for the parent or grandparent and verifies against the committeesigned objects
V4 timetimestamp ≥ parent + 1 and < term endthe header only: no wall clock, no L1 landing time
V5 anchorfirst transaction is anchorV5; its L1 block is at least 48 s and at most 30 min older than the block, monotone from the parent, and equals the node's own L1 header; if the anchor advanced, every due forced inclusion is includedL1 blocks at least 48 s old; a node lacking the block holds it as pending, never invalid
V6 executionthe received payload, submitted unchanged to the engine, is VALID and its hash equals the signed hash; the anchor's receipt status is 1deterministic execution

Failure is silence: the block is dropped and its signature kept as possible equivocation evidence. Two pending states (unknown parent, L1 block not yet seen) are held and re-evaluated. There is no V7 at the node: the guarantee that what lands is what was certified comes from the landing (lesson 6).

Why the anchor age matters

Under ePBS an L1 payload is canonical in practice one slot after it was revealed. If a block could anchor the newest L1 block, honest nodes with slightly different L1 views would disagree on V5. Requiring the anchored block to be at least 48 seconds old (2.5 times the canonical-at-N+1 latency at 12-second slots, 24 slots at 2-second slots) makes every honest view agree, and expressing disagreement as pending instead of invalid means a lagging node never rejects a good block.

Self-check

Why does V4 have no upper bound tied to when the block lands on L1?

Today's upper bound (the landing time) is what makes a preconfirmed block retroactively invalid when its proposal lands late. Etna bounds timestamps by the term instead, which every node knows in advance.

A node's wall clock is 40 seconds fast. Does it reject valid blocks?

No. No validity rule reads the wall clock. Its clock only affects when it would sign a timeout as an attester (lesson 5), and even that is a signing policy, not a validity rule.

What happens to a block whose anchor transaction reverts?

It is invalid (V6 requires receipt status 1). Today such a block is valid but silently lacks its checkpoint.

Challenge this

V5 lets a sequencer anchor an L1 block up to 30 minutes old. What can a sequencer gain by anchoring as stale as allowed, and which rule bounds the harm? (Hint: lesson 10, the attester anchor-lag policy, and the 102-minute bound.)
