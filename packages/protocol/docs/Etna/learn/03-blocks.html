Lesson 3: blocks and validity

Prerequisite: lesson 2. Design pages: Preconfirmation & certificates §1 to §3, Anchor §1 and §2, Forced inclusion §4.

Goal

Be able to decide, as a node, whether a received 1-second block is valid, using only signed objects and L1 data at least 48 seconds old.

The idea

Today a node rebuilds the block from attributes and never checks that its result matches what the sequencer signed. Etna binds every block to a signed header and makes the check exact. The sequencer signs a header PH = {version, chainId, termId, view, vcHash, height, timestamp, parentHash, blockHash, txListHash, carriedCertHash, anchorNumber}: the term, the view, the hash of the object that opened the view, the block's execution hash, the keccak of the exact compressed transaction bytes, the certificate it carries and the number of the L1 block it anchors. The execution hash commits to the block's own L2 header, whose parentBeaconBlockRoot holds the anchored L1 block's hash (an L1 execution block hash, never zero) and whose 7-byte extraData is basefeeSharingPctg(1) ‖ termId(4) ‖ view(1) ‖ kind(1), with kind 0 NORMAL, 1 FORCED (a forced-batch block, view 254), 2 GENESIS_CHILD (the first Etna block) or 3 FI (a forced-inclusion block); view 255 is the open-empty, dead-mode or no-committee sentinel. vcHash and the carried certificate travel in the blob record, not in the block, so a ZK guest rebuilds the signed header from blob data and the block alone. The block contains no protocol transaction and no Taiko-specific pre-execution hook: its only pre-execution calls are L2's own EIP-4788 and EIP-2935 system calls (anchor-free blocks, issue #22147). The seat is carried nowhere: (termId, view) and the holder list imply it.

No rule reads a transaction receiptdeterministic execution of a fixed payload plus equalities on header fields

Failure is silence: the block is dropped and its signature kept as possible equivocation evidence. The two pending states (unknown parent, L1 block not yet seen) are held and re-evaluated. There is no V7 at the node: the guarantee that what lands is what was certified comes from the landing (lesson 6). Fork choice needs no clock either: the canonical tip is the valid block with the highest (term, view, height) whose ancestors within its view are all certified except at most two leaf blocks; of two blocks at one height under one opening object a node keeps the certified one, else the first seen, and stores both headers as evidence.

An attester asks for more than V1 to V6 before it signs (lesson 4): V8 (the block does not skip a due forced inclusion) and two size rules the guest asserts as well (certificate page V9 and V10). V9: a block's canonical record (headerCore ‖ seqSig ‖ VC bytes ‖ txListBytes) is at most MAX_ENVELOPE = 130,035 bytes, so with its 9 framing bytes it fits one blob of 130,044 bytes and any single certified block can be landed alone at every slot time. V10: the sequencer blocks of one term total at most TERM_BYTES_MAX = 5 × LANDING_UNIT = 5 × 254,000 = 1,270,000 bytes, about 9.8 blobs, which holds one sequencer's throughput to about 20 KiB/s of compressed output; forced-inclusion blocks and forced batches are exempt (round 4, R4H-6), and an FI block's record is about 250 bytes and carries no payload, the entry's own blob or calldata being the witness (round 6 fix pass). Both serve the landing reward (round 6, R6H-3; lesson 7): because no record exceeds one blob, a greedily packed landing that is not its term's last carries more than 260,088 bytes of payload, at most about 12,500 bytes of a term go uncounted, and after k greedy landings bytesLanded exceeds (k − 1) × LANDING_UNIT, so every greedy landing is paid however the sequencer sized its blocks and a term needs at most five.

Why the anchor age matters

Under ePBS an L1 payload is canonical in practice one slot after it was revealed. If a block could anchor the newest L1 block, honest nodes with slightly different L1 views would disagree on V5. Requiring the anchored block to be at least 48 seconds old (2.5 times the canonical-at-N+1 latency at 12-second slots, 24 slots at 2-second slots) makes every honest view agree, and expressing disagreement as pending instead of invalid means a lagging node never rejects a good block. V5 is monotone, not "must advance": during an L1 stall leaders keep anchoring the last block.

Self-check

Why does V4 have no upper bound tied to when the block lands on L1?

Today's upper bound (the landing time) is what makes a preconfirmed block retroactively invalid when its proposal lands late. Etna bounds timestamps by the term instead, which every node knows in advance.

A node's wall clock is 40 seconds fast. Does it reject valid blocks?

No. No validity rule reads the wall clock. Its clock only affects whether it would sign an attestation or a timeout as an attester (lessons 4 and 5), and even that is a signing policy, not a validity rule.

Where does an Etna block say which L1 block it anchors, and who checks it?

In two places bound together: the signed header carries the L1 block's number and the block's own header carries its hash in parentBeaconBlockRoot, which the execution hash commits to. Nodes check the pair against their own L1 view (V5); the guest checks that the witnessed L1 header with that number hashes to the field and chains by parent hash to the landing's anchor tip; the inbox checks only the tip (blockhash, else EIP-2935, else refuse). On L2 the block's EIP-4788 system call records the hash keyed by the block's timestamp, and anyone may later reveal that L1 block's state root as a checkpoint, bound to the recorded hash by keccak (Anchor page §3). Today the anchor is a transaction whose revert leaves the block valid and silently drops its checkpoint; an Etna block has no such transaction to revert.
