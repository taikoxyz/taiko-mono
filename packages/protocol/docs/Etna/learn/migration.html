Etna · Accepted C4 specification

Migration without moving custody

Change the rollup engine while preserving the contracts, assets and message history users depend on.

Open, subsequent review: cycle-2 round 1 found that a DAO-fixed activation boundary can become stale before execution, and that a legacy proof has no specified call authenticating the terminal header timestamp used in genesisLockHash. W22 proposes C4 corrections. The W22 proposal separates two authenticated facts: a historical checkpoint proves the installation at initialization, while the final drain call decodes and authenticates the exact terminal legacy header before sealing its height, hash, root and L2 timestamp as the Etna parent. A later legacy proof may advance the finalized tip between those steps; an old installation timestamp cannot stand in for the terminal timestamp. These are candidate C4-R03/R07 rules, not accepted behavior. The accepted source below predates them; this lesson does not teach the correction as merged or migration as implementation-ready.

Based on merged C4 at ad85e9f. This lesson adds no protocol rules. Read C1's checkpoint lesson first; open each panel after the preceding idea makes sense.

Keep the address and everything the address means

Custody continuity is a state requirement

Problem. A bridge's stored history says which messages were processed, which tokens are canonical and which assets remain in custody. Keeping its address while erasing history could permit another mint.

Assumed, C4-R09. Existing SignalService, Bridge, Vault and wrapper addresses on both chains remain. Balances, mappings, permit state, message statuses and authenticated signal caches stay in place. A completed old message remains completed; an eligible retry uses the retained authenticated path. Custody continuity.

Assumed, C4-R01/R11. A manifest commits exact implementations, dependencies, layouts and authority paths, including reachable routers and inherited selectors. Unsupported live variants block arming. A caller cannot substitute a root or implementation. Manifest; storage compatibility.

Proven conditionally. Preserving authenticated state and encodings prevents migration itself from reviving a completed message. Addresses alone prove nothing about the soundness of inherited custody and caches. C4-R09 continuity argument.

Give the legacy tail a deadline and a public escape

Freeze intake before deciding the tail

Problem. Anyone may submit a retained legacy proof, but generating its required SGX leg still needs an admitted instance. Removing the submitter whitelist does not remove that production dependency.

Assumed, C4-R02–R05. Install and authenticate guarded L2 prerequisites; the committed DAO upgrade arms a schedule. The timestamp cutoff closes new legacy proposals and paid forced requests. Etna intake stays closed until activation. The frozen tail cannot grow while callers try to prove it.

If the tail finishes, authenticate the terminal installation and enter READY. If the deadline arrives first, anyone may begin authenticated abandonment. That atomically closes legacy proving. Callers verify the frozen suffix in descending order, matching each forced source against its original queue record. Only complete checks and repair permit the visible queue-head change.

Proven conditionally. Phase closure prevents proving and abandoning the same tail concurrently. A proof ordered first updates the boundary; abandonment ordered first makes a later proof fail. Exact source matching and delayed head update prevent omitted or duplicated requeues. C4-R05 phase and repair rule.

Limit. The deadline removes an admitted prover's veto on abandonment. Authentic preimages, funding and L1 inclusion remain necessary. A hash cannot recover missing bytes. Named premises.

A request can owe no fee and still be unsettled

Keep execution progress separate from payment

Problem. The old proposer was paid when a forced request entered its proposal. If that proposal is abandoned, the authenticated request returns to the queue. Paying the old fee again would spend escrow that is no longer there.

Assumed, C4-R06. A requeued entry keeps its source identity with zero remaining fee. Separately, legacySettled stays false: requeue is not its first Etna disposition. Never-proposed legacy entries retain their remaining escrow and also begin unsettled.

Assumed accounting boundary, accepted under D63. First Etna consumption captures the remaining legacy fee, marks settlement and zeroes the fee atomically: execution credits the includer’s pull ledger, while a void, including through fiClear, burns it. Later re-consumption or replay cannot repeat payment, refund or burn. The separate legacyReplayable bit is set by a void and cleared by execution; changing that bit moves no money. There is no old first/nonfirst-void or stall-count rule. Open: the legacy expiry and LEGACY_BLOB execution promise still need user disposition and profile/proving evidence; settlement is not a promise that the original transactions execute.

Start the new clock at activation

The preceding block cannot contain a future record

Problem. Activation can authenticate the immediately preceding L1 block D. But D predates ACTIVE and its bootstrap record. A long gap before activation must not make the new record appear older than it is.

Assumed, C4-R07/R08. D supplies an already-readable canonical hash and timestamp. The actual activation block supplies the new number and time. Required references must authenticate ACTIVE and the bootstrap record, so their floor is the activation block, not D. C4-R07.

The first permitted term is recomputed from actual activation using the owning term and minimum-anchor-age parameters. Its start leaves the reviewed age allowance after activation. The L2 parent remains the actual finalized legacy block, without a fabricated root or committee certificate. Initialization; parameter ownership.

Open, C2/S2/C7/C8: exact bootstrap provenance, opening identities and complete first-header regimes. Boundary facts do not fill missing proof or signature rules. C4-R08.

Remove operational privileges without erasing storage

The DAO keeps upgrade authority

Problem. An old pause, resolver setter, wrapper owner mint or unused initializer can remain a back door despite new permissionless roles.

Assumed, C4-R10 and D26. The revision removes listed ordinary powers: Anchor withdrawal, resolver registration and wrapper owner mint/burn, while authenticated vault branches remain. Effective pause gates, listed legacy mutation and force-DONE routes are disabled for every caller. The manifest covers delegated and inherited paths. Exact retained-surface table.

The nonproxy QuotaManager is not described as upgradeable. Its ownership is renounced before arming while quota/consumption state remains. This does not refill quotas or cap an uncapped asset. Quota treatment.

Assumed, D30. Bridge rejects plain Ether from everyone, including DAO and former pauser. Authenticated payable sendMessage flows and the payable upgrade path remain. Uniform plain-Ether rejection.

No initial treasury sweep.

Accumulated pre-Etna base-fee treasury and stray assets remain in Anchor until a later explicit DAO upgrade recovers them. Removing ordinary withdrawal does not remove that balance. Accepted treasury consequence.

Proven conditionally: a complete manifest and removals leave no listed operational DAO selector outside upgradeability. An arbitrary future DAO upgrade remains a trust boundary; current rules cannot prove future code preserves them. C4-R10 authority inventory.

A restart preserves history but initializes successor controls

The restored parent and its successor need different treatment

Problem. A historical parent does not by itself authorize a fresh successor after recovery. The old FI clock/run controls are withdrawn; D61/D63 accept the hatch field synchronization. Exact restart identity and authorization remain separate open obligations.

Assumed, C4-R12. A reviewed forward upgrade recovers a conflicting provisional suffix only at the permitted published floor. It cannot roll custody below the newest published checkpoint. Recovery floor.

Check your understanding

Can a proof finalize the tail after abandonment begins but before repair ends?

No. Beginning abandonment closes proving atomically with the boundary snapshot. A proof ordered first instead changes the boundary used. C4-R05.

A requeued entry has no fee. Does that prove it was already settled?

No. legacySettled is separate and remains false on requeue. Fee entitlement is not disposition history. The D63-accepted adapter already defines settlement: first execution credits the captured fee, first void burns it, and later replay changes no settled money. The original stall-void rules are superseded; the legacy content promise remains open. C4-R06.

After a long L1 gap, can bootstrap use the old preceding block D as its reference floor?

No. D predates ACTIVE. The reference floor and age allowance start at actual activation; the first term is recomputed. No maximum L1 gap is presumed. C4-R07/R08.

Challenge this

  • A-MANIFEST: can a delegate, custom wrapper or initializer preserve a power the direct interface removes?
  • A-DATA / A-RECOVERY-FUNDING: can everyone obtain exact preimages and fund repair and unpaid replay? A commitment and deadline provide neither.
  • A-LEGACY: were roots, caches, mappings and custody sound before migration? Address reuse cannot repair a compromised initial state.
  • Open hatch integration: can a restart or replay bypass queue obligations or recreate settled claims? Demand the owning sections’ authenticated transition and new timing rules.
