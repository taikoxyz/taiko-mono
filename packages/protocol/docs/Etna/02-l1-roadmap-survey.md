# Etna L1 roadmap survey

Research cut: **2026-09-30 UTC**. All linked primary documents below were retrieved through live-capable web fetches during this session. This is a dated source snapshot, not a prediction or a live deployment audit. Fork selection and EIP maturity are separate axes.

**Proven/source:** Glamsterdam is not yet recorded as activated on mainnet. Its meta specification, [EIP-7773](https://eips.ethereum.org/EIPS/eip-7773), is **Review**, with Sepolia scheduled for **2026-10-06 13:53:36 UTC** and Hoodi/mainnet activation fields blank. [Ethereum.org](https://ethereum.org/roadmap/glamsterdam/) says testing on devnets, expected Q4 2026, date not confirmed. Hegotá's [EIP-8081](https://eips.ethereum.org/EIPS/eip-8081) is **Draft**, has no activation dates, and schedules **FOCIL and Frame Transactions**. [Ethereum.org](https://ethereum.org/roadmap/hegota/) gives an unconfirmed Q2 2027 expectation. Neither fork should be described as shipped.

**Assumed A-FRAMES:** the user supplies an Etna launch premise that Frame Transactions will be available. That premise is stronger than today's deployment evidence. Etna can use it in the preferred transaction path, but should retain the ordinary atomic transaction path described below. Nothing in this survey upgrades an EIP proposal into an Ethereum guarantee.

## How to read status

[EIP-7723](https://eips.ethereum.org/EIPS/eip-7723) defines **PFI** = Proposed for Inclusion, **CFI** = Considered for Inclusion, **SFI** = Scheduled for Inclusion, **DFI** = Declined for Inclusion, and **Included** = actually activated. SFI can still be removed. `Draft`, `Review`, `Last Call`, and `Final` describe the document itself; a Draft can be SFI and a Final informational EIP need not be a consensus feature.

Source precedence for this survey is: current fork meta EIP for inclusion state; current individual EIP for semantics and document status; official announcements for activation; official explanatory pages for context. The EF's [September priorities](https://blog.ethereum.org/2026/09/07/protocol-priorities) and [Hegotá opinion/tier list](https://blog.ethereum.org/2026/09/07/protocol-hegota-eips) are useful statements of preference, not substitutes for the meta EIP.

Three source conflicts matter:

- The current Glamsterdam explanation still says its meta EIP is Draft; the directly fetched meta is **Review**. An older `/en/roadmap/glamsterdam` search result even says H1 2026. Neither stale text overrides the meta/activation table.
- The explanatory page calls EIP-2780 an intrinsic-gas reduction. The directly fetched EIP is now **Resource-based intrinsic transaction gas** and explicitly says a plain ETH transfer to an existing account remains 21,000 execution gas.
- EF's September opinion recommends shipping Frames with keyed nonces and recent roots, and grades Block-in-Blobs DFI. The meta still lists keyed nonces/recent roots as CFI and Block-in-Blobs as PFI. Those are the fork selection states used here.

## Gas pricing and bounded operations

**Proven/source:** larger L1 blocks do not remove the need to bound one atomic Etna action. The existing [EIP-7825 transaction cap](https://eips.ethereum.org/EIPS/eip-7825) is **Final** and specifies 16,777,216 gas. Glamsterdam introduces separate execution/state metering and other pricing changes, so an old gas estimate is not a valid launch estimate. Proof verification, data bytes, signature checks, root publication, reward accounting and any forced-queue work must jointly fit the launch fork's limits.

| Gas/accounting feature | Document status | Fork selection / target | Etna classification and consequence |
|---|---|---|---|
| [2780 — Resource-based intrinsic transaction gas](https://eips.ethereum.org/EIPS/eip-2780) | Review | Glamsterdam SFI | **Required compatibility** with host gas semantics; no reliance on cheaper transfers. Runtime pre-execution out-of-gas is an included failure, not transaction invalidity. Fallback if absent: pre-Glamsterdam gas schedule. |
| [7778 — Block Gas Accounting without Refunds](https://eips.ethereum.org/EIPS/eip-7778) | Review | Glamsterdam SFI | **Required compatibility**, no liveness reliance on refunds freeing block capacity. Reclaimable storage does not create a free recovery budget. |
| [7976 — Increase Calldata Floor Cost](https://eips.ethereum.org/EIPS/eip-7976) | Review | Glamsterdam SFI | **Required compatibility.** Current floor is 64 gas per calldata byte, both zero and nonzero. Calldata fallback must be small enough and funded. |
| [7981 — Increase Access List Cost](https://eips.ethereum.org/EIPS/eip-7981) | Review | Glamsterdam SFI | **Required compatibility.** Access lists cannot evade data charges; current surcharge 64 gas per encoded address/key byte. No correctness dependency on their discount. |
| [8037 — State Creation Gas Cost Increase](https://eips.ethereum.org/EIPS/eip-8037) | Review | Glamsterdam SFI | **Required compatibility.** CPSB and separate state metering affect role registration, queue growth, slash records and frame payment limits. Bond/reward budgets must cover both gas dimensions. No requirement that this change exist; support whichever host schedule is active. |
| [8038 — State-access gas cost update](https://eips.ethereum.org/EIPS/eip-8038) | Review | Glamsterdam SFI | **Required compatibility.** Reprice checkpoint writes, multi-party challenges and cold account access; cap iteration independently of participant population. |
| [7904 — Compute Gas Cost Analysis](https://eips.ethereum.org/EIPS/eip-7904) | Review, Informational | Glamsterdam “Other EIPs / Informational” | **Ignored as a consensus dependency.** Current analysis recommends **no** compute/precompile repricing. Do not repeat the earlier title as if a repricing had been selected. |
| [8261 — Gas Limit Schedule](https://eips.ethereum.org/EIPS/eip-8261) | Review, Informational | Glamsterdam “Other EIPs / Informational” | **Optionally benefits.** Recommended client defaults and maxima, not a new block-validity guarantee. Etna must not require a claimed 150M/200M gas floor. |
| [8131 — Unified Transaction Content Floor](https://eips.ethereum.org/EIPS/eip-8131) | Draft | Hegotá CFI | **Required compatibility if activated**, no feature dependency. Extends 64 gas/byte floor to all user-controlled transaction content. Retain margin for the full envelope/proof, not only batch calldata. |
| [8279 — Block Access List Byte Floor](https://eips.ethereum.org/EIPS/eip-8279) | Draft | Hegotá CFI | **Required compatibility if activated.** Counts BAL growth in the transaction floor. Benchmark large checkpoint/registration/slashing updates under the final version. |
| [3298 — Remove storage-clear refund and refund cap](https://eips.ethereum.org/EIPS/eip-3298) | Draft | Hegotá CFI | **Required compatibility if activated.** Never promise challenge profitability based on expected storage-clear refunds. |
| [8368 — CPSB Recalibration for New Gas Limit](https://eips.ethereum.org/EIPS/eip-8368) | Draft | Hegotá PFI; explicitly a placeholder | **Open compatibility cost**, not a chosen numeric value. Its new reference gas limit and CPSB are TBD. Recalibrate gas escrow and launch limits after host parameters settle. |

“Required compatibility” means applications must obey the active L1 rules, **not** “cannot launch unless this proposal is included.” If a repricing slips, the previous schedule remains usable; if it ships, gas-cost tests must use it. This distinction prevents a cost-estimation task from becoming an unnecessary protocol dependency.

**Proven/arithmetic:** at a 64 gas/byte floor, 32 KiB of calldata alone contributes 2,097,152 floor gas, and 128 KiB contributes 8,388,608, before accounting for the complete transaction and interactions with execution/state metering. These are data-floor contributions, not additive full transaction gas estimates. The fallback should bound total encoded bytes and support partial queue draining/smaller batches. A design that requires revealing an arbitrarily large withheld blob set in one calldata action fails this feasibility check.

**Open:** no actual Etna verifier bytecode exists in this research task, so a final verification-gas bound cannot be measured here. A launch gate must validate worst-case frame and ordinary-transaction paths under the finalized L1 gas schedule. Do not claim a minute-level latency bound independent of gas prices, competing L1 demand, or available prover throughput.

## Blob capacity: what is verified, and what is not

**Proven/source:** the [Fusaka announcement](https://blog.ethereum.org/2025/11/06/fusaka-mainnet-announcement) scheduled mainnet for 2025-12-03 and BPO1/BPO2 for 2025-12-09/2026-01-07. The later [January 20 checkpoint](https://blog.ethereum.org/2026/01/20/checkpoint-8) explicitly reports the BPO forks as live, with **target 14 / maximum 21 blobs per L1 block**, compared with 6/9 before those BPO increases. EIP-4844 defines 4,096 field elements of 32 bytes, or 131,072 raw bytes per blob; actual batch payload capacity is lower after field encoding and metadata.

**Open:** this survey did not authenticate a live mainnet client's full current `blobSchedule`, and it did not find a later authoritative activation in the sources retrieved. Therefore 14/21 is the latest explicitly verified activated schedule here, **not a claim that no later schedule exists**. Neither current fork meta by itself promises a particular future Etna blob throughput. EIP-7892's example timestamps/counts are expressly illustrative; never treat those examples as mainnet activation evidence.

**Proven/design consequence:** a rollup must handle scarce/expensive blobspace even if the nominal limit grows. In a blob landing, the L1 transaction's blob versioned hashes must be bound into the same proved batch statement and checked against the actual transaction; the proof alone does not establish publication. In calldata mode, the exact bytes and proof are carried together. All proofs and live recovery data must be retrievable; finite Ethereum blob retention does not supply permanent Etna historical archival. DA of preconfirmed blocks before landing remains Etna's own problem.

## Minimum L1 dependency set

| Dependency | Status / assumption | Launch requirement | Fallback / cannot-launch condition |
|---|---|---|---|
| Canonical Ethereum execution, collision-resistant commitments, signature verification and eventual finality | **Assumed A-L1/A-CRYPTO**; ordinary Ethereum behavior | Required for settlement and existing bridge custody | **Cannot launch safely without these.** A permanent L1 halt cannot be repaired by an L2 role auction. |
| Atomic contract call validating proof, exact prior head, data commitment, forced-queue interval and next state before publishing checkpoints | **Proven capability** of ordinary EVM execution; proof-system implementation remains a separate launch obligation | Required for R7 and bridge safety | **Cannot launch without a sound deployable verifier/circuit and a bounded action.** No ePBS/BAL/FOCIL feature substitutes for it. |
| L1 data publication | [EIP-4844](https://eips.ethereum.org/EIPS/eip-4844) **Final**, existing blob baseline; calldata already exists | At least one usable data mode required | Blob congestion/unavailability → bounded calldata mode and smaller batches. If neither mode can be afforded/included, halt safely; do not advance a root without DA. |
| Frames preferred envelope | EIP-8141 **Draft**, Hegotá SFI; **Assumed A-FRAMES** at Etna launch | Required by user premise, used for proposed race optimization | If delayed, atomic ordinary transaction preserves R7 but loses frame-specific invalidity/gas behavior. Label this degraded launch explicitly instead of pretending Frames shipped. |
| Public-mempool/builder support for chosen frame form | **Open** deployment/relay behavior, distinct from consensus validity | Required only for the preferred delivery route | Retry through ordinary transactions. A terminal VERIFY usable through direct builders must not become a hidden mandatory permissioned relay. |
| Beacon-root authentication, only if Etna uses CL facts | [EIP-4788](https://eips.ethereum.org/EIPS/eip-4788) **Final**, existing baseline | Optional in the minimum design; required for any specific mechanism that invokes it | Omit optional CL randomness/fact consumers or use an equivalently authenticated execution-header proof path. If an indispensable mechanism has neither, **cannot launch that mechanism**. Never replace it with a trusted RPC oracle. |
| Eventual affordable inclusion for an honest actor and ability to obtain required data/proofs | **Assumed A-L1/A-ECON/A-EXEC/A-ARCHIVE** | Required for liveness, not a new EIP | No unconditional fallback under permanent censorship, every-prover failure, or unbounded gas prices. Finite timeout bonds penalize voluntarily accepted duties; they cannot create L1 capacity. |

For EIP-4788 consumers, the system stores **parent beacon block roots**, not automatically the current finalized execution root. The application must verify the needed Merkle links and finality fact, and handle retention before a root is overwritten. EIP-7688 changes merkleization; root type and fork schema must be bound. An authenticated CL fact is permitted by R5; a proposer lookahead or timing rule in slots is not.

**Proven/independence argument:** Etna's preconfirmation cadence is driven by its own seconds-based issuance rule. Landing is driven by proof readiness, data size and L1 inclusion. Replacing Ethereum's production interval with 6, 4 or 2 seconds changes how quickly an eligible L1 action may land but does not change the Etna role registry, sequencing predicate or timeout value in seconds. L1 block-number thresholds remain block-number thresholds, with no promised fixed conversion to seconds. Timers evaluated on L1 can execute only when a block arrives; their expiry never guarantees a transaction at that exact wall-clock instant.

## Consequences to carry into the design

1. **Required:** keep one atomic `data + proof + head transition + checkpoint` acceptance rule regardless of the transaction envelope. Frame invalidity and mempool admission are separate properties; use the precise verdict in [03](03-frame-transactions-research.md).
2. **Required:** expose an ordinary public transaction route for force requests and recovery. ePBS and FOCIL improve the environment; they are not Etna role authorities and do not remove the need for Etna queue rules.
3. **Required:** bound calldata, blob count, forced work and verification cost per action against final gas semantics. Reserve explicit recovery funding rather than assuming cheaper gas after an upgrade.
4. **Required:** never derive role assignment or recovery deadlines from CL proposer lookahead, SLOTNUM, validator epochs, or an assumed 12-second constant. URC remains removed.
5. **Open launch checks:** pin exact accepted Frame and host-fork specifications; verify multiple EL implementations and builder/mempool support; calibrate verifier gas, throughput and proof latency; authenticate the launch network's blob schedule. These are compatibility/evidence gates, not requests for discretionary DAO operation.

## Anchor-removal dependency clarification — 2026-10-01

The updated design uses the **standard EIP-4788 and EIP-2935 execution behavior and canonical contracts on L2**. They are prerequisites to migration: verify canonical runtime code and builder/importer/prover parity before enabling the nonzero origin-hash header rule. If absent or inconsistent, this revision cannot launch. This adds no dependence on L1 CL lookahead, slots, future fork inclusion, or the L1 beacon-roots oracle. The L2 field contains an authenticated L1 **execution** hash; it is not an SSZ beacon root. The original roadmap statuses above retain their September30 research date. Current EIP text and issue corrections were checked on October1 in the [anchor-removal source audit](notes/anchor-removal-source-audit.md). See [checkpoint design](design/checkpoints.html) for finite ring semantics and permanent permissionless pins.
