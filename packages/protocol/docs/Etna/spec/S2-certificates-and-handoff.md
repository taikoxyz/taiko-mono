## 2. Terms, views and the committee

### S2-R01. Terms, views and the opening object

**[assumed: proposed rule]** A term has at most `V_MAX + 1` views, 0 to `V_MAX`. View `v` is open from the moment a node holds its opening object: for `v = 0` the closing view change of term `t − 1` (for the first Etna block, none: C7 H3), for `v ≥ 1` the view change that closed `v − 1`, for a view reopened by REPLACE or RESUME that view change. All blocks under one opening object carry one `vcHash`, its logical id (S2-R10); between consecutive signed headers `vcHash` changes exactly at the first block under a new opening object, and every change of `(termId, view)` is such a block (C7 V2 checks it; S2 defines the objects). The opening object travels with the first block of the view together with one valid witness; later headers carry its logical id. Which witness travels is not part of the chain: a node that holds another valid witness of the same logical id holds the same opening object (D16, B-S2-01). A term whose walk finds fewer than K_MIN_CERT seats is in **no-committee mode**: no attestations, certificates or view changes exist, takeover is only at term end, landings are certificate-free under C2's sentinel rules, and the API exposes the sequenced and landed levels only. The semantic values of `extraData`'s bytes (C1-R03, C7 H1 and H3): `termId = t`; `view = v` for holder views, 254 for a forced batch; `kind` 0 NORMAL (sequencer block), 1 FORCED (view 254), 2 GENESIS_CHILD (the first Etna block), 3 FI (a forced-inclusion block, C3). The permitted `(view, kind)` pairs are C7 H3's to check; the pairs the certificate page states are `(v ≤ V_MAX, NORMAL)`, `(v ≤ V_MAX, FI)`, `(254, FORCED)` and `(0, GENESIS_CHILD)` for the first Etna block. **[assumed: accepted owner interface]** C7 H3/C8-R06 own the complete kind/view table: kind FI is voluntary request execution in a holder view or sentinel255; kind FORCED belongs only to hatch view254. There is no ordinary per-block FI duty under D39/D41. S2 imports that table without creating another definition. **Adversary schedule:** a leader presents one block under another view's header, or opens a view with an object that closes nothing; both fail the `vcHash` chain rule and H1's equality. Source: certificate page §1 and §3; issue #22147.

### S2-R02. The attester committee and its quorum

**[assumed: proposed rule]** `committee(t)` is up to `K = 32` seats drawn by S1's committee walk (sequencing page §8), which excludes the primary holder by owner and the backups by seat only; S1 owns every selection rule, the pin and the walk's gas. S2 states the quorum: with `m` the number of non-empty slots, `Q(m) = ⌊2m/3⌋ + 1`. A drawn seat whose owner is suspended or lapsed at `termStart(t)` is an empty slot that stays in the walk's output, so `m` shrinks and `Q(m)` scales; with a share `s` of the domain suspended the expected `m` is about `32(1 − s)` (round 6, R6-C1). `m < K_MIN_CERT = 8` is no-committee mode. Every security statement here is written for `m = 32` and scales as `2Q(m) − m`, the provably slashable double-signers behind a locked block: 12 at 32, 6 at 16, 4 at 8; nodes publish `m` beside every level (S2-R18). Keys: the sequencer key is secp256k1 and code-less at registration (S3 rule S8); the attester key is BLS12-381 with a proof of possession (A-BLS); both bind to one owner, the slashable identity (S1); every read of a key for term `t` takes the key valid at `termStart(t)` (S1, round 6, R6S-4). **Adversary schedule:** owners park seats in an open-ended suspension before a seed is fixed to shrink the committees they are drawn into; parked seats sit in no committee, so parking lowers the parkers' own chances; inside A-T11 `m < K_MIN_CERT` has probability about `3·10⁻⁷` per term (§6); seats parked longer than STALE_EXIT can be exited by anyone (S1 `exitStale`). Source: certificate page §1; limitation L16.

## 3. Objects: the signed header, attestations, certificates, locks and votes

### S2-R03. The signed header and the identity that binds the envelope
**[assumed: proposed rule]** The leader of `(t, v)` signs, per block,

```text
PH = { version, chainId, termId, view, vcHash, height, timestamp, parentHash, parentPhHash,
       blockHash, txListHash, carriedCertHash, anchorNumber }
phHash = keccak256(abi.encode(DOMAIN_PH, chainId, PH fields in declaration order))
seqSig = ECDSA(keccak(DOMAIN_BLOCK ‖ chainId ‖ phHash))
```

`phHash` follows C8's hashing convention like every other signed object of this section (§1 notation): keccak256 over one canonical `abi.encode` with the domain tag `DOMAIN_PH` and the chain id first, then the thirteen PH fields in the order declared above (W22 adds `parentPhHash`). This resolves what the candidate page left open: the certificate page §1 writes `phHash = keccak(SSZ(PH))`, which is superseded and recorded as an erratum (§10, open item 2); the arbiter decided it on J-2 of J's review of #22197 (2026-10-01), because C1-R03's identity vector V10 and C2's guest rebuild both consume this encoding and the choice blocked their test vectors. One reference `phHash` vector (S2-V14) is the shared fixture those two consumers read.

`blockHash` is the execution block hash the leader's engine produced, committing to the whole L2 header including `parentBeaconBlockRoot` (C1-R01) and `extraData` (C1-R03). `txListHash` is the keccak of the exact compressed transaction bytes, so C2's blob encoding is a pure function of the certified chain. `carriedCertHash` is the hash of the full carried certificate, every field of S2-R05's `C = { t, v, vcHash, redraw, height, phHash, bitmap, aggSig }`, `bitmap` and `aggSig` included, under C8's convention (keccak256 over one canonical `abi.encode`, a domain tag and the chain id first; C8 names the tag and fixes its byte value and the byte layout, and nothing else), so C2-R04's V3 clause (the carried certificate's preimage hashes to `PH.carriedCertHash`) and S2-R21's S6 carried-certificate form read one preimage (C7 V3 bounds its height to `{n − 1, n − 2}`); or, for the first two blocks of a view, the opening object's logical id `vcHash` itself (S2-R10; D16: the opening object's witness is outside every identity, so the first two headers of a view do not change with the witness that happens to travel). A certificate's own `bitmap` and `aggSig` are a different matter from that opening witness: they enter `phHash` only through the carried certificate, so a leader that signs two headers at one height carrying two witnesses of one certificate signs two `phHash` values under one `vcHash`, which is S1 (S2-R21), and an honest leader signs one header per height. `anchorNumber` is the anchored L1 block's number (C7 V5). The seat is carried nowhere: `(termId, view)` and S1's holder list imply it.

The identity rule, answering candidate B's P-B-C1-01 (C1-R03 and C1's identity vector): the object signed, attested, certified, locked and landed is `phHash`, never `blockHash`. Two envelopes for one execution hash with different `vcHash` or `carriedCertHash` have different `phHash`, hence distinct attestation, certificate and lock identities, and two signed headers at one `(t, v, vcHash, height)` with different `phHash` are S1 evidence (S2-R21). Produced hash equals signed hash by three checks: (i) a node submits the received payload unchanged, with the envelope's `parentBeaconBlockRoot`, through `engine_newPayload`, never a rebuild, and requires VALID and an engine hash equal to `PH.blockHash`; (ii) attesters sign `phHash` only after (i); (iii) C2's guest recomputes `blockHash` from blob data, rebuilds PH from the blob record's `headerCore` and the block header, checks `extraData` against PH, the block's kind and BASEFEE_SHARING_PCTG (C7 H1), checks that the witnessed L1 header at `PH.anchorNumber` hashes to `parentBeaconBlockRoot`, and verifies `ecrecover(seqSig) == leader(t, v)` as a public input. `vcHash` (the logical id) is a `headerCore` field of the blob record (C2-R02); the opening witness and carried certificate travel in the blob record’s object entries rather than the execution block. The logical vcHash excludes its witness; carriedCertHash binds the full certificate, including bitmap and aggSig. **Adversary schedule:** one execution hash under two envelopes, or an envelope omitted by a prover: the omitted one is an irreproducible signed header, unlandable, and the pair is S1; rebuilding from attributes without a hash comparison (the pre-Etna failure) is excluded by (i). Source: certificate page §1 and §2; issue #22147.

**[proven: identity, conditional on A-C7 and A-V7]** PH binds the anchor hash through `blockHash` and its number through `anchorNumber`; `vcHash` and `carriedCertHash` are PH fields, so `phHash` separates envelopes sharing `blockHash`; the guest's rebuild and `ecrecover` make the landed PH equal the gossiped PH or the range unlandable. `abi.encode` of fixed-width typed fields is injective, so two PH values with any differing field have different preimages and, modulo keccak collisions, different `phHash`. Not proven here: that `headerCore` is injective over PH's fields (C2, §10), which the encoding decision leaves as the open residual it was.

**[assumed: W22 authenticated parent identity]** `parentPhHash` commits to the exact parent envelope, independently of `parentHash`, which commits to the execution parent. For a later holder block it equals the S2-R03 hash of the held parent PH; at view entry it equals the opening's authenticated `lockPhHash`; for GENESIS_CHILD it equals C4's sealed `genesisLockHash`; a child of a certificate-free landed parent uses that authenticated LastLanded `phHash`. No PH body is fabricated for a synthetic boundary. C7 verifies the equality to the actually accepted parent envelope and checks that a carried certificate names the exact ancestor PH on this parentPhHash chain at its carried height; C2's guest reconstructs every parent link, including across range splits, and binds the same field in `headerCore`. This changes the PH encoding and all hashes/signatures over it; C1/C2/C7/C8 adoption and re-generated exact fixtures are required before this proposal can establish the bound. The execution header and execution hash are unchanged. A caller-supplied ancestor PH or sequencer signature without this hash linkage is never ancestry evidence.

### S2-R04. Attestations and the signing policy

**[assumed: proposed rule]** Attester `i` of `committee(t)` at redraw count `n` signs

```text
A_i = BLS(sk_i, keccak(DOMAIN_ATTEST ‖ chainId ‖ t ‖ v ‖ vcHash ‖ redraw ‖ height ‖ phHash))
```

The struct carries `vcHash` explicitly so every L1 rule can read the opening object without a header preimage, and `redraw: u8` (round 4, R4-C1; round 5, R5-C4). `i` attests block `b` at height `h` iff C7's V1 to V6, V8, V9 and V10 pass, R06's certificate-lock/attested-tip ancestry gate passes (including its redraw-only backfill case), `i` holds no class-H or class-F closing vote for this opening under any signer term or redraw count, `i` has signed no timeout for `(t, v)` under this `vcHash` (the opening generation of `b`; a timeout signed under an earlier opening of the same `(t, v)`, closed by REPLACE or RESUME, does not suppress attestation under the new one, and that earlier timeout stays valid evidence for the S3 conditions keyed by the old `vcHash`: D16, B-S2-04, "a signer of the RESUME timeout cannot attest its first reopened block" otherwise), and `PH.timestamp ≥ receivedAt − STALE_MAX` and `PH.timestamp ≤ now + CLOCK_SKEW`, `receivedAt` being when this node first received the block. The lower bound is measured at receipt, not at signing (round 5 fix pass): a block published on time stays attestable later, which lets a redrawn committee certify a held leader's blocks, while a late or private one never becomes attestable to the others. Policy gates signing only; clocks never enter validity. One attestation per `(t, v, vcHash, redraw, height)` per key; a key in both draws may attest a held block again under the new count only through R06's normal or redraw-backfill gate; a new member may use the same backfill gate for timely received held ancestors. Attestations gossip on their own topic and anyone aggregates; dedup, the gossip key and the slashing-protection record all key on `(t, v, vcHash, redraw, height)`. Before signing, authenticate and ingest the carried certificate under R06 and persist the new attested tip and attestation atomically; a crash must not erase either. A held timeout certificate does not imply the key sent a timeout: the explicit stored-H/F-vote bar is independent and is persisted before that vote is signed. Attesting over `phHash` rather than `blockHash` is load-bearing: it commits to `carriedCertHash`, which makes the lock lie (S3b) objective. **Adversary schedule:** a leader publishes more than STALE_MAX after the timestamp, or privately, and later asks a redrawn committee to certify: nobody who received late attests; a future-stamped block is refused by the upper bound. Source: certificate page §1 and §4; round 5, R5H-1.

### S2-R05. Certificates and the certificate record

**[assumed: proposed rule]** `C(h) = { t, v, vcHash, redraw, height, phHash, bitmap: u32, aggSig }` with `popcount(bitmap) ≥ Q(m)` over the committee of that redraw count, checked against `committeeRoot[t]` through a committee proof carrying the redraw proofs `1..n` (S2-R16). Anyone holding `Q` attestations builds it. Two certificates over one header are ordinary and never an offence; two over different headers at one `(t, v, vcHash, redraw, height)` are the existing S3a form; R21 additionally defines the W22 cross-height branch form. Anyone may call `recordCertificate(C, committeeProof)` on L1: the inbox verifies the certificate against the committee of its redraw count (one aggregate verification, A-BLS, plus S1's walk when the term is not yet pinned, since the call pins the term first if needed), refuses a certificate not above the stored height before verifying it, keeps the highest `(height, phHash)` per `(t, v, vcHash)` beside the recorded view changes and emits `CertificateRecorded`. The key's `vcHash` is the logical id (S2-R10): the certificate's own `bitmap` and `aggSig` are its witness, verified and then irrelevant to the key, and the call hashes no opening witness (D16). The record bounds the lock of any FALLBACK for that view (S2-R14 (iv)). **Adversary schedule:** a blocking minority withholds TERM_END so that no view change of `committee(t)` forms, then a later committee's FALLBACK would close the view below its certified blocks; the record needs no quorum, so the minority cannot deny it (round 6, R6S-3). Source: certificate page §1 and §5 (iv); interfaces page §1.

### S2-R06. The lock

**[assumed: W22 persistent signing state]** Keep the certificate lock `lock_i = (height, phHash)` and its authenticated PH chain. Raise it only to a certificate/eligible landed pair whose chain extends that exact lock; equal height requires equal identity. A higher certificate on another branch is retained as conflicting evidence and never replaces this lock merely because its height is greater. Ingest a header's carried certificate before attesting it. Opening transitions inherit the certificate lock subject to the existing R14/R15 rules; only R15's authenticated mature recovery transition can reset it; R15 also preserves a compatible higher certificate lock. Records, redraws, restarts, elapsed time and a competing certificate are not resets.

For each key and opening `X=(t,v,vcHash)`, also persist `attestedTip_i[X]`, the highest PH that key has attested under X at any redraw count. The **ancestry signing gate** admits either (a) a PH strictly above and descending from the certificate lock which strictly extends the tip through R03 parent links, or is the identical tip re-signed under a new redraw count; with no tip only the certificate-lock condition is needed; or (b) at redraw count greater than zero, a timely held PH in X comparable by authenticated ancestry with both the certificate lock and the tip (if a tip exists). In case (b), equality or being an ancestor is permitted; comparison with a synthetic boundary uses only a proved extension from that boundary, never a fabricated PH body. This redraw-only backfill exception changes only these two ancestry/height gates: every other R04 check, including original timely receipt, C7 validity, one signature per height/count, no timeout, no H/F vote and generation retirement, remains. It applies to new members as well as overlapping members. Persist a new tip only when the signed PH extends the old one, or initialize an absent tip; an ancestor signature never lowers it or the certificate lock. Same-count duplicates only rebroadcast their stored signature. A redraw never clears this tip. A certificate may extend the certificate lock while conflicting with an uncertified attested tip: it may raise the certificate lock, but it does not erase the tip or permit an attestation on the conflicting branch. A redraw backfill of their authenticated common ancestor may still pass the two-chain gate; it changes neither retained chain. This permits a closing on the certified branch without signing a conflicting block.

A closing vote need only extend the certificate lock, not the highest uncertified attested tip. Thus a low TERM_END at an ancestor of a partial tip, or a closing on a certified branch conflicting with an uncertified tip, can still hand off when R09 permits. A new logical opening has its own empty tip; its inherited certificate lock still applies. R15's eligible mature reset retires signing in displaced generations: only their required RESUME messages remain permitted, never their old H/F votes or attestations. Persist this retirement and all signing state before broadcast; R09's lost-record rule applies. Existing signatures remain evidence in their original scope.

**[proven: honest-history invariant, conditional on these policies]** A key's attested PHs in one opening form one ancestry chain across all its redraw counts. Its certificate locks form one ancestry chain until R15’s mature recovery transition selects its authenticated recovery target (or retains a compatible higher lock). Every carried certificate it attests over is an ancestor of that certificate lock at signing. A later H/F vote extends that lock; an earlier H/F vote prevents any later old-opening attestation by R04. These facts, rather than height monotonicity alone, underlie R21's order-independent branch evidence. A malicious leader can strand partial signers on an uncertified fork until a new opening; no progress bound is claimed for an equivocating leader, and the leader's conflicting headers remain S1 evidence. R20's separately accepted G5/G5-F residuals are not repaired here.

### S2-R07. Timeouts and the TIMEOUT trigger
**[assumed: proposed rule]** `TO_i = BLS(sk_i, keccak(DOMAIN_TIMEOUT ‖ chainId ‖ t ‖ v ‖ vcHash ‖ redraw ‖ kind ‖ toLockHeight ‖ toLockPhHash))`, `kind ∈ {TIMEOUT, TERM_END, FALLBACK, REPLACE, RESUME}`: a statement that view `(t, v, vcHash)` should close, carrying the signer's lock (D29, replacing round 3's lock-free timeout). For TIMEOUT, TERM_END and FALLBACK, `(toLockHeight, toLockPhHash)` is `lock_i` at signing, or `lastLanded` under S2-R09 clause (2); for REPLACE and RESUME it is `lastLanded`. A key whose lock rises re-signs its timeout with the new lock. A timeout is never evidence. A node counts a timeout toward a timeout certificate only once it holds `C(toLock)`, or the clause (2) L1 record, and the blocks up to `toLock`; it ignores a timeout it cannot verify within PENDING_TTL. A timeout certificate `TC(X, kind, r)` is `Q(m)` counted timeouts of one kind for the closing context `X = (t, v, closes)`: by `committee(t)` at redraw count `r`, or for FALLBACK by one signing committee. `TCmax` is the highest `(toLockHeight, toLockPhHash)` among them. No key votes on a TC whose top height carries two `phHash` values. The leader liveness signal (round 4, R4H-4; bounded in round 5, R5H-1 and R5-C1; window origin from round 6, R6H-4; this section is normative): an attester signs kind TIMEOUT for `(t, v, vcHash, redraw)`, only while `v < V_MAX` and before S2-R08's TIMEOUT cutoff, iff both hold:

1. for TIMEOUT seconds by its clock no new certificate of the view has appeared, counted in a window that starts when it first holds the view's opening object (for view 0 at `termStart(t)` once it holds the closing view change of `t − 1`; for `v ≥ 1`, or a view reopened by REPLACE or RESUME, when it holds the opening view change; for a member of a redrawn committee when the redraw forms) and restarts on each new certificate of the view;
2. it holds no block of the view, under the current redraw count, that it attested and that is still uncertified.

The window origin covers a leader that publishes nothing (timed out TIMEOUT after its view opened) and forbids timing out a view before holding its opening object. Condition 2 reads the attester's own attestations, not arrival: gossip deduplicates a re-sent header, so an arrival-based restart could not tell a holding leader from a dead one; since S2-R04 excludes bodiless, unavailable, misanchored, oversized and misstamped blocks, "attested" means "served and valid". `TO_i` is rebroadcast every TO_REBROADCAST while the condition holds; a timeout re-signed at a higher lock replaces it (S2-R22). **Adversary schedule** (certificate page §1 (a) to (d)): (a) a leader held by an abstaining minority has its blocks at `lock + 1` and `lock + 2` attested by the honest attesters and left uncertified, so nobody honest times it out; the term is blank, never transferred; (b) a dead leader leaves every block certified or unattested, is timed out by every honest attester and pays MISS (S3); (c) a leader that withholds payloads, gossips bodiless, invalid or future-stamped headers, or squats, gets nothing attested, is timed out and bled, and cannot re-sign `lock + 1` with other content (S1); (d) in a real partition, or when a block is attested by only part of the committee (published at the edge of the staleness window or of C3's anchor-lag policy) and the leader then stops, the attesters that attested do not time out, fewer than `Q` sign, and the view runs to TERM_END without certificates or MISS; with `c` colluding members withholding timeouts the split needs only `m − Q(m) + 1 − c` honest attesters to have attested (11 − c at `m = 32`), so at `c ≥ 11` a colluding leader keeps a view producing nothing, gaining a term without serving at the cost of the term's revenue. Source: certificate page §1, §5, §10.

**[assumed: CS-R3-01 consumer; open: review]** A RESUME timeout, as well as its subsequent vote, requires R15's eligible recovery transition. Its unsigned local recovery observation is authenticated by that rule; no new field enters the timeout preimage. A young or noncanonical landing cannot trigger a RESUME timeout: R04 treats a persisted timeout as a signing bar even before a lock reset or vote. REPLACE formation keeps its existing R07/R09 gates and does not require its own future landing.

**[assumed: W22 FALLBACK timeout routing; C8 envelope adoption open]** A FALLBACK timeout travels with an unsigned `signerTerm` routing selector and a supplied or referenced authenticated proof of membership in `committee(signerTerm)`. R10's signer-term bound and redraw-zero rule apply to this routing choice. Count its signature only within `TC(X, FALLBACK, signerTerm, 0)` for that one committee, once per selected position; never pool positions from different committees. The R07 timeout preimage above is unchanged and does not sign the selector. A key belonging to two later committees may therefore have the same signed timeout authenticated separately in both; this is not equivocation or evidence that the key signed a different selector. The subsequent lock vote signs `signerTerm` under R09. R22 owns the corresponding routing and deduplication rules. **Adversary schedule:** a peer relabels an honest timeout to a committee excluding that key (membership fails), or combines partial counts from two committees (neither TC reaches its own Q); no timeout is slashing evidence and no selector substitution frames the key.

### S2-R08. The term-end signal

**[assumed: proposed rule]** Subject to S2-R09 and S2-R16 (D29): a key holding a class-H vote for `X = (t, v, vcHash)`, or a REDRAW above the current count, casts no TERM_END vote and keeps rebroadcasting the vote it holds. Otherwise an attester of `committee(t)` signs kind TERM_END for `(t, v, vcHash)` at the earlier of: (a) the moment it holds a certificate `C(h)` under the same opening object for a block whose timestamp is `termEnd(t) − 1`, the term's last possible block under C7 V4, and that block extends its lock (`h ≥ lock_i`, on the lock's chain); (b) `now ≥ termEnd(t) + END_GRACE` by its clock, whether or not any block of the view arrived. Under (a) the key signs a TERM_END timeout carrying `h` and votes `h` directly, without a timeout certificate. Under (b) it signs a TERM_END timeout carrying its lock and votes at `TCmax` of a TERM_END timeout certificate under S2-R09; a key that has timed out under (b) but not yet voted still votes `h` if (a) fires first. No attestation cutoff is added. **TIMEOUT cutoff (D29, R-E):** no key signs a TIMEOUT timeout for term `t` once its clock reads `termEnd(t) + END_GRACE − TIMEOUT`. The cutoff narrows the split of one committee's votes between the two class-H kinds near term end but does not close it; a split that leaves neither kind at `Q` ends in a FALLBACK (S2-R14; §10, open item 14). (a) is clock-free. The condition is on the key's own state because heights on two branches of one view are not tied to timestamps: an equivocating leader (S1) can build a sparse branch whose block stamped `termEnd − 1` sits below the lock of keys that attested a denser branch, so its certificate fires (a) only for keys whose lock it extends; on another branch, or under another `vcHash` of a REPLACE-forked object, it fires nothing and those keys time out at their own lock under (b) and vote at the certificate's `TCmax`. FALLBACK is signed by a later committee (S2-R14); REPLACE and RESUME after a reset (S2-R15). **Adversary schedule:** a leader that publishes the block stamped `termEnd − 1` on its one chain hands over on the grid (S2-R12); otherwise (b) starts closure at END_GRACE; R12’s four-grid-position example additionally requires a responsive quorum and one shared closing candidate. Split votes and hidden higher certificates follow R14/R20 instead. Source: certificate page §1, §5, §10; after the #22188 review and its fix pass.

**[proven: (a) is never a lock lie]** Every header the key attested under the opening object, at any redraw count (the comparison S3b makes), carried a certificate at or below `lock_i` (R04/R06 ingest the carried certificate before signing and retain its authenticated ancestry in the certificate lock; redraw backfill never lowers that lock), and `lock_i ≤ h` when (a) fires, so no certificate carried by an attested header lies above or outside the ancestry of its vote at `h`; the attested header itself may be higher than `h`; a certificate on another branch does not extend the lock and fires nothing, so the vote under (b) is at `TCmax ≥ lock_i` (S2-R09's precondition), at least every certificate it attested over. Source: certificate page §16; D29.

### S2-R09. Lock votes

**[assumed: proposed rule]** `LV_i = BLS(sk_i, keccak(DOMAIN_LOCK ‖ chainId ‖ t ‖ v ‖ vcHash ‖ redraw ‖ kind ‖ signerTerm ‖ lockHeight ‖ lockPhHash ‖ l1RefNumber ‖ l1RefHash ‖ prevLock))`: the vote for where the view's batch ends. `signerTerm` follows `kind` (D29, R-D) and is `t` for every kind except FALLBACK, where it is the signing committee's term; the view change's logical id excludes it (S2-R10), so one witness still verifies against one common message. `l1Ref` is zero except for REPLACE and RESUME, where it is an L1 block `(number, hash)` inside the signed bytes (round 3, S1), compared on L1 by `blockhash` or EIP-2935; S2 is normative for it (round 5, R5S-3), through this rule's authenticated reference definition below. The old forced ring is removed by D41.

**The closing vote (D29; amends D16 and D21).** A lock vote's closing context is `X = (t, v, closes)`. Class H is {TIMEOUT, TERM_END}, signed by `committee(t)`; class F is {FALLBACK}, signed by a later committee (§1's class table). In class H a key signs at most one closing vote per `(X, class)`; in class F at most one per `(X, signerTerm)` (D29, R-D). The vote's signed fields (`kind`, `signerTerm`, `lockHeight`, `lockPhHash`, `l1Ref`, and `prevLock = 0`) are fixed at the first signing. Every later signing for that `(X, class)`, or for class F that `(X, signerTerm)`, either re-sends the identical bytes or, under a higher redraw count, re-signs them unchanged except `redraw`. A key never re-votes, upward or downward. A key holding a class-H vote for `X` signs no other class-H vote for `X` and keeps rebroadcasting the one it holds. Before signing, the key persists the full signed vote and the R04 stop-attesting flag for X in its slashing-protection record; the flag applies to every later attestation under X, independent of kind, signerTerm or redraw. It broadcasts only after persistence, and persists its REDRAW signatures with its closing votes (S2-R16). **Lost record (D29, R-I):** a key that cannot prove its record intact for an opening opened at or before the loss signs nothing under it: no attestation, timeout, closing vote or REDRAW. The key votes at `lock* = TCmax` of a timeout certificate it holds (S2-R07), only if `lock*` extends the exact certificate lock of R06 (equal height means equal `phHash`) and the precondition "What a key votes on" below holds; under S2-R08 (a) it votes `h` without a timeout certificate. B's W11 trace (B-D21-01: an upward re-vote of the old view's closing, recorded first, displacing a locked successor with nothing slashable) has no honest counterpart: the second closing is S3c′ evidence against every key in both witnesses (S2-R21, S2-V21).

**The REPLACE and RESUME vote chain (D16, B-S2-02; scope amended by D21; kept by D29).** REPLACE and RESUME keep D21's vote chain and its S3c (a) to (c); they are in neither class. Their **vote scope** is `(t, v, vcHash, kind)`, `vcHash` the logical id of the view the vote closes; it spans redraw counts (D21, S2-9). `prevLock: u64` is the `lockHeight` of the key's own previous lock vote in the same scope at a lower `lockHeight`, and exactly 0 for the key's first vote in that scope; it starts at 0 again at every new term, view, opening generation or kind, and does not restart at a redraw. For these kinds the key stores the whole signed tuple `(lockHeight, lockPhHash, l1Ref, prevLock)` per `(scope, lockHeight)` and returns the stored vote on any re-proposal, restart, rebroadcast or new redraw count; only `redraw` may change. It never rebuilds the vote from its current lock, L1 view or predecessor (B's W12 small correction on persistence). Honest votes under one scope are monotone: a key votes again only for a strictly higher lock (a further landing moved `lastLanded`, S2-R15), with `prevLock` equal to its previous height, or re-signs its stored vote unchanged under a new redraw count, and it never signs two votes at one `lockHeight` that differ in any other signed field (for REPLACE, a second `l1Ref` at the same lock; §10, open item 13). S3c (a) to (c) is defined once, in S2-R21, each clause order-free.

**[assumed: cross-family signing, J-1]** A class-H or class-F vote does not consume a REPLACE/RESUME vote scope, and a REPLACE/RESUME vote does not consume a class-H or class-F scope. The same key may sign both when each rule’s own lock, reset and reference predicates hold. After a landed reset, S2-R15 still forbids old-generation H/F votes; this permission does not override that prohibition. No mixed H/REPLACE, H/RESUME, F/REPLACE or F/RESUME pair is S3c or S3c′ evidence. A recovery record alone changes no lock. **Adversary schedule:** record REPLACE before H, or H before REPLACE, at the same landed lock; both remain eligible in their separate families under S2-R13, and only an actual landing chooses the branch. A false recovery reference remains S3d evidence.

**The staleness rule for an L1 reference (stated here once).** An L1 block a vote relies on, the `l1Ref` of a REPLACE or RESUME vote or the block read for `lastLanded` under clause (2) below, must lie in the key's own verified L1 view, be canonical there, and be at least ANCHOR_MIN_AGE old; S2-R15 cites this rule. **[assumed: CS-R3-01 S2-local reading; open: A/J review and joint C5/C7 alignment]** For a reference N and the canonical head H used for this check, age means `timestamp(H) − timestamp(N) >= ANCHOR_MIN_AGE`, with N an ancestor of H (or H itself only if the configured age permits). Canonicality, timestamps and the authenticated historical read come from that one coherent view; elapsed receipt time, local wall-clock time and a block number alone cannot establish age. Recheck that view before committing a dependent signing transition. This reuses the existing seconds parameter, not a slot or epoch count. It is this S2 consumer’s proposed operational reading; C7 V5 uses the PH timestamp for its distinct anchor check. [C5-R05](C5-l1-dependencies-and-frames.md#c5-r05-epbs-empty-slots-and-the-canonical-at-n1-premise-behind-anchor_min_age) and C5 §12/§14 retain the joint depth/rationale and consumer-alignment obligation. This reading neither changes C7 nor equates maturity with Ethereum finality.

**Authenticated reference [assumed: SL-2 proposal; open: A/J review and §12's C2/S3/C5/C8 adoption].** For a signed `l1Ref = (N, hashN)`, the staleness rule above applies and `N > activationL1Number`; C4's existing restart/reference floors also apply. No REPLACE or RESUME vote may use the activation block itself, whose start has no Etna `replaceableFrom`. A1 at N means exactly `timestamp(N) > replaceableFrom(start(N))`: the timestamp comes from N's canonical L1 header authenticated against `hashN`, and `replaceableFrom` is C2-R08's function evaluated at the start of N, before **all** transactions or changes to its inputs in N. This includes landings, announcements, REPLACE/RESUME records spending the deferral, DAO grace changes in either direction, and restart or upgrade changes, including changed bytecode constants. The node obtains that value from the authenticated parent state and the implementation/parameter profile in force at N's start, or from authenticated replay recovering the same state and profile; the RPC post-state at N, a later live value, and the signing or evidence block's timestamp are not substitutes. REPLACE requires this A1 predicate. RESUME names the block containing the replacement, dead-mode or hatch landing resumed from and uses C3-R09's alternative: this A1 predicate **or** the authenticated `hatchTip[N]` at the **end** of N matching the signed `(lockHeight, lockPhHash)`. The start-of-block A1 read does not move the hatch-tip read before N's landings. A1 describes the reference block's start state, not whether the voted lock's own fresh grace has elapsed; the existing live record and landing gates still govern, including their separate RESUME/hatch rules. A reference to restart block K therefore reads the pre-restart A1 value without bypassing those live gates. The key signs only after authenticating a passing route and satisfying the other existing vote gates; if the needed history or profile is unavailable, it waits or refuses the vote, without inventing a value or treating unavailable data as a false predicate or an accusation. The no-framing comparison with S3d is conditional on S3 reading these same authenticated inputs through the proposed C2-R08 history and complete writer coverage; it makes no new claim about evidence-time canonicality, noncanonical-opening inertness, or stale/future-reference accountability (the separate open slashing-01/slashing-03 integration).

**Adversary schedule (SL-2):** a grace decrease in N leaves `replaceableFrom(start(N)) > timestamp(N) > replaceableFrom(end(N))`. A malicious proposer supplies N's standard RPC post-state and requests a REPLACE vote. A client accepting that value would sign a vote the proposed S3d historical read can slash; a key following this rule authenticates the start-of-N state/profile and refuses the vote (S2-V47(a)).

**What a key votes on.** For TIMEOUT, TERM_END under S2-R08 (b) and FALLBACK, `lock*` is `TCmax` of a timeout certificate `j` holds (S2-R07; D29). Attester `j` votes on `lock*` iff `lock* ≥ lock_j` on the authenticated PH ancestry of R06 (equal height requires equal `phHash`) and it holds and has executed every block up to `lock*` (range-fetching if needed), and either (1) it holds `C(lock*)`, authenticated by R05 under the certificate's own signed `(t, v, vcHash, redraw)`, with `(height, phHash)` equal to `lock*` and `(t, v, vcHash)` equal to the lock PH's authenticated context, or (2) `lock* = lastLanded` on L1 and `j` has verified that L1 landing record (D16, B-S2-03): the record exists in the inbox, its end `(height, phHash)` equals `lock*`'s, and the L1 block carrying it meets the staleness rule above. For a RESUME vote that L1 block is the one `l1Ref` names; for every other kind it is the latest L1 block of `j`'s view at that age, read for the inbox's `lastLanded`. (2) covers the lock after a forced batch or replacement (R15 selects its mature recovery target, which a sentinel-view range or forced batch can leave uncertified; if R15 retains a compatible higher lock, that higher lock still needs its certificate under clause (1)), the lock a later view inherits from such a RESUME (an empty view after it closes at the same uncertified lock), and the migration parent for the first view of the first term (C4's initial `lastLanded`, the genesis child's parent, with the `phHash` C4 assigns to that record), which no certificate ever covers. Every other `lock*` needs (1). **[assumed: CS-3 clarification proposed to A, cycle-2 round 2]** Clause (1) permits a certificate from an earlier term or opening inherited by the closing view. R05 resolves its committee from `C.t` and its authenticated redraw history, never from the FALLBACK's closed term, its `signerTerm`, or a submitter-selected root. The PH context above is authenticated by R03/R06's exact PH identity and ancestry, not by a free header supplied alongside the certificate. S2-V46 covers the empty-view case; C2-R05 L5 must adopt the same certificate rule. This changes neither clause (2)'s local L1-record/age checks nor R14's transaction-pre-state exception. **Adversary schedule:** a submitter substitutes a convenient committee or a same-height sibling certificate (the signed certificate context, R05 membership/redraw witness and exact PH identity reject it); an unverifiable or lower proposed lock gets no signature; a proposer naming `lastLanded` that the attester's L1 view does not show, or shows younger than ANCHOR_MIN_AGE, gets none either; for TIMEOUT, TERM_END and FALLBACK any second closing vote of one key for one `(X, class)` (class F: one `(X, signerTerm)`) that differs in more than `redraw` is S3c′ (a), at any two heights; for REPLACE and RESUME two conflicting locks at one height are S3c (a) and a descending pair is S3c (b) or (c) unless it is consistent with an honest history, the residual argued below. Source: certificate page §1 and §5; round 3, S5; B's W8 verdict on #22197 (2026-10-01), B-S2-02 and B-S2-03; D16.

**[proven: an honest key never meets S3c′, S3e or S3c, in any calldata order]** Classes H and F: an honest key signs one logical vote per `(X, class)`, per `(X, signerTerm)` in class F, so two of its votes for one `X` and class differ at most in `redraw`, which S3c′ ignores; and S2-R16 orders its REDRAW signatures against its class-H closing votes, so it never holds both a REDRAW for count `n` and a class-H vote below `n` for one view (S3e). REPLACE and RESUME: inside one scope an honest key's distinct `lockHeight` values strictly increase in signing order; two of its votes at one height differ in nothing but the redraw count, and each vote's `prevLock` is the highest height it voted in the scope below its own, 0 if none. (a) never fires: two honest votes at one height differ only in the redraw count. (b) never fires: `prevLock` is a height below the vote's own, or 0, and every `lockHeight` is above 0 (**assumed:** the lowest lock any vote names is C4's migration parent, above height 0; S2-V18). (c) never fires: for honest `a`, `b` with `lockHeight_b < lockHeight_a`, `b` was signed first, so `prevLock_a ≥ lockHeight_b`. Nothing depends on which vote a challenger lists first.

**[proven: the REPLACE and RESUME residual, conditional on S2-R15]** Under D21's clauses a truthfully chained descending pair is caught by (b) on the descending vote, a stale `prevLock` by (c), across a redraw included (S2-V16 (7)), and two votes at one height that differ in any field but the redraw count by (a), two REPLACE votes at one lock with two `l1Ref` values included. A pair `a`, `b` of one scope with `lockHeight_b < lockHeight_a` escapes S3c iff each vote's `prevLock` is below its own height and `prevLock_a ∈ [lockHeight_b, lockHeight_a)`, exactly when the pair is consistent with an honest history. Such a pair is two REPLACE or RESUME view changes at two locks, and `recordViewChange` accepts one only at the current `lastLanded` (S2-R15), so a higher one follows a further landing, which is I4's listed landed replacement or forced batch route; the residual voids nothing that route does not. The earlier statement that the first-recorded rule arbitrates two class-H closings of one scope at two locks without loss to a locked block was B-D21-01's target and is withdrawn (D29).

### S2-R10. The view change and its formation

**[assumed: proposed rule]**

```text
VC(t, v) = { t, v, closes: vcHash, kind, lockHeight, lockPhHash, l1Ref,                         // logical fields
             signerTerm, redraw, bitmap: u32, aggSig,                                          // witness
             prevLocks: u64[popcount(bitmap)] }                     // witness, REPLACE and RESUME only (D29)
```

**The logical id (D16, B-S2-01; field list amended by D21, S2-7).** `vcHash` hashes the logical fields only, under C8's convention with the new tag `DOMAIN_VC`, and excludes every witness field: `signerTerm`, `redraw`, `bitmap`, `aggSig` and `prevLocks`. The identity of an opening object is logical: the witness is carried beside the object, and any **valid** witness proves the same object. A witness is valid iff all of the following hold (D21; (v) to (viii) added by D29): (i) `signerTerm = t` for every kind except FALLBACK; (ii) `popcount(bitmap) ≥ Q(m)` over `committee(signerTerm)` at redraw count `redraw`; (iii) that committee is checked against `committeeRoot[signerTerm]` through S2-R16's committee proof; (iv) `aggSig` verifies as the aggregate of the lock votes `LV_i` of the set bits over the object's logical fields with the witness's `signerTerm` and `redraw`, and with `prevLock = 0` for TIMEOUT, TERM_END and FALLBACK (one common message, 2 pairings, §6) or each key's own `prevLock` from `prevLocks` for REPLACE and RESUME (distinct messages, §6); (v) for TIMEOUT, TERM_END, REPLACE and RESUME, the redraw proofs `1..redraw` are REDRAW aggregates for `(t, v, closes, n)` (S2-R16); (vi) a FALLBACK witness has `redraw = 0`; (vii) for FALLBACK, `t < signerTerm ≤ t + 2,048` (FB_SIGNER_HORIZON, ROLE_HORIZON / TERM, a constant, §6; R-J), `committee(signerTerm)` being read from the pinned or walked `committeeRoot`; C2-R10's horizon governs landability at L4, never validity; (viii) every key is the key valid at `termStart(signerTerm)` (S1). V2, `recordViewChange`, S2-R14 (i) and L4 each apply (i) to (viii). Since D29 the witness of TIMEOUT, TERM_END and FALLBACK is exactly D21's four fields, which closes the `prevLocks` half of open item 12 for those kinds; REPLACE and RESUME keep `prevLocks`. B's finding was that a hash over `bitmap` and `aggSig` made "two valid quorum subsets for the same ordinary closing lock yield different opening hashes", so that "a malicious next holder or quorum can create two LOCKED conflicting descendants under two witnesses, land one, and no S1, S3a or S3b evidence matches; zero forfeiture". Under the logical id two witnesses `Q` and `Q + 1` of one closing lock open one generation: the descendants under both carry one `vcHash`, two of them at one height are S1 (two signed PHs under one `vcHash`, S2-R21), their attestations S3a, and the locks S3b compares lie in one generation. A new generation is created only by an opening whose logical fields differ, which every kind does: TIMEOUT opens `(t, v + 1)` with `closes` equal to the closed view's id, so `v` and `closes` differ from the object it closes; TERM_END opens `(t + 1, 0)` and differs in `t`, `kind` and `closes`; FALLBACK differs from a view change of `committee(t)` at the same lock in `kind` only, so the two are two generations (the L5 race, S2-R14, I4; D21), while two FALLBACKs at one lock signed by two later committees are one generation, as are two TIMEOUTs at one lock under redraw counts 0 and 1, since `signerTerm` and `redraw` are witness fields (D21, S2-7; S2-V20); REPLACE reopens `(t, v)` and differs from the original opening in `closes` (the original id), `kind` and the non-zero `l1Ref`; RESUME differs likewise in `kind` and in `l1Ref`, the L1 block of the landing resumed from, so two RESUMEs after two landings are two generations. Two view changes with equal logical fields and different witnesses are, by construction, one. The sentinel objects of S2-R01 have no witness and are logical already. **Formation (D29, replacing round 3's re-vote formation).** A node holding `TC(X, kind, r)` proposes `VC` at `TCmax`, attaching `C(TCmax)` or, when `TCmax = lastLanded`, the clause (2) L1 record (S2-R09; B's W12 small correction). Each key votes once (S2-R09). There is no re-proposal and no re-vote: a higher lock reaches the timeout certificate as a re-signed timeout (S2-R07) before any key votes, never as a second vote. Under S2-R08 (a) the keys vote `h` without a timeout certificate. REPLACE and RESUME form at `lastLanded` with `prevLocks` as before. Clocks decide only whether to sign; the decision to switch is the existence of the signed object, so two honest nodes holding it switch identically and a node lacking it learns it from the next view's first block (V2). **Adversary schedule:** a stale proposer cannot propose below `TCmax`, which every voter recomputes from the certificate it holds; a colluding quorum that forms a second closing of one `X` and class at another lock or under another redraw count signs two votes per key in both witnesses, S3c′ (b) or S3e (S2-R21); a key that has voted cannot be moved to a higher lock, which is the liveness cost D29 accepts (a TERM_END or TIMEOUT split that leaves no kind at `Q` ends in a FALLBACK, S2-R08). Source: certificate page §1 and §5; D29.

## 4. View changes, the handoff, fallback, replacement and redraw

### S2-R11. Kinds and what each opens

**[assumed: proposed rule]** After `VC(t, v, TIMEOUT)`, `leader(t, v + 1)` starts at `lock* + 1` carrying the view change; after TERM_END or a FALLBACK closing `(t, v)`, `leader(t + 1, 0)` likewise; after REPLACE or RESUME, the same holder reopens the same view number under the new opening object (S2-R15). A view without certificates yields a view change at the previous lock (an empty batch). After `V_MAX` view changes the term idles to its end. The first two blocks of a view carry the view change instead of a certificate (V3). Blocks of one holder under different opening objects, that is under different logical ids (an original tail and a REPLACE fork), are never equivocation; blocks of one holder under two witnesses of one logical id, including witnesses of two signer terms or two redraw counts, are blocks under one opening object, and two of them at one height are S1 (S2-R10, S2-R17; D16, D21). **Adversary schedule:** a backup starting above the lock or on another branch fails V2; a holder that re-aggregates the closing votes into a second witness to open "another" view gets the same `vcHash` and the same slashing domain. Source: certificate page §3 and §5; D16.

### S2-R12. The pipelined handoff and the four-slot bound

**[assumed: proposed rule]** Leader policy: a leader issues the block stamped `termEnd(t) − 1` even when empty, so its term closes by S2-R08 (a). Happy path: that block is published at `termEnd − 1`; `C(h)` forms by about `termEnd − 0.3 s`; TERM_END timeouts and lock votes at `h` gossip at once and the view change forms at about `termEnd`; `leader(t + 1, 0)` publishes `PH(h + 1)` stamped `termEnd` about 0.5 s later, carrying it (2.5 s inside S2-R04's receipt bound; V2 admits the timestamp since `termStart(t + 1) = termEnd(t)`), and continues on the 1-s grid: no slot is empty. Clock fallback: when the leader does not issue that block, or `C(h)` does not form, (b) applies: TERM_END timeouts at `termEnd + END_GRACE`, a timeout certificate one hop later and the closing votes at its `TCmax` one hop after that, so the view change forms at about `+ END_GRACE + 0.6 s` or later (at least two TC hops, §6); the first block of `t + 1` is stamped `termEnd + END_GRACE + 1` and published once its leader holds the view change, so at most `END_GRACE + 2 = 4` slots (`termEnd − 1` to `termEnd + 2`) are empty, once per term, while the view change forms within about 1 s of `termEnd + END_GRACE`. The grid is a rewarded duty, never a validity rule (V4). **Adversary schedule:** with only the last block withheld, no conflicting partial signatures/hidden higher certificate, and a responsive quorum on one TC, the stated trace has those four empty grid positions; publishing it later than `termEnd − 1 + STALE_MAX` gets it attested by nobody, and (b) closes the term as well. Source: certificate page §5 and §7; after the #22188 review.

### S2-R13. Recording duties and operational record selection

**[assumed: duties retained from D29]** Anyone may record a valid object. (1) The next leader records every committee(t) opening it carries. (2) Each signer records its closing within TO_REBROADCAST of formation unless that context already has an operational class-H record. (3) At termEnd + END_GRACE + 0.5 s, absent a TERM_END closing, the last-view leader and lowest set-bit signer of the highest certificate they hold submit that certificate; other holders submit a higher certificate after one further L1 block without such a record. (4) A first-block attester records its opening and all intervening closings after lastVCHash if one further L1 block passes without the applicable operational record. A nonfinal F does not discharge (2) or (4). These are service duties, not objective non-receipt offences. A signer may not possess the aggregate; “lowest bit” is a sender only if it holds the certificate. Every honest holder remains a fallback sender. No broadcast-at-labelling duty or receipt-time validity gate is added.

**[assumed: record schema]** Context X = (t, v, closes) has C8-R07’s three existing slots: 0 for class H (TIMEOUT and TERM_END share it), 1 for F, 2 for recovery (REPLACE and RESUME share it). Verify the witness before inserting; retain the logical id, kind, lock fields, record block/time and existing dead bit. The verified witness remains in transaction calldata; no stored witness reader exists. Same logical id, any valid witness, is an idempotent no-op and never restarts age. An occupied operational slot rejects another logical id in that family. A retired entry may be overwritten; past calldata/events remain evidence. Class F additionally obeys R14’s permanent death/finality rules.

**[assumed: one operational predicate]** At a transaction’s pre-state head L = lastLanded, a record r is **head-compatible** iff r.lockHeight > L.height or (r.lockHeight == L.height and r.lockPhHash == L.phHash). An H record is **operational** iff it exists, is not dead and is head-compatible. This predicate does not prove ancestry at a greater height: the landing guest and L4 chain must do that. An H below L, or conflicting at L’s height, supplies neither a cap, first-record priority, F supersession nor full backing. It is historical evidence only. R14 defines F eligibility; recovery is operational only at the exact L pair and while its R15 conditions hold. All record selectors, recording-duty checks and the fully-backed test use these definitions, not “any row exists”.

**[assumed: family selection]** H and F compete only to close the original opening, under R14. Recovery competes only with recovery for its replacement/resumption fork. A landing that consumes a closing must match its family’s selected logical id if one exists; an unrecorded original H cannot evade an operational H, and an unrecorded recovery cannot evade the operational recovery. Recovery does not suppress H/F, cap the original or make F final/nonfinal. H/F does not suppress a valid C2-R09 recovery landing. Both original and eligible recovery remain landable until one actually lands. S2-R15 specifies the original cap and recovery reset. This clarifies C2-R05 L4 and C2-R09 and needs their explicit adoption (§12); a global first-record selector would violate this rule.

**[proven: late-H trace, conditional on the proposed selectors]** Land original block 41 while LastLanded was 40, then record H(lock40). The record is historical; it cannot cap the current original path at 40. The slot would accept a valid later H(lock41), but its availability does not follow: R20’s coalition can exhaust every honest key’s H vote at 40, leaving no honest H41 or redraw. At equal height, only exact phHash equality is compatible; matching execution blockHash alone is insufficient. No execution parentHash is read from LastLanded. Reverse the order: operational H40 exists before the landing, so R15’s cap rejects original 41 before any head update. These orders produce distinct results by design (G5), never a retroactive rollback.

**[assumed: timing/cost limit]** The former +26.5 s/+6.5 s universal inclusion claims are replaced by the explicit block schedule in V23b. At least one honest funded holder must send; A-T1 bounds inclusion after submission, not how fast a private certificate becomes known. Gas and sender-race duplication are unmeasured (§6).

### S2-R14. FALLBACK: later-committee closure and finality

**[assumed: formation]** A later committee(t′), t < t′ <= t + FB_SIGNER_HORIZON, forms one class-F vote per (X, signerTerm) at TCmax under R07/R09. Its local clock and latest L1 timestamp must reach termEnd(t) + END_GRACE + VC_FALLBACK × (t′ − t). It holds no class-H closing for X, sees no operational H, holds/sees no eligible F at or above its lock, and proposes no lock below the recorded certificate. This is signing policy, not a receipt-dependent V2 predicate.

**[assumed: gates, evaluated before effects]**

- (i) **Admission:** a new F verifies its witness and signer-term time gate, is head-compatible under R13, has no operational H, and is at or above the recorded certificate for X. It does not overwrite a surviving different F. Presenting the same logical F with another witness changes neither its record time nor its lifecycle.
- (ii) **Consumption:** L4 consumes only a final F. **[assumed: A-W20-05 error binding]** After the preceding identity/witness checks, evaluate finality on transaction pre-state first. For a non-final F, a lock below the current recorded certificate fails `FallbackBelowCertificate`; otherwise the non-finality fails `FallbackNotFinal`. For a final F, skip that latest-certificate-floor check entirely, so neither error rejects final F40 after a later C41 (V30). Its lock is authenticated by R09(1)'s exact-lock certificate, verified on L1 under R05 using that certificate's signed context and redraw history, or by equality with the actual transaction-pre-state lastLanded.(height, phHash). **[assumed: CS-3 clarification; open: A/C2 adoption]** C2-R05 L5 must use R09(1), not require a certificate of the FALLBACK's closed-term committee: an empty view can inherit an earlier committee's certified lock (S2-V46). An in-memory cursor advanced through a block or empty closing is not lastLanded for that exception. Neither a latest higher certificate nor a different witness retroactively rejects a final F. The proposed cap of R15 still applies.
- (iii) **Death before finality:** a head-compatible H recorded or actually consumed before F finality, a higher certificate recorded before finality, or a successful landing that bypasses F within R15’s explicit candidate-context set before finality permanently sets that F’s existing dead bit. The bit is never cleared for that record/id. H becoming historical later does not resurrect the killed F. Only a strictly higher-lock F may replace a dead/noncompatible nonfinal slot entry after all admission gates. The slot’s stored lockHeight never decreases, including after death; a final F cannot be overwritten. A repeated dead F is rejected, not re-aged. The successful-landing hook is a required C2 adoption in §12; a recording-only implementation is incorrect.
- (iv) **Certificate-floor order:** first evaluate finality using the pre-mutation record. If F is final, recordCertificate may update the highest certificate but does not kill F, and L4 does not reapply the latest-certificate floor to it. Otherwise a higher recorded certificate kills F before the certificate record is overwritten. Thus no historical-certificate oracle or additional finality bit is needed.
- (v) **Finality:** an existing, non-dead F, whose prefinal invalidations under R14(iii)/R15 are represented by dead, is final from the first L1 block B with B.number >= recordedAtBlock + FB_CONTEST_BLOCKS and B.timestamp >= recordedAtTimestamp + FB_CONTEST, using the parent’s surviving record. In the eligibility block every mutator evaluates this before its own effects. A competing H/F then fails `ClosingSlotFinal`, and a higher-certificate record cannot kill F. The prior-block invalidations of (iii) persist in dead; (iv) prevents any same-block invalidation after the boundary. Authorized recovery after finality does not revoke finality; the historical F supplies no cap to the new recovery opening. Once actually consumed, F remains historical evidence of the selected opening; it supplies no cap to unrelated later openings. V23/V23b/V30/V31 specify the orderings. L1 reorgs revert these records with the chain.

**[assumed: node policy unchanged, recovery claim narrowed]** An honest node holding a higher certificate of the closed opening refuses to build or attest on an off-lock F branch even when F is final. Finality does not lower its local lock. R06/R15 permit reset only on a landed recovery, not a timeout, record, or passage to another view. It submits available certificate evidence and serves data; if the conflict persists it seeks a certificate-free C3 hatch or S1 dead-mode landing under their gates. A certified REPLACE is not a guaranteed exit for keys whose higher incompatible lock causes R04 to reject its first block. No TIMEOUT-plus-one-view-change or 600-second end-to-end recovery bound is claimed. V33 gives the countertrace and conditional recovery procedure. This is an inherited liveness residual, not evidence that silence is slashable.

**[proven: final-F versus higher-C trace]** With no prior kill, F40 reaches both time gates. Record C41 afterwards, then consume F40: the stored highest certificate is 41, F.dead remains false, and the certificate-floor check is skipped for that final F. If C41 is recorded before either gate matures, F.dead becomes true and F40 can never consume. The existence of C41 alone says nothing about whether its data reached the F voters. S3b applies only to a key’s authenticated carried-certificate/lock-vote pair (R21).

### S2-R16. Committee redraw
**[assumed: proposed rule]** An attester that attested a block of `(t, v)` but has seen no certificate for TIMEOUT seconds may sign `RD_i = BLS(sk_i, keccak(DOMAIN_REDRAW ‖ chainId ‖ t ‖ v ‖ vcHash ‖ n))`, `n ∈ {1, 2}`. With `⌊m/2⌋ + 1` such signatures (17 of 32) the committee of `(t, v)` is redrawn as the first `K` seats of S1's walk `keccak(seed ‖ 0x03 ‖ t ‖ n ‖ m)` with the committee walk's exclusions, for the same leader, view and opening object; at most REDRAW_MAX redraws per view. Its members attest the view's valid blocks they received on time (S2-R04's receipt bound), the leader continues once a certificate forms, and their TIMEOUT window starts when the redraw forms. Attestations, certificates and lock votes of the redrawn committee carry `n`, and the landing verifies certificates against the committee of the recorded redraw count (the committee proof carries `n` and the redraw proofs `1..n`). In a view change `n` is a witness field, not a logical one (S2-R10; D21), so view changes of counts 0 and 1 at one lock are one opening object, and a key in both draws holds one closing vote per `(X, class)` across counts, re-signed unchanged except `redraw` (S2-R09; D29). A redraw proof for count `n` is `{ n, bitmap, aggSig }`: the aggregate of `⌊m/2⌋ + 1` REDRAW signatures for `(t, v, vcHash, n)` by the committee at count `n − 1`, so REDRAW `n = 1` is signed by `committee(t)` as drawn and REDRAW `n = 2` by the committee of count 1 (interfaces page §4, `RedrawProof`). A REDRAW message has one statement per `(t, v, vcHash, n)` and no conflicting form of its own, changes no holder and applies no penalty; its only evidence is S3e, which pairs it with a class-H closing vote of the same view below `n` (S2-R21; D29); it names no block (a vote naming one let a cartel majority name a block the leader never signed; fix pass). It raises the blanking threshold from 11 to 16 of 32 and needs a blocking minority in every redraw. **Ordering against closing votes (D29; third sentence as corrected by R-M):** a key that has signed a class-H closing vote for `(t, v, O)` signs no REDRAW for `(t, v, O)`. A key that has signed `REDRAW(t, v, O, n)` signs no class-H closing vote for `(t, v, O)` at a redraw count below `n`. A key holding a redraw proof for `n` casts no class-H closing vote for `(t, v, O)` at a count below `n`; a FALLBACK's redraw field is unaffected. REDRAW signatures are persisted before broadcast. The first two sentences make S3e objective; the third is limited to class H because S2-R10 (vi) fixes every FALLBACK at `redraw = 0`, and the uncorrected sentence ("no closing vote below `n`") barred every FALLBACK after any redraw, which let one colluding leader wedge the handoff until `replaceableFrom` (D29, attack 3 on repaired G; S2-V28). Leftover REDRAW signers (D29, R-L): honest keys that signed a REDRAW that never forms cannot vote class H at the current count, so with `c` colluders abstaining, `m − Q(m) + 1 − c` such signers (1 at `c = 10`, `m = 32`) leave no class-H closing at `Q` and the view ends in a FALLBACK (I3; §10, open item 15). **Adversary schedule:** a cartel majority redraws a committee that has already certified (the precondition is unverifiable on L1), buying a re-roll toward `Q` and, if it finds `Q`, a lock reset whose only slashable keys sit in both committees; at one third of the seats this path has probability about `6·10⁻⁷` per view (the page's figure, not reproduced, §10) against `4·10⁻⁵` for the slashable path (reproduced, §6), cheaper only in provable cost (L2, L16). Source: certificate page §5 and §8; round 4, R4-C1.

**[assumed: proposed rule]** Fork choice reads no clock: the canonical tip is the valid block with the highest `(t, v, height)` whose ancestors within its view are all certified except at most `CERT_LAG_MAX + 1` leaf blocks. ## 7. Argument and adversary coverage

**[proven: wholly unattested private blocks are unlandable, conditional on A-V7]** A block the committee never received has no certificate (V6 needs its execution); one block can be built on it, carrying the previous certificate, but cannot be certified, so nothing carries a certificate above it: this wholly unattested private state is at most 2 blocks; TIMEOUT initiates recovery under R07’s quorum conditions, and it can neither end a landing nor lie under one (S2-R15).

**[proven conditional: W22 locked bound inside one opening/redraw; open until owner adoption]** Let target n be locked by certificate C_b on block b carrying valid C_n. Use C_b's Q signers, not C_n's signers. Suppose a competing ordinary branch in X becomes the selected chain. If it ends in a certificate C_d of the same redraw and displaces n, b and d are incomparable PH endpoints, even when their heights differ. The two signer sets intersect in at least `2Q(m_b)−m_b`, and R21's S3a branch descent is evidence against each common key. If it instead closes through an H vote of that redraw, intersect C_b with the Q closing votes: a lock below n gives R21's S3b height predicate; a lock at or above n on an incompatible branch gives its ancestry predicate. The challenger supplies the public full C_b and class-H VC aggregate witnesses under R21's new set-bit form. Their authenticated intersection proves the offences without extracting any private individual signature; the comparison uses carried C_n, not the higher C_b.height. The closing's actual accepted ancestry is authenticated by the C2 guest/opening projection, and the locking node already checks C_n on b's ancestry. A closing that extends n does not displace n. Both endpoint-quorum membership and the fixed-draw premise are necessary; an intermediate carried certificate may have another redraw without changing this endpoint intersection. At m=32 this is 12 positions, at16 six, at8 four. Owner deduplication, already-slashed positions, evidence availability and S3's windows still constrain recoverable backing. No fixed same-draw bound is assigned to a competing endpoint/closing from another draw, FALLBACK signer committee or recovery route: those remain R18/I4's separately published cases. R21 and V38/V39/V44/V45 prove honest histories cannot create the new evidence, in either signing order. This is a conditional protocol argument, not a claim that D78 already supplied the objective witness or that its gas/codec is closed. **[proven: the second-closing bound, D29]** A block locked under a view whose opening closed an unlanded ancestor view `X` is also displaced by a second closing of `X` of the same class at another lock (B-D21-01). Two such closings within one redraw count are S3c′ (b) against at least `2Q(m) − m` keys; at different counts, S3e against at least `⌊m/2⌋ + 1 + Q(m) − m` keys of the lower count's draw, its REDRAW bitmap and closing bitmap being two subsets of one committee in which no honest key is in both (S2-R16). Neither bound is relied on before the block is fully backed: the second closing can be recorded first, or a FALLBACK can become final, before any honest record (S2-R18; D29, attacks 0 and 1 on repaired G), so the 2-s "locked" label claims only the bound inside its own opening.

**[proven: W1’s applicable boundary]** If no quorum certificate for the private payload exists, the tail cannot satisfy C2’s end-certificate/guest checks. If the original closing becomes operational before the competing original landing, R15’s cap prevents that landing once adopted by C2.
