## 2. Terms, views and the committee

### S2-R01. Terms, views and the opening object

**[assumed: proposed rule]** A term has at most `V_MAX + 1` views, 0 to `V_MAX`. View `v` is open from the moment a node holds its opening object: for `v = 0` the closing view change of term `t − 1` (for the first Etna block, none: C7 H3), for `v ≥ 1` the view change that closed `v − 1`, for a view reopened by REPLACE or RESUME that view change. All blocks under one opening object carry one `vcHash`, its logical id (S2-R10); between consecutive signed headers `vcHash` changes exactly at the first block under a new opening object, and every change of `(termId, view)` is such a block (C7 V2 checks it; S2 defines the objects). The opening object travels with the first block of the view together with one valid witness; later headers carry its logical id. Which witness travels is not part of the chain: a node that holds another valid witness of the same logical id holds the same opening object (D16, B-S2-01). A term whose walk finds fewer than K_MIN_CERT seats is in **no-committee mode**: no attestations, certificates or view changes exist, takeover is only at term end, landings are certificate-free under C2's sentinel rules, and the API exposes the sequenced and landed levels only. The semantic values of `extraData`'s bytes (C1-R03, C7 H1 and H3): `termId = t`; `view = v` for holder views, 254 for a forced batch; `kind` 0 NORMAL (sequencer block), 1 FORCED (view 254), 2 GENESIS_CHILD (the first Etna block), 3 FI (a forced-inclusion block, C3). The permitted `(view, kind)` pairs are C7 H3's to check; the pairs the certificate page states are `(v ≤ V_MAX, NORMAL)`, `(v ≤ V_MAX, FI)`, `(254, FORCED)` and `(0, GENESIS_CHILD)` for the first Etna block. For a range landed under sentinel 255 (open-empty, dead, no-committee) the page defines the opening object and the certificate-free landing but states neither the `view` byte's value nor a `kind` for its blocks; that gap is handed to C7 H3 and listed in §10 (open item 8), not filled here. **Adversary schedule:** a leader presents one block under another view's header, or opens a view with an object that closes nothing; both fail the `vcHash` chain rule and H1's equality. Source: certificate page §1 and §3; issue #22147.

### S2-R02. The attester committee and its quorum

**[assumed: proposed rule]** `committee(t)` is up to `K = 32` seats drawn by S1's committee walk (sequencing page §8), which excludes the primary holder by owner and the backups by seat only; S1 owns every selection rule, the pin and the walk's gas. S2 states the quorum: with `m` the number of non-empty slots, `Q(m) = ⌊2m/3⌋ + 1`. A drawn seat whose owner is suspended or lapsed at `termStart(t)` is an empty slot that stays in the walk's output, so `m` shrinks and `Q(m)` scales; with a share `s` of the domain suspended the expected `m` is about `32(1 − s)` (round 6, R6-C1). `m < K_MIN_CERT = 8` is no-committee mode. Every security statement here is written for `m = 32` and scales as `2Q(m) − m`, the provably slashable double-signers behind a locked block: 12 at 32, 6 at 16, 4 at 8; nodes publish `m` beside every level (S2-R18). Keys: the sequencer key is secp256k1 and code-less at registration (S3 rule S8); the attester key is BLS12-381 with a proof of possession (A-BLS); both bind to one owner, the slashable identity (S1); every read of a key for term `t` takes the key valid at `termStart(t)` (S1, round 6, R6S-4). **Adversary schedule:** owners park seats in an open-ended suspension before a seed is fixed to shrink the committees they are drawn into; parked seats sit in no committee, so parking lowers the parkers' own chances; inside A-T11 `m < K_MIN_CERT` has probability about `3·10⁻⁷` per term (§6); seats parked longer than STALE_EXIT can be exited by anyone (S1 `exitStale`). Source: certificate page §1; limitation L16.

## 3. Objects: the signed header, attestations, certificates, locks and votes

### S2-R03. The signed header and the identity that binds the envelope
**[assumed: proposed rule]** The leader of `(t, v)` signs, per block,

```text
PH = { version, chainId, termId, view, vcHash, height, timestamp, parentHash,
       blockHash, txListHash, carriedCertHash, anchorNumber }
phHash = keccak256(abi.encode(DOMAIN_PH, chainId, PH fields in declaration order))
seqSig = ECDSA(keccak(DOMAIN_BLOCK ‖ chainId ‖ phHash))
```

`phHash` follows C8's hashing convention like every other signed object of this section (§1 notation): keccak256 over one canonical `abi.encode` with the domain tag `DOMAIN_PH` and the chain id first, then the twelve PH fields in the order declared above. This resolves what the candidate page left open: the certificate page §1 writes `phHash = keccak(SSZ(PH))`, which is superseded and recorded as an erratum (§10, open item 2); the arbiter decided it on J-2 of J's review of #22197 (2026-10-01), because C1-R03's identity vector V10 and C2's guest rebuild both consume this encoding and the choice blocked their test vectors. One reference `phHash` vector (S2-V14) is the shared fixture those two consumers read.

`blockHash` is the execution block hash the leader's engine produced, committing to the whole L2 header including `parentBeaconBlockRoot` (C1-R01) and `extraData` (C1-R03). `txListHash` is the keccak of the exact compressed transaction bytes, so C2's blob encoding is a pure function of the certified chain. `carriedCertHash` is the hash of the carried certificate (C7 V3 bounds its height to `{n − 1, n − 2}`), or, for the first two blocks of a view, the opening object's logical id `vcHash` itself (S2-R10; D16: the witness is outside every identity, so the first two headers of a view do not change with the witness that happens to travel). `anchorNumber` is the anchored L1 block's number (C7 V5). The seat is carried nowhere: `(termId, view)` and S1's holder list imply it.

The identity rule, answering candidate B's P-B-C1-01 (C1-R03 and C1's identity vector): the object signed, attested, certified, locked and landed is `phHash`, never `blockHash`. Two envelopes for one execution hash with different `vcHash` or `carriedCertHash` have different `phHash`, hence distinct attestation, certificate and lock identities, and two signed headers at one `(t, v, vcHash, height)` with different `phHash` are S1 evidence (S2-R21). Produced hash equals signed hash by three checks: (i) a node submits the received payload unchanged, with the envelope's `parentBeaconBlockRoot`, through `engine_newPayload`, never a rebuild, and requires VALID and an engine hash equal to `PH.blockHash`; (ii) attesters sign `phHash` only after (i); (iii) C2's guest recomputes `blockHash` from blob data, rebuilds PH from the blob record's `headerCore` and the block header, checks `extraData` against PH, the block's kind and BASEFEE_SHARING_PCTG (C7 H1), checks that the witnessed L1 header at `PH.anchorNumber` hashes to `parentBeaconBlockRoot`, and verifies `ecrecover(seqSig) == leader(t, v)` as a public input. `vcHash` (the logical id) is a `headerCore` field of the blob record (C2-R02); the opening object's witness and the carried certificate travel in the blob record's view-change and certificate entries, not in the L2 block and not inside any hash the chain carries. **Adversary schedule:** one execution hash under two envelopes, or an envelope omitted by a prover: the omitted one is an irreproducible signed header, unlandable, and the pair is S1; rebuilding from attributes without a hash comparison (the pre-Etna failure) is excluded by (i). Source: certificate page §1 and §2; issue #22147.

**[proven: identity, conditional on A-C7 and A-V7]** PH binds the anchor hash through `blockHash` and its number through `anchorNumber`; `vcHash` and `carriedCertHash` are PH fields, so `phHash` separates envelopes sharing `blockHash`; the guest's rebuild and `ecrecover` make the landed PH equal the gossiped PH or the range unlandable. `abi.encode` of fixed-width typed fields is injective, so two PH values with any differing field have different preimages and, modulo keccak collisions, different `phHash`. Not proven here: that `headerCore` is injective over PH's fields (C2, §10), which the encoding decision leaves as the open residual it was.

### S2-R04. Attestations and the signing policy

**[assumed: proposed rule]** Attester `i` of `committee(t)` at redraw count `n` signs

```text
A_i = BLS(sk_i, keccak(DOMAIN_ATTEST ‖ chainId ‖ t ‖ v ‖ vcHash ‖ redraw ‖ height ‖ phHash))
```

The struct carries `vcHash` explicitly so every L1 rule can read the opening object without a header preimage, and `redraw: u8` (round 4, R4-C1; round 5, R5-C4). `i` attests block `b` at height `h` iff C7's V1 to V6, V8, V9 and V10 pass, `h > lock_i` on the lock's chain, `i` has signed no timeout for `(t, v)` under this `vcHash` (the opening generation of `b`; a timeout signed under an earlier opening of the same `(t, v)`, closed by REPLACE or RESUME, does not suppress attestation under the new one, and that earlier timeout stays valid evidence for the S3 conditions keyed by the old `vcHash`: D16, B-S2-04, "a signer of the RESUME timeout cannot attest its first reopened block" otherwise), and `PH.timestamp ≥ receivedAt − STALE_MAX` and `PH.timestamp ≤ now + CLOCK_SKEW`, `receivedAt` being when this node first received the block. The lower bound is measured at receipt, not at signing (round 5 fix pass): a block published on time stays attestable later, which lets a redrawn committee certify a held leader's blocks, while a late or private one never becomes attestable to the others. Policy gates signing only; clocks never enter validity. One attestation per `(t, v, vcHash, redraw, height)` per key; a key in both draws attests a held block again under the new count. Attestations gossip on their own topic and anyone aggregates; dedup, the gossip key and the slashing-protection record all key on `(t, v, vcHash, redraw, height)`. Attesting over `phHash` rather than `blockHash` is load-bearing: it commits to `carriedCertHash`, which makes the lock lie (S3b) objective. **Adversary schedule:** a leader publishes more than STALE_MAX after the timestamp, or privately, and later asks a redrawn committee to certify: nobody who received late attests; a future-stamped block is refused by the upper bound. Source: certificate page §1 and §4; round 5, R5H-1.

### S2-R05. Certificates and the certificate record

**[assumed: proposed rule]** `C(h) = { t, v, vcHash, redraw, height, phHash, bitmap: u32, aggSig }` with `popcount(bitmap) ≥ Q(m)` over the committee of that redraw count, checked against `committeeRoot[t]` through a committee proof carrying the redraw proofs `1..n` (S2-R16). Anyone holding `Q` attestations builds it. Two certificates over one header are ordinary and never an offence; two over different headers at one `(t, v, vcHash, redraw, height)` are S3a. Anyone may call `recordCertificate(C, committeeProof)` on L1: the inbox verifies the certificate against the committee of its redraw count (one aggregate verification, A-BLS, plus S1's walk when the term is not yet pinned, since the call pins the term first if needed), refuses a certificate not above the stored height before verifying it, keeps the highest `(height, phHash)` per `(t, v, vcHash)` beside the recorded view changes and emits `CertificateRecorded`. The key's `vcHash` is the logical id (S2-R10): the certificate's own `bitmap` and `aggSig` are its witness, verified and then irrelevant to the key, and the call hashes no opening witness (D16). The record bounds the lock of any FALLBACK for that view (S2-R14 (iv)). **Adversary schedule:** a blocking minority withholds TERM_END so that no view change of `committee(t)` forms, then a later committee's FALLBACK would close the view below its certified blocks; the record needs no quorum, so the minority cannot deny it (round 6, R6S-3). Source: certificate page §1 and §5 (iv); interfaces page §1.

### S2-R06. The lock

**[assumed: proposed rule]** Each attester keeps `lock_i`: the highest certificate it holds together with the block chain under it, or the highest height landed on L1 in its own view, whichever is higher (certificate page §1; the second clause is absent from the glossary, §10). It is monotone within a term and reset only by observing a landed replacement or forced batch (S2-R15), never by a record. **Adversary schedule:** attesting below the lock or on another branch is refused by S2-R04, so nothing an honest key attests lies below a certificate it holds (S3b relies on it). Source: certificate page §1 and §6.

### S2-R07. Timeouts and the TIMEOUT trigger
**[assumed: proposed rule]** `TO_i = BLS(sk_i, keccak(DOMAIN_TIMEOUT ‖ chainId ‖ t ‖ v ‖ vcHash ‖ redraw ‖ kind))`, `kind ∈ {TIMEOUT, TERM_END, FALLBACK, REPLACE, RESUME}`: a statement that view `(t, v, vcHash)` should close, carrying no lock (round 3). The leader liveness signal (round 4, R4H-4; bounded in round 5, R5H-1 and R5-C1; window origin from round 6, R6H-4; this section is normative): an attester signs kind TIMEOUT for `(t, v, vcHash, redraw)`, only while `v < V_MAX`, iff both hold:

1. for TIMEOUT seconds by its clock no new certificate of the view has appeared, counted in a window that starts when it first holds the view's opening object (for view 0 at `termStart(t)` once it holds the closing view change of `t − 1`; for `v ≥ 1`, or a view reopened by REPLACE or RESUME, when it holds the opening view change; for a member of a redrawn committee when the redraw forms) and restarts on each new certificate of the view;
2. it holds no block of the view, under the current redraw count, that it attested and that is still uncertified.

The window origin covers a leader that publishes nothing (timed out TIMEOUT after its view opened) and forbids timing out a view before holding its opening object. Condition 2 reads the attester's own attestations, not arrival: gossip deduplicates a re-sent header, so an arrival-based restart could not tell a holding leader from a dead one; since S2-R04 excludes bodiless, unavailable, misanchored, FI-skipping, oversized and misstamped blocks, "attested" means "served and valid". `TO_i` is rebroadcast every TO_REBROADCAST while the condition holds. **Adversary schedule** (certificate page §1 (a) to (d)): (a) a leader held by an abstaining minority has its blocks at `lock + 1` and `lock + 2` attested by the honest attesters and left uncertified, so nobody honest times it out; the term is blank, never transferred; (b) a dead leader leaves every block certified or unattested, is timed out by every honest attester and pays MISS (S3); (c) a leader that withholds payloads, gossips bodiless, invalid or future-stamped headers, or squats, gets nothing attested, is timed out and bled, and cannot re-sign `lock + 1` with other content (S1); (d) in a real partition, or when a block is attested by only part of the committee (published at the edge of the staleness window or of C3's anchor-lag policy) and the leader then stops, the attesters that attested do not time out, fewer than `Q` sign, and the view runs to TERM_END without certificates or MISS; with `c` colluding members withholding timeouts the split needs only `m − Q(m) + 1 − c` honest attesters to have attested (11 − c at `m = 32`), so at `c ≥ 11` a colluding leader keeps a view producing nothing, gaining a term without serving and one term's delay of due forced-inclusion entries (V8 binds only certified and landed blocks) at the cost of the term's revenue. Source: certificate page §1, §5, §10.

### S2-R08. The term-end signal

**[assumed: proposed rule]** An attester of `committee(t)` signs kind TERM_END for `(t, v, vcHash)`, then its lock vote, at the earlier of: (a) the moment it holds a certificate `C(h)` under the same opening object for a block whose timestamp is `termEnd(t) − 1`, the term's last possible block under C7 V4, and that block extends its lock (`h ≥ lock_i`, on the lock's chain); (b) `now ≥ termEnd(t) + END_GRACE` by its clock, whether or not any block of the view arrived. The lock vote is at `max(lock_i, h)`, which is `h` whenever (a) fires. (a) is clock-free. The condition is on the key's own state because heights on two branches of one view are not tied to timestamps: an equivocating leader (S1) can build a sparse branch whose block stamped `termEnd − 1` sits below the lock of keys that attested a denser branch, so its certificate fires (a) only for keys whose lock it extends; on another branch, or under another `vcHash` of a REPLACE-forked object, it fires nothing and those keys vote their own lock under (b). FALLBACK is signed by a later committee (S2-R14); REPLACE and RESUME after a reset (S2-R15). **Adversary schedule:** a leader that publishes the block stamped `termEnd − 1` on its one chain hands over on the grid (S2-R12); otherwise (b) closes the term at most `END_GRACE + 2` slots later on the attesters' clocks, whatever the leader withholds. Source: certificate page §1, §5, §10; after the #22188 review and its fix pass.

**[proven: (a) is never a lock lie]** Every header the key attested under the opening object, at any redraw count (the comparison S3b makes), carried a certificate at or below `lock_i` (S2-R04 attests only above the lock; the carried certificate is at most the parent's height, V3), and `lock_i ≤ h` when (a) fires, so no attestation of the key lies above its vote at `h`; a certificate on another branch does not extend the lock and fires nothing, so the vote under (b) is the key's monotone lock, at least every certificate it attested over. Source: certificate page §16.

### S2-R09. Lock votes

**[assumed: proposed rule]** `LV_i = BLS(sk_i, keccak(DOMAIN_LOCK ‖ chainId ‖ t ‖ v ‖ vcHash ‖ redraw ‖ kind ‖ lockHeight ‖ lockPhHash ‖ l1RefNumber ‖ l1RefHash ‖ prevLock))`: the vote for where the view's batch ends. `l1Ref` is zero except for REPLACE and RESUME, where it is an L1 block `(number, hash)` inside the signed bytes (round 3, S1), compared on L1 by `blockhash` or EIP-2935; S2 is normative for it (round 5, R5S-3): for REPLACE, an L1 block at which C2's predicate A1 held, evaluated on the inbox state before that block's landings; for RESUME, the L1 block containing the forced or replacement landing resumed from (A1 held there on the state before that landing, which S3d recomputes against C2's forced ring).

**The vote chain (D16, B-S2-02; scope amended by D21).** The **vote scope** is `(t, v, vcHash, kind)`, `vcHash` the logical id of the view the vote closes; it spans redraw counts (D21, S2-9). `prevLock: u64` is the `lockHeight` of the key's own previous lock vote in the same scope at a lower `lockHeight`, and exactly 0 for the key's first vote in that scope. It is per scope, not per term: it starts at 0 again at every new term, view, opening generation or kind, because an honest key's lock is monotone only inside one scope (a RESET lowers the lock to `lastLanded` and the next votes are of kind RESUME, a new scope). It does not restart at a redraw: the lock of a key in both draws is monotone across the redraw (S2-R06), so a key that re-signs the same `(lockHeight, lockPhHash)` under the new redraw count keeps the same `prevLock`, and that re-sign is not evidence (it differs from the earlier vote only in the redraw count, which S3c (a) ignores). The key keeps its last `(lockHeight, prevLock)` per scope in the same slashing-protection record as its attestations (S2-R04). A re-sending of an identical vote reuses the same signed bytes and is not a new vote. Honest votes under one scope are monotone: a key re-votes only for a strictly higher lock extending its previous one, with `prevLock` equal to that previous height, or re-signs its current vote unchanged under a new redraw count, and it never signs two votes at one `lockHeight` that differ in any other signed field (for REPLACE, a second `l1Ref` at the same lock). S3c is defined once, in S2-R21, by three clauses (a) to (c), each order-free: symmetric in the pair or reading one vote, which answers B's "argument order as evidence frames the honest key".

**The staleness rule for an L1 reference (stated here once).** An L1 block a vote relies on, the `l1Ref` of a REPLACE or RESUME vote or the block read for `lastLanded` under clause (2) below, must lie in the key's own L1 view, be canonical there, and be at least ANCHOR_MIN_AGE old; S2-R15 cites this rule.

**What a key votes on.** Attester `j` votes on a proposed `lock*` iff `lock* ≥ lock_j` and it holds and has executed every block up to `lock*` (range-fetching if needed), and either (1) it holds `C(lock*)`, or (2) `lock* = lastLanded` on L1 and `j` has verified that L1 landing record (D16, B-S2-03): the record exists in the inbox, its end `(height, phHash)` equals `lock*`'s, and the L1 block carrying it meets the staleness rule above. For a RESUME vote that L1 block is the one `l1Ref` names; for every other kind it is the latest L1 block of `j`'s view at that age, read for the inbox's `lastLanded`. (2) covers the lock after a forced batch or replacement (S2-R15 resets the lock to `lastLanded`, which sentinel-view ranges and forced batches leave uncertified), the lock a later view inherits from such a RESUME (an empty view after it closes at the same uncertified lock), and the migration parent for the first view of the first term (C4's initial `lastLanded`, the genesis child's parent, with the `phHash` C4 assigns to that record), which no certificate ever covers. Every other `lock*` needs (1). **Adversary schedule:** an unverifiable or lower proposed lock gets no signature; a proposer naming `lastLanded` that the attester's L1 view does not show, or shows younger than ANCHOR_MIN_AGE, gets none either; two conflicting locks at one height are S3c (a); a descending pair is S3c (b) or (c) unless it is consistent with an honest history, the residual argued under the proof below. Source: certificate page §1 and §5; round 3, S5; B's W8 verdict on #22197 (2026-10-01), B-S2-02 and B-S2-03; D16.

**[proven: an honest vote history is never S3c, in any calldata order]** Inside one scope an honest key's distinct `lockHeight` values strictly increase in signing order (monotonicity above); two of its votes at one height differ in nothing but the redraw count (a re-sign), and each vote's `prevLock` is the highest height it voted in the scope below its own, 0 if none. (a) never fires: two honest votes at one height differ only in the redraw count, which (a) ignores. (b) never fires: `prevLock` is a height below the vote's own, or 0, and every `lockHeight` is above 0 (**assumed:** the lowest lock any vote names is C4's migration parent, a block of the pre-Etna chain above height 0; S2-V18). (c) never fires: take honest votes `a` and `b` with `lockHeight_b < lockHeight_a`; heights rise in signing order, so `b` was signed before `a` first was, hence `lockHeight_b` is among the heights below `lockHeight_a` that the key voted before `a`, and `prevLock_a`, the highest of them, is at least `lockHeight_b`, so `prevLock_a < lockHeight_b` is false. Nothing in (a), (b) or (c) depends on which vote a challenger lists first.

**[proven: what S3c catches, and the residual]** A truthfully chained descending history (a vote at `h₂ < h₁` after a vote at `h₁`, with `prevLock = h₁`) is caught by (b) on the descending vote by itself, as D16 states (the pair also meets (c) when the earlier vote's `prevLock` is below `h₂`); one that keeps a stale `prevLock` below `h₂` is caught by (c), including across a redraw (`(50, redraw 0, prev 0)` then `(40, redraw 1, prev 0)`, S2-V16). Two votes at one height that differ in any field but the redraw count are caught by (a) whatever their `prevLock` values, including two REPLACE votes at one lock with two `l1Ref` values, which would otherwise open two REPLACE generations from one quorum (D21, S2-8). D16's second form, one `prevLock` and two heights, is the case `prevLock_a = prevLock_b < lockHeight_b` of (c) and needs no clause of its own. Residual, stated once and exact (D21, S2-10): a pair `a`, `b` of one scope with `lockHeight_b < lockHeight_a` escapes S3c iff each vote's `prevLock` is below its own height and `prevLock_a ∈ [lockHeight_b, lockHeight_a)`; that is exactly the condition under which the signed fields of the pair are consistent with an honest history (`b`, then a vote at `prevLock_a` if it exceeds `lockHeight_b`, then `a`), so an uncaught pair, whatever order the key really signed it in, has the effect of an honest upward re-vote: two view changes at two locks of one scope, which the first-recorded rule of S2-R13 arbitrates on L1 and which reverts no locked block without `2Q(m) − m` S3b pairs (§7, the locked bound). Every other descending or fabricated pair is caught. S3b, not S3c, carries the locked guarantee.

### S2-R10. The view change and its formation

**[assumed: proposed rule]** 

```text
VC(t, v) = { t, v, closes: vcHash, kind, lockHeight, lockPhHash, l1Ref,                         // logical fields
             signerTerm, redraw, bitmap: u32, aggSig, prevLocks: u64[popcount(bitmap)] }       // witness
vcHash(VC) = keccak256(abi.encode(DOMAIN_VC, chainId, t, v, closes, kind,
                                  lockHeight, lockPhHash, l1RefNumber, l1RefHash))
```

`Q` lock votes over one lock by the committee the witness names, naming the opening object it closes (round 3, S6: a REPLACE or RESUME view change closes the original object and its own logical id opens a new one, so the fork's later view change closes a different object and never collides with it on L1). It closes `(t, v, closes)`, opens the next view, and is the seal of the view's batch, which ends exactly at the lock; no sequencer-signed seal exists.

**The logical id (D16, B-S2-01; field list amended by D21, S2-7).** `vcHash` hashes the logical fields only, under C8's convention with the new tag `DOMAIN_VC`, and excludes every witness field: `signerTerm`, `redraw`, `bitmap`, `aggSig` and `prevLocks`. The identity of an opening object is logical: the witness is carried beside the object, and any **valid** witness proves the same object, where valid means `signerTerm = t` for every kind except FALLBACK and `signerTerm > t` for FALLBACK (S2-R14 bounds it further), `popcount(bitmap) ≥ Q(m)` over `committee(signerTerm)` at redraw count `redraw`, checked against `committeeRoot[signerTerm]` through S2-R16's committee proof, and `aggSig` verifies as the aggregate of the lock votes `LV_i` of the set bits over the object's logical fields, with the witness's `redraw` and each key's own `prevLock` from `prevLocks` (S2-R09; distinct messages, so the verification pairs each key with its message, §6). D21 names the witness `(signerTerm, redraw, bitmap, aggSig)`; `prevLocks` stays in it because the aggregate cannot be verified without each key's `prevLock` (open item 12). B's finding was that a hash over `bitmap` and `aggSig` made "two valid quorum subsets for the same ordinary closing lock yield different opening hashes", so that "a malicious next holder or quorum can create two LOCKED conflicting descendants under two witnesses, land one, and no S1, S3a or S3b evidence matches; zero forfeiture". Under the logical id two witnesses `Q` and `Q + 1` of one closing lock open one generation: the descendants under both carry one `vcHash`, two of them at one height are S1 (two signed PHs under one `vcHash`, S2-R21), their attestations S3a, and the locks S3b compares lie in one generation. A new generation is created only by an opening whose logical fields differ, which every kind does: TIMEOUT opens `(t, v + 1)` with `closes` equal to the closed view's id, so `v` and `closes` differ from the object it closes; TERM_END opens `(t + 1, 0)` and differs in `t`, `kind` and `closes`; FALLBACK differs from a view change of `committee(t)` at the same lock in `kind` only, so the two are two generations (the L5 race, S2-R14, I4; D21), while two FALLBACKs at one lock signed by two later committees are one generation, as are two TIMEOUTs at one lock under redraw counts 0 and 1, since `signerTerm` and `redraw` are witness fields (D21, S2-7; S2-V20); REPLACE reopens `(t, v)` and differs from the original opening in `closes` (the original id), `kind` and the non-zero `l1Ref`; RESUME differs likewise in `kind` and in `l1Ref`, the L1 block of the landing resumed from, so two RESUMEs after two landings are two generations. Two view changes with equal logical fields and different witnesses are, by construction, one. The sentinel objects of S2-R01 have no witness and are logical already. Formation (round 3, S5): any node holding `Q` timeouts of one `(t, v, vcHash, kind)` proposes `VC(t, v, kind, lock*)` with `lock*` the highest certified block it holds, attaching `C(lock*)`; attesters vote under S2-R09; a higher honest lock arrives as a higher vote, the proposer re-proposes at it and every attester may re-vote upward, so with `Q` honest online attesters the view change forms at the honest maximum in one extra round trip without any key signing two conflicting locks. Clocks decide only whether to sign; the decision to switch is the existence of the signed object, so two honest nodes holding it switch identically and a node lacking it learns it from the next view's first block (V2). **Adversary schedule:** a stale proposer is out-voted upward, never equivocated against. Source: certificate page §1 and §5.

## 4. View changes, the handoff, fallback, replacement and redraw

### S2-R11. Kinds and what each opens

**[assumed: proposed rule]** After `VC(t, v, TIMEOUT)`, `leader(t, v + 1)` starts at `lock* + 1` carrying the view change; after TERM_END or a FALLBACK closing `(t, v)`, `leader(t + 1, 0)` likewise; after REPLACE or RESUME, the same holder reopens the same view number under the new opening object (S2-R15). A view without certificates yields a view change at the previous lock (an empty batch). After `V_MAX` view changes the term idles to its end. The first two blocks of a view carry the view change instead of a certificate (V3). Blocks of one holder under different opening objects, that is under different logical ids (an original tail and a REPLACE fork), are never equivocation; blocks of one holder under two witnesses of one logical id, including witnesses of two signer terms or two redraw counts, are blocks under one opening object, and two of them at one height are S1 (S2-R10, S2-R17; D16, D21). **Adversary schedule:** a backup starting above the lock or on another branch fails V2; a holder that re-aggregates the closing votes into a second witness to open "another" view gets the same `vcHash` and the same slashing domain. Source: certificate page §3 and §5; D16.

### S2-R12. The pipelined handoff and the four-slot bound

**[assumed: proposed rule]** Leader policy: a leader issues the block stamped `termEnd(t) − 1` even when empty, so its term closes by S2-R08 (a). Happy path: that block is published at `termEnd − 1`; `C(h)` forms by about `termEnd − 0.3 s`; TERM_END timeouts and lock votes at `h` gossip at once and the view change forms at about `termEnd`; `leader(t + 1, 0)` publishes `PH(h + 1)` stamped `termEnd` about 0.5 s later, carrying it (2.5 s inside S2-R04's receipt bound; V2 admits the timestamp since `termStart(t + 1) = termEnd(t)`), and continues on the 1-s grid: no slot is empty. Clock fallback: when the leader does not issue that block, or `C(h)` does not form, (b) applies: TERM_END at `termEnd + END_GRACE`, the view change at about `+ END_GRACE + 0.5 s`, the first block of `t + 1` at about `+ END_GRACE + 1 s` with a timestamp of at most that time, so at most `END_GRACE + 2 = 4` slots (`termEnd − 1` to `termEnd + 2`) are empty, once per term. The grid is a rewarded duty, never a validity rule (V4). **Adversary schedule:** withholding the last block gains nothing but those four slots; publishing it later than `termEnd − 1 + STALE_MAX` gets it attested by nobody, and (b) closes the term as well. Source: certificate page §5 and §7; after the #22188 review.

### S2-R13. Recording duties
**[assumed: proposed rule]** Recording is a duty, because the FALLBACK gates (S2-R14) rest on `committee(t)`'s own records reaching L1 first. (1) The next leader records, with `recordViewChange`, every view change of `committee(t)` it carries. (2) Every signer of a view change records it within TO_REBROADCAST of its formation if no record exists, for every view of the term, including one closed mid-term by TIMEOUT (round 5 fix pass). (3) If no TERM_END view change of `committee(t)` has formed by `termEnd(t) + END_GRACE + 0.5 s`, the view's highest certificate is recorded with `recordCertificate`, staggered: the leader of the term's last view and the member at the lowest set bit of that certificate's bitmap (a signer, so it holds it) send it then; every other member only after one L1 block without a record, each reading the record first and sending only a higher certificate (round 6, R6S-3 and the fix pass). On the happy path the duty costs nothing. `recordViewChange(vc)` may be called by anyone: it verifies the witness as S2-R10 defines validity and stores the logical id `vcHash(vc)` with its lock fields, keeping the witness it was given as the record's own evidence of validity but hashing and comparing nothing of it (D16), its `signerTerm` and `redraw` included (D21). The storage rule, stated once here and cited from S2-R14 (iii): per `(t, v, closes)` the record keeps the first live view change of `committee(t)` (TIMEOUT or TERM_END, `signerTerm = t`) and, separately, at most one live FALLBACK; a `committee(t)` view change at a higher lock supersedes the FALLBACK slot without erasing it, both slots are readable by L4, and a landing must match the live `committee(t)` entry if one exists, where "match" is equality of logical ids: a landing or a later call that presents the same logical fields under another valid witness matches, and a second record of a logical id already recorded is a no-op, a FALLBACK presented under a witness of another signer term or a view change under another redraw count included (D21, S2-V20); FALLBACK, REPLACE and RESUME acceptance is S2-R14 and S2-R15. **Adversary schedule:** a blocking minority that withholds TERM_END makes the record necessary; it costs honest members about 165k gas per `recordCertificate` for a pinned term (duty (3); a `recordViewChange` under duties (1) and (2) costs the view-change verification row of §6), plus S1's walk when unpinned (the usual case at `termEnd + 2.5 s` unless a `recordAssignment(t)` pin preceded it), normally one or two records per withheld term, more only when late senders race into one L1 block, where a certificate not above the stored height is refused before verification (L2). If the cartel also holds both first senders, the honest record comes one L1 block later (`termEnd + 26.5 s` at 12-s slots, `+ 6.5 s` at 2-s), still before any landing can consume a FALLBACK. Source: certificate page §5; roles page; round 6, R6S-3.

### S2-R14. FALLBACK: the later committee's closure and its L1 gate
**[assumed: proposed rule]** If no view change closing term `t` exists by `termEnd(t) + END_GRACE + VC_FALLBACK`, the committee of a later term `t'` within C2's landing horizon may sign a FALLBACK view change for `(t, v)` with `signerTerm = t'` for the highest `(v, lock)` it holds, once `termEnd(t) + END_GRACE + VC_FALLBACK × (t' − t)` has passed by its clock and by its latest L1 block's timestamp (nearer committees first), only while it holds no view change of `committee(t)` for that view and sees none recorded, only while it holds no FALLBACK of the same `(t, v)` at or above its lock and sees none recorded (D21, S2-7: a nearer committee's FALLBACK at that lock already closes the view, and one at the same lock is the same generation), and never below a recorded certificate of `committee(t)` for the view (round 5, R5S-5; round 6, R6H-4, R6S-3). It can target every view of term `t`, including one closed by an unrecorded TIMEOUT view change. L1 enforces four gates:

- (i) `recordViewChange` and C2's landing check L4 accept a FALLBACK for `(t, v, closes)` only if `block.timestamp ≥ termEnd(t) + END_GRACE + VC_FALLBACK × (signerTerm − t)` and no live view change of `committee(t)` is recorded for it; the gate reads the logical fields, takes `signerTerm` from the witness presented, verifies the witness as S2-R10 defines validity, and hashes no witness (D16, D21); one FALLBACK logical id presented under witnesses of two signer terms is one object, recorded once (S2-R13);
- (ii) a landing that consumes a FALLBACK must present a certificate at its lock, or the lock must equal `lastLanded`, so a FALLBACK never lands uncertified blocks and V7 holds across committees;
- (iii) a TIMEOUT or TERM_END view change of `committee(t)` at a higher lock supersedes a recorded FALLBACK until a landing has consumed it (the two record slots of S2-R13; L4 takes the `committee(t)` view change if presented); both kinds in one call are refused;
- (iv) `recordViewChange` and L4 refuse a FALLBACK whose lock is below the certificate recorded for `(t, v, vcHash)` (S2-R05), and a FALLBACK recorded before a higher certificate is dead once that certificate is recorded (ignored by the first-recorded rule, consumable by no landing), so a later committee closes the view at the certified lock.

Node side (attestation policy, not validity; C7 A-OBJECTS, D22 item 4): an honest attester does not attest under, and an honest next leader does not build on, a FALLBACK while it holds a certificate of `committee(t)` for that view above the FALLBACK's lock; V2 verifies the FALLBACK from its fields and witness only, so validity does not depend on the order in which a node received the certificate. Consecutive dark committees each add one VC_FALLBACK interval, never a wedge. Conflicting late view changes: first live record per `(t, v, closes)` wins. **Adversary schedule:** S3b applies to a FALLBACK vote only for a key that also attested under the same opening object, that is a key drawn into both `committee(t)` and `committee(t')` (seats are drawn per term, so such keys exist); every other signer has no attestation under `(t, v)`, so its lock below `committee(t)`'s highest certificate is not an objective lie (receipt is unprovable), which is why gate (iv) is needed. The certificate page §5 says "S3b never applies" to FALLBACK signers, an overclaim against its own §16 and the slashing page; §10 open item 9 records both wordings and this section keeps S2-R21's. L1 protects the locked blocks through (i) to (iv) without any view change of `committee(t)`, the record of S2-R13 (3) reaching L1 one or two L1 blocks before any landing can consume a lower FALLBACK (§7, W1). Residual L5 (b): a FALLBACK consumed in the same L1 block as, or before, the honest record (needing `Q` of a later committee, a next leader on it, a proof ready and L1 ordering against the record, outside A-T1) orphans the FALLBACK lock's descendants until that landing. The same race covers a view change of `committee(t)` and a FALLBACK at one lock: they differ in `kind`, so they are two generations and their descendants are no equivocation; whichever L1 accepts decides, already an accepted exception beside "locked" (S2-R18, I4; D21). Two FALLBACKs at one lock are not this race: they are one generation, so two descendants at one height are S1 and S3a (S2-V20). L5 (a): a colluding `committee(t)` that abstains all term and records its own TERM_END just before `committee(t + 1)`'s FALLBACK invalidates up to about ANCHOR_MIN_AGE plus L1 inclusion of the honest fallback chain. Source: certificate page §5, §6, §12; interfaces page §1; limitation L5.

### S2-R15. REPLACE, RESUME, the lock reset and the landing binding
**[assumed: proposed rule]** REPLACE and RESUME serve C2's replacement rule and are attested only when A1 holds at the signed L1 reference in the attester's own view, that reference meeting S2-R09's staleness rule. `recordViewChange` accepts one only if `vc.lockHeight == lastLanded.height`, `vc.lockPhHash == lastLanded.phHash` and `block.timestamp > replaceableFrom`; the record is dead (ignored, no priority) once `lastLanded.height > vc.lockHeight`, so the original view's own TIMEOUT or TERM_END view change is then recorded or landed in its place; an accepted record has no closing effect (round 4, R4H-5, R4-C3): it is the first-recorded view change the fork's landing must match and priority evidence that defers C2's forced path by LAND_CHAIN_GRACE once. Until a replacement or forced batch lands, landing the original stays valid; whichever lands first wins, the loser invalid and free (C2's trailing-VERIFY shape). Lock reset: when a node observes a landed replacement or forced batch (never a record), every certificate above `lastLanded` is void for it, its lock resets to `lastLanded`, and it enters RESET (§5): under the old opening object it signs only RESUME timeouts and lock votes (also at term end, where the RESUME view change doubles as the handoff), never TIMEOUT or TERM_END, so no mandatory post-reset message can be a lock lie (round 3, S2). The RESUME lock vote is at `lock* = lastLanded`, which a forced batch or a sentinel-view range leaves without a certificate: the attester votes on it under S2-R09's clause (2), the verified L1 landing record at `l1Ref`, not a certificate (D16, B-S2-03: "after a valid forced landing honest voters cannot form the RESUME view change" under the certificate requirement). The RESUME view change is a new generation (S2-R10: `kind` and `l1Ref` differ), under which the holder reopens `(t, v)` from `lastLanded + 1`; a key's TIMEOUT or TERM_END signed under the old generation does not block its attestations under the new one (S2-R04) and stays evidence under the old `vcHash`. S3b exempts no lock and the inbox keeps no ring of landed locks (round 5, R5S-1); no honest signer needs one, since an honest TIMEOUT, TERM_END or FALLBACK vote is at least the carried certificate the key verified at V3 when it last attested, votes are monotone, and inside a reset the key signs only RESUME. The landing binding (V7, C2's; what certificates add): the inbox keeps `lastLanded = (t, v, height, phHash)` and `lastVCHash`; a landing continues the open view from `lastLanded.height + 1` with an end certificate whose `phHash` equals the guest's end `phHash`, or opens a view by the view-change chain from `lastVCHash`, each lock equal to `lastLanded` when applied and the first block's `vcHash` (a guest public input) equal to the last view change's logical id; it refuses any view change other than the one first recorded, compared by logical id, so the landing may present any valid witness of the recorded object and never needs the witness the record holds (S2-R13; D16). `lastVCHash` is a logical id. Sentinel-view ranges (254, 255) carry no certificate, and the view that resumes after one votes its first lock under S2-R09 (2). **Adversary schedule:** a REPLACE record meant to void a landable backlog voids nothing (L6, C2); a TIMEOUT view change at a landed lock below a certified block is a lock lie, slashed under S3b. Source: certificate page §6; round 4, R4H-5; round 5, R5S-1, R5S-3.

**[proven: consequences of the binding, conditional on A-V7]** A block with no certificate on itself or a descendant is unlandable; the landed set equals the certified set every node holds (V7); blocks above a view's lock never land.

### S2-R16. Committee redraw
**[assumed: proposed rule]** An attester that attested a block of `(t, v)` but has seen no certificate for TIMEOUT seconds may sign `RD_i = BLS(sk_i, keccak(DOMAIN_REDRAW ‖ chainId ‖ t ‖ v ‖ vcHash ‖ n))`, `n ∈ {1, 2}`. With `⌊m/2⌋ + 1` such signatures (17 of 32) the committee of `(t, v)` is redrawn as the first `K` seats of S1's walk `keccak(seed ‖ 0x03 ‖ t ‖ n ‖ m)` with the committee walk's exclusions, for the same leader, view and opening object; at most REDRAW_MAX redraws per view. Its members attest the view's valid blocks they received on time (S2-R04's receipt bound), the leader continues once a certificate forms, and their TIMEOUT window starts when the redraw forms. Attestations, certificates and lock votes of the redrawn committee carry `n`, and the landing verifies certificates against the committee of the recorded redraw count (the committee proof carries `n` and the redraw proofs `1..n`). In a view change `n` is a witness field, not a logical one (S2-R10; D21), so view changes of counts 0 and 1 at one lock are one opening object, and a key in both draws continues one vote chain (S2-R09). A redraw proof for count `n` is `{ n, bitmap, aggSig }`: the aggregate of `⌊m/2⌋ + 1` REDRAW signatures for `(t, v, vcHash, n)` by the committee at count `n − 1`, so REDRAW `n = 1` is signed by `committee(t)` as drawn and REDRAW `n = 2` by the committee of count 1 (interfaces page §4, `RedrawProof`). A REDRAW message has one statement per `(t, v, vcHash, n)` and no conflicting form, so it needs no slashing rule, changes no holder and applies no penalty; it names no block (a vote naming one let a cartel majority name a block the leader never signed; fix pass). It raises the blanking threshold from 11 to 16 of 32 and needs a blocking minority in every redraw. **Adversary schedule:** a cartel majority redraws a committee that has already certified (the precondition is unverifiable on L1), buying a re-roll toward `Q` and, if it finds `Q`, a lock reset whose only slashable keys sit in both committees; at one third of the seats this path has probability about `6·10⁻⁷` per view (the page's figure, not reproduced, §10) against `4·10⁻⁵` for the slashable path (reproduced, §6), cheaper only in provable cost (L2, L16). Source: certificate page §5 and §8; round 4, R4-C1.

### S2-R17. Fork choice and the equivocation key

**[assumed: proposed rule]** Fork choice reads no clock: the canonical tip is the valid block with the highest `(t, v, height)` whose ancestors within its view are all certified except at most `CERT_LAG_MAX + 1` leaf blocks. Two blocks at equal `(t, v, vcHash, height)`: keep the certified one, else the first seen; store both headers as evidence. Every equivocation key (attestations, timeouts, headers, fork choice, gossip dedup other than of lock votes (S2-R22) and the slashing-protection record) is `(term, view, opening object, redraw, height)` where the opening object is its logical id `vcHash` (S2-R10; D16); the lock-vote scope is `(t, v, vcHash, kind)` as S2-R09 defines it, spanning redraw counts and using the logical `vcHash` like every other key (D21). A REPLACE fork opens a new opening object (its logical fields differ), so nothing signed under the original conflicts with it, and S3b compares locks only within one opening object; two witnesses of one closing lock, of one signer term or of two, of one redraw count or of two, are one opening object, so everything signed under either is in one slashing domain (D21). **Adversary schedule:** an original tail against its REPLACE fork is not equivocation; C2's "whichever lands first" decides. A quorum or next holder that builds two conflicting descendants of one lock under two witnesses (B-S2-01) builds them under one key: the pair is S1 for the holder and S3a for every attester in both certificates. Source: certificate page §3 and §6; D16.

## 7. Argument and adversary coverage

**[proven: withheld blocks are worthless, conditional on A-V7]** A block the committee never received has no certificate (V6 needs its execution); one block can be built on it, carrying the previous certificate, but cannot be certified, so nothing carries a certificate above it: private state is at most 2 blocks and dies within TIMEOUT, and it can neither end a landing nor lie under one (S2-R15).

**[proven: the locked bound within one redraw count]** A locked block at height `h` cannot be below the lock of a later view change of the same redraw count unless at least `2Q(m) − m` attesters are slashable: `C(h)` carried by the locking block and the view change's `Q` lock votes are two `Q`-subsets of `m`, intersecting in at least `2Q − m` keys, each of which attested a header whose carried certificate is above its lock vote, the S3b evidence. Across a redraw the intersection can be empty: reverting then needs `⌊m/2⌋ + 1` REDRAW signers plus `Q` of the redrawn committee, unslashable except for keys in both (probability in §6; A-T11 bounds it). No lock is exempt (round 5, R5S-1). The bound does not depend on which witness opened the view: both the locking block and the later view change name the opening object by its logical id (S2-R10), so a second witness of the same closing lock, from another signer term or redraw count included, opens no second domain in which the `2Q − m` pairs could be split (D16, B-S2-01; D21, S2-7); two witnesses of one lock that each carry a different descendant chain give S1 pairs for the holder and S3a pairs for the attesters in both certificates at the first height where the chains differ (S2-V15).

**[proven: W1 needs two view changes, conditional on A-T1, A-T11 and A-V7]** Withheld blocks `h + 1 .. h + m` of term `t` land only if the term closes at a lock at or above `h + m`, a second view change for `(t, v_last)` under the same scope: it needs `Q` lock votes at `h + m`, which an honest key refuses because it holds neither `C(h + m)` nor the withheld blocks (S2-R09), so under A-T11 (fewer than `Q` colluders in one committee) none forms; S3c is not what stops it, since an upward vote chained on `h` is a permitted re-vote. The recorded honest view change beats the withholder's landing (minutes of proving) to L1 and is the one L4 accepts (S2-R13, S2-R15). A FALLBACK is no second view change here: L1 refuses it while the honest view change is live, before `termEnd + 12 s` and below a recorded certificate of `committee(t)`, and under A-T1 the record owed from `termEnd + 2.5 s` reaches L1 within one or two L1 blocks; residual L5.

**[proven: the timeout rule's cases, conditional on A-C7]** A holder that gets no block attested for TIMEOUT, counted from the opening object, is timed out by every honest attester whatever headers it gossips; a holder whose blocks the honest attesters attested and a minority keeps uncertified is never timed out by them, because the rule reads the attester's own attestations.

**[proven: every condition S2 feeds is objective]** Each is a signature pair, a code-size check or an L1 fact (S2-R21); silence is never slashed and never changes eligibility, because a colluding committee could manufacture it at zero cost; silence forfeits rewards and costs the MISS bleed (S3), nothing else. Source for this subsection: certificate page §16.

## 8. The withholding defence, the private-data limit, the evidence objects and gossip

### S2-R19. The withholding defence W1 to W5
**[assumed: proposed rule set]** Bonded attestations, timeouts on the attester's own state, and making withheld data worthless; non-receipt is never proven. Trace: the holder builds `n, n + 1` privately after the last public certificate `C(n − 1)` and goes silent; attesters hold nothing attested and pending, so they sign TIMEOUT after 5 s; `Q` timeouts yield `VC(t, v, lock n − 1)` in about 0.4 s; `leader(t, v + 1)` builds on `n − 1` carrying it; anyone records it on L1 within seconds; the private `n, n + 1` are orphaned and unlandable, since no `VC(t, v)` with lock at or above `n` exists, a second one needs `Q` lock votes at `n` from keys that do not hold `C(n)` (refused by S2-R09, so none forms under A-T11; §7, W1), and L4 lands only the first recorded (S2-R13).

- **W1 handoff ambush.** The next leader's first block carries `VC(t, v_last)` with lock `(h, H)`; honest nodes accept nothing else at `h + 1`; the withheld `h + 1 .. h + m` need a second view change (`Q` votes at a lock no honest key can verify, S2-R09; §7) or a FALLBACK gated by S2-R14; if the leader releases just before term end and `Q` attesters certify, the TERM_END locks reflect it, else the lock stays at `h`. Only the view change's existence, lock and record matter, never when it forms. **Proven** in §7 under A-T1, A-T11 and A-V7.
- **W2 private MEV.** Nothing reaches the committee, so nothing is attested: timeout after 5 s; private blocks never land; STALE_MAX refuses publication more than 3 s late. Residual: the certification window plus ordinary ordering power.
- **W3 prover grief and bytes availability.** Landing needs no live sequencer: `Q` attesters hold every block below any lock and serve ranges; anyone lands. If all `Q` withhold, the range never lands and is replaced (L3). The retention duty, its length RETAIN_SECONDS and the argument that no L1-accountable publication duty exists are C2-R18's, stated there once; S2 adds only the gossip-side serving rule of S2-R22.
- **W4 selective withholding.** A missing block stops certification there; a node holding the next block range-requests it from any bitmap member of the carried certificate.
- **W5 seal withholding.** No seal exists; certificates and view changes are assembled by anyone from gossiped signatures.

W6 (anyone proves given availability) and W7 (blob withholding after landing) are C2's. Source: certificate page §7.

### S2-R20. Certified-but-private data: no escalation rule

**[assumed: limitation L3, proposed for acceptance in C6's register; not yet accepted]** `Q + 1` colluders (leader plus `Q` attesters) can certify a block only they hold and lock a view change on it; honest attesters cannot sign that lock and the next leader cannot extend it: the one case where "certified" does not imply "available". Candidate A's rounds 1 and 2 showed that no L1 rule can distinguish "unavailable" from "available but unprovable", and that any data-post answer the inbox cannot verify either slashes honest committees or prices nothing, so the earlier availability escalation was removed. The consequence is a stall until C2's replacement predicate opens, after which the holder reopens from `lastLanded`; the private blocks never land and their signers earn nothing but are not slashed: the harm of `Q` colluders refusing to certify, extended to the replacement delay, the price of having no accusation object (invariant I5, S3). Outside A-T11. Source: certificate page §6; limitation L3.
