## 2. The predicate and its results

### C7-R01. Composition and the three results

**[assumed: proposed rule]** For a block `b` a node holding `PH`, `seqSig`, the payload, its message set (S2's objects) and its L1 view evaluates, in the order of C7-R14, C1's component (C1-R01, C1-R02, C1-R03), the header rules H1 to H3 (C7-R02 to C7-R04) and the rules V1 to V6, V8, V9 and V10 (C7-R05 to C7-R13). The result is:

- **unknown context** if C1's component returns `UNKNOWN_CONTEXT`, or the parent is not held (V3's pending-parent state), or the anchored L1 block `a` is not in the node's L1 view (V5's pending-anchor state), and no rule evaluable without the missing context has failed (C7-R14 evaluates every such rule before a hold is entered, V6 excepted because its cost depends on the payload, so a hold is never entered by a block that an evaluable rule other than V6 already rejects); the block is held and re-evaluated when the context arrives, within PENDING_TTL or ANCHOR_WAIT (quoted, S2 §6); what happens when a hold expires is the drop without a verdict (the arbiter's decision under D14: a node that lacked context never produces **invalid**), which S2 §5's machine, still written as a transition to INVALID, is to be revised to match in W10; §11 open item 5 records the decision and stays open until that revision lands;
- **invalid** if any evaluable rule fails, C1's `INVALID_C1` included; failure is silence: the block is dropped, `seqSig` is retained as evidence (S2-R17, S2-R21), and nothing is gossiped about the failure;
- **valid** if C1's component returns `C1_PASS` and every rule of the list passes.

H1 to H3 are listed as separate conjuncts in C7; the pages fold them into V6, and this sentence is the only place C7 says so. `C1_PASS` is never whole-block validity (C1-R01); a valid block is **SEQUENCED** in S2's BLOCK machine and nothing more: certification, locking, landing and finality are S2's and C2's. No rule reads a wall clock, the L1 head, "latest" registry state or a landing time; the only inputs are signed objects, the node's own chain, L1 blocks at least ANCHOR_MIN_AGE old and the registry snapshot at `termStart(t)` (certificate page §3; claim "V1 to V6 are identical across honest nodes"). **Adversary schedule:** a producer that makes honest nodes disagree by feeding them different context (the pending states hold, never reject, so disagreement is delay, not a fork); a producer that relies on a node's missing context being read as invalidity (excluded: a missing context never produces **invalid**); a node that reads its own clock into the verdict (excluded by construction; S2-R04's clock bounds gate signing only). Source: certificate page §3 and §10; C1-R01.

**[proven: the results are exhaustive and determined, conditional on open item 5 for a hold that expires]** Every rule is a predicate on the inputs named above; each is either evaluable (its inputs held) or not. If an evaluable rule fails the result is **invalid** whatever else is missing; if none fails and some rule is unevaluable the result is **unknown context**; otherwise every rule is evaluable and passes, **valid**. Two honest nodes holding the same inputs compute the same result because no rule reads node-local state other than those inputs (A-EXEC for V6, A-L1VIEW for V5, A-REGISTRY for V1 and V2). The verdict **invalid** versus **valid** does not depend on evaluation order; only the moment at which **unknown context** resolves does, which C7-R14 fixes so that a block failing any rule evaluable without the parent or the anchor is never held, a block the signer did not produce in particular; V6, always last, is the one rule a hold may precede.

## 3. The header rules H1 to H3

### C7-R02. H1, extraData

**[assumed: proposed rule]** `extraData` is exactly P-EXTRA = 7 bytes in C1-R03's layout, `basefeeSharingPctg(1) ‖ termId(4) ‖ view(1) ‖ kind(1)`; byte 0 equals BASEFEE_SHARING_PCTG (quoted, C1 P-FEE-SHARE); `termId` and `view` equal `PH.termId` and `PH.view`; `kind` equals the block's kind under H3. The physical widths and the rejection of other lengths are C1-R03's; H1 adds the three equalities. Checked by nodes and asserted by the guest, which rebuilds PH from the blob record and compares (certificate page §2 (iii)). **Adversary schedule:** a sequencer presents one execution block under another view's signed header (the `(termId, view)` equality binds the block to one PH, and two PHs at one `(t, v, vcHash, height)` are S1 evidence, S2-R21); a block that pays the sequencer a fee share other than the published constant (the byte is checked, not read, so the engine's fee decoder and the published constant cannot disagree, TH25). Source: Anchor page §1 H1; certificate page §3 V6; issue #22147.

### C7-R03. H2, the anchor field

**[assumed: proposed rule]** `parentBeaconBlockRoot ≠ 0`. The equality of that word with the hash of the node's own canonical L1 block numbered `PH.anchorNumber` is V5's check (C7-R09, C1-R01), not H2's; H2 is the one check on the field that needs no context, so it is evaluated before the holds (C7-R14, step 6), and a node lacking block `a` is pending-anchor at step 11, never invalid under H2. The non-zero word is what separates an Etna header from a Shasta header; the fork-time argument built on it (no contract immutable and no stored fork time can disagree with the clients) is C1-R07 and C1-R09's and is not repeated here. **Adversary schedule:** a child block with a zero root after activation, including during an L1 stall (invalid under H2 and C1-R01; leaders keep anchoring the last L1 block, V5 being monotone rather than must-advance); the first-Etna-block attack of C1's attack table (C1-R07). Source: Anchor page §1 H2, §5; certificate page §3 V5, V6; issue #22147.

### C7-R04. H3, the kind byte and the permitted (view, kind) table

**[assumed: proposed rule]** `kind` is FORCED (1) iff `view = 254`; GENESIS_CHILD (2) only for the first Etna block, whose parent is C4's genesis parent (the last Shasta-finalized block, the newest checkpoint in the L1 SignalService at the drain, Anchor page M3), whose view opens with no view change, and which is exempt from V8's obligation, binding from its child; FI (3) for a forced-inclusion block whose content is C3-R07's; NORMAL (0) otherwise. The semantic values are S2-R01's (`termId = t`, `view = v` for holder views, 254 for a forced batch, 255 the open-empty, dead-mode and no-committee sentinel). The complete table the certificate page leaves unstated (S2 §10, open item 8) follows from H3's "otherwise" clause and from the Anchor page's "FI (a forced-inclusion block inside an ordinary or sentinel view)":

| `view` | permitted `kind` | Owner of the content rule | Owner of the opening object |
|---|---|---|---|
| `0 .. V_MAX` (holder views) | NORMAL; FI | S2 (a sequencer block); C3-R07 | S2-R01 (the closing view change of the previous view, or REPLACE or RESUME) |
| `0`, first Etna block only | GENESIS_CHILD | C4 M3 (a sequencer block exempt from V8, V5's floor at the drain block) | C4 (no view change; the genesis lock is `lastLanded`) |
| `254` | FORCED only | C3-R11 (a pure function of `lastLanded` and the lander's anchor `A`) | C2 L4 (a forced batch carries no view change and no certificate) |
| `255` | NORMAL; FI | S2-R01 and C2 L4 (the sentinel regimes: open-empty, dead mode, no-committee mode); C3-R07 for FI | S1-R16 (the sentinel opening object, fresh after any landing; S2-R01 names it) |

Every other pair is invalid; FORCED outside 254, GENESIS_CHILD at any block but the first Etna block, and any kind but FORCED at 254 fail H3. Whether the genesis child's view byte is 0 is the certificate page's implication, not its statement, and whether the first Etna term may itself be a sentinel regime (view 255 with kind GENESIS_CHILD) is unstated: both are §11 open items 3 and 4. **Adversary schedule:** a sequencer marks an ordinary block FI to advance the cursor past a due entry without serving it (the content is then checked under C3-R07 against the entry at the cursor, C3-R08, so a block claiming FI must derive the entry's transactions); a sequencer marks a later block GENESIS_CHILD to escape V8 (refused: only the block whose parent is the genesis parent); a forced batch presented under a holder view, or a holder block under 254, to borrow the other's exemptions (the iff binds them). Source: Anchor page §1 H3 and §1's kind list; certificate page §1 and §3 V6; forced-inclusion page §3, §4, §6; issue #22147.

## 4. The validity rules V1 to V10

Each rule names its check, who evaluates it (node, attester, guest), why it is identical across honest nodes, and the schedule it covers. The attester evaluates exactly what the node evaluates (S2-R04 reads C7's result); "guest" marks the rules C2-R04 asserts inside the proof.

### C7-R05. V1, signer

**[assumed: proposed rule]** `ecrecover(seqSig) == leader(PH.termId, PH.view)`, the holder of S1-R12's walk at `termStart(t)`, read with the sequencer key valid at `termStart(t)` (S1-R05), under S2-R03's signing domain. Node and guest: the guest verifies the recovery and exports the leader as a public input that C2's L4 checks against `isHolder` (C2-R05; certificate page §2 (iii)). Kind FORCED blocks have no signature and skip V1 (forced-inclusion page §6). Identical across honest nodes because it reads a signed object and registry state at least LOOKBACK old (A-REGISTRY). **Adversary schedule:** a block signed by anyone but the holder (dropped; a non-holder cannot even be timed out, S2-R07); a block signed by a holder for a view it does not hold (the leader of `(t, v)` is a function of `(t, v)`); a block signed by a holder whose rights read "latest" state, the pre-Etna failure (excluded by S1-R05's read at `termStart(t)`). Source: certificate page §3 V1; S1-R05; S1-R12.

### C7-R06. V2, view entry

**[assumed: proposed rule]** `PH.timestamp ∈ [termStart(t), termEnd(t))`, stated once here and shared with V4 (C7-R08). If `v ≥ 1` or `b` is the first block of `t`: `PH.vcHash` names a carried view change closing the previous view, verified against its signer committee (A-OBJECTS: S2-R10, and for a FALLBACK the gates of S2-R14), and `PH.parentHash` is the lock's block. V2 checks the `vcHash` chain rule of S2-R01 between consecutive signed headers. A sentinel-view chain opens with S1-R16's object (round 2, S9). A FALLBACK is not accepted as the closing object while the node holds a certificate of `committee(t)` for the closed view above the FALLBACK's lock (round 6, R6S-3; S2-R14's node side). Kind FORCED blocks skip V2 (C3-R11); kind GENESIS_CHILD opens with no view change (H3). Node, attester and, for the chain structure only, the guest: the guest checks the `vcHash` chain and that the first block of the range carries `vcHashOfFirstBlock` (C2-R04); it verifies no committee signature, which C2's L4 and L5 do on L1. Identical across honest nodes because it reads signed objects and S1-R05's registry read at `termStart(t)` (through S1-R12's holder) and never the L1 head; a node that has not yet received the higher certificate may accept a FALLBACK until it does, and L1 alone decides what lands (certificate page §3, V2's last column). **Adversary schedule:** a backup starting above the lock or on another branch; a leader opening a view with an object that closes nothing; one execution hash under two `vcHash` envelopes (two PHs, S2-R03's identity rule); a block of term `t` stamped in `t + 1` (the window). Source: certificate page §3 V2; S2-R01; S1-R16; round 2, S9; round 6, R6S-3; issue #22147.

### C7-R07. V3, parent and carried certificate

**[assumed: proposed rule]** The parent is accepted in `(t, v)`, else the block is pending-parent (a range request, bounded by PENDING_TTL, quoted S2 §6); `carriedCertHeight ∈ {n − 1, n − 2}` (CERT_LAG_MAX = 1, quoted S2 §6); the carried certificate verifies against the committee of its redraw count (A-OBJECTS: S2-R05) and names the ancestor at that height; the first two blocks of a view carry the view change instead (S2-R11). Node and attester; the guest rebuilds `carriedCertHash` into PH from the blob record and verifies no certificate (C2-R04). Identical across honest nodes: signed objects. **Adversary schedule:** a withheld parent (held, then at the TTL dropped without a verdict, D14; S2 §5's INVALID wording stands until W10's revision, §11 open item 5); a block carrying a certificate for a block off its ancestor line, or with fewer than `Q` bits, or of the wrong `(t, v)` (invalid, and S6 evidence under S2-R21 when signed); a tail of unattested progress longer than CERT_LAG_MAX + 1 (the leader holds, S2 §5). Source: certificate page §3 V3.

### C7-R08. V4, time

**[assumed: proposed rule]** `PH.timestamp ≥ parent.timestamp + 1`; the upper bound `PH.timestamp < termEnd(t)` the page writes in V4 as well is V2's window (C7-R06) and is stated once there. No wall clock and no L1 landing time: the 1-s cadence is a rewarded duty whose hard bound is S2-R07's timeout, never a validity rule (after the #22188 review, 2026-10-01). Kind FI blocks have `timestamp = parent.timestamp + 1` exactly (C3-R07). Kind FORCED blocks skip the window's upper bound: `ts_0 = max(parent.timestamp + 1, T_A + ANCHOR_MIN_AGE)` and `ts_j = ts_0 + j` (C3-R11). Node, attester and guest (C2-R04: "timestamps obey V4"). S2-R08 (a) relies on `termEnd(t) − 1` being the term's last possible timestamp; S3-R21 relies on the lower bound with V2's window giving at most TERM (quoted, S1) blocks per term. Identical across honest nodes: two integers of the chain. **Adversary schedule:** the pre-Etna retroactive invalidity, where the upper bound was the L1 landing time (rejected alternative, certificate page §17); a block stamped in the future (gated by S2-R04's CLOCK_SKEW at signing, not by validity); a term that crosses its end (the window). Source: certificate page §3 V4; C1-R03's strictly increasing timestamps.

### C7-R09. V5, anchor

**[assumed: proposed rule]** The header's `parentBeaconBlockRoot` is the hash of L1 block `a` whose number is `PH.anchorNumber`, and `a` is the node's own canonical L1 block at that number (hash equality, A-L1VIEW); `anchorNumber` is monotone from the parent's (for the first Etna block, whose parent is a Shasta block, the floor is C4's drain block recorded at `drainedAt`, so the genesis child cannot be produced before that block's timestamp plus ANCHOR_MIN_AGE); and, at the block that carries the anchor, `L1[a].timestamp ≤ PH.timestamp − ANCHOR_MIN_AGE` and `≥ PH.timestamp − ANCHOR_MAX_AGE`. Monotone, not must-advance: during an L1 stall leaders keep anchoring the last block, and a stall longer than ANCHOR_MAX_AGE halts honest production until L1 resumes (C2-R19).

*Which block carries the anchor, and inheritance (D14).* V5's two age bounds are evaluated at the block that carries an anchor, against that block's own `PH.timestamp`. A block of kind NORMAL or GENESIS_CHILD carries its own anchor. A block of kind FI inherits its parent's anchor (C3-R07: the parent's `parentBeaconBlockRoot` and `anchorNumber`, `timestamp = parent.timestamp + 1`) and inherits its parent's V5 verdict: the node checks that the two anchor fields equal the parent's and does not re-evaluate the age bounds against the FI block's own timestamp. MAX_FI_RUN = 2 (C3-R08's run clause) bounds the drift of the anchor's age past ANCHOR_MAX_AGE to 2 s, and the NORMAL block that must follow the run is evaluated against its own timestamp, which forces the producer to advance the anchor. A forced batch (view 254) is constructed by C3-R11: its block 0 carries the lander's anchor `A` and is evaluated at `ts_0 = max(parent.timestamp + 1, T_A + ANCHOR_MIN_AGE)` under both bounds, `T_A ≤ ts_0 − ANCHOR_MIN_AGE` (true by construction) and `T_A ≥ ts_0 − ANCHOR_MAX_AGE` (the upper-age bound, which the inbox checks as one of C3-R11's checks). Block 0 is the batch's first block, whose parent is the `lastLanded` of the landing that carries the batch (C3-R11); it is evaluated under both bounds even when its parent is kind FORCED with the same anchor, since forced batches may chain (C3-R11 (7)) and inheritance never crosses a landing. The later blocks of the batch, 1 to `m − 1`, like block 0 of kind FORCED, inherit `A` and block 0's verdict exactly as a kind FI block inherits its parent's. The batch's construction, the inbox check and the lander's choice of `A` are C3-R11's; C7 states only the predicate. This rule is stated once here; C3-R07, C3-R11 and C2-R04 cite it (D14; J's review of #22199 (2026-10-01), J-1).

The L1 state root is not an L2 input. The former V5(e) clause, forced-inclusion placement, is V8 (round 3, H6). Node and attester under A-L1VIEW; the guest asserts the same equality against the witnessed RLP header, the monotonicity and the age bounds at the block that carries the anchor, with the inheritance above for kind FI and for FORCED blocks after block 0 (C2-R04, C2-R19), and the inbox checks only the anchor tip (C2 L7) and, for a forced batch, block 0's upper-age bound (C3-R11). Identical across honest nodes because it reads L1 blocks at least ANCHOR_MIN_AGE old and, for an inheriting block, the parent's fields and verdict, which step 7 of C7-R14 has fixed; a node lacking `a` is pending-anchor (ANCHOR_WAIT, quoted S2 §6), never invalid; a reorg of `a` invalidates `b` identically everywhere and the range is unlandable (TH17, TH12). **Adversary schedule:** a fabricated anchor hash (TH17: attestable only if `Q` attesters skip V5, revealable only on an unlanded chain, which cannot land and is replaced; C2-R19); a stale anchor inside the 1,800-s legal window (not invalid; C3's attester policy FI_ANCHOR_LAG and S2-R07 time such a holder out when an entry is due); a holder that parks its anchor at exactly ANCHOR_MAX_AGE while an entry is due (J-1: the FI child is valid by inheritance, the NORMAL block after the run must carry a fresh anchor, and the stall clock keeps running; the proof below); a producer that stretches a stale anchor with FI blocks (bounded to MAX_FI_RUN = 2 s: a third consecutive FI block fails V8, C3-R08, and a kind FI block without a due entry fails V8 too); a forced lander that picks an old `A` to give the batch a pre-signal origin (refused by the upper-age bound at block 0, checked by the inbox under C3-R11); an anchor younger than ANCHOR_MIN_AGE (honest V5 disagreement under ePBS, the reason for the floor); a producer keeping a pre-signal origin (fails V5 after ANCHOR_MAX_AGE, plus at most MAX_FI_RUN = 2 s through inheritance, at every honest attester, C1's A-ORIGIN-PROGRESS as C2-R19 composes it). Source: certificate page §3 V5; Anchor page §1 H2, §2, §5 M3; round 3, H6; issue #22147; TH12, TH17; D14.

**[proven: a producer parked at the boundary always has a valid child while L1 progresses, conditional on C3-R07, C3-R08, A-L1VIEW and A-L1LIVE]** Let the head `p` carry an anchor exactly ANCHOR_MAX_AGE old at `p.timestamp` while an entry is due at `cursor(p)`. The FI child that C3-R08 requires inherits `p`'s anchor and verdict, so it passes V5 although the anchor is 1,801 s old at its own timestamp; a second FI child, if an entry is still due, passes likewise at 1,802 s; the next block must be NORMAL (C3-R08's run clause) and is evaluated against its own timestamp, so it passes V5 only with an anchor at most ANCHOR_MAX_AGE old at that timestamp, which exists under A-L1LIVE (L1 has produced a block in the last ANCHOR_MAX_AGE) and which the node holds once it is ANCHOR_MIN_AGE old (A-L1VIEW). So a valid child exists at every height while L1 progresses, the per-block stall clock of C3-R05 keeps running towards the cut, and a TIMEOUT view needs no waiver for this case. The drift of a landed block's origin age past ANCHOR_MAX_AGE is at most MAX_FI_RUN = 2 s, which C2-R19's A-ORIGIN-PROGRESS must compose with C3's inclusion bound (obligation on C2, §11: C2-R19 still reads "at most ANCHOR_MAX_AGE older than the block"). When A-L1LIVE fails, that is during an L1 stall longer than ANCHOR_MAX_AGE, honest production still halts (C2-R19), unchanged. For the forced batch, the bound at block 0 is satisfiable under A-L1LIVE: the batch lands after C2's deadline, so L1 blocks with `T_A ≥ parent.timestamp + 1 − ANCHOR_MAX_AGE` exist whenever L1 produced a block in the last ANCHOR_MAX_AGE, and the lander picks any such `A` inside the EIP-2935 window (C3-R11). (D14; J's review of #22199 (2026-10-01), J-1.)

### C7-R10. V6, execution

**[assumed: proposed rule]** The node submits the received payload unchanged, with the envelope's `parentBeaconBlockRoot`, through `engine_newPayload`, never a rebuild, and requires VALID and an engine hash equal to `PH.blockHash` (S2-R03 (i)); execution runs C1-R02's system operations, EIP-4788 then EIP-2935, before ordinary transactions, outside the block gas limit. No rule reads a transaction receipt: the block contains no protocol transaction, so no revert can leave a silent checkpoint gap. Node, attester (S2-R03 (ii) signs only after (i)) and guest, which recomputes `blockHash` from blob data and executes every block VALID from the parent state to exactly its `blockHash` (C2-R04). ### C7-R11. V8, forced-inclusion placement (the rule is C3-R08)

**[assumed: proposed rule, C7's part only]** V8 is one conjunct of the predicate. ### C7-R12. V9, record size

**[assumed: proposed rule]** The canonical record of a sequencer block, `headerCore ‖ seqSig ‖ [viewChangeBytes] ‖ txListBytes`, is at most RECORD_MAX = 130,035 bytes, so the framed single-block payload of C2-R02 (9 framing bytes plus the record) fits one blob of 130,044 usable bytes (quoted, C2 §12, open there) and any single certified block is landable alone at every slot time. Identical across honest nodes: a byte count of a fixed encoding. **Adversary schedule:** a block no landing could carry, which halted the chain until replacement (round 2, H1); with records of up to three blobs, the earlier bound, a term cut into blocks that left each landing carrying little more than one blob, so it needed more landings than the reward paid (round 6, R6H-3; C2-R16's proof reads V9 at exactly this value). Source: certificate page §3 V9; round 2, H1; round 3, H3 (framing corrected); round 6, R6H-3 and the fix pass.

### C7-R13. V10, term budget

**[assumed: proposed rule]** The sum of canonical record bytes over the sequencer blocks of one term is at most TERM_BYTES_MAX = 5 × LANDING_UNIT = 1,270,000 bytes (LANDING_UNIT quoted, C2 §12), and each block's zk-gas is within the per-block zk-gas limit the execution client already enforces (value unstated on the pages, §7). ## 5. The validation order and the consumers

### C7-R14. Order and the evaluator table

**[assumed: proposed order; the pages give two partial orders, §11 open item 2]** The certificate page's BLOCK machine (§10) places V1 and V2 before the pending holds and V1 to V6 before SEQUENCED; the Anchor page's per-block machine (§11) places H1, then H2 (V5), then H3, then the system calls and transactions, then the engine-hash check (V6). Composing them: every rule evaluable from the header, the signed objects and the registry snapshot alone is evaluated before either hold, so that C7-R01's definition (an evaluable failing rule gives **invalid**, never a hold) is met by construction; a rule that needs the parent follows the parent hold and a rule that needs the anchor follows the anchor hold; execution is last.

### C7-R15. Who consumes which result

**[assumed: interface to S2 and C2]** S2-R04 attests `b` only when the result is **valid** and its signing policy holds; a block in **unknown context** sits in PENDING_PARENT or PENDING_ANCHOR below SEQUENCED, is never attested and carries no confirmation level; an **invalid** block is INVALID in the BLOCK machine with every descendant (S2 §5; S2 §10's label-mapping row). C2's guest asserts, for every block of a landed range, the rules marked "guest" in the table of C7-R14 and treats a failure as "no valid proof": the range is unlandable, never slashable (C2-R04; certificate page §2 (iii)). The inbox evaluates no C7 rule; what it checks (sequence, rights, certificate, blob hashes, anchor tip, queue state) is C2-R05. The former Anchor rules A3 to A6 of the pre-#22147 design are the following rules and nothing else: A3 is V5's monotone `anchorNumber` plus C1-R06's conflict check; A4 is V2's timestamp window plus H1's `termId` equality; A5 is V2 and V3 on consecutive signed headers; A6 is H3 plus C3-R11's forced-batch content rule (certificate page §3, "Where the former Anchor rules went"). **Adversary schedule:** a client that attests a pending block (excluded by S2-R04 reading the result); a guest that proves a range containing an invalid block (A-EXEC and C2's T3: the journal's end hash would differ from the certified one or the proof would not exist).

## 6. State machine

## 8. Argument and adversary coverage

**[proven: identical across honest nodes, conditional on A-EXEC, A-L1VIEW, A-REGISTRY and A-OBJECTS]** Each rule reads only a signed object (V1, V2, V3, H1), two integers of the chain (V4), an L1 block at least ANCHOR_MIN_AGE old or, for an inheriting block, the parent's anchor fields and verdict (V5, H2; C7-R09), the parent's derived state and entries that never change once saved (V8), a byte count (V9), a sum over the node's own chain (V10) or a deterministic execution (V6, H3). None reads a wall clock, "latest" state or the L1 head. So two honest nodes with the same inputs return the same result (C7-R01's proof), and a node with fewer inputs returns **unknown context**, never a different verdict. This is the certificate page's claim "V1 to V6 are identical across honest nodes; no rule reads wall clock or 'latest'", extended to V8 to V10 by the same reading. Not proven here: that the guest's implementation of the same rules agrees with the node's (A-EXEC, a conformance obligation, §10).

**[proven: one block, one envelope]** H1 binds `(termId, view)` into the header, hence into `blockHash`, which PH names under `seqSig`; a block presented under another view's PH fails H1 at every node and, if both PHs are signed, is S1 evidence (S2-R21). Two envelopes for one execution hash differing in `vcHash` or `carriedCertHash` are two PHs (S2-R03's identity rule) and V2's chain rule accepts at most one at each position of a chain.

**[proven: no clock in validity, conditional on open item 5]** V4 reads `parent.timestamp` and `termEnd(t)`; V5 reads an L1 block's own timestamp; the attestation bounds STALE_MAX and CLOCK_SKEW gate signing only (S2-R04). The only timers in C7 are the holds of C7-R01, which end an evaluation without a verdict (the arbiter's decision, D14); if the page's INVALID after the TTL were a verdict, validity would depend on the node's clock and the claim would fail, which is why open item 5 stays listed until S2 §5 is revised to the drop in W10.

**[assumed: V8's in-flight stability is C3-R08's consequence, relied on here]** C3-R08 states that an entry becoming due while blocks are in flight binds the first block after the anchor advances past its due time and that nothing is reorged by an FI. C7 adds only the order fact it needs: `T_p`, `cursor(p)` and `clearTip(p)` are fixed by steps 7 and 11 before step 12 reads them, so V8's verdict on `h` is a function of `p` alone (C7-R01's order argument).
