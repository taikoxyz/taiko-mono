## 1. Scope, vocabulary and claim convention

**[assumed: section boundary]** C7 owns the one deterministic statement every node, attester and proof guest implements to decide whether an L2 block is valid: the composition of C1's header component, the header rules H1 to H3 and the validity rules V1 to V10 (V7 is C2's landing binding and V8 is C3-R05(b)'s request-block rule; both are only named here, with the step at which V8 is evaluated), the three results, the validation order, the permitted `(view, kind)` table, and one test-vector obligation per rule. C1 owns the physical header profile, the system operations and the oracle (C1-R01 to C1-R03 are C7's component, invoked, not restated); C2 owns the landing, the journal, what the guest proves beyond the predicate, V7 and the origin authentication A-ORIGIN; C3 owns the forced-inclusion queue and its schedule (C3-R01, C3-R04), request blocks with their content and the contiguity rule V8 itself (C3-R05), consumption at landing and the gate (C3-R06), the hatch (C3-R07), what the guest asserts of request blocks (C3-R08) and the constants V8 reads (D41); C4 owns the migration, the genesis parent, the activation record and the restart fields (C4-R07, C4-R08, C4-R12); S1 owns `leader(t, v)`, `committee(t)` and the registry snapshot; S2 owns the opening objects, certificates, view changes, the attestation policy, the confirmation levels and the equivocation key; S3 owns slashing; C6 the registers; C8 the consolidated interfaces. None of their text is duplicated here (`00-decomposition.md` §1; D9, D10).

**[assumed: notation]** **assumed** heads a proposed rule or a premise; **proven** means an argument on this page, not machine verification; **open** means unresolved, with the closure condition named. An identifier `C7-Rnn` has exactly one normative definition; the rule names H1 to H3 and V1 to V10 are the pages' labels and are kept beside the ids so that C1, C2, C3 and S2 can keep citing them. §7 is C7's only register of numbers; "quoted" marks a value another section owns that a C7 rule reads. Round citations name candidate A's red-team round; "issue #22147" names the anchor-free revision; "after the #22188 review" names A's revision on candidate B's review of PR #22184 (2026-10-01).

| Block `b` at height `n` | An L2 execution block together with the signed header `PH` and `seqSig` that name it (S2-R03), its payload, and for the first block under an opening its opening object (C7-R06). | First block under an opening | The block whose `PH.vcHash` names an opening object its parent's PH does not name (C7-R06, D17). Every other block is a later block of its parent's opening. Which `(termId, view)` each carries is C7-R06's chain rule (D22). |

| VALID_GOSSIP, VALID_LANDED | The two named predicates of C7-R01: the whole C7 predicate a node or attester evaluates before landing, and the conjunction of C2-R04's assertions and C2-R05's checks by which an importer accepts a landed range (C7-R15). |
| Parent `p` | The block at `n − 1` on the chain `b` names through `PH.parentHash`. |

| Request block; `head(A_b)` | An L2 block executing exactly one queue entry: kind FI (voluntary, a sequencer block in a holder view or view 255) or kind FORCED (inside a hatch, view 254) (C3 §1, C3-R05). `head(A_b)`, `tail(A_b)` and `lastLanded(A_b)` are the inbox's values in the L1 state at the block's anchor `A_b`. ## 2. The predicate and its results

### C7-R01. Composition and the three results

**[assumed: proposed rule]** For a block `b` a node holding `PH`, `seqSig`, the payload, its message set (S2's objects) and its L1 view evaluates, in the order of C7-R14, C1's component (C1-R01, C1-R02, C1-R03), the header rules H1 to H3 (C7-R02 to C7-R04) and the rules V1 to V6, V8, V9 and V10 (C7-R05 to C7-R13), each applied as the mode matrix of C7-R04 says for the block's kind and regime. The result is:

- **unknown context** if C1's component returns `UNKNOWN_CONTEXT`, or an object the block names is not held in a form that can be checked (the parent, V3's pending-parent state; the opening object or a witness for it that verifies; the carried certificate's preimage; the parent's own verdict, while the held parent is unresolved and not landed at the block's own reference, C7-R07; the records of the block's chain above `lastLanded(A_b)` that V8 reads, C7-R11), or an L1 block at a fixed reference is not in the node's L1 view (the anchored block `a`, the L1 reference block at which C7-R07 reads a parent's landing, S1's registry snapshot `S(t)`, or the L1 reference a sentinel object signs: the pending-anchor state), and no rule evaluable without the missing context has failed (C7-R14 evaluates every such rule before a hold is entered, V6 excepted because its cost depends on the payload, steps 11 and 12 included while step 7 is unresolved (D58 (2)), so a hold is never entered by a block that an evaluable rule other than V6 already rejects); the block is held and re-evaluated when the context arrives, within PENDING_TTL or ANCHOR_WAIT (quoted, S2 §6), re-entering at the earliest step of C7-R14 not yet passed with complete fixed inputs (B's W12 verdict on #22199, item 1); a hold that expires has one outcome, D14's: the block is dropped without a verdict and re-entered the same way on receipt of the missing context (D17, B-C7-06), so a node that lacked context never produces **invalid**; S2 §5's BLOCK machine as merged (D78) writes the same outcome, `DROP_WITHOUT_VERDICT (C7)` (§11 open item 5);
- **invalid** if any evaluable rule fails, C1's `INVALID_C1` included; failure is silence: the block is dropped, `seqSig` is retained as evidence (S2-R17, S2-R21), and nothing is gossiped about the failure; the verdict is final under A-L1VIEW, since no rule fails on an input that a later message or landing could change: step 7 fails on the parent only when the parent's verdict is **invalid**, itself final, and the held record at the block's own reference shows no landing of it, a record no later landing changes (C7-R07, D60 (1)), and a parent whose verdict is unresolved is a hold; and only §6's reorg transition, outside A-L1VIEW, reaches INVALID from another verdict;
- **valid** if C1's component returns `C1_PASS` and every rule of the list passes.

H1 to H3 are listed as separate conjuncts in C7; the pages fold them into V6, and this sentence is the only place C7 says so. `C1_PASS` is never whole-block validity (C1-R01); a valid block is **SEQUENCED** in S2's BLOCK machine and nothing more: certification, locking, landing and finality are S2's and C2's. No rule reads a wall clock, the L1 head, "latest" registry state, a landing time or the node's wider message set; the only inputs are the signed objects the block and its ancestors name, the node's own chain, L1 facts read at a fixed reference that a signed object names and that is at least ANCHOR_MIN_AGE old (V5's block `a`; the L1 landing record C7-R07 reads, at the block's own reference only, D58 (1); S1's snapshot `S(t)`; the sentinel tests of C7-R04, at the L1 reference S1-R16's object signs; the queue state V8 reads at the block's anchor) and the registry snapshot at `termStart(t)` (certificate page §3; claim "V1 to V6 are identical across honest nodes"; D22).

*The two named predicates (D17, B-C7-04).* **VALID_GOSSIP** is the whole of the above: the predicate every node and attester evaluates on a block before it lands, and the result S2-R04 reads. **VALID_LANDED** is the conjunction of what the guest asserts (C2-R04) and what the inbox checks (C2-R05), nothing more and nothing less: the predicate by which an importer accepts a landed range on the strength of the L1 record; its exact rule set is C2's to list, and C7 reads it (§11). The two differ, as far as C2's listing is not yet available, in two conjuncts and one input (assumed, C7-R15, §11 item 18; whether the verification of intermediate opening objects against their committees is a third conjunct is checked against C2-R04 and C2-R05). The first conjunct is the verification of a carried intermediate certificate against its committee (V3, C7-R07), which the guest skips and the inbox checks only for the end certificate (C2-R05 L5). The second is V8's contiguity against `head(A_b)` (C7-R11), which C3-R08 keeps as gossip validity: the guest asserts C3-R08's order of request blocks and `s_i ≤ T_{A_b}` but not contiguity, and these with the inbox's step-1 checks are all that is enforced at landing, so outside T11 a quorum that breaks contiguity can land a request block VALID_GOSSIP rejects, in two forms (D60 (2)): (a) a **late replay**, an id whose replayable bit is set, executed at most once from an anchor at or after its save (C3-R08, C3-T32), the limitation the user signed in D55(3) (L-HATCH-DEPOSIT); (b) a **fresh out-of-order execution**, a kind-FI block carrying an id above `head(A_b)` (contiguity fails at step 12) landed with an empty replay list and a void count `v` that voids the ids it skipped, so that C3-R08's order `[fiHeadBefore + v, fiHeadAfter)` and `s_i ≤ T_{A_b}` pass and the id executes fresh, not as a replay (B's W8 verdict at `06cae6c` (comment 5952455406), item 2; vector C7-T10's fresh-execution case). Both forms stay within C3's queue accounting (C3-R04's `v ≤ E` and `n ≥ R` and the range limits hold, and no id executes twice); C7 names no evidence object for either; D55(3) covers only form (a), and form (b) is on the D50 completion list for the user (D60 (2)). The input is V5's: before landing V5 reads the node's own L1 view, and at landing the same conjunct reads the anchored header that C2-R19 authenticates against L1 history; no conjunct is missing there (D22 item 1, C7-4; C7-15). A landed range satisfies VALID_LANDED by construction of the landing; an importer whose pre-landing VALID_GOSSIP verdict on a landed block was **invalid** yields to the landing, the way its lock yields to a landed replacement (S2-R15's lock reset), and the object that failed is evidence, never a reason to fork from the landed chain (C7-R15). Agreement among honest nodes on the chain they certify before landing rests on A-QUORUM; the certificate gap between the two predicates is closed by evidence (C7-R15), not by a verification of every carried certificate on L1, and only where the carried certificate's preimage was published (D22 item 6; the unpublished case is C7-R15's residual); the contiguity gap is not closed by evidence and is bounded by C3-R08's order and C3's queue accounting, with D55(3) as the signed limit of its replay form only and its fresh form on the D50 completion list (D60 (2)).

*What validity does not assert (S2 §10's C7 row, D29) [assumed: clarifying non-claim, no new predicate].* Neither VALID_GOSSIP nor VALID_LANDED asserts landability or a confirmation label. A block **valid** under VALID_GOSSIP can be unlandable at C2's L4 (S2-R13's recording duties, S2-R14 (i) to (v), S2-R15's landing binding, C2-R10's horizon) and stays **valid**; landability is C2's and S2's, never an input to this predicate. "Fully backed" is S2-R18's confirmation level, never a validity condition. The FALLBACK witness bound this predicate reads is S2-R10 (vii) at FB_SIGNER_HORIZON, not C2-R10's horizon (A-OBJECTS).

**Adversary schedule:** a producer that makes honest nodes disagree by feeding them different context (the pending states hold, never reject, so disagreement is delay, not a fork); a producer that relies on a node's missing context being read as invalidity (excluded: a missing context never produces **invalid**); a node that reads its own clock into the verdict (excluded by construction; S2-R04's clock bounds gate signing only); a node that reads an object it acquired later, a higher certificate in particular, into a verdict it already holds (excluded: every input is an object the block or its ancestors name, C7-R14's re-entry argument; the refusal of a FALLBACK while a higher certificate is held is S2-R14's attestation policy, D17); a holder and a malicious quorum landing a chain that VALID_GOSSIP rejects (lands under VALID_LANDED: for a failing carried certificate, with the evidence of C7-R15 on L1 when the preimage was published; for a request block that breaks contiguity, outside T11, with no evidence object, as a late replay (D55(3)) or a fresh out-of-order execution with an empty replay list (D60 (2)), both within C3's accounting); a node that reads the L1 landing record or a sentinel test at its own L1 head, so that two nodes disagree by when they looked (excluded: C7-R07 and C7-R04 fix the reference by a signed object, D22). Source: certificate page §3 and §10; C1-R01; D14; D17 (B's W8 verdict on #22199 (2026-10-01), B-C7-04 and B-C7-06); D22.

**[proven: the results are exhaustive and determined]** Every rule is a predicate on the inputs named above; each is either evaluable (its inputs held) or not. If an evaluable rule fails the result is **invalid** whatever else is missing; if none fails and some rule is unevaluable the result is **unknown context**; otherwise every rule is evaluable and passes, **valid**. So a block whose inputs are complete, the parent's own verdict among them (by induction on height, a parent whose inputs are complete has one), returns **valid** or **invalid**, and **unknown context** is only missing context: a known **invalid** parent with a held reference state that records no landing of it is a failure of step 7, not a hold (D60 (1); B's W8 verdict at `06cae6c` (comment 5952455406), item 1). A hold that expires produces no result and changes no input, so the block's eventual verdict is the one it would have had without the expiry (C7-R14's re-entry argument). Two honest nodes holding the same inputs compute the same result because no rule reads node-local state other than those inputs (A-EXEC for V6, A-L1VIEW for V5 and for the landing record at its fixed reference, A-REGISTRY for V1 and V2; A-L1VIEW for the sentinel tests at the reference S1-R16's object signs and for V8's queue state at the block's anchor). The verdict **invalid** versus **valid** does not depend on evaluation order; only the moment at which **unknown context** resolves does, which C7-R14 fixes so that a block failing any rule evaluable without the parent or the anchor is never held, a block the signer did not produce in particular, with one exception, of two forms: a node that does not hold S1's snapshot `S(t)` cannot evaluate V1, so a block of such a term is held pending-anchor at step 2 whoever signed it, and a node that does not hold the L1 block a sentinel object names as its reference cannot evaluate that object's authorization, so the first block under it is held pending-anchor at step 4 whoever signed it (item 6), the hold slot either occupies bounded by ANCHOR_WAIT and by S2-R22's pre-relay filter, which a relaying peer applies with its own L1 view and which admits only a term within one of the current (C7-R14's adversary schedule); V6, always last, is the one rule a hold may precede (C7-R14; D58 (2)). For a child whose parent is accepted only by its landing, the one landing input is the record at the child's own reference (C7-R07; D58 (1)): a node whose L1 view has not reached that reference holds the child pending-anchor; a child whose parent is **invalid** and whose held state at its own reference records no landing of the parent is **invalid** at step 7 at every node holding those inputs, finally, a landing recorded later changing nothing at that reference (D60 (1)); and a child whose parent's verdict is unresolved is held at step 7 (an evaluable rule of its own, at step 11 or 12 among others, may still fail, D58 (2)); no later block is an input to the child's verdict, so a node missing an input differs only in the moment of its verdict, like any other missing context.

## 3. The header rules H1 to H3

### C7-R02. H1, extraData

**[assumed: proposed rule]** `extraData` is exactly P-EXTRA = 7 bytes in C1-R03's layout, `basefeeSharingPctg(1) ‖ termId(4) ‖ view(1) ‖ kind(1)`; byte 0 equals BASEFEE_SHARING_PCTG (quoted, C1 P-FEE-SHARE); `termId` and `view` equal `PH.termId` and `PH.view`; `kind` equals the block's kind under H3. Which term `termId` names is the mode matrix of C7-R04: `t` for a holder view, the term containing `PH.timestamp` for a sentinel-255 block, and, for a hatch, the term containing `ts_0` in every block (D17; C3-R07 states `termId = termOf(ts_0)` and the guest derives it with the other PH-equivalent fields). The physical widths and the rejection of other lengths are C1-R03's; H1 adds the three equalities. Checked by nodes and asserted by the guest, which rebuilds PH from the blob record and compares (certificate page §2 (iii)). **Adversary schedule:** a sequencer presents one execution block under another view's signed header (the `(termId, view)` equality binds the block to one PH, and two PHs at one `(t, v, vcHash, height)` are S1 evidence, S2-R21); a block that pays the sequencer a fee share other than the published constant (the byte is checked, not read, so the engine's fee decoder and the published constant cannot disagree, TH25). Source: Anchor page §1 H1; certificate page §3 V6; issue #22147.

### C7-R03. H2, the anchor field

**[assumed: proposed rule]** `parentBeaconBlockRoot ≠ 0`. The equality of that word with the hash of the node's own canonical L1 block numbered `PH.anchorNumber` is V5's check (C7-R09, C1-R01), not H2's; H2 is the one check on the field that needs no context, so it is evaluated before the holds (C7-R14, step 6), and a node lacking block `a` is pending-anchor at step 11, never invalid under H2. The non-zero word is what separates an Etna header from a Shasta header; the fork-time argument built on it (no contract immutable and no stored fork time can disagree with the clients) is C1-R07 and C1-R09's and is not repeated here. **Adversary schedule:** a child block with a zero root after activation, including during an L1 stall (invalid under H2 and C1-R01; leaders keep anchoring the last L1 block, V5 being monotone rather than must-advance); the first-Etna-block attack of C1's attack table (C1-R07). **[assumed: proposed rule]** The header's `parentBeaconBlockRoot` is the hash of L1 block `a` whose number is `PH.anchorNumber`, and `a` is the node's own canonical L1 block at that number (hash equality, A-L1VIEW); `anchorNumber` is monotone from the parent's (for the first Etna block, whose parent is a legacy block, the floor is C4-R07's anchor and reference floor `activationL1Number`, the L1 block that contains the activation record, not the drain header D, which precedes the record and supplies only C4-R08's hash binding (D25; B's W12 verdict on #22199, item 2), so the genesis child cannot be stamped before `activationTimestamp + ANCHOR_MIN_AGE`; for the first block after a CONFLICT restart the floor is C4-R12's `restartL1Number`); and, at every block, against its own `PH.timestamp`, `L1[a].timestamp ≤ PH.timestamp − ANCHOR_MIN_AGE` and `≥ PH.timestamp − ANCHOR_MAX_AGE`. Monotone, not must-advance: during an L1 stall leaders keep anchoring the last block, and a stall longer than ANCHOR_MAX_AGE halts honest production until L1 resumes (C2-R19).

*Every block carries its own anchor (D41).* A kind-FI request block has its own anchor `A_b` under V5, like a NORMAL block (C3-R05(b)); each block of a hatch carries the lander's anchor `A` and is evaluated under both bounds at its own `ts_j` (C3-R07: `T_A ≤ ts_0 − ANCHOR_MIN_AGE ≤ ts_j − ANCHOR_MIN_AGE`, and check 5, `T_A ≥ ts_0 + m − 1 − ANCHOR_MAX_AGE`, gives `T_A ≥ ts_j − ANCHOR_MAX_AGE` for every `j`, which the inbox checks at landing). No block of any kind inherits a V5 verdict, so the drift of a landed block's origin age past ANCHOR_MAX_AGE is zero (C3 §7: DRIFT_MAX = 0). This withdraws, as superseded by D41 (whose decision supersedes D14's inheritance and D22 items 3, 5 and 7), the inheritance rule of D14, the drift bounds of D22 item 3 (2 s, 63 s and 65 s) and the proof that a producer parked at ANCHOR_MAX_AGE always has a valid child: that proof answered J-1's trace, in which V8 forced an FI child onto a stale anchor, and after D39 no rule forces any block to be a request block, so the trace has no instance (§8's J-1 row). A producer whose anchor reaches ANCHOR_MAX_AGE advances it in its next block, which exists under A-L1LIVE and A-L1VIEW.

The L1 state root is not an L2 input. The former V5(e) clause, forced-inclusion placement, became V8 (round 3, H6) and is now C3-R05(b)'s contiguity (C7-R11). Node and attester under A-L1VIEW; the guest asserts the same equality against the witnessed RLP header, the monotonicity and the age bounds at every block (C2-R04, C2-R19), together with `s_i ≤ T_{A_b}` for every kind-FI block (C3-R08), and the inbox checks the anchor tip (C2 L7) and, for a hatch, check 5 of C3-R07. Identical across honest nodes because it reads L1 blocks at least ANCHOR_MIN_AGE old; a node lacking `a` is pending-anchor (ANCHOR_WAIT, quoted S2 §6), never invalid; a reorg of `a` invalidates `b` identically everywhere and the range is unlandable (TH17, TH12). **Adversary schedule:** a fabricated anchor hash (TH17: attestable only if `Q` attesters skip V5, revealable only on an unlanded chain, which cannot land and is replaced; C2-R19); a stale anchor inside the 1,800-s legal window (not invalid; no rule obliges a block to serve a request, D39, and the request's own bound is C3's hatch, C3 §9); a hatch lander that picks an old `A` to give the hatch a pre-signal origin (refused: every block is evaluated under the upper-age bound at its own timestamp, and check 5 is the inbox's form of it; `A` is also at or after the last executed entry's save, C3-R07 check 5); a kind-FI block anchored before its entry's save, to run a request in a pre-signal origin (`i < tail(A_b)` fails at step 12, and the guest asserts `s_i ≤ T_{A_b}`, C3-R05(b), C3-R08; vector C3-T22); an anchor younger than ANCHOR_MIN_AGE (honest V5 disagreement under ePBS, the reason for the floor); a producer keeping a pre-signal origin (fails V5 after ANCHOR_MAX_AGE at its own timestamp at every honest attester, with no drift, C1's A-ORIGIN-PROGRESS as C2-R19 composes it). Source: certificate page §3 V5; Anchor page §1 H2, §2, §5 M3; round 3, H6; issue #22147; TH12, TH17; C3-R05, C3-R07 and C3-R08 (D41); the history in D14 and D22.

### C7-R10. V6, execution

**[assumed: proposed rule]** The node submits the received payload unchanged, with the envelope's `parentBeaconBlockRoot`, through `engine_newPayload`, never a rebuild, and requires VALID and an engine hash equal to `PH.blockHash` (S2-R03 (i)); execution runs C1-R02's system operations, EIP-4788 then EIP-2935, before ordinary transactions, outside the block gas limit. No rule reads a transaction receipt: the block contains no protocol transaction, so no revert can leave a silent checkpoint gap. Node, attester (S2-R03 (ii) signs only after (i)) and guest, which recomputes `blockHash` from blob data and executes every block VALID from the parent state to exactly its `blockHash` (C2-R04). Identical across honest nodes: deterministic execution of a fixed payload plus equalities on header fields (A-EXEC). **Adversary schedule:** produced hash differs from signed hash, the pre-Etna rebuild-from-attributes failure (excluded three times, S2-R03); a fake anchor receipt or a synthetic anchor transaction (C1-R02: no transaction position is reserved, a zero-transaction block is valid); builder and importer disagreeing on operation order or gas accounting (C1-R02's adversary schedule; taiko-geth#601 is the C4 prerequisite). Source: certificate page §2, §3 V6; Anchor page §1, §11; C1-R02; issue #22147.

**[assumed: proposed rule, revision note 2026-10-03, finding forced-inclusion-02]** **prevRandao.** Every Etna block, of every kind and view (NORMAL, FI, GENESIS_CHILD, FORCED; holder views, sentinel view 255 and hatch view 254), has `header.mixHash` (the payload's `prevRandao`) equal to `keccak256(abi.encode(uint256 parent.difficulty, uint256 b.number))`, where `parent` is the header of `b`'s parent and `b.number` is `b`'s height. This is the derivation the current Shasta/Unzen clients use and Etna keeps unchanged [assumed: inherited; source `CalculateShastaMixHash`, packages/taiko-client/bindings/encoding/input.go:153, and packages/taiko-client-rs/crates/driver/src/derivation/pipeline/shasta/pipeline/payload.rs:438-439]. Under Unzen, `difficulty` is an execution output of the parent (its zk gas used, packages/taiko-client/pkg/preconf/payload.go:23) [assumed: Unzen execution-client behaviour; open, §11 item 27: the clients pass `difficulty` to `engine_newPayload` as the `headerDifficulty` sidecar (packages/taiko-client-rs/crates/driver/src/sync/engine.rs:270-281), and Etna relies on the execution client recomputing it as the block's zk gas used and rejecting a payload whose supplied value differs]. The field is therefore derivable, which is why C2-R02's `headerCore` omits it. Node and attester check the equality as part of V6, before `engine_newPayload`; a block whose `prevRandao` differs is **invalid** at step 13. The guest recomputes it from the parent header it already holds (the witnessed parent header for the first block of a range, the previous block's header after that) when it rebuilds each header to `blockHash` (C2-R04). Identical across honest nodes [proven: it is a pure function of the parent header and the height, both fixed before `b` is evaluated]. L2 `PREVRANDAO` carries no randomness: anyone holding the parent header predicts it [proven, from the formula]; Etna makes no randomness claim for it, as Shasta made none. **Adversary schedule:** a leader choosing `prevRandao` to steer an L2 contract (invalid at step 13); two clients filling the field differently for a hatch block, where no signer fixes it (excluded: C3-R07's content list cites this rule).

### C7-R11. V8, request blocks (the rule is C3-R05(b), with contiguity)

**[assumed: proposed rule, C7's part only]** V8 is one conjunct of the predicate: "V8, request blocks (C3-R05(b), with contiguity)" (C3 §10's C7 row, D41). Its content is C3-R05(a) and (d) (the decoded manifest within FI_GAS_LIMIT or LEGACY_FI_GAS_LIMIT and FI_ZK_GAS_LIMIT, over-budget transactions skipped, empty past FI_EXPIRY for BLOB and LEGACY entries, the C1-R05 pin as a system operation), checked by execution at step 13. **Request-block validity is landable (C3-R06), up to the gate.** C3-R06's landability claim: every prefix range of a VALID_GOSSIP chain above `lastLanded` satisfies C3-R06's steps 1, 3 and 4 for some `(fiHeadAfter, v, fiReplayIds)`, and only the gate (step 2) and the two MAX_FI_PER_LANDING bounds can refuse it, a refusal D39 states (G6, C2-R10). ### C7-R12. V9, record size

**[assumed: proposed rule]** The canonical record of a sequencer block, `headerCore ‖ seqSig ‖ [viewChangeBytes] ‖ txListBytes`, is at most RECORD_MAX = 130,035 bytes, so the framed single-block payload of C2-R02 (9 framing bytes plus the record) fits one blob of 130,044 usable bytes (quoted, C2 §12, open there) and any single certified block is landable alone at every slot time. ### C7-R13. V10, term budget

**[assumed: proposed rule]** The sum of canonical record bytes over the sequencer blocks of one term is at most TERM_BYTES_MAX = 5 × LANDING_UNIT = 1,270,000 bytes (LANDING_UNIT quoted, C2 §12), and each block's zk-gas is within the per-block zk-gas limit the execution client already enforces (BLOCK_ZK_GAS_LIMIT, quoted from C3 §7 as 100 M under zk_gas_spec, §7). Kind-FI request records, replay blocks included, are sequencer records and count toward the sum (C3-R05(b): "inside V9 and V10"; C3 §10's C2 row); hatch blocks (view 254) are exempt, the guest skipping V10 for view 254 (C3-R07). The exemption of FI blocks that round 4 (R4H-6) introduced is withdrawn with the obligation it protected (D41): no rule requires a request block (D39), so a budget spent on request records makes no block invalid except under V10 itself, and including a request is the sequencer's choice under C3-R11's serving policy. Node, attester and guest. Identical across honest nodes: a sum over the term's blocks on the node's own chain. Consequence, not a rule: the bound sets the client throughput target (about 20 KiB/s, C2 §12), which the DAO can raise only with C2-R16's exposure and S3's reserve re-derived (round 6, R6H-3). **Adversary schedule:** a term too large for anyone to land at a profit (round 3, H2); a holder at its buffer certifying a term nobody is paid to land (round 3, H2; answered by C2-R16 and C2-R17 given this bound); a backlog that bleeds an honest leader through the budget (R4H-6's case; after D39 no block must carry a request, so a backlog consumes budget only when the sequencer chooses to serve it, and the request's bound is the hatch's, C3 §9). Source: certificate page §3 V10; round 3, H2; round 4, R4H-6; round 6, R6H-3; C3-R05 and C3-R07 (D41).

*Holds and re-entry (B's W12 verdict on #22199, item 1).* Each step has three outcomes: **passed**, its inputs complete and fixed and its check true; **failed**, its inputs complete and its check false, which ends evaluation with **invalid**; **unresolved**, an input missing (`S(t)` at steps 2 and 4, the opening object or a witness that verifies at step 4, a sentinel object's reference block at step 4, the parent, the carried certificate's preimage, the L1 reference block, or the parent's own verdict while the held parent is unresolved and not landed at the block's own reference at step 7, the parent's PH at steps 8 to 10, block `a` and the parent's PH (monotonicity) at step 11, and the records of the chain above `lastLanded(A_b)` or the L1 block `A_b` at step 12; no step's input is the parent's acceptance except step 7's own, which fails only on the parent's final **invalid** and the held record at the block's reference (D60 (1)), so no step can be read as failing on an acceptance that the parent's own verdict or the landing record at the block's reference may still supply; vector C7-T17's request-block case). The node evaluates steps 1 to 12 in order, records each outcome and, at an unresolved step, continues with the next step whose inputs are complete, so every rule evaluable without the missing context is evaluated before a hold (C7-R01); step 13 runs only when steps 1 to 12 have all passed. If no step failed and one is unresolved, the block is held: pending-parent when an object that travels with the parent range is missing or the parent is not yet accepted, pending-anchor when an L1 block at a fixed reference is. **When both are missing** the block is pending-parent, and its drop time is PENDING_TTL from entering that hold; when the last parent-range object arrives and an L1 block is still missing, it re-enters, evaluates what it can, and enters pending-anchor with ANCHOR_WAIT from that moment, so each hold has one TTL and the drop time is fixed. The choice affects only how long a node keeps the block, never its verdict, since a drop is no verdict and the block re-enters on receipt. When context arrives, within PENDING_TTL or ANCHOR_WAIT, or after the TTL on receipt (C7-R01), the block **re-enters at the earliest step not yet passed** and evaluates every step not yet passed, in order; a passed step is not re-run. So a block held before its opening object arrived evaluates step 4 on re-entry, whichever hold it waited in and whichever context arrived first, a landing included, and no check is skipped (vector C7-T17). Re-entry starts only from a hold or a drop: an **invalid** block is never re-entered, because no step fails on an input that can still arrive (C7-R07's hold on a parent whose verdict is unresolved, D60 (1)).

## 6. State machine

**[assumed: projection of C7-R01 and C7-R14 onto S2 §5's BLOCK machine]** The BLOCK machine below is S2 §5's restricted to C7's part, with C7-R14's step numbers written on the arrows; the states above SEQUENCED are S2's. A hold has one exit on expiry, the drop without a verdict (D14; D17, B-C7-06): INVALID is not a TTL outcome anywhere in C7, so that no verdict reads a node's clock (§8); the dropped block is re-entered at the earliest step not yet passed on receipt of the missing context, with the same verdict (C7-R14's re-entry argument; B's W12 verdict on #22199, item 1). S2 §5's machine, which at `0403a54` wrote the exit as `--> RECEIVED | INVALID`, is aligned to this in the S2 revision (W10; §11 open item 5 is the citation obligation).

```text
RECEIVED --a step of 1..12 fails--> INVALID (seqSig kept as evidence; final; step 7 fails on the parent only when it is invalid and the held record at the block's own reference shows no landing of it, C7-R07, D60 (1))

PENDING_PARENT | PENDING_ANCHOR --TTL elapsed--> DROPPED (no verdict) --missing context received--> RECEIVED (re-enter at the earliest step not yet passed)
RECEIVED --steps 1..12 pass, step 13 fails--> INVALID (final)
RECEIVED --every step passes--> VALID = S2's SEQUENCED

any --the block lands (C2)--> accepted under VALID_LANDED, whatever the local VALID_GOSSIP verdict was (C7-R15)
```

The last transition is D22's (item 4, C7-11), a resolution of a hold, not a revision of a verdict; the range transition D38 added after it is deleted with the range reference (D58 (1)). Acceptance reads the landing at the block's own fixed L1 reference only, a block whose held parent is unresolved and not landed there is held at step 7, and one whose parent is **invalid** and not landed there is **invalid** at step 7 (C7-R07, D60 (1)), and the arrival of the reference block is ordinary context. A block re-enters at its earliest step not yet passed, never at step 7 by default: a block held with step 2 or step 4 unresolved (its `S(t)` or its opening object missing) as well as step 7 evaluates step 2 or step 4 first when it re-enters, so a landing never lets a block become **valid** with its signer or its opening unchecked (vector C7-T17's landing case). A block whose own reference precedes its **invalid** parent's landing is **invalid** at step 7, finally, whatever later blocks extend it (D58 (1), D60 (1)); the added transition above reaches INVALID by re-entry, never by revising a verdict. INVALID has no outgoing transition except the landing acceptance under VALID_LANDED, which is C2's and leaves the VALID_GOSSIP verdict as it was; this is the S2 §5 reading C7 asks for (§11, the S2 row).

This is the certificate page's claim "V1 to V6 are identical across honest nodes; no rule reads wall clock or 'latest'", extended to V8 to V10 by the same reading. Which chain honest attesters certify before landing is a separate claim, resting on A-QUORUM (C7-R15); the verdict on any one block is not. Not proven here: that the guest's implementation of the same rules agrees with the node's (A-EXEC, a conformance obligation, §10).

**[open: totality; proven only for the defined cells of C7-R04's matrix (B's W12 verdict on #22199, item 2)]** For every row whose cells are defined, the row names an authorization (a signer checked by V1, or the L1 landing record for FORCED), an opening and parent rule and the subset of V1 to V10 it evaluates; the rows cover every permitted `(view, kind)` pair of C7-R04's first table, and every pair outside it fails H3. The predicate is **not total** while these cells are undefined, each a byte or a predicate an implementer would otherwise choose, not a measurement: the sentinel `carriedCertHeight` byte (S2 and C8, item 15), the FORCED row's PH-equivalent `vcHash` and `carriedCertHeight` (C3 with C2 and C8, item 23), the genesis child's signer beyond the default, its closing view change and every launch outside view 0 of `firstEtnaTerm`, the no-committee launch included, which has no permitted row (S1 and S2 with C4, item 14), and the first block after a CONFLICT restart (C2, S2 and C8, item 25). The sentinel cells that S1 has now defined (the reference, the regime tests, the first block's parent, the bond, exclusion, span and same-owner checks) leave this list (D38(b), D45, D48, D52). What remains is the late-landing delay that C7-R07's timing condition states, a pause of honest production on the landed parent, not an undefined cell. With complete inputs in a defined cell every block is **valid** or **invalid** (C7-R01, D60 (1)): no permanent hold remains as a third result.

**[proven: one block, one envelope]** H1 binds `(termId, view)` into the header, hence into `blockHash`, which PH names under `seqSig`; a block presented under another view's PH fails H1 at every node and, if both PHs are signed, is S1 evidence (S2-R21). Two envelopes for one execution hash differing in `vcHash` or `carriedCertHash` are two PHs (S2-R03's identity rule) and V2's chain rule accepts at most one at each position of a chain.

**[proven: no clock in validity, conditional on A-L1VIEW]** V4 reads `parent.timestamp` and `termEnd(t)`; V5 reads an L1 block's own timestamp; acceptance by landing reads the L1 record at a fixed reference (C7-R07); the sentinel tests (the regime, dead mode with `lastLandedTerm`, S1-R18's post-deadline path with `termEnd(t′) + LAND_WINDOW`, the parent `lastLanded`, the bond and exclusion reads, the span `termStart(u) < r + DELAY_REG`) read the state and the timestamp of the L1 reference S1-R16's object signs, never a node's clock or L1 head (D22 item 4, D38(b), D45(3)); V8 reads the L1 state at the block's own anchor (C7-R11); the attestation bounds STALE_MAX and CLOCK_SKEW gate signing only (S2-R04). The only timers in C7 are the holds of C7-R01, which end an evaluation without a verdict and leave the block to re-enter on receipt (D14; D17, B-C7-06); an INVALID after the TTL would make validity depend on the node's clock, which is why C7 lists no such transition (§6). S2 §5's alignment (open item 5) is a citation obligation and no longer a condition of this claim.

**[proven: V8's verdict is fixed by the block's own inputs, conditional on A-L1VIEW and A-FI]** Step 12 reads the queue state in the L1 state at the block's own anchor `A_b`, which step 11 has fixed, the entry fields, which never change once saved, and the request blocks recorded on the block's held chain above `lastLanded(A_b)`, which are signed objects.
