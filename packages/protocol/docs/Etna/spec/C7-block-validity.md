## 1. Scope, vocabulary and claim convention

**[assumed: section boundary]** C7 owns the one deterministic statement every node, attester and proof guest implements to decide whether an L2 block is valid: the composition of C1's header component, the header rules H1 to H3 and the validity rules V1 to V10 (V7 is C2's landing binding and V8 is C3-R08's rule; both are only named here, with the step at which V8 is evaluated), the three results, the validation order, the permitted `(view, kind)` table, and one test-vector obligation per rule. C1 owns the physical header profile, the system operations and the oracle (C1-R01 to C1-R03 are C7's component, invoked, not restated); C2 owns the landing, the journal, what the guest proves beyond the predicate, V7 and the origin authentication A-ORIGIN; C3 owns the forced-inclusion queue, due-ness, the derived cursor and stall clock (C3-R05), the void set (C3-R06), FI block content (C3-R07), the placement rule V8 itself with its waiver (C3-R08), the forced batch (C3-R11) and the constants V8 reads; C4 owns the migration, the genesis parent and the drain block; S1 owns `leader(t, v)`, `committee(t)` and the registry snapshot; S2 owns the opening objects, certificates, view changes, the attestation policy, the confirmation levels and the equivocation key; S3 owns slashing; C6 the registers; C8 the consolidated interfaces. None of their text is duplicated here (`00-decomposition.md` §1; D9, D10).

**[assumed: notation]** **assumed** heads a proposed rule or a premise; **proven** means an argument on this page, not machine verification; **open** means unresolved, with the closure condition named. An identifier `C7-Rnn` has exactly one normative definition; the rule names H1 to H3 and V1 to V10 are the pages' labels and are kept beside the ids so that C1, C2, C3 and S2 can keep citing them. §7 is C7's only register of numbers; "quoted" marks a value another section owns that a C7 rule reads. ## 2. The predicate and its results

### C7-R01. Composition and the three results

**[assumed: proposed rule]** For a block `b` a node holding `PH`, `seqSig`, the payload, its message set (S2's objects) and its L1 view evaluates, in the order of C7-R14, C1's component (C1-R01, C1-R02, C1-R03), the header rules H1 to H3 (C7-R02 to C7-R04) and the rules V1 to V6, V8, V9 and V10 (C7-R05 to C7-R13), each applied as the mode matrix of C7-R04 says for the block's kind and regime. The result is:

- **unknown context** if C1's component returns `UNKNOWN_CONTEXT`, or the parent is not held (V3's pending-parent state), or the anchored L1 block `a`, or the L1 reference block at which C7-R07 reads a parent's landing, is not in the node's L1 view (the pending-anchor state), and no rule evaluable without the missing context has failed (C7-R14 evaluates every such rule before a hold is entered, V6 excepted because its cost depends on the payload, so a hold is never entered by a block that an evaluable rule other than V6 already rejects); the block is held and re-evaluated when the context arrives, within PENDING_TTL or ANCHOR_WAIT (quoted, S2 §6); a hold that expires has one outcome, D14's: the block is dropped without a verdict and re-entered at the same step on receipt of the missing context (D17, B-C7-06), so a node that lacked context never produces **invalid**; S2 §5's machine is aligned to the same outcome in the S2 revision (W10; §11 open item 5 is the citation obligation only);
- **invalid** if any evaluable rule fails, C1's `INVALID_C1` included; failure is silence: the block is dropped, `seqSig` is retained as evidence (S2-R17, S2-R21), and nothing is gossiped about the failure;
- **valid** if C1's component returns `C1_PASS` and every rule of the list passes.

H1 to H3 are listed as separate conjuncts in C7; the pages fold them into V6, and this sentence is the only place C7 says so. `C1_PASS` is never whole-block validity (C1-R01); a valid block is **SEQUENCED** in S2's BLOCK machine and nothing more: certification, locking, landing and finality are S2's and C2's. No rule reads a wall clock, the L1 head, "latest" registry state, a landing time or the node's wider message set; the only inputs are the signed objects the block and its ancestors name, the node's own chain, L1 facts read at a fixed reference that a signed object names and that is at least ANCHOR_MIN_AGE old (V5's block `a`; the L1 landing record C7-R07 reads; the sentinel tests of C7-R04 (open until S1-R16's object names a reference, §11 item 20)) and the registry snapshot at `termStart(t)` (certificate page §3; claim "V1 to V6 are identical across honest nodes"; D22).

*The two named predicates (D17, B-C7-04).* **VALID_GOSSIP** is the whole of the above: the predicate every node and attester evaluates on a block before it lands, and the result S2-R04 reads. **VALID_LANDED** is the conjunction of what the guest asserts (C2-R04) and what the inbox checks (C2-R05), nothing more and nothing less: the predicate by which an importer accepts a landed range on the strength of the L1 record; its exact rule set is C2's to list, and C7 reads it (§11). The two differ, as far as C2's listing is not yet available, in one conjunct and one input (assumed, C7-R15, §11 item 18; whether the verification of intermediate opening objects against their committees is a second conjunct is checked against C2-R04 and C2-R05). The conjunct is the verification of a carried intermediate certificate against its committee (V3, C7-R07), which the guest skips and the inbox checks only for the end certificate (C2-R05 L5). The input is V5's: before landing V5 reads the node's own L1 view, and at landing the same conjunct reads the anchored header that C2-R19 authenticates against L1 history; no conjunct is missing there (D22 item 1, C7-4; C7-15). A landed range satisfies VALID_LANDED by construction of the landing; an importer whose pre-landing VALID_GOSSIP verdict on a landed block was **invalid** yields to the landing, the way its lock yields to a landed replacement (S2-R15's lock reset), and the object that failed is evidence, never a reason to fork from the landed chain (C7-R15). Agreement among honest nodes on the chain they certify before landing rests on A-QUORUM; the gap between the two predicates is closed by evidence (C7-R15), not by a verification of every carried certificate on L1, and only where the carried certificate's preimage was published (D22 item 6; the unpublished case is C7-R15's residual).

**Adversary schedule:** a producer that makes honest nodes disagree by feeding them different context (the pending states hold, never reject, so disagreement is delay, not a fork); a producer that relies on a node's missing context being read as invalidity (excluded: a missing context never produces **invalid**); a node that reads its own clock into the verdict (excluded by construction; S2-R04's clock bounds gate signing only); a node that reads an object it acquired later, a higher certificate in particular, into a verdict it already holds (excluded: every input is an object the block or its ancestors name, C7-R14's re-entry argument; the refusal of a FALLBACK while a higher certificate is held is S2-R14's attestation policy, D17); a holder and a malicious quorum landing a chain that VALID_GOSSIP rejects (lands under VALID_LANDED with the evidence of C7-R15 on L1, when the preimage was published); a node that reads the L1 landing record or a sentinel test at its own L1 head, so that two nodes disagree by when they looked (excluded: C7-R07 and C7-R04 fix the reference by a signed object, D22). Source: certificate page §3 and §10; C1-R01; D14; D17 (B's W8 verdict on #22199 (2026-10-01), B-C7-04 and B-C7-06); D22.

**[proven: the results are exhaustive and determined]** Every rule is a predicate on the inputs named above; each is either evaluable (its inputs held) or not. If an evaluable rule fails the result is **invalid** whatever else is missing; if none fails and some rule is unevaluable the result is **unknown context**; otherwise every rule is evaluable and passes, **valid**. A hold that expires produces no result and changes no input, so the block's eventual verdict is the one it would have had without the expiry (C7-R14's re-entry argument). Two honest nodes holding the same inputs compute the same result because no rule reads node-local state other than those inputs (A-EXEC for V6, A-L1VIEW for V5 and for the landing record at its fixed reference, A-REGISTRY for V1 and V2; the sentinel rows excepted until S1-R16's object names an L1 reference, §11 item 20). The verdict **invalid** versus **valid** does not depend on evaluation order; only the moment at which **unknown context** resolves does, which C7-R14 fixes so that a block failing any rule evaluable without the parent or the anchor is never held, a block the signer did not produce in particular; V6, always last, is the one rule a hold may precede.

## 3. The header rules H1 to H3

### C7-R02. H1, extraData

**[assumed: proposed rule]** `extraData` is exactly P-EXTRA = 7 bytes in C1-R03's layout, `basefeeSharingPctg(1) ‖ termId(4) ‖ view(1) ‖ kind(1)`; byte 0 equals BASEFEE_SHARING_PCTG (quoted, C1 P-FEE-SHARE); `termId` and `view` equal `PH.termId` and `PH.view`; `kind` equals the block's kind under H3. Which term `termId` names is the mode matrix of C7-R04: `t` for a holder view, the term containing `PH.timestamp` for a sentinel-255 block, and, for a forced batch, the term containing `ts_0` (D17; C3-R11 carries it and the guest derives it with the other PH-equivalent fields). The physical widths and the rejection of other lengths are C1-R03's; H1 adds the three equalities. Checked by nodes and asserted by the guest, which rebuilds PH from the blob record and compares (certificate page §2 (iii)). **Adversary schedule:** a sequencer presents one execution block under another view's signed header (the `(termId, view)` equality binds the block to one PH, and two PHs at one `(t, v, vcHash, height)` are S1 evidence, S2-R21); a block that pays the sequencer a fee share other than the published constant (the byte is checked, not read, so the engine's fee decoder and the published constant cannot disagree, TH25). Source: Anchor page §1 H1; certificate page §3 V6; issue #22147.

### C7-R03. H2, the anchor field

**[assumed: proposed rule]** `parentBeaconBlockRoot ≠ 0`. The equality of that word with the hash of the node's own canonical L1 block numbered `PH.anchorNumber` is V5's check (C7-R09, C1-R01), not H2's; H2 is the one check on the field that needs no context, so it is evaluated before the holds (C7-R14, step 6), and a node lacking block `a` is pending-anchor at step 11, never invalid under H2. The non-zero word is what separates an Etna header from a Shasta header; the fork-time argument built on it (no contract immutable and no stored fork time can disagree with the clients) is C1-R07 and C1-R09's and is not repeated here. **Adversary schedule:** a child block with a zero root after activation, including during an L1 stall (invalid under H2 and C1-R01; leaders keep anchoring the last L1 block, V5 being monotone rather than must-advance); the first-Etna-block attack of C1's attack table (C1-R07). Source: Anchor page §1 H2, §5; certificate page §3 V5, V6; issue #22147.

## 4. The validity rules V1 to V10

Each rule names its check, who evaluates it (node, attester, guest), why it is identical across honest nodes, and the schedule it covers. The attester evaluates exactly what the node evaluates (S2-R04 reads C7's result); "guest" marks the rules C2-R04 asserts inside the proof.

### C7-R05. V1, signer

**[assumed: proposed rule]** `ecrecover(seqSig) == leader(PH.termId, PH.view)`, the holder of S1-R12's walk at `termStart(t)`, read with the sequencer key valid at `termStart(t)` (S1-R05), under S2-R03's signing domain. Node and guest: the guest verifies the recovery and exports the leader as a public input that C2's L4 checks against `isHolder` (C2-R05; certificate page §2 (iii)). Kind FORCED blocks have no signature and skip V1 (forced-inclusion page §6); for the sentinel-255 regimes and the genesis child the signer V1 checks is the one C7-R04's matrix names for the row (a bonded address under S1-R15 or S1-R17, the sortition holder under S1-R18, the first term's leader by default for GENESIS_CHILD; for a later block under a sentinel opening, the signer of the first block under that opening, D22 item 1, C7-13; that clause needs the parent and is evaluated at step 8 (C7-R14); at step 2 V1 checks the row's bond test only), with the open cells of that matrix as its residue. Identical across honest nodes because it reads a signed object and registry state at least LOOKBACK old (A-REGISTRY). **Adversary schedule:** a block signed by anyone but the holder (dropped; a non-holder cannot even be timed out, S2-R07); a block signed by a holder for a view it does not hold (the leader of `(t, v)` is a function of `(t, v)`); a block signed by a holder whose rights read "latest" state, the pre-Etna failure (excluded by S1-R05's read at `termStart(t)`); a sentinel chain whose blocks are signed by different bonded addresses (excluded: the later-block signer clause, D22, C7-13; vector C7-T16). Source: certificate page §3 V1; S1-R05; S1-R12; D22.

### C7-R06. V2, view entry: the window, the logical opening and its first block

**[assumed: proposed rule]** `PH.timestamp ∈ [termStart(t), termEnd(t))`, stated once here and shared with V4 (C7-R08); for a sentinel-255 block `t` is the term containing `PH.timestamp` (C7-R04's matrix). `PH.vcHash` is D16's logical opening id (§1): the object it names is S2-R01's view change for a holder view (the TIMEOUT, TERM_END or FALLBACK view change that closed the previous view, or the REPLACE or RESUME view change that reopens the same view number under a new logical opening), S1-R16's object for a sentinel-255 chain, and none for kind FORCED and GENESIS_CHILD (C7-R04). The named object is held and verified against its signer committee from its own fields and its witness beside the id (A-OBJECTS: S2-R10); a FALLBACK is verified from its fields and witness only, a quorum of `committee(signerTerm)` at its redraw count with `signerTerm > t`, and S2-R14's L1 gates are not a V2 input: they belong to C2's L4 at landing and to S2-R14's attester policy (D22 item 4, C7-3 and C7-14). The **first block under an opening** is the block whose `PH.vcHash` names an opening object its parent's PH does not name (D17, B-C7-01); every other block is a later block of its parent's opening. For the first block under an opening, `PH.parentHash` is the opening's lock block, the block of `(lockHeight, lockPhHash)` the view change names, or `lastLanded` for S1-R16's object, and that parent is accepted (C7-R07) under the previous opening, the one its own PH names, or is `lastLanded` by the L1 record at the view change's signed `l1Ref` (D16, S2-R09: a RESUME or REPLACE locks at `lastLanded` and needs the L1 record, not a certificate, S2-R15; for S1-R16's object the reference is item 20's; the genesis parent is C4's). For a later block, `PH.vcHash` equals the parent's and the block extends its parent, accepted under that same opening (C7-R07).

*The `(termId, view)` chain rule (S2-R01, restored under D22 item 2, C7-7).* (a) A later block carries its parent's `(PH.termId, PH.view)`. (b) The first block under an opening carries the `(termId, view)` its object opens: a TIMEOUT `VC(t, v)` opens `(t, v + 1)`; a TERM_END or FALLBACK `VC(t, v)` opens `(t + 1, 0)`; a REPLACE or RESUME `VC(t, v)` opens `(t, v)`; S1-R16's object for `(lastLanded, t)` opens `(t, 255)`. So every change of `(termId, view)` between a block and its parent is a first block under an opening that opens exactly the new pair, which is S2-R01's "every change of `(termId, view)` is such a block". Kind FORCED and GENESIS_CHILD carry their row's pair (C7-R04). The rule reads the same for every way an opening arises: the first view of a term (opened by the TERM_END or FALLBACK view change of `t − 1`, whose lock is the last certified block of `t − 1`), a TIMEOUT (the first block of `v + 1` extends `lock*`), a FALLBACK (the later committee's lock), and the same-view REPLACE and RESUME reopenings (`v` unchanged, the logical opening new, the lock `lastLanded`). No refusal of a FALLBACK on the strength of a certificate the node happens to hold belongs here: whether a node attests under a FALLBACK while it holds a higher certificate of `committee(t)` is S2-R14's node side, an attestation policy that reads the node's message set, where D17 (B-C7-05) places it; V2 reads only the objects the block names. Kind FORCED blocks skip V2 (C3-R11); kind GENESIS_CHILD has no opening object and V2 applies its window only (C7-R04). Node, attester and, for the chain structure only, the guest: the guest checks that `vcHash` changes exactly at the first block under an opening and that the first block of the range carries `vcHashOfFirstBlock` (C2-R04); it verifies no committee signature, which C2's L4 does on L1 for the view changes a landing consumes. Identical across honest nodes because it reads the objects the block names, S1-R05's registry read at `termStart(t)` (through S1-R12's holder) and, for a lock at `lastLanded`, the L1 record at the reference the opening object signs (A-L1VIEW), never the L1 head or the node's wider message set (D22). **Adversary schedule:** a backup starting above the lock or on another branch (the first block under its opening must extend the lock); a leader opening a view with an object that closes nothing (S2-R10's verification); a block with its parent's `vcHash` whose `parentHash` is not that parent (fails at step 8: a later block must extend its parent); a second block that names the opening and the lock as its parent (valid as a first block under the opening, since the lock's PH does not name the opening; it is an equivocating sibling of the first, S2-R17, not invalid under V2, D22 item 1, C7-0); a view taken over with no view change, a block of `(t, v + 1)` under `(t, v)`'s `vcHash` (fails rule (a)), a holder of `(t + 1, 0)` extending `t`'s uncertified tail under `t`'s `vcHash` (fails rule (a)), and a block of `(t, 3)` naming `VC(t, 0, TIMEOUT)` to skip the locks of views 1 and 2 (fails rule (b): that object opens `(t, 1)`) (D22 item 2, C7-7; vectors C7-T05); one execution hash under two `vcHash` envelopes (two PHs, S2-R03's identity rule); a block of term `t` stamped in `t + 1` (the window); two openings with equal fields and different witnesses (D16: one id, so one opening and one equivocation key, S2-R17). Source: certificate page §3 V2; S2-R01; S2-R10; S2-R11; S2-R15; S1-R16; round 2, S9; issue #22147; D16; D17 (B's W8 verdict on #22199 (2026-10-01), B-C7-01 and B-C7-05); D22 (items 1, 2 and 4).

**[proven: every block has exactly one admissible parent rule and one admissible `(termId, view)`]** A block's PH names one opening and its parent's PH names one opening; the two ids are equal or they are not. If not, the block is the first under its opening, the lock rule applies and rule (b) fixes its `(termId, view)` from the object's kind and fields; if equal, the extension rule applies and rule (a) fixes it as the parent's. The cases are disjoint and exhaustive, so the contradiction B-C7-01 found (block 101 of view 1 failing a parent-accepted-in-`(t, v)` rule while block 102 failed a lock rule) cannot arise: 101 names view 1's opening, which its parent 100 does not, so 101 extends the lock 100, accepted under view 0's opening; 102 names the same opening as 101 and extends 101 (vector C7-T05). A third block 103 naming the same opening with parent 100 is, by the same case split, a first block under the opening (100 does not name it), extends the lock and is valid; it competes with 101 at one height under one opening, which is S2-R17's equivocation, never a V2 failure (D22 item 1). No block, other than kind FORCED and GENESIS_CHILD, whose pair is their matrix row's (C7-R04), can change `(termId, view)` without being a first block under an object that opens exactly the new pair, so a view or term is never entered without its view change and its lock (D22 item 2).

### C7-R07. V3, parent and carried certificate

**[assumed: proposed rule]** The parent is held and accepted, else the block is pending-parent (a range request, bounded by PENDING_TTL, quoted S2 §6); under which opening it is accepted is C7-R06's rule (the previous opening for the first block under an opening, the same opening otherwise), so V3 never asks for a parent accepted under the opening the block itself begins (D17, B-C7-01). **Accepted** (D22 item 4, C7-11) means: valid under VALID_GOSSIP, or landed by the L1 record as read at a fixed L1 reference, namely the `l1Ref` that the opening object the block's PH names signs, at least ANCHOR_MIN_AGE old, or, when that object names none (a TIMEOUT, TERM_END or FALLBACK, whose `l1Ref` is zero, S2-R09), the block's own anchor `a` (inherited for kind FI, C7-R09); the reference for S1-R16's object is item 20's. The landing is thereby an input fixed by the block's signed fields, never the node's L1 head: two nodes that hold the same objects and the same L1 block at that reference agree on acceptance in whatever order the landing and the block arrived. A node that lacks the reference block holds the block pending-anchor at step 7 and re-enters there (C7-R01). *Limit of this reference, open (§11 item 24, routed to the arbiter as an amendment of D22 item 4).* The fixed reference cannot contain the parent's landing in two cases, so a parent accepted only by its landing has no accepted child there. (1) An FI child: it inherits its parent's anchor `a` (C7-R09), and a landing that carries the parent names `a`, so it lies after `a`; with an entry due and the run below MAX_FI_RUN the child must be FI (C3-R08), a NORMAL child fails V8 at step 12, and under a TIMEOUT, TERM_END or FALLBACK opening the FI child fails step 7 at every node, forever; production waits for the next opening that waives V8 (C3-R08) or names an `l1Ref` containing the landing. (2) A later block under a REPLACE or RESUME opening: its reference is the opening's `l1Ref`, fixed before any landing of the chain it opens, so a parent of that chain accepted only by its landing is never accepted, whatever the block's own anchor. Candidate closures for the arbiter: (a) read the landing at the later of the opening's `l1Ref` and the block's own anchor, both signed and at least ANCHOR_MIN_AGE old, which closes case (2) and leaves case (1) as a limit of at most one term with an entry due; (b) C3 waives V8 for the first block whose parent is accepted only by its landing. Until the arbiter decides, the reading above stands (D22 item 4 binds) and vector C7-T06's landing case states the results under it. `carriedCertHeight ∈ {n − 1, n − 2}` (CERT_LAG_MAX = 1, quoted S2 §6); the carried certificate verifies against the committee of its redraw count (A-OBJECTS: S2-R05) and names the ancestor at that height; the first two blocks under an opening carry the view change instead (S2-R11); kind FORCED, GENESIS_CHILD and sentinel-255 blocks carry nothing (C7-R04). The certificate verification is a conjunct of VALID_GOSSIP only: the guest rebuilds `carriedCertHash` into PH from the blob record and verifies no certificate (C2-R04), and the inbox verifies the end certificate alone (C2-R05 L5), so VALID_LANDED does not contain it (C7-R01, C7-R15). Node and attester. Identical across honest nodes: the objects the block names. **Adversary schedule:** a withheld parent (held, then at the TTL dropped without a verdict and re-entered on receipt, C7-R01); a block carrying a certificate for a block off its ancestor line, or with fewer than `Q` bits, or of the wrong `(t, v)` (invalid under VALID_GOSSIP, and S6 evidence under S2-R21 when signed); a holder and a malicious quorum that land a correctly executed chain carrying such a certificate (it lands under VALID_LANDED; the landed block is the evidence object of C7-R15 when the certificate's preimage was published, and a residual otherwise; D17, B-C7-04; D22 item 6); a block whose parent was invalid under VALID_GOSSIP and then landed, received before the landing at one node and after it at another (the same verdict at both: acceptance reads the landing at the block's fixed L1 reference, and §6 re-evaluates the descendants of a landed INVALID block; D22 item 4, C7-11; vector C7-T06); a tail of unattested progress longer than CERT_LAG_MAX + 1 (the leader holds, S2 §5). Source: certificate page §3 V3; D17 (B-C7-01, B-C7-04); D22 (items 4 and 6).

### C7-R08. V4, time

**[assumed: proposed rule]** `PH.timestamp ≥ parent.timestamp + 1`; the upper bound `PH.timestamp < termEnd(t)` the page writes in V4 as well is V2's window (C7-R06) and is stated once there. No wall clock and no L1 landing time: the 1-s cadence is a rewarded duty whose hard bound is S2-R07's timeout, never a validity rule (after the #22188 review, 2026-10-01). Kind FI blocks have `timestamp = parent.timestamp + 1` exactly (C3-R07). Kind FORCED blocks skip the window's upper bound: `ts_0 = max(parent.timestamp + 1, T_A + ANCHOR_MIN_AGE)` and `ts_j = ts_0 + j` (C3-R11). Node, attester and guest (C2-R04: "timestamps obey V4"). S2-R08 (a) relies on `termEnd(t) − 1` being the term's last possible timestamp; S3-R21 relies on the lower bound with V2's window giving at most TERM (quoted, S1) blocks per term. Identical across honest nodes: two integers of the chain. **Adversary schedule:** the pre-Etna retroactive invalidity, where the upper bound was the L1 landing time (rejected alternative, certificate page §17); a block stamped in the future (gated by S2-R04's CLOCK_SKEW at signing, not by validity); a term that crosses its end (the window). Source: certificate page §3 V4; C1-R03's strictly increasing timestamps.

### C7-R09. V5, anchor

**[assumed: proposed rule]** The header's `parentBeaconBlockRoot` is the hash of L1 block `a` whose number is `PH.anchorNumber`, and `a` is the node's own canonical L1 block at that number (hash equality, A-L1VIEW); `anchorNumber` is monotone from the parent's (for the first Etna block, whose parent is a Shasta block, the floor is C4's drain block recorded at `drainedAt`, so the genesis child cannot be produced before that block's timestamp plus ANCHOR_MIN_AGE); and, at the block that carries the anchor, `L1[a].timestamp ≤ PH.timestamp − ANCHOR_MIN_AGE` and `≥ PH.timestamp − ANCHOR_MAX_AGE`. Monotone, not must-advance: during an L1 stall leaders keep anchoring the last block, and a stall longer than ANCHOR_MAX_AGE halts honest production until L1 resumes (C2-R19).

*Which block carries the anchor, and inheritance (D14).* V5's two age bounds are evaluated at the block that carries an anchor, against that block's own `PH.timestamp`. A block of kind NORMAL or GENESIS_CHILD carries its own anchor. A block of kind FI inherits its parent's anchor (C3-R07: the parent's `parentBeaconBlockRoot` and `anchorNumber`, `timestamp = parent.timestamp + 1`) and inherits its parent's V5 verdict: the node checks that the two anchor fields equal the parent's and does not re-evaluate the age bounds against the FI block's own timestamp. C3-R08's hard cap MAX_FI_RUN = 2 (D17, B-C7-03: an FI block is valid only if fewer than MAX_FI_RUN consecutive FI blocks precede it, counted back from its parent, so after MAX_FI_RUN consecutive FI blocks the next block must be NORMAL even while entries are due, and that NORMAL block advances the obligation to the following block) bounds the drift of an inherited anchor's age past ANCHOR_MAX_AGE: each FI block is stamped exactly one second after its parent (C3-R07) and at most MAX_FI_RUN of them can follow the block that carried the anchor, so after a block that carried its own anchor the drift is at most MAX_FI_RUN × 1 s = 2 s (derived; the forced-batch bounds follow below); the NORMAL block that must follow the run is evaluated against its own timestamp, which forces the producer to advance the anchor. Before D14 this draft said that a parent at exactly ANCHOR_MAX_AGE has no valid child; that sentence is false under this rule and survives in C7 only as the closed J-1 trace of §8 and item 13 (D17, B-C7-03 and B-C7-07). A forced batch (view 254) is constructed by C3-R11: its block 0 carries the lander's anchor `A` and is evaluated at `ts_0 = max(parent.timestamp + 1, T_A + ANCHOR_MIN_AGE)` under both bounds, `T_A ≤ ts_0 − ANCHOR_MIN_AGE` (true by construction) and `T_A ≥ ts_0 − ANCHOR_MAX_AGE` (the upper-age bound, which the inbox checks as one of C3-R11's checks). Block 0 is the batch's first block, whose parent is the `lastLanded` of the landing that carries the batch (C3-R11); it is evaluated under both bounds even when its parent is kind FORCED with the same anchor, since forced batches may chain (C3-R11 (7)): inheritance never crosses a landing into block 0 of a forced batch. That sentence is scoped to block 0 of a forced batch and to nothing else (D22 item 3, C7-9): a kind FI block inherits its parent's anchor fields and V5 verdict whatever made the parent accepted (C7-R07), and for a parent accepted by its landing the verdict it inherits is the one C2-R04 asserted at that landing, so the inheritance reads the parent's fields, never L1 landing state. Such a child exists only where its fixed reference contains the parent's landing, that is under an opening whose signed `l1Ref` does; under any other opening an FI child of a parent accepted only by its landing is never accepted (C7-R07's limit, case (1); §11 item 24, open). The later blocks of the batch, 1 to `m − 1`, like block 0 of kind FORCED, inherit `A` and block 0's verdict exactly as a kind FI block inherits its parent's.

*The drift bounds (D22 item 3, C7-1 and C7-9; derived).* The age of an inherited anchor past ANCHOR_MAX_AGE, at the inheriting block's own timestamp, is: (i) at most MAX_FI_RUN × 1 s = 2 s for an FI run after a block that carried its own anchor (C3-R07's one-second stamp, C3-R08's cap); (ii) at most `j` s for forced block `j`, since `ts_j = ts_0 + j` and block 0's anchor is at most ANCHOR_MAX_AGE old at `ts_0`, with `j ≤ m − 1 ≤ 63` because `m ≤ 64` (C3-R11), so at most 63 s (an origin at most 1,863 s old); (iii) at most 63 + MAX_FI_RUN = 65 s for an FI run whose first block's parent is the last block of a forced batch (the first block of a RESUME, or of a sentinel chain from that `lastLanded`), since kind FORCED is outside C3-R08's run (C3-R11 stores the run as zero) and two FI blocks may follow, an origin at most 1,865 s old. The NORMAL block after any run is evaluated at its own timestamp, so the three cases do not compose further. The maximum, 65 s, equals C2's DRIFT_MAX (quoted, C2-R19), and C3 states the same 1,863 s and 1,865 s (C3-R11, C3 §10). The batch's construction, the inbox check and the lander's choice of `A` are C3-R11's; C7 states only the predicate. This rule is stated once here; C3-R07, C3-R11 and C2-R04 cite it (D14; J's review of #22199 (2026-10-01), J-1).

The L1 state root is not an L2 input. The former V5(e) clause, forced-inclusion placement, is V8 (round 3, H6). Node and attester under A-L1VIEW; the guest asserts the same equality against the witnessed RLP header, the monotonicity and the age bounds at the block that carries the anchor, with the inheritance above for kind FI and for FORCED blocks after block 0 (C2-R04, C2-R19), and the inbox checks only the anchor tip (C2 L7) and, for a forced batch, block 0's upper-age bound (C3-R11). ## 6. State machine

**[assumed: projection of C7-R01 and C7-R14 onto S2 §5's BLOCK machine]** The BLOCK machine below is S2 §5's restricted to C7's part, with C7-R14's step numbers written on the arrows; the states above SEQUENCED are S2's. A hold has one exit on expiry, the drop without a verdict (D14; D17, B-C7-06): INVALID is not a TTL outcome anywhere in C7, so that no verdict reads a node's clock (§8); the dropped block is re-entered at the same step on receipt of the missing context, with the same verdict (C7-R14's re-entry argument). S2 §5's machine, which at `0403a54` wrote the exit as `--> RECEIVED | INVALID`, is aligned to this in the S2 revision (W10; §11 open item 5 is the citation obligation).

```text
RECEIVED --step 1..6 fail--> INVALID (seqSig kept as evidence)
RECEIVED --step 7: parent unknown--> PENDING_PARENT --parent arrives, <= PENDING_TTL--> RECEIVED (re-enter at step 7)
RECEIVED --step 7: parent not valid under VALID_GOSSIP and C7-R07's reference L1 block not in view--> PENDING_ANCHOR --L1 view catches up, <= ANCHOR_WAIT--> RECEIVED (re-enter at step 7)
RECEIVED --steps 8..10 fail--> INVALID (with every descendant)
RECEIVED --step 11: L1[anchorNumber] not in view--> PENDING_ANCHOR --L1 view catches up, <= ANCHOR_WAIT--> RECEIVED (re-enter at step 11)
PENDING_PARENT | PENDING_ANCHOR --TTL elapsed--> DROPPED (no verdict) --missing context received--> RECEIVED (re-enter at step 7 or 11)
RECEIVED --step 7 certificate, steps 12..13 fail--> INVALID (with every descendant)
RECEIVED --every step passes--> VALID = S2's SEQUENCED
any --L1 reorg of the anchored block a--> INVALID (with every descendant; V5 re-evaluated)
any --the block lands (C2)--> accepted under VALID_LANDED, whatever the local VALID_GOSSIP verdict was (C7-R15)
INVALID descendant d --an INVALID ancestor of d lands, recorded at or before d's fixed L1 reference (C7-R07)--> RECEIVED (re-enter d at step 7; its verdict is the one it has at a node that saw the landing first)
```

The last transition is D22's (item 4, C7-11): acceptance reads the landing at the descendant's own fixed L1 reference, so a descendant judged before its node saw the landing is re-evaluated once, against that same reference, and descendants whose reference precedes the landing keep their verdict.

## 8. Argument and adversary coverage

**[proven: identical across honest nodes, conditional on A-EXEC, A-L1VIEW, A-REGISTRY and A-OBJECTS, for every row of C7-R04's matrix except the sentinel rows until §11 item 20 closes]** Each rule reads only an object the block or its ancestors name (V1, V2, V3, H1), the L1 landing record at the fixed reference a signed object or the block's anchor names (V3's acceptance and V2's `lastLanded` lock, C7-R07; D22 item 4), two integers of the chain (V4), an L1 block at least ANCHOR_MIN_AGE old or, for an inheriting block, the parent's anchor fields and verdict (V5, H2; C7-R09), the parent's derived state and entries that never change once saved (V8), a byte count (V9), a sum over the node's own chain (V10) or a deterministic execution (V6, H3). None reads a wall clock, "latest" state, the L1 head or the node's wider message set (C7-R14's re-entry argument; the FALLBACK refusal that read the message set is S2-R14's policy, D17). So two honest nodes with the same inputs return the same result in whatever order they received them (C7-R01's proof), and a node with fewer inputs returns **unknown context**, never a different verdict. This is the certificate page's claim "V1 to V6 are identical across honest nodes; no rule reads wall clock or 'latest'", extended to V8 to V10 by the same reading. Which chain honest attesters certify before landing is a separate claim, resting on A-QUORUM (C7-R15); the verdict on any one block is not. Not proven here: that the guest's implementation of the same rules agrees with the node's (A-EXEC, a conformance obligation, §10).

**[proven: the mode matrix makes the predicate total, excluding the sentinel rows until §11 item 20 closes, the first block under a TIMEOUT opening of `(t + 1, v)` whose lock is stamped at or below `termEnd(t) − 2` with an entry due (item 22), and a child of a parent accepted only by its landing where C7-R07's fixed reference cannot contain that landing (item 24)]** Every row of C7-R04's matrix names an authorization (a signer checked by V1, or the L1 landing record for FORCED), an opening and parent rule and the subset of V1 to V10 it evaluates; the rows cover every permitted `(view, kind)` pair of C7-R04's first table, and every pair outside it fails H3. The open cells (the sentinel registry read, the sentinel `carriedCertHeight` byte, the no-committee holder's walk position and its first block's parent, the sentinel regime tests at the object's L1 reference, the FORCED row's `vcHash` and `carriedCertHeight`, the genesis child's signer, `vcHash` and closing view change) are gaps in a cell's definition, listed with owners in §11, not gaps in the predicate's domain; the vectors that depend on them (C7-T15, C7-T16) are fixed when they close. The three exclusions are gaps of a different kind. Without the sentinel L1 reference, the regime test reads a node's L1 view at a time, so the sentinel rows are evaluable but not yet identical across nodes. A first block of `(t + 1, v)` on a lock stamped at or below `termEnd(t) − 2` with an entry due has a valid form only under a waiver: an FI block stamped `lock.timestamp + 1` falls outside the window of `t + 1`, and a NORMAL block fails V8 unless C3-R08 waives it. The third is C7-R07's limit: an FI child, or a later block under a REPLACE or RESUME opening, whose fixed reference cannot contain its parent's landing has no accepted parent (item 24).

**[proven: one block, one envelope]** H1 binds `(termId, view)` into the header, hence into `blockHash`, which PH names under `seqSig`; a block presented under another view's PH fails H1 at every node and, if both PHs are signed, is S1 evidence (S2-R21). Two envelopes for one execution hash differing in `vcHash` or `carriedCertHash` are two PHs (S2-R03's identity rule) and V2's chain rule accepts at most one at each position of a chain.

**[proven: no clock in validity, excluding the sentinel rows until §11 item 20 closes]** V4 reads `parent.timestamp` and `termEnd(t)`; V5 reads an L1 block's own timestamp; acceptance by landing reads the L1 record at a fixed reference (C7-R07); the sentinel tests (dead mode, the no-committee deadline, `lastLanded`, `lastLandedTerm`) are to read the L1 reference S1-R16's object names, which it does not yet carry (D22 item 4); the attestation bounds STALE_MAX and CLOCK_SKEW gate signing only (S2-R04). S2 §5's alignment (open item 5) is a citation obligation and no longer a condition of this claim.

**[assumed: V8's in-flight stability is C3-R08's consequence, relied on here]** C3-R08 states that an entry becoming due while blocks are in flight binds the first block after the anchor advances past its due time and that nothing is reorged by an FI.
