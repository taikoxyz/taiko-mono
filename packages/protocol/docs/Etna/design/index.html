Ordinary permissionless calls persist checkpoints at the existing SignalService. Prior rounds 05–06 reviewed the earlier design; fresh rounds 07–08 will determine this revision’s verdict. Classification “Proven” means a stated deduction or source fact under named assumptions. “Assumed” is an environmental or cryptographic premise. “Open” requires evidence or a decision. Mechanism specifications below are proposed rules; their claimed consequences carry those labels. No contracts or clients are implemented here.

Read the design in dependency order

  1. This page fixes canonical data, execution, preconfirmation meaning, atomic landing, and forced inclusion.
  2. Public data staging fixes complete context, public-age eligibility, producer authorization and exact commitments.
  3. Execution codec defines canonical bodies, headers, standard hash-recording calls, manifests and gas accounting.
  4. Roles defines voluntary services, registration and bounded collateral.
  5. Accountability defines evidence, response deadlines, payouts and detection limits.
  6. Checkpoint persistence replaces automatic anchor writes with ordinary permissionless pin/reveal calls.
  7. Bridge and migration preserves existing custody addresses and removes operational administration.
  8. Arguments and verdict gives assumptions, proof sketches, requirement disposition and rejected alternatives.

A valid public transaction can extend the accepted head without contacting them. DAO ownership authorizes upgrades only. Contract-authenticated root and bridge calls remain mandatory: they are provenance boundaries, not a human whitelist.

2. Canonical state and deterministic encoding

Proposed rule: retain an append-only accepted-segment receipt and a single current head. All integers are unsigned with checked conversion; identifiers and hashes are full-width. Consensus objects use canonical ABI encoding, not packed ambiguous strings; dynamic arrays must have exact lengths and no trailing bytes. Every object fixes its exact domain and ABI types; there is no implicit conversion between string and bytes32 tags. The statement/stage context domain uses literal string "SegmentStatement" as specified in staging. For every Head, define HEAD_TAG=keccak256(bytes("ETNA_HEAD_V1")), Dhead=keccak256(abi.encode("ETNA_V1",uint256(l1ChainId),uint256(l2ChainId),address(inbox),address(anchor),uint64(H.revision),bytes32(HEAD_TAG))), and hashHead(H)=keccak256(abi.encode(bytes32(Dhead),H)). This applies to ordinary parents and the exact migration bootstrap head.

Proposed rule: Head.segmentCommitment is the execution contextHash/taskHash, excluding producer, beneficiary, job assignment and staging salt; statements contain the old head hash and terminal fields but not their own hash, avoiding a circular hash definition. The immutable receipt separately retains the full accepted statementHash for authorization and payments. Thus changing only payment, producer or stage-salt fields cannot mutate the precomputed execution head or its children. The next head is constructed from the successful execution context, with nextForceTime=origin.timestamp. A child binds the entire old head, including the parent's queue snapshot. Retain parentConsumption[oldHeadHash] as the immutable AcceptedReceipt returned by getAcceptedReceipt: later consumption cannot erase a missed service deadline.

Proposed rule — noncircular task identity: taskHash is the domain-separated contextHash of the exact StageContext specified on the staging page. Its execution fields include oldHeadHash, terminal outputs, origin, frozen force interval, DA commitments, manifestRoot, blockHashesRoot and revision. It excludes producer, beneficiary, rewardAuthorizationHash, taskHash, jobId, stageId and the constructed new head. Every submission recomputes it, including jobId=0. The salted stageId is computed offline from that context, so future L1 inclusion metadata does not change the precomputed head. Different payment assignments share an execution head/task but have different receipt statement hashes. Descendant stage contexts can be fixed at parent sealing without waiting for a future job ID or L1 registration.

Proposed rule: a manifest specifies every header-affecting value before sealing: ordered raw typed Ethereum transactions, timestamp, gas limit, coinbase, parent hash, fork revision, per-block L1 checkpoint and expected execution outputs. The first block is parent number+1; each subsequent block links to its predecessor. Segment number is parent segment number+1. No execution field depends on future L1 landing time, sender, base fee, block hash or forced-queue tail. The separate L1 admission rent is evaluated at landing and never enters the execution context or predicted head. Transaction and receipt roots and all consensus header fields are recomputed, never trusted as hints. The exact uncompressed RLP body, Ethereum header/transaction profile, block fragment manifests, segment manifest root and gas rules are normative in the execution codec; the blob wrapper below transports those same bytes.

Proposed bootstrap exception: only the exact segment-zero head constructed in migration has originNumber=0, originHash=0 and an empty force snapshot. Its first successor uses an authenticated real origin at or after activation, consumes no forced requests, checks Inbox ACTIVE and standard hash-recording execution and establishes the ordinary snapshot. These sentinels are never checkpoint roots or accepted-segment receipts.

Authenticated L1 facts without lookahead

Proposed rule: anyone can call HeaderStore.pinHeader(bytes rlpHeader). The helper parses the launch-fork header canonically, requires number < block.number, nonzero blockhash(number), and exact hash equality, then stores the number/hash/state-root/timestamp tuple immutably. A repeated identical pin is a no-op; conflicting content reverts. Pin while the EVM history lookup is available. Historical pins remain usable; they do not reserve a batch or publish L2 data.

Proven under A-L1: a valid pin authenticates an ancestor header in that L1 history. A reorg that changes the ancestor also removes descendant pin/acceptance transactions; nodes track the new history. No trusted RPC root is accepted. Every Etna block records exactly this origin hash in parentBeaconBlockRoot; older per-block checkpoint choices and their additional ancestry witnesses are not admitted in revision 1. Open: the bounded L1 header parser and its implementation need launch-fork conformance vectors; any future CL-based optimization would additionally need versioned SSZ witnesses, not a hardcoded generalized index.

Proposed rule: outside the exact bootstrap exception, each segment's origin number and timestamp are nondecreasing relative to its parent's origin; equal number requires the identical authenticated header. Origin reuse is allowed when a segment seals early. Origin age at landing is at most 900 seconds. L2 timestamps strictly increase; no block exceeds origin.timestamp+60; terminal time must be no later than the landing block's timestamp. Nodes accepting live preconfs allow at most 2 seconds of future local-clock skew. Local receipt time is not on-chain misconduct evidence.

3. One-second preconfirmations

Proposed rule: a healthy publisher issues one candidate block per second, including empty blocks when necessary, up to the segment resource bounds. One second is the issuance interval, not L1 inclusion, proof completion, or finality. A user receives a soft result after transport plus signature checking and execution; an admitted transaction waits0…1 second for its candidate, then adds actual propagation and local execution/checking latency under A-NET/A-EXEC. A practical soft response is approximately1–2 seconds when those additional costs fit a one-second budget; these costs must be measured, with explicit UNKNOWN when dependencies are missing. The one-second cadence is not a claim of zero network/execution time or a measured deployment SLA.

Proposed validation order: bound all lengths; require exact encoding/domain and canonical low-s signature; authenticate the preexisting duty reserve if displaying “bonded”; load the exact parent and fixed origin context; check number/time/gas/fee rules and the mandatory forced prefix implied by the parent segment; authenticate exact header-origin equality and the active migration context; execute standard pre-execution calls and every ordinary transaction; recompute and compare every signed block field and hash; verify any displayed custody claims and data completeness. Only then mark VALID_IN_VIEW. A malformed/provably wrong payload is INVALID; unavailable parent/state/origin is UNKNOWN. Neither HTTP admission nor signature alone is a confirmation.

Proposed rule: the protocol has no global “first received” fork-choice rule. Nodes prefer the unique L1 accepted chain, and may expose a separately named provisional branch from the user's selected service. A node can check an individual candidate locally without all nodes choosing the same soft branch. Honest recipients re-gossip complete validated block records and their signatures; any holder can answer a public data request. On conflicting signed obligations, retain both signatures for evidence, stop extending that service's branch, and request data; on L1 acceptance of a different branch, discard the incompatible unsafe suffix and notify applications. Do not carry nonce, balance or bridge assumptions across that rollback.

Assumed A-NET: bounded healthy-network propagation and adequate execution hardware. Open/R4: worst-case 10-million-gas block execution and proof throughput must be measured; the one-second target may require reducing the gas bound before launch. Proven limitation: honest custodians can make a branch available but cannot make L1 select it. A separately valid mature public branch may land and reorg it. The design never calls this pre-L1 finality.

4. Atomic propose-with-proof

Proposed state machine: BUILDING → SEALED → STAGING + PROVING → MATURE_AND_PROVED → ACCEPTED → L1_FINAL. Before acceptance, a competing parent consumption changes applicability to STALE; a 900-second origin or staging expiry changes it to EXPIRED. A missing assigned worker changes a voluntary service job, not canonical eligibility: another prover may submit at any time. No “proposed but unproven canonical” state exists in the Etna Inbox.

Proposed initial reward schema: _rewardAuthorization must be empty and rewardAuthorizationHash=keccak256(empty bytes). Initial rewards are only the specified forced-fee credits, existing L2 gas allocation and escrowed ProofJobs settled against immutable receipts. Adding another format requires an explicit revision upgrade. submitSegment is payable solely for the canonical admission rent and refundable excess. Transaction/blob gas fees are separately paid through the L1 envelope; they are not credited as Inbox msg.value.

Proposed verifier policy: require a deployable ZK verifier and fixed program key per revision; no TEE-only proof and no operational owner-managed key list. Exact verifier and forced-input boundary

Proposed initial proof adapter: require a conjunction of RISC0_RETH and SP1_RETH proofs of the complete Etna relation below. Each uses an immutable revision-specific Etna program/key, with public proving artifacts; these are new program revisions, not a claim that today's legacy programs already prove Etna. The wrapper has no operational key manager, TEE-only alternative or timeout bypass. Proof bytes are exactly abi.encode(bytes risc0Proof, bytes sp1Proof), reject noncanonical offsets/trailing bytes, with total length≤16384. Both adapters must accept the identical publicInputHash. Safety requires at least one correctly enforced complete relation; shared specification bugs remain possible. Liveness requires capability to generate both proofs, which may run in parallel. If either required artifact/verifier is unavailable, this revision cannot launch; a different proof policy requires a reviewed revision upgrade.

Permissionless descending-price admission

Proposed rule: every successful canonical action pays a mandatory ETH rent. Let age=block.timestamp−rentReferenceTime, with the reference initialized at activation and reset to the timestamp of every accepted successor. For age<900, q=ceil(50_000_000_000_000_000 ×(900−age)/900) wei; at age≥900, q=0. Use checked uint256 arithmetic, integer quotient plus one iff remainder is nonzero; reject narrowing overflow. Recompute q in the same action after checking the exact current head. Require msg.value≥q; add exactly q to a permanent nonwithdrawable ETH sink and credit msg.value−q to msg.sender. Every validity check, payment, clock update, receipt and checkpoint is atomic. Failure rolls all state/value effects back; ordinary Ethereum transaction fees can still be charged. This adds a justified anti-capture cost while retaining TAIKO bonds and L2 ETH fee accounting.

No bidder registry, exclusive winner or reservation exists. Any applicable data+proof action paying the current quote may win. A view quote reports its head/reference/time and is not a reservation. The payer may cap its value; the same head's price only falls, while a competing accepted head makes its old statement stale. The sink is neither the coinbase nor a DAO treasury, and no role can withdraw it. The frame sender and payer authorization bind the exact frame value and cost budget. Separate role economics specifies the solvency terms and bounded capture argument.

Proven conditional cost: at head age660, q=13,333,333,333,333,334 wei. Under a competing prover ready and willing to pay, plus inclusion by that age, an actor retaining every canonical win must accept each head by then or lose a win; each such win sinks at least that amount. Fast successive wins in one L1 block each cost0.05 ETH. This deters capture whose net external benefit is below the required rent; it cannot cap arbitrary MEV or guarantee different owners. After900 seconds rent vanishes, preserving a route without a protocol admission fee. Assumed: someone can still fund proving and L1 costs; old origins/stages may have expired and must be rebuilt with fresh inputs. Waiting for zero rent is not a promise that an old proof remains valid.

Public data before canonical eligibility

Proposed rule: every canonical candidate must first have its complete body/blob and complete execution context published through the permissionless DARegistry. The registry records actual current-transaction blob hashes or full calldata, not an unsupported caller commitment. It assigns no sequence position, accepted head, worker or checkpoint. The final action republishes the complete matching data and valid execution proof atomically, after at least360 seconds and before the selected staging receipt is older than900 seconds. See exact encodings, authorization, receipt state machine and limitations.

Proven distinction: a stage is a public candidate, possibly invalid or stale, with no canonical reservation. Only submitSegment proposes and accepts a canonical transition. Earlier public copies are permitted by literal R7; this design pays for two publications and does not claim a single total L1 transaction from first broadcast to settlement. If “propose with proof” instead means that no prior L1 data copy is allowed, this revision needs that stronger requirement changed; it does not silently claim that interpretation.

Assumed: W=360 seconds budgets60 seconds to retrieve/notice a chosen candidate,180 seconds to prepare its proof and120 seconds margin. It gives a funded entrant time to prepare the same branch, not guaranteed pre-maturity inclusion, fair ordering or capacity to prove all spam candidates. All execution inputs must be available at staging. No first-reveal-at-landing candidate can pass. Properly staged public competition can still invalidate another proof or soft branch.

Proposed early accountability: every displayed bonded fragment additionally promises publication of its complete ≤32,768-byte calldata fragment and exact ordered FR preimage by issuedAt+240 seconds. The registry records the first matching publication; a late response cannot erase default or earn a late Q payout. Every chunk of a bonded block needs its own reserve. This is distinct from sealed segment staging; see the exact version-2 duty. Its extra calldata cost is explicit, and it provides neither a global gossip timestamp nor canonical priority.

Proposed accountability: a signed sealed-context publication-by covenant defaults if its first matching public stage is later than issuedAt+240 seconds, even if it eventually reveals. A separately authenticated canonical producer who contradicts its own signed block can lose that block's reserved duty collateral. A named fee recipient alone is never sufficient evidence of authorization. No protocol claim equates a block fragment hash with a blob commitment.

5. Forced inclusion that does not move an in-flight proof's target

Problem: if proof validity depends on the force queue at landing, an attacker can append a request just before each minute-long proof arrives. If proof validity ignores the queue forever, the attacker can keep landing cheap empty proofs and starve public transactions. The successor's mandatory work must be immutable before its proof begins and advance with canonical history.

Proposed rule: a force request stores the hash, ETH fee, enqueue timestamp and enqueue L1 block number; its bytes are published in that enqueue transaction. This is a censorship escape, not ordinary segment proposal. Requests are append-only, cannot be owner-voided, and never expire. Their maximum encoded length is 2048 bytes; decoded transaction gas limit is at most 1,000,000. A deterministic reject outcome clears malformed, unsupported or state-invalid requests; a valid but reverting transaction executes and counts as processed. “Forced inclusion” means a proved execution attempt under ordinary Ethereum transaction validity, not guaranteed application success.

Proposed fee accounting: quoteForceFee returns 10^15 wei×(1+floor(pending/50)). At inclusion require msg.value≥that quote, escrow exactly that request's fee, and credit excess to the caller. Processing releases the escrow exactly once: floor(fee/2) to the proof-bound beneficiary, remainder to an irreversible ETH sink. Unprocessed requests retain full fee liabilities. No arbitrary balance surplus funds these credits.

Proposed snapshot rule: at origin block O, choose queue cut C. Verify C≤currentTail, queue[C−1].l1Number≤O.number if C>0, and queue[C].l1Number>O.number if C<currentTail. Enqueue block numbers are monotonically nondecreasing, so these boundary checks fix the unique tail after O. Origin must precede the landing block, eliminating intra-block ambiguity. The accepted statement freezes C and O.timestamp for its child; later enqueues cannot change them.

Proposed consumption rule: starting at parent.forceCursor, take exactly the first up to four requests whose index is below parent.nextForceCut and whose enqueueTimestamp+120≤parent.nextForceTime. These transactions or deterministic rejection outcomes precede discretionary transactions. The contract derives the required end cursor in at most four inspections plus the boundary check; the circuit proves the exact bytes, order and outcomes. Neither chosen segment length nor a claimant's signature can waive this work. Requests from beyond the frozen cut are not consumed early.

Worked example: parent H has cursor=18, cut=25, snapshot time=1000. Requests 18–22 were queued at 850; request 23 at 900. The child must process 18–21 because they are due and the cap is four. Request 22 remains first for the next applicable child; request 23 is not yet due at time1000. Request 25, enqueued while the proof runs, cannot invalidate it. The child's own fixed origin supplies the following snapshot. New arrivals behind request22 never add predecessors to it.

Proven conditional progress: origins may repeat but must remain within900 seconds of landing; therefore an indefinitely progressing chain cannot keep a fixed old snapshot. Once a request is due and in the snapshot, every accepted successor either processes it or removes up to four earlier due requests. Cheap empty-proof grinding can still waste discretionary proving work, but cannot indefinitely avoid a fixed eligible FIFO item while advancing. Assumed: at least one affordable valid proof can process the bounded prefix. During a total prover outage the chain halts safely; no DAO action manufactures a proof.

6. Message flows and user-visible latency

Revised timing example: form at t=0…60, stage at t≈60 while proving until t≈240, become eligible at t≈420, then land, paying the contemporaneous rent. A healthy funded example is7–8 minutes; with120 seconds for stage inclusion and another120 for final inclusion, the illustrative path reaches660 seconds plus header acquisition. The proving interval in the diagram runs in parallel with public-data maturation.

Proposed operation: soft production continues while older segments are being proved, subject to a local 900-block unsafe horizon. Crossing that horizon stops new soft confirmations; it does not create unbounded promises or block an L1 rescue. A backup prover uses the same public sealed statement; if the worker's proof is unavailable, it recomputes. If the origin expires or a different parent wins, rebase/reseal/reprove and notify users. No claim is made that every backup preserves minute latency after arbitrary repeated failures.

8. L1 dependencies integrated into the design

Required: sound Ethereum execution/consensus, a deployable sound ZK verifier, usable L1 DA and affordable eventual inclusion. Without them the chain cannot launch safely or cannot make liveness progress. Assumed launch feature: EIP-8141, currently Draft/SFI for Hegotá; if delayed, use ordinary atomic transactions with paid losing races. Optional: ePBS, BAL, FOCIL and increased blob throughput. They do not assign Etna roles or verify private dissemination. No L1 EIP-4788 beacon-root input, SLOTNUM, keyed nonces, proposer lookahead or shorter-slot feature is required by this candidate. The standard EIP-4788 and EIP-2935 contracts and execution behavior on L2 are required before migration; this is a local L2 prerequisite, not a dependency on Ethereum’s CL lookahead. Without verified runtime code and client/prover parity, this revision cannot launch.

Proven timing independence: changing Ethereum block production from12 seconds to6,4 or2 changes the opportunity to include actions, not any Etna seconds-based deadline or service assignment rule. EVM BLOCKHASH's block-count window is handled by permissionless header pinning; it is never converted into a fixed number of seconds. Mainnet gas repricing is a compatibility requirement, not a reason to assume cheaper rescue. The dated survey records exact current statuses, competing source claims and fallbacks.
