L2 blocks without an anchor, shared contracts (R2), and migration

An Etna L2 block carries its L1 anchor in its own header and contains no Taiko-specific transaction (anchor-free blocks, issue #22147): parentBeaconBlockRoot holds the hash of the anchored L1 block, extraData holds the term, view and block kind, and the signed header PH binds the rest. The standard EIP-4788 pre-execution call of L2's own beacon-roots contract records each anchor hash, from which anyone can reveal the L1 checkpoint into the L2 SignalService. Every proxy keeps its address: the Inbox, Anchor and L2 SignalService are upgraded in place with new behaviour, and the L1 SignalService, the Bridge, the Vaults and the quota manager are upgraded in place by compatible implementations that only remove their pause and owner-only operational powers, storage unchanged (after the #22188 review, 2026-10-01). Every anchor is bound at landing to an L1 block that was canonical when the landing was included. Source: judge synthesis of the three B8 designs, revised for anchor-free blocks (issue #22147).

What today does and why it fails

Today the first transaction of every L2 block is anchorV4, which the golden-touch account sends under engine carve-outs and a 1,000,000-gas reserve; it checks a 255-block ancestors ring, writes blockHashes[parent] and forwards a strictly newer checkpoint to the L2 SignalService: equal numbers are ignored silently, nothing on L2 checks the hash or state root, and a reverted anchor does not invalidate the block (00 §5, §9.2). The only L1 binding is the guest's chain to the proposal's originBlockHash, which the propose step recorded and which disappears with it (TH17, Critical: the L2 Bridge mints against L1 state roots). The block is not self-describing; anchor freshness is 12-second arithmetic. The L1 syncer address is an implementation immutable of the SignalService, so whichever contract lands batches must keep the Inbox proxy address or force a SignalService implementation bump.

1. The anchor lives in the header: parentBeaconBlockRoot and extraData

An Etna L2 block contains no Taiko-specific transaction and no Taiko-specific pre-execution hook (anchor-free blocks, issue #22147): no transaction carries the anchor, every transaction in the block is an ordinary one, and the only pre-execution calls are the standard EIP-4788 and EIP-2935 system calls into L2's own copies of those contracts (§3). Fee sharing (extraData[0]) and zk-gas metering stay Taiko-specific as today, so the claim is "no Taiko-specific transaction or pre-execution hook", not "a fully standard EVM". Two header fields carry what must sit inside blockHash:

  • parentBeaconBlockRoot = the hash of L1 block a, the block's anchor: an L1 execution block hash, not a beacon root. It is non-zero for every Etna block: sequencer, FI, forced, sentinel-view and genesis-child blocks.
  • extraData = exactly 7 bytes, layout unchanged so the engine's length check and fee decoder need no change: basefeeSharingPctg(1) ‖ termId(4) ‖ view(1) ‖ kind(1). Kind 0 NORMAL (a sequencer block), 1 FORCED (a forced-batch block, view 254), 2 GENESIS_CHILD (the first Etna block), 3 FI (a forced-inclusion block inside an ordinary or sentinel view; new, so that the forced-inclusion cursor needs no stored field). View 255 is the open-empty, dead-mode or no-committee sentinel.
  • Everything else as today: coinbase is the sequencer's fee address; timestamp, gasLimit and base fee follow the existing rules.

Where the other fields went. The signed header is unchanged: PH = {version, chainId, termId, view, vcHash, height, timestamp, parentHash, blockHash, txListHash, carriedCertHash, anchorNumber}. blockHash commits to the whole L2 header, including parentBeaconBlockRoot and extraData, so PH binds the anchor hash through blockHash and its number through anchorNumber. vcHash and the carried certificate live in PH, which the sequencer signs, and in the blob record (headerCore, landing page §2), from which the guest rebuilds PH for every block; they are not copied into the block. The seat is carried nowhere: (termId, view) and the holder list imply it. Equivocation evidence is two signed PHs, as before, and extraData's (termId, view) keeps one block from being presented under another view's PH. The forced-inclusion cursor is derived, never stored: after a landing it is fiQueue.head, and a block of kind FI or FORCED advances its parent's cursor by one (forced-inclusion page §4). Deliberately absent: a sequencer address (ecrecover of the header signature is the identity; a copy in the header would be a third value nothing can check) and a batch id (ranges are lander-chosen; a block does not know its batch).

Header rules (anchor-free blocks, issue #22147), checked by nodes under V6 and asserted by the guest (certificate page §3):

  1. H1 extraData. Exactly 7 bytes; byte 0 equals BASEFEE_SHARING_PCTG; (termId, view, kind) equal PH's (termId, view) and the block's kind.
  2. H2 anchor field. parentBeaconBlockRoot ≠ 0 and, by V5, equal to the hash of the node's own canonical L1 block at PH.anchorNumber, with anchorNumber monotone from the parent's and that block's timestamp within [PH.timestamp − ANCHOR_MAX_AGE, PH.timestamp − ANCHOR_MIN_AGE] (1,800 s and 48 s). A node lacking the block is pending-anchor, never invalid; a reorg of it invalidates the block identically everywhere. The L1 state root is not an L2 input: it is bound to the hash by keccak at reveal (§3).
  3. H3 kind. FORCED iff view 254; GENESIS_CHILD only for the first Etna block, whose parent is the genesis parent, whose view opens with no view change, and which is exempt from V8's obligation (it binds from its child); FI blocks per the forced-inclusion page F3.

The checks of the earlier design's Anchor rules move as follows. Term binding is V2's PH.timestamp ∈ [termStart(t), termEnd(t)) plus H1's termId equality (kind FORCED exempt, as its timestamps may cross a term boundary). View binding is checked on consecutive PHs by nodes (V2, V3) and by the guest: vcHash changes exactly at the first block under a new opening object, every change of (termId, view) is such a block, and a REPLACE or RESUME view change changes vcHash under the same view number, so all blocks under one opening object carry one vcHash; for sentinel views the opening object is keccak("ETNA_DEAD" ‖ lastLanded.blockHash ‖ t), accepted as fresh after any landing (so a dead-mode or no-committee chain that lost a landing race reopens without equivocating; round 2, S9). Forced blocks are H3 plus the forced-batch content rule. A monotone, conflict-free checkpoint becomes V5's monotone anchorNumber plus the reveal's conflict check (§3): within any landed range every anchored number maps to one hash, because all anchored headers lie on one parent-hash chain (§2). Nothing needs a receipt-status check: no transaction carries the anchor, so no revert can leave a silent checkpoint gap.

What nothing on L2 verifies at block production, and why: the L1 block behind the anchor hash (needs L1: nodes by V5, the guest and the inbox at landing), the certificate and view change (needs committee keys and pairings: attesters off-chain, inbox at landing), the sequencing right (needs the registry: inbox at landing). Checking any of these on L2 would make 1-s block production depend on fresh, proven L1 state.

Cost, stated plainly. Anchor-free blocks are an L2 execution-client hard fork: both clients drop the anchor carve-outs, run L2's EIP-4788 and EIP-2935 system calls and accept kind 3, so taiko-geth and alethia-reth ship ETNA_FORK_TIME = ETNA_T0 exactly as they shipped Shasta and Unzen, and the guest ships the same rules. If the stand-alone anchor-removal fork proposed in issue #22147 ships before Etna, Etna inherits it and adds only its extraData layout and kind values; otherwise Etna's L2 fork includes it (§5). Per block the change removes the anchor's execution, its 1,000,000-gas reserve and the fresh blockHashes[parent] slot, which closes the earlier open question about that slot's cost under an EIP-8037-style L2 gas rule; L2's EIP-4788 and EIP-2935 system calls overwrite ring slots after warm-up and run outside the block gas limit. Per checkpoint actually used, one reveal costs about 100k gas assumed (the issue review's figure, unmeasured).

2. Binding every anchor to a true L1 block (TH17)

Production-time freshness is V5 on the certificate page: the anchored block, named by PH.anchorNumber and by the header's parentBeaconBlockRoot, is at least 48 s and at most 30 min older than the block, equal to the node's own canonical L1 block at that number, and monotone rather than must-advance (during an L1 stall leaders keep anchoring the last block). Landing-time binding (anchor-free blocks, issue #22147): the journal carries the anchor tip's number, hash and timestamp; the guest witnesses the RLP of every distinct anchored L1 header of the range, checks that its keccak equals the parentBeaconBlockRoot of each block that anchors it and that its number equals that block's PH.anchorNumber, chains all of them by parent hash to the anchor tip, and checks anchorNumber monotone and V5's age bounds. It checks no state root, because L2 receives one only through a reveal, which re-checks keccak on-chain (§3). The inbox checks only the tip (L7, unchanged: blockhash, else EIP-2935, else refuse). Hence every record that a block of a landed range writes into L2's EIP-4788 contract is the hash of an L1 block canonical at landing, and every checkpoint revealed from it is that block's true hash and state root. proven given T3, EIP-2935 semantics and keccak. Before landing, a fake anchor (possible only if ≥ Q attesters skipped V5) can be revealed only on the unlanded chain, which cannot land and is replaced; bridge withdrawals should wait for "landed" as before, and the Bridge quota bounds the residual. A batch whose landing slips past L1's EIP-2935 window (an outage longer than 4.55 h at 2-s slots) is unlandable and replaced.

L1, the call unchanged. Inbox-side invariants, because the SignalService checks none: end height strictly increasing, hashes non-zero. The call is made once per landing accepted with two ZK leaves unless an unfinalized provisional record precedes it on its chain; then the landing writes none and is subsumed by the one checkpoint written when the newest record it follows is finalized. A landing accepted with one leaf in single-proof mode is provisional and writes no checkpoint at landing: its record waits for a proof of the same journal from the other leaf or for DEGRADED_FINALITY = 24 h without a conflict, checkpoints are written in order, and a proof conflict halts every landing and checkpoint write until a DAO upgrade names the sound leaf (landing page §7; after the #22188 review, 2026-10-01), so in degraded proving mode L2→L1 messages wait up to 24 h for their checkpoint (limitation L-PF). msg.sender == _authorizedSyncer holds because the proxy address is unchanged. Under EIP-8037 the fresh checkpoint words cost about 196k state gas per landing (two words at 97,920 each): unavoidable under R2, paid by the lander.

L2 recording (anchor-free blocks, issue #22147). Before any transaction of each L2 block, the standard EIP-4788 system call stores the block's timestamp at slot timestamp % 8191 and its parentBeaconBlockRoot, the L1 anchor hash, at slot timestamp % 8191 + 8191 of L2's beacon-roots contract (BEACON_ROOTS_ADDRESS 0x000F3df6D732807Ef1319fB7B8bB8522d0Beac02), whose get() takes the raw 32-byte timestamp and reverts unless that exact timestamp is stored. Etna's timestamps strictly increase (V4), so with 1-s blocks each of the last 8,191 L2 seconds holds the anchor hash of the block at that second, and the record for timestamp T is readable until the block at T + 8,191 overwrites it: a guaranteed window of 8,191 s (about 2.3 h) whatever the L1 slot time. On L2 this "beacon roots" contract therefore holds L1 execution block hashes, not beacon roots, and any L2 contract that reads it gets those.

L2 reveal and pin (anchor-free blocks, issue #22147; the pin and the parser bounds adopted from the Astra candidate, PR #22188). revealCheckpoint(uint64 _l2Timestamp, bytes calldata _headerRlp) and pinCurrentOrigin() on the L2 SignalService, whose implementation is upgraded in place behind the same proxy (VERSION stays 1; the only new storage is one bool per pinned origin, §4), are callable by anyone in L2 mode (an implementation immutable; the L1 implementation rejects both). read4788(t) is the one oracle read both use: require EXTCODEHASH(BEACON_ROOTS) == EXPECTED_4788_CODEHASH (an immutable pinned to the canonical EIP-4788 runtime), staticcall with 100,000 gas and the raw 32-byte timestamp, require success and exactly 32 return bytes; a missing or malformed read reverts. pinCurrentOrigin() reads h = read4788(block.timestamp), requires it non-zero, stores pinnedOrigins[h] = true (a duplicate is a no-op) and emits OriginPinned(h, uint64(block.timestamp)): the processing block's anchor becomes permanently revealable. revealCheckpoint requires 0 < _headerRlp.length ≤ 1,536 and h = keccak256(_headerRlp) to be authenticated by one of two paths: a positive _l2Timestamp ≤ block.timestamp, for which read4788(_l2Timestamp) must return h (the ring, readable for 8,191 s), or _l2Timestamp = 0, for which pinnedOrigins[h] must be true (no deadline; a positive timestamp never falls back to the pin). It then strictly decodes the header: one RLP list of 12 to 32 scalar items, no nested list, no trailing bytes, minimal length encodings; item 3, the state root, exactly 32 bytes and not zero; item 8, the number, a minimal unsigned integer of at most 6 bytes, cast to uint48 (an L1 header beyond those bounds needs a reviewed parser revision, §19). If _checkpoints[1][number] already exists, it requires the identical hash and root and returns (idempotent; a conflict reverts); otherwise it stores CheckpointRecord{blockHash, stateRoot} and emits the existing CheckpointSaved. Optionally, a versioned proof envelope lets proveSignalReceived reveal and verify in one transaction; the Bridge is unchanged, since it forwards opaque proof bytes. Neither call has a pause gate, and after the compatible upgrade of §4 the L2 SignalService has no pause at all: its _authorizePause override reverts for every caller and the __paused slot is kept only for layout, so nothing short of a DAO upgrade can halt claims or checkpoint persistence (after the #22188 review, 2026-10-01). The L2 saveCheckpoint path is closed by the current-root guard from the first Etna block (§5). proveSignalReceived still reads version 1; VERSION is bumped on neither layer. proven given keccak: a reveal stores only the true hash and state root of an L1 header whose hash L2's EIP-4788 contract recorded from a block's parentBeaconBlockRoot.

Persistence policy (client, not validity). When its anchor advances, a sequencer includes a reveal of the new anchor as an ordinary transaction (about 100k gas, assumed until measured), so L2 keeps receiving checkpoints at today's cadence, one per anchored L1 block; anyone else may reveal; relayers reveal before claiming, or use the extended proof. A missed reveal is never a fault: a newer L1 state root proves every signal an older one did, so only the newest revealable anchor matters, and the head block's own record always holds the newest anchor. Consumers: the "latest synced L1 block" is the L2 head's parentBeaconBlockRoot resolved through L1, not Anchor.getBlockState(); L2's CheckpointSaved now comes from reveal transactions; a bridge message is processable once a checkpoint at or above its L1 block is revealed, or such an anchor hash is still recorded so that the claimer can reveal it first.

proven by construction (R2): addresses of both SignalServices, the Bridge and the Vaults are unchanged, so R2 holds. Bytecode: the Bridge, the ERC20, ERC721 and ERC1155 Vaults (and the quota manager they call) and the L1 SignalService are upgraded in place by compatible implementations that remove pause/unpause and the owner-only operational functions (changeBridgedToken and every owner setter: a frozen configuration changes only by a DAO upgrade), keep every storage layout, message format, selector used by clients and address, add no storage, and pass a selector audit of the inherited EssentialContract surface (§4; A5, revised after the #22188 review, 2026-10-01); the L2 SignalService implementation is upgraded in place (adds revealCheckpoint and pinCurrentOrigin, closes the L2 syncer path from the first Etna block and loses its pause and owner powers with the others; one namespaced pin mapping, VERSION unchanged); the Anchor implementation is upgraded in place to the treasury plus the current-root guard (slots 0 to 257 keep their types; nothing is appended).

4. R2 decision: upgrade the proxies in place

Upgrade every proxy in place and keep every address: the Inbox, the Anchor and the L2 SignalService with new behaviour, and the L1 SignalService, the Bridge, every Vault and the quota manager with compatible implementations that remove only their operational powers, addresses and storage unchanged (the L2 SignalService upgrade comes with anchor-free blocks, issue #22147; the compatible upgrades after the #22188 review, 2026-10-01). Reasons: the L1 syncer is an implementation immutable, and a new inbox would force a new implementation on the L1 contract that guards all bridged value; the L2 SignalService needs new code for the reveal, the pin and the current-root guard in any case and takes it behind its existing proxy with one namespaced pin mapping and VERSION unchanged, so every cached signal and stored checkpoint stays valid; the bond ledger and the forced-inclusion queue carry over with no token migration; relayer, indexer and both clients already point at the proxies; rollback is one upgradeTo per upgraded contract. Costs accepted: Shasta slots stay allocated; the public-function libraries are redeployed and re-linked with the new registry and slashing libraries beside them. The fallback, only if the in-place storage audit fails: a new L1 SignalService implementation whose constructor names the new syncer, layout untouched.

5. Migration

Two upgrade-class L1 transactions (round 4, R4-C5). Let U be the L1 time at which the DAO's upgrade transaction executes: deploy the linked libraries, the verifier with image windows, the Etna Inbox implementation, then upgradeToAndCall(impl, initEtna(lastFinalizedBlockNumber)). initEtna carries no T0: it verifies the L1 SignalService's checkpoint at that number equals the core state's last finalized hash (this pins the L2 height that the core state does not store), sets the initial lastLanded and opens register(). Let A ≥ U be the time of the second call, armEtna(T0), which requires T0 ≥ A + MIGRATION_LEAD (7 days) and sets the term grid once; the DAO makes it after reading the domain seat count on-chain and the owner structure off-chain (round 3's single transaction fixed T0 against an empty registry, so the launch condition could only be read after T0 was immovable). T0 defines the term grid; its phase relative to L1 slots is irrelevant (R5). The arming proposal also bridges the in-place upgrades of the Anchor and of the L2 SignalService, both carrying EXPECTED_4788_CODEHASH and, for the SignalService, the L2 mode as implementation immutables, and no fork time, guarded by the current-root read (§4 and the guard below; round 6 fix pass), to the L2 DelegateController as one action that must execute and finalize on L2 after L2's EIP-4788 contract is deployed (the guard reverts on a missing oracle) and before T0; both execution clients and the guest ship the fork time. The compatible upgrades of the shared contracts (§4; after the #22188 review, 2026-10-01) are separate upgrade transactions, on L1 by the DAO and on L2 through the DelegateController, executed before T0 and independent of the fork: they change nothing the fork reads, so their order against the steps above is free.

Fork-time guard (anchor-free blocks, issue #22147; the current-root form adopted from the Astra candidate, PR #22188, replacing a block.timestamp ≥ ETNA_T0 gate). The bridged upgrade installs (i) an Anchor implementation whose anchorV4 requires read4788(block.timestamp) == 0 (§3) and which has no other privileged entry point, and (ii) an L2 SignalService implementation whose saveCheckpoint requires the same zero read and which adds revealCheckpoint and pinCurrentOrigin, both requiring a non-zero read. The guard reads the fact the clients enforce: a Shasta header carries a zero parentBeaconBlockRoot, which the standard EIP-4788 call records before any transaction, and an Etna header a non-zero one (H2), so the legacy writers are closed from the first transaction of the first Etna block and no contract immutable can disagree with the client fork time. Without the guard, that block could carry a golden-touch anchorV4, signed with the public golden-touch key, whose ring check still passes there (and again in the next block once a forged call has advanced the ring) and which would save a forged checkpoint through the L2 syncer path (the issue #22147 review). A missing or malformed oracle read reverts and never selects legacy mode, so the guarded implementations must be installed after L2's EIP-4788 contract exists (the order below). After T0 the execution clients drop every golden-touch carve-out, so a golden-touch transaction is an ordinary, fee-paying transaction that can reach nothing privileged. proven given the guard and H2.

13. Attacks defended and not defended

  • TH17 false or stale anchor: defended at landing, bounded before it. A sequencer anchoring the hash of a fake L1 header, whose state root contains a fake L1 deposit, can have its block attested only if ≥ Q attesters skipped V5; the fake hash is then recorded by L2's EIP-4788 contract and revealable on that unlanded chain only; the range can never land (the guest needs a header preimage that chains by parent hash to the tip the inbox checks, and the fake header does not); it is replaced and the sequencer earns nothing from it (no penalty: round 4 removed the abandonment rule, R4H-5). Before landing the poisoned checkpoint lives at most about an hour, which is why bridge withdrawals should wait for "landed" and why the unchanged Bridge quota bounds the residual.
  • Fork-time forgery window: defended (anchor-free blocks, issue #22147). A golden-touch anchorV4 in the first anchor-free block could otherwise pass its ring check and save a forged checkpoint through the L2 syncer path; the current-root guard of §5 makes both anchorV4 and the L2 saveCheckpoint revert in every block whose header carries a non-zero root, that is every Etna block, and the clients drop the golden-touch carve-outs at T0. proven given the guard and H2.
  • Forged reveal: defended (anchor-free blocks, issue #22147). revealCheckpoint stores a checkpoint only for a header whose keccak L2's EIP-4788 contract recorded from a block's parentBeaconBlockRoot or that pinCurrentOrigin stored from the same source, decodes the header within fixed bounds (§3), and reverts on a conflict with a stored checkpoint; a reveal of a fake anchor exists only on an unlanded chain (TH17 above, §2).
  • TH4 and W1: defended. Term, view, opening-object hash and carried-certificate hash sit in PH under the sequencer's signature, and (termId, view, kind) also sit in extraData, hence in blockHash, so one block cannot be presented under another view's PH; the seat is implied by (termId, view); equivocation evidence is two signed PHs and names them whatever the envelope said.
  • TH12 reorg of an anchored block: defended, residual. A reorg deeper than 48 s invalidates the block identically everywhere; the certified suffix is unlandable and replaced; the holder loses the suffix's revenue and pays no penalty (round 4: no rule reads a missing landing).
  • TH2 prover cartel at migration: defended. Whitelisted Shasta provers can delay the first Etna landing by at most a day; then anyone abandons their unproven tail, and the forced inclusions it consumed are requeued, their count fixed by the ring buffer (M2; after the #22188 review, 2026-10-01), so the cartel can neither hold the migration (a proof-backed drain is rejected for that reason, R1) nor make it discard a forced request.
  • TH7 across the cut-over: defended. Queue entries survive with their save time and become due under the new rule, and entries that an abandoned Shasta proposal had consumed are requeued at the abandonment with fee zero, due at the fork (M2; after the #22188 review, 2026-10-01), so no forced request accepted by Shasta is discarded by the migration; the stall clock starts at the drain block (M3), so the cut-over itself voids nothing, and a legacy entry that a later stall voids refunds nothing, having no requester and no bond (round 6, R6H-1).
  • TH8 migration griefing: defended. No Etna rule debits anyone before the drain; the genesis check is an equality against the SignalService; the Shasta-tail abandonment (M2) is gated only by time, checks the supplied proposals against the ring buffer, puts no bond at stake and discards no forced request.
  • TH19 DAO inaction: defended. After armEtna nothing needs the DAO; a hostile rollback cannot rewrite landed history without also upgrading the SignalService.
  • TH20 image rotation across migration: defended. Two verifiers coexist and neither path can write the other's checkpoint.
  • TH25: defended for this block's constants through the published parameters; the guest parses L1 headers itself, and on L2 only the reveal decodes one, so an L1 header-format change is a guest release and possibly an L2 SignalService upgrade, never an inbox upgrade. Not defended: an L1 fork moving the state-root or number field index (none scheduled).
  • TH21 SignalService pause: removed (after the #22188 review, 2026-10-01). After the compatible upgrades of §4 no address can pause either SignalService, the Bridge or a Vault, and L2 block production calls no SignalService at all, so nothing short of a DAO upgrade halts claims, landing or anchoring; before them, L1's saveCheckpoint had no pause gate, so a paused SignalService halted claims but never landing or anchoring. The schedule this covers: a pauser key or the DAO's operational key stopping bridging; it no longer exists. What is given up is the emergency brake: a live exploit of a custody contract is stopped only by a DAO upgrade, the Bridge quota, immutable after the upgrade, bounding the loss rate in the meantime (limitation L-OP).
  • L2 beacon-roots semantics: documented, not defended. An L2 contract that reads L2's EIP-4788 contract gets L1 execution block hashes, not beacon roots (anchor-free blocks, issue #22147); code ported from L1 that expects beacon roots misreads them (limitations L22).

14. Failure analysis

  • Sequencers all offline. No new anchors on L2, so L1→L2 messages wait; L2→L1 messages in landed blocks are unaffected; the sequencing page's fallbacks apply. All malicious: stale-but-true anchors bounded by ANCHOR_MAX_AGE; false anchors unlandable, replaced, unpaid; they cannot get a surviving bad checkpoint into either SignalService. A sequencer that skips the reveal policy delays only what any relayer's reveal restores.
  • Attesters all offline. Blocks are sequenced only and unlandable until dead mode; anchors in dead-mode blocks are still L1-bound. All malicious: bounded per TH17; they cannot make a false checkpoint land.
  • Landers and provers all offline. No new L1 checkpoints of L2, so L2→L1 bridging stalls; L1→L2 continues on the attested chain; after 4.55 h at 2-s slots anchored blocks fall out of L1's 2935 window and certified ranges become unlandable, which only shortens the replacement path. One ZK leaf down: landings continue after two hours in single-proof mode but are provisional, so L2→L1 bridging waits up to 24 h behind each until the other leaf confirms it (landing page §7; after the #22188 review, 2026-10-01).
  • Revealers all offline (anchor-free blocks, issue #22147). L2's EIP-4788 contract still records every anchor; L1→L2 claims wait until someone reveals, which anyone can do at any time for the newest anchor, since the head block's record holds it; nothing is lost but latency.
  • L1 builders. Can delay landings or reorg an anchored block; cannot forge a checkpoint.
  • DAO offline after U. Etna runs; the Anchor's legacy balance stays where it is; no rollback possible (not a liveness need). Execution-client maintainers. A missed fork release forks the client set, as for any hard fork; mitigated by the lead time. A deployment of L2's EIP-4788 contract before the taiko-geth sealer fix runs on every geth node would split those nodes from the chain (liveness, not safety); hence the order of §5.

15. False positives and false negatives

  • Anchor age. FP: an attester more than 48 s behind L1 holds the block as pending; a sequencer whose L1 node is dead for 30 minutes keeps anchoring a block that falls out of V5's ANCHOR_MAX_AGE bound, so every block it then produces fails V5, no honest attester attests any of them, it holds no attested block of the view, and every honest attester times it out at 5 s: it loses the view and pays MISS, outside the cases of the certificate page's §1(d) (the normative trigger, certificate page §1(c); round 6, R6H-5). FN: anchoring at exactly 30 minutes each block keeps L1→L2 latency at the bound without penalty.
  • Reorged anchored block. FP: an honest holder's range is replaced after a deep reorg and it loses that range's revenue; no penalty. FN: none.
  • Reveal conflict. FP: none on a landed chain, where every anchored number maps to one hash (§2); on an unlanded chain a conflicting reveal reverts, and that chain is replaced anyway. Reveal window (L2's EIP-4788 contract, 8,191 s; anchor-free blocks, issue #22147). FN: a reveal by timestamp of an anchor whose last record is more than 8,191 s old can fail, once a later block has reused that ring slot; harmless, since a newer anchor proves everything an older one did, bridge clients retry against the newest checkpoint, and a pinned origin stays revealable with revealCheckpoint(0, header) at any later time; a queued pinCurrentOrigin() pins whatever anchor the processing block carries, so a censoring sequencer can delay a durable checkpoint by the forced-inclusion bound but never prevent one (limitations L22; adopted from the Astra candidate, PR #22188).
  • Lost getters (anchor-free blocks, issue #22147). FN for legacy readers: the Anchor's blockHashes, a permanent L2 hash lookup, shrinks to EIP-2935's last 8,191 L2 blocks; getBlockState().anchorBlockNumber and the Anchored event stop at the fork; consumers move to the header field (the issue's review found no other on-chain consumer). open confirm that no L2 application relies on the permanent lookup (limitations L21).
  • Drain deadline. FP: a proposal that would be proven at hour 25 is abandoned: its ordinary content is lost (announced, M4), its forced inclusions are requeued with fee zero and the fee its proposer was paid for them is not recovered (at most 10 × fee per proposal, M2); no bond at stake. FN: none; the abandonment cannot drop a forced request, because the ring buffer fixes the count of forced sources in the tail, and it cannot be called before T0 + DRAIN_DEADLINE. Genesis and first term. None: both are L1 storage.

16. Robustness

6/4/2-s slots: no rule counts slots; the only block-denominated bounds are L1-given (blockhash 256, EIP-2935 8191) and shrink to 512 s and 16,382 s at 2 s; the worst anchor age keeps a 2.8× margin; the guest's header chain grows to about 2,880 headers, under the cap; blockhash alone fails below 12-s slots, so the 2935 path is the common one. Without Frame Transactions: nothing here depends on EIP-8141. ePBS Empty slots: execution block numbers stay contiguous; no gaps in blockhash or L1's 2935 ring; canonical-at-N+1 is why ANCHOR_MIN_AGE is 48 s rather than one block. EIP-4788: no L1 beacon root is read; L2's EIP-4788 contract is keyed by L2 timestamp, so its 8,191-s reveal window is the same at every L1 slot time (anchor-free blocks, issue #22147).

18. Alternatives rejected

  • Freshness relative to a seal; a minimum anchor depth in L1 blocks (4 s at 2-s slots); a permissionless genesis-ready flag (replaced by a DAO-armed T0 and the drain-derived first term); a T0 fixed inside initEtna (round 3; removed in round 4 because it fixed the grid against an empty registry); a contract-enforced launch condition (a Sybil-able count would only be gamed); an inbox-recorded L1-hash log fed by landings (covers only blocks some transaction touched, and a dead pipeline is exactly when nobody does); a void rule for legacy forced inclusions; retiring the blob request entry point; the Anchor share as the reward pool (a bridge hop and a relayer near liveness economics, and the proposed sweep could not be relayed as written); a sequencer field or coinbase binding in the header; a batch id in the header; a hard drain that voids provable proposals; sequencing from T0 on the unfinalized tail; proof verification before the writes; a block-denominated maximum anchor age; certificate or rights verification on L2 at block production (100k+ gas per block and coupling block production to fresh L1 state); a reduced reorg slash rate; an objective attester slash for certifying an L1-rejected anchor (a deep reorg would make honest attesters guilty); a one-day migration lead; a new inbox address with a SignalService bump (fallback only).
  • For anchor-free blocks (issue #22147): a Taiko-specific pre-execution call writing {number, hash, stateRoot} (custom execution logic in four implementations and a 70-byte value beyond Ethereum's header limits; the issue's option 2); the L1 state root in parentBeaconBlockRoot with the number in extraData (the number is unauthenticated); vcHash and the carried certificate in the L2 header (extraData is capped at 32 bytes, and PH already binds them); reading L1's EIP-4788 beacon roots for the seed or for anchoring (slot-keyed probes, Empty-slot gaps, a 4.6-h window at 2-s L1 slots), a different use from L2's EIP-4788 contract, which the L2 header feeds with the L1 execution block hash keyed by L2 timestamp, so none of those objections applies to it.

Anchoring through L2's EIP-4788 contract is no longer rejected: the earlier rejection assumed the anchor transaction was needed to put the Etna fields inside blockHash; PH binds them, extraData binds (termId, view, kind) and the blob record carries the rest (anchor-free blocks, issue #22147).
