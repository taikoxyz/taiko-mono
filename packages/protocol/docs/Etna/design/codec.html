Etna · proposed revision 1 codec

Every execution input is public and unambiguous

Core · Staging · Roles · Accountability · Migration · Arguments · Learning course
Proposed rules for review, not an implementation or readiness claim. This page closes the inner-body, manifest, header and anchor representation. It preserves existing Ethereum transaction/header encodings inside a bounded uncompressed container. No key material is needed to review these rules.

Classification: tables, formats and transitions labeled “proposed rule” are normative design choices. Proven identifies a source fact or consequence under stated premises; Assumed identifies an environmental/cryptographic dependency; Open identifies required launch evidence. Root soundness still depends on the complete relation, implementation correctness and A-CRYPTO/A-L1/A-UPGRADE.

1. Pin execution rules separately from block inputs

Proposed rule — inherited profile: use the public Taiko Unzen/Osaka execution profile at taikoxyz/alethia-reth@0fb47d966f290c032e0ce88bdc8877121768d253, with its committed dependency lockfile, Ethereum fork rules through Osaka, and Taiko system-transaction treatment. Its crates/chainspec/src/hardfork.rs explicitly maps Unzen to Cancun, Prague and Osaka. These rules are fixed for this Etna revision; a future L1 hard fork does not silently change L2 execution. New L2 execution rules require a reviewed protocol revision and matching immutable proving programs. The independent Go reference is the Taiko-geth dependency pinned in this repository's go.mod:308, commit prefix 8e98046bfd6a. The full Alethia commit above is the normative inherited reference; the Go code is corroborating evidence, not a second selectable execution policy.

Proposed rule — explicit Etna overrides: the following choices override inherited consensus/derivation behavior where it differs. All inherited opcode, account, storage, intrinsic-gas, refund, transaction-validity and receipt rules otherwise remain the pinned profile's rules. Both required ZK programs prove this same profile and these overrides; an implementation cannot choose whichever client accepts a payload.

2. Exact canonical body

Proposed rule: the complete body is the following single canonical Ethereum RLP value. It is uncompressed: no zlib, dictionaries, alternate encodings or private permutations. RLP integers use the shortest big-endian nonnegative encoding, with zero represented by the empty byte string. Fixed-size byte fields retain their exact size, including leading zero bytes. Reject nonminimal RLP, wrong list/string kinds, wrong arity, out-of-range integers, duplicate or omitted required records, and all trailing bytes.

BodyV1 := RLP([ version, blocks, forced ])
version := uint8(1)
blocks  := [ Block_0, ..., Block_(N-1) ]              // 1 ≤ N ≤ 60
Block_i := [ headerRlpBytes, [ txRaw_0, ..., txRaw_m ] ]
forced  := [ ForceBody_0, ..., ForceBody_(F-1) ]      // 0 ≤ F ≤ 4
ForceBody_j := [ queueIndex, rawForcedTx, outcome, receiptHash ]

queueIndex  : uint64 encoded as a minimal RLP integer
rawForcedTx : RLP byte string, 0…2048 bytes; malformed bytes are allowed here
outcome     : uint8 encoded as a minimal RLP integer, exactly 0…4
receiptHash : exactly 32 bytes, including 32 zero bytes for outcomes 0…2

headerRlpBytes : RLP byte string containing one complete canonical header RLP
 txRaw_k      : RLP byte string containing one complete signed transaction envelope
// All transaction envelopes, including legacy transactions, are strings here.
// A legacy transaction's internal RLP list is never substituted for that string.

bodyHash = keccak256(the complete BodyV1 byte sequence)
B_i = the exact canonical RLP encoding of Block_i
recordHash_i = keccak256(B_i)

Proposed rule — bounds before allocation: body length is 1…122,880 bytes in the one-blob mode or 1…32,768 in calldata mode. Every body/header/transaction length is checked against the enclosing remaining bytes before allocation. A header byte string is 1…1,024 bytes. Each block has 1…1,024 transaction strings including the anchor; total transaction count across the segment is at most 8,192. Each transaction string is nonempty and no larger than the body-mode cap. The outer schema has at most four nested list levels; inner header/transaction parsing is separately bounded by its exact schema and byte cap, not recursively treated as arbitrary outer RLP. These parser caps coexist with stricter EVM intrinsic and block/segment gas constraints.

Proposed rule — transaction bytes: txRaw is the Ethereum network signed encoding, not an RPC JSON object or unsigned call description. Type 0 is its canonical signed nine-field RLP list. Types 1, 2 and 4 are their single type byte followed by the canonical EIP-2718 payload list, with respectively 11, 12 and 13 fields. Typed envelopes require the configured L2 chain ID. Legacy signatures may be ordinary unprotected Ethereum signatures or EIP-155 signatures for that L2 chain ID; this preserves Ethereum's legacy replay semantics rather than inventing a new signing scheme. Recovery, low-s, integer bounds, authorization processing and validity otherwise follow the pinned execution profile, except the reserved-system rule. Access lists and type-4 authorization lists are public inside those exact bytes.

Proven — public reconstruction: the block header, signed transaction order, anchor arguments and every rejected forced transaction are present in the public body. A local executor with the parent state and authenticated public context can reproduce execution. ZK state/MPT witnesses may remain private because they prove facts against the committed prior state; they cannot supply a missing transaction, alternative anchor call or private forced-input byte string. Missing parent state still yields UNKNOWN under A-ARCHIVE, not an invented successful local validation.

3. Complete header, with no free private knobs

Proposed rule: headerRlpBytes has exactly the 21 fields of the post-Osaka Ethereum execution header, in the order below. Fixed hashes are 32 bytes, beneficiary 20 bytes, bloom 256 bytes and nonce 8 bytes; integers use canonical Ethereum RLP. No optional suffix field is omitted or appended in this revision. The hash of these exact bytes is the block hash committed by the signed claim and ordered block-hash tree. Expected execution outputs in the header are claims to verify, not trusted hints.

4. Bounded L1 header authentication

Proposed rule: HeaderStore accepts one canonical RLP header list of at most 4,096 bytes and 12…32 top-level fields. It extracts the stable execution-header prefix positions: parentHash at 0, stateRoot at 3, number at 8 and timestamp at 11. Require parentHash/stateRoot to be exactly 32 bytes, number/timestamp to be minimal nonnegative integers fitting uint48, number<block.number, nonzero BLOCKHASH(number), and keccak256(the exact complete RLP bytes)==BLOCKHASH(number). Parse lengths before allocation, reject noncanonical encodings/trailing bytes, and retain the authenticated number/hash/stateRoot/timestamp tuple immutably. Repeated identical pins are idempotent.

Proven — append-compatible scope: appended fork fields are authenticated because the comparison hashes the entire header, not merely the extracted prefix. They are not trusted caller assertions and are not execution inputs selected by a prover. The parser need not invent the future Glamsterdam/Hegota suffix schema merely to import these four fields. It does not import an L1 header from an arbitrary RPC response without the EVM history check.

Open — launch conformance: confirm that the deployed L1 fork preserves these extracted positions and the complete header fits the 4,096-byte/32-field bounds. A fork that reorders the stable prefix or exceeds those bounds needs a reviewed parser revision before Etna can rely on it. The fixed 21-field L2 header schema above is a separate Etna execution choice and must not be confused with this L1 append-compatible parser.

5. Exact basefee and ETH accounting

Proven/source: today's Rust client reproduces the EIP-4396 calculation at packages/taiko-client-rs/crates/protocol/src/shasta/constants.rs:103–176. It uses parent minus grandparent time and divides the fee delta by the unadjusted gas target. The pinned public Alethia source fixes elasticity 2, denominator 8, adjusted-target cap 95%, a two-second target, and the clamps below. Etna changes only that target to one second in this calculation; the resulting header limit and gas consumption are independently fixed above.

// All intermediate arithmetic is unsigned uint256 with checked conversion.
// p is the immediately preceding L2 header; g is its parent.
// Read both from authenticated execution ancestry, never from wall-clock time.
if p.number == 0:
    nextBaseFee = 25_000_000 wei
else:
    require p.timestamp > g.timestamp
    dt = p.timestamp - g.timestamp                  // seconds
    G = floor(p.gasLimit / 2)                       // require G > 0
    A = min(floor(G * dt / 1), floor(p.gasLimit * 95 / 100))
    f = p.baseFeePerGas
    if p.gasUsed == A: candidate = f
    if p.gasUsed > A:
        delta = max(floor(floor(f * (p.gasUsed-A) / G) / 8), 1)
        candidate = f + delta
    if p.gasUsed < A:
        delta = floor(floor(f * (A-p.gasUsed) / G) / 8)
        candidate = max(f - delta, 0)
    minimum = 10_000_000 wei for Taiko mainnet L2 chain ID 167000;
              5_000_000 wei for the configured non-mainnet deployment
    nextBaseFee = min(max(candidate, minimum), 1_000_000_000 wei)

Proposed rule: migration preserves the actual parent and grandparent headers and parent basefee; the first Etna block does not reset fees to the genesis value. The new one-second target applies when computing the first Etna header. The genesis-only branch above remains specified for completeness. If required ancestor information is missing, validation is UNKNOWN until recovered; it is not replaced by a guessed timestamp or default fee.

Proposed rule — ordinary transaction fees: let charged gas after the pinned refund/data-floor rules be g, block basefee be f and the transaction's effective priority fee be t. Debit the normal sender's gas payment under the pinned execution rules. Credit all g×t to coinbase. From B=g×f, credit all B to coinbase and zero new basefee to Anchor. No basefee is burned, no TAIKO is used to pay EVM gas and no L1 beneficiary is substituted for header coinbase. At this fixed100% share there is no split-rounding remainder. This follows main source at31df8fe8ef7c027840abf122ec36f87c41c3ce94; the earlier research snapshot used75%. Historical migration execution retains each legacy proposal’s recorded share.

Proven/source: the pinned public Taiko-geth core/state_transition.go:595–607 implements the coinbase/treasury basefee split and excludes anchor transactions. Its buyGas at lines 305–309 exempts an anchor's ETH prepayment/balance check, while ordinary nonce checks remain. The anchor's gas still consumes block resources, and lines 704–713 prevent an ETH refund for gas that it did not pay. These are the semantics retained below, not a requirement to fund a special operator account.

Proven — arithmetic example: with p.gasLimit=10,000,000, p.gasUsed=6,000,000, dt=1 and f=100,000,000 wei, G=A=5,000,000. The increase is 2,500,000 wei, giving 102,500,000 wei. With the same fields and dt=2, A=9,500,000; the decrease is 11,250,000 wei, giving 88,750,000 wei. A normal transaction consuming 21,000 gas at the first fee with a 2,000,000-wei tip credits 2,152,500,000,000 wei of basefee plus 42,000,000,000 wei tip to coinbase and zero to Anchor. All values are ETH-wei.

6. One public signed anchor, using one fixed origin

Proposed rule: the publisher selects the segment origin before constructing its first block. Every block's transaction zero contains the full signed Ethereum type-2 anchor transaction. Its checkpoint is exactly (origin.number,origin.hash,origin.stateRoot), its _originHash=origin.hash, and its revision equals s.revision. The node authenticates the selected earlier L1 header in its own L1 view before issuing the preconfirmation; it need not wait for a pin transaction. HeaderStore must authenticate that identical tuple by canonical landing, and anyone may pin it during staging/proving while BLOCKHASH history remains available. The fixed tuple is included in the public StageContext; pin timing selects no new execution field. Reusing that same checkpoint in the remaining blocks is permitted; the Anchor's block-history work still occurs, while unchanged checkpoint publication is idempotent. No older per-block origin, L1 ancestry chain or privately selected checkpoint is permitted in this initial revision.

Proposed rule — protect the reserved identity: reject every nonzero-index transaction whose recovered sender is the system address, whatever its destination. Also reject an ordinary type-4 transaction if any canonically recoverable authorization tuple names that address as its recovered authority, even if the authorization's nonce or chain selection would otherwise make it ineffective. Other type-4 authorities retain the pinned EIP-7702 behavior. This restriction is needed because embedded authorization could otherwise alter the system account's nonce or delegation without using it as the outer transaction sender. The activation preflight must verify that the retained system account has no delegated/ordinary code and has the expected nonce. The circuit validates the reserved-identity restriction, not only the txpool. A forced request violating it receives outcome 1.

Proposed rule — bounded public activation proof: the entire beginEtna calldata, including selector, ABI offsets, lengths and padding, is at most 16,384 bytes. Each of its two MPT arrays has 1…65 nodes; each node is at most 532 bytes and is canonical Ethereum secure-trie RLP. Nodes appear in traversal order; embedded children are not duplicated as extra proof nodes; no unused or trailing node is accepted. The account proof authenticates the configured Inbox under origin.stateRoot; the storage proof authenticates the exact activation field defined in the migration plan under that account's storageRoot. These bytes are part of the anchor, Block record, bodyHash and DA; they are not prover-only witness inputs.

Open — activation measurement: before launch, the actual activation account/storage proofs must fit both the 16,384-byte calldata bound and the 1,000,000-gas anchor limit with the selected implementation. Arbitrary possible Ethereum tries are not asserted to meet that gas limit. If the real activation proof cannot fit, this revision cannot activate unchanged; revise and review the migration profile before launch. After activation, anchors have only the fixed 164-byte calldata and do not require such MPT proofs.

Proven — locality: a node can compare the checkpoint directly with its authenticated origin tuple and execute the public transaction. No future L1 landing timestamp, stage ID, job ID, producer authorization, segment taskHash, manifestRoot or bodyHash appears in the current segment's anchor calldata. That exclusion prevents a state-root/hash cycle. A first-segment activation proof refers to already established L1 activation state, not to the future first Etna execution root.

7. Forced bytes, including rejected requests, are in DA

Proposed rule: forced.length equals forceEnd-forceStart and the exact mandatory prefix supplied by Inbox's authenticated requiredForceHash. ForceBody indices are that consecutive increasing interval. For every entry, including outcomes 0, 1 and 2, keccak256(rawForcedTx) must equal its queue record's transactionHash. Its public outcome and receiptHash must equal the corresponding explicit ForceOutcome calldata and the proof-bound forceOutcomesRoot. A proof cannot replace malformed bytes with a private decoding witness or claim a hash without showing the bytes.

Proposed rule — execution position: process these at most four requests, in queue order, immediately after the first block's successful anchor and before any discretionary transaction. State-valid requests execute consecutively at transaction indices 1 onward; rejected requests do not enter the Ethereum transaction list or increment a sender nonce. Validate each next request against the state resulting from the anchor and earlier executed requests. With at most 1,000,000 declared gas per eligible request and the 1,000,000-gas anchor, the full forced prefix fits the 10,000,000 first-block limit. Publishers cannot shrink that limit or claim earlier discretionary execution made the prefix state-invalid.

Proposed rule — exact outcome classes: retain the core tags: 0 malformed encoding/signature envelope; 1 unsupported type or protocol resource/identity restriction; 2 state-invalid under the selected execution rules; 3 executed successfully; 4 executed and reverted. First check that the raw envelope has an unambiguous canonical outer Ethereum structure. An unsupported typed prefix with a canonical complete RLP payload is outcome 1; an empty/truncated/noncanonical envelope is outcome 0. For supported types, malformed outer fields or invalid outer sender-signature encoding is 0, then protocol bounds and the reserved-system restriction are checked for 1, then ordinary transaction nonce/balance/basefee validity for 2. Canonically represented nonreserved EIP-7702 authorizations that fail an authorization-specific validity check are skipped exactly as the pinned EIP-7702 profile prescribes; their failure alone does not reject the outer transaction or manufacture outcome 0/2. A structurally malformed authorization list still makes the envelope malformed. A valid transaction that reverts in EVM is 4, never a rejection. Unknown types do not need imaginary signature-field schemas merely to classify their canonical unsupported envelope.

Proposed rule — receipts: outcomes 0…2 have exactly 32 zero bytes for receiptHash. For 3 or 4, hash the exact Ethereum receipt envelope produced at that first-block position: legacy RLP for type 0; type byte plus receipt RLP for a typed transaction. The receipt includes status, cumulativeGasUsed including the anchor/prior executed requests, logsBloom and logs. Its status must match 3 versus 4. Every included forced raw transaction is byte-for-byte the matching txRaw entry in the first block, in FIFO order. The declared gas bound is checked before execution; all normal execution gas constraints still apply.

Proven — data and ordering: copying a rejected request's bytes into a private proof witness cannot satisfy this codec. Inserting a discretionary transaction before the forced prefix changes the public order and fails the relation. Keeping raw rejected requests public permits every observer with the same parent state to independently challenge the classification in its local validation, while the validity proof enforces it for L1 acceptance.

8. Exact manifests and fixed fragmentation

Proposed rule: the early block claim and the sealed segment use different commitments, with explicit domains. A DutyClaim's manifestRoot is the block fragment root FR below. A SegmentStatement/StageContext manifestRoot is the ordered segment manifest MR. Neither substitutes for the separately defined ordered blockHashesRoot or bodyHash.

// All abi.encode calls are ordinary canonical ABI, never abi.encodePacked.
BLOCK_FRAGMENT_TAG = keccak256(bytes("ETNA_BLOCK_FRAGMENTS_V1"));
SEGMENT_MANIFEST_TAG = keccak256(bytes("ETNA_SEGMENT_MANIFEST_V1"));
FD = keccak256(abi.encode(BLOCK_FRAGMENT_TAG,
    uint256(l1ChainId), uint256(l2ChainId), address(inbox), address(anchor),
    uint64(revision)));

// B_i is the complete standalone Block_i RLP, including header and anchor.
n = B_i.length;                       // require 0 < n ≤ body-mode cap
count = ceil(n / 32768);               // exactly 1…4
chunk[j] = B_i[32768*j : min(n,32768*(j+1))];
lengths[j] = uint32(chunk[j].length);   // positive; all but last equal 32768
hashes[j] = keccak256(chunk[j]);        // bytes32
FR_i = keccak256(abi.encode(FD, uint48(blockNumber), bytes32(blockHash),
    uint32(n), uint32[] lengths, bytes32[] hashes));

struct BlockManifest {
    uint48 number;
    bytes32 blockHash;
    bytes32 recordHash;               // keccak256(B_i)
    uint32 recordLength;              // exact B_i.length
    bytes32 fragmentRoot;             // FR_i
}
// rows contains exactly one tuple per block in canonical order, no caller hints.
MR = keccak256(abi.encode(SEGMENT_MANIFEST_TAG, s.domain, s.oldHeadHash,
    uint48(s.firstL2Number), uint48(s.endL2Number), BlockManifest[] rows));

DutyClaim.manifestRoot = FR_i;
DutyClaim.fragmentCount = count;
DutyClaim.fragmentIndex = j;
DutyClaim.dataDigest = hashes[j];
DutyClaim.byteLength = lengths[j];
SegmentStatement.manifestRoot = MR;
StageContext.manifestRoot = MR;

Proposed rule: both fragment arrays have exactly count entries. No empty last fragment, implicit zero padding, variable-size intermediate chunk, sorted digest list or duplicate-last-chunk convention is accepted. A client reconstructs B_i from all promised chunks, verifies lengths/digests/FR_i and parses the complete record, then checks its header hash and executes it. A signed fragment alone is not a complete block. Each version-2 bonded chunk must be publicly posted by issuedAt+240 with this exact FR preimage and its complete ≤32,768 bytes. A challenge response answers the same separately reserved chunk; it is not required to post the entire segment. A generic blob stage is not this early-fragment receipt; see publication binding.

Proven — no hidden cycle: construct public origin and header inputs, signed anchor/user transaction bytes, execute, obtain the complete headers and B_i, then compute fragments/FR_i and the body/manifest/block roots. Only afterward compute contextHash/taskHash, salted stageId, the full statement and producer authorization. Current block headers/anchors never contain those later hashes. FR_i depends on the block and fixed execution domain, not the future end-of-segment boundary, assigned job or staging salt, so early one-second DutyClaims remain computable before a segment is sealed. Its header already binds segmentNumber through extraData; repartitioning that changes the number or forced-prefix position requires new headers/records/proofs and invalidates incompatible old soft claims. The segment MR additionally commits its chosen parent/range. bodyHash commits the forced-record bytes, including rejected requests; MR is not falsely claimed to contain those separate rows.

9. Bind early preconfirmation to these exact bytes

Proposed rule: the preconfirmation wire message carries the exact B_i bytes and the public origin/revision/segment context needed to validate its header. Its publisher attribution uses the EIP-712 DutyClaim schema in the EtnaDuty version-2 domain: blockHash equals keccak256(headerRlpBytes), manifestRoot equals FR_i, and each signed position's digest/length matches its deterministic chunk. The subject remains the specified revision/base-accepted-head/L2-height tuple. No detached RPC header, unsigned alternative transaction list or different anchor descriptor may replace the bytes under that signature.

Proposed rule: a complete displayed bonded block needs a valid separately reserved publisher claim for every chunk; all share the same owner, subject, blockHash, FR_i, fragmentCount and revision. Optional custodians supply their own equivalent chunk promises. A timely publication by anyone satisfies all matching claims; each absolute deadline still follows its own signed issuedAt. The outer P2P framing is transport metadata, not another consensus encoding: only the canonical bytes and complete signed claims establish this promise. If a node displays an unbonded candidate, it still performs full codec/header/anchor/execution checks and explicitly marks that no bonded publication service covers it. Unknown parent state or origin remains UNKNOWN.

Proven: a one-chunk record can be signed as soon as that block executes; it does not wait for the later segment's MR, proof, stage ID or producer authorization. A later stage-age gate constrains canonical eligibility separately. This codec therefore supplies local validity inputs, not a global soft fork-choice or finality rule.

10. Worked examples and rejection boundaries

Proposed conformance fixtures: Codec vectors gives numeric ABI offsets, Keccak/manifest roots, a 32,769-byte split and negative cases using these exact formulas. Its toy framing example is deliberately not an execution-valid segment.

Proven — codec-only RLP example: bytes c901c6c5820102c103c0 decode unambiguously as [1, [[headerBytes=0102, [txBytes=03]]], []]. The inner block bytes are c5820102c103. This is intentionally not a valid Ethereum block: the header and transaction fail their inner schemas. It is a small framing fixture, not evidence of a valid execution/proof. Encoding legacy raw bytes as a nested RLP list instead of a byte string produces a different schema and must be rejected.

Proven — fragmentation example: if an actual complete B_i has 50,000 bytes, count=2, lengths=[32,768,17,232], and the slices are [0,32,768) and [32,768,50,000). FR_i commits that exact order, both keccak digests and total length 50,000. Two 10-TAIKO positions cover the two promises. This block cannot fit the 32,768-byte calldata body mode even before container/force overhead, so it requires the blob path. A 32,768-byte B_i has exactly one chunk, never an empty second chunk; its enclosing BodyV1 is larger and therefore also exceeds the calldata-mode body cap.

Proven — forced example: let the frozen mandatory queue interval be [20,23). Record 20 contains empty malformed bytes (outcome 0), 21 a valid transfer (outcome 3), and 22 a valid call that reverts (outcome 4). All three raw byte strings are in forced[]. The first block transaction list begins [anchor, exact bytes of 21, exact bytes of 22, discretionary…]. Record 20 has a zero receiptHash and no transaction-trie entry. The other two receipt hashes include their actual cumulative gas positions. This example illustrates ordering; success/state validity depends on the authenticated parent state.

Proven — consequences and limits: exact public encoding prevents a producer from privately changing ordering, anchor fields or rejected forced bytes while retaining the same accepted data commitment, under A-CRYPTO and correct relation enforcement. It does not create data from an unavailable blob, solve L1 censorship, prove fair competition, or make a provisional branch final. A larger body must be sealed into smaller segments or use the permitted larger DA mode with a new consistent context; it cannot truncate bytes under an existing proof.
