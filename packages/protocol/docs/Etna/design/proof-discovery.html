Share a proof without reserving the race

A prover can announce work and offer a completed proof leaf. Every recipient checks the exact statement and remains free to prove and submit independently.

Research candidate; production feasibility remains unresolved. Current R4/R6/R7 acceptance is open. This page specifies proposed rules; historical model-generated review does not establish a usable, affordable operating profile. See the resource and funding evidence and comment dispositions.
Proposed, optional client behavior. This module adds advisory network messages only. The existing Inbox, statement encoding, producer authorization, job accounting, two-proof predicate and public data requirements remain authoritative. An advertisement has no on-chain effect and creates no service obligation.

Source and scope: this adopts the explicit proof-sharing and landing-intent topics in Claude's Etna design, PR #22184. That design emphasizes fungible proofs. Etna's present full statement also binds producer, beneficiary, job and stage, so reuse here is deliberately restricted to the same exact public input. Changing payment assignment is not a network optimization.

Classification: message schemas and client behavior below are proposed. Deductions marked proven assume the unchanged verifier and hash rules are correctly implemented. Network delivery and willing peers are assumed. Interoperability, verification cost and bandwidth measurements are open; the prior red-team convergence is not an implementation test of this addition.

1. The problem: complementary work can remain undiscovered

Alice may already have the required RISC0 leaf while Bob has the SP1 leaf for the identical segment statement. If they cannot discover each other's work, each might repeat the missing computation. A small advertisement lets them request and verify a useful artifact without making either prover an assigned gatekeeper.

The same coordination can reduce duplicate work when someone expects to submit soon. Such an expectation can be false. A client must never make a competitor's announcement a prerequisite for progress or stop its only recovery path because of it.

2. A reusable leaf has an exact identity

The recipient independently computes statementHash = keccak256(abi.encode(s)) from the complete canonical SegmentStatement. It recomputes publicInputHash from that hash, the existing proof domain and the authenticated requiredForceHash, exactly as the core verifier boundary specifies. Matching task hashes, body hashes or terminal state roots alone is insufficient.

// Interface sketches for peer messages, not contract entrypoints.
ProofIdentity {
  l1ChainId, l2ChainId, inbox, anchor,
  revision, immutableCircuitId,
  statementHash, publicInputHash, oldHeadHash, stageId
}

ProofOffer {
  identity: ProofIdentity,
  backendId, programKeyId,
  leafHash, leafByteLength
}

LandingIntent {
  identity: ProofIdentity,
  estimatedReadyInSeconds
}

ProofRequest  { offerDigest }
ProofResponse { offerDigest, exactLeafBytes }

Proposed encoding: fixed field order above; addresses are ABI address words, chain IDs and stageId are uint256, revision is uint64, advertised length and ready interval are uint32, and all hashes, circuit/backend/program identifiers are bytes32. The identity is a nested static ABI tuple. An offer contains exactly one identity and one backend leaf descriptor; it carries no unbounded list, executable callback or URL. The backend identifiers identify the existing RISC0_RETH or SP1_RETH adapter, and the program-key identifier must equal that adapter's immutable revision manifest. They are labels to check against existing configuration, not a new key registry.

Proposed offer digest: keccak256(abi.encode("ETNA_PROOF_OFFER_V1", offer)). The response leaf must hash to leafHash and have exactly the offered byte length. The digest identifies a peer transfer; it authenticates neither the statement, producer assent nor proof validity. The transport may identify its peer, but these messages require no protocol-role membership or signature and supply no slashable promise. Existing canonical authorizations are separate signed objects with their existing domains.

A receiver checks the repeated chain, revision, parent and stage fields against the canonical statement and configured deployment before allocating proof work. It obtains that statement, required force records and full data through existing bounded retrieval paths, not from an untrusted substitute named by the offer. An unknown dependency means the advertisement is unverified; it does not make the candidate block invalid.

3. Receive, verify, combine, then submit

  1. Apply local peer, bandwidth, outstanding-request and CPU budgets. Decode a single bounded advertisement and discard unsupported domains, revisions and program identifiers cheaply. A rate limit is a local scheduling policy, not a consensus parameter or global participant ban.
  2. Recompute the exact statement identity from authenticated inputs. A leaf for a different beneficiary, producer, job, stage, force prefix or proof domain is a different artifact, even when the execution body is identical.
  3. Request the named offer from that peer. Reject oversized length declarations before allocation and stop oversized responses while streaming. An individual leaf can never exceed the existing 16,384-byte total proof-envelope cap; two individually bounded leaves may still be too large together.
  4. Check exact length and hash, then independently verify the leaf against the matching immutable backend/program and recomputed publicInputHash. Keep artifact verification separate from current canonical applicability: a correct proof can become stale when another segment consumes its parent.
  5. For matching valid leaves, construct the existing canonical abi.encode(bytes risc0Proof, bytes sp1Proof). Include ABI offsets, lengths and padding in the 16,384-byte total limit; reject excess or noncanonical encoding. Verify the complete adapter predicate. No new proof aggregation format is introduced.
  6. Recheck the current parent, revision eligibility, full data and stage maturity, forced prefix, producer/reward authorizations, value and rent funding, and all ordinary Inbox gates before submitting. The data and whole-call bounds remain unchanged; a proof offer cannot replace canonical data availability.

Proposed local state machine: SEEN → IDENTITY_CHECKED → REQUESTED → VERIFIED_LEAF → COMPLETE_ENVELOPE. At any step, malformed or demonstrably wrong artifacts are discarded. A timeout leads to UNAVAILABLE or another peer request. Parent consumption or expiry makes a complete envelope STALE or EXPIRED under the existing rules. Neither a missing offer nor a missed intent ETA changes a block's execution validity, a bond, a reward or a job deadline.

Proven under A-CRYPTO/A-IMPLEMENTATION: two verified required leaves for the identical existing public input satisfy the same cryptographic conjunction regardless of which peers supplied the bytes. This permits transfer of existing proofs. It does not establish that an arbitrary combining caller has the statement's necessary authorization or an entitlement to its rewards.

4. Worked example: what can and cannot be reused

Alice and Bob agree on revision 1, stage 91 and the same complete statement S with beneficiary Carol and job 7. Suppose Alice offers a valid 4,000-byte RISC0 leaf and Bob a valid 6,000-byte SP1 leaf for S's exact public input. These sizes are illustrative, not measured backend sizes. The canonical two-bytes ABI envelope is 128 + 32×ceil(4000/32) + 32×ceil(6000/32) = 10,144 bytes, inside the existing 16,384-byte cap.

A recipient verifies both against the pinned program keys, then may relay the complete existing submission if all its authorization, DA, stage, parent and funding checks pass. Carol remains the named beneficiary. The relay does not earn a new reward merely by combining the leaves.

Dave copies the body but changes the beneficiary from Carol to Dave. The execution task may be identical, but statementHash and publicInputHash change. Neither advertised leaf is valid for Dave's new statement. He must obtain appropriately bound new proofs and authorizations. Likewise, an SP1 proof for revision 2 cannot complete Alice's revision-1 envelope.

Alice also advertises “ready in 30 seconds” and goes offline. Bob can request elsewhere or prove and submit immediately whenever the existing gates allow it. The 30 seconds creates no exclusive lease, priority, on-chain commitment or requirement to wait.

5. False advertisements are a resource problem, not a consensus vote

Client defenses and their limits
Attack Response Residual
Advertise many fake leaves to consume verification CPU. Cheap identity/length checks first; bounded local queues; independently verify fetched artifacts; do not forward unverified bytes as verified. Sybil peers can still consume bandwidth and some verification effort. Measure admission and scheduling policy; no open network makes that cost zero.
Announce an imminent landing and never submit. No consensus reservation; clients retain independent proving and submission paths. ETA has no bond or job semantics. A client that voluntarily stops its only prover can hurt itself. An advisory promise provides no compensation.
Replace a beneficiary, proof key, queue prefix or revision. Recompute the exact public input and use the pinned backend/program; reject mismatched leaves. A common error in the authoritative statement or relation is outside transport checks.
Replay a valid old offer after its parent was consumed. Keep proof correctness distinct from current applicability; check the Inbox head before relay. A competing landing may still win after that check. Ordinary stale submissions may pay gas; frame behavior remains as separately specified.
Withhold the bytes after offering their digest. Mark that transfer unavailable, try other peers or prove independently. The offer itself is not an objectively bonded publication duty. Existing signed service claims, if any, retain their separate evidence rules.

Proven scope: none of these messages reduces the proof threshold, extends a stage lifetime, waives full DA, grants a lease, cancels a job, reserves a bounty or changes slashing. No canonical action waits for an intent holder, a selected peer or an assigned worker.

Assumed: useful peers have incentives to share completed leaves, and at least one party can fund independent recovery. This module promises interoperability, not free proving or a profitable public-proof market. Open: cross-client encoding vectors, streaming limits, worst-case verification scheduling and observed sharing rates belong in the launch evidence.

Challenge this addition

Try combining two offers that agree on the body but differ in one payment, queue or revision field. Try filling every peer queue with valid-looking identities and invalid leaves. Then disconnect every advertising peer. The client should preserve exact verifier binding, bounded local work and an independent submission path; it should never infer a new canonical right from network metadata.
