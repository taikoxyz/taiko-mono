Checkpoints, custody and migration

Open — launch blocker. This is a source-grounded migration specification, not an authenticated deployment manifest. No live proxy address, implementation, owner, treasury recipient or stored state has been verified. R2 is achievable only if the preflight conditions below hold; this page does not declare the design implementation-ready.

How to read the claims

Proven identifies a baseline source fact or a deduction with a stated argument. Assumed identifies a normative design obligation under A-IMPL: the eventual implementation, circuit and migration procedure conform to this specification. Open identifies evidence still required. A section's label applies to its paragraphs, lists, interface sketches and diagram unless an item is explicitly relabeled. A proposed interface is never a claim that code already exists.

Assumed — the boundary that remains fixed

Retain every existing L1 and L2 SignalService, Bridge, ERC20Vault, ERC721Vault and ERC1155Vault proxy address. Retain the L2 Anchor proxy, resolver proxies and all existing protocol-controlled token wrapper proxies as well. Upgrade implementations and their immutable wiring; do not deploy replacement custody addresses or move user escrow. New L1 Inbox, role registry, header store and optional frame sender addresses are permitted. An implementation contract deployed for an existing proxy is not a replacement Bridge or Vault address.

The DAO owns the upgrade authority only. Every ordinary protocol role is open under objective rules. Root publication and asset release retain contract-to-contract provenance checks: Inbox → L1 SignalService, Anchor → L2 SignalService, Bridge → Vault and Vault → wrapper. These checks authenticate proof-verified state transitions; they do not select a human operator. Token approvals, message owners' retry/recall choices and users' ability to spend their own assets remain intact.

The frozen addresses are only part of R2. The upgrade preserves storage locations, message encodings, chain IDs, escrow, signal-slot formula, trusted historical checkpoints, received-signal caches, message-status history, token mappings and token balances. No preconfirmed root enters a settlement checkpoint merely because a publisher or custodian signed it.

The new SignalService implementation makes checkpoint writes idempotent and non-overwriting: an empty entry accepts a nonzero hash/root, an identical existing entry succeeds without changing state, and a conflicting existing entry reverts. The existing mapping suffices; no storage slot is added for this rule. Inbox and Anchor enforce advancement; SignalService need not impose a global latest-height variable. A same-history conflicting root therefore fails even if a caller accidentally attempts a duplicate write.

Proven argument under A-IMPL + A-CRYPTO. If the Inbox accepts only a sound proof for the current parent and the checkpoint matches the proof's terminal state, a bridge withdrawal can authenticate only a signal in that accepted L2 state or an already trusted historical state. A voluntary publisher, custodian or job worker never receives checkpoint authority. Their signatures cannot mint escrow-backed assets.

Assumed A-L1. A checkpoint saved in an Ethereum transaction is accepted settlement state, not a declaration of Ethereum consensus finality. Wallets and relayers call it finalized only after the enclosing L1 block is finalized under Ethereum's own rules. An L1 reorg rolls back head, checkpoint, cache and bridge effects in that L1 history. Cross-layer users must also wait for canonical derivation and finality; the L2 Anchor alone cannot establish L1 finality.

Assumed — revision1 addition: deploy a new permissionless DARegistry and pin its address/code semantics in the new Inbox revision. It is not a replacement custody contract. Its earlier generic publication creates no checkpoint; only a mature staged context accepted with complete republished DA and a valid proof reaches the SignalService interface below. See staging. The first Etna block therefore follows activation, staging and maturity; this introduces no additional DAO action.

anchorEtna is an execution-system action any builder can derive, not a credential assigned to a private operator. The engine and circuit reject user transactions impersonating a system action, a non-first anchor, duplicate/missing anchors, a false root, a checkpoint different from the segment origin and a wrong revision. Contract-only provenance from Anchor to SignalService remains mandatory. The baseline golden-touch sender is a deterministic system convention, not an authorization grant to a role; retaining that sender convention must not require a privately held key.

The anchor's origin and revision are commitments, not independent oracles: the L2 EVM cannot read an arbitrary L1 HeaderStore. Every initial Etna block uses the exact segment-origin HeaderStore tuple supplied to the L1 verifier; no additional older checkpoint is selected. A full node checks that same exact origin binding before marking a preconfirmation valid; absence of the header witness is UNKNOWN. No unverified root becomes valid merely because the anchor Solidity call returned.

Retain the parent-block accumulator in slots 256–257 and the blockHashes mapping at slot 251. The first Etna anchor extends the actual last legacy L2 block; it does not reset the ancestor accumulator. The revision change and exact type-2 system-transaction envelope are fixed by the migration boundary, the codec profile and proven execution. The transition must include the new implementation's code hash, retained proxy address and exact old ancestor state. A preinstalled transitional Anchor supports anchorV4 throughout the finite legacy drain; removing it before that drain finishes would halt historical derivation. The one-way switch described below disables it at the first Etna block.

Open. The complete engine encoding and circuit implementation of the system transaction must be specified and audited with the core derivation rules. The source currently validates GOLDEN_TOUCH_ADDRESS, but neither that address nor a successful call independently proves correct L1 data (Anchor.sol:86–88,124–138,173–185). This sketch is not evidence of an already available secret-free client implementation.

The L2 native token stays ETH. Follow the refreshed main source allocation:100% of new Etna basefee goes to coinbase,0% to Anchor. Historical drain execution uses its recorded legacy percentage; this change never rewrites prior fees or balances. sweepNativeFees moves accumulated legacy fees and any other native ETH to one immutable, existing fee-treasury recipient identified by the migration manifest; callers cannot choose a destination or collect a cut. A failed recipient transfer leaves the balance untouched and affects neither anchoring nor settlement. Service/job rewards are separately prefunded; liveness must not depend on a treasury operator paying them. Ownership of the recipient's own funds is ordinary asset ownership, not a protocol operating role.

Disable legacy withdraw(address,address) for everyone. Do not add arbitrary-token recovery: accidentally sent non-native tokens remain in place unless a later DAO-authorized implementation upgrade defines a audited recovery. No runtime treasury address setter exists. The migration does not silently assume that any specific live treasury address is known.

The final selector audit includes proxy fallback and receive functions, router-local UUPS/Ownable methods, delegated old code, inherited methods, multicalls, externally callable initializers and every immutable/resolver target. A generic fallback to old code is forbidden. Denying a selector only in a front-end ABI is insufficient. In particular, baseline EssentialContract.pause() is nonvirtual; an implementation cannot claim to remove it through an override Solidity does not permit. Replace the relevant base behavior with identical storage, or ensure its authorization hook unconditionally reverts and remove effective pause checks.

Wrapper initialization is a separate case: an existing wrapper rejects unused initialization selectors, while a genuinely new wrapper created for a previously unseen canonical asset must still initialize. New wrapper deployment and initialization occur atomically through the retained Vault, set DAO ownership and immutable Vault binding, and consume all initialization versions. The deployment implementation's uninitialized proxy must never be externally exposed between creation and initialization. A live wrapper outside the DAO upgrade authority or with incompatible/custom initialization is a preflight failure, not an exception to R1.

The detached quota utility is not replaced with an implicit administrator. Removing quotas trades an operational circuit breaker for proof/security assumptions. Bridge safety rests on authenticated roots, replay protection, correct escrow and verifier soundness. Adding a new automatic limit would require a separately specified permissionless, nonblocking mechanism; this draft does not use one.

Proven limitation. Upgrade-only DAO authority still permits a future malicious upgrade to reintroduce powers or steal custody. R1 expressly retains that trust boundary. “Permanently disabled” means no call can reactivate the selector within the installed revision; it cannot mean immutable across arbitrary future DAO upgrades. Safety includes A-UPGRADE: authorized future revisions preserve the intended invariants.

Assumed — preserve historical assets and proofs

Keep keccak256(abi.encode("TAIKO_MESSAGE", message)), existing message field widths and all status enum values unchanged. A message sent before the upgrade may be processed, retried or recalled after it under its original owner and fee rules. Preserve nextMessageId, every NEW/RETRIABLE/DONE/FAILED/RECALLED record and both chains' original Bridge addresses. Do not reset old contexts or statuses via a recovery initializer.

Keep the sent-signal storage key keccak256(abi.encodePacked("SIGNAL", uint64(chainId), app, signal)) and store the signal value itself, as current source does. Keep VERSION = 1 so historical received caches and checkpoints continue to resolve. The new implementation reads old namespaces at the same slots, keeps its remote SignalService immutable at the existing remote proxy and preserves current one-hop proof verification. No arbitrary import of cached truths is allowed.

Retain existing trusted checkpoints below the migration boundary and require new accepted L2 end heights to be strictly greater than that boundary. A valid old message proof can use its preserved checkpoint or a later accepted root containing the persistent sent signal. The later-root option needs access to the signal's proof witness; it does not excuse deleting old proof support. A historical root of uncertain validity cannot be blessed by copying it.

Vault proxy balances and ownership of deposited NFTs never move. Preserve canonical-to-bridged and bridged-to-canonical mappings, ERC20 denylist and migration state. Every existing wrapper retains supply, balances, allowances, ownership of IDs, operators, metadata and permit nonce domain. No wrapper address is changed as part of Etna. Creation of a wrapper for a genuinely new asset remains the existing lazy-deployment design and does not create a new Vault.

Assumed A-LEGACY. Historical checkpoints, received caches, custody and wrapper accounting are already sound at the pinned migration state. Upgrading a broken bridge cannot retroactively prove its past safe. The migration must audit this assumption through authenticated deployment history, state snapshots and replay; if it fails, preserving all state and claiming unchanged trust is unsound. Resolving a historic exploit would be a separate, explicitly approved recovery design.

Proven worked example under A-IMPL + A-LEGACY. Alice locks 100 canonical tokens on L1 before cutover; message m is NEW on L2. The same L1 Vault still holds those 100 tokens, the L1 sent-signal slot remains set, the L2 Bridge retains NEW and the canonical token key maps to the same wrapper. After cutover a relayer proves m against a retained valid root, the same L2 Vault mints 100 units, and the same Bridge marks DONE. Replaying m fails because DONE survived. Resetting either the status map or canonical mapping would break this argument even though all proxy addresses stayed fixed.

Assumed — staged cutover state machine

There is no atomic transaction spanning Ethereum and Taiko. The launch uses an audited finite migration state machine. The DAO authorizes and installs upgrades before activation; thereafter a public actor completes already committed work and calls objective activation. If the DAO never acts after installation, no ordinary Etna transition depends on it. Governance inactivity before required installation means Etna has not launched, not that a central sequencer can operate it.

The migration manifest commits chain IDs, all retained proxy addresses, exact old/new code hashes, implementation immutables, DAO identity, treasury recipient, resolver bindings, trusted root boundary, initializer versions, permitted drain verifier and expected L2 upgrade-state commitment. It is fixed by the initial upgrade authorization; no runtime setter, operator-selected head or per-token exemption may amend it.

The DRAINING path is finite because the legacy proposal tail and forced tail are frozen before processing. Each forced drain proposal contains exactly the next stored legacy source plus one deterministic default regular source required for compatibility, hence exactly two derived blocks. It cannot introduce attacker-selected discretionary transactions or extend the queue. Legacy enqueues after the cutoff fail and clients direct new requests to Etna's queue. There is no cancellation timer that erases pending requests, committed data, bonds or user escrow.

Proven source constraint. The existing forced queue stores a fee in gwei and a blob slice, not the new protocol's one raw transaction of at most 2048 bytes (IForcedInclusionStore.sol:9–16; LibForcedInclusion.sol:42–71). Blindly importing those entries into the new FIFO changes their semantics and may exceed its bounds. Draining them under the legacy derivation is therefore mandatory for this migration design. Already-paid historical fees and existing liveness bonds retain their accounting; fees for the unproposed forced suffix become proof-completion credits as specified below. No unit is silently interpreted as token-wei.

Install a migration-compatible SignalService implementation at the existing L1 proxy. Its code pins both the legacy Inbox and new Inbox addresses plus the manifest. During DRAINING it admits checkpoint writes only from the legacy Inbox; after the new Inbox's irreversible ACTIVE flag it admits only the new Inbox. This phase predicate is public deterministic state, not an address-owner allowlist. The new Inbox can set ACTIVE only after its drain certificate checks the exact legacy terminal checkpoint and pending counters. Switching authority and saving the first Etna checkpoint are atomic when applicable; no separate transaction can choose an arbitrary root between them.

Before activation the new Inbox's head is uninitialized: getHead and submitSegment revert rather than exposing an all-zero usable parent. Activation constructs the unique bootstrap head H0 specified below from the verified legacy certificate, without caller-selected fields or a snapshot of the queue at the activation transaction. Its empty first force interval deliberately leaves room for the bounded activation anchor in calldata mode. The first accepted segment establishes the ordinary authenticated queue snapshot for successors. Checkpoint writes at the legacy boundary are only identical idempotent writes; no legacy root is overwritten.

Existing old Inbox bonds do not become service collateral. Keep a permissionless exit adapter over the original bond ledger until every liability is discharged: existing participant balance and withdrawal request time are preserved; matured withdrawals remain callable by their owner under the original objective conditions; finalized old liveness deductions apply exactly once. Do not sweep residual balances to the DAO or let a new service registration claim the same token twice. All new Etna service deposits use the new registry's separate uint256 TAIKO ledger.

Atomicity is local to each chain. Required L2 upgrades and wrapper changes may span multiple ordinary legacy blocks, but all must be included in the finalized migration-root certificate before ACTIVE. Required L1 shared upgrades and drain freezing must either fit one audited upgrade bundle or be installed behind a committed inactive phase gate whose intermediate states preserve existing custody. No launch assertion relies on a simultaneous wall-clock activation or a particular L1 slot duration.

No parameter is denominated in an Ethereum consensus slot or epoch. The migration waits for authenticated state transitions and Ethereum finality, not a fixed number of present-day 12-second intervals. Open — preflight and rehearsal required before implementation readiness

The research session performs no deployment, key access, production test or production modification. The following is a future validation plan and acceptance record, not a claim that tests passed. Public read-only chain evidence may populate the manifest; private resources or secret keys are unnecessary.

  1. Pin finalized L1 and canonical L2 blocks. Record every proxy, implementation code hash, upgrade mechanism, owner/pending owner, initialized version, pause flag, resolver entry and immutable dependency from public state. Reconcile against deployment artifacts and source/compiler hashes. List every protocol wrapper and every live or historical migration pair; logs alone need reconciliation against state.
  2. Produce a complete selector/call-graph matrix for direct, inherited, fallback, router, receive, initializer and UUPS paths. Demonstrate that only upgrade entrypoints authorize DAO operations. Verify that an old pauser, pending owner, quota owner, whitelist member and wrapper owner cannot operate an Etna path.
  3. Compare compiled old/new storage layout byte offsets and hashed domains for every retained proxy family and every live custom variant. Include token permit domains/nonces and storage packing. Reject unspecified custom proxies rather than applying an approximate layout.
  4. Replay archived messages across the upgrade: NEW→DONE, NEW→RETRIABLE→DONE, failure/recall where already enabled, cached empty proof, old full Merkle proof and proof against a later root. Try duplicate processing, root overwrite and canonical-token duplicate-wrapper creation. Verify unchanged custody and status accounting.
  5. Rehearse the finite drain against a local copy of the pinned state. Race final legacy proofs, forced-only drains and activation; attempt late enqueues, stale proof replay, double old-bond withdrawal, duplicate forced fee collection, changed manifest and activation before L2 upgrades are proved. Every invalid transition must revert atomically.
  6. Test all participants offline except one newly funded unregistered prover. That prover must finish finite old work with public data, activate, submit an Etna segment and serve queued requests without governance. Repeat with old data unavailable: activation must remain blocked and report the exact missing obligation.
  7. Test adversarial cross-layer timing and L1 reorgs: partial L2 installation, old checkpoint publication at the switch, duplicate activation, first Etna anchor on the wrong legacy parent, wrong origin binding, conflicting same-height checkpoint and reorg of the installation transaction. No mixed-root withdrawal may succeed.
  8. Measure worst-case proof, forced processing, first anchor and migration bundle gas under the target fork. If an L1 bundle exceeds applicable limits, specify and audit intermediate phase gates before launch. Verify both optional frames and ordinary transaction fallback produce identical checkpoint effects.

A manifest is complete only when every row has authenticated chain evidence and the old/new bytecode matches the audited source. In particular, the names in historical deployment documents do not establish current implementation authority. The absence of this record is a material readiness blocker, not a cosmetic address-filling task.

Proven limitation. Reusing SignalService does not solve withholding. Its checkpoint contains height/hash/root, not proof of timely gossip. An attacker may reveal a valid private branch with proof and canonical data without ever promising to gossip it. This page neither makes that slashable nor strengthens a preconfirmation into a bridge withdrawal right; the core withholding verdict still governs R6.

Assumed accepted tradeoffs. No operational emergency pause, quota manager or owner-directed wrapper swap remains. Proof/verifier bugs and malicious upgrades can therefore cause losses without a discretionary response switch. Adding an administrator would fail the stated R1. Ordinary users retain control of their own messages and tokens; this does not promise liveness for malicious recipient contracts or external tokens with their own transfer restrictions.

Open human decisions. Authenticate the actual deployment manifest; approve a concrete legacy drain/circuit plan; determine whether any non-DAO-owned or actively migrating wrapper prevents universal upgrade-only ownership; identify the existing fixed treasury recipient; approve the risk of removing emergency pausing/quotas. None is silently resolved by choosing a convenient address or abandoning old obligations.

Assumed — what this design does not build

  • New custody deployments: rejected because they violate R2 and require moving escrow and replay history.
  • An owner-managed list of checkpoint writers: rejected because runtime authorization would violate R1. The finite migration uses contract provenance and a one-way public phase predicate only.
  • Permanent old/new ForkRouter dispatch: rejected because old administrative selectors and shared-storage semantics expand the audit boundary. Historical proofs are supported by compatible current code, not by a generic legacy fallback.
  • Blind SignalService VERSION bump: rejected because it hides historical checkpoints and caches without resolving old message obligations.
  • Importing old blob-slice forced entries as new raw transactions: rejected because payload and inclusion semantics differ. Finish them under authenticated legacy rules.
  • DAO voiding unprovable pending work: rejected because it grants operational discretion and may erase censorship-resistance obligations. Missing data is a launch blocker.
  • Leaving token wrappers outside permissionlessness: rejected because owner mint/pause can defeat R1 and custody safety even when Inbox itself is open.
  • An upgrade to the non-upgradeable quota manager: impossible through UUPS; detach all dependency edges instead.
  • Production implementation or tests: excluded from this research task. Interface sketches and this rehearsal plan do not substitute for a future audited implementation and measured launch checks.
