## Confirmed finding B-02-01 — incompatible EIP-712 publication type names

**Severity:** Medium. **Class:** specification gap, not an alleged deployed exploit. **Requirements:** R3, R6.

**Evidence:**

- `design/staging.html:200` says the exact EIP-712 type name is `PublicationClaim`; line 209 supplies the literal `PublicationClaim(uint256 bucketId,uint256 position,uint256 revision,bytes32 baseHeadHash,uint256 issuedAt,bytes32 contextHash)` type hash (`#accountability`).
- `design/accountability.html:10` instead calls the exact type `EtnaPublication(uint256 bucketId,uint256 position,uint256 revision,bytes32 baseHeadHash,uint256 issuedAt,bytes32 contextHash)` (`#obligations`); its interface comment repeats `EtnaPublication` (`#state-machine`).
- `design/roles.html:85` also says `EtnaPublication`, while sending readers to staging for normative exact encoding. Staging sends reserved service-liability rules to accountability. The documents therefore do not supply a single consistent interoperation rule.

**Preconditions:** a publisher/client follows staging's explicit type hash; the evidence verifier follows accountability's explicit exact type. The same owner, bucket, position, domain and six field values are otherwise valid. No cryptographic break or unusual network failure is needed.

**Trace:**

1. An owner opens the ordinary 600-TAIKO bucket and signs the sealed covenant using staging's `PublicationClaim` type hash.
2. A client following that page verifies the signature and treats the reserved publication duty as accountable.
3. The owner does not stage the context by `issuedAt+240`.
4. A reporter supplies that authentic signed claim before evidence close. A verifier implementing `EtnaPublication` hashes a different typed structure and fails the advertised signing-key check.
5. The promised publication-default penalty cannot be collected through that verifier. Reversing which component follows which page causes the symmetric interoperation failure.

**Cost and gain:** ordinary bucket collateral and registration cost; the 10-TAIKO position is reserved but its publication-default slash can become unavailable, giving up to 10 TAIKO of avoided penalty per affected position and any unbounded external value from an incorrectly advertised covenant. No additional token mint, forged root or bypass of mandatory 360-second staging follows. An honest deployment can also simply reject all these otherwise intended claims, disabling this optional service.

**False positives / false negatives:** this is a deterministic evidence false negative between conforming-to-different-pages components. It does not let a third party forge another owner's signature. Clients and verifier choosing the same interpretation avoid the failure, but that is a choice the current exact specification has not consistently made.

**Minimal fix:** select one literal type name, update all three pages and interface comments, and publish one common domain/type/struct/digest/signature vector. Do not silently support both schemas under the same revision as an implementation convenience; if both are deliberately supported, specify their identities and mixed-schema equivocation behavior. A shared vector is a specification artifact; production code is unnecessary to resolve this finding.

## Detailed falsification traces

### Staging, private knowledge and active role holders

**First reveal at acceptance:** construct valid private Y extending accepted H, with full proof but no prior stage. Its atomic acceptance fails the receipt-age check. Publishing only a body hash fails calldata staging; publishing an unrelated blob fails the final exact KZG/body relation. This is an effective mechanical exclusion under A-DA/A-CRYPTO (`staging.html#registry`, `#acceptance`; `index.html#da`).

**Opaque or false descriptor:** a blob stage can contain unproved execution outputs, because the registry cannot execute a blob. Such a stage is not a canonical reservation. An impossible descriptor cannot pass final proof validation, and an entrant may ignore it. A valid accepted candidate must retroactively establish the exact descriptor/body relation. Paid inspection spam remains a resource risk, not evidence that public age can be forged. No assumption that honest peers process every candidate was used.

**Active holder selectively serves early fragments:** a holder can supply valid X to selected users, keep other peers unable to execute it, answer a fragment challenge just before its 600-second deadline, and satisfy a sealed publication covenant at the end of its 240-second allowance. It avoids a service-default slash if those are its only promises. Peers missing dependencies must stay UNKNOWN; already informed users retain only revocable soft state. This can confer a temporary computation/order-flow advantage, but a candidate still cannot be canonical until 360 seconds after actual complete staging. Detection of prior selective gossip can be zero; detection of the specified missed deadline is deterministic given an authentic report and the common encoding fixed in B-02-01.

**Same-owner pipeline contradiction:** owner P signs X rooted at base H and later authorizes contradictory Y whose immediate parent is a later accepted H1. The bounded conflict predicate does not match H to H1, even if economic ownership is identical. Using a separate owner address also avoids attribution. Those are real false negatives for the owner-consistency mechanism, explicitly present in `staging.html:180–181` and `accountability.html#canonical-conflict`. Cost: ordinary computation, staging and landing fees, plus refundable service collateral unless another promise is broken. Gain: replace the soft suffix, retain associated fees/MEV, or waste rivals' work. Neither case creates an unavailable canonical predecessor or avoids Y's own public-data age. Given the authorized revocable-soft scope, I do not rate the reorg itself a new High. Client language must not advertise this predicate as a universal owner promise never to reverse its provisional ancestry.

**Salt/reorg/expiry:** duplicating a stage cannot refresh its time; a new salt cannot erase first publication or missed covenants. Reorged receipts and their dependent acceptance disappear together. An expired stage necessarily has an origin that is at least as old; a new salt alone cannot revive it. Changing origin changes context and requires appropriate body/proof reconstruction and a new maturation interval (`staging.html:97–120`). These close the attempted cheap timestamp-reset paths.

### Proving pipeline, origin expiry and recovery

For a current unchanged head, the stated healthy schedule is internally feasible: form for 60 seconds, allow 120 for stage inclusion, wait 360 for maturity while proving, and allow 120 for final inclusion: 660 seconds plus origin/header acquisition. There is 240 seconds of nominal room before origin age 900, if the origin was selected consistently. Sequentially acquiring a fresh recent header with the assumed 120-second inclusion allowance still leaves room in this example. This is a conditional schedule, not measured capacity.

For pipelined descendants, `Head.segmentCommitment=contextHash` excludes stage salt, producer/payment and job assignment; a sealed parent's successor head is computable before landing. Each descendant can stage and prove in advance, then land after its predecessor. Consequently 360-second public age need not impose another 360 seconds per segment on a healthy speculative chain (`index.html:62–64`, `staging.html:57–60`). Execution-affecting fields remain fixed; changing them invalidates descendants. No circular dependency was found in this specified head construction.

If the selected branch loses, stage cost and proof computation are wasted and the suffix must be rebuilt. A transaction becoming stale is outside the assumption that a transaction *remaining valid* is included within 120 seconds. Nevertheless each such competing parent consumption is canonical progress. This protects chain progress, not each honest prover's profitability or each discretionary user transaction.

If all current holders disappear, a new funded prover retrieves canonical history under A-ARCHIVE, selects a fresh origin, builds a bounded child, stages it, proves, waits and submits. It needs no old publisher authorization: it can self-authorize a new full statement over the public execution context. Old jobs and unusable stages reserve no parent. If all capable provers everywhere disappear, halt until a prover returns is the correctly stated assumption failure, not an R1 counterexample.

### Observation B-02-O1 — optional jobs cannot fund every otherwise viable pipelined candidate

**Status:** informational design consequence; optional-service coverage limitation, not a confirmed canonical-liveness vulnerability. **References:** `roles.html:96`, `staging.html:194–196`, `arguments.html#l1`.

Job acceptance requires the task's parent already be canonical and `origin+900 >= deadline+120`, with `deadline >= acceptedAt+300`. Therefore acceptance requires `acceptedAt <= origin+480` even when data and a proof are otherwise ready.

Concrete schedule: parent P starts at t=0 and lands at t=660 under the published worst-allowance example. Its speculative child C uses origin t=60, seals at t=120, and stages by t=240; C is mature at t=600 and its origin remains valid through t=960. At t=660, C can validly land with a ready independent proof. But a job for C could not be accepted before P landed, and at t=660 its minimum deadline is t=960, requiring origin freshness through t=1080. `60+900 < 1080`, so acceptance fails. Waiting does not repair it.

No attacker is required; a delayed parent or competitor can make this situation more frequent. The practical cost is private/off-chain funding of speculative proofs or rebuilding under a fresh origin, with another public-age interval. The safety guard correctly prevents impossible jobs. The document should explicitly disclose this funding limitation instead of treating optional on-chain jobs as a general pipeline subsidy. If such subsidy is required, separately specify conditional-parent job acceptance/cancellation, or an already-completed-proof purchase, without reserving canonical rights. Removing the freshness guard alone is not a safe fix.

### Frozen FIFO and empty-proof grinding

Appending a force request while a proof is in flight cannot change that proof's mandatory prefix: it derives from its parent's immutable snapshot. Attempting to select an earlier arbitrary queue cut fails the boundary checks around the pinned origin. Origin reuse permits temporary delay, but at accepted time t+1020 an origin must be at least the victim enqueue time plus 120. A subsequent chain with that mature snapshot must remove up to four predecessors per successor until the victim is attempted. A stream of empty valid segments cannot preserve a fixed eligible victim forever while advancing.

The supplied bound `t+1020+(1+ceil((p+1)/4))*Δ` is conservative and conditional on accepted-successor spacing Δ. It is not an independent proof of Δ. Four requests of at most 2048 bytes and one million gas each fit the stated mandatory work envelope in principle; complete proof/anchor resource feasibility remains a launch benchmark. Reverting valid transactions execute; invalid transactions receive proved rejection. This is not a guarantee of application success or unchanged account nonce.

An attacker can buy a large predecessor backlog, but later enqueues cannot move ahead of the victim. The 1,000-entry empty-to-full example costs 10.5 ETH and sinks 5.25 ETH even if the attacker earns all processing rewards; interleaved service can reduce the fee, but simultaneously removes predecessors. This is a concrete grief cost. It does not prove censorship unprofitable when external gains exceed costs (`index.html#forced`, `roles.html#competition`, `arguments.html#l2`).

### Deadline false positives, cancellation and exits

Fresh-job maturity is included in its deadline. A timely different first child cancels a job without slashing its honest loser; a competing consumption after the deadline cannot erase default because the receipt is historical. A worker cannot block independent submissions while waiting. Changed stage ID does not silently substitute a different assigned job. Revision retirement has its own dated cancellation predicate.

A responder or stager that is honestly censored, underfunded, or delayed past the assumed bounds may be objectively in default. This is a false accusation of intent, but not false evidence of missing the specified service deadline. Deposits Q fund reimbursement after response, not the responding account's upfront ETH. Basefee growth can exceed the quote. These are visible funding/inclusion assumptions, not an unconditional honest-party protection claim.

One global revelation serves the same digest for multiple challenges with separate deadlines; an earlier missed deadline remains a default. Rotation and exit cannot erase recorded reserves, and evidence/response boundary comparisons preserve exact-deadline responses and strict-after settlement. All observers colluding or hiding signatures until evidence close can make service detection zero. None changes mandatory canonical proof/DA validation.

### One-second cadence and changing L1 intervals

The 900-block unsafe horizon covers the illustrative initial 660-second landing delay at one issuance per second. Speculative stages permit continuing production while older proofs mature. Resource-driven early sealing can reuse an origin rather than waiting for another L1 header. A failure/reorg sequence can exhaust the horizon and halt soft issuance; the design admits this and does not claim an unconditional availability SLA.

Actual admission-to-result latency includes scheduling, propagation, signature checks and execution. A one-second issuance interval alone is insufficient to measure that latency. A-EXEC/A-NET must be translated into a measured bound with sufficient admission/scheduling headroom. This is a benchmark/service-definition launch gate, not a demonstrated impossibility of the conditional target.

No future CL schedule was consumed. At 12/6/4/2-second blocks, the 256-block recent-header window is approximately 3072/1536/1024/512 seconds on regularly produced chains, each above the assumed 120-second pin-inclusion budget. This comparison is a scenario check, not normative slots-to-seconds arithmetic. Pins can persist after the lookup window. Missed pinning or indefinitely unavailable fresh headers is an environmental failure; no assumption that old unpinned hashes remain available was used.

### DAO inactivity and migration

After the authorized installation, finite proposal/force tails cannot grow. Historical proofs decrease outstanding work; deterministic forced drain commits one pending request and permits anyone to prove it. The committer gets neither an exclusive proof right nor a caller-selected recipient. Activation is permissionless once the authenticated terminal state, L2 upgrades and drained counters are proven. Existing addresses, old replay records and checkpoint provenance are explicitly preserved. SignalService authority changes by the one-way migration phase, not a later DAO confirmation (`migration.html#migration`, `#drain-adapter`).

Missing legacy DA, absent compatible legacy proof programs, incompatible wrapper ownership or incomplete installation can block activation. These are substantial preflight conditions, already explicitly called launch blockers; I do not manufacture compatibility evidence or treat a stopped pre-installation DAO as failure of a launched protocol's routine operation. The selected migration has no timeout that invents a root or deletes pending user work. Actual layout comparisons, old-message replay and drain rehearsal remain necessary validation of this design.

## Review boundary and recommended disposition

Resolve B-02-01 as a design correction before implementation. Record O1 as an optional-service funding limitation or specify a remedy if pipeline job funding is intended. Do not classify the absence of deployed benchmarks, live manifests or audited circuit binaries as invented exploitable code: those are separate, explicit launch gates. Conversely, the signature disagreement is present in the current normative documents and cannot be deferred merely as a benchmark.

This review supplies one independent round with no new Critical/High found, not proof that none exists and not a convergence verdict. The judge must combine independent findings, close Medium dispositions and adjudicate R6's actual bounded economic coverage without changing R7 or demanding irreversible soft confirmations.
