## J04-01 — Medium: activation does not define the complete initial Head

**Evidence:** `index.html:35–40,62,69` (`#state`, `#origin`) defines and consumes Head fields; `index.html:172–175` (`#forced`) derives required work from the parent's snapshot. `migration.html:235–244` (`#migration`) permits Etna requests before ACTIVE and initializes “the full head” with legacy terminal fields, revision, segment number zero, an empty consumed cursor and “the fixed first force snapshot.” `migration.html:248–268` lists the certificate/event, but no initial snapshot/origin/commitment assignments. Searches across all seven normative pages found no missing initialization formula elsewhere.

The required initial `nextForceCut`, `nextForceTime`, `originNumber`, `originHash` and `segmentCommitment` are not fixed. The ordinary successor rule `Head.segmentCommitment=contextHash` does not identify an Etna StageContext for the legacy migration boundary. The certificate's legacy terminal root/height/hash/time does not select these other values. “Fixed” is an invariant to achieve, not a definition of the value being fixed.

**Concrete trace and viability:**

1. A valid finite legacy drain completes, and the new Inbox already has queued Etna requests, as `migration.html:235` permits.
2. An activation implementation chooses an empty initial snapshot; another independently developed implementation chooses a snapshot through an authenticated activation-related origin. Both can preserve every stated legacy terminal field and describe their chosen snapshot as fixed.
3. They construct different initial Head hashes and potentially different first mandatory force intervals. Even with the same complete first body and sound proof programs, their first statement parent hashes and requiredForceHash inputs disagree.
4. Similar unstated choices remain for the initial origin and segment commitment. A funded independent prover cannot derive the unique intended first transition from the normative specification alone.

No attacker can exploit an implemented selector on the evidence available here: **this is a reproducible specification/interoperability gap, not demonstrated theft or a proof forgery**. An opportunistic enqueuer can exercise the branch where the missing snapshot choice matters, but it is not necessary to create the ambiguity. The omission may become a first-segment halt or incompatible verifier/client behavior when implemented. Medium is appropriate; the complete R7 relation still cannot pass with the omission accepted as a risk.

**Required documentation correction:** define every initial Head field from authenticated certificate/manifest/public state or an explicit immutable bootstrap constant; define its exact hash and any bootstrap exception to ordinary successor commitment/origin rules. State precisely when/how the initial queue snapshot is selected, whether requests queued while inactive are deferred, and why none can be skipped permanently. An explicit empty initial cut/time with a defined origin sentinel and domain-separated boundary commitment is one possible construction, not a rule presently in this snapshot. Any selected construction must show how the first real origin and successor snapshot restore the ordinary FIFO induction without DAO discretion.

Add a small deterministic initial-head/first-successor example, including requests arriving before and around activation. Production code or a benchmark is unnecessary to specify these choices. Review the resulting immutable change before closing this finding.

### Coupled first-calldata composition observation

B-OBS-01's arithmetic is sound **conditionally**. Canonical ABI calldata of 16,356 bytes can be below the 16,384-byte activation cap. Four executed 2,048-byte forced transactions appear both in the transaction list and in forced records. Including only those bytes and the four required 32-byte receipt hashes gives:

`16,356 + 2 × 4 × 2,048 + 4 × 32 = 32,868 > 32,768`.

That already exceeds the calldata body limit before a header, anchor transaction envelope or RLP metadata. Early sealing cannot remove a mandatory first-block prefix. The report has **not** exhibited a valid authenticated launch-state witness of that size fitting one million gas, and J04-01 has not fixed whether the first snapshot contains the four requests. Blob mode remains an explicit larger transport. Those missing preconditions prevent elevating this observation into a demonstrated chain-wide halt.

Correcting bootstrap must nevertheless make the intended first-body/fallback feasibility reviewable. An explicit empty initial cut can remove this particular first-block force load; alternatively specify a fitting complete activation profile or an explicit reviewed blob requirement for activation. Existing byte/gas preflight (`codec.html:124,214`; `migration.html:438`, `#preflight`) must measure the **combined** mandatory body, not only independent anchor and force bounds. Neither a synthetic upper-bound sum nor a future individual-component benchmark proves an actual fallback works.

## C-F1 — real paid-retrieval incentive, not the claimed High

The trace is viable on its stated service assumptions. At a 20-gwei opening basefee, Q is 0.176 ETH. A holder that can remain the selected responder, and whose publication cost is below Q, can profit by selling the on-chain reveal; it can wait until the deadline without losing its reserve. There is no universal positive-profit guarantee because another holder may respond first, no one is compelled to open a challenge, and publication/funding costs vary. There is also no rule making early selective refusal itself a slashable absolute deadline.

The High consequence is not established for these reasons:

- The actual DutyClaim promises **public recovery through a funded 600-second challenge**, not an absolute publication deadline from issuance or personal server uptime (`accountability.html:15–19`). A timely complete response performs that obligation. The payment is the challenger's explicit Q, not minted protocol reward or someone else's diverted credit. Late response cannot cure a missed included deadline; a separate missed sealed covenant remains punishable (`accountability.html:20,35`).
- A recipient without the complete bytes must display UNKNOWN and withhold soft confirmation; a recipient that already validated the block has the bytes and may re-gossip or earn the response fee itself (`codec.html:175–177`; `index.html:79–80`; `accountability.html:166`). The attack cannot simultaneously rely on a properly validated honest recipient and assume the signer is the only possible revealer.
- Every canonical producer, including the same active holder under a fresh address, must publish the complete exact candidate at least 360 seconds before acceptance. The holder cannot turn this optional service delay into a first-reveal canonical action or a reservation of the accepted head (`staging.html:90–120,228–231`). A replacement may construct a different child from accepted state.
- Winning a mature competing branch can roll back soft state even if the losing branch was public promptly. No soft-priority/finality promise is inferred. An additional mandatory early-fragment covenant would improve that service, but would not give it canonical priority over an already mature competitor.

**Disposition:** reject C-F1 as a new High or missing required absolute P2P-publication duty. Explicitly accept the bounded service limitation: delayed recovery and profitable paid revelation may occur within the advertised promise. Never advertise its bond as deterrence of every earlier gossip refusal. R6's universal first-reveal prevention and objective actual-duty penalties survive this trace; R6 still fails full economic closure for the separate reason below. This decision rests on the actual obligations and recovery paths, not solely on a disclaimer in the design.

## J04-02 — Medium: ordinary canonical-control deterrence remains unclosed

**Evidence:** `roles.html:51–55` (`#role-matrix`) makes service reserves voluntary; `roles.html:208,216–222` (`#parameters`, `#competition`) provides zero exclusive lease, proportional reserved-duty capital and queue/slash sink models, but says R6's strong economic-monopolization deterrence is not established. `codec.html:51,103` fixes staged coinbase and its 75% basefee share plus tips. `staging.html:57–60` excludes later L1 payment assignment from execution context while preserving header coinbase. `arguments.html:124,133–134,167` (`#requirements`, `#limits`, `#launch`) leaves this economic review open.

**C-F2's concrete sequence is viable as a concentration channel:** a funded actor repeatedly builds/stages/proves valid segments with its own coinbase and obtains favorable L1 ordering. It uses no service bucket or accepted job and need not enqueue a force request. It therefore bears none of the optional position/job capital or default losses and no force-spam sink merely for winning another ordinary segment. It pays normal proving, staging, republication, gas and any builder costs, while receiving canonical fees and ordering value. Copying its exact public stage preserves its execution coinbase; a competitor choosing a different coinbase needs a different context and qualifying stage. An entrant remains technically admissible, and the trace does not establish guaranteed victory over every funded entrant.

A bounded cost/gain description of this tactic is:

`net gain = won L2 fees + ordering value − proving − stage DA/gas − landing DA/gas − builder payments`.

This is **not** the design's `9 × slashed positions`, `900 × defaulted jobs`, or `0.5 × sum(force fees)` loss model. For the described actor, those three terms may all be zero. The design supplies no selected bounds, inequality, counter-incentive or mandatory charge relating repeat ordinary control to those gains. Stating that outside MEV is unbounded would not answer a request for a bounded model under named assumptions; conversely, no proof against unlimited MEV is required here.

Existing mechanisms do target real tactics:

- Zero exclusive lease and no globally finite ticket capacity eliminate **protocol-right squatting**; an incumbent cannot buy a contractual veto.
- Complete mandatory staging and its public lead remove **private first-reveal information advantage** at canonical acceptance, including for raw producers.
- Mandatory FIFO restricts **censorship of eligible forced transactions**; irreversible force fees price queue flooding. Voluntary reserves price **accepted service abandonment**.

Those are substantive defenses. They do not by themselves establish the requested economic deterrence for **repeated ordinary canonical-order capture**. The queue escape charges the enqueuing user/spammer and enforces bounded inclusion; it does not impose the stated spam cost on an ordinary winner. A uniform honest-participation operating cost is not, without a bounded argument, evidence that repeating the concentration tactic is deterred. Neither open entry nor the prior judge's acceptance of concentration risk closes that distinct hard-gate obligation.

**Severity/exploitability:** Medium specification/economic-coverage gap. Sustained capital/builder advantage is a real prerequisite; no exclusive admission bypass, invalid state, theft, unlimited profit, or automatic permanent monopoly is established. This reopens the hard-gate interpretation of prior J02-03, rather than counting the already described concentration risk as a newly discovered High.

**Required correction:** identify the intended monopoly tactics and add either (a) a concrete mandatory, permissionless economic mechanism targeting repeat ordinary control, with precise charges/rewards, identity-independent scope and nonblocking recovery; or (b) a bounded cost/gain argument showing how existing mandatory mechanisms deter that tactic under explicitly selected inclusion/fee/proving/value assumptions. Specify why alternatives such as rotation, caps, auctions and decay are selected or rejected for that tactic. Do not merely restate optional service reserves, demand an identity oracle, promise equal shares, or assign an unmeasured universal MEV ceiling. Later empirical calibration may remain launch work, but the mechanism/model and claimed bounded effect must exist in the design now. If no compatible construction is established, publish the unmet R6 clause and the smallest requested relaxation rather than declare all gates passing.
