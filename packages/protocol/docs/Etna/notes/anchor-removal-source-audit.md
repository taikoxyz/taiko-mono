# Anchor removal: source and EIP audit

Research checked on 2026-10-01 against `taiko-mono@7217121d516ce37e8c1684d168d6e5b525f8765c` and the current primary EIP text. This is a design audit, not a production patch, deployment inventory, gas benchmark or executed migration rehearsal. Repository references below identify the inspected source lines; design documents may change as this research is incorporated. No signing key or secret was inspected or reproduced.

David's [final direction in issue #22147](https://github.com/taikoxyz/taiko-mono/issues/22147#issuecomment-5756531478) is binding for this proposal: keep the EIP-4788 pre-execution call strictly standard. Automatic Anchor storage updates are not a requirement. His [preceding correction](https://github.com/taikoxyz/taiko-mono/issues/22147#issuecomment-5756503026) withdraws the unauthenticated state-root/extraData-number variant, confirms the fork-time forgery window and client parity prerequisite, accepts on-demand checkpoints, and narrows the compatibility claim to **no Taiko-specific pre-execution hook**. The original issue body still contains superseded claims; it must not be read without these comments.

`SignalService` is already the checkpoint store: `_authorizedSyncer` is described as Inbox on L1 and Anchor on L2 at [SignalService.sol](../../../contracts/shared/signal/SignalService.sol):35–40. `saveCheckpoint` at 174–184 authenticates that caller, rejects zero hash/root, stores a `CheckpointRecord{blockHash,stateRoot}`, and emits `CheckpointSaved`. **It does not enforce increasing numbers, idempotence or no-overwrite, and it is not pause-gated.** The advancing-number rule currently comes from Anchor. L1 checkpoint publication is a separate path: [Inbox.sol](../../../contracts/layer1/core/impl/Inbox.sol):364–370 publishes the finalized L2 end number/root/hash through the same interface.

The externally visible checkpoint is `Checkpoint{uint48 blockNumber, bytes32 blockHash, bytes32 stateRoot}` at [ICheckpointStore.sol](../../../contracts/shared/signal/ICheckpointStore.sol):12–20. The mapping value stores only the last two fields; the number is its key. The issue's pseudocode assigning a whole `Checkpoint` into `_checkpoints` does not match that implementation.

There is **no current latest-checkpoint pointer** in SignalService. `_getCheckpoint` already rejects absent entries by testing `record.blockHash != 0` at `SignalService.sol:206–217`. Proof verification checks the uint48 bound at 280–282, loads that checkpoint at 284, and compares its state root to the proof root at 285–287. Therefore the issue's alleged missing-entry acceptance through `rootHash == 0` is not present in this inspected version. A reveal path should preserve nonzero hash/root invariants; an additional explicit root check is defense in depth, not a fix for an observed missing-checkpoint bypass.

## 2. Exact standard EIP behavior

Primary sources, retrieved on the audit date:

- [EIP-4788 specification](https://eips.ethereum.org/EIPS/eip-4788#specification), especially [contract reads/writes](https://eips.ethereum.org/EIPS/eip-4788#beacon-roots-contract) and [block processing](https://eips.ethereum.org/EIPS/eip-4788#block-processing).
- [EIP-2935 specification](https://eips.ethereum.org/EIPS/eip-2935#specification), especially [block processing](https://eips.ethereum.org/EIPS/eip-2935#block-processing), [history contract](https://eips.ethereum.org/EIPS/eip-2935#block-hash-history-contract), and [gas costs](https://eips.ethereum.org/EIPS/eip-2935#gas-costs).
- [EIP-7702 behavior](https://eips.ethereum.org/EIPS/eip-7702#behavior) and [delegation context](https://eips.ethereum.org/EIPS/eip-7702#delegation-indicator).

### EIP-4788 records one bytes32 under the L2 timestamp

The canonical destination is `0x000F3df6D732807Ef1319fB7B8bB8522d0Beac02`. Before ordinary transactions, the execution client calls it from `0xfffffffffffffffffffffffffffffffffffffffe` with exactly the header's 32-byte `parent_beacon_block_root`, 30,000,000 call gas and zero value. The receiving contract distinguishes read from write by **caller**, not a Solidity selector. At `i = block.timestamp % 8191` it writes timestamp into slot `i` and the input root into slot `i + 8191`.

An ordinary reader must make a call/staticcall carrying the raw 32-byte big-endian timestamp, for example the bytes produced by `abi.encode(uint256(t))`. `abi.encodeWithSignature("get(uint256)", t)` is wrong: the canonical contract has no such ABI and rejects non-32-byte reads. Reads reject zero timestamps and reject requests whose stored timestamp does not exactly match the query. Return data is one bytes32. A successful low-level call alone is insufficient evidence: calls to an empty account can succeed with empty return data.

Under the proposal, the input is an **L1 execution block hash**. The storage and execution mechanics remain standard, but the field's meaning differs from Ethereum L1's parent beacon block root. Describe this as standard EIP execution with a Taiko header-validity assignment, not identical Ethereum consensus semantics. Contracts expecting an Ethereum beacon-root oracle must not misinterpret this L2 oracle as one.

The recorded hash authenticates an L1 header only because derivation and every proving implementation require exact equality to the authenticated selected origin hash. Merely checking nonzero roots in the L2 execution client is insufficient for bridge provenance. The full hash must cover the exact complete L1 header, not a reconstructed prefix.

### The ring is modulo timestamp, not a queue of 8191 blocks

For distinct increasing integer timestamps, an entry at `t` can first collide at `t+8191`, then at positive integer multiples of 8191. Thus it cannot be overwritten by a different timestamp with `0 < t'-t < 8191`. It may survive longer if those residues are not used. A timestamp leap to `t+8191` overwrites after **one successor block**. The guarantee concerns chain timestamps, not elapsed operator wall-clock time.

At an exact two-second cadence the first same-residue timestamp is `t+16382`, because 8191 is odd. That cadence-dependent 4.55-hour calculation is not a general retention guarantee. At an exact one-second cadence it is `t+8191`, roughly 2.28 hours. If equal timestamps are permitted, the next equal timestamp immediately overwrites the same entry, possibly with a different anchor hash; a reveal of the prior hash then fails. Etna can avoid this ambiguity by retaining its strictly increasing L2 timestamp rule. Do not derive the safety rule from an assumed average cadence or call overwriting “harmless” without specifying which historical reveal may disappear.

### Gas, transaction indices and receipts

Both EIPs define pre-transaction **system operations**: fixed 30,000,000 call gas, zero value, no EIP-1559 payment/burn, and no charge against the block gas limit. The canonical runtime still performs storage work included in the resulting state root and execution proof. No ordinary signed transaction is inserted into the transaction trie, no sender nonce is consumed by an ordinary transaction, and no transaction receipt/index is created for this operation. Ordinary transaction zero can be any valid user transaction, or there can be no transactions.

The EIPs explicitly permit silent no-code execution. This is a deployment precondition, not evidence that the oracle is populated: authenticate canonical runtime code and fork activation before relying on reveals. Do not invent a new Taiko revert rule, emitted log, synthetic receipt, mandatory reveal transaction, privileged gas allowance or extra state write around the upstream operation. A user reveal is an ordinary transaction: it pays ordinary fees, contributes gasUsed/receipt/transaction-root entries, and may revert without invalidating an otherwise valid block. The EIP-2935 system update does not warm the account/storage for later user transactions; its first ordinary access pays normal cold-access costs.

The standard EIP-4788 genesis case uses a zero root and no system operation. Do not transplant a blanket nonzero-root rule into genesis. For an upgrade, the first Etna block is a non-genesis child and must use its authenticated nonzero origin as specified by the new fork relation.

### EIP-2935 is independent bounded L2 history

At `0x0000F90827F1C53a10cb7A02335B175320002935`, the standard pre-transaction call stores `parent.hash` at `(block.number-1) % 8191`. Ordinary callers query a raw 32-byte block number; only the last 8191 predecessor numbers are served. There is no backfill at activation, and full availability warms up over 8191 blocks. At genesis there is no history write; block 1 writes genesis's hash. The `BLOCKHASH` opcode remains limited to its existing 256-block window and its semantics/costs are unchanged.

This replaces a useful recent-history capability, not Anchor's permanent mapping API. Existing historic mapping storage can remain readable under a compatibility getter, but no further entries appear unless a separate persistence mechanism is deliberately added. Such a mechanism must not be silently smuggled into the supposedly standard pre-execution call.

## 3. System caller and EIP-7702 spoofing

An ordinary signed transaction cannot choose an arbitrary `from` identity: sender recovery determines it. Nor does specifying the system address as the transaction **destination** make it the caller of the beacon-roots contract. Assuming ordinary address/signature security and no privileged code placed at the system address, an attacker cannot manufacture a call from the reserved `0xffff…fffe` address.

EIP-7702 does not grant an arbitrary authority field. It computes `authority = ecrecover(keccak(MAGIC || rlp([chain_id,address,nonce])), signature)` and checks that authority's nonce/code before installing delegation. The attacker can name the system address as the **delegation target**, but this merely executes that target's code in the attacker's own account context; it does not grant the target's identity. Installing code at the system authority would require its valid authorization. Calling/delegatecalling the oracle's code from another account does not write the canonical oracle's storage with a forged system caller; delegatecall uses the caller's storage context.

An RPC simulation may allow `eth_call` with a chosen `from` address. That simulation does not authorize a transaction or persist chain state. The security requirement is enforced execution, not trusting simulated RPC output as a checkpoint.

The legacy golden-touch account is different: its signing material is documented as public. A funded ordinary transaction or a valid EIP-7702 authorization for that account remains constructible while its privileged path exists. Blocking only outer transaction senders or only a local mempool is insufficient. Once all old write privileges/selectors and fee exemptions are retired, the account can be treated as an ordinary account; preserving an eternal Taiko-only authorization blacklist is unnecessary for standard EIP-4788 safety. Before that boundary, delegated calls and imported blocks must be covered by the migration audit.

## 4. Requirements for a safe permissionless header reveal

These are proposed implementation requirements, not claims that this endpoint exists today.

1. **Pin domain and activation.** Enable reveals only for the intended L2 implementation/mode and active header interpretation. L1 continues using Inbox-authenticated `saveCheckpoint` and rejects reveals explicitly. Do not rely on the incidental fact that L1 4788 stores SSZ roots. Authenticate destination/runtime deployment in the migration manifest; reject unusable timestamps and pre-activation domain ambiguity.
2. **Read the standard oracle exactly.** Staticcall the canonical address with one 32-byte timestamp; require success, exactly 32 return bytes and a nonzero recorded hash. The no-code success/empty-data case must fail here.
3. **Authenticate before interpreting.** Require `keccak256(headerRlp) == recordedHash` over all supplied bytes. Do not accept a caller-supplied number/root, a hash of a prefix, or an unrelated RPC `blockNumber`. A number carried only in extraData is not directly available/authenticated to the reveal contract.
4. **Parse a complete bounded canonical list.** Check byte/field count bounds before unbounded allocations; reject trailing bytes, nonminimal RLP lengths, nested lists in scalar positions, leading-zero integer encodings and overflow. Position 3 must be exactly 32 nonzero bytes. Position 8 must be a canonical nonnegative integer fitting uint48 **before** conversion: empty bytes represent zero; a nonempty integer begins with a nonzero byte and has at most six bytes. Restrict zero if the Etna origin domain excludes genesis. If number/timestamp/parent hash are also used for activation or origin rules, validate their full types too. Appended L1 fields remain hash-authenticated; a fork reordering the prefix or exceeding the configured bounds needs an explicit parser revision.
5. **Persist the actual record type.** Store `CheckpointRecord{blockHash,stateRoot}` under `[VERSION][number]`. If already present, require identical hash and root and succeed idempotently; reject a conflict. Out-of-order valid reveals are allowed. Emit `CheckpointSaved` on a fresh write under the chosen event policy; clients must not infer monotonic reveal order. No latest pointer is needed by the present store. If one is added, advance it by max and label it “latest revealed,” never “latest anchored.”
6. **Preserve proof provenance.** Legacy HopProofs still resolve exact persisted number/root. If reveal material is optionally embedded into proof bytes, authenticate it through the same path and bind its number/root to the hop before trie verification. Preserve empty cached proofs and an unambiguous legacy/versioned decoding split. The view verifier must authenticate in memory without claiming to have persisted a checkpoint. A corrupt or missing oracle value must not fall back to caller assertions.

The repository pins Optimism `v1.8.0` at [package.json](../../../package.json):59 and resolves it in [pnpm-lock.yaml](../../../../../pnpm-lock.yaml):302–304. [LibTrieProof.sol](../../../contracts/shared/libs/LibTrieProof.sol):4–5 imports its RLP reader/writer. The [pinned reader's public source](https://github.com/ethereum-optimism/optimism/blob/v1.8.0/packages/contracts-bedrock/src/libraries/rlp/RLPReader.sol) exposes `readList`, `readBytes`, `readRawBytes` and a maximum list length of 32; it is not an Ethereum-header schema or integer decoder. The issue's `readUint256` sketch must not be copied. Upstream source retrieval via `gh` was unavailable in this environment; the tag source was read through web extraction instead. Repository source independently establishes the dependency and current use.

`proveSignalReceived` returns **0** today even after caching the verified signal (`SignalService.sol:113–127`). [Bridge.sol](../../../contracts/shared/bridge/Bridge.sol):339–341 uses the returned cache-operation count, and 380–395 deducts a per-operation refund from gas-based reimbursement. Do not return the number of reveal SSTOREs as cache operations. A separate reveal is outside a later claim's gas measurement. Folding a reveal into a claim can be measured inside that claim but does not guarantee full reimbursement; fee caps and owner/relayer paths still apply. Avoid wrappers that inadvertently change `msg.sender` and Bridge owner/relayer behavior. No 40k or 100k reveal estimate in the discussion has been benchmarked by this audit.

## 6. Activation hazards the revised Etna design must close

**The first anchorless block is a real attack window.** At the first successor to the last anchored block, the old ring computed without the new parent still matches the digest stored by that last anchor (`Anchor.sol:175–179,207–222`). An attacker can invoke the still-authorized legacy endpoint with a fabricated advancing checkpoint. “It will naturally stop working,” local mempool filtering, or eventual cleanup is insufficient. Disable the legacy write authority and all old selectors before ordinary transactions of the first anchorless block execute, including imported/type-4/delegated routes. Preserve valid legacy draining before that boundary. A fixed timestamp gate works only when the cutover specification makes the same timestamp a safe, precommitted boundary for every implementation.

**Current Etna bootstrap relies on the transaction being removed.** Before this revision, [codec.html](../design/codec.html):14,107–108 requires one signed anchor at transaction zero; [migration.html](../design/migration.html):448–458 uses `beginEtna` to prove Inbox ACTIVE and flip a namespaced L2 phase word. Deleting those calls does not set that phase word. The replacement must authenticate the sealed legacy parent and first origin/activation under the proof relation, and make contract writer retirement effective independently of an optional reveal. A mandatory first reveal/initialization transaction would recreate an anchor dependency; a custom automatic phase write would violate the chosen standard-hook constraint. Header/proof rules and precommitted contract configuration must close this jointly.

**Deploying the canonical bytecode can change consensus immediately.** The issue's author confirms that at its inspected geth version the builder omitted the 4788 operation while import executed it; no-code state hid the mismatch. The issue also reports different behavior in its inspected reth revision. These are dated source findings, not an audit of every current production binary. Roll out and verify builder/importer/reexecution/guest parity before deploying 4788 code on an already-active chain. New-network genesis allocation has a different deployment path but still needs exact runtime hashes and activation parameters. Independently verify 2935 activation and warm-up. This note did not inspect remote chain state or claim either address currently contains code.

**Retained proof obligations are broader than nonzero header data.** The Etna segment's single origin remains fixed before execution/staging, every L2 header must bind that origin hash, HeaderStore still authenticates the exact complete L1 header, and every execution/proving implementation must apply ordinary EIP system writes in the same order. Preserve the complete state/receipts/transaction roots, forced transaction ordering, terminal head commitment and old-head relation after removing the transaction-zero offset and gas reserve. Fee sharing and zk-gas metering remain Taiko-specific features; anchor removal does not make the whole execution profile identical to Ethereum.

**Liveness is a separate, testable premise.** A newer root can authenticate a signal only if that signal still exists at the relevant remote service/slot, the prover can obtain the newer account/storage proofs and header, and a transaction can be included before any needed transient oracle entry is lost. Current `_sendSignal` writes the signal to its deterministic slot (`SignalService.sol:220–236`), but future upgrades or historical service-address changes require separate treatment. “A newer root proves everything an older root did” is too broad as a generic Ethereum-state claim. Ordinary optional builder reveals can improve checkpoint availability without becoming a block validity rule.

## 7. Audit of the selected persistent-pin and transition design

The subsequent [design decision](anchor-removal-decision.md) closes the transient-ring liveness gap with an **ordinary** `pinCurrentOrigin()` call. It reads the current timestamp's authenticated nonzero hash and saves `pinnedOrigins[hash] = true` in a dedicated storage namespace. `revealCheckpoint(0, headerRlp)` authenticates against that permanent pin; a positive timestamp retains the temporary-ring fast path. A later header reveal still checks the complete preimage, uint48 number, nonzero state root and conflicting checkpoint invariant. Pins authenticate hashes, not arbitrary numbers or roots, and cannot be used to pin caller-chosen words.

This addition preserves standard EIP-4788 because it is voluntary, paid ordinary execution, with no pre-execution call, transaction-index privilege or consensus inclusion obligation. A forced request containing only the `pinCurrentOrigin()` selector captures the origin **when processed**, not when queued, so FIFO delay cannot make a baked-in timestamp expire. The later reveal against the pinned hash has no ring deadline. Success still requires ordinary sender nonce/balance/fee validity, enough execution gas, usable block production, and availability of the selected L1 header/proofs. A force request that is merely attempted but reverts or is invalid does not establish a pin. Repeated pins are idempotent and cost at most one persistent mapping entry per distinct authenticated origin; callers pay the storage cost.

The selected migration reads canonical 4788 at `block.timestamp` to distinguish legacy zero-root execution from Etna nonzero-root execution. It is safe under the combined requirements: (a) authenticate the exact canonical runtime and deploy it only after execution parity, (b) use the raw bounded staticcall and demand exactly 32 return bytes, (c) fail closed on missing/malformed data, never interpret that as legacy zero, (d) prove root equals zero throughout the legacy profile, (e) prove root equals the exact authenticated nonzero origin throughout Etna, and (f) retain strictly increasing L2 timestamps. The standard pre-transaction write flips the observed condition before the first ordinary Etna call, so both Anchor's legacy selector and L2 SignalService's authorized writer must reject that first block. L1's Inbox writer remains a separate explicit mode. No new L2 phase word or activation transaction is required.

The L1 Inbox ACTIVE check, exact stored H0 parent and authenticated origin number at/after the activation block replace the former `beginEtna` activation proof. This relies on the full statement and client validation of the named L1 view; a bare nonzero header check is insufficient. Old genesis/legacy ring data cannot authorize Etna execution, and a stale getter cannot select the transition. The shared current-root reader uses a fixed 100,000-gas staticcall budget and exact returned-size check; canonical runtime comparison and all layout commitments belong in the migration certificate. The reader's gas limit is an implementation bound that requires a preflight measurement under the pinned fork, not a new gas subsidy.

The decision also reduces the common L1-header cap to 1,536 bytes and 32 scalar fields, so an authenticated origin's header reveal can fit the separately proved forced-transaction byte limit. That bound restricts which future L1 headers can be used without an upgrade; it does not establish a reveal-gas ceiling or imply arbitrary bridge proofs fit the forced queue.

## 8. Evidence and launch verification still required

- Cross-client and proving-program execution vectors for empty blocks, ordinary transaction zero, the first fork block, reorgs and both EIP writes; no synthetic receipts; exact gas/header roots; no-code versus canonical-code deployment.
- Reveal vectors for raw calldata width, empty return data, zero/missing/overwritten timestamp, `t+8191` collision, duplicate/out-of-order/conflicting checkpoints, wrong complete header hash, malformed/nonminimal RLP, uint48 overflow and appended L1 fields.
- Authenticated migration rehearsal with legacy signed/delegated calls at every possible position, all fork-router paths, old writer revocation, preserved checkpoint/cache state and preserved custody/withdrawal paths.
- Before/after generated storage layouts and ordinary reveal/claim gas measurements under the exact selected L2 fork. This audit changes no contracts and does not run Solidity tests.
