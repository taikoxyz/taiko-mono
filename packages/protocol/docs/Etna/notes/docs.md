# Phase 1 source notes: protocol documentation

Baseline: `961bbd8ff55a0f66f44ad04160eb51638d655b66` (main). This note reads the five requested documents and the root/protocol `CLAUDE.md`; code excerpts are spot checks to distinguish current reference behavior from historical text. No deployment configuration or production state was queried. `Proven-from-source` means the cited file states or implements the claim; it does not mean a deployment has that code, a circuit enforces it, or the cryptography is independently audited. Paths below are repository-relative; line references are at the baseline. URC and its lookahead paths are **removed in Etna**, per the research scope.

## 1. Guide for a new engineer

**Proven-from-source.** Treat `Derivation.md` as the relevant Shasta derivation narrative. It explicitly introduces “proposal” for the on-chain unit previously called a batch, and “finalization” for confirmation of its post-state (`packages/protocol/docs/Derivation.md:3-10`). Other requested documents preserve older designs: the old proof guide describes calldata before blobs and `TaikoL2.anchor`, the contestable-validity guide describes proof-tier escalation, and the multihop guide describes a signal-root relay scheme. None alone defines the current protocol.

The useful conceptual sequence is:

1. A proposer publishes transaction/block-manifest data to L1 blobs and submits a proposal. Forced-inclusion users can separately enqueue their own blob source; forced sources precede the proposer source (`packages/protocol/docs/Derivation.md:84-88`).
2. Nodes derive deterministic blocks from the landed proposal, blob sources, parent block, and L1 history. Invalid source metadata can produce a single anchor-only replacement block rather than reject the whole proposal (`packages/protocol/docs/Derivation.md:154-196`).
3. Every derived block contains the system anchor transaction that imports an L1 checkpoint into L2 (`packages/protocol/docs/Derivation.md:319-345`).
4. A proof of a contiguous proposal range advances the L1 finalized L2 head and exports the end checkpoint to L1 SignalService. Current code allows overlap with previously finalized proposals, but the proof must advance at least one unfinalized proposal (`packages/protocol/contracts/layer1/core/impl/Inbox.sol:292-318,321-398`).
5. The SignalService checkpoint permits another party to prove a remote message was sent; a bridge then consumes authenticated messages. Publishing a checkpoint is therefore an asset-security boundary, not merely a progress metric (checkpoint verification mechanism: `packages/protocol/contracts/shared/signal/SignalService.sol:174-183,284-295`; bridge privilege narrative: `packages/protocol/docs/actors_privileges_deployments.md:20-31`).

**Open.** Preconfirmation authorization, gossip validation, execution validation, and reorg policy cannot be established from these five documents: the current landing-derived rules depend on metadata not yet known before landing. The Go and Rust client reads must supply those properties. In particular, local execution validity does not by itself prove that a future landed proposal will derive the identical block.

## 2. Derivation rules from the Shasta document

### 2.1 Inputs and separation of metadata

**Proven-from-source.** Metadata has proposal, source, and block levels (`packages/protocol/docs/Derivation.md:12-18`). The proposal carries a sequential identifier, proposer, landing timestamp, parent proposal hash, origin L1 block number/hash, and base-fee sharing percentage. The origin is the parent of the L1 landing block. `endOfSubmissionWindowTimestamp` is described as the last proposer slot timestamp and zero for whitelisted preconfirmations (`packages/protocol/docs/Derivation.md:24-33`). The slot wording is historical context, not a permitted Etna mechanism.

Nodes subscribe to `IInbox.Proposed`; the event plus the L1 event block and its parent reconstruct metadata (`packages/protocol/docs/Derivation.md:59-88`). A proposal manifest is a conceptual aggregation of source manifests, not itself the object stored in blobs. Each source is a block array, each block describing timestamp, coinbase, anchor block number, gas limit, and transactions (`packages/protocol/docs/Derivation.md:90-120`).

### 2.2 Blob/source validation

**Proven-from-source.** Each source is processed independently and in order; forced inclusions come first. The documented steps are: require a nonempty blob-hash array; require offset at most `131072 - 64`; read 32-byte version `0x1` and 32-byte payload size; ZLIB-decompress the payload; RLP-decode it; enforce at most 192 blocks before Unzen or 768 from Unzen, selected by landed L1 block timestamp; require exactly one block for a forced-inclusion source (`packages/protocol/docs/Derivation.md:148-166`). A failed step substitutes only that source with the default source manifest (`packages/protocol/docs/Derivation.md:168-196`).

The default is one block with the computed timestamp lower bound, proposer as coinbase, inherited parent anchor and gas limit, and no user transactions. Its anchor transaction remains (`packages/protocol/docs/Derivation.md:170-185`). This isolation is explicitly intended to prevent invalid proposer data from erasing an independent forced source (`packages/protocol/docs/Derivation.md:196`).

**Open.** The source document does not specify a decompressed-byte cap, exact RLP canonicality/trailing-byte behavior, invalid-transaction filtering, or all blob-slice field-element rules. Those must come from current codec/client implementation, not the historical proof guide.

### 2.3 Forced inclusion

**Proven-from-source.** A user submits blob data and calls `Inbox.saveForcedInclusion(blobReference)`. A proposer requests `numForcedInclusions`, consumes FIFO up to 10, and must request at least the capped number already due. The proposer source follows those dequeued entries (`packages/protocol/docs/Derivation.md:84-88`). The forced source has one block; timestamp, coinbase, anchor, and gas limit supplied by the user are overwritten with protocol-derived values. Only the transaction list comes from the user (`packages/protocol/docs/Derivation.md:198-212`).

**Open.** This narrative does not alone prove a wall-clock inclusion guarantee: it assumes proposals continue, does not specify queue admission costs/age/cap details, and must be combined with current L1 forced-inclusion and proposer-checker logic. Inclusion of a transaction list also does not guarantee successful execution of an invalid or reverting transaction.

### 2.4 Timestamps, anchors, gas, and headers

| Rule | Proven-from-source details and exact reference |
|---|---|
| Timestamp | For each successive parent, lower bound `max(parent.timestamp + 1, proposal.timestamp - TIMESTAMP_MAX_OFFSET, SHASTA_FORK_TIME)`; upper bound `proposal.timestamp`; out-of-bounds replaces the entire source (`packages/protocol/docs/Derivation.md:218-224`). |
| Anchor number | Reject decreasing anchors, an anchor after origin, or excessive lag; proposer source must advance an anchor, while forced sources inherit the parent (`packages/protocol/docs/Derivation.md:226-236`). Explicit stagnant-source code spot check: `packages/taiko-client-rs/crates/driver/src/derivation/pipeline/shasta/validation.rs:145-185`. |
| Anchor authenticity | Driver must obtain the actual L1 hash and state root for the anchor number (`packages/protocol/docs/Derivation.md:238-240`). |
| Coinbase | Forced source uses proposal proposer; regular source uses its supplied block coinbase (`packages/protocol/docs/Derivation.md:242-247`). |
| Gas | Per-block change bounded by 200 parts per million (±0.02%); minimum/maximum 10,000,000/45,000,000; out-of-range source replaced; then add 1,000,000 anchor gas (`packages/protocol/docs/Derivation.md:249-263,372-374`). |
| Miscellaneous fields | Number and index advance; difficulty is `keccak(abi.encode(parent.difficulty, number))`; numBlocks is assigned only after validations that may replace the source (`packages/protocol/docs/Derivation.md:265-284`). |
| Header | First extraData byte is basefeeSharingPctg; bytes 1..6 encode proposalId; parentHash is the previous L2 block; mixHash reflects prevRandao; state/transaction/receipt roots follow execution (`packages/protocol/docs/Derivation.md:294-317`). |
| Base fee | EIP-4396; genesis exception at first Shasta block; default initial 0.025 gwei, mainnet lower clamp 0.01 gwei, other-chain lower clamp 0.005 gwei, upper clamp 1 gwei (`packages/protocol/docs/Derivation.md:351-378`). |

The document's constants include 2-second target block time, Hoodi/mainnet anchor-offset limits 128/512 L1 blocks, and timestamp windows 1536/6144 seconds illustrated as `12 * block offset`. It says Shasta fork time is “not scheduled” (`packages/protocol/docs/Derivation.md:362-380`). **Open deployment claim:** neither that schedule nor those values should be assumed to be a live deployment fact.

### 2.5 Anchor behavior and proof settlement

**Proven-from-source.** The document describes `Anchor.anchorV4` with checkpoint `(uint48 anchorBlockNumber, bytes32 anchorBlockHash, bytes32 anchorStateRoot)`, a golden-touch caller, exactly 1,000,000 transaction gas checked by node software, and persistent checkpoint updates only for fresher L1 blocks (`packages/protocol/docs/Derivation.md:319-345`). Current ABI takes `ICheckpointStore.Checkpoint calldata`, and the anchor delegates newer checkpoints through `checkpointStore.saveCheckpoint` (`packages/protocol/contracts/layer2/core/Anchor.sol:121-138,171-185`; checkpoint shape: `packages/protocol/contracts/shared/signal/ICheckpointStore.sol:12-20`).

**Proven-from-source with limitation.** The document says proposing merely checks sufficient L1 bond and no pending withdrawal, without reserving/debiting a bond per proposal; balance is changed by slashing (`packages/protocol/docs/Derivation.md:141-144`). It describes at most one late-proof liveness-bond settlement, with 50% of the debit credited to actual prover and the remainder burned (`packages/protocol/docs/Derivation.md:347-349`). Current inbox explicitly skips bond transfers if prover whitelist is enabled (`packages/protocol/contracts/layer1/core/impl/Inbox.sol:336-358`), so the prose is not unconditional.

## 3. Historical proof tiers versus current reference

**Proven-from-source: historical model.** `contestable_validity_rollup.md` identifies a transition by parent hash and allows its block hash/signal root to change as stronger proofs arrive. It distinguishes liveness bond (assigned prover commitment), validity bond (actual prover commitment), and contest bond (challenger commitment) (`packages/protocol/docs/contestable_validity_rollup.md:3-13`). The first transition is reserved to an assigned prover until its tier window expires, then opens while excluding that assigned prover; other transitions race without that window (`packages/protocol/docs/contestable_validity_rollup.md:15-19`). Contested transitions can be reproven at a higher tier (`packages/protocol/docs/contestable_validity_rollup.md:21-31`). Reward examples burn some losing bond to limit collusion; the document then discusses an alternate “erase history” bond rule (`packages/protocol/docs/contestable_validity_rollup.md:43-89`). Fees are a proposer/prover social contract for the first proof of first transition (`packages/protocol/docs/contestable_validity_rollup.md:91-95`). These are useful design-history lessons, not evidence the current inbox has such a contest game.

**Proven-from-source: current spot check.** Current `Inbox.prove` verifies a contiguous commitment, links its parent to the current finalized block, checks last proposal hash, updates finalization/checkpoint state, and calls a verifier within the same atomic transaction. It accepts overlap but cannot prove an unproposed proposal or fail to advance (`packages/protocol/contracts/layer1/core/impl/Inbox.sol:292-318,321-398`). `ComposeVerifier` decodes an ordered array of distinct nonzero verifier IDs and requires both individual proof verification and a sufficient verifier combination (`packages/protocol/contracts/layer1/verifiers/compose/ComposeVerifier.sol:58-89`). `ZkRequiredVerifier` accepts exactly two subproofs with permitted SGX+ZK or Risc0+SP1 combinations (`packages/protocol/contracts/layer1/verifiers/compose/ZkRequiredVerifier.sol:31-50`); `SgxAndZkVerifier` requires SGX_RETH plus Risc0_RETH or SP1_RETH (`packages/protocol/contracts/layer1/verifiers/compose/SgxAndZkVerifier.sol:25-34`). Which verifier a deployment points to remains open without public deployment provenance.

**Proven-from-source: durable proving ideas, historical fields.** The old proving guide usefully explains the need to bind DA bytes, transaction validity, anchor correctness, block header, chain history, and cross-chain roots into the proof statement (`packages/protocol/docs/how_taiko_proves_blocks.md:9-35,39-62,109-137,179-193`). But it specifies the old `anchor(bytes32 l1Hash, bytes32 l1SignalRoot, uint64 l1Height, uint64 parentGasUsed)` interface and signal storage roots (`packages/protocol/docs/how_taiko_proves_blocks.md:37-71,179-185`). It also says extraData is empty and difficulty zero (`packages/protocol/docs/how_taiko_proves_blocks.md:161-175`), unlike current derivation header metadata. Do not copy old fields, base-fee accounting, golden-touch signature algorithm, or transaction-validity lists into a current implementation without code/circuit checks.

## 4. Roles, privilege claims, and provenance caveats

**Proven-from-source: document claims.** The actors document presents `AddressManager.setAddress` keyed by `(chainId, domain)` and `AddressResolver`-mediated role checking (`packages/protocol/docs/actors_privileges_deployments.md:5-11`). It grants Bridge token transfer/mint and failed-transfer release capabilities, vaults canonical/bridged token mint/burn capabilities, and an old Taiko domain token mint/burn capability (`packages/protocol/docs/actors_privileges_deployments.md:13-31`). It describes onlyOwner, an onlyAuthorized role granted by an owner, transparent proxies, and testnet EOA owners with eventual TimelockController ownership (`packages/protocol/docs/actors_privileges_deployments.md:33-60`). These are descriptive historical claims with no chain ID/address/code-hash snapshot, not a verified current permission map.

**Proven-from-source: current contradictory evidence.** Current `EssentialContract` inherits UUPS plus two-step ownership, and owner-only upgrade and pause authorization (`packages/protocol/contracts/shared/common/EssentialContract.sol:4-10,207-209`). Current SignalService sets syncer and remote SignalService as implementation immutables, checks the syncer directly on checkpoint writes, and admits an immutable pauser alongside owner (`packages/protocol/contracts/shared/signal/SignalService.sol:35-43,81-92,174-183,200-201`). Current Anchor has an owner-only asset withdrawal because it receives a share of L2 base fees (`packages/protocol/contracts/layer2/core/Anchor.sol:140-155`). Thus permissionless entry into a proposer role alone would not remove every operational privilege.

**Open.** A complete current deployment account must verify proxy address, implementation address/code hash, implementation immutable arguments, owner/pauser, resolver mappings, proof verifier selection, whitelist configuration, fork routing, and checkpoint migration/version against public chain state. These source reads deliberately do not claim the result. The requested design must state which old operational privileges are eliminated or objectively automated, separately from DAO upgrade ownership.

## 5. Multi-hop SignalService proof model and its limits

**Proven-from-source: historical explanation.** The multihop guide uses a slot keyed by `keccak256(abi.encodePacked("SIGNAL", chainId, app, signal))`, storing `1` (`packages/protocol/docs/multihop_bridging_deployment.md:11-25`). A world-state root requires both account and storage proofs; a known SignalService storage root permits only a storage proof (`packages/protocol/docs/multihop_bridging_deployment.md:27`). The described core rollup relays roots, letting a one-hop receiver prove the sender's slot and verify the relevant SignalService address (`packages/protocol/docs/multihop_bridging_deployment.md:31-52`). Two hops require two proofs and intermediate service-address authentication (`packages/protocol/docs/multihop_bridging_deployment.md:56-58`). Optional per-hop root caches can shorten later proof chains; final-hop state roots cannot be recached under that model (`packages/protocol/docs/multihop_bridging_deployment.md:62-92`).

**Proven-from-source: current reference is narrower.** Current `sendSignal` stores the signal itself, not `1` (`packages/protocol/contracts/shared/signal/SignalService.sol:107-109,220-236`). Current verification decodes `HopProof[]` but insists on exactly one proof, nonempty account and storage proofs, uint48 block ID, a saved checkpoint whose state root equals supplied rootHash, and verification against the immutable remote SignalService at a slot expected to contain `_signal` (`packages/protocol/contracts/shared/signal/SignalService.sol:271-295`). Current received-signal caching records a boolean by VERSION and slot; empty proof is accepted only for a cached received signal (`packages/protocol/contracts/shared/signal/SignalService.sol:124-126,265-268`). Checkpoints are separately keyed by VERSION and block number; a version bump invalidates old root/cache access (`packages/protocol/contracts/shared/signal/SignalService.sol:49-75`). The architecture still depends critically on authentic state roots; arbitrary multihop routing/root caching is not provided by this current implementation merely because the historical document exists.

**Assumed: proof meaning.** Given collision-resistant slot hashing, sound Merkle-Patricia proofs, correct checkpoint authorization, and the remote application address authenticated by the consuming application, proving a nonzero signal slot establishes the remote application's signal. Correct finalized checkpoint production, not economic bonding by itself, prevents forged bridge messages. These are named security assumptions, not proofs furnished by documentation.

## 6. Glossary

| Term | Meaning established by source |
|---|---|
| Proposal | L1-submitted construction data unit, formerly “batch” (`packages/protocol/docs/Derivation.md:9`). |
| Derivation source | One normal or forced blob-source manifest within a proposal (`packages/protocol/docs/Derivation.md:84-105`). |
| Manifest | Ordered metadata and transaction-list specification from which nodes derive blocks (`packages/protocol/docs/Derivation.md:90-120`). |
| Default manifest | Source-local anchor-only replacement after validation failure (`packages/protocol/docs/Derivation.md:168-185`). |
| Origin block | L1 block immediately before the proposal's landing block (`packages/protocol/docs/Derivation.md:31,64`). |
| Anchor | Privileged per-block transaction synchronizing an L1 checkpoint into L2 (`packages/protocol/docs/Derivation.md:319-345`). |
| Checkpoint | `uint48 blockNumber`, block hash, world-state root (`packages/protocol/contracts/shared/signal/ICheckpointStore.sol:12-20`). |
| Finalization | Confirmation of a proposal's post-state; distinct from Ethereum finality of the L1 transaction that records it (`packages/protocol/docs/Derivation.md:10`; current transaction path `packages/protocol/contracts/layer1/core/impl/Inbox.sol:364-398`). |
| Signal | Application-scoped message identifier whose deterministic slot is stored by SignalService (`packages/protocol/contracts/shared/signal/SignalService.sol:107-109,160-170,220-236`). |
| Signal root | Historical term for SignalService account's storage root, distinct from world-state root (`packages/protocol/docs/multihop_bridging_deployment.md:27`). |
| Proof tier | Historical strength/window/bond category in contestable proving, not a synonym for current verifier ID (`packages/protocol/docs/contestable_validity_rollup.md:21-39`; `packages/protocol/contracts/layer1/verifiers/compose/ComposeVerifier.sol:13-25`). |
| Liveness bond | Historical assigned-prover completion commitment; current derivation mentions optimistic L1 proposer balance and late-proof settlement (`packages/protocol/docs/contestable_validity_rollup.md:9`; `packages/protocol/docs/Derivation.md:141-144,347-349`). |
| Golden touch | System account authorized to send anchor transactions; node/circuit constraints still determine whether their content is valid (`packages/protocol/docs/Derivation.md:342-345`; historical proving details `packages/protocol/docs/how_taiko_proves_blocks.md:39-71`). |

## 8. Repository conventions relevant to this research

**Proven-from-source.** Root guidance says use `gh`, never commit secrets, and document nontrivial behavior (`CLAUDE.md:63-68,78-83,92-99`). Protocol guidance prescribes UUPS/resolver/storage gaps, no existing storage reordering, appending fields, and before/after layout verification for actual contract upgrades (`packages/protocol/CLAUDE.md:71-75,245-253`). Those are design constraints here; no Solidity implementation or layout mutation was made. Conventional scoped PR titles are explicitly described by `CONTRIBUTING.md:25-33`, with `docs` avoiding a release bump. The parent's `docs(protocol): ...` title is consistent with this documentation-only work.
