# G4: What exactly do the raiko guest programs prove? On-chain, prove() only checks lastProposalHash and the parent-hash link; every Transition.{proposer,timestamp,blockHash}, endBlockNumber/endStateRoot, firstProposalParentBlockHash, and all derivation rules (forced-inclusion one-block rule, timestamp/anchor/gas bounds, default-manifest substitution, anchor checkpoint content) are bound only through hashCommitment. No summary states the guest's statement, whether it re-derives from blobs via KZG/versioned hashes, or how it binds Proposal fields not emitted in Proposed (timestamp, originBlockNumber/Hash).

Sources read: taiko-mono at local HEAD `7c0e974` (shallow clone), and the external prover repository **`taikoxyz/raiko2`** (not `taikoxyz/raiko`; the tag `v0.8.0-rc1` does not exist on `raiko`) at tag `v0.8.0-rc1` = commit `8b2147a0e74ba6387938cf35544797fb1b61cc07`, which is exactly the commit Proposal0021 rotated the mainnet image IDs to (`packages/protocol/script/layer1/proposals/Proposal0021.md:5-8`, `:96-100`). raiko2 paths below are relative to that checkout; taiko-mono paths are relative to the repository root.

## Short answer

The RISC0/SP1 **proposal guest** (`raiko2_guest_common::prove_shasta_proposal`) proves, for one proposal, the statement:

> Given a `Proposal` struct P (all nine fields, including the ones not emitted in `Proposed`), a set of raw blobs, a parent-L2-header window, Merkle state witnesses, and an L1 header chain ending at P.originBlockHash: the KZG versioned hashes of the blobs equal `P.sources[*].blobSlice.blobHashes`; applying the Shasta derivation rules (the Rust client's own `taiko-client-protocol` crate, compiled into the guest) to those blobs under P's metadata yields a block-manifest list; executing each derived block on the witnessed parent state (dropping invalid txs) yields **exactly** the supplied canonical L2 blocks (header-for-header, tx-for-tx); every block's first tx is the canonical golden-touch `anchorV4` whose `(blockNumber, blockHash, stateRoot)` is a real header in the hash chain that ends at P.originBlockHash (or equals the parent's stored checkpoint in the forced/stalled cases); and the journal is `keccak(VERIFY_PROOF, chainId, verifier, keccak(proposalId, keccak(abi.encode(P)), P.parentProposalHash, firstParentBlockHash, actualProver, P.proposer, P.timestamp, hash(endCheckpoint), endBlockNumber, endBlockHash, endStateRoot))`.

The **aggregation guest** verifies N such receipts, checks the carries chain (ids +1, `proposal_hash -> parent_proposal_hash`, `end blockHash -> next parent_block_hash`, same chain id/verifier/actualProver), rebuilds `IInbox.Commitment` from them, and commits `keccak(blockImageId, keccak("VERIFY_PROOF", chainId, verifier, hashCommitment(commitment), address(0)))`, which is byte-identical to what `Risc0Verifier`/`SP1Verifier` recompute from the on-chain `Commitment`.

The guest does **not** prove the `Proposed` event was emitted or that P is on L1. It proves consistency with a **supplied** P; the sole authenticity anchor is the on-chain `lastProposalHash == getProposalHash(lastProposalId)` check, which works because `hashProposal = keccak256(abi.encode(Proposal))` covers `timestamp`, `originBlockNumber`, `originBlockHash` and every `blobHash`, and because each on-chain proposal embeds `parentProposalHash`, so the last hash transitively fixes every proposal in the batch. This is stated verbatim in raiko2 (`CONCEPTS.md:161-168`; `crates/guest-common/src/lib.rs:138-143`).

## 1. What L1 checks directly (recap, for the binding table)

- `prove` decodes `ProveInput{Commitment}` (`Inbox.sol:325`, `IInbox.sol:140-144`), bounds-checks ids (`Inbox.sol:788-812`), computes `proposalAge = block.timestamp - transitions[offset].timestamp` (`Inbox.sol:336`), requires `lastFinalizedBlockHash == (offset==0 ? firstProposalParentBlockHash : transitions[offset-1].blockHash)` (`Inbox.sol:343-346`), requires `commitment.lastProposalHash == getProposalHash(lastProposalId)` (`Inbox.sol:348-351`), settles the liveness bond against `transitions[offset].proposer` (`Inbox.sol:357-359`, `:729-744`), saves `{endBlockNumber, endStateRoot, transitions[last].blockHash}` as the L1 checkpoint (`Inbox.sol:364-370`), and finally calls `verifyProof(age or 0, LibHashOptimized.hashCommitment(commitment), _proof)` (`Inbox.sol:394-398`).
- `hashCommitment` is keccak over the fixed word layout `[0x20, firstProposalId, firstProposalParentBlockHash, lastProposalHash, actualProver, endBlockNumber, endStateRoot, 0xe0, len, (proposer, timestamp, blockHash)*]` (`LibHashOptimized.sol:37-80`); `hashProposal = keccak256(abi.encode(_proposal))` (`LibHashOptimized.sol:24-27`).
- `Proposal` = `{id, timestamp, endOfSubmissionWindowTimestamp, proposer, parentProposalHash, originBlockNumber, originBlockHash, basefeeSharingPctg, sources[]}` (`IInbox.sol:60-79`); at propose time `timestamp = block.timestamp`, `proposer = msg.sender`, `parentProposalHash = getProposalHash(id-1)`, `originBlockNumber = block.number-1`, `originBlockHash = blockhash(block.number-1)` (`Inbox.sol:610-621`); only `id, proposer, parentProposalHash, endOfSubmissionWindowTimestamp, basefeeSharingPctg, sources` are emitted (`Inbox.sol:747-756`, `IInbox.sol:169-176`). Every `blobHash` in `sources` is the EVM `blobhash()` of the proposing tx (`LibBlobs.sol:44-47`), also for forced inclusions (`LibForcedInclusion.sol:51-52`).
- Verifiers: `Risc0Verifier.verifyProof` ignores `_proposalAge` (`:50`), decodes `(seal, blockImageId, aggregationImageId)` (`:58-59`), requires both ids trusted (`:62-64`), computes `publicInput = hashPublicInputs(commitmentHash, address(this), address(0), taikoChainId)` (`:66-68`; `LibPublicInput.sol:18-36` = `keccak("VERIFY_PROOF", chainId, verifier, hash, signer)`), `r0Agg = keccak(blockImageId, publicInput)` (`:70-71`; `LibPublicInput.sol:43-52`), `journalDigest = sha256(r0Agg)` (`:74`) and staticcalls the RISC0 router with `(seal, aggregationImageId, journalDigest)` (`:77-80`). `SP1Verifier` is the same with `aggregationProgram = proof[0:32]`, `blockProvingProgram = proof[32:64]`, public values `abi.encodePacked(sp1Agg)` (`SP1Verifier.sol:58-83`). `SgxVerifier` uses the instance address as `_proofSigner` and checks an ECDSA signature over the same `hashPublicInputs` (`SgxVerifier.sol:467-479`). Mainnet composition is `ZkRequiredVerifier` (`compose/ZkRequiredVerifier.sol:37-50`), every leaf receives the same `_commitmentHash` (`compose/ComposeVerifier.sol:74-89`).
- Trusted ids on mainnet: RISC0 proposal `0xd6ab71c2…`, aggregation `0xdd9b8abf…`; SP1 proposal vkey `0x0025425c…`/`0x12a12e11…`, aggregation `0x0051ac1d…`/`0x28d60ecf…` (`LibRisc0Constants.sol:37-40`, `LibSP1Constants.sol:57-64`, `Proposal0021.md:57-66`). The raiko2 checkout carries the matching ELF/VK artifacts (`crates/guests/elf/risc0.provenance.json`, `sp1.provenance.json`) but only ELF sha256s, not image ids; I did not rebuild the guests, so the id-to-source link rests on Proposal0021's reproduction recipe (`Proposal0021.md:113-140`).

## 2. Guest entrypoints and journal

- RISC0 proposal guest: reads bincode `GuestInput`, calls `prove_shasta_proposal`, commits the 32-byte result (`guests/risc0/src/shasta_proposal.rs:17-30`). SP1 proposal guest is identical (`guests/sp1/src/shasta_proposal.rs:13-31`).
- RISC0 aggregation guest: for every receipt, `receipt.verify(image_id)` where `image_id = input.image_id` (the **proposal** image id, `guests/risc0/src/shasta_aggregation.rs:18-20`, `:37-48`), requires a 32-byte journal (`:49-54`), then `aggregate_shasta_zk_with_verifier(.., image_id_b256, ..)` and commits its output (`:58-68`). SP1 aggregation guest: `verify_sp1_proof(&input.image_id, sha256(block_input))` per sub-proof and `image_id_b256 = big-endian(vkey words)` = the on-chain `blockProvingProgram` (`guests/sp1/src/shasta_aggregation.rs:12-33`; `crates/primitives-shasta/src/instance.rs:53-57`).
- `GuestInput = {witnesses: Vec<StatelessInput>, taiko: TaikoManifest, proposal_ancestor_headers, proposal_state_nodes, proof_carry_data}` (`crates/primitives-shasta/src/input.rs:15-28`). `TaikoManifest = {proposal_id, l1_header, proposal_event{proposal: Proposal}, chain_spec, prover_data{actual_prover, checkpoint, last_anchor_block_number,..}, blob_proof_type, data_sources[{tx_data_from_calldata, tx_data_from_blob, blob_commitments, blob_proofs, is_forced_inclusion}], l1_ancestor_headers}` (`crates/protocol/src/manifest.rs:36-42`, `:46-53`, `:71-91`; `crates/protocol-shasta/src/lib.rs:27-32`). `ProofCarryData = {chain_id, verifier, transition_input{proposal_id, proposal_hash, parent_proposal_hash, parent_block_hash, actual_prover, transition{proposer,timestamp}, checkpoint{blockNumber,blockHash,stateRoot}}}` (`crates/protocol-shasta/src/shasta/mod.rs:179-200`).
- **Journal of the proposal guest** = `hash_shasta_subproof_input(carry) = keccak("VERIFY_PROOF", chain_id, verifier, keccak(proposal_id, proposal_hash, parent_proposal_hash, parent_block_hash, actual_prover, proposer, timestamp, hash_checkpoint(cp), cp.blockNumber, cp.blockHash, cp.stateRoot))` (`crates/protocol-shasta/src/libhash/shasta.rs:25-64`; `encode.rs:34-35`; the comment at `shasta.rs:37-39` states why every continuity field is hashed). Hashing is plain keccak over concatenated words (`libhash/values.rs:55-61`), i.e. the same as `EfficientHashLib.hash`.

## 3. What `prove_shasta_proposal` checks (`crates/guest-common/src/lib.rs:773-1062`)

Order of checks in `prove_shasta_proposal_with_block_verifier`:

1. **Blobs / KZG** (`lib.rs:787-790` -> `crates/primitives-shasta/src/blob.rs:30-130`). Per source: `data_sources.len() == proposal.sources.len()` (`blob.rs:31-40`); a source with empty `blobHashes` must carry no payload at all (`:58-69`); otherwise `#blobs == #commitments == #proofs == #blobHashes` (`:80-101`); for each blob `verify_blob_proof_of_equivalence(blob, commitment, proof)` (`:112`), and `commitment_to_version_hash(commitment) == blobHashes[idx]` (`:119-125`). The equivalence proof is a KZG point-evaluation at `z = sha256(sha256(blob) || versionedHash)` verified against the commitment (`crates/primitives/src/blob/util.rs:22-32`, `:210-249`); versioned hash = `sha256(commitment)` with byte 0 = `0x01` (`util.rs:173-176`). **So yes: the guest re-derives from raw blobs and binds them to the on-chain versioned hashes**; the blob hashes themselves are bound by `hashProposal`.
2. **Chain id / carry invariants** (`lib.rs:798-892`): chain id must be a built-in Taiko chain (`:805`; `crates/primitives/src/chain_spec.rs:46-56` lists 167000/167001/167011/167013), all witnesses same chain (`:813-820`); `carry.chain_id`, `carry.proposal_id == taiko.proposal_id == proposal.id` (`:822-852`); uint48 bounds (`:855-874`); **`carry.proposal_hash == hash_proposal(proposal)`** where `hash_proposal = keccak256(proposal.abi_encode())` (`:875-879`; `libhash/shasta.rs:109-111`); `carry.parent_proposal_hash == proposal.parentProposalHash` (`:880-883`); `carry.transition.proposer == proposal.proposer` (`:884-887`); `carry.transition.timestamp == proposal.timestamp` (`:888-891`).
3. **Runtime** (`lib.rs:894-899`): chain spec/fork schedule come from the compiled-in `builtin_taiko_chain_spec(chain_id)`, not from the input (`:81-88`; test `:1232-1245` pins mainnet Shasta at `1_775_135_700`); golden-touch fixed-k signer (`:897-898`; `packages/taiko-client-rs/crates/protocol/src/signer.rs:20`, `:82-83`, `:93-95`).
4. **Parent anchor number** (`lib.rs:902` -> `:391-419`): read `Anchor._blockState` slot 256 of the parent L2 state through the Merkle witness (`:44`, `:329-337`, `:399-407`; address derived from chain id, `chain_spec.rs:63-74`), and require the host hint `prover_data.last_anchor_block_number` to equal it if present (`:409-416`).
5. **Derivation** (`lib.rs:903-910` -> `:446-530`): last source must be non-forced (`:455-461`); `data_sources.len() == sources.len()` (`:463-468`); parent context = last full ancestor header `{timestamp, gas_limit, number}` + verified parent anchor (`:471-480`); `ProposalMetadata = {proposal.timestamp, proposal.originBlockNumber, proposal.proposer, chain_id}` (`:481-486`); per-source block cap 192/768 keyed on `proposal.timestamp` vs the built-in Unzen activation (`:430-439`, `:490-491`); each source goes through `prepare_source_manifest_with_max_blocks` (`:493-501`), which is the **Rust client's derivation** re-exported into the guest:
   - `crates/protocol-shasta/src/shasta/constants.rs:3`, `manifest.rs:6`, `blob_coder.rs:9` are `pub use taiko_client_protocol::shasta::…`; `Cargo.toml:81` pins `taiko-client-protocol = {git = taikoxyz/taiko-mono, package = "protocol", rev = 170f50bb…}` (that rev is not in the local shallow clone; the local crate at HEAD was used for the comparison below).
   - empty `blobHashes` -> default manifest, and any payload for such a source is a hard error (`derivation.rs:245-250`, `:321-335`); `offset > BYTES_PER_BLOB-64` -> default (`:251-252`, `:380-382`); blob decode via `BlobCoder::decode_blobs`, then `[version 0x1][size][zlib][RLP]` via `decompress_and_decode_with_max_blocks`, where undecodable / trailing-bytes / >max_blocks all degrade to default (`derivation.rs:337-378`; `packages/taiko-client-rs/crates/protocol/src/shasta/manifest.rs:114-154`, `:220`);
   - **forced-inclusion one-block rule**: `if source.isForcedInclusion && manifest.blocks.len() != 1 { default }` (`derivation.rs:261-263`);
   - forced or default sources get inherited metadata: `timestamp = lower bound`, `coinbase = proposer`, `anchor = parent anchor`, `gasLimit = parent (minus anchor gas)` (`:265-279`, `:173-194`);
   - validation: timestamps in `[max(parent+1, proposal.ts - TIMESTAMP_MAX_OFFSET, fork_ts), proposal.ts]` (`:384-424`); anchors non-decreasing, `<= originBlockNumber`, `>= origin - MAX_ANCHOR_OFFSET`, and a non-forced source must raise the anchor above the parent's (`:426-458`); gas limit within +/-200 ppm and `[10M, 45M]` (`:460-504`); any failure -> default manifest with inherited metadata (`:293-311`). Constants 192/768/128/512/12*offset/10M/45M/200 live in `packages/taiko-client-rs/crates/protocol/src/shasta/constants.rs:22-47`, `:83-94`, `:244-252`.
   - `witnesses.len()` must equal the derived block count (`lib.rs:519-524`).
6. **Per block** (`lib.rs:928-985`): (a) anchor tx: first tx, EIP-1559, `to == Anchor predeploy`, chain id, `alethia_reth_consensus::validate_anchor_transaction`, `maxFee == baseFee`, `priorityFee == 0`, empty access list, **signature == golden-touch fixed-k signature** (`:551-623`), canonical `anchorV4` selector and canonical ABI (`:103-136`); (b) header/manifest binding: `timestamp`, `coinbase`, `gasLimit == manifest.gasLimit + 1_000_000`, `extraData == basefeeSharingPctg || proposalId`, `mixHash == keccak(parent.difficulty, number)`, and the anchor calldata `blockNumber == manifest.anchorBlockNumber` (`:625-676`, `:532-549`); (c) chain continuity `parent_hash == previous validated hash`, `number == prev+1` (`:948-959`); (d) **execution**: the ZK path *rebuilds* the block from the canonical anchor tx plus the **derived** manifest txs (`:1029-1062`) via `reconstruct_block_from_transactions_with_witness_resources`, which executes on the witnessed pre-state (root = last ancestor header's `state_root`), skips invalid/unrecoverable txs, computes the post-state root and assembles the filtered block, then runs Taiko consensus/post-execution checks (`crates/stateless/src/validation.rs:235-299`; executor from `alethia_reth_block::derived_block`, `validation.rs:6-9`, not read); the generated block must equal the canonical block header-for-header and tx-for-tx (`lib.rs:710-741`, `:1057-1058`), and the returned hash is the generated header's hash (`:1059`). This closes the gap recorded in `docs/issues/2026-04-21-shasta-zk-path-does-not-rebuild-block-from-derived-txlist.md:1-13`, `:30-44`.
7. **Anchor checkpoint content / L1 linkage** (`lib.rs:989-994` -> `:144-313`): `taiko.l1_header.number == proposal.originBlockNumber` and `hash(l1_header) == proposal.originBlockHash` (`:163-171`); `proposal.timestamp > l1_header.timestamp` (`:178-183`, sanity bound only). Then either (i) stalled-anchor bypass when all anchors equal the parent anchor and `origin - anchor > MAX_ANCHOR_OFFSET` (`:157-162`; `crates/primitives-shasta/src/anchor.rs:39-56`): every checkpoint must equal the parent's `SignalService` checkpoint read through the Merkle witness from L2 storage (`:185-201`, `:343-389`; slots from `chain_spec.rs:25-34`); or (ii) source-aware progression: forced-source blocks must carry exactly the parent anchor and also match the parent's stored checkpoint (`:203-230`; `anchor.rs:115-186`), the normal source is window-checked (`anchor.rs:64-103`), and each remaining checkpoint `(number, blockHash, stateRoot)` must appear in `taiko.l1_ancestor_headers`, a contiguous parent-hash-linked header chain whose last element must have `number == originBlockNumber` and `hash == originBlockHash` (`:246-310`). Hence the anchored `stateRoot`/`blockHash` are those of a real ancestor of the L1 block whose hash the Inbox itself recorded via `blockhash()`.
8. **Outputs bound to the carry** (`lib.rs:995-1019`): `carry.parent_block_hash == first block's parent_hash`, `carry.checkpoint == (last number, last validated hash, last state_root)`; journal = `hash_shasta_subproof_input(carry)` (`:1023`).

## 5. Binding table: how each on-chain-unchecked field is fixed

| Field | Bound by |
| --- | --- |

| `Proposal.timestamp`, `originBlockNumber`, `originBlockHash`, `endOfSubmissionWindowTimestamp`, `basefeeSharingPctg`, every `blobHash` (not emitted / emitted) | All inside `abi.encode(Proposal)` (`IInbox.sol:60-79`, `LibHashOptimized.sol:24-27`), so a wrong value changes `proposal_hash`, breaks the `parent_proposal_hash` chain (`instance.rs:108-111`) and finally `lastProposalHash`. | Intermediate proposals (`firstProposalId .. last-1`) | `parentProposalHash = getProposalHash(id-1)` at propose (`Inbox.sol:616`) + guest `carry.parent_proposal_hash == P.parentProposalHash` (`lib.rs:880-883`) + aggregation chain (`instance.rs:108-111`). |
| `Transition.proposer`, `Transition.timestamp` | `== P.proposer`, `== P.timestamp` (`lib.rs:884-891`). So the liveness-bond payer and `proposalAge` are prover-*supplied* but proof-*bound* to the on-chain `msg.sender`/`block.timestamp` of propose; `proposalAge` itself is not in any hash and is ignored by all leaf verifiers (`Risc0Verifier.sol:50`, `SP1Verifier.sol:51`, `SgxVerifier.sol:460`). |
| `Transition.blockHash` (each) | `carry.checkpoint.blockHash == hash of last generated block` (`lib.rs:1012-1015`), with intra-proposal `parent_hash` continuity (`:948-953`) and inter-proposal continuity (`instance.rs:121-124`). |

## 6. What is NOT proven (trust boundary of finalization)

1. **No L1 inclusion / receipt proof of `Proposed`** (`lib.rs:138-143`; `CONCEPTS.md:161-168`). Soundness rests entirely on `hashProposal` collision resistance plus the ring-buffer equality; any contract change that finalizes without an exact ring-buffer match must add a second anchor in the guest (raiko2 says so explicitly).
2. **No proof that `originBlockHash` is canonical L1** – unnecessary because `blockhash()` computed it on-chain (`Inbox.sol:610-618`); but everything anchored (checkpoints, `stateRoot` values fed to `SignalService`) is only as good as that header chain.
3. **`actualProver` is a free choice of the prover** (above); the prover whitelist (`Inbox.sol:337`, `:771-779`) is the only identity check.
4. **Compiled-in assumptions**: chain-id list and fork schedule (`chain_spec.rs:46-56`; `lib.rs:421-439`), predeploy addresses (`chain_spec.rs:63-74`), `Anchor._blockState` at slot 256 (`lib.rs:44`, `:329-337`) and the `SignalService` checkpoint slot (`chain_spec.rs:25-34`), `ANCHOR_GAS_LIMIT = 1_000_000` (`lib.rs:62`, `:656-661`), the alethia-reth EVM/consensus rules (`Cargo.toml:88-96`; base-fee/EIP-4396 validation is delegated to `TaikoBeaconConsensus`, `validation.rs:432-441`, not read here). A mismatch with the deployed L2 contracts or the Go/Rust drivers is a liveness failure (nothing proves) or, if a rule is weaker in the guest, a soundness failure.
5. **Trusted image ids** are owner-rotated; every proof is only as sound as the allowlisted guest (`Risc0Verifier.sol:43-46`, `:62-64`), and ids cannot be tied to source without rebuilding (`Proposal0021.md:113-140`).
6. **The Go prover does not check the proof's public input**; it independently rebuilds `Commitment` from the `Proposed` event, the L1 block time and L2 headers (`builder.go:60-94`; timestamp from `proposal_iterator.go:120-125` via `metadata_shasta.go:107-110`) and the request carries only `{proposal_id, checkpoint, l1_inclusion_block_number, l2 block range, last_anchor_block_number, prover}` (`compose_proof_producer.go:24-40`, `:344-357`, `:363`, `:369`; `proof_submitter.go:143-198`). Any disagreement surfaces as an on-chain `verifyProof` revert, not as a guest failure.
