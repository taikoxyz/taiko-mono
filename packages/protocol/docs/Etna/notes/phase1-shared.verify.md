## Missed facts

- **Quota manager is optional and silently disabled when zero.** Both consumers skip the call entirely when the immutable is `address(0)`: Bridge.sol:652 `if (_amount != 0 && address(quotaManager) != address(0))` and ERC20Vault.sol:532 `if (_amount != 0 && address(quotaManager) != address(0))`. The Bridge constructor documents this (Bridge.sol:159 `Optional (may be zero)`). A deployment (e.g. L2) constructed with a zero quota manager has no outflow rate limit at all; the summary's quota discussion treats the limit as always present — Bridge.sol:159, 652; ERC20Vault.sol:532
- **`updateQuota` instantly resets consumption.** `_updateQuota` writes `Quota(0, _quota, _quota)` (QuotaManager.sol:76), i.e. `updatedAt = 0` and `available = quota`; and `availableQuota` returns the full quota when `updatedAt == 0` (QuotaManager.sol:110). So an owner call to `updateQuota` (even with the same value) refills the window immediately — QuotaManager.sol:74-77, 110
- **Resolver-miss revert is not translated to `B_SIGNAL_NOT_RECEIVED`.** In `_proveSignalReceived`/`_isSignalReceived` the `resolve(_chainId, LibNames.B_BRIDGE, false)` argument is evaluated outside the `try`, so for an unregistered `srcChainId` `processMessage` reverts with `RESOLVED_TO_ZERO_ADDRESS` — Bridge.sol:637-638, 688-689; ResolverBase.sol:19
- **A destOwner that rejects Ether makes a message permanently unprocessable.** `processMessage` ends with `_message.destOwner.sendEtherAndVerify(refundAmount, _SEND_ETHER_GAS_LIMIT)` (Bridge.sol:400), which `require`s success (LibAddress.sol:54). Any message whose `destOwner` cannot receive ETH within 135k gas reverts on every `processMessage` attempt (the comment at Bridge.sol:70-72 acknowledges this). Likewise the relayer payment at L395 reverts if `msg.sender` cannot receive — Bridge.sol:395, 400; LibAddress.sol:52-54
- **Whole fee is refunded to destOwner when destOwner self-processes.** Relayer payment happens only under `stats.processedByRelayer && _message.gasLimit != 0` (Bridge.sol:370); otherwise `refundAmount += _message.fee` (L368) goes to destOwner at L400 — Bridge.sol:367-370, 400
- **`saveCheckpoint` has no pause gate.** Neither `whenNotPaused` nor any other modifier besides the syncer check appears on `saveCheckpoint` (SignalService.sol:174-177). Pausing the L2 SignalService therefore cannot break the anchor transaction; only proving is halted — SignalService.sol:174-184
- **Hard-coded Permit2 address.** `ERC20Vault.PERMIT2 = 0x000000000022D473030F116dDEE9F6B43aC78BA3` is a compile-time constant used by `sendTokenWithPermit2` via `IPermit2(PERMIT2).permitTransferFrom(...)`; on a chain without Permit2 at that address only that entrypoint fails — ERC20Vault.sol:31-35, 567
- **`destOwner` defaults to `msg.sender` in all three vaults** when the op's `destOwner` is zero: ERC20Vault.sol:413, ERC721Vault.sol:69, ERC1155Vault.sol:71 `destOwner: _op.destOwner != address(0) ? _op.destOwner : msg.sender`
- **`SignalService.init` rejects a zero owner** (SignalService.sol:98 `require(_owner != address(0), ZERO_ADDRESS());`) whereas Bridge/vaults/DefaultResolver fall back to `msg.sender` via `__Essential_init` (EssentialContract.sol:195) — SignalService.sol:97-100
- **BridgedERC20 migration bypasses the vault gate.** In `mint`, `msg.sender == migratingAddress` is accepted without `_authorizedMintBurn` (BridgedERC20.sol:116-119), and `changeMigrationStatus` is `onlyFrom(erc20Vault)` (L99). The summary lists only the "normal mode" gate — BridgedERC20.sol:93-101, 112-126
- **`pause()` is itself `whenNotPaused` and `unpause()` is `whenPaused`**, and the authorisation hook runs *after* the state write (EssentialContract.sol:150-165) — harmless because a revert unwinds, but a reader auditing ordering should know — EssentialContract.sol:150-165
- **README.md:102 is stale relative to code.** It says `retryMessage` "can be called **only** by the user"; code lets anyone retry a non-last attempt when `gasLimit != 0` (Bridge.sol:424-426). The summary describes the code correctly but does not flag the README contradiction — README.md:102; Bridge.sol:424-426
- **`ForkRouter` constructor calls `_disableInitializers()`** (ForkRouter.sol:37), so the router impl can never be initialized directly; `IBridge.Context` is documented as "2 slots" (IBridge.sol:57) while the transient context uses 3 — ForkRouter.sol:37; IBridge.sol:57
- `LibL2Addrs.PERMISSIONLESS_EXECUTOR = 0x4EBeC8a624ac6f01Bb6C7F13947E6Af3727319CA` (LibL2Addrs.sol:8) is omitted from the address list — LibL2Addrs.sol:8
- Read-only helpers `isMessageFailed`, `isMessageReceived`, `isMessageSent` (Bridge.sol:472-511) are not listed under interfaces; `isMessageFailed` returns `false` (not revert) when `srcChainId != block.chainid` — Bridge.sol:472-511

## Overall

The summary is safe to rely on: every one of the 90 indexed claims matches the code at the cited lines, with only one imprecision (C37 — the resolver-miss path reverts with `RESOLVED_TO_ZERO_ADDRESS`, not `B_SIGNAL_NOT_RECEIVED`) and one one-line offset (C17, LibTrieProof constant at L21). Gates, timing constants, layouts, constructor wiring, mainnet addresses and the Inbox/Anchor call sites are all accurate. What a reader must re-check are the omissions rather than the statements: the quota manager is optional (zero address disables rate limiting entirely, Bridge.sol:652 / ERC20Vault.sol:532) and `updateQuota` resets the window (QuotaManager.sol:76, 110); `processMessage` hard-reverts when `destOwner` or the relayer cannot accept Ether within 135k gas (Bridge.sol:395, 400), which is a liveness hazard the summary only describes as a "gas cap"; `saveCheckpoint` is not pausable (SignalService.sol:174-177); and `ERC20Vault` bakes in the Permit2 address (ERC20Vault.sol:35). The open questions in section 11 (mainnet `recallEnabled`, whether the mainnet proxy sits behind a router, proxy owners, live quota values) genuinely cannot be settled from source and remain open.
