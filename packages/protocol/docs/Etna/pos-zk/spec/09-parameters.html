09 — Glossary, parameters and derivations

PARAM-01 — parameter-table discipline Every protocol parameter appears in the table below with: its identifier, unit, proposed value or formula, the derivation or source, and a tag from {derived, sourced, unmeasured, decided}. A parameter with no derivation and no source may not be given a value: it must be marked unmeasured with the experiment that would fix it. No proposed value may be described as a benchmark, and changing a value is a governance action recorded in the decision log. Every parameter has exactly one registered spelling: where a rule uses another spelling of a registered parameter, the registered spelling is canonical and the alias MUST NOT be used in clients, parameters or migration text — in particular W_EVIDENCE (not W_evidence), T_PROCESS (not T_process) and T_PROOF_MAX_PERMITTED (not T_proof_bound). This closes review round 3 finding R3-PRF-08: the registered table is the single naming authority, and the surviving alias spellings are resolved here. Failure modes addressed: magic numbers, values copied from another system's workload, and proposed parameters read as measured results. Proven

Glossary

TermDefinition
L2 PoS consensusThe permissionless validator protocol that orders and finalizes L2 blocks. It is the sequencing authority in this design (D4).
PoS-sequenced validity rollupThe honest name for this architecture: L2 PoS determines binding order; Ethereum provides data availability, proof verification and settlement (GEN-09).
EpochA logical interval during which a fixed validator-set version is authoritative. Epochs are numbered; the set for epoch e is fixed before e begins.
Voting powerThe effective stake of a validator in an epoch's set. Only bonded, active TAIKO counts (INV-03).
QuorumThe single normative predicate 3 * s > 2 * W (checked arithmetic), where s is the voting power that signed and W the epoch's total voting power; the L2 client, the zkVM guest and the L1 contract evaluate it identically (CONS-03, CS-09). A strict/non-strict mismatch would split chain acceptance from L1 acceptance.
PoLCProof of lock change: a set of more than two thirds of prevotes for a value at a given height and round, which is what allows a locked validator to unlock at a later round (CONS-04).
Commit certificateThe evidence that more than two thirds of an epoch's voting power precommitted a block at a (height, round, block id). Its publication plus a receiver's own data check is what yields STATUS-04.
Certificate (epoch-scoped)A certificate is judged under its own epoch's set and remains valid forever (CONS-08).
CheckpointThe L1 record of the last accepted batch: height, block hash, state root, epoch and validator-set root (L1-07).
BatchA contiguous range of L2 blocks accepted on L1 by one transaction carrying both its data and its proof.
Unsettled depthThe number of L2 blocks between the highest L1-accepted checkpoint and the block under consideration (HALT-03).
Data commitmentThe canonical commitment to a batch's data — keccak256 over the exact bytes, computed by the L1 contract on the calldata path, or by the guest on the blob path in addition to the KZG binding (DA-02, DA-03).
Proving latencyThe wall-clock time of the proof computation for one batch, measured from the moment the batch's blocks are final and the witness is available to the moment the proof exists. It excludes batch collection, witness generation, queueing, L1 inclusion and Ethereum finality.
Ethereum-finalIn a finalized Ethereum block, or at the configured finality depth. Only Ethereum-final L1 facts may enter L2 consensused state (SYS-02).
Weak subjectivityThe trusted starting point a fresh node needs. Here the L1 checkpoint is the natural source (MEM-11).
Safe haltA correct participant stopping rather than choosing between histories (HALT-01). It is a correct outcome, not a protocol failure, and under the selected Mode B it is no longer the only end state: a settlement stall past T_STALL is answered by the permissionless recovery of REC-02. (user decision D-7: Mode B selected — a halt is still correct, but the recovery path now exists for the settlement-stall case and only for that case.)
Censorship resistanceThe conditional statistical property of LIVE-04, not a guarantee: proposer selection is hash-based and weighted (CONS-06), so a coalition with less than one third of the voting power is selected for strictly fewer than one third of slots in expectation, and a transaction that reaches honest validators is included by the first honest proposer with room for it. The protocol provides no per-transaction inclusion guarantee and no L1 forced-inclusion path. Under A-CONS-2 (01 §4) that is a real but conditional resistance: a network-level adversary able to isolate a user from every honest proposer can exclude that user's transactions indefinitely, and because a withdrawal is initiated by an L2 transaction, such an adversary can also prevent the user from starting a withdrawal; the protocol offers no remedy, and a partial relaxation of R10 is disclosed. (user decision D-6: forced inclusion removed)

PARAM-04 — the per-epoch configuration registry and the configHash preimage The consensus-relevant configuration is fixed per epoch, not globally. The Inbox MUST keep an append-only per-epoch configuration registry: a mapping epoch → configHash whose entry is computed by the contract from its own storage and deployed code and never supplied by the caller, written for an epoch before that epoch starts and within the same two-epoch lookahead window and append-obligation discipline that MEM-09(1) fixes for the per-epoch set entry, and immutable once written: no function, upgrade initialiser, recovery path or governance call may edit, delete or rewrite the entry of an epoch already entered, and an upgrade takes effect for future epochs only. A batch whose epoch has no registry entry MUST be rejected before proof verification (ConfigNotCommitted(epoch); L1-05 row 23, L1-08). The registry value is the journal field configHash of PRF-02, whose preimage is the closed, domain-tagged enumeration owned by PRF-02(5): a single canonical abi.encode with the domain tag "TAIKO_ETNA_CONFIG_V1" and the chain id first (GEN-05), followed by the epoch schedule and the L1-side clock, the quorum form, the payload-framing version, the batch-length bound, the enabled DA modes, a parameter version, and the recovery parameters. The guest MUST recompute the hash from the configuration it actually applied and reject the proof unless the recomputation equals the registry value the L1 contract supplied; paramVersion is incremented whenever the enumeration changes, so two different enumerations can never share a domain. (S5 §5: the config registry, its append-only semantics and its per-epoch immutability, and the defined configHash preimage. This closes R4-PB-02, R4-LIV-04 and part of R4-MB-02.) Failure modes: a single mutable global hash lets a proof made under one configuration be accepted under another; a registry entry that can be edited after its epoch started lets governance change the rules under which a batch was already certified and executed — configuration capture by upgrade. Proven unmeasured (the mechanism is normative; every value the preimage commits to is registered elsewhere in this table and remains unmeasured until Phase B)
