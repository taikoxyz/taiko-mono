09 — Glossary, parameters and derivations

PARAM-01 — parameter-table discipline Every protocol parameter appears in the table below with: its identifier, unit, proposed value or formula, the derivation or source, and a tag from {derived, sourced, unmeasured, decided}. A parameter with no derivation and no source may not be given a value: it must be marked unmeasured with the experiment that would fix it. No proposed value may be described as a benchmark, and changing a value is a governance action recorded in the decision log. Every parameter has exactly one registered spelling: where a rule uses another spelling of a registered parameter, the registered spelling is canonical and the alias MUST NOT be used in clients, parameters or migration text — in particular W_EVIDENCE (not W_evidence), T_PROCESS (not T_process) and T_PROOF_MAX_PERMITTED (not T_proof_bound). Two names that look like aliases are not: WITHDRAWAL_DELAY (the L2→L1 release delay owned by MSG-03) and D_WITHDRAW (the validator unbonding delay owned by MEM-05 clause 4) are distinct parameters with distinct consumers, and no rule may substitute one for the other. PUBLICATION_PROOF_DEADLINE was a pending alias of the registered T_PROVE_DEADLINE; the name-alignment pass is complete, page 04's DA-09 now uses T_PROVE_DEADLINE, and the alias MUST NOT be used in clients, parameters or migration text. The forced-inclusion names left the tombstone with the mechanism (increment 04): FI_INCLUSION_DELAY, FI_RECORD_GAS_MAX, FI_MAX_TX_PER_RECORD, FI_ANCHOR_MAX_AGE, L2_BLOCK_GAS_LIMIT, FI_MAX_PER_BATCH, FI_ITEM_MAX_BYTES and the capacity relations are live again and registered in the rows below (joined there by the two names the same increment registers new, FI_MIN_DRAIN and the unmeasured fee floor FI_MIN_EXEC_FEE_CAP, whose Open schedule premise is F-FI-7, so the live forced-inclusion set counts nine names), because the narrow forced-inclusion rule they serve is live as FI-10–FI-14 (increment 04): the D-16 deferral of the obligation is superseded; only the withdrawn spelling FI_PREFIX_CAP stays tombstoned with a MUST-NOT-USE reason, and no rule, client, parameter or migration text may use it. (decision D-16; increment 04: the parameter set is live again — reconciled from the deferred-set wording, and the rows below carry its units and tags. This closes review round 1 finding R4-NR-02.) (INC4R5-RC-01: this registration sentence now names the second new forced-inclusion parameter, the unmeasured fee floor FI_MIN_EXEC_FEE_CAP, with the Open premise F-FI-7 its safety rests on, so the live forced-inclusion set is complete at nine names.) Censorship resistanceA conditional property with two parts. The consensus side also fixes the order of appearance: a block MUST NOT contain a transaction of a forced record once a higher-index transaction of that same record has already appeared in the executed payload of the range, so a record's transactions can appear only in the record's own order and no producer's inclusion order can defeat the proof's index-order condition (CONS-01(v), FI-11(4)); a block that violates the order requirement is invalid, exactly as one that had room to carry a demanded transaction and omitted it. Enforcement of the resolution walk is in the proof (PRF-04(vi)), never an admission gate: land rejects nothing because the register is non-empty, a validator signing a block that violates FI-11(4) — including the order requirement — is subject to no new offence, and the rejected proof is the whole enforcement of the walk. (R4R1-M-01: the falsifier list and the register row now carry the restated F-FI-3 of the per-transaction walk.) It bounds exclusion per unit of a censor's L1 spending, not exclusion per unit of time, and it is conditional on a non-censoring L1. (2) Unpublished data: the conditional statistical property of LIVE-04, not a guarantee — proposer selection is hash-based and weighted (CONS-06), so a coalition with less than one third of the voting power is selected for strictly fewer than one third of slots in expectation, and a transaction that reaches honest validators is included by the first honest proposer with room for it. PARAM-04 — the per-epoch configuration registry and the configHash preimage The consensus-relevant configuration is fixed per epoch, not globally. The Inbox MUST keep an append-only per-epoch configuration registry: a mapping epoch → configHash whose entry is computed by the contract from its own storage and deployed code and never supplied by the caller, written for an epoch before that epoch starts and within the same two-epoch lookahead window and append-obligation discipline that MEM-09(1) fixes for the per-epoch set entry, and immutable once written: no function, upgrade initialiser or governance call may edit, delete or rewrite the entry of an epoch already entered (no stall-resolution action exists in v1: D-16), and an upgrade takes effect for future epochs only. A batch whose epoch has no registry entry MUST be rejected before proof verification (ConfigNotCommitted(epoch); L1-05 row 23, L1-08). The registry value is the journal field configHash of PRF-02, whose preimage is the closed, domain-tagged enumeration owned by PRF-02(5): a single canonical abi.encode with a leading bytes32 domain tag and the chain id first (GEN-05), followed by the epoch schedule and the L1-side clock, the quorum form, the payload-framing version, the batch-length bound, the enabled DA modes, a parameter version, and the unsettled-depth cap D_MAX — the one field of version 1's tail that a live v1 rule still reads; the five recovery names withdrawn by D-15/D-16 are deliberately absent from it; L2_BLOCK_GAS_LIMIT is live again as the FI capacity relation's registered input, but it is not committed through any preimage — the relation reads it from the anchored L1 view the proof already fixes, and no enumeration changes (increment 04; 04-coordination.md §3). Three closed enumerations exist and the tag names which one is in force: version 1 (paramVersion = 1, tag "TAIKO_ETNA_CONFIG_V1") is that field list and remains valid only for an epoch already entered under it, and MUST NOT be used for a new epoch; version 2 (paramVersion = 2, tag "TAIKO_ETNA_CONFIG_V2") adds a uint64 L2_BLOCK_GAS_LIMIT encoded immediately after uint32 MAX_BATCH_BLOCKS — the name is live again as the capacity relation's input, read from the anchored L1 view and not from this preimage (increment 04) — and likewise remains valid only for an epoch already entered under it and MUST NOT be used for a new epoch; version 3 (paramVersion = 3, tag "TAIKO_ETNA_CONFIG_V3") is current for any new epoch and is the live-only field list of PRF-02(5). The guest MUST recompute the hash from the configuration it actually applied — the version-3 enumeration for a batch in a new epoch, and an epoch already entered's own enumeration otherwise — and reject the proof unless the recomputation equals the registry value the L1 contract supplied; paramVersion is incremented whenever the enumeration changes, so two different enumerations can never share a domain.
