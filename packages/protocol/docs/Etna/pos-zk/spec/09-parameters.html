09 — Glossary, parameters and derivations

PARAM-01 — parameter-table discipline Every protocol parameter appears in the table below with: its identifier, unit, proposed value or formula, the derivation or source, and a tag from {derived, sourced, unmeasured, decided}. A parameter with no derivation and no source may not be given a value: it must be marked unmeasured with the experiment that would fix it. No proposed value may be described as a benchmark, and changing a value is a governance action recorded in the decision log. Every parameter has exactly one registered spelling: where a rule uses another spelling of a registered parameter, the registered spelling is canonical and the alias MUST NOT be used in clients, parameters or migration text — in particular W_EVIDENCE (not W_evidence), T_PROCESS (not T_process) and T_PROOF_MAX_PERMITTED (not T_proof_bound). Two names that look like aliases are not: WITHDRAWAL_DELAY (the L2→L1 release delay owned by MSG-03) and D_WITHDRAW (the validator unbonding delay owned by MEM-05 clause 4) are distinct parameters with distinct consumers, and no rule may substitute one for the other. PUBLICATION_PROOF_DEADLINE was a pending alias of the registered T_PROVE_DEADLINE; the name-alignment pass is complete, page 04's DA-09 now uses T_PROVE_DEADLINE, and the alias MUST NOT be used in clients, parameters or migration text. The forced-inclusion names are registered with the same force: FI_INCLUSION_DELAY, FI_RECORD_GAS_MAX, FI_MAX_TX_PER_RECORD, FI_ANCHOR_MAX_AGE, L2_BLOCK_GAS_LIMIT and the capacity relation FI_MAX_PER_BATCH × FI_MAX_TX_PER_RECORD × FI_RECORD_GAS_MAX ≤ MAX_BATCH_BLOCKS × L2_BLOCK_GAS_LIMIT are the names the FI-10–FI-14 rules consume, together with the registered relations FI_RECORD_GAS_MAX ≤ L2_BLOCK_GAS_LIMIT, FI_ANCHOR_MAX_AGE ≥ L1_FINALITY_DEPTH and FI_INCLUSION_DELAY < T_PROVE_DEADLINE; FI_PREFIX_CAP is a withdrawn spelling of FI_MAX_PER_BATCH and MUST NOT appear in clients, parameters or migration text. The registered parameter carries DA-09's semantics: L1 blocks, from the record's own l1BlockNumber. Glossary

TermDefinition
L2 PoS consensusThe permissionless validator protocol that orders and finalizes L2 blocks. It is the sequencing authority in this design (D4).
PoS-sequenced validity rollupThe honest name for this architecture: L2 PoS determines binding order; Ethereum provides data availability, proof verification and settlement (GEN-09).
EpochA logical interval during which a fixed validator-set version is authoritative. Epochs are numbered; the set for epoch e is fixed before e begins.
Voting powerThe effective stake of a validator in an epoch's set. Only bonded, active TAIKO counts (INV-03); which of those entries a set version actually commits is decided by the L1-heartbeat eligibility of MEM-13, which removes no weight (decision D-14).
L1 heartbeat (eligibility attestation)A signature by an entry's registered ECDSA secp256k1 heartbeat key over the versioned DOMAIN_HEARTBEAT payload, naming exactly one tumbling heartbeat window hbWindow and a strictly increasing per-entry sequence hbSeq; anyone may carry it to L1, and on acceptance it is recorded as lastHeartbeatAt(v) = hbWindow · HEARTBEAT_WINDOW, lastHeartbeatWindow(v) and lastHeartbeatSeq(v); it is the only liveness evidence the set-commitment rule reads, it changes no stake, weight or standing, and it is not the Ed25519 consensus vote key (decision D-14; round-5 repair R5T-C-2: the payload is window- and sequence-bound; MEM-13).
QuorumThe single normative predicate 3 * s > 2 * W (checked arithmetic), where s is the voting power that signed and W the epoch's total voting power; the L2 client, the zkVM guest and the L1 contract evaluate it identically (CONS-03, CS-09). A strict/non-strict mismatch would split chain acceptance from L1 acceptance.
PoLCProof of lock change: a set of more than two thirds of prevotes for a value at a given height and round, which is what allows a locked validator to unlock at a later round (CONS-04).
Commit certificateThe evidence that more than two thirds of an epoch's voting power precommitted a block at a (height, round, block id). Its publication plus a receiver's own data check is what yields STATUS-04.
Certificate (epoch-scoped)A certificate is judged under its own epoch's set and remains valid forever (CONS-08).
CheckpointThe L1 record of the last accepted batch: height, block hash, state root, epoch and validator-set root (L1-07).
BatchA contiguous range of L2 blocks accepted on L1 by one transaction whose proof the Inbox verifies; its data is carried by that transaction or bound to a live publication record (DA-08). (D-11: data may be published before the proof; the checkpoint still advances only on a valid proof.)
Unsettled depthThe number of L2 blocks between the highest L1-accepted checkpoint and the block under consideration (HALT-03).
Data commitmentThe canonical commitment to a batch's data — keccak256 over the exact bytes, computed by the L1 contract on the calldata path, or by the guest on the blob path in addition to the KZG binding (DA-02, DA-03).
Proving latencyThe wall-clock time of the proof computation for one batch, measured from the moment the batch's blocks are final and the witness is available to the moment the proof exists. It excludes batch collection, witness generation, queueing, L1 inclusion and Ethereum finality.
Ethereum-finalIn a finalized Ethereum block, or at the configured finality depth. Only Ethereum-final L1 facts may enter L2 consensused state (SYS-02).
Weak subjectivityThe trusted starting point a fresh node needs. Here the L1 checkpoint is the natural source (MEM-11).
Safe haltA correct participant stopping rather than choosing between histories (HALT-01). It is a correct outcome, not a protocol failure, and under D-15 it is no longer the only end state for exactly one case: a settlement stall past T_STALL_GOV may be cleared by the timelocked, resume-only stall resolution of GOV-04, which depends on governance liveness (A-GOV-2, LIM-01). Every other halt remains terminal unless its own condition clears, and there is no permissionless recovery. (D-15: the Mode B permissionless recovery is withdrawn; a halt is still correct, and the replacement is a governance action with no protocol bound on when it is queued.)
Censorship resistanceA conditional property with two parts. (1) Published data: the narrow forced-inclusion obligation of FI-10–FI-14 — a due record must be resolved by the capped FIFO prefix of the due set at its due point (and in any case no later than its deadline), included in a proven batch or discharged as void on objective grounds; the obligation is an upper bound on exclusion, never a lower bound on inclusion (LIVE-04). (2) Unpublished data: the conditional statistical property of LIVE-04, not a guarantee — proposer selection is hash-based and weighted (CONS-06), so a coalition with less than one third of the voting power is selected for strictly fewer than one third of slots in expectation, and a transaction that reaches honest validators is included by the first honest proposer with room for it. There is no general inclusion list: no queue of arbitrary transactions, no escrow and no forced-inclusion fee, and no L1 entry point for unpublished data (FI-PLANNED-01). Under A-CONS-2 (01 §4) the statistical half is real but conditional: a network-level adversary able to isolate a user from every honest proposer — or to censor L1 inclusion itself (01 A-L1-1) — can prevent the data from ever being published, and because a withdrawal is initiated by an L2 transaction, such an adversary can also prevent the user from starting a withdrawal; the protocol offers no remedy against that, and a partial relaxation of R10 is disclosed. (user decision D-12: narrow forced inclusion over published data ships in v1 and supersedes D-6/D-10; the general inclusion list is what remains deferred. D-11: publication is the anchor the narrow rule reads.)
Publication recordThe L1 record that a batch's (or a transaction's) data was published to blobs or calldata before its proof. It advances no checkpoint and decides nothing until a proof references it; it is the one register the forced-data rules read, and its entries are bounded by T_PROVE_DEADLINE (D-11, D-12; 04).
Forced-inclusion breachThe offence of a proposal over a batch that leaves a record of the capped FIFO prefix of the due set unresolved past its due point — not past the record's proving deadline, which is DA-09's separate clock — bounded by FI_MAX_PER_BATCH. The obligation is an upper bound on exclusion, never a lower bound on inclusion; the offence is ECON-04 clause (6) and its economics are ECON-13 (D-12).
Aggregation proofThe one proof object the protocol accepts per purpose: an n-of-m proof whose inner proofs each prove the same journal and whose public input names the contributing registered backend families. L1 verifies it once, and the per-purpose count of distinct live families is enforced over that public input (D-13; L1-14, PRF-15).

PARAM-04 — the per-epoch configuration registry and the configHash preimage The consensus-relevant configuration is fixed per epoch, not globally. The Inbox MUST keep an append-only per-epoch configuration registry: a mapping epoch → configHash whose entry is computed by the contract from its own storage and deployed code and never supplied by the caller, written for an epoch before that epoch starts and within the same two-epoch lookahead window and append-obligation discipline that MEM-09(1) fixes for the per-epoch set entry, and immutable once written: no function, upgrade initialiser, stall-resolution action or governance call may edit, delete or rewrite the entry of an epoch already entered, and an upgrade takes effect for future epochs only. A batch whose epoch has no registry entry MUST be rejected before proof verification (ConfigNotCommitted(epoch); L1-05 row 23, L1-08). The registry value is the journal field configHash of PRF-02, whose preimage is the closed, domain-tagged enumeration owned by PRF-02(5): a single canonical abi.encode with a leading bytes32 domain tag and the chain id first (GEN-05), followed by the epoch schedule and the L1-side clock, the quorum form, the payload-framing version, the batch-length bound, the enabled DA modes, a parameter version, and the stall-resolution parameters of GOV-04. Two closed enumerations exist and the tag names which one is in force: version 1 (paramVersion = 1, tag "TAIKO_ETNA_CONFIG_V1") is that field list and remains valid only for an epoch already entered under it, and MUST NOT be used for a new epoch; version 2 (paramVersion = 2, tag "TAIKO_ETNA_CONFIG_V2") is current for any new epoch and is the same field list plus a uint64 L2_BLOCK_GAS_LIMIT encoded immediately after uint32 MAX_BATCH_BLOCKS, the per-block L2 gas limit FI-12's capacity relation is stated against. The guest MUST recompute the hash from the configuration it actually applied — including L2_BLOCK_GAS_LIMIT for a version-2 entry — and reject the proof unless the recomputation equals the registry value the L1 contract supplied; paramVersion is incremented whenever the enumeration changes, so two different enumerations can never share a domain. (S5 §5: the config registry, its append-only semantics and its per-epoch immutability, and the defined configHash preimage. This closes R4-PB-02, R4-LIV-04 and part of R4-MB-02.) This closes the single-tag preimage: PARAM-04 now states the V1/V2 pair with V2 current for any new epoch, and the V2 enumeration carries uint64 L2_BLOCK_GAS_LIMIT immediately after uint32 MAX_BATCH_BLOCKS. Failure modes: a single mutable global hash lets a proof made under one configuration be accepted under another; a registry entry that can be edited after its epoch started lets governance change the rules under which a batch was already certified and executed — configuration capture by upgrade.
