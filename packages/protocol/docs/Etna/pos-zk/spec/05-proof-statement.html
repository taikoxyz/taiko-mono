05 — Proof statement: what the ZK proof establishes, and what it does not

A ZK proof does not establish that no hidden competing chain exists. It establishes that the evidence presented is sufficient, under the stated consensus assumptions, for the claimed transition from an authenticated predecessor to a claimed successor. If at least one third of the epoch's voting power violates A-CONS-1, two conflicting certificates can both be cryptographically valid and both can produce accepting proofs. ZK verification does not repair failed consensus assumptions.

PRF-01 — statement overview: one combined guest A single guest program proves the conjunction of two claims for one batch: (W1) consensus finality — that the batch's head block carries a valid commit certificate over (chain id, epoch, height, round, block id) signed by more than two thirds of the voting power of the epoch's validator set, where that set is authenticated from L1 state and epoch is the L1-committed function of height; a batch never spans an epoch boundary (PRF-05), so exactly one epoch and one set root are in play; and (W2) execution — that executing the batch's blocks, decoded from the committed payload per PRF-06, in the order fixed by the consensus chain, from the predecessor state root yields the claimed successor state root. The guest also proves (W3) data binding — that the data it executed is the data the accepting L1 transaction publishes (see PRF-07) — and (W4) recovery authorization: that the batch was certified and executed under the configuration the L1 contract binds (configHash) and under the recovery generation the contract derives from its own storage (recoveryGeneration, PRF-02(5)–(6)); the guest checks that generation against the value the contract supplies as a public input and rejects a stale batch. Acceptance requires all four. The statement is not changed by the k-of-n withdrawal-root policy: every additional proof required at an epoch boundary proves this same statement, over the same journal, and only the number of independent implementations required before a checkpoint may finalize a withdrawal changes (L1-13, PRF-14). (PR #22262 review comment 1, item 3: k-of-n multiplies verification of this statement at the roots that finalize withdrawals; it does not create a second statement.) (user decision D-7: Mode B selected — the statement carries the recovery authorization, so an alternative history is never accepted on execution validity alone; a certificate from a previous generation is void for canonical purposes above the restored checkpoint but remains admissible as evidence.) (review round 1, findings B R1-03, B R1-04) Failure mode if split: a proof that a block was finalized without proving what it executed (or vice versa) admits a batch whose state transition was never agreed, or a state transition over data that was never certified. Proven (argument; premises listed per rule)

Public inputs

PRF-02 — public inputs (exact list, order is normative) This journal is the one authoritative public-input vector of the protocol. L1-05's binding table is the contract-side derivation table that points at this list, and the field-by-field reconciliation between the two is kept at L1-05 §2.1. A mismatch between the two lists is a protocol defect: it either makes the contract hash a value no guest ever committed to, so statementHash cannot match any honest proof and no batch can land, or it leaves a load-bearing value unbound, so a lander (any account, L1-04) chooses it. The guest commits to exactly the following journal, encoded canonically per GEN-05. The L1 verifier contract does not accept a caller-supplied journal: for every field marked L1 it derives the value itself from L1 state or from the transaction, and it recomputes the Fiat–Shamir challenge rather than trusting the prover's value.

// no per-epoch array. epoch MUST equal epoch_of(height) for every height in the range (a

Six constraints on this list are normative. (user decision D-7: Mode B selected — constraints (5) and (6) are added so the journal carries the recovery authorization.) (1) epoch is a pure function of height: for every height in [firstHeight, lastHeight], epoch = epoch_of(height) under the L1-committed epoch schedule (CONS-13, CONS-14), and the L1 contract recomputes that equality from its own activation record, so a prover cannot label a batch with an epoch that judges it more favourably. (2) validatorSetRoot is read by the L1 contract from the staking contract's per-epoch mapping for that epoch — L1 resolves epoch → root from its own state, without trusting the proof — and that mapping is append-only and immutable once the epoch starts (MEM-09). (3) There is exactly one validator-set commitment in this specification: the MEM-08 Merkle root over (chainId, k, index, pubkey, effStake) leaves, with node domain ETNA_SET_NODE and canonical ETNA_SET_KEY order; CONS-10's validators_hash and next_validators_hash MUST be that same root under that same encoding, so the header-chain binding and the Merkle membership proof always check the same object. (review round 1, findings B R1-03, B R1-05) (4) Epoch-transition inputs are L1-derived. setVersion, setVersionBlock, anchorSetRoot and anchorSetTotalVotingPower are read by the L1 contract from the staking contract's per-epoch mapping and the stored predecessor checkpoint and are never supplied by the prover; the two anchor fields are zero exactly when firstHeight is not the first block of its epoch, and the guest MUST reject a witness whose zero/non-zero pattern disagrees with the L1-derived values. These are the public inputs against which PRF-05(ii)'s transition checks are recomputed. The two set-version values are fixed by the staking contract's per-epoch entry, not invented: setVersion is the batch epoch's 1-based position in the append-only per-epoch registry (k = epoch − e_0 + 1, a pure function of the epoch and the activation record's offset e_0; MEM-09(2)), and setVersionBlock is the L1 block number of the commitSet() call, stored with that entry (N(k); MEM-09(2)); the L1 contract reads both from the staking contract's own state and accepts no submitter copy. The guest MUST recompute rather than accept them: it MUST recompute setVersion from the epoch and the activation record and reject a proof whose reconstructed R_k does not commit to it (every MEM-08 leaf and interior preimage carries k), and it MUST recompute set_version_commit from the L1-pinned pair and reject a header whose value differs; neither value may be taken from the witness, a host hint or the header itself (PRF-13). This closes review round 4 finding R4-PB-06: the epoch entry now carries the append block and fixes the version as the registry position, so L1-05 rows 27–28 and this constraint name a derivation that exists, and the guest checks it instead of trusting it. This closes review round 3 finding R3A-04: the epoch-anchor checks named public inputs that did not exist in the journal, so the transition evidence could not be recomputed at all. (5) The configuration and the recovery authorization are L1-derived, never prover-chosen, and the configuration is per-epoch. recoveryGeneration is read by the L1 contract from its own storage — the same record that holds the accepted predecessor checkpoint — and is never supplied by the prover: the contract derives the current generation itself, from that record, and only then hashes the journal into statementHash. The guest MUST require the journal's recoveryGeneration to equal the generation the contract supplies as a public input, and MUST reject a batch whose generation is stale. configHash is the registry value for the batch's epoch: the L1 contract reads it from the append-only per-epoch configuration registry of PARAM-04 (L1-05 row 23), the entry is fixed once and immutable for that epoch, and a batch whose epoch has no entry MUST be rejected before proof verification. The guest MUST recompute configHash from the configuration fields it actually applied and reject the proof unless the recomputation equals the journal value. The preimage is a single canonical abi.encode, domain-tagged and chain-id-prefixed (GEN-05), of exactly: bytes32("TAIKO_ETNA_CONFIG_V1"), uint256 l1ChainId, uint256 l2ChainId, uint64 epoch, uint64 EPOCH_LEN_L2, uint64 H_0, uint64 e_0, uint64 L1_0, uint64 EPOCH_LEN_L1, uint64 L2_BLOCK_INTERVAL, uint8 quorumForm (value 1: the predicate 3 · s > 2 · W of CONS-03), uint8 payloadFramingVersion (PRF-07(0)), uint32 MAX_BATCH_BLOCKS, uint8 daModesEnabled (bit 0 calldata, bit 1 blob, bit 2 hybrid), uint64 paramVersion, and the recovery parameters uint64 T_STALL, uint64 T_RECOVERY_DELAY, uint64 REC_COOLDOWN, uint256 B_REC_BASE, uint256 B_REC_KEEP, uint64 D_MAX. The enumeration is closed at paramVersion = 1: adding, removing or reordering a field requires a new paramVersion and a new domain tag, so two different enumerations can never share a domain and upgrades take effect for future epochs only, never for an epoch already entered. (S5 §5: configHash is per-epoch, fixed in the registry and never changed for that epoch, and the preimage is the enumerated, domain-tagged list above rather than a vacuous commitment.) Each of the two fields MUST have its own row in L1-05 and its own line in L1-05 §2.1; by the preamble above, a field without a row is the declared protocol defect. (user decision D-7: Mode B selected — the L1 contract derives the current recovery generation from its own storage, so a prover cannot choose the generation it is judged under.) (6) Execution validity alone is never sufficient. A batch is accepted only on the conjunction of (W1) finality, (W2) execution, (W3) data binding and the recovery authorization of (5). An alternative history may never be accepted on execution validity alone, and a stale-generation proof MUST be rejected even when its execution and data-binding claims are internally valid. A certificate produced under a previous generation is void for canonical purposes at every height above the restored checkpoint — the history it certifies is not the chain recovery restored — but it remains admissible as evidence: it is still a signed object, the evidence rules of ECON-04 still read it, and a signer is not excused because a recovery intervened (REC-02, late certificates). (user decision D-7: Mode B selected — a certificate from a previous generation is void for canonical purposes above the restored checkpoint but remains admissible as evidence.) PRF-03 — private witness; the validator set is never prover-defined The witness contains, and the guest fully constrains, at least: (a) the epoch's validator entries — each a (public key, effective stake) pair — with Merkle inclusion and ordering proofs against validatorSetRoot; (b) the head block's commit evidence — per-signer signatures, the signer bitmap, and the canonical vote bytes each signature covers; (c) the header chain from prevHeight + 1 to lastHeight, including each header's validators_hash and next_validators_hash — each MUST be the single canonical MEM-08 root of the set it commits to, under the one encoding fixed in PRF-02(3), so a header whose field is a hash of any other encoding is invalid; the guest MUST check each header's validators_hash against the L1-pinned validatorSetRoot of the batch's epoch, and MUST check next_validators_hash against an L1-pinned value only for the one header PRF-05(ii) names — the anchor header of a batch that starts at an epoch boundary — and MUST NOT accept a witness-supplied root as authentication for any set (PRF-13). This closes review round 3 finding R3A-04: PRF-03(c) required a next_validators_hash check on every header that had no L1-pinned value to check it against, leaving a witness root as the only available answer. (d) the epoch-boundary evidence required by PRF-05 — a batch never crosses a boundary, so the transition evidence is carried only by the batch that starts at an epoch boundary and is exactly: the anchor header B_anchor of the closing epoch, its commit certificate, and the closing epoch's validator entries with their Merkle inclusion proofs against the L1-pinned anchorSetRoot; (e) the committed payload bytes — the byte string dataCommitment binds, framed per PRF-07(0) — and the pre-state witness needed for execution: the guest MUST derive every executed block body by decoding these bytes and MUST NOT accept a second, independent copy of the payload; (f) the blob field elements used by PRF-07 (on the blob path, the same committed byte string). No witness element may define the authoritative validator set. A set is accepted only if its recomputed commitment equals validatorSetRoot, and that root comes from L1 state, never from the proof payload. Failure mode: a prover supplies a set it controls together with matching signatures, and the proof "verifies" a finality claim about a chain no independent validator ever saw. Proven (premise: the PRF-02 L1 derivations)

What the guest checks

PRF-04 — consensus-evidence checks For the head block's commit certificate the guest checks, in this order: (i) every signature verifies under the corresponding public key from the authenticated set, over the canonical vote bytes the guest reconstructs — never the witness-supplied bytes — with type = PRECOMMIT and the per-signature fields bound as CONS-02/CONS-03 require: the signed message MUST be a PRECOMMIT at the certificate's (epoch, height, round, block id), with validator_index equal to the signer's position in the canonical set order (the same index the signer bitmap uses), and with the certificate's epoch, height and round equal to those of the head block. A vote whose type, validator_index or block_id differs from that reconstruction does not count, even if the signature verifies. (review round 1, finding B R1-17) (ii) signers are distinct — the bitmap has exactly one bit per distinct signer and no bit outside the set, and that authenticated bitmap MUST be exposed in the journal's signerBitmap field and in no other form, so that land(data, proof) can record the participation of exactly the signers the guest verified (ECON-02 clause 5) (review round 2, finding E-R2-05); (iii) quorum holds under the single predicate 3 * s > 2 * W with checked arithmetic: s is the sum of the effective stake of the distinct signers, computed from the authenticated entries, and W = totalVotingPower; the guest evaluates checked_mul(3, s) > checked_mul(2, W) — the journal's quorumThreshold is the predicate's right-hand product, checked_mul(2, totalVotingPower) per PRF-02, never a pre-computed threshold. No threshold is stored or compared and no "strictly greater than the threshold" form is permitted: the predicate is exactly 3 * s > 2 * W, evaluated identically by the L2 client, this guest and the L1 contract, with CONS-03 as its sole owner. A strict versus non-strict mismatch is a protocol defect because it splits chain acceptance from L1 acceptance: a certificate the L2 finalizes can be rejected by the guest or by the L1 contract, or the reverse, so a legitimately finalized block becomes unsettleable. (review round 1, finding CS-09: the guest's s > floor(2 · totalVotingPower / 3) + 1 form required one more unit of signer power than the client's 3s > 2W, so a minimally finalized certificate could not be proven.) (iv) totalVotingPower equals the sum of the authenticated entries' effective stakes; (v) the head block hash equals the hash of the reconstructed head header, and the header chain links back to prevBlockHash by parent hash with no gaps. (vii) finalityCommitment is recomputed, never accepted. From the head certificate it verified in (i)–(iii), the guest MUST recompute the commitment in the canonical encoding of L1-05 row 15 — over chainId, epoch, lastHeight, headBlockHash, the certificate's round, the hash of the authenticated signer bitmap of (ii), and the hash of the certificate's ordered signature list — and MUST require equality with the journal's finalityCommitment; a value taken from a host hint and echoed without recomputation, or any mismatch, invalidates the proof (PRF-13). This closes review round 3 finding R3-PRF-02: the field was declared proof-bound and pointed at PRF-04 for its in-guest derivation, but no clause derived it, so the contract's only commitment to the finality evidence was chosen by the lander. (user decision D-6: clause (vi), the forced-inclusion check, is removed with forced inclusion; the remaining clauses keep their lettering — no clause is renumbered.) (viii) recovery authorization. The guest MUST require the journal's recoveryGeneration to equal the generation the L1 contract supplies as a public input for this batch, and MUST reject the proof when that generation is stale — when the batch's certified evidence belongs to an earlier generation than the one the contract derives from its own storage. It MUST likewise bind configHash: the configuration values it reads from the witness (epoch schedule, quorum predicate, DA-mode rules, parameter version and the recovery parameters) MUST hash to the journal's configHash, so a proof made under a different configuration cannot stand as this batch's. A stale-generation batch is rejected on this clause even when its finality, execution and data-binding checks all pass: execution validity alone never makes an alternative history acceptable. (user decision D-7: Mode B selected — the guest check is generation equality with the contract-supplied value, and a batch whose generation is stale is rejected.) Failure modes addressed: double counting a signer, counting stake twice, a rounding discrepancy between guest and contract, and a certificate over a block that is not the one whose header chain was executed. Proven
PRF-05 — epoch and set checks; a batch never spans an epoch boundary A batch MUST NOT span an epoch boundary — epoch_of(firstHeight) = epoch_of(lastHeight), and the guest rejects any witness for which this fails. This keeps the statement honest (one epoch, one set root, one quorum denominator) and removes the need for a per-epoch array in the journal. Batching therefore aligns with the L1-committed epoch schedule (CONS-13); because a batch is far shorter than an epoch, this is a batching constraint and not a liveness cost: a height range that would cross a boundary MUST be split into two batches — one ending at the last height of the epoch, one opening the next — and because the split point is forced by the schedule (L1-06's lastLandedHeight + 1), no height can be dropped at the split. Given that constraint, the guest checks that: (i) epoch is a pure function of height: for every height in the batch, epoch = epoch_of(height) under the L1-committed schedule (CONS-13, CONS-14), and the L1 contract recomputes the same equality from its own activation record, so the claimed epoch is never a free choice; (ii) the transition trigger is the first block of the batch range, never the batch head. Write e = epoch and f = firstHeight. Every header in the range MUST satisfy validators_hash = validatorSetRoot, the L1-pinned root of clause (iii). If f is the first block of its epoch (f = h_first(e)), the batch starts at an epoch boundary and MUST carry the transition evidence: the header at f MUST carry the epoch_anchor field of CONS-10(6), and the guest MUST recompute it from the anchor header B_anchor and the closing epoch's commit certificate it verifies — the certificate MUST be a valid epoch-(e-1) commit certificate for B_anchor under the L1-pinned anchorSetRoot and anchorSetTotalVotingPower, under the same signature, distinct-signer and quorum checks as PRF-04(i)–(iii), with B_anchor in place of the head block and the closing epoch's set in place of the batch epoch's set — and MUST reject the block if epoch_anchor does not recompute from it; the same header MUST also carry set_version_commit, which the guest MUST recompute from the L1-pinned (epoch, setVersion, setVersionBlock) inputs of clause (iii) and reject if it is non-zero and does not recompute. If f is not the first block of its epoch, the batch does not start at an epoch boundary and MUST NOT carry transition evidence: every header of the range carries epoch_anchor = 0 and set_version_commit = 0, as CONS-10(6) requires of every block that is not the first of its epoch, and the guest MUST reject a witness in which either field is non-zero. This is not a prover choice: a batch may not span a boundary and ranges are contiguous from lastLandedHeight + 1 (L1-06), so the epoch-opening block h_first(e) can be neither the continuation of a batch that began earlier nor left to a later batch — it is always the first block of its batch range — and therefore the batch that opens an epoch always triggers these checks, while a prover that extends the batch past the opening block still has its first block checked. The anchor header's next_validators_hash is the one next_validators_hash the guest checks against an L1-pinned value: the guest MUST require B_anchor.next_validators_hash = validatorSetRoot, the L1-pinned root of the epoch being opened, which is exactly CONS-10(4)'s epoch-change equality, enforced on both sides against L1. For every other header the field commits to the set of the epoch after the batch's epoch, which is not a public input of this batch: the guest MUST NOT authenticate it against a witness-supplied root (PRF-13), MUST require only that all headers of the range carry the same non-zero value, and the binding is completed when that header is presented as the anchor header of the next opening batch, whose own validatorSetRoot L1 pins. The canonical encodings of epoch_anchor, cert_hash and set_version_commit are owned by CONS-10(6) and are not restated here; the epoch-boundary evidence may not be skipped. This closes review round 3 finding R3A-04: the anchor check was triggered by the batch head, which a prover dodged by choosing a longer batch, and next_validators_hash had no L1-pinned value; the trigger is now the first block of the range, which no choice of batch length can avoid, and the one header checked against an L1-pinned value is named together with the reason it is sufficient. (iii) the epoch's set commitment equals the value the L1 staking contract holds for that epoch, supplied as a public input rather than as a witness: the contract resolves epoch → root from its own per-epoch mapping (MEM-09), which is append-only and immutable once the epoch starts, so L1 needs no trust in the proof to obtain it; the journal carries the batch epoch's validatorSetRoot and totalVotingPower, its setVersion and setVersionBlock — the pair (setVersion(e), N(setVersion(e))) of the L1 mapping entry (MEM-09(2)) — and, for a batch that starts at an epoch boundary, the closing epoch's anchorSetRoot and anchorSetTotalVotingPower; every one of these values is derived by the L1 contract from L1 state and none is supplied by the prover. PRF-06 — execution checks The guest executes every block in the range in consensus order, starting from prevStateRoot, applies each block's transactions under the L2 execution rules, and checks that each resulting state commitment equals the state root committed by that block's header; the final state commitment must equal postStateRoot. The executed block bodies are decoded from the committed payload, never taken from a separate witness stream. The guest MUST decode each block's body from the byte string the journal's dataCommitment binds — the canonical framing of PRF-07(0) — and MUST reject the proof unless the transactions it decodes for every height in [firstHeight, lastHeight] yield, under that header's own transactions-root construction, exactly the transactions_root committed by that height's header; a body that cannot be decoded from the committed bytes, or whose decoded transactions do not reproduce that root, invalidates the proof. The witness may not supply a block body independently of the committed payload: PRF-03(e) carries the committed payload bytes to the guest and MUST NOT be read as permitting a second, independent copy. This decode-and-root check is what makes dataCommitment a binding rather than a claim: without it the guest could execute a certified chain whose bodies came from somewhere other than the published bytes, and the accepting L1 transaction would commit to data that was never executed. (review round 2, finding P-R2-01) The state commitment function is Ethereum-compatible (Merkle–Patricia root over the account and storage tries), because the design preserves type-1 execution semantics; substituting a different commitment scheme is a normative change and not an implementation choice. Fee-vault accounting is part of the execution check, and the sweep of ECON-02 clause 7(b) is reconciled in it, never excluded from it. Write F(h) for the execution base fees and priority fees that block h's own execution collects under the L2 fee rules; write feeCredits for the monotone counter clause 7(a) requires the L2 fee policy to increment by exactly the ETH it routes to the vault, and feeSwept for the monotone counter the vault increments by exactly the ETH each canonical sweep moves out, with feeSwept ≤ feeCredits at all times. For every block in the range the guest MUST evaluate (F1)–(F4) against the state transition it executed and MUST reject the proof if any of them fails. (F1) The fee credit is exact. feeCredits(h) − feeCredits(h−1) == F(h): every unit of execution base fee and priority fee the block's own execution collects MUST be credited to the vault, and a block that diverts, destroys or redirects any part of those fees to another beneficiary makes the equality fail, so it is not provable and not acceptable (CONS-01(viii), ECON-04). (F2) Every vault debit is a canonical sweep, attributed in full. Every ETH outflow from the vault over block h, other than the Bridge fee a sweep caller supplies and the same call consumes, MUST be a sweep the guest reconstructs from its own execution of that block: a call to the vault's one sweep entry point of clause 7(b), which takes no argument that influences destination or amount, emitting exactly one bridge message built by the vault from protocol constants (sender = the vault, destination chain = L1, destOwner and to = the reward pool of clause 5(a), method data = the canonical bridge invocation selector, nonce = the vault's monotone sweep counter). The sweep MUST move exactly the vault's outstanding recorded fee balance feeCredits − feeSwept at that instant, no more and no less, so a forced credit is never swept toward the pool and feeSwept ≤ feeCredits is preserved. Write V(h) for the ETH value that message carries — the amount released to the pool, which is the vault's net debit for that sweep: the preserved Bridge requires value + fee == msg.value, the fee is additional ETH supplied by the sweep caller (clause 7(b)) and consumed in the same call, so it cancels in this reconciliation and MUST NOT be subtracted from the swept amount. Any other vault debit — a transfer, a payout to another beneficiary, or a message whose fields or recipient differ — fails this clause. The guest attributes debits by the executed message, so it needs no trust in the vault's intent and no code-hash pin. (F3) Forced credits are accounted, not punished. Write X(h) for the ETH credited to the vault over block h by any route other than the fee credit of (F1) and the Bridge fee a sweep caller supplies under clause 7(b); that Bridge fee is credited and consumed inside the same sweep call, so it is neither fee revenue nor a forced credit and it cancels in this reconciliation exactly as (F2) states. A forced credit cannot be prevented and MUST NOT make a block unprovable: it is not fee revenue, it MUST NOT enter feeCredits, and clause 7(b) requires the vault to leave it outstanding instead of sweeping it. The guest MUST also check the exact balance identity balance(h) − balance(h−1) == (feeCredits(h) − feeCredits(h−1)) + X(h) − V(h), which holds exactly when every credit is accounted and no debit exists outside (F2). (F4) The ordinary block and the sweep block. With no sweep, V(h) = 0, and with no forced credit, X(h) = 0, so (F1) and (F3) reduce to the exact balance(h) − balance(h−1) == F(h) for an ordinary block, a predicate checkable from that block's own state transition. A block containing a legitimate sweep satisfies balance(h) − balance(h−1) == F(h) + X(h) − V(h) and is therefore provable: the swept amount is attributed, never read as a fee shortfall. A mismatch is unprovable, and the same recomputable predicate is the fee-diversion evidence of ECON-04. Why this construction, stated in the rule. The sweep cannot be a system-level operation whose effect is excluded from the proven execution accounting, the way an L1→L2 deposit is: it is an ordinary L2 transaction, the batch's own postStateRoot commits to the vault's reduced balance, and a guest that ignored the debit would fail the state-root check above. The debit can be excluded only from the predicate, by attributing it to the canonical message, which is what (F2) does. Nor may the sweep be required to be the last call of its block with an accounting carve-out: the sweep is permissionless, so any account could sweep early and make an honest block unprovable, and for a compliant block the carve-out would be equivalent to (F2) and (F3) while punishing ordering. The guest therefore sees the sweep call and its canonical message in full and does not see it as a fee shortfall; it sees a forced credit and accounts for it, and no forced credit changes revenue. (PR #22262 review comment 2, item 4; review comment 3, item 6: the bare vault-balance-delta predicate made every sweep-containing block unprovable and its proposer slashable, and it left the D-8 funding path impossible; this is the checkable predicate that replaces it. Ordinary blocks, sweep blocks and diversion are each decided by the same recomputable arithmetic.) (S5 §8: the guest checks the fee-vault credit as part of execution.) Failure modes addressed: skipping blocks, reordering blocks, executing against a different pre-state, fee diversion (the fee-credit and debit-attribution checks make it unprovable, without making an honest sweep unprovable), a forced credit to the vault (accounted so it cannot halt settlement), and a state-root scheme the bridge cannot verify. Proven (premise: the L2 execution rules are fixed by the preserved EVM semantics)
PRF-07 — data-commitment binding for both data paths (0) Payload framing — the one canonical serialisation, normative for both paths. The batch payload P is a single byte string and is the only object the guest decodes and executes; (a) and (b) bind this payload and nothing else. P is the ordered concatenation, in ascending height order, of exactly one frame per height in [firstHeight, lastHeight]: P = frame(firstHeight) || frame(firstHeight + 1) || ... || frame(lastHeight), with frame(h) = be32(len(body_h)) || body_h. be32(x) is the 4-byte big-endian encoding of the unsigned 32-bit byte length of the element that follows, so the i-th frame (zero-based) is the body of height firstHeight + i; body_h is that block's body in the canonical execution-layer encoding whose transaction list the header's transactions_root commits to (the RLP list of the block's transactions in execution order), with no additional wrapper, separator, compression or framing field. No framing value is taken from the witness: the decoder consumes frames left to right, the height of each frame follows from its position, and the journal fixes the expected frame count at lastHeight - firstHeight + 1. A payload is invalid if a body length does not fit in 32 bits, if a length prefix would run past the end of the committed region, if the frame count differs from that number, or if any committed byte remains after the last frame; trailing bytes are not tolerated, so the decode is injective and P is a function of the published bytes and of the journal's height range alone. In the calldata path (daMode = 1) _data MUST be exactly P; on the blob path (daMode = 2) the blob concatenation MUST be P followed by zero padding to the end of the last blob in the committed range; and in CALLDATA_AND_BLOB both published copies MUST encode the same payload — _data = P and the blob concatenation MUST be P followed by zero padding — because two committed copies that differed would name two different data objects. This framing is part of the one statement both backends implement (PRF-09): a backend that framed or decoded differently would implement a different statement. Bodies enter the guest only by decoding these bytes, as PRF-06 requires. (review round 2, finding P-R2-04) Exactly one of the following holds for the commitment construction, and the journal records which. (a) Calldata path. The object committed by dataCommitment is the whole published byte string, not a prefix of it: here, the exact calldata payload the guest executes and L1 publishes. The L1 contract computes dataCommitment itself with the DA-02 construction, whose payloadRoot is keccak256(_data); the guest independently recomputes the same construction over the bytes it executed and requires equality. Both sides hash the same whole byte string, so the calldata path needs no probabilistic argument and remains the unconditionally sound path. (review round 1, finding B R1-06) (b) Blob path. The committed object is again the whole published byte string: for each blob in the transaction, all 4096 field elements — 131,072 bytes — including any unused remainder, in blob index order. No prefix-only commitment is permitted; the unused remainder of a blob MUST be committed too. A commitment over a prefix would fix the challenge point before the free suffix was chosen, and a prover could then choose the suffix to satisfy p_D(z) = p_B(z) by solving one linear equation — that was the round-1 attack. (i) For each index i, the contract requires blobhash(i) in this transaction to be non-zero and to equal the i-th versioned hash committed by the proof. (ii) The contract derives, per blob, the Fiat–Shamir point z_i = uint256(keccak256(abi.encode(bytes32("TAIKO_ETNA_CHALLENGE"), l2ChainId, statementCoreHash, dataCommitment, blobHashesHash, uint16(i)))) % BLS_MODULUS, where dataCommitment is the journal value the proof binds and blobHashesHash is the ordered versioned-hash hash, and requires the proof's challengeZ[i] to match. Because dataCommitment commits the whole published string, the challenge moves whenever the committed bytes move; the prover cannot choose a point after fixing its data. (iii) For each blob the contract calls the EIP-4844 point-evaluation precompile at 0x0A with (versionedHash_i, z_i, y_i, commitment_i, proof_i), which verifies both kzg_to_versioned_hash(commitment_i) == versionedHash_i and the KZG opening p_B(z_i) = y_i; the call costs 50,000 gas sourced (EIP-4844). (iv) The guest MUST interpret each blob exactly as EIP-4844 does: the 4096 field elements are the evaluations of the committed polynomial in bit-reversed order over the 4096th roots of unity, exactly as blob_to_kzg_commitment defines it (g1_lincomb(bit_reversal(setup_lagrange), blob)) — not coefficients. The guest MUST use that same convention (inverse bit-reversal plus Lagrange interpolation, or an equivalent FFT) or every honest blob proof fails, and it MUST reject any element ≥ BLS_MODULUS. (v) The guest MUST recompute dataCommitment over the full blob byte strings it executed with the DA-03(0) construction and require equality with the journal value used in (ii); it MUST also require p_D(z_i) = y_i for every blob. (review round 1, findings B R1-01, B R1-02, B R1-06) Why (b) is sound: the argument is over the joint event, not over a fixed challenge. The journal pins a payload D (the bytes the guest executed) and, per blob, a challenge z_i(D) derived from the transcript that contains dataCommitment = f(keccak(D)); the precompile pins the published blob polynomial p_B and a value y_i. To pass, a prover must exhibit a D with p_D(z(D)) = p_B(z(D)) where z itself depends on keccak(D) — a fixed-point condition, not a linear equation in the free part of D. The earlier statement that the bound is "per attempt at a fixed challenge" is wrong: it described an experiment in which the payload is fixed before z. In the correct experiment the prover searches over candidate payloads and wins only when a hash output lands on a root of (p_D - p_B); for any fixed candidate the probability is at most 4095/|F| ≈ 2-243 derived, so a search over q hash outputs succeeds with probability at most q · 2-243 (plus the 2-254.9 modular-reduction bias). D is not a free variable in any case: the executed payload is bound to the certified header chain — the certificate covers the head block id, the header chain links to the predecessor, and each header's transaction root fixes its transactions (PRF-04(v), PRF-06) — so a prover cannot vary D after the certificate is signed without invalidating it. Premises: KZG binding, the random-oracle model for the Fiat–Shamir derivation, canonical field elements, and correct in-guest field arithmetic in the EIP-4844 convention. The blob path is an implementation gate: it may not be relied on until this fixed-point argument has had independent cryptographic review and the in-guest evaluation cost has been measured. If any premise fails, or that review does not close, the blob path is unsound, which is why the calldata path remains unconditionally available. Proven unmeasured Open (blob path: independent cryptographic review of the fixed-point argument and the in-guest cost of the EIP-4844 evaluation are outstanding — see 03 and Q-A3)
PRF-08 — why one certificate per batch suffices, and its premises The guest verifies the commit certificate of the head block only. Every other block in the batch is covered by the header hash chain back to prevBlockHash, which the contract has already accepted as a finalized checkpoint. No ancestor certificate is verified on-chain or in-guest. Argument: under CONS-05 a validator precommits a block only after validating it and its parent relation, and a certificate requires more than two thirds of voting power, so at least one third of the voting power is correct and locked. A certificate for the head therefore implies the head is the unique finalized block at its height, hence that the entire prefix it commits to is the unique finalized prefix. Premises: fewer than one third of the epoch's voting power is Byzantine (A-CONS-1); correct validators obey CONS-02 and CONS-04; the set is L1-authenticated. If a premise fails the argument fails with it, and the proof does not detect that. Proven Assumed (premises named above; this is the reasoning a light client uses)
PRF-13 — bindings must be cryptographically enforced, never asserted Any value a prover could otherwise choose freely — the validator set, the quorum threshold, the predecessor, the data commitment, the challenge point, the configuration hash, the recovery generation and the program identity — must be derived by the L1 contract itself, or recomputed inside the guest from a value the contract derived, or checked by an L1 precompile. A binding that consists only of "the caller passed it" is not a binding and must not appear in this specification. (user decision D-7: Mode B selected — the recovery generation is one of the values the L1 contract must derive rather than accept from the caller.) Backends and lifecycle

PRF-09 — both backends realise the same statement; acceptance policy RISC Zero and SP1 must both implement this statement with a byte-identical journal, so that a batch's proof is portable between backends. Acceptance policy for settlement (closed): exactly one proof per batch, checked against exactly one registered verifier route. A route is the triple (programImageId, verifier, backendFamily) of L1-09; a proof is accepted when the single route named by its program image is registered for the batch's epoch, its verifier is a deployed, audited contract implementing this statement, and that verifier returns exactly abi.encode(true). On the settlement path the Inbox MUST NOT require, and MUST NOT accept as a substitute, a second proof: "any single accepted backend" is the settlement policy. The withdrawal-root path is the one exception, and it is conjunctive, not substitutive: an epoch-boundary checkpoint becomes a withdrawal root only when k distinct registered backend families have each verified the same accepted statement (L1-13); the additional proofs are evidence for one journal, never alternatives to each other, and a second proof is still never accepted as a substitute for a first on any path. Two-independent-backends acceptance is a different policy that may be adopted only by the procedure that governs a rule change (GOV-02, GOV-03), never as a launch toggle. This revision adopts exactly that policy for the withdrawal-root path only: the adopted form is specified by L1-13 and PRF-14, and any further change to it remains a rule change under GOV-02/GOV-03. A soundness bug in an accepted backend is a bridge-theft-class failure; the withdrawal-root policy of PRF-14 removes the easiest exploitation path — a withdrawal released on the weakest backend's soundness — but it is explicitly not a repair, and the residual failure class is stated in PRF-14 and L1-13(6). (review round 2, finding E-R2-04: the policy is closed, one route per proof, and the enabling rule of L1-09 is an upgrade.) Failure mode: an unstated policy leaves an implementer to decide whether one or two proofs are required, which changes both the security argument and the fleet sizing; an enabling rule any account could exercise would let an attacker install a verifier that returns true (L1-09). Proven Open (open only for the concrete inventory: the deployed, audited (programImageId, verifier, backendFamily) routes and their activation epochs, which MUST contain at least k distinct families with a live accepted route for every epoch or no withdrawal root can form (L1-13(5)). Until at least one such route is registered at activation, no batch can land and settlement cannot start; the inventory is a recorded launch input, not a policy choice — the policy above is not open.)
PRF-14 — backend independence: what k-of-n buys at the withdrawal roots, and its residual (1) The policy is over the same statement, not a second one. The k-of-n requirement of L1-13 applies only to the epoch-boundary checkpoints that finalize withdrawals. Each of the k proofs is a proof of the same accepted statementHash under PRF-02's single journal and the same GEN-05 encoding; the policy adds verification, never a statement, a witness rule or a journal field. A proof under one family is never a substitute for a proof under another: all k are required conjunctively before the checkpoint becomes a withdrawal root, and the settlement path is untouched (PRF-09). (2) Independence is registered metadata, not an on-chain fact. The unit of independence is the backendFamily tag of L1-09. Two images of the same implementation family count once, however many routes they have. That two tagged families really are independently implemented — separate codebases, separate circuits and separately reviewed — is asserted by the registering upgrade and audited at migration under A-GOV-1; it cannot be derived from a program image id or a verifier address, and no artifact may claim the tag is cryptographically enforced. (3) What it buys. For the withdrawal path it replaces "the proof system is as sound as the weakest accepted backend" with "a false withdrawal root requires every one of k independently implemented backends to accept a false statement, or a defect common to all of them". A backend-specific soundness bug — a circuit defect, a syscall or accelerator-constraint defect, a verifier-contract defect, a backend-specific witness bug — is not reproduced under the other k−1 families, so the root is not designated. (4) What it does not buy, stated rather than implied. (a) Common-mode defects are not covered. The statement, the guest logic, the payload framing, the L1 derivations and this specification are shared by every backend; a defect there is reproduced by all k implementations and the policy adds nothing. Two backends implementing one specification are not two independent designs, and no rule may present k-of-n as protection against a faulty guest or a faulty specification. (b) Settlement is not covered. Non-boundary batches are still accepted on one proof (PRF-09), so one unsound backend can still land a forged ordinary checkpoint. (c) The residual is a stop, not a theft. A forged checkpoint — one whose record disagrees with the real L2 chain at that height, in its stateRoot or in its blockHash — cannot be honestly extended: PRF-06 requires every executed block's resulting state commitment to equal that block's own header root, and the header chain links to the predecessor's block hash, so no honest batch can be landed above the forged record and settlement stops there. Recovery cannot clear that stop, because the forged record is the latest accepted checkpoint (REC-01). (d) The exit path inherits a dependency. Withdrawals then require k families to be available and funded to produce the attach proofs; the liveness consequences are stated in L1-13(5) and are not repaired by this rule. Premises of (3) and (4c): the collision resistance of the state commitment, the determinism of execution, the honest registration of family tags (A-GOV-1), and k distinct audited implementations actually existing at activation. (5) Affordability gate. k and n are fixed by S1's measured proving cost, not here. If S1 reports the per-epoch multiplier of L1-13(4) as unaffordable, the requirement MUST be withdrawn by a recorded change order that also discloses in LIM-01 that withdrawal soundness is single-backend and relies on the veto of MSG-04 plus disclosure. k = 1 MUST NOT be shipped as if it were k-of-n, and until k distinct families are registered and operating, no artifact may claim the property of (3). Failure mode: the design accepts one proof from any one registered backend, so the whole withdrawal path inherits the weakest backend's soundness, while the multi-proof composition and every pause lever the baseline had are removed. k-of-n at the withdrawal roots answers the backend-specific half of that; treating it as a general repair, or letting a common-mode defect pass unmentioned, would answer the other half with an overclaim. Proven Assumed unmeasured Open (the argument is conditional on k independently implemented, audited families existing, on A-GOV-1 for the family tags, and on S1's proving-cost numbers for affordability; the route inventory and the attach incentive are Open)
PRF-10 — program-image, verifier and version upgrades The guest program identity (image id / verification key) is bound by the verifier contract, not by the prover. An upgrade adds a new accepted identity; it must not remove the ability to accept proofs for batches whose head block was finalized under the previous identity (MIG-05, GOV-03). The Inbox may stop accepting an identity only after finality of — or a published deadline past — all batches that require it, and must never accept a withdrawn identity for new batches. Removing an accepted identity is a governance upgrade and is treated as malicious governance (GOV-02). Failure modes addressed: a verifier left accepting a superseded vulnerable identity; a proof generated under an old identity becoming unusable after an upgrade, which would strand an unsettled batch and halt settlement until the batch is re-proven or the permissionless, bonded recovery of REC-02 takes effect. (user decision D-7: Mode B selected — a stall above the last accepted checkpoint is resolved by resumed proving or by recovery, never by a privileged shortcut.) Assumed (the migration discipline is normative; its operational correctness is an implementation gate)
PRF-11 — syscall, hint and accelerator trust model Nothing computed by the host is trusted. Values entering the guest through host reads, hints or unconstrained regions are unverified assertions at the point they enter, and each must be constrained before use or verified by an explicit check. Accelerated primitives are trusted only to the extent the proof system's circuits constrain their input–output relation; the implementer must record for each primitive used (a) whether the backend documents it as circuit-accelerated or as guest software and (b) which constraint system enforces it. The guest must not treat a recovered public key, a decompressed point, or a claimed set membership as verified unless the corresponding relation is checked. Point validity, canonical field elements and the edge cases required by each backend's documented usage constraints are part of the trusted code base and must be checked explicitly. Failure modes addressed: the host-controlled-input class of vulnerabilities (including published advisories against both backends) and backend-specific precompile traps, such as non-canonical field elements yielding unverifiable proofs, on-curve validity not being enforced by the precompile, and points at infinity being unsupported. Proven (sourced constraints in 03)
PRF-12 — recursion and aggregation: what it does and does not prove Proofs for several batches may be aggregated into one recursive proof before submission only if the aggregation program hard-codes the accepted inner program identities and exposes in its own journal the set of (predecessor, successor, data commitment) triples it verified. Aggregation is a cost/latency optimisation: it changes nothing about the statement, and an aggregated proof must fail to verify if any inner journal is inconsistent with the outer claim. The protocol must also be able to operate without aggregation, one proof per batch, because aggregation adds a recursion program to the trusted computing base. Failure mode: an aggregation layer whose membership check is asserted rather than enforced turns many valid proofs into one arbitrary claim — the same class of recursion-circuit defect that a published advisory against one backend concerned. Assumed (design constraint stated; in-guest cost of aggregation is unmeasured)
