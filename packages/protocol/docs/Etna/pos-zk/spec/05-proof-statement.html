05 — Proof statement: what the ZK proof establishes, and what it does not

A ZK proof does not establish that no hidden competing chain exists. It establishes that the evidence presented is sufficient, under the stated consensus assumptions, for the claimed transition from an authenticated predecessor to a claimed successor. If at least one third of the epoch's voting power violates A-CONS-1, two conflicting certificates can both be cryptographically valid and both can produce accepting proofs. ZK verification does not repair failed consensus assumptions.

PRF-01 — statement overview: one combined guest A single guest program proves the conjunction of two claims for one batch: (W1) consensus finality — that the batch's head block carries a valid commit certificate over (chain id, epoch, height, round, block id) signed by more than two thirds of the voting power of the epoch's validator set, where that set is authenticated from L1 state and epoch is the L1-committed function of height; a batch never spans an epoch boundary (PRF-05), so exactly one epoch and one set root are in play; and (W2) execution — that executing the batch's blocks, in the order fixed by the consensus chain, from the predecessor state root yields the claimed successor state root. The guest also proves (W3) data binding — that the data it executed is the data the accepting L1 transaction publishes (see PRF-07). Acceptance requires all three. (review round 1, findings B R1-03, B R1-04) Failure mode if split: a proof that a block was finalized without proving what it executed (or vice versa) admits a batch whose state transition was never agreed, or a state transition over data that was never certified. Proven (argument; premises listed per rule)

Public inputs

PRF-02 — public inputs (exact list, order is normative) This journal is the one authoritative public-input vector of the protocol. L1-05's binding table is the contract-side derivation table that points at this list, and the field-by-field reconciliation between the two is kept at L1-05 §2.1. A mismatch between the two lists is a protocol defect: it either makes the contract hash a value no guest ever committed to, so statementHash cannot match any honest proof and no batch can land, or it leaves a load-bearing value unbound, so a lander (any account, L1-04) chooses it. The guest commits to exactly the following journal, encoded canonically per GEN-05. The L1 verifier contract does not accept a caller-supplied journal: for every field marked L1 it derives the value itself from L1 state or from the transaction, and it recomputes the Fiat–Shamir challenge rather than trusting the prover's value.

                             // epoch starts                                  (L1: staking contract)

  uint256 quorumThreshold;   // NOT a threshold: the quorum predicate's right-hand product,

  uint64  firstBlockTimestamp; // header timestamp of firstHeight; fixes the FI-02 dueness clock

  uint64  lastBlockTimestamp;  // header timestamp of lastHeight; the pair fixes the drift bound

  address feeRecipient;      // L2 proposer payout address of the first block's header; it receives

// INVARIANT: firstHeight and lastHeight lie in the SAME epoch. A batch may not span an
// epoch boundary (PRF-05), so one epoch/set-root pair is sufficient and the journal needs
// no per-epoch array. epoch MUST equal epoch_of(height) for every height in the range (a
// pure function of height under the L1-committed schedule, CONS-13/CONS-14) and
// validatorSetRoot MUST be the single canonical MEM-08 root L1 holds for that epoch
// (review round 1, findings B R1-03, B R1-04, B R1-05). Review round 1, finding R1-CROSS:
// an earlier revision carried a single epoch while PRF-05 required per-epoch checks, which
// made a boundary-crossing batch unprovable.
Three constraints on this list are normative. (1) epoch is a pure function of height: for every height in [firstHeight, lastHeight], epoch = epoch_of(height) under the L1-committed epoch schedule (CONS-13, CONS-14), and the L1 contract recomputes that equality from its own activation record, so a prover cannot label a batch with an epoch that judges it more favourably. (2) validatorSetRoot is read by the L1 contract from the staking contract's per-epoch mapping for that epoch — L1 resolves epoch → root from its own state, without trusting the proof — and that mapping is append-only and immutable once the epoch starts (MEM-09). (3) There is exactly one validator-set commitment in this specification: the MEM-08 Merkle root over (chainId, k, index, pubkey, effStake) leaves, with node domain ETNA_SET_NODE and canonical ETNA_SET_KEY order; CONS-10's validators_hash and next_validators_hash MUST be that same root under that same encoding, so the header-chain binding and the Merkle membership proof always check the same object. (review round 1, findings B R1-03, B R1-05) Vector contents, reconciled with L1-05. daMode, firstBlockTimestamp, lastBlockTimestamp, finalityCommitment, feeRecipient and signerBitmap are in this journal because each is load-bearing; l1ChainId and configHash are retained because they scope the statement; and previousCheckpointHash is not a public input — it is L1's local hash of the stored predecessor record, while the guest binds the predecessor through prevHeight/prevBlockHash/prevStateRoot. (review round 2, finding E-R2-02: this journal is now the single authoritative vector and L1-05 reconciles to it field-by-field; the signerBitmap field is the per-signer input required by review round 2 finding E-R2-05.) Failure mode if any field were caller-supplied: a prover could assert its own validator set, quorum threshold or predecessor, and the proof would be sound but meaningless. This is the highest-risk integration point identified in the zkVM research (03). Proven (conditional on the L1 derivations being implemented as stated)
PRF-03 — private witness; the validator set is never prover-defined The witness contains, and the guest fully constrains, at least: (a) the epoch's validator entries — each a (public key, effective stake) pair — with Merkle inclusion and ordering proofs against validatorSetRoot; (b) the head block's commit evidence — per-signer signatures, the signer bitmap, and the canonical vote bytes each signature covers; (c) the header chain from prevHeight + 1 to lastHeight, including each header's validators_hash and next_validators_hash — both MUST be the single canonical MEM-08 root of the set they commit to, under the one encoding fixed in PRF-02(3), so a header whose field is a hash of any other encoding is invalid; (d) the epoch-boundary evidence required by PRF-05 — a batch never crosses a boundary, so this is the end-of-epoch or start-of-epoch evidence of the batch that touches the boundary; (e) the batch's transaction data and the pre-state witness needed for execution; (f) the blob field elements used by PRF-07. No witness element may define the authoritative validator set. A set is accepted only if its recomputed commitment equals validatorSetRoot, and that root comes from L1 state, never from the proof payload. Failure mode: a prover supplies a set it controls together with matching signatures, and the proof "verifies" a finality claim about a chain no independent validator ever saw. Proven (premise: the PRF-02 L1 derivations)

What the guest checks

PRF-04 — consensus-evidence checks For the head block's commit certificate the guest checks, in this order: (i) every signature verifies under the corresponding public key from the authenticated set, over the canonical vote bytes the guest reconstructs — never the witness-supplied bytes — with type = PRECOMMIT and the per-signature fields bound as CONS-02/CONS-03 require: the signed message MUST be a PRECOMMIT at the certificate's (epoch, height, round, block id), with validator_index equal to the signer's position in the canonical set order (the same index the signer bitmap uses), and with the certificate's epoch, height and round equal to those of the head block. A vote whose type, validator_index or block_id differs from that reconstruction does not count, even if the signature verifies. (review round 1, finding B R1-17) (ii) signers are distinct — the bitmap has exactly one bit per distinct signer and no bit outside the set, and that authenticated bitmap MUST be exposed in the journal's signerBitmap field and in no other form, so that land(data, proof) can record the participation of exactly the signers the guest verified (ECON-02 clause 5) (review round 2, finding E-R2-05); (iii) quorum holds under the single predicate 3 * s > 2 * W with checked arithmetic: s is the sum of the effective stake of the distinct signers, computed from the authenticated entries, and W = totalVotingPower; the guest evaluates checked_mul(3, s) > checked_mul(2, W) — the journal's quorumThreshold is the predicate's right-hand product, checked_mul(2, totalVotingPower) per PRF-02, never a pre-computed threshold. No threshold is stored or compared and no "strictly greater than the threshold" form is permitted: the predicate is exactly 3 * s > 2 * W, evaluated identically by the L2 client, this guest and the L1 contract, with CONS-03 as its sole owner. A strict versus non-strict mismatch is a protocol defect because it splits chain acceptance from L1 acceptance: a certificate the L2 finalizes can be rejected by the guest or by the L1 contract, or the reverse, so a legitimately finalized block becomes unsettleable. (review round 1, finding CS-09: the guest's s > floor(2 · totalVotingPower / 3) + 1 form required one more unit of signer power than the client's 3s > 2W, so a minimally finalized certificate could not be proven.) (iv) totalVotingPower equals the sum of the authenticated entries' effective stakes; (v) the head block hash equals the hash of the reconstructed head header, and the header chain links back to prevBlockHash by parent hash with no gaps; and (vi) the forced-inclusion check: the guest recomputes the capped FIFO prefix DueCap(T) defined by FI-02 — the same predicate the L1 backstop in land(data, proof) computes, with T the batch's first-block timestamp — from the L1-stored queue (the queue head, the eligibility timestamps and the consumed set are L1 state, supplied as public inputs or derived from values the contract reads), and requires that the batch's first block contains exactly those requests, that forcedInclusionCommitment is the canonical hash of that ordered list, and that no other request is covered. This check is what makes the L1 backstop real: without it, an L1-05 binding row that claims forcedInclusionCommitment is proof-bound is merely asserted, and a quorum could omit a forced inclusion, consume the request and collect its fee while every other check passes (review round 1, finding C R1-02). Failure modes addressed: double counting a signer, counting stake twice, a rounding discrepancy between guest and contract, and a certificate over a block that is not the one whose header chain was executed. Proven
PRF-05 — epoch and set checks; a batch never spans an epoch boundary A batch MUST NOT span an epoch boundary — epoch_of(firstHeight) = epoch_of(lastHeight), and the guest rejects any witness for which this fails. This keeps the statement honest (one epoch, one set root, one quorum denominator) and removes the need for a per-epoch array in the journal. Batching therefore aligns with the L1-committed epoch schedule (CONS-13); because a batch is far shorter than an epoch, this is a batching constraint and not a liveness cost: a height range that would cross a boundary MUST be split into two batches — one ending at the last height of the epoch, one opening the next — and because the split point is forced by the schedule (L1-06's lastLandedHeight + 1), no height can be dropped at the split. Given that constraint, the guest checks that: (i) epoch is a pure function of height: for every height in the batch, epoch = epoch_of(height) under the L1-committed schedule (CONS-13, CONS-14), and the L1 contract recomputes the same equality from its own activation record, so the claimed epoch is never a free choice; (ii) the head header's validators_hash equals the epoch's set root, and if the batch's head is the last block of its epoch, that header's next_validators_hash commits to the next epoch's set (CONS-10); if the batch's head is the first block of its epoch, the head header MUST carry the epoch_anchor field of CONS-10(6) and the guest MUST recompute it from the anchor certificate it verifies — including the cert_hash of the closing epoch's commit certificate for B_anchor, the last block finalized in that epoch — and reject the header if epoch_anchor does not recompute; the canonical encodings of epoch_anchor and cert_hash are owned by CONS-10(6) and are not restated here; the epoch-boundary evidence is checked by the batch on each side of the boundary and may not be skipped; (iii) the epoch's set commitment equals the value the L1 staking contract holds for that epoch, supplied as a public input rather than as a witness: the contract resolves epoch → root from its own per-epoch mapping (MEM-09), which is append-only and immutable once the epoch starts, so L1 needs no trust in the proof to obtain it; when the batch's head opens its epoch, the head header's set_version_commit field MUST equal the CONS-10(6) commitment to the L1 mapping entry (set_version(e), N(set_version(e))) of the batch's epoch e, recomputed by the guest against the same public input, and a non-zero set_version_commit that fails to recompute makes the header invalid; its canonical encoding is owned by CONS-10(6) and is not restated here; (review round 1, finding CS-08: the epoch-boundary checks now name the CONS-10(6) objects epoch_anchor, cert_hash and set_version_commit and defer their encodings to their owner.) (iv) there is exactly one validator-set commitment in this specification: the MEM-08 Merkle root — leaves keccak256(abi.encode(ETNA_SET_LEAF, chainId, k, index, pubkey, effStake)), interior nodes keccak256(abi.encode(ETNA_SET_NODE, chainId, k, left, right)), canonical order by keccak256(abi.encode(ETNA_SET_KEY, chainId, pubkey)), odd nodes promoted unchanged. CONS-10's validators_hash and next_validators_hash MUST be that same root under that same encoding. A second, flat or ad-hoc encoding is forbidden: with two encodings the header-chain binding and the Merkle membership proof would check different objects, so one of the two bindings could fail silently while the other still passes, and the set would be authenticated by only one of the two L1 facts the design claims. (review round 1, findings B R1-03, B R1-04, B R1-05) Failure modes addressed: set substitution at a boundary, a fork created by switching sets at different heights on different branches, a long-range attacker relabelling a fork with a past epoch whose set it still controls, and a prover choosing an "easy" set. Proven (the lock carry-over premise is CONS-09, marked Assumed-with-argument)
PRF-06 — execution checks The guest executes every block in the range in consensus order, starting from prevStateRoot, applies each block's transactions under the L2 execution rules, and checks that each resulting state commitment equals the state root committed by that block's header; the final state commitment must equal postStateRoot. The state commitment function is Ethereum-compatible (Merkle–Patricia root over the account and storage tries), because the design preserves type-1 execution semantics; substituting a different commitment scheme is a normative change and not an implementation choice. Failure modes addressed: skipping blocks, reordering blocks, executing against a different pre-state, and a state-root scheme the bridge cannot verify. Proven (premise: the L2 execution rules are fixed by the preserved EVM semantics)
PRF-07 — data-commitment binding for both data paths Exactly one of the following holds, and the journal records which. (a) Calldata path. The object committed by dataCommitment is the whole published byte string, not a prefix of it: here, the exact calldata payload the guest executes and L1 publishes. The L1 contract computes dataCommitment itself with the DA-02 construction, whose payloadRoot is keccak256(_data); the guest independently recomputes the same construction over the bytes it executed and requires equality. Both sides hash the same whole byte string, so the calldata path needs no probabilistic argument and remains the unconditionally sound path. (review round 1, finding B R1-06) (b) Blob path. The committed object is again the whole published byte string: for each blob in the transaction, all 4096 field elements — 131,072 bytes — including any unused remainder, in blob index order. No prefix-only commitment is permitted; the unused remainder of a blob MUST be committed too. A commitment over a prefix would fix the challenge point before the free suffix was chosen, and a prover could then choose the suffix to satisfy p_D(z) = p_B(z) by solving one linear equation — that was the round-1 attack. (i) For each index i, the contract requires blobhash(i) in this transaction to be non-zero and to equal the i-th versioned hash committed by the proof. (ii) The contract derives, per blob, the Fiat–Shamir point z_i = uint256(keccak256(abi.encode(bytes32("TAIKO_ETNA_CHALLENGE"), l2ChainId, statementCoreHash, dataCommitment, blobHashesHash, uint16(i)))) % BLS_MODULUS, where dataCommitment is the journal value the proof binds and blobHashesHash is the ordered versioned-hash hash, and requires the proof's challengeZ[i] to match. Because dataCommitment commits the whole published string, the challenge moves whenever the committed bytes move; the prover cannot choose a point after fixing its data. (iii) For each blob the contract calls the EIP-4844 point-evaluation precompile at 0x0A with (versionedHash_i, z_i, y_i, commitment_i, proof_i), which verifies both kzg_to_versioned_hash(commitment_i) == versionedHash_i and the KZG opening p_B(z_i) = y_i; the call costs 50,000 gas sourced (EIP-4844). (iv) The guest MUST interpret each blob exactly as EIP-4844 does: the 4096 field elements are the evaluations of the committed polynomial in bit-reversed order over the 4096th roots of unity, exactly as blob_to_kzg_commitment defines it (g1_lincomb(bit_reversal(setup_lagrange), blob)) — not coefficients. The guest MUST use that same convention (inverse bit-reversal plus Lagrange interpolation, or an equivalent FFT) or every honest blob proof fails, and it MUST reject any element ≥ BLS_MODULUS. (v) The guest MUST recompute dataCommitment over the full blob byte strings it executed with the DA-03(0) construction and require equality with the journal value used in (ii); it MUST also require p_D(z_i) = y_i for every blob. (review round 1, findings B R1-01, B R1-02, B R1-06) Why (b) is sound: the argument is over the joint event, not over a fixed challenge. The journal pins a payload D (the bytes the guest executed) and, per blob, a challenge z_i(D) derived from the transcript that contains dataCommitment = f(keccak(D)); the precompile pins the published blob polynomial p_B and a value y_i. To pass, a prover must exhibit a D with p_D(z(D)) = p_B(z(D)) where z itself depends on keccak(D) — a fixed-point condition, not a linear equation in the free part of D. The earlier statement that the bound is "per attempt at a fixed challenge" is wrong: it described an experiment in which the payload is fixed before z. In the correct experiment the prover searches over candidate payloads and wins only when a hash output lands on a root of (p_D - p_B); for any fixed candidate the probability is at most 4095/|F| ≈ 2-243 derived, so a search over q hash outputs succeeds with probability at most q · 2-243 (plus the 2-127 modular-reduction bias). D is not a free variable in any case: the executed payload is bound to the certified header chain — the certificate covers the head block id, the header chain links to the predecessor, and each header's transaction root fixes its transactions (PRF-04(v), PRF-06) — so a prover cannot vary D after the certificate is signed without invalidating it. Premises: KZG binding, the random-oracle model for the Fiat–Shamir derivation, canonical field elements, and correct in-guest field arithmetic in the EIP-4844 convention. The blob path is an implementation gate: it may not be relied on until this fixed-point argument has had independent cryptographic review and the in-guest evaluation cost has been measured. If any premise fails, or that review does not close, the blob path is unsound, which is why the calldata path remains unconditionally available. Proven unmeasured Open (blob path: independent cryptographic review of the fixed-point argument and the in-guest cost of the EIP-4844 evaluation are outstanding — see 03 and Q-A3)
PRF-08 — why one certificate per batch suffices, and its premises The guest verifies the commit certificate of the head block only. Every other block in the batch is covered by the header hash chain back to prevBlockHash, which the contract has already accepted as a finalized checkpoint. No ancestor certificate is verified on-chain or in-guest. Argument: under CONS-05 a validator precommits a block only after validating it and its parent relation, and a certificate requires more than two thirds of voting power, so at least one third of the voting power is correct and locked. A certificate for the head therefore implies the head is the unique finalized block at its height, hence that the entire prefix it commits to is the unique finalized prefix. Premises: fewer than one third of the epoch's voting power is Byzantine (A-CONS-1); correct validators obey CONS-02 and CONS-04; the set is L1-authenticated. If a premise fails the argument fails with it, and the proof does not detect that. Proven Assumed (premises named above; this is the reasoning a light client uses)
PRF-13 — bindings must be cryptographically enforced, never asserted Any value a prover could otherwise choose freely — the validator set, the quorum threshold, the predecessor, the data commitment, the challenge point, the configuration hash and the program identity — must be derived by the L1 contract itself, or recomputed inside the guest from a value the contract derived, or checked by an L1 precompile. A binding that consists only of "the caller passed it" is not a binding and must not appear in this specification. Failure mode: a proof that is sound in isolation but whose public inputs are attacker-chosen — the standard way ZK-rollup integrations fail. Proven

Backends and lifecycle

PRF-09 — both backends realise the same statement; acceptance policy RISC Zero and SP1 must both implement this statement with a byte-identical journal, so that a batch's proof is portable between backends. Acceptance policy (closed): exactly one proof per batch, checked against exactly one registered verifier route. A route is the pair (programImageId, verifier) of L1-09; a proof is accepted when the single route named by its program image is registered for the batch's epoch, its verifier is a deployed, audited contract implementing this statement, and that verifier returns exactly abi.encode(true). The Inbox MUST NOT require, and MUST NOT accept as a substitute, a second proof: "any single accepted backend" is the policy. Two-independent-backends acceptance is a different policy that may be adopted only by the procedure that governs a rule change (GOV-02, GOV-03), never as a launch toggle. A soundness bug in an accepted backend is a bridge-theft-class failure not repairable by the protocol. (review round 2, finding E-R2-04: the policy is closed, one route per proof, and the enabling rule of L1-09 is an upgrade.) Failure mode: an unstated policy leaves an implementer to decide whether one or two proofs are required, which changes both the security argument and the fleet sizing; an enabling rule any account could exercise would let an attacker install a verifier that returns true (L1-09). Proven Open (open only for the concrete inventory: the deployed, audited (programImageId, verifier) pairs and their activation epochs. Until at least one such route is registered at activation, no batch can land and settlement cannot start; the inventory is a recorded launch input, not a policy choice — the policy above is not open.)
PRF-10 — program-image, verifier and version upgrades The guest program identity (image id / verification key) is bound by the verifier contract, not by the prover. An upgrade adds a new accepted identity; it must not remove the ability to accept proofs for batches whose head block was finalized under the previous identity (MIG-05, GOV-03). The Inbox may stop accepting an identity only after finality of — or a published deadline past — all batches that require it, and must never accept a withdrawn identity for new batches. Removing an accepted identity is a governance upgrade and is treated as malicious governance (GOV-02). Failure modes addressed: a verifier left accepting a superseded vulnerable identity; a proof generated under an old identity becoming unusable after an upgrade, which would strand an unsettled batch and — under Mode A — halt settlement. Assumed (the migration discipline is normative; its operational correctness is an implementation gate)
PRF-11 — syscall, hint and accelerator trust model Nothing computed by the host is trusted. Values entering the guest through host reads, hints or unconstrained regions are unverified assertions at the point they enter, and each must be constrained before use or verified by an explicit check. Accelerated primitives are trusted only to the extent the proof system's circuits constrain their input–output relation; the implementer must record for each primitive used (a) whether the backend documents it as circuit-accelerated or as guest software and (b) which constraint system enforces it. The guest must not treat a recovered public key, a decompressed point, or a claimed set membership as verified unless the corresponding relation is checked. Point validity, canonical field elements and the edge cases required by each backend's documented usage constraints are part of the trusted code base and must be checked explicitly. Failure modes addressed: the host-controlled-input class of vulnerabilities (including published advisories against both backends) and backend-specific precompile traps, such as non-canonical field elements yielding unverifiable proofs, on-curve validity not being enforced by the precompile, and points at infinity being unsupported. Proven (sourced constraints in 03)
PRF-12 — recursion and aggregation: what it does and does not prove Proofs for several batches may be aggregated into one recursive proof before submission only if the aggregation program hard-codes the accepted inner program identities and exposes in its own journal the set of (predecessor, successor, data commitment) triples it verified. Aggregation is a cost/latency optimisation: it changes nothing about the statement, and an aggregated proof must fail to verify if any inner journal is inconsistent with the outer claim. The protocol must also be able to operate without aggregation, one proof per batch, because aggregation adds a recursion program to the trusted computing base. Failure mode: an aggregation layer whose membership check is asserted rather than enforced turns many valid proofs into one arbitrary claim — the same class of recursion-circuit defect that a published advisory against one backend concerned. Assumed (design constraint stated; in-guest cost of aggregation is unmeasured)
