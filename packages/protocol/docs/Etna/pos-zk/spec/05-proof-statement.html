05 — Proof statement: what the ZK proof establishes, and what it does not

A ZK proof does not establish that no hidden competing chain exists. It establishes that the evidence presented is sufficient, under the stated consensus assumptions, for the claimed transition from an authenticated predecessor to a claimed successor. If at least one third of the epoch's voting power violates A-CONS-1, two conflicting certificates can both be cryptographically valid and both can produce accepting proofs. ZK verification does not repair failed consensus assumptions.

PRF-01 — statement overview: one combined guest A single guest program proves the conjunction of two claims for one batch: (W1) consensus finality — that the batch's head block carries a valid commit certificate over (chain id, epoch, height, round, block id) signed by more than two thirds of the voting power of the epoch's validator set, where that set is authenticated from L1 state and epoch is the L1-committed function of height; a batch never spans an epoch boundary (PRF-05), so exactly one epoch and one set root are in play; and (W2) execution — that executing the batch's blocks, decoded from the committed payload per PRF-06, in the order fixed by the consensus chain, from the predecessor state root yields the claimed successor state root. The guest also proves (W3) data binding — that the data it executed is the data the statement's data binding names: the payload the accepting L1 transaction publishes, or the payload of the recorded publication that transaction references (PRF-07, DA-07–DA-09). The contract-side check differs between the two cases; the guest's recomputation does not (PRF-07(b)(i)) — and (W4) recovery authorization: that the batch was certified and executed under the configuration the L1 contract binds (configHash) and under the recovery generation the contract derives from its own storage (recoveryGeneration, PRF-02(5)–(6)); the guest checks that generation against the value the contract supplies as a public input and rejects a stale batch. Acceptance requires all four, and for a batch judged against a non-empty required forced-data prefix acceptance additionally requires the narrow forced-data inclusion check of PRF-04(vi) (FI-11; decision D-12). (decision D-12: the statement carries the narrow forced-data inclusion check as well, and that check's enforcement point is the proof, never land's admission rules.) The statement is unchanged by aggregation and by the per-purpose family count. The protocol accepts exactly one proof object per purpose, and that object is an n-of-m aggregation proof whose every inner proof proves this same statement over the same journal (PRF-15, L1-14); the aggregation's public input, which records the contributing registered backend families, is a property of the object — never a second statement and never an added journal field. Only the number of distinct families the object must attest changes with the purpose: at least K_SETTLE_BACKENDS (= 1) for settlement, at least K_PROOF_BACKENDS for a withdrawal root (L1-13, PRF-14). (decision D-13: one proof object per batch, n-of-m aggregated underneath; the statement of PRF-01 is not weakened by aggregation, and PRF-02's journal is unchanged.) (PR #22262 review comment 1, item 3: the family count multiplies verification of this statement at the roots that finalize withdrawals; it does not create a second statement.) (user decision D-7: Mode B selected — the statement carries the recovery authorization, so an alternative history is never accepted on execution validity alone; a certificate from a previous generation is void for canonical purposes above the restored checkpoint but remains admissible as evidence.) (review round 1, findings B R1-03, B R1-04) Failure mode if split: a proof that a block was finalized without proving what it executed (or vice versa) admits a batch whose state transition was never agreed, or a state transition over data that was never certified. Public inputs

PRF-02 — public inputs (exact list, order is normative) This journal is the one authoritative public-input vector of the protocol. L1-05's binding table is the contract-side derivation table that points at this list, and the field-by-field reconciliation between the two is kept at L1-05 §2.1. A mismatch between the two lists is a protocol defect: it either makes the contract hash a value no guest ever committed to, so statementHash cannot match any honest proof and no batch can land, or it leaves a load-bearing value unbound, so a lander (any account, L1-04) chooses it. The guest commits to exactly the following journal, encoded canonically per GEN-05. The L1 verifier contract does not accept a caller-supplied journal: for every field marked L1 it derives the value itself from L1 state or from the transaction, and it recomputes the Fiat–Shamir challenge rather than trusting the prover's value.

Six constraints on this list are normative. (user decision D-7: Mode B selected — constraints (5) and (6) are added so the journal carries the recovery authorization.) (1) epoch is a pure function of height: for every height in [firstHeight, lastHeight], epoch = epoch_of(height) under the L1-committed epoch schedule (CONS-13, CONS-14), and the L1 contract recomputes that equality from its own activation record, so a prover cannot label a batch with an epoch that judges it more favourably. (2) validatorSetRoot is read by the L1 contract from the staking contract's per-epoch mapping for that epoch — L1 resolves epoch → root from its own state, without trusting the proof — and that mapping is append-only and immutable once the epoch starts (MEM-09). (3) There is exactly one validator-set commitment in this specification: the MEM-08 Merkle root over (chainId, k, index, pubkey, effStake) leaves, with node domain ETNA_SET_NODE and canonical ETNA_SET_KEY order; CONS-10's validators_hash and next_validators_hash MUST be that same root under that same encoding, so the header-chain binding and the Merkle membership proof always check the same object. (review round 1, findings B R1-03, B R1-05) (4) Epoch-transition inputs are L1-derived. setVersion, setVersionBlock, anchorSetRoot and anchorSetTotalVotingPower are read by the L1 contract from the staking contract's per-epoch mapping and the stored predecessor checkpoint and are never supplied by the prover; the two anchor fields are zero exactly when firstHeight is not the first block of its epoch, and the guest MUST reject a witness whose zero/non-zero pattern disagrees with the L1-derived values. These are the public inputs against which PRF-05(ii)'s transition checks are recomputed, except in the recovery-restart form (b), where the two anchor fields are read from L1 as usual but no certificate is judged against them and the header's epoch_anchor is recomputed from prevHeight/prevBlockHash/prevStateRoot/firstHeight (REC-04(3)). The two set-version values are fixed by the staking contract's per-epoch entry, not invented: setVersion is the batch epoch's 1-based position in the append-only per-epoch registry (k = epoch − e_0 + 1, a pure function of the epoch and the activation record's offset e_0; MEM-09(2)), and setVersionBlock is the L1 block number of the commitSet() call, stored with that entry (N(k); MEM-09(2)); the L1 contract reads both from the staking contract's own state and accepts no submitter copy. The guest MUST recompute rather than accept them: it MUST recompute setVersion from the epoch and the activation record and reject a proof whose reconstructed R_k does not commit to it (every MEM-08 leaf and interior preimage carries k), and it MUST recompute set_version_commit from the L1-pinned pair and reject a header whose value differs; neither value may be taken from the witness, a host hint or the header itself (PRF-13). (5) The configuration and the recovery authorization are L1-derived, never prover-chosen, and the configuration is per-epoch. recoveryGeneration is read by the L1 contract from its own storage — the same record that holds the accepted predecessor checkpoint — and is never supplied by the prover: the contract derives the current generation itself, from that record, and only then hashes the journal into statementHash. The guest MUST require the journal's recoveryGeneration to equal the generation the contract supplies as a public input, and MUST reject a batch whose generation is stale. configHash is the registry value for the batch's epoch: the L1 contract reads it from the append-only per-epoch configuration registry of PARAM-04 (L1-05 row 23), the entry is fixed once and immutable for that epoch, and a batch whose epoch has no entry MUST be rejected before proof verification. PRF-03 — private witness; the validator set is never prover-defined The witness contains, and the guest fully constrains, at least: (a) the epoch's validator entries — each a (public key, effective stake) pair — with Merkle inclusion and ordering proofs against validatorSetRoot; (b) the head block's commit evidence — per-signer signatures, the signer bitmap, and the canonical vote bytes each signature covers; (c) the header chain from firstHeight to lastHeight (ordinarily prevHeight + 1; after a completed retirement firstHeight = resumeHeight > prevHeight + 1, and the walk's foot is the single checkpoint link of REC-04(1)–(2)), including each header's validators_hash and next_validators_hash — each MUST be the single canonical MEM-08 root of the set it commits to, under the one encoding fixed in PRF-02(3), so a header whose field is a hash of any other encoding is invalid; the guest MUST check each header's validators_hash against the L1-pinned validatorSetRoot of the batch's epoch, and MUST check next_validators_hash against an L1-pinned value only for the one header PRF-05(ii) names — the anchor header of an ordinary epoch-boundary batch; at a recovery restart that opens the epoch there is no such header and no next_validators_hash is checked against an L1-pinned value (PRF-05(ii), form (b)) — and MUST NOT accept a witness-supplied root as authentication for any set (PRF-13). This closes review round 3 finding R3A-04: PRF-03(c) required a next_validators_hash check on every header that had no L1-pinned value to check it against, leaving a witness root as the only available answer. (d) the epoch-boundary evidence required by PRF-05 — a batch never crosses a boundary, so the transition evidence is carried only by the batch that starts at an epoch boundary and is exactly: the anchor header B_anchor of the closing epoch, its commit certificate, and the closing epoch's validator entries with their Merkle inclusion proofs against the L1-pinned anchorSetRoot; when the batch starts at an epoch boundary as a recovery restart, that evidence does not exist — the anchor block's height is retired — and the opening header instead carries the recovery anchor of REC-04(3), recomputed in-guest from the L1-derived journal values with no witness element (PRF-05(ii), form (b)); (e) the committed payload bytes — the byte string dataCommitment binds, framed per PRF-07(0) — and the pre-state witness needed for execution: the guest MUST derive every executed block body by decoding these bytes and MUST NOT accept a second, independent copy of the payload; (f) the blob field elements used by PRF-07 (on the blob path, the same committed byte string). No witness element may define the authoritative validator set. A set is accepted only if its recomputed commitment equals validatorSetRoot, and that root comes from L1 state, never from the proof payload. Failure mode: a prover supplies a set it controls together with matching signatures, and the proof "verifies" a finality claim about a chain no independent validator ever saw. What the guest checks

PRF-04 — consensus-evidence checks For the head block's commit certificate the guest checks, in this order: (i) every signature verifies under the corresponding public key from the authenticated set, over the canonical vote bytes the guest reconstructs — never the witness-supplied bytes — with type = PRECOMMIT and the per-signature fields bound as CONS-02/CONS-03 require: the signed message MUST be a PRECOMMIT at the certificate's (epoch, height, round, block id), with validator_index equal to the signer's position in the canonical set order (the same index the signer bitmap uses), and with the certificate's epoch, height and round equal to those of the head block. A vote whose type, validator_index or block_id differs from that reconstruction does not count, even if the signature verifies. (review round 1, finding B R1-17) (ii) signers are distinct — the bitmap has exactly one bit per distinct signer and no bit outside the set, and that authenticated bitmap MUST be exposed in the journal's signerBitmap field and in no other form, so that land(data, proof) can record the participation of exactly the signers the guest verified (ECON-02 clause 5) (review round 2, finding E-R2-05); (iii) quorum holds under the single predicate 3 * s > 2 * W with checked arithmetic: s is the sum of the effective stake of the distinct signers, computed from the authenticated entries, and W = totalVotingPower; the guest evaluates checked_mul(3, s) > checked_mul(2, W) — the journal's quorumThreshold is the predicate's right-hand product, checked_mul(2, totalVotingPower) per PRF-02, never a pre-computed threshold. No threshold is stored or compared and no "strictly greater than the threshold" form is permitted: the predicate is exactly 3 * s > 2 * W, evaluated identically by the L2 client, this guest and the L1 contract, with CONS-03 as its sole owner. A strict versus non-strict mismatch is a protocol defect because it splits chain acceptance from L1 acceptance: a certificate the L2 finalizes can be rejected by the guest or by the L1 contract, or the reverse, so a legitimately finalized block becomes unsettleable. (review round 1, finding CS-09: the guest's s > floor(2 · totalVotingPower / 3) + 1 form required one more unit of signer power than the client's 3s > 2W, so a minimally finalized certificate could not be proven.) (iv) totalVotingPower equals the sum of the authenticated entries' effective stakes; (v) the head block hash equals the hash of the reconstructed head header; the batch's own headers link to one another by parent hash with no gap, every header from lastHeight down to firstHeight, and then the chain takes exactly one further link, from the first header's parent_hash to prevBlockHash (REC-04(1)–(2)). When firstHeight = prevHeight + 1 that link is the ordinary successor relation to the predecessor checkpoint. When firstHeight > prevHeight + 1 the batch is a recovery restart: the heights below firstHeight are retired and have no canonical block, the single link is the whole connection to the restored checkpoint, and the guest MUST NOT require a header at any height below firstHeight, MUST NOT read the skipped heights as a missing parent link, and MUST reject a witness whose first header does not descend from prevBlockHash. D is not a free variable in any case: the executed payload is bound to the certified header chain — the certificate covers the head block id, the header chain links to the predecessor, and each header's transaction root fixes its transactions (PRF-04(v), PRF-06) — so a prover cannot vary D after the certificate is signed without invalidating it. The referenced case changes one link of this chain, not its conclusion. Link (a) becomes (a′): the recorded versioned hash of the referenced publication names a blob that was published in that transaction, which the consensus layer checked against the actual blob sidecars when that block was processed sourced (EIP-4844); the contract checks the record's identity, immutability and equality with this statement (DA-08), and the record's liveness (DA-09). Links (b)–(d) and the joint fixed point are identical, because the precompile does not require the blob to be in the executing transaction. The variant that omits the precompile on the referenced path is rejected as unsound: a "recorded hash plus in-guest evaluation" binding would evaluate the polynomial over the very bytes the guest already executed and tie them to nothing — the recorded hash would then bind nothing about the executed payload. Binding the executed bytes to the recorded commitment without the precompile requires the guest to recompute each blob's KZG commitment from the executed bytes (an MSM) or to verify the opening in-guest (pairings); both are UNVERIFIED on both backends (03, 04 §4), so that variant is Open and MUST NOT be relied on. Premises: KZG binding, the random-oracle model for the Fiat–Shamir derivation, canonical field elements, correct in-guest field arithmetic in the EIP-4844 convention, and — for the referenced case only — an immutable publication record whose recorded versioned hashes are the ones consensus checked against the published blobs, established at publication by the element-wise blobhash equality DA-07(5) requires and not assumed (review round 5, finding R5T-PDE-02). The blob path is an implementation gate: it may not be relied on until this fixed-point argument has had independent cryptographic review and the in-guest evaluation cost has been measured. If any premise fails, or that review does not close, the blob path is unsound, which is why the calldata path remains unconditionally available. Proven unmeasured Open (blob path: independent cryptographic review of the fixed-point argument and the in-guest cost of the EIP-4844 evaluation are outstanding — see 03 and Q-A3)
PRF-08 — why one certificate per batch suffices, and its premises The guest verifies the commit certificate of the head block only. Every other block in the batch is covered by the header hash chain back to prevBlockHash, which the contract has already accepted as a finalized checkpoint. No ancestor certificate is verified on-chain or in-guest. Argument: under CONS-05 a validator precommits a block only after validating it and its parent relation, and a certificate requires more than two thirds of voting power, so at least one third of the voting power is correct and locked. A certificate for the head therefore implies the head is the unique finalized block at its height, hence that the entire prefix it commits to is the unique finalized prefix. Premises: fewer than one third of the epoch's voting power is Byzantine (A-CONS-1); correct validators obey CONS-02 and CONS-04; the set is L1-authenticated. If a premise fails the argument fails with it, and the proof does not detect that. Proven Assumed (premises named above; this is the reasoning a light client uses)
PRF-13 — bindings must be cryptographically enforced, never asserted Any value a prover could otherwise choose freely — the validator set, the quorum threshold, the predecessor, the data commitment, the challenge point, the configuration hash, the recovery generation and the program identity — must be derived by the L1 contract itself, or recomputed inside the guest from a value the contract derived, or checked by an L1 precompile. A binding that consists only of "the caller passed it" is not a binding and must not appear in this specification. (user decision D-7: Mode B selected — the recovery generation is one of the values the L1 contract must derive rather than accept from the caller.) Failure mode: a proof that is sound in isolation but whose public inputs are attacker-chosen — the standard way ZK-rollup integrations fail. Proven

Backends and lifecycle

PRF-09 — both backends realise the same statement; acceptance policy RISC Zero and SP1 must both implement this statement with a byte-identical journal, so that a batch's proof is portable between backends and every inner proof of an aggregation proves one journal. Acceptance policy for settlement (closed): exactly one proof object per batch, checked against exactly one registered verifier route, and that object is an n-of-m aggregation proof. A route is the triple (programImageId, verifier, backendFamily) of L1-09; an object is accepted when the single route named by its program image is registered for the batch's epoch, its verifier is a deployed, audited contract implementing this statement, and that verifier returns exactly abi.encode(true). The object is verified as an aggregation proof (PRF-15): its public input names the contributing registered backend families, and the Inbox enforces the required distinct-family count per purpose — at least K_SETTLE_BACKENDS (= 1) for settlement, at least K_PROOF_BACKENDS for a withdrawal root (L1-14). On the settlement path the Inbox MUST NOT require, and MUST NOT accept as a substitute, a second proof object: one accepted aggregation proof is the settlement policy. The withdrawal-root path is the one place the count is raised, and it is a count inside the one object, not a second verification: an epoch-boundary checkpoint becomes a withdrawal root when one aggregation proof for the accepted statement attests at least k distinct registered families (L1-13); inner proofs are evidence for one journal, never alternatives to each other, and a second proof object is still never accepted as a substitute for a first on any path. (decision D-13: settlement accepts exactly one proof object, now an aggregation proof, and the distinct-family count is enforced per purpose.) Two-independent-backends acceptance is a different policy that may be adopted only by the procedure that governs a rule change (GOV-02, GOV-03), never as a launch toggle. This revision adopts exactly that policy for the withdrawal-root path only: the adopted form is specified by L1-13 and PRF-14, and any further change to it remains a rule change under GOV-02/GOV-03. A soundness bug in an accepted backend is a bridge-theft-class failure; the withdrawal-root policy of PRF-14 removes the easiest exploitation path — a withdrawal released on the weakest backend's soundness — but it is explicitly not a repair, and the residual failure class is stated in PRF-14 and L1-13(6). (review round 2, finding E-R2-04: the policy is closed, one route per proof, and the enabling rule of L1-09 is an upgrade. Decision D-13: the object is now an aggregation proof; the closed policy is unchanged — one object, one route — and the aggregation program's own route and image are part of the route inventory this rule leaves Open.) Failure mode: an unstated policy leaves an implementer to decide whether one or two proofs are required, which changes both the security argument and the fleet sizing; an enabling rule any account could exercise would let an attacker install a verifier that returns true (L1-09). Proven Open (open only for the concrete inventory: the deployed, audited (programImageId, verifier, backendFamily) routes and their activation epochs, which MUST contain at least k distinct families with a live accepted route for every epoch or no withdrawal root can form (L1-13(5)). Until at least one such route is registered at activation, no batch can land and settlement cannot start; the inventory is a recorded launch input, not a policy choice — the policy above is not open.)
PRF-14 — backend independence: what k-of-n buys at the withdrawal roots, and its residual (1) The policy is over the same statement, not a second one, and it is a count inside one proof object. The k-of-n requirement of L1-13 applies only to the epoch-boundary checkpoints that finalize withdrawals. It is satisfied by one aggregation proof whose public input attests at least k distinct registered families, every inner proof proving the same accepted statementHash under PRF-02's single journal and the same GEN-05 encoding; the policy adds inner verification and a count, never a statement, a witness rule or a journal field. One family is never a substitute for another inside the count: k distinct bits are required before the checkpoint becomes a withdrawal root, and the settlement path requires one bit (PRF-09, PRF-15). (2) Independence is registered metadata, not an on-chain fact. The unit of independence is the backendFamily tag of L1-09. Two images of the same implementation family count once, however many routes they have. That two tagged families really are independently implemented — separate codebases, separate circuits and separately reviewed — is asserted by the registering upgrade and audited at migration under A-GOV-1; it cannot be derived from a program image id or a verifier address, and no artifact may claim the tag is cryptographically enforced. (3) What it buys. For the withdrawal path it replaces "the proof system is as sound as the weakest accepted backend" with "a false withdrawal root requires inner proofs from k independently implemented backends to all accept a false statement, or a defect in the aggregation program itself, or a defect common to all of them". A backend-specific soundness bug — a circuit defect, a syscall or accelerator-constraint defect, a verifier-contract defect, a backend-specific witness bug — is not reproduced under the other k−1 families, so the root is not designated. (4) What it does not buy, stated rather than implied. (a) Common-mode defects are not covered. The statement, the guest logic, the payload framing, the L1 derivations and this specification are shared by every backend; a defect there is reproduced by all k implementations and the policy adds nothing. Two backends implementing one specification are not two independent designs, and no rule may present k-of-n as protection against a faulty guest or a faulty specification. (b) Settlement is not covered. Non-boundary batches are still accepted on one proof (PRF-09), so one unsound backend can still land a forged ordinary checkpoint. (c) The residual is a stop, not a theft. A forged checkpoint — one whose record disagrees with the real L2 chain at that height, in its stateRoot or in its blockHash — cannot be honestly extended: PRF-06 requires every executed block's resulting state commitment to equal that block's own header root, and the header chain links to the predecessor's block hash, so no honest batch can be landed above the forged record and settlement stops there. Recovery cannot clear that stop, because the forged record is the latest accepted checkpoint (REC-01). (d) The exit path inherits a dependency. Withdrawals then require k families to be available and funded so that the aggregation proof can be produced; the liveness consequences are stated in L1-13(5) and are not repaired by this rule. (e) The aggregation program is a single point of trust, and it is the newest one. Every inner verification happens inside one program (PRF-15); the L1 count checks how many families the object claims, not that the claim is true, so a defect or a malicious image in the aggregation program reproduces across every family and every purpose at once — it is a common-mode component by construction, deliberately introduced to buy L1 cost and multi-family settlement. Its rotation is therefore a trust event, not routine maintenance, and the residual is stated rather than hidden. (decision D-13: the honest limits PRF-14 records are kept, and the aggregation program's trust is added to them.) Premises of (3) and (4c)–(4e): the collision resistance of the state commitment, the determinism of execution, the honest registration of family tags (A-GOV-1), the honest implementation and review of the aggregation program's image, and k distinct audited implementations actually existing at activation. (5) Affordability gate, with the aggregation line. k and n are fixed by S1's measured proving cost, not here, and the S1 gate MUST carry the aggregation line decision D-13 names: verifying inner proofs inside the aggregation circuit is the dominant new term, so the measurement MUST report the cost of an aggregation over m inner proofs before N_PROOF_BACKENDS and M_AGG_MAX are fixed (PRF-15(6)). If S1 reports the aggregation cost of L1-13(4) as unaffordable, the requirement MUST be withdrawn by a recorded change order that also discloses in LIM-01 that withdrawal soundness is single-backend and relies on the veto of MSG-04 plus disclosure. k = 1 MUST NOT be shipped as if it were k-of-n, and until k distinct families are registered and operating, no artifact may claim the property of (3). Failure mode: the design accepts one proof from any one registered backend, so the whole withdrawal path inherits the weakest backend's soundness, while the multi-proof composition and every pause lever the baseline had are removed. k-of-n at the withdrawal roots answers the backend-specific half of that; treating it as a general repair, or letting a common-mode defect pass unmentioned, would answer the other half with an overclaim. Proven Assumed unmeasured Open (the argument is conditional on k independently implemented, audited families existing, on A-GOV-1 for the family tags, on the honest aggregation image of (4)(e), and on S1's proving-cost numbers — now including the aggregation line — for affordability; the route and image inventory and the attestation incentive are Open)
PRF-10 — program-image, verifier and version upgrades The guest program identity (image id / verification key) is bound by the verifier contract, not by the prover. An upgrade adds a new accepted identity; it must not remove the ability to accept proofs for batches whose head block was finalized under the previous identity (MIG-05, GOV-03). The Inbox may stop accepting an identity only after finality of — or a published deadline past — all batches that require it, and must never accept a withdrawn identity for new batches. Removing an accepted identity is a governance upgrade and is treated as malicious governance (GOV-02). The aggregation program's image is one of these images, and its rotation is the most consequential one. Under decision D-13 every accepted proof object is verified through the aggregation route, so its image is a registered, rotatable image like any other (L1-09, PRF-15(6)): an upgrade MUST install a new aggregation image by the same rule-change procedure, the new image MUST accept every statementHash the previous image accepted for a range that is still unsettleable, and no rotation may strand a landed-but-unattested boundary checkpoint of L1-13. Its rotation path MUST be bounded — a recorded procedure with a fixed maximum delay, not a DAO-cycle-slow process — because a defective aggregation image is the one component whose failure reproduces across every backend and both purposes (PRF-14(4)(e)). The bound is T_AGG_ROTATE_MAX, registered in PARAM-01 and unmeasured; the path itself is a rule change, never a runtime call. (decision D-13: the aggregation program is itself a registered, rotatable image; its rotation path matters more, not less, and must be bounded rather than DAO-cycle-slow.) Failure modes addressed: a verifier left accepting a superseded vulnerable identity; a proof generated under an old identity becoming unusable after an upgrade, which would strand an unsettled batch and halt settlement until the batch is re-proven or the permissionless, bonded recovery of REC-02 takes effect. (user decision D-7: Mode B selected — a stall above the last accepted checkpoint is resolved by resumed proving or by recovery, never by a privileged shortcut.) Assumed Open (the migration discipline is normative; its operational correctness is an implementation gate, and the aggregation image's rotation bound is an owed parameter — decision D-13)
PRF-11 — syscall, hint and accelerator trust model Nothing computed by the host is trusted. Values entering the guest through host reads, hints or unconstrained regions are unverified assertions at the point they enter, and each must be constrained before use or verified by an explicit check. Accelerated primitives are trusted only to the extent the proof system's circuits constrain their input–output relation; the implementer must record for each primitive used (a) whether the backend documents it as circuit-accelerated or as guest software and (b) which constraint system enforces it. The guest must not treat a recovered public key, a decompressed point, or a claimed set membership as verified unless the corresponding relation is checked. Point validity, canonical field elements and the edge cases required by each backend's documented usage constraints are part of the trusted code base and must be checked explicitly. Failure modes addressed: the host-controlled-input class of vulnerabilities (including published advisories against both backends) and backend-specific precompile traps, such as non-canonical field elements yielding unverifiable proofs, on-curve validity not being enforced by the precompile, and points at infinity being unsupported. Proven (sourced constraints in 03)
PRF-12 — recursion and aggregation: what it does and does not prove Aggregation is now the accepted proof object, not an optional wrapper. Under decision D-13 the one proof the protocol accepts on each path is an n-of-m aggregation proof (PRF-15): each inner proof proves the same PRF-02 journal, the aggregation program verifies every inner proof against the verification algorithm its registered route names, and the outer public input exposes the contributing family set. Aggregating several batches into one recursive proof remains a cost/latency optimisation only under the earlier constraint: the program must hard-code the accepted inner program identities and expose in its own journal the set of (predecessor, successor, data commitment) triples it verified, and the aggregated proof must fail to verify if any inner journal is inconsistent with the outer claim. The protocol does not require multi-family aggregation to settle — an aggregation attesting one family is the degenerate case and satisfies settlement's count of one — but it does require the aggregation program on every accepted path, so that program is in the trusted computing base by construction, and the correctness of its inner-verification membership check is the property this rule names. Failure mode: an aggregation layer whose membership check is asserted rather than enforced turns many valid proofs into one arbitrary claim — the same class of recursion-circuit defect that a published advisory against one backend concerned. Assumed Open (the design constraint is stated; the in-guest cost of aggregation is unmeasured, the aggregation program's honesty is the trust of PRF-14(4)(e), and the program's own image and rotation are PRF-15(6)'s — decision D-13)
PRF-15 — one proof object, n-of-m aggregated underneath (1) The object. The protocol accepts exactly one proof object per purpose: for settlement (PRF-09) and for the withdrawal-root attestation of L1-13. That object is an n-of-m aggregation proof: L1 verifies it through exactly one registered route — the aggregation route of L1-09 — and its public input exposes the set of registered backend families whose inner proofs the program verified. A "plain" single-backend proof is the degenerate n = K_SETTLE_BACKENDS aggregation; the accepted object is still the aggregation program's proof, and L1 verification cost stays one verification. (decision D-13: one proof object per batch, n-of-m aggregated underneath; the protocol treats it as a single proof.) (2) The inner statement is unchanged. Every inner proof proves the same PRF-02 journal under the same GEN-05 encoding, identified by one statementHash. An inner proof for a different journal, range, predecessor, data commitment, epoch or set root is not part of the object, and an object whose inner statements are not all that one journal MUST fail to verify. Aggregation adds no field to the journal and does not weaken PRF-01. (3) The aggregation public input. The object's public input MUST be canonically encoded per GEN-05 and MUST include at least: the domain tag and the chain ids; statementHash, the single accepted statement; routeSetHash, a commitment to the ordered registered route set the program verified against (the Inbox recomputes it from its own registry for the batch's epoch and requires equality, L1-14); and familyBitmap, the canonical bitmap over the Inbox's append-only family index whose set bits name the families whose inner proofs the program verified. The bitmap's length is fixed by the registry, bits outside the families live for the epoch MUST be zero, and the count is derived by L1, never taken from the caller. (decision D-13: the aggregation proof's public input exposes the set of contributing backend families, as a bitmap over the registered families.) (4) What the aggregation program MUST do. For each inner proof the program MUST verify it against the verification algorithm of that route's registered verifier and registered program image — never against a witness-supplied verifier, image id or verification key, and never against a route outside routeSetHash. It MUST set a family bit if and only if at least one inner proof under a route of that family verified successfully against the same statementHash: the bitmap is an output of the program's verification logic, not an unconstrained input, and the code MUST be written so that this is a structural property rather than a checked assertion. It MUST NOT be able to claim a family it did not verify. (decision D-13: the program must verify each inner proof against its registered verifier and must not be able to claim a family it did not verify; the L1 count check exists because the program is trusted, not because it is assumed honest.) (5) What L1 enforces, and what it cannot. The Inbox MUST enforce the required distinct-family count per purpose over the bitmap, intersected with the families that have a live registered route for the batch's epoch: at least K_SETTLE_BACKENDS (= 1) for settlement, at least K_PROOF_BACKENDS for a withdrawal root (L1-13, L1-14). The aggregation route's own family tag is reserved and MUST NOT be counted. L1 cannot verify the bitmap's truthfulness — only the program can — so the count check bounds the object's claim, and the trust in the claim is the trust in the image (PRF-14(4)(e)). (6) Registration, rotation and cost. The aggregation program is itself a registered, rotatable image under L1-09 and PRF-10; its rotation path MUST be bounded — a recorded procedure with a maximum delay, not a DAO-cycle-slow process — because every accepted proof passes through it. Verifying inner proofs inside the aggregation circuit is expensive: N_PROOF_BACKENDS, the inner count bounded by M_AGG_MAX, and the aggregation work's funding share AGG_PROVER_PPM (registered in PARAM-01; any funding rule for it is ECON-02's, owned elsewhere) MUST be fixed by S1's measured aggregation cost, and the S1 gate MUST carry an aggregation line (PRF-14(5)). (decision D-13: the aggregation program is a single point of trust whose rotation matters more, not less — its rotation bound is T_AGG_ROTATE_MAX — and the cost moves to the prover.) Failure mode: an aggregation layer whose family claim is an unconstrained input turns many unverified inner statements into one accepted count; and a single defective aggregation image becomes the cheapest way to forge every checkpoint and every withdrawal root at once, which is why the image is registered and rotatable, the count is derived on L1, and the residual is stated rather than hidden. Proven Assumed unmeasured Open (the object, its public input and the per-purpose counts are specified; the program's honesty is the trust assumption of PRF-14(4)(e), n and m and the aggregation cost are unmeasured, the rotation bound is an owed parameter, and the concrete route and image inventory is the Open item of PRF-09/L1-09)
