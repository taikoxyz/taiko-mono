05 — Proof statement: what the ZK proof establishes, and what it does not

A ZK proof does not establish that no hidden competing chain exists. It establishes that the evidence presented is sufficient, under the stated consensus assumptions, for the claimed transition from an authenticated predecessor to a claimed successor. If at least one third of the epoch's voting power violates A-CONS-1, two conflicting certificates can both be cryptographically valid and both can produce accepting proofs. ZK verification does not repair failed consensus assumptions.

PRF-01 — statement overview: one combined guest A single guest program proves the conjunction of two claims for one batch: (W1) consensus finality — that the batch's head block carries a valid commit certificate over (chain id, epoch, height, round, block id) signed by more than two thirds of the voting power of the epoch's validator set, where that set is authenticated from L1 state, and that every epoch boundary crossed by the batch is accompanied by an authenticated set transition; and (W2) execution — that executing the batch's blocks, in the order fixed by the consensus chain, from the predecessor state root yields the claimed successor state root. The guest also proves (W3) data binding — that the data it executed is the data the accepting L1 transaction publishes (see PRF-07). Acceptance requires all three. Failure mode if split: a proof that a block was finalized without proving what it executed (or vice versa) admits a batch whose state transition was never agreed, or a state transition over data that was never certified. Proven (argument; premises listed per rule)

Public inputs

PRF-02 — public inputs (exact list, order is normative) The guest commits to exactly the following journal, encoded canonically per GEN-05. The L1 verifier contract does not accept a caller-supplied journal: for every field marked L1 it derives the value itself from L1 state or from the transaction, and it recomputes the Fiat–Shamir challenge rather than trusting the prover's value. 
Journal {
  bytes32 domain;            // "ETNA_JOURNAL_V1" right-padded ASCII    (L1: constant)
  uint256 l1ChainId;         //                                        (L1: block.chainid)
  uint256 l2ChainId;         //                                        (L1: config)
  uint64  prevHeight;        // predecessor checkpoint height          (L1: Inbox storage)
  bytes32 prevBlockHash;     // predecessor L2 block hash              (L1: Inbox storage)
  bytes32 prevStateRoot;     // predecessor L2 state root              (L1: Inbox storage)
  uint64  epoch;             // epoch of the head block                (L1: checked vs schedule)
  bytes32 validatorSetRoot;  // canonical set commitment for that epoch(L1: staking contract)
  uint256 totalVotingPower;  // sum of effective stake in that set     (L1: staking contract)
  uint256 quorumThreshold;   // strict two-thirds threshold            (L1: recomputed)
  bytes32 configHash;        // consensus-relevant config commitment   (L1: Inbox storage)
  uint64  firstHeight;       // first L2 height in the batch           (L1: checked)
  uint64  lastHeight;        // head height                            (L1: checked)
  bytes32 headBlockHash;     // head block hash                        (L1: checked vs chain)
  bytes32 postStateRoot;     // successor state root                   (L1: new checkpoint value)
  bytes32 dataCommitment;    // keccak256 of the canonical batch data  (L1/D5 binding, DA-01..DA-03)
  bytes32 blobHashesHash;    // keccak256 of ordered versioned hashes  (L1: from BLOBHASH)
  bytes32 challengeZ;        // Fiat-Shamir point over all other fields(L1: recomputed; must match)
  bytes32[] evaluationsY;    // one polynomial evaluation per blob     (L1: passed to precompile)
}
Failure mode if any field were caller-supplied: a prover could assert its own validator set, quorum threshold or predecessor, and the proof would be sound but meaningless. This is the highest-risk integration point identified in the zkVM research (03). Proven (conditional on the L1 derivations being implemented as stated)
PRF-03 — private witness; the validator set is never prover-defined The witness contains, and the guest fully constrains, at least: (a) the epoch's validator entries — each a (public key, effective stake) pair — with Merkle inclusion and ordering proofs against validatorSetRoot; (b) the head block's commit evidence — per-signer signatures, the signer bitmap, and the canonical vote bytes each signature covers; (c) the header chain from prevHeight + 1 to lastHeight, including each header's validators_hash and next_validators_hash; (d) for every epoch boundary crossed, the transition evidence required by PRF-05; (e) the batch's transaction data and the pre-state witness needed for execution; (f) the blob field elements used by PRF-07. No witness element may define the authoritative validator set. A set is accepted only if its recomputed commitment equals validatorSetRoot, and that root comes from L1 state, never from the proof payload. Failure mode: a prover supplies a set it controls together with matching signatures, and the proof "verifies" a finality claim about a chain no independent validator ever saw. Proven (premise: the PRF-02 L1 derivations)

What the guest checks

PRF-04 — consensus-evidence checks For the head block's commit certificate the guest checks, in this order: (i) every signature verifies under the corresponding public key from the authenticated set, over the canonical vote bytes for (domain tag, l2ChainId, epoch, height, round, block id); (ii) signers are distinct — the bitmap has exactly one bit per distinct signer and no bit outside the set; (iii) the sum of the effective stake of the signers, computed from the authenticated entries, is strictly greater than quorumThreshold, where the threshold is the minimal integer q with 3q > 2 · totalVotingPower, computed with the same rounding rule as the L1 contract so that no guest/contract mismatch is possible; (iv) totalVotingPower equals the sum of the authenticated entries' effective stakes; (v) the head block hash equals the hash of the reconstructed head header, and the header chain links back to prevBlockHash by parent hash with no gaps. Failure modes addressed: double counting a signer, counting stake twice, a rounding discrepancy between guest and contract, and a certificate over a block that is not the one whose header chain was executed. Proven
PRF-05 — epoch and set-transition checks For every epoch boundary inside the batch the guest checks that: (i) the last header of the closing epoch commits, in next_validators_hash, to the commitment of the opening epoch's set, encoded per CONS-10; (ii) the first block of the new epoch commits, in its consensus evidence, to the last block finalized in the previous epoch (CONS-09); (iii) each epoch's set commitment equals the value the L1 staking contract fixes for that epoch, supplied as a public input rather than as a witness; (iv) epoch numbers are strictly increasing across the batch. A batch that spans a boundary must carry the transition evidence; transitions may not be skipped. Failure modes addressed: set substitution at a boundary, a fork created by switching sets at different heights on different branches, and a prover choosing an "easy" set. Proven (the lock carry-over premise is CONS-09, marked Assumed-with-argument)
PRF-06 — execution checks The guest executes every block in the range in consensus order, starting from prevStateRoot, applies each block's transactions under the L2 execution rules, and checks that each resulting state commitment equals the state root committed by that block's header; the final state commitment must equal postStateRoot. The state commitment function is Ethereum-compatible (Merkle–Patricia root over the account and storage tries), because the design preserves type-1 execution semantics; substituting a different commitment scheme is a normative change and not an implementation choice. Failure modes addressed: skipping blocks, reordering blocks, executing against a different pre-state, and a state-root scheme the bridge cannot verify. Proven (premise: the L2 execution rules are fixed by the preserved EVM semantics)
PRF-07 — data-commitment binding for both data paths Exactly one of the following holds, and the journal records which. (a) Calldata path. The L1 contract hashes the exact calldata slice carrying the batch data and requires dataCommitment to equal that hash; the guest independently recomputes the same hash over the data it executed and requires equality. Both sides hash the same bytes, so no probabilistic argument is needed. (b) Blob path. (i) For each index i, the contract requires blobhash(i) in this transaction to be non-zero and to equal the i-th versioned hash committed by the proof. (ii) The contract recomputes challengeZ = H(all other journal fields) and requires the proof's challengeZ to match, so the prover cannot choose the point after fixing its data. (iii) For each blob the contract calls the EIP-4844 point-evaluation precompile at 0x0A with (versionedHash_i, z, y_i, commitment_i, proof_i), which verifies both kzg_to_versioned_hash(commitment_i) == versionedHash_i and the KZG opening p(z) = y_i; the call costs 50,000 gas sourced (EIP-4844). (iv) The guest computes, from the blob field elements it actually executed, the evaluation p'(z) of the polynomial those elements interpolate, and requires p'(z) == y_i for every blob. (v) The guest also requires keccak256(executed data) == dataCommitment as in (a). Why (b) is sound: the published blob is fixed by the protocol's KZG commitment before the prover fixes z, because z is derived by the contract from the prover's own committed values. If the executed data and the published blob differ as polynomials, their evaluations agree at z with probability at most deg/|F| (about 2-243) per attempt, and each attempt requires a fresh commitment. Premises: KZG binding, the random-oracle model for the Fiat–Shamir derivation, canonical field elements, and correct in-guest field arithmetic. If any premise fails the blob path is unsound, which is why the calldata path remains unconditionally available. Proven unmeasured (in-guest cost of the evaluation is not measured; see 03)
PRF-08 — why one certificate per batch suffices, and its premises The guest verifies the commit certificate of the head block only. Every other block in the batch is covered by the header hash chain back to prevBlockHash, which the contract has already accepted as a finalized checkpoint. No ancestor certificate is verified on-chain or in-guest. Argument: under CONS-05 a validator precommits a block only after validating it and its parent relation, and a certificate requires more than two thirds of voting power, so at least one third of the voting power is correct and locked. A certificate for the head therefore implies the head is the unique finalized block at its height, hence that the entire prefix it commits to is the unique finalized prefix. Premises: fewer than one third of the epoch's voting power is Byzantine (A-CONS-1); correct validators obey CONS-02 and CONS-04; the set is L1-authenticated. If a premise fails the argument fails with it, and the proof does not detect that. Proven Assumed (premises named above; this is the reasoning a light client uses)
PRF-13 — bindings must be cryptographically enforced, never asserted Any value a prover could otherwise choose freely — the validator set, the quorum threshold, the predecessor, the data commitment, the challenge point, the configuration hash and the program identity — must be derived by the L1 contract itself, or recomputed inside the guest from a value the contract derived, or checked by an L1 precompile. A binding that consists only of "the caller passed it" is not a binding and must not appear in this specification. Failure mode: a proof that is sound in isolation but whose public inputs are attacker-chosen — the standard way ZK-rollup integrations fail. Proven

Backends and lifecycle

PRF-09 — both backends realise the same statement; acceptance policy RISC Zero and SP1 must both implement this statement with a byte-identical journal, so that a batch's proof is portable between backends. The Inbox accepts a proof from any registered verifier whose program-image identity is on the accepted list for the epoch's configuration. Acceptance policy: the protocol chooses between (a) any single accepted backend, and (b) two independent backends for every batch. Policy (a) is the default because two proofs per batch double the proving fleet requirement under HALT-03; policy (b) must be adopted if the measured soundness posture of either backend is unacceptable. Either way a soundness bug in an accepted backend is a bridge-theft-class failure not repairable by the protocol. Failure mode: an unstated policy leaves an implementer to decide whether one or two proofs are required, which changes both the security argument and the fleet sizing. Open (resolved by the launch decision; both branches' consequences are stated)
PRF-10 — program-image, verifier and version upgrades The guest program identity (image id / verification key) is bound by the verifier contract, not by the prover. An upgrade adds a new accepted identity; it must not remove the ability to accept proofs for batches whose head block was finalized under the previous identity (MIG-05, GOV-03). The Inbox may stop accepting an identity only after finality of — or a published deadline past — all batches that require it, and must never accept a withdrawn identity for new batches. Removing an accepted identity is a governance upgrade and is treated as malicious governance (GOV-02). Failure modes addressed: a verifier left accepting a superseded vulnerable identity; a proof generated under an old identity becoming unusable after an upgrade, which would strand an unsettled batch and — under Mode A — halt settlement. Assumed (the migration discipline is normative; its operational correctness is an implementation gate)
PRF-11 — syscall, hint and accelerator trust model Nothing computed by the host is trusted. Values entering the guest through host reads, hints or unconstrained regions are unverified assertions at the point they enter, and each must be constrained before use or verified by an explicit check. Accelerated primitives are trusted only to the extent the proof system's circuits constrain their input–output relation; the implementer must record for each primitive used (a) whether the backend documents it as circuit-accelerated or as guest software and (b) which constraint system enforces it. The guest must not treat a recovered public key, a decompressed point, or a claimed set membership as verified unless the corresponding relation is checked. Point validity, canonical field elements and the edge cases required by each backend's documented usage constraints are part of the trusted code base and must be checked explicitly. Failure modes addressed: the host-controlled-input class of vulnerabilities (including published advisories against both backends) and backend-specific precompile traps, such as non-canonical field elements yielding unverifiable proofs, on-curve validity not being enforced by the precompile, and points at infinity being unsupported. Proven (sourced constraints in 03)
PRF-12 — recursion and aggregation: what it does and does not prove Proofs for several batches may be aggregated into one recursive proof before submission only if the aggregation program hard-codes the accepted inner program identities and exposes in its own journal the set of (predecessor, successor, data commitment) triples it verified. Aggregation is a cost/latency optimisation: it changes nothing about the statement, and an aggregated proof must fail to verify if any inner journal is inconsistent with the outer claim. The protocol must also be able to operate without aggregation, one proof per batch, because aggregation adds a recursion program to the trusted computing base. Failure mode: an aggregation layer whose membership check is asserted rather than enforced turns many valid proofs into one arbitrary claim — the same class of recursion-circuit defect that a published advisory against one backend concerned. Assumed (design constraint stated; in-guest cost of aggregation is unmeasured)
