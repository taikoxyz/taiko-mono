Etna PoS + ZK — reference specification

Verdict (Phase 3, 2026-10-05; guarantee class revised by change order 04, decision D-15 and decision D-16): a permissionless, TAIKO-staked L2 PoS consensus (Tendermint/CometBFT-class, single-slot finality) combined with ZK proofs of consensus finality and EVM execution can satisfy the requirements in 01-requirements-and-threat-model.md under the stated assumptions, in Mode B: the certificate and its evidence are unchanged, but a PoS confirmation above the last L1-accepted checkpoint is provisional. Decision D-16 shapes what v1 contains: v1 ships the core — L1-anchored PoS sequencing, validity-proof settlement with the batch data carried or referenced (D-11), the checkpoint boundary, the exit from the last settled state (MEM-15), k-of-n withdrawal roots attested by distinct backend families with the rule-triggered veto, and the signed recovery generation — and four mechanisms are deferred to a register: narrow forced inclusion (D-12), heartbeat eligibility (D-14), the governance stall resolution (D-15) and aggregation (D-13) (DEFERRED.md). Consequently v1 has no recovery path of any kind: a settlement stall halts the chain; funds are safe, the boundary holds and the exit works, but clearing the stall requires a future protocol update whose procedure is not yet specified. At or below the last L1-accepted checkpoint no timeout, rotation, admission rule or published upgrade may change history. This is a specification-level verdict: nothing here is implemented, benchmarked or deployed. (decision D-16: v1 is the core plus the deferred register; no recovery path exists, and no interface may present a stalled chain as resumable by a v1 rule.)

This is a PoS-sequenced validity rollup. Transaction order is determined by L2 PoS, not by Ethereum proposers. Ethereum provides data availability, proof verification, settlement, and bridge anchoring. It does not sequence L2 blocks.

Status labels are normative. Every deliverable — specification, learning site, user interface text — must use the exact labels of STATUS-01–STATUS-11. No stronger word ("final", "irreversible", "confirmed") may be substituted for a weaker status. Above the last L1-accepted checkpoint no confirmation is stronger than PoS-certified / provisional, and any interface that shows one must say that it is provisional and that v1 provides no in-protocol path that replaces it (STATUS-11); no interface may promise that a stalled chain resumes, because v1 has no recovery path of any kind and clearing a settlement stall requires a future protocol update whose procedure is not yet specified (DEFERRED.md §3). (decision D-16: the timelocked, resume-only stall resolution of D-15 is deferred, and no artifact may present a stalled chain as resumable by a v1 rule.)

General rules

GEN-01 — what this document is This specification defines a protocol design. It contains no implementation, no deployment, and no measurement. No claim in any deliverable may describe a proposed parameter as a measured result, and no performance number may appear without a source or an explicit unmeasured tag. Failure mode: an unaudited design is mistaken for a working system; reviewers and users cannot tell which claims are evidence-backed. Proven derived
GEN-02 — fixed decisions bind the design D1–D7 are constraints. A design element that conflicts with one of them is a defect, not a tradeoff. Changing one requires a new user decision recorded in the decision log. Failure mode: silent relaxation of D5 or D7, which the user expressly forbade. A recorded project decision may relax or supersede a fixed decision only where the decision log records it and names what survives: D-11 relaxes D5 (data may be published before the proof; the checkpoint still advances only on a valid proof), D-15 supersedes D-7 (the permissionless bonded recovery is withdrawn; the boundary of REC-01 is kept) and D-16 supersedes the D-12/D-13/D-14/D-15 additions (narrow forced inclusion, aggregation, heartbeat eligibility and the governance stall resolution are deferred to DEFERRED.md; v1 ships the core only and has no recovery path of any kind). Any other change to D1–D7 is a defect. (D-11, D-15, D-16: the recorded relaxations and supersessions are named here so that GEN-02 and the decision log cannot diverge.) Proven
GEN-03 — one rule, one place, stable identifiers Every normative rule has exactly one stable identifier of the form PREFIX-NN, is stated in full on exactly one page, and is referenced elsewhere by link. Identifiers are never reused or renumbered; gaps are permitted. Failure mode: divergent copies of a rule; an implementer cannot tell which version is normative. Proven
GEN-04 — evidence tags Every rule carries Proven (argument with named premises), Assumed (justification plus the consequence of failure), or Open (the evidence that would close it). Every number carries derived, sourced, or unmeasured. Failure mode: assumptions are read as guarantees; unmeasured numbers are read as benchmarks. Proven
GEN-05 — hashing and domain separation Every protocol hash is keccak256 over a single canonical abi.encode of typed fields, never abi.encodePacked and never a bare concatenation, with a right-padded ASCII domain tag and the chain id as the first two fields. Every signed message carries its own domain tag; a signature is invalid outside its domain. Failure mode: cross-domain replay; second-preimage style ambiguity between concatenated fields. Proven (reused from prior Etna C8-R02/R03 and verified as a sound convention)
GEN-06 — time, and the ban on L1 lookahead All timing parameters are expressed in seconds or L1 block numbers. Consensus rounds, epoch numbers and validator-set versions are logical identifiers. No normative rule may depend on Ethereum proposer lookahead, on a fixed L1 slot duration, or on reading a wall clock during validation; wall clocks may only pace local signing and timeout actions. Failure mode: the protocol breaks when Ethereum changes its slot timing, or an implementer invents a timing rule the specification never fixed (R12). Proven
GEN-07 — controlled vocabulary Status labels are fixed by STATUS-01–STATUS-11; other terms are fixed by the glossary in 09. A document may not introduce a synonym for a status label or redefine a glossary term locally. Failure mode: the same word means different guarantees in different deliverables. Proven
GEN-08 — evidence categories for feasibility claims Every feasibility claim is classified as exactly one of: (1) compatibility in principle, (2) evidence from an existing implementation or published benchmark — with version, hardware, workload and methodology — (3) an analytical estimate, or (4) an unmeasured implementation question. Categories are never merged, and category (2) claims must state whether the measurement transfers to this workload. Failure mode: a benchmark for a different workload is presented as evidence for this one. Proven
GEN-09 — honest naming of the architecture The design is described as a PoS-sequenced validity rollup. The term based rollup must not be used for it, and no deliverable may imply that Ethereum proposers determine L2 transaction order. Failure mode: users infer an L1-sequencing guarantee the design does not provide (D4). Proven

Status labels

Each label below is normative: it fixes the evidence a participant must hold, the guarantee a user may rely on, the conditions that can revoke it, and who can observe it.

STATUS-01 — proposed A block body received from a leader. Evidence: the object itself. Guarantee: none — it may be invalid. Revocable: discarded freely. Visible to: whoever received it. Treating a received proposal as progress is the origin of most "we saw it first" disputes.Proven
STATUS-02 — locally execution-valid This node executed the block against a known parent state and every consensus and validity rule passed. Guarantee: this node will not build on an invalid block. Revocable: yes, if the parent is displaced. Visible to: this node only. Local validity is not agreement and not availability (STATUS-09).Proven
STATUS-03 — voted A validator signed a vote for this block at a given (height, round). Guarantee: the vote irreversibly constrains that validator's future votes through the lock rule (CONS-04). Revocable: never — a vote is a signed commitment; signing a conflicting vote is slashable equivocation (CONS-11). Votes are the only irreversible act a validator performs; everything else can be retried.Proven
STATUS-04 — PoS-certified / provisional A published commit certificate over (chain id, epoch, height, block hash) carrying signed voting power s that satisfies the predicate 3 * s > 2 * W (checked arithmetic, with W the epoch's total voting power; the L2 client, the zkVM guest and the L1 contract evaluate it identically, and a strict/non-strict mismatch would split chain acceptance from L1 acceptance), plus the receiver's own data-availability check for the block body. The certificate and its evidence are unchanged in every mode; the guarantee is that the block is certified by more than two thirds of the epoch's voting power under the published consensus rules, and that — above the last L1-accepted checkpoint — it is provisional: v1 provides no in-protocol path that replaces it (decision D-16 defers every replacement mechanism), the design does not promise that it is irreversible, and the deferred register records the replacement mechanisms and their unresolved findings (DEFERRED.md). History at or below the latest L1-accepted checkpoint is never replaced by any path (REC-01), and a settlement stall halts the chain rather than resolving it. For history at or below an Ethereum-finalized checkpoint even an L1 reorganisation cannot change it (STATUS-07). No timeout, rotation, admission rule, published upgrade or operator action may replace history at any height; v1 has no recovery path of any kind, and clearing a settlement stall requires a future protocol update whose procedure is not yet specified. This status is never the first status a user may rely on as irreversible: STATUS-06 and above are. No artifact may call a confirmation at this status "final", "settled" or "irreversible", and every interface that shows a confirmation above the last L1-accepted checkpoint must disclose that it is provisional and that v1 provides no in-protocol path that replaces it (STATUS-11). Failure mode: the certificate is the same evidence in every mode, so a reader assumes the guarantee is the same. Above the checkpoint it is not: a user who treats the confirmation as settled can lose the outcome it describes, and in v1 no protocol action settles or replaces it either. At or below the latest L1-accepted checkpoint the same label is backed by the rule that no path may change that history (REC-01), and at or below an Ethereum-finalized checkpoint even an L1 reorganisation cannot change it (STATUS-07). Proven (conditional on INV-01's premises) (decision D-16: the certificate and its evidence are unchanged; the guarantee above the checkpoint is provisional, v1 provides no replacement path, and clearing a settlement stall requires a future protocol update whose procedure is not yet specified)
STATUS-05 — proof-ready A completed ZK proof bound to this batch's data commitment exists off-chain. Guarantee: the batch can be landed. Revocable: a proof of a different batch is not a substitute; a better proof of the same data commitment may replace it. Separating "a proof exists" from "the batch is settled" prevents premature withdrawal.Proven
STATUS-06 — accepted on L1 The Inbox accepted (data, proof) in one transaction and advanced its checkpoint (L1-01). Guarantee: the batch's data is public on Ethereum and the transition is L1-committed. Revocable: only by an L1 reorganisation below finality. This is the first status a user may rely on as irreversible: no L2 rule can revoke an accepted batch, and the only revocation is an L1 reorganisation below finality. It is the status that unlocks bridge withdrawals and message authentication. (decision D-16: STATUS-04 is provisional above the checkpoint; STATUS-06 and above are the first irreversible statuses, and nothing at or below an accepted batch may be touched by any path — the deferred stall resolution is not implemented.)Proven
STATUS-07 — Ethereum-finalized The accepting L1 transaction is in a finalized Ethereum block, or the L1 fact the claim depends on is at the configured Ethereum finality depth (SYS-02). L2 state may only depend on L1 facts that can no longer be reorganised; otherwise a PoS-finalized L2 block can become unprovable. Proven
STATUS-08 — withdrawal-eligible Status STATUS-06 or STATUS-07, a withdrawal root at a height not below the signal's height — an epoch-boundary checkpoint carrying attestations from at least K_PROOF_BACKENDS distinct registered backend families, verified on L1 (L1-13) — the message-authentication path, the delay required by MSG-03 measured from the root's l1BlockNumber, and the absence of an unexpired withdrawal veto; an ordinary checkpoint that is not a withdrawal root MUST NOT anchor a value release, and a veto delays but never cancels an already-proven withdrawal (MSG-04). Withdrawal availability is strictly later than L1 acceptance; without aggregation (deferred by D-16) the root costs k verifications on L1 rather than one, and the two user-visible delays (up to one epoch plus the slowest attestation, and up to T_VETO) are disclosed rather than hidden. (decision D-16: aggregation is deferred, so the root is k attestations from k distinct families verified on L1; MSG-04's veto is a bounded delay, not a pause lever.) Proven
STATUS-09 — local receipt is not availability A node that holds a block may not treat its own possession as evidence that the data is available to others, and may not report a status above STATUS-03 to another party on the basis of local possession alone. Failure mode: users infer retrievability from a peer's claim; the certified-but-unavailable class of failures becomes invisible until a halt. Proven
STATUS-10 — an elapsed timeout is never evidence of absence No rule may conclude that a certificate, proof, or block does not exist because a timeout elapsed. Timeouts trigger local actions (view change, retry, halt), never an assertion about what exists elsewhere, and never an invalidation (HALT-01). Failure mode: a withheld-then-revealed certificate would invalidate a decision taken on the strength of a timeout. Proven
STATUS-11 — label disclosure obligation Any interface, document or learning page that shows a progress indicator must use these labels and must state which status is being shown. A "confirmation" shown to a user before STATUS-06 must be accompanied by the statement that the batch's data and proof are not yet on Ethereum. In addition, any interface that shows a confirmation above the last L1-accepted checkpoint must say that it is provisional and that v1 provides no in-protocol path that replaces it: the statement must not present the confirmation as final, settled or irreversible, and must not promise that a stalled chain resumes, because v1 has no recovery path of any kind and clearing a settlement stall requires a future protocol update whose procedure is not yet specified (D-16; DEFERRED.md §3); a status indicator that shows only "confirmed" without the provisional disclosure violates this rule. The protocol MUST expose, as public facts an interface can read: (i) the height of the latest L1-accepted checkpoint — the Inbox's current pointer lastLandedHeight and its record, not an Ethereum-final view (L1-06, L1-07); (ii) whether the chain is currently halted for backpressure, which validators enforce and the consensus client exposes because no L1 contract can enforce the cap (HALT-03, LIVE-02); and (iii) whether a withdrawal root exists for a height and, while a withdrawal veto is active, the timestamp at which it ends (L1-13, MSG-04), because an interface that shows a withdrawal must state the two additional delays of STATUS-08 and must not present a proven withdrawal as executable while an unexpired veto stands. (D-13: the root and its family count are public facts; the aggregation that would have reduced the verification count to one is deferred by D-16, and MSG-04's veto is public and self-expiring, so an interface can state exactly when it ends.) An interface MUST NOT present a confirmation above the latest L1-accepted checkpoint as final, and MUST NOT promise that a stalled chain resumes. This closes review round 4 findings R4-LIV-10 and STATUS-11: the boundary and the backpressure halt are readable facts, so an interface can state the provisional guarantee and disclose that no v1 rule resumes a stalled chain (D-16). Failure mode: users treat a 2 s PoS confirmation as settlement (R14, D6 "user expectations"); in v1 the confirmation is provisional and no protocol action settles or replaces it, so disclosure is the only protection the protocol gives a user who acts on a provisional outcome, because losses are not compensated (ECON-11). Proven (decision D-16: a confirmation above the last L1-accepted checkpoint must be disclosed as provisional with no in-protocol replacement path, and no interface may promise that a stalled chain resumes)

Verdict summary and its exact scope

Within scope: a specification-level design in which permissionless TAIKO-staked L2 validators certify blocks every 2 s; batches settle on Ethereum only when a ZK proof of consensus finality and execution lands and advances the checkpoint — the batch's data MAY have been published and recorded in an earlier L1 transaction under D-11, and a publication alone settles nothing — and the protocol verifies one proof from one registered backend per purpose (aggregation is deferred by D-16); the shared SignalService/Bridge/vault addresses are preserved by in-place upgrade; k-of-n withdrawal roots are attested by distinct backend families with the rule-triggered veto; no discretionary path can change history at any height; nothing at or below the latest L1-accepted checkpoint can be changed by any path (at or below an Ethereum-finalized checkpoint even an L1 reorganisation cannot change it, STATUS-07); and above the latest L1-accepted checkpoint a confirmation is provisional, with v1 providing no in-protocol path that replaces it. (decision D-16: v1 is the core plus the deferred register; no recovery path exists, and clearing a settlement stall requires a future protocol update whose procedure is not yet specified.)

Outside scope: that the design is implemented, audited, benchmarked or safe to deploy; that proving throughput or 2 s cadence has been measured; that any attack is unprofitable; that ZK verification repairs failed consensus assumptions; that a PoS confirmation above the last L1-accepted checkpoint is irreversible (it is provisional and v1 provides no path that replaces it); that a settlement stall can be cleared by any v1 rule — it cannot, so a stalled chain may stay halted for an unbounded time and clearing it requires a future protocol update whose procedure is not yet specified (D-16); that forced inclusion, heartbeat eligibility or aggregation exist in v1 (they are deferred); or that any loss a discard causes is compensated.
