04 — L1 integration: atomic data + proof, data availability, forced inclusion, bridge anchoring

This page carries D5 and D8. It fixes how a batch becomes STATUS-06 — accepted on L1: one L1 transaction carrying the batch data and its validity proof, out of which the Inbox itself derives the data commitment, and out of which a single monotone checkpoint advance follows. It also fixes where that data is canonical (DA-01), how the blob path binds data to the proof (DA-03), how forced inclusion works without an override that could violate Mode A (FI-01–FI-05), and how the preserved SignalService/Bridge addresses authenticate against these checkpoints (MSG-01–MSG-03).

Baseline for every comparison to "today" on this page: Taiko monorepo revision 7718753c1 (2026-10-05), file packages/protocol/contracts/layer1/core/impl/Inbox.sol. Nothing on this page is implemented, deployed, audited or measured (GEN-01). Every number is tagged derived / sourced / unmeasured.

Assumption disclosure. Acceptance here is a liveness path guarded by cryptography, not a safety guarantee by itself. Wherever a statement depends on <1/3 Byzantine stake (A-CONS-1) or on the availability assumptions (A-CONS-5, A-DA-2) it says so at the claim (01-requirements-and-threat-model.md §4).

1. One atomic acceptance

L1-01 — single atomic accept entry point; no data-first path The Inbox MUST expose exactly one function that can accept a batch and advance the checkpoint. Its name is land(data, proof) — the batch data first, the validity proof second, one entry point and no other. One call MUST carry, in one L1 transaction: (a) the batch range, given as uint64 firstBlockHeight and uint64 lastBlockHeight of L2 blocks; (b) the batch data, given as the bytes calldata _data argument and/or the blob sidecars of that same transaction; (c) the proof, given as _proof; and (d) the claimed post-state and finality values of L1-05. Data and proof are inseparable: there MUST NOT exist any entry point, overload, fallback, multicall helper, or recovery path that records the data (or a commitment to it) in one transaction and the proof in another. There MUST NOT exist a "propose then prove" path in any mode. Every other artifact that names this entry point — the migration state gate (MIG-03), the parameter register, the glossary and the client interfaces — MUST use the same name land(data, proof): a second name (for example accept(data, proof)) is a defect, because the migration gate and the audited interface would then be specified against a selector that does not exist. (review round 1, finding B R1-16) Failure mode: the batch's data becomes public before any proof exists, so a batch can be published and never proven — the data occupies L1 capacity, consumes the settlement budget, and settles nothing. Allowing it in one mode re-opens D5 for every mode, because the recovery path becomes the cheapest way to publish data. Proven sourced (D5; contrast below)

L1-02 — no entry point records a pending or incomplete batch No entry point of the Inbox — public, external, or reachable through an upgrade initialiser — may write a batch record, a predecessor link, a proposal hash, a data commitment, or a checkpoint pending a proof. The only accepted state that exists for a range is the checkpoint written by a successful land(data, proof) call. An "announce" / "intent" / "commit" function may exist only if all three hold: (i) nothing it writes is read by land(data, proof), by the verifier route, or by any admission check; (ii) it cannot become a precondition for a later acceptance — in particular, a later land(data, proof) for the same range MUST succeed whether or not the announce function was ever called, and in any order; (iii) its failure or omission has no effect on liveness or on any other rule. The safest design has none, and this specification designs none. Failure mode: an announce function that later becomes load-bearing converts "publish data" into a privileged step — the first caller of the announce function acquires a sponsorship right over the range, and a range whose announcement was never made (or was made and then made unreadable) is unlandable. This is the propose-then-prove failure of L1-01 arriving through the back door. Proven

Baseline for comparison: the propose-time hash is exactly such a load-bearing record (Inbox.sol:286 → Inbox.sol:348-351), and init2() (Inbox.sol:217-244) is an onlyOwner initialiser that rewrites lastFinalizedProposalId and lastFinalizedBlockHash directly. Neither construct exists in this design; see MIG-04.

L1-03 — failed verification leaves the batch unaccepted with no partial effect land(data, proof) MUST execute in this exact order: (1) decode and shape-check the input in memory only, with no state writes; (2) derive every contract-derived public input of L1-05 from L1 storage and from this transaction; (3) if blobs are used, perform the DA-03 checks and record the accepted (versionedHash, z, y) tuples in memory; (4) call the active verifier route with the statement hash; (5) treat the proof as invalid unless the call returns exactly abi.encode(true) — a revert, an empty return, or any other return value is invalid; (6) only then write the checkpoint record, advance the height pointer, mark covered forced inclusions consumed, and pay out L1-11; (7) emit events last. If any step fails, land(data, proof) MUST revert with a typed error and produce no partial effect: no checkpoint, no height advance, no consumed forced inclusion, no payout, no event. Failure mode: a checkpoint exists that no proof ever justified, or a forced inclusion is marked consumed by a batch that was never accepted. A "verify last, write first" ordering survives only as long as the verifier always reverts and nothing can swallow the revert; the moment a route returns false, or an upgrade or a low-level call absorbs the failure, the write becomes permanent and the chain's checkpoint advances without a proof. Proven

Why the baseline ordering is safe today, and why this design still changes it. At 7718753c1, prove() writes the SignalService checkpoint (Inbox.sol:364-370), updates _coreState and emits Proved (Inbox.sol:376-387) before calling _proofVerifier.verifyProof(...) (Inbox.sol:394-398). That is not a vulnerability in that contract as written, for one stated reason: the verifier call is in the same transaction and a reverting verifier unwinds the whole transaction, restoring the checkpoint and the core state. The baseline research records exactly this: "the ordering is still structurally 'optimistic write, then verify' — a property a same-tx redesign must preserve" (research/taiko-baseline-contracts.md §3.3). This design does not rely on that property. Reasons, in order of importance: (a) the interface tolerates a verifier that returns false instead of reverting, and a try/catch or a future routing layer could absorb a revert; (b) the checkpoint is a public authentication anchor for the preserved bridge surface (MSG-01), so its integrity must not depend on an external contract's revert discipline; (c) correctness must be readable from the function body rather than inferred from EVM unwind semantics. Verify-first costs nothing in gas terms that this specification claims to know — the cost of land(data, proof) is UNMEASURED and would be measured by a gas-snapshot run over a batch of the target size; no such measurement exists.

L1-04 — admission: no gate, no expiring range, any prover Any account MUST be able to call land(data, proof). The admission rules of land(data, proof) MUST contain: no whitelist and no allowlist (of provers, proposers, or relayers); no owner-, DAO-, or operator-controlled approval; no minimum bond, stake, or reputation to submit; no deadline, timestamp, block-number or age condition that can make a range permanently unacceptable; and no dependency on tx.origin, block.coinbase, gas price, or L1 proposer identity (GEN-06). For any unsettled range, any account that can produce a valid (data, proof) pair MUST be able to land it. Structural bounds are permitted and MUST be exactly these: the range must be contiguous and start at lastLandedHeight + 1 (L1-06); the batch must be non-empty; and every loop in land(data, proof) must be bounded by the transaction's own contents (its blob count, its forced-inclusion coverage list, its claimed range length), never by an unbounded external structure. Backpressure on production — the consensus-enforced unsettled-depth cap of HALT-03 and DA-06 — MUST NOT be implemented as an admission condition on land(data, proof). Failure mode: a validly PoS-finalized extension of the L1 checkpoint becomes permanently unacceptable, i.e. a legitimate extension of finalized history can never be settled. Under Mode A the protocol may halt but may not discard finalized history; an admission gate or an expiry is exactly a rule that discards it, because the only honest response left is to abandon settlement for that range. This rule is required by Mode A, not merely compatible with it (04-architecture-decision.md §5.3, L1-ADMIT-NO-EXPIRY; research/mode-a-feasibility-analysis.md §4). Proven (Mode A obligation)

Baseline mechanisms this rule deletes, each currently live: ProverWhitelist gating (Inbox.sol:337, Inbox.sol:771-779, error ProverNotWhitelisted); the IProposerChecker indirection whose mainnet implementation admits one operator per epoch (PreconfWhitelist.sol:136-140); DeadlineExceeded on propose (Inbox.sol:764-766); _maxProofSubmissionDelay (Inbox.sol:102); and the ring-buffer capacity check NotEnoughCapacity (Inbox.sol:591-593), which is the mechanism by which unproven history is silently discarded when the buffer wraps.

2. What the proof is bound to

L1-05 — public-input binding list, and who derives what The statement the proof is checked against MUST bind every value in the table below, at the stated provenance. L1-derived values the contract reads from its own storage or from block.chainid; tx-derived values the contract recomputes from the transaction's calldata and blobs and MUST ignore any submitter-supplied copy — except where the EVM cannot read the bytes at all (blob contents), where the value is a claimed input that the proof binds and the guest completes, and the table says so; claimed values are supplied by the submitter and are bound by the proof, so a wrong claim makes the proof invalid rather than making the contract misbehave. The contract MUST NOT accept from the submitter any value in the L1-derived or tx-derived rows. The canonical byte encoding of these values into the guest's public-input vector, and the guest-side recomputation of each one, are fixed on PRF-02 and PRF-07; this rule fixes which values L1 supplies and how it obtains them. The contract hashes the whole vector, with the domain tag and chain id first (GEN-05), into statementHash and passes only that hash and the opaque proof to the verifier route of L1-09. Failure mode: a public input that the submitter can choose — a validator-set root, a predecessor, a data commitment, a threshold — lets a prover prove a true statement about the wrong object and land a batch the protocol never agreed to. L1-06 — monotone checkpoint advancement Let lastLandedHeight be the height of the current checkpoint record (0 before the first one). land(data, proof) MUST require firstBlockHeight == lastLandedHeight + 1 and MUST reject with RangeNotContiguous() otherwise. It MUST also reject any batch whose unsettled depth lastBlockHeight − lastLandedHeight exceeds D_MAX (UnsettledDepthExceeded()), which is the contract-side half of the backpressure rule HALT-03: the cap becomes objectively detectable from L1 state alone rather than being an unverifiable claim about validator behaviour (review round 1, finding C R1-03). The check is a pure comparison against storage and costs no external call; for a duplicate or earlier range it MUST revert AlreadyLanded(). After a successful land(data, proof), lastLandedHeight = lastBlockHeight strictly increases. No function in any mode — including an upgrade initialiser, a recovery path, or a governance call — may decrease lastLandedHeight, replace or delete a checkpoint record at a height ≤ the current one, or write a checkpoint at a height greater than lastLandedHeight + 1. The only legitimate way a checkpoint disappears is an L1 reorganisation that reverts the entire land(data, proof) transaction (L1-12) — the contract never chooses to move backwards. Genesis establishes the first checkpoint exactly once, and it is never rewritten (MIG-03). Failure mode: a non-monotone checkpoint lets a later transaction replace the state root that the bridge surface authenticates against, which retroactively invalidates messages already proven against it — a rewrite of L2-finalized history through the L1 anchor, forbidden by Mode A (REC-01). A gap (writing lastLandedHeight + 2) is the same defect in weaker form: it leaves an unprovable hole in the authenticated chain. Proven

Contrast: init2() at Inbox.sol:217-244 sets lastFinalizedProposalId and lastFinalizedBlockHash to arbitrary owner-chosen values, and Inbox.sol:376-378 overwrites the finalised pointer on every prove(). Under L1-06 neither is expressible.

L1-07 — checkpoint record contents and its exact encoding The Inbox MUST store one checkpoint record per landed height and MUST make it readable by height. The record fields are, in this order and with these types: 
struct Checkpoint {
    uint64  height;           // L2 block height of the head of this batch
    bytes32 blockHash;        // L2 head block hash at height
    bytes32 stateRoot;        // L2 execution state root at height
    uint64  epoch;            // L2 epoch that contains height
    bytes32 setRoot;          // validator-set commitment valid at epoch
    bytes32 dataCommitment;   // data commitment of this batch (DA-02 / DA-03)
    uint64  l1BlockNumber;    // PROVENANCE: L1 block that accepted it
}
The record hash is keccak256(abi.encode(bytes32("TAIKO_ETNA_CKPT"), uint256(block.chainid), height, blockHash, stateRoot, epoch, setRoot, dataCommitment, l1BlockNumber)) — a single canonical abi.encode with the right-padded ASCII domain tag and the chain id as the first two fields (GEN-05). l1BlockNumber is required so that L1-12 and MSG-03 can evaluate Ethereum finality depth from storage without reconstructing an event log; it is provenance, not part of the state-transition binding, and it is written once and never edited. The accepting transaction's hash is not a field: the EVM does not expose it to the executing contract, so consumers obtain it from the BatchLanded event. blockHash, stateRoot, setRoot and dataCommitment MUST be non-zero; a record that fails any of these MUST NOT be written. The record MUST be the same object the L1 SignalService authentication path resolves for that block number (MSG-01). Failure modes: (a) storing only a hash of the batch — as the baseline does, since the only proof-side state persisted is CoreState.lastFinalizedBlockHash and a Checkpoint{blockNumber, stateRoot, blockHash} — makes the epoch, the validator-set commitment and the data commitment unauthenticated for every later consumer, in particular for the next proof's predecessor binding and for the bridge; (b) an encoding that is not a single canonical abi.encode admits a second preimage for the same record, so previousCheckpointHash no longer identifies one record. L1-09 — proof-system policy, verifier routing and the L1 ability to move to a new circuit A batch may be proven by any route whose (programImageId, verifier) pair is registered for the batch's epoch and not retired (MIG-05); exactly one route is required per proof, not one route per batch, and acceptance is first-valid-wins (L1-10) — two provers may submit under different registered routes for the same range, and the first proof that verifies is the one that lands. A route is the triple (routeVersion : uint64, programImageId : bytes32, verifier : address). Routes MUST live in the Inbox's own storage — not in a mutable registry owned by another contract — because the baseline verifiers (SP1Verifier, Risc0Verifier) are non-upgradeable Ownable2Step contracts replaced by redeployment, and an upgrade of a verifier contract must never be able to change which statement the Inbox accepts. Both zkVM backends implement the same statement; whether the policy is "one backend active" or "either backend verifies" is fixed by PRF-09, and land(data, proof) MUST implement that policy literally for the batch's epoch: with an either-verifies policy it MUST try each enabled route whose image is in that epoch's accepted set and accept the proof if any returns true; with a single-route policy it MUST call exactly the one route the policy designates. Enabling a new route is additive and MUST NOT be rejectable by any account (L1-04); every landed checkpoint MUST record the routeVersion used. Retiring an image is not an ordinary operation: it is permitted only under the same procedure that governs a rule change (GOV-02, GOV-03), and MUST NOT be executed while any PoS-finalized-but-unsettled range could be proved only under the retired image. A new image MUST accept every history that the previous image accepted (PRF-10). (review round 1, finding B R1-14) Failure modes: (a) a mutable external registry lets the verifier be re-pointed without the specification changing — the statement is then whatever someone wired up; (b) retiring an image while an unsettled finalized range depends on it makes that range permanently unprovable, which is Mode A's forbidden outcome arriving through an upgrade (04-architecture-decision.md §5.3, UPG-PRESERVE); (c) reading "exactly one active route" as one route per batch would make a batch unprovable under any other registered backend, contradicting the per-epoch accepted-image registry (MIG-05) and the portability of the statement. Proven Assumed (the retirement bar assumes A-GOV-1: the DAO does not execute a malicious upgrade)

4. Races, fees, and L1 reorganisation

L1-10 — submission races, re-submission, and what a proof is a proof of The first valid submission wins. Concretely: land(data, proof) MUST be atomic with respect to the checkpoint pointer, so two transactions in one L1 block are ordered by L1, the first one advances lastLandedHeight, and the second MUST revert AlreadyLanded() if it targets an overlapping or duplicate range, or MUST be evaluated against the new checkpoint if it extends it. Re-submission of the same batch (same dataCommitment, same range) by a different account MUST be accepted whenever the first submission did not land; it MUST NOT be rejected because another account previously submitted, attempted, or announced the same range. A proof is a proof of exactly the statement of L1-05: a proof for a different batch — a different range, a different predecessor, a different data commitment, a different epoch or set root — MUST NOT be usable as a substitute, and MUST fail verification because those values are in statementHash. The reward of L1-11 MUST be paid to msg.sender, the account that paid for the landing transaction; the protocol MUST NOT attempt to attribute it to any address named inside the proof. Consequently, a proof observed in the public mempool can be landed first by another account, which then collects the reward; this is an accepted property of permissionless landing, not a defect to be patched with a first-submitter reservation, and the mitigation available to provers is private orderflow or bundling. Failure modes: (a) a first-submitter reservation is a permissioned gate that expires a range into unrecoverability when the reserving account disappears (L1-04); (b) accepting a proof for a different batch lets a prover attach a valid proof to unrelated data — the whole point of binding the data commitment is that it cannot be done; (c) paying the reward to a proof-declared address lets anyone who copies a proof redirect the payout and makes the identity of the prover unfalsifiable. Proven
L1-11 — fees and the reward accounting identity The Inbox MUST hold two separate ledgers and MUST enforce their conservation with checked arithmetic (no unchecked subtraction; violation reverts FeeAccountingUnderflow()): a forced-inclusion ledger holding requester fees, and a prover reward ledger funded by L2 fee revenue (ECON-02) and by any msg.value the submitter adds. On a successful land(data, proof) the identity is: 
forcedInclusion_after = forcedInclusion_before
                       - sum of feeHeld[r] for r in coveredRequestIds   // paid to feeRecipient;
                                                                        // feeHeld[r] = 0 if refunded
proverReward_after    = proverReward_before + msg.value - rewardPaid
rewardPaid            = min(REWARD_QUOTE, proverReward_before + msg.value)
require(forcedInclusion_after >= 0); require(proverReward_after >= 0);
require(rewardPaid <= proverReward_before + msg.value);
Each covered request's fee MUST be paid at most once: land(data, proof) MUST mark the request consumed in the same write that pays it, and a second payment for the same requestId MUST be impossible. land(data, proof) MUST NOT require a non-zero rewardPaid: if the reward ledger is empty, the batch still lands with rewardPaid = 0 and the event records 0. REWARD_QUOTE MUST NOT depend on anything the submitter controls except the gas actually consumed, and MUST NOT depend on the proof's contents beyond validity. Escrow invariant (single accounting path). The forced-inclusion ledger is a segregated escrow. It MUST be debited only by the coverage payout of the request whose fee it holds or by that request's refund, and by nothing else — never for rewards, gas or any other purpose. For every queued request that has not been refunded, the escrow MUST hold at least feeHeld[r]: 
invariant:  forcedInclusionEscrow >= sum over outstanding requests of feeHeld[r]
coverage:   feeHeld[r] -> feeRecipient; escrow -= feeHeld[r]; consumed[r] = true
refund:     feeHeld[r] -> requester;    escrow -= feeHeld[r]; feeHeld[r] = 0; refunded[r] = true
mutual exclusion: refunded[r] => coverage pays 0 for r (and still consumes it);
                  consumed[r]  => refund reverts RefundNotAvailable(r)
revert conditions: land(data, proof) reverts FeeAccountingUnderflow() if applying coverage would
                  break the invariant (unreachable while the invariant holds); the refund reverts
                  RefundNotAvailable(r) iff r is not yet refundable or refunded[r] is true.
                  The invariant is inductive — each refund zeroes exactly the fee it removes —
                  so a refund can never fail for lack of balance.
A refund MUST NOT remove the request or affect its coverage obligation: it terminates the fee, not the duty, and coverage and refund are mutually exclusive per request. Conversely, coverage of an already-refunded request pays nothing but still marks the request consumed, so the queue still drains and the duty is still discharged. The Inbox MUST NOT be able to become unable to pay a refund or to settle a batch: that is the invariant's content, and any upgrade, entry point or payout that can spend the escrow outside these two paths violates it. (review round 1, findings B R1-07, C R1-10, C R1-11) Failure modes: (a) an empty reward pool blocking acceptance turns economics into an admission gate, which L1-04 forbids and which makes settlement depend on a treasury rather than on a proof; (b) paying a forced-inclusion fee twice is a direct drain of the ledger; (c) a reward that scales with a submitter-chosen quantity is a self-dealing surface. Proven unmeasured (REWARD_QUOTE and the gas cost of land(data, proof) are UNMEASURED; closing them requires a gas-snapshot run over batches of the target size, which does not exist)
L1-12 — L1 reorganisation handling, and no unfinalised L1 fact is settled If the L1 block containing a land(data, proof) transaction is reorganised out below Ethereum finality, the transaction is undone by Ethereum: no checkpoint record exists, no height advanced, no request consumed, no fee paid, and no event is part of the canonical chain. The batch remains PoS-finalized in Mode A, and MUST be re-landable with the same dataCommitment under L1-04. The Inbox MUST NOT contain any function that "repairs" a reorganisation by writing a chosen checkpoint, height, or state root: the only response is re-execution of land(data, proof). Because a checkpoint chain is built by strict succession (L1-06), a reorg that drops one land(data, proof) transaction also drops every later transaction that extended from it, since those transactions cannot satisfy firstBlockHeight == lastLandedHeight + 1 on the new branch; a submitter whose transaction is invalidated this way MUST re-submit. Independently of the Inbox, no L2 rule may treat an unfinalised L1 fact as settled: L2 consensused state may consume only Ethereum-final L1 facts, or L1 facts at the configured finality depth, per SYS-02 and STATUS-07. Checkpoint.l1BlockNumber (L1-07) records inclusion, not finality; any consumer that needs finality MUST compare it against the configured depth. Failure modes: (a) an owner-recovery setter for the checkpoint turns an L1 reorg into a discretionary rewrite of the L2 anchor; (b) an L2 rule that acts on an L1 fact at depth 0 can act on a fact that later disappears, so a PoS-finalized L2 block can be left depending on an L1 event that no longer exists — the exact condition under which a finalized L2 block becomes unprovable. Proven

5. Data availability (D8)

DA-01 — the canonical data-availability location is the accepting L1 transaction The canonical copy of a batch's data MUST be the accepting L1 transaction itself: its calldata and/or the blob sidecars of that same transaction, as bound by DA-02 and DA-03. A batch is accepted on L1 only together with that data. The design MUST NOT define a second canonical location, and MUST NOT treat any location outside that transaction as sufficient for STATUS-06. Failure mode: two canonical locations means two answers to "what is the batch?", and the weaker one is the one an implementer will build against. Proven
DA-02 — calldata path: the contract computes the data commitment itself In the calldata path the Inbox MUST compute the data commitment itself over the exact calldata slice supplied to land(data, proof), and MUST pass that value as the public input. The construction is fixed as: 
dataRoot       = keccak256(_data)                      // one byte string: no field ambiguity
payloadRoot    = dataRoot
dataCommitment = keccak256(abi.encode(
                     bytes32("TAIKO_ETNA_DATA"),        // right-padded ASCII domain tag (GEN-05)
                     uint256(block.chainid),            // chain id is the second field (GEN-05)
                     uint64(firstBlockHeight),
                     uint64(lastBlockHeight),
                     uint8(daMode),                     // 1 = CALLDATA, 2 = BLOB, 3 = CALLDATA_AND_BLOB;
                                   // DA-03(0) fixes payloadRoot per mode
                     payloadRoot))
keccak256(_data) hashes one opaque byte string rather than a concatenation of fields, so it introduces no second-preimage ambiguity and is not an abi.encodePacked of multiple values. The committed object is the whole _data byte string — no prefix of it. For daMode = 2 the same outer encoding is used with payloadRoot = keccak256(committedBytes) defined in DA-03(0); for daMode = 3 DA-03's hybrid payloadRoot replaces the calldata-only value so that the full blob strings are inside the commitment. (review round 1, findings B R1-01, B R1-06) The byte-level layout of _data — how L2 blocks serialise into the batch payload — is fixed once, on PRF-07; this rule fixes only how L1 commits to it. The guest MUST recompute dataCommitment from the payload it actually executed, and MUST reject the batch if the recomputation differs. Because both sides hash the same whole byte string, this path needs no probabilistic argument and remains the unconditionally sound path; the blob path (DA-03) is the one that carries the fixed-point argument and is an implementation gate. On this calldata path the Inbox MUST ignore any submitter-supplied dataCommitment; if one is present in the input it MUST either be absent from the ABI or be checked equal and rejected with DataModeMismatch() on mismatch. (On the blob path the EVM cannot read the bytes, so the claimed value is proof-bound and completed in-guest instead; see DA-03(0).) Failure mode: taking the commitment from the submitter decouples the proof from the calldata, so a valid proof can be paired with arbitrary data in the same transaction — the strongest and simplest binding available is thrown away. Proven
DA-03 — blob path: whole-blob commitment, BLOBHASH, on-chain KZG opening, and in-guest evaluation at the per-blob challenge point For a batch whose data is in blobs, let n = blobCount and let blob index i range over [blobIndexStart, blobIndexStart + n). The Inbox MUST perform (i) and (ii) for every i, and the guest MUST perform (iv) and (v).
(0) What is committed. dataCommitment commits the whole published byte string that the guest executes and that L1 publishes, not a prefix of it. For daMode = BLOB the committed object is the concatenation, in blob index order, of the full 131,072-byte string of every blob in the transaction — all 4096 field elements per blob, including any unused remainder; for daMode = CALLDATA_AND_BLOB it is the batch calldata payload followed by that same concatenation. Every published byte is inside the commitment, and the unused remainder of a blob MUST be committed too. No prefix-only commitment is permitted. A commitment over a prefix (the first k field elements, the non-zero prefix, or the portion the payload "uses") is forbidden: if the commitment covered only a prefix, the challenge point would be fixed before the free suffix was chosen, and a prover could choose the suffix to satisfy p_D(z) = p_B(z) by solving one linear equation — that was the round-1 attack. The encoding is DA-02's outer encoding, with daMode set to the derived mode and: 
committedBytes = blob_0 || blob_1 || ... || blob_{n-1}      // each exactly 131,072 bytes (4096 elements)
payloadRoot    = keccak256(committedBytes)                  // daMode = BLOB
dataCommitment = keccak256(abi.encode(bytes32("TAIKO_ETNA_DATA"), uint256(block.chainid),
                                      uint64(firstBlockHeight), uint64(lastBlockHeight),
                                      uint8(daMode), payloadRoot))
// HYBRID (daMode = 3): payloadRoot = keccak256(abi.encode(bytes32("TAIKO_ETNA_HYBRID"),
//        uint256(block.chainid), keccak256(_data), keccak256(blob_0 || ... || blob_{n-1})))
The EVM cannot read blob contents, so on the blob path — and for the blob component of hybrid — the contract cannot recompute payloadRoot: it takes the claimed dataCommitment, binds it into statementHash and derives z_i from it, while (v) requires the guest to recompute the same value over the full blob bytes it executed. The value is therefore not a free submitter choice: a wrong value makes the proof unverifiable rather than making the contract misbehave. (review round 1, findings B R1-01, B R1-06)

(i) BLOBHASH equality. The Inbox MUST read the transaction's own blob versioned hash with the BLOBHASH opcode and require, for each i:

bytes32 vh = blobhash(i);
require(vh != bytes32(0) && vh == _input.blobVersionedHashes[i - blobIndexStart], BlobHashMismatch(i));

A zero value means no blob at that index in this transaction; because BLOBHASH is transaction-scoped, no other transaction's blobs can be substituted. The loop is bounded by the transaction's own blob count, whose protocol limit is the Ethereum per-block limit — target 6, maximum 9 blobs per block under EIP-7691 sourced.

(ii) On-chain KZG point evaluation. The Inbox MUST call the EIP-4844 point-evaluation precompile at address 0x0A with the 192-byte input abi.encodePacked(vh, z_i, y_i, commitment_i, proof_i) — z_i and y_i as 32-byte big-endian canonical field elements, commitment_i and proof_i as 48-byte compressed BLS12-381 G1 points. The call MUST succeed and MUST return exactly abi.encode(4096, BLS_MODULUS); otherwise land(data, proof) reverts BlobOpeningFailed(i). The precompile verifies kzg_to_versioned_hash(commitment_i) == vh and verify_kzg_proof(commitment_i, z_i, y_i, proof_i), and rejects non-canonical field elements. Its gas cost is 50,000 per call sourced (EIP-4844), so a batch using n blobs costs 50,000 · n gas for these calls derived; the total cost of land(data, proof) remains UNMEASURED.

(iii) The challenge point z_i is derived on-chain by Fiat–Shamir, per blob. It MUST NOT be supplied by the submitter. With statementCoreHash the hash of the public inputs of L1-05 rows 1–17 excluding rows 18–19 (i.e. excluding the challenges themselves), the Inbox MUST compute, for each blob index i:

z_i = uint256(keccak256(abi.encode(
          bytes32("TAIKO_ETNA_CHALLENGE"), uint256(l2ChainId), statementCoreHash,
          dataCommitment, blobHashesHash, uint16(i)))) % BLS_MODULUS;

The domain tag, l2ChainId (Inbox config), statementCoreHash, dataCommitment, blobHashesHash and the blob index are all inside the transcript, so the challenge moves whenever the committed bytes move: dataCommitment commits the whole published byte string (0) and blobHashesHash commits the ordered versioned hashes. On the blob path the contract takes dataCommitment from the proof-bound input (0) and the guest recompletes it from the executed bytes in (v), so dataCommitment and z_i cannot be chosen independently of the executed payload. The modulus reduction is required because a keccak-256 output is not automatically a canonical scalar (BLS_MODULUS < 2^255), and the precompile rejects non-canonical elements. The reduction biases the distribution by at most BLS_MODULUS / 2^256 ≈ 2^-127 in statistical distance derived, which is irrelevant to the 2^-243 bound below. The blob index i is inside the transcript so that two blobs of the same batch never share a challenge.

(iv) The guest proves the evaluation of the data it executed, in the EIP-4844 convention. The guest receives (vh_i, z_i, y_i) as public inputs and the blob bytes as part of the data it executed. It MUST interpret each 131,072-byte blob exactly as EIP-4844 does: the 4096 big-endian field elements are the evaluations of the committed polynomial in bit-reversed order over the 4096th roots of unity — element j is the evaluation at ωbrp(j), where brp is the bit-reversal permutation of the 12-bit index — which is what blob_to_kzg_commitment commits to, g1_lincomb(bit_reversal(setup_lagrange), blob). They are not coefficients of p(X). The guest MUST use this same convention (inverse bit-reversal plus Lagrange interpolation over the evaluations, or an equivalent FFT) or every honest blob proof fails; any other interpretation is invalid. It MUST reject the batch if any element is ≥ BLS_MODULUS, and MUST reject it unless p_data,i(z_i) == y_i.

(v) The guest recompletes the data commitment. The guest MUST recompute payloadRoot = keccak256(committedBytes) and dataCommitment from the full blob byte strings it executed with the (0) construction — every blob, every byte, no prefix — and MUST reject the batch unless the result equals the journal value used in (iii). This is what makes the claimed blob-path dataCommitment proof-bound.

Why this is sound (the joint event, not a fixed challenge). The chain is: (a) blobhash(i) names the blob that is in this transaction; (b) the precompile establishes kzg_to_versioned_hash(commitment_i) == vh_i, so commitment_i is the KZG commitment of that blob's polynomial p_B,i; (c) the precompile's verify_kzg_proof establishes p_B,i(z_i) = y_i; (d) the guest establishes p_D,i(z_i) = y_i over the payload D it executed, and (v) requires dataCommitment to be recomputed from that same D. Therefore (p_D,i - p_B,i)(z_i) = 0. But z_i is not fixed while D is chosen: z_i is a deterministic function of the transcript that contains dataCommitment = f(keccak(D)). The event a cheating prover needs is the joint event p_D(z(D)) = p_B(z(D)) with z(D) derived from keccak(D) — a fixed-point condition, not a linear equation in the free part of D. Stated as a search over hash outputs: for any fixed D the difference is a non-zero polynomial of degree ≤ 4095 with at most 4095 roots, so an evaluation at the pseudorandom point z(D) agrees with probability at most 4095 / |F| ≈ 2^-243 derived, and a search over q candidate payloads succeeds with probability at most q · 2^-243 (plus the 2^-127 reduction bias). The earlier statement of the bound "per attempt at a fixed challenge" was wrong: it assumed D was fixed before the challenge, which is exactly what (0) and (iii) prevent. D is moreover not a free variable: the executed payload is bound to the certified header chain — the certificate covers the head block id, the header chain links to the predecessor and each header's transaction root fixes its transactions (PRF-04(v), PRF-06) — so a prover cannot vary D after the certificate is signed without invalidating it. Hence, with overwhelming probability, p_D,i = p_B,i: the guest executed exactly the data the blob commits to. (review round 1, findings B R1-01, B R1-02)

Premises. This argument requires all five of: (1) KZG binding for blob commitments (A-CRYPTO-3); (2) the random-oracle model for the Fiat–Shamir derivation of z_i; (3) correct in-guest field arithmetic over the BLS12-381 scalar field, including the exact bit-reversed evaluation-form interpretation and Lagrange interpolation; (4) canonical field elements in both the blob and the guest's field elements (evaluation form); and (5) the in-guest recomputation of dataCommitment over the full blob bytes of (0)/(v). If any premise fails, the binding does not hold. This is a proof sketch with named premises, not a machine-checked theorem, and adversarial review question Q-A3 is carried against a grinding prover (04-architecture-decision.md §7).

Provenance and honesty. This construction was derived in this project (04-architecture-decision.md §4.1); it is not an established published design and has no implementation. It is an implementation gate: it may not be relied on until the fixed-point argument above has had independent cryptographic review and its in-guest cost has been measured. Its in-guest cost is UNMEASURED; measuring it requires an implementation of the in-guest evaluation on both backends with cycle counts at a stated blob size, which does not exist (04-architecture-decision.md §7, item F2). In-guest MSM and in-guest pairings are deliberately avoided, because the zkVM feasibility work found them UNVERIFIED on both backends: the guest performs field arithmetic and Lagrange evaluation only, and the pairing happens on L1 inside the precompile (PRF-11). The alternative to measure is the RISC Zero patched c-kzg library, which would put a different and larger trusted computing base inside the guest. Precompile semantics, address and gas are cited from EIP-4844; blob counts from EIP-7691.

Failure modes: (a) a submitter-chosen z, or a commitment that covers only a prefix of a blob, lets a prover pick the evaluation point after fixing part of its data, which reduces the binding to a single linear equation it can solve; (b) accepting blobhash from calldata instead of reading it lets a transaction reference blobs it did not publish; (c) performing the KZG opening in-guest would require MSM and pairings that are unverified on both backends, i.e. an unquantified soundness assumption; (d) without the canonical-field-element requirement the guest's polynomial is ambiguous, and two different byte strings map to the same polynomial; (e) without (0) and the EIP-4844 convention of (iv), an honest prover computes a different polynomial and every blob-path batch fails. Proven sourced derived unmeasured Open (measured in-guest cost; independent cryptographic review of the fixed-point argument; review question Q-A3)

Hybrid mode. When daMode = CALLDATA_AND_BLOB, the whole published byte string is _data || blob_0 || … || blob_{n-1} (each blob its full 131,072 bytes), and

payloadRoot = keccak256(abi.encode(bytes32("TAIKO_ETNA_HYBRID"), uint256(block.chainid),
                                  keccak256(_data), keccak256(blob_0 || ... || blob_{n-1})));

Both bindings then apply independently: the calldata part is bound by the contract's own hash over _data, the blob parts by the whole-blob-byte commitment of (0) and the per-blob challenges of (iii)–(v). No vh-only or prefix-only commitment may stand in for the blob bytes, and a batch is invalid if either binding fails. (review round 1, finding B R1-06)

Failure mode: the protocol claims availability while the only party who can reconstruct the batch is the prover, which is exactly the "certified-but-unavailable" class that the architecture decision records as Mode A's strongest counterexample (04-architecture-decision.md §5.1). DA-05 — retrievability window, archive requirement, and the blob-retention limit Blobs are not a permanent store. Ethereum guarantees blob sidecar retrievability for MIN_EPOCHS_FOR_BLOB_SIDECARS_REQUESTS = 4096 epochs sourced (EIP-4844), which is roughly 18 days at Ethereum's present slot cadence derived — the design does not depend on that wall-clock figure and expresses the window in epochs and L1 block numbers (GEN-06). Calldata is not permanent either: on the p2p layer clients stop serving historical headers, bodies and receipts older than 14,299 epochs sourced (EIP-4444, recorded in research/recovery-and-withholding-raw.md). The design therefore MUST specify, in 09: (a) a RETRIEVABILITY_WINDOW in L1 block numbers, not shorter than the blob-retention window; (b) an ARCHIVE_REQUIREMENT fixing how many independent archive nodes must retain the full accepting-transaction calldata and full blob sidecars for at least that window, with the duty owned by ROLE-03; (c) the statement that past the window, retrievability depends on those archives and not on Ethereum. Under D5 this failure class cannot recur for a pending batch: data is published only in the transaction that proves it, so there is no interval in which a batch's data is on L1 while its proof is not. The retention clock starts at acceptance, not at a separate proposal. In-repo evidence that this failure class is real, not hypothetical: at revision 7718753c1, init3() (Inbox.sol:246-258) is a one-time onlyOwner function that voids queued forced inclusions by moving the queue head to the tail, and its NatSpec states the reason — the skipped entries' blobs have expired from the blob retention window and can no longer be derived after the June 2026 incident, and their fees remain in the contract. 04-architecture-decision.md §4 records the same finding. A design that publishes data before a proof re-creates exactly that state. Proven sourced derived
DA-06 — retention duty and its link to the backlog cap The consensus-enforced unsettled-depth cap of HALT-03 exists because of this rule. Define unsettledAge as the L1-block distance between the oldest PoS-finalized-but-not-landed L2 block and the current L1 block. Correct validators MUST refuse to vote for a block that would make unsettledAge exceed MAX_UNSETTLED_AGE, so that the oldest unsettled batch never leaves the retrievability window before it can be proven and landed. The retention duty MUST satisfy RETRIEVABILITY_WINDOW ≥ MAX_UNSETTLED_AGE + SETTLEMENT_PIPELINE + EVIDENCE_WINDOW, where SETTLEMENT_PIPELINE is the worst-case proving plus L1-inclusion plus Ethereum-finality time (ECON-03) and EVIDENCE_WINDOW is the misconduct-evidence window (ECON-07). The cap is a rule on production; it MUST NOT be applied to land(data, proof) (L1-04), because refusing an available, valid proof would strand finalized history. When the cap binds, the honest outcome is a safe halt (HALT-01), never a rollback. Failure mode: without the cap, blocks keep being finalized whose data ages out of the retention window before any proof exists; the batch then cannot be proven by anyone, and Mode A forbids discarding it, so the chain is permanently stuck on a range whose data no longer exists anywhere the protocol promised. The cap converts an unbounded, unrecoverable failure into a bounded, recoverable halt. Proven unmeasured (RETRIEVABILITY_WINDOW, MAX_UNSETTLED_AGE and the pipeline terms are unmeasured parameters; all four are fixed in 09)

require(setEquals(coveredIds, DueCap(T)));                   // else ForcedInclusionNotCovered(id)
require(T <= block.timestamp);                               // two-sided bound, side 1: no future-dating
require(block.timestamp <= T + FORCED_INCLUSION_MAX_DRIFT);  // side 2: no back-dating beyond the drift
                                                             // else BatchTimestampDrift(...)
consume(coveredIds);                                         // each id exactly once, in FI-01 order
coveredIds MUST be strictly ascending and duplicate-free; a duplicate MUST revert ForcedInclusionNotCovered(). Exact equality — not containment — is required so that a proposer can neither omit a due request nor pad the batch with requests that are not due in order to change their relative order. Because firstBlockHeight is forced to lastLandedHeight + 1 (L1-06), a proposer cannot move the batch boundary to escape the duty.
(c) One predicate, one clock, and the containment direction. The two layers MUST use the predicate above on the same L1-visible state; there is no height-based dueness, no second clock, and no proof-supplied dueness flag. For any batch the L2 predicate admits, L1's due set MUST be a subset of the L2 predicate's due set, DueCap_L1(T) ⊆ DueCap_L2(T); the converse holds automatically because the L2 view is a historical prefix of L1 state (a request consumed or cancelled in that view is consumed or cancelled in L1's), so the two sets MUST in fact coincide — that is what makes setEquals satisfiable. The eligibility timestamp is compared through values the L1 contract recomputes from its own state: r.eligibleAtL1Timestamp is L1 storage, and T is sandwiched by L1's own clock (T ≤ block.timestamp ≤ T + FORCED_INCLUSION_MAX_DRIFT). The finality-depth lag is absorbed by FORCED_INCLUSION_DELAY_SECONDS: it MUST be at least L1_FINALITY_DEPTH expressed in seconds plus MAX_BATCH_BLOCKS × L2_BLOCK_INTERVAL plus a clock-skew and observation margin, so that any request with eligibleAtL1Timestamp ≤ T was already Ethereum-final in the parent's L1 view and could not have been invisible to the L2 predicate. Without this containment, L2 could declare a request not-yet-due while L1 declares it due, and a legitimately finalized range would be permanently unlandable — the outcome L1-04 forbids. (review round 1, findings B R1-08, C R1-06, C R1-07)
FORCED_INCLUSION_MAX_DRIFT MUST be strictly smaller than FORCED_INCLUSION_DELAY_SECONDS, so the omission window it opens is a fraction of the eligibility delay: a request hidden by back-dating in one batch is inside every later batch's due set once L1 time passes eligibleAtL1Timestamp + FORCED_INCLUSION_MAX_DRIFT, and it can never be permanently excluded. The value is a liveness parameter fixed in 09 and is UNMEASURED — closing it requires measured L2/L1 clock skew under the stated operating assumptions. (review round 1, finding B R1-07) Failure modes: (a) without the L2 rule, the queue drains at proposer discretion and the duty is only a fee; (b) without the L1 backstop, a colluding quorum can omit a request forever while continuing to land batches; (c) containment instead of equality lets a proposer reorder due requests relative to each other; (d) without the two-sided bound on T in L1 time, a proposer can label a batch with a timestamp older than a request's eligibility and claim the request was not yet due; (e) without the containment direction of (c), a finality-lag mismatch makes an honestly finalized range permanently unlandable. Proven unmeasured
FI-03 — escape hatch under sustained censorship A request MUST NOT be voidable. There MUST NOT exist an owner, DAO, operator, or recovery function that removes a request from the queue, rewrites its eligibleAtL1Timestamp, or marks it consumed without a corresponding accepted batch — contrast init3() (Inbox.sol:253-258), which does exactly that. When a request has remained eligible and uncovered for longer than FORCED_INCLUSION_ESCAPE_THRESHOLD (seconds), the following MUST hold: (a) the request stays in the queue and remains coverable by any future batch, forever; (b) the requester becomes entitled to a refund of the fee it paid, claimable from the Inbox at any time thereafter, without removing the request or affecting its coverage obligation; refunds MUST be paid from the segregated escrow of L1-11 under its solvency invariant, in which each request's fee is held until exactly one of coverage or refund occurs — the two are mutually exclusive for one request, and a refunded request that is later covered is still consumed and still carries its coverage obligation but pays zero to feeRecipient; a refund MUST NOT be able to make the Inbox unable to pay a later refund or to settle a batch, and the only reverts on the refund path are RefundNotAvailable() (not yet refundable, or already refunded) and the invariant's unreachable FeeAccountingUnderflow() (review round 1, findings B R1-07, C R1-10, C R1-11); a refund does not restore inclusion, and the hatch MUST NOT be described as an inclusion right — it is a fee remedy whose only effect on inclusion is that the duty continues to block settlement while the request is uncovered; (c) land(data, proof) continues to reject batches that fail FI-02, so a chain that keeps producing without covering the request stops being able to settle, which is the halt defined by HALT-01; (d) honest participants MUST NOT respond by discarding, rolling back, or re-founding finalized history (HALT-02). The hatch deliberately does not provide an L1-side force-exit of L2-held value: the funds are in L2 state, and no rule here may invent an L1 path that mints or releases them. That limitation MUST be disclosed wherever the hatch is described. Failure modes: (a) a voidable queue destroys the censorship remedy and destroys the evidence of the censorship (WH-02); (b) an "escape" that mints or releases L2-held value on L1 is a bridge exploit with an honest name; (c) an escape that invalidates finalized history is Mode B by the back door and is forbidden by D2 in ordinary operation. Proven
FI-04 — forced inclusion can only add to a future block; it can never reorder or revoke past history A covered request's payload MUST enter as a transaction in an L2 block whose height is strictly greater than lastLandedHeight — i.e. in a block of the batch currently being landed, or a future one, never in an already-landed block. A request MUST NOT be able to change the content, ordering, or state root of any block at a height ≤ lastLandedHeight, and MUST NOT be able to change any checkpoint record (L1-06). Within the batch that covers it, the request's position relative to other covered requests is fixed to FIFO request order (FI-02); its position relative to non-forced transactions is a derivation rule owned by CONS-01. A request that is never covered MUST remain queued rather than be discarded (FI-03). There MUST NOT exist a code path that uses a forced inclusion, or the fact that one is overdue, to re-execute, invalidate or replace a landed batch (REC-01). Failure mode: a censorship remedy that can reorder or revoke past history is a retroactive-reordering mechanism — the mechanism D2 forbids — and it would let an attacker use the forced-inclusion queue to rewrite settled outcomes, including bridge messages already authenticated against a checkpoint. Proven
FI-05 — griefing controls and fee escalation The required fee for a request MUST escalate with queue depth: 
fee = floor(BASE_FEE * (FEE_DOUBLE_THRESHOLD + pending) / FEE_DOUBLE_THRESHOLD)  // pending = queue length
fee = min(fee, MAX_FEE);                                                          // no overflow, no unbounded grief
This is the shape used at revision 7718753c1 (LibForcedInclusion.sol:89-93, with baseFee = 1_000_000 gwei and threshold = 50 at MainnetInbox.sol:49-50) sourced; this design's BASE_FEE, FEE_DOUBLE_THRESHOLD and MAX_FEE are set in 09 and are UNMEASURED. Additional controls are mandatory: (a) a request MUST NOT be cancellable once block.timestamp ≥ eligibleAtL1Timestamp — before that it is cancellable, and cancellation refunds the fee minus a fixed CANCELLATION_COST in the same write that zeroes feeHeld[r] and marks the request cancelled, so the escrow invariant of L1-11 is preserved and the retained CANCELLATION_COST is never refundable (review round 1, finding B R1-07); (b) each request consumes exactly one slot of the L2 block space it eventually occupies, and the number of requests a single batch can cover MUST be bounded by MAX_FORCED_INCLUSIONS_PER_BATCH, so that both land(data, proof) and block production have bounded cost; (c) the fee MUST rise with queue depth as specified above, and the protocol MUST NOT depend on any bound on the queue length for correctness: because FI-02 requires only the capped prefix of the due list, an arbitrarily long queue can slow coverage but can never make every proposal invalid, and it can never halt production. This is a correction recorded in review round 1 (finding C R1-01): an earlier revision of this rule required the whole due set to be covered while capping coverage per batch, which allowed a permissionless attacker to post MAX_FORCED_INCLUSIONS_PER_BATCH + 1 requests and make every proposal invalid at negligible cost. (d) land(data, proof)'s due-prefix computation MUST stop after collecting MAX_FORCED_INCLUSIONS_PER_BATCH eligible entries, so its cost is bounded by the cap and not by the queue length. Failure modes: (a) a free or cheap queue lets an attacker fill the due set so that every land(data, proof) reverts, stalling settlement at negligible cost; (b) an unbounded due-set loop makes land(data, proof) unaffordable or uncallable as the queue grows; (c) cancellable-after-eligible requests let an attacker withdraw the evidence of censorship exactly when it matters. Note honestly that this remains a cost-imposing liveness attack even with escalation: its profitability is UNMEASURED, and closing it requires the fee schedule and the measured cost of covering a request. Proven sourced unmeasured

Why a sub-threshold cartel cannot starve inclusion

This is a conditional liveness argument with named premises, not a guarantee. Proposer selection is hash-based weighted selection (CONS-06), and a cartel holding f < 1/3 of the stake that counts toward quorum (A-CONS-1) holds fewer than 1/3 of proposer slots in expectation over any window of s slots. Let p = f be the cartel's slot share. The probability that the cartel leads s slots in a row is p^s, so the expected waiting time for an honest slot is 1/(1-p) ≤ 1.5 slots derived. An honest proposer MUST include the due set or its proposal is invalid (FI-02a, CONS-01), and honest validators precommit only valid proposals, so the request is covered as soon as an honest proposer leads. The cartel's residual power is to make coverage late, not to prevent it, and lateness is bounded by the selection rule, not by a timeout judgement (STATUS-10). Two honest caveats: this holds only while A-CONS-1 holds — at ≥1/3 Byzantine stake the argument does not apply and the protocol claims nothing; and it assumes proposer selection is not predictable enough for the cartel to buy the specific slots in which a request becomes due, which is an assumption about the selection function that MUST be stated in CONS-06, not here. (review round 1, finding CS-02: the slot-share premise is CONS-06(b)'s Assumed fairness claim, and the superseded residue rotation is replaced by hash-based weighted selection.)

MSG-02 — replay protection and domain separation The preserved surface keeps its existing encodings, and both MUST be frozen by MIG-02 because they determine every stored slot and every cached proof: the signal slot is keccak256(abi.encodePacked("SIGNAL", chainId, app, signal)) (SignalService.sol:160-171), and the bridge message hash is keccak256(abi.encode("TAIKO_MESSAGE", message)) with Message.srcChainId and Message.destChainId inside the struct (Bridge.sol:536-539).
