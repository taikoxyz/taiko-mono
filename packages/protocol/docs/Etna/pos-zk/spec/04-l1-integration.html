04 — L1 integration: one proof-gated acceptance, data availability, bridge anchoring, and the limits of inclusion

This page carries D5, D8, D11 and D13. It fixes how a batch becomes STATUS-06 — accepted on L1: one L1 transaction carrying the validity proof — and carrying the batch data or binding it to a live publication record that put that data in blobs earlier (DA-07–DA-09) — out of which the Inbox itself derives the data commitment, and out of which a single monotone checkpoint advance follows. (decision D-11: data may be published before the proof; data sitting in blobs has no effect on protocol state, which still advances only on a valid proof.) It also fixes where that data is canonical (DA-01), how the blob path binds data to the proof (DA-03, DA-08), the inclusion guarantees and limits v1 actually has — none: decision D-16 defers the narrow forced-inclusion rule over published data (FI-10–FI-14), whose rules are tombstones that MUST NOT be implemented, and there is no general inclusion list either, so the isolation consequence stated at FI-REMOVED-01 and LIVE-04 is the whole statement — and how the preserved SignalService/Bridge addresses authenticate against these checkpoints (MSG-01–MSG-03).

Two changes on this page deliberately lengthen exits. An L2→L1 release is anchored on a withdrawal root: an accepted checkpoint that carries proofs of its own accepted statement from k distinct registered backend families, verified one per attestation on L1 (L1-13), and a rule-triggered, self-expiring withdrawal veto of at most T_VETO may delay releases while an on-chain-verified proof contradiction is investigated (MSG-04). Both are user-visible: an exit waits for k attestations of a checkpoint at or above the signal's height, and a veto can add up to T_VETO to any pending withdrawal. The exit is available during a settlement stall whenever its proving market functions: a root for the latest L1-accepted checkpoint can be attested permissionlessly, with no new L2 blocks and no settlement progress — the statement, the family records and the accepted image set are L1 state that already exists — and the withdrawal delay is measured from the root's own record, so it runs on L1 whether or not the chain is producing blocks (L1-13(2)–(3), MSG-03); the k−1 attestation proofs are funded proving work (L1-13(5)), and an absent or unfunded proving market is the named falsifier of MEM-15(2b). This closes review round 7 finding F1: the summary no longer presents the exit as independent of proving. Neither mechanism cancels a proven withdrawal, and neither is a repair for an unsound backend. (PR #22262 review comment 1, item 3: withdrawals are the one place proof soundness is multiplied, and the removed pause lever is replaced by a bounded rule-triggered veto. Decision D-16: aggregation is deferred, so PRF-15 and L1-14 are tombstones and L1-13 reverts to k attestations each verified on L1.)

1. One acceptance transaction: proof-gated, data carried or published earlier

The figure shows the carried case. Under decision D-11 the data MAY have been published in an earlier L1 transaction, and the accepting transaction then carries the proof and the reference to the publication record while the blobs stay in the publication transaction (DA-07, DA-08). The verify-first ordering, the derived statement hash and the single checkpoint write of L1-03 are unchanged in both cases; what changes is where the contract reads the blob versioned hashes from and whether BLOBHASH can be used at all. (decision D-11: data may be published before the proof.)

L1-01 — single accept entry point; proof-gated, data carried or published earlier The Inbox MUST expose exactly one function that can accept a batch and advance the checkpoint. Its name is land(data, proof) — the batch data (or the reference to where it was published) first, the validity proof second, one entry point and no other. One call MUST carry, in one L1 transaction: (a) the batch range, given as uint64 firstBlockHeight and uint64 lastBlockHeight of L2 blocks; (b) the batch data, given as the bytes calldata _data argument and/or the blob sidecars of that same transaction, or — when the data was published earlier — a reference to the live publication record that carries it (DA-07, DA-08); (c) the proof, given as _proof; and (d) the claimed post-state and finality values of L1-05. The proof and the checkpoint write are inseparable — the protocol state advances only on a valid proof — but the data and the proof need not share one transaction: there MUST NOT exist any entry point, overload, fallback, multicall helper, or recovery path that accepts a batch, writes a checkpoint or advances the height pointer pending a proof. The permissionless publication path of DA-07 records data and writes no batch state; it is not a batch record and never a precondition for the carried path (L1-02). There MUST NOT exist a "propose then prove" path in any mode — a publication record is not a proposal and land(data, proof) MUST succeed without one whenever the data is carried. (decision D-11: D5's one-transaction rule is relaxed for the data, not for the proof or the checkpoint; there is still no data-first path that advances protocol state.) Every other artifact that names this entry point — the migration state gate (MIG-03), the parameter register, the glossary and the client interfaces — MUST use the same name land(data, proof): a second name (for example accept(data, proof)) is a defect, because the migration gate and the audited interface would then be specified against a selector that does not exist. (review round 1, finding B R1-16) Batch-length consequence of one-transaction publication. Because a batch's blobs MUST fit in one L1 transaction — the accepting one when the data is carried, the publication one when it is published earlier (DA-07(5)) — the batch's blob count is capped by Ethereum's per-L1-block blob limit rather than by a separate protocol choice: at the DA-bound rate one 2-second L2 block is one 131,072-byte blob (EIP-4844), so BATCH_BLOCKS × blobs_per_block ≤ 9 (hard) and BATCH_BLOCKS ≤ 6 (sustainable at EIP-7691's 6 target / 9 maximum blobs per L1 block), and MAX_BATCH_BLOCKS MUST respect the same bound (registered, with its sourced constants and derivation, in 09; L1-05 row 7). (Phase B plan §8.6: the blob ceiling is a derived bound on K, and the registered placeholder of 32 is not publishable at the DA-bound rate.) Failure mode: the batch's data becomes public before any proof exists, so a batch can be published and never proven — the data occupies L1 capacity and settles nothing. D-11 accepts that risk explicitly and controls it rather than forbidding it: a publication record writes no batch state and admits nothing, so the failure is a stalled range and a wasted publication, never a forged checkpoint; the proving deadline of DA-09 stops a dead publication from being referenced past the blobs' retrievability; and the publication record is retained as the anchor of DA-10, whose exclusion obligation is deferred by decision D-16 and is not a v1 rule (DEFERRED.md §1). What is not relaxed is the rule this entry point carries: no entry point may accept a batch, write a checkpoint or advance the pointer pending a proof, and the carried path (data and proof in one transaction) MUST remain available for every unsettled range (L1-04). Proven sourced (D-11 relaxes D5 for the data and keeps the proof-gated checkpoint; contrast below)

L1-02 — no entry point records a pending or incomplete batch No entry point of the Inbox — public, external, or reachable through an upgrade initialiser — may write a batch record, a predecessor link, a proposal hash, a data commitment, or a checkpoint pending a proof. The only accepted state that exists for a range is the checkpoint written by a successful land(data, proof) call. An "announce" / "intent" / "commit" function may exist only if all three hold: (i) nothing it writes is read by land(data, proof), by the verifier route, or by any admission check; (ii) it cannot become a precondition for a later acceptance — in particular, a later land(data, proof) for the same range MUST succeed whether or not the announce function was ever called, and in any order; (iii) its failure or omission has no effect on liveness or on any other rule. The safest design has none, and this specification designs none. The one record land(data, proof) may read is not a batch record. The publication record of DA-07 writes no batch record, no predecessor link, no proposal hash, no claimed post-state and no checkpoint; it records where data is. It is the one record the accepting transaction MAY reference and it is referenced only on the submitter's choice: (i) the carried path of DA-03 reads no publication record at all, so a range is always landable without one; (ii) a missing, expired or mismatched record cannot make a range permanently unacceptable, because a fresh publication may be created at any time by any account (DA-07(4), DA-09(2)); and (iii) referencing a record never confers a right on its publisher, who remains a stranger to the acceptance. A publication record MUST NOT be read by any admission check of the carried path, and the side mapping that records which record a landed batch referenced (L1-09) is written after acceptance, never before it. (decision D-11: publication is data availability, not a pending batch; L1-02's ban on pending batch state is unchanged.) Failure mode: an announce function that later becomes load-bearing converts "publish data" into a privileged step — the first caller of the announce function acquires a sponsorship right over the range, and a range whose announcement was never made (or was made and then made unreadable) is unlandable. This is the propose-then-prove failure of L1-01 arriving through the back door. Proven

L1-03 — failed verification leaves the batch unaccepted with no partial effect land(data, proof) MUST execute in this exact order: (1) decode and shape-check the input in memory only, with no state writes; (2) derive every contract-derived public input of L1-05 from L1 storage and from this transaction; (3) if the accepting transaction carries blobs, perform the DA-03 checks and record the accepted (versionedHash, z, y) tuples in memory; if the input references a publication record (L1-05 row 35), perform the DA-08 record checks and its deadline check (DA-09) — and perform the DA-03 checks too when the transaction also carries the blobs — all in memory only; (4) call the active verifier route with the statement hash and the opaque proof; (5) treat the proof as invalid unless the call returns exactly abi.encode(true) — a revert, an empty return, or any other return value is invalid; (6) only then write the checkpoint record, advance the height pointer, record the proof-bound signerBitmap into the staking contract's per-epoch participation accumulator (ECON-02 clause 5), and pay out L1-11; (7) emit events last. If any step fails, land(data, proof) MUST revert with a typed error and produce no partial effect: no checkpoint, no height advance, no payout, no event. (user decisions D-6 and D-16: the forced-inclusion consumption write was removed with the queue; D-12 restored it as the FI-10 settlement record, and D-16 defers the whole forced-inclusion machinery, so no such record is written and this step writes the checkpoint only. Decision D-16 also removes the aggregation public input from step (4), because aggregation is deferred instead of accepted.) (decision D-11: the shape check of (3) distinguishes the carried, referenced and carried-and-referenced cases and performs no check that could read a blob the transaction does not carry; an expired or mismatched publication reverts here, before verification, with no partial effect.) Failure mode: a checkpoint exists that no proof ever justified. A "verify last, write first" ordering survives only as long as the verifier always reverts and nothing can swallow the revert; the moment a route returns false, or an upgrade or a low-level call absorbs the failure, the write becomes permanent and the chain's checkpoint advances without a proof. Proven

Why the baseline ordering is safe today, and why this design still changes it. At 7718753c1, prove() writes the SignalService checkpoint (Inbox.sol:364-370), updates _coreState and emits Proved (Inbox.sol:376-387) before calling _proofVerifier.verifyProof(...) (Inbox.sol:394-398). That is not a vulnerability in that contract as written, for one stated reason: the verifier call is in the same transaction and a reverting verifier unwinds the whole transaction, restoring the checkpoint and the core state. The baseline research records exactly this: "the ordering is still structurally 'optimistic write, then verify' — a property a same-tx redesign must preserve" (research/taiko-baseline-contracts.md §3.3). This design does not rely on that property. Reasons, in order of importance: (a) the interface tolerates a verifier that returns false instead of reverting, and a try/catch or a future routing layer could absorb a revert; (b) the checkpoint is a public authentication anchor for the preserved bridge surface (MSG-01), so its integrity must not depend on an external contract's revert discipline; (c) correctness must be readable from the function body rather than inferred from EVM unwind semantics. Verify-first costs nothing in gas terms that this specification claims to know — the cost of land(data, proof) is UNMEASURED and would be measured by a gas-snapshot run over a batch of the target size; no such measurement exists.

L1-04 — admission: no gate, no expiring range, any prover Any account MUST be able to call land(data, proof). The admission rules of land(data, proof) MUST contain: no whitelist and no allowlist (of provers, proposers, or relayers); no owner-, DAO-, or operator-controlled approval; no minimum bond, stake, or reputation to submit; no deadline, timestamp, block-number or age condition that can make a range permanently unacceptable; and no dependency on tx.origin, block.coinbase, gas price, or L1 proposer identity (GEN-06). For any unsettled range, any account that can produce a valid (data, proof) pair MUST be able to land it. No height is permanently retired (L1-06): in v1 no rule discards history above the latest L1-accepted checkpoint — every replacement mechanism is deferred by decision D-16 — and the contiguity rule firstBlockHeight = lastLandedHeight + 1 never skips a height, so every height is producible by any proposer as part of a batch that extends the current checkpoint. A batch at or below that checkpoint neither extends it nor becomes landable, but that rejection under L1-06 is ordinary contiguity, not a retirement record and not an expiry. (decision D-16: there is no discarded branch and no resumed chain in v1; the signed generation remains the binding a future replacement update would use, and the full-range-discard rules REC-02/REC-04 and GOV-04 are tombstones.) Structural bounds are permitted and MUST be exactly these: the range must start at firstBlockHeight = lastLandedHeight + 1 (L1-06), where contiguous means linked to the current checkpoint by exactly that equality — the chain never has a height gap, so the single checkpoint link is the ordinary successor relation of L1-06 (the restart linkage of REC-04 is a D-16 tombstone); the batch must be non-empty; the range length is the submitter's choice and no rule mandates a fixed or canonical length — a prover lands whatever contiguous range it has data and a proof for, so that settlement happens when the data is worth publishing rather than on a fixed clock; a racing submission that loses to another valid batch is void and its prover is not paid (L1-10), which is the disclosed cost of a permissionless landing market; and every loop in land(data, proof) must be bounded by the transaction's own contents (its blob count, its claimed range length), never by an unbounded external structure. (user decisions D-6 and D-16: the forced-inclusion coverage list and the FIFO-prefix loop bound were removed with the queue; the loop bound is the transaction's own contents only, and the forced-inclusion machinery that D-12 added is deferred by D-16 and MUST NOT be implemented.) Backpressure on production — the consensus-enforced unsettled-depth cap of HALT-03 and DA-06 — MUST NOT be implemented as an admission condition on land(data, proof). Publication is admission-free and the proving deadline is not an admission gate. Publication MUST be callable by any account with no gate of any kind (DA-07(1)), and the expiry of a publication record (DA-09) is a property of that record, never of the range: after it, the same unsettled range MUST still be landable by the carried path or against a fresh publication of the same data, and no rule may treat the range as expired, too old or permanently unacceptable. A lander that references a dead record MUST be rejected with a typed error and MUST be able to retry with carried data or a new record in the same or a later L1 block. (decision D-11: the deadline is a liveness control on a data record, not a new admission condition on finalized history.) Failure mode: a validly PoS-finalized extension of the L1 checkpoint becomes permanently unacceptable, i.e. a legitimate extension of history above the checkpoint can never be settled. The protocol may halt, and in v1 no path replaces history above the latest L1-accepted checkpoint: every replacement mechanism is deferred by decision D-16 (REC-02/GOV-04 are tombstones), and REC-01 forbids any path from touching history at or below it; an admission gate or an expiry removes the range from settlement outside any sanctioned procedure, so a valid proof can no longer settle it — the failure this rule forbids. (decision D-16: no replacement path exists in v1, and the no-gate, no-expiry admission rule is unchanged.) This rule is required under Mode B too, not merely compatible with it (04-architecture-decision.md §5.4, L1-ADMIT-NO-EXPIRY; research/mode-a-feasibility-analysis.md §4). Proven (the D-16 deferral of every replacement mechanism leaves the no-gate, no-expiry admission rule in force; decision D-11: a publication record's deadline is not an admission gate on the range)

L1-09 — proof-system policy, verifier routing and the L1 ability to move to a new circuit One closed acceptance policy: exactly one route per proof object. A batch is accepted only on exactly one valid proof object, checked against exactly one registered route. A route is the triple (programImageId : bytes32, verifier : address, backendFamily : bytes32); routeVersion is only the storage key that names the route, not a fourth semantic component. A route is ordinary; an aggregation route may exist only if a future update revives the deferred aggregation object, and in v1 there MUST NOT be an aggregation route (decision D-16: PRF-15 and L1-14 are tombstones, and no aggregation program may be registered or relied on). The verifier MUST be a deployed contract (verifier.code.length > 0) that implements the statement of PRF-01 and has been audited to it; a route whose verifier is not deployed, not audited, or whose checked image id differs from programImageId MUST NOT be registered, and a registration that would install one MUST revert. Acceptance is first-valid-wins (L1-10): two provers may submit proofs under different registered routes for the same range, and the first proof that verifies lands — but each individual proof is verified by exactly one route, and land(data, proof) MUST NOT require, and MUST NOT accept as a substitute, a second proof (this is PRF-09's closed policy).
Who may register a route: an upgrade, and no one else. Adding, changing or retiring a route is a rule change executed by an upgrade of the Inbox under GOV-02/GOV-03; it MUST NOT be callable at runtime by any account, owner, operator or DAO transaction (GOV-01: the DAO governs upgrades only). There MUST NOT exist a permissionless or owner-only registration entry point. The earlier sentence "enabling a new route is additive and MUST NOT be rejectable by any account" is deleted: it was a bridge-theft hole, because any account could have installed a verifier that returns abi.encode(true), after which any batch could be landed with an arbitrary state root. The permissionless requirement is L1-04's, and it applies to calling land(data, proof), never to changing the rules under which a proof is checked.
Routes MUST live in the Inbox's own storage — not in a mutable registry owned by another contract — because the baseline verifiers (SP1Verifier, Risc0Verifier) are non-upgradeable Ownable2Step contracts replaced by redeployment, and an upgrade of a verifier contract must never be able to change which statement the Inbox accepts. A route is usable for an epoch only when its image is in that epoch's accepted set (MIG-05, Inbox slot 261), which itself changes only by upgrade; MIG-05's per-epoch accepted set and this rule MUST agree, and a disagreement — a registered verifier whose image is not accepted for the epoch, or an accepted image with no deployed verifier — is a protocol defect, because it makes a PoS-finalized range unsettleable.
Every landed checkpoint MUST record the routeVersion used; that record is an Inbox mapping or the BatchLanded event and MUST NOT alter the frozen L1-07 checkpoint record. The accepted statementHash, daMode, the dataBindingSource and publicationId of L1-05 rows 34–35 (when the batch referenced a publication) are recorded alongside it, in the same side-mapping pattern, by L1-13, together with the accepting route's backendFamily as the first family attestation of that height. (decision D-11: a batch's data location is derivable from L1 state without altering the frozen record; decision D-16: no aggregation count is recorded, because a settlement proof attests no family set and each family attestation is a separate proof verified on L1.)
Backend families. backendFamily is a tag naming the independent implementation family a route belongs to, assigned at registration by the registering upgrade. It is the only object that makes "distinct backends" checkable on-chain: two routes carrying the same tag count once for the withdrawal-root family count of L1-13, and no rule may count two images of the same family twice. A family is live for an epoch when it has at least one route accepted for that epoch (MIG-05); only a live family may attest a withdrawal root for that epoch, and two routes of one family attest it once. (decision D-16: the canonical family index and the familyBitmap that decision D-13 defined over it are deferred with the aggregation object; the family tag itself is unchanged and is counted by attestation at L1-13(3).) The tag cannot be derived from a program image or a verifier address, so its correctness — that two tagged families really are independently implemented — is asserted by the registering upgrade and audited at migration under A-GOV-1; it is not an on-chain-verifiable property and no rule may claim it is. Changing, merging or splitting a family tag is a rule change under GOV-02/GOV-03, never a runtime call.
Retiring an image is not an ordinary operation: it is permitted only under the same procedure that governs a rule change (GOV-02, GOV-03), and MUST NOT be executed while any PoS-finalized-but-unsettled range could be proved only under the retired image. A new image MUST accept every history that the previous image accepted (PRF-10). (review round 1, finding B R1-14; review round 2, finding E-R2-04: the policy is one closed policy, registration is an upgrade and never permissionless, a route's verifier must be deployed and audited, and exactly one route is required per proof.) Failure modes: (a) a mutable external registry lets the verifier be re-pointed without the specification changing — the statement is then whatever someone wired up; (b) retiring an image while an unsettled finalized range depends on it makes that range permanently unprovable — a discard arriving through an upgrade; no v1 path may discard history at all — every replacement mechanism is deferred by decision D-16 (REC-02 and GOV-04 are tombstones) — and no upgrade may do it (04-architecture-decision.md §5.4, UPG-PRESERVE); (c) a runtime registration path, however framed, lets any account install a verifier that returns true and then land an arbitrary state root: complete loss of the proof system and bridge theft, since withdrawals authenticate against whatever checkpoint lands (MSG-03); (d) requiring two proofs when the policy is one — or one when the policy is two — silently changes both the security argument and the proving-fleet sizing. L1-13 — withdrawal roots: k distinct-backend attestations, one verification per attestation, and the exit during a stall (1) What a withdrawal root is. A withdrawal root is a checkpoint accepted under L1-07 that carries valid proofs of its own accepted statement from k distinct registered backend families, with k = K_PROOF_BACKENDS, n = N_PROOF_BACKENDS and 2 ≤ k ≤ n; both values are unmeasured and registered in 09. Families are the backendFamily tags of L1-09; two routes carrying the same tag count once, and a family counts only if its route's image is in the epoch's accepted set (MIG-05). The accepted statement is the PRF-02 journal the checkpoint was landed with, identified by the statementHash recorded at acceptance; the k-of-n policy adds verification of that one statement and never a second statement (PRF-14). The intended formation point is the epoch-boundary checkpoint — for epoch e, the record whose height equals h_last(e) under the L1-committed schedule (CONS-13(2)), which exists for every epoch the chain has settled past — but nothing in this rule may hold an exit for a new epoch: see (3), where any already-accepted checkpoint, and in particular the latest one, is attestable: its recorded statement, its family records and the epoch's accepted image set are L1 state that already exists, while each proof is produced off-chain and is funded per (5). (decision D-16: aggregation is deferred, so a root is k attestations verified on L1, not one aggregation proof, and the formation point is widened so the last accepted checkpoint is always attestable — which, given the proofs of (5), is what keeps the exit available during a stall.) This closes review round 7 finding F1: the widened formation point is a property of the attestation call, not of proof production, which is funded proving work under (5). (2) Only a withdrawal root finalizes a withdrawal. An L2→L1 withdrawal or message authentication (MSG-03) MUST be proven against the stateRoot of a withdrawal root at a height not below the height at which the signal was stored. A checkpoint that is not a withdrawal root MUST NOT anchor any value release, however many ordinary proofs it carries. A signal stored at any height h becomes releasable as soon as any withdrawal root at a height ≥ h exists; it is not tied to the epoch it was created in, so one epoch that fails to form a root does not by itself strand it. A withdrawal root is always at or below the current L1-accepted checkpoint, and nothing at or below that checkpoint is ever rewritten (REC-01). The release delay WITHDRAWAL_DELAY of MSG-03 is measured from the root checkpoint record's own l1BlockNumber (L1-07) — the L1 block that accepted it, never the attestation transaction and never a later settlement event — so the clock runs entirely on L1 state that already exists and is unaffected by a halt. (decision D-16: the delay is measured from the root and remains satisfiable while the chain is halted.) (3) How a root is formed, and why the exit survives a stall. At acceptance the Inbox MUST record, in a side mapping keyed by height, the accepted statementHash and daMode — the same side-mapping pattern L1-09 already uses for routeVersion, so the frozen L1-07 record is not altered. The route that accepted the batch counts as the first family attestation. Any account MAY then call attestWithdrawalRoot(height, programImageId, proof); the call MUST verify the proof against the recorded statementHash under a route whose image is in that epoch's accepted set (MIG-05) and whose family has not already attested that height, MUST reject a proof for any other statement with StatementMismatch, MUST reject a second attestation from the same family for the same height with FamilyAlreadyAttested, and MUST record the family. When k distinct families have attested, the height MUST be marked a withdrawal root and an event emitted. The attach path MUST NOT write a checkpoint, MUST NOT move L1-06's pointer, and MUST be permissionless. It is not a batch-acceptance transaction and publishes no batch data: the data is already canonical in the accepting transaction (DA-01) or in the publication record it referenced (DA-08), so D5 is not relaxed by this path, and an attestation can neither accept, advance nor replace a batch. The on-chain verification of an attestation MUST depend only on L1 state that already exists at the accepted checkpoint — the recorded statementHash, the recorded family attestations and the epoch's accepted image set (MIG-05) — which is the part an L1 contract can check. It MUST NOT require a new L2 block, a new batch, a new checkpoint, an epoch boundary or any settlement progress; the statement it attests is the recorded one. The proof itself is not derived from L1 state: it is produced off-chain from the accepted certificate, the batch's data and the pre-state witness, and any account may supply it; producing it is funded proving work under (5). In particular, the latest L1-accepted checkpoint MUST be attestable by this path at any time while the chain is halted: the call admits an attestation for it whenever the chain is halted, the statement and the accepted image set it checks are already on L1, and the release delay of (2) continues to run on the L1 clock all the while. A settlement stall therefore cannot make the path unavailable at the contract; whether a root actually forms depends on the k−1 proofs being produced and paid for, which (5) fixes and MEM-15(2b) discloses as an assumption with its falsifier. An image upgrade or retirement MUST NOT remove an attestation already recorded, and PRF-10's preservation clause — a new image MUST accept every history the previous image accepted — applies to the recorded statementHash, so an upgrade does not by itself strand an un-attested checkpoint. (decision D-16: the exit contradiction is resolved here — the root for the last accepted checkpoint is attestable permissionlessly, with no new L2 blocks and no settlement progress; the proofs it needs are produced off-chain and funded under (5).) This closes review round 7 finding F1: the unenforceable "the attestation depends only on L1 state" MUST is replaced by the checkable L1-side claim, and the off-chain proving dependency is stated rather than denied. (4) The cost is one verification per attestation, never per batch. One root costs k on-chain verifications and k−1 additional proofs beyond the accepting one. Ordinary settlement is untouched: a batch is still accepted on exactly one proof (L1-09, PRF-09), and the additional proofs are produced only for the checkpoints that are actually designated as roots. The additional proofs for one root are independent and MAY be produced in parallel, so the added latency is the slowest of them, not their sum. Requiring k proofs per checkpoint rather than only for designated roots would cost (k−1) additional proofs per batch, and is not proposed; if S1 measures the per-root multiplier as unaffordable, the fallback is stated in (7), never a silent k = 1. (decision D-16: one verification per attestation on L1, and the aggregation route that would have moved them inside one proof is deferred.) (5) Exit-path liveness is weaker than settlement liveness, and is stated. Forming roots depends on k independent implementations being available. If one family is temporarily unavailable, a signal waits for a root that k available families attest; because (3) allows any already-accepted checkpoint to be attested, the wait is for the attestations, not for a new epoch or new blocks. If fewer than k families have a live accepted route for every subsequent epoch, no new root is formed and signals cannot be released. The value is not lost — it stays in the preserved Bridge and vault contracts — but the exit is delayed indefinitely. W_ROOT_WAIT_MAX = E_EPOCH + T_PROOF_MAX_PERMITTED, registered in 09, is the maximum additional wait only while at least k families operate; outside that condition the wait is unbounded. 4. Races, fees, and L1 reorganisation

L1-10 — submission races, re-submission, and what a proof is a proof of The first valid submission wins. Concretely: land(data, proof) MUST be atomic with respect to the checkpoint pointer, so two transactions in one L1 block are ordered by L1, the first one advances lastLandedHeight, and the second MUST revert AlreadyLanded() if it targets an overlapping or duplicate range, or MUST be evaluated against the new checkpoint if it extends it. Re-submission of the same batch (same dataCommitment, same range) by a different account MUST be accepted whenever the first submission did not land; it MUST NOT be rejected because another account previously submitted, attempted, or announced the same range. A proof is a proof of exactly the statement of L1-05: a proof for a different batch — a different range, a different predecessor, a different data commitment, a different epoch or set root — MUST NOT be usable as a substitute, and MUST fail verification because those values are in statementHash. The reward of L1-11 MUST be paid to msg.sender, the account that paid for the landing transaction; the protocol MUST NOT attempt to attribute it to any address named inside the proof. Consequently, a proof observed in the public mempool can be landed first by another account, which then collects the reward; this is an accepted property of permissionless landing, not a defect to be patched with a first-submitter reservation, and the mitigation available to provers is private orderflow or bundling. Failure modes: (a) a first-submitter reservation is a permissioned gate that expires a range into unrecoverability when the reserving account disappears (L1-04); (b) accepting a proof for a different batch lets a prover attach a valid proof to unrelated data — the whole point of binding the data commitment is that it cannot be done; (c) paying the reward to a proof-declared address lets anyone who copies a proof redirect the payout and makes the identity of the prover unfalsifiable. DA-01 — the canonical data-availability location is the transaction the accepted statement binds The canonical copy of a batch's data MUST be exactly one of: (a) the accepting L1 transaction itself — its calldata and/or the blob sidecars of that same transaction, as bound by DA-02 and DA-03 — or (b), under decision D-11, the L1 transaction whose blobs a publication record names, where the accepting transaction references that record and the statement binds its effects (DA-07, DA-08). A batch is accepted on L1 only together with a binding to one of those two locations, and the Inbox MUST record which one in the side mapping of L1-09. A batch MUST NOT be accepted with the two in conflict: when the accepting transaction both carries the blobs and references a record, the two sets MUST agree element-wise (DA-08(2)). The design MUST NOT define a third canonical location, and MUST NOT treat any location outside (a) and (b) as sufficient for STATUS-06. (decision D-11: data may be published before the proof; the canonical location is the one the accepted statement binds, not necessarily the accepting transaction.) Failure mode: two canonical locations means two answers to "what is the batch?", and the weaker one is the one an implementer will build against. The two locations above are not two answers for one batch: exactly one binding is recorded, the referenced case requires the record to agree with the statement field for field, and the carried-and-referenced case requires the two to agree with each other. Proven Open (the referenced location's binding is DA-08's; its one Open part is the rejected precompile-less variant there.)
DA-02 — calldata path: the contract computes the data commitment itself In the calldata path the Inbox MUST compute the data commitment itself over the exact calldata slice supplied to land(data, proof), and MUST pass that value as the public input. The construction is fixed as: 
dataRoot       = keccak256(_data)                      // one byte string: no field ambiguity
payloadRoot    = dataRoot
dataCommitment = keccak256(abi.encode(
                     bytes32("TAIKO_ETNA_DATA"),        // right-padded ASCII domain tag (GEN-05)
                     uint256(block.chainid),            // chain id is the second field (GEN-05)
                     uint64(firstBlockHeight),
                     uint64(lastBlockHeight),
                     uint8(daMode),                     // 1 = CALLDATA, 2 = BLOB, 3 = CALLDATA_AND_BLOB;
                                   // DA-03(0) fixes payloadRoot per mode
                     payloadRoot))
keccak256(_data) hashes one opaque byte string rather than a concatenation of fields, so it introduces no second-preimage ambiguity and is not an abi.encodePacked of multiple values. The committed object is the whole _data byte string — no prefix of it. For daMode = 2 the same outer encoding is used with payloadRoot = keccak256(committedBytes) defined in DA-03(0); for daMode = 3 DA-03's hybrid payloadRoot replaces the calldata-only value so that the full blob strings are inside the commitment. (review round 1, findings B R1-01, B R1-06) The byte-level layout of _data — how L2 blocks serialise into the batch payload — is fixed once, on PRF-07; this rule fixes only how L1 commits to it. The guest MUST recompute dataCommitment from the payload it actually executed, and MUST reject the batch if the recomputation differs. Because both sides hash the same whole byte string, this path needs no probabilistic argument and remains the unconditionally sound path; the blob path (DA-03) is the one that carries the fixed-point argument and is an implementation gate. On this calldata path the Inbox MUST ignore any submitter-supplied dataCommitment; if one is present in the input it MUST either be absent from the ABI or be checked equal and rejected with DataModeMismatch() on mismatch. (On the blob path the EVM cannot read the bytes, so the claimed value is proof-bound and completed in-guest instead; when the blobs are not carried by the accepting transaction it is additionally bound to the referenced publication record by DA-08(1); see DA-03(0).) Failure mode: taking the commitment from the submitter decouples the proof from the calldata, so a valid proof can be paired with arbitrary data in the same transaction — the strongest and simplest binding available is thrown away. DA-03 — blob path: whole-blob commitment, recorded or same-transaction hashes, on-chain KZG opening, and in-guest evaluation at the per-blob challenge point For a batch whose data is in blobs, let n = blobCount and let blob index i range over [blobIndexStart, blobIndexStart + n). The Inbox MUST perform (i) and (ii) for every i, and the guest MUST perform (iv) and (v).
(0) What is committed. dataCommitment commits the whole published byte string that the guest executes and that L1 publishes, not a prefix of it. For daMode = BLOB the committed object is the concatenation, in blob index order, of the full 131,072-byte string of every blob in the transaction — all 4096 field elements per blob, including any unused remainder; for daMode = CALLDATA_AND_BLOB it is the batch calldata payload followed by that same concatenation. Every published byte is inside the commitment, and the unused remainder of a blob MUST be committed too. No prefix-only commitment is permitted. A commitment over a prefix (the first k field elements, the non-zero prefix, or the portion the payload "uses") is forbidden: if the commitment covered only a prefix, the challenge point would be fixed before the free suffix was chosen, and a prover could choose the suffix to satisfy p_D(z) = p_B(z) by solving one linear equation — that was the round-1 attack. The encoding is DA-02's outer encoding, with daMode set to the derived mode and: 
committedBytes = blob_0 || blob_1 || ... || blob_{n-1}      // each exactly 131,072 bytes (4096 elements)
payloadRoot    = keccak256(committedBytes)                  // daMode = BLOB
dataCommitment = keccak256(abi.encode(bytes32("TAIKO_ETNA_DATA"), uint256(block.chainid),
                                      uint64(firstBlockHeight), uint64(lastBlockHeight),
                                      uint8(daMode), payloadRoot))
// HYBRID (daMode = 3): payloadRoot = keccak256(abi.encode(bytes32("TAIKO_ETNA_HYBRID"),
//        uint256(block.chainid), keccak256(_data), keccak256(blob_0 || ... || blob_{n-1})))
The EVM cannot read blob contents, so on the blob path — and for the blob component of hybrid — the contract cannot recompute payloadRoot: it takes the claimed dataCommitment, binds it into statementHash and derives z_i from it, while (v) requires the guest to recompute the same value over the full blob bytes it executed. The value is therefore not a free submitter choice: a wrong value makes the proof unverifiable rather than making the contract misbehave. (review round 1, findings B R1-01, B R1-06)

(i) BLOBHASH equality — the carried case. When the accepting transaction carries the batch's blobs, the Inbox MUST read the transaction's own blob versioned hash with the BLOBHASH opcode and require, for each i:

bytes32 vh = blobhash(i);
require(vh != bytes32(0) && vh == _input.blobVersionedHashes[i - blobIndexStart], BlobHashMismatch(i));

A zero value means no blob at that index in this transaction; because BLOBHASH is transaction-scoped, no other transaction's blobs can be substituted. The loop is bounded by the transaction's own blob count, whose protocol limit is the Ethereum per-block limit — target 6, maximum 9 blobs per block under EIP-7691 sourced.

(i′) Recorded-hash equality — the referenced case. When the accepting transaction does not carry the blobs, this check is unavailable and MUST NOT be attempted: BLOBHASH is transaction-scoped and returns bytes32(0) for a blob the executing transaction does not carry, so a check against it would either revert on every honest batch or — worse — be satisfied by a different blob the transaction happens to carry. The contract instead takes each vh_i from the referenced publication record, after DA-08(1) has checked the record's identity, immutability, range, daMode, dataCommitment and blobHashesHash against the statement. Steps (ii)–(v) are then unchanged. (decision D-11: the recorded hash replaces the same-transaction hash; the opening, the challenge derivation and the guest's checks are identical.)

(ii) On-chain KZG point evaluation. The Inbox MUST call the EIP-4844 point-evaluation precompile at address 0x0A with the 192-byte input abi.encodePacked(vh, z_i, y_i, commitment_i, proof_i) — z_i and y_i as 32-byte big-endian canonical field elements, commitment_i and proof_i as 48-byte compressed BLS12-381 G1 points. The call MUST succeed and MUST return exactly abi.encode(4096, BLS_MODULUS); otherwise land(data, proof) reverts BlobOpeningFailed(i). The precompile verifies kzg_to_versioned_hash(commitment_i) == vh and verify_kzg_proof(commitment_i, z_i, y_i, proof_i), and rejects non-canonical field elements. Its gas cost is 50,000 per call sourced (EIP-4844), so a batch using n blobs costs 50,000 · n gas for these calls derived; the total cost of land(data, proof) remains UNMEASURED.

The precompile is not transaction-scoped. Its input is (versioned_hash, z, y, commitment, proof) and it verifies the opening of the supplied commitment against the supplied versioned hash; it never reads the executing transaction's blobs. In the referenced case the Inbox therefore passes the recorded versioned hash of (i′) as vh and the call succeeds with no blob present — commitment_i, proof_i and y_i are submitter-supplied and proof-bound exactly as in the carried case. This is what preserves the binding in the referenced case: the recorded hash is the commitment's identity, not a label chosen at landing. (decision D-11: a proof referencing a previously published blob keeps the on-chain opening; what it loses is only same-transaction equality.)

(iii) The challenge point z_i is derived on-chain by Fiat–Shamir, per blob. It MUST NOT be supplied by the submitter. With statementCoreHash the hash of the whole PRF-02 public-input vector except the two challenge fields challengeZ/evaluationsY themselves — so the transcript covers daMode, feeRecipient, configHash, blobHashesHash, signerBitmap and every other input, but not the values it derives — the Inbox MUST compute, for each blob index i:

z_i = uint256(keccak256(abi.encode(
          bytes32("TAIKO_ETNA_CHALLENGE"), uint256(l2ChainId), statementCoreHash,
          dataCommitment, blobHashesHash, uint16(i)))) % BLS_MODULUS;

The domain tag, l2ChainId (Inbox config), statementCoreHash, dataCommitment, blobHashesHash and the blob index are all inside the transcript, so the challenge moves whenever the committed bytes move: dataCommitment commits the whole published byte string (0) and blobHashesHash commits the ordered versioned hashes. On the blob path the contract takes dataCommitment from the proof-bound input (0) and the guest recompletes it from the executed bytes in (v), so dataCommitment and z_i cannot be chosen independently of the executed payload. The modulus reduction is required because a keccak-256 output is not automatically a canonical scalar (BLS_MODULUS < 2^255), and the precompile rejects non-canonical elements. The reduction biases the distribution by at most ceil(2^256 / BLS_MODULUS) / 2^256 ≈ 1 / BLS_MODULUS ≈ 2^-254.9 in statistical distance (an earlier revision stated BLS_MODULUS / 2^256 ≈ 2^-127, which inverted the ratio and understated the bias by roughly 127 bits; the union bound is unaffected) derived, which is irrelevant to the 2^-243 bound below. The blob index i is inside the transcript so that two blobs of the same batch never share a challenge.

(iv) The guest proves the evaluation of the data it executed, in the EIP-4844 convention. The guest receives (vh_i, z_i, y_i) as public inputs and the blob bytes as part of the data it executed. It MUST interpret each 131,072-byte blob exactly as EIP-4844 does: the 4096 big-endian field elements are the evaluations of the committed polynomial in bit-reversed order over the 4096th roots of unity — element j is the evaluation at ωbrp(j), where brp is the bit-reversal permutation of the 12-bit index — which is what blob_to_kzg_commitment commits to, g1_lincomb(bit_reversal(setup_lagrange), blob). They are not coefficients of p(X). The guest MUST use this same convention (inverse bit-reversal plus Lagrange interpolation over the evaluations, or an equivalent FFT) or every honest blob proof fails; any other interpretation is invalid. It MUST reject the batch if any element is ≥ BLS_MODULUS, and MUST reject it unless p_data,i(z_i) == y_i.

(v) The guest recompletes the data commitment. The guest MUST recompute payloadRoot = keccak256(committedBytes) and dataCommitment from the full blob byte strings it executed with the (0) construction — every blob, every byte, no prefix — and MUST reject the batch unless the result equals the journal value used in (iii). This is what makes the claimed blob-path dataCommitment proof-bound.

Why this is sound (the joint event, not a fixed challenge). The chain is: (a) blobhash(i) names the blob that is in this transaction; (b) the precompile establishes kzg_to_versioned_hash(commitment_i) == vh_i, so commitment_i is the KZG commitment of that blob's polynomial p_B,i; (c) the precompile's verify_kzg_proof establishes p_B,i(z_i) = y_i; (d) the guest establishes p_D,i(z_i) = y_i over the payload D it executed, and (v) requires dataCommitment to be recomputed from that same D. Therefore (p_D,i - p_B,i)(z_i) = 0. But z_i is not fixed while D is chosen: z_i is a deterministic function of the transcript that contains dataCommitment = f(keccak(D)). The event a cheating prover needs is the joint event p_D(z(D)) = p_B(z(D)) with z(D) derived from keccak(D) — a fixed-point condition, not a linear equation in the free part of D. Stated as a search over hash outputs: for any fixed D the difference is a non-zero polynomial of degree ≤ 4095 with at most 4095 roots, so an evaluation at the pseudorandom point z(D) agrees with probability at most 4095 / |F| ≈ 2^-243 derived, and a search over q candidate payloads succeeds with probability at most q · 2^-243 (plus the 2^-254.9 reduction bias). The earlier statement of the bound "per attempt at a fixed challenge" was wrong: it assumed D was fixed before the challenge, which is exactly what (0) and (iii) prevent. D is moreover not a free variable: the executed payload is bound to the certified header chain — the certificate covers the head block id, the header chain links to the predecessor and each header's transaction root fixes its transactions (PRF-04(v), PRF-06) — so a prover cannot vary D after the certificate is signed without invalidating it. Hence, with overwhelming probability, p_D,i = p_B,i: the guest executed exactly the data the blob commits to. (review round 1, findings B R1-01, B R1-02)

The referenced case changes one link of that chain. Link (a) becomes (a′): the recorded versioned hash of the referenced publication names a blob that was published in the publication transaction, which the consensus layer checked against the actual blob sidecars when that block was processed sourced (EIP-4844); the Inbox checks the record's identity, immutability and field equality with the statement (DA-08(1)) and the record's liveness (DA-09). Links (b)–(d) and the joint fixed point are identical, because the precompile does not require the blob to be in the executing transaction. The variant that omits the precompile on the referenced path is rejected as unsound: a binding of "recorded hash plus in-guest evaluation" would evaluate the polynomial over the very bytes the guest already executed and tie them to nothing, so the recorded hash would bind nothing about the executed payload. Binding the executed bytes to the recorded commitment without the precompile requires the guest to recompute each blob's KZG commitment from the executed bytes (an MSM) or to verify the opening in-guest (pairings); both are UNVERIFIED on both backends (PRF-11, 03), so that variant is Open and MUST NOT be relied on. What the referenced case does not preserve is same-transaction availability of the bytes; that is a liveness property handled by DA-05's archive duty and DA-09's deadline, not a soundness property of this binding. (decision D-11.)

Premises. This argument requires all five of: (1) KZG binding for blob commitments (A-CRYPTO-3); (2) the random-oracle model for the Fiat–Shamir derivation of z_i; (3) correct in-guest field arithmetic over the BLS12-381 scalar field, including the exact bit-reversed evaluation-form interpretation and Lagrange interpolation; (4) canonical field elements in both the blob and the guest's field elements (evaluation form); and (5) the in-guest recomputation of dataCommitment over the full blob bytes of (0)/(v). The referenced case adds one premise: (6) the publication record of DA-07 is immutable, its identity is recomputed by the Inbox from its stored content, and its recorded versioned hashes are the ones consensus checked against the published blob sidecars — established at publication by the element-wise blobhash equality DA-07(5) requires and not assumed (review round 5, finding R5T-PDE-02). If any premise fails, the binding does not hold. This is a proof sketch with named premises, not a machine-checked theorem, and adversarial review question Q-A3 is carried against a grinding prover (04-architecture-decision.md §7).

Provenance and honesty. This construction was derived in this project (04-architecture-decision.md §4.1); it is not an established published design and has no implementation. It is an implementation gate: it may not be relied on until the fixed-point argument above has had independent cryptographic review and its in-guest cost has been measured. Its in-guest cost is UNMEASURED; measuring it requires an implementation of the in-guest evaluation on both backends with cycle counts at a stated blob size, which does not exist (04-architecture-decision.md §7, item F2). In-guest MSM and in-guest pairings are deliberately avoided, because the zkVM feasibility work found them UNVERIFIED on both backends: the guest performs field arithmetic and Lagrange evaluation only, and the pairing happens on L1 inside the precompile (PRF-11). The alternative to measure is the RISC Zero patched c-kzg library, which would put a different and larger trusted computing base inside the guest. Precompile semantics, address and gas are cited from EIP-4844; blob counts from EIP-7691.

Failure modes: (a) a submitter-chosen z, or a commitment that covers only a prefix of a blob, lets a prover pick the evaluation point after fixing part of its data, which reduces the binding to a single linear equation it can solve; (b) accepting a blob versioned hash from bare calldata — instead of reading it with BLOBHASH in the carried case or from an immutable publication record in the referenced case — lets a transaction reference blobs it never published; (decision D-11); (c) performing the KZG opening in-guest would require MSM and pairings that are unverified on both backends, i.e. an unquantified soundness assumption; (d) without the canonical-field-element requirement the guest's polynomial is ambiguous, and two different byte strings map to the same polynomial; (e) without (0) and the EIP-4844 convention of (iv), an honest prover computes a different polynomial and every blob-path batch fails. Proven sourced derived unmeasured Open (measured in-guest cost; independent cryptographic review of the fixed-point argument; review question Q-A3; the referenced case reuses the precompile and adds only premise (6) — decision D-11)

DA-04 — no witness, certificate or off-chain store substitutes for on-chain data None of the following may be used, alone or in combination, to satisfy DA-01: the prover's private witness or any hint stream; a validity proof of any kind; a committee, quorum, or validator attestation; a "data-availability certificate"; a bare blob reference — a versioned hash or blob index with neither the blob in the accepting transaction nor an L1 publication record naming it (DA-07). A recorded publication is admissible under DA-01(b) and is not a bare reference: the record is immutable L1 state, its identity is recomputed by the Inbox, and the opening of the blob it names is verified on-chain (DA-08(3)). (decision D-11: what replaces "the blob must be in this transaction" is "the blob must be named by a record the Inbox verifies", not "the prover says so".) The following remain inadmissible in every case: an external DA layer, an off-chain store (HTTP, IPFS, S3, a node's local disk), or an operator promise. The guest MUST NOT be able to execute a batch whose payload it received only through a private witness while the corresponding public data is absent: the data commitment of DA-02/DA-03 MUST be computed over data that is at the location the accepted statement binds — the accepting transaction, or the transaction named by the live publication record (DA-08(1)) — and never over data that exists only in the witness. (decision D-11.) Failure mode: the protocol claims availability while the only party who can reconstruct the batch is the prover, which is exactly the "certified-but-unavailable" class that the architecture decision records as Mode A's strongest counterexample (04-architecture-decision.md §5.1). DA-05 — retrievability window, archive requirement, and the blob-retention limit Blobs are not a permanent store. Ethereum guarantees blob sidecar retrievability for MIN_EPOCHS_FOR_BLOB_SIDECARS_REQUESTS = 4096 epochs sourced (EIP-4844), which is roughly 18 days at Ethereum's present slot cadence derived — the design does not depend on that wall-clock figure and expresses the window in epochs and L1 block numbers (GEN-06). Calldata is not permanent either: on the p2p layer clients stop serving historical headers, bodies and receipts older than 14,299 epochs sourced (EIP-4444, recorded in research/recovery-and-withholding-raw.md). The design therefore MUST specify, in 09: (a) a RETRIEVABILITY_WINDOW in L1 block numbers, not shorter than the blob-retention window; (b) an ARCHIVE_REQUIREMENT fixing how many independent archive nodes must retain the full accepting-transaction calldata and full blob sidecars, and, for every batch whose data was published earlier, the full blob sidecars of its publication transaction (DA-07), for at least that window, with the duty owned by ROLE-03; (c) the statement that past the window, retrievability depends on those archives and not on Ethereum. Under D-11 this failure class is deliberate and bounded, not absent: data may be published before the proof, so there is an interval in which a batch's data is on L1 while its proof is not. The interval is bounded by the proving deadline of DA-09, which MUST be inside the blob-retention window, and by the fact that publication writes no batch state (DA-07(2)); for a referenced batch the retention clock that matters starts at publication, not at acceptance, and the archive duty above covers the publication transaction's blobs for the whole window so the data remains retrievable after the deadline and after acceptance. (decision D-11: the interval D5 eliminated is accepted, disclosed and bounded rather than denied.) In-repo evidence that this failure class is real, not hypothetical: at revision 7718753c1, init3() (Inbox.sol:246-258) is a one-time onlyOwner function that voids a queue of pending entries by moving the queue head to the tail, and its NatSpec states the reason — the skipped entries' blobs have expired from the blob retention window and can no longer be derived after the June 2026 incident. 04-architecture-decision.md §4 records the same finding. The queue init3() voided belonged to the baseline design, not to this specification; what it demonstrates is the data-expiry failure class that any design publishing data before a proof re-creates — the class decision D-11 now accepts with the deadline of DA-09 as its control, and whose forced-inclusion consequence was the FI-* family's, deferred with that machinery by decision D-16 (DA-10 is retained unread). (decision D-11: the interval is bounded by a proving deadline inside blob retention; the baseline queue itself is not a mechanism of this specification.) Proven sourced derived
DA-06 — retention duty and its link to the backlog cap There is exactly one production-side cap: the unsettled-depth cap D_MAX of HALT-03, expressed in L2 blocks and derived there as D_MAX = floor((RETENTION_WINDOW − T_PROOF_MAX_PERMITTED − T_SETTLE_PIPELINE) / L2_BLOCK_INTERVAL). RETENTION_WINDOW is in seconds and is the assumed retrievability duration of unsettled L2 data held by validators and nodes (ROLE-03, A-CONS-5), not the retention of any L1 artifact; every term is registered in 09. The cap exists because of this retention duty: without it, blocks keep being finalized whose data ages out of that window before any proof exists, the batch then cannot be proven by anyone, and no rule discards it at all: decision D-16 defers every replacement mechanism, so v1 has no discard-and-restart (REC-02 and GOV-04 are tombstones). (decision D-16: the chain may halt on such a range, and clearing the stall requires a future protocol update; neither the withdrawn permissionless recovery nor the deferred governance action is a rule of this specification.) Correct validators MUST refuse to vote for a block whose unsettled depth would exceed D_MAX − MARGIN_V (HALT-03): the cap is a rule on production and has exactly one enforcement point, and it MUST NOT be applied to land(data, proof) (L1-04, L1-06), because refusing an available, valid proof would strand finalized history. When the cap binds, the honest outcome is a safe halt (HALT-01), never a rollback.
Relation to the post-acceptance retention window. RETRIEVABILITY_WINDOW (DA-05) is a different object in a different unit: it is an archive duty over the accepted artifacts — the accepting transaction's calldata and blob sidecars — measured in L1 block numbers and starting at acceptance. It is not a cap and not an input to D_MAX; they measure different objects at different times and MUST NOT be combined into one inequality, so the earlier inequality that mixed them is deleted. The one obligation that remains on the post-acceptance side is stated in its own unit: RETRIEVABILITY_WINDOW MUST be at least the blob-retention window (DA-05(a)) and, converted to seconds at Ethereum's fixed slot cadence, at least W_EVIDENCE (ECON-07, registered in 09), so an accepted batch's artifacts stay retrievable at least as long as evidence about it can still be submitted. The former second cap MAX_UNSETTLED_AGE (an L1-block distance) is deleted as redundant: it restated D_MAX in a second unit, so an implementer could satisfy one and violate the other. (review round 2, findings R2-LIV-07 and R2-LIV-08: one cap, one unit, one enforcement point — production — and no second window standing in for it.)
Relation to the publication deadline, and what it is not. T_PROVE_DEADLINE (DA-09) is a third object in a third unit: it is a per-record clock on one publication, measured in L1 blocks from the record's own l1BlockNumber, bounding how long that record may be referenced before its blobs leave the retrievability window. It is not a cap, it is not production-side, and it MUST NOT be combined with D_MAX into one inequality: D_MAX bounds how much unsettled L2 history may be produced, and the deadline bounds how long a dead record may be presented as live data. (decision D-16: the forced-inclusion work bound of D-12 is deferred with that machinery and is not a v1 rule; one backpressure cap stays HALT-03/DA-06's D_MAX.) The two compose rather than overlap: the cap keeps the unsettled range provable from data validators and archives hold, and the deadline keeps every referenced record inside the blobs' retrievability. Missing the deadline is a liveness event on a record — recoverable by carrying the data or re-publishing it (DA-09(2)) — and MUST NOT be turned into a second admission condition on land(data, proof) (L1-04). (decision D-11: one production cap is unchanged; the publication deadline is a data-record clock, explicitly not a second cap.) Failure mode: without the cap, blocks keep being finalized whose data ages out of the retention window before any proof exists; the batch then cannot be proven by anyone, and v1 has no path that replaces it: decision D-16 defers every replacement mechanism (REC-02/GOV-04 are tombstones), so the chain stays stuck on a range whose data no longer exists anywhere the protocol promised until a future protocol update. The cap converts an unbounded failure into a halt, and it does so as a consensus rule on production, not as an L1 admission gate that would refuse a valid proof and strand finalized history. (decision D-16: clearing the stall requires a future protocol update whose procedure is not yet specified; neither the withdrawn recovery's bond and delay nor the deferred governance action is a rule of this specification.) Proven unmeasured (D_MAX, RETENTION_WINDOW, MARGIN_V, T_PROOF_MAX_PERMITTED, T_SETTLE_PIPELINE, RETRIEVABILITY_WINDOW and the publication deadline's T_PROVE_DEADLINE are unmeasured parameters; all are fixed in 09 — decision D-11)

5.1 Publication before proof: the record, the reference and the deadline (D-11)

DA-07 — permissionless publication of a batch's data, and the publication record's identity (1) The path. Any account MUST be able to publish a batch's data — the whole committed byte string of PRF-07(0) — to L1 in a type-3 transaction, and have that transaction's blob versioned hashes recorded on L1 while the blobs are still retrievable. The entry point is publish(...); it MUST be permissionless: no whitelist, no allowlist, no bond, no fee to the protocol, no owner, operator or DAO approval, and no dependency on tx.origin, block.coinbase, gas price or L1 proposer identity (GEN-06). There MUST NOT be more than one publication entry point. (decision D-11: publication is the permissionless step that collapses the withholding window; withholding then requires that no observer publish at all.) (2) What publication writes, and what it never writes. A publication writes exactly one publication record: the blob range's ordered versioned hashes read with BLOBHASH in that transaction, the claimed batch range, data commitment and daMode it was published for, the L1 block number, and a monotonically increasing sequence number. It MUST NOT write a checkpoint, a batch record, a predecessor link, a claimed post-state, a route, or any value read by any admission check of the carried path; it MUST NOT move lastLandedHeight; and it MUST NOT be a precondition for land(data, proof) (L1-02). Data sitting in blobs has no effect on the protocol's L1 state: it becomes relevant only when a proof references it (DA-08), and the protocol state still advances only on a valid proof (L1-01). This is why the publication path is not the "data-first path" D5 forbade. (decision D-16: the forced-inclusion rule that would have reused this record as its forced-data register is deferred with the whole FI-* machinery, so this record is D-11's data-availability object only; DA-10's anchor is retained and is not read by any v1 rule.) The register's ordered view. The register MUST expose each record at its stored sequence index together with the record's stored l1BlockNumber, and l1BlockNumber MUST be non-decreasing in sequence — the counter is assigned in the L1 block that writes the record — so a record's position is derivable from L1 state in one bounded lookup. (decision D-16: the FI-11 due-frontier dependency and the row-36 forcedBoundary recomputation are deferred with the forced-inclusion machinery; the ordering property is retained because it costs nothing and is what any revived mechanism would need.) (3) The identity. A record's identity MUST be recomputable by the Inbox from the record's own stored content, so a caller cannot point at a record with a label that says something else:
publicationId = keccak256(abi.encode(bytes32("TAIKO_ETNA_PUBLICATION"), uint256(block.chainid), uint256(l2ChainId), uint64(firstBlockHeight), uint64(lastBlockHeight), uint8(daMode), bytes32(dataCommitment), bytes32(blobHashesHash), uint64(l1BlockNumber), uint64(sequence))),
where blobHashesHash = keccak256(abi.encode(bytes32("TAIKO_ETNA_PUBLICATION_HASHES"), uint256(block.chainid), bytes32[](orderedVersionedHashes))) and sequence is the Inbox's monotonic publication counter; both encodings follow GEN-05 (domain tag and chain id first, one canonical abi.encode, never abi.encodePacked). The sequence is stored with the record. Two publications of identical data are two records with different identities — this is what lets a dead record be replaced by a fresh one without a new rule (DA-09(2)) — and a record is immutable once written. A caller-supplied publicationId that does not equal the recomputation from the stored record MUST be rejected with PublicationIdentityMismatch(). (4) What publication does not prove, and what it does not privilege. The EVM cannot read blob contents, so the claimed range, dataCommitment, daMode and payload framing are claims. A record with wrong claims can never be used by a valid proof, because the accepting statement's journal must equal the record's fields and the guest recompletes the commitment (DA-08(1), PRF-07(b)(v)); a bad record therefore harms its publisher and nothing else. Multiple records for one range MUST be permitted, and no rule may prefer one publisher's record over another: the accepting proof names the record it binds, and permissionless publication is not a first-publisher right. (5) Liveness, and the recorded hashes are the transaction's own blobs'. The publication transaction MUST carry the blobs of its whole claimed range — the Inbox MUST require blobhash(i) != 0 for every index in it, reverting PublicationBlobRangeInvalid(i) otherwise — so the data is on L1 and retrievable when the record is written. The recorded hashes MUST be checked against those blobs, element-wise. The _blobVersionedHashes argument of L1-08 is calldata and is never authoritative: the Inbox MUST require _blobVersionedHashes.length == _blobCount and, for every i in [0, _blobCount), _blobVersionedHashes[i] == blobhash(_blobIndexStart + i), reverting PublicationBlobHashMismatch(i) on any mismatch; the equivalent permitted form is to read the hashes with BLOBHASH and ignore the argument, and there is no third form. blobhash returns the versioned hash the consensus layer derived from the blob's commitment (kzg_to_versioned_hash, EIP-4844), so element-wise equality is exactly the provenance that premise (6) of DA-03 needs, and the recorded hash list is the transaction's own blob entries, in range order. More hashes than blobs, or fewer. The claimed range MUST contain at least one blob. A publication that supplies more hashes than the transaction carries blobs in the range is rejected at the first index whose blobhash is zero or differs (PublicationBlobHashMismatch, never a stored zero and never an invented hash); one that supplies fewer than _blobCount is rejected by the length equality before any hash is written; and blobs the transaction carries outside [_blobIndexStart, _blobIndexStart + _blobCount) are not recorded and are not part of the record. No record may be written whose ordered hash list is empty or contains a hash with no corresponding blob. (review round 5, finding R5T-PDE-02: DA-07(5) checked only that the recorded versioned hashes were non-zero while the ABI took them as calldata, so premise (6) of the DA-03/DA-08 referenced binding was unchecked; the element-wise blobhash equality is now a required check, and the mismatch cases are stated.) The record's proving deadline and the consequence of missing it are DA-09's. Failure mode: a publication path that writes batch state or gates acceptance becomes the propose-then-prove path L1-01 forbids; one that is permissioned becomes a censorship lever; and one whose record identity is a free label lets a proof point at a record that says something other than what it verified. Proven derived unmeasured (the path and identity are specified; the gas of publish and of a record lookup is UNMEASURED — decision D-11)
DA-08 — landing against a recorded publication: carried, referenced, or both (1) The reference. land(data, proof) MAY name a publicationId (L1-05 row 35). If it does, the Inbox MUST load that record, MUST recompute its identity from the stored content (DA-07(3)) and reject a mismatch, and MUST require: the record's l2ChainId is this Inbox's L2 chain; its (firstBlockHeight, lastBlockHeight), daMode and dataCommitment equal the statement's own range, mode and dataCommitment; its blobHashesHash equals the journal's blobHashesHash; and the record is live (DA-09). Any mismatch MUST revert with PublicationMismatch(publicationId) and produce no partial effect (L1-03). The record does not enter the journal: the journal binds its effects (rows 6, 7, 16, 24), so two records of the same data yield the same statement and the same proof. (decision D-11: the proof references recorded blob hashes rather than requiring the blobs in its own transaction.) (2) Carried, referenced, or both — and who decides. The binding source MUST be derived by the contract, never asserted by the submitter: if publicationId == 0 the batch is on the carried path and DA-03(i) applies to this transaction's own blobs; if it is non-zero the batch is on the referenced path; and if the accepting transaction also carries blobs in the batch's range (blobhash(i) != 0) it is on the carried-and-referenced path, where the carried ordered versioned hashes MUST equal the record's element-wise and DA-03(i) applies as well. The three cases are recorded in the side mapping of L1-09 together with the accepted statementHash, so a batch's data location is derivable from L1 state; the frozen L1-07 record is not altered. A submitter MUST NOT be able to make the contract skip a check by mislabelling the case: the case is decided by blobhash and the record, never by a separate input field. (3) The on-chain check in the referenced case, and the one thing that is lost. BLOBHASH is transaction-scoped and returns bytes32(0) for a blob the executing transaction does not carry, so the referenced case MUST NOT bind through it (DA-03(i′)). The EIP-4844 point-evaluation precompile at 0x0A is not transaction-scoped: its input is (versioned_hash, z, y, commitment, proof) and it verifies the opening of the supplied commitment against the supplied versioned hash. In the referenced case the contract therefore performs the same DA-03(ii)–(iii) checks with the recorded versioned hash in place of blobhash(i): kzg_to_versioned_hash(commitment_i) == recordedVersionedHash_i and verify_kzg_proof(commitment_i, z_i, y_i, proof_i), with z_i derived on-chain by DA-03(iii) from the landing statement's own transcript; commitment_i, proof_i and y_i are submitter-supplied and proof-bound exactly as in the carried case. The guest's obligations are unchanged (PRF-07(b)(iv)–(v)). What is lost relative to the atomic path is only same-transaction equality: the accepting transaction no longer proves that it carries the data; it proves that the data was published in the referenced transaction and recorded while retrievable. The content binding is not weakened, because the recorded versioned hash is the one the consensus layer checked against the published blob sidecars when that block was processed sourced (EIP-4844). The weaker variant is rejected: an implementation that omits the precompile on the referenced path and rests the binding on the recorded hash plus an in-guest evaluation is not sound — the in-guest evaluation is computed from the very bytes the guest already executed and ties them to nothing. Binding the executed bytes to the recorded commitment without a precompile requires recomputing each blob's KZG commitment from the executed bytes in-guest (an MSM) or verifying the opening in-guest (pairings); both are UNVERIFIED on both backends (PRF-11, 03), so that variant is Open and MUST NOT be relied on. (decision D-11: the reference keeps the on-chain opening and loses only the same-transaction hash equality.) (4) Liveness, not soundness, is what changes. On the referenced path the accepting transaction need not carry the payload, so the batch's bytes MUST remain retrievable from the publication transaction for provers to build the proof and for nodes to reconstruct the chain: that is DA-05's archive duty over the publication transaction's blobs, and DA-09's deadline bounds how long the record may be referenced while its blobs are inside Ethereum's retention window. Failure to retrieve the published bytes prevents a proof from being built; it does not let a wrong proof verify. (5) Availability of the record itself. If the publication transaction is reorganised out below Ethereum finality (L1-12), the record does not exist on the canonical chain and a proof referencing it MUST be rejected until the data is published again or carried by a new acceptance transaction; no checkpoint is affected, because publication writes none. Failure mode: treating a recorded hash as if it were an opening — accepting the executed bytes because they hash to a value the guest itself produced — is the naive blob path DA-03 exists to prevent; and treating the reference as a second canonical data location is the two-answers failure of DA-01, which the single recorded binding source and the single statement hash prevent. Proven sourced Open (the referenced binding reuses the precompile and is as strong as DA-03's; the Open part is only the rejected precompile-less variant, whose falsifier is an in-guest KZG commitment or opening implementation with measured cost on an accepted backend. Precompile input semantics: EIP-4844 — decision D-11)
DA-09 — proving deadline inside blob retention, and its consequence when missed (1) The deadline and the status. A publication record MUST carry a deadline fixed at publication, deadlineBlock = record.l1BlockNumber + T_PROVE_DEADLINE, and a status that is one of PUBLISHED, PROVEN or DISCARDED: PUBLISHED when written, PROVEN when a batch referencing it is accepted, and DISCARDED at deadlineBlock if it is still PUBLISHED. Only a record still PUBLISHED MAY be referenced; a DISCARDED record MUST be rejected with PublicationExpired; a PROVEN record is retained for the register's bookkeeping and is not referenceable for the same range again because that range is landed. land(data, proof) MUST require block.number ≤ record.deadlineBlock, with T_PROVE_DEADLINE measured in L1 blocks from the record's own l1BlockNumber (registered in 09; unmeasured). The record entry itself MUST remain readable for at least PUB_RECORD_RETENTION L1 blocks, which MUST be at least T_PROVE_DEADLINE so that a referenceable record is never pruned early; pruning a record that is still referenceable is a protocol defect, and a pruned record is treated as absent. The deadline MUST be inside the blob-retention window: expressed in the same unit, T_PROVE_DEADLINE + T_SETTLE_PIPELINE (converted to L1 blocks) MUST be at most the blob-retention window of DA-05, so a record is never referenceable after the blobs it names have stopped being retrievable from Ethereum. It MUST also be usable: converted to seconds, T_PROVE_DEADLINE ≥ T_PROOF_MAX_PERMITTED + T_SETTLE_PIPELINE + margin, the same terms and units as CONS-13(3)'s lookahead inequality. Both inequalities are derived; every term is unmeasured, and the parameter page owes the row and the derivation. (decision D-16: the D-12 ordering FI_INCLUSION_DELAY < T_PROVE_DEADLINE is withdrawn with the deferred forced-inclusion machinery; review round 5, finding R5T-PDE-06 tied two parameters that are no longer v1 parameters.) (decision D-11: the proving deadline is the June-2026 control — no record may be referenced past retrievability.) (2) What happens when it is missed. At the deadline the record's status MUST become DISCARDED and it MUST be dead: land(data, proof) referencing it MUST revert with PublicationExpired(publicationId, deadlineBlock), MUST write nothing, and MUST produce no partial effect (L1-03). The batch is not discarded as a range and its provisional history is not touched: it remains landable (a) by the carried path, with the data in the accepting transaction's calldata or blobs, or (b) against a new publication record of the same data, which any account MAY create because publication is permissionless (DA-07(1)). The earlier record's clock is immutable and MUST NOT be extended, so re-publication starts a new clock rather than reviving the old one. Nothing on this path accepts a batch or advances, retires or rewrites any height. (decision D-11: the deadline is deliberately not an admission gate on the range, because the range must remain landable with fresh data — L1-04.) (3) The provisional history above the last proven checkpoint. The deadline changes nothing about it by itself. A confirmation above the last accepted checkpoint is PoS-certified / provisional and no v1 path replaces it: every replacement mechanism is deferred by decision D-16 (REC-02/GOV-04 are tombstones), while REC-01 forbids any path from touching history at or below the checkpoint; expiry neither discards it nor keeps it alive. If no party re-publishes or carries the data, the range is simply never proven: settlement stalls above the checkpoint, and v1 offers no route to replace the unsettled history. If an archive still holds the bytes, any prover MAY re-publish and land, and the batch settles normally. Stated plainly: the deadline bounds how long a dead publication may be presented as live data; it does not by itself resolve a withholding failure. The obligation to prove published-but-unproven data within a deadline, and to discard and re-publish it when the deadline is missed, was the narrow forced-inclusion rule of decision D-12 (the FI-* family); decision D-16 defers that whole machinery, so v1 has no such obligation and a proposer that leaves a published record unproven is not in breach. This rule owns only the record's own liveness and the reference check, and the exclusion deadline it once anchored with DA-10 is not a v1 rule (DEFERRED.md §1). (4) Interaction with the unsettled-depth cap. D_MAX of HALT-03 and DA-06 stays the one production-side cap, measured in L2 blocks, and this deadline MUST NOT be implemented as an admission condition on land(data, proof) or as a second cap in another unit (L1-04, DA-06). The two clocks measure different objects: D_MAX bounds how much unsettled L2 history may be produced, and T_PROVE_DEADLINE bounds how long one record may be referenced. They MUST NOT be combined into one inequality. Their composition is: the cap keeps the unsettled range provable from the data validators and archives hold, and the deadline keeps a referenced record inside the blobs' retrievability; a batch that misses its deadline is a liveness event handled by re-publication; if no party re-publishes, settlement stalls and v1 has no replacement path (decision D-16; REC-02/GOV-04 are tombstones), never a rule violation the cap must catch. Failure mode: without a deadline, a proof may reference a publication whose blobs have aged out, so the protocol accepts a batch whose canonical data no longer exists where the protocol said it would — the June 2026 class (DA-05) arriving through the new path. With a deadline that is also an admission gate on the range, a valid proof for finalized history becomes permanently unacceptable, which L1-04 forbids. The two-sided inequality and the re-publication escape are the narrow path between them. Proven derived unmeasured Open (T_PROVE_DEADLINE and the derived inequalities are unmeasured; the parameter page owes them. The forced-inclusion deadline of D-12 is deferred by decision D-16 and is not a v1 rule — decision D-11)
DA-10 — published data is the anchor for the exclusion deadline (retained; deferred with D-16) Deferred with the forced-inclusion machinery (decision D-16). This rule fixed the anchor of the D-12 exclusion deadline: published-but-unproven data was to be provable-by-deadline, and discardable and re-publishable when the deadline was missed, with that deadline anchored to the publication record of DA-07 and measured from the record's l1BlockNumber — the L1 block at which the data was published — and from nothing else. A batch's certification time, its landing time, a proposer's clock, a node's local receipt time, an off-chain view and any caller-supplied timestamp MUST NOT anchor it (GEN-06). Only a record whose identity the Inbox recomputes from its own stored content may anchor a deadline (DA-07(3)), so the exclusion obligation is derivable from L1 state alone and is the same for every observer. Decision D-16 defers the exclusion obligation this anchor served, so no v1 rule reads this anchor, and it MUST NOT be implemented as an admission condition on land(data, proof). The rule id and its statement are retained so that a revived mechanism inherits a fixed anchor rather than re-deriving one; the preserved text is in git history at 7917ba264 and the register is DEFERRED.md §1. (decisions D-11, D-12 and D-16: the anchor rule answers to the D-16 keep-list, but the obligation it anchored is deferred.) Failure mode: an exclusion deadline measured from an object other than the recorded publication — a proposer's claim, a node's local arrival time, a landing transaction — is unverifiable, discretionary and re-startable, so a censoring proposer could move the deadline it is judged by; and a deadline that nothing on L1 anchors would make the forced-inclusion obligation unenforceable at the proof, which is where D-12 puts its enforcement. Deferred (the anchor is structural but unread in v1: the forced-inclusion rules that consumed it are the FI-10–FI-14 tombstones on this page — decision D-16)

Why proposer rotation gives conditional inclusion resistance — and what v1 does not add

This is a conditional statistical argument with named premises, not a guarantee, and it is the mechanism behind LIVE-04's statement. Proposer selection is hash-based weighted selection (CONS-06), and a coalition holding f < 1/3 of the stake that counts toward quorum (A-CONS-1) holds fewer than 1/3 of proposer slots in expectation over any window of s slots. Let p = f be the coalition's slot share. The probability that it leads s slots in a row is p^s, so the expected waiting time for an honest slot is 1/(1-p) ≤ 1.5 slots derived. A transaction that reaches honest validators is included by the first honest proposer with room for it (LIVE-04, FI-REMOVED-01). In v1 this argument is the whole of the inclusion story: decision D-16 defers the narrow forced-inclusion rule of D-12, so publication creates no obligation and a proposer may leave published data unproven without breach. The coalition's residual power is to make inclusion late, not to prevent it, and lateness is bounded by the selection rule, not by a timeout judgement (STATUS-10). Three honest caveats: the argument holds only while A-CONS-1 holds — at ≥1/3 Byzantine stake it does not apply and the protocol claims nothing; it assumes proposer selection is not predictable enough for the coalition to buy the specific slots in which a transaction would be included, which is CONS-06(b)'s Assumed fairness claim; and it holds only under the network assumption A-CONS-2 — a network-level adversary able to isolate a user from every honest proposer can exclude that user indefinitely and can prevent the user from starting a withdrawal, and the protocol offers no remedy (FI-REMOVED-01). (user decisions D-6 and D-16: the argument stands on proposer rotation and CONS-06 alone; it supplements nothing, because the D-12 narrow rule is deferred and the A-CONS-2 caveat is the disclosed gap.)

MSG-04 — rule-triggered, time-limited withdrawal veto (1) What it is, and what it is not. The protocol has exactly one circuit breaker on the value-release path: a withdrawal veto that delays L2→L1 releases for a bounded window. It is rule-triggered and permissionless: no owner, DAO, operator, validator quorum or upgrade starts it, extends it, shortens it or stops it early, and there MUST NOT exist any pause/unpause-style entry point for it (MIG-04, INV-04). It is not the pause lever this design removes: it cannot be invoked at will, it cannot be extended by any party, it expires by itself, and it cancels and rewrites nothing. It is a mitigation with a bounded window and it is explicitly not a fix for an unsound backend: it cannot un-prove a forged statement, cannot remove a checkpoint already accepted (L1-06, REC-01), and cannot recall value already released. (2) Trigger: a verified contradiction, and nothing else. The trigger is exactly one objective on-chain event: a proof that the Inbox verifies itself, under a registered route, of a statement that conflicts with an accepted checkpoint's own statement — the same L2 chain id, height range, predecessor and dataCommitment, and a different postStateRoot or headBlockHash from the record. The entry point is contestProof(...), callable by any account, and the contract MUST recompute the statement hash over the submitted journal itself, verify the proof against that recomputed hash, and compare the journal's range, predecessor and dataCommitment with the checkpoint record's own values; it MUST accept no pre-computed conflict verdict and no caller-supplied comparison. A local view, a timeout, a missing proof, an allegation, a bond or a privileged account MUST NOT start it: an elapsed timeout is never evidence of absence (STATUS-10). Because execution and the state commitment are deterministic, two verified statements that conflict cannot both be true, so the trigger is evidence that at least one accepted proof system is unsound — it is not a suspicion. Each verified contradiction MUST be recorded by a hash and consumed exactly once: a repeated call with the same contradiction MUST revert, and a new window requires a new verified contradiction. The trigger does not require a distinct backend family: a single implementation contradicting itself is already evidence of unsoundness, so the veto still exists at a configuration where only one family is deployed. (3) Bounded duration, not extendable by anyone. The veto starts at the L1 timestamp of the triggering transaction and MUST end automatically at startedAt + T_VETO, with T_VETO unmeasured and registered in 09. It MUST NOT be extended, renewed or shortened by any account or upgrade, and there MUST NOT be a second veto state or a manual end. A new verified contradiction while a window is active MAY start a new window ending no later than its own trigger plus T_VETO, and the value of T_VETO in force at each start fixes that window for its whole life. The total time the release path can be delayed is therefore bounded by T_VETO per verified contradiction and is not bounded by these rules alone across contradictions — but each contradiction is evidence of a real soundness failure, and a party able to produce them has already broken the assumption the withdrawal path rests on. (4) Effect on already-proven withdrawals. A withdrawal already proven against a withdrawal root but not yet executed is delayed, never cancelled: it needs no new proof, its root and state root are untouched, and it becomes executable when the window ends and the other conditions of MSG-03 hold. Value released before the trigger cannot be recalled and no rule may imply otherwise. The veto MUST NOT gate land(data, proof) (L1-04), settlement, consensus, staking, validator exits, rewards, root attestation (L1-13) or the L1→L2 direction; it gates only L2→L1 value release and message authentication on the bridge surface. It MUST NOT be implemented with the removed pause facilities or as a condition on anything but the release path (MIG-04). (5) Disclosure. The Inbox MUST expose the veto as a public fact an interface can read — whether it is active and the timestamp at which it ends — and STATUS-11's public-facts obligation includes it. Every artifact that describes withdrawal timing MUST state plainly that a verified proof contradiction can add up to T_VETO to any pending withdrawal, that this lengthens exits and never shortens them, and that the veto delays rather than repairs: it is a bounded circuit breaker for the window in which an unsound backend's effect is being investigated, and the remedy for a genuinely unsound backend is a governance upgrade that retires its route (GOV-02, MIG-05), not this rule. No artifact may present the veto as a fix for an unsound backend. Failure modes: (a) an owner-, DAO- or operator-controlled pause returns through this door, which MIG-04 and INV-04 forbid — hence the objective trigger, the permissionless invoker and the automatic expiry; (b) a veto a griefer can start without evidence is a free denial of service on every exit — hence the on-chain-verified contradiction and its one-shot consumption; (c) a time-unbounded or extendable veto is an indefinite freeze — hence the self-expiry and the ban on extension; (d) cancelling proven withdrawals would make the veto a discretionary reversal of accepted state, which no rule permits; (e) describing the veto as a repair for an unsound backend would overstate a mechanism that cannot un-prove anything.
