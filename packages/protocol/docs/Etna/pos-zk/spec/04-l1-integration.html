04 — L1 integration: atomic data + proof, data availability, forced inclusion, bridge anchoring

This page carries D5 and D8. It fixes how a batch becomes STATUS-06 — accepted on L1: one L1 transaction carrying the batch data and its validity proof, out of which the Inbox itself derives the data commitment, and out of which a single monotone checkpoint advance follows. It also fixes where that data is canonical (DA-01), how the blob path binds data to the proof (DA-03), how forced inclusion works without an override that could violate Mode A (FI-01–FI-05), and how the preserved SignalService/Bridge addresses authenticate against these checkpoints (MSG-01–MSG-03).

Baseline for every comparison to "today" on this page: Taiko monorepo revision 7718753c1 (2026-10-05), file packages/protocol/contracts/layer1/core/impl/Inbox.sol. Nothing on this page is implemented, deployed, audited or measured (GEN-01). Every number is tagged derived / sourced / unmeasured.

Assumption disclosure. Acceptance here is a liveness path guarded by cryptography, not a safety guarantee by itself. Wherever a statement depends on <1/3 Byzantine stake (A-CONS-1) or on the availability assumptions (A-CONS-5, A-DA-2) it says so at the claim (01-requirements-and-threat-model.md §4).

1. One atomic acceptance

L1-01 — single atomic accept entry point; no data-first path The Inbox MUST expose exactly one function that can accept a batch and advance the checkpoint. Its name is land(bytes calldata _proof, LandInput calldata _input). One call MUST carry, in one L1 transaction: (a) the batch range, given as uint64 firstBlockHeight and uint64 lastBlockHeight of L2 blocks; (b) the batch data, given as the bytes calldata _batchData argument and/or the blob sidecars of that same transaction; (c) the proof, given as _proof; and (d) the claimed post-state and finality values of L1-05. Data and proof are inseparable: there MUST NOT exist any entry point, overload, fallback, multicall helper, or recovery path that records the data (or a commitment to it) in one transaction and the proof in another. There MUST NOT exist a "propose then prove" path in any mode. Failure mode: the batch's data becomes public before any proof exists, so a batch can be published and never proven — the data occupies L1 capacity, consumes the settlement budget, and settles nothing. Allowing it in one mode re-opens D5 for every mode, because the recovery path becomes the cheapest way to publish data. Proven sourced (D5; contrast below)

Contrast with the baseline. At revision 7718753c1 the two paths are separate and there is no combined one:

L1-02 — no entry point records a pending or incomplete batch No entry point of the Inbox — public, external, or reachable through an upgrade initialiser — may write a batch record, a predecessor link, a proposal hash, a data commitment, or a checkpoint pending a proof. The only accepted state that exists for a range is the checkpoint written by a successful land call. An "announce" / "intent" / "commit" function may exist only if all three hold: (i) nothing it writes is read by land, by the verifier route, or by any admission check; (ii) it cannot become a precondition for a later acceptance — in particular, a later land for the same range MUST succeed whether or not the announce function was ever called, and in any order; (iii) its failure or omission has no effect on liveness or on any other rule. The safest design has none, and this specification designs none. Failure mode: an announce function that later becomes load-bearing converts "publish data" into a privileged step — the first caller of the announce function acquires a sponsorship right over the range, and a range whose announcement was never made (or was made and then made unreadable) is unlandable. This is the propose-then-prove failure of L1-01 arriving through the back door. Proven

Baseline for comparison: the propose-time hash is exactly such a load-bearing record (Inbox.sol:286 → Inbox.sol:348-351), and init2() (Inbox.sol:217-244) is an onlyOwner initialiser that rewrites lastFinalizedProposalId and lastFinalizedBlockHash directly. Neither construct exists in this design; see MIG-04.

L1-03 — failed verification leaves the batch unaccepted with no partial effect land MUST execute in this exact order: (1) decode and shape-check the input in memory only, with no state writes; (2) derive every contract-derived public input of L1-05 from L1 storage and from this transaction; (3) if blobs are used, perform the DA-03 checks and record the accepted (versionedHash, z, y) tuples in memory; (4) call the active verifier route with the statement hash; (5) treat the proof as invalid unless the call returns exactly abi.encode(true) — a revert, an empty return, or any other return value is invalid; (6) only then write the checkpoint record, advance the height pointer, mark covered forced inclusions consumed, and pay out L1-11; (7) emit events last. If any step fails, land MUST revert with a typed error and produce no partial effect: no checkpoint, no height advance, no consumed forced inclusion, no payout, no event. Failure mode: a checkpoint exists that no proof ever justified, or a forced inclusion is marked consumed by a batch that was never accepted. A "verify last, write first" ordering survives only as long as the verifier always reverts and nothing can swallow the revert; the moment a route returns false, or an upgrade or a low-level call absorbs the failure, the write becomes permanent and the chain's checkpoint advances without a proof. Proven

Why the baseline ordering is safe today, and why this design still changes it. At 7718753c1, prove() writes the SignalService checkpoint (Inbox.sol:364-370), updates _coreState and emits Proved (Inbox.sol:376-387) before calling _proofVerifier.verifyProof(...) (Inbox.sol:394-398). That is not a vulnerability in that contract as written, for one stated reason: the verifier call is in the same transaction and a reverting verifier unwinds the whole transaction, restoring the checkpoint and the core state. The baseline research records exactly this: "the ordering is still structurally 'optimistic write, then verify' — a property a same-tx redesign must preserve" (research/taiko-baseline-contracts.md §3.3). This design does not rely on that property. Reasons, in order of importance: (a) the interface tolerates a verifier that returns false instead of reverting, and a try/catch or a future routing layer could absorb a revert; (b) the checkpoint is a public authentication anchor for the preserved bridge surface (MSG-01), so its integrity must not depend on an external contract's revert discipline; (c) correctness must be readable from the function body rather than inferred from EVM unwind semantics. Verify-first costs nothing in gas terms that this specification claims to know — the cost of land is UNMEASURED and would be measured by a gas-snapshot run over a batch of the target size; no such measurement exists.

L1-04 — admission: no gate, no expiring range, any prover Any account MUST be able to call land. The admission rules of land MUST contain: no whitelist and no allowlist (of provers, proposers, or relayers); no owner-, DAO-, or operator-controlled approval; no minimum bond, stake, or reputation to submit; no deadline, timestamp, block-number or age condition that can make a range permanently unacceptable; and no dependency on tx.origin, block.coinbase, gas price, or L1 proposer identity (GEN-06). For any unsettled range, any account that can produce a valid (data, proof) pair MUST be able to land it. Structural bounds are permitted and MUST be exactly these: the range must be contiguous and start at lastLandedHeight + 1 (L1-06); the batch must be non-empty; and every loop in land must be bounded by the transaction's own contents (its blob count, its forced-inclusion coverage list, its claimed range length), never by an unbounded external structure. Backpressure on production — the consensus-enforced unsettled-depth cap of HALT-03 and DA-06 — MUST NOT be implemented as an admission condition on land. Failure mode: a validly PoS-finalized extension of the L1 checkpoint becomes permanently unacceptable, i.e. a legitimate extension of finalized history can never be settled. Under Mode A the protocol may halt but may not discard finalized history; an admission gate or an expiry is exactly a rule that discards it, because the only honest response left is to abandon settlement for that range. This rule is required by Mode A, not merely compatible with it (04-architecture-decision.md §5.3, L1-ADMIT-NO-EXPIRY; research/mode-a-feasibility-analysis.md §4). Proven (Mode A obligation)

Baseline mechanisms this rule deletes, each currently live: ProverWhitelist gating (Inbox.sol:337, Inbox.sol:771-779, error ProverNotWhitelisted); the IProposerChecker indirection whose mainnet implementation admits one operator per epoch (PreconfWhitelist.sol:136-140); DeadlineExceeded on propose (Inbox.sol:764-766); _maxProofSubmissionDelay (Inbox.sol:102); and the ring-buffer capacity check NotEnoughCapacity (Inbox.sol:591-593), which is the mechanism by which unproven history is silently discarded when the buffer wraps.

2. What the proof is bound to

L1-05 — public-input binding list, and who derives what The statement the proof is checked against MUST bind every value in the table below, at the stated provenance. L1-derived values the contract reads from its own storage or from block.chainid; tx-derived values the contract recomputes from the transaction's calldata and blobs and MUST ignore any submitter-supplied copy; claimed values are supplied by the submitter and are bound by the proof, so a wrong claim makes the proof invalid rather than making the contract misbehave. The contract MUST NOT accept from the submitter any value in the L1-derived or tx-derived rows. The canonical byte encoding of these values into the guest's public-input vector, and the guest-side recomputation of each one, are fixed on PRF-02 and PRF-07; this rule fixes which values L1 supplies and how it obtains them. The contract hashes the whole vector, with the domain tag and chain id first (GEN-05), into statementHash and passes only that hash and the opaque proof to the verifier route of L1-09. Failure mode: a public input that the submitter can choose — a validator-set root, a predecessor, a data commitment, a threshold — lets a prover prove a true statement about the wrong object and land a batch the protocol never agreed to. A value that L1 could derive but accepts from the submitter is a permissioned design with extra steps. Proven

L1-06 — monotone checkpoint advancement Let lastLandedHeight be the height of the current checkpoint record (0 before the first one). land MUST require firstBlockHeight == lastLandedHeight + 1 and MUST reject with RangeNotContiguous() otherwise; for a duplicate or earlier range it MUST revert AlreadyLanded(). After a successful land, lastLandedHeight = lastBlockHeight strictly increases. No function in any mode — including an upgrade initialiser, a recovery path, or a governance call — may decrease lastLandedHeight, replace or delete a checkpoint record at a height ≤ the current one, or write a checkpoint at a height greater than lastLandedHeight + 1. The only legitimate way a checkpoint disappears is an L1 reorganisation that reverts the entire land transaction (L1-12) — the contract never chooses to move backwards. Genesis establishes the first checkpoint exactly once, and it is never rewritten (MIG-03). Failure mode: a non-monotone checkpoint lets a later transaction replace the state root that the bridge surface authenticates against, which retroactively invalidates messages already proven against it — a rewrite of L2-finalized history through the L1 anchor, forbidden by Mode A (REC-01). A gap (writing lastLandedHeight + 2) is the same defect in weaker form: it leaves an unprovable hole in the authenticated chain. Proven

Contrast: init2() at Inbox.sol:217-244 sets lastFinalizedProposalId and lastFinalizedBlockHash to arbitrary owner-chosen values, and Inbox.sol:376-378 overwrites the finalised pointer on every prove(). Under L1-06 neither is expressible.

L1-07 — checkpoint record contents and its exact encoding The Inbox MUST store one checkpoint record per landed height and MUST make it readable by height. The record fields are, in this order and with these types: 
struct Checkpoint {
    uint64  height;           // L2 block height of the head of this batch
    bytes32 blockHash;        // L2 head block hash at height
    bytes32 stateRoot;        // L2 execution state root at height
    uint64  epoch;            // L2 epoch that contains height
    bytes32 setRoot;          // validator-set commitment valid at epoch
    bytes32 dataCommitment;   // data commitment of this batch (DA-02 / DA-03)
    uint64  l1BlockNumber;    // PROVENANCE: L1 block that accepted it
}
The record hash is keccak256(abi.encode(bytes32("TAIKO_ETNA_CKPT"), uint256(block.chainid), height, blockHash, stateRoot, epoch, setRoot, dataCommitment, l1BlockNumber)) — a single canonical abi.encode with the right-padded ASCII domain tag and the chain id as the first two fields (GEN-05). l1BlockNumber is required so that L1-12 and MSG-03 can evaluate Ethereum finality depth from storage without reconstructing an event log; it is provenance, not part of the state-transition binding, and it is written once and never edited. The accepting transaction's hash is not a field: the EVM does not expose it to the executing contract, so consumers obtain it from the BatchLanded event. blockHash, stateRoot, setRoot and dataCommitment MUST be non-zero; a record that fails any of these MUST NOT be written. The record MUST be the same object the L1 SignalService authentication path resolves for that block number (MSG-01). Failure modes: (a) storing only a hash of the batch — as the baseline does, since the only proof-side state persisted is CoreState.lastFinalizedBlockHash and a Checkpoint{blockNumber, stateRoot, blockHash} — makes the epoch, the validator-set commitment and the data commitment unauthenticated for every later consumer, in particular for the next proof's predecessor binding and for the bridge; (b) an encoding that is not a single canonical abi.encode admits a second preimage for the same record, so previousCheckpointHash no longer identifies one record. Proven derived

L1-09 — proof-system policy, verifier routing and the L1 ability to move to a new circuit Exactly one active route MUST be consulted per land call. A route is the triple (routeVersion : uint64, programImageId : bytes32, verifier : address). Routes MUST live in the Inbox's own storage — not in a mutable registry owned by another contract — because the baseline verifiers (SP1Verifier, Risc0Verifier) are non-upgradeable Ownable2Step contracts replaced by redeployment, and an upgrade of a verifier contract must never be able to change which statement the Inbox accepts. Both zkVM backends implement the same statement; whether the policy is "one backend active" or "either backend verifies" is fixed by PRF-09, and land MUST implement that policy literally: with an either-verifies policy it MUST try each enabled route for the active image and accept the proof if any returns true; with a single-route policy it MUST call exactly the active route. Enabling a new route is additive and MUST NOT be rejectable by any account (L1-04); every landed checkpoint MUST record the routeVersion used. Retiring an image is not an ordinary operation: it is permitted only under the same procedure that governs a rule change (GOV-02, GOV-03), and MUST NOT be executed while any PoS-finalized-but-unsettled range could be proved only under the retired image. A new image MUST accept every history that the previous image accepted (PRF-10). Failure modes: (a) a mutable external registry lets the verifier be re-pointed without the specification changing — the statement is then whatever someone wired up; (b) retiring an image while an unsettled finalized range depends on it makes that range permanently unprovable, which is Mode A's forbidden outcome arriving through an upgrade (04-architecture-decision.md §5.3, UPG-PRESERVE). Proven Assumed (the retirement bar assumes A-GOV-1: the DAO does not execute a malicious upgrade)

4. Races, fees, and L1 reorganisation

L1-10 — submission races, re-submission, and what a proof is a proof of The first valid submission wins. Concretely: land MUST be atomic with respect to the checkpoint pointer, so two transactions in one L1 block are ordered by L1, the first one advances lastLandedHeight, and the second MUST revert AlreadyLanded() if it targets an overlapping or duplicate range, or MUST be evaluated against the new checkpoint if it extends it. Re-submission of the same batch (same dataCommitment, same range) by a different account MUST be accepted whenever the first submission did not land; it MUST NOT be rejected because another account previously submitted, attempted, or announced the same range. A proof is a proof of exactly the statement of L1-05: a proof for a different batch — a different range, a different predecessor, a different data commitment, a different epoch or set root — MUST NOT be usable as a substitute, and MUST fail verification because those values are in statementHash. The reward of L1-11 MUST be paid to msg.sender, the account that paid for the landing transaction; the protocol MUST NOT attempt to attribute it to any address named inside the proof. Consequently, a proof observed in the public mempool can be landed first by another account, which then collects the reward; this is an accepted property of permissionless landing, not a defect to be patched with a first-submitter reservation, and the mitigation available to provers is private orderflow or bundling. Failure modes: (a) a first-submitter reservation is a permissioned gate that expires a range into unrecoverability when the reserving account disappears (L1-04); (b) accepting a proof for a different batch lets a prover attach a valid proof to unrelated data — the whole point of binding the data commitment is that it cannot be done; (c) paying the reward to a proof-declared address lets anyone who copies a proof redirect the payout and makes the identity of the prover unfalsifiable. Proven
L1-11 — fees and the reward accounting identity The Inbox MUST hold two separate ledgers and MUST enforce their conservation with checked arithmetic (no unchecked subtraction; violation reverts FeeAccountingUnderflow()): a forced-inclusion ledger holding requester fees, and a prover reward ledger funded by L2 fee revenue (ECON-02) and by any msg.value the submitter adds. On a successful land the identity is: 
forcedInclusion_after = forcedInclusion_before
                       - sum of feeHeld[r] for r in coveredRequestIds   // paid to feeRecipient
proverReward_after    = proverReward_before + msg.value - rewardPaid
rewardPaid            = min(REWARD_QUOTE, proverReward_before + msg.value)
require(forcedInclusion_after >= 0); require(proverReward_after >= 0);
require(rewardPaid <= proverReward_before + msg.value);
Each covered request's fee MUST be paid at most once: land MUST mark the request consumed in the same write that pays it, and a second payment for the same requestId MUST be impossible. land MUST NOT require a non-zero rewardPaid: if the reward ledger is empty, the batch still lands with rewardPaid = 0 and the event records 0. REWARD_QUOTE MUST NOT depend on anything the submitter controls except the gas actually consumed, and MUST NOT depend on the proof's contents beyond validity. Failure modes: (a) an empty reward pool blocking acceptance turns economics into an admission gate, which L1-04 forbids and which makes settlement depend on a treasury rather than on a proof; (b) paying a forced-inclusion fee twice is a direct drain of the ledger; (c) a reward that scales with a submitter-chosen quantity is a self-dealing surface. Proven unmeasured (REWARD_QUOTE and the gas cost of land are UNMEASURED; closing them requires a gas-snapshot run over batches of the target size, which does not exist)
L1-12 — L1 reorganisation handling, and no unfinalised L1 fact is settled If the L1 block containing a land transaction is reorganised out below Ethereum finality, the transaction is undone by Ethereum: no checkpoint record exists, no height advanced, no request consumed, no fee paid, and no event is part of the canonical chain. The batch remains PoS-finalized in Mode A, and MUST be re-landable with the same dataCommitment under L1-04. The Inbox MUST NOT contain any function that "repairs" a reorganisation by writing a chosen checkpoint, height, or state root: the only response is re-execution of land. Because a checkpoint chain is built by strict succession (L1-06), a reorg that drops one land transaction also drops every later transaction that extended from it, since those transactions cannot satisfy firstBlockHeight == lastLandedHeight + 1 on the new branch; a submitter whose transaction is invalidated this way MUST re-submit. Independently of the Inbox, no L2 rule may treat an unfinalised L1 fact as settled: L2 consensused state may consume only Ethereum-final L1 facts, or L1 facts at the configured finality depth, per SYS-02 and STATUS-07. Checkpoint.l1BlockNumber (L1-07) records inclusion, not finality; any consumer that needs finality MUST compare it against the configured depth. Failure modes: (a) an owner-recovery setter for the checkpoint turns an L1 reorg into a discretionary rewrite of the L2 anchor; (b) an L2 rule that acts on an L1 fact at depth 0 can act on a fact that later disappears, so a PoS-finalized L2 block can be left depending on an L1 event that no longer exists — the exact condition under which a finalized L2 block becomes unprovable. Proven

5. Data availability (D8)

DA-01 — the canonical data-availability location is the accepting L1 transaction The canonical copy of a batch's data MUST be the accepting L1 transaction itself: its calldata and/or the blob sidecars of that same transaction, as bound by DA-02 and DA-03. A batch is accepted on L1 only together with that data. The design MUST NOT define a second canonical location, and MUST NOT treat any location outside that transaction as sufficient for STATUS-06. Failure mode: two canonical locations means two answers to "what is the batch?", and the weaker one is the one an implementer will build against. Proven
DA-02 — calldata path: the contract computes the data commitment itself In the calldata path the Inbox MUST compute the data commitment itself over the exact calldata slice supplied to land, and MUST pass that value as the public input. The construction is fixed as: 
dataRoot       = keccak256(_batchData)                 // one byte string: no field ambiguity
payloadRoot    = dataRoot
dataCommitment = keccak256(abi.encode(
                     bytes32("TAIKO_ETNA_DATA"),        // right-padded ASCII domain tag (GEN-05)
                     uint256(block.chainid),            // chain id is the second field (GEN-05)
                     uint64(firstBlockHeight),
                     uint64(lastBlockHeight),
                     uint8(daMode),                     // 1 = CALLDATA, 3 = CALLDATA_AND_BLOB
                     payloadRoot))
keccak256(_batchData) hashes one opaque byte string rather than a concatenation of fields, so it introduces no second-preimage ambiguity and is not an abi.encodePacked of multiple values. The byte-level layout of _batchData — how L2 blocks serialise into the batch payload — is fixed once, on PRF-07; this rule fixes only how L1 commits to it. The guest MUST recompute dataCommitment from the payload it actually executed, and MUST reject the batch if the recomputation differs. The Inbox MUST ignore any submitter-supplied dataCommitment; if one is present in the input it MUST either be absent from the ABI or be checked equal and rejected with DataModeMismatch() on mismatch. Failure mode: taking the commitment from the submitter decouples the proof from the calldata, so a valid proof can be paired with arbitrary data in the same transaction — the strongest and simplest binding available is thrown away. Proven
DA-03 — blob path: BLOBHASH, on-chain KZG opening, and in-guest evaluation at the challenge point For a batch whose data is in blobs, let n = blobCount and let blob index i range over [blobIndexStart, blobIndexStart + n). The Inbox MUST perform (i) and (ii) for every i, and the guest MUST perform (iv).

(i) BLOBHASH equality. The Inbox MUST read the transaction's own blob versioned hash with the BLOBHASH opcode and require, for each i:

bytes32 vh = blobhash(i);
require(vh != bytes32(0) && vh == _input.blobVersionedHashes[i - blobIndexStart], BlobHashMismatch(i));

A zero value means no blob at that index in this transaction; because BLOBHASH is transaction-scoped, no other transaction's blobs can be substituted. The loop is bounded by the transaction's own blob count, whose protocol limit is the Ethereum per-block limit — target 6, maximum 9 blobs per block under EIP-7691 sourced.

(ii) On-chain KZG point evaluation. The Inbox MUST call the EIP-4844 point-evaluation precompile at address 0x0A with the 192-byte input abi.encodePacked(vh, z_i, y_i, commitment_i, proof_i) — z_i and y_i as 32-byte big-endian canonical field elements, commitment_i and proof_i as 48-byte compressed BLS12-381 G1 points. The call MUST succeed and MUST return exactly abi.encode(4096, BLS_MODULUS); otherwise land reverts BlobOpeningFailed(i). The precompile verifies kzg_to_versioned_hash(commitment_i) == vh and verify_kzg_proof(commitment_i, z_i, y_i, proof_i), and rejects non-canonical field elements. Its gas cost is 50,000 per call sourced (EIP-4844), so a batch using n blobs costs 50,000 · n gas for these calls derived; the total cost of land remains UNMEASURED.

(iii) The challenge point z is derived on-chain by Fiat–Shamir. It MUST NOT be supplied by the submitter. With statementCoreHash the hash of the public inputs of L1-05 rows 1–17 excluding rows 18–19 (i.e. excluding the challenges themselves), the Inbox MUST compute, per blob index:

z_i = uint256(keccak256(abi.encode(
          bytes32("TAIKO_ETNA_CHALLENGE"), uint256(block.chainid),
          statementCoreHash, uint16(i)))) % BLS_MODULUS;

The modulus reduction is required because a keccak-256 output is not automatically a canonical scalar (BLS_MODULUS < 2^255), and the precompile rejects non-canonical elements. The reduction biases the distribution by at most BLS_MODULUS / 2^256 ≈ 2^-127 in statistical distance derived, which is irrelevant to the 2^-243 bound below. Index i is inside the domain so that two blobs of the same batch never share a challenge.

(iv) The guest proves the evaluation of the data it executed. The guest receives (vh_i, z_i, y_i) as public inputs and the blob bytes as part of the data it executed. It MUST interpret each 131,072-byte blob as 4096 coefficients p(X) = Σj cj Xj, where cj is the big-endian integer of the j-th 32-byte chunk, and it MUST reject the batch if any chunk is ≥ BLS_MODULUS. It MUST recompute p_data,i(z_i) by Lagrange evaluation over those 4096 coefficients and MUST reject the batch unless p_data,i(z_i) == y_i.

Why this is sound. The chain is: (a) blobhash(i) names the blob that is in this transaction; (b) the precompile establishes kzg_to_versioned_hash(commitment_i) == vh_i, so commitment_i is the KZG commitment of that blob's polynomial p_blob,i; (c) the precompile's verify_kzg_proof establishes p_blob,i(z_i) = y_i; (d) the guest establishes p_data,i(z_i) = y_i. Therefore (p_data,i - p_blob,i)(z_i) = 0. If the two polynomials differ, their difference is a non-zero polynomial of degree ≤ 4095, which has at most 4095 roots; over a uniform z the equality holds with probability at most 4095 / |F| ≈ 2^-243 derived. The prover cannot choose z after choosing its data: z_i is a deterministic function of statementCoreHash, which contains dataCommitment, which for the blob path contains the versioned hashes, which are kzg_to_versioned_hash of the very commitments the prover must fix before z_i is computable. Grinding is therefore per-candidate-blob: for a real payload that differs from the committed blob polynomial, each candidate blob yields an independent random equation with success probability ≈ 2^-243. Hence, with overwhelming probability, p_data,i = p_blob,i: the guest executed exactly the data the blob commits to.

Premises. This argument requires all four of: (1) KZG binding for blob commitments (A-CRYPTO-3); (2) the random-oracle model for the Fiat–Shamir derivation of z_i; (3) correct in-guest field arithmetic over the BLS12-381 scalar field, including the exact Lagrange evaluation and the 4096-coefficient interpretation; (4) canonical field elements in both the blob and the guest's coefficients. If any premise fails, the binding does not hold. This is a proof sketch with named premises, not a machine-checked theorem, and adversarial review question Q-A3 is carried against a grinding prover (04-architecture-decision.md §7).

Provenance and honesty. This construction was derived in this project (04-architecture-decision.md §4.1); it is not an established published design and has no implementation. Its in-guest cost is UNMEASURED; measuring it requires an implementation of the in-guest evaluation on both backends with cycle counts at a stated blob size, which does not exist (04-architecture-decision.md §7, item F2). In-guest MSM and in-guest pairings are deliberately avoided, because the zkVM feasibility work found them UNVERIFIED on both backends: the guest performs field arithmetic and Lagrange evaluation only, and the pairing happens on L1 inside the precompile (PRF-11). The alternative to measure is the RISC Zero patched c-kzg library, which would put a different and larger trusted computing base inside the guest. Precompile semantics, address and gas are cited from EIP-4844; blob counts from EIP-7691.

Failure modes: (a) a submitter-chosen z lets a prover pick the evaluation point after fixing its data, which reduces the binding to a single linear equation it can solve; (b) accepting blobhash from calldata instead of reading it lets a transaction reference blobs it did not publish; (c) performing the KZG opening in-guest would require MSM and pairings that are unverified on both backends, i.e. an unquantified soundness assumption; (d) without the canonical-field-element requirement the guest's polynomial is ambiguous, and two different byte strings map to the same polynomial. Proven sourced derived unmeasured Open (measured in-guest cost; review question Q-A3)

Hybrid mode. When daMode = CALLDATA_AND_BLOB, the payload is _batchData || blobChunk[0] || … || blobChunk[n-1], and

payloadRoot = keccak256(abi.encode(bytes32("TAIKO_ETNA_HYBRID"), uint256(block.chainid),
                                  keccak256(_batchData), vh[0], ..., vh[n-1]));

Both bindings then apply independently: the calldata part is bound by the contract's own hash, the blob parts by the construction above. A batch is invalid if either binding fails.

DA-04 — no witness, certificate or off-chain store substitutes for on-chain data None of the following may be used, alone or in combination, to satisfy DA-01: the prover's private witness or any hint stream; a validity proof of any kind; a committee, quorum, or validator attestation; a "data-availability certificate"; a blob reference (a versioned hash or blob index without the blob's presence in this transaction); an external DA layer, an off-chain store (HTTP, IPFS, S3, a node's local disk), or an operator promise. The guest MUST NOT be able to execute a batch whose payload it received only through a private witness while the corresponding public data is absent: the data commitment of DA-02/DA-03 MUST be computed over data that is in the accepting transaction. Failure mode: the protocol claims availability while the only party who can reconstruct the batch is the prover, which is exactly the "certified-but-unavailable" class that the architecture decision records as Mode A's strongest counterexample (04-architecture-decision.md §5.1). Proven
DA-05 — retrievability window, archive requirement, and the blob-retention limit Blobs are not a permanent store. Ethereum guarantees blob sidecar retrievability for MIN_EPOCHS_FOR_BLOB_SIDECARS_REQUESTS = 4096 epochs sourced (EIP-4844), which is roughly 18 days at Ethereum's present slot cadence derived — the design does not depend on that wall-clock figure and expresses the window in epochs and L1 block numbers (GEN-06). Calldata is not permanent either: on the p2p layer clients stop serving historical headers, bodies and receipts older than 14,299 epochs sourced (EIP-4444, recorded in research/recovery-and-withholding-raw.md). The design therefore MUST specify, in 09: (a) a RETRIEVABILITY_WINDOW in L1 block numbers, not shorter than the blob-retention window; (b) an ARCHIVE_REQUIREMENT fixing how many independent archive nodes must retain the full accepting-transaction calldata and full blob sidecars for at least that window, with the duty owned by ROLE-03; (c) the statement that past the window, retrievability depends on those archives and not on Ethereum. Under D5 this failure class cannot recur for a pending batch: data is published only in the transaction that proves it, so there is no interval in which a batch's data is on L1 while its proof is not. The retention clock starts at acceptance, not at a separate proposal. In-repo evidence that this failure class is real, not hypothetical: at revision 7718753c1, init3() (Inbox.sol:246-258) is a one-time onlyOwner function that voids queued forced inclusions by moving the queue head to the tail, and its NatSpec states the reason — the skipped entries' blobs have expired from the blob retention window and can no longer be derived after the June 2026 incident, and their fees remain in the contract. 04-architecture-decision.md §4 records the same finding. A design that publishes data before a proof re-creates exactly that state. Proven sourced derived
DA-06 — retention duty and its link to the backlog cap The consensus-enforced unsettled-depth cap of HALT-03 exists because of this rule. Define unsettledAge as the L1-block distance between the oldest PoS-finalized-but-not-landed L2 block and the current L1 block. Correct validators MUST refuse to vote for a block that would make unsettledAge exceed MAX_UNSETTLED_AGE, so that the oldest unsettled batch never leaves the retrievability window before it can be proven and landed. The retention duty MUST satisfy RETRIEVABILITY_WINDOW ≥ MAX_UNSETTLED_AGE + SETTLEMENT_PIPELINE + EVIDENCE_WINDOW, where SETTLEMENT_PIPELINE is the worst-case proving plus L1-inclusion plus Ethereum-finality time (ECON-03) and EVIDENCE_WINDOW is the misconduct-evidence window (ECON-07). The cap is a rule on production; it MUST NOT be applied to land (L1-04), because refusing an available, valid proof would strand finalized history. When the cap binds, the honest outcome is a safe halt (HALT-01), never a rollback. Failure mode: without the cap, blocks keep being finalized whose data ages out of the retention window before any proof exists; the batch then cannot be proven by anyone, and Mode A forbids discarding it, so the chain is permanently stuck on a range whose data no longer exists anywhere the protocol promised. The cap converts an unbounded, unrecoverable failure into a bounded, recoverable halt. Proven unmeasured (RETRIEVABILITY_WINDOW, MAX_UNSETTLED_AGE and the pipeline terms are unmeasured parameters; all four are fixed in 09)

6. Forced inclusion

FI-01 — request format, bond/fee, and eligibility delay A user censored on L2 MUST be able to request inclusion by an L1 transaction: 
function requestForcedInclusion(bytes calldata _txData) external payable returns (uint64 requestId_);

struct ForcedInclusionRequest {
    uint64  id;                       // FIFO, assigned in request order, never reused
    address requester;                // receives a refund under FI-03
    uint64  eligibleAtL1Timestamp;    // = block.timestamp + FORCED_INCLUSION_DELAY_SECONDS
    bytes32 payloadHash;              // keccak256(_txData)
    bytes   txData;                   // the transaction to be included, stored in L1 STATE
}
The payload MUST be calldata carried in the request transaction and stored in the Inbox's own L1 storage — not a blob. A blob-backed request re-creates the DA-05 expiry class: the reference would outlive nothing, and after the retention window the request could neither be included nor refunded, which is precisely what happened to the queue voided by init3() (Inbox.sol:246-258). The requester MUST pay a fee at request time (formula and escalation in FI-05); excess MUST be refunded. The delay parameter FORCED_INCLUSION_DELAY_SECONDS is expressed in seconds (GEN-06) and its value is fixed in 09; the baseline's 576 seconds (MainnetInbox.sol:48) is recorded as today's value at 7718753c1 sourced, not as this design's value unmeasured. _txData.length MUST be bounded by MAX_FORCED_INCLUSION_BYTES so that the request's storage cost and its later inclusion are bounded. Requests are strictly FIFO by id; id is never reused. Failure modes: (a) a blob-backed request expires and becomes unincludable and unrefundable; (b) an unbounded payload lets one request consume an entire L2 block, converting the censorship remedy into a denial-of-service tool; (c) a reused or reorderable id lets a proposer shuffle or selectively drop the queue. Proven sourced unmeasured
FI-02 — the inclusion duty: an L2 validity rule with an L1 backstop The duty has two layers and both are normative. (a) L2 validity rule (CONS-01). A proposal is invalid unless its first block includes, as transactions and in FIFO request order, every request that is eligible and has been observed at the configured Ethereum finality depth as of the proposal's parent; correct validators MUST reject a proposal that omits one. (b) L1 backstop in land. The Inbox MUST compute due and require exact equality with the covered set bound by the proof: 
due = { r in queue : r.eligibleAtL1Timestamp <= _input.firstBlockTimestamp && !consumed[r] }
require(keccak256(abi.encode(bytes32("TAIKO_ETNA_FI"), block.chainid, coveredIds))
        == forcedInclusionCommitment);                       // L1-05 row 20
require(setEquals(coveredIds, due));                         // else ForcedInclusionNotCovered(id)
require(block.timestamp <= _input.firstBlockTimestamp + FORCED_INCLUSION_MAX_DRIFT);
                                                             // else BatchTimestampDrift(...)
consume(coveredIds);                                         // each id exactly once, in FI-01 order
coveredIds MUST be strictly ascending and duplicate-free; a duplicate MUST revert ForcedInclusionNotCovered(). Exact equality — not containment — is required so that a proposer can neither omit a due request nor pad the batch with requests that are not due in order to change their relative order. FORCED_INCLUSION_MAX_DRIFT is the bound that stops a batch from back-dating firstBlockTimestamp to dodge requests that became eligible in the meantime; it is a liveness parameter whose value is fixed in 09 and is UNMEASURED — closing it requires measured L2/L1 clock skew under the stated operating assumptions. Because firstBlockHeight is forced to lastLandedHeight + 1 (L1-06), a proposer cannot move the batch boundary to escape the duty. Failure modes: (a) without the L2 rule, the queue drains at proposer discretion and the duty is only a fee; (b) without the L1 backstop, a colluding quorum can omit a request forever while continuing to land batches; (c) containment instead of equality lets a proposer reorder due requests relative to each other; (d) without the drift bound, a proposer can label a batch with a timestamp older than a request's eligibility and legitimately claim the request was not yet due. Proven unmeasured
FI-03 — escape hatch under sustained censorship A request MUST NOT be voidable. There MUST NOT exist an owner, DAO, operator, or recovery function that removes a request from the queue, rewrites its eligibleAtL1Timestamp, or marks it consumed without a corresponding accepted batch — contrast init3() (Inbox.sol:253-258), which does exactly that. When a request has remained eligible and uncovered for longer than FORCED_INCLUSION_ESCAPE_THRESHOLD (seconds), the following MUST hold: (a) the request stays in the queue and remains coverable by any future batch, forever; (b) the requester becomes entitled to a refund of the fee it paid, claimable from the Inbox at any time thereafter, without removing the request or affecting its coverage obligation; (c) land continues to reject batches that fail FI-02, so a chain that keeps producing without covering the request stops being able to settle, which is the halt defined by HALT-01; (d) honest participants MUST NOT respond by discarding, rolling back, or re-founding finalized history (HALT-02). The hatch deliberately does not provide an L1-side force-exit of L2-held value: the funds are in L2 state, and no rule here may invent an L1 path that mints or releases them. That limitation MUST be disclosed wherever the hatch is described. Failure modes: (a) a voidable queue destroys the censorship remedy and destroys the evidence of the censorship (WH-02); (b) an "escape" that mints or releases L2-held value on L1 is a bridge exploit with an honest name; (c) an escape that invalidates finalized history is Mode B by the back door and is forbidden by D2 in ordinary operation. Proven
FI-04 — forced inclusion can only add to a future block; it can never reorder or revoke past history A covered request's payload MUST enter as a transaction in an L2 block whose height is strictly greater than lastLandedHeight — i.e. in a block of the batch currently being landed, or a future one, never in an already-landed block. A request MUST NOT be able to change the content, ordering, or state root of any block at a height ≤ lastLandedHeight, and MUST NOT be able to change any checkpoint record (L1-06). Within the batch that covers it, the request's position relative to other covered requests is fixed to FIFO request order (FI-02); its position relative to non-forced transactions is a derivation rule owned by CONS-01. A request that is never covered MUST remain queued rather than be discarded (FI-03). There MUST NOT exist a code path that uses a forced inclusion, or the fact that one is overdue, to re-execute, invalidate or replace a landed batch (REC-01). Failure mode: a censorship remedy that can reorder or revoke past history is a retroactive-reordering mechanism — the mechanism D2 forbids — and it would let an attacker use the forced-inclusion queue to rewrite settled outcomes, including bridge messages already authenticated against a checkpoint. Proven
FI-05 — griefing controls and fee escalation The required fee for a request MUST escalate with queue depth: 
fee = floor(BASE_FEE * (FEE_DOUBLE_THRESHOLD + pending) / FEE_DOUBLE_THRESHOLD)  // pending = queue length
fee = min(fee, MAX_FEE);                                                          // no overflow, no unbounded grief
This is the shape used at revision 7718753c1 (LibForcedInclusion.sol:89-93, with baseFee = 1_000_000 gwei and threshold = 50 at MainnetInbox.sol:49-50) sourced; this design's BASE_FEE, FEE_DOUBLE_THRESHOLD and MAX_FEE are set in 09 and are UNMEASURED. Additional controls are mandatory: (a) a request MUST NOT be cancellable once block.timestamp ≥ eligibleAtL1Timestamp — before that it is cancellable, and cancellation refunds the fee minus a fixed CANCELLATION_COST; (b) each request consumes exactly one slot of the L2 block space it eventually occupies, and the number of requests a single batch can cover MUST be bounded by MAX_FORCED_INCLUSIONS_PER_BATCH, so that both land and block production have bounded cost; (c) the queue length MUST be bounded relative to MAX_UNSETTLED_AGE so that the due set cannot grow faster than batches can clear it; (d) land's due-set computation MUST be bounded by MAX_FORCED_INCLUSIONS_PER_BATCH plus the queue growth permitted by (c), never by an unbounded loop over all requests ever made. Failure modes: (a) a free or cheap queue lets an attacker fill the due set so that every land reverts, stalling settlement at negligible cost; (b) an unbounded due-set loop makes land unaffordable or uncallable as the queue grows; (c) cancellable-after-eligible requests let an attacker withdraw the evidence of censorship exactly when it matters. Note honestly that this remains a cost-imposing liveness attack even with escalation: its profitability is UNMEASURED, and closing it requires the fee schedule and the measured cost of covering a request. Proven sourced unmeasured

Why a sub-threshold cartel cannot starve inclusion

This is a conditional liveness argument with named premises, not a guarantee. Proposer selection is by stake-weighted rotation (CONS-06), and a cartel holding f < 1/3 of the stake that counts toward quorum (A-CONS-1) holds fewer than 1/3 of proposer slots in expectation over any window of s slots. Let p = f be the cartel's slot share. The probability that the cartel leads s slots in a row is p^s, so the expected waiting time for an honest slot is 1/(1-p) ≤ 1.5 slots derived. An honest proposer MUST include the due set or its proposal is invalid (FI-02a, CONS-01), and honest validators precommit only valid proposals, so the request is covered as soon as an honest proposer leads. The cartel's residual power is to make coverage late, not to prevent it, and lateness is bounded by the rotation, not by a timeout judgement (STATUS-10). Two honest caveats: this holds only while A-CONS-1 holds — at ≥1/3 Byzantine stake the argument does not apply and the protocol claims nothing; and it assumes proposer selection is not predictable enough for the cartel to buy the specific slots in which a request becomes due, which is an assumption about the selection function that MUST be stated in CONS-06, not here.

MSG-02 — replay protection and domain separation The preserved surface keeps its existing encodings, and both MUST be frozen by MIG-02 because they determine every stored slot and every cached proof: the signal slot is keccak256(abi.encodePacked("SIGNAL", chainId, app, signal)) (SignalService.sol:160-171), and the bridge message hash is keccak256(abi.encode("TAIKO_MESSAGE", message)) with Message.srcChainId and Message.destChainId inside the struct (Bridge.sol:536-539). Replay on the same chain is prevented by the receiving Bridge's per-message status (NEW / RETRIABLE / DONE / FAILED / RECALLED, IBridge.sol:9-15): a message that is DONE, FAILED or RECALLED MUST NOT be processable again, and the failure signal is msgHash ^ 3 (Bridge.sol:544-546). Failure modes: (a) a signal verified on chain A being replayable on chain B — prevented only by the chain id being inside the hash; (b) a stale received-signal cache entry whose checkpoint was replaced by a different history, which would let a message be proven against a state root that is no longer the protocol's; (c) changing the slot derivation silently, which orphans every outstanding message and every cached proof without any event. MSG-03 — withdrawal eligibility and delays No value may leave the bridge surface on the strength of anything weaker than STATUS-06. An L2→L1 withdrawal or message authentication MUST require a checkpoint written by a successful land whose stateRoot covers the signal, plus the delay WITHDRAWAL_DELAY measured from that checkpoint's l1BlockNumber; where the claim depends on an L1 fact that can still be reorganised, it MUST additionally require STATUS-07 — the accepting L1 transaction at the configured Ethereum finality depth. An L1→L2 release MUST require the Anchor to have observed the L1 deposit at that same finality depth (SYS-02), never at inclusion depth. WITHDRAWAL_DELAY MUST be derived from the whole settlement pipeline — proving latency, L1 inclusion, Ethereum finality and the evidence window — and its derivation is owned by ECON-03; its value is in 09 and is UNMEASURED. No withdrawal path MUST depend on a private witness, a committee certificate, an off-chain store, or an operator action (DA-04). The design MUST disclose, wherever withdrawal timing is described, that a settlement halt delays withdrawals indefinitely while losing nothing: under Mode A the funds are not forfeited, they are unavailable until settlement resumes (LIM-01). Failure modes: (a) releasing value against an inclusion-depth L1 fact lets an L1 reorganisation make the release unbacked; (b) releasing against a checkpoint that a later transaction could replace is exactly the rewrite that Mode A forbids, executed on the bridge; (c) a delay shorter than the evidence window lets a proven-misbehaving party exit before its stake can be slashed (ECON-07).
