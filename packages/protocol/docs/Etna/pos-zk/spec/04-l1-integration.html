04 — L1 integration: atomic data + proof, data availability, bridge anchoring, and the limits of inclusion

This page carries D5 and D8. It fixes how a batch becomes STATUS-06 — accepted on L1: one L1 transaction carrying the batch data and its validity proof, out of which the Inbox itself derives the data commitment, and out of which a single monotone checkpoint advance follows. It also fixes where that data is canonical (DA-01), how the blob path binds data to the proof (DA-03), the honest limit on inclusion — no per-transaction guarantee and no L1 forced-inclusion path (FI-REMOVED-01, FI-PLANNED-01, LIVE-04) — and how the preserved SignalService/Bridge addresses authenticate against these checkpoints (MSG-01–MSG-03). (user decision D-6: forced inclusion removed)

Two changes on this page deliberately lengthen exits. An L2→L1 release is anchored on an epoch-boundary checkpoint that carries proofs from k distinct registered backend families (L1-13), and a rule-triggered, self-expiring withdrawal veto of at most T_VETO may delay releases while an on-chain-verified proof contradiction is investigated (MSG-04). Both are user-visible: an exit may have to wait for an epoch boundary and for the slowest of k proofs, and a veto can add up to T_VETO to any pending withdrawal. Neither cancels a proven withdrawal, and neither is a repair for an unsound backend. (PR #22262 review comment 1, item 3: withdrawals are the one place proof soundness is multiplied, and the removed pause lever is replaced by a bounded rule-triggered veto.)

Baseline for every comparison to "today" on this page: Taiko monorepo revision 7718753c1 (2026-10-05), file packages/protocol/contracts/layer1/core/impl/Inbox.sol. Nothing on this page is implemented, deployed, audited or measured (GEN-01). Every number is tagged derived / sourced / unmeasured.

Assumption disclosure. Acceptance here is a liveness path guarded by cryptography, not a safety guarantee by itself. Wherever a statement depends on <1/3 Byzantine stake (A-CONS-1) or on the availability assumptions (A-CONS-5, A-DA-2) it says so at the claim (01-requirements-and-threat-model.md §4).

1. One atomic acceptance

L1-01 — single atomic accept entry point; no data-first path The Inbox MUST expose exactly one function that can accept a batch and advance the checkpoint. Its name is land(data, proof) — the batch data first, the validity proof second, one entry point and no other. One call MUST carry, in one L1 transaction: (a) the batch range, given as uint64 firstBlockHeight and uint64 lastBlockHeight of L2 blocks; (b) the batch data, given as the bytes calldata _data argument and/or the blob sidecars of that same transaction; (c) the proof, given as _proof; and (d) the claimed post-state and finality values of L1-05. Data and proof are inseparable: there MUST NOT exist any entry point, overload, fallback, multicall helper, or recovery path that records the data (or a commitment to it) in one transaction and the proof in another. There MUST NOT exist a "propose then prove" path in any mode. Every other artifact that names this entry point — the migration state gate (MIG-03), the parameter register, the glossary and the client interfaces — MUST use the same name land(data, proof): a second name (for example accept(data, proof)) is a defect, because the migration gate and the audited interface would then be specified against a selector that does not exist. (review round 1, finding B R1-16) Batch-length consequence of atomicity. Because the data and the proof share one transaction, the batch's blob count is capped by Ethereum's per-L1-block blob limit rather than by a separate protocol choice: at the DA-bound rate one 2-second L2 block is one 131,072-byte blob (EIP-4844), so BATCH_BLOCKS × blobs_per_block ≤ 9 (hard) and BATCH_BLOCKS ≤ 6 (sustainable at EIP-7691's 6 target / 9 maximum blobs per L1 block), and MAX_BATCH_BLOCKS MUST respect the same bound (registered, with its sourced constants and derivation, in 09; L1-05 row 7). (Phase B plan §8.6: the blob ceiling is a derived bound on K, and the registered placeholder of 32 is not publishable at the DA-bound rate.) Failure mode: the batch's data becomes public before any proof exists, so a batch can be published and never proven — the data occupies L1 capacity, consumes the settlement budget, and settles nothing. Allowing it in one mode re-opens D5 for every mode, because the recovery path becomes the cheapest way to publish data. Proven sourced (D5; contrast below)

L1-02 — no entry point records a pending or incomplete batch No entry point of the Inbox — public, external, or reachable through an upgrade initialiser — may write a batch record, a predecessor link, a proposal hash, a data commitment, or a checkpoint pending a proof. The only accepted state that exists for a range is the checkpoint written by a successful land(data, proof) call. An "announce" / "intent" / "commit" function may exist only if all three hold: (i) nothing it writes is read by land(data, proof), by the verifier route, or by any admission check; (ii) it cannot become a precondition for a later acceptance — in particular, a later land(data, proof) for the same range MUST succeed whether or not the announce function was ever called, and in any order; (iii) its failure or omission has no effect on liveness or on any other rule. The safest design has none, and this specification designs none. Failure mode: an announce function that later becomes load-bearing converts "publish data" into a privileged step — the first caller of the announce function acquires a sponsorship right over the range, and a range whose announcement was never made (or was made and then made unreadable) is unlandable. This is the propose-then-prove failure of L1-01 arriving through the back door. Proven

L1-03 — failed verification leaves the batch unaccepted with no partial effect land(data, proof) MUST execute in this exact order: (1) decode and shape-check the input in memory only, with no state writes; (2) derive every contract-derived public input of L1-05 from L1 storage and from this transaction; (3) if blobs are used, perform the DA-03 checks and record the accepted (versionedHash, z, y) tuples in memory; (4) call the active verifier route with the statement hash; (5) treat the proof as invalid unless the call returns exactly abi.encode(true) — a revert, an empty return, or any other return value is invalid; (6) only then write the checkpoint record, advance the height pointer, record the proof-bound signerBitmap into the staking contract's per-epoch participation accumulator (ECON-02 clause 5), and pay out L1-11; (7) emit events last. If any step fails, land(data, proof) MUST revert with a typed error and produce no partial effect: no checkpoint, no height advance, no payout, no event. (user decision D-6: the forced-inclusion consumption write is removed with the queue.) Failure mode: a checkpoint exists that no proof ever justified. A "verify last, write first" ordering survives only as long as the verifier always reverts and nothing can swallow the revert; the moment a route returns false, or an upgrade or a low-level call absorbs the failure, the write becomes permanent and the chain's checkpoint advances without a proof. Proven

Why the baseline ordering is safe today, and why this design still changes it. At 7718753c1, prove() writes the SignalService checkpoint (Inbox.sol:364-370), updates _coreState and emits Proved (Inbox.sol:376-387) before calling _proofVerifier.verifyProof(...) (Inbox.sol:394-398). That is not a vulnerability in that contract as written, for one stated reason: the verifier call is in the same transaction and a reverting verifier unwinds the whole transaction, restoring the checkpoint and the core state. The baseline research records exactly this: "the ordering is still structurally 'optimistic write, then verify' — a property a same-tx redesign must preserve" (research/taiko-baseline-contracts.md §3.3). This design does not rely on that property. Reasons, in order of importance: (a) the interface tolerates a verifier that returns false instead of reverting, and a try/catch or a future routing layer could absorb a revert; (b) the checkpoint is a public authentication anchor for the preserved bridge surface (MSG-01), so its integrity must not depend on an external contract's revert discipline; (c) correctness must be readable from the function body rather than inferred from EVM unwind semantics. Verify-first costs nothing in gas terms that this specification claims to know — the cost of land(data, proof) is UNMEASURED and would be measured by a gas-snapshot run over a batch of the target size; no such measurement exists.

L1-04 — admission: no gate, no expiring range, any prover Any account MUST be able to call land(data, proof). The admission rules of land(data, proof) MUST contain: no whitelist and no allowlist (of provers, proposers, or relayers); no owner-, DAO-, or operator-controlled approval; no minimum bond, stake, or reputation to submit; no deadline, timestamp, block-number or age condition that can make a range permanently unacceptable; and no dependency on tx.origin, block.coinbase, gas price, or L1 proposer identity (GEN-06). For any unsettled range, any account that can produce a valid (data, proof) pair MUST be able to land it. A height retired by a completed recovery is not an unsettled range: the canonical chain begins at resumeHeight, a batch below it neither extends the current checkpoint nor becomes landable later, and its rejection under L1-06 is a structural rule of the recovered chain, not an admission gate and not an expiry. Structural bounds are permitted and MUST be exactly these: the range must start at max(lastLandedHeight + 1, resumeHeight) (L1-06), where contiguous means linked to the current checkpoint — firstBlockHeight = previousHeight + 1 in the ordinary case, and the single restored-checkpoint link of REC-04 when a completed retirement skipped heights; the batch must be non-empty; the range length is the submitter's choice and no rule mandates a fixed or canonical length — a prover lands whatever contiguous range it has data and a proof for, so that settlement happens when the data is worth publishing rather than on a fixed clock; a racing submission that loses to another valid batch is void and its prover is not paid (L1-10), which is the disclosed cost of a permissionless landing market; and every loop in land(data, proof) must be bounded by the transaction's own contents (its blob count, its claimed range length), never by an unbounded external structure. (user decision D-6: the forced-inclusion coverage list is removed from the permitted loop bounds.) Backpressure on production — the consensus-enforced unsettled-depth cap of HALT-03 and DA-06 — MUST NOT be implemented as an admission condition on land(data, proof). Failure mode: a validly PoS-finalized extension of the L1 checkpoint becomes permanently unacceptable, i.e. a legitimate extension of history above the checkpoint can never be settled. Under Mode B the protocol may halt, and only a completed recovery following a settlement stall — permissionless, bonded, delayed and cancellable — may replace history strictly above the latest L1-accepted checkpoint, never at or below it; an admission gate or an expiry removes the range from settlement outside that one sanctioned procedure, so a valid proof can no longer settle it — the failure this rule forbids. This rule is required under Mode B too, not merely compatible with it (04-architecture-decision.md §5.4, L1-ADMIT-NO-EXPIRY; research/mode-a-feasibility-analysis.md §4). Proven (Mode B: the recovery boundary leaves the no-gate, no-expiry admission rule in force)

2.1 Public-input reconciliation: every field of both lists

PRF-02's journal is the single authoritative public-input vector; L1-05's table is its contract-side derivation table. A mismatch between the two lists is a protocol defect: a value L1 hashes that the guest never committed to makes statementHash unmatchable, so every honest proof fails and no batch can land; a load-bearing value in neither list is unbound, so the lander (any account, L1-04) chooses it. The table maps every L1-05 row to a journal field or to "not a public input". In the reverse direction, a PRF-02 journal field with no matching row below is a protocol defect of the same class — the guest would commit to a load-bearing value that the contract never derives and binds — exactly as PRF-02 declares.

L1-09 — proof-system policy, verifier routing and the L1 ability to move to a new circuit One closed acceptance policy: exactly one route per proof. A batch is accepted only on exactly one valid proof, checked against exactly one registered route. A route is the triple (programImageId : bytes32, verifier : address, backendFamily : bytes32); routeVersion is only the storage key that names the route, not a fourth semantic component. The verifier MUST be a deployed contract (verifier.code.length > 0) that implements the statement of PRF-01 and has been audited to it; a route whose verifier is not deployed, not audited, or whose checked image id differs from programImageId MUST NOT be registered, and a registration that would install one MUST revert. Acceptance is first-valid-wins (L1-10): two provers may submit proofs under different registered routes for the same range, and the first proof that verifies lands — but each individual proof is verified by exactly one route, and land(data, proof) MUST NOT require, and MUST NOT accept as a substitute, a second proof (this is PRF-09's closed policy).
Who may register a route: an upgrade, and no one else. Adding, changing or retiring a route is a rule change executed by an upgrade of the Inbox under GOV-02/GOV-03; it MUST NOT be callable at runtime by any account, owner, operator or DAO transaction (GOV-01: the DAO governs upgrades only). There MUST NOT exist a permissionless or owner-only registration entry point. The earlier sentence "enabling a new route is additive and MUST NOT be rejectable by any account" is deleted: it was a bridge-theft hole, because any account could have installed a verifier that returns abi.encode(true), after which any batch could be landed with an arbitrary state root. The permissionless requirement is L1-04's, and it applies to calling land(data, proof), never to changing the rules under which a proof is checked.
Routes MUST live in the Inbox's own storage — not in a mutable registry owned by another contract — because the baseline verifiers (SP1Verifier, Risc0Verifier) are non-upgradeable Ownable2Step contracts replaced by redeployment, and an upgrade of a verifier contract must never be able to change which statement the Inbox accepts. L1-13 — withdrawal roots: epoch-boundary checkpoints carrying k distinct-backend attestations (1) What a withdrawal root is. For epoch e, the epoch-boundary checkpoint is the L1-07 record whose height equals h_last(e), the last L2 height of the epoch under the L1-committed schedule (CONS-13(2)). It exists for every epoch the chain has settled past: batches are contiguous (L1-06) and none may span an epoch boundary (PRF-05), so the batch containing h_last(e) can end only at h_last(e). A withdrawal root is an epoch-boundary checkpoint that carries valid proofs of its own accepted statement from k distinct registered backend families, with k = K_PROOF_BACKENDS, n = N_PROOF_BACKENDS and 2 ≤ k ≤ n; both values are unmeasured and registered in 09. Families are the backendFamily tags of L1-09; two routes carrying the same tag count once. The accepted statement is the PRF-02 journal the checkpoint was landed with, identified by the statementHash recorded at acceptance; the k-of-n policy adds verification of that one statement and never a second statement (PRF-14). (2) Only a withdrawal root finalizes a withdrawal. An L2→L1 withdrawal or message authentication (MSG-03) MUST be proven against the stateRoot of a withdrawal root at a height not below the height at which the signal was stored. A checkpoint that is not a withdrawal root MUST NOT anchor any value release, however many ordinary proofs it carries. A signal stored at any height h becomes releasable as soon as any withdrawal root at a height ≥ h exists; it is not tied to the epoch it was created in, so one epoch that fails to form a root does not by itself strand it. A withdrawal root is always at or below the current L1-accepted checkpoint and is unaffected by a later completed recovery, which restores that checkpoint exactly (REC-01). (3) How a root is formed. At acceptance the Inbox MUST record, in a side mapping keyed by height, the accepted statementHash and daMode — the same side-mapping pattern L1-09 already uses for routeVersion, so the frozen L1-07 record is not altered. The route that accepted the batch counts as the first family attestation. Any account MAY then call attestWithdrawalRoot(height, programImageId, proof); the call MUST verify the proof against the recorded statementHash under a route whose image is in that epoch's accepted set (MIG-05) and whose family has not already attested that height, MUST reject a proof for any other statement with StatementMismatch, and MUST record the family. When k distinct families have attested, the height MUST be marked a withdrawal root and an event emitted. The attach path MUST NOT write a checkpoint, MUST NOT move L1-06's pointer, and MUST be permissionless. It is not a batch-acceptance transaction and publishes no batch data: the data is already canonical in the accepting transaction (DA-01), so D5 is not relaxed by this path, and an attestation can neither accept, advance nor replace a batch. An image upgrade or retirement MUST NOT remove an attestation already recorded, and PRF-10's preservation clause — a new image MUST accept every history the previous image accepted — applies to the recorded statementHash, so an upgrade does not by itself strand an un-attested boundary checkpoint. (4) The cost is per epoch, never per batch. One root costs k verifications and k−1 additional proofs per epoch. With B landed batches per epoch the proving volume becomes 1 + (k−1)/B times the one-proof-per-batch baseline, and ordinary settlement is untouched: a non-boundary batch is still accepted on exactly one proof (L1-09, PRF-09). B is unmeasured; E_EPOCH = 1,800 s is derived and MAX_BATCH_BLOCKS bounds B from below only. The additional proofs for one root are independent and MAY be produced in parallel, so the added latency is the slowest of them, not their sum. Requiring k proofs per checkpoint rather than per epoch would cost (k−1) additional proofs per batch — B times the multiplier — and is not proposed; if S1 measures even the per-epoch multiplier as unaffordable, the fallback is stated in (7), never a silent k = 1. (5) Exit-path liveness is weaker than settlement liveness, and is stated. Forming roots depends on k independent implementations being available. If one family is temporarily unavailable, a signal above the last root waits for a later epoch boundary whose root is formed by k available families: at least one further epoch plus its proofs. If fewer than k families have a live accepted route for every subsequent epoch, no new root is formed and signals above the last root cannot be released. The value is not lost — it stays in the preserved Bridge and vault contracts — but the exit is delayed indefinitely. W_ROOT_WAIT_MAX = E_EPOCH + T_PROOF_MAX_PERMITTED, registered in 09, is the maximum additional wait only while at least k families operate; outside that condition the wait is unbounded. The attach proofs are paid by whoever submits them and no funding rule for them exists in this specification, so the exit path's liveness also depends on those proofs being economic (Open; the natural funding source is the proving share of ECON-02, which is owned elsewhere). The Open route inventory of L1-09 is therefore a launch gate for withdrawals: fewer than k deployed, audited families means withdrawals cannot open at all, and that consequence MUST be disclosed rather than papered over. Nothing in this rule gates validator exits, staking withdrawals, land(data, proof) (L1-04) or the L1→L2 direction. (6) What k-of-n buys, and its residual. For the withdrawal path it replaces "soundness equals that of the weakest backend" with "a false root requires every one of k independent implementations to accept a false statement, or a defect common to all of them". It does not cover a common-mode defect in the shared statement, the guest logic, the payload framing or this specification (PRF-14), and it does not cover settlement: one unsound backend can still land a forged ordinary checkpoint under the one-proof policy. Because PRF-06 requires every executed block's resulting state commitment to equal that block's own header root, and the header chain to link to the predecessor block hash, a forged state root cannot be honestly extended: no honest batch can be landed above the forged record and settlement stops there. That stop is the residual of this fix, and recovery cannot clear it because the forged record is the latest accepted checkpoint (REC-01). Closing the residual requires k proofs on every checkpoint — the per-batch multiplier of (4) — and is not proposed here. Premises: family independence is asserted by the registering upgrade and audited at migration (A-GOV-1), never derivable on-chain from an image id; the stop argument uses the collision resistance of the state commitment and the determinism of execution. (7) Affordability gate and honest fallback. k and n are fixed by the S1 proving-cost measurement, not chosen here. If S1 reports the per-epoch multiplier as unaffordable, the requirement MUST be withdrawn by a recorded change order that simultaneously discloses in LIM-01 that withdrawal soundness is single-backend and rests on the veto of MSG-04 plus disclosure; k = 1 MUST NOT be shipped silently, and no artifact may claim the multi-backend property of this rule unless k distinct families are actually registered and operating. Changing k, n or T_VETO is an upgrade (GOV-02, GOV-03); an upgrade that raises k applies only to batches landed after it and MUST NOT block the designation of an already-landed boundary checkpoint, and a change to T_VETO fixes only windows started after it, never one already running. Failure modes: (a) a withdrawal released against an ordinary checkpoint inherits the weakest backend's soundness, which is the single point of failure this rule removes; (b) requiring k proofs on every batch multiplies the whole proving fleet by k to protect a path only the epoch boundary needs; (c) letting an unavailable backend block root formation without stating it converts a soundness fix into an undisclosed exit-path liveness failure; (d) treating k-of-n as a repair for a common-mode defect, or for a forged checkpoint that admits no honest continuation, would overstate what the mechanism can do. Proven Assumed unmeasured Open (the mechanism and its argument are specified; k, n, the S1 multiplier, the route inventory and the attach incentive are open, and the last of those is an honest gap in the exit path's liveness)

4. Races, fees, and L1 reorganisation

L1-10 — submission races, re-submission, and what a proof is a proof of The first valid submission wins. Concretely: land(data, proof) MUST be atomic with respect to the checkpoint pointer, so two transactions in one L1 block are ordered by L1, the first one advances lastLandedHeight, and the second MUST revert AlreadyLanded() if it targets an overlapping or duplicate range, or MUST be evaluated against the new checkpoint if it extends it. Re-submission of the same batch (same dataCommitment, same range) by a different account MUST be accepted whenever the first submission did not land; it MUST NOT be rejected because another account previously submitted, attempted, or announced the same range. A proof is a proof of exactly the statement of L1-05: a proof for a different batch — a different range, a different predecessor, a different data commitment, a different epoch or set root — MUST NOT be usable as a substitute, and MUST fail verification because those values are in statementHash. The reward of L1-11 MUST be paid to msg.sender, the account that paid for the landing transaction; the protocol MUST NOT attempt to attribute it to any address named inside the proof. Consequently, a proof observed in the public mempool can be landed first by another account, which then collects the reward; this is an accepted property of permissionless landing, not a defect to be patched with a first-submitter reservation, and the mitigation available to provers is private orderflow or bundling. Failure modes: (a) a first-submitter reservation is a permissioned gate that expires a range into unrecoverability when the reserving account disappears (L1-04); (b) accepting a proof for a different batch lets a prover attach a valid proof to unrelated data — the whole point of binding the data commitment is that it cannot be done; (c) paying the reward to a proof-declared address lets anyone who copies a proof redirect the payout and makes the identity of the prover unfalsifiable. Proven
L1-11 — fees, the L2→L1 sweep, and the reward accounting identity The Inbox MUST hold exactly one reward-related ledger and MUST enforce its conservation with checked arithmetic (no unchecked subtraction; violation reverts FeeAccountingUnderflow()): a prover reward ledger. Its inflows are (i) any msg.value the submitter adds and (ii) where the recorded allocation policy assigns a proving share of the reward pool of ECON-02 clause 5(a), exactly that share, credited by a permissionless transfer that debits the pool in the same transaction. The swept L2 fee revenue is not an inflow of this ledger: it is credited to the pool, and this ledger MUST NOT be presented as a second destination or as a claim on an unarrived sweep. (user decision D-8: L2 fee revenue reaches L1 only by the sweep of ECON-02 clause 7, into the single reward pool) On a successful land(data, proof) the identity is: 
proverReward_after    = proverReward_before + msg.value - rewardPaid
rewardPaid            = min(REWARD_QUOTE, proverReward_before + msg.value)
require(proverReward_after >= 0);
require(rewardPaid <= proverReward_before + msg.value);
land(data, proof) MUST NOT require a non-zero rewardPaid: if the reward ledger is empty, the batch still lands with rewardPaid = 0 and the event records 0. REWARD_QUOTE MUST NOT depend on anything the submitter controls except the gas actually consumed, and MUST NOT depend on the proof's contents beyond validity. The ledger MUST be debited only by the rewardPaid of a successful land(data, proof) and by nothing else — never for validator payouts, gas, refunds or any other purpose — and no entry point, payout or upgrade may spend it outside that path. (user decision D-6: the forced-inclusion ledger, its segregated escrow, its coverage and refund paths and their mutual-exclusion argument are removed with the queue; the prover reward ledger keeps its conservation identity and the FeeAccountingUnderflow() revert.) L2 fee revenue: one sweep, one destination, no second ledger. The L2 fee revenue of ECON-02 reaches L1 by exactly one path: the permissionless sweep of ECON-02 clause 7, which moves the balance of the L2 fee vault (L2FeeVault) through the preserved Bridge (MSG-01) to the reward pool account of ECON-02 clause 5(a). The sweep is callable by any account at any time; it takes no argument that influences the destination, its destination and message are built by the vault itself from protocol constants (the canonical invocation selector, the reward-pool address as destOwner, and to set to the pool), and the pool is credited only when the preserved Bridge authenticates that message on the bridge invocation path (MSG-02). Any other message to the pool is the sender's own loss, never the protocol's: the pool accepts no credit that did not arrive by the bridge invocation, and the Inbox MUST NOT compensate a mis-sent transfer. (S5 §7: the sweep is protocol-constructed and the pool is credited only from the recognized bridge path.) The Inbox MUST NOT hold, mirror, escrow or reserve the swept balance, MUST NOT credit it to the ledger below on arrival, and MUST NOT gain a second reward-related ledger for it; the only credit this ledger may receive from the pool is the proving share of the recorded allocation policy, debited from the pool in the same transaction. A sweep that has not arrived is not a balance, not a receivable and not a promise, and if it fails the rewards it would have funded stop rather than become a claim on future revenue (ECON-02 clause 7(d)). (user decision D-8: security is funded from L2 fees, routed through the preserved Bridge into the single reward pool) Scope. This ledger is the Inbox's only reward-related state, and validator rewards are not a term of its conservation identity: validator payouts come from the segregated ETH reward pool of the L1 staking contract (ECON-02 clause 5), never from the Inbox's ledger, so the identity above is unaffected by them; the swept L2 fee revenue is not a term of it either, because that revenue is credited to the pool by the sweep above and never to this ledger (ECON-02 clause 7). (review round 2, finding E-R2-05: the reward mechanism is stated on the staking contract and does not drain or double-count the Inbox ledger.) Failure modes: (a) an empty reward pool blocking acceptance turns economics into an admission gate, which L1-04 forbids and which makes settlement depend on a treasury rather than on a proof; (b) a second payout path out of the reward ledger drains it; (c) a reward that scales with a submitter-chosen quantity is a self-dealing surface; (d) crediting the swept L2 fee revenue to a second Inbox-side balance, or treating an unarrived sweep as a receivable, spends the same ETH twice and makes the reward identity unfalsifiable. Proven unmeasured (REWARD_QUOTE, the gas cost of land(data, proof), the L2 sweep's gas and the preserved Bridge's L2→L1 message fee (ECON-02 clause 7) are UNMEASURED; closing them requires a gas-snapshot run over batches of the target size, which does not exist)
L1-12 — L1 reorganisation handling, and no unfinalised L1 fact is settled If the L1 block containing a land(data, proof) transaction is reorganised out below Ethereum finality, the transaction is undone by Ethereum: no checkpoint record exists, no height advanced, no fee paid, and no event is part of the canonical chain. (user decision D-6: the consumed-request reference is removed with the queue.) The batch remains PoS-certified / provisional — valid, and above the latest L1-accepted checkpoint replaceable only by a completed recovery following a settlement stall — and MUST be re-landable under L1-04. It is not re-landable with the old proof once a completed recovery has advanced the generation: the stale generation makes the proof unusable, and the data may be re-batched against the restored checkpoint by any proposer. (S5 §2: the "re-landable with the same dataCommitment" sentence is corrected — after a recovery the stale generation makes that proof unusable, and the data may be re-batched against the restored checkpoint by any proposer.) The Inbox MUST NOT contain any function that "repairs" a reorganisation by writing a chosen checkpoint, height, or state root: the only response is re-execution of land(data, proof). Because a checkpoint chain is built by strict succession (L1-06), a reorg that drops one land(data, proof) transaction also drops every later transaction that extended from it, since those transactions cannot satisfy firstBlockHeight == max(lastLandedHeight + 1, resumeHeight) on the new branch; a submitter whose transaction is invalidated this way MUST re-submit. Independently of the Inbox, no L2 rule may treat an unfinalised L1 fact as settled: L2 consensused state may consume only Ethereum-final L1 facts, or L1 facts at the configured finality depth, per SYS-02 and STATUS-07. Checkpoint.l1BlockNumber (L1-07) records inclusion, not finality; any consumer that needs finality MUST compare it against the configured depth. Failure modes: (a) an owner-recovery setter for the checkpoint turns an L1 reorg into a discretionary rewrite of the L2 anchor; (b) an L2 rule that acts on an L1 fact at depth 0 can act on a fact that later disappears, so a PoS-finalized L2 block can be left depending on an L1 event that no longer exists — the exact condition under which a finalized L2 block becomes unprovable. Proven

5. Data availability (D8)

DA-01 — the canonical data-availability location is the accepting L1 transaction The canonical copy of a batch's data MUST be the accepting L1 transaction itself: its calldata and/or the blob sidecars of that same transaction, as bound by DA-02 and DA-03. A batch is accepted on L1 only together with that data. The design MUST NOT define a second canonical location, and MUST NOT treat any location outside that transaction as sufficient for STATUS-06. Failure mode: two canonical locations means two answers to "what is the batch?", and the weaker one is the one an implementer will build against. Proven
DA-02 — calldata path: the contract computes the data commitment itself In the calldata path the Inbox MUST compute the data commitment itself over the exact calldata slice supplied to land(data, proof), and MUST pass that value as the public input. The construction is fixed as: 
dataRoot       = keccak256(_data)                      // one byte string: no field ambiguity
payloadRoot    = dataRoot
dataCommitment = keccak256(abi.encode(
                     bytes32("TAIKO_ETNA_DATA"),        // right-padded ASCII domain tag (GEN-05)
                     uint256(block.chainid),            // chain id is the second field (GEN-05)
                     uint64(firstBlockHeight),
                     uint64(lastBlockHeight),
                     uint8(daMode),                     // 1 = CALLDATA, 2 = BLOB, 3 = CALLDATA_AND_BLOB;
                                   // DA-03(0) fixes payloadRoot per mode
                     payloadRoot))
keccak256(_data) hashes one opaque byte string rather than a concatenation of fields, so it introduces no second-preimage ambiguity and is not an abi.encodePacked of multiple values. The committed object is the whole _data byte string — no prefix of it. For daMode = 2 the same outer encoding is used with payloadRoot = keccak256(committedBytes) defined in DA-03(0); for daMode = 3 DA-03's hybrid payloadRoot replaces the calldata-only value so that the full blob strings are inside the commitment. (review round 1, findings B R1-01, B R1-06) The byte-level layout of _data — how L2 blocks serialise into the batch payload — is fixed once, on PRF-07; this rule fixes only how L1 commits to it. The guest MUST recompute dataCommitment from the payload it actually executed, and MUST reject the batch if the recomputation differs. Because both sides hash the same whole byte string, this path needs no probabilistic argument and remains the unconditionally sound path; the blob path (DA-03) is the one that carries the fixed-point argument and is an implementation gate. On this calldata path the Inbox MUST ignore any submitter-supplied dataCommitment; if one is present in the input it MUST either be absent from the ABI or be checked equal and rejected with DataModeMismatch() on mismatch. (On the blob path the EVM cannot read the bytes, so the claimed value is proof-bound and completed in-guest instead; see DA-03(0).) Failure mode: taking the commitment from the submitter decouples the proof from the calldata, so a valid proof can be paired with arbitrary data in the same transaction — the strongest and simplest binding available is thrown away. Proven
DA-03 — blob path: whole-blob commitment, BLOBHASH, on-chain KZG opening, and in-guest evaluation at the per-blob challenge point For a batch whose data is in blobs, let n = blobCount and let blob index i range over [blobIndexStart, blobIndexStart + n). The Inbox MUST perform (i) and (ii) for every i, and the guest MUST perform (iv) and (v).
(0) What is committed. dataCommitment commits the whole published byte string that the guest executes and that L1 publishes, not a prefix of it. For daMode = BLOB the committed object is the concatenation, in blob index order, of the full 131,072-byte string of every blob in the transaction — all 4096 field elements per blob, including any unused remainder; for daMode = CALLDATA_AND_BLOB it is the batch calldata payload followed by that same concatenation. Every published byte is inside the commitment, and the unused remainder of a blob MUST be committed too. No prefix-only commitment is permitted. A commitment over a prefix (the first k field elements, the non-zero prefix, or the portion the payload "uses") is forbidden: if the commitment covered only a prefix, the challenge point would be fixed before the free suffix was chosen, and a prover could choose the suffix to satisfy p_D(z) = p_B(z) by solving one linear equation — that was the round-1 attack. The encoding is DA-02's outer encoding, with daMode set to the derived mode and: 
committedBytes = blob_0 || blob_1 || ... || blob_{n-1}      // each exactly 131,072 bytes (4096 elements)
payloadRoot    = keccak256(committedBytes)                  // daMode = BLOB
dataCommitment = keccak256(abi.encode(bytes32("TAIKO_ETNA_DATA"), uint256(block.chainid),
                                      uint64(firstBlockHeight), uint64(lastBlockHeight),
                                      uint8(daMode), payloadRoot))
// HYBRID (daMode = 3): payloadRoot = keccak256(abi.encode(bytes32("TAIKO_ETNA_HYBRID"),
//        uint256(block.chainid), keccak256(_data), keccak256(blob_0 || ... || blob_{n-1})))
The EVM cannot read blob contents, so on the blob path — and for the blob component of hybrid — the contract cannot recompute payloadRoot: it takes the claimed dataCommitment, binds it into statementHash and derives z_i from it, while (v) requires the guest to recompute the same value over the full blob bytes it executed. The value is therefore not a free submitter choice: a wrong value makes the proof unverifiable rather than making the contract misbehave. (review round 1, findings B R1-01, B R1-06)

(i) BLOBHASH equality. The Inbox MUST read the transaction's own blob versioned hash with the BLOBHASH opcode and require, for each i:

bytes32 vh = blobhash(i);
require(vh != bytes32(0) && vh == _input.blobVersionedHashes[i - blobIndexStart], BlobHashMismatch(i));

A zero value means no blob at that index in this transaction; because BLOBHASH is transaction-scoped, no other transaction's blobs can be substituted. The loop is bounded by the transaction's own blob count, whose protocol limit is the Ethereum per-block limit — target 6, maximum 9 blobs per block under EIP-7691 sourced.

(ii) On-chain KZG point evaluation. The Inbox MUST call the EIP-4844 point-evaluation precompile at address 0x0A with the 192-byte input abi.encodePacked(vh, z_i, y_i, commitment_i, proof_i) — z_i and y_i as 32-byte big-endian canonical field elements, commitment_i and proof_i as 48-byte compressed BLS12-381 G1 points. The call MUST succeed and MUST return exactly abi.encode(4096, BLS_MODULUS); otherwise land(data, proof) reverts BlobOpeningFailed(i). The precompile verifies kzg_to_versioned_hash(commitment_i) == vh and verify_kzg_proof(commitment_i, z_i, y_i, proof_i), and rejects non-canonical field elements. Its gas cost is 50,000 per call sourced (EIP-4844), so a batch using n blobs costs 50,000 · n gas for these calls derived; the total cost of land(data, proof) remains UNMEASURED.

(iii) The challenge point z_i is derived on-chain by Fiat–Shamir, per blob. It MUST NOT be supplied by the submitter. With statementCoreHash the hash of the whole PRF-02 public-input vector except the two challenge fields challengeZ/evaluationsY themselves — so the transcript covers daMode, feeRecipient, configHash, blobHashesHash, signerBitmap and every other input, but not the values it derives — the Inbox MUST compute, for each blob index i:

z_i = uint256(keccak256(abi.encode(
          bytes32("TAIKO_ETNA_CHALLENGE"), uint256(l2ChainId), statementCoreHash,
          dataCommitment, blobHashesHash, uint16(i)))) % BLS_MODULUS;

The domain tag, l2ChainId (Inbox config), statementCoreHash, dataCommitment, blobHashesHash and the blob index are all inside the transcript, so the challenge moves whenever the committed bytes move: dataCommitment commits the whole published byte string (0) and blobHashesHash commits the ordered versioned hashes. On the blob path the contract takes dataCommitment from the proof-bound input (0) and the guest recompletes it from the executed bytes in (v), so dataCommitment and z_i cannot be chosen independently of the executed payload. The modulus reduction is required because a keccak-256 output is not automatically a canonical scalar (BLS_MODULUS < 2^255), and the precompile rejects non-canonical elements. The reduction biases the distribution by at most ceil(2^256 / BLS_MODULUS) / 2^256 ≈ 1 / BLS_MODULUS ≈ 2^-254.9 in statistical distance (an earlier revision stated BLS_MODULUS / 2^256 ≈ 2^-127, which inverted the ratio and understated the bias by roughly 127 bits; the union bound is unaffected) derived, which is irrelevant to the 2^-243 bound below. The blob index i is inside the transcript so that two blobs of the same batch never share a challenge.

(iv) The guest proves the evaluation of the data it executed, in the EIP-4844 convention. The guest receives (vh_i, z_i, y_i) as public inputs and the blob bytes as part of the data it executed. It MUST interpret each 131,072-byte blob exactly as EIP-4844 does: the 4096 big-endian field elements are the evaluations of the committed polynomial in bit-reversed order over the 4096th roots of unity — element j is the evaluation at ωbrp(j), where brp is the bit-reversal permutation of the 12-bit index — which is what blob_to_kzg_commitment commits to, g1_lincomb(bit_reversal(setup_lagrange), blob). They are not coefficients of p(X). The guest MUST use this same convention (inverse bit-reversal plus Lagrange interpolation over the evaluations, or an equivalent FFT) or every honest blob proof fails; any other interpretation is invalid. It MUST reject the batch if any element is ≥ BLS_MODULUS, and MUST reject it unless p_data,i(z_i) == y_i.

(v) The guest recompletes the data commitment. The guest MUST recompute payloadRoot = keccak256(committedBytes) and dataCommitment from the full blob byte strings it executed with the (0) construction — every blob, every byte, no prefix — and MUST reject the batch unless the result equals the journal value used in (iii). This is what makes the claimed blob-path dataCommitment proof-bound.

Why this is sound (the joint event, not a fixed challenge). The chain is: (a) blobhash(i) names the blob that is in this transaction; (b) the precompile establishes kzg_to_versioned_hash(commitment_i) == vh_i, so commitment_i is the KZG commitment of that blob's polynomial p_B,i; (c) the precompile's verify_kzg_proof establishes p_B,i(z_i) = y_i; (d) the guest establishes p_D,i(z_i) = y_i over the payload D it executed, and (v) requires dataCommitment to be recomputed from that same D. Therefore (p_D,i - p_B,i)(z_i) = 0. But z_i is not fixed while D is chosen: z_i is a deterministic function of the transcript that contains dataCommitment = f(keccak(D)). The event a cheating prover needs is the joint event p_D(z(D)) = p_B(z(D)) with z(D) derived from keccak(D) — a fixed-point condition, not a linear equation in the free part of D. Stated as a search over hash outputs: for any fixed D the difference is a non-zero polynomial of degree ≤ 4095 with at most 4095 roots, so an evaluation at the pseudorandom point z(D) agrees with probability at most 4095 / |F| ≈ 2^-243 derived, and a search over q candidate payloads succeeds with probability at most q · 2^-243 (plus the 2^-254.9 reduction bias). The earlier statement of the bound "per attempt at a fixed challenge" was wrong: it assumed D was fixed before the challenge, which is exactly what (0) and (iii) prevent. D is moreover not a free variable: the executed payload is bound to the certified header chain — the certificate covers the head block id, the header chain links to the predecessor and each header's transaction root fixes its transactions (PRF-04(v), PRF-06) — so a prover cannot vary D after the certificate is signed without invalidating it. Hence, with overwhelming probability, p_D,i = p_B,i: the guest executed exactly the data the blob commits to. (review round 1, findings B R1-01, B R1-02)

Premises. This argument requires all five of: (1) KZG binding for blob commitments (A-CRYPTO-3); (2) the random-oracle model for the Fiat–Shamir derivation of z_i; (3) correct in-guest field arithmetic over the BLS12-381 scalar field, including the exact bit-reversed evaluation-form interpretation and Lagrange interpolation; (4) canonical field elements in both the blob and the guest's field elements (evaluation form); and (5) the in-guest recomputation of dataCommitment over the full blob bytes of (0)/(v). If any premise fails, the binding does not hold. This is a proof sketch with named premises, not a machine-checked theorem, and adversarial review question Q-A3 is carried against a grinding prover (04-architecture-decision.md §7).

Provenance and honesty. This construction was derived in this project (04-architecture-decision.md §4.1); it is not an established published design and has no implementation. It is an implementation gate: it may not be relied on until the fixed-point argument above has had independent cryptographic review and its in-guest cost has been measured. Its in-guest cost is UNMEASURED; measuring it requires an implementation of the in-guest evaluation on both backends with cycle counts at a stated blob size, which does not exist (04-architecture-decision.md §7, item F2). In-guest MSM and in-guest pairings are deliberately avoided, because the zkVM feasibility work found them UNVERIFIED on both backends: the guest performs field arithmetic and Lagrange evaluation only, and the pairing happens on L1 inside the precompile (PRF-11). The alternative to measure is the RISC Zero patched c-kzg library, which would put a different and larger trusted computing base inside the guest. Precompile semantics, address and gas are cited from EIP-4844; blob counts from EIP-7691.

Failure modes: (a) a submitter-chosen z, or a commitment that covers only a prefix of a blob, lets a prover pick the evaluation point after fixing part of its data, which reduces the binding to a single linear equation it can solve; (b) accepting blobhash from calldata instead of reading it lets a transaction reference blobs it did not publish; (c) performing the KZG opening in-guest would require MSM and pairings that are unverified on both backends, i.e. an unquantified soundness assumption; (d) without the canonical-field-element requirement the guest's polynomial is ambiguous, and two different byte strings map to the same polynomial; (e) without (0) and the EIP-4844 convention of (iv), an honest prover computes a different polynomial and every blob-path batch fails. Proven sourced derived unmeasured Open (measured in-guest cost; independent cryptographic review of the fixed-point argument; review question Q-A3)

payloadRoot = keccak256(abi.encode(bytes32("TAIKO_ETNA_HYBRID"), uint256(block.chainid),

DA-05 — retrievability window, archive requirement, and the blob-retention limit Blobs are not a permanent store. Ethereum guarantees blob sidecar retrievability for MIN_EPOCHS_FOR_BLOB_SIDECARS_REQUESTS = 4096 epochs sourced (EIP-4844), which is roughly 18 days at Ethereum's present slot cadence derived — the design does not depend on that wall-clock figure and expresses the window in epochs and L1 block numbers (GEN-06). Calldata is not permanent either: on the p2p layer clients stop serving historical headers, bodies and receipts older than 14,299 epochs sourced (EIP-4444, recorded in research/recovery-and-withholding-raw.md). The design therefore MUST specify, in 09: (a) a RETRIEVABILITY_WINDOW in L1 block numbers, not shorter than the blob-retention window; (b) an ARCHIVE_REQUIREMENT fixing how many independent archive nodes must retain the full accepting-transaction calldata and full blob sidecars for at least that window, with the duty owned by ROLE-03; (c) the statement that past the window, retrievability depends on those archives and not on Ethereum. DA-06 — retention duty and its link to the backlog cap There is exactly one production-side cap: the unsettled-depth cap D_MAX of HALT-03, expressed in L2 blocks and derived there as D_MAX = floor((RETENTION_WINDOW − T_PROOF_MAX_PERMITTED − T_SETTLE_PIPELINE) / L2_BLOCK_INTERVAL). Relation to the post-acceptance retention window. RETRIEVABILITY_WINDOW (DA-05) is a different object in a different unit: it is an archive duty over the accepted artifacts — the accepting transaction's calldata and blob sidecars — measured in L1 block numbers and starting at acceptance. It is not a cap and not an input to D_MAX; they measure different objects at different times and MUST NOT be combined into one inequality, so the earlier inequality that mixed them is deleted. The one obligation that remains on the post-acceptance side is stated in its own unit: RETRIEVABILITY_WINDOW MUST be at least the blob-retention window (DA-05(a)) and, converted to seconds at Ethereum's fixed slot cadence, at least W_EVIDENCE (ECON-07, registered in 09), so an accepted batch's artifacts stay retrievable at least as long as evidence about it can still be submitted. (review round 2, findings R2-LIV-07 and R2-LIV-08: one cap, one unit, one enforcement point — production — and no second window standing in for it.) Failure mode: without the cap, blocks keep being finalized whose data ages out of the retention window before any proof exists; the batch then cannot be proven by anyone, and only the sanctioned recovery of REC-02 — a settlement stall past T_STALL, a bond and a delay — may replace it, so the chain stays stuck on a range whose data no longer exists anywhere the protocol promised until that recovery completes. The cap converts an unbounded, unrecoverable failure into a halt bounded by T_STALL + T_RECOVERY_DELAY plus resume time — but it does so as a consensus rule on production, not as an L1 admission gate that would refuse a valid proof and strand finalized history. Why proposer rotation gives conditional inclusion resistance

This is a conditional statistical argument with named premises, not a guarantee, and it is the mechanism behind LIVE-04's statement. Proposer selection is hash-based weighted selection (CONS-06), and a coalition holding f < 1/3 of the stake that counts toward quorum (A-CONS-1) holds fewer than 1/3 of proposer slots in expectation over any window of s slots. Let p = f be the coalition's slot share. The probability that it leads s slots in a row is p^s, so the expected waiting time for an honest slot is 1/(1-p) ≤ 1.5 slots derived. A transaction that reaches honest validators is included by the first honest proposer with room for it (LIVE-04, FI-REMOVED-01). The coalition's residual power is to make inclusion late, not to prevent it, and lateness is bounded by the selection rule, not by a timeout judgement (STATUS-10). Three honest caveats: the argument holds only while A-CONS-1 holds — at ≥1/3 Byzantine stake it does not apply and the protocol claims nothing; it assumes proposer selection is not predictable enough for the coalition to buy the specific slots in which a transaction would be included, which is CONS-06(b)'s Assumed fairness claim; and it holds only under the network assumption A-CONS-2 — a network-level adversary able to isolate a user from every honest proposer can exclude that user indefinitely and can prevent the user from starting a withdrawal, and the protocol offers no remedy (FI-REMOVED-01). MSG-03 — withdrawal eligibility and delays No value may leave the bridge surface on the strength of anything weaker than STATUS-06. An L2→L1 withdrawal or message authentication MUST require a withdrawal root (L1-13) whose stateRoot covers the signal at a height not below the height at which the signal was stored, plus the delay WITHDRAWAL_DELAY measured from that root's l1BlockNumber, plus the absence of an unexpired withdrawal veto (MSG-04); an ordinary checkpoint that is not a withdrawal root MUST NOT anchor any value release; where the claim depends on an L1 fact that can still be reorganised, it MUST additionally require STATUS-07 — the accepting L1 transaction at the configured Ethereum finality depth. No withdrawal path MUST depend on a private witness, a committee certificate, an off-chain store, or an operator action (DA-04). Withdrawal disclosure. The design MUST disclose, wherever withdrawal timing is described and without burying it, the two user-visible costs of the soundness fix: (i) an exit is proven only against an epoch-boundary withdrawal root, which adds up to E_EPOCH plus the slowest of k proofs while at least k backend families operate, and is unbounded if they do not (L1-13(5)); and (ii) an unexpired veto (MSG-04) can add up to T_VETO to any pending withdrawal. The design MUST also disclose that a settlement halt delays withdrawals — indefinitely if no trigger fires and no recovery completes — and that the permissionless recovery of REC-02 is the sanctioned release once the stall passes T_STALL. Funds are not forfeited by a halt: the value stays in the preserved Bridge and vault contracts, and a completed recovery restores the L2 state to the latest L1-accepted checkpoint exactly. A confirmation above that checkpoint is provisional and may be replaced, so a rolled-back L2 effect must be resubmitted — it is not replayed automatically — and off-chain losses are not covered. Protocol penalties are not compensation for user losses, and no universal bound on economic loss may be stated or implied (ECON-11(2)–(3); LIM-01). MSG-04 — rule-triggered, time-limited withdrawal veto (1) What it is, and what it is not. The protocol has exactly one circuit breaker on the value-release path: a withdrawal veto that delays L2→L1 releases for a bounded window. It is rule-triggered and permissionless: no owner, DAO, operator, validator quorum or upgrade starts it, extends it, shortens it or stops it early, and there MUST NOT exist any pause/unpause-style entry point for it (MIG-04, INV-04). It is not the pause lever this design removes: it cannot be invoked at will, it cannot be extended by any party, it expires by itself, and it cancels and rewrites nothing. It is a mitigation with a bounded window and it is explicitly not a fix for an unsound backend: it cannot un-prove a forged statement, cannot remove a checkpoint already accepted (L1-06, REC-01), and cannot recall value already released. (2) Trigger: a verified contradiction, and nothing else. The trigger is exactly one objective on-chain event: a proof that the Inbox verifies itself, under a registered route, of a statement that conflicts with an accepted checkpoint's own statement — the same L2 chain id, height range, predecessor and dataCommitment, and a different postStateRoot or headBlockHash from the record. The entry point is contestProof(...), callable by any account, and the contract MUST recompute the statement hash over the submitted journal itself, verify the proof against that recomputed hash, and compare the journal's range, predecessor and dataCommitment with the checkpoint record's own values; it MUST accept no pre-computed conflict verdict and no caller-supplied comparison. A local view, a timeout, a missing proof, an allegation, a bond or a privileged account MUST NOT start it: an elapsed timeout is never evidence of absence (STATUS-10). Because execution and the state commitment are deterministic, two verified statements that conflict cannot both be true, so the trigger is evidence that at least one accepted proof system is unsound — it is not a suspicion. Each verified contradiction MUST be recorded by a hash and consumed exactly once: a repeated call with the same contradiction MUST revert, and a new window requires a new verified contradiction. The trigger does not require a distinct backend family: a single implementation contradicting itself is already evidence of unsoundness, so the veto still exists at a configuration where only one family is deployed. (3) Bounded duration, not extendable by anyone. The veto starts at the L1 timestamp of the triggering transaction and MUST end automatically at startedAt + T_VETO, with T_VETO unmeasured and registered in 09. It MUST NOT be extended, renewed or shortened by any account or upgrade, and there MUST NOT be a second veto state or a manual end. A new verified contradiction while a window is active MAY start a new window ending no later than its own trigger plus T_VETO, and the value of T_VETO in force at each start fixes that window for its whole life. The total time the release path can be delayed is therefore bounded by T_VETO per verified contradiction and is not bounded by these rules alone across contradictions — but each contradiction is evidence of a real soundness failure, and a party able to produce them has already broken the assumption the withdrawal path rests on. (4) Effect on already-proven withdrawals. A withdrawal already proven against a withdrawal root but not yet executed is delayed, never cancelled: it needs no new proof, its root and state root are untouched, and it becomes executable when the window ends and the other conditions of MSG-03 hold. Value released before the trigger cannot be recalled and no rule may imply otherwise. The veto MUST NOT gate land(data, proof) (L1-04), settlement, consensus, staking, validator exits, rewards, root attestation (L1-13) or the L1→L2 direction; it gates only L2→L1 value release and message authentication on the bridge surface. It MUST NOT be implemented with the removed pause facilities or as a condition on anything but the release path (MIG-04). (5) Disclosure. The Inbox MUST expose the veto as a public fact an interface can read — whether it is active and the timestamp at which it ends — and STATUS-11's public-facts obligation includes it. Every artifact that describes withdrawal timing MUST state plainly that a verified proof contradiction can add up to T_VETO to any pending withdrawal, that this lengthens exits and never shortens them, and that the veto delays rather than repairs: it is a bounded circuit breaker for the window in which an unsound backend's effect is being investigated, and the remedy for a genuinely unsound backend is a governance upgrade that retires its route (GOV-02, MIG-05), not this rule. No artifact may present the veto as a fix for an unsound backend. Failure modes: (a) an owner-, DAO- or operator-controlled pause returns through this door, which MIG-04 and INV-04 forbid — hence the objective trigger, the permissionless invoker and the automatic expiry; (b) a veto a griefer can start without evidence is a free denial of service on every exit — hence the on-chain-verified contradiction and its one-shot consumption; (c) a time-unbounded or extendable veto is an indefinite freeze — hence the self-expiry and the ban on extension; (d) cancelling proven withdrawals would make the veto a discretionary reversal of accepted state, which no rule permits; (e) describing the veto as a repair for an unsound backend would overstate a mechanism that cannot un-prove anything. Proven Assumed unmeasured Open (T_VETO is unmeasured; the gas of contestProof and the incentive to run it are Open — no reward is specified and the caller pays, so the veto's availability under adversarial conditions is not assumed, only its bounded effect; the argument that a conflict implies unsoundness uses the determinism of execution and the collision resistance of the state commitment)
