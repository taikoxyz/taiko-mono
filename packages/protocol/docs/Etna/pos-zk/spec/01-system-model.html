SYS-01 — participants and channels Statement. The system has exactly the participants of the first table above and the four channels C1–C4 of the second. (a) Validators, provers, full nodes and archive nodes are permissionless; users need no registration; the DAO has no runtime role (SYS-04); L1 Ethereum is data availability, proof verification, settlement and bridge anchoring, and is never the sequencer (D4, GEN-09). (b) No participant may rely on a channel for a guarantee the channel does not carry: finality exists only as the published commit certificate of STATUS-04 over C1/C2; data availability exists only through C2/C3 plus the retention assumption of A-CONS-5/A-DA-2 and the best-effort service described in DA-05 and ROLE-03 — retention is not an enforceable protocol duty, failure to serve is not provable on L1 for most classes, and a holder's failure produces a halt, not a penalty (*review round 1, finding C R1-04*); L1-derived state exists only through C4 and only when Ethereum-final (SYS-02). (c) Every validator must run its own L2 consensus and execution client and must have access to an Ethereum client it can use to establish L1 finality itself; a validator must not accept L1 finality, or L2 block availability, on the word of another L2 peer (STATUS-09). (d) Provers, full nodes, archive nodes and users must not be required to hold TAIKO or to be registered; conversely, holding TAIKO confers no protocol right other than validator participation (MEM-01). (e) Each role's required software and its channel dependencies are those of the third table; an implementation may add local caches and redundant paths but may not remove a requirement. Failure mode: a participant treats a best-effort channel (C2) or a reorganisable L1 view (C4) as if it carried finality or availability — producing the "we saw it first" and "we hold it, so it is available" errors that STATUS-01 and STATUS-09 exist to prevent. 3. L1→L2: only Ethereum-final facts may enter L2 consensused state

L2 execution and bridge message authentication consume facts that originate on L1: an L1 block hash, an L1 state root, an L1 log, or an L1 storage value. Such a fact is reorganisable until Ethereum itself finalizes it. Under Mode A a PoS-finalized L2 block may never be rolled back (D2, REC-01). If a finalized L2 block's validity or execution depended on a reorganisable L1 fact, then after a reorganisation of that fact no correct proof of the block could be constructed, L1 admission would stall forever at that batch (L1-06 accepts only extensions of its checkpoint), and Mode A would forbid the only remaining fix. The rule below removes that hazard structurally rather than hoping it does not occur.

SYS-02 — only Ethereum-final L1 facts enter L2 consensused state Statement. (a) Fact. An L1 fact is a tuple (kind, n, h_n, payload) where kind ∈ {block_hash, state_root, log, storage_value}, n is the L1 block number it was read from, h_n is that block's hash, and payload is the value plus, for state-derived kinds, a Merkle–Patricia proof against the state root of an L1 block numbered m >= n. (b) Ethereum-final. For a validator v holding, from an Ethereum consensus client that v operates itself, a finalized checkpoint whose epoch-boundary L1 block has number n*, a fact is Ethereum-final for v iff n + F_L1 <= n* and, for state-derived kinds, m + F_L1 <= n* as well. No other evidence form is admissible: depth-below-head heuristics, a peer's assertion, an RPC provider's word and an L1 block that is merely "safe" are not Ethereum-final. (c) Consumption. An L2 block may consume an L1 fact only if the block body commits to the fact's coordinates (kind, n, h_n) (and m and the state root for state facts), the committed coordinates are immutable once the block is proposed, and every validator that votes for the block has established that the fact is Ethereum-final for itself at vote time. A validator that cannot establish this must abstain, not vote; its local action is a view change (CONS-07), never a conclusion about what exists elsewhere (STATUS-10). (d) Re-verifiability. For every consumed fact the proof of 05 must bind the same coordinates, and the accepting L1 transaction must be able to re-establish them without trusting the prover (L1-05, PRF-02). If a class of L1 facts has no such path, that class must not be consumed by L2 consensused state at all. (e) Accepted cost. L1→L2 information latency is bounded below by Ethereum finality: T_L1→L2(min) = T_incl + T_eth_final + F_L1 · T_l1slot + T_obs + T_l2_rt, where T_incl is L1 inclusion (UNMEASURED), T_eth_final is Ethereum's own finality lag (a property of Ethereum, not measured here), T_l1slot is Ethereum's slot duration (not fixed by this specification, GEN-06 — a runtime input), T_obs is the time for a validator's own L1 client to observe the finalized checkpoint (UNMEASURED), and T_l2_rt is the L2 round trip to STATUS-04 (UNMEASURED). D1 does not require this latency to be 2 s. The measurement that would pin the terms: operate at least ten geographically distributed validators with pinned L1 and L2 clients for at least one week and record the distribution of inclusion, finalized-checkpoint observation and certificate publication times. (f) Bridge messages inherit the same bound: an L1-anchored message may not be consumed by L2 state before the carrying L1 transaction is Ethereum-final. (g) L2-side checkpoint writer (reserved system sender) — reconciled, not assumed away. The write path that publishes an L1 fact into L2 consensused state (today the L2 Anchor's golden-touch-gated anchorV4, migration MIG-04) remains a single reserved system sender; this rule does not claim the gate is gone. Its ONLY remaining power is to publish an L1 fact of the form (a) that this rule already constrains — an Ethereum-final L1 block hash and state root at the required coordinates, on the canonical chain, at the next height — and it may not choose which fact to publish beyond the SYS-02 rule: a payload that is not that fact, or that is not Ethereum-final for the validators consuming it, is invalid and correct validators reject the block that consumes it. Whether the retained sender is enforced as a rule-checked write (validators can reject a bad payload) or as an unchecked write (they cannot) is unresolved. Removal of the sender — a rule-checked system transaction or consensus-verified observation — is an Open migration item (MIG-04). Consequence, stated rather than assumed away: if it can choose which fact to publish, or can withhold one, it is a discretion surface in ordinary operation and R1/R2 of the requirements matrix (01 §7) are not yet satisfied; bridge authentication then rests on that sender's honesty and A-GOV-1, not on a consensus rule (*review round 1, finding B R1-09*). Failure mode: a PoS-finalized L2 block whose execution or message authentication depends on a reorganisable L1 fact becomes unprovable against canonical L1; L1 admission then stalls permanently at that batch and Mode A forbids the only fix, rolling the finalized L2 block back (REC-01). The chain halts with a finalized prefix it can never settle. Premises: A-L1-1 and A-CONS-1; the parameter values are unmeasured. Proven Assumed unmeasured Open (open for the removal of the reserved checkpoint writer of SYS-02(g), migration item MIG-04)

4. Timing: cadence is not finality, proof, settlement or withdrawal

SYS-03 — cadence is separated from every other latency Statement. The six timelines below are distinct. No rule, parameter, interface or status display may equate any two of them, and no parameter may be derived by assuming any two are equal. (a) T1 block cadence is the interval between consecutive L2 proposals under the stated operating assumptions, fixed at 2 s by D1; it is a production cadence, not a guarantee that a block at any given height exists, is final, is provable, is settled or is withdrawable. (b) T2 PoS finality latency is proposal to published commit certificate (STATUS-04); its structure is owned by 02. (c) T3 proof latency is PoS-finalized batch to STATUS-05; D6 fixes only that a few minutes to 30 minutes is normal operation, which is a design envelope, not a measurement. (d) T4 L1 acceptance is proof-ready to STATUS-06; it depends on L1 inclusion and on the admission rules of L1-04, which contain no expiry and no discretion. (e) T5 Ethereum finality is accepted on L1 to STATUS-07; it is a property of Ethereum plus F_L1 (SYS-02). (f) T6 withdrawal availability is STATUS-08; it depends on T4/T5, the message-authentication path and the delay of MSG-03, derived from the whole pipeline (ECON-03). (g) Any user-facing progress display must follow STATUS-11 and state which timeline it shows; a "2 s confirmation" display before STATUS-06 must say that the batch's data and proof are not yet on Ethereum. Failure mode: users and reviewers read "2 s blocks" as 2 s finality, settlement or withdrawal; R4 and D6 explicitly separate these, and STATUS-11 makes the conflation a disclosure violation. SYS-04 — no DAO or emergency operator in ordinary operation Statement. (a) No DAO, owner, pauser, ejecter, prover manager, verifier owner or emergency operator is required for any of: ordinary block production and finality; view change, timeout handling or leader rotation; epoch handoff and validator-set update; proof production, submission or acceptance; validator activation, key rotation or exit; or withdrawal. One exception is stated rather than hidden: the L2-side checkpoint writer retained by SYS-02(g) remains a reserved system sender in ordinary operation, its only power being to publish the SYS-02-constrained Ethereum-final L1 fact, and its removal is an Open migration item (MIG-04). (b) Every lever in the table above must be removed or made non-operative for ordinary operation by the migration (MIG-04), and no new lever of the same kind may be introduced. The retained checkpoint writer is not claimed to be non-operative: it fails the test below, so it is recorded as a residual privilege rather than as a removed lever. A lever is "non-operative" if no participant's required action depends on it and no failure of ordinary progress can be repaired by it. (c) The privileged actors the design retains are the DAO, for upgrades only (GOV-01), and the reserved checkpoint writer of SYS-02(g). That retention is a trust assumption (A-GOV-1), not a safety guarantee; an upgrade must accept every previously finalized history (GOV-03, PRF-10). (d) When ordinary progress is impossible the correct behaviour is a safe halt (HALT-01); there is no operator path to restart, rescue or roll back (HALT-04, REC-01). Failure mode: a lever left live can void queued work (the init3 class), censor proposing or proving, write or block the L2 checkpoint, or change which proofs count; each makes a role's permissionlessness and Mode A's no-rollback promise untrue in practice, and each is exactly the "the DAO/emergency key would fix it" non-argument the requirements forbid. Assumed in the retained DAO upgrade authority (A-GOV-1) and in the reserved checkpoint writer's compliance with SYS-02(g) (Open migration item MIG-04). Proven Assumed Open

6. Role catalogue

Each role rule below states entry, duties and resources, rewards and funding source, objective penalties, exit, behaviour when the role fails, permissionlessness, and barriers or concentration risks. Parameter values named here live in 09; economics in 07.

ROLE-01 — validator role Statement. (a) Entry and activation. Permissionless and objective: self-bond TAIKO at the existing L1 token address (MEM-01), bind an operator key (MEM-07), and join the first-come activation queue (MEM-03). There is no whitelist, no admission vote and no per-address cap; voting power is effective stake (MEM-02) and the set for each epoch is a deterministic function of L1-committed state (CONS-13, MEM-09). (b) Duties. When selected, propose a valid block within the round budget (CONS-06); validate every block it votes for against parent state; cast at most one vote per (height, round) and obey the lock rule and its unlocking condition (CONS-02, CONS-04); hold and serve the block data it voted for for at least the retention window — a liveness assumption (A-CONS-5, A-DA-2, DA-05), not an enforceable protocol duty: failure to serve is not provable on L1 for most classes and produces a halt, not a penalty (*review round 1, finding C R1-04*). No inclusion duty attaches to a validator: a proposer includes what the objective rules admit, and omitting a particular transaction is neither a proposal-validity failure nor an offence — inclusion resistance is the conditional statistical property of LIVE-04, and the offence catalogue of ECON-04 contains no censorship offence. (c) Required resources — each item is UNMEASURED for this design and the measurement that would pin it is named: sustained bandwidth for C1 gossip plus C2 fetches at the observed block size and cadence; CPU able to execute a worst-case block inside the cadence budget; storage for L2 state plus the retention window; L1 RPC access through an Ethereum client the validator operates itself, able to produce the finalized-checkpoint evidence of SYS-02(b) — a third-party endpoint may serve advisory reads but must not be the sole source of finality evidence; TAIKO effective stake at or above the minimum of ECON-09. (d) Rewards. Denominated and paid in ETH from the segregated validator reward pool held by the L1 staking contract (ECON-02(1), (5)(a)) — never from the Inbox's prover-reward ledger (L1-11). Payment is conditioned on attested participation: the authenticated signer bitmap of the head certificate, recorded by land for every epoch the batch's heights cover (ECON-02(5)(b)). Claims are permissionless — any address may claim for the entry's recorded owner (ECON-02(5)(c)) — and open only after evidenceClose(e), when the epoch's allocation and its frozen participant set are fixed (ECON-02(5)(c)–(d), ECON-07); a claim before then reverts. An entry that did not sign is paid nothing; no reward may depend on TAIKO appreciation. This closes review round 3 finding R3-CE-02: ROLE-01(d) no longer pays validator rewards in the batch-acceptance transaction, and it states the participation-conditioned, post-window, permissionless claim of ECON-02(5). (e) Penalties. Only for objectively verifiable offences, with the encodings, windows and recipients of ECON-04, ECON-05 and ECON-07: equivocation (CONS-11) and the other listed offences. A lock-rule violation is penalised only in the form in which it is objectively provable — a conflicting signed pair at the same (height, round), which is also the only lock-related offence with admissible evidence — because proving the absence of an unlocking proof-of-lock-change is not an admissible evidence object (ECON-04, CONS-11). A cross-round or cross-epoch divergence under a withholding adversary may leave no such pair and therefore no admissible evidence: the claim that a safety-relevant divergence always implies at least one third objectively slashable is Assumed, not established, and the fork-accountability argument is not a deterrent guarantee (CONS-09(4)(a); the limitation is recorded in the consensus rows of LIM-01). Local suspicion, mere non-receipt of a message, or elapsed time is never evidence (WH-02, STATUS-10). This closes review round 1 finding CS-07 for this role rule: the penalised lock offence is the same-(height, round) conflicting pair, and everything else is local suspicion. (f) Exit. An objective unbonding queue (MEM-05) whose delay is derived from the whole settlement pipeline (ECON-03); exit never invalidates past votes, and stake is slashable for offences committed while in the set (MEM-06). (g) Failure behaviour. An offline or Byzantine validator is bypassed by view change and leader rotation (CONS-07) and, where objective evidence exists, slashed. Safety of STATUS-04 holds only under A-CONS-1; degraded liveness is the only consequence of A-CONS-2 failing. (h) Permissionlessness and barriers. Entry is objective, but the real barriers are the capital cost of TAIKO (including the market-access assumption A-ECO-2), hardware and operational cost, the unbonding lockup, and stake concentration: no per-address cap prevents concentration (MEM-10), and no claim is made that one does. Failure mode: an implementer invents an admission gate, a discretionary slashing trigger or a reward source, or a validator is described as guaranteeing something outside A-CONS-1/A-CONS-2. ROLE-02 — prover role Statement. (a) Entry. Permissionless: any account may submit any valid (data, proof) pair for any unsettled range, with no whitelist, registration, bond gate or expiring range (L1-04, L1-10). The only entry resources are the ability to produce a valid proof and to pay L1 gas in ETH. (b) Duties. None is imposed on a named prover; the protocol's liveness requires at least one honest, adequately-resourced prover per committed batch within the assumed envelope (A-DA-2). A prover that publishes a proof must bind exactly the public inputs of PRF-02 — including the SYS-02 coordinates of every consumed L1 fact — and must land data and proof in one L1 transaction (D5, L1-01). (c) Resources (each UNMEASURED): an L2 node able to reconstruct the execution witness from public data (A-DA-4); proving hardware with the throughput given by batch gas × cycles per gas; bandwidth and storage to fetch bodies, state and witnesses; ability to submit L1 transactions. (d) Rewards. Paid for the accepted batch from the same L1 transaction (L1-11, ECON-02); payment is objective (acceptance) and discretionary to no one. A proof of a different data commitment earns nothing (STATUS-05). (e) Penalties. None beyond the cost of the failed L1 transaction: a rejected proof leaves no partial effect (L1-03) and consumes only gas. The design does not claim that this deters a well-funded denial-of-proving attacker (T-9); the response is permissionless replacement and, if no prover appears, the consensus-enforced backlog cap (HALT-03). (f) Exit. A prover has no registered role and may stop at any time without affecting safety or finality; no unbonding applies. (g) Failure behaviour. If proving stops, settlement stalls while L2 keeps producing until the backlog cap binds; the honest responses are waiting and replacement by another prover for the same data commitment — never a data-first path (D5) and never invalidation of finalized history (REC-01). (h) Barriers and concentration. Proving hardware and witness-reconstruction cost create economies of scale; the premise limiting centralisation is A-DA-4 (anyone can rebuild the witness from public data). No cap or anti-concentration rule exists, and a prover cartel can delay settlement but cannot change finalized history. Failure mode: proving is turned back into a permissioned or bonded role (the baseline's ProverWhitelist), or a prover is blamed or slashed for something that is not objectively provable. Assumed on A-DA-2 and A-DA-4; resources unmeasured. Assumed unmeasured
ROLE-03 — full node and archive node role Statement. (a) Entry. Permissionless, no registration, no stake, no consensus role. (b) Duties and assumptions. A full node executes and validates the chain it follows and, while it runs, serves block bodies, state and execution witnesses on C2 for at least the retention window; an archive node additionally retains history beyond the blob retention period so that old batches remain re-provable and auditable (DA-05, DA-06). A full node may refuse service — that is not misconduct — but a validator's own retention obligation under ROLE-01(b) is not discharged by another node's possession of the data (STATUS-09). Retention is a liveness assumption (A-CONS-5, A-DA-2), not an enforceable protocol duty: failure to serve is not provable on L1 for most classes, and a holder's failure produces a halt, not a penalty (*review round 1, finding C R1-04*). (c) Resources (UNMEASURED): storage for state plus the retention window, and the full history for an archive node; bandwidth to serve peers; CPU for execution and witness reconstruction. (d) Rewards. The protocol defines no payment for full or archive service; operators bear the cost, and that is a disclosed sustainability and concentration risk (ECON-12, LIM-01). Any future payment must have an objective funding identity (ECON-02). (e) Penalties. None: there is no stake and no consensus role, so there is nothing objective to slash. (f) Exit. Free at any time; if enough nodes exit, availability fails and the chain halts safely (HALT-01) instead of rewriting history. (g) Failure behaviour. A node that holds data but will not serve it, or that has lost it, is a withholding case (WH-01): detection is local, the honest participant reduces what it claims to be retrievable, and the chain does not pretend the data is available. (h) Barriers. Storage and bandwidth cost with no protocol revenue; and a full node is not a validator and must not be described as one. Failure mode: availability is inferred from one node's possession, or the absence of a data-serving reward silently turns A-CONS-5 into an unstated assumption with no cost accounting. Assumed on A-CONS-5, A-DA-2 and A-DA-4; resources unmeasured. Assumed unmeasured
ROLE-04 — user rights: inclusion, exit, disclosure Statement. (a) Entry. None: any account may submit L2 transactions and use the preserved bridge and signal surface (D3, MSG-01) without registration and without holding TAIKO. (b) Rights and duties. (i) Inclusion — a user may submit a transaction and rely only on the statistical proposer rotation of CONS-06 under A-CONS-2: proposer selection is hash-based and weighted, so a transaction that reaches honest validators is included by the first honest proposer with room for it. There is no forced-inclusion path and no protocol remedy against a network-level adversary: such an adversary can exclude a user's transactions indefinitely and, because a withdrawal is initiated by an L2 transaction, can also prevent the user from starting a withdrawal. This is the disclosed limitation of LIVE-04 and LIM-01, and no rule may present the rotation as a per-transaction guarantee. (user decision D-6: forced inclusion removed; a user-authorized partial relaxation of R10) (ii) Exit — a bridge withdrawal becomes withdrawal-eligible only through the message-authentication path and the delay of MSG-03, derived from the full settlement pipeline (ECON-03); no operator can accelerate, block or reverse it outside those rules. (iii) Disclosure — any interface that shows progress must use the STATUS-01–STATUS-11 labels and state which status it shows; a display before STATUS-06 must state that the batch's data and proof are not yet on Ethereum. (c) Resources. L2 gas in ETH; an L1 account and ETH for bridge transactions; a client able to follow the chain's status. (d) Rewards. The protocol pays users nothing; users are not a protocol payee. (e) Penalties. None beyond L2 gas and L1 transaction fees; a user is never slashed for a protocol offence. (f) Exit and failure. If the L2 halts, funds are not lost but exit is delayed; a halt is safe and is never resolved by invalidating finalized history (Mode A, REC-01); L1-accepted messages remain valid (L1-06). (g) Permissionlessness and barriers. No KYC and no allowlist; the real barriers are the L1 gas cost of bridge exits, the need to hold ETH, and dependence on A-L1-1 for L1 inclusion liveness plus A-CONS-2 for the statistical inclusion property. Failure mode: rotation under A-CONS-2 is presented as a per-transaction inclusion guarantee or as an L1 remedy the protocol does not provide, or a UI or downstream assumption presents a pre-settlement block as settled, which STATUS-11 exists to prevent. Assumed on A-L1-1 for L1 inclusion liveness and on A-CONS-2 for the statistical inclusion property of LIVE-04; outside those assumptions the protocol offers no inclusion remedy. Proven Assumed
ROLE-05 — DAO role: upgrades only Statement. (a) Entry and authority. The existing L1 governance, holding the upgrade authority of the preserved proxies (MIG-02); it is the only privileged actor the design retains. (b) Scope. Upgrades only (GOV-01): implementation, program-image and parameter upgrades that (i) accept every previously finalized history as valid (GOV-03, PRF-10), (ii) preserve the D3 addresses and storage layouts (MIG-02, MIG-06), and (iii) introduce no privileged path in ordinary operation (SYS-04). The DAO must not be required for block production, finality, proof submission or acceptance, activation, exit or withdrawal, and has no rescue function (HALT-04). (c) Resources. None operational. (d) Rewards. None from this design; the destination of slashed stake is a separate human decision (ECON-06). (e) Penalties. None: governance capture is a trust assumption and a separate failure class, not an offence (GOV-02). (f) Exit. Not applicable; users do not exit governance, they exit funds by withdrawal. (g) Failure behaviour. A malicious or captured DAO is a class-F2 failure: after an upgrade that changes the rules, the safety claims of this specification do not apply. The honest response is detection and disclosure (LIM-01, LIM-03), not prevention, and the trust assumption A-GOV-1 is stated at every claim that depends on it. (h) Concentration. Governance power follows token holdings; this design neither fixes nor claims to fix that, and the non-claim of MEM-10 applies. Failure mode: the DAO is quietly used as an emergency operator, contradicting the selected Mode A (D2) and R2, and reviving the "the DAO would fix it" non-argument the requirements forbid. Assumed on A-GOV-1; the assumption is disclosed, not discharged. Assumed

7. Assumptions and fault boundary

Every claim on this page that concerns safety or liveness is conditional on the named assumption. An assumption is not a guarantee: it states what happens if it fails. The full set is in 01-requirements-and-threat-model.md §4–§5 and the assurance page 10.

The three failure classes of 01 §5 map onto this page as follows: F1 (liveness-assumption failure, safety intact) is the halt, backpressure and replacement behaviour of HALT-01– HALT-03; F2 (safety-assumption failure: ≥1/3 Byzantine stake, key compromise, zkVM soundness break, malicious governance) removes the safety claims of STATUS-04 and of SYS-02; F3 (implementation bug) is out of scope, but no rule on this page may make F3 undetectable.

What this model does NOT claim.

  • No whitelist-free performance guarantee. Permissionless entry and objective admission are structural properties (R1); they are not a promise of 2 s cadence, proving throughput, settlement time or withdrawal latency. Those values are unmeasured and registered in PARAM-03.
  • No liveness outside the assumptions. Outside A-CONS-2, A-CONS-5 or A-DA-2 the honest outcome is a safe halt that may last arbitrarily long; the model does not promise recovery, and D2 forbids buying recovery by rolling back finalized history (LIVE-01).
  • No claim that ZK repairs failed consensus assumptions. A proof attests that a certificate is internally consistent with a validator set and a quorum rule; it cannot attest that no other certificate exists. If A-CONS-1 fails, two conflicting certificates can both verify.
  • No claim that concentration is prevented. No per-address cap exists for validators or provers (MEM-10), and no claim is made that governance concentration is prevented.
  • No claim that the D3 addresses remain compatible by themselves. Preservation is conditional on exact storage-layout discipline (MIG-02).
