03 — Membership, TAIKO staking, exits, weak subjectivity

This page owns the MEM-* rules: how existing TAIKO becomes consensus stake held on L1, how that stake becomes voting power in an epoch-scoped validator set, how validators enter and leave, how a consensus key is bound and retired, and what a node may and may not trust when it syncs. Status labels are STATUS-01–STATUS-11; timing is expressed in seconds or L1 block numbers with no L1 proposer lookahead (GEN-06); every protocol hash is one canonical abi.encode with a right-padded domain tag and the chain id first (GEN-05). Nothing on this page is implemented, deployed, benchmarked or audited (GEN-01).

What this page does not decide. Rewards, the offence catalogue, penalty sizes and the destination of slashed stake are ECON-01–ECON-12; the epoch schedule, certificate format and header fields are CONS-05, CONS-10 and CONS-13; the atomic land(data, proof) path and checkpoint record are L1-01–L1-08 (the name is fixed by L1-01, and clients, parameters and migration scripts MUST use it); signature, bitmap and quorum checks in the guest are PRF-04 and epoch transitions are PRF-05. Membership fixes only the ledger, the set and the trust boundary.
Fixed decisions applied here. Staking and slashable collateral are the existing TAIKO token and nothing else; gas stays ETH (D7). SignalService, Bridge and the three vaults keep their existing addresses by in-place upgrade (D3); the staking custody contract is a new contract at a new address, which D3 does not forbid. No rule on this page can invalidate a PoS-finalized block in Mode A (D2, REC-01) — the L1 heartbeat eligibility of MEM-13 is revived by increment 02 as a selection filter on future set versions — it never reduces weight, and an ineligible entry is never decayed, discounted or slashed — while the L1-time rotation of CONS-16 remains deferred by decision D-16, is not normative in v1, and MUST NOT be implemented because its closing height has no L1 referent —, no rule creates a data-first admission path (D5 as relaxed by D-11: a batch's data may be published before its proof, but only a valid proof bound to that data lets a checkpoint advance), and no rule depends on an L1 proposer or a fixed L1 slot duration (GEN-06). Every safety claim below is conditional on the Byzantine-stake assumption A-CONS-1 (< 1/3 of the stake that counts toward quorum in the relevant set version) and, where it needs data to be served, on A-CONS-5/A-DA-2 (01-requirements-and-threat-model.md §4). Where a rule needs an assumption, it says so at the rule. This closes review round 8 finding R8-EBA F5: the fixed-decision note now states D5 in its D-11-relaxed form (data may be published before the proof; only a validated checkpoint advances) rather than the superseded one-transaction form.

1. Custody: one asset, one ledger

MEM-01 — L1 staking custody of TAIKO at the existing token address The staked asset is the existing L1 ERC-20 TAIKO at 0x10dea67478c5F8C5E2D90e5E9B26dBe60c54d800 (token.taiko.eth). The address is verified in taiko-baseline-contracts.md §6.1, which records TaikoToken (TKO) at that proxy from LibL1Addrs.sol:73 and TaikoToken.sol:12-13; the token has 18 decimals and a fixed supply of 1,000,000,000 ether minted once in init (TaikoToken.sol:41, sourced). No new token is created. No wrapped, bridged or L2-represented TAIKO counts as consensus stake — in particular the L2 BridgedTaikoToken has no role in consensus — and neither ETH nor any other asset is accepted as consensus collateral. Gas remains ETH (D7). Custody is a new L1 contract at a new address. New addresses are permitted: D3 preserves only the SignalService, Bridge and vault addresses by in-place upgrade, and this contract is not one of them. Bonded amounts are stored as uint256 TAIKO base units (18 decimals), never as a rounded integer multiple of gwei. The consensus ledger is not the Inbox's existing bond ledger: Bond{uint64 balance; uint48 withdrawalRequestedAt} is gwei-denominated with a ceiling of 2^64 − 1 gwei ≈ 1.845e10 TAIKO and a granularity of ≈ 18.4 TAIKO (derived, economics-raw.md §1.4, LibBonds.sol:18, IBondManager.sol:13-19), and its only slash path is a best-effort, offence-agnostic liveness debit (LibBonds.sol:148-170; economics-raw.md §1.4 point 2). Disposition of that ledger is a migration concern (MIG-03). The custody contract holds only staked TAIKO. It never lends, pledges, rehypothecates or stakes the principal elsewhere; it exposes no arbitrary-call, no owner-triggered transfer and no upgrade-triggered transfer of bonded balances, and no party other than the objective rules of this page and of ECON-01 / ECON-05 can move a bonded balance. Ownership of the contract, if any, is limited to an upgrade authority that cannot move balances (SYS-04). The token contract itself is neither replaced nor upgraded by this design; a DAO upgrade that changes the token's transfer semantics is a governance failure class (GOV-02), not a staking rule. Failure mode: a second token or a wrapped representation makes the security budget a function of a different market and breaks D7; reusing the gwei bond ledger puts rounding and a best-effort debit into the consensus path, where one base unit changes voting power and a failed debit silently converts a slash into no punishment; a transferable bonded balance reintroduces the withdrawal race that MEM-06 exists to defeat. Proven sourced gas of the deposit / exit / withdraw paths: unmeasured — measured by a gas-report run of the pinned custody contract under L1 mainnet-equivalent conditions.
MEM-02 — Effective stake, voting power, and why getVotes is not an oracle (1) For set version k (MEM-08) the ledger exposes, as a pure function of Ethereum-final L1 state at the snapshot point defined in MEM-09: effStake_k(v) = LedgerState(N(k)).active[v] — the entry's plain bonded weight — where active[v] is the sum of TAIKO base units that entry v has bonded and that (i) completed activation (MEM-03), (ii) has not had an exit become effective (MEM-05) and (iii) has not been slashed away (MEM-06). An entry with effStake_k(v) = 0 is not in the set. Every active and eligible entry is in the root: the ledger value is filtered only by the L1 heartbeat predicate of MEM-13 — an entry with effStake_k(v) > 0 that is not eligible is not selected into that version's root and is absent from it — and nothing scales, discounts or zeroes the ledger value: exclusion is a selection filter, never a reduction of stake. (increment 02: MEM-13 is revived; the roster is the active entries that are eligible at the version's fixed evaluation instant, and no rule removes weight. F1 repair: the instant is the heartbeat window containing the L1-side epoch start at which the version became coverable, not the commit's own instant; F1 realisation: that window is computed on the L1 block-height grid from the activation record's schedule, so no past block is read and nothing is written per epoch.) (2) Voting power is exactly the effective stake: VP_k(v) = effStake_k(v) — one TAIKO base unit is one unit of weight. There is no multiplier, no age bonus, no quadratic, time-weighted or reputation term, and no discount for common ownership; the former inactivity-decay carve-out is withdrawn, so nothing scales, discounts or truncates effective stake. No liveness rule reduces a validator's weight: the heartbeat eligibility of MEM-13 excludes an ineligible entry from future set versions only (clause (1)), and the only paths by which a validator's weight changes are its owner's own exit (MEM-05) and a slashing for an offence (MEM-06). The published set carries TotalVP_k = Σ_v effStake_k(v) over the entries the version commits — the active and eligible roster; the quorum predicate applied to TotalVP_k is CONS-03's and is not restated here. Duplicate public keys within one set version are invalid (MEM-08); weight is counted per (pubkey, effStake) entry, and the protocol neither records nor infers beneficial ownership (MEM-10). (user decisions D-14 and D-16; increment 02: the decay multiplier was withdrawn, and the eligibility layer that replaced it is revived as a selection filter on future set versions — no rule removes weight and exclusion is not a penalty.) (3) balanceOf, getVotes and getPastVotes must never be read by a consensus rule. On the existing token, votes and balance demonstrably diverge: renounceVotingPower() is irreversible and zeroes a holder's votes while the balance and total supply are unchanged (TaikoToken.sol:53-74, :92-96; economics-raw.md §1.1 line 53); four accounts are hard-coded vote-excluded — address(0), TAIKO_FOUNDATION_TREASURY 0x363e846B91AF677Fb82f709b6c35BD1AaFc6B3Da, TAIKO_DAO_CONTROLLER 0xfC3C4ca95a8C4e5a587373f1718CD91301d6b2D3 and TAIKO_ERC20_VAULT 0x996282cA11E5DEb6B5D122CC3B9A1FcAAD4415Ab (TaikoToken.sol:17-21, :130-136; economics-raw.md §1.1 line 41); vote checkpoints are timestamp-based (clock() = block.timestamp, TaikoTokenBase.sol:22-30); and delegate() is blocked when a non-voting account is either party (TaikoToken.sol:83-90). Reusing that surface would let a governance action delete consensus weight, and would count accounts that never bonded and are not slashable, breaking INV-03 ("no consensus without TAIKO at risk"), which is itself conditional on A-CONS-1. Failure mode: the protocol counts weight that is not at risk and cannot be confiscated, so a certificate can be produced by parties who lose nothing when they equivocate; or a renunciation immediately zeroes a live validator's weight and the epoch loses quorum for reasons no staking participant chose. 2. Activation and the validator lifecycle

MEM-03 — Activation: objective, permissionless, first-come queue (1) Entry is permissionless. Any L1 account may create an entry by bonding at least S_min TAIKO and registering a consensus key (MEM-07) and an ECDSA heartbeat key (MEM-13(1)), both bound to the same entry; the heartbeat key MUST be non-zero, and a bond naming address(0) MUST be rejected and create no entry (R-INCR2-02). The bonding address is the entry identifier: an L1 account may have at most one live entry — activating, active, exit-requested or unbonding — at a time, so a bond from an account with a live entry MUST revert, and the signed payload of MEM-13(2), which binds that address as v, therefore names exactly one entry. A withdrawn entry is not live; re-entry from the same account (§2.1) is a new entry with unset heartbeat records, a new key and a new FIFO position. (R-INCR2-03: one live entry per bonding address makes the payload's identifier unique without changing the signed preimage, the domain tag or any other rule's use of v.) The heartbeat key is not a consensus key: it cannot vote, cannot move, request or cancel an exit, cannot rotate the consensus key, and never appears in a set root; its only power is the liveness attestation of MEM-13. (increment 02: bonding registers the heartbeat key alongside the consensus key; the key is owner-set and owner-rotated, forward-only.) There is no allowlist, no invitation, no operator approval, no identity requirement and no discretionary cap on the number of participants (R1); the only admission bound is the objective consensus-performance limit n_k ≤ N_MAX of MEM-14, which delays admission and never denies it and leaves the FIFO order of clause (2) unchanged. (PR #22262 review comment 6011464863, item 2(b): admission gains one objective bound and keeps R1's permissionlessness up to it.) The gate is the objective predicate amount ≥ S_min; the derivation of S_min is ECON-09 and its value is a parameter subject to PARAM-01. No third-party on-ramp exists in v1: the bonded amount is credited to msg.sender, because separating the economic owner from the slashed party without a delegation contract is exactly what MEM-04 rules out. (2) Ordering key and per-epoch activation rate limit. Activation entries are ordered by the strictly increasing tuple (l1BlockNumber, txIndex, logIndex) of the L1 block that included the bonding transaction, where logIndex is the index of the entry's event in that block's log list. Ties cannot occur. Serving is FIFO by this key — first-come, first-served at the protocol level — and, once an entry's coordinates are fixed, no fee, stake size, key attribute, entity or reputation can reorder it or make the protocol serve a later entry first. At most ACTIVATION_RATE_LIMIT entries may become active per epoch, taken from the head of the queue in key order; the limit never selects among entries and never cancels one. Two honest disclosures, because the ordering key is L1 inclusion order and L1 block builders and proposers can be influenced by priority fees: (a) FIFO is not a proof of fairness under adversarial L1 ordering — an adversary can pay to place its own bonding transactions earlier, and no in-protocol rule can prevent that; the protection this rule gives is that entry is delayed, never denied: the protocol never cancels an entry, never removes it from the queue except by its owner's cancelActivation() or its own failure to bind a key, never lets another entry pass it in the queue, and never refuses its eventual activation for any reason other than the per-epoch rate limit; (b) ACTIVATION_RATE_LIMIT bounds how fast the set grows, so a saturated queue lengthens every waiting entry's time-to-activation without changing any entry's position (the EIP-7514 activation-churn cap is the sourced precedent; economics-raw.md §2.5). (*review round 1, finding D ECO-09*) (3) Activation delay. ACTIVATION_DELAY is expressed in seconds and must satisfy ACTIVATION_DELAY ≥ T_L1_final(p_f) + 2 · E_EPOCH + M_act, where T_L1_final(p_f) is the p_f-quantile time for the bonding transaction's L1 block to become Ethereum-final, 2 · E_EPOCH is the two-epoch set-commitment lookahead of MEM-09 clause (1) (a root is appended during e and governs e+2), and M_act is a margin; the numerical values are UNMEASURED (see the register at the end of this page). An entry becomes active at the first set version k whose snapshot point N(k) satisfies timestamp(N(k)) ≥ timestamp(bondingBlock) + ACTIVATION_DELAY, subject to the FIFO head order and ACTIVATION_RATE_LIMIT of clause (2); it is first governed by the epoch two ahead of version k's commit, never by an epoch already being voted on. Activation makes an entry selectable; selection additionally requires eligibility. An entry that has completed activation enters the first set version whose snapshot point finds it active and eligible under MEM-13(3): the roster is the active entries whose heartbeat predicate holds at that version's fixed evaluation instant, subject to the FIFO order, the per-epoch rate limit and N_MAX. An active entry that has not attested is excluded from that version's root only — it is not lapsed, no stake is touched, and re-attesting restores eligibility as MEM-13(4) states, including for an append that is still pending. (increment 02: the liveness predicate of MEM-13 is revived; exclusion is a selection filter, not a lapse.) (review round 2, finding R2A-01) (4) An entry that never activates. If the key is never bound, or the operator never comes online, or the entry is never reached in the FIFO head, then: the stake stays in activating; it never appears in any set root; it is never part of TotalVP_k; it is never slashable for a consensus offence, because it never signs a vote; and it accrues no reward. An entry whose key binding is incomplete is skipped for throughput accounting and keeps its position, so one unfinished entry cannot block the queue behind it. Cancellation is owner-only (cancelActivation()); no third party can cancel an entry or consume another entry's position, and the only ways an entry is ever passed or delayed are the L1 ordering of clause (2) and the per-epoch rate limit (griefing defence, threat model T-13). An entry that activates but never signs a vote is not lapsed and cannot be lapsed, and no stake is touched: it is not selected into the set versions whose evaluation window MEM-13(3) fixes later than the window it last named by more than one — exclusion is a selection filter, not a lapse — while its stake, its position and its rights are untouched and re-attesting restores eligibility as MEM-13(4) states, including for an append that is still pending. The only ways its weight is reduced or removed remain its owner's exit (MEM-05) and a slashing for an offence (MEM-06). (increment 02: a non-participating cohort is excluded from future rosters and keeps its committed weight; production halts only when a committed roster cannot gather quorum.) Failure mode: if the ordering key were a fee or a stake size, entry becomes an auction and R1's permissionlessness is nominal; if ACTIVATION_DELAY were zero, an entry included in the same L1 block as a snapshot could change the set of an epoch already being voted on, breaking the agreement precondition A-CONS-4; if a stalled entry could block the head of the queue, a griefer could freeze all activation for the price of one bond. Proven unmeasured (T_L1_final(p_f), E_EPOCH, M_act, ACTIVATION_RATE_LIMIT — measured by the inclusion/finality distribution study and the consensus parameter table.)

MEM-14 — maximum validator-set size (objective admission bound) (1) The bound. Every published set version MUST satisfy n_k ≤ N_MAX (MEM-08(1)), where N_MAX is a registered parameter (09): an integer number of validator entries per set version, N_MAX ≥ 1. n_k counts the entries the version actually commits — active and eligible under MEM-13(3) — so the bound is checked against that filtered roster. (increment 02: n_k counts eligible entries; the admission bound and its consequences below are unchanged.) The bound exists because consensus cost grows with the set: each height costs O(n²) vote broadcasts (each of the n validators sends two votes to the other n−1; consensus-survey-raw.md §3.3, survey OQ-15), each round must complete inside the 2 s cadence (CONS-07, falsifier F3), and each batch costs n in-guest Ed25519 verifications over distinct messages (PRF-04). Without a bound, any payer can grow the set until rounds stop completing — a liveness attack that needs no Byzantine stake at all. N_MAX is therefore a consensus-performance parameter, not a decentralisation mechanism, and no rule, interface or document may present it as one (MEM-10(4), ECON-10(1)). (2) Admission is objective and permissionless up to the bound. The admission predicate of MEM-03 is amount ≥ S_min and the set version the entry would first enter has fewer than N_MAX entries. Nothing else gates admission: no allowlist, no operator approval, no fee, no stake size beyond S_min, no identity, and the one-live-entry-per-bonding-address condition of MEM-03(1) is an identifier-uniqueness condition, not a gate on who may participate — every account may bond, once at a time. (R-INCR2-03: the condition is restated here so the admission predicate is complete.) The bound is applied where a set version is formed — to the ledger state read at the snapshot point N(k) inside commitSet() (MEM-09(1)) — and it MUST NOT be applied by evicting an entry from an already committed set root: a published root is immutable (MEM-09(4), CONS-08) and no rule may remove an entry from a set it is already committed to. An entry that cannot enter because the bound is reached keeps its FIFO position and is delayed, never denied: it is served when a slot frees through an exit (MEM-05) or a forced exit (lifecycle transition 7), in the objective order of MEM-03(2), and meanwhile it stays bonded, is never in a set root, is never slashable for a consensus offence because it never signs, and can be cancelled by its owner (cancelActivation()). Heartbeat eligibility does not free a slot: an entry excluded by MEM-13(3) is absent from a version's roster but keeps its entry, its bond and its FIFO position, so a slot frees only through an exit (MEM-05) or a forced exit (lifecycle transition 7). (increment 02: exclusion is a selection filter, not a lapse, and it never frees admission capacity.) Three limits act together and are distinct: ACTIVATION_RATE_LIMIT bounds the rate of activation per epoch (MEM-03(2)); N_MAX bounds the stock of entries in a set version; the churn cap bounds the rate of exit (ECON-03(6)). (3) Sizing, and it is unmeasured. N_MAX MUST be fixed at or below the largest n at which S2 — the round-timing measurement at 50 / 100 / 200 validators (05-phase-b-plan.md §1, S2) — shows one round completing inside the 2 s cadence with the declared delay bound, and at or below the largest n whose S1-measured in-guest Ed25519 verification cost keeps a batch's proof inside T_PROOF_MAX_PERMITTED (MEM-05, 09). Neither measurement exists, so N_MAX is unmeasured; it is not a free choice and MUST NOT be published above the smaller of the two measured limits. (4) The honest consequences, which are not to be papered over. (a) The bound caps the honest set size, exactly as ECON-10(1) warns of a slot cap, and makes slots a scarce resource: a secondary market in entries or consensus keys is possible, and the protocol neither prevents it nor recognises it (MEM-10(1)). (b) Filling every slot is not free and is fully at risk: it costs N_MAX · S_min bonded TAIKO, every base unit of it slashable for the epochs in which it is committed (MEM-06), so the bound turns "grow the set until consensus stops" from an unbounded griefing surface into a bounded and slashable one. This is a bound on the attack's price, not a claim that capture is prevented, and no document may make that claim. (c) The bound does not bound concentration: it constrains the number of entries, not stake, so one entry may hold an arbitrarily large share (MEM-10(1), (3)). (d) The bound supersedes the sentence in ECON-09(3) that the resulting count n = S_total / S_min "is not bounded by any consensus rule"; that sentence and its "no normative set-size window" reading must be reconciled by the owner of page 07, so that Budget_ETH(n) (ECON-12) is an input over a bounded range. This answers PR #22262 review comment 6011464863, item 2(b): the set can no longer be grown until consensus stops completing rounds, and the bound is stated with the O(n²) message load, the in-guest signatures per batch and the two measurements that fix it. Failure mode: an unbounded permissionless set lets any payer add validators until the 2 s cadence fails — a liveness attack with no Byzantine stake — while a bound presented without its cost model is sold as decentralisation; conversely a bound enforced by eviction or by refusing exits would rewrite a committed set, which MEM-09(4) and CONS-08 forbid. unmeasured Open (N_MAX's value awaits S1 and S2; the rule itself is normative. The reconciliation of ECON-09(3) is owed by page 07, not by this page.)

3. Delegation

MEM-04 — No delegation in v1 (recorded decision, alternative documented) v1 has exactly one economic owner per entry: the L1 address that bonded the stake is the only address that may request exit, cancel an exit, rotate the consensus key, or receive unbonded proceeds (MEM-03, MEM-05, MEM-07). No contract, pool, custodian or third party may hold stake on behalf of another party and appear in a set root, and no rule recognises delegated, re-delegated, pooled or liquid-staked TAIKO as consensus stake. The protocol does not attempt to prevent such markets from existing; it declines to count them (MEM-10, ECON-10). This is the decision recorded in 04-architecture-decision.md §3 ("v1 supports no delegation: self-bonded operator keys only") and in DECISIONS.md; the alternative below is documented, not silently deferred. The reasons are structural, not paternalistic. (a) Slash pass-through. If slashing does not reduce delegator shares pro rata, delegators hold a free option on operator misbehaviour and the operator's own stake can be smaller than the harm caused. (b) Slashable exit and redelegation. The unbonding period only works if unbonding delegations and redelegations remain slashable for offences committed while the tokens were bonded to the source validator; Cosmos makes all three slashable, which is why its staking module is one of the largest and most intricate modules in the SDK (economics-raw.md §2.6, sourced). (c) Evidence attribution. Equivocation evidence is objective and attributable to a key, but allocating the loss across many beneficial owners requires a share accounting surface with unbonding entries and redelegations, which does not exist in v1 and cannot be improvised after an incident. (d) Polkadot's 2026 staking reform moves to self-stake-only slashing, direct evidence that the delegator/operator alignment problem is hard to solve even with the most sophisticated stake-allocation algorithm in production (economics-raw.md §2.6, sourced). If delegation is ever required — for example because the entry floor would exclude small holders — the minimum honest design is fixed now so that a future proposal cannot quietly ship less: (i) operator self-stake at least equal to its own bond floor, slashable first; (ii) explicit, documented pass-through of slashing to delegators, including unbonding delegations and redelegations; (iii) a recorded decision that the pass-through's simplicity limits are accepted, with the accepted loss distribution stated. Failure mode: shipping delegation without all three of pass-through, slashable unbonding and slashable redelegation sells an unpriced option to delegators and converts the protocol's safety claim into a claim about a contract that does not exist; or an "operator" with little of its own stake is bribed to equivocate while delegators keep the upside. MEM-05 — Exit request and unbonding delay derivation (1) Exit request. The owner calls requestExit(); the entry enters exit-requested and remains in every set it is already committed to, keeps voting, and remains fully slashable until the exit takes effect. This is a deliberate change from the existing bond ledger, where hasSufficientBond is false the moment a withdrawal is requested (LibBonds.sol:130-141; economics-raw.md §1.4 point 1): an exiting validator that stopped validating would silently shrink the set, and the exit delay would buy no protection at all. Heartbeat eligibility (MEM-13) is an independent filter on future versions: it does not change exit effectiveness, the churn cap's order, the entry's exposure for every epoch in which it was committed, or any withdrawal condition; an exit-requested entry that stops heartbeating is simply absent from future rosters while remaining fully slashable for committed epochs. (increment 02: the eligibility filter never gates, delays or accelerates an exit.) (2) Exit becomes effective at the first set version whose snapshot point is at or after the exit request transaction's L1 block and which the churn limit of ECON-03(6) does not exclude; from that version the entry's effStake = 0 and it appears in no later set root (MEM-09). The owner may withdraw only when all three hold: (a) the exit has been effective for at least D_WITHDRAW; (b) the evidence window W_EVIDENCE has closed for every epoch the entry was in; and (c) no unsettled or collectible slashing exposure remains (MEM-06). (4) Delay formula. D_WITHDRAW ≥ T_PROOF_MAX_PERMITTED + T_detect + T_evidence_submit + T_L1_include(p) + T_L1_final + T_PROCESS + M. Every term is unmeasured; the table below states what measures each one. T_L1_include(p) must be a quantile, never a mean, and may not assume a fixed L1 slot duration (GEN-06). (5) Why not nominal proving latency. The one-transaction form of D5 is relaxed by D-11: a batch's data may be published first and its proof may reference that publication, so a data-first window does exist (DA-09, DA-10) — but it is a proving window bounded by T_PROVE_DEADLINE, not an objection window: a publication advances no protocol state, acceptance still needs a valid proof bound to that data (L1-02), and no rule lets a third party object to published data or delay acceptance by watching it. Detection therefore cannot rely on "the data sat on L1 for N hours before the proof arrived"; the delay must cover evidence that is generated only after settlement, or generated concurrently on L2 and then carried to L1. That makes T_L1_include(p) and T_L1_final load-bearing rather than rounding errors, and it makes 30 minutes of proving latency a lower bound on nothing: the evidence clock starts at the offence, which happens at L2 consensus time, possibly long before the batch is provable (economics-raw.md §2.5, lines 340-354). If a correlated penalty is adopted, D_WITHDRAW must additionally exceed that penalty's application delay; the two must be chosen together or neither works (economics-raw.md §3.2 point 2; the penalty itself is ECON-05). MEM-06 — Slashing follows stake at offence time (1) For every epoch e in which entry v appears in a set root, the ledger records SlashBase(v, e) := effStake_{setVersion(e)}(v) and retains the pair (e, SlashBase(v, e)) in L1 state until the later of (i) the end of the evidence window for e and (ii) settlement of any slash for e. An offence committed at epoch e is charged against SlashBase(v, e), never against the balance at the time the evidence is submitted. (2) Exposure accounting. Let max_exposure(v) = max{ SlashBase(v, e) : e open } over epochs whose evidence window has not closed and whose slashes are not settled. At any moment the owner may withdraw at most bonded(v) − max_exposure(v); equivalently, the contract retains at least the largest single-epoch exposure until every such epoch closes. Slashing is bounded by the bonded balance: the protocol has no claim on assets outside the custody contract, and an unpaid penalty is not collectible from the operator elsewhere (this limitation is stated for users under ECON-11). (3) The withdrawal-race defence, precisely. An offender's rational sequence is: equivocate at epoch e; request exit; wait D_WITHDRAW; withdraw; be slashed on a remainder. It is defeated only because three rules hold together: (i) SlashBase(v, e) is fixed at epoch e and is the charge base; (ii) withdrawal is capped by the exposure of every open epoch, so the stake that could be charged cannot leave first; and (iii) D_WITHDRAW is strictly longer than the time needed to detect, submit, include, finalise and process evidence (MEM-05 clause 4). If any one of the three fails, the race succeeds — they are jointly necessary, and none of them is a parameter that may be relaxed alone. (4) A slash for a given offence is applied at most once: the identity of an offence is (v, epoch, offence type, evidence digest), and a second submission of the same identity is a no-op. Duplicate, replay and false-accusation handling is ECON-08; the per-(v, e) charge base is this rule's. Failure mode: slashing the current balance lets an offender withdraw first and be slashed on what is left — a real, documented failure mode that both Ethereum (state.slashings[epoch] plus the withdrawable_epoch clamp) and Cosmos ("we want to 'follow the stake'", x/evidence) specifically engineered against (economics-raw.md §2.4, sourced). A short delay plus a best-effort debit makes the penalty decorative. Proven sourced (the safety effect of the penalty is conditional on A-ECO-1 and on A-CONS-1, exactly as ECON-01 states; this rule fixes attribution, not deterrence.)

5. Keys: binding, rotation, stale keys

MEM-07 — Key binding, rotation, and stale-key handling (1) One key per entry per set version. An entry has at most one consensus key at any set version: an Ed25519 public key in its canonical 32-byte compressed encoding (RFC 8032). Write pk(v, k) for the key of entry v at set version k; it is a field of the entry in the set root (MEM-08). A second key for the same entry at the same version is invalid, not an error to be resolved by preference. This clause governs the consensus key; the heartbeat key is separate. The ECDSA heartbeat key of MEM-13 is set or rotated by the entry's owner alone and forward-only: it MUST be non-zero, and a bond or rotation naming address(0) is rejected, a rejected rotation leaving the stored key and the records untouched; a heartbeat signed under a retired key is invalid whenever it was produced, retirement is permanent and a retired key MUST NOT be re-bound to any entry; a heartbeat key MUST NOT be bound to two entries, rotating it never resets lastHeartbeatAt(v), lastHeartbeatWindow(v) or lastHeartbeatSeq(v) (a rotation is not a freshness reset), and it never appears in a set root or in a (pubkey, effStake) leaf (MEM-08). (increment 02: the heartbeat key's binding, rotation and retirement are stated at MEM-13(1); the consensus key surface is unchanged. R-INCR2-02: the non-zero condition is restated here; R-INCR2-04: retirement is permanent and re-binding a retired key is invalid.) (2) Binding. A key enters a set root only through an L1 transaction signed by the entry's owner address, which sets the key for that entry; the transaction itself is the authentication, so no separate signature object is required. If an aggregate or threshold vote-signature scheme is ever adopted, the binding must additionally carry a proof of possession for the new key, because only then does a rogue-key attack exist (A-CRYPTO-2); with the individual Ed25519 scheme selected in 04-architecture-decision.md §2, a registered key whose secret the owner does not hold simply cannot vote, and that entry's own stake bears the consequence. (3) Rotation is forward-only and version-scoped. The owner calls rotateKey(newPk). For every set version k already published, pk(v, k) is unchanged and unchangeable. The new key applies from the first version k whose snapshot point is at or after the rotation transaction, i.e. pk(v, k) = newPk for N(k) ≥ rotationBlock and pk(v, k) = oldPk for all earlier k. The old key is retired at that moment. (4) Stale keys cannot vote. A vote for epoch e carries the signer's key (or is matched by the guest to the key of the leaf at the signer's bitmap index). It is valid if and only if the signing key equals pk(v, setVersion(e)) for the entry whose effStake is committed in R_{setVersion(e)}. A vote signed with a rotated-away key at an epoch that commits the new key is invalid: it must be discarded, must not count toward quorum (CONS-03), and its signer is not slashable for it because it is not a vote under the protocol's rules. Symmetrically, a vote signed with the old key at an epoch that commits the old key remains valid forever, no matter how many rotations happened later (CONS-08). (5) A later key must not rewrite past behaviour. No rule may validate a tallied vote against the validator's current key, and no rotation, exit or withdrawal may invalidate, reattribute or expunge a vote, vote conflict or evidence object from an epoch that committed the earlier key. Equivocation evidence under a retired key stays slashable against SlashBase(v, e) for the epochs in which that key was committed, exactly like any other evidence (MEM-06). (6) Keys are one-shot identities. A key that has ever appeared in a published set root is retired permanently: binding it again to any entry, including the same entry, is invalid. This keeps the mapping (key, epoch) → entry injective, so attribution of evidence never depends on how a key was later reused. A key may never be bound to two entries at the same time. (7) Compromise and loss. A compromised consensus key can equivocate and burn the entry's stake, but it can never move the stake: only the owner address can exit, withdraw or rotate (MEM-01, MEM-05). Rotation stops future damage but is not retroactive. A lost key is replaced by the same rotateKey path, effective only from the next set version, so votes signed under the lost key in committed epochs stand as signed. If the owner address itself is lost, the bonded stake is stranded: no rule of this specification can move it, and no DAO or emergency path exists to rescue it (SYS-04, HALT-04). Failure mode: checking signatures against the current key instead of the epoch's committed key lets a rotation launder a past equivocation (the evidence no longer matches the "current" set) and rejects valid historical votes; allowing key reuse lets a pre-signed message be attributed to a different entry's stake. Proven Assumed (the un-forgeability of Ed25519 is A-CRYPTO-2; the rule is Proven given it.)

6. The validator set as an L1-committed object

MEM-08 — Validator-set commitment construction (1) A published set is the tuple (chainId, k, R_k, TotalVP_k, n_k, entries): the chain id, the set version k, the root R_k, the total effective stake, the entry count, and the full ordered entry list [(pubkey_i, effStake_i)]. The list is published so that any party can reconstruct the tree cheaply; the root is the authoritative commitment. (2) Canonical order. Entries are sorted ascending by keccak256(abi.encode(DOMAIN_SET_KEY, chainId, pubkey)). Public keys are unique within a version (MEM-02), so the order is total and ties cannot occur. Sorting makes the root independent of insertion order, snapshot iteration order and tree-building implementation. index is the 0-based position in this order; the signer bitmap used by PRF-04 indexes this same order, so bitmap bit i denotes entry i. (3) Leaves and interior nodes are domain-separated (GEN-05): leaf and interior tags differ, and the empty-set tag differs from both, so no node can be reinterpreted at a different position or as a different object. Odd nodes are promoted unchanged to the next level; a node is never duplicated to fill a level, which removes the duplicate-last-node ambiguity. The full encoding is in the table below. (4) What the root commits to — exactly. R_k commits to the chain id, the set version k, and the ordered list of (pubkey, effStake) pairs — and nothing else. In particular it does not commit to the epoch mapping (which version governs which epoch is L1 Inbox state, MEM-09), to the validators' owner addresses, to bond age, tenure, reputation, region or any score, or to rotation history. Adding a field that affects voting power requires a new set version and a rule change; it may not be smuggled into an existing root. Eligibility (MEM-13) is not a leaf field and is not committed: an entry excluded by the eligibility predicate is simply absent from R_k and from TotalVP_k, exactly as an inactive entry is, and the exclusion is not recorded in the root. (increment 02: eligibility filters the roster; the root's shape and fields are unchanged.) (5) Total. TotalVP_k = Σ_i effStake_i is published in the same L1 transaction as the root and is recomputed by the guest from the leaves; a mismatch, or a leaf with effStake = 0, invalidates the set. A sum is not derivable from a Merkle root, so the published total is a checked field, not a convenience. (6) Authority. The root is written into L1 state by the registry contract (commitSet()) and read from L1 state by the Inbox; it is never supplied by the prover. The proof's public input "validator-set commitment" is therefore an L1 fact (L1-05), the Inbox re-derives it when verifying, and a prover cannot choose it (PRF-03). Membership in the guest is then: recompute the leaf from (pubkey, effStake), verify its Merkle path to R_k, and require that the key which verified the vote signature is the leaf's pubkey (PRF-04). 7. Sybil resistance and concentration

MEM-10 — Sybil resistance and the non-claim about per-address caps (1) There is no per-address, per-operator or per-validator cap on stake in v1 (the one-live-entry-per-bonding-address condition of MEM-03(1) is an identifier rule, not a stake cap: a single entry may still hold any amount; R-INCR2-03), and the admission bound of MEM-14 is a bound on the number of entries in a set version — a consensus-performance limit — not a cap on stake: one entry may hold any amount, so N_MAX does not bound concentration and MUST NOT be described as doing so. (PR #22262 review comment 6011464863, item 2(b): an entry-count bound is not a stake cap.) There is a floor S_min per entry, derived from cost recovery and permissionless entry (ECON-09), and the accounting rule that weight is counted per (pubkey, effStake) entry (MEM-02). One beneficial owner may hold many entries; the protocol does not require, verify, represent or attempt to detect beneficial ownership, and it makes no claim that splitting or merging identities is prevented. (2) What the design actually relies on. The cost of acquiring the float: AttackCost(t) = b · S_total · P(t) · (1 + σ(t)) + OC(t) + E[Slash] with b = 1/3 under A-CONS-1, P(t) the TAIKO price and σ(t) the slippage and illiquidity premium for acquiring b · S_total within the attack window — both UNMEASURED and time-varying (economics-raw.md §2.8). Splitting stake across identities does not change that term. (3) The cost-overhead argument, stated exactly. Let C be a per-address cap, S_total the total bonded stake, k = S_total / C the number of addresses needed to hold everything, and k_op the marginal cost of operating one additional validator identity (key generation and custody, monitoring, per-validator overhead, and any amortised flat bond). An adversary seeking a fraction b of stake acquires b · S_total tokens and spreads them over b · k addresses; the capital cost of the attack is unchanged, and the cap adds only b · k · k_op. The ratio (cap overhead)/(attack cost) is k_op / C: it shrinks as the cap rises and never cancels the dominant term (economics-raw.md §2.7 points 1-2). In the fuller form the acquisition term also carries P(t) · (1 + σ(t)), so the overhead is k_op / (C · P(t) · (1 + σ(t))) in the same units — the conclusion is unchanged: the cap constrains labels, not capital. (4) A cap never bounds concentration, and the only way to make it bind is to make entry expensive. k is unbounded above because addresses and keys are free to create; k_op is bounded above by the honest cost of entry, which R1 forbids making prohibitive. If the protocol caps validator slots instead, slot acquisition becomes the binding constraint and a wealthy adversary outbids honest operators for existing slots rather than acquiring tokens (a secondary market in slots). This design does cap validator slots: N_MAX of MEM-14, and this paragraph is its honest description, not a disclaimer. The bound is a consensus-performance parameter sized from S1 and S2; it caps the honest set size, makes slots scarce, and does not bound concentration (it constrains entries, not stake); every consequence in this paragraph and in ECON-10(1) applies to it and is repeated at MEM-14(4). What the design refuses is only the claim that the bound is decentralisation (PR #22262 review comment 6011464863, item 2(b): the slot cap is owned here rather than left implicit); Cosmos' MaxValidators is a consensus-performance parameter, not a decentralisation mechanism, and Polkadot's 2026 self-stake minimum is a floor on operator commitment, not a cap on stake (economics-raw.md §2.7 point 3, sourced). (5) What actually constrains concentration is (a) the total cost of acquiring the float — a liquidity and slippage question, not an address question; (b) rewards that are concave in stake, so the marginal token is worth less to a large holder; and (c) transparency. The protocol can deliver (c) and does: the full entry list of every set version is public (MEM-08), so concentration is observable even when it cannot be prevented (economics-raw.md §2.7 point 5). (6) Any claim that a cap "prevents monopolisation" must be deleted or restated as the cost-overhead statement of clause (3), with k_op marked unmeasured. "Per-address caps prevent monopolization" is an explicit non-argument of this project (01-requirements-and-threat-model.md §6.4). Failure mode: a cap is presented as decentralisation, so reviewers and users believe concentration is bounded when the only effect is an additive, sub-linear overhead; or the cap makes entry costly and excludes honest small participants while a wealthy adversary splits anyway. Proven unmeasured (k_op, P(t), σ(t) and the resulting AttackCost are unmeasured; they are measured from a reference-validator cost study and from order-book depth and traded volume, respectively.)

8. Weak subjectivity and long-range attacks

MEM-11 — Weak subjectivity: the L1 checkpoint as the source, and the freshness window (1) The weak-subjectivity checkpoint is the L1 checkpoint. A node bootstraps from the checkpoint record most recently accepted by the L1 Inbox and Ethereum-final (L1-07, SYS-02): an L2 height, block hash, state root, epoch and set version. The source is the latest L1-accepted checkpoint, regardless of how long a halt has lasted: a long halt does not make genesis, a peer's tip, a social checkpoint or an older record an admissible substitute, and it does not extend the freshness window of clause (2). The node reads it from L1 state; no social input, no peer vote and no checkpoint provider role is introduced. The reason is that this checkpoint is Ethereum-committed and publicly auditable, and it is exactly what L1 will accept as a predecessor — a node needs an L1 view anyway to verify settlement (mode-a-feasibility-analysis.md §C5). (2) Freshness window. A node must not bootstrap from a checkpoint older than WS_MAX, where WS_MAX ≤ D_WITHDRAW − (T_detect + T_evidence_submit + T_L1_include(p) + T_L1_final + T_PROCESS) − M_ws. The derivation: an offence committed at the checkpoint's epoch remains slashable only until the offender's stake can be released, which is at least D_WITHDRAW after its exit (MEM-05, MEM-06); if the anchor is older than that minus the time it takes to land evidence, then a checkpoint's signers may already be beyond reach and the anchor no longer carries the slashing guarantee it is trusted for. Substituting MEM-05 clause 4 gives the derived upper bound WS_MAX ≤ T_PROOF_MAX_PERMITTED + M − M_ws. Every term is UNMEASURED; M_ws is the long-range margin. The consequence of exceeding the window is fixed here and is not softened by the length of the halt: if the latest L1-accepted checkpoint is older than WS_MAX, a fresh node MUST NOT call the history it would sync verified — it is, at best, an unverifiable claim (STATUS-11) — and new entry is blocked until a newer checkpoint exists: a fresh validator cannot be admitted and a fresh node must not bootstrap from the stale anchor. Recovery then requires a new L1-accepted checkpoint, which requires a batch to land and be accepted under the settlement rules; no rule admits a stale checkpoint to restore entry. (*review round 1, finding D ECO-08*) (3) It is an upper bound, not a target. WS_MAX is the largest age at which a checkpoint can still be defended by slashing; a smaller value is always safer, and the published value must be justified by measurement, not chosen for convenience (PARAM-03). (4) Disclosure. The freshness window, the current checkpoint's age, and the fact that a checkpoint was used to bootstrap must be visible to users of a node, in the vocabulary of STATUS-11. State synced from an anchor is never presented as verified beyond the anchor. (5) The assumption, stated at the claim. This rule rests on A-CONS-6 (new joiners can obtain a checkpoint no older than the published window) and on A-L1-1 (Ethereum liveness and safety). It is a trust requirement, not a cryptographic guarantee: if L1 cannot accept a checkpoint for longer than WS_MAX — an L2 halt, a proving outage, a blob-retention failure — then no fresh checkpoint exists, a new node cannot safely sync, and new entry is blocked until a newer checkpoint exists; the node must not present the stale history as verified. The chain's liveness failure becomes a sync failure and an entry failure, and that consequence is disclosed rather than hidden. Failure mode: a node that treats an arbitrarily old anchor as authoritative accepts a history whose signers can no longer be punished — the long-range attack of MEM-12 — while believing it holds a protocol guarantee. Proven Assumed derived unmeasured (the inequality is derived from MEM-05; its inputs are unmeasured, and the conditional is A-CONS-6 + A-L1-1.)
MEM-12 — Long-range attack handling; no silent trusted checkpoint provider (1) The attack, in this design. An attacker who held at least 1/3 of the stake at some past epoch e and has since exited retains the Ed25519 secrets committed in R_{setVersion(e)} and can produce an alternative L2 history branching at or before e whose signatures are cryptographically indistinguishable from honest ones. A defensive quorum of the old set can be reconstructed from the attacker's own keys, so no signature check can detect the fork, and the attacker cannot be punished once its stake has been released (consensus-survey-raw.md §7.4; recovery-and-withholding-raw.md §10 item 10, which records that "weak subjectivity is objective/trustless" is a misconception). (2) Two defences, both required. (a) Checkpoint anchoring: a node must never adopt an L2 history that conflicts with its L1 checkpoint; the L1 checkpoint is a fork-choice revert limit, not merely a hint. (b) Freshness (MEM-11): a checkpoint older than WS_MAX is not usable, and the honest statement is that a very old checkpoint must not be used. Supporting membership-side defences: certificates are judged only under their own epoch's set (CONS-08); setVersion(e) is immutable once the epoch starts (MEM-09); keys are retired on rotation so (key, epoch) → entry stays injective (MEM-07); and the unbonding delay keeps the stake that signed a history slashable long enough for evidence (MEM-05, MEM-06). (3) Validating from genesis is not a substitute. The L1 staking ledger is objective, but the epoch chain is not objective by itself: a long-range attacker can produce valid signatures from a historical TAIKO-staked set, so two internally valid histories exist and only L1 says which one the protocol accepts (consensus-survey-raw.md §7.4 point 2). A node that cannot obtain a fresh L1 checkpoint cannot resolve this by re-executing more history. (4) What a node must do when it cannot obtain a fresh checkpoint. If L1 is unreachable, or no Ethereum-final checkpoint is younger than WS_MAX, the node must: (i) refuse to treat any L2 history as protocol-verified; (ii) not report or relay a status above STATUS-03 for such a history, and not present it as settlement-backed; (iii) not silently substitute a checkpoint obtained from a peer, an RPC endpoint, or any third-party service; and (iv) surface the condition to its operator, naming the checkpoint's age and the required bound. It may retry, and it may halt and wait (HALT-01). It must not "succeed" by trusting an unverified history. (5) No checkpoint provider role. This specification creates no registry, contract, address, role or reward for checkpoint distribution, and no node may treat one as authoritative. A node operator may configure an out-of-band anchor locally; that is a node-local trust decision outside the protocol, and it must then be labelled visibly as an operator-supplied anchor and must not be relayed to others as protocol-verified. Restart-from-checkpoint rules are HALT-02's; this rule fixes the membership-side refusal to fabricate trust. Failure mode: a node silently follows a fabricated history and reports it as verified, so users act on a chain the protocol never accepted; or an unstated third-party checkpoint provider becomes a privileged role, contradicting SYS-04 and silently re-introducing the operator R1/R2 forbid. Proven Assumed Open (the cryptographic indistinguishability of past-key signatures is Proven given A-CRYPTO-2; the freshness value is Open and unmeasured; the conditional is A-CONS-6.)

Limitations stated on this page, not hidden. (i) Every safety claim here is conditional on A-CONS-1 and, where a slash must actually be collected, on A-ECO-1 at the prevailing price. (ii) Slashing is bounded by the bonded balance; the protocol has no claim on other assets. (iii) The unbonding delay and the freshness window are upper-bound constructions whose inputs are unmeasured; a shorter delay is not available without weakening the withdrawal-race defence. (iv) Admission is bounded by N_MAX (MEM-14), a consensus-performance limit whose value is unmeasured and which caps the honest set size and makes slots scarce; it constrains entries, not stake, so it does not bound concentration, and a per-address cap does not either; the one-live-entry-per-bonding-address condition of MEM-03(1) is an identifier rule and likewise bounds neither stake nor concentration (R-INCR2-03). (v) Weak subjectivity is a trust requirement: a node that cannot obtain a fresh L1 checkpoint must stop, and there is no third-party provider to rescue it. (vi) Losing the owner address strands the stake permanently. (vii) Heartbeat eligibility is live (MEM-13, increment 02): an entry is selected into a set version only if its ECDSA heartbeat key attested on L1 in that version's fixed evaluation window or the window immediately before it — the L1-block-height window containing the first L1 block of the L1-side epoch in which the version's append became coverable, derived from the activation record (MEM-13(3); F1 realisation); the commit's own timestamp no longer selects the roster, and after a parameter change the instant semantics of MEM-13(6) govern; an ineligible entry is excluded from that future version's root, total and count and is never decayed, discounted or slashed — no rule removes weight, and exclusion is not an offence or an exit. An operational lapse is an outage — the entry loses its slots in the versions whose fixed evaluation window follows the window it last named by more than one — and re-attesting restores eligibility as MEM-13(4) states, even for an append that is still pending. Two falsifiers are carried Open: F8 (an adversary able to censor, delay past the window or price out honest entries' L1 heartbeats excludes honest validators from future versions and can raise its own share of them) and F9 (the pre-signing horizon is bounded, not closed: a signature made within HEARTBEAT_ANCHOR_AGE blocks before the window it names is accepted in it, and the same term makes an all-ineligible append window reachable). The reachability half that would clear a stall inside an epoch whose committed roster cannot form quorum, CONS-16, remains deferred by D-16 and tombstoned: its closing height h_close(e) is an L2 fact no L1 rule pins, so a completer would supply it as an unverifiable claim (F7), and a quorum-loss halt inside an already committed epoch still ends only when that cohort returns to vote or through a later protocol update. A cohort that keeps heartbeating keeps its weight: a declaration of presence is not proof of participation. (increment 02: the heartbeat layer is revived; the rotation remains deferred, and DEFERRED.md §2 records the deferred rotation and its revive criterion.) (viii) The residual is that v1 has no liveness repair of any kind inside an epoch already committed: MEM-13 filters future rosters, but nothing draws a reachable set around a stalled cohort, and with the governance stall resolution also deferred (D-16) there is no recovery path — a settlement or production stall halts the chain, and clearing it requires a future protocol update whose procedure is not yet specified. Funds are safe and the exit of MEM-15 works. (user decision D-16: the guarantee is disclosed as absent rather than supplied by an unreviewed mechanism.) (ix) The L1-time rotation of CONS-16 remains deferred by D-16 and MUST NOT be implemented even though MEM-13 is now live: v1 has no early epoch close and no re-partition, and the rotation's gate is sharper than its former precondition — its closing height h_close(e) is the highest height any validator produced, an L2 fact L1 cannot supply, so a completer would pin it only by an unverifiable claim (F7 in DEFERRED.md §2). (increment 02: the delta that revives MEM-13 also sharpens this gate; the rotation is not revived and its parameters stay withdrawn.) (x) The exit guarantee of MEM-15 reaches only signals already at or below the latest L1-accepted checkpoint: value above it, and value never messaged, still cannot leave while production is halted. That residual is unbounded and is disclosed in LIVE-05 and LIM-01.
