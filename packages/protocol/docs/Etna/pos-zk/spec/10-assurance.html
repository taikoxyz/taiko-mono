10 — Invariants, conditional liveness, limitations and rejected alternatives

Safety invariants

INV-01 — unique certified prefix, relative to the authenticated checkpoint Under the stated premises, at most one block per height per generation receives a valid commit certificate, and a certificate of a superseded recovery generation is void at the acceptance rule; within one generation every such block is an ancestor of every later such block, so the uniqueness of the finalized prefix holds for the certificates produced under the consensus rules (CONS-02, CONS-03, CONS-04). The unconditional "at most one block per height ever" form is deleted because a completed stall resolution deliberately produces two valid, forever-valid certificates at the same height, one of them under a superseded recovery generation (CONS-08, GOV-04(f)). A completed rotation of CONS-16 is the second, narrower event of the same class: it re-partitions only heights that no validator produced, it never re-judges a produced height, and each height is judged only under the epoch the L1-committed boundary record assigns it; because a valid certificate entails that its height was produced and finalized (CONS-05), no certificate can exist for a re-partitioned height, so CONS-08(3) is not weakened by the re-partition itself; if the precondition is violated the offending certificate is void for canonical purposes and remains admissible as evidence (CONS-12, CONS-16(4); the precondition that no produced height is re-judged is Open, falsifier F7). (PR #22262 review comment 6011464863, item 2(a): the rotation is the second, narrower event of the generation class.) (S5 §6: INV-01 is restated generation-scoped exactly as CONS-12 now is; the unconditional claim is deleted.) Relative to the authenticated checkpoint (L1-07): history at or below the latest L1-accepted checkpoint can never be changed by the stall resolution or any other protocol path, and at or below an Ethereum-finalized checkpoint even an L1 reorganisation cannot change it (STATUS-07); above the latest L1-accepted checkpoint the certified history is canonical except that it may be replaced in whole by a completed stall resolution — the action of GOV-04 — and by nothing else, with that rule's exact objective trigger (a settlement stall past T_STALL_GOV), its timelock T_GOV_RESUME, its resume-only effect and its void-on-progress rule. The exact replacement and the resumed checkpoint are owned by REC-01 and GOV-04: the latest L1-accepted checkpoint is left exactly as it is and everything above it is discarded wholesale — the action has no choice about which transactions inside that range survive, so a stall resolution cannot be used to pick winners. That is a statement about the discard, not a promise about the outcome: the discarded transactions are not replayed automatically and their inclusion is not guaranteed, so every party whose transaction was discarded must resubmit it, and the design does not promise that the same set of transactions will end up included. No timeout, rotation, admission rule, ordinary upgrade, operator action or failure of a liveness assumption may replace history; only a completed GOV-04 action may, and only above the latest L1-accepted checkpoint. This closes finding R2: the selective-rollback outcome claim is replaced by the enforceable wholesale-discard property and the resubmission consequence. Replacement is never justified by execution validity alone: the proof statement binds the configuration under which the batch was certified and carries the recovery generation (PRF-02), so an alternative history cannot be accepted merely because its execution is valid. A certificate produced under a superseded generation is void for canonical purposes above the resumed checkpoint but remains admissible as evidence (GOV-04(f)). Premises: (P1) fewer than one third of the voting power of every epoch is Byzantine (A-CONS-1); (P2) correct validators obey the vote-uniqueness rule (CONS-02) and the lock rule (CONS-04); (P3) the commit rule requires more than two thirds of the epoch's voting power, counted over distinct authenticated signers (CONS-03); (P4) each epoch's set is the L1-committed set (CONS-10, MEM-08); (P5) the per-height lock of CONS-04 is enforced, and cross-height continuity is exactly the parent-validity condition of CONS-01(iii) — no lock state crosses an epoch boundary, because the lock is per height (*review round 2, finding R2A-10*) (CONS-09). Failure mode: reading the certificate as the guarantee. The certificate is the same evidence in every mode, so a reader — or an interface — can conclude that a confirmation above the checkpoint is permanent; it is not, because the stall resolution may discard that history, and clearing a stall depends on governance liveness. The other half matters equally: no premise failure and no other mechanism licenses a rollback, and if any premise fails, two conflicting certificates can both be cryptographically valid while a ZK proof cannot detect it. Both proofs verify. The protocol's response to that class remains disclosure, detection through objective evidence where it exists, and slashing — never a claim that the invariant holds. Proven Assumed (argument from the CometBFT Proof of Safety and the fork-accountability lemma, pinned in 02; P5 is review target F1) (D-15: uniqueness holds for the certificates produced under the consensus rules and within one recovery generation; above the last L1-accepted checkpoint the canonical history may be replaced only by the timelocked, resume-only stall resolution of GOV-04, which depends on governance liveness — the assumption A-GOV-2, recorded in LIM-01)
INV-02 — no batch is accepted without its data There is no state in which an accepted, checkpoint-advancing L1 record exists without (a) the batch data being retrievable from the transaction the accepted statement binds — the accepting transaction when the data is carried, the live publication record when it is referenced (DA-01, DA-08) — and (b) a valid proof binding execution to exactly that data. This holds structurally: acceptance happens in one transaction whose proof the Inbox verifies, and the data commitment is bound by DA-02 or DA-03. A publication advances no checkpoint and is not a batch record, so the data-first admission path remains excluded (L1-02). No outage, degraded mode, governance action or operator procedure may create an exception: the stall resolution of GOV-04 discards unsettled history but accepts no batch and manufactures no checkpoint, so it cannot admit a batch without data (REC-01 e, L1-02). (D-15: the stall resolution is not an exception to this invariant; it accepts nothing and advances no checkpoint.) Failure mode: a data-first admission design creates exactly the class observed in this repository — init3() (Inbox.sol:246-258) had to void queued requests whose blob references expired before they could be derived. That class is controlled here by DA-09's proving deadline: a pending batch exists only as a publication record bounded by that deadline, never as an advanceable checkpoint. Proven (D5 as relaxed by D-11: data may be published before the proof, and acceptance still happens only with a valid proof that binds it; the in-repo incident is evidence that the alternative is not hypothetical)
INV-03 — no consensus without TAIKO at risk Voting power exists only for stake that is bonded in the L1 staking contract and active in the epoch's set; a key with no eligible stake cannot vote, and a vote is counted only if the signer's stake is in the authenticated set. Slashing follows the stake held at the time of the offence (MEM-06), so exiting after an offence does not escape the penalty. Failure modes addressed: voting power acquired without at-risk capital, and the withdrawal race in which an offender unbonds between the offence and the evidence. Proven
INV-04 — no privilege or discretion in ordinary operation Every step of ordinary operation — activation, proposing, voting, proving, evidence submission, reward claiming and exit — is reachable by any address satisfying the objective rules, with no allowlist, no owner approval, no DAO vote and no operator key. A privileged lever is permitted only for upgrades, and each such lever is enumerated with its scope in MIG-04. Failure mode: a protocol that claims permissionless operation while a ProverWhitelist or an owner-only init3() can alter who may participate or what queued work survives. Proven Open (open for the operational audit of the completed migration: the rule is normative, but whether every lever has been removed is verified only at migration time)

Conditional liveness

LIVE-01 — the liveness statement and exactly where it ends The following is the complete liveness claim, and it is conditional on every clause. If (L1) more than two thirds of each epoch's voting power is online and message delay between correct validators is below the round-timeout bound for long enough to complete a round; (L2) a correct proposer is eventually selected by rotation when timeouts elapse; (L3) correct validators hold and can serve the data of the blocks they voted for, at least until settlement or the retention window ends; (L4) for every committed batch, at least one adequately-resourced prover completes its proof inside the envelope, or another prover does — this is a per-batch statement, not a mean-rate one: a sustained average that meets the throughput inequality of LIVE-03 does not imply that no individual batch exceeds the envelope (*review round 1, finding R1-09*); (L5) Ethereum includes valid transactions within a bounded delay and does not reorganise below the finality depth; (L6) the L1 staking contract commits each epoch's set root before the epoch begins; (L7) a new node can obtain a weak-subjectivity checkpoint within the freshness window; then L2 produces a block every 2 seconds, blocks reach STATUS-04 within the round budget, and committed batches reach STATUS-06 within the proof-queue envelope. A settlement stall is not cleared by the protocol's own liveness: after T_STALL_GOV governance may queue the stall-resolution action of GOV-04, which after the timelock T_GOV_RESUME discards everything above the last L1-accepted checkpoint and resumes from it; until that action executes the chain is halted, and because the trigger fixes only when an entry may be queued, clearing a stall depends on governance liveness with no protocol bound — the assumption A-GOV-2, recorded in LIM-01. Independent of every clause above, and therefore not conditional on (L1), (L2), (L4) or (L6): every L2→L1 message included at or below the latest L1-accepted checkpoint stays withdrawable on L1 with no new L2 block, no consensus participation, no quorum and no validator cooperation (MEM-15), and settlement can keep raising that checkpoint over already-certified heights while production is halted. (PR #22262 review comment 6011464863, item 2(c): the exit path is a liveness guarantee in its own right, not a conditional clause.) Liveness ends at the first clause that fails. Where it ends has changed (D-15): (L1) fails → the chain halts rather than forks; (L3) fails for data above the last L1-accepted checkpoint → the chain halts, and the stall resolution is the only rule that can restore progress, by discarding that range once governance queues it — no rule treats the data as available; (L4) fails → settlement halts after the unsettled-depth cap binds, and after T_STALL_GOV the stall resolution may discard the unsettled range once it is queued, so the stall is no longer terminal by itself but is not protocol-bounded either; (L5) fails → nothing settles and no L1 inclusion path can restore progress (LIVE-04), and the stall resolution is not an inclusion remedy; (L6) fails → the chain cannot enter the next epoch, and the stall resolution cannot manufacture the missing L1 set commitment, so that halt persists until the entry is appended and Ethereum-final; (L7) fails → a new node must not silently trust an unverified history. A void or cancelled entry returns the chain to the halted state. Offline validators specifically — the case review comment 6011464863 item 2 raised — split into two classes and the difference matters: a quorum lost to attrition (entries that stop attesting) is bounded by the heartbeat eligibility of MEM-13 and the rotation of CONS-16, conditionally on their Open items; a simultaneous stop of one third or more has no production-time bound, because the heartbeat is a declaration of presence and L1 cannot tell a cohort that keeps heartbeating from one that is online and participating (the F6-closure residual, disclosed in LIVE-05 and LIM-01). In both classes, value at or below the latest L1-accepted checkpoint remains withdrawable on L1 with no L2 liveness (MEM-15); the exact statement is LIVE-05. There is no clause whose failure licenses rewriting history at or below the latest L1-accepted checkpoint, and above it a failure licenses nothing either: only the exact trigger, timelock, resume-only effect and void-on-progress rule of GOV-04 do — and only when governance acts on them. (D-15: a settlement stall is not cleared by the protocol's own liveness; it is cleared only by the timelocked, resume-only governance action of GOV-04, so it depends on governance liveness (A-GOV-2), and the halt conditions that action cannot clear remain) Assumed unmeasured (the timeout bound, the retention window and the envelope are parameters whose values require measurement, 09)
LIVE-02 — backpressure and halt triggers Correct validators apply backpressure before liveness is lost, never by discarding committed history: (a) at unsettled depth D_MAX they refuse to vote for further blocks (HALT-03); (b) if the proof queue would exceed the retention window even at D_MAX, D_MAX itself is reduced by a published governance parameter change — an upgrade, not a runtime action; (c) they halt when HALT-01 conditions hold. A normal proof inside the D6 envelope (up to 30 minutes, 900 blocks at 2 s) must never trigger (a), (b) or any stall-resolution action. Failure mode: backpressure implemented as "drop the oldest unsettled batch", which is an unsanctioned rollback — not the stall resolution of GOV-04, with its objective trigger, timelock, resume-only effect and void-on-progress rule — and therefore violates REC-01. (D-15: only the sanctioned stall resolution may replace history, within the boundary owned by REC-01 and GOV-04) Proven unmeasured (D_MAX's value and the retention window)
LIVE-03 — throughput sustainability conditions The proving pipeline is sustainable if and only if three inequalities hold, all evaluated with measured inputs before launch: (i) rate: the fleet's sustained proven execution rate is at least the L2's sustained execution rate; (ii) concurrency: the number of proofs in flight is at least L / Δ, where L is the proof latency bound and Δ is the batch's L2 time span (a queueing identity, not a measurement); (iii) data: the L2's data production rate does not exceed the L1 data capacity available to the batches, which for blob data is the blob target/maximum per L1 block divided by the L1 slot duration. If any inequality fails, the backlog grows without bound and the correct response is LIVE-02 backpressure — not a longer latency assumption and not a rollback. Failure modes addressed: "tolerate individual slow proofs" being mistaken for sustainable throughput, and a design that quietly assumes unlimited prover capacity. Every input to these inequalities is unmeasured in this specification; the formulas are the deliverable. Open (requires measurement of cycles per L2 gas and proven cycles per second per machine, 03 §7)
LIVE-04 — censorship resistance, stated honestly Censorship resistance has two parts, and neither is a per-transaction guarantee. (1) Published data. The protocol provides a narrow, L1-anchored inclusion obligation: any account may publish a transaction's data (DA-07), and from the record's due point a batch must resolve it by the capped FIFO prefix of the due set or discharge it as void on FI-13's objective grounds (FI-10–FI-13), enforced at the proof (FI-11) and never by an admission gate on land. Omission of a due record within the required prefix is a proposal-validity failure (CONS-01(v)) and a breach (ECON-04 clause (6), ECON-13). The obligation is an upper bound on exclusion, never a lower bound on inclusion: it fixes no height or time by which inclusion must begin, a backlog drains over successive batches by the cap, and it reaches only data that reached L1. No general inclusion list exists: there is no queue of arbitrary transactions, no escrow and no forced-inclusion fee, and no L1 entry point for unpublished data (FI-PLANNED-01). (2) Unpublished data. For a transaction whose data never reaches L1, resistance is the conditional statistical property described here. Proposer selection is hash-based and weighted (CONS-06), and it is a public deterministic function (CONS-06(d)), so it is fully predictable: a coalition can identify in advance the slot in which a target transaction would be included, and buying or coercing the scheduled proposer of a single slot is possible and cheap — no rule prices, detects or penalises slot-buying, and this specification assumes no cost floor that prevents it. What bounds sustained censorship is the selection share, not unpredictability: a coalition with less than one third of the voting power is selected for strictly fewer than one third of slots in expectation, and a transaction that reaches honest validators is included by the first honest proposer with room for it. That last clause is a behavioural premise, not a protocol rule, and it is the honest limit of this resistance: no inclusion duty attaches to a validator for unpublished data (ROLE-01(b)), and omission outside the narrow rule's due prefix is neither a proposal-validity failure nor an offence (CONS-01, ECON-04), and no rule defines "room", reserves block space or constrains proposer ordering. Under A-CONS-2 the statistical half is real but conditional. A network-level adversary able to isolate a user from every honest proposer can prevent the data from ever being published — and so can an adversary able to censor L1 inclusion itself (A-L1-1) — and because a withdrawal is initiated by an L2 transaction, such an adversary can also prevent the user from starting a withdrawal. The protocol offers no remedy against either, and a partial relaxation of R10 is disclosed. The stall resolution of GOV-04 is not an inclusion remedy: it discards unsettled history above the last L1-accepted checkpoint, it cannot include a transaction, it does not compensate an exclusion, and it gives no user an L1 path into L2. (user decisions D-12 and D-11: narrow forced inclusion over published data ships in v1 and supersedes D-6/D-10; D-11 supplies the L1 anchor the narrow rule reads. D-15: the stall resolution replaces the withdrawn permissionless recovery, and it is not a substitute for inclusion.) This closes review round 3 finding R3-CE-05: selection is stated to be fully predictable and slot-buying possible and cheap, and the resistance is bounded by the selection share plus the honest-proposer behaviour that ROLE-01(b) expressly does not impose. Failure mode: presenting the narrow obligation as a per-transaction inclusion guarantee, or letting a user believe it reaches data that was never published — or that a general L1 escape hatch exists — would let the user size exposure on a promise the protocol never makes. Proven Assumed (the narrow obligation is structural and proof-enforced, and the absence of a general inclusion path is structural; the residual resistance claim is conditional on A-CONS-2 and A-L1-1)
LIVE-05 — halts caused by offline validators: escapability, time bounds, and what remains unbounded This rule states, for each way validators can stop the chain without being Byzantine, exactly what a user can still do and what the protocol does not bound. It adds no mechanism: the mechanisms are MEM-13 (L1-heartbeat eligibility: an entry is eligible for a version only if it attested within HEARTBEAT_WINDOW ending at that version's commit point, and ineligible entries are excluded from the root rather than decayed), CONS-16 (L1-time-keyed rotation), MEM-15 (exit from the last settled state) and GOV-04 (stall resolution), and each bound below is exactly as conditional as the rule it comes from. No rule removes weight within a set version, so the exclusions below are roster exclusions in a future version and never a change to the version that signed anything. (decision D-14: the inactivity decay is withdrawn and replaced by heartbeat eligibility; the falsifier the revocation introduces is F8.)

What is claimed, exactly. (i) A halt caused by offline validators no longer traps value that is already settled: every message at or below the latest L1-accepted checkpoint is withdrawable on L1 with no new L2 blocks, no quorum and no validator (MEM-15), and this part needs only Ethereum's liveness, not the L2's. (ii) That path does not depend on the stall resolution, on the rotation, or on any validator returning. (iv) It is not bounded for a simultaneous stop of one third or more, because a cohort that keeps heartbeating keeps its weight in W'.
