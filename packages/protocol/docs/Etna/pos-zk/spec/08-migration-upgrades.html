08 — Migration, upgrades and governance

What this page owns. The migration boundary from the Shasta deployment at revision 7718753c1 (MIG-01), the per-contract upgrade list and storage-layout constraints (MIG-02), the disposition of everything in flight across the boundary (MIG-03), removal of operational privileges (MIG-04), program-image, verifier and mixed-client rules (MIG-05), the no-replacement-deployment rule (MIG-06), and governance (GOV-01–GOV-03). Status labels are those of STATUS-01–STATUS-11; this page introduces no new label and no new status word.

Evidence base: taiko-baseline-contracts.md (the 800-line baseline, cited as path:line), prior-etna-digest.md, 04-architecture-decision.md and 01-requirements-and-threat-model.md §4–§5. Nothing on this page is implemented, deployed or measured (GEN-01).

The atomic settlement entry point is named land(data, proof) by L1-01; that name is fixed, and clients, parameters and migration scripts MUST use it.

This page is a plan, not a deployment. Every address below is as recorded in the repository's address libraries and hand-maintained deployment logs; no on-chain read was performed (baseline §10 gap 8). The preconditions in § Preconditions must be executed against the live chain before a migration bundle is built, and the bundle itself is gas-unmeasured.

The boundary in one picture

The migration is a single, irreversible switch from the Shasta rule set to the Etna PoS + ZK rule set over the same preserved contract addresses. It is not a chain restart: the new consensus begins at the last Shasta state that Ethereum already accepted, and every later rule must accept that state as its own past (GOV-03). Under the selected recovery mode, history at or below the latest L1-accepted checkpoint — the checkpoint record written by the most recently accepted batch, which a completed recovery restores exactly — is untouchable by any protocol path, and history above it is provisional and may be replaced only by REC-02 (REC-01); the migration itself is never a recovery and never a substitute for one. (user decision D-7: Mode B selected — the boundary object is accepted as the past, and the guarantee classes above and below it are those of REC-01.)

If a recovery is in flight during a migration or upgrade window. The migration's own transitions T1–T3 cannot overlap a recovery: the recovery path exists only under ETNA_ACTIVE (REC-02) and the state machine has no transition out of ETNA_ACTIVE, so at the T1–T3 boundary there is no pending invocation. For a later upgrade, a pending recovery is L1-side state the upgrade must carry unchanged: it may not cancel it, shorten or extend T_RECOVERY_DELAY, alter the checkpoint it restores, change the bond destination, or substitute itself for it (REC-01(d), GOV-03(e)). Cancellation stays exactly where REC-02 puts it — the acceptance of any valid batch extending the current checkpoint — and the upgrade must preserve the checkpoint record and the generation counter across the implementation change (GOV-03(c), MIG-05). (user decision D-7: the recovery is permissionless and bonded, and no upgrade may be used as a substitute for it.)

Normative rules

MIG-01 — migration boundary and preserved addresses The migration boundary is the last Shasta state accepted on L1 that is Ethereum-final at activation — the 4-tuple (C*, B*, H*, S*) where C* is the L2 chain id, B* the L2 block number of the last checkpoint written into the preserved L1 SignalService by a successful Inbox.prove() (Inbox.sol:364-370) before T3, H* the L2 block hash recorded for B*, and S* its L2 state root. "Last" is bounded by time, not chosen: T3 additionally requires the write to be at least L1_FINALITY_DEPTH L1 blocks old because prove() is disabled in DRAINED (MIG-03(1)(b)), so the boundary is an Ethereum-final L1 fact rather than a tip the bundle can pick. B* is identified on-chain by the equality _checkpoints[VERSION][B*].blockHash == IInbox.CoreState.lastFinalizedBlockHash and S* by _checkpoints[VERSION][B*].stateRoot; the bundle supplies (B*, S*) and T3 reverts unless both equalities hold, so the boundary is derived from the finalized tip and never chosen. Uniqueness of B* rests on keccak-256 collision resistance (A-CRYPTO-3) and on the monotonicity of L1-06. The starting point is the deployed system at revision 7718753c1: an Inbox with two separate entry points, propose() (Inbox.sol:270-290) and prove() (Inbox.sol:321-400), i.e. the data-first path D5 forbids; a disabled bond mechanism (minBond = 0, livenessBond = 0, MainnetInbox.sol:37-38) whose liveness settlement is additionally suppressed while a prover whitelist is enabled (Inbox.sol:356-359); a ProverWhitelist gating prove() (Inbox.sol:337,771-779; mainnet 0xEa798547d97e345395dA071a0D7ED8144CD612Ae); a PreconfWhitelist as IProposerChecker selecting one operator per epoch (PreconfWhitelist.sol:136-140; mainnet 0xFD019460881e6EeC632258222393d5821029b2ac); and the June 2026 blob-expiry incident, in which queued blob references outlived Ethereum's retention window and the owner-only init3() voided them with fees retained (Inbox.sol:246-258, called on mainnet in the Proposal0019 bundle, deployments/mainnet-contract-logs-L1.md:222-223) — the recorded instance of the data-first failure class that D5 removes. The new design has no inclusion queue and no pending data reference for a censored transaction; its replacement is the honest statement of LIVE-04. State that migrates (read once at T3, written to the migration/genesis slots 258–260 and — as the genesis checkpoint record — into the L1-07 checkpoint map of slot 264 (§genesis record, MIG-02), then frozen and never re-interpreted): H*; the L1 SignalService checkpoint record for B*; the existing TAIKO ERC-20 balances at the preserved token address 0x10dea67478c5F8C5E2D90e5E9B26dBe60c54d800, which are neither moved nor rewritten (new stake custody is a new L1 staking contract holding TAIKO via transferFrom, MEM-01, D7); the Bridge state nextMessageId (Bridge slot 251) and messageStatus (slot 252); and the vault deposit maps bridgedToCanonical, canonicalToBridged, btokenDenylist, lastMigrationStart (ERC20Vault slots 301–304) and the two NFT vault maps (slots 301–302). State that does not migrate: Shasta proposals that were proposed and never proven — they are not part of any finalized prefix, they wrote no checkpoint and have no bridge effect; pending bond balances in the Inbox ledger (slot 257), which are not carried into the new stake ledger and never count as voting power, but stay claimable (MIG-03); and blob references whose blobs have left Ethereum's retention window (A-DA-3), which cannot be proven and must not be promised. (user decision D-6: forced inclusion is removed — no inclusion queue, refund path, fee, escrow or request format migrates, and none exists in the new design; the June 2026 blob-expiry incident is kept only as historical evidence of the data-first failure class, and what does migrate is enumerated above.) Failure mode: a migration whose bundle can pick the history splits the chain or anchors a non-finalized height; treating an unproven proposal, a legacy bond or an expired blob as migrated state strands user funds or manufactures voting power that no L1 stake backs. Proven (premises: A-CRYPTO-3 for the uniqueness of B*, and A-CONS-1 — < 1/3 Byzantine stake — for the uniqueness of the finalized prefix that the boundary inherits, A-GOV-1 for an honestly executed bundle) sourced

MIG-02 — per-contract upgrade list and storage-layout constraints Each upgraded or preserved proxy's storage is partitioned into (a) a frozen inherited prefix occupying slots 0–250, in which slot 0 holds _initialized/ _initializing, slot 51 _owner, slot 101 _pendingOwner and slot 201 __reentry/__paused, with the ranges 1–50, 52–100, 102–150, 151–200 and 202–250 byte-identical to the generated layouts at the pin; (b) the contract's own region, whose last used slot and trailing gap are fixed by the table below; and (c) nothing else. New state may be declared only after the last used slot of the contract's own region, and it consumes exactly one gap slot per 32 bytes declared (packed variables may share a slot; a declaration crossing a slot boundary consumes two); the trailing gap must shrink by exactly the number of slots consumed and keep the same final slot index (300 for the L1 contracts, 350/400/450/500 for the vaults). The genesis checkpoint record written at activation

Normative. In the same transaction as T3 (MIG-03), activateEtna(B*, S*) MUST write the boundary object as the first L1-07 checkpoint record, and that write MUST satisfy every L1-07 MUST. The only fields the bundle may not derive are read from the equalities T3 already checks:

Checkpoint genesis = Checkpoint({
    height:         B*,                 // uint64; the boundary height of MIG-01
    blockHash:      H*,                 // bytes32; non-zero (T3's SignalService equality)
    stateRoot:      S*,                 // bytes32; non-zero (T3's second equality)
    epoch:          epoch_of(B*),       // uint64; recomputed by the contract from the activation
                                        // record (CONS-13); 0 at activation
    setRoot:        staking.epochSetRoot(0),  // bytes32; non-zero — T3 requires the epoch-0 set root
    dataCommitment: keccak256(abi.encode(bytes32("TAIKO_ETNA_GENESIS"), uint256(block.chainid),
                                         uint64(B*), H*, S*)),   // non-zero by construction
    l1BlockNumber:  uint64(block.number)      // the activation block, written once, never edited
});
lastLandedHeight = B*;                  // in the same write

Defined predecessor. The first land(data, proof) after activation MUST compute L1-05 row 2's previousCheckpointHash from this record with L1-07's canonical encoding. It is non-zero by construction and a zero or undefined predecessor value is forbidden: an implementation that leaves previousCheckpointHash at bytes32(0), or that computes it from an unset record, is non-conforming. Because the record's height, blockHash and stateRoot are exactly (B*, H*, S*) and its epoch and set root are L1-derived, the genesis record and the preserved L1 SignalService checkpoint for B* cannot diverge (MSG-01). The record MUST NOT be used to restart a withdrawal delay: eligibility already stored in the SignalService and in _receivedSignals is unchanged (MIG-03(6)).

What the genesis dataCommitment is, and is not. It is the tagged commitment to the boundary object itself, and it is the only record in this specification whose commitment is not a batch data commitment. It MUST NOT be presented as, or used as, evidence that any batch's data was published in the activation transaction; it MUST NOT be spliced into a proof's public inputs; and the first genuine batch's dataCommitment MUST come only from a successful land(data, proof) (DA-01–DA-03). Inventing a batch-shaped non-zero commitment for the boundary, or treating the boundary record as a batch acceptance, is exactly what D5/DA-01 forbid. (review round 2, findings E-R2-01 and E-R2-03: the genesis is now a legal L1-07 record with a defined, non-zero predecessor, written in the transaction that disables the legacy path, and the old rule left dataCommitment and previousCheckpointHash undefined.)

MIG-03 — treatment of pending proposals, unproven batches, legacy bonds, bridge messages and withdrawals (1) One settlement path at a time, and what D5 does and does not cover. land(data, proof) reverts unless migrationState == ETNA_ACTIVE; prove() reverts unless migrationState is SHASTA_ACTIVE or FROZEN — it reverts MigrationDrained() from T2 onward and is absent or unconditionally reverting in ETNA_ACTIVE. No state exists in which both are callable, so at most one path can advance the checkpoint. FROZEN is entered by the migration bundle, which in the same transaction disables propose(); states advance only in the order of T1–T3 and no transition is skippable.
D5's scope, stated honestly. D5 — one L1 transaction carrying a batch's data and its proof, out of which the checkpoint advances — governs every batch accepted by the Etna path, i.e. every call to land(data, proof). The Shasta wind-down is a different protocol whose rule set is propose() + prove(): its batches are never Etna batches, can never be accepted by land(data, proof) (the gate above makes that call revert outside ETNA_ACTIVE), and can never advance an Etna checkpoint, because the Etna checkpoint chain begins at the genesis record T3 writes (§genesis record) and every later record is written only by land(data, proof). What the legacy path can do during the wind-down — and this is the exception, named rather than denied — is advance the preserved L1 SignalService checkpoint from a proposal whose data was published in an earlier propose() transaction (Inbox.sol:270-290,321-400); that is exactly the data-first flow D5 forbids for this protocol. The exception is bounded four ways: (i) the legacy entry points MUST be disabled no later than the activation transition T3 — a named transition, not "eventually": prove() reverts MigrationDrained() from the moment the machine enters DRAINED (T2) and is absent or unconditionally reverting in ETNA_ACTIVE, so after T3 no legacy batch, proposal or proof can advance any checkpoint and no function may import one; (ii) the genesis checkpoint MUST be taken at a defined, Ethereum-final L1 boundary: T3's guard requires block.number ≥ drainedAtL1Block + L1_FINALITY_DEPTH, and because prove() cannot run in DRAINED, the checkpoint T3 adopts was written at least L1_FINALITY_DEPTH L1 blocks earlier, so it is an Ethereum-final L1 fact and not a tip the bundle can choose (MIG-01, T3); (iii) no legacy batch may become the genesis checkpoint after Etna activation: the genesis record is written exactly once, inside T3, from the boundary object fixed by T3's two equalities, and after T3 there is no mode in which a legacy entry point exists; (iv) the honest claim is therefore "no exception within the Etna protocol, and the legacy path is disabled at a named transition (T3)". The stronger claim "no exception anywhere, in any state, ever" is not made on this page, and INV-02's invariant is to be read with this named carve-out: it holds for every batch the Etna protocol accepts. (review round 2, finding E-R2-01: the migration exception is named and bounded, the legacy path is disabled at T2/T3 rather than "in DRAINED or later", and the genesis is taken at an Ethereum-final boundary.) (2) Proposed but never proven. A proposal with no accepted prove() at the end of the drain window is void: it contributes no checkpoint, no state root and no bridge effect, and its proof path closes permanently at DRAINED. Because propose() is disabled at FROZEN, the proposal-hash ring buffer cannot be overwritten during the window (the overwrite at Inbox.sol:626 happens only inside propose()), so every unproven proposal stays provable until the deadline subject only to data availability (A-DA-2, A-DA-3). The migration announcement must state the drain deadline in L1 block numbers and that L2 transactions inside unproven proposals are not carried over. (3) Bonds. Legacy bond balances (Inbox slot 257) are not converted into stake and confer no voting power. The post-migration implementation retains exactly one legacy selector, withdrawLegacyBond(address _to, uint64 _amount), which debits that ledger under the legacy floor and delay baked at deployment from the pre-migration getConfig() (mainnet minBond = 0, withdrawalDelay = 1 weeks, MainnetInbox.sol:37,39), and it remains callable in every state. No new bond may be created after the freeze and no legacy balance may be slashed. (user decision D-6: clause (4) of the previous revision, forced inclusions, is deleted with forced inclusion — there is no request format, queue, fee, escrow or refund path to carry across the boundary, and no legacy inclusion selector survives. The remaining clauses keep their numbers: nothing is renumbered, so existing cross-references stay valid.) (5) Bridge messages. The migration upgrade must not reset nextMessageId, messageStatus, _receivedSignals or _checkpoints; must not change the SIGNAL slot derivation (SignalService.sol:160-171,232-235); and must not change SignalService.VERSION, because one version bump invalidates the received-signal cache and hides every checkpoint simultaneously (SignalService.sol:52,63,179). An L2→L1 message sent at height ≤ B* stays provable after activation because every post-activation checkpoint is a record of a state that contains its signal; an L1→L2 message stays provable while the Anchor keeps writing L1 checkpoints with blockNumber = L1 block number and monotone _blockState.anchorBlockNumber (Anchor.sol:173-186). A message is processed at most once because its status is set by processMessage, and MIG-01's boundary rule prevents a second history from producing a second proof of receipt. (6) Withdrawals. A withdrawal that was withdrawal-eligible at the freeze remains eligible during and after the migration: eligibility depends on a stored signal and a stored checkpoint, both preserved unchanged, and no delay is extended, restarted or re-based by any transition. Failure modes: two live settlement paths produce two histories; a data reference that outlives its retention window is unprovable — the June 2026 blob-expiry incident at the baseline is the recorded instance of that data-first class, and this specification declares such proposals void in advance instead of voiding anything silently; a VERSION bump makes every in-flight message unprovable; counting a legacy bond as stake manufactures voting power no L1 stake backs. MIG-04 — removal of operational privileges Every lever in the table below is removed from the runtime ABI of the contract that holds it. Removal is a deliberate behaviour change of the preserved surfaces: D3 preserves addresses, not powers. After the removals, ordinary operation reads no owner, no whitelist, no resolver entry and no pause flag: block production, voting, proving, settlement and exit complete with no privileged transaction. The only authority that remains is DAO upgrade authority — MainnetDAOController.execute (MainnetDAOController.sol:24-31, itself owned by the TaikoDAO) calling upgradeToAndCall through _authorizeUpgrade (EssentialContract.sol:207) — and it is never a runtime dependency (GOV-01). No runtime authority is created by the migration: the new staking contract and the new verifier route are permissionless (MEM-03, L1-04), and any owner those new contracts have is upgrade authority only. Where a removal changes incident response (no runtime pause, no runtime image rotation, no runtime token remapping), the consequence is disclosed in the table and the remedy is a DAO upgrade, not a hidden key. (user decision D-6: forced inclusion is removed, so no inclusion path or inclusion lever exists in the post-migration ABI and none appears in the ordinary-operation enumeration above.) Failure mode: a surviving owner function is a capture target and a liveness dependency (R2), and makes the "no privilege or discretion in ordinary operation" invariant (INV-04) false; init2() in particular can rewrite lastFinalizedBlockHash, which the recovery boundary forbids: no path may change history at or below the latest L1-accepted checkpoint, and above it only the permissionless recovery may (REC-01). (user decision D-7: the prohibition is the boundary of REC-01, not a Mode A-only posture.) MIG-05 — program-image and verifier upgrades; mixed-version clients and in-flight proofs The set of program images accepted for an epoch e is the value of the registry (Inbox slot 261, acceptedProgramImage[imageId] = acceptedFromEpoch) at the same L1-committed boundary that fixes the validator-set root for e (MEM-09), so an image change takes effect for epochs that start after the L1 transaction that recorded it. Registry entries are never deleted: an image that was accepted for an epoch remains accepted for that epoch forever (CONS-08). Adding an accepted image or a verifier route is an upgrade, never a runtime call: the accepted-image set is Inbox slot 261, the route registry is slot 267, and both are written only by the Inbox implementation installed by an upgrade (L1-09, GOV-02); a permissionless or owner-only registration entry point MUST NOT exist, and a route whose verifier is not a deployed, audited contract MUST NOT be registered. (review round 2, finding E-R2-04) (user decision D-6: the route registry is renumbered to slot 267 after the five forced-inclusion slots were removed from the Inbox budget; MIG-02 owns the re-derived arithmetic.) An image may be given a retiredAtEpoch marker, after which it may not be used for batches whose epoch is at or after the marker, but retirement must not invalidate a certificate, a checkpoint or a settled batch. Consequently: a proof generated before an upgrade for a batch in an epoch whose accepted set contains its image remains acceptable after the upgrade and needs no re-proving; a proof whose image is not in the accepted set of the batch's epoch is rejected by the verifier route (L1-09); and land(data, proof) must never reject a valid (data, proof) pair merely because the proof's image was superseded for later epochs. There is no mixed-version consensus window: because the accepted set is a deterministic function of L1-committed state and the upgrade is epoch-gated, all clients that have processed the boundary L1 block derive the same set, and a client that disagrees is producing invalid blocks rather than a second rule set. Both backends must implement the same statement and the same acceptance policy (PRF-09); the guest/verifier version registry itself is defined by PRF-10, which this rule uses and does not restate. Failure modes: a mid-epoch image switch splits which proofs are acceptable and lets an unsettled batch become unprovable; deleting an old image strands already-finalized history; a "mixed-version" leniency silently accepts two rule sets. Proven Assumed (premises: A-CRYPTO-1 soundness applies per image, and the epoch boundary is the L1-committed one of MEM-09; if the registry boundary and the set boundary ever diverge, the split risk in the failure mode above returns)

MIG-06 — no replacement deployments for the preserved surfaces The migration is an in-place implementation upgrade of every proxy in the table below, at the address recorded there. No new contract is deployed to a new address to replace any of them, and no new address is introduced into any interface that a user or a peer contract resolves: the SIGNAL slot derivation, the resolver results for the Bridge and vault peers, and the L1/L2 address libraries are unchanged. The settlement Inbox and the L2 Anchor are upgraded in place too, because the two immutable checkpoint-writer links are wired to those exact addresses — L1 SignalService._authorizedSyncer is the Shasta Inbox (SignalService.sol:35-37,174-175; DeployShastaContracts.s.sol:130) and L2 SignalService._authorizedSyncer is the Anchor proxy (DeployShastaL2Contracts.s.sol:46-53) — and because Anchor.blockHashes (slot 251) is a permanent L2 map that must keep answering getBlockHash. An implementer must know that these immutables are properties of the implementation code, not of proxy storage, so an implementation upgrade can change them; this rule therefore forbids changing them rather than relying on immutability to enforce it. A re-deployed SignalService implementation must be constructed with the same _authorizedSyncer, _remoteSignalService and VERSION values as the implementation it replaces. L2 SignalService checkpoint writer, reconciled. This is the operative instruction for the L2 SignalService: the migration bundle and the re-deployed implementation MUST keep _authorizedSyncer = the Anchor proxy on L2 (and = the Inbox on L1, MSG-01). The aspiration recorded elsewhere in this specification — that the preserved L2 address be repointed to a write path that is not a single privileged address — is not achieved by this migration and cannot be achieved by it without a different _authorizedSyncer, which this rule forbids. It therefore requires a separate, recorded decision and a later upgrade, and is carried as Open in MIG-04's golden-touch row. Until that decision exists, the L2 checkpoint writer remains the reserved system sender of SYS-02(g) and the claim that no single privileged writer remains is not made. (review round 2, finding E-R2-09: MIG-06's same-immutables rule is the one the migration follows; the removal is Open with its consequence — the L2 checkpoint writer keeps a reserved-sender privilege that R1/R2 do not yet exclude.) Verifiers, the L1 staking contract and the prover-reward path are not preserved surfaces: they are new deployments referenced by address from the upgraded Inbox (L1-09). TaikoToken is not deployed, moved or migrated. Failure mode: a replacement deployment changes every address users and peer contracts have integrated, breaks the checkpoint-writer link (after which the preserved SignalService can never be checkpointed again and every cross-chain message stops verifying) and duplicates bridge state across two Bridges. Governance

GOV-01 — DAO governs upgrades only; the trust assumption is stated The DAO's only authority over this protocol is the ability to execute an upgrade: MainnetDAOController.execute(bytes) (onlyOwner, owned by the TaikoDAO; MainnetDAOController.sol:24-31) calling upgradeToAndCall / upgradeTo on the proxies it owns (EssentialContract.sol:207), plus the migration transitions T1–T3 that are delivered as upgrades. After ETNA_ACTIVE no DAO-dependent runtime state may exist: no consensus rule, admission rule, proof-acceptance rule, exit rule or bridge rule may read a value the DAO can change without an upgrade, and no DAO transaction may be required for ordinary liveness — block production, voting, proving, settlement and exit must all complete without one. (user decision D-6: forced inclusion is removed, so no inclusion rule exists and none appears in this enumeration; inclusion resistance is the conditional property of LIVE-04.) The trust assumption is explicit and is not repairable by the protocol: A-GOV-1 (01-requirements-and-threat-model.md §4.4) states that the DAO does not execute a malicious upgrade; if it does, the safety claims of this specification do not apply to the resulting rule set (failure class F2). For contrast, the prior Etna design recorded exactly two DAO-dependent states — CONFLICT after a provisional landing, and a certificate-free landing during a one-leaf outage (prior-etna-digest.md:113,119); this design has zero. Failure modes: any runtime DAO lever is a capture target and a liveness dependency (R2); a hidden owner flag makes the no-privilege invariant (INV-04) false; describing A-GOV-1 as a guarantee is exactly the non-argument "the DAO would fix it". Proven Assumed (proven relative to the MIG-04 removal table being complete; the residual trust is A-GOV-1, whose failure is GOV-02)
GOV-02 — malicious governance is a separate failure class A malicious or compromised DAO is failure class F2, not a protocol failure: no rule, contract, monitor or evidence object in this design detects, prevents or repairs it, and one upgrade can rewrite any rule — including this one — reassign any storage slot, or remove the staking requirement. The honest responses are exactly three: (i) before-the-fact disclosure, (ii) comparability, i.e. every upgrade bundle is published with the target implementation addresses, the storage-layout diff and the expected post-upgrade boundary object, so any deviation is publicly detectable, and (iii) the ability of users to exit before an announced upgrade takes effect, subject to the delays of MSG-03 and ECON-03. This design does not claim that a DAO upgrade cannot invalidate finalized history; it claims that no rule of this protocol can, and that a governance rewrite is reported as a rules change rather than as a recovery. The status guarantee (STATUS-04, STATUS-06) is made relative to the rules in force — history at or below the latest L1-accepted checkpoint is untouchable by any protocol path (Ethereum finality is the separate, stronger property of STATUS-07), and history above it is provisional and replaceable only by the recovery of REC-02, never by a governance transaction (REC-01) — and after a governance rewrite it must be re-established by the new rules. (user decision D-7: Mode B selected — a governance rewrite is still reported as a rules change, never as a recovery.) Failure mode: reading A-GOV-1 as a guarantee, or claiming that ZK verification, bonds or a timelock make governance capture safe; the prior Etna digest records the same conclusion ("the DAO is assumed honest; capture is out of scope", prior-etna-digest.md:113). Proven Assumed
GOV-03 — upgrades must not invalidate finalized history and are never a substitute for recovery Every upgrade, including the migration of MIG-01–MIG-06, must accept all history finalized under the rules in force before it: (a) a certificate valid under the epoch and validator-set rules of its own epoch remains valid forever (CONS-08) and no post-upgrade rule may require it to be re-derived; (b) the post-upgrade verifier route must still accept a proof of any not-yet-settled batch under the program image that was in force for that batch's epoch (MIG-05), so no batch becomes unprovable because of an upgrade; (c) checkpoint advancement stays monotone (L1-06): an upgrade may not lower the finalized tip or rewrite the checkpoint record for any height at or below the boundary with different contents; and (d) at migration the accepted history is the boundary of MIG-01, and no alternative history at or below B* may ever be adopted afterwards (HALT-02); and (e) no upgrade may be used as a substitute for recovery: an upgrade MUST accept every history at or below the latest L1-accepted checkpoint, history above that checkpoint may be replaced only by the recovery path of REC-02 and never by a governance transaction, and a pending recovery MUST survive the upgrade unchanged — the upgrade may not cancel it, shorten or extend T_RECOVERY_DELAY, alter the checkpoint it restores or the bond destination, or replace it with any other action (REC-01(d)). Compliance is checked by the published target/layout diff required by GOV-02 and, for (b), by an acceptance test that lands one already-generated pre-upgrade proof after the upgrade, on both backends (PRF-09, PRF-10). (user decision D-7: Mode B selected — an upgrade must never be used as a substitute for recovery, and it must carry a pending recovery unchanged.) Failure mode: a "normal upgrade" silently strands a proven-but-unsettled batch, rolls the checkpoint back, cancels a pending recovery, or is used to replace history that only recovery may replace — the boundary violation REC-01 forbids, and the class recorded as the prior Etna design's XS-FIN-01 finding (prior-etna-digest.md:142). (user decision D-7: the boundary of REC-01 and the recovery path of REC-02 are the only sanctioned history replacement.) Proven Assumed (premises: CONS-08, L1-06, A-CRYPTO-3, and A-CONS-1 — < 1/3 Byzantine stake — for the uniqueness of the finalized prefix that (a) presupposes; a DAO that ignores this rule is handled by GOV-02, not by this rule)
