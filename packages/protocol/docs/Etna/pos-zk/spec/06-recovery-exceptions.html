06 — Withholding, safe halt, restart, and the one named stall resolution

A PoS confirmation above the latest L1-accepted checkpoint is provisional. The permissionless bonded recovery was withdrawn by D-15; the timelocked, resume-only governance stall resolution that replaced it is live again as GOV-04 under increment 05 — one DAO-queued entry, a stored T_GOV_RESUME deadline, a permissionless execute() that consumes the entry, and a full-range discard of everything strictly above the latest L1-accepted checkpoint. It is the one named exception short of recovery; aggregation (D-13) and the heartbeat rotation (CONS-16) stay deferred and tombstoned, while narrow forced inclusion (D-12) and heartbeat eligibility (D-14) are live again by increment 04 and increment 02 — see the deferred-work register DEFERRED.md. A settlement stall halts the chain: funds are safe, the boundary of REC-01 holds and the exit guarantee of MEM-15 — a withdrawal proven against the last accepted checkpoint, with no new L2 blocks, no quorum and no validator — works; the stall is cleared only by the executed GOV-04 action, and clearing it still depends on governance liveness with no protocol bound (F-GOV-1, A-GOV-2). At or below the latest L1-accepted checkpoint — the checkpoint record written by the most recently accepted batch — nothing may be changed; above it history is provisional, and the only protocol path that replaces it is the executed GOV-04 action. Ethereum finality is the separate, stronger property of STATUS-07. Any interface that shows a confirmation above the last accepted checkpoint must say that it is provisional, must name the one rule-bound action that may replace it (GOV-04), and must not present that action as a guarantee that a resolution will ever be queued or executed. (increment 05: the governance stall resolution is live with a consumed entry and a stored deadline, and clearing a settlement stall still depends on governance liveness; value above the last accepted checkpoint has no L1-provable claim and is not protected by the window. Increment 02: heartbeat eligibility is live but is a selection filter on future set versions, not a history-replacing path.)

REC-01 — recovery boundary: no path may replace history at or below the latest L1-accepted checkpoint No contract function, client rule, timeout, validator rotation, admission rule, governance proposal executed through the ordinary upgrade path, operational procedure, or recovery invocation may change the canonical history at or below the latest L1-accepted checkpoint — the checkpoint record written by the most recently accepted batch. Above it, history is provisional: in v1 no protocol path replaces it, because every replacement mechanism is absent: the permissionless recovery was withdrawn by D-15; the governance stall resolution and aggregation remain deferred by D-16; and the narrow forced inclusion that was deferred with them has since been revived as a live inclusion obligation by increment 04 — an inclusion rule that reads no L2 history and writes none, adds no recovery action and cannot replace a checkpoint (FI-14). The heartbeat eligibility revived by increment 02 is a selection filter on future set versions and not a path that replaces history, and the rotation that would consume it remains a gated tombstone (DEFERRED.md). (increment 02: the revived mechanism is a selection filter on future set versions; increment 04: the revived inclusion obligation replaces no history; no replacement path is added and REC-01's guarantee is unchanged.) A future protocol update that adds a replacement path must preserve this boundary. Ethereum finality is a separate and stronger property, not the recovery floor: once the accepting L1 transaction is in a finalized Ethereum block, even an L1 reorganisation cannot undo it (STATUS-07); until then an accepted checkpoint is revocable only by an L1 reorganisation below finality (STATUS-06, L1-12), so an implementer must never read that property back as the recovery floor. Concretely: (a) no function exists whose effect is to replace an accepted block hash at or below the latest L1-accepted checkpoint or to discard state at or below it, and no function that discards state above it exists either — v1 has no downward movement of the canonical L2 chain; (b) no admission rule may reject a batch that extends the current L1 checkpoint (L1-04); (c) a certificate is judged under the validator set of its own epoch and stays valid as evidence forever (CONS-08), so validator rotation cannot re-judge it; the signed recovery generation scopes certificates, locks and uniqueness (CONS-04, CONS-12), and in v1 no rule increments it, because the action that would is deferred by D-16 (09); (d) no upgrade may be used as a substitute for recovery: an upgrade must accept every history at or below the latest L1-accepted checkpoint (GOV-03), and no upgrade may discard history above it either, because no rule specifies a stall-clearing action and clearing a stall requires a future protocol update whose procedure is not yet specified (D-16; DEFERRED.md §3); (e) no data-first path in the sense this rule fixes may be introduced to "work around" an unsettled batch, in recovery or otherwise, because that would let an unproven history be treated as settled (L1-02, HALT-04). Publication is not that path (D-11): a batch's data MAY be published to L1 before its proof and recorded as a publication record, because publication writes no checkpoint, advances no protocol state and becomes relevant only when a later proof references it; what D5 forbids, and what this clause forbids, is a path by which a checkpoint or any other protocol state advances on data alone. The proving deadline that bounds a published-but-unproven record, and its discard-and-republish consequence, are owned by 04 and are not restated here. The live inclusion obligation reads no recovery mechanism, because v1 has none: the forced-data register, the settlement frontier and the deletion-only prune of FI-10–FI-14 are settlement-side state; no rule of the FI family reads, writes or is discharged by a recovery, a stall resolution or a restored checkpoint, and the boundary above is untouched by them (increment 04; FI-14(2)). (D-11: data may be published before the proof; publication writes no checkpoint, so it is not a data-first path in this rule's sense.) (decision D-16: the boundary is unchanged — nothing at or below the latest L1-accepted checkpoint is ever rewritten and history above it is provisional; v1 has no replacement path at all, because the governance stall resolution and aggregation are deferred and clearing a stall requires a future protocol update whose procedure is not yet specified, while the narrow forced inclusion revived by increment 04 replaces no history.) This rule is the boundary between the two guarantee classes: no path may change history at or below the latest L1-accepted checkpoint, and history above it is provisional. Its violation would turn a bounded rollback into unbounded history replacement, which no user decision authorises. Halting remains the correct local action when settlement cannot proceed, and in v1 nothing replaces history: the deferred mechanisms are not implemented (DEFERRED.md). This closes the reviewer finding that made the Ethereum-finalized checkpoint the recovery floor: the floor is the latest L1-accepted checkpoint, and Ethereum finality is the separate, stronger property of STATUS-07 (D-15; restated by D-16). Proven (structural: the boundary of the replacement window plus four positive obligations)

Safe halt

HALT-01 — safe halt obligation A correct validator halts — it stops signing and stops advancing its finalized view — rather than choose between two histories or advance on unknown state. It halts when any of the following holds and cannot be resolved by a rule-legal action: (a) it cannot obtain the data for a finalized or locked block (A-CONS-5 failed); (b) it cannot obtain a quorum for a height within the timeout ladder (A-CONS-2 failed); (c) the L1 facts it must consume are not yet Ethereum-final, or its L1 view disagrees with the consensus view (SYS-02); (d) the L1 validator-set commitment for the epoch it is about to enter is absent (CONS-13); (e) the unsettled-depth cap would be exceeded (HALT-03). Halting is a correct outcome, not a failure of the protocol: it is the action that preserves every height at or below the latest L1-accepted checkpoint and keeps the node inside its rules. A node that halts must keep serving what it has, and must keep its state so it can resume. Halting never authorises discarding history, and never authorises treating a publication as settlement: publishing a batch's data before its proof is permitted (D-11), but a publication record advances no checkpoint, so no participant may act on it as if a batch had landed (REC-01(e)). A validator's halt is a local safety action and is not a recovery trigger: v1 has no recovery path of any kind, so there is no stall-resolution action to invoke and no early declaration. A halt caused by an unlandable batch is answered by retrying and by continuing to serve; if settlement nevertheless stalls, the chain stays halted, funds remain safe, the boundary of REC-01 holds and the exit of MEM-15 works, but clearing the stall requires a future protocol update whose procedure is not yet specified (DEFERRED.md §3). No recovery exists to clear any halt: no mechanism changes a validator set or manufactures a missing epoch-set entry or an unavailable quorum, so a halt under (b) or (d) persists until the entry is appended and Ethereum-final or the quorum returns (LIVE-01). The heartbeat eligibility of MEM-13 is live (increment 02) and excludes an entry that stops signing from set versions committed after its last covered window, but exclusion changes only future composition: the committed roster that stalled the chain is immutable and the rotation that would consume a restart set (CONS-16) remains a gated tombstone, so where (b) is caused by validators that have stopped attesting, the halt is not escapable by any rule of v1 that acts on the committed epoch. This closes review round 4 finding R4-LIV-09: recovery is not presented as the remedy for halts it cannot clear. (decision D-16: v1 has no recovery path of any kind and clearing a settlement stall requires a future protocol update whose procedure is not yet specified; increment 02: the heartbeat eligibility is live but excludes only from future set versions, so it is not a recovery route for a committed epoch.) Failure modes: an implementer, faced with a stuck chain, invents an "unstick" action; or a participant treats its own halt as authority to roll history back. Neither is permitted — v1 has no sanctioned replacement path at all, and the mechanisms that could have provided one are deferred (DEFERRED.md). Proven Assumed (the halt conditions are normative; whether they are met is assumed)
HALT-02 — restart rules After a halt, a correct participant resumes only from the highest finalized block whose data and certificate it can independently reconstruct. It must never adopt an alternative history at or below the latest L1-accepted checkpoint, and must never treat a timeout during the halt as evidence that a certificate does not exist (STATUS-10). On restart: (a) each validator enforces a signed-message uniqueness check over its own signing history — no message of the same type at the same height, round and recovery generation may be signed twice, including after a restart or a state resync, and a validator that cannot prove it has not already signed for a (height, round, type, generation) must not sign (the amnesia case is treated as a signing fault, not as a fresh start); (b) a validator that resumes must re-verify the epoch and set for the height it is resuming at rather than trusting its cached set; (c) nodes must not accept a replayed historical message as new — every vote carries the epoch and round, and the receiving rules reject messages for heights already finalized; (d) a resumed node's first act is a data and certificate sync, not a proposal. The restart-after-resolution linkage that D-15 specified — resuming from a checkpoint restored by an executed stall resolution, the resume point resumeHeight = lastLandedHeight + 1, and the withdrawn recovery linkage and recovery anchor — is deferred by D-16 with the governance stall resolution and MUST NOT be implemented; it is kept as the tombstone REC-04 and in DEFERRED.md §3. In v1 there is no restored-checkpoint case to link to, and the ordinary contiguity rule of CONS-01(iii) and the ordinary anchor duty of CONS-09(1)–(2) apply unchanged. (decision D-16: the governance stall resolution and its restart linkage are deferred, so the restart rules are the ordinary ones.) Failure modes addressed: "amnesia" double-signing after a restart, replaying old votes, and a restart that silently adopts a competing branch — the classic way a safe halt becomes an unsafe restart. Proven (the signing-history rule rests on the validator's own durable state, an implementation gate)
HALT-03 — consensus-enforced unsettled-depth cap (backpressure) Define the unsettled depth at a height as the number of L2 blocks between the highest L1-accepted checkpoint and the block being considered. A correct validator must not prevote or precommit a block whose unsettled depth would exceed D_MAX − MARGIN_V. Exactly one enforcement point: the validators. land MUST NOT reject an over-depth batch, because doing so could make a legitimately finalized range permanently unlandable and would violate L1-04 (*review round 2, finding R2-LIV-07*). D_MAX is derived from the retention window, the permitted proof latency and the settlement pipeline, and not from the retention window alone: D_MAX = floor((RETENTION_WINDOW − T_PROOF_MAX_PERMITTED − T_SETTLE_PIPELINE) / L2_BLOCK_INTERVAL), recorded with its derivation in 09. MARGIN_V is mandatory and is at least the number of L2 blocks produced during one Ethereum finality depth, because a validator's view of the L1 checkpoint is itself only usable at that depth (SYS-02); without the margin a validator can systematically under-estimate depth and overshoot the cap. The cap is a consensus rule with a single enforcement point. Honest statement of what that costs: because the cap cannot be enforced at L1 without stranding a legitimate extension, a quorum that ignores it is not objectively punishable at L1, and a cap violation is therefore a liveness failure that is disclosed rather than a slashing offence (WH-02, LIM-01). When the cap binds, production stops and the chain is in the safe-halt state until provers catch up. No recovery action relaxes the cap, and none exists in v1: v1 has no recovery path of any kind (D-16), a cap binding is a halt and not a trigger for any action, and production resumes only when provers catch up and the unsettled depth falls back under the cap. (decision D-16: the unsettled-depth cap is unchanged; the deferred stall resolution is not implemented, and no mechanism may be used to advance past the cap or to bypass it.) The cap must also be jointly satisfiable with the evidence window: the coupling inequality is stated normatively in ECON-07(7), and D_MAX must be reduced until it holds (*review round 2, finding P-R2-08*). It is also jointly constrained with the D6 envelope, and RETENTION_WINDOW is chosen from that constraint rather than independently: a proof that consumes the whole envelope must leave an unsettled depth at or below the depth at which validators stop, so D_MAX · L2_BLOCK_INTERVAL ≥ T_PROOF_ENVELOPE + T_SETTLE_PIPELINE + MARGIN_V · L2_BLOCK_INTERVAL, equivalently D_MAX − MARGIN_V ≥ (T_PROOF_ENVELOPE + T_SETTLE_PIPELINE) / L2_BLOCK_INTERVAL (the margin term is MARGIN_V · L2_BLOCK_INTERVAL, in seconds, because MARGIN_V is measured in L2 blocks). (registration audit: the seconds-form allowance of this inequality is the registered MARGIN_D, with MARGIN_D ≥ MARGIN_V · L2_BLOCK_INTERVAL, as stated in 09.) Because this rule derives D_MAX from RETENTION_WINDOW, the inequality is also a lower bound on the retention window: in particular RETENTION_WINDOW MUST be large enough that floor((RETENTION_WINDOW − T_PROOF_MAX_PERMITTED − T_SETTLE_PIPELINE) / L2_BLOCK_INTERVAL) − MARGIN_V ≥ (T_PROOF_ENVELOPE + T_SETTLE_PIPELINE) / L2_BLOCK_INTERVAL (a sufficient form is RETENTION_WINDOW ≥ T_PROOF_ENVELOPE + T_PROOF_MAX_PERMITTED + 2 · T_SETTLE_PIPELINE + MARGIN_V · L2_BLOCK_INTERVAL + L2_BLOCK_INTERVAL), so the retention window is derived backwards from the inequality, never selected on its own and checked afterwards. If the inequality is violated, D_MAX − MARGIN_V can be zero or negative, in which case no block at a positive unsettled depth may be voted and production cannot advance past the current checkpoint. The envelope term is D6's planning assumption T_PROOF_ENVELOPE, not T_PROOF_MAX_PERMITTED (the permitted bound of 09): the promise is that a normal proof never binds the cap. This closes review round 3 finding R3-LIV-02: HALT-03 carries the joint cap/envelope inequality, so a normal 30-minute proof can never trigger the cap, and RETENTION_WINDOW is stated to be chosen from that inequality rather than independently. D_MAX is a bound on commitment creation, not on proving latency, and a normal proof taking the whole of the D6 envelope (up to 30 minutes, i.e. 900 blocks at 2 s) is not misconduct and not grounds for any recovery action (none exists in v1, D-16). Failure modes addressed: unbounded growth of unsettled history (which is exactly the state in which an availability failure becomes unrecoverable), and an implementer treating a slow proof as a fault. Proven unmeasured (D_MAX's value depends on measured retention and proving throughput)
HALT-04 — no emergency operator, no discretionary DAO rescue, and no recovery path in v1 No emergency key, guardian, or operational procedure may be required to preserve any invariant of this specification, and none may be introduced to "resolve" a halt. There is no exception, named or unnamed: v1 has no recovery path of any kind — neither permissionless nor governance-mediated — because no replacement mechanism is live — three of the four add-on mechanisms remain deferred by D-16 and the fourth, heartbeat eligibility, is a future-version selection filter revived by increment 02, not a recovery path (DEFERRED.md). (increment 02: the heartbeat filter is live but is not a recovery path.) No operator, DAO or governance actor may advance, rewind or replace the checkpoint, and no queued or timelocked action exists. Nothing may be required and no DAO intervention is permitted: specifically, there is no function that a privileged party can call to advance, rewind, or replace the checkpoint; and no publication may be used to unblock settlement: publishing a batch's data before its proof is permitted (D-11), but the publication record advances no checkpoint and confers no status, so it can never substitute for a proof (REC-01(e)). If progress requires information or participation that no rule-legal action can obtain, the protocol says so and stops; it does not promote a privileged fix. A settlement stall therefore stays a disclosed halt: funds are safe, the boundary holds and the exit of MEM-15 works, but clearing the stall requires a future protocol update whose procedure is not yet specified, and that dependency is a disclosed assumption rather than a v1 mechanism. (decision D-16: v1 has no recovery path of any kind; no operator, DAO or governance rescue exists, the one-named- exception wording added for D-15 is removed, and the future-update dependency is disclosed with its register entry.) Failure modes: a halt is quietly "fixed" by an operator, which both violates R2 and disguises a liveness limitation as a functioning protocol; or recovery is captured by a privileged party, which would be the same failure under a different name. In v1 there is no recovery mechanism to capture, and the halt is disclosed instead. Proven (enforced by the migration's removal of privileged levers, MIG-04)

WH-02 — objective evidence versus local suspicion A protocol-level penalty requires objective, self-contained, on-chain verifiable evidence: two signed messages of the same type at the same height and round with different block ids (CONS-11), or a signed message that violates a rule whose inputs are entirely on-chain. Everything else — a message that did not arrive, a height that did not advance, a proof that has not been submitted, a peer that did not answer a request — is local suspicion. Local suspicion may trigger local actions (retry, view change, reputation, peer selection, disclosure) but may never trigger a penalty, a recovery action, or a statement about what exists elsewhere. There is no stall-resolution trigger in v1: the objective settlement-stall predicate of the deferred action is deferred by D-16 and MUST NOT be implemented (DEFERRED.md §3), so non-receipt of a batch, proof or certificate remains local suspicion and nothing on L1 can convert a stall into a history-changing action. (decision D-16: v1 has no recovery path, the deferred trigger is not normative, and local suspicion never triggers a penalty or any recovery action.) (decision D-16; increment 04, narrow forced inclusion: the forced-inclusion rules of D-12 — the due set, the capped FIFO prefix, the order-and-non-omission duty of CONS-01(v) and the resolution modes of FI-13 — are live again and enforced in the proof, but they add no recovery path and no penalty: the breach of ECON-04 clause (6) stays a tombstone, a proposer that excludes a transaction is answered by proof rejection rather than a slash, and for unpublished transactions the protocol has no inclusion duty (LIVE-04).) Failure modes addressed: false accusations, and the more dangerous error of treating a timeout as a fault ("the sequencer was slashed after a landing deadline" is exactly the reasoning this rule forbids). Proven
WH-03 — false positives and false negatives, labelled unmeasured The specification must state, for every detection rule, both error directions: a false positive penalises a correct participant (for example, a validator whose vote was merely delayed being treated as absent), and a false negative lets a faulty participant escape (for example, a one-off selective-delivery attack that leaves no signed conflict). For each rule the specification states which direction is worse and why, and records that the rates are unmeasured with what would measure them (a fault-injection testbed with a modelled adversarial network). No rule may claim a detection rate. Failure mode: an unmeasured detection rate presented as a guarantee, or a design where the only safe path is perfect detection. unmeasured
WH-04 — reveal-later certificate: the analysis across locks, view changes and reconfiguration The protocol must resist the following schedule, which is mandatory in this specification: (1) a proposer selectively distributes a block to a subset; (2) honest validators vote according to their local views; (3) the attacker privately obtains a finality-related certificate; (4) other participants attempt a leader change or a validator change; (5) the attacker reveals the certificate after the alternative path has progressed. The required conclusion is that two conflicting histories cannot both be canonical at the same time: at or below the latest L1-accepted checkpoint no conflicting history can receive a replacement guarantee at all, and above it no protocol path in v1 replaces the canonical history, so a certificate revealed later is evidence against an equivocator when it conflicts under the same generation, never a second canonical history. That conclusion rests on the conjunction of three mechanisms, never on signature counting alone: (decision D-16: the reveal-later schedule no longer includes any recovery path, because the governance stall resolution and the other add-on mechanisms are deferred; the conclusion is scoped to the rules v1 actually has.)
  • Locks. A validator that precommitted a block at round R is locked on it and will not prevote a conflicting block at that height unless it sees a proof-of-lock-change at a strictly later round (CONS-04). Because a certificate implies more than one third of the voting power is correct and locked, no conflicting commit can form. This is why an unpublished certificate is harmless to safety: it is the lock, not the publication, that protects the decision.
  • View changes. A view change may change the proposer, but it may not unlock a validator that has not seen a later-round proof-of-lock-change. Therefore step (4)'s "alternative path" cannot produce a conflicting commit merely because the original certificate was hidden.
  • Reconfiguration. No lock state crosses an epoch boundary. The lock is per height (CONS-04(1)): it is released by that height's commit or by a strictly later same-height proof-of-lock-change, and CONS-09(3) states that a validator carries no lock state from a height of epoch e into e+1; a lock formed at a height of e on a value that did not finalize there is resolved at that height and is not carried forward as an independent constraint. Cross-height continuity is therefore exactly the parent-validity condition of CONS-01(iii), enforced at the boundary by the anchor duty of CONS-09(1)–(2): the first block of the new epoch must descend from the last block finalized in the closing epoch. The handoff's protection is that a certificate is judged under its own epoch's set and remains valid forever (CONS-08), so the closing epoch's decision is not re-judged by the new set and a stakeholder that rotates keys or changes its stake cannot escape it; the signed recovery generation is part of the lock and uniqueness rules (CONS-12), and no rule of v1 increments it because the action that would is deferred by D-16 — and a validator that equivocates across the boundary is caught by a same-(height, round) conflicting pair under the same generation, the only lock-related offence with admissible evidence (ECON-04). This closes review round 3 finding R3A-03: the retracted cross-height lock carry-over is removed from WH-04's reconfiguration mechanism, and the protection it names is the parent-validity condition plus epoch-scoped permanent certificates, not a surviving lock.
Failure mode: a design in which the alternative path discards the per-height lock within a height, or in which a validator-set change re-judges a certificate under a new set instead of under its own epoch's set (CONS-08), in which case the reveal-later schedule succeeds and two conflicting histories can both be treated as canonical without any slashable equivocation. (No path of v1 discards a second history above the latest L1-accepted checkpoint; the lock and reconfiguration mechanisms above are what prevent the conflict from arising in the first place, and the signed generation is the barrier any future replacement path must use — D-16.) Proven Assumed (premises: A-CONS-1 in every epoch; correct validators enforce CONS-02/CONS-04; the boundary argument of CONS-09, which is the named review target F1)

Governance stall resolution — deferred by decision D-16 (tombstone)

v1 has no recovery path of any kind, permissionless or governance-mediated (decision D-16). The timelocked, resume-only governance stall resolution that D-15 selected is deferred, together with aggregation (D-13); narrow forced inclusion (D-12) has since been revived as a live inclusion obligation by increment 04, which adds no recovery path. Heartbeat eligibility (D-14) has since been revived by increment 02 as a future-version selection filter, while the rotation that consumes it stays a gated tombstone (increment 02: heartbeat eligibility revived; increment 04: narrow forced inclusion revived as an inclusion rule; the rotation stays gated). A settlement stall halts the chain: funds are safe, the boundary of REC-01 holds and the exit of MEM-15 works, but clearing the stall requires a future protocol update whose procedure is not yet specified. The rules below are kept only as tombstones and MUST NOT be implemented; the register entry is DEFERRED.md §3.

The guarantee attached to a confirmation above the last accepted checkpoint is PoS-certified / provisional (STATUS-04). Any interface that shows such a confirmation MUST say that it is provisional and that v1 provides no in-protocol path that replaces it; calling it irreversible is a defect. (decision D-16: the replacement mechanism is deferred, the guarantee class above the checkpoint remains provisional, and no artifact may present a stalled chain as resumable by a v1 rule.)

The mechanism is deferred to the register: DEFERRED.md §3. The v1 position is the opposite of a recovery rule: v1 has no recovery path of any kind. (decision D-16: the governance stall resolution is deferred with the other add-on mechanisms, and clearing a settlement stall depends on a future protocol update whose procedure is not yet specified.) It is withdrawn to the register, DEFERRED.md §3, together with the mechanism it analysed. The v1 position is the disclosure it was written to support, stated without an analysis of a mechanism that does not exist: v1 has no recovery path of any kind; a settlement stall halts the chain; funds are safe, the boundary of REC-01 holds and the exit of MEM-15 works; and clearing the stall requires a future protocol update whose procedure is not yet specified. Its premises (A-CONS-1, A-CONS-2, A-DA-2, A-L1-1) and its Open items are not v1 obligations, and no measurement is owed for its falsifiers: the register keeps the findings so a future revival starts from them. (decision D-16: the governance stall resolution is deferred, so its resistance analysis is a tombstone and its Open items are closed by withdrawal rather than by measurement.) The id is retained so the reviewed analysis is not lost. deferred by D-16 (tombstone; register entry DEFERRED.md §3)
REC-04 — restart linkage after a stall resolution — DEFERRED by D-16 (tombstone) Deferred by decision D-16; not normative in v1 and MUST NOT be implemented. This id formerly stated the restart linkage after an executed governance stall resolution: the restored checkpoint, the resume point resumeHeight = lastLandedHeight + 1, and the withdrawal of the former predecessor-linkage and recovery-anchor rules. It is withdrawn to the register, DEFERRED.md §3, because v1 has no recovery path of any kind and therefore no discard and no restart-after-resolution case at all. The restart rules that remain normative are HALT-02: a correct participant resumes only from the highest finalized block whose data and certificate it can independently reconstruct, and the ordinary contiguity rule of CONS-01(iii), the ordinary anchor duty of CONS-09(1)–(2), and the signed generation check (CONS-10) apply unchanged. No retired-height record, recovery anchor or height gap exists in v1, and none may be introduced for a case that cannot occur. (decision D-16: the restart linkage is deferred with the governance stall resolution; the ordinary restart rules are the only ones.) Failure mode: an implementer keeps a recovery-anchor code path for a case that no v1 rule creates, and so invents a rule the specification withdrew. The id is retained so the reviewed linkage is not lost. deferred by D-16 (tombstone; register entry DEFERRED.md §3)
