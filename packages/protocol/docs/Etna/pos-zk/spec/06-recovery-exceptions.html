06 — Withholding, safe halt, restart, and the one named stall resolution

A PoS confirmation above the latest L1-accepted checkpoint is provisional. The permissionless bonded recovery was withdrawn by D-15; the timelocked, resume-only governance stall resolution that replaced it is live again as GOV-04 under increment 05 — one DAO-queued entry, a stored T_GOV_RESUME deadline, a permissionless execute() that consumes the entry; the action resumes settlement above the latest L1-accepted checkpoint and does not erase that range. It is the one named exception short of recovery; aggregation (D-13) and the heartbeat rotation (CONS-16) stay deferred and tombstoned, while narrow forced inclusion (D-12) and heartbeat eligibility (D-14) are live again by increment 04 and increment 02 — see the deferred-work register DEFERRED.md. A settlement stall halts the chain: funds are safe, the boundary of REC-01 holds and the exit guarantee of MEM-15 — a withdrawal proven against the last accepted checkpoint, with no new L2 blocks, no quorum and no validator — works; the stall is cleared only by the executed GOV-04 action, and clearing it still depends on governance liveness with no protocol bound (F-GOV-1, A-GOV-2). At or below the latest L1-accepted checkpoint — the checkpoint record written by the most recently accepted batch — nothing may be changed; above it history is provisional, and the only protocol path that may act on it is the executed GOV-04 action, which resumes settlement there and does not replace or erase the range. Ethereum finality is the separate, stronger property of STATUS-07. Any interface that shows a confirmation above the last accepted checkpoint must say that it is provisional, must name the one rule-bound action that may act on it (GOV-04: it resumes settlement and invalidates a superseded certificate only as a batch's head evidence), and must not present that action as a guarantee that a resolution will ever be queued or executed. (increment 05: the governance stall resolution is live with a consumed entry and a stored deadline, and clearing a settlement stall still depends on governance liveness; value above the last accepted checkpoint has no L1-provable claim and is not protected by the window. Increment 02: heartbeat eligibility is live but is a selection filter on future set versions, not a history-replacing path. R5R2-C-01: the resolution resumes settlement; it does not erase the range above the checkpoint, and a superseded certificate is invalidated only as a batch's head evidence.)

REC-01 — recovery boundary: no path may replace history at or below the latest L1-accepted checkpoint No contract function, client rule, timeout, validator rotation, admission rule, governance proposal executed through the ordinary upgrade path, operational procedure, or recovery invocation may change the canonical history at or below the latest L1-accepted checkpoint — the checkpoint record written by the most recently accepted batch. Above it, history is provisional and the only rule-bound action that may act on it is the executed stall-resolution action of GOV-04 (analysed in REC-02), under its objective trigger, stored timelock, resume-only and void-on-progress rules: it resumes settlement on the same chain and invalidates a superseded certificate only as a batch's head evidence — it neither replaces nor erases the range. The permissionless recovery stays withdrawn by D-15; aggregation remains deferred by D-16; the narrow forced inclusion revived by increment 04 is an inclusion rule that reads no L2 history and writes none, adds no recovery action and cannot replace a checkpoint (FI-14); and the heartbeat eligibility revived by increment 02 is a selection filter on future set versions, not a path that replaces history, with the rotation that would consume it still a gated tombstone (DEFERRED.md). (increment 05: the one named action on the range above the checkpoint is the revived, rule-bound stall resolution, which resumes settlement and never replaces or erases the range; increment 02: the revived mechanism is a selection filter on future set versions; increment 04: the revived inclusion obligation replaces no history; REC-01's guarantee at or below the checkpoint is unchanged. R5R2-C-01: resume, not erasure.) A future protocol update that adds a replacement path must preserve this boundary. Ethereum finality is a separate and stronger property, not the recovery floor: once the accepting L1 transaction is in a finalized Ethereum block, even an L1 reorganisation cannot undo it (STATUS-07); until then an accepted checkpoint is revocable only by an L1 reorganisation below finality (STATUS-06, L1-12), so an implementer must never read that property back as the recovery floor. Concretely: (a) no function exists whose effect is to replace an accepted block hash at or below the latest L1-accepted checkpoint or to discard state at or below it; the only rule-bound action on the range above that checkpoint is an executed stall resolution, which leaves the checkpoint record itself untouched and erases nothing above it — it invalidates a superseded certificate only as a batch's head evidence (GOV-04(c)); (b) no admission rule may reject a batch that extends the current L1 checkpoint (L1-04); (c) a certificate is judged under the validator set of its own epoch and stays valid as evidence forever (CONS-08), so validator rotation cannot re-judge it, and a certificate above a restored checkpoint is void for canonical purposes once its signed generation is superseded, but remains admissible as evidence; the signed recovery generation scopes certificates, locks and uniqueness (CONS-04, CONS-12), is incremented exactly once by a successful execute() of GOV-04 and by nothing else, and is judged by the two-case rule — the current value for a batch extending the checkpoint, the block's own header value for a certificate at or below it (CONS-05(2)); (d) no upgrade may be used as a substitute for the stall resolution: an upgrade must accept every history at or below the latest L1-accepted checkpoint (GOV-03), and history above that checkpoint may be acted on only by the executed action of GOV-04 — which resumes settlement and does not replace or erase it — and never by the ordinary upgrade path, which may neither perform the resume, nor move the entry's stored deadline, nor reset the generation (GOV-03(e)); (e) no data-first path in the sense this rule fixes may be introduced to "work around" an unsettled batch, in recovery or otherwise, because that would let an unproven history be treated as settled (L1-02, HALT-04). Publication is not that path (D-11): a batch's data MAY be published to L1 before its proof and recorded as a publication record, because publication writes no checkpoint, advances no protocol state and becomes relevant only when a later proof references it; what D5 forbids, and what this clause forbids, is a path by which a checkpoint or any other protocol state advances on data alone. The proving deadline that bounds a published-but-unproven record, and its discard-and-republish consequence, are owned by 04 and are not restated here. The live inclusion obligation reads no recovery mechanism: the forced-data register, the settlement frontier and the deletion-only prune of FI-10–FI-14 are settlement-side state; no rule of the FI family reads, writes or is discharged by a recovery, a stall resolution or a restored checkpoint, and the boundary above is untouched by them (increment 04; FI-14(2)). (RDC-04: the reason given was that v1 had no recovery mechanism; the executed stall resolution is live, and the obligation simply does not read it.) (D-11: data may be published before the proof; publication writes no checkpoint, so it is not a data-first path in this rule's sense.) (increment 05: the boundary is unchanged — nothing at or below the latest L1-accepted checkpoint is ever rewritten and history above it is provisional; the one rule-bound action on the range above the checkpoint is the stall resolution of GOV-04, which resumes settlement there and invalidates a superseded certificate only as a batch's head evidence, with aggregation still deferred and clearing a settlement stall still dependent on governance liveness, while the narrow forced inclusion revived by increment 04 replaces no history. R5R2-C-01: the action resumes; it does not replace or erase.) This rule is the boundary between the two guarantee classes: no path may change history at or below the latest L1-accepted checkpoint, and history above it is provisional. Its violation would turn a bounded rollback into unbounded history replacement, which no user decision authorises. Halting remains the correct local action when settlement cannot proceed; the stall resolution of GOV-04 is the only sanctioned way history above the checkpoint is the only sanctioned action on history above it, and it resumes settlement there rather than replacing or erasing it — it is objective, timelocked, resume-only and consumed by its own execution (DEFERRED.md). This closes the reviewer finding that made the Ethereum-finalized checkpoint the recovery floor: the floor is the latest L1-accepted checkpoint, and Ethereum finality is the separate, stronger property of STATUS-07 (D-15; restated by D-16). Proven (structural: the boundary of the replacement window plus four positive obligations)

Safe halt

HALT-01 — safe halt obligation A correct validator halts — it stops signing and stops advancing its finalized view — rather than choose between two histories or advance on unknown state. It halts when any of the following holds and cannot be resolved by a rule-legal action: (a) it cannot obtain the data for a finalized or locked block (A-CONS-5 failed); (b) it cannot obtain a quorum for a height within the timeout ladder (A-CONS-2 failed); (c) the L1 facts it must consume are not yet Ethereum-final, or its L1 view disagrees with the consensus view (SYS-02); (d) the L1 validator-set commitment for the epoch it is about to enter is absent (CONS-13); (e) the unsettled-depth cap would be exceeded (HALT-03). Halting is a correct outcome, not a failure of the protocol: it is the action that preserves every height at or below the latest L1-accepted checkpoint and keeps the node inside its rules. A node that halts must keep serving what it has, and must keep its state so it can resume. Halting never authorises discarding history, and never authorises treating a publication as settlement: publishing a batch's data before its proof is permitted (D-11), but a publication record advances no checkpoint, so no participant may act on it as if a batch had landed (REC-01(e)). A validator's halt is a local safety action and is not a stall-resolution trigger: the action is available only while the objective settlement-stall condition of GOV-04(a) holds, its queueing is a DAO transaction, and no participant can invoke it on its own or declare it early. A halt caused by an unlandable batch is answered by retrying and by continuing to serve; if settlement nevertheless stalls past T_STALL_GOV, the timelocked, resume-only stall resolution of GOV-04 is the sanctioned remedy for that stall, with funds safe, the boundary of REC-01 holding and the exit of MEM-15 working, but clearing still depends on governance liveness with no protocol bound (F-GOV-1, A-GOV-2). The stall resolution clears no other halt: it changes no validator set and manufactures no missing epoch-set entry and no unavailable quorum, so a halt under (b) or (d) persists until the entry is appended and Ethereum-final or the quorum returns (LIVE-01). The heartbeat eligibility of MEM-13 is live (increment 02) and excludes an entry that stops signing from set versions committed after its last covered window, but exclusion changes only future composition: the committed roster that stalled the chain is immutable and the rotation that would consume a restart set (CONS-16) remains a gated tombstone, so where (b) is caused by validators that have stopped attesting, the halt is not escapable by any rule of v1 that acts on the committed epoch. This closes review round 4 finding R4-LIV-09: recovery is not presented as the remedy for halts it cannot clear. (increment 05: the stall resolution is live and is the named remedy only for the settlement-stall case, with governance liveness disclosed as F-GOV-1; increment 02: the heartbeat eligibility is live but excludes only from future set versions, so it is not a recovery route for a committed epoch.) Failure modes: an implementer, faced with a stuck chain, invents an "unstick" action; or a participant treats its own halt as authority to roll history back. Neither is permitted — the only sanctioned action on history above the checkpoint is the rule-bound action of GOV-04, which resumes settlement there and erases nothing (R5R2-C-01: resume, not replacement), and which no participant can invoke on its own (DEFERRED.md). Proven Assumed (the halt conditions are normative; whether they are met is assumed)
HALT-02 — restart rules After a halt, a correct participant resumes only from the highest finalized block whose data and certificate it can independently reconstruct. It must never adopt an alternative history at or below the latest L1-accepted checkpoint, and must never treat a timeout during the halt as evidence that a certificate does not exist (STATUS-10). On restart: (a) each validator enforces a signed-message uniqueness check over its own signing history — no message of the same type at the same height, round and recovery generation may be signed twice, including after a restart or a state resync, and a validator that cannot prove it has not already signed for a (height, round, type, generation) must not sign (the amnesia case is treated as a signing fault, not as a fresh start); (b) a validator that resumes must re-verify the epoch and set for the height it is resuming at rather than trusting its cached set; (c) nodes must not accept a replayed historical message as new — every vote carries the epoch and round, and the receiving rules reject messages for heights already finalized; (d) a resumed node's first act is a data and certificate sync, not a proposal. After an executed stall resolution the restored checkpoint is the current L1-accepted checkpoint — execution writes no checkpoint and leaves the record untouched (GOV-04(c)) — so it is the highest canonical checkpoint: a node must adopt it, must not treat a block above it as settled on the strength of a superseded-generation certificate, and must apply every clause of this rule unchanged — no double signing, no replayed message, no ordering by timeout. The resumed chain begins at resumeHeight = lastLandedHeight + 1, derived and never stored; the restored checkpoint block is its immediate predecessor, there are no skipped heights and no recovery anchor, and the ordinary contiguity rule of CONS-01(iii) and the ordinary anchor duty of CONS-09(1)–(2) apply unchanged, with B_anchor the restored checkpoint block at firstHeight − 1; the anchor certificate is judged under the generation of B_anchor's own header (CONS-05(2)(b), PRF-05(ii)(a)) and the batch's head under the current generation (REC-04). (increment 05: restart after a resolution is the ordinary linkage at the restored checkpoint, with the two-case generation rule making the anchor certificate judgeable; the recovery anchor and the withdrawn recovery linkage do not apply. R5R2-C-01: the range above the checkpoint is not erased; only a superseded certificate's use as head evidence is invalidated.) Failure modes addressed: "amnesia" double-signing after a restart, replaying old votes, and a restart that silently adopts a competing branch — the classic way a safe halt becomes an unsafe restart. Proven (the signing-history rule rests on the validator's own durable state, an implementation gate)
HALT-03 — consensus-enforced unsettled-depth cap (backpressure) Define the unsettled depth at a height as the number of L2 blocks between the highest L1-accepted checkpoint and the block being considered. A correct validator must not prevote or precommit a block whose unsettled depth would exceed D_MAX − MARGIN_V. Exactly one enforcement point: the validators. land MUST NOT reject an over-depth batch, because doing so could make a legitimately finalized range permanently unlandable and would violate L1-04 (*review round 2, finding R2-LIV-07*). D_MAX is derived from the retention window, the permitted proof latency and the settlement pipeline, and not from the retention window alone: D_MAX = floor((RETENTION_WINDOW − T_PROOF_MAX_PERMITTED − T_SETTLE_PIPELINE) / L2_BLOCK_INTERVAL), recorded with its derivation in 09. MARGIN_V is mandatory and is at least the number of L2 blocks produced during one Ethereum finality depth, because a validator's view of the L1 checkpoint is itself only usable at that depth (SYS-02); without the margin a validator can systematically under-estimate depth and overshoot the cap. The cap is a consensus rule with a single enforcement point. Honest statement of what that costs: because the cap cannot be enforced at L1 without stranding a legitimate extension, a quorum that ignores it is not objectively punishable at L1, and a cap violation is therefore a liveness failure that is disclosed rather than a slashing offence (WH-02, LIM-01). When the cap binds, production stops and the chain is in the safe-halt state until provers catch up. No action relaxes the cap: a cap binding is a halt and not a stall-resolution trigger, the GOV-04 action changes no cap and cannot advance past it, and production resumes only when provers catch up and the unsettled depth falls back under the cap. (increment 05: the unsettled-depth cap is unchanged; the live stall resolution is not a cap-relaxing mechanism, and no mechanism may be used to advance past the cap or to bypass it.) The cap must also be jointly satisfiable with the evidence window: the coupling inequality is stated normatively in ECON-07(7), and D_MAX must be reduced until it holds (*review round 2, finding P-R2-08*). It is also jointly constrained with the D6 envelope, and RETENTION_WINDOW is chosen from that constraint rather than independently: a proof that consumes the whole envelope must leave an unsettled depth at or below the depth at which validators stop, so D_MAX · L2_BLOCK_INTERVAL ≥ T_PROOF_ENVELOPE + T_SETTLE_PIPELINE + MARGIN_V · L2_BLOCK_INTERVAL, equivalently D_MAX − MARGIN_V ≥ (T_PROOF_ENVELOPE + T_SETTLE_PIPELINE) / L2_BLOCK_INTERVAL (the margin term is MARGIN_V · L2_BLOCK_INTERVAL, in seconds, because MARGIN_V is measured in L2 blocks). (registration audit: the seconds-form allowance of this inequality is the registered MARGIN_D, with MARGIN_D ≥ MARGIN_V · L2_BLOCK_INTERVAL, as stated in 09.) Because this rule derives D_MAX from RETENTION_WINDOW, the inequality is also a lower bound on the retention window: in particular RETENTION_WINDOW MUST be large enough that floor((RETENTION_WINDOW − T_PROOF_MAX_PERMITTED − T_SETTLE_PIPELINE) / L2_BLOCK_INTERVAL) − MARGIN_V ≥ (T_PROOF_ENVELOPE + T_SETTLE_PIPELINE) / L2_BLOCK_INTERVAL (a sufficient form is RETENTION_WINDOW ≥ T_PROOF_ENVELOPE + T_PROOF_MAX_PERMITTED + 2 · T_SETTLE_PIPELINE + MARGIN_V · L2_BLOCK_INTERVAL + L2_BLOCK_INTERVAL), so the retention window is derived backwards from the inequality, never selected on its own and checked afterwards. If the inequality is violated, D_MAX − MARGIN_V can be zero or negative, in which case no block at a positive unsettled depth may be voted and production cannot advance past the current checkpoint. The envelope term is D6's planning assumption T_PROOF_ENVELOPE, not T_PROOF_MAX_PERMITTED (the permitted bound of 09): the promise is that a normal proof never binds the cap. This closes review round 3 finding R3-LIV-02: HALT-03 carries the joint cap/envelope inequality, so a normal 30-minute proof can never trigger the cap, and RETENTION_WINDOW is stated to be chosen from that inequality rather than independently. D_MAX is a bound on commitment creation, not on proving latency, and a normal proof taking the whole of the D6 envelope (up to 30 minutes, i.e. 900 blocks at 2 s) is not misconduct and not grounds for a stall-resolution trigger: a slow proof neither makes the trigger true (it is strictly larger than the D6 envelope) nor justifies any action (GOV-04(a), (g)). Failure modes addressed: unbounded growth of unsettled history (which is exactly the state in which an availability failure becomes unrecoverable), and an implementer treating a slow proof as a fault. Proven unmeasured (D_MAX's value depends on measured retention and proving throughput)
HALT-04 — no emergency operator, no discretionary DAO rescue, and one named rule-bound exception No emergency key, guardian, or operational procedure may be required to preserve any invariant of this specification, and none may be introduced to "resolve" a halt. There is exactly one named exception, and it is not a DAO rescue: the rule-bound, timelocked, resume-only stall resolution of GOV-04 (analysed in REC-02). Governance chooses nothing at execution: no state, no checkpoint, no height, no validator set and no configuration value; the entry names nothing, resumeHeight is derived, the effect is fixed by L1 state, the timelock of an entry already queued is stored and cannot be moved, and the discretion over the values future entries will use is named F-GOV-4 rather than denied. The action is not an operator, guardian or discretionary DAO rescue: the permissionless recovery stays withdrawn (D-15), aggregation stays deferred (D-16), heartbeat eligibility revived by increment 02 is a future-version selection filter and not a recovery path, and the rotation that would consume it stays a gated tombstone (DEFERRED.md). No operator, DAO or governance actor may advance, rewind or replace the checkpoint outside that action, and the action itself writes no checkpoint. Nothing may be required and no DAO intervention is permitted: specifically, there is no function that a privileged party can call to advance, rewind, or replace the checkpoint; and no publication may be used to unblock settlement: publishing a batch's data before its proof is permitted (D-11), but the publication record advances no checkpoint and confers no status, so it can never substitute for a proof (REC-01(e)). If progress requires information or participation that no rule-legal action can obtain, the protocol says so and stops; it does not promote a privileged fix. A stall that no valid action can clear — including one governance never queues or never executes — stays a disclosed halt: funds are safe, the boundary holds and the exit of MEM-15 works, and clearing a settlement stall by the GOV-04 action depends on governance liveness with no protocol-level bound (F-GOV-1, A-GOV-2). (increment 05: the one-named-exception wording is restored in its corrected form — the exception is the rule-bound, consumed-entry action, not a discretionary rescue — and the governance-liveness dependency is disclosed with its falsifier.) Failure modes: a halt is quietly "fixed" by an operator, which both violates R2 and disguises a liveness limitation as a functioning protocol; or recovery is captured by a privileged party, which would be the same failure under a different name. The one live action is rule-bound and consumed by its own execution, so there is no discretionary recovery lever to capture; the halt is disclosed instead. (increment 05.) Proven (enforced by the migration's removal of privileged levers, MIG-04)

WH-02 — objective evidence versus local suspicion A protocol-level penalty requires objective, self-contained, on-chain verifiable evidence: two signed messages of the same type at the same height and round with different block ids (CONS-11), or a signed message that violates a rule whose inputs are entirely on-chain. Everything else — a message that did not arrive, a height that did not advance, a proof that has not been submitted, a peer that did not answer a request — is local suspicion. Local suspicion may trigger local actions (retry, view change, reputation, peer selection, disclosure) but may never trigger a penalty, a recovery action, or a statement about what exists elsewhere. Non-receipt is never converted into an action by a participant's local view: the objective settlement-stall predicate of GOV-04(a) is read from L1 state alone and can be satisfied only by a genuine stall, queueing is a DAO transaction, and execution is permissionless only over an entry that already exists, is live and is past its stored deadline — so local suspicion still never triggers a penalty or a history-changing action. (increment 05: the trigger is live but L1-observable and never participant-declared; non-receipt remains local suspicion.) (decision D-16; increment 04, narrow forced inclusion: the forced-inclusion rules of D-12 — the due set, the capped FIFO prefix, the order-and-non-omission duty of CONS-01(v) and the resolution modes of FI-13 — are live again and enforced in the proof, but they add no recovery path and no penalty: the breach of ECON-04 clause (6) stays a tombstone, a proposer that excludes a transaction is answered by proof rejection rather than a slash, and for unpublished transactions the protocol has no inclusion duty (LIVE-04).) Failure modes addressed: false accusations, and the more dangerous error of treating a timeout as a fault ("the sequencer was slashed after a landing deadline" is exactly the reasoning this rule forbids). Proven
WH-03 — false positives and false negatives, labelled unmeasured The specification must state, for every detection rule, both error directions: a false positive penalises a correct participant (for example, a validator whose vote was merely delayed being treated as absent), and a false negative lets a faulty participant escape (for example, a one-off selective-delivery attack that leaves no signed conflict). For each rule the specification states which direction is worse and why, and records that the rates are unmeasured with what would measure them (a fault-injection testbed with a modelled adversarial network). No rule may claim a detection rate. Failure mode: an unmeasured detection rate presented as a guarantee, or a design where the only safe path is perfect detection. unmeasured
WH-04 — reveal-later certificate: the analysis across locks, view changes and reconfiguration The protocol must resist the following schedule, which is mandatory in this specification: (1) a proposer selectively distributes a block to a subset; (2) honest validators vote according to their local views; (3) the attacker privately obtains a finality-related certificate; (4) other participants attempt a leader change or a validator change; (5) the attacker reveals the certificate after the alternative path has progressed. The required conclusion is that two conflicting histories cannot both be canonical at the same time: at or below the latest L1-accepted checkpoint no conflicting history can receive a replacement guarantee at all, and above it the only rule-bound action on history is the executed stall resolution, which resumes settlement and invalidates a superseded-generation certificate only as a batch's head evidence rather than adopting it, so a certificate revealed later is evidence against an equivocator when it conflicts under the same generation, never a second canonical history. That conclusion rests on the conjunction of three mechanisms, never on signature counting alone: (increment 05: the reveal-later schedule includes the one named rule-bound action, whose effect is resume-only and cannot make a superseded certificate canonical, and the range above the checkpoint is not erased (R5R2-C-01); the conclusion is scoped to the rules v1 actually has.)
  • Locks. A validator that precommitted a block at round R is locked on it and will not prevote a conflicting block at that height unless it sees a proof-of-lock-change at a strictly later round (CONS-04). Because a certificate implies more than one third of the voting power is correct and locked, no conflicting commit can form. This is why an unpublished certificate is harmless to safety: it is the lock, not the publication, that protects the decision.
  • View changes. A view change may change the proposer, but it may not unlock a validator that has not seen a later-round proof-of-lock-change. Therefore step (4)'s "alternative path" cannot produce a conflicting commit merely because the original certificate was hidden.
  • Reconfiguration. No lock state crosses an epoch boundary. The lock is per height (CONS-04(1)): it is released by that height's commit or by a strictly later same-height proof-of-lock-change, and CONS-09(3) states that a validator carries no lock state from a height of epoch e into e+1; a lock formed at a height of e on a value that did not finalize there is resolved at that height and is not carried forward as an independent constraint. Cross-height continuity is therefore exactly the parent-validity condition of CONS-01(iii), enforced at the boundary by the anchor duty of CONS-09(1)–(2): the first block of the new epoch must descend from the last block finalized in the closing epoch. The handoff's protection is that a certificate is judged under its own epoch's set and remains valid forever (CONS-08), so the closing epoch's decision is not re-judged by the new set and a stakeholder that rotates keys or changes its stake cannot escape it; the signed recovery generation is part of the lock and uniqueness rules (CONS-12), and it is incremented exactly once per executed stall resolution (GOV-04(c)) — and a validator that equivocates across the boundary is caught by a same-(height, round) conflicting pair under the same generation, the only lock-related offence with admissible evidence (ECON-04). This closes review round 3 finding R3A-03: the retracted cross-height lock carry-over is removed from WH-04's reconfiguration mechanism, and the protection it names is the parent-validity condition plus epoch-scoped permanent certificates, not a surviving lock.
Failure mode: a design in which the alternative path discards the per-height lock within a height, or in which a validator-set change re-judges a certificate under a new set instead of under its own epoch's set (CONS-08), in which case the reveal-later schedule succeeds and two conflicting histories can both be treated as canonical without any slashable equivocation. REC-03 — governance stall resolution: resistance analysis, residuals and falsifiers (revived by increment 05) Premises, stated separately from the conclusion. The claim below is conditional on all four, and none may be silently dropped: (P1) A-CONS-1 — fewer than one third of the voting power is Byzantine, in every epoch; (P2) A-CONS-2 — after GST, delivery among correct validators is timely, so finalization continues with the honest supermajority (CONS-07); (P3) A-DA-2 — at least one honest, adequately-resourced prover completes each committed batch's proof inside the envelope, and the batch data is obtainable by it (or published to L1 by any observer before the proving deadline, with the publication recorded while the blobs are retrievable, DA-01); (P4) A-L1-1 — L1 includes valid transactions within a bounded delay and does not reorganise below finality. All four are assumptions, not measurements, and the economic conditions they touch are unmeasured until Phase B (09). (increment 05: the analysis is re-derived around the consumed-entry governance action; the withdrawn recovery's bond, reward and invoker-incentive premises are removed with the mechanism they priced.)
The claim, restricted to what the action supports. Within P1–P4, a sub-threshold coalition — any set of participants holding less than one third of the voting power — cannot make the stall-resolution trigger true. Finalization continues with the honest supermajority (P1, P2); proposer selection is stake-weighted and rotates, so a coalition selected for strictly fewer than one third of slots in expectation cannot censor indefinitely (CONS-06); data is served (P3) and, where a holder has the body, publication is permissionless, so any account may put it on L1 in its own transaction (ECON-13); proving is permissionless and rewarded, and any account may land a proof (L1-10, L1-11); and L1 includes the landing transaction (P4). The checkpoint therefore keeps advancing, lastLandedHeight strictly increases, and T_STALL_GOV is strictly larger than the D6 envelope (GOV-04(a), (g)), so the trigger never becomes true and no entry can be validly queued. This is a claim about rule-legal behaviour under P1–P4; everything outside them is a residual or a falsifier below.
What making the trigger true would require. It means holding the checkpoint still for the whole window, so it requires breaking P3 or P4, and there are exactly three ways: (i) suppress every prover, so no proof exists to land (P3 fails); (ii) censor every landing transaction at L1, so a produced proof is never included (P4 fails); or (iii) price the protocol out of the blob market for the whole stall window, so no landing transaction is includable at a payable cost — an L1 block-space and market-power condition, not an L2 action (L1-01, ECON-02 clause 1).
What the replacement removes. There is no bond to size, no escalation, no cooldown, no completion transition, no cancellation predicate to define, no certificate bundle for L1 to verify, no maximality question about which certified heights to retire, and no completion reward: the action has no calldata that influences its outcome, execute() takes no outcome-affecting argument, and no value is transferred at all. An adversary cannot buy a trigger, cannot farm a completion and cannot exploit an under- or over-sized bundle. Conversely, a selective outcome is impossible by construction: the action names nothing and treats the whole class above the checkpoint alike — its signals are not carried into the resumed settlement — so an attacker inside that range cannot save its own effects while destroying a counterparty's (R5R2-C-01: the action selects nothing and erases nothing).
The generation fix, in its corrected two-case form. The generation fix is what keeps a superseded certificate out of the head role: it cannot serve as the head certificate of a batch extending the checkpoint (CONS-05(2)(a)), while the range itself is not erased and any block of it may stand as an ancestor of a head produced under the new generation. The generation is a field of the signed vote and header bytes; the action increments it exactly once and validators sign the new generation. A batch extending the checkpoint must carry the current generation (CONS-05(2)(a)); a certificate at or below the checkpoint — including the anchor certificate of the first post-resolution epoch-opening batch — carries the generation of the block it certifies and is not compared with the current one (CONS-05(2)(b), PRF-05(ii)(a)). A block of the superseded generation at resumeHeight descends from the same restored checkpoint as the resumed first block, so contiguity alone cannot separate them; the signed generation does, by denying the certificate the head role (R5R2-C-01: supersession is head-only, not erasure). No retired-height record and no recovery anchor remain.
Residuals, stated honestly. (1) Governance liveness. (2) Stalled transactions are not carried into the resumed settlement. (3) Why a superseded-generation certificate cannot be the head, and where the boundary is. A superseded-generation certificate is void at the acceptance rule and cannot serve as a batch's head certificate (REC-02, Generation fix; CONS-05(2)(a), CONS-12). For a height > resumeHeight, the canonical parent at height − 1 is a block of the resumed chain, so a descendant the resumed chain does not include also fails the parent-validity condition of CONS-01(iii); a block of the range that the resumed chain does include is an ordinary ancestor and is not rejected on account of the generation in its own header (PRF-05(ii)(a)). At height = resumeHeight the superseded block and the resumed first block both descend from the restored checkpoint, so contiguity alone cannot separate them and the signed generation is the binding mechanism that denies the head role: a new-generation block at that height is new history signed by the validators under the new generation, while the superseded block's old-generation certificate can never be accepted as head evidence — though the block remains valid history that a later batch may extend. The superseded branch can be neither the head (superseded generation) nor the anchor (B_anchor is pinned by prevBlockHash to the restored checkpoint block, which execution leaves untouched). (R5R2-C-01: the range is superseded, not erased; the requirement is head-only.) That is why no retirement record is needed and why the lock scoping follows the generation (CONS-04(2)).
(4) Validator duty at the restart. A correct validator MUST NOT prevote or precommit any block at firstHeight unless it has itself verified, from Ethereum-final L1 state, the checkpoint record at prevHeight and that firstHeight = lastLandedHeight + 1; a validator that cannot obtain them stays silent or prevotes NIL, which is a stall and not a safety loss (CONS-15, HALT-02). It MUST NOT treat a block above the restored checkpoint as settled on the strength of a superseded-generation certificate, and it MUST verify the header's recovery_generation under the two-case rule: the current value for a block above the checkpoint, the block's own header value at or below it (CONS-05(2)). (increment 05: the ordinary checkpoint and two-case generation checks replace the withdrawn substitute duty. R5R2-C-01: the range is not erased and the generation rule is head-only.) Failure mode: an implementer keeps a recovery-anchor code path or a max(…) contiguity form for a case that no rule creates, or lets the first post-resolution block name a block above the restored checkpoint as its parent, or compares the anchor certificate with the current generation and makes the first epoch-opening batch after a resolution unprovable. The single checkpoint link of (1), the two-case generation rule of (2) and the signed generation of (3) are the answers, and none needs a retired anchor. Proven Assumed (the linkage is the ordinary contiguity rule; the anchor certificate is pinned by prevBlockHash and judged under its own header generation; the validator duty rests on each validator's own Ethereum-final L1 view, SYS-02 — increment 05)
