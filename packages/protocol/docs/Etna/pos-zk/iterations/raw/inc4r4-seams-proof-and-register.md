# Increment 04 round 4 — seams between the rules, the proof and the register

**Reviewer:** independent adversarial reviewer, increment 4 round 4, angle seams-proof-and-register. **Snapshot:** d94117998, extracted with git archive.

**Counts: Critical 1 · High 0 · Medium 0 · Low 1.**

The round-3 repairs are mostly consistent across the seam: FI-11(4)'s quotation of CONS-01(v) is word-for-word identical for the whole quoted passage, PRF-04(vi) pins the same turns, names the same exhaustive byte classes and the same intrinsic-gas/signature requirements, keeps the increasing-index condition scoped to executed transactions, and states the credit-ordering edge as the disclosed F-FI-3 rather than denying it; FI-12's cap/R still agree with the walk and the duty; the register rows carry the corrected properties. The Critical is a pair of individually true clauses that are jointly false — the same shape as rounds 1-3 — created by the round-3 repair itself: the repair excluded the block's base fee from the forceability and void tests (correctly, against producer steering) and added a gas-based executability floor, but executability also requires the transaction's declared fee cap to cover the block's base fee, and nothing guarantees that.

---

## F1 — Critical: a live, byte-valid, permissionless record whose transaction declares a fee cap below the block base fee is forceable and demanded but carried by no valid block, so it pins the frontier until expiry

**Severity: Critical.** Rationale: FI-13(2) deliberately excludes the base fee from forceability, voidness and dueness, and FI-13(1)(b)'s exhaustive byte-decidable classes contain no fee-market class; at the same time FI-13(1)(a)'s discharge ground is exactly two conditions (declared nonce not equal to the sender's nonce at the turn, or balance below gasLimit x maxFeePerGas + value) and the walk therefore calls a transaction with nonce equal and a sufficient balance executable and requires it to appear. A transaction whose maxFeePerGas is below the base fee of every block it could occupy cannot be included in any valid block (Ethereum-equivalent execution validity; the guest cannot execute it either), so the position is unresolvable while the record is live, every proof in [c, c + R) is rejected, R is computed rather than chosen and the advance of FI-11(3)(a) is unconditional — a chain-wide settlement freeze reachable by one permissionless publication, repeatable at one publication per T_PROVE_DEADLINE. This is the R4R1-M-01 class the increment exists to close, reintroduced through the fee seam.

**File + rule id.** spec/04 FI-13(2), final sentences: "the including block's base fee, its gas limit and its remaining gas are **not inputs** to forceability, voidness or dueness" and "So the predicate calls no unexecutable transaction forceable ... **no transaction exists that (2) calls forceable and no valid block can carry**"; FI-13(2)(v) (the charge is "gasLimit x maxFeePerGas + value — t's own declared maximum charge", with no fee-cap floor); FI-13(2)(ii) (the round-3 repair adds only the intrinsic-gas floor); FI-13(1)(a) (the two-condition discharge ground); FI-13(1)(b) (the exhaustive classes (A)-(D): decode failure, chain-id mismatch, unrecoverable signature, intrinsic-gas shortfall); FI-13(1) final sentence and FI-13(5) (totality); spec/02 CONS-01(v) ("a transaction this clause demands is one a valid block can carry"); spec/05 PRF-04(vi) (the guest must reject a proof in which a transaction that can execute at its turn does not appear); spec/04 FI-11(3)(a) (unconditional advance). The register carries the same false claim: spec/09, "intrinsic-gas floor is part of forceability, so the two checks agree on **a transaction no valid block can carry**".

**Assumptions.** None beyond the specification's own: publication is permissionless (DA-07); the record's payload is opaque data the contract does not validate; execution validity is Ethereum-equivalent, so a block containing a transaction with maxFeePerGas below its base fee is invalid, and the guest's re-execution rejects it too.

**Attack trace.** 1. The attacker signs a well-formed type-2 transaction t with maxPriorityFeePerGas = maxFeePerGas = 0 (or 1 wei), nonce equal to its own current nonce, gasLimit at or above the intrinsic gas of its data (a plain transfer, 21000), value 0, and a balance that trivially covers gasLimit x maxFeePerGas + value = 0. Every byte-decidable requirement of FI-13(2) holds: chain id matches, the signature recovers, the gas limit is at or above the intrinsic floor and below FI_RECORD_GAS_MAX, and the record stays within FI_ITEM_MAX_BYTES and the transaction-count bound. 2. The attacker publishes the record (DA-07); the contract stores it unvalidated. 3. After FI_INCLUSION_DELAY the record is due at A and live (not dead), and no (1)(b) limb applies: it is not over-bound and none of the exhaustive classes (A)-(D) holds. 4. At t's turn the walk applies (1)(a)'s discharge test: the nonce equals the sender's nonce, and the balance is not below gasLimit x maxFeePerGas + value — so t is not discharged and must execute. 5. No valid block can include t: the L2 charges the execution base fee (CONS-01(viii), ECON-02 clause 7(a)) and a transaction whose fee cap is below the block's base fee is not includable; the base fee of an Ethereum-equivalent chain does not fall to a zero or one-wei cap by any rule this specification registers. 6. Therefore the position is unresolvable while the record is live. Once the frontier reaches it (d(A) is monotone, R = min(d(A) - c, FI_MAX_PER_BATCH) is computed, and the walk must resolve every position in [c, c + R)), FI-11(2)(4) and PRF-04(vi) reject every proof, FI-11(3)(a) cannot be satisfied, and land can never succeed — settlement stops chain-wide until the record dies (T_PROVE_DEADLINE after publication). The attacker repeats with one publication per cycle; no key, stake, validator or producer cooperation is needed.

**Fault-model verdict.** Inside the fault model. The attacker uses one permissionless publication and one self-signed L2 transaction that is never executed; nothing in the fault model is violated, and the honest path cannot resolve the record either (there is no valid block to carry t while its cap is below the base fee).

**Attacker cost.** One L1 publication per T_PROVE_DEADLINE, plus one self-signed transaction with a zero fee cap.

**Requirement affected.** FI-12(5)'s no-halt claim; FI-13(5)'s totality as a rule property; FI-11(3)(a)'s satisfiability; CONS-01(v)'s claim that a demanded transaction is one a valid block can carry; the increment's headline guarantee (F-FI-2's conditionality does not cover this: this is not an arrival-rate case).

**Suggested repair (owner's call).** Restore totality by making the fee dimension a *registered* constant, not the block's base fee, so no producer input enters and the class is decidable from the record's bytes and registered constants like classes (A)-(D): add a fifth exhaustive class — "a transaction whose declared maxFeePerGas is below the registered FI_MIN_EXEC_FEE_CAP" — and a registered relation that FI_MIN_EXEC_FEE_CAP is at or above the maximum base fee the L2 fee schedule can produce in any window (an Open premise recorded like the FI capacity relation, F-FI-1), or, equivalently, extend (2)(v)'s executability test to require maxFeePerGas at or above that registered floor so a low-cap transaction is discharged rather than demanded. Then delete or qualify the two claims that are now false (FI-13(2)'s "no transaction exists that (2) calls forceable and no valid block can carry", CONS-01(v)'s "a transaction this clause demands is one a valid block can carry", and the 09 row's "a transaction no valid block can carry") so they read "... that no valid block can carry for a reason this predicate or the enumerated classes cover". Extending the discharge ground to the block's actual base fee instead would reopen R6-D12-05's producer steering (a producer can push the base fee up by block contents), so the registered-floor form is the one consistent with this round's reasoning.

**Evidence.** spec/04 FI-13(1)(a), (1)(b)(A)-(D), (2)(i)-(v) and (2) final sentences, (3), (5); spec/05 PRF-04(vi); spec/02 CONS-01(v) and (viii); spec/09 FI rows; grep: maxFeePerGas occurs in the FI rules only inside the balance charge, and "base fee" only in the exclusion sentence.

## F2 — Low: the register's FI row repeats the same "no valid block can carry" claim and does not carry the enumerated byte classes

**Severity: Low.** Rationale: the register is the surface an implementer reads first, and the row states the byte classes only via the intrinsic-gas floor; with F1's class added the register and the index should name the exhaustive class list so the register and the rules cannot drift (the same reasoning as round-3 F1, which fixed the rule and the proof but not the register).

**File + rule id.** spec/09 FI rows (the row quoting the intrinsic-gas floor and "a transaction no valid block can carry"); spec/index.html FI/MEM row if it summarises the resolution modes. **Fix:** add the class list (decode failure, chain-id mismatch, unrecoverable signature, intrinsic-gas shortfall, and the F1 fee-cap class) and re-word the claim.

**Evidence.** spec/09 FI rows; spec/index.html; FI-13(1)(b)/(2).

## Seam checks that pass (both sides read)

1. **FI-11(4)'s quotation of CONS-01(v) is word-for-word identical.** I normalised whitespace and compared the passage from "For every block h of the range" through "...a block that cannot is not." inclusive, plus the sentence "The obligation itself is enforced in the proof ... the rejected proof is the whole enforcement.": 2599 characters match exactly between spec/02 CONS-01(v) and spec/04 FI-11(4); the texts diverge only after the quotation ends (CONS-01(v) continues with its increment note, FI-11(4) with its review note).
2. **PRF-04(vi) enforces the same turn, predicate, scope and classes.** It pins the turn by position with the same three cases (immediately before the transaction's own position when it appears; immediately before the record's next appearing transaction when it does not; the end of the batch's execution when no later transaction appears), requires the guest to recompute that pre-state from the batch's own execution and never from a witness-supplied position, accepts a discharge only under the same two conditions (nonce not equal there, or balance below gasLimit x maxFeePerGas + value), rejects a transaction that can execute at its turn and is omitted or claimed discharged, scopes the increasing-index condition to appearing transactions only, and names the same exhaustive byte classes (decode failure, chain-id mismatch, unrecoverable signature, intrinsic-gas shortfall) plus the intrinsic-gas and signature-recovery requirements inside the predicate. It also carries the corrected producer story: the void limbs have no producer-set input, and the only producer-set input to the walk is where a third-party credit lands relative to a turn, named as the residual F-FI-3. No clause in the guest check rests on the retracted "producer cannot move the balance" claim.
3. **FI-12's cap and R agree with the walk and the duty.** R = min(d(A) - c, FI_MAX_PER_BATCH) is still the size of the window the walk must resolve (c' = c + R meets the advance with equality), W is the live prefix and the gas condition batchGasCapacity >= W x itemGasBound is conservative because void and dead positions cost no gas but live void ones are still counted in W; the per-block duty has no count, quota or capacity constant and defers to the cap in positions per batch (CONS-01(v), FI-11(4)); FI-12(5)'s no-halt argument depends on the walk being total, which F1 falsifies for one class.
4. **The register rows carry the corrected properties,** with the F2 gap: the over-bound limb is stated live-only in 09, the balance is stated movable by anyone with the credit enabling but never discharging, and the F-FI-3 residual is named. **Round-3 copy edits:** "void individually" is gone, the over-bound void carries its live-only qualifier, and the course pages carry no review identifiers (grep). **L1-04, the exit and the tombstones:** FI-11(1) keeps the obligation out of the admission rules, the exit non-interaction rule at spec/04 is unchanged with zero FI names on the membership/exit page, ECON-04(6)/ECON-13(4) remain tombstones, and PRF-04(vi) still states the rejected proof is the whole enforcement.

## Verdict

**Not clean, not safe to ship.** Critical 1 (F1: the fee-cap seam — a permissionless, byte-valid, live record that the rules call executable but no valid block can carry; the round-1/2 settlement-halt class, created by the round-3 repair's exclusion of the base fee), High 0, Medium 0, Low 1 (F2: register wording and class list). The rest of the round-3 repair is consistent across the rule/proof/register seam — the quotation is verbatim, the turn and predicate match, the index-order scope and the F-FI-3 disclosure match — so F1 is a bounded, local repair in the same style the increment has used: a registered fee floor decided from the record's bytes, with the three "no valid block can carry" claims qualified. I would not ship with the fee seam open.
