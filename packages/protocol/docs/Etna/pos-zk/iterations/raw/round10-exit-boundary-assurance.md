## F1 — ECON-02(5)(d): "inside the prefix the call can freeze" leaves the already-frozen target undefined; read literally, a claim or a proving-share transfer reverts whenever any epoch is pending

**Severity: Low.** One-line rationale: the clause that decides whether a claim or a transfer may take effect is written in terms of the *pending* prefix, so an already-frozen target is never "inside" it; the literal reading makes every claim and every proving-share transfer revert whenever any other epoch is pending — which is almost always — while the intended reading (apply if the target is frozen, whether already or within the prefix this call freezes) is recoverable only from context.

**File + rule id.** `spec/07-economics-slashing.html` `#ECON-02` clause 5(d): "Every call that can change the pool's balance or fix a later epoch's amounts — an inflow credit, a validator claim, a proving-share transfer, or the freeze of a later epoch — MUST first execute the pending epochs' freezes in ascending epoch order, starting from the earliest, and MUST freeze at most `FREEZE_MAX` epochs in one call. … A call MAY freeze that bounded ascending prefix and return; it MUST NOT freeze an epoch out of order or skip one. **A call whose own effect needs an epoch frozen — a validator claim, a proving-share transfer, or the freeze of a later epoch — MUST apply that effect only if the epoch is inside the prefix the call can freeze, and MUST otherwise revert with no effect.**"

**Why it is a defect.** The prefix is defined over *pending* epochs ("Call an epoch pending when `evidenceClose` has passed and it is not yet frozen"), and `freezeEpoch(e)` "MUST revert if e is … already frozen". An already-frozen target is therefore never inside the prefix. Read literally:
- a claim for an already-frozen epoch `e` reverts whenever any other epoch is pending, even after the prefix has been frozen by the same call (the prefix contained the pending epochs, not `e`); and since a new epoch becomes pending every `EPOCH_LEN_L1` (≈30 min), the condition re-triggers continuously, so claims and proving-share transfers could never be paid; and
- draining first does not help under that reading: with the pending set empty the prefix is empty, so `e` is still not "inside" it.
That reading is self-defeating, so the intended meaning must be "the epoch is frozen at the end of the prefix step (it was already frozen, or it lies within the prefix this call freezes)". The clause is normative and it is the condition that gates the payout of validator rewards and the proving-share transfer that funds the exit (L1-13(5)/L1-11), so the two readings should not both be available. The fix is four words: "… only if the epoch is **frozen at the end of that prefix step — already frozen, or** inside the prefix the call can freeze …".

**Assumptions.** None. No adversary; the divergence appears between two literal implementations.

**Attack trace (no adversary).** An implementer transcribes the sentence as `require(inPrefix(e))`. The staking contract's first claim reverts while any epoch is pending; the deployer's test suite fails immediately and the rule must be re-read. If instead the sentence is implemented literally *and* the pending set is kept empty by a diligent drainer, a claim for an old epoch still reverts the moment the next epoch becomes pending — a self-inflicted liveness failure on validator rewards and on the exit's funded transfer. Both readings are safe (no funds move wrongly, nothing is lost), which is why this is Low and not higher.

**Fault-model verdict.** N/A (textual); no fund loss, no false guarantee, no conflicting histories.

**Evidence.** `spec/07#ECON-02` clause 5(d) (the pending definition, the out-of-order/skip prohibition, the prefix-effect sentence, the resume path, and the close-time paragraph that follows it); `spec/09#FREEZE_MAX` row; `spec/04#L1-13`(5) and `#L1-11` (the transfer and the reward this condition gates).

## Confirmation of the round-9 residue (all verified at the rule text)

1. **The cascade is genuinely bounded and resumable in every path.** "MUST freeze at most `FREEZE_MAX` epochs in one call"; all four paths are enumerated (inflow credit, validator claim, proving-share transfer, `freezeEpoch`); a call "MAY freeze that bounded ascending prefix and return" and "MUST NOT freeze an epoch out of order or skip one"; `freezeEpoch(e)` freezes earliest→e and reverts if the pending count up to e exceeds `FREEZE_MAX`; a backlog of p drains in `ceil(p / FREEZE_MAX)` permissionless calls. No leftover of the old unbounded phrasing survives (the only "whole pending set" occurrences are the inflow rule, which is itself bounded by `FREEZE_MAX`).
2. **The inflow path preserves the close-time property.** "A call that credits an inflow MUST NOT credit it while any pending epoch remains: it freezes the whole pending set when that set holds at most `FREEZE_MAX` epochs, and otherwise the authenticated message MUST revert and stay retriable under MSG-02's per-message status model … so an arrival is never counted by an epoch whose `evidenceClose` precedes it." This matches the fee path: the sweep is a Bridge message whose failure modes are MSG-02 statuses (`FAILED`/`RECALLED`, ECON-02(7)(iii)), and no reward may be promised from fees that have not arrived.
3. **FREEZE_MAX cannot deny, dilute or inflate.** Registered in 09 (214) with unit, owner, "`FREEZE_MAX ≥ 1`", "no value is proposed", the derivation rule (measured cost of one freeze ÷ block gas limit, GEN-08), the measurement named in PARAM-03 (09:445) and an index-map row; changing it is a recorded upgrade, not a runtime call. Ascending order plus the no-skip rule keeps `reserved_before(e)` complete, so no later freeze dilutes an earlier epoch; the inflow gate prevents a later arrival from being counted by an earlier-close epoch; claims and transfers discharge reservations "against the same balance, so free is unchanged by them"; the only balance-raising event outside the gate is a forced ETH credit, which can only increase the base pro rata and is already disclosed as such.
4. **Close-time amounts still hold.** The free balance can only change through an inflow (gated until pending = 0) or a deterministic release of already-present ETH (floor remainder at the last claim, empty-participant-set release at the freeze), neither of which is caller-chosen; the per-epoch record, running reserved total and checked views are unchanged.
5. **The exit's two dependencies are stated everywhere the exit is promised.** `MEM-15`(1) names both, (2a) names the recorded certificate/data/pre-state witness, (2b) is titled "The proving dependencies" with (a) funding and (b) retained inputs and a falsifier covering both; `L1-13`(5), `MSG-03`(5) ("produced and funded from inputs that remain retrievable — the recorded certificate, the batch's data and the pre-state witness"), `STATUS-08` ("must supply from inputs that remain retrievable"), `LIVE-01` ("not independent of proving or of retention"), `LIVE-05`, `LIM-01`, the guarantee-class preamble, the index verdict/preamble/rows (index:35, 42, 287, 363, 491, 517) and the course all carry both.
6. **The attestation front-running race is disclosed** in the same form and with the same mitigation as the landing race: "an attestation proof observed in the public mempool can be copied and submitted first by another account, which then collects `attestRewardPaid` and leaves the prover who produced the proof unpaid … the mitigation available to provers is private orderflow or bundling, and the payout stays best-effort and never gates the attestation" (`L1-11`, 04:544) — matching the landing disclosure (04:527) and the course.
7. **No new unbounded loop.** The cascade is the only new loop; `land`'s loops remain bounded by the transaction's contents; the decomposition views "MUST NOT … iterat[e] the set of epochs" (running reserved total); the k-family path is bounded by k and one call; the veto is one-shot per contradiction.
8. **Round-9 residue elsewhere did not introduce a defect in my scope.** `CONS-02`'s store prohibition is explicit and complete ("The store MUST NOT be cleared, truncated, rewritten or restarted from empty by any rule — a restart, a resync or a revived stall resolution included"); `CONS-05`'s vote and certificate tuples carry `recovery_generation` and the signed value must equal the certificate's; the tombstone scan found 11 hits, all previously classified (09's tombstone lists, 10's historical change-order ledger, and live rules citing `MEM-13`'s tombstone section for the v1 quorum-loss disclosure it deliberately owns, which LIVE-05 states in parallel). The `spec/08` markup/truncation repair is outside my angle; the files I parsed rendered complete, with no truncation in pages 02–10 or the course.
9. **Exit, veto, boundary, upgrade and reorg: unchanged and still sound.** MSG-04(4) keeps the veto off root attestation and off every path but release; L1-13(2)/(3) still make any accepted checkpoint attestable, keep the root at or below the checkpoint and forbid the attach path from writing a checkpoint or moving the pointer; MIG-05's per-epoch image sets remain never-deleted; L1-12 leaves a reorg as a suffix that takes the accepting transaction and every later attestation with it.

**Considered and dismissed (not findings).** (a) The unrewarded drain: a claimant must pay `ceil(p / FREEZE_MAX)` cheap permissionless calls to reach its epoch, but the claimant's own payout is the incentive and `FREEZE_MAX` is calibrated to the block gas limit, so the "no keeper" claim survives. (b) The drainer needs the index of the k-th pending epoch; it is derivable off-chain from `evidenceClose(e)` and the existence of `allocRecord[e]`, so no view is required. (c) A forced ETH credit can land between an epoch's close and its freeze and raise that epoch's allocation; it is out of the model, deterministic and pro-participant, and the spec already discloses it. (d) The released floor remainder / empty-set release can raise a later epoch's base; both are deterministic releases of ETH already in the pool, not arrivals, and no caller chooses them.

## Verdict

**Round 10 is clean for the exit and the bounded cascade: Critical 0, High 0, Medium 0, Low 1.** The round-9 residue is real: the cascade is bounded and resumable in every path, `FREEZE_MAX` is registered with no value invented and cannot be turned into a denial, dilution or inflation lever, the close-time property is preserved by the inflow gate, the exit's two dependencies are carried by every artifact that promises the exit, and the front-running race is disclosed in the same terms as the landing race. The one Low is a four-word wording fix in the new prefix-effect sentence; it changes no guarantee and risks no funds.

**Would I build on this specification?** Yes, and I would not hold convergence for F1 — it is a wording repair I would make in the same pass as any other copy edit, not a mechanism change. For the exit and the guarantee class the design is now specified to the level where two implementations should agree, and it states its own limits (funding, retention, family availability, best-effort payouts, no recovery path) rather than implying them.
