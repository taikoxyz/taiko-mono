## F1 — 09's eligibility paraphrases omit the non-zero-sequence guard, so a register-only reader could read the filter as vacuous for an entry that has never attested

**Severity: Low.** One-line rationale: the guard is stated in MEM-13(3), MEM-09(1), the index and the delta, but the register's two sentences that describe eligibility say "an active entry whose last accepted heartbeat named neither that window nor the one immediately before it is excluded" and "eligibility … requires the last accepted heartbeat to have named the window containing `L1_first(C(e))` … or the window immediately before it" — neither says the entry must have attested at least once. The owner rules are explicit, so this is completeness, not contradiction; but the register is the surface an implementer may read first, and the place where the omission bites is exactly the low-height case the guard exists for: with `I*(e) − HEARTBEAT_WINDOW = 0` (the two shifted launch epochs, when `L1_0 < HEARTBEAT_WINDOW`), the unguarded arithmetic admits `lastHeartbeatAt(v) = 0` and only the guard excludes it.

**File + rule id.** `spec/09-parameters.html`, row "L1 heartbeat (eligibility attestation)" (09:38): "… and an active entry whose last accepted heartbeat named neither that window nor the one immediately before it is excluded from the version's roster"; row `HEARTBEAT_WINDOW` (09:362): "eligibility for the set version committed for epoch `e` requires the last accepted heartbeat to have named the window containing `L1_first(max(e - LOOKAHEAD_EPOCHS, e_0))` … or the window immediately before it"; row `lastHeartbeatSeq(v)` (09:376) states the *acceptance* guard and "never reset by a key rotation" but not the eligibility guard. Against them: `spec/03#MEM-13`(3) ("if and only if **`lastHeartbeatSeq(v) > 0` and** `lastHeartbeatAt(v) ≥ I*(e) − HEARTBEAT_WINDOW` … An entry with no accepted heartbeat is ineligible regardless of the arithmetic"), `spec/03#MEM-09`(1) ("the predicate **`lastHeartbeatSeq(v) > 0` and** `lastHeartbeatAt(v) ≥ I*(e) − HEARTBEAT_WINDOW` … an entry with no accepted heartbeat is ineligible regardless of the arithmetic"), `spec/index.html` MEM-13 row ("only if it has an accepted heartbeat (`lastHeartbeatSeq(v) > 0`) and …"), and the delta (three places). The course's one-line gloss ("a version selects the active entries whose heartbeat covers the L1-block window its epoch start fixes", `learn/04`) relies on the same implicature.

**Assumptions.** None.

**Attack trace (no adversary).** An implementer reads the register's filter sentence and implements the window comparison alone. On a chain whose `L1_0 < HEARTBEAT_WINDOW`, the shifted launch instant is `I* = HEARTBEAT_WINDOW`, so `I* − HEARTBEAT_WINDOW = 0`; every active entry's `lastHeartbeatAt` is `0` until it attests, so the unguarded comparison admits every never-attested entry into the versions for `e_0 + 1` and `e_0 + 2` — the exact admission R2-DI-01 closed, and it would silently undo the launch transition's purpose (the shift's whole point is that only entries that attested in the window containing `L1_0` are eligible). The authoritative rules are correct, so this is an implementation-risk path, not a specification contradiction.

**Fault-model verdict.** N/A (register completeness). No path admits a never-attested entry if the owner rules are read.

**Attacker cost.** None (a mis-implementation, not an attack).

**Requirement affected.** PARAM-01/GEN-03 (the register must describe the rule it registers without losing a conjunct); R2-DI-01's closure; the launch transition's guarantee.

**Suggested repair.** One clause in the 09 heartbeat row and the `HEARTBEAT_WINDOW` row: "… and it has attested at least once (`lastHeartbeatSeq(v) > 0`)" (and optionally the same clause in the course's eligibility line). No rule, table value or mechanism changes.

## Verification of the claims charged to this round (all confirmed)

1. **The guarded predicate, wherever it appears.** `MEM-13`(3): "if and only if `lastHeartbeatSeq(v) > 0` and `lastHeartbeatAt(v) ≥ I*(e) − HEARTBEAT_WINDOW`" — with the explicit note that a never-attested entry "cannot enter a roster on a low-height L1". `MEM-09`(1): the roster filter states the same two conjuncts and the same note. The index's MEM-13 row states the guard and attributes it (R2-DI-01). The delta states it in three places. No page states the unguarded *formula*: every other description is a prose paraphrase that presupposes a last accepted heartbeat (F1 is the one surface where that presupposition is doing the work). The register's `HEARTBEAT_WINDOW` row and the index row both carry the launch-transition shift, and 09's row is explicit that it "matches MEM-13(3)" and that "from `e_0 + 3` the clamp advances and the unshifted definition resumes".
2. **A never-attested entry is ineligible on every path.** (i) Steady state: once `I*(e) > HEARTBEAT_WINDOW`, `lastHeartbeatAt(v) = 0` fails the inequality; (ii) the two launch epochs: `I*(e) = (k+1)·HEARTBEAT_WINDOW`, so `I*(e) − HEARTBEAT_WINDOW = k·HEARTBEAT_WINDOW` which can be 0 — the guard, present in both owner rules, decides it; (iii) a lowest-missing refill: the instant is derived from the target epoch the same way and the guard is in the filter, so a refilled epoch is no more permissive; (iv) the activation entry for `e_0` is unfiltered **by stated policy** (CONS-14(1)), which is not a filtered roster and cannot be reached by this path. I also checked the arithmetic at the boundary: an entry attesting in the window containing `L1_0` has `lastHeartbeatAt = k·HEARTBEAT_WINDOW ≥ I* − HEARTBEAT_WINDOW` ✓, so the guard does not exclude an honest launch attester.
3. **The sequence guard cannot be gamed.** Replay: acceptance requires the named window to be the current one (`(2a)`(b)), the sequence to strictly advance (`(2a)`(c)) and the named window's start block to be strictly later than the recorded value (`(2a)`(d)), and records are monotone (`(2b)`) — so an accepted signature cannot be re-submitted in its window (d) or in any later window (b). A higher sequence from a retired key: `(2a)`(a) requires the recovered key to be exactly `heartbeatKey(v)` and not retired, `(1)` makes a signature under a retired key "invalid whenever it was produced" and retirement permanent and un-rebindable, and the non-zero-key rule closes `ecrecover`'s `address(0)` wildcard. A sequence advance without a window advance is rejected by `(2a)`(d); a window advance without a sequence advance is rejected by `(2a)`(c); the two records are written together on acceptance (`(2b)`); a key rotation never resets `lastHeartbeatAt`, `lastHeartbeatWindow` or `lastHeartbeatSeq` (`(1)`); and `v` names exactly one live entry (bonding address, one live entry per address), so cross-entry replay is excluded by the preimage.
4. **The pending-change ordering influence is bounded to a pending change.** `MEM-13`(6): "while a change is pending, an append caller's ordering relative to it selects whether the version is evaluated under `W_old` or `W_new`; this is binary, it is bounded to the pending change, it cannot name an arbitrary instant, and it needs the ordering control of F8's class". The exclusion run is sized: "every version evaluated before the entry re-attests whose evaluation instant falls in `(A + W', A + W_old]` excludes it, so a backlog drained in a single block loses a contiguous run of versions, about `(W_old − W') / EPOCH_LEN_L1` of them and bounded by the backlog actually drained". The index row carries both, and `MEM-13`(3) names the exception in its caller-independence claim ("the one bounded exception … bounded to a pending change and of F8's ordering class"). The 09 `HEARTBEAT_WINDOW` row's "cannot permanently empty" carries the reviewer caveat that the Open still admits a one-version exclusion.
5. **The round-2 repairs are real, and the launch transition is coherent end to end.** The shift is defined identically in `MEM-13`(3), `MEM-09`(1) (a call before the shifted instant "MUST revert rather than append"), `CONS-14`(1), the 09 `HEARTBEAT_WINDOW` row and the delta; the duty is a rule in `CONS-14`(1) ("A validator whose entry is active at activation … MUST … have an accepted heartbeat naming the window containing `L1_0` … before the first `commitSet()` that appends a filtered version") and is carried into the MIG-03 announcement; the launch deadline is re-based ("the entries for epoch 1 and epoch 2 MUST be committed as early as the launch-transition opening of MEM-13(3) permits and, in every case, before any block of the epoch each governs may be voted for or finalized"), which resolves the deadline/opening coupling I would otherwise have attacked; and the transitional cost is disclosed in 08 (up to one heartbeat window of delay, and the first-boundary halt clearing on the permissionless lowest-missing append). The false "in the future when the entry is appended" is replaced by the invariant, checked for the shifted instant too; and CONS-14(1)'s genesis justification is now the policy one, with the T3 key-path timing stated rather than assumed.
6. **Nothing outside the increment moved.** REC-01's normative text is intact (the increment adds annotations only, including "no replacement path is added and REC-01's guarantee is unchanged"); the exit (MEM-15, L1-13) is untouched and reads no membership record; `MEM-13`(4) states "D-7, D-8 and D-9 are untouched", no heartbeat term enters 07 and the ECON-02(5) participation accumulator is unchanged; D-11 is untouched; exclusion removes no weight and the decay tombstones stay withdrawn; no live-context read of `T_ROTATE`, `T_ROTATE_DELAY`, `CONS-16`, `T_INACTIVE`, `D_LAPSE_MAX`, `lastObserved` or any other withdrawn name (the index's parameter-map row states the rotation names "MUST NOT be used by any rule, client, parameter or migration text").

## Checked and dismissed (not findings)

- **The shift's residual window.** The launch duty's deadline and the append opening are both the first window boundary after `L1_0`; if `L1_0` sits near the end of its window, the post-activation remainder is short. This is closed in substance by the same repair: the genesis roster's entries have their heartbeat key path before activation (CONS-14(1), 08 T3), so the whole window containing `L1_0` — including the part before `L1_0` — is available for the duty, which is why "a full attestation window" is accurate for entries that follow it. No rule relies on pre-activation acceptance.
- **The index's instant gloss.** Its phrase "the heartbeat window containing the L1-side epoch start at which its append became coverable" is ambiguous for the two clamped epochs only because the register and MEM-13(3) are the surfaces that name the shift explicitly; the index disclaims being a second copy and its guard statement is correct. Not a finding.
- **Re-bond reuse of heartbeat records.** A new entry at a previously used bonding address is the same owner's act and the spec requires at most one live entry per address; no adversary gains eligibility from it.
