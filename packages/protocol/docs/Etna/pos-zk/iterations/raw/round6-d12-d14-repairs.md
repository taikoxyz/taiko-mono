## R6-D12-01 — Critical — the expiry discharge still has no ground in the proof, and the interface mandates the very prune that FI-14 forbids; a dead record that cannot be executed or supplied blocks the FIFO prefix for ever.

*Rationale: FI-10 says a record past its DA-09 deadline "MUST be discarded from the due set ... and no proof may be required to include it", but the only two rules that move the frontier the guest reads (FI-11(5) and PRF-04(vi)) accept only "included in the batch or discharged as void under FI-13", and FI-13's only void ground is non-includability — expiry is no ground; meanwhile L1-08 still mandates `pruneExpiredPublications`, which FI-14's prohibition list ("skips a prefix element except by include-or-void under FI-13") says must not exist.*

- **Rules / missing rule.**
  - `spec/04` **FI-10** ("Expiry and discard"): "A record whose DA-09 deadline has passed without a proof is dead: it MUST be discarded from the due set by an objective, permissionless advance of the frontier — no judgement, key, vote or DAO action is used — and **no proof may be required to include it**." The same rule defines `d(A)` as "the number of records with `l1BlockNumber + FI_INCLUSION_DELAY ≤ A`" **with no status or liveness filter**, and the required prefix as `[c, min(d(A), c + FI_MAX_PER_BATCH))` with `c` = the predecessor checkpoint's `settledCount`.
  - `spec/05` **PRF-04(vi)** / `spec/04` **FI-11(5)**: the guest "MUST require ... that every position in `[c, c')` holds a record at A which is **included in the batch or discharged as void under FI-13** — a position with no record at A is neither included nor void and MUST make the proof invalid".
  - `spec/04` **FI-13**: "it is void **only if** the guest determines from the batch's own execution that its transactions were not includable in any block of the batch"; and "No other ground discharges a record, at any layer: ... **not the record's own age while it is still live**." The added qualifier implies age discharges a dead record but no rule makes it a discharge ground.
  - `spec/04` **FI-14**: "there MUST NOT exist a function that ... **skips a prefix element except by include-or-void under FI-13** ...".
  - `spec/04` **L1-08** (interface): `function pruneExpiredPublications(uint32 _maxRecords) external returns (uint64 settledFrontier_);` with the comment "the objective expiry prune"; and `event ForcedFrontierAdvanced(...)` is documented as "advanced by an accepted batch **or by the objective expiry prune**". **Missing rule:** either an FI-13 void ground for a record past its deadline, or the deletion of `pruneExpiredPublications` and of FI-10's "no proof may be required to include it"; plus a rule stating which cursor (`settledCount` c, `dueHead`, `nextSeq`) moves on expiry and how they relate.
  - `spec/09` `FI_INCLUSION_DELAY` row: "the search range is the **live register window [dueHead, nextSeq)** of the packed clock (slot 277)"; `spec/08` MIG-02 slot 277 packs `nextSeq + dueHead + dueTail + dueCount + pruneCursor`. No rule in 02–05 owns `dueHead`, `dueTail`, `dueCount` or `pruneCursor`, and no rule relates them to `c`. `spec/04` **L1-05 row 36** reads the proof-visible frontier as "`settledFrontier` is read from the **predecessor checkpoint's own settlement record** (FI-10)", and FI-10 says that record is "written **atomically by that height's accepting land(data, proof)**" — so `pruneExpiredPublications`'s returned `settledFrontier_` is **not** the `c` the guest uses.
- **Assumptions.** DA-09(1)'s deadline; the mandated L1-08 ABI; F-FI-2 (arrival > drain), which the specification states is permitted and only a latency concern; no adversary required for the rule conflict.
- **Concrete attack trace (no adversary, two horns).**
  1. A record becomes due (FI-10) and is not resolved before `deadlineBlock` — reachable whenever the arrival rate of includable records exceeds `FI_MAX_PER_BATCH` per accepted batch (F-FI-2, explicitly permitted) or during a settlement stall (the case GOV-04 exists for). DA-09(1) makes it `DISCARDED`.
  2. *Horn A (implement the mandated prune).* Any account calls `pruneExpiredPublications`. It advances the register clock and emits `ForcedFrontierAdvanced`, but the guest's `c` comes from the predecessor checkpoint's settlement record, which only an accepted `land(data, proof)` writes (FI-10, L1-05 row 36). If instead `land` copies the pruned frontier into the new settlement record so that the proof can pass, then a permissionless, proof-free L1 call has discharged a due record that was never included or voided — the enforcement point has moved off the proof, which FI-11 and D-12 forbid and which FI-14's "skips a prefix element except by include-or-void under FI-13" names as a construct that must not exist. **The interface mandates the construct FI-14 forbids.**
  3. *Horn B (implement FI-14).* The prune is out. The dead record sits at position `c` inside `d(A)` (no status filter); FI-13 gives no void ground if its transactions are individually includable; therefore every acceptable batch must **execute the dead record's transactions**, contradicting FI-10's "no proof may be required to include it" and making DA-09(2)'s re-publication remedy add work instead of releasing it (the user pays L1 twice and the first record's transactions are still forced).
  4. *Horn B, unavailability.* Once the record entry is pruned (`PUB_RECORD_RETENTION ≥ T_PROVE_DEADLINE` permits pruning after the deadline; "a pruned record is treated as absent") or its blobs leave the retrievability window, its byte string cannot be supplied or verified: the guest cannot include its transactions (needs the bytes) and cannot evaluate non-includability (needs the transactions). `[c, c')` can then never be satisfied, `c'` can never reach `min(d(A), c+cap)`, and **every proof** fails; GOV-04 restores the checkpoint record and with it the same `settledCount`, so resuming does not clear the record. Settlement is stuck permanently, with no in-protocol cure.
- **Inside/outside the fault model.** The rule conflict is intrinsic — inside, no adversary. Horn B's permanent-halt ending needs the record to be left unresolved past its deadline (F-FI-2 or a stall, i.e. ≥1/3 non-participation) **and** the entry/blobs to become unavailable; Horn A's suppression is available to any account and needs no fault at all.
- **Attacker resources and cost.** None for the contradiction. One permissionless L1 transaction for Horn A; ordinary L1 publications to keep the queue above the drain for Horn B's expiry.
- **Requirement / fixed decision affected.** D-12 (the published data is discardable and re-publishable at the deadline; enforcement is the proof); FI-10, FI-11(5), FI-13, FI-14; DA-09(1)/(2); L1-08's mandated ABI; the register's cursor model (MIG-02 slot 277).
- **Evidence.** `spec/04-l1-integration.html` FI-10, FI-11(5), FI-13, FI-14, L1-05 row 36, L1-08 lines 314–319 and event 362–364; `spec/05-proof-statement.html` PRF-04(vi); `spec/09-parameters.html` rows `FI_INCLUSION_DELAY`, `PUB_RECORD_RETENTION`, `T_PROVE_DEADLINE`; `spec/08-migration-upgrades.html` MIG-02 slot 277 (lines 283, 326–333). Related un-repaired item: DA-09(1) says the record "MUST carry ... a status" that becomes `DISCARDED` at the deadline, while MIG-02 line 281 says the entry "is immutable once written ... never by mutating the record" (round-5 R5T-PDE-10) — one of the two texts must own the status.

## R6-D12-02 — High — the new `FI_ANCHOR_MAX_AGE` check is an admission gate on `land` that can make a certified range permanently unacceptable, and no registered relation ties the age bound to the proving envelope.

*Rationale: the round-5 repair for C-1/F3 placed the freshness bound at landing (`block.number − A > FI_ANCHOR_MAX_AGE` reverts), but a batch's anchored view `A` is committed by its own blocks and can never be refreshed, and nothing requires `FI_ANCHOR_MAX_AGE` to cover `T_PROOF_MAX_PERMITTED + T_SETTLE_PIPELINE + L1_FINALITY`; so an honest, in-envelope batch that lands late is rejected for ever — the exact admission condition L1-04 lists as forbidden.*

- **Rules / missing rule.** `spec/04` **FI-11** (L1-side checks): "MUST reject a view ... whose age at landing exceeds the registered maximum — `block.number − A > FI_ANCHOR_MAX_AGE`, reverting `ForcedViewStale(A, block.number)`". `spec/04` **L1-04**: "The admission rules of `land(data, proof)` MUST contain: ... **no deadline, timestamp, block-number or age condition that can make a range permanently unacceptable**"; and L1-06 (round-2 R2-LIV-07): "no batch is ever rejected at land for being too old". `spec/09` rows `FI_ANCHOR_MAX_AGE` / `FI registered relations`: the **only** registered relation is `FI_ANCHOR_MAX_AGE ≥ L1_FINALITY_DEPTH`; `T_PROVE_DEADLINE` is separately tied to the envelope (`≥ T_PROOF_MAX_PERMITTED + T_SETTLE_PIPELINE + margin`) and does **not** bound `A`'s age. **Missing rule:** either `FI_ANCHOR_MAX_AGE ≥ (T_PROOF_MAX_PERMITTED + T_SETTLE_PIPELINE + L1_FINALITY)` converted to L1 blocks (so no in-envelope batch can age out), or a consensus-side duty to anchor freshly (CONS-01 has no anchor-recency condition) with the landing gate removed, or an explicit re-anchor path for a certified range.
- **Assumptions.** A producer anchors the freshest Ethereum-final view at production (`A ≲ prod − L1_FINALITY_DEPTH`); the proof is produced inside the permitted envelope and landed afterwards. No adversary, no parameter is required to be wrong — `FI_ANCHOR_MAX_AGE` is "unmeasured".
- **Concrete attack trace (no adversary).**
  1. A batch over `[h, h+k]` is produced at L1 height `prod` with `A` = the Ethereum-final head then visible; it is certified (CONS-01 has no anchor-freshness clause, so correct validators must sign).
  2. The proof is produced inside `T_PROOF_MAX_PERMITTED` and landed at height `H`. `H − A ≈ (H − prod) + L1_FINALITY_DEPTH`.
  3. If `H − A > FI_ANCHOR_MAX_AGE` — possible for any finite `FI_ANCHOR_MAX_AGE` because **no rule bounds the time between certification and landing** (the carried path has no `T_PROVE_DEADLINE`, and L1-04 says the range length and hence the landing moment are the submitter's choice) — `land` reverts `ForcedViewStale` at every future height: `A` is fixed inside the batch's own blocks, and the same heights cannot be re-produced with a different anchor except by GOV-04's stall resolution (a settlement stall + `T_STALL_GOV` + `T_GOV_RESUME`).
  4. Result: a valid, in-envelope proof for a PoS-certified extension of the checkpoint is permanently unacceptable outside the sanctioned procedure — L1-04's named failure mode and L1-06's "never rejected for being too old".
- **Inside/outside the fault model.** Inside: no assumption failure and no adversary; only unmeasured parameters and ordinary proving/landing latency. A griefer can also make it happen to a specific certified batch by delaying its landing (the landing race is permissionless and a losing submission is void, L1-04).
- **Attacker resources and cost.** None for the ordinary case; for a targeted case, one winning landing of a competing batch plus normal L1 fees.
- **Requirement / fixed decision affected.** L1-04, L1-06, FI-11, DA-09's "the range remains landable"; the C-1/F3 repair is the mechanism that introduced it.
- **Evidence.** `spec/04-l1-integration.html` FI-11 (L1-side checks), L1-04, L1-06; `spec/09-parameters.html` rows 188 and 189 (`FI_ANCHOR_MAX_AGE`, `FI registered relations`); `spec/09-parameters.html` row 179 (`T_PROVE_DEADLINE`, the envelope relation that is not applied to `A`).

## R6-D12-03 — High — CONS-01(v) imposes the prefix **per block** at `FI_MAX_PER_BATCH` records while the proof and the registered relation are **per batch**; the registered relation permits a registration in which no block can carry the required prefix (round-1 halt class), and the alternative reading makes CONS-01(v) vacuous.

*Rationale: round 5 changed the cap's divisor to `itemGasBound` but left the consensus-side unit untouched, so the two checks FI-11 says "must agree" still disagree, and the register allows `FI_MAX_PER_BATCH × itemGasBound > L2_BLOCK_GAS_LIMIT`.*

- **Rules / missing rule.** `spec/02` **CONS-01(v)**: "The block MUST contain, among its executed transactions, the FIFO prefix of P **up to `FI_MAX_PER_BATCH` records** ... except that a record is not required if ... it is not includable in the block under FI-13's predicate." `spec/04` **FI-12**: `cap(batch) = min(FI_MAX_PER_BATCH, floor(batchGasCapacity / itemGasBound))`, `batchGasCapacity` = "the sum of the gas limits of the batch's own headers"; `spec/09` **FI capacity relation**: `FI_MAX_PER_BATCH × FI_MAX_TX_PER_RECORD × FI_RECORD_GAS_MAX ≤ MAX_BATCH_BLOCKS × L2_BLOCK_GAS_LIMIT` (batch-level only). `spec/04` **FI-11**: "The same predicate is the per-block clause CONS-01(v) ... the two checks must agree, and a disagreement is a protocol defect." **Missing rule:** either a per-block capacity cap in CONS-01(v) (`≤ floor(blockGasLimit/itemGasBound)`) plus a registered per-block relation, or the obligation stated once, per batch, in both places.
- **Assumptions.** The registered relation holds; `FI_RECORD_GAS_MAX ≤ L2_BLOCK_GAS_LIMIT` holds; the values are unmeasured but nothing forbids the combination below.
- **Concrete attack trace (configuration, no adversary).** Register `FI_MAX_PER_BATCH = 10`, `FI_MAX_TX_PER_RECORD = 1`, `FI_RECORD_GAS_MAX = 30M = L2_BLOCK_GAS_LIMIT`, `MAX_BATCH_BLOCKS = 10` — the relation holds with equality (10×30M ≤ 10×30M). A publication becomes due. CONS-01(v) requires its first block to contain up to 10 records, i.e. ≤ 300M gas of forced transactions in a 30M-gas block; each record's single transaction is individually includable (≤ `FI_RECORD_GAS_MAX`, fits the block gas limit) so none is void under FI-13. No block satisfies (v); correct validators must vote NIL; no batch can be certified or landed — a permanent settlement halt caused by one L1 publication, which is the failure D-12 says must not return. Reading "up to" as an upper bound instead makes (v) say nothing about how many records are required, leaving the consensus-side check empty and the proof-side cap as the only obligation — the disagreement FI-11 calls a protocol defect, and the opening for R6-D12-04.
- **Inside/outside the fault model.** Inside: a legal registration and one permissionless publication; no adversary and no assumption failure.
- **Attacker resources and cost.** One L1 publication (plus influence over, or just the misfortune of, the parameter registration).
- **Requirement / fixed decision affected.** D-12 ("a backlog drains over successive batches instead of halting the chain"); FI-11's agreement requirement; FI-12's "why this cannot halt"; HALT-01/03.
- **Evidence.** `spec/02-consensus.html` CONS-01(v); `spec/04-l1-integration.html` FI-12, FI-11; `spec/09-parameters.html` rows 181, 184, 186, 189. Round-5 F5, re-confirmed on this snapshot: the text of CONS-01(v) is unchanged.

## R6-D12-04 — High — FI-12's anti-shrink MUST still has no enforcement point: the submitter computes `cap` from its own headers, `cap = 0` is reachable under a legal registration, and the drain rate stays the submitter's choice.

*Rationale: the round-5 repair restated the divisor but added no check anywhere — the guest clause (PRF-04(vi)) computes `min(FI_MAX_PER_BATCH, floor(batchGasCapacity/itemGasBound))` and requires only `c' ≥ min(d(A), c+cap)`; the L1 contract (L1-05 row 36) and CONS-01(v) never see `batchGasCapacity`.*

- **Rules / missing rule.** `spec/04` **FI-12**: "When the window is non-empty the batch **MUST** have `batchGasCapacity ≥ FI_MAX_PER_BATCH × itemGasBound`, so a submitter cannot shrink its batch to shrink the obligation: for every batch that can be required to do the work, `cap(batch) = FI_MAX_PER_BATCH`"; claim (iii) "On acceptance the frontier advances by `min(pending, cap) ≥ 1` whenever a record is pending". `spec/05` **PRF-04(vi)** enumerates the guest checks and contains no minimum-capacity check. `spec/04` **L1-05 row 36** binds only `anchoredL1Block, settledFrontier, dueFrontier, settledAfter, forcedOpeningsHash` — no capacity term. **Missing rule:** a guest check that rejects any batch with a non-empty window and `batchGasCapacity < FI_MAX_PER_BATCH × itemGasBound`, plus the L1-side or consensus-side mirror FI-11 requires.
- **Assumptions.** Legal registration: `FI_MAX_TX_PER_RECORD = 2`, `FI_RECORD_GAS_MAX = L2_BLOCK_GAS_LIMIT` (allowed, `≤`), `FI_MAX_PER_BATCH = 8`, `MAX_BATCH_BLOCKS = 16`; the relation `8 × 2 × L2 ≤ 16 × L2` holds with equality. `L1-04`: "the range length is the submitter's choice"; `MIN_BATCH_BLOCKS` is non-normative.
- **Concrete attack trace.**
  1. Submit a one-block batch. `batchGasCapacity = L2_BLOCK_GAS_LIMIT`, `itemGasBound = 2 × L2`, hence `cap = min(8, floor(L2 / 2L2)) = min(8, 0) = 0`.
  2. The required prefix `[c, min(d(A), c + 0)) = [c, c)` is empty, `c' ≥ c` is satisfied without advancing, PRF-04(vi)'s position check is vacuous, and the guest accepts. FI-12's MUST is violated but nothing rejects it.
  3. Every publication now expires unresolved and is "discarded"; the frontier never advances. D-12's narrow forced inclusion is structurally vacuous **by submitter choice**, i.e. round 1's "configuration that inverts the two discards every record before it can ever be due" reproduced without touching a parameter.
  4. With `cap ≥ 1` the same lever divides the drain rate by up to `FI_MAX_PER_BATCH`; adding cheap padding publications puts arrival above drain (F-FI-2) so a user's record passes its deadline unresolved and the loop of R6-D12-01 follows.
- **Inside/outside the fault model.** Inside: no assumption failure; producing and landing batches are permissionless roles. (Honest validators applying CONS-01(v) literally would refuse the short block — which is R6-D12-03's halt — so at least one of the two rules must be wrong.)
- **Attacker resources and cost.** Ordinary L1 gas for batches it would land anyway, plus padding publications; no stake.
- **Requirement / fixed decision affected.** D-12's cap ("inclusion is a capped FIFO prefix ... the failure mode that produced review round 1's critical finding must not return"); FI-12 claims (1)–(3); FI-11's "the enforcement point is the proof".
- **Evidence.** `spec/04-l1-integration.html` FI-12, FI-11(3)–(5), L1-05 row 36; `spec/05-proof-statement.html` PRF-04(vi) (the cap formula appears there with no floor check); `spec/09-parameters.html` rows 181, 184, 186. Round-5 H-4, re-confirmed.

## R6-D12-05 — High — the void predicate still depends on the producer-controlled block environment, so a due record can be objectively voided without executing anything (repeatable censorship escape).

*Rationale: FI-13's includability test uses "the sender's balance covers the maximum charge the transaction can impose **at that block's base fee**" and "its gas limit fits the block's gas limit"; the producer sets block contents and therefore the base fee, so a due transaction can be made non-includable in every block of a batch and the record discharged as void — the round-5 F4 route, which the per-record bounds did not touch.*

- **Rules / missing rule.** `spec/04` **FI-13** predicate and discharge: void "only if the guest determines from the batch's own execution that its transactions were not includable **in any block of the batch**"; the rule's own failure mode: "a discharge rule with any subjective or unbounded ground becomes a censorship instrument (a proposer voids what it dislikes)". The non-steerability paragraph is scoped explicitly to "the per-record bounds" only. `spec/04` **FI-12** claims the content route is closed and that "Nothing a producer chooses enters the capacity test". **Missing rule:** a floor on the batch's fee environment (e.g. the void test must use the transaction's own `maxFeePerGas` against a bound the protocol fixes, not against a producer-set base fee), or an obligation to include a due record whenever the block's *remaining* gas permits, with "full block" defined; and a decision on whether a full block counts as "not a member of its body".
- **Assumptions.** The proposer builds blocks and can fill them (paying L2 gas, much of which CONS-01(viii) credits to the fee vault); publication is permissionless and visible on L1 `FI_INCLUSION_DELAY` blocks before the record is due.
- **Concrete attack trace.**
  1. A user publishes the data of a transaction with an ordinary `maxFeePerGas`.
  2. During the `FI_INCLUSION_DELAY` window the coalition fills L2 blocks (a permitted, paying activity), pushing the EIP-1559 base fee above the published transaction's `maxFeePerGas`.
  3. At the due point every block of the batch has a base fee above it, so the transaction is not includable in any block: the guest voids the record, the frontier advances, and D-12's obligation is discharged with nothing executed. FI-13's per-record bounds are irrelevant here — it is the environment component that is steered.
  4. The user re-publishes; the cycle repeats at one L1 blob transaction per cycle for the user and one filled batch for the censor. If instead "a full block" is read as not admitting the transaction, the producer can equally keep every block full and the record can be neither included nor voided, so `c'` can never satisfy `c' ≥ min(d(A), c+cap)` — the same outcome by the other ambiguous reading.
- **Inside/outside the fault model.** Inside: one proposer acting in its ordinary role, no assumption failure, no stake, no L1 censorship. The user's counter — publish with an enormous `maxFeePerGas` and balance — turns the escape into a fee race, but the rule as written gives the producer the choice.
- **Attacker resources and cost.** L2 gas to keep blocks full (partly recycled through the fee vault) plus one batch; the user pays one L1 publication per cycle.
- **Requirement / fixed decision affected.** D-12 (upper bound on exclusion); FI-13's stated failure mode; LIVE-04(1); FI-12's "cannot halt" (a steerable void is the poison-halt escape hatch in the other direction).
- **Evidence.** `spec/04-l1-integration.html` FI-13 (predicate, discharge, non-steerability paragraph, failure mode); `spec/02-consensus.html` CONS-01(v) (the same predicate as an excusal) and CONS-01(viii). Round-5 F4, re-confirmed in its environment form.

## R6-D12-06 — Medium — MEM-13(5), CONS-16(1) and 09 row `T_ROTATE` assert that a cohort that has stopped attesting is already ineligible for the resumed set version; no rule makes the cohort's last attestation precede the rotation by a window, and the disclosed pre-signing residual covers exactly that window.

*Rationale: `T_ROTATE ≥ HEARTBEAT_WINDOW` bounds how long the chain has been stalled, not how long ago the cohort last attested; heartbeats are permissionless, L1-local and independent of L2 production, and MEM-13(2c) discloses that a finite pre-signed inventory defers exclusion, so the rotation can resume under the roster that stalled it.*

- **Rules / missing rule.** `spec/03` **MEM-13(2a)(b)** accepts a heartbeat only in the window it names; **(2b)** records `lastHeartbeatAt(v)` = the named window's start; **(3)** eligibility at a commit is `lastHeartbeatAt(v) ≥ t_root(e) − HEARTBEAT_WINDOW`; **(2c)** discloses the pre-signing horizon; **(5)** "a cohort that stops attesting is excluded at the next boundary ... and production resumes". `spec/02` **CONS-16(1)**: "`T_ROTATE ≥ HEARTBEAT_WINDOW` ... **so a cohort that has stopped attesting is already ineligible for the set version the resumed heights are assigned to**"; **CONS-16(3)**: `e_r` is "the lowest epoch ... whose stored `t_root(e_r)` is **at or after the invocation timestamp**". `spec/09` row 201 repeats the inference. **Missing rule:** either an explicit assumption (the cohort's last accepted heartbeat names a window that ended at least `HEARTBEAT_WINDOW` before the invocation) or a definition of `e_r` whose `t_root` is strictly later than `max(invocation, last-attested-window-end) + HEARTBEAT_WINDOW`.
- **Assumptions.** A cohort holding ≥1/3 of the committed weight stops producing L2 blocks (the case the rotation exists for) but keeps its heartbeat key online, or has handed a pre-signed inventory to any relayer; commits continue during the stall because `commitSet()` is permissionless and L1-clocked (MEM-09(1)).
- **Concrete attack trace.**
  1. The chain stalls at `t_L`. The trigger fires at `t_L + T_ROTATE`; a rotation is invoked at `T_inv ≥ t_L + T_ROTATE`.
  2. The cohort attests in the window containing `T_inv` (or its relayer submits a pre-signed payload then, which clause (2c) permits). `lastHeartbeatAt` = that window's start `w·W ≥ T_inv − W`.
  3. `e_r` is the lowest epoch with `t_root(e_r) ≥ T_inv`; `HEARTBEAT_WINDOW ≥ E_EPOCH_L1` (MEM-13(6)) and commits happen at least once per L1-side epoch, so `t_root(e_r) − lastHeartbeatAt(v) < W`: the cohort **is** eligible at `setVersion(e_r)`, `R_k` is the same stalled roster, and the rotated chain cannot reach `3s > 2W'`. Production does not resume.
  4. The only remaining path is GOV-04, which restores the checkpoint and resumes under the same committed version; each subsequent rotation repeats the same race until the cohort's pre-signed inventory runs out — the disclosure at (2c), not the guaranteed exclusion stated at MEM-13(5)/CONS-16(1).
- **Inside/outside the fault model.** The cohort is ≥1/3 (outside A-CONS-1's safety premise), but the rotation exists precisely for the ≥1/3-stall case and MEM-13(5)/CONS-16(1) state exclusion as a property rather than an assumption; the pre-signing residual is disclosed, so this is a Medium — an over-claim, not a new leak.
- **Attacker resources and cost.** One signing sitting (offline) plus a relayer submitting one L1 transaction per window per entry; no L2 participation.
- **Requirement / fixed decision affected.** D-14's liveness half ("exclusion at the next boundary"); CONS-16's reachability claim; MEM-13(5).
- **Evidence.** `spec/03-membership-staking.html` MEM-13(2a)–(2c), (3), (5), (6); `spec/02-consensus.html` CONS-16(1), (3); `spec/09-parameters.html` rows 201, 204–208.

## Checked, and holds (round-5 repairs I could not re-break)

- **R5T-C-2 / round-5 C-2 (heartbeat replay).** Verified against MEM-13(2)–(2c) and 09 rows 204–208: the preimage binds a versioned tag, chain id, entry, `hbWindow` and a strictly increasing `hbSeq`; acceptance requires the named window to be current and unrecorded and the sequence to advance; the recorded instant is `hbWindow · HEARTBEAT_WINDOW`, never the carrier's timestamp; a signature naming a later window cannot be accepted before that window begins, so it cannot back-date an earlier version. No replay of a captured signature moves eligibility. Holds.
- **R5T-C-1 / F3 / R5T-PDE-07 (stale anchored view).** FI-11's greatest-anchored-view rule plus `FI_ANCHOR_MAX_AGE` do bound the postponement: at any admissible landing height `H`, `A ≥ H − FI_ANCHOR_MAX_AGE`, so a record published at `b` is due at every admissible view once `H ≥ b + FI_INCLUSION_DELAY + FI_ANCHOR_MAX_AGE`, and the batch-range choice cannot shrink it. The algebra is right; the C-1 freeze is closed (its side effect is R6-D12-02).
- **R5T-PDE-01 (content route).** FI-13's per-record bounds (`FI_ITEM_MAX_BYTES`, `FI_MAX_TX_PER_RECORD`, gas sum ≤ `itemGasBound`) plus FI-12's restated divisor close the "one publication with `FI_MAX_PER_BATCH + 1` individually includable transactions" halt: an over-bound record is void in every block of every batch from its own immutable bytes. Holds (its interaction with the unenforced capacity MUST is R6-D12-04).
- **R5T-PDE-02 (recorded hashes vs `BLOBHASH`).** DA-07(5) now requires element-wise `_blobVersionedHashes[i] == blobhash(_blobIndexStart + i)` and rejects length mismatches; PRF-07(b)(i) refuses `BLOBHASH` on the referenced path. Holds.
- **R5T-PDE-03 (frontier past the register).** FI-11(5) bounds `c' ≤ nextSeq(A)`, rejects a position with no record at A, and L1-05 row 36 adds `ForcedFrontierBeyondRegister`. Holds.
- **R5T-PDE-06 (due delay vs deadline).** `FI_INCLUSION_DELAY < T_PROVE_DEADLINE` is now stated in FI-10 and registered in 09 row 189; the stronger latency form stays a disclosed unmeasured item (F-FI-2). Holds.
- **MEM-13(4) no-rule-removes-weight** and **D-14's exclusion-not-decay framing**: no rule reduces stake, weight or standing; exclusion filters future versions only. Holds.
- **MSG-03 / L1-13 / MSG-04 (message path).** Neither withdrawal eligibility nor root formation reads an anchored L1 view: MSG-03 requires a withdrawal root plus `WITHDRAWAL_DELAY` and finality, and L1-13(2) ties a signal to a root at height ≥ the signal's height; so `FI_ANCHOR_MAX_AGE` has no missing consumer there, and the L1→L2 deposit observation duty is on the Anchor at finality depth. Checked, no new finding.

## Answers to the charged questions

1. **Does the restated cap close both routes to a permanent halt?** The *content* route (round 5) is closed by FI-13's per-record bounds; the *count* route is not: CONS-01(v)'s per-block unit still contradicts the per-batch cap and the registered relation permits an infeasible registration (R6-D12-03), and the capacity MUST that would make `cap = FI_MAX_PER_BATCH` true is enforced nowhere (R6-D12-04).
2. **Is the capacity relation in enforcement units maintained by any rule?** Maintained as a *value* constraint in 09 row 186, but no enforcement point exists: neither PRF-04(vi), nor L1-05 row 36, nor CONS-01(v) rejects a below-threshold `batchGasCapacity` (R6-D12-04), and the constructive gas-limit premise is explicitly Open (F-FI-1).
3. **Does `FI_ANCHOR_MAX_AGE` bound staleness in every path that reads an anchored view, and can a producer still postpone a due point?** The due point can no longer be postponed beyond `FI_ANCHOR_MAX_AGE` — that part holds — but the bound is placed on `land`'s admission rules, where it can permanently reject a certified, in-envelope range (R6-D12-02). No other rule reads the anchored view without the bound.
4. **Is the includability predicate genuinely non-steerable?** Only its per-record-bounds half is; the environment half (base fee, block gas limit, block room) remains producer-set, and voiding a due record without executing anything is still available (R6-D12-05).
5. **Is the heartbeat window binding replay-proof across windows, epoch boundaries and the two-epoch lookahead?** Yes for replay (checked above); no for the *inference* that a stalled cohort is excluded when the resumed version is drawn (R6-D12-06), and a cohort can stay eligible without running anything for the length of its disclosed pre-signed inventory.
6. **Does the poison-payload void rule admit a censorship escape?** Yes — R6-D12-05 (environment-steered void) and, indirectly, R6-D12-01 (a dead record that can only be discharged by executing it or by the forbidden prune).

## Fault-model summary

- Inside the fault model, no adversary or assumption failure needed: R6-D12-01 (rule conflict), R6-D12-02 (in-envelope batch ages out), R6-D12-03 (legal registration halts the chain), R6-D12-04 (submitter-chosen cap, `cap = 0` reachable), R6-D12-05 (single proposer voids a due record).
- Outside/borderline: R6-D12-01's permanent-halt ending and R6-D12-06 need ≥1/3 non-participation (the stall case the specifications' own recovery paths exist for) and/or data aging out of the retrievability window.
