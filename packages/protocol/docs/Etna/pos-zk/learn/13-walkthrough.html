13 — Putting it all together: one batch end to end

Problem this lesson solves. It follows a single user transaction all the way from an L2 proposal to an eligible withdrawal, naming the exact status label, the evidence held and what could still go wrong at every step.

In plain language

The batch. A user transaction enters the L2 mempool. The proposer selected by the epoch's weighted rotation (CONS-06) builds a block at height H and proposes it; the block body is what a receiver first holds, which is only proposed. Each validator executes the block against the parent state and checks every consensus and validity rule (CONS-01) — there is no forced-inclusion duty to check, because the design has no forced-inclusion path (FI-REMOVED-01) — which makes it locally execution-valid for that node only. Validators then prevote and precommit; once a commit certificate carrying strictly more than two thirds of the epoch's voting power is published and the node has checked data availability for itself, the block is PoS-finalized (Mode A). Under Mode A that status is never revoked.

The batch closes and the proof is built. A batch is a contiguous range of L2 blocks — the parameter table's placeholder is 32 blocks, about 64 seconds at the 2 s cadence, and the value is unmeasured. The batch data and the finality evidence are the witness for one combined guest program; a prover that finishes produces a proof bound to exactly this batch's data commitment, which is proof-ready. A normal proof may take the whole D6 envelope of up to 30 minutes — 900 L2 blocks — and that is not misconduct (LIVE-02). L2 keeps producing throughout, until the consensus-enforced unsettled-depth cap binds, at which point production stops safely (HALT-03).

Landing is one transaction. Anyone may call the Inbox's single acceptance entry point with the batch data and the proof; the Inbox derives every contract-derived public input itself, checks blob openings if blobs are used, runs the active verifier route, and only then writes one checkpoint and advances the height pointer (L1-01, L1-03). There is no state between "transaction exists" and "batch accepted": the data, the proof and the checkpoint write are the same transaction (DA-01). That is accepted on L1.

Ethereum finality and the exit. Once the accepting L1 transaction is in a finalized Ethereum block, the batch is Ethereum-finalized. Then, and only then plus the message-authentication path and WITHDRAWAL_DELAY, does a withdrawal become withdrawal-eligible: the checkpoint's stateRoot must cover the signal, and where the claim depends on a reorganisable L1 fact the accepting transaction must be Ethereum-final (MSG-03). The delay is a derived parameter whose terms are unmeasured, and a settlement halt delays withdrawals indefinitely while forfeiting nothing.

What the labels force an interface to say. A progress indicator must use these labels and state which one it is showing; a "confirmation" shown before accepted on L1 must be accompanied by the statement that the batch's data and proof are not yet on Ethereum (STATUS-11). Two statuses are local (proposed, locally execution-valid), one is a commitment (voted), and the rest are progressively stronger public states.

Precise definitions

  • proposed — a block body received from a leader; evidence is the object itself; guarantee none; discarded freely (STATUS-01).
  • locally execution-valid — this node executed it against a known parent and all rules passed; the guarantee is only that this node will not build on an invalid block; revoked if the parent is displaced (STATUS-02).
  • voted — a validator signed a vote at a (height, round); the signature irreversibly constrains its future votes through the lock rule; conflicting votes are slashable equivocation (STATUS-03, CONS-11).
  • PoS-finalized — a published commit certificate over (chain id, epoch, height, block hash) with strictly more than two thirds of the epoch's power, plus the receiver's own data-availability check; permanent in Mode A (STATUS-04).
  • proof-ready — a completed ZK proof bound to this batch's data commitment; a proof of a different batch is no substitute (STATUS-05).
  • accepted on L1 — the Inbox accepted data and proof in one transaction and advanced its checkpoint; revocable only by an L1 reorganisation below finality (STATUS-06, L1-12).
  • Ethereum-finalized — the accepting L1 transaction is in a finalized block, or the L1 fact the claim depends on is at the configured finality depth (STATUS-07).
  • withdrawal-eligible — accepted on L1 or Ethereum-finalized, plus the message-authentication path and any delay required by MSG-03 (STATUS-08).
  • Local receipt is not availability, and an elapsed timeout is never evidence of absence (STATUS-09, STATUS-10).

Attacks this prevents

  • Premature withdrawal. No value leaves on a PoS confirmation: the path requires a checkpoint written by a verified land, plus the delay, plus finality where needed (STATUS-08, MSG-03).
  • Data published without a proof. The one atomic entry point makes the data-first class impossible for a pending batch (L1-01, INV-02).
  • Checkpoint writes without verification. The Inbox verifies before it writes, so no partial effect and no accepted unproven batch exists (L1-03).
  • Witness-only execution. A batch whose payload arrived only through a private witness cannot land (DA-04).

Attacks this does not prevent

  • Loss of the data before the proof exists. If every holder of a finalized block's data disappears, settlement halts and may be permanent (LIVE-01, LIM-01).
  • ≥ 1/3 Byzantine stake. Two conflicting certificates can both verify; the labels above do not repair it (INV-01).
  • Prover centralisation and slowness. Any prover may take over the same batch, but if nobody completes a proof the cap eventually binds and production stops (HALT-03, WH-01).
  • Losses and speed. Penalties do not compensate, no universal bound on loss is claimed, and a halt delays withdrawals indefinitely (ECON-11, MSG-03).

Self-check

At which status may a user safely treat the transaction as settled on Ethereum?

At accepted on L1: the data and a valid proof are in one L1 transaction and the checkpoint has advanced. Withdrawal additionally needs the delay and, where relevant, Ethereum-finalized (MSG-03). Anything earlier must be labelled as not yet on Ethereum (STATUS-11).

A batch is PoS-finalized and its prover goes offline. Does another prover have to start from scratch?

No. Any permissionless prover may produce the proof for the same data commitment and land it; a proof of a different batch is not a substitute, and a slow proof inside the D6 envelope is not misconduct (L1-04, L1-10, HALT-03).

The L1 transaction lands, then an L1 reorg removes it. Is the L2 block no longer finalized?

It remains PoS-finalized under Mode A. The transaction is undone by Ethereum — no checkpoint, no fee paid — and the batch must be re-landed with the same data commitment; the Inbox must not "repair" a reorg by writing a chosen checkpoint (L1-12, STATUS-06).

Challenge this. The walkthrough relied on: (i) an honest proposer at this height and honest validators executing CONS-01; (ii) A-CONS-1 and the partial-synchrony assumptions A-CONS-2/A-CONS-3 for the four-second claim — an expectation, not a measurement; (iii) A-CONS-5 and A-DA-2 for retaining data and completing proofs; (iv) A-L1-1 for L1 inclusion and finality; (v) A-CRYPTO-1/A-CRYPTO-2 for proof soundness and signature unforgeability; (vi) every timing entry being a planning envelope built from decided or unmeasured inputs, with K = 32 blocks, D_MAX, the round budget and WITHDRAWAL_DELAY unmeasured; (vii) no halt occurring during the walkthrough.
