05 — Changing the validators without changing history

Problem this lesson solves. It explains how the validator set can change from epoch to epoch without re-judging — and therefore without invalidating — the certificates that older sets already signed.

In plain language

If the people who decide the order never changed, a chain would be simple and useless: honest operators retire, keys rotate, new stake arrives. The hard part is changing the deciders without changing the past. A design that lets a new set re-judge old blocks turns every handover into an opportunity to rewrite history. A design that freezes the set forever cannot accept new stake. This lesson is about the rule that gets both.

Epochs. An epoch is a logical interval during which one validator-set version is authoritative. Epochs are numbered, and the set for epoch e is fixed before e begins (glossary, CONS-13). "Logical" matters: the rule is about identifiers, not a wall clock (GEN-06).

Set roots. The set is an ordered list of (public key, effective stake) entries, committed to as a root (the validatorSetRoot of the proof statement) (MEM-08, PRF-02). Two properties make it usable: block headers authenticate it (CONS-10), and the authoritative value comes from L1 state — the proof's witness may carry the entries, but no witness element may define the set (PRF-03, PRF-13). A prover that supplies its own set and matching signatures would otherwise "prove" finality about a chain no independent validator ever saw.

One-epoch lookahead. The set commitment for an epoch is made before that epoch begins — the rule is stated as set-snapshot timing with one-epoch lookahead (MEM-09, CONS-13). The reason is not elegance: if the set were decided during the epoch, L2 progress would wait on an L1 transaction, and nodes could disagree about which set applies at a given height. The design instead assumes — and names as an assumption — that set transitions are deterministic functions of L1-committed state, so all correct nodes agree on set version k for a given epoch (A-CONS-4).

An epoch-scoped certificate never expires. A certificate is judged under its own epoch's set and remains valid forever (CONS-08, glossary). This is not a convenience; Mode A's whole promise depends on it. The recovery rule states it as a positive obligation: validator rotation cannot re-judge a certificate, and no admission rule may reject a batch that extends the current checkpoint (REC-01 c). In one sentence: new sets get new heights; they do not get a new opinion about old heights.

The handoff is the delicate part. At the boundary, the last header of the closing epoch must commit to the opening epoch's set, and the first block of the new epoch must commit to the last block finalized in the previous epoch — locks carry across the boundary (CONS-09, PRF-05). The argument that this keeps safety across a boundary is stated as Assumed-with-argument, not proven: the architecture decision calls it "the delicate modification" (M2), the assurance page records it as argued rather than machine-checked and names it review target F1, and it appears as premise P5 of the uniqueness invariant (INV-01, LIM-01, 04 — architecture decision §2.1 and §7). The honest reading: if the handoff argument fails, a boundary fork needs one third equivocation across the boundary — objective and slashable — but the specification does not claim the argument is proven.

Precise definitions

  • Epoch. A logical interval with one authoritative validator-set version; numbered, and the set is fixed before the epoch begins (glossary, CONS-13).
  • Validator-set version / set root. The committed form of the epoch's ordered (public key, effective stake) entries; constructed per MEM-08 and supplied to the proof as an L1-derived public input (MEM-08, PRF-02).
  • One-epoch lookahead. The set snapshot for an epoch is committed before that epoch starts (MEM-09, CONS-13), so that set transitions are a deterministic function of L1-committed state (A-CONS-4).
  • Epoch-scoped certificate. A certificate judged under the set of its own epoch and valid forever (CONS-08); rotation cannot re-judge it (REC-01 c).
  • Set-transition evidence. What a batch spanning a boundary must carry: the closing epoch's commitment to the next set, the new epoch's commitment to the last finalized block, the L1-fixed set commitment, and strictly increasing epoch numbers (PRF-05).
  • Handoff and lock carry-over. The boundary rule that the new epoch's first block commits to the previous epoch's last finalized block and locks carry over (CONS-09); evidence tag Assumed-with-argument (PRF-05 note, LIM-01).
  • Weak subjectivity. The trusted starting point a fresh node needs; here the L1 checkpoint is the natural source, with a freshness window (glossary, MEM-11).

Read the last row carefully. With a 300-block epoch, a set root committed at the start of epoch e for epoch e+1 has about 10 minutes to become Ethereum-final, while the sourced Ethereum finality figure is about 12.8 minutes. The specification's own response is exactly what its tags say: EPOCH_LEN_L2 is a placeholder until measured, and EPOCH_LEN_L1 is a derived formula whose inputs are unmeasured. The course does not pick a value, and no lesson may present 300 (or 10 minutes) as measured (LIM-01, PARAM-03).

A second, smaller illustration of lifetime. Suppose a batch's head block is in epoch 7 and the batch is proven much later, when the chain has entered epoch 40. The guest checks the head block's certificate under epoch 7's set — the root the L1 staking contract fixes for that epoch — and the epoch-boundary transitions the batch crosses (PRF-05). The 33 epochs of rotation in between (derived: 40 − 7) change nothing about that judgement: the certificate remains valid forever (CONS-08). One certificate per batch needs verifying, and its validity extends to the prefix it commits to, under the premises of PRF-08.

Attacks this prevents

  • Set substitution. A prover supplying a set it controls together with matching signatures: the set is accepted only if its commitment equals the L1-derived validatorSetRoot (PRF-03, PRF-13).
  • Retroactive re-judging. A later set invalidating an earlier certificate. Rotation cannot re-judge, and no admission rule may reject a batch extending the current checkpoint (CONS-08, REC-01 c).
  • Set ambiguity at a height. Nodes disagreeing about which set applies: the set is a deterministic function of L1-committed state, fixed before the epoch begins (A-CONS-4, CONS-13).
  • Stalling on L1 inside an epoch. One-epoch lookahead means L2 does not wait for an L1 transaction to learn its own validator set (MEM-09).
  • Skipped transitions. A batch spanning a boundary must carry the transition evidence; transitions may not be skipped (PRF-05).

Attacks this does not prevent

  • A boundary fork. The handoff argument is Assumed-with-argument. If it fails a conflicting history at the boundary needs one third equivocation across the boundary — objectively slashable, but not prevented by the argument being written down (CONS-09, LIM-01, INV-01 P5).
  • A safety failure above one third. Two conflicting certificates can both verify and a proof cannot detect it (A-CONS-1).
  • Malicious governance. Governance can rewrite rules, including these; the specification states that as a separate failure class outside the protocol's protection (GOV-02, LIM-01).
  • Long-range and weak-subjectivity attacks. A fresh node still needs a trusted checkpoint within a freshness window; rotation does not remove that need (MEM-11, MEM-12).
  • Implementation defects in the commitment construction or the transition checks (LIM-01, scope row).

Self-check

A validator joins after block H was finalized. Does H have to be voted on again?

No. A certificate is judged under its own epoch's set and remains valid forever (CONS-08), so validator rotation cannot re-judge it (REC-01 c). New sets get new heights, not a new opinion about old ones.

When must the set root for epoch e be committed, and why?

Before epoch e begins, with one-epoch lookahead (MEM-09, CONS-13), so that all correct nodes agree on the set version and L2 never waits on an L1 transaction inside an epoch (A-CONS-4).

What is the evidence status of the handoff lock-carry-over argument?

Assumed-with-argument. PRF-05's note says exactly that of CONS-09; the architecture decision calls it the delicate modification M2, the assurance page records it as argued rather than machine-checked with review target F1, and it is premise P5 of INV-01. It is not presented as a proof.

Challenge this. The lesson relied on: (i) the L1 staking contract being able to supply the set root for the epoch a certificate belongs to, since PRF-02 marks validatorSetRoot as an L1-derived input; (ii) set transitions being deterministic functions of L1-committed state (A-CONS-4); (iii) the handoff argument holding — it is Assumed-with-argument, and F1 is the named falsifier; (iv) 300 blocks and the 12.8-minute Ethereum finality figure being a placeholder and a sourced configuration value, with the 10 < 12.8 comparison being the course's arithmetic rather than a specification statement; (v) epochs being logical identifiers rather than wall-clock intervals (GEN-06). Falsifier: show that a certificate from an old epoch is judged against a newer set anywhere in the specification, or that the handoff is described as proven — either would contradict CONS-08 or the Assumed tag.
