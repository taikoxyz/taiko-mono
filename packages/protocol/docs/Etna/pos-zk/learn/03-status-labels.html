03 — What "confirmed" actually means

Problem this lesson solves. It gives the eight status labels with the evidence each one requires, the guarantee it carries and the condition that can revoke it, so that no interface or document has to invent a word like "confirmed".

In plain language

A status label is not decoration. Each one is a promise about evidence: what a participant must actually hold before the label is true. "proposed" means only that an object arrived. "voted" means a validator signed. "PoS-finalized" means a published certificate with more than two thirds of an epoch's voting power, plus the receiver's own data check. A word like "confirmed" names no evidence, so nobody can check it and nobody can be shown to have been wrong when they used it.

The specification closes that hole twice. GEN-07 makes the status labels the controlled vocabulary and forbids introducing a synonym for one or redefining a glossary term locally. STATUS-11 adds a disclosure obligation: any interface, document or learning page that shows a progress indicator must use these labels, must state which status is being shown, and — for anything shown before the label accepted on L1 — must say that the batch's data and proof are not yet on Ethereum.

There are eight labels (01 — requirements and threat model §2, STATUS-01–STATUS-08). One of them carries two names because it has two modes: in the selected Mode A the label is PoS-finalized and it is permanent; in the unselected Mode B the same certificate would be labelled PoS-certified / provisional and would be revocable through the published recovery rules. The rest of the course uses the Mode A name because Mode A is what was selected, and says so whenever the difference matters.

Rules about labels are not labels. Three more rule ids complete the picture: STATUS-09 (a node's local possession is not availability for anyone else), STATUS-10 (an elapsed timeout is never evidence that something does not exist) and STATUS-11 (the disclosure obligation). They constrain what may be claimed; they are not statuses a block can hold.

Precise definitions

  • Status label. One of the eight names fixed by the specification, each with an evidence set, a guarantee, a revocation condition and an audience (STATUS-01–STATUS-11, GEN-07).
  • Evidence. What the holder of the status must have — not what it has heard about. For finality this includes a published commit certificate and the receiver's own data check (STATUS-04).
  • Guarantee. What a user may rely on once the evidence exists. For locally execution-valid it is local: this node will not build on an invalid block (STATUS-02).
  • Revocation. The condition that can take the status away. A vote can never be revoked — it is a signed commitment — while accepted on L1 is revocable by an L1 reorganisation below finality (STATUS-03, STATUS-06).
  • Disclosure obligation. The duty of any progress display to use the labels, to say which status it shows, and to carry the "data and proof are not yet on Ethereum" statement before accepted on L1 (STATUS-11).

Now the same display, rewritten. Each line names a status and carries the STATUS-11 sentence when it is shown before accepted on L1:

  • "proposed — no guarantee" (STATUS-01).
  • "locally execution-valid on this node — not agreement with anyone else" (STATUS-02).
  • "PoS-finalized (Mode A) — the batch's data and proof are not yet on Ethereum" (STATUS-04 and STATUS-11). A display may only show this once a published certificate exists and the party showing it has done the data check the rule requires; otherwise it is showing evidence it does not hold.
  • "proof-ready — still not settled on Ethereum" (STATUS-05).
  • "accepted on L1 — data and proof are on Ethereum" (STATUS-06).
  • "Ethereum-finalized" (STATUS-07) and then "withdrawal-eligible" (STATUS-08) once the message path and delay are satisfied.

Attacks this prevents

  • Silent status inflation. A display that shows a weaker status with a stronger word, so a user acts on a guarantee the evidence does not support (STATUS-11, and the specification's warning against substituting "confirmed" for a weaker status).
  • Vocabulary drift across documents. The same word meaning different guarantees in the specification, a UI and a blog post (GEN-07).
  • Withdrawal on a "confirmation". A user treating a 2 s or certificate-time display as settlement when accepted on L1 has not happened (STATUS-06, STATUS-08).
  • Ambiguous "final". Collapsing PoS-finalized and Ethereum-finalized, which have different evidence and different revocation conditions (STATUS-04 vs STATUS-07).

Attacks this does not prevent

  • A dishonest interface that simply ignores the labels. The specification states the obligation and its failure mode; this course did not find a stated on-chain enforcement mechanism for STATUS-11 in the pages that exist at revision 2026-10-05 — a finding to report rather than paper over.
  • The underlying failures the labels describe: an unavailable finalized block still halts settlement, and a one-third Byzantine coalition still breaks the uniqueness premise (HALT-01, INV-01).
  • A user who reads the correct label and does not understand it.
  • Anything outside the rule's trigger: STATUS-11 speaks of interfaces, documents and learning pages that show a progress indicator (the course's reading of its scope; the specification text governs).

Self-check

Which two labels can the bare word "final" hide, and why does it matter?

PoS-finalized (STATUS-04, evidence: a published commit certificate plus the receiver's data check) and Ethereum-finalized (STATUS-07, evidence: the accepting L1 transaction in a finalized Ethereum block). They have different evidence and different revocation conditions, so collapsing them changes what a user may rely on.

What must accompany a "confirmation" shown before accepted on L1?

The statement that the batch's data and proof are not yet on Ethereum (STATUS-11), and the display must name the status it is actually showing.

My node holds the block body. May it report the block to a peer as accepted on L1?

No, twice over. Local possession is not availability (STATUS-09), and a node may not report a status above voted on the basis of local possession alone. Accepted on L1 requires the L1 transaction that carried data and proof (STATUS-06).

Challenge this. The lesson relied on: (i) the eight-label enumeration of 01-requirements §2 with 4a/4b sharing one number and one mode being unselected; (ii) the claim that summarising a rule in a table does not restate it — the specification text remains normative and wins; (iii) the invented UI strings being an illustration, not a measurement of any real interface; (iv) the course's reading that STATUS-08 applies to a withdrawal claim rather than to a block, while the requirements document describes all eight as statuses "a block or batch may hold" — a tension the lesson flags rather than resolves; (v) "final" and "confirmed" being banned only when substituted for a weaker status, not as English words.
