Glossary

Every term the course uses, in one table, with the meaning the specification fixes for it.

This is a design. Nothing described by these terms is implemented, deployed, audited or measured. Terms are defined here in plain language; the authoritative definitions and the exact rules are in the specification glossary.

The idea

The design uses a controlled vocabulary. Each term below has exactly one meaning everywhere: in the specification, in a client, in an interface and in this course. Two rules follow from that.

Status labels are normative. A status is not a mood or a progress bar; it fixes the evidence a participant holds and the guarantee a user may rely on. No stronger word may be substituted for a weaker one: a batch that is PoS-certified is not “settled”, and a batch that is accepted on L1 is not yet Ethereum-final.

“Final” is reserved for Ethereum-final. A PoS confirmation above the latest checkpoint accepted on Ethereum is PoS-certified / provisional: the certificate is valid, but a permissionless, bonded, delayed recovery may still replace the history it belongs to. The word “final” is used only for the accepting L1 transaction in a finalized Ethereum block.

The status ladder

Terms

TermMeaning
BatchA contiguous range of L2 blocks accepted on Ethereum by one proof-gated L1 transaction whose statement binds the range’s data — carried by that transaction, or published earlier in blobs and referenced as a live publication record — and its validity proof. There is no path that accepts data without a proof, and publication on its own accepts nothing.
BlobAn EIP-4844 data container on Ethereum. A batch’s data may travel as blobs instead of calldata, and blobs are the form a publication record carries; either way the checkpoint advances only on a valid proof.
Blob bound on batch sizeA derived limit on how many L2 blocks one batch may contain. At the DA-bound target rate one 2-second L2 block is one 131,072-byte blob, EIP-7691 allows 6 blobs per L1 block as the target and 9 as the maximum, and a batch’s data must fit in one L1 transaction — the accepting one when the data is carried, or the publication one when it is published earlier — so a batch is at most about 6 blocks at the target rate, and 9 blocks is the hard ceiling. Batch length is set by data and by one-transaction publication, not by preference. derived from sourced constants.
BlockAn L2 block: ordered transactions and the state that results from executing them. Blocks are produced every two seconds under the stated operating assumptions.
Bridge message authenticationThe rule that a cross-chain message may be acted on only when the L1 checkpoint that anchors it is accepted and the message’s own authentication path passes. It is what makes an L1-accepted batch unlock withdrawals.
CadenceHow often a new L2 block is produced: one every two seconds. Cadence is not finality, not proving latency, not L1 acceptance and not withdrawal latency.
CalldataThe byte field of an Ethereum transaction. A batch may publish its data as calldata; the accepting contract then computes the data commitment itself from the exact bytes.
Censorship resistanceA conditional statistical property, not a guarantee. Proposer selection is hash-based and weighted, so a coalition with less than a third of voting power is selected for fewer than a third of slots in expectation, and a transaction that reaches honest validators is included by the first honest proposer with room for it. There is no per-transaction inclusion guarantee and no general inclusion list; data published to L1 comes under the narrow forced-inclusion obligation, which bounds exclusion but promises inclusion at no particular height (FI-10–FI-14).
CheckpointThe L1 record of the last accepted batch: L2 height, block hash, state root, epoch and validator-set root. It is the anchor a fresh node syncs from and the fork-choice limit a node must not contradict.
Commit certificateThe evidence that more than two thirds of an epoch’s voting power precommitted one block at a given height and round. A certificate is judged under its own epoch’s set and remains valid forever.
Commit ruleA block is certified at a node when it holds a valid commit certificate for that height, it has performed its own data-availability check, and its parent is the block that node certified at the previous height. The rule prevents two conflicting certificates; it does not make the confirmation permanent above the latest accepted checkpoint.
Configuration registry and configuration hashThe Inbox’s append-only mapping from an epoch to its configHash. The entry is computed by the contract from its own storage and deployed code, written before that epoch starts, and immutable once written: no upgrade, recovery path or governance call may edit or rewrite the entry of an epoch already entered, so an upgrade binds future epochs only. configHash is a public input of the proof, and the guest recomputes it from the configuration it actually applied. The per-epoch registry is what stops a routine upgrade from moving the configuration hash and making every in-flight proof fail.
Data availability (DA)Whether the data needed to reconstruct a batch is actually retrievable by others. A node holding a block may not treat its own possession as evidence that the data is available to anyone else. A batch’s canonical data location is the accepting L1 transaction — its calldata or blob sidecars — or the live publication record that transaction references (DA-01).
Data commitmentThe canonical hash commitment to a batch’s data. On the calldata path the L1 contract computes it; on the blob path the guest checks it in addition to the blob binding.
Effective stakeThe TAIKO a validator has bonded in the custody ledger, is active with, has not exited from and has not had slashed. Effective stake is voting power, one base unit to one unit of weight; there is no multiplier or age bonus, and no rule reduces it for silence. Eligibility for a future set version is a separate condition: an entry that has not posted a heartbeat within HEARTBEAT_WINDOW keeps this effective stake but is not selected into that version.
EpochA logical interval during which one validator-set version is authoritative. Epochs are numbered, and the set for an epoch is fixed on L1 before the epoch begins.
Epoch handoffThe rules that carry locks and certified history across an epoch boundary. A certificate is always judged against its own epoch’s set, so changing the set never re-judges old votes.
EquivocationOne validator signing two conflicting messages of the same type at the same (height, round). It is the only consensus offence with self-authenticating evidence: the two signed messages are the whole proof.
ETHEther. All gas, all L1 costs and all validator and prover rewards are denominated and paid in ETH; TAIKO is never the reward asset.
Ethereum-finalA status: the accepting L1 transaction is in a finalized Ethereum block, or the L1 fact a claim depends on has reached the configured finality depth. Only Ethereum-final L1 facts may enter L2 consensused state.
Forced inclusionThe narrow obligation that follows publishing a transaction’s data to L1: once the published record is due, a batch must resolve it within the capped first-in-first-out prefix — include it in a proven batch, or discharge it as void on objective grounds. It is an upper bound on exclusion, never a promise that any particular transaction is included at any height, and it reaches nothing that is not published; the design has no general inclusion list (FI-10–FI-14).
GossipThe peer-to-peer channel over which proposals, votes and certificates are spread. Losing a message is never evidence about a validator: only signed objects count.
Heartbeat (L1 liveness attestation)An attestation, signed with a validator’s ECDSA (secp256k1) heartbeat key and submitted in an Ethereum transaction, that the validator is alive; L1 records lastHeartbeatAt(v). Eligibility for a future set version requires a heartbeat within HEARTBEAT_WINDOW ending at that version’s commit point. An entry that has not attested is excluded from the root — never decayed, slashed or reduced — keeps its full effective stake, and becomes eligible again by attesting. The heartbeat key is distinct from the Ed25519 consensus key and is bound to the same entry at bonding time. Anyone may submit the attestation, and a relayer may batch many validators’ signatures in one transaction. The honest costs are a periodic Ethereum transaction and a second key; an operational lapse is an outage, because a forgotten heartbeat loses the slot until the validator attests again. The window and the transaction cost are unmeasured.
InboxThe L1 contract that accepts a batch — binding the data carried by the accepting transaction or the live publication record it references, together with a validity proof — advances the checkpoint and holds the prover reward ledger. It is the only writer of checkpoint records.
L1 / L2L1 is Ethereum: it provides data availability, proof verification, settlement and bridge anchoring. L2 is this chain, whose own proof-of-stake validators decide ordering and finality.
LockA validator’s signed commitment to one block (or to nil) at one height. The lock constrains what the validator may vote for at that height; it is created and released only by the lock rule.
Lock ruleA validator must not precommit a block without a proof-of-lock-change for it at that round, and must not prevote anything other than its locked value while locked at that height. A lock is released by the commit of the locked value at that height within the current generation, by a strictly later same-height PoLC for a different value, or by the retirement of the height in a completed recovery. A lock at a retired height is void: the validator is not stuck, and the old locked value is not evidence of misbehaviour and not a reason to halt.
PoLCProof of lock change: more than two thirds of prevotes for a particular block or nil at a given height and round. It is what lets a locked validator unlock at a later round, and it must be verified, never taken from a proposal’s advisory field.
PoS-certified / provisionalA block is PoS-certified when a valid commit certificate exists for its height and round, the certificate carries more than two thirds of the epoch’s voting power, and this node has performed its own data-availability check. Above the latest checkpoint accepted on Ethereum the status is provisional: the certificate is valid, but a permissionless, bonded, delayed recovery may replace the history it belongs to. Only the accepting L1 transaction, once Ethereum-final, is called final.
ProposerThe validator selected to propose the block for a height and round. Selection is a public deterministic function weighted by voting power, so the proposer of any future slot is computable in advance.
ProverAnyone who produces a validity proof for an unsettled batch and lands it in one L1 transaction that carries the data or references a live publication record. Entry is permissionless; no duty, bond or registration is imposed, and a slow prover inside the thirty-minute envelope commits no offence.
Proof (validity proof)A zero-knowledge proof that the batch’s blocks were correctly executed and that the consensus finality evidence for them is valid, bound to the batch’s data. Ethereum verifies it; a verifier contract accepts nothing weaker.
Proof-readyA status: a completed proof bound to this batch’s data commitment exists off-chain. It means the batch can be landed, not that it has been.
Publication recordThe L1 record written when any account publishes a batch’s data in blobs before its proof: the ordered blob versioned hashes, the claimed batch range, the data mode and data commitment, the L1 block number, a sequence number and a proving deadline. It writes no batch state, advances no height and accepts nothing; a proof may reference a live record, and a record that is not proven before its deadline is discarded and can be re-published (DA-07–DA-09).
QuorumThe single predicate 3 · s > 2 · W in checked arithmetic, where s is the voting power that signed and W the epoch’s total voting power. The L2 client, the zkVM guest and the L1 contract evaluate it identically; equality does not reach quorum.
RecoveryThe permissionless, bonded and delayed replacement of history above the latest checkpoint accepted on Ethereum (REC-02). After a settlement stall anyone may invoke it by posting the bond; honest progress accepted before the completion transaction is included cancels it and sends the whole bond to the treasury. It restores the current L1 checkpoint wholesale, chooses no configuration value, may not touch anything at or below the checkpoint, and permanently retires the heights it discards.
Recovery bondThe ETH an invoker posts on L1 to start a recovery. It splits at invocation into a non-refundable component, transferred to the protocol treasury and never returned, and a refundable balance returned only if the recovery completes. The non-refundable component is paid on every attempt, whether the recovery completes, is cancelled or fails in any other way; it is sized to the cost of a spurious trigger, B_REC_KEEP ≥ C_SPURIOUS = C_GAS_REC + C_REORG + C_DISRUPTION, so it prices spam and manipulation rather than the value the rollback destroys. The bond escalates with the number of attempts in a rolling window, and a cooldown follows every attempt. A completed recovery also earns the invoker the fee-funded completion reward REC_REWARD from the reward pool, bounded by the pool’s realised balance and zero when the pool cannot pay — the recovery still completes. The sizing components and the reward inputs are unmeasured.
Recovery generationA counter held with the accepted checkpoint and incremented by exactly one per completed recovery. It is a public input of the proof, so a batch certified under an older generation is rejected. It is only a cheap invalidation of proofs that were already generated: the property that a discarded branch cannot be reinstated rests on the retired heights, because a batch is judged by where it starts, not by which proof was used.
ReplayWhat happens to the L2 transactions in blocks a recovery replaces: they are not replayed automatically and inclusion is not guaranteed, so the user must resubmit them. Replay protection is expressed only in the preserved encodings of MSG-02: an L1→L2 message is authenticated by its SIGNAL slot keccak256(abi.encodePacked("SIGNAL", chainId, app, signal)), and an L2→L1 message by keccak256(abi.encode("TAIKO_MESSAGE", message)). A message whose receipt lies inside the discarded range rolls back with that range and may be relayed again; a receipt at or below the restored checkpoint persists and must never execute twice. Recovery adds no further replay key.
Retention windowHow long batch data and witnesses must remain retrievable for settlement to be possible. Retention is a liveness assumption, not an enforceable duty: failing to serve produces a halt, not a penalty.
Retired height / resumeHeightAfter a completed recovery, resumeHeight is recorded on L1 as the last discarded height plus one. Every height below it is permanently retired: it can never be certified or landed again, by anyone, at any generation. A batch must start at max(lastLandedHeight + 1, resumeHeight), correct validators must not sign a proposal below it, and locks at retired heights are void. Retirement is bounded: resumeHeight − lastLandedHeight ≤ D_MAX.
Rollup (PoS-sequenced validity rollup)The honest name for this architecture. L2 proof-of-stake determines the binding order of transactions; Ethereum provides data availability, proof verification and settlement. It is not a based rollup, and Ethereum proposers do not sequence L2 blocks.
Safe haltA correct participant stopping rather than choosing between conflicting histories. A halt is a permitted outcome, including a long or permanent one: a settlement stall past T_STALL has the recovery path, while a halt over missing data or participation at or below the latest accepted checkpoint can still be permanent.
Set rootThe commitment to one validator-set version: the chain id, the version number and the ordered list of (public key, effective stake) pairs, and nothing else. It is written to L1 state by the staking contract; a prover may never choose it.
Set versionA numbered snapshot of the validator set. Versions are append-only, drawn from the entries eligible by heartbeat at the commit point, fixed on L1 two epochs ahead, and immutable once an epoch starts.
Settlement stall (T_STALL)The one objective trigger for recovery: no batch extending the current L1 checkpoint has been accepted for T_STALL. The threshold is strictly larger than the proof envelope, so a normal slow proof or a single prover failure inside the envelope cannot trigger it, and it is measured on L1, so no participant’s local view can declare it early. The value is unmeasured. An empty or below-cost reward pool reaches the trigger with no adversary at all, and recovery cannot repair an economics stall.
Signer bitmapThe authenticated bit field saying which validators signed a certificate. It is a public input of the proof, and the only object that can carry attested participation to L1 for reward payment.
Slashing / slashableDebiting bonded TAIKO because objective evidence proves a listed offence. Slashable stake is stake committed to an epoch whose evidence window is still open; a slash never rewrites history and is not compensation.
StakeTAIKO bonded in the L1 custody ledger. It is not transferable, not delegable, not represented by a receipt token, and not readable from the token’s vote checkpoints.
Status labelsThe controlled progress vocabulary: proposed, locally execution-valid, voted, PoS-certified / provisional, proof-ready, accepted on L1, Ethereum-final, withdrawal-eligible. Any interface that shows progress must use these labels, say which one it is showing, and label a confirmation above the latest accepted checkpoint as replaceable.
TAIKOThe existing ERC-20 token used for staking and slashable collateral, at 18 decimals. It is not the reward asset and the protocol cannot mint it.
Total voting powerThe sum of effective stake over the entries of one set version, published with the set root. It is the denominator of the quorum predicate and of the correlated penalty.
TreasuryThe fixed protocol address that receives every slashed amount except the reporter bounty, the non-refundable recovery-bond component on every attempt, and the whole recovery bond when a recovery is cancelled by honest progress. When a correlated penalty is collected there are three named destinations: a keeper fee of CORR_KEEPER_PPM of the amount collected paid to the caller, the reporter bounty where a separate evidence submitter is entitled to it, and the remainder to the treasury. The destination is fixed: the treasury is where penalties end up, there is no burn address, and the reporter bounty is strictly below the total penalty debited.
Unsettled depthThe number of L2 blocks between the highest L1-accepted checkpoint and the block under consideration. Correct validators refuse to vote past a cap on this depth, which is how production backpressures when proofs fall behind.
ValidatorAn operator that bonds TAIKO, registers a consensus key and an ECDSA heartbeat key, and takes part in proposing and voting. Its duties are to propose when selected, validate what it votes for, obey the lock rule, hold the data it voted for, and post a heartbeat on L1 to stay selectable for future set versions; it earns ETH only for participation that a landed batch attests, while a missed heartbeat costs the slot and not stake.
Validator setThe validators of one epoch, fixed on L1 before the epoch starts and drawn from the entries that are eligible by heartbeat at the commit point. It is a deterministic function of committed L1 state; no committee, sortition or per-address cap exists.
Voting powerExactly a validator’s effective stake in the epoch’s set version. The same weights are used for quorum and for proposer selection.
Weak subjectivityThe trusted starting point a fresh node needs. Here it is the latest L1-accepted, Ethereum-final checkpoint, and it must be no older than a fixed freshness window; a node that cannot obtain a fresh one must not present the history it syncs as verified. This is what handles long-range attacks.
WitnessThe data a prover needs to re-execute a batch and build the proof: block bodies, state and the L1 facts the blocks consumed. It is reconstructed from public data; it is never a substitute for on-chain data availability.
Withdrawal delay (D_WITHDRAW)How long after an exit becomes effective an owner must wait before withdrawing, on top of the requirement that every evidence window the stake was exposed to has closed. It is derived from the whole detection-and-settlement pipeline, not from proving latency alone.
Withdrawal-eligibleA status: an L1-accepted (or Ethereum-final) batch plus the message-authentication path and any required delay. It is strictly later than L1 acceptance.
zkVM / guestThe virtual machine that executes the proof program and the program itself. The guest verifies consensus finality and execution inside the proof; the verifier contract checks the resulting proof on L1.

What this gives you

  • One word for one thing, so a claim made in one page can be checked against another without translating it.
  • A status ladder where each rung states exactly what evidence backs it, and no rung can be quoted as a stronger one.
  • Certification and Ethereum finality separated: a provisional PoS confirmation and the finality of the accepting L1 transaction.
  • Terms for the failure vocabulary — unsettled depth, retention, safe halt, weak subjectivity — so a limitation can be named precisely.

What it does not give you

  • The definitions are not a summary of guarantees. A definition says what a word means, not that the mechanism works; nothing here is measured.
  • No term may be read as a promise of a later status: PoS-certified does not imply proof-ready, and accepted on L1 does not imply withdrawal-eligible.
  • The glossary does not resolve the design’s outstanding choices; where a value or a mechanism is not fixed, the term says so rather than inventing precision.

Check yourself

What is the difference between PoS-certified and Ethereum-final?

PoS-certified is an L2 consensus fact: a published commit certificate carrying more than two thirds of the epoch’s voting power, plus this node’s own data-availability check. Above the latest checkpoint accepted on Ethereum it is provisional and may be replaced by recovery. Ethereum-final is a fact about L1: the accepting L1 transaction is in a finalized Ethereum block, and only that status is final.

What does unsettled depth count, and why is it capped?

It counts the L2 blocks between the highest L1-accepted checkpoint and the block being considered. It is capped because unsettled history is the state in which a data-availability failure becomes unrecoverable; when the cap is reached, validators stop voting and the chain waits for proofs rather than dropping data. If settlement then stalls past T_STALL, recovery may replace that unsettled range and permanently retire the heights it discards, but it cannot reconstruct data at or below the accepted checkpoint, and it cannot re-open the range it retired. The cap must leave room for a normal thirty-minute proof.

What is a PoLC, and when does it release a lock?

A PoLC is more than two thirds of prevotes for a particular block or nil at a height and round. It releases a lock at that height only when it is for a value different from the locked one and at a strictly later round than the lock; a PoLC at the same round, at an earlier round, at another height or for the value already locked does not unlock. A validator must verify the PoLC itself and may not trust a proposal’s advisory hint.

A validator misses its L1 heartbeats for a while. What does it lose?

Its place in the set versions committed while it was not attesting. Eligibility for a future set version requires a heartbeat within HEARTBEAT_WINDOW ending at the commit point, so an entry that has not attested is excluded from that root. Nothing else changes: its bonded stake and effective stake are untouched, it is not slashed or decayed, and attesting again restores eligibility for the following boundary. The other cost is operational — a periodic Ethereum transaction and the second heartbeat key — and anyone may submit the attestation, so a relayer may batch many validators’ signatures into one transaction.

Assumptions

  • The specification’s glossary is the naming authority; if a term here and a rule there disagree, the rule wins and this page is wrong.
  • Status labels are used with their fixed meanings; interfaces show which status they display and never substitute a stronger word.
  • “Final” is reserved for Ethereum-final; a PoS confirmation is called PoS-certified / provisional wherever it appears.
  • Numbers quoted in definitions (two seconds, thirty minutes, two thirds) are design inputs or derived arithmetic, not measurements.
  • Future set versions can be populated because validators post their heartbeats and Ethereum includes them. If honest heartbeats can be censored on L1, an online validator can still be excluded from a future version; that is the named falsifier of the exclusion argument and the argument is Open.
