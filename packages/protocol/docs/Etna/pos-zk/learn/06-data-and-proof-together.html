Data and proof travel together

This lesson explains the single rule that shapes settlement: one Ethereum transaction carries the batch data and its proof, and the Inbox accepts neither without the other. It covers the two ways data can be published, how the blob binding works, and what happens when verification fails. This is a design: nothing is deployed, and the costs below are arithmetic on published constants, not measurements of this system.

The idea

There is exactly one function that can advance the chain’s L1 checkpoint: land(data, proof). One call, one transaction, carries the batch’s block range, its data (as calldata, as blob sidecars, or both) and the zero-knowledge proof of the previous lesson. The Inbox verifies the proof against a statement hash it derives itself, and only then writes the new checkpoint.

That gives the design a property that is worth stating in plain words: there is no state in which data has been published but not yet proven, and no state in which a proof has been accepted for data that is not public in the same transaction. The two travel together or not at all.

Data can travel in two forms. Calldata is ordinary transaction input; the contract can read it, so the contract itself hashes the exact bytes and nothing is left to trust. Blobs are the cheaper bulk-data form introduced by EIP-4844, but the EVM cannot read a blob’s contents — it can only see a versioned hash. For blobs, the binding is split: the contract checks a cryptographic opening of the blob at a challenge point, and the proof guest shows that the data it actually executed is a polynomial that takes the same value at the same point. Together those two facts pin the executed bytes to the published blobs.

How it works

1. One entry point, and its order of operations

land(data, proof) must execute in a fixed order: decode and shape-check the input in memory (no state writes); derive every L1-side public input from storage and from this transaction; if blobs are used, perform the blob checks and keep the results in memory; call the active verifier with the statement hash; treat a revert, an empty return or any return other than exactly abi.encode(true) as invalid; only then write the checkpoint, advance the height, record the signer bitmap and pay the reward; emit events last. If any step fails, the call reverts with a typed error and leaves no partial effect (L1-03).

2. There is deliberately no data-first path

No entry point, overload, helper or recovery path may record the data, or a commitment to it, in one transaction and the proof in another. There is no “propose then prove” flow, and no function may write a pending batch record that a later land depends on (L1-02). The reason is concrete: data published without a proof occupies L1 capacity and settles nothing, and it creates an interval in which the batch can only be settled if somebody still holds the data until a proof appears. Publishing the data and the proof together removes that interval entirely. The canonical copy of a batch’s data is therefore the accepting L1 transaction itself, and no witness, certificate, blob reference or off-chain store is a substitute for it.

3. The calldata path: the contract hashes the bytes

On this path the Inbox computes the commitment itself over the exact calldata slice: dataRoot = keccak256(_data), then dataCommitment = keccak256(abi.encode(domain, chainId, firstHeight, lastHeight, daMode, dataRoot)). The committed object is the whole byte string, never a prefix, and a submitter-supplied copy of the commitment must be ignored. The guest decodes the payload from those bytes, executes it, and recomputes the same commitment; a mismatch invalidates the batch. Because both sides hash the same single byte string, this path needs no probabilistic argument at all (DA-02).

4. The blob path: an opening on L1 and an evaluation in the guest

A blob is 131,072 bytes: 4,096 field elements of a polynomial over the BLS12-381 scalar field. The commitment covers every one of those bytes, including any unused remainder at the end — a commitment over a prefix would leave the prover free to choose the suffix after the challenge point was fixed.

  1. The Inbox reads the transaction’s own versioned hash with the BLOBHASH opcode. The opcode is transaction-scoped, so no other transaction’s blobs can be substituted, and a zero value means no blob at that index.
  2. It calls the EIP-4844 point-evaluation precompile at address 0x0A, which checks that the supplied commitment hashes to that versioned hash and that the polynomial opens to the claimed value at the claimed point. The call must return exactly abi.encode(4096, BLS_MODULUS); anything else reverts.
  3. The challenge point z is derived on L1 by Fiat–Shamir from the statement itself — the statement hash, the data commitment, the ordered blob versioned hashes and the blob index. The submitter cannot choose it.
  4. The guest interprets the blob in the EIP-4844 convention (the elements are evaluations in bit-reversed order, not coefficients), rejects any element that is not a canonical field element, and checks that the polynomial of the data it executed takes the same value y at z.
  5. The guest recomputes the data commitment over the full blob byte strings it executed and requires equality with the journal value used to derive the challenge.

Why this binds the two objects together: the opening proves p_blob(z) = y; the guest proves p_data(z) = y; so the difference of the two polynomials has a root at z. But z is not fixed while the prover chooses its data — it is derived from a transcript that contains the commitment to that data. A cheating prover would need a fixed point: data whose hash-derived challenge is a root of the difference polynomial. For any candidate payload the chance is at most 4,095 / |F| ≈ 2−243 derived, so searching q candidates gives at most q · 2−243, under the random-oracle model for the challenge and the binding property of KZG (DA-03).

When both calldata and blobs are used, the whole published string is the calldata payload followed by the full blobs, and both bindings apply independently: a batch is invalid if either fails.

5. Any prover may land a batch

Admission has no gate: no whitelist, no approval, no bond, no reputation and no deadline that could make an unsettled range permanently unacceptable. The structural bounds are exactly three: the range must be contiguous and start at the previous checkpoint’s height plus one; the batch must be non-empty; and every loop must be bounded by the transaction’s own contents (L1-04).

The first valid submission wins. Two transactions in the same L1 block are ordered by Ethereum, so the first advances the checkpoint and the second either reverts or is evaluated against the new one. Re-submitting the same batch after a failed attempt is accepted, and it is never rejected because somebody else announced, attempted or submitted the range first. A proof is a proof of exactly one statement: the same proof presented with a different range, predecessor, data commitment, epoch or set root fails verification, because all of those values are inside the statement hash. The reward goes to the account that paid for the L1 transaction, not to an address named inside the proof, and copying a proof from the public mempool and landing it first is accepted behaviour; a prover’s mitigation is private orderflow or bundling (L1-10).

6. What a failed verification does

Nothing is accepted. If the proof is invalid, if a blob opening fails, if the range is not contiguous, or if any check reverts, the whole call reverts: no checkpoint is written, the height does not advance, no reward is paid and no event is emitted. The batch stays unsettled and anybody may try again with a correct witness or a correct proof later. There is no “accepted but unproven” state to clean up, and no recovery path that could create one.

Worked example

A six-block batch whose payload is about 600,000 bytes, published first one way and then the other. The gas figures are arithmetic on published Ethereum constants, not measurements of this system.

Which is cheaper overall depends on blob prices and on the verifier’s gas, neither of which is measured here.

What this gives you

  • One atomic rule to implement and to reason about: no checkpoint without both the data and a valid proof, and no way to create a pending state.
  • A calldata path whose binding is a hash the contract computes itself, with no probabilistic argument.
  • A blob path that still binds the executed bytes to the published blobs, using an L1 precompile for the cryptographic opening and in-guest field arithmetic for the evaluation.
  • Permissionless landing: any account may submit a valid pair, and re-submission is allowed until one lands.
  • A clean failure story: a failed verification reverts and changes nothing, so there is nothing to reconcile afterwards.

What it does not give you

  • No fast path for publishing data early: if you need data on L1 before a proof exists, this design does not offer it, in any mode.
  • No permanent storage: Ethereum guarantees blob sidecars for a bounded window (4,096 epochs, about 18 days at the present cadence, sourced), and historical calldata is pruned on the p2p layer under EIP-4444 (14,299 epochs, sourced); past that, retrievability depends on archive nodes keeping the accepting transaction’s bytes.
  • No protection against a prover being front-run: the reward follows the landing transaction, so copying a public proof is allowed.
  • No measured cost or in-guest blob-evaluation cost; the blob binding’s fixed-point argument has not yet been independently checked.

Check yourself

Can a batch’s data be on Ethereum before its proof?

No. There is exactly one entry point, land(data, proof), and one transaction carries both. No function may record the data, or a commitment to it, or a pending batch that a later call depends on. A batch is either accepted with its data and a valid proof, or not accepted at all.

On the blob path the contract cannot read the blob bytes. What stops a prover from committing to data it did not execute?

The guest recomputes the data commitment over the full blob bytes it executed, and the challenge point is derived from a transcript that includes that commitment. To cheat, a prover would need executed data whose hash-derived challenge is a root of the difference between its polynomial and the blob’s polynomial — a fixed point, not a linear equation — which succeeds with probability at most about 2−243 per candidate payload under the stated assumptions.

Someone copies your proof from the mempool and lands it first. What happens?

The batch lands — it is the same data and the same statement — and the reward goes to the account that paid for the L1 transaction. The proof cannot be reused for a different batch, because the range, predecessor, data commitment, epoch and set root are all inside the statement hash. A prover who wants to avoid this uses private orderflow or bundles its own landing transaction.

Assumptions. This lesson relies on: somebody publishing the data in the accepting transaction, as calldata or as blob sidecars of that same transaction; Ethereum’s blob-retention window holding long enough for the batch to be proven and for evidence to be submitted, with archive nodes keeping the bytes afterwards; KZG binding and the random-oracle model for the Fiat–Shamir challenge on the blob path; the in-guest blob evaluation being implemented correctly in the EIP-4844 convention; and a verifier route being registered and reachable on L1. If the blob path’s argument does not hold, the calldata path still binds data by a hash the contract computes itself.
