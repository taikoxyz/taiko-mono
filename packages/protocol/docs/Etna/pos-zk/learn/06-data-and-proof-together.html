Data first, proof binds

This lesson explains how a batch’s data reaches Ethereum and how the accepting transaction binds it: one proof-gated call, carrying the proof and either the data itself or a reference to a live publication record. It covers publication before the proof and what publication writes, the calldata and blob bindings, how the proof binds the configuration and the signed recovery generation, and what happens when verification fails. This is a design: nothing is deployed, and the costs below are arithmetic on published constants, not measurements of this system.

The idea

There is exactly one function that can advance the chain’s L1 checkpoint: land(data, proof). One call, one transaction, carries the batch’s block range, the zero-knowledge proof of the previous lesson, and the batch data — either in the transaction itself (as calldata, as blob sidecars, or both) or as a reference to a live publication record that already holds it. The Inbox verifies the proof against a statement hash it derives itself, and only then writes the new checkpoint (L1-01).

That gives the design a property worth stating in plain words: the protocol state advances only on a valid proof, and only the accepting transaction writes a checkpoint. Data may be published to Ethereum before the proof. Publication is permissionless, records where the data is, and writes no batch state at all; data sitting in blobs changes nothing about the chain and becomes relevant only when a proof references it. A publication that is not proven before its deadline is discarded and can be published again — it never becomes a second acceptance path.

The statement also binds the configuration under which the batch was certified and the recovery generation it belongs to. A proof is therefore evidence about one specific history: it cannot be replayed into a different configuration, and a batch whose certificate carries a superseded generation is void at the acceptance rule. v1 has no recovery path, so the generation never advances here and no height is ever retired; the binding is the scoping rule a future update would exercise, not a rule that fires in v1. Execution validity alone is never enough to accept an alternative history (PRF-01).

Data can travel in two forms. Calldata is ordinary transaction input; the contract can read it, so the contract itself hashes the exact bytes and nothing is left to trust. Blobs are the cheaper bulk-data form introduced by EIP-4844, but the EVM cannot read a blob’s contents — it can only see a versioned hash. For blobs, the binding is split: the contract checks a cryptographic opening of the blob at a challenge point, using the versioned hashes the accepting transaction carries or the recorded versioned hashes of the publication it references, and the proof guest shows that the data it actually executed is a polynomial that takes the same value at the same point. Together those two facts pin the executed bytes to the published blobs.

How it works

1. One proof-gated entry point, and its order of operations

land(data, proof) must execute in a fixed order: decode and shape-check the input in memory (no state writes); derive every L1-side public input from storage and from this transaction; if the transaction carries the batch’s blobs, perform the blob checks against its own versioned hashes; if the input references a publication record, load that record, recompute its identity and require its range, data mode, data commitment and recorded versioned hashes to agree with the statement, and require the record to be live; call the active verifier with the statement hash; treat a revert, an empty return or any return other than exactly abi.encode(true) as invalid; only then write the checkpoint, advance the height, record the signer bitmap and pay the reward; emit events last. If any step fails, the call reverts with a typed error and leaves no partial effect (L1-03).

2. Data may be published first; publication writes no batch state

Any account may publish a batch’s data to L1 in a transaction of its own. The publication transaction carries the whole committed byte string in blobs, and the Inbox writes one publication record: the ordered blob versioned hashes, the claimed batch range, the data mode and data commitment it was published for, the L1 block number, a sequence number and a proving deadline (DA-07).

What the record does not write matters as much as what it does. It is not a batch, not a proposal and not a pending checkpoint: it writes no batch record, no predecessor link, no claimed post-state and no value that any admission check reads. No entry point may record a batch, a predecessor link or a data commitment pending a proof (L1-02). Data in blobs changes no protocol state; it becomes relevant only when a proof references it, and the carried path — data and proof in one transaction — always remains available for any unsettled range and never needs a publication record.

Because publication is permissionless, putting the data on L1 before the proof is a liveness tool rather than a second acceptance path: whoever holds the data can publish it while the blobs are retrievable, so withholding it requires that no observer publish. The exposure is bounded by a deadline inside Ethereum’s blob-retention window: a publication that is not proven before its deadline is discarded, a proof referencing it is rejected, and the same data can be published again. Re-publication creates a new record with a fresh clock and a new identity; it revives nothing and accepts nothing (DA-09). The range itself is never discarded with the record: it stays landable from carried data or against a fresh publication of the same data (L1-04).

3. The calldata path: the contract hashes the bytes

On this path the Inbox computes the commitment itself over the exact calldata slice: dataRoot = keccak256(_data), then dataCommitment = keccak256(abi.encode(domain, chainId, firstHeight, lastHeight, daMode, dataRoot)). The committed object is the whole byte string, never a prefix, and a submitter-supplied copy of the commitment must be ignored. The guest decodes the payload from those bytes, executes it, and recomputes the same commitment; a mismatch invalidates the batch. Because both sides hash the same single byte string, this path needs no probabilistic argument at all (DA-02). Calldata is the carried form: it travels in the accepting transaction, and the publication record carries blob versioned hashes.

4. The blob path: an opening on L1 and an evaluation in the guest

A blob is 131,072 bytes: 4,096 field elements of a polynomial over the BLS12-381 scalar field. The commitment covers every one of those bytes, including any unused remainder at the end — a commitment over a prefix would leave the prover free to choose the suffix after the challenge point was fixed.

  1. Where the versioned hashes come from. If the accepting transaction carries the batch’s blobs, the Inbox reads the transaction’s own versioned hash with the BLOBHASH opcode. The opcode is transaction-scoped, so no other transaction’s blobs can be substituted, and a zero value means no blob at that index. If the input references a publication record and the transaction does not carry the blobs, BLOBHASH cannot be used — it returns zero for a blob this transaction does not carry — so the Inbox takes each versioned hash from the record, after checking that the record’s identity, range, data mode and data commitment match the statement and that the record is live (DA-08).
  2. It calls the EIP-4844 point-evaluation precompile at address 0x0A, which checks that the supplied commitment hashes to the supplied versioned hash and that the polynomial opens to the claimed value at the claimed point. The precompile is not transaction-scoped: it verifies the commitment it is given against the versioned hash it is given, so the same opening check holds when the blobs were published earlier. The call must return exactly abi.encode(4096, BLS_MODULUS); anything else reverts.
  3. The challenge point z is derived on L1 by Fiat–Shamir from the statement itself — the statement hash, the data commitment, the ordered blob versioned hashes and the blob index. The submitter cannot choose it.
  4. The guest interprets the blob in the EIP-4844 convention (the elements are evaluations in bit-reversed order, not coefficients), rejects any element that is not a canonical field element, and checks that the polynomial of the data it executed takes the same value y at z.
  5. The guest recomputes the data commitment over the full blob byte strings it executed and requires equality with the journal value used to derive the challenge.

Why this binds the two objects together: the opening proves p_blob(z) = y; the guest proves p_data(z) = y; so the difference of the two polynomials has a root at z. But z is not fixed while the prover chooses its data — it is derived from a transcript that contains the commitment to that data. A cheating prover would need a fixed point: data whose hash-derived challenge is a root of the difference polynomial. For any candidate payload the chance is at most 4,095 / |F| ≈ 2−243 derived, so searching q candidates gives at most q · 2−243, under the random-oracle model for the challenge and the binding property of KZG (DA-03). The recorded versioned hash is the identity consensus already checked against the published blob sidecars when the publication block was processed, so referencing it loses same-transaction equality and not the content binding.

When both calldata and blobs are used, the whole published string is the calldata payload followed by the full blobs, and both bindings apply independently: a batch is invalid if either fails. When the accepting transaction both carries blobs and references a record, the two ordered sets must agree element-wise (DA-08).

5. Any prover may land a batch

Admission has no gate: no whitelist, no approval, no bond, no reputation and no deadline that could make an unsettled range permanently unacceptable. A publication record’s deadline expires that record, never the range: after it, the range is still landable with carried data or against a fresh publication of the same data. The structural bounds are exactly three: the range must be contiguous and start at the previous checkpoint’s height plus one; the batch must be non-empty; and every loop must be bounded by the transaction’s own contents (L1-04).

The first valid submission wins. Two transactions in the same L1 block are ordered by Ethereum, so the first advances the checkpoint and the second either reverts or is evaluated against the new one. Re-submitting the same batch after a failed attempt is accepted, and it is never rejected because somebody else announced, attempted or submitted the range first. A proof is a proof of exactly one statement: the same proof presented with a different range, predecessor, data commitment, epoch, set root, configuration or recovery generation fails verification, because all of those values are inside the statement hash. The reward goes to the account that paid for the L1 transaction, not to an address named inside the proof, and copying a proof from the public mempool and landing it first is accepted behaviour; a prover’s mitigation is private orderflow or bundling (L1-10).

6. The proof binds the configuration and the recovery generation

The statement hash includes the configuration under which the batch was certified and its recovery generation, so a proof that was valid for one configuration or generation cannot be reused under another. The configuration is not a single mutable global value: the Inbox keeps an append-only per-epoch registry mapping each epoch to its configHash. The entry is computed by the contract from its own storage and deployed code, written before the epoch starts, and immutable once written: no upgrade or governance call may edit or rewrite the entry of an epoch that has already begun, so an upgrade binds future epochs only (PARAM-04). That immutability is what keeps upgrades from breaking settlement. If the configuration could change under a running epoch, a routine upgrade would move the configuration hash, and every in-flight proof — made under the configuration that was current when the batch was certified and executed — would fail verification, leaving its batch unlandable.

The guest recomputes configHash from the configuration it actually applied and requires equality with the registry value the L1 contract supplies (PRF-02). The recovery generation is carried in the signed vote and header bytes and is part of the statement. A certificate carrying a superseded generation is void at the acceptance rule, and that is what stops a branch scoped to an older generation from ever being accepted again. v1 has no recovery path, so nothing increments the generation here: there is no restoration, no retired height and no resumeHeight. Every batch starts at lastLandedHeight + 1, the ordinary contiguity rule (L1-06). The generation scoping is the rule a future protocol update would have to exercise; in v1 it is inert, and a certificate from any generation remains usable as evidence of what was signed (PRF-01).

What this rules out is the tempting shortcut of accepting an alternative history just because its execution is valid. A batch that does not descend from the current checkpoint, or whose certificate carries a generation other than the one the contract supplies, fails acceptance even if every execution step inside it is correct.

7. What a failed verification does

Nothing is accepted. If the proof is invalid, if a blob opening fails, if a referenced publication is expired or does not match the statement, if the range is not contiguous, or if any check reverts, the whole call reverts: no checkpoint is written, the height does not advance, no reward is paid and no event is emitted. The batch stays unsettled and anybody may try again with a correct witness or a correct proof later. There is no “accepted but unproven” state to clean up: a discarded publication accepted nothing, and re-publishing the data is enough to try again.

Worked example

A six-block batch whose payload is about 600,000 bytes, published once as calldata and once as blobs. The gas figures are arithmetic on published Ethereum constants, not measurements of this system.

The comparison between the two data forms is the engineering point: the same 600,000 bytes cost about 9.6 million execution gas as calldata and about 250,000 gas of execution for the blob openings, with the blob data itself paid on a separate market. Which is cheaper overall depends on blob prices and on the verifier’s gas, neither of which is measured here.

The example payload is below the target-rate budget on purpose. At the target rate one 2-second L2 block is one 131,072-byte blob, so the largest sustainable batch is six blocks — 786,432 bytes, exactly the EIP-7691 target of six blobs per L1 block — and nine blocks (1,179,648 bytes) is the hard ceiling, because a batch’s data must fit in one L1 transaction: the accepting transaction when the data is carried, or the publication transaction when it is published earlier (L1-01).

What this gives you

  • One proof-gated rule to implement and to reason about: no checkpoint without a valid proof, no way to create a pending batch state, and no second path that can accept a batch.
  • A permissionless publication path: data can be on Ethereum before the proof, publishing writes no batch state, and a record that is not proven before its deadline is discarded and re-published by anyone.
  • A statement that also binds the per-epoch configuration and the signed recovery generation: the configuration entry for an epoch is fixed before the epoch starts and immutable once written, so an upgrade cannot move the configuration hash under an in-flight proof, and a certificate carrying a superseded generation is void at the acceptance rule.
  • A calldata path whose binding is a hash the contract computes itself, with no probabilistic argument.
  • A blob path that still binds the executed bytes to the published blobs when they were carried in the accepting transaction or referenced through a publication record, using an L1 precompile for the cryptographic opening and in-guest field arithmetic for the evaluation.
  • Permissionless landing: any account may land a batch with a valid proof and data carried or bound to a live publication record, and re-submission is allowed until one lands.
  • A clean failure story: a failed verification reverts and changes nothing, and an expired publication is simply replaced, so there is nothing to reconcile afterwards.

What it does not give you

  • No guarantee that published data is proven, or that it is referenced by anyone: a publication that misses its deadline is discarded and a proof referencing it is rejected, though the same data can be published again.
  • No way to settle without a valid proof: publication writes no batch state and advances no height, the carried path never depends on a record, and no function may write a pending batch that a later call depends on.
  • No permanent storage: Ethereum guarantees blob sidecars for a bounded window (4,096 epochs, about 18 days at the present cadence, sourced), and historical calldata is pruned on the p2p layer under EIP-4444 (14,299 epochs, sourced); past that, retrievability depends on archive nodes keeping the accepting or publication transaction’s bytes.
  • No protection against a prover being front-run: the reward follows the landing transaction, so copying a public proof is allowed.
  • No measured cost or in-guest blob-evaluation cost; the blob binding’s fixed-point argument has not yet been independently checked.
  • No way to land a batch whose certificate carries a superseded generation once a future update advances it, though its proof remains usable as evidence of what was certified and executed. In v1 the generation never advances, nothing is retired and no range is discarded.

Check yourself

Can a batch’s data be on Ethereum before its proof?

Yes. Any account may publish the batch’s data to L1 in blobs before a proof exists. Publication is permissionless, writes a publication record and no batch state, and accepts nothing: the checkpoint still advances only when a valid proof lands. A proof may bind the data by referencing the live publication record, and a record that is not proven before its deadline is discarded and can be published again.

A publication record is written and no proof is ever produced. What happens to the batch and to the data?

The record reaches its deadline and is discarded: a proof referencing it is rejected, and its clock cannot be extended. Nothing is accepted and no height advances. The range is not discarded with the record — it stays landable with the data carried in the accepting transaction, or against a fresh publication of the same data, which any account may create because publication is permissionless.

On the blob path the contract cannot read the blob bytes. What stops a prover from committing to data it did not execute?

The guest recomputes the data commitment over the full blob bytes it executed, and the challenge point is derived from a transcript that includes that commitment. When the data was published earlier, the versioned hashes come from the publication record and the precompile checks the supplied commitment against them, so the opening still holds. To cheat, a prover would need executed data whose hash-derived challenge is a root of the difference between its polynomial and the blob’s polynomial — a fixed point, not a linear equation — which succeeds with probability at most about 2−243 per candidate payload under the stated assumptions.

Someone copies your proof from the mempool and lands it first. What happens?

The batch lands — it is the same data, the same publication reference and the same statement — and the reward goes to the account that paid for the L1 transaction. The proof cannot be reused for a different batch, because the range, predecessor, data commitment, epoch and set root are all inside the statement hash. A prover who wants to avoid this uses private orderflow or bundles its own landing transaction.

The statement binds a recovery generation. What does that mean in v1?

It scopes certificates: a certificate carrying a generation other than the one the L1 contract supplies is void at the acceptance rule, so a branch certified under a superseded generation can never be accepted again. v1 has no recovery path, so nothing advances the generation and no height is retired; every batch still starts at lastLandedHeight + 1. A settlement stall halts the chain instead of replacing history, funds at or below the last accepted checkpoint stay safe and the exit works, and clearing the stall needs a future protocol update. A certificate from any generation remains usable as evidence of what its signers signed.

Why can a routine upgrade not invalidate the proofs that are already in flight?

Because the configuration is registered per epoch. Each epoch’s configHash is written before the epoch starts and is immutable once written, and an upgrade binds future epochs only. With a single mutable global configuration, an upgrade would move the hash under a running epoch, and every proof made under the previous configuration would fail verification, leaving its batch unlandable.

Assumptions. This lesson relies on: somebody publishing the data while the blobs are retrievable, either by carrying it in the accepting transaction as calldata or blob sidecars, or by publishing it earlier and referencing the live publication record; Ethereum’s blob-retention window holding long enough for the batch to be proven and for evidence to be submitted, with archive nodes keeping the bytes afterwards; KZG binding and the random-oracle model for the Fiat–Shamir challenge on the blob path; the in-guest blob evaluation being implemented correctly in the EIP-4844 convention; and a verifier route being registered and reachable on L1. If the blob path’s argument does not hold, the calldata path still binds data by a hash the contract computes itself.
