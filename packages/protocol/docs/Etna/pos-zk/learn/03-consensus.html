How the chain agrees

This lesson gives an implementer the exact consensus objects, the round procedure, the two-thirds quorum, the lock rule, the commit rule, proposer selection and view changes — and the two things a validator must never do.

This is a design, not a running system. Nothing described here is implemented, deployed, audited or measured. Timeouts, round-trip times and set sizes are unmeasured. The authoritative rules — including every edge case of the lock and epoch rules — are stated once in specification 02; this lesson links to them rather than restating them.

The idea

Consensus proceeds one height at a time. For height H the set tries round 0, then round 1, and so on. Each round has three steps. In the propose step exactly one validator — chosen by a hash over the epoch's committed weights — broadcasts a block. In the prevote step every validator signs a vote for either that block or NIL. If more than two thirds of the epoch's voting power prevotes the same value, that set of votes is a proof-of-lock-change (PoLC); in the precommit step validators sign again, and a validator that has seen a PoLC for a block locks on it. When more than two thirds of the voting power has precommitted the same block at the same height and round, those signatures are the block's commit certificate and the block is PoS-certified at a node that also holds its data. Above the latest checkpoint accepted on Ethereum that certification is provisional.

Two rules make this safe rather than merely ordered. The signing rule says a validator may sign at most one message of each type per (chain id, height, round) — ever, including after a crash. The lock rule says that once a validator has locked on a block, it prevotes that block until a strictly later round of the same height shows a PoLC for something else; it must never unlock on the proposer's say-so, on a same-round PoLC, or on a PoLC from a different height. Together they mean a conflicting certificate would require at least one third of the epoch's power to break a rule, and the breaking would be visible in signed evidence.

Time is a liveness tool, not a safety tool. A round timer that expires moves this node to the next round; it never proves anything about what other nodes hold, and it never invalidates a block.

How it works

The objects on the wire

Every object is encoded in exactly one canonical way: a single abi.encode of typed fields, with a right-padded ASCII domain tag and the chain id as the first two fields, and a signature that is invalid outside its domain. Signatures are Ed25519 (32-byte public key, 64-byte signature), made over the exact encoded bytes with no pre-hash.

The rules an implementer must enforce

Proposal validity

A proposal is valid at (H,R) only if the chain id, height, round and epoch match the L1-committed schedule; the proposer index matches the selection below and its signature verifies under the key committed at that index in the epoch's set root; the block's parent hash is the block this validator certified at H−1; and local execution of the block against that parent's post-state succeeds and reproduces every header field the block commits to (state root, receipts root, gas used, logs bloom, transaction root). A validator must not sign a prevote or precommit for a proposal that fails any of these; its only legal alternative in that round is NIL.

Quorum: more than two thirds, distinct signers, stake-weighted

Let the epoch have committed voting powers w_i ≥ 1 from its L1-committed set and W = Σ w_i. For a set Q of distinct authenticated signers with s = Σ_{i∈Q} w_i, quorum holds exactly when 3·s > 2·W in checked arithmetic (CONS-03). The comparison is strict: 3·s = 2·W does not reach quorum. Voting power comes only from the L1-committed set — never from a vote, a certificate, a witness or a prover-supplied list — and the same integers are used for quorum and for proposer selection. Verification requires popcount(signers) = len(signatures), no index counted twice, no set bit without a signature and no non-zero pad bit. NIL votes never contribute to a block quorum. The L2 client, the proof's guest program and the L1 contract evaluate the identical predicate; a strict/non-strict mismatch would split chain acceptance from L1 acceptance.

The lock rule, and how a validator unlocks

A validator's lock is a persistent local triple (locked_height, locked_value, locked_round). It is per height: it constrains votes at height H only, survives restart while H is unresolved, and is released by (a) the commit of H, after which it has done its work and constrains no later height, or (b) an unlock. Unlock happens only against a PoLC at (H, p) for a different value with locked_round < p < R — strictly later, same height, different value. A PoLC at the same round, at an earlier round, or for the value already locked does not unlock; a PoLC at another height neither unlocks this height's lock nor creates a lock at that other height. A validator must not precommit a block without holding a PoLC for that block at that (height, round), and while locked and not unlocked it must prevote its locked value. The pol_round field of a proposal is only a hint: a validator must verify the PoLC itself and must never treat the field as evidence. A validator that holds a lock at H and then sees a valid commit certificate at H for a different block has evidence that its assumptions failed: it halts and must not treat the certificate as an unlock.

The commit rule

A commit certificate at (H,R) for block B is (chain_id, epoch, recovery_generation, H, R, B, set_root(epoch), signers, signatures). It is valid only if epoch = epoch_of(H), set_root(epoch) equals the L1-committed set root for that epoch, recovery_generation equals the generation the L1 contract holds and the generation signed by every contributing vote, and more than two thirds of that set's voting power signed PRECOMMIT for B at (H,R), with exactly one verified signature per set bit (CONS-05). A node treats B as certified when it holds a valid certificate, and it has performed its own data-availability check for B's body, and parent(B) is the block it certified at H−1. The local decision is a function of the certificate, the node's own data check and its own certified prefix — nothing else. This rule prevents two conflicting certificates; above the latest checkpoint accepted on Ethereum a confirmation is provisional, and v1 has no rule that replaces it — a settlement stall halts the chain rather than forking it.

Proposer selection and view changes

For height H and round R in epoch e with cumulative weights cum_i and total W: pos(H,R) = uint256(keccak256(abi.encode("TAIKO_ETNA_PROPOSER_V1", chainId, e, H, R))) mod W, and the proposer is the unique i with cum_{i−1} ≤ pos < cum_i. The intervals are half-open, so the proposer is unique and the tie-break is fixed (the lower index wins) (CONS-06). Anyone holding the epoch's set root can recompute the proposer — which also means the next proposer is publicly predictable.

The round timer is T(H,R) = min(TIMEOUT_MAX, TIMEOUT_MIN · 2^min(R − R_progress, R_cap)) seconds (CONS-07), where R_progress is the highest round at which this node saw a PoLC or a commit certificate, and R_cap = ceil(log2(TIMEOUT_MAX / TIMEOUT_MIN)). Proposed values are TIMEOUT_MIN = 3 s and TIMEOUT_MAX = 30 s, giving a ladder of 3, 6, 12, 24, 30, 30, … seconds; both values are unmeasured, because they depend on the unmeasured message-delay and execution bounds. A correct validator advances to (H,R+1) when either the timer expires or it has received a PoLC at (H,R) and completed its own precommit step; it must not advance past a commit. A locked validator advances normally — the lock constrains what it signs, not whether it moves on.

What a validator signs, and what it must never sign

At most one of each, per (chain id, H, R)

  • one PROPOSAL, if it is the selected proposer;
  • one PREVOTE: its locked value if it is locked and not unlocked, otherwise the valid proposal it knows, otherwise NIL;
  • one PRECOMMIT: a block it holds a PoLC for at that round, otherwise NIL.

The uniqueness rule applies to NIL too. Before signing, the client consults a persistent store of every (round, value) it has already signed per (chain id, height, type); the store must be written durably before the signature is broadcast and must survive restart. If the store is missing, unreadable or corrupt, the validator must not sign and must not start fresh — re-signing after a restart is the amnesia fault.

Never

  • a second message of the same type at the same (chain id, height, round), including a second NIL;
  • a prevote for anything other than the locked value while locked and not validly unlocked;
  • a precommit for a block without holding a PoLC for that block at that (height, round);
  • anything for a proposal that fails the validity check;
  • a message whose epoch field disagrees with the epoch of its height under the L1-committed schedule;
  • anything at all after a halt — a halting validator stops signing.

Why a missing certificate is not evidence that it does not exist

A certificate is an object that travels over a best-effort network; not receiving it is a fact about your mailbox, not about the world. An elapsed timeout is therefore never evidence of absence, and no rule may conclude from a timeout that a certificate, proof or block does not exist (STATUS-10). Timeouts trigger local actions only: a view change, a retry, or a halt.

What a node should do instead, in order:

  1. advance the round if the timer expired or a PoLC for this round arrived, and keep the lock unchanged;
  2. ask peers for the certificate or the missing object and verify it as an object — signatures, bitmap, set root and quorum checked locally, regardless of who sent it;
  3. if it holds a lock on a different block at that height and a valid conflicting certificate arrives, halt and publish the evidence it has, rather than choosing a branch;
  4. never invalidate a block or help form a second conflicting certificate, and never delegate the choice to an operator; no node may replace history above the latest checkpoint accepted on Ethereum, and v1 has no rule that does.

Equivocation is the one thing a pair of signed objects can prove: two signed messages of the same type, at the same (chain id, height, round, validator index), with different signed values — or with different signed epoch fields — are self-authenticating evidence, and any party may submit them (CONS-11). A prevote for one value and a precommit for another at the same round is not equivocation; it is the normal step sequence. Signing at different rounds or different heights is not equivocation either.

Worked example: why a locked validator prevents two conflicting commits

Take an epoch with total voting power W = 1,000,000 TAIKO base units. The quorum predicate is strict: a certificate needs signed power s with 3·s > 2,000,000, so s ≥ 666,667. Suppose 800,000 units are held by correct validators and 200,000 by an adversary.

The same arithmetic works for the epoch boundary. The first block of a new epoch must descend from the last block certified in the previous epoch, and every correct validator must itself verify the previous epoch's certificate for that anchor before it prevotes or precommits anything in the new epoch. A conflicting history across the boundary therefore reduces to the same case: at least one third of the previous epoch's power must have broken a rule.

What this gives you

  • Single-slot certification: one certificate per height, no confirmation depth, no probabilistic waiting.
  • Certificates are epoch-scoped and stay valid forever as certificates, so validator rotation cannot re-judge or re-sign a past decision; rotation is not a replacement path — no rule of v1 replaces history above the latest accepted checkpoint.
  • A lock and a signed-vote rule that make the cost of a conflicting commit one third of the epoch's stake, and make the most damaging fault objectively provable when it appears as a same-height, same-round pair.
  • A deterministic, publicly computable proposer schedule, so anyone can audit who was supposed to propose and when.
  • Timeouts that affect liveness only: exceeding any timing bound slows the chain, never breaks safety.

What it does not give you

  • No safety without the stake assumption. With one third or more of an epoch's power malicious or compromised, two conflicting certificates can both be valid, and the ZK proof verifies both.
  • No measured timing. TIMEOUT_MIN, TIMEOUT_MAX, the message-delay bound and the block-execution bound are unmeasured; the 3 s / 30 s ladder is a proposal, not a result.
  • No liveness guarantee. A permanently withheld PoLC stalls a locked validator by design; the honest outcome is that it cannot make progress, not that it invents a rule. A settlement stall halts the chain safely: value at or below the last accepted checkpoint can still leave on L1, and the one route back is the stall resolution — a DAO-queued entry, a stored deadline, one execution by any account — which nothing obliges governance to use.
  • No machine-checked epoch handoff. The safety argument across an epoch boundary — per-height locks, the parent-validity condition and the epoch anchor — is an argued property, not a machine-checked one. A cross-round divergence under withholding can also leave no admissible evidence, so the claim that at least one third is always objectively punishable is not made.
  • No hidden evidence. A certificate shows one vote per signer; it can never prove that a validator did not also sign something else. Only a conflicting signed pair does that.
  • No unpurchasable proposer slot. Selection is public and predictable, so a coalition can identify the slot in which a target transaction would be included. No rule prices or penalises slot-buying.

Check yourself

A validator is locked on block X at height 100, round 2. At round 5 it receives a PoLC for block Y at round 4, and a PoLC for block X at round 3. May it prevote Y at round 5?

Yes, if the round-4 PoLC is for a value different from X and locked_round = 2 < 4 < 5, and it verifies the PoLC itself. The round-3 PoLC for X is irrelevant. A PoLC at the same round as the lock, at an earlier round, or for the already-locked value does not unlock; a PoLC at another height neither unlocks nor creates a lock.

Your node times out waiting for a certificate at height 100. Can you conclude the certificate does not exist and certify something else?

No. An elapsed timeout is never evidence of absence. The timeout moves your node to the next round of height 100 and nothing else. Fetch the certificate from peers and verify it as an object; if a valid certificate later appears for a block conflicting with your lock, halt and publish what you have.

Why must the sign-state store survive a restart, and what should a node do if it is lost?

Because the uniqueness rule is the whole basis of equivocation evidence: a validator that re-signs after a restart can produce two conflicting signed messages without intending to, and the pair is indistinguishable from deliberate equivocation. If the store is missing, unreadable or corrupt, the validator must stop signing and must not start from an empty store; a halt is the safe outcome.

Assumptions

  • Fewer than one third of each epoch's voting power is Byzantine, in every epoch (this is the safety assumption; it is per epoch because a certificate is judged under its own epoch's set).
  • Correct validators actually execute the signing rule, the lock rule and the validity check; the safety argument assumes the client is correct, not merely present.
  • Validators' signing keys are not compromised, and each validator's durable sign-state store is intact across restarts.
  • Message delivery among correct validators is timely often enough for rounds to complete (this is the liveness assumption).
  • The L1 staking contract commits each epoch's set root before the epoch begins, and validators read it from Ethereum-final L1 state.
  • The validator-set commitment is the one canonical encoding of L1-committed stake; no proposer, signer or prover supplies it.
