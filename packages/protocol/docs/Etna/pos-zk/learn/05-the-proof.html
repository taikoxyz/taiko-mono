What the proof proves

This lesson states the zero-knowledge statement an engineer has to implement, separates public inputs from witness, and lists precisely what a valid proof does not establish. It is a design: nothing here is deployed, and the proving costs and latencies are not yet measured.

The idea

A batch of L2 blocks is a proposed transition: some range of blocks, a claimed new state root, and the consensus evidence that those blocks were certified. Before Ethereum accepts that transition, somebody must show that the evidence is sufficient and the execution is correct. The design does this with one zero-knowledge proof covering three claims at once:

  • W1 — consensus finality: the batch’s head block carries a valid commit certificate, signed by more than two thirds of the voting power of the epoch’s validator set, where that set and that epoch are authenticated from Ethereum state.
  • W2 — execution: executing the batch’s blocks in consensus order, starting from the previous checkpoint’s state root, produces the claimed new state root.
  • W3 — data binding: the bytes the guest executed are the bytes published in the accepting L1 transaction.

A public input is a value the proof is checked against: it is visible to the verifier and is part of what the proof is about. A witness is the private material the prover supplies to the guest — the set leaves, the signatures, the headers, the payload. The discipline of this design is that every value that defines authority is a public input taken from Ethereum, and never something the prover chose.

How it works

1. The statement is a conjunction, not three proofs

One guest program proves W1, W2 and W3 together, and one proof is accepted per batch. There is no separate “finality proof” and “execution proof” that could be paired with the wrong counterpart: a proof that a block was certified without proving what it executed, or an execution proof over data that was never certified, is exactly the failure this avoids (PRF-01). A batch never spans an epoch boundary, so exactly one epoch, one validator set root and one quorum denominator appear in the statement; a range that would cross a boundary is split, and because every batch starts at the previous checkpoint’s height plus one, no height can be dropped at the split (PRF-05).

2. Public inputs versus witness

The public-input vector is a single canonical list, encoded with a domain tag and the chain id first, and its order is normative. The L1 contract hashes that vector into a statement hash and passes only the hash and the opaque proof to the verifier. The guest commits to exactly the same vector, so the two sides cannot disagree about what was proven (PRF-02).

3. Why every authority value comes from L1

Four values decide who was allowed to speak, and all four are L1 facts:

  • Epoch. epoch = epoch_of(height) under the L1-committed schedule. The contract recomputes it and rejects a mismatch, so a prover cannot label a batch with an epoch whose set judges it more favourably.
  • Validator set root. Read from the staking contract’s per-epoch mapping, which is append-only and immutable once the epoch starts. The header’s set commitments must be the same root under the same encoding.
  • Configuration. configHash is read from the Inbox’s append-only per-epoch registry. Its entry is written before the epoch starts and is immutable once written, and an upgrade binds future epochs only, so a routine upgrade cannot change the configuration under which an in-flight proof was made and make it fail. The guest recomputes the hash from the configuration it actually applied (PARAM-04).
  • Quorum. Not a stored threshold: the predicate is exactly 3 · s > 2 · W with checked arithmetic, evaluated identically by the L2 client, the guest and the L1 contract. The journal’s quorum field is the product 2 · W, so no division or rounding can differ between the three.
  • Predecessor. The previous checkpoint’s height, block hash and state root come from the Inbox record, so the proof always runs from the state Ethereum already accepted.
  • Recovery generation. recoveryGeneration is read from L1 storage and required to equal the generation the contract supplies for the height being built, so a batch certified under an older generation is rejected even though its proof is otherwise valid — with one case: a certificate for a block at or below the last accepted checkpoint is judged under the generation in that block's own header, never compared with the current one. It is a signed field of the vote and block-header bytes and the mechanism that scopes certificates, locks and uniqueness. The generation advances only when a stall resolution is executed: the DAO queues one entry during a settlement stall, its deadline is stored in the entry, and after that deadline anyone may execute it once, which increments the generation and discards the provisional range above the checkpoint, so the discarded branch can never land. No height is retired. A certificate from a superseded generation remains admissible as evidence of what was signed.

If any of these could be chosen by the prover, the proof would be sound but meaningless: it would prove a true statement about a set, an epoch or a predecessor that the protocol never agreed to. That is why the guest rejects a witness-supplied root even when the arithmetic is consistent (PRF-03).

4. What the guest actually checks

  1. Reconstruct the canonical precommit bytes for the head certificate and verify each signature against the key at the signer’s index in the authenticated set. A signature over different bytes, a different vote type or a different index does not count.
  2. Check that the signers are distinct, that the bitmap has exactly one bit per signer and no bit outside the set, and that the bitmap length is fixed by the set size, not by the number of signers.
  3. Sum the effective stake of the distinct signers and evaluate 3 · s > 2 · W, with W equal to the sum of the authenticated leaves’ effective stakes.
  4. Link the header chain back to the predecessor block hash with no gaps, and check that the head hash is the hash of the reconstructed head header.
  5. Recompute the finality commitment from the certificate the guest verified, rather than echoing a value from a hint.
  6. Check that recoveryGeneration equals the generation the L1 contract supplies as a public input for the height being built: a batch certified under a superseded generation is void. The generation advances only through an executed stall resolution — once per entry, after a DAO queue and the entry's stored deadline — and a block at or below the latest accepted checkpoint is judged under the generation in its own header.
  7. Decode each block body from the committed payload, execute the blocks in order from the predecessor state root, and check that each block’s transactions reproduce the transaction root committed by its header and that the final state root equals the claimed one.
  8. Recompute the data commitment over the bytes it executed and compare it with the journal.
  9. Recompute the forced-inclusion boundary from the anchored register state and require it to match the journal, then require every position the settlement frontier advances past to be resolved — dead first and unconditionally, when the record’s own deadline has passed at the anchored view, decided from its own stored block number; otherwise, for a live record, void when it is over a registered bound or every transaction is set aside; otherwise executed by walking the record’s transactions in the record’s own order, running each that can run at its turn and setting aside each that cannot, with at least one running — before the new frontier is written (FI-11, lesson 11).

5. Why one certificate is enough

The guest verifies the certificate of the head block only. Every earlier block in the range is covered by the header hash chain back to the predecessor, which Ethereum already accepted as a checkpoint. Under the fault assumption, a certificate for the head implies the head is the unique certified block at its height, and therefore that the whole prefix it commits to is the unique certified prefix (PRF-08). If that assumption is broken, the argument goes with it, and the proof cannot detect that.

6. What the proof does not prove

  • That no hidden competing chain exists. The proof establishes that the evidence presented is sufficient for the claimed transition from an authenticated predecessor. It does not establish that no other history exists elsewhere.
  • That the data is retrievable. It proves that the executed bytes are the published bytes. Whether anybody still serves them later is a retention question, not a proof question.
  • That the chain keeps producing. Liveness — enough validators online, enough provers working — is an assumption about participants, not a theorem about the statement. It also proves nothing about recovery: if settlement stalls, the chain halts safely until a stall resolution is executed — the DAO may queue one entry, and after its stored deadline anyone may execute it once to discard the provisional range above the checkpoint and resume production. Value at or below the last accepted checkpoint still exits on L1 through a withdrawal root that k distinct backend families attest, produced by a funded proving market from data that is still retrievable (MEM-15(2b)), but nothing obliges governance to queue or execute an entry, so a stall may persist.
  • That validators behaved. If at least one third of an epoch’s voting power breaks the signing or locking rules, two conflicting certificates can both be cryptographically valid and both can produce accepting proofs. ZK verification does not repair a failed consensus assumption.
  • Who proved it. There is no prover registry: any account may land a batch, and the proof says nothing about the prover’s identity.
  • That the starting point is the real history. The proof runs from the L1 checkpoint. Which checkpoint is real is settled by Ethereum and by the freshness bound for new nodes, not by the proof.

What this gives you

  • A single object that a light client, a bridge or a third party can check without replaying the chain: a proof bound to a statement hash the L1 contract computes itself.
  • Certification and execution tied together, so a valid state root can never be paired with data that was never certified, or the reverse.
  • An unambiguous quorum predicate with one owner, evaluated identically in the client, the guest and the contract.
  • A statement whose authority-defining values are all Ethereum facts, so the proof cannot be redirected to a friendlier set, epoch or predecessor.
  • Data binding for both publish paths: a hash the contract computes itself for calldata, and a KZG-plus-guest argument for blobs.

What it does not give you

  • No protection when the fault assumption fails: two valid certificates can both be proven, and the protocol’s answer is detection, disclosure and slashing, not a proof that the fork does not exist.
  • No proof of availability: the proof says the bytes are committed and published, not that they will still be served tomorrow.
  • No proof of liveness or of future production.
  • No protection against a soundness bug in the zkVM backend or the guest program; that is a bridge-theft class failure which the protocol cannot repair.
  • No aggregation: v1 accepts one proof per batch from one registered backend, so an accepted batch's soundness is that of that backend. The n-of-m aggregation over independent backends is not part of v1, and the redundancy it would add does not hold here.
  • No cost figure: the in-guest blob evaluation and the total proving cost are not yet measured.

Check yourself

The proof verifies. Does that mean no competing L2 history exists?

No. It means the evidence presented is sufficient, under the fault assumption, for the claimed transition from the authenticated predecessor. If at least one third of an epoch’s voting power signed two conflicting histories, both can be cryptographically valid and both can produce accepting proofs. The proof verifies evidence; it does not verify that the evidence is unique.

Which of these are public inputs: the validator set root, the full validator set, the block payload, the signatures?

The validator set root is a public input read from L1. The full set, the payload bytes and the signatures are witness material: the guest recomputes the root from the set and compares it with the L1 value, and it decodes the payload from the committed bytes rather than accepting a second copy.

Why must a batch never cross an epoch boundary?

Because the epoch determines the set root, the total voting power and therefore the quorum denominator. Keeping one epoch per batch keeps exactly one of each in the journal and removes per-epoch arrays. A range that would cross a boundary is split; because each batch starts at the previous checkpoint’s height plus one, no height is left out at the split.

Assumptions. This lesson relies on: fewer than one third of the epoch’s voting power breaking the signing and locking rules, and correct validators obeying them; the zkVM backend and the guest program being sound; the L1 values the contract reads being Ethereum-final; on the blob path, the KZG binding and the random-oracle model used for the challenge point; and the prover holding a complete witness, which means somebody still has the headers, bodies and signatures. If the fault assumption fails, the proof does not detect it; if a backend has a soundness bug, the proof proves something false.
