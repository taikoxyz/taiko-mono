08 — Data and proof travel together

Problem this lesson solves. It explains why this design has no "publish the data now, prove it later" path, what the June 2026 baseline queue expiry shows about that class of failure, and how the blob path binds the data a prover executed to the data Ethereum published.

In plain language

Atomicity is one transaction, not two. The Inbox exposes exactly one function that can accept a batch and advance the checkpoint, and one call must carry the range, the batch data (as calldata and/or the blob sidecars of that same transaction), the proof, and the claimed post-state values (L1-01). Fixed decision D5 states the same constraint: data and its valid ZK proof land in the same L1 transaction, and no data-first path exists in any mode, including recovery (D5).

What a data-first path costs. Today's baseline has exactly the split D5 forbids: propose() accepts a data-only proposal with no proof argument at all, and prove() is a separate transaction that later re-reads the frozen propose-time commitment (L1-01, contrast table). Between those two transactions the data is public on L1 while no proof exists. If the proof never comes, the data has occupied L1 capacity, consumed the settlement budget, and settled nothing — and the record that ties the data to a future proof can itself expire.

The real example: June 2026. The repository at revision 7718753c1 shows the failure class, not a hypothetical. The baseline's forced-inclusion mechanism was disabled after the June 2026 incident, and the queued entries' blobs had expired from the blob retention window and can no longer be derived. The one-time owner function init3() (Inbox.sol:246-258) moves the queue head to the tail, permanently discarding every queued entry, and its documentation records that the fees remained in the contract. This design does not rebuild that queue: forced inclusion is removed entirely (FI-REMOVED-01), so there is no queued request reference that can outlive its data and no owner-reachable queue state to void. What remains is the atomicity rule — data and its proof land in one transaction, so the acceptance path never waits on a reference created earlier (L1-01) — together with the retention limit and the backlog cap, stated honestly with their own limits (DA-05, DA-06). What the repository establishes is the expiry and the void; the cause of the June 2026 incident is recorded as unverified in the baseline research and is not claimed here (taiko-baseline-contracts.md).

No second door. The rule is not only about one function name: no entry point — public, external, or reachable through an upgrade initialiser — may write a batch record, predecessor link, proposal hash, data commitment or checkpoint pending a proof, and an "announce" function may exist only if nothing it writes is ever read by the acceptance path (L1-02). Admission is equally bare: any account may land any unsettled range with a valid (data, proof) pair; there is no whitelist, no bond, and no deadline, timestamp or age condition that can make a range permanently unacceptable (L1-04). The checkpoint only moves forward (L1-06).

How a blob is bound to the proof (DA-03), in plain words. A blob is published in the same transaction as the proof, and four things link the two:

  1. The contract reads the transaction's own blob versioned hashes with the BLOBHASH opcode and requires each to be non-zero and equal to the hash the proof committed to — a blob from another transaction cannot be substituted (DA-03(i)).
  2. The contract derives the challenge point z itself, by hashing all the other public inputs (a Fiat–Shamir derivation). The submitter cannot supply z, so the prover cannot choose the evaluation point after choosing its data (DA-03(iii)).
  3. The contract calls the EIP-4844 point-evaluation precompile at address 0x0A with (versionedHash, z, y, commitment, proof). The precompile verifies both that kzg_to_versioned_hash(commitment) equals the versioned hash and the KZG opening p_blob(z) = y — the pairing happens on L1, inside the precompile (DA-03(ii)).
  4. The guest independently interprets the blob bytes it actually executed as 4096 coefficients, rejects any non-canonical chunk, evaluates its own polynomial at z, and rejects the batch unless p_data(z) = y (DA-03(iv)). If the executed data and the published blob were different polynomials, they would agree at the random point with probability at most 4095 / |F|, about 2-243 per attempt — and each attempt requires a fresh commitment. The specification calls this a proof sketch with named premises, not a machine-checked theorem, and its in-guest cost is unmeasured (DA-03).

Why the calldata path needs no probability argument. There, the contract hashes the exact calldata slice and passes that digest as the public input, and the guest recomputes the same hash over the data it executed and requires equality (DA-02, PRF-07(a)). Both sides hash the same bytes, so the binding is an equality, not a statistical argument — which is why the calldata path remains unconditionally available if any blob-path premise fails.

What failure does. The acceptance call executes in a fixed order and writes nothing until the verifier has returned exactly abi.encode(true). A revert, an empty return or any other value means the batch is unaccepted, and land must revert with no partial effect: no checkpoint, no height advance, no payout, no event (L1-03). And a failed attempt does not poison the range: the first valid submission wins, but re-submission of the same batch by a different account must be accepted whenever the first submission did not land, and the reward is paid to the account that paid for the landing transaction (L1-10).

Precise definitions

  • Atomic acceptance. One entry point, one transaction, data and proof inseparable; no propose-then-prove path in any mode (L1-01, D5).
  • Pending record. Any batch record, predecessor link, proposal hash, data commitment or checkpoint written before a proof exists; forbidden, including through upgrade initialisers (L1-02).
  • Admission rule. The conditions under which land may be called: any account, no gate, no expiring range; only contiguity, non-emptiness and transaction-bounded loops are permitted (L1-04).
  • Canonical data availability. The accepting L1 transaction itself — its calldata and/or its blob sidecars. No second canonical location, and nothing outside that transaction is sufficient for STATUS-06 (DA-01).
  • Calldata path. The contract computes the data commitment over the exact calldata slice and requires the guest's recomputation to match (DA-02).
  • Blob path. BLOBHASH equality, an on-chain KZG opening at a Fiat–Shamir challenge, and an in-guest evaluation at the same point (DA-03).
  • Retention and its limit. Blobs are not a permanent store; retrievability is specified as a window in L1 block numbers with an archive requirement, and the retention clock starts at acceptance (DA-05).
  • No forced-inclusion path (FI-REMOVED-01). The design has no L1 request, queue, escrow, duty or escape hatch, so no data-carrying request exists whose reference could expire; the remaining response to censorship is the conditional statistical property of LIVE-04, not a data-availability rule (FI-REMOVED-01).
  • Data-commitment binding. Exactly one of the two paths holds per batch, and the guest must reject the batch if its recomputation differs; this is the rule that makes a proof unusable for unrelated data (PRF-07).

Two rows carry the lesson. The blob path's guarantee is probabilistic and conditional on four named premises; the calldata path's is an exact equality. And the June 2026 row is why the design does not keep a queued reference at all: a reference that outlives its data is how a queue becomes unincludable and unrefundable, and this design removes that state rather than promising to operate it better (FI-REMOVED-01).

Attacks this prevents

  • Publish-and-never-prove. Data cannot be put on L1 ahead of its proof, so a batch cannot consume settlement capacity while settling nothing (L1-01).
  • The expiring-reference class. Because the data travels with the proof, there is no interval in which a batch's data is on L1 while its proof is not; the retention clock starts at acceptance (DA-05).
  • Proof/data decoupling. The contract computes the data commitment itself and the guest recomputes it over what it executed, so a valid proof cannot be attached to unrelated data (DA-02, PRF-07).
  • Grinding the challenge point. The prover cannot pick z after fixing its data, because the contract derives it from the other public inputs (DA-03(iii)).
  • Blob substitution. Reading BLOBHASH from the transaction itself stops a batch from referencing blobs it did not publish (DA-03(i)).
  • Partial effects from failed verification. No checkpoint, height advance, consumed inclusion or payout survives a failed proof (L1-03).
  • First-submitter capture. Re-submission by another account is allowed when the first attempt did not land, and no announce or reservation step can gate a range (L1-10, L1-04).

Attacks this does not prevent

  • Nobody proving the batch. Atomicity removes the data-first failure, not the prover-outage failure: if no prover finishes, settlement stalls and the backlog cap eventually halts production safely (HALT-03).
  • Loss of the L2 copies before the batch lands. The data is retrievable from the L2 network until acceptance, which is a liveness assumption, not an enforcement (A-CONS-5, A-DA-2).
  • Blob expiry after acceptance. Past the retrievability window, retrievability depends on archives rather than on Ethereum, and the design says so (DA-05).
  • An unmeasured blob-path cost. Whether the in-guest evaluation is usable at scale is unmeasured; the calldata path remains available unconditionally (PARAM-03).
  • L1 censorship of the atomic transaction. Data and proof cannot land, and there is no forced-inclusion path to fall back on because the design deliberately has none; that is a disclosed consequence of L1 failure with no protocol remedy (T-7, LIVE-04).
  • A soundness bug in a backend or in the guest program. A mis-proven statement is outside what atomicity can repair (PRF-09).

Self-check

Why is a published blob not enough on its own to bind the data to the proof?

Because the proof could have been computed over different data. The precompile checks the KZG opening of the published blob, and the guest separately checks that the polynomial of the data it executed agrees with the accepted evaluation at the same challenge point; only the two together pin the executed data to the published blob (DA-03).

Why can the prover not choose the challenge point z?

It is derived on-chain by the contract by hashing the other public inputs, which include the data commitment and hence the versioned hashes of the very blobs the prover must fix first; a submitter- supplied z is not accepted (DA-03(iii)).

Your proof transaction fails. What state changed, and can someone else still land the batch?

No partial effect: no checkpoint, no height advance, no payout, no event (L1-03). Another account may land the same batch with the same data commitment; re-submission must be accepted if the first attempt did not land, and the reward goes to whoever pays for the landing transaction (L1-10).

Challenge this. The lesson used: (i) D5 and L1-01–L1-04 as the constraints; (ii) the baseline comparison being valid only at revision 7718753c1, whose propose()/prove() split is the data-first path D5 deletes; (iii) the June 2026 record, where the repository establishes the blob expiry, the queue void and the retained fees, while the cause is explicitly unverified; (iv) the blob binding's four premises — KZG binding, the random- oracle model for Fiat–Shamir, correct in-guest field arithmetic, canonical field elements — whose in-guest cost is unmeasured; (v) the calldata path's exact-equality binding; (vi) the removal of forced inclusion (FI-REMOVED-01), so no queue state exists whose reference could expire.
