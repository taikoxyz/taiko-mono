When things go wrong

This lesson gives you the failure-handling rules: what happens when a proposer hides a block, when votes or certificates do not arrive, when validators go offline, when data cannot be found or when settlement stalls — and the guarantee class that follows: a confirmation above the last batch accepted on Ethereum is provisional. A settlement stall halts the chain safely: nothing at or below the last accepted checkpoint changes, value at or below it still exits on Ethereum alone, and v1 has no path that clears the stall. This is a design description; none of it is implemented, measured, audited or deployed.

The idea

Failures are ordinary inputs to this protocol, not exceptions bolted on afterwards. Two rules do most of the work.

A timeout is never evidence of absence. When a timer expires, a node may change what it does — retry, change the view, halt — but it may not conclude that a vote, a certificate or a block does not exist somewhere else, and it may not invalidate anything (STATUS-10). A certificate that is revealed after everyone gave up is still the valid certificate.

A validator’s lock keeps two histories from both being certified. A validator that precommits a block at a height is locked on it. It will not prevote a conflicting block at that height unless it sees a proof-of-lock-change at the same height and a strictly later round (CONS-04). A certified height implies more than a third of the voting power is honest and locked, so a conflicting certificate would need those validators to break the lock — which is exactly the behaviour the rule forbids and slashing punishes.

A confirmation above the last batch accepted on Ethereum is provisional. The L2 certificate is real, and more than two thirds of the epoch’s voting power signed it; but until the batch carrying it is accepted on L1 with its proof, no v1 rule makes it permanent, and v1 has no path that replaces it. That is the guarantee class of every confirmation above the checkpoint, and every interface that shows one must say so (STATUS-04, STATUS-11).

A settlement stall halts the chain, and the halt is safe. A stall means that no batch extending the current L1 checkpoint has been accepted for long enough that a normal slow proof, or a single prover failure inside the normal envelope, cannot be the explanation. When it holds, the chain stops making progress, and nothing restarts it. Everything at or below the last accepted checkpoint is preserved exactly; every confirmation above it stays provisional, and v1 has no rule that discards it either.

A user can always leave from the last settled state. While the chain is halted, a withdrawal whose signal is already inside the last accepted checkpoint stays executable on Ethereum alone: it needs no new L2 blocks, no quorum and no validator, only the withdrawal delay measured on L1 (MEM-15). That exit is what keeps a halted chain safe for holders. Value above the last accepted checkpoint, or value that was never messaged, has no L1-provable claim while the chain is halted; it becomes withdrawable only when a later checkpoint covers it.

Nothing in v1 clears a stall. There is no automatic path, no permissionless path and no governance-mediated path: clearing the stall needs a future protocol update whose procedure is not yet specified. The chain stays halted until then. Nothing at or below the last accepted checkpoint is touched by any rule, and no rule discards the provisional range above it either; the halt simply stops production. Value above the checkpoint stays provisional, a transaction in that range is not settled and not replayed, and inclusion is not guaranteed (ECON-11).

Locks are scoped by generation. A lock constrains votes at its height within the generation it was taken in, and it is released only by the rules above. v1 never begins a new generation, so no lock is ever superseded and no lock can wedge the chain through a restart. A certificate carrying a superseded generation would be void at the acceptance rule, though it remains admissible as evidence of what its signers signed (CONS-04, CONS-12).

A cohort that goes silent takes production with it. Within a set version nothing changes: the committed weights still include validators that have stopped signing, so if enough of them stop that quorum cannot be met, production halts — there is no degraded threshold. Nothing replaces the silent weight either. Membership has no liveness gate, so an entry that goes quiet stays in every committed set version, and v1 has no rule that removes it or that draws a replacement set. The silent validators keep their whole bonded stake; they forfeit only the rewards they did not earn. Clearing the halt needs a future protocol update, not a rotation.

The halt can still be permanent. Halting remains the correct action for missing data at or below the accepted checkpoint, for a missing validator-set commitment, for an L1 view that disagrees with consensus, and for a failure of the stake assumption. In those cases no rule-legal action can restore progress, and a halt can be permanent (HALT-01).

How it works

Withholding: what can be hidden, and what it costs

The design assumes messages can be late, lost or delivered selectively. For each object that can be withheld, the honest action is fixed (WH-01). No case of non-receipt justifies concluding that an object does not exist, and no case of non-receipt alone justifies slashing.

What is evidence, and what is only suspicion

A protocol penalty needs objective, self-contained, on-chain-verifiable evidence: two signed messages of the same type at the same height and round with different block ids, or a signed message that violates a rule whose inputs are all on-chain (WH-02). Everything else — a message that did not arrive, a height that did not advance, a proof that has not been submitted, a peer that did not answer — is local suspicion. It can change local behaviour: retry, view change, peer selection, disclosure. It cannot trigger a penalty or a statement about what exists elsewhere. Silence is not provable.

The lock, stated precisely

A validator’s lock is a local triple (locked_height, locked_value, locked_round). It is per height: it constrains votes at that height only, it survives a restart while the height is unresolved, and it is released in exactly two ways:

  • the locked value commits at that height within the current generation — once the value the validator locked on commits, the lock has done its work; or
  • the validator sees a proof-of-lock-change at the same height H, for a different value, at a round strictly later than its locked_round and earlier than the current round.

Nothing else unlocks. A proof-of-lock-change at the same round, at an earlier round, or for the value already locked does not unlock; a proof-of-lock-change at another height neither unlocks this height nor creates a lock there. The pol_round field carried in a proposal is only a hint; the validator must verify the proof itself. And a validator that holds a lock at a height and then sees a valid commit certificate for a different block at that height has evidence that the assumptions failed: it halts, and it does not treat the certificate as an unlock or as a reason to abandon the halt. v1 never begins a new generation, so no lock is ever superseded by a restart; a certificate carrying a superseded generation would be void at the acceptance rule, and the lock remains in force until the ordinary rules release it.

Why this protects safety: a commit certificate requires more than two thirds of the epoch’s voting power. If a second, conflicting commit certificate existed, the two signer sets would overlap in more than one third of the power, and those validators would have had to sign conflicting blocks at the same height. The lock rule says the honest ones never do. A certificate that exists but has not been published can delay a node that has not seen it; it cannot displace a decision.

Halt: what it is, and what it costs

A correct validator halts — stops signing and stops advancing its certified view — when any of the following holds and no rule-legal action can resolve it (HALT-01):

  • it cannot obtain the data for a certified or locked block;
  • it cannot obtain a quorum for a height within the timeout ladder;
  • the L1 facts it must consume are not yet Ethereum-final, or its L1 view disagrees with the consensus view;
  • the L1 validator-set commitment for the epoch it is about to enter is absent; or
  • the unsettled-depth cap would be exceeded.

Halting is not a fork, not a rollback and not a vote to abandon the chain. A halting node keeps serving what it has and keeps its state so it can resume. There is no emergency key and no operator override, and v1 has no recovery path of any kind: a settlement stall halts the chain, funds at or below the last accepted checkpoint are safe, the exit works, and clearing the stall needs a future protocol update whose procedure is not yet specified (HALT-04). If progress needs information that no rule-legal action can obtain, the protocol says so and stops.

Halting remains the correct outcome for a settlement stall and for a missing ingredient that no action can replace — anything at or below the last checkpoint accepted on Ethereum.

A settlement stall, step by step

  1. Production stops. No batch extending the current L1 checkpoint is accepted for long enough that a normal slow proof or a single prover failure cannot be the explanation. Nothing declares the stall early from a local view: the condition is a fact about the checkpoint, which every observer reads from Ethereum.
  2. Halt. Correct validators stop signing and keep their state and the data they hold. The chain serves what it has. Nothing at or below the last accepted checkpoint changes, and every confirmation above it stays provisional.
  3. Exit while halted. A withdrawal whose signal is at or below the last accepted checkpoint stays executable on Ethereum alone, subject only to the withdrawal delay on the L1 clock (MEM-15). Value above the checkpoint, or value that was never messaged, has no L1-provable claim until a later checkpoint covers it.
  4. No recovery path. Nothing in v1 clears the stall. There is no automatic route, no permissionless route and no governance-mediated route, and the design gives no protocol-level guarantee of liveness after a stall. Clearing it needs a future protocol update whose procedure is not yet specified.
  5. What is preserved. The last accepted checkpoint and everything at or below it are never rewritten; the recovery generation is carried in the signed vote and header bytes and v1 never advances it, so no height is retired and no branch is discarded. A transaction above the checkpoint is unsettled rather than replayed, and its inclusion is not guaranteed.

What a stall means for users

  • Below the accepted checkpoint, funds are not lost, and exit needs no L2 liveness. A withdrawal whose signal is at or below the checkpoint stays executable on Ethereum alone, subject only to the withdrawal delay on the L1 clock (MEM-15). A halt does not forfeit it.
  • Above the accepted checkpoint, a confirmation stays provisional. No v1 rule makes it permanent, and no v1 rule discards it either; it simply is not settled, and value above the checkpoint has no L1-provable claim until a later checkpoint covers it.
  • Accepted history stays valid. Anything at or below a checkpoint or batch accepted on L1 is never touched by any rule.
  • Off-chain losses are not compensated. A trade, a signed message or a position built on a provisional confirmation has no protocol remedy (ECON-11).
  • Validators are not punished for halting. Halting is the required behaviour when the rules say so, and a lock that the ordinary rules release is not treated as misconduct.
  • Operators must not improvise. Publishing data without a proof accepts nothing — publication writes no batch state — so it cannot unstick the chain; picking a branch, by contrast, converts a safe halt into an unsafe divergence. No operator action clears a stall: v1 offers no path at all.
  • A halt below the checkpoint may still be permanent. If every holder of an accepted block’s data has disappeared, nothing in the protocol can reconstruct it, and no rule may replace accepted history. That is a disclosed liveness cost of permanent settlement.
  • A stalled chain does not resume in v1. Clearing the stall needs a future protocol update whose procedure is not yet specified, and there is no protocol-level bound on how long a halt lasts.

Resuming a node afterwards

After a halt, a correct participant resumes only from the highest certified block whose data and certificate it can independently reconstruct (HALT-02). It never adopts an alternative history at a height it has already certified, and it never treats a timeout during the halt as evidence that a certificate does not exist. On resuming four rules apply:

  1. Each validator enforces a signed-message uniqueness check over its own signing history: no message of the same type at the same height and round may be signed twice, including after a restart or a resync. A validator that cannot prove it has not already signed for a (height, round, type) must not sign — lost memory is treated as a signing fault, not as a fresh start.
  2. A resuming validator re-verifies the epoch and the validator set for the height it is resuming at instead of trusting its cache.
  3. Replayed historical messages are rejected: every vote carries its epoch and round, and receiving rules reject messages for heights already certified.
  4. A resumed node’s first act is a data-and-certificate sync, not a proposal.

A node-level resync is not a rewrite of settled history: it starts from the last checkpoint accepted on Ethereum and resumes from there, and HALT-02’s rules govern what a node may do at heights it has already certified. No v1 rule discards an unsettled height or rewrites a certified one.

Why the chain halts instead of discarding unsettled history

An unbounded halt is not free: if settlement stops and nothing restarts it, the chain stops serving users, and the only remedies are outside the protocol. The design keeps the settled part settled and makes the unsettled part explicitly provisional. A checkpoint or batch accepted on Ethereum is never rewritten, and the history above it is never discarded by a v1 rule either; it simply is not settled, and the halt continues until a future protocol update supplies a path back. That is the trade: a strict boundary at the last accepted checkpoint, paid for with a liveness cost that no v1 rule removes.

The honest costs are disclosed, not priced away. Transactions above the checkpoint are not settled and their inclusion is not guaranteed; whether the chain resumes at all is left to a future protocol update whose procedure is not yet specified, and the design states no protocol-level guarantee of liveness after a stall. Nothing in v1 lets any party choose a state, a checkpoint or a height, and nothing in v1 prices the halt with a bond.

A lock, walked through. A validator is locked on block B at (H, round 2). At round 5 it receives a proposal for a different block B′ whose hint says pol_round = 4. The hint is not evidence: the validator must obtain and verify the proof-of-lock-change itself. If that proof is for B′ at (H, round 4), it unlocks and prevotes B′, because 4 is strictly later than its locked round 2 and the value differs. If the proof is for round 2, or for B, it stays locked and prevotes B. If instead it obtains a commit certificate for a different block at H, it halts — it does not treat the certificate as an unlock. v1 never begins a new generation, so no restart can supersede the lock; it stays in force until the rules above release it, and the conflicting certificate remains evidence that the assumptions failed.

A prover that never finishes, and then a stall. A batch is certified at time t. At t + 30 minutes there is still no proof. Nothing special happens yet: a proof consuming the whole envelope is normal, not misconduct; other provers may produce a proof for the same data commitment and land it, and the first valid landing wins. If in addition no batch extending the current checkpoint is accepted for long enough that a normal slow proof cannot explain it, the chain stalls. Correct validators stop signing and keep serving what they hold, and nothing in v1 clears the stall. While it is halted, a user whose withdrawal signal is at or below the last accepted checkpoint can still exit on Ethereum alone, subject only to the L1 withdrawal delay. Nothing above the checkpoint is discarded by any rule, and nothing is replayed; the certified batch and the transactions in it are simply unsettled, their inclusion is not guaranteed, and clearing the stall needs a future protocol update whose procedure is not yet specified.

What this gives you

  • A fixed, minimal response for every class of missing message or data, without inventing rules at run time.
  • Safety that does not depend on seeing a certificate: the lock protects the decision, not the publication.
  • A principled resume: a node restarts from the highest certified block whose data and certificate can be reconstructed, never from a competing branch.
  • A settled prefix that is never rewritten: history above it is provisional, and no v1 rule replaces or discards it.
  • A recovery generation that cannot be steered: it is a signed field that scopes certificates, v1 never advances it, and no state, checkpoint or height can be chosen through it.
  • An exit that needs no L2 liveness: a withdrawal whose signal is at or below the last accepted checkpoint is executable on Ethereum alone (MEM-15).
  • Locks scoped by generation: a lock constrains votes at its height within the generation it was taken in, and v1 never begins a new one.
  • A clear account of silence: an entry that stops signing keeps its stake and its place in every committed set version, and a cohort that stops signing halts production rather than shedding weight.

What it does not give you

  • Availability. If data for a block at or below the accepted checkpoint is gone, the halt can be permanent; retention is an assumption, not an enforced duty.
  • Permanent confirmations above the last accepted checkpoint. A certified block there is provisional: no v1 rule makes it permanent, and off-chain losses are not compensated.
  • Guaranteed liveness after a stall. v1 has no way to clear one — no automatic, permissionless or governance-mediated path — and clearing it needs a future protocol update whose procedure is not yet specified, with no protocol-level bound on how long a halt lasts.
  • A way to move or discard history. No v1 rule discards the confirmation above the checkpoint or replaces it, so a stalled chain waits: transactions above the checkpoint are not settled, their inclusion is not guaranteed, and a party that needs one must be prepared to resubmit it later.
  • Punishment for silence. Only conflicting signed messages are objectively provable; a node that never answers is not slashable, and a validator that goes quiet loses neither its place in the committed set nor its stake.
  • A way to keep producing after quorum is lost, and no rule that takes weight from anyone. Production halts; the committed set does not change, and nothing removes the silent weight or draws a replacement set.
  • An instant or operator unstick button. No v1 path clears a settlement stall: not governance, not an operator, not an emergency key and not a bond.
  • Any measured detection rate, timeout value or retention window. Those are not yet measured.

Check yourself

Validators have waited past every timeout and seen no certificate for height H. May they certify a different block at H?

No. A timeout changes local round state only. The lock still binds: without a proof-of-lock-change at H for a different value at a strictly later round, a validator prevotes its locked value. If a certificate for the locked block eventually appears, it is accepted then.

A node is restarted from a backup and cannot prove which messages it already signed. What does it do?

It must not sign for any (height, round, type) it cannot prove it has not already signed. Lost memory is treated as a signing fault, not as a fresh start, because double-signing is the one objectively punishable offence and the one that can break safety.

Is publishing a batch’s data to L1 without a proof a way to unblock settlement?

No. Publication is permissionless, but it writes a publication record and no batch state: it accepts nothing and advances no height, so settlement resumes only when a valid proof lands. A publication that is never proven before its deadline is discarded and can be published again, so it never becomes a second acceptance path.

Is a PoS confirmation above the last accepted checkpoint final?

No. It is valid but provisional: no v1 rule makes it permanent, and v1 has no path that replaces or discards it either. Accepted checkpoints and accepted batches are never touched. Value above the checkpoint has no L1-provable claim until a later checkpoint covers it, and no protocol penalty compensates an off-chain loss.

What clears a settlement stall?

Nothing in v1. There is no automatic path, no permissionless path and no governance-mediated path, and there is no protocol-level guarantee of liveness after a stall. Clearing it needs a future protocol update whose procedure is not yet specified. Nothing at or below the last accepted checkpoint is touched, and the exit from that state stays available on Ethereum alone.

Does a lock survive a generation change?

v1 never begins a new generation, so no lock is ever superseded and no validator is freed by a restart; the lock stays in force at its height until the commit of the locked value or a strictly later proof-of-lock-change releases it. A certificate carrying a superseded generation would be void at the acceptance rule, which is what the signed generation scopes.

The chain has stalled. Does anything restart it?

No. v1 has no recovery path of any kind: nothing automatic, nothing permissionless and nothing governance-mediated restarts the chain. The chain stays halted until a future protocol update supplies a path, and there is no protocol-level bound on how long that takes. A user can still exit from the last settled state on Ethereum alone while the halt lasts.

What is the recovery generation for?

It is a counter carried in the signed vote and header bytes that scopes certificates, locks and uniqueness: a certificate carrying a superseded generation is void at the acceptance rule, so a branch scoped to an older generation could never be accepted again. v1 has no recovery path, so the generation never advances here and no height is retired.

A third of the voting power stops signing. Is the chain stuck?

For the set version already committed the silent weight still counts, so quorum can fail and production halts. Nothing is taken from the silent validators: membership has no liveness gate, so they keep their stake and their place in every committed set version. There is no rotation and no replacement set, so v1 has no rule that clears the halt; clearing it needs a future protocol update.

Assumptions

  • Fewer than one third of each epoch’s voting power is malicious, and the rest follows the lock and vote-uniqueness rules.
  • Enough validators are online to form quorums in normal operation. Inside a set version the protocol has no degraded mode, and no rule removes a validator that goes quiet, so a silent cohort halts production.
  • Somebody keeps the data for every certified block until its proof lands, or publishes it to L1 while the blobs are retrievable.
  • At least one prover finishes each batch before the retention assumption expires.
  • v1 has no stall parameter and no recovery path. A settlement stall halts the chain, the exit from the last settled state stays available on Ethereum alone, and clearing the stall needs a future protocol update whose procedure is not yet specified; there is no protocol-level bound on how long a halt lasts.
  • The reward pool is actually funded and the reward is not below the cost of landing; an empty or below-cost pool reaches a settlement stall with no adversary at all.
  • Outside L1-level censorship and the absence of any prover, a sub-threshold coalition cannot force a settlement stall.
  • Ethereum itself keeps producing, including and finalizing blocks.
  • The timeout values, the retention window and the cap are placeholders awaiting measurement.
