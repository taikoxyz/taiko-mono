When things go wrong

This lesson gives you the failure-handling rules: what happens when a proposer hides a block, when votes or certificates do not arrive, when a set goes offline, when data cannot be found or when settlement stalls — and the guarantee class that follows: a confirmation above the last batch accepted on Ethereum is provisional, and a bonded, delayed, permissionless recovery can replace it. This is a design description; none of it is implemented, measured, audited or deployed.

The idea

Failures are ordinary inputs to this protocol, not exceptions bolted on afterwards. Two rules do most of the work.

A timeout is never evidence of absence. When a timer expires, a node may change what it does — retry, change the view, halt — but it may not conclude that a vote, a certificate or a block does not exist somewhere else, and it may not invalidate anything (STATUS-10). A certificate that is revealed after everyone gave up is still the valid certificate.

A validator’s lock keeps two histories from both being certified. A validator that precommits a block at a height is locked on it. It will not prevote a conflicting block at that height unless it sees a proof-of-lock-change at the same height and a strictly later round (CONS-04). A certified height implies more than a third of the voting power is honest and locked, so a conflicting certificate would need those validators to break the lock — which is exactly the behaviour the rule forbids and slashing punishes.

A confirmation above the last batch accepted on Ethereum is provisional. The L2 certificate is real, and more than two thirds of the epoch’s voting power signed it; but until the batch carrying it is accepted on L1 with its proof, the protocol’s own rules can replace it. That is the guarantee class this design selected, and every interface that shows such a confirmation must say so (STATUS-04, STATUS-11). (user decision D-7: Mode B selected)

A settlement stall is the one thing that triggers a recovery. A stall means that no batch extending the current L1 checkpoint has been accepted for T_STALL — long enough that a normal slow proof, or a single prover failure inside the normal envelope, cannot be the explanation (REC-02). Anyone may then start a recovery, permissionlessly, by posting a bond on L1. There is no operator, no DAO vote and no validator quorum in the path.

The recovery is delayed, and honest progress cancels it. It takes effect only after T_RECOVERY_DELAY. If any valid batch extending the current checkpoint is accepted during that window, the recovery is cancelled — and the invoker’s bond is slashed to the protocol treasury, so trying is not free. A certificate or a proof for a discarded height does not cancel it, because those heights are by construction not yet settled.

When it completes, unsettled history is replaced. Everything above the last checkpoint accepted on Ethereum — inclusions, ordering, balances and bridge messages that were only provisional — is discarded, and the chain resumes from that checkpoint. Checkpoints and batches already accepted on Ethereum are never touched, and neither is anything below them. A rolled-back L2 transaction is not replayed automatically: it must be resubmitted, and inclusion is not guaranteed. Off-chain losses are not compensated by any protocol penalty (ECON-11).

Where recovery cannot help, the chain still halts. Halting remains the correct action for missing data at or below the accepted checkpoint, for a missing validator-set commitment, for an L1 view that disagrees with consensus, and for a failure of the stake assumption. In those cases no rule-legal action can restore progress, and a halt can be permanent (HALT-01).

How it works

Withholding: what can be hidden, and what it costs

The design assumes messages can be late, lost or delivered selectively. For each object that can be withheld, the honest action is fixed (WH-01). No case of non-receipt justifies concluding that an object does not exist, and no case of non-receipt alone justifies slashing.

What is evidence, and what is only suspicion

A protocol penalty needs objective, self-contained, on-chain-verifiable evidence: two signed messages of the same type at the same height and round with different block ids, or a signed message that violates a rule whose inputs are all on-chain (WH-02). Everything else — a message that did not arrive, a height that did not advance, a proof that has not been submitted, a peer that did not answer — is local suspicion. It can change local behaviour: retry, view change, peer selection, disclosure. It cannot trigger a penalty or a statement about what exists elsewhere. Silence is not provable.

The lock, stated precisely

A validator’s lock is a local triple (locked_height, locked_value, locked_round). It is per height: it constrains votes at that height only, it survives a restart while the height is unresolved, and it is released in exactly two ways:

  • the height commits — once H commits the lock has done its work; or
  • the validator sees a proof-of-lock-change at the same height H, for a different value, at a round strictly later than its locked_round and earlier than the current round.

Nothing else unlocks. A proof-of-lock-change at the same round, at an earlier round, or for the value already locked does not unlock; a proof-of-lock-change at another height neither unlocks this height nor creates a lock there. The pol_round field carried in a proposal is only a hint; the validator must verify the proof itself. And a validator that holds a lock at a height and then sees a valid commit certificate for a different block at that height has evidence that the assumptions failed: it halts, and it does not treat the certificate as an unlock.

Why this protects safety: a commit certificate requires more than two thirds of the epoch’s voting power. If a second, conflicting commit certificate existed, the two signer sets would overlap in more than one third of the power, and those validators would have had to sign conflicting blocks at the same height. The lock rule says the honest ones never do. A certificate that exists but has not been published can delay a node that has not seen it; it cannot displace a decision.

Halt: what it is, and what it costs

A correct validator halts — stops signing and stops advancing its certified view — when any of the following holds and no rule-legal action can resolve it (HALT-01):

  • it cannot obtain the data for a certified or locked block;
  • it cannot obtain a quorum for a height within the timeout ladder;
  • the L1 facts it must consume are not yet Ethereum-final, or its L1 view disagrees with the consensus view;
  • the L1 validator-set commitment for the epoch it is about to enter is absent; or
  • the unsettled-depth cap would be exceeded.

Halting is not a fork, not a rollback and not a vote to abandon the chain. A halting node keeps serving what it has and keeps its state so it can resume. There is no emergency key, no operator override and no governance rescue that can advance, rewind or replace the checkpoint (HALT-04). If progress needs information that no rule-legal action can obtain, the protocol says so and stops.

A pure settlement stall is different: it has a rule-legal action, the recovery. Halting remains the correct outcome when the missing ingredient is data or participation that recovery cannot replace — anything at or below the last checkpoint accepted on Ethereum. (user decision D-7: Mode B selected)

Recovery, step by step

  1. Trigger. Only one condition starts it: a settlement stall — no batch extending the current L1 checkpoint has been accepted for T_STALL. The threshold is derived from the proof envelope plus witness generation, queueing, L1 inclusion and a margin, and it is strictly larger than the envelope, so a normal slow proof cannot trigger it.
  2. Invocation. Anyone posts a bond in an L1 transaction containing only the claim and the bond. No DAO, operator or validator quorum is involved, and the invoker does not choose the restored checkpoint, the validator set or any configuration value.
  3. Delay and cancellation. The recovery takes effect only after T_RECOVERY_DELAY. Acceptance of any valid batch extending the current checkpoint during that window cancels it and sends the bond to the protocol treasury. The reveal of a certificate or proof for a discarded height does not cancel it, because those heights are not yet settled.
  4. Completion. Everything above the last checkpoint accepted on Ethereum is replaced, and the chain resumes from it, re-entering the epoch schedule at that point with whatever validator set the L1 staking contract already fixes. Ethereum-final checkpoints and accepted batches are untouched.
  5. Afterwards. A late proof for a discarded height is void above the restored checkpoint, though its data commitment may be reused against it; a late certificate remains usable as evidence. A rolled-back transaction is not replayed and must be resubmitted. Repeated recovery is limited by an escalating bond and a cooldown.

(user decision D-7: Mode B selected)

What a halt, and what a recovery, mean for users

  • Below the accepted checkpoint, funds are not lost; exit is delayed. A withdrawal needs the settlement pipeline to resume. A halt delays withdrawals while nothing is forfeited (MSG-03).
  • Above the accepted checkpoint, a confirmation can be replaced. A recovery discards that range and resumes from the last checkpoint accepted on Ethereum. A transaction in the replaced range is not replayed automatically and must be resubmitted. (user decision D-7: Mode B selected)
  • Accepted history stays valid. Anything already anchored to a checkpoint or batch accepted on L1 remains authenticated, and recovery may not touch it.
  • Off-chain losses are not compensated. A trade, a signed message or a position built on a provisional confirmation has no protocol remedy (ECON-11).
  • Validators are not punished for halting. Halting is the required behaviour when the rules say so.
  • Operators must not improvise. “Unsticking” the chain by publishing data without a proof, or picking a branch, converts a safe halt into an unsafe restart. The only legitimate actions are the rule-legal ones, and for a settlement stall the rule-legal action is the published recovery.
  • A halt below the checkpoint may still be permanent. If every holder of an accepted block’s data has disappeared, nothing in the protocol can reconstruct it, and recovery may not replace accepted history. That is a disclosed liveness cost of permanent settlement.

Restarting afterwards

After a halt, a correct participant resumes only from the highest certified block whose data and certificate it can independently reconstruct (HALT-02). It never adopts an alternative history at a height it has already certified, and it never treats a timeout during the halt as evidence that a certificate does not exist. On restart four rules apply:

  1. Each validator enforces a signed-message uniqueness check over its own signing history: no message of the same type at the same height and round may be signed twice, including after a restart or a resync. A validator that cannot prove it has not already signed for a (height, round, type) must not sign — lost memory is treated as a signing fault, not as a fresh start.
  2. A resuming validator re-verifies the epoch and the validator set for the height it is resuming at instead of trusting its cache.
  3. Replayed historical messages are rejected: every vote carries its epoch and round, and receiving rules reject messages for heights already certified.
  4. A resumed node’s first act is a data-and-certificate sync, not a proposal.

Recovery is not a restart of settled history: it restores the last checkpoint accepted on Ethereum and resumes from there, and HALT-02’s rules still govern what a node may do at heights it has already certified. (user decision D-7: Mode B selected)

Why unsettled history is replaced instead of halting forever

An unbounded halt is not free: if settlement stops and nothing in the protocol can restart it, the chain stops serving users, and the only remedies are outside the protocol. The selected design keeps the settled part settled and makes the unsettled part explicitly provisional. A checkpoint or batch accepted on Ethereum is never rewritten; history above it can be replaced by a bonded, delayed, permissionless recovery whose invoker pays if honest progress arrives. That is the trade: an outage-free path back to a working chain, paid for with a weaker guarantee above the last accepted checkpoint. (user decision D-7: Mode B selected)

The resistance argument is not a claim that abuse is impossible. Recovery is a manipulation primitive with a price: an adversary who can cause or prolong a stall may be able to replace unfavourable unsettled history. The bond, the delay, cancellation by any valid batch, the treasury penalty and the limits on repeated recovery are the defences, and the conditions under which the argument would fail are stated with the rule (REC-03). (user decision D-7: Mode B selected)

A lock, walked through. A validator is locked on block B at (H, round 2). At round 5 it receives a proposal for a different block B′ whose hint says pol_round = 4. The hint is not evidence: the validator must obtain and verify the proof-of-lock-change itself. If that proof is for B′ at (H, round 4), it unlocks and prevotes B′, because 4 is strictly later than its locked round 2 and the value differs. If the proof is for round 2, or for B, it stays locked and prevotes B. If instead it obtains a commit certificate for a different block at H, it halts — it does not treat the certificate as an unlock.

A prover that never finishes, and then a recovery. A batch is certified at time t. At t + 30 minutes there is still no proof. Nothing special happens yet: a proof consuming the whole envelope is normal, not misconduct; other provers may produce a proof for the same data commitment and land it, and the first valid landing wins. If in addition no batch extending the current checkpoint is accepted for T_STALL, the settlement-stall trigger is met. Anyone may then post a bond and start a recovery. During T_RECOVERY_DELAY any valid batch cancels it and the bond is slashed to the protocol treasury. If nothing lands, the recovery completes: the chain resumes from the last checkpoint accepted on Ethereum, and every block above it — including the certified batch and any transaction in it — is replaced. A rolled-back transaction must be resubmitted; nothing replays it. (user decision D-7: Mode B selected)

What this gives you

  • A fixed, minimal response for every class of missing message or data, without inventing rules at run time.
  • Safety that does not depend on seeing a certificate: the lock protects the decision, not the publication.
  • A principled restart: resume from the highest certified block whose data and certificate can be reconstructed, never from a competing branch.
  • A settled prefix that is never rewritten and a rule-legal path for everything above it, so a settlement stall is not a permanent outage.
  • A priced, permissionless recovery: no operator and no DAO, and the invoker’s bond goes to the protocol treasury if honest progress cancels the attempt. (user decision D-7: Mode B selected)

What it does not give you

  • Availability. If data for a block at or below the accepted checkpoint is gone, the halt can be permanent; retention is an assumption, not an enforced duty.
  • Permanent confirmations above the last accepted checkpoint. A certified block can be replaced by a recovery, a rolled-back transaction must be resubmitted, and off-chain losses are not compensated. (user decision D-7: Mode B selected)
  • A recovery that cannot itself be abused. It is a manipulation primitive with a price, and the argument that a sub-threshold coalition cannot force the trigger is conditional, not proven.
  • Punishment for silence. Only conflicting signed messages are objectively provable; a node that never answers is not slashable.
  • A degraded or read-only mode. A minority outage halts the chain rather than continuing with reduced participation.
  • An operator unstick button. A settlement stall can be cleared only by the permissionless, bonded, delayed recovery — not by an operator, DAO or emergency key.
  • Any measured detection rate, timeout value, recovery parameter or retention window. Those are not yet measured.

Check yourself

Validators have waited past every timeout and seen no certificate for height H. May they certify a different block at H?

No. A timeout changes local round state only. The lock still binds: without a proof-of-lock-change at H for a different value at a strictly later round, a validator prevotes its locked value. If a certificate for the locked block eventually appears, it is accepted then.

A node is restarted from a backup and cannot prove which messages it already signed. What does it do?

It must not sign for any (height, round, type) it cannot prove it has not already signed. Lost memory is treated as a signing fault, not as a fresh start, because double-signing is the one objectively punishable offence and the one that can break safety.

Why is publishing data without a proof not an acceptable way to unblock settlement?

It would create an accepted record before anything justifies it, break the rule that data and proof live in one transaction, and turn a safe halt into an unverified history. The design has no data-first path by construction, and no recovery may introduce one.

Is a PoS confirmation above the last accepted checkpoint final?

No. It is valid but provisional: after a settlement stall, anyone may start a bonded, delayed recovery that replaces history above the last checkpoint accepted on Ethereum. Accepted checkpoints and accepted batches are never touched, and a rolled-back transaction is not replayed — it must be resubmitted.

What does a recovery cost an invoker whose attempt is cancelled?

Its bond. If any valid batch extending the current checkpoint is accepted during the delay, the recovery is cancelled and the bond goes to the protocol treasury, so starting a recovery is never free. Repeated recovery is further limited by an escalating bond and a cooldown.

Assumptions

  • Fewer than one third of each epoch’s voting power is malicious, and the rest follows the lock and vote-uniqueness rules.
  • Enough validators are online to form quorums in normal operation; the protocol has no degraded mode when they are not.
  • Somebody keeps the data for every certified block until its proof lands.
  • At least one prover finishes each batch before the retention assumption expires.
  • The recovery trigger, bond, delay and cancellation values are unmeasured placeholders, and the argument that they cannot be abused rests on stated conditions rather than on measurement.
  • Outside L1-level censorship and the absence of any prover, a sub-threshold coalition cannot force the settlement-stall trigger.
  • Ethereum itself keeps producing, including and finalizing blocks.
  • The timeout values, the retention window and the cap are placeholders awaiting measurement.
