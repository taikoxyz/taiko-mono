12 — The bridge and the addresses that must not move

Problem this lesson solves. It explains why the SignalService, Bridge and three vaults keep their exact addresses while their implementations are upgraded in place, how a cross-chain message is authenticated against an L1 checkpoint, and what a user should check before trusting one.

In plain language

The preserved surfaces. D3 fixes it: preserve the existing L1 and L2 SignalService, Bridge, ERC20Vault, ERC721Vault and ERC1155Vault addresses by in-place upgrade, with no replacement deployments (D3, MIG-06). The settlement Inbox and the L2 Anchor are upgraded in place too, because the bridge depends on them.

Why the addresses stay. A replacement deployment would change every address users and peer contracts have integrated, and would break the checkpoint-writer link: the L1 SignalService's _authorizedSyncer is the Inbox and the L2 SignalService's is the Anchor, so re-deploying either writer leaves the preserved SignalService unable to be checkpointed. It would also duplicate bridge state and abandon live messages and cached proofs (MIG-06, MIG-03). D3 preserves the addresses, not the powers: the migration removes the owner-only init2()/init3(), the prover whitelist, the proposer checker, pause flags, the quota manager, the dynamic resolver and the vault's changeBridgedToken, so ordinary operation reads no owner, whitelist or pause flag (MIG-04, INV-04).

How a message is authenticated. An L2→L1 message starts as a signal in the L2 SignalService. To claim it on L1, a relayer supplies an MPT proof. The L1 SignalService resolves its stored checkpoint for the claimed L2 block number, requires the checkpoint's stateRoot to equal the proof's root hash, then verifies the MPT proof against that root for the remote SignalService account and the SIGNAL-derived slot. The Inbox must be the only contract that writes a checkpoint into the L1 SignalService, and _authorizedSyncer must remain immutable for the deployment's lifetime (MSG-01). A message is only as good as the checkpoint it is proven against, and the checkpoint is only as good as the Inbox that wrote it.

What the checkpoint now carries. It is written only after proof verification succeeds (L1-03) and advances monotonically (L1-06). It carries the L2 height, block hash, state root, epoch, validator-set root, data commitment and the accepting L1 block number — so a consumer can tell which consensus and which published data produced the root, and the key stays the L2 block number so existing lookups are unchanged (L1-07).

Replay protection survives the upgrade. The signal slot is keccak256(abi.encodePacked("SIGNAL", chainId, app, signal)) and the message hash is keccak256(abi.encode("TAIKO_MESSAGE", message)) with the chain ids inside the message struct, so a signal or message for one chain cannot verify on another. On the same chain, the receiving Bridge's per-message status (NEW / RETRIABLE / DONE / FAILED / RECALLED) prevents reprocessing, and the failure signal is msgHash XOR 3 (MSG-02). The migration must not change either encoding, must not reset nextMessageId or the status map, and must not bump the SignalService VERSION, because one bump invalidates the received-signal cache and hides every checkpoint at once (MIG-03).

Withdrawals. No value may leave the bridge surface on the strength of anything weaker than accepted on L1: a checkpoint whose stateRoot covers the signal, plus WITHDRAWAL_DELAY from that checkpoint's l1BlockNumber, plus Ethereum-finalized where the claim depends on a reorganisable L1 fact; an L1→L2 release requires the Anchor to have observed the deposit at the same finality depth. A settlement halt delays withdrawals indefinitely while forfeiting nothing: under Mode A the funds are unavailable until settlement resumes, not lost (MSG-03).

Storage layout, simply. Think of each proxy's storage as numbered boxes. Slots 0–250 are the frozen inherited prefix, so the checkpoint map, signal cache, message-status map and vault maps keep their numbers. New state may be declared only after the last used slot of the contract's own region, and each 32 bytes consumes exactly one trailing gap slot. Deprecated slots are frozen, not free: a zeroed slot must not be reused. Every upgraded contract's layout must be regenerated and diffed before and after (pnpm layout); a reordered, retyped or reused slot can silently corrupt the checkpoint or status map, which is unrecoverable without rewriting user-visible history (MIG-02).

Precise definitions

  • D3 and MIG-06. The preserved surfaces keep their addresses by in-place upgrade; no replacement deployments; the Inbox and Anchor are upgraded in place too (D3, MIG-06).
  • Storage-layout constraint (MIG-02). Frozen prefix 0–250; new state only after the contract's last used slot; one gap slot per 32 bytes; deprecated slots frozen; layout diffed before and after (MIG-02).
  • In-flight objects (MIG-03). Unproven Shasta proposals are void at the drain deadline; every legacy forced-inclusion queue entry still present at the freeze is consumed or refunded in full, never silently voided, and queued entries are never re-interpreted under the new design (MIG-03(4), FI-REMOVED-01); legacy bonds are not stake; messages, signal cache and withdrawals continue monotone (MIG-03).
  • Privilege removal (MIG-04). Every owner, whitelist, pause, quota and resolver lever is removed from the runtime ABI; the only remaining authority is DAO upgrade authority, never a runtime dependency (MIG-04).
  • Message authentication (MSG-01). The Inbox is the immutable _authorizedSyncer and sole checkpoint writer; verification resolves the checkpoint and checks the state root before the MPT proof (MSG-01).
  • Replay and domains (MSG-02). Existing slot and message encodings are frozen because they determine every stored slot and cached proof; chain ids prevent cross-chain replay and per-message status prevents same-chain double processing (MSG-02).
  • Withdrawal eligibility (MSG-03). Nothing weaker than accepted on L1, plus the delay from the checkpoint's l1BlockNumber, plus Ethereum-finalized where the claim depends on a reorganisable L1 fact (MSG-03).

What a user should check before trusting a cross-chain message

  1. Which status is claimed? A message may be proven only against a batch at accepted on L1 or later — never against a PoS confirmation alone (MSG-03, STATUS-11).
  2. Does a non-zero checkpoint exist for the claimed L2 block number, with the fields of L1-07, and is the sequence monotone (L1-06)?
  3. Where the claim depends on a reorganisable L1 fact, is the accepting L1 transaction Ethereum-final (STATUS-07, L1-12)?
  4. Do the chain ids and domains match the preserved encodings, and is the message status not DONE, FAILED or RECALLED (MSG-02)?
  5. Has WITHDRAWAL_DELAY elapsed from the checkpoint's l1BlockNumber? Its value is unmeasured: a derived parameter, not a promise of speed.
  6. Is the address the preserved proxy above, obtained from a source you verified yourself — not from a search result or a message (MIG-06)?
  7. Does the interface name the status in the controlled vocabulary, rather than substituting "final" or "confirmed" (STATUS-11, GEN-07)?

Attacks this prevents

  • A second checkpoint writer or a mutable syncer. Only the Inbox writes checkpoints and _authorizedSyncer stays immutable, so a non-Inbox source cannot install a root the bridge trusts (MSG-01).
  • Checkpoint rewrite through an owner lever. Monotone advancement and the removal of init2() mean no transaction can lower the checkpoint or replace a state root the bridge authenticated against (L1-06, MIG-04).
  • Cross-chain and same-chain replay. Chain ids inside the signal slot and message struct stop cross-chain verification; per-message status stops a second processing (MSG-02).
  • Releases against a reorganisable fact. Withdrawals require the checkpoint and, where needed, Ethereum finality — never inclusion depth (MSG-03, L1-12).

Attacks this does not prevent

  • A malicious governance upgrade. One upgrade can rewrite any rule, including the sole-writer link; that is F2, outside the protocol's protection (GOV-02).
  • Theft through a proof-soundness bug. A soundness break in an accepted zkVM backend or the guest forges batches — the bridge-theft class, mitigated only by audit and version discipline (LIM-01).
  • One third or more of Byzantine stake. A message proven against a checkpoint from a conflicted history is not repaired by verification (INV-01).
  • Loss of the data behind an old checkpoint. If every holder disappears, re-proof and audit are impossible and the halt can be permanent (LIM-01, DA-05).
  • Speed, and the reality of the addresses. A halt delays withdrawals indefinitely — funds are unavailable, not forfeited (MSG-03); and the addresses were recorded, not chain-verified (MIG-06).

Self-check

Why can a cross-chain message not be verified against a PoS confirmation?

Authentication resolves a checkpoint written into the L1 SignalService, and a checkpoint exists only after a successful land — accepted on L1. A PoS-finalized batch that has not landed has no L1 checkpoint to prove against (MSG-01, MSG-03).

The migration replaces a contract implementation. Does the address move, and may an old zeroed slot be reused?

The address does not move: every preserved surface is an in-place implementation upgrade, and no new address may enter any interface a user or peer resolves (MIG-06). Deprecated slots are frozen, not free; new state is declared only after the last used slot (MIG-02).

A relayer shows you a valid MPT proof for your withdrawal. Is that enough?

Not by itself: the proof must match a checkpoint written by the Inbox for the claimed L2 block, the message status must not already be DONE, FAILED or RECALLED, WITHDRAWAL_DELAY must have elapsed from that checkpoint's l1BlockNumber, and where the claim depends on a reorganisable L1 fact the accepting transaction must be Ethereum-final (MSG-01, MSG-02, MSG-03).
