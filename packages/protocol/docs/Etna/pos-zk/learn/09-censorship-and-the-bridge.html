Censorship and the bridge

This lesson gives you two things: the honest inclusion statement — published data carries a proof-enforced obligation that is not a latency guarantee, unpublished data has none, and what remains absent for data that never reaches L1 — and the bridge message path, including which contracts keep their addresses and what an integrator should check. The mechanism itself is lesson 11. This is a design description; nothing here is implemented, measured, audited or deployed.

The idea

Start with the uncomfortable half. If your transaction’s data reaches L1, the protocol makes it available to everyone and starts one narrow inclusion obligation: after the record’s due point, a batch that lands must advance a settlement frontier past it by resolving the record — dead first and unconditionally, when the record’s own deadline has passed at the anchored view, decided from its own stored block number; otherwise, while the record is live, the walk reads its transactions in the record’s own order and each one either runs or is set aside at its turn, and a live record all of whose transactions are set aside is void — and that duty is checked inside the proof (lesson 11). It is not a latency guarantee: a transaction can be set aside and a record can be discharged without being executed, a settlement stall can let it age out, and arrivals beyond the drain make waits unbounded. What remains absent is different: there is no general inclusion list, so no queue of arbitrary transactions, no escrow, no refund and no L1 entry point can force an unpublished transaction into L2 or start a withdrawal.

A settlement stall is not an inclusion remedy either. v1 has no recovery path of any kind: a settlement stall halts the chain, value at or below the last accepted checkpoint still exits on Ethereum alone through a withdrawal root that k distinct backend families attest, and clearing the stall needs a future protocol update. A stall is not an inclusion remedy either: the obligation binds a batch that lands, so none of it operates while settlement is stopped, and none of it makes unpublished data includable.

For data that never reaches L1, resistance is statistical. Proposer selection is weighted random: a coalition with less than one third of the voting power is selected for fewer than one third of slots in expectation, so a transaction that reaches honest validators is included by the first honest proposer with room for it (CONS-06). But the selection is a public deterministic function, so the slot in which a target transaction would be included can be computed in advance and bought or coerced, and no rule prices, detects or penalises that. Worse, an adversary that can cut a user off from every honest proposer — or that can censor L1 inclusion itself — can keep the data off L1 and so exclude that user indefinitely; and because a withdrawal is begun by an L2 transaction, the same adversary can prevent the user from starting a withdrawal at all. The protocol offers no remedy against that. Publishing the data yourself changes this in one direction only: it starts the obligation of lesson 11, which binds a producer that lands batches but cannot reach data that never reaches L1, and it still creates no latency guarantee. That is the whole statement; anything softer would be inaccurate.

The second half is the bridge. A cross-chain message is authenticated against an L1 checkpoint that the settlement Inbox writes when a batch lands with its data and its proof. The SignalService, the Bridge and the three vaults keep the addresses they have today, on both chains, and are upgraded in place rather than replaced, because live message state, cached proofs and the immutable checkpoint-writer links are all keyed to those exact addresses.

Slots and checkpoints

How it works

Censorship, in five sentences

  1. Publish your transaction’s data to L1 and one rule starts: after the record’s inclusion delay, every batch that lands must advance a settlement frontier past it by resolving it — dead first and unconditionally, when the record’s own deadline has passed at the anchored view, decided from its own stored block number; otherwise, while the record is live, its transactions are read in the record’s own order and each one either runs or is set aside at its turn, and a live record all of whose transactions are set aside is void — and the proof checks it. The record is the forced-data record; there is no flag, no escrow and no fee.
  2. There is no general inclusion list either: no queue, no escrow, no fee, and no way to force an unpublished transaction into L2.
  3. The per-block duty is order and non-omission only: a block never takes a later record’s forced transaction ahead of an earlier one, and must carry a forceable forced transaction when its own remaining gas covers it. The duty is scoped to the transaction’s turn: the no-room set-aside turns on the remaining gas, at that turn, of the block in which the turn lies, and a later block’s room neither rescues nor condemns a transaction whose turn has passed. There is no per-block count and no per-block gas quota, and no new slashable offence: the rejected proof is the whole enforcement (CONS-01(v), CONS-06).
  4. Proposer selection is weighted by committed stake and is a pure public function, so a coalition holding less than one third of the voting power proposes fewer than one third of slots in expectation — an expectation over windows, not a bound on any particular window. Because the schedule is public and deterministic, the slot in which a target transaction would be included is computable in advance, and buying or coercing that single slot is possible and cheap; no rule prices, detects or penalises it (for published data, the obligation of lesson 11 applies on top of this).
  5. A network-level adversary able to isolate a user from every honest proposer — or to censor L1 inclusion itself — can keep the data off L1 and so exclude that user’s transactions indefinitely, and can therefore also prevent the user from starting a withdrawal. The obligation begins at publication, so it offers no remedy here. This is a disclosed limitation, not an oversight.

What remains is real but conditional, in two different ways. For unpublished data: if a transaction reaches honest validators and an honest proposer has room for it, it is included, and “room” is a behavioural premise, not a protocol rule. For published data: the obligation of lesson 11 binds a producer that lands batches, and it bounds exclusion per unit of the censor’s L1 spending rather than by time. Any interface that claims a latency guarantee, that the obligation reaches unpublished data, or that an L1 escape hatch exists for arbitrary transactions, is wrong. A settlement stall changes none of that: v1 has no recovery path, no rule of the mechanism operates while no batch lands, and there is still no remedy against isolation.

How a message is authenticated

A cross-chain message is a signal inside L2 state, and L2 state is authenticated by the checkpoint of an accepted batch. The steps are fixed:

  1. The signal is placed in L2 state. The SignalService stores it at keccak256(abi.encodePacked("SIGNAL", chainId, app, signal)). The chain id is inside the slot, so a signal for one chain does not verify on another.
  2. A batch containing that state is accepted on L1. The Inbox’s land(data, proof) verifies the proof and only then writes, in the same transaction, the preserved SignalService checkpoint for the batch’s head block and the Inbox’s own richer record. The SignalService record keeps exactly its existing three fields {blockNumber, stateRoot, blockHash} under the same version key and the same slot derivation; the Inbox record carries epoch, setRoot, dataCommitment and the accepting L1 block number (MSG-01).
  3. A verifier resolves the checkpoint by L2 block number and requires checkpoint.stateRoot == proof.rootHash, then verifies a Merkle–Patricia proof for the remote SignalService account and the SIGNAL-derived slot against that root.
  4. The receiving Bridge processes the message once. The message hash is keccak256(abi.encode("TAIKO_MESSAGE", message)) with the source and destination chain ids inside the struct; per-message status is NEW / RETRIABLE / DONE / FAILED / RECALLED, and a message that is DONE, FAILED or RECALLED cannot be processed again; the failure signal is msgHash ^ 3 (MSG-02).
  5. A withdrawal waits for a withdrawal root, then for its delay. No value leaves on anything weaker than L1 acceptance, and the release is proven against a withdrawal root: k attestations of an already-accepted checkpoint’s statement from k distinct registered backend families, each verified on L1, one verification per attestation. Forming a root needs no new L2 block, no settlement progress, no quorum and no permission — any account may carry the attestations, and the latest accepted checkpoint is attestable while the chain is halted. The root’s state root must cover the signal, and an ordinary checkpoint that is not a withdrawal root anchors no release. WITHDRAWAL_DELAY — derived from the whole settlement pipeline and not yet measured — runs from the root checkpoint record’s own l1BlockNumber, never from the attestation transaction, and an unexpired, rule-triggered withdrawal veto can add up to T_VETO, delaying but never cancelling a proven withdrawal. Where the claim depends on an L1 fact that can still be reorganized, the transaction must additionally be at the configured Ethereum finality depth (MSG-03, MSG-04). An L1→L2 release requires the Anchor to have observed the deposit at that same finality depth, never at inclusion depth.

Nothing else authenticates a message: not a committee certificate, not a data-availability certificate, not an off-chain store, not a private witness, and not an operator (DA-04).

The k−1 further attestations are not derivable from L1 state. Producing each one is off-chain proving work that needs the recorded certificate, the checkpoint’s data and the pre-state witness; the proving share funds that work through the Inbox ledger, best-effort and never gating a submission. The exit therefore depends on a funded proving market and on the data still being retrievable: if fewer than k families operate, if nobody is paid to produce the proofs, or if the data has aged out of every archive, no root forms and the release condition is never met (MEM-15(2b)). That is a stated assumption, not a guarantee — the price of proving the exit instead of trusting a committee.

Which contracts keep their addresses, and why

The preserved surfaces are SignalService, Bridge, ERC20Vault, ERC721Vault and ERC1155Vault, together with the settlement Inbox and the L2 Anchor, which are also upgraded in place. No replacement deployment is made for any of them, and no new address is introduced into any interface a user or peer contract resolves (MIG-06).

The addresses cannot move without breaking things that are keyed to them. The Bridge’s nextMessageId and per-message status, the vaults’ deposit maps, and every cached received-signal entry and cached proof are stored at these addresses. Both checkpoint-writer links are wired to them and remain wired: on L1 the SignalService’s authorized writer is the Inbox, and on L2 it is the Anchor. The Anchor’s block-hash map must keep answering getBlockHash for historical heights. Replacing a proxy would strand live message state, break the writer link so that the preserved SignalService could never be checkpointed again, and duplicate bridge state across two contracts.

Before trusting a cross-chain message

An integrator should not treat “the relayer said so” as evidence. The checks that actually matter are on-chain:

  1. Resolve the checkpoint for the claimed L2 block number in the L1 SignalService, and confirm it was written by a successful land(data, proof) for that height.
  2. Confirm checkpoint.stateRoot == proof.rootHash, and that the Merkle–Patricia proof is for the remote SignalService account and the correct SIGNAL slot.
  3. Read the Inbox’s own record alongside the SignalService record — same blockHash and stateRoot — if the claim depends on which consensus and which data produced that root; the three-field SignalService record alone does not carry epoch, setRoot or dataCommitment.
  4. Check the chain ids inside the message and the signal slot, and the message status: a message that is DONE, FAILED or RECALLED is finished.
  5. Confirm a withdrawal root exists for the height — attestations from k distinct backend families, one verification each — and not merely a checkpoint: an ordinary checkpoint anchors no release. Check that WITHDRAWAL_DELAY has run from the root checkpoint record’s l1BlockNumber, that no veto is unexpired, and wait for Ethereum finality if the claim depends on an L1 fact that can still be reorganized.
  6. Check the basis of the claim: accepted data and proof, and a funded proving market that produced the k−1 further attestations from data that is still retrievable — not a committee certificate, data-availability certificate, off-chain store or operator promise.

A withdrawal, end to end. A user calls the L2 Bridge; the message gets status NEW and its hash is keccak256(abi.encode("TAIKO_MESSAGE", message)). The signal sits at its SIGNAL-derived slot in L2 state. When a batch containing that state lands, the accepting transaction writes the checkpoint. A withdrawal root then forms over that accepted checkpoint’s statement: k attestations from k distinct backend families, each verified on L1, carried permissionlessly by anyone and produced by provers paid, best-effort, from the proving share. The L1 verifier resolves the root’s checkpoint state root, matches it to the message’s Merkle–Patricia proof for the SignalService account and slot. From there the value can leave once WITHDRAWAL_DELAY has run from the root record’s l1BlockNumber, no veto is unexpired, and any required Ethereum finality is reached. The bridge does not know or care which proposer included the L2 block; it cares that the state root the root attests covers the signal.

What this gives you

  • An honest inclusion statement you can build a risk model on: a proof-enforced obligation over published data that is not a latency guarantee, no general inclusion list, and for unpublished data only statistical resistance bounded by the selection share, with a named isolation failure (lesson 11).
  • A message authentication path anchored on L1-accepted data and proof, whose value release needs a withdrawal root that k distinct backend families attest, with replay protection, domain separation and per-message status.
  • Stable integration points: the same SignalService, Bridge and vault addresses on both chains, and unchanged slot and message encodings.
  • A concrete checklist for deciding when a cross-chain message is trustworthy.

What it does not give you

  • A general inclusion list, or any L1 path to force an unpublished transaction into L2 or to start a withdrawal. Nothing changes this: the obligation begins at publication, and v1 has no recovery path, so there is no later event that includes a censored transaction.
  • A promise that a published record is included at, before or by any particular height: a transaction can be set aside at its turn, a record can be discharged as dead by its own deadline, decided from its own stored block number, or as void while it is live, instead of included, and the obligation bounds the censor’s L1 spending rather than the user’s wait. A transaction set aside may become runnable later through the sender’s own further transactions or through a credit from any account — a credit can only ever enable a transaction, never set one aside, and where a credit lands relative to a turn is the producer’s ordering decision — and re-publication is the remedy (lesson 11).
  • Any remedy against an adversary that can isolate a user from every honest proposer, or that can censor L1 inclusion itself: if the data never reaches L1, exclusion can be indefinite.
  • Protection against slot-buying: selection is predictable and no rule prices or penalises it.
  • Early exit for unsettled value: a withdrawal whose signal is above the last accepted checkpoint still needs a later accepted batch, and v1 has no other path to it; a signal at or below the checkpoint stays executable on Ethereum alone, but only once a withdrawal root of k distinct-family attestations forms over it, funded by a proving market that can produce the k−1 further proofs from data that is still retrievable (MEM-15).
  • Confidence in the recorded addresses beyond the record: they were not chain-verified in the design work.

Check yourself

A coalition holds 25% of the stake. Can it keep one specific transaction out forever?

By selection alone, no: it proposes fewer than 25% of slots in expectation, so the first honest proposer with room includes the transaction. If the data reaches L1, the coalition must also deal with the obligation of lesson 11: while the record is live it cannot settle past it, and it must run every transaction that can run at its turn — only a transaction that cannot run there may be set aside — so keeping the record out means letting it age out to dead without settling, showing it void while it is live, or halting its own frontier. Re-publication starts a fresh record, so the censor’s cost is roughly one L1 publication per deadline window. But if the coalition can also keep the data off L1 — by cutting the user off from every honest proposer at the network level, or by censoring L1 inclusion of the publication — then yes, indefinitely, including preventing a withdrawal from being started, and the protocol has no remedy. The obligation is per unit of L1 spending, not a latency bound, and v1 has no recovery path either way.

What is the minimum evidence that an L2→L1 message may be released?

A checkpoint written by a successful land(data, proof) whose state root covers the signal, a withdrawal root over it — k attestations from k distinct backend families, each verified on L1, for which a funded proving market must produce the k−1 further proofs from data that is still retrievable — a matching Merkle–Patricia proof for the remote SignalService account and the SIGNAL slot, correct chain ids, the message not already finished, the withdrawal delay elapsed since the root checkpoint record’s l1BlockNumber, no unexpired veto, and Ethereum finality if the claim depends on an L1 fact that can still be reorganized (MEM-15(2b)).

Why not deploy a fresh Bridge at a new address after an upgrade?

Because live state is keyed to the existing address: message ids and statuses, vault deposit maps, cached received signals and cached proofs, the signal slot derivation, resolver results, and both immutable checkpoint-writer links. A replacement would strand that state, break checkpointing for the preserved SignalService, and duplicate bridge state.

Assumptions

  • Fewer than one third of each epoch’s voting power is malicious, so proposer slots are shared in proportion to stake in expectation.
  • For unpublished data, an honest proposer with room includes a transaction that reached it; no rule requires this, it is a behavioural premise.
  • Users can reach honest proposers at the network level; under isolation this lesson’s resistance statement does not apply and there is no remedy.
  • Ethereum includes transactions and finalizes them; L2 consumes only Ethereum-final L1 facts.
  • Somebody publishes a censored transaction’s data while an observer holds it; publication starts the obligation of lesson 11, so the protocol has no remedy only if the data is never published.
  • At least one honest or rational producer lands batches, and arrivals of livable records stay within the drain the obligation can force; otherwise the deadline is an exit and waits grow without bound (lesson 11).
  • Somebody retains accepted batch data and blob sidecars for the retrieval window.
  • A funded proving market produces the k−1 further attestation proofs a withdrawal root needs, from data and a witness that are still retrievable; if it does not, no root forms and the exit waits indefinitely (MEM-15(2b)).
  • Preserved addresses are taken from the repository and deployment logs and were not chain-verified here.
