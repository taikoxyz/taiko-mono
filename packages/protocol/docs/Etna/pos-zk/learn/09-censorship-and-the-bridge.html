Censorship and the bridge

This lesson gives you two things: the honest inclusion statement — there is no forced-inclusion path and no per-transaction inclusion guarantee — and the bridge message path, including which contracts keep their addresses and what an integrator should check. It also states what recovery does not fix: recovery is not an inclusion remedy, and forced inclusion is planned as a later protocol update. This is a design description; nothing here is implemented, measured, audited or deployed.

The idea

Start with the uncomfortable half. This design has no forced-inclusion path and no per-transaction inclusion guarantee (LIVE-04, FI-REMOVED-01). Your transaction gets included when an honest proposer includes it. There is no queue, no escrow, no refund and no L1 entry point that can force a transaction into L2 or start a withdrawal.

Recovery is not an inclusion remedy. A bonded, delayed recovery can replace unsettled history above the last checkpoint accepted on Ethereum (REC-02), but it cannot put a transaction into a block or compel any proposer to include one, so it does not lift an exclusion. This version still has no forced-inclusion path, and forced inclusion is planned as a later protocol update (FI-REMOVED-01).

Proposer selection is weighted random: a coalition with less than one third of the voting power is selected for fewer than one third of slots in expectation, so a transaction that reaches honest validators is included by the first honest proposer with room for it (CONS-06). But the selection is a public deterministic function, so the slot in which a target transaction would be included can be computed in advance and bought or coerced, and no rule prices, detects or penalises that. Worse, an adversary that can cut a user off from every honest proposer can exclude that user indefinitely — and because a withdrawal is begun by an L2 transaction, the same adversary can prevent the user from starting a withdrawal at all. The protocol offers no remedy. That is the whole statement; anything softer would be inaccurate.

The second half is the bridge. A cross-chain message is authenticated against an L1 checkpoint that the settlement Inbox writes when a batch lands with its data and its proof. The SignalService, the Bridge and the three vaults keep the addresses they have today, on both chains, and are upgraded in place rather than replaced, because live message state, cached proofs and the immutable checkpoint-writer links are all keyed to those exact addresses.

Slots and checkpoints

How it works

Censorship, in four sentences

  1. There is no inclusion duty on any validator: omitting a transaction is not a proposal-validity failure and not an offence (CONS-06).
  2. Proposer selection is weighted by committed stake and is a pure public function, so a coalition holding less than one third of the voting power proposes fewer than one third of slots in expectation — an expectation over windows, not a bound on any particular window.
  3. Because the schedule is public and deterministic, the slot in which a target transaction would be included is computable in advance, and buying or coercing the proposer of that single slot is possible and cheap; no rule prices, detects or penalises it.
  4. A network-level adversary able to isolate a user from every honest proposer can exclude that user’s transactions indefinitely, and can therefore also prevent the user from starting a withdrawal. The protocol offers no remedy; this is a disclosed limitation, not an oversight.

What remains is real but conditional: if a transaction reaches honest validators and an honest proposer has room for it, it is included. “Room” is a behavioural premise, not a protocol rule — nothing defines it, reserves block space, or constrains the proposer’s ordering. Any interface that implies a per-transaction guarantee, or an L1 escape hatch, is wrong. Recovery does not change that: it can replace history that was never settled, but it cannot include a censored transaction, so it is not a remedy against isolation.

How a message is authenticated

A cross-chain message is a signal inside L2 state, and L2 state is authenticated by the checkpoint of an accepted batch. The steps are fixed:

  1. The signal is placed in L2 state. The SignalService stores it at keccak256(abi.encodePacked("SIGNAL", chainId, app, signal)). The chain id is inside the slot, so a signal for one chain does not verify on another.
  2. A batch containing that state is accepted on L1. The Inbox’s land(data, proof) verifies the proof and only then writes, in the same transaction, the preserved SignalService checkpoint for the batch’s head block and the Inbox’s own richer record. The SignalService record keeps exactly its existing three fields {blockNumber, stateRoot, blockHash} under the same version key and the same slot derivation; the Inbox record carries epoch, setRoot, dataCommitment and the accepting L1 block number (MSG-01).
  3. A verifier resolves the checkpoint by L2 block number and requires checkpoint.stateRoot == proof.rootHash, then verifies a Merkle–Patricia proof for the remote SignalService account and the SIGNAL-derived slot against that root.
  4. The receiving Bridge processes the message once. The message hash is keccak256(abi.encode("TAIKO_MESSAGE", message)) with the source and destination chain ids inside the struct; per-message status is NEW / RETRIABLE / DONE / FAILED / RECALLED, and a message that is DONE, FAILED or RECALLED cannot be processed again; the failure signal is msgHash ^ 3 (MSG-02).
  5. A withdrawal waits. No value leaves on anything weaker than L1 acceptance: the checkpoint must cover the signal, and WITHDRAWAL_DELAY — derived from the whole settlement pipeline and not yet measured — is measured from the checkpoint’s l1BlockNumber. Where the claim depends on an L1 fact that can still be reorganized, the transaction must additionally be at the configured Ethereum finality depth (MSG-03). An L1→L2 release requires the Anchor to have observed the deposit at that same finality depth, never at inclusion depth.

Nothing else authenticates a message: not a committee certificate, not a data-availability certificate, not an off-chain store, not a private witness, and not an operator (DA-04).

Which contracts keep their addresses, and why

The preserved surfaces are SignalService, Bridge, ERC20Vault, ERC721Vault and ERC1155Vault, together with the settlement Inbox and the L2 Anchor, which are also upgraded in place. No replacement deployment is made for any of them, and no new address is introduced into any interface a user or peer contract resolves (MIG-06).

The addresses cannot move without breaking things that are keyed to them. The Bridge’s nextMessageId and per-message status, the vaults’ deposit maps, and every cached received-signal entry and cached proof are stored at these addresses. Both checkpoint-writer links are wired to them and remain wired: on L1 the SignalService’s authorized writer is the Inbox, and on L2 it is the Anchor. The Anchor’s block-hash map must keep answering getBlockHash for historical heights. Replacing a proxy would strand live message state, break the writer link so that the preserved SignalService could never be checkpointed again, and duplicate bridge state across two contracts.

Before trusting a cross-chain message

An integrator should not treat “the relayer said so” as evidence. The checks that actually matter are on-chain:

  1. Resolve the checkpoint for the claimed L2 block number in the L1 SignalService, and confirm it was written by a successful land(data, proof) for that height.
  2. Confirm checkpoint.stateRoot == proof.rootHash, and that the Merkle–Patricia proof is for the remote SignalService account and the correct SIGNAL slot.
  3. Read the Inbox’s own record alongside the SignalService record — same blockHash and stateRoot — if the claim depends on which consensus and which data produced that root; the three-field SignalService record alone does not carry epoch, setRoot or dataCommitment.
  4. Check the chain ids inside the message and the signal slot, and the message status: a message that is DONE, FAILED or RECALLED is finished.
  5. Check that WITHDRAWAL_DELAY has elapsed since the checkpoint’s l1BlockNumber, and wait for Ethereum finality if the claim depends on an L1 fact that can still be reorganized.
  6. Check the basis of the claim: accepted data and proof, not a committee certificate, data-availability certificate, off-chain store or operator promise.

A withdrawal, end to end. A user calls the L2 Bridge; the message gets status NEW and its hash is keccak256(abi.encode("TAIKO_MESSAGE", message)). The signal sits at its SIGNAL-derived slot in L2 state. When a batch containing that state lands, the accepting transaction writes the checkpoint. The L1 verifier resolves it, matches stateRoot to the proof root, and verifies the Merkle–Patricia proof for the SignalService account and slot. From there the value can leave once WITHDRAWAL_DELAY has elapsed and any required Ethereum finality is reached. The bridge does not know or care which proposer included the L2 block; it cares that the state root in the checkpoint covers the signal.

What this gives you

  • An honest inclusion statement you can build a risk model on: no guarantee, statistical resistance bounded by the selection share, and a named isolation failure with no remedy.
  • A message authentication path anchored on L1-accepted data and proof, with replay protection, domain separation and per-message status.
  • Stable integration points: the same SignalService, Bridge and vault addresses on both chains, and unchanged slot and message encodings.
  • A concrete checklist for deciding when a cross-chain message is trustworthy.

What it does not give you

  • Any per-transaction inclusion guarantee, inclusion duty, or L1 path to force a transaction or start a withdrawal. Recovery does not change this: it replaces unsettled history, it does not include a censored transaction.
  • Any remedy against an adversary that can isolate a user from every honest proposer; exclusion can be indefinite.
  • Protection against slot-buying: selection is predictable and no rule prices or penalises it.
  • Early exit: a withdrawal still needs the checkpoint and the delay, and a settlement stall delays it until either a batch lands or a recovery completes — and a recovery can replace an unsettled withdrawal message.
  • A remedy against isolation: this version has no forced-inclusion path, and forced inclusion is planned as a later protocol update.
  • Confidence in the recorded addresses beyond the record: they were not chain-verified in the design work.

Check yourself

A coalition holds 25% of the stake. Can it keep one specific transaction out forever?

It proposes fewer than 25% of slots in expectation, so by selection alone, no: the first honest proposer with room includes the transaction. But if the coalition can also cut the user off from every honest proposer at the network level, then yes — indefinitely, including preventing a withdrawal from being started — and the protocol has no remedy. A recovery is not a remedy either: it can replace unsettled history, but it cannot include the censored transaction.

What is the minimum evidence that an L2→L1 message may be released?

A checkpoint written by a successful land(data, proof) whose state root covers the signal, a matching Merkle–Patricia proof for the remote SignalService account and the SIGNAL slot, correct chain ids, the message not already finished, the withdrawal delay elapsed since the checkpoint’s l1BlockNumber, and Ethereum finality if the claim depends on an L1 fact that can still be reorganized.

Why not deploy a fresh Bridge at a new address after an upgrade?

Because live state is keyed to the existing address: message ids and statuses, vault deposit maps, cached received signals and cached proofs, the signal slot derivation, resolver results, and both immutable checkpoint-writer links. A replacement would strand that state, break checkpointing for the preserved SignalService, and duplicate bridge state.

Assumptions

  • Fewer than one third of each epoch’s voting power is malicious, so proposer slots are shared in proportion to stake in expectation.
  • An honest proposer with room includes a transaction that reached it; no rule requires this, it is a behavioural premise.
  • Users can reach honest proposers at the network level; under isolation this lesson’s resistance statement does not apply and there is no remedy.
  • Ethereum includes transactions and finalizes them; L2 consumes only Ethereum-final L1 facts.
  • Somebody retains accepted batch data and blob sidecars for the retrieval window.
  • Preserved addresses are taken from the repository and deployment logs and were not chain-verified here.
