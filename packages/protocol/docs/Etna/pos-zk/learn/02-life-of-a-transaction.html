The life of a transaction

This lesson follows one transaction from submission to withdrawal and gives you the status ladder that tooling and RPCs should show — including which confirmations are only provisional — with the evidence, the guarantee and the remaining risk at each step.

This is a design, not a running system. Nothing described here is implemented, deployed, audited or measured. Numbers are tagged derived, sourced or unmeasured. The authoritative rules are in the specification.

The idea

A transaction passes through three machines that run at different speeds. The L2 validator set orders it and makes it certified in a few message round trips. Execution turns it into state that any node can check. Then a prover and Ethereum settle it: the batch containing the transaction is proven, its data and proof land in one L1 transaction, and the resulting checkpoint becomes the anchor that bridge messages authenticate against.

Each stage produces a different kind of evidence, so each stage deserves a different word. "Proposed" is a claim someone made. "Locally execution-valid" is something you checked. "Voted" is a signed commitment by one validator that it can never take back. "PoS-certified" is a certificate from more than two thirds of an epoch's voting power plus your own check that you hold the data — a confirmation that is provisional until the batch is accepted on L1. "Accepted on L1" is a public fact on Ethereum and the first status the protocol's own rules can no longer replace. A user interface that collapses these into one green tick is not simplifying; it is lying about which question was answered. (user decision D-7: Mode B selected)

The timeline

How it works

Step by step

  1. Submission. A user sends a transaction to an L2 node. The node checks it loosely, adds it to its mempool and gossips it to peers over the best-effort L2 P2P channel. Nothing about this step is final or ordered.
  2. Ordering. For each height H and round R, exactly one validator is the proposer: a hash of (chain id, epoch, H, R) selects a point in the epoch set's cumulative-weight intervals, so the proposer is computable by anyone holding the set root and cannot be disputed. The proposer builds a block, executes it and signs one proposal. Two distinct signed proposals at one round are equivocation and are slashable. The proposer has no other power: it cannot certify anything and cannot choose the validator set.
  3. Local execution and validity. Every other validator executes the block against the parent state it certified and checks the consensus rules: right proposer and signature, right parent, execution reproduces every header field, and the remaining block limits hold (CONS-01). A validator that is not satisfied votes NIL rather than signing for a block it could not check. This is a local guarantee only: it says this node will not build on an invalid block, not that anyone else agrees.
  4. Votes and certification. Validators prevote and then precommit. A precommit is a signed, irreversible commitment: the lock rule ties a validator to the value it precommitted and only a strictly later same-height proof-of-lock-change for a different value releases it. When more than two thirds of the epoch's voting power has precommitted the same block at the same height and round, the block is PoS-certified (CONS-05) — but only at a node that also holds the block body and can serve it, and the confirmation stays provisional until the batch is accepted on L1. A certificate without the data does not give you that status.
  5. Batching. A contiguous range of certified blocks becomes a batch. The batch never spans an epoch boundary, so one epoch and one validator-set root govern every height in it (PRF-05). The design's nominal batch length is a planning placeholder; the L1 admission bound is a separate parameter and is also unset.
  6. Proving. A prover — anyone, with no registration — assembles a witness and produces one proof for the batch: that the head block carries a valid commit certificate over the epoch's authenticated set with more than two thirds of its voting power, that executing the batch's blocks from the predecessor state yields the claimed successor state root, and that the executed bytes are the published bytes. A completed proof bound to this batch's data commitment is proof-ready; it is still only off-chain evidence until it lands.
  7. Landing. The prover calls one function, land(data, proof), in one L1 transaction. The contract derives the public inputs it can derive itself, checks the blob openings if the blob path is used, calls the verifier, and only then writes a checkpoint. If verification fails the transaction reverts with no partial effect: no checkpoint, no height advance, no payout. The range must be contiguous with the previous checkpoint, and the checkpoint chain never moves backwards (L1-06). First valid submission wins; re-submission of the same batch by anyone else is allowed while it has not landed.
  8. Ethereum finality. The accepting L1 transaction can still be reorganised out until Ethereum finalizes the block that contains it, or until the configured finality depth is reached. An L1 reorganisation simply undoes the transaction; the batch stays certified on L2 and is re-landable with the same data commitment.
  9. Withdrawal. A bridge message authenticates against a checkpoint the Inbox wrote. Value leaves only with that checkpoint plus the message-authentication path plus the withdrawal delay (MSG-03), and the claim must rest on L1 facts at the configured finality depth, never at inclusion depth.

The status ladder

These are the statuses to use in tooling, RPC responses and interfaces. Each row is a different guarantee; a tool that shows one must say which (STATUS-11). Above the last checkpoint accepted on Ethereum, a confirmation must be labelled provisional and must say that it can be replaced; L1 acceptance onward is irreversible under the protocol's own rules. Two things this example makes concrete. First, the transaction is certified on L2 long before it is settled on Ethereum: 1.5 s of consensus versus minutes of proving and L1 time, and until settlement it is only provisional. Second, the batch head is 416, not 412: certification of a block and settlement of a batch are different objects, and the checkpoint records the batch head.

Worked example: a rollback at height h

A transaction is included in block 830, and the batch containing it, with head 832, is PoS-certified. Nothing further is accepted on Ethereum: no batch extending the checkpoint at height 800 lands, and the stall passes the T_STALL threshold. Anyone may now start a recovery by posting a bond on L1. The recovery waits T_RECOVERY_DELAY; if a valid batch extending checkpoint 800 lands during that window the recovery is cancelled and the bond is slashed to the protocol treasury. If the delay passes with no batch, the chain resumes from checkpoint 800, and everything above it — including block 830 and the transaction in it — is replaced. (user decision D-7: Mode B selected)

Rule for anything that displays status

Name the status from the ladder, state which evidence backs it, and say what is still missing. A confirmation shown before L1 acceptance must be labelled provisional and must say that it can be replaced by recovery. A "withdrawable" badge must say which checkpoint it anchors to. If a tool cannot say which status it is showing, it must not show one. (user decision D-7: Mode B selected)

What this gives you

  • A single transaction-to-withdrawal path with a named, checkable status at every step.
  • A separation between certification (seconds, validators), proof (minutes, provers) and settlement (L1 inclusion and Ethereum finality), so expectations and timeouts can be set per stage.
  • A landing rule that is atomic and monotone: a batch's data and proof arrive together, and the checkpoint chain never moves backwards.
  • A clear boundary between provisional and irreversible: a PoS confirmation above the last accepted checkpoint can be replaced by recovery, while L1 acceptance onward is not touched by it. (user decision D-7: Mode B selected)
  • Re-landability after an L1 reorganisation: the L2 batch is not lost, only its L1 record.

What it does not give you

  • No 2 s settlement. L2 certification is fast; proving and L1 acceptance are not.
  • No status stronger than its evidence. A certificate does not prove that data is retrievable by others; local possession is not availability.
  • No measured timings. The 1.5 s happy path, the 30-minute envelope, L1 inclusion and the withdrawal delay are all unmeasured.
  • No permanence above the accepted checkpoint. A certified block can be replaced by recovery after a settlement stall, a rolled-back transaction must be resubmitted, and off-chain losses are not compensated. (user decision D-7: Mode B selected)
  • No rescue of missing data at or below the accepted checkpoint. If nobody can produce a batch's data, the chain can halt with a certified prefix it cannot settle; recovery may not replace accepted history.
  • No inclusion guarantee. A transaction that reaches honest validators is included by the first honest proposer with room for it; an adversary that isolates a user from every honest proposer can exclude that user indefinitely.

Check yourself

Your node has a valid commit certificate for height 412 but cannot retrieve the block body. Is height 412 certified for you?

No. Certification at a node requires the certificate and that node's own data-availability check: it must hold the body, be able to serve it, and see the parent chain link back without gaps. A certificate commits to a block hash, not to bytes. The correct action is to keep asking peers for the body; if it never arrives, the node halts rather than certifying on unknown data.

A block is PoS-certified with more than two thirds of the stake behind it. Can it still be replaced?

Yes, if it sits above the last checkpoint accepted on Ethereum and settlement stalls. The certificate is valid; the confirmation is provisional. Anyone may start a bonded, delayed recovery that replaces that history, and a rolled-back transaction must be resubmitted. Once the batch is accepted on L1, the protocol's own rules can no longer replace it.

A prover has produced a proof for batch 385–416 but has not yet sent the L1 transaction. Which status is the batch in, and what can still change it?

Proof-ready. The proof exists off-chain and the batch can be landed, but nothing is public on Ethereum yet. Any account can land the same batch first and collect the reward, and a better proof of the same data commitment could replace this one — but a proof for a different range or a different data commitment cannot be substituted.

Why must a batch's range start at the previous checkpoint plus one, and what happens after an L1 reorganisation?

The checkpoint chain is monotone and contiguous: firstBlockHeight must equal the last landed height plus one, so no height is skipped and no accepted height is rewritten. If an L1 reorganisation removes the accepting transaction, the checkpoint and everything built on it disappear from L1, but the L2 batch remains certified and can be re-landed with the same data commitment. The contract never repairs a reorganisation by writing a chosen checkpoint.

Assumptions

  • Fewer than one third of each epoch's voting power is malicious, so no two conflicting certificates exist.
  • More than two thirds of the epoch's validators are online and message delay is within the round-timeout bound, so rounds complete.
  • Validators and nodes hold the block data they voted for and can serve it; somebody keeps the data until the proof lands.
  • At least one adequately-resourced prover proves each committed batch inside the permitted window.
  • Ethereum includes valid transactions, and the accepting transaction is not reorganised out below the finality depth.
  • The bridge's message-authentication path and its delay are set from the same settlement pipeline the delay formula names.
  • The recovery trigger, bond, delay and cancellation values are unmeasured placeholders, and the argument that they cannot be abused rests on stated conditions rather than on measurement.
