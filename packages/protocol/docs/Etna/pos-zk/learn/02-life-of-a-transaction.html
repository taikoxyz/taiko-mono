The life of a transaction

This lesson follows one transaction from submission to withdrawal and gives you the status ladder that tooling and RPCs should show — including which confirmations are only provisional — with the evidence, the guarantee and the remaining risk at each step.

This is a design, not a running system. Nothing described here is implemented, deployed, audited or measured. Numbers are tagged derived, sourced or unmeasured. The authoritative rules are in the specification.

The idea

A transaction passes through three machines that run at different speeds. The L2 validator set orders it and makes it certified in a few message round trips. Execution turns it into state that any node can check. Then a prover and Ethereum settle it: the batch containing the transaction is proven, one L1 transaction accepts the proof and binds the data it carries or references, and the resulting checkpoint becomes the anchor that bridge messages authenticate against.

Each stage produces a different kind of evidence, so each stage deserves a different word. "Proposed" is a claim someone made. "Locally execution-valid" is something you checked. "Voted" is a signed commitment by one validator that it can never take back. "PoS-certified" is a certificate from more than two thirds of an epoch's voting power plus your own check that you hold the data — a confirmation that is provisional until the batch is accepted on L1. "Accepted on L1" is a public fact on Ethereum and the first status the protocol's own rules can no longer replace. A user interface that collapses these into one green tick is not simplifying; it is lying about which question was answered.

The timeline

How it works

Step by step

  1. Submission. A user sends a transaction to an L2 node. The node checks it loosely, adds it to its mempool and gossips it to peers over the best-effort L2 P2P channel. Nothing about this step is final or ordered.
  2. Ordering. For each height H and round R, exactly one validator is the proposer: a hash of (chain id, epoch, H, R) selects a point in the epoch set's cumulative-weight intervals, so the proposer is computable by anyone holding the set root and cannot be disputed. The proposer builds a block, executes it and signs one proposal. Two distinct signed proposals at one round are equivocation and are slashable. The proposer has no other power: it cannot certify anything and cannot choose the validator set.
  3. Local execution and validity. Every other validator executes the block against the parent state it certified and checks the consensus rules: right proposer and signature, right parent, execution reproduces every header field, and the remaining block limits hold (CONS-01). A validator that is not satisfied votes NIL rather than signing for a block it could not check. This is a local guarantee only: it says this node will not build on an invalid block, not that anyone else agrees.
  4. Votes and certification. Validators prevote and then precommit. A precommit is a signed, irreversible commitment: the lock rule ties a validator to the value it precommitted and only a strictly later same-height proof-of-lock-change for a different value releases it. When more than two thirds of the epoch's voting power has precommitted the same block at the same height and round, the block is PoS-certified (CONS-05) — but only at a node that also holds the block body and can serve it, and the confirmation stays provisional until the batch is accepted on L1. A certificate without the data does not give you that status.
  5. Batching. A contiguous range of certified blocks becomes a batch. The batch never spans an epoch boundary, so one epoch and one validator-set root govern every height in it (PRF-05). Its length is bounded by data, not by preference: at the target rate one 2-second block is one 131,072-byte blob, EIP-7691 allows six blobs per L1 block as the target and nine as the maximum, and a batch's data must fit in one L1 transaction — the accepting one when it is carried, the publication one when it is published earlier — so a batch is at most about six blocks at the target rate and nine is the hard ceiling. Within that bound the submitter chooses the length; nothing fixes it. And the bound is on bytes rather than on blocks: six is the count when every block is full of data, so lightly loaded blocks let one batch cover proportionally more of them (L1-01).
  6. Proving. A prover — anyone, with no registration — assembles a witness and produces one proof for the batch: that the head block carries a valid commit certificate over the epoch's authenticated set with more than two thirds of its voting power, that executing the batch's blocks from the predecessor state yields the claimed successor state root, and that the executed bytes are the published bytes. A completed proof bound to this batch's data commitment is proof-ready; it is still only off-chain evidence until it lands.
  7. Landing. The prover calls one function, land(data, proof), in one L1 transaction. The data argument carries the batch data or names a live publication record that already holds it; publishing the data earlier is permissionless and writes no batch state. The contract derives the public inputs it can derive itself, checks the blob openings against this transaction's own versioned hashes or the referenced record's recorded hashes, calls the verifier, and only then writes a checkpoint. If verification fails the transaction reverts with no partial effect: no checkpoint, no height advance, no payout. The range must start at lastLandedHeight + 1: contiguous with the previous checkpoint, and the checkpoint chain never moves backwards (L1-06). First valid submission wins; re-submission of the same batch by anyone else is allowed while it has not landed.
  8. Ethereum finality. The accepting L1 transaction can still be reorganised out until Ethereum finalizes the block that contains it, or until the configured finality depth is reached. An L1 reorganisation simply undoes the transaction; the batch stays certified on L2 and is re-landable with the same data commitment (L1-12).
  9. Withdrawal. A bridge message authenticates against a checkpoint the Inbox wrote, but value leaves only with a withdrawal root over an already-accepted checkpoint: k attestations from k distinct backend families, each verified on L1, which need no new L2 block, no settlement progress, no quorum and no permission. WITHDRAWAL_DELAY runs from the root checkpoint record’s l1BlockNumber, an unexpired veto can add up to T_VETO, and the k−1 further proofs must be produced by a funded proving market from data that is still retrievable (MEM-15(2b), MSG-03). The claim must rest on L1 facts at the configured finality depth, never at inclusion depth.

Above the last checkpoint accepted on Ethereum, a confirmation must be labelled provisional; no rule of v1 replaces it, and L1 acceptance onward is irreversible under the protocol's own rules.

Two things this example makes concrete. First, the transaction is certified on L2 long before it is settled on Ethereum: 1.5 s of consensus versus minutes of proving and L1 time, and until settlement it is only provisional. Second, the batch head is 390, not 412: certification of a block and settlement of a batch are different objects, and the checkpoint records the batch head.

Worked example: a settlement stall at height 830

A transaction is included in block 830, and the batch containing it, with head 832, is PoS-certified. Nothing further is accepted on Ethereum: no batch extending the checkpoint at height 800 lands, and the stall persists. In v1 there is no recovery path. No bond can be posted, no recovery can be started, and no governance action resumes the chain: the certificate for the batch stays valid and the confirmation stays provisional, while the chain simply halts. Value at or below checkpoint 800 can still leave on L1 through the exit path, with no new L2 block, no quorum and no validator. Clearing the stall is left to a future protocol update whose procedure is not yet specified, and block 830 remains exactly where it is until then.

Two boundaries hold throughout. Heights at or below 800 are accepted on Ethereum and are never rewritten. Heights above 800 are provisional: v1 does not discard them, does not retire them and does not replay them, so the transaction keeps its place; whether a future update replaces that range is not specified here. The unsettled depth is still bounded by D_MAX, because validators stop producing past the unsettled-depth cap — a bound on depth, not on the length of a halt.

Rule for anything that displays status

Name the status from the ladder, state which evidence backs it, and say what is still missing. A confirmation shown before L1 acceptance must be labelled provisional and must say that a settlement stall halts the chain and that no rule of v1 replaces it. A "withdrawable" badge must say which checkpoint its withdrawal root anchors to, and whether the root exists, the delay has run and any veto has expired. If a tool cannot say which status it is showing, it must not show one.

What this gives you

  • A single transaction-to-withdrawal path with a named, checkable status at every step.
  • A separation between certification (seconds, validators), proof (minutes, provers) and settlement (L1 inclusion and Ethereum finality), so expectations and timeouts can be set per stage.
  • A landing rule that is proof-gated and monotone: one transaction binds the proof and the data it carries or references, and the checkpoint chain never moves backwards.
  • A clear boundary between provisional and irreversible: a PoS confirmation above the last accepted checkpoint is provisional, while no rule of v1 rewrites it and L1 acceptance onward is not touched.
  • Re-landability after an L1 reorganisation: the L2 batch is not lost, only its L1 record, and it can be re-landed with the same data commitment.

What it does not give you

  • No 2 s settlement. L2 certification is fast; proving and L1 acceptance are not.
  • No status stronger than its evidence. A certificate does not prove that data is retrievable by others; local possession is not availability.
  • No measured timings. The 1.5 s happy path, the 30-minute envelope, L1 inclusion and the withdrawal delay are all unmeasured.
  • No settlement above the accepted checkpoint. A certified block is provisional; if the settlement stall persists, v1 has no recovery path and the chain halts — a transaction above the checkpoint cannot be withdrawn while the halt lasts, and off-chain losses are not compensated.
  • No unconditional exit. Even a message at or below the last accepted checkpoint needs a withdrawal root: k distinct backend families must attest, the k−1 further proofs must be funded and produced from data that is still retrievable, and an unexpired veto can delay the release (MEM-15(2b), MSG-03).
  • No replacement path. No rule of v1 rewrites history above the last accepted checkpoint: nothing is discarded, nothing is retired and nothing is replayed, so no one can pick winners inside the provisional range — there is no replacement to invoke. If a future protocol update adds one, its scope must be wholesale, and unwound transactions would not be replayed automatically.
  • No rescue of missing data at or below the accepted checkpoint. If nobody can produce a batch's data, the chain can halt with a certified prefix it cannot settle; no rule of v1 replaces accepted history, so the halt persists until a future protocol update.
  • No latency guarantee, and no remedy for isolation. A published record carries an inclusion obligation enforced inside the proof: a landing batch must advance the settlement frontier past it by resolving it — the walk reads its transactions in the record’s own order, each one either runs or is set aside at its turn, a record all of whose transactions are set aside is void, and a record past its deadline is dead. That is not a promise about time, and an adversary that isolates a user from every honest proposer — or censors the publication itself — can keep the data off L1 and exclude the user indefinitely (lesson 11).

Check yourself

Your node has a valid commit certificate for height 412 but cannot retrieve the block body. Is height 412 certified for you?

No. Certification at a node requires the certificate and that node's own data-availability check: it must hold the body, be able to serve it, and see the parent chain link back without gaps. A certificate commits to a block hash, not to bytes. The correct action is to keep asking peers for the body; if it never arrives, the node halts rather than certifying on unknown data.

A block is PoS-certified with more than two thirds of the stake behind it. Can it still be replaced?

No rule of v1 replaces it. The certificate is valid and the confirmation above the last checkpoint accepted on Ethereum is provisional, but there is no recovery path: if settlement stalls, the chain halts. Value at or below the last accepted checkpoint can still leave on L1, and clearing the stall requires a future protocol update whose procedure is not specified. Once the batch is accepted on L1, the protocol's own rules can no longer replace it.

A prover has produced a proof for batch 385–390 but has not yet sent the L1 transaction. Which status is the batch in, and what can still change it?

Proof-ready. The proof exists off-chain and the batch can be landed, but no checkpoint exists yet. The data may already be on Ethereum, since anyone may publish it before the proof and publication writes no batch state. Any account can land the same batch first and collect the reward, and a better proof of the same data commitment could replace this one — but a proof for a different range or a different data commitment cannot be substituted.

Why must a batch's range start at the previous checkpoint plus one, and what happens after an L1 reorganisation?

The checkpoint chain is monotone and contiguous: firstBlockHeight must equal lastLandedHeight + 1, so no height is skipped and no accepted height is rewritten. If an L1 reorganisation removes the accepting transaction, the checkpoint and everything built on it disappear from L1, but the L2 batch remains certified and can be re-landed with the same data commitment. The contract never repairs a reorganisation by writing a chosen checkpoint.

Assumptions

  • Fewer than one third of each epoch's voting power is malicious, so no two conflicting certificates exist.
  • More than two thirds of the epoch's validators are online and message delay is within the round-timeout bound, so rounds complete.
  • Validators and nodes hold the block data they voted for and can serve it; somebody keeps the data until the proof lands, and anyone may publish it to L1 first.
  • At least one adequately-resourced prover proves each committed batch inside the permitted window.
  • Ethereum includes valid transactions, and the accepting transaction is not reorganised out below the finality depth.
  • The bridge's message-authentication path and its delay are set from the same settlement pipeline the delay formula names.
  • v1 has no recovery path: a settlement stall halts the chain, and clearing it depends on a future protocol update whose procedure is not specified.
