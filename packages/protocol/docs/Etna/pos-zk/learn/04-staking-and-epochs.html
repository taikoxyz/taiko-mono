Stake, validators and epochs

This lesson follows one bonded TAIKO stake from the L1 transaction that creates it, through activation and the L1 heartbeat that keeps it selectable, into the epoch that first counts it, and out again through the exit queue. It closes with where a brand-new node starts. Everything here is a design: nothing is deployed or measured, and every number is tagged derived, sourced or unmeasured.

The idea

A validator is not appointed. It is created by locking the existing TAIKO token on Ethereum in a staking contract, registering a signing key, and waiting for the protocol’s own schedule to place it in a validator set. Holding TAIKO in a wallet does nothing: only stake that is bonded, activated and inside the set for an epoch counts as voting power.

The chain is divided into epochs of fixed length. Each epoch has exactly one validator set, and that set is decided on Ethereum before the epoch starts, not during it. Every block header carries a commitment to the current set and to the next one, so a reader can check who was allowed to sign without trusting a peer.

Being in a set is a recurring condition, and it is renewed by an act on Ethereum. To be selected into the set version committed for a future epoch, a validator must post a periodic attestation on L1 — a heartbeat — at least once in every window of HEARTBEAT_WINDOW L1 blocks. The window that judges a version is fixed by the L1 block at which the version first became coverable — two L1-side epochs before the epoch it governs — not by the block that carries the commit, so when inside its window an attestation lands cannot change who is selected. For the first two versions after activation, the judging window is fixed one full window after activation, so everyone has the same full window in which to attest. One that stops attesting is simply not selected next time: it keeps its whole stake and can rejoin the future rosters by attesting again. A version already committed is never changed, and a silent cohort that keeps attesting keeps its weight, so this changes who is in the next set, not how much participation a committed set needs.

Voting power is the bonded stake: one base unit for one unit of weight, with no multipliers and no delegation. Bonding registers two keys — an Ed25519 key for consensus votes and an ECDSA key for heartbeats — and the L1 address that bonded the stake is the only address that can rotate either key, request an exit or receive the unbonded tokens.

Leaving is deliberately slow. An exit request keeps the validator in every set it was already committed to, still voting and still slashable, until the exit takes effect at a later epoch boundary; the tokens then wait out a further delay before withdrawal. The delay exists so that misbehaviour committed while the stake was bonded remains punishable afterwards.

A brand-new node does not replay the chain from genesis and call the result verified. It starts from the newest checkpoint Ethereum has already accepted — a height, a block hash, a state root, an epoch and a set version — and treats Ethereum as the only authority on which history is the real one.

How it works

1. Bonding: one asset, held on Ethereum

The staked asset is the existing L1 ERC-20 TAIKO at 0x10dea67478c5F8C5E2D90e5E9B26dBe60c54d800, which has 18 decimals sourced. A new L1 custody contract holds bonded TAIKO; it never lends or rehypothecates it, and no party other than the protocol’s objective rules can move a bonded balance. Neither ETH nor a bridged L2 representation of TAIKO counts as consensus stake; gas stays ETH. The bond call is bond(amount, ed25519PubKey, heartbeatKey): it registers the Ed25519 consensus key and the ECDSA heartbeat key of §3 (function names in this lesson are illustrative; the rules are what bind). The caller’s own L1 address is the economic owner, and the amount must be at least S_min, the entry floor. S_min is derived from operator economics — annual operating cost divided by the margin between gross reward rate and operating cost — and its value is unmeasured.

2. Activation: a queue with objective rules

Activation entries are ordered by the L1 coordinates of the bonding transaction: (l1BlockNumber, txIndex, logIndex). Ties cannot occur, and once an entry’s coordinates are fixed nothing — not fee, not stake size, not identity — can reorder it. At most ACTIVATION_RATE_LIMIT entries become active per epoch, always taken from the head of the queue; the limit delays entries but never cancels one or lets a later entry pass an earlier one. An entry becomes active when its keys are bound, its ACTIVATION_DELAY has elapsed, and it has been served from the queue. The delay must cover Ethereum finality of the bonding transaction plus the two-epoch lookahead below, so a reorganisation cannot erase a stake after it was counted and an operator has time to bring a node online. The delay, the rate limit and S_min are all unmeasured. An entry that never binds its keys never appears in any set root, and an active entry that never attests is absent from the versions judged against windows its record does not cover: neither is slashable for a consensus offence and neither earns anything, but both keep their stake, and an entry still in the queue keeps its position (MEM-03).

3. Keys: one consensus key per set version

An entry has at most one consensus key per set version: an Ed25519 public key in its canonical 32-byte compressed form. The key enters a set root only through an L1 transaction signed by the entry’s owner, which is itself the authentication. Rotation is forward-only: rotateKey(newPubKey) applies from the first set version whose snapshot point is at or after the rotation transaction, and every already-published version keeps the old key. A key that has ever appeared in a published set root is retired permanently, so the mapping from (key, epoch) to entry stays one-to-one. A vote is judged against the key committed for that epoch, never against the validator’s current key; a vote signed with a rotated-away key at an epoch that commits the new key is invalid and does not count toward quorum.

The entry also registers a second, heartbeat key at bonding: an ECDSA (secp256k1) key used only to attest that the entry is alive on L1. It is separate from the consensus key because Ethereum has no Ed25519 precompile and an ECDSA signature is cheap to check there. The owner may rotate it, forward-only like the consensus key, and a signature under a retired key is invalid; rotating it does not reset the entry’s heartbeat record, so a rotation is never a way to refresh freshness. The heartbeat key can never vote, move stake, request an exit or trigger a slash: its only power is the eligibility attestation described next.

4. Membership is renewed by an L1 heartbeat

A set version is built from the entries that are active and eligible when it is committed. Eligibility is an L1 act of the entry itself: to be selected into the version committed for an epoch, a validator must have posted a heartbeat in the window that version is judged against — the window containing the first L1 block of the epoch in which the version’s entry becomes coverable, or the window immediately before it. The window is a fixed number of L1 blocks, not a fixed amount of time; its length is unmeasured, and it is sized to cover at least one L1-side epoch plus the jitter of an L1 inclusion, so an operator that attests once per L1-side epoch has a signing occasion in every window. Because the window is fixed from that L1 block, the block that carries the commit, and the moment inside the window when an attestation lands, cannot change who is selected. A heartbeat is a signature by the entry’s heartbeat key and it costs one L1 transaction; anyone may carry it, and a relayer may batch many in one transaction, because validity depends on the signature and not on the carrier.

A heartbeat is a per-window credential, not a standing one. The signed message names exactly one window and binds a recent L1 block — its number and its hash — and the contract records the start L1 block of the named window, never the time or the block number of the carrying transaction. A signature cannot be replayed in a later window, a signature for a future window cannot be recorded before that window begins, and a signature cannot be produced long before the window it names, because the L1 block it binds must be no older than a bounded anchor age unmeasured. A key that stops signing therefore stays eligible only for versions judged against the window it last named or the one after it, with the bounded pre-signing term allowing one further window.

An entry that is not eligible is excluded from the committed roster — from the root, the total voting power and the entry count — and nothing else changes. It is not decayed, discounted, zeroed or removed: it keeps its whole bonded balance, its owner, its exit and cancel-exit rights, and its full exposure for every epoch it was committed to, and it is eligible again at the first version judged against a window it has attested for, or the one after it. No rule removes weight. If no active entry is eligible when the append is due, commitSet() reverts and the append is missed, so the boundary halt of §6 becomes reachable until a later append succeeds — an honest cost, written down as one and not a penalty.

What this changes is who is in the next set, not what a committed set requires. A cohort that stops attesting is excluded from the versions committed after its coverage ends, so from then on the remaining eligible weight is the whole of the version’s total and quorum is reachable by the entries that keep attesting. But no committed version is repaired: a silent cohort already inside an epoch’s roster still counts there, and if quorum cannot be met inside that epoch the chain still halts. And an entry — or a whole cohort — that keeps heartbeating but withholds its votes keeps its weight, stays in future versions and can still stall them. A heartbeat is a declaration of presence on L1, not proof of participation: the mechanism changes who is selectable, never what a committed version requires.

The honest costs are four. A periodic L1 transaction per validator per window, paid by the validator or by whoever relays it, and the relayer needs a recent L1 block hash at signing time, so signing fully offline for long periods is over. A second key to register, rotate and keep custody of. An operational lapse becomes an outage: the validator loses its slots in future versions until it re-attests and a later version passes, while losing no stake, because silence is still not an offence. And a window measured in L1 blocks rather than in seconds: the duty is one attestation per HEARTBEAT_WINDOW L1 blocks, so its spacing in real time moves with L1 block time and is unmeasured.

Two named falsifiers, and one open gap

F8. An adversary able to censor, delay past a window, or price out honest entries’ L1 heartbeat transactions excludes honest validators from future set versions at no slashable cost, and because exclusion changes future composition it can raise the adversary’s own share of those versions. The protocol does not attempt to detect or resist this.

F9. The pre-signing horizon is bounded, not closed: a signature made within the bounded anchor age before the window it names is accepted in that window, so an entry can be absent for up to that term around a window boundary without losing coverage, and the same term makes an append window in which no active entry is eligible reachable.

The window length itself. The window a version is judged against is derived when the version is committed, so a change to the window length that takes effect while an epoch is in flight can leave an entry outside that one version even though the grid in force when it signed covered it. Nothing in the design delays such a change to an epoch boundary or freezes a window per epoch: this is stated as an open gap, not repaired.

5. The set is an Ethereum object

A set version k is published as (chainId, k, R_k, TotalVP_k, n_k, entries): the Merkle root, the total voting power, the entry count and the full list of (pubkey, effStake) pairs. Leaves are domain-separated and sorted by keccak256(abi.encode(DOMAIN_SET_KEY, chainId, pubkey)), so the root is independent of insertion order. TotalVP_k is published in the same L1 transaction as the root because a sum cannot be recovered from a Merkle root, and the proof guest recomputes it from the leaves. The root is written by commitSet(), a function that takes no arguments and may be called by anyone: the caller chooses nothing, and the contract computes the contents from its own state (MEM-08). The entry list contains every active and eligible entry: the contract includes each such entry with its full effective stake, and an entry whose heartbeat does not cover the version’s evaluation window is simply absent from the root, the total and the count — never present at a reduced weight.

6. Epochs, and why the set is fixed two epochs ahead

Heights are partitioned into epochs of L = 900 blocks, which is 30 minutes at the 2-second cadence derived; suitability at the target set size is unmeasured. The epoch of a height is a pure function of that height and of constants recorded on L1 when the chain activates (CONS-13).

The staking contract has its own L1-side clock, expressed in L1 blocks and anchored at the activation transaction. During L1-side epoch e the contract appends the set entry for epoch e+2, and the committed entries and their weights are read from the same L1 state at that append. The roster is the active entries that are eligible at that instant: the heartbeat predicate is evaluated inside the same call, from L1 state, and the caller chooses nothing. That entry must be an Ethereum-final L1 fact before any block of e+2 is proposed or voted on, and the L2 may not enter epoch e before the L1-side clock has reached the start of that epoch. The two-epoch lead is what makes the set immutable in practice: the entry for the epoch being entered was fixed while the previous one was still producing, so no prover, caller or late arrival can influence who judges an epoch after its blocks exist (MEM-09).

The lead must satisfy 2 · E_EPOCH ≥ T_PROOF_MAX_PERMITTED + T_SETTLE_PIPELINE + L1_FINALITY + margin, where E_EPOCH is the epoch duration and the terms are the longest permitted proving time, the settlement pipeline, Ethereum finality and a safety margin. Every input to that inequality is unmeasured; at the proposed values the two-epoch window is about 60 minutes derived. The append is driven by the L1-side schedule alone, never by settlement progress: settlement lags production by the whole proving pipeline, so a gate keyed to it would stop production at every boundary. If the entry for the epoch being entered is missing or not yet Ethereum-final at the moment of entry, correct validators do not proceed: the chain halts at the last certified block of the closing epoch rather than borrowing a set. The same halt is reachable when no active entry is eligible in the window in which an append is due, because commitSet() reverts rather than appending an empty version; a later window and a later attestation restore the append.

Every block header commits to two set roots: validators_hash, the root of the epoch containing that block, and next_validators_hash, the root of the following epoch. The first block of an epoch and the last block of the previous one must agree on the same root, and the root itself is read from the staking contract’s per-epoch mapping rather than from any header, witness or prover.

7. Exits, and why the delay exists

requestExit() moves the entry to exit-requested. It stays in every set version it is already committed to, keeps voting, and remains fully slashable. The exit becomes effective at the first snapshot whose point is at or after the request block and which the per-epoch churn cap does not exclude; the cap may defer exits to later snapshots, served in request order, but never cancels or penalises one. From the effective version the entry’s effective stake is zero and it appears in no later set root. Withdrawal then requires three things together: the exit has been effective for at least D_WITHDRAW; the evidence window has closed for every epoch the entry was in; and no unsettled or collectible penalty remains (MEM-05).

D_WITHDRAW is bounded below by the whole accountability pipeline: T_PROOF_MAX_PERMITTED + T_detect + T_evidence_submit + T_L1_include(p) + T_L1_final + T_PROCESS + M. Each term is unmeasured, and the inclusion term must be a quantile, never a mean. The delay is long because it must cover the whole path from offence to an L1-applied penalty: the offence clock starts on L2, possibly long before the batch is provable, and data published to L1 before its proof settles nothing. Penalties are charged against the stake the entry held at the offence epoch, not at the epoch the evidence arrives, so an exit cannot launder an old offence.

8. Rotation cannot change who was allowed to vote

A certificate names its epoch, and that value must equal the epoch of its height under the L1-committed schedule. It is judged under that epoch’s committed set root and no other, and once valid it stays valid forever: no expiry, no “current set” check, and no re-verification under a later set. Set roots are stored per epoch and are never overwritten. A validator that joins in a later epoch cannot cause a block certified earlier to be re-judged or re-signed; rotation changes who may certify future heights only. Rotation is not a recovery path, and it stays deferred: the one rule that can replace history above the latest checkpoint accepted on Ethereum is the stall resolution — a DAO-queued entry with a stored deadline, executed once by any account, discarding the whole provisional range and resuming from the checkpoint — and everything above that checkpoint is provisional. Rotation would re-partition only heights no validator produced, which is a different and unused mechanism, and a settlement stall halts the chain until the resolution runs.

9. Weak subjectivity: where a new node starts

A fresh node bootstraps from the most recent checkpoint that the L1 Inbox accepted and that is Ethereum-final: an L2 height, block hash, state root, epoch and set version. It reads this from L1 state; there is no checkpoint provider role, no peer vote and no social input. The node must not start from a checkpoint older than WS_MAX, whose derived upper bound is T_PROOF_MAX_PERMITTED + M − M_ws; the value is unmeasured. The freshness bound exists because of long-range attacks: an attacker who held stake in a past epoch keeps those signatures, and a history signed by a past set is cryptographically indistinguishable from the real one. Only Ethereum’s accepted checkpoint says which history the protocol accepts. If the newest accepted checkpoint is older than the window, the node must not call the history it would sync verified, and new entry is blocked until a newer checkpoint exists (MEM-11). Replaying from genesis does not remove the problem: two internally valid histories can both exist.

What this gives you

  • Permissionless entry: any L1 account with enough TAIKO can bond and join, with no allowlist and no approval.
  • A set fixed before its epoch, committed on Ethereum and carried in every block header; the whole entry list is published, so concentration is at least observable.
  • Voting power exactly equal to bonded stake, with no multipliers a client would have to reproduce.
  • An exit path that is slow but predictable, and a penalty that follows the stake held at the offence epoch rather than the stake at the moment evidence arrives.
  • A defined starting point for a new node: the newest Ethereum-final checkpoint, with a freshness bound.
  • A set version decided on Ethereum two epochs ahead from the entries whose heartbeat covers the window the version is judged against — fixed by the L1 block at which its epoch became coverable: a missed heartbeat costs future slots and never stake, and re-attesting restores the entry at a later version.

What it does not give you

  • No delegation and no liquid-staking credit in this version: one economic owner per entry, and a pooled or delegated balance is not counted as consensus stake.
  • No cap on how much stake one owner may control, and no claim that splitting or merging identities is prevented.
  • No bound on concentration; the published entry list makes it visible, it does not limit it.
  • No protection for a lost owner key: if the address that bonded the stake is lost, the stake is stranded, because no rule and no operator can move a bonded balance.
  • No working entry in a market where the reward rate does not exceed operating cost: S_min would then have no finite value.
  • No fresh checkpoint during a long halt: new nodes and new validators wait for a newer Ethereum-accepted checkpoint, and an old anchor must never be presented as verified.
  • No rule that compels participation. The heartbeat changes who is selected into future set versions, but a cohort that keeps attesting and withholds its votes keeps its weight and can still halt production. Nor does it repair a version already committed: a chain stalled inside an epoch whose committed roster cannot form quorum has no replacement set in v1, and clears only if that cohort returns or a future update changes the rules.

Check yourself

I bonded during epoch 13. When can my key first sign a vote?

Not before epoch 15 in the earliest case. The first set entry that can contain you is the one appended for epoch 15 during the L1-side clock of epoch 13, and it must be Ethereum-final before epoch 15 begins. On top of that you must have bound a key, waited out ACTIVATION_DELAY, and been served from the FIFO queue within ACTIVATION_RATE_LIMIT. If any of those is late, your first epoch is later.

Why does an exit request not remove me from the set immediately?

Because stake that signed a certificate must stay punishable. An exiting validator remains in every set it is already committed to, keeps voting and remains fully slashable until the exit takes effect at a later snapshot. Withdrawal then waits out D_WITHDRAW, which covers proving, detection, evidence submission, L1 inclusion and finality, processing and a margin, and only after the evidence window has closed for every epoch the entry was in.

Why can a brand-new node not simply replay the chain from genesis?

An attacker that held a large share of the stake in a past epoch keeps the private keys of that epoch and can sign a competing history that verifies exactly as well as the real one. More history does not resolve that; only Ethereum’s accepted checkpoint does. A checkpoint older than WS_MAX is not safe either, because its signers’ stake may already have been released and they can no longer be punished.

I stopped attesting for a while. Do I lose my stake or my place?

Not your stake, and not the places you were already committed to. Eligibility is a filter on future set versions: a heartbeat must cover the window a version is judged against — fixed from the L1 block at which that version’s epoch became coverable — so a lapse makes you absent from the versions judged against later windows, with your whole bonded balance, your owner and your exit rights intact. Re-attesting restores you at the first version whose window you have attested for, or the one after it, and you must keep attesting to stay selectable. A committed version is never re-drawn, so a version that already contains a quiet cohort still counts that cohort’s weight.

Why is eligibility an L1 transaction rather than a message among validators?

Because the roster is an Ethereum object and the rule that builds it runs there. A heartbeat is affirmative, self-authenticated evidence that does not depend on any batch landing, so it still works while the chain is stalled; a message among validators would be neither visible to the staking contract nor usable to filter a version the contract commits. The price is a periodic L1 transaction, a second key, and a lost slot when the attestation lapses.

Can an adversary keep an honest validator out of the next set?

Yes, if it can censor or delay that validator’s L1 heartbeat past its window: exclusion then requires withholding one L1 transaction per entry per window, and the protocol neither detects nor resists it. That is falsifier F8, and it is a real power, because removing an honest validator from future versions raises the adversary’s share of those versions’ total. It is not a stake loss for the excluded validator, which can re-attest.

Assumptions. This lesson relies on: fewer than one third of the voting power of the relevant epoch’s set breaking the rules; enough validators online for a quorum to form; each validator getting an L1 heartbeat transaction included inside each window, which is what makes honest validators selectable and is the assumption F8 leans on; at least one holder keeping each block’s data until the batch is settled; Ethereum continuing to accept, include and finalize transactions, so the L1 clock and the set commitments advance; a new node being able to obtain an Ethereum-final checkpoint no older than WS_MAX; and the reward pool paying enough that operating a validator is rational at S_min. If a checkpoint cannot be obtained, the honest outcome is a refusal to call the history verified, and new entry stops until one exists.
