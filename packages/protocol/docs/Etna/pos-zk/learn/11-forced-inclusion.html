11 — Getting in when nobody will include you

Problem this lesson solves. It explains how a user gets a transaction into an L2 block when no proposer will include it, why a forced-inclusion request must be calldata rather than a blob, and what forced inclusion does not guarantee.

In plain language

The problem. In this design L2 PoS proposers determine transaction order (D4), so a proposer can leave a transaction out. A user's recourse is an L1 transaction, not a complaint: the Inbox accepts a forced-inclusion request and L2 must eventually include it, or the settled chain cannot advance past it.

The request. The user calls requestForcedInclusion(bytes _txData) on L1, pays a fee, and receives a requestId. The request records the requester, an eligibility timestamp (block.timestamp + FORCED_INCLUSION_DELAY_SECONDS), the payload hash and the payload itself, with ids assigned strictly FIFO and never reused (FI-01). The delay is expressed in seconds and gives proposers a window to include it voluntarily before the duty attaches.

Why calldata and not a blob. The payload must be carried in the request transaction as calldata and stored in the Inbox's own L1 state. A blob-backed request would re-create the expiry class: Ethereum guarantees blob sidecar retrievability for MIN_EPOCHS_FOR_BLOB_SIDECARS_REQUESTS = 4096 epochs — roughly 18 days at the present cadence — and after that window the request could be neither included nor refunded (DA-05). That is precisely what happened to the queue voided by the owner-only init3() in June 2026, whose skipped entries' blobs had expired; a surviving init3()-style selector is forbidden and queued requests are never re-interpreted across migration (FI-03, MIG-04).

The duty has two layers, and both are normative. On L2, a proposal is invalid unless its first block includes, as transactions and in FIFO request order, every request that is eligible and observed at the configured Ethereum finality depth; correct validators reject a proposal that omits one (CONS-01, FI-02a). On L1, land recomputes the due set itself and requires exact equality — not containment — with the covered set bound by the proof, plus a timestamp-drift bound so a batch cannot back-date firstBlockTimestamp to dodge a request that just became eligible (FI-02b). Because the batch range must start at lastLandedHeight + 1, a proposer cannot move the batch boundary to escape the duty (L1-06).

Forced inclusion can only add to the future. A covered request's payload may enter only an L2 block at a height strictly greater than lastLandedHeight: it can never change the content, ordering or state root of an already-landed block, and never a checkpoint record. Within the batch that covers it, its position relative to other covered requests is fixed to FIFO request order; its position relative to non-forced transactions is CONS-01's derivation rule. No code path may use a forced inclusion, or the fact that one is overdue, to re-execute, invalidate or replace a landed batch (FI-04).

The escape hatch under sustained censorship. A request must not be voidable: no owner, DAO, operator or recovery function may remove it, rewrite its eligibility timestamp, or mark it consumed without an accepted batch — the exact opposite of init3(). When a request has been eligible and uncovered longer than FORCED_INCLUSION_ESCAPE_THRESHOLD, three things happen: it stays in the queue and remains coverable by any future batch, forever; the requester may claim a refund of the fee it paid, without removing the request or affecting its coverage obligation; and land keeps rejecting batches that fail the equality check, so a chain that keeps producing without covering the request stops being able to settle. The hatch deliberately does not provide an L1-side force-exit of L2-held value: the funds are in L2 state, and no rule may invent an L1 path that mints or releases them (FI-03, HALT-01).

Griefing controls. The request fee escalates with queue depth and is capped by MAX_FEE; a request is cancellable only before it becomes eligible, and cancellation refunds the fee minus a fixed cost; a request consumes exactly one slot of the L2 block space it eventually occupies; a batch covers at most MAX_FORCED_INCLUSIONS_PER_BATCH; and land's due-set computation must be bounded by those limits, never by an unbounded loop over all requests ever made (FI-05).

Why a sub-threshold cartel cannot starve inclusion. Proposer selection is stake-weighted rotation: over any window of W consecutive proposer slots, validator i is proposer exactly w_i times, so a coalition holding f < 1/3 of the stake that counts toward quorum holds strictly fewer than one third of the slots (CONS-06). The residual power is to make coverage late, not to prevent it, and lateness is bounded by the rotation, not by a timeout judgement (STATUS-10). Two honest caveats, in the specification's own words: this holds only while A-CONS-1 holds — at one third or more of Byzantine stake the argument does not apply and the protocol claims nothing; and it assumes proposer selection is not predictable enough for the cartel to buy the specific slots in which a request becomes due, an assumption about the selection function that CONS-06 must state, not this argument. CONS-06 adds a third: the counting property is over proposer slots, not produced blocks, and a cartel that forces timeouts on honest slots can increase its share of produced blocks.

What it does not guarantee. The request transaction itself is an L1 transaction: if Ethereum censors it, or censors the land transaction, the remedy is unavailable — a disclosed consequence of A-L1-1, not a protocol fault. Forced inclusion cannot reorder or revoke the past, cannot force an exit of L2-held funds, and gives no wall-clock deadline: the protocol never converts a timeout into an assertion about what exists elsewhere. And the profitability of queue griefing is unmeasured even with escalation (FI-05, 06 — required scenarios).

Precise definitions

  • Forced-inclusion request. An L1-stored record — id, requester, eligibility timestamp, payload hash, payload — created by requestForcedInclusion, FIFO and never reused, with the payload in calldata in L1 state and never a blob (FI-01).
  • Inclusion duty. An L2 validity rule (proposal invalid if a due request is missing, duplicated or reordered) plus an L1 backstop (exact equality between the computed due set and the covered set, with a drift bound) (FI-02).
  • Escape hatch. After the escape threshold: the request stays queued and coverable forever, the requester may claim a fee refund without removing it, and settlement keeps rejecting batches that omit it — but there is no L1 force-exit of L2 value (FI-03).
  • No retroactive power. A covered request can only enter a block above lastLandedHeight; it can never reorder or revoke past history or a checkpoint (FI-04).
  • Griefing controls. Depth-escalating, capped fee; cancellation only before eligibility; one L2 slot per request; bounded coverage and bounded due-set computation (FI-05).
  • Sub-threshold cartel bound. A coalition with less than one third of the weight holds strictly fewer than one third of proposer slots in every W-slot window; an honest proposer must include the due set or its proposal is invalid (CONS-06, CONS-01).
  • The omission offence. Provable censorship of a due forced inclusion is a slashing offence with an objective evidence encoding — the block, the L1 request record, the omission proof and the leader identity (ECON-04).
  • R10. The requirement forced inclusion must satisfy: censorship resistance without an override that violates D2 (01 — requirements and threat model §7).

Attacks this prevents

  • Selective omission by a sub-threshold cartel. The due set must be included by an honest proposer or the proposal is invalid, and validators reject invalid proposals; the cartel can delay coverage, not prevent it (FI-02, CONS-01).
  • Colluding-quorum omission while still landing batches. The L1 backstop recomputes the due set and requires exact equality; an omitting batch reverts with no partial effect (FI-02, L1-03).
  • Queue voiding and expired requests. No selector may remove a request; the payload is calldata in L1 state, so the June-2026 blob-expiry class cannot recur for the queue (FI-03, DA-05).
  • Using inclusion to rewrite history. A request can only enter a future block; it can never reorder or revoke a landed batch or checkpoint (FI-04).
  • Queue flooding and last-minute withdrawal of evidence. Escalating capped fees, one slot per request, bounded coverage, and cancellation only before eligibility (FI-05).
  • Unprovable accusations. Only objective evidence — the request record, the omitted block, the omission proof and the leader identity — supports the omission offence; a late or missing preference never does (ECON-04, WH-02).

Attacks this does not prevent

  • One third or more of Byzantine stake. The rotation argument stops applying, the protocol claims nothing, and a cartel of that size can halt the chain (CONS-06, LIM-01).
  • L1 censorship of the request or of land. If the L1 transaction cannot land, the remedy is unavailable and settlement halts; that is a disclosed consequence of A-L1-1 (06 — required scenarios).
  • An L1 force-exit of L2-held funds. FI-03 refunds the request fee only; the funds are in L2 state and no L1 path may mint or release them (FI-03).
  • Any wall-clock inclusion deadline. The protocol never converts an elapsed timeout into an assertion about what exists elsewhere (STATUS-10); coverage is late-bounded only through the rotation argument.
  • Predictable-slot capture and griefing profitability. Selection is a public deterministic function and the assumption about slot predictability is owned by CONS-06/LIM-01; the profitability of queue griefing is unmeasured (FI-05).

Self-check

Why can a forced-inclusion request not be a blob pointer?

Because blobs expire from retrievability — 4096 epochs (roughly 18 days at the present cadence, sourced and derived) — after which the request could be neither included nor refunded. That is the class observed in June 2026 and voided by the owner-only init3(). The request payload is therefore calldata stored in L1 state (FI-01, DA-05).

A cartel holds 30% of stake and never includes a due request. Can it starve inclusion forever?

Not while A-CONS-1 holds. A coalition below one third holds fewer than one third of proposer slots in every window, and an honest proposer must include the due set or its proposal is invalid; honest validators precommit only valid proposals, so the request is covered when an honest proposer leads (CONS-06, FI-02). It can make coverage late. At one third or more the argument does not apply and the protocol claims nothing.

Does the escape hatch let a censored user take their L2 funds out on L1?

No. The hatch refunds the request fee, keeps the request queued and coverable forever, and leaves land rejecting batches that omit it — which is a safe halt, not an exit. The funds are in L2 state, and no rule may invent an L1 path that mints or releases them (FI-03).

Challenge this. The lesson relied on: (i) A-CONS-1 — fewer than one third of the stake that counts toward quorum is Byzantine, and the rotation property of CONS-06; (ii) honest validators enforcing proposal validity and honest proposers including the due set, which are duties, not measured behaviour; (iii) the caveat that proposer selection is public and predictable, whose mitigation is owned by CONS-06 and LIM-01, not by this lesson; (iv) the L1 liveness assumption A-L1-1, without which neither the request nor the landing transaction can be included; (v) every fee, delay and size parameter of this design being unmeasured, with only the baseline constants and EIP-4844/7691/4444 figures tagged sourced; (vi) the arithmetic being an expectation over rotation, never a wall-clock guarantee. Falsifier: find a sentence here that promises inclusion by a deadline, presents a design fee value as measured, or claims the hatch can move L2 value.
