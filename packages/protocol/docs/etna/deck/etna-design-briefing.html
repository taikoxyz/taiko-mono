What does not change

Execution

The same EVM on alethia-reth, with EIP-4396 base fees and zk gas recorded in difficulty, as in Unzen.

Proof rule

Two proofs per settlement, at least one ZK, through the same ZkRequiredVerifier contract as today.

Data availability

Block data goes to L1 in blobs, using Unzen's blob encoding.

Bridge model

L1 holds L2 checkpoints in the SignalService. L2 verifies L1 storage proofs against an L1 state root.

Still a paid queue on the Inbox, with a fee that grows with the backlog.

The DAO owns the upgradeable proxies. Block numbers continue: Etna's first block is S + 1.

Framing

The security model in one slide

Funds

L1 recognizes only landed checkpoints, each with two proofs. A fully malicious committee cannot take funds on L1.

Finality

A commit is final while Byzantine voting power stays below 1/3. Governance recovery can discard blocks above the latest checkpoint.

Liveness

Needs more than 2/3 of voting power online, L1 finalizing, and landings continuing.

Censorship resistance

A due forced inclusion must be included or legally skipped, or the block cannot be proven. There is no wall-clock deadline.

Upgrade trust

The Inbox, registry, L1 SignalService and Bridge are DAO-owned proxies. An upgrade can bypass any rule in the spec.

Proof assumptions

Verifier soundness is assumed. So is completeness: every valid block must be provable, or settlement stalls.

Target: Stage 0. Stage 1 is not a goal for now. Out of scope: PoS issuance rewards.

1 · Sequencing and blocks

Who orders transactions

Today
  • A proposer posts a proposal with blobs to the L1 Inbox by calling propose.
  • L1 inclusion fixes the order. Every node derives the same L2 blocks from L1 data.
  • Preconfirmations are layered on top, through whitelisted preconfers and a lookahead.
Etna
  • The spec calls it "a PoS-sequenced validity rollup, not a based rollup".
  • A committee of TAIKO stakers runs stock CometBFT v0.40.0. The engine is not forked.
  • CometBFT's mempool is off. Transactions travel over the EL's devp2p and the proposer's EL picks them.
  • Each CometBFT block carries one envelope. Its height is the EL block number. The target interval is about 4 s.
  • Ethereum provides blobs for data, proof verification, settlement and the bridge's anchor.

1 · Sequencing and blocks

The cast changes

Today: proposers and preconfers, provers, and drivers that derive from L1. In Etna:

Off chain
  • Validator. Stakes TAIKO and registers a key. Runs CometBFT, the ABCI application, alethia-reth, its own L1 node and an external signer.
  • Full node. The same stack without a registered key. Validates every block.
  • EL-only backend. An EL that imports only landed blocks, for RPC and indexing.
  • Lander. Permissionless. Builds batches, obtains two proofs and calls land.
  • Prover. Produces the two proofs for a batch.
On L1
  • EtnaInbox. Genesis parameters, land, checkpoints, the forced-inclusion queue and its fees, the rules schedule, and recover.
  • EtnaStakingRegistry. Stake, top-ups, exits, withdrawals, double-sign slashing and DAO forfeiture.
  • SignalService. Stores the checkpoints the Inbox writes, so the bridge can verify L2 to L1 messages.

1 · Sequencing and blocks

The consensus engine is stock CometBFT

  • CometBFT v0.40.0 runs in its own process and drives the application over an ABCI++ socket. Proposer selection, timeouts and locking are stock.
  • Keys are secp256k1eth. Sign-bytes are hashed with keccak256, and the validator address is an Ethereum address, so L1 can check any vote with ecrecover.
  • The chain id binds the deployment and the recovery generation.
  • Consensus starts at S + 1. Each block's Data.Txs holds exactly one item, the envelope.
  • app_hash is the hash of the executed EL block. The transaction result is a fixed value, and consensus parameters are never updated.
  • CometBFT evidence enters blocks as usual, but the application does not punish on it. Slashing happens only on L1.
  • Proposer-based timestamps are not enabled. Block time is BFT time.
  • The block interval comes from timeout_commit: about 4 s, sized for roughly 128 validators.

1 · Sequencing and blocks

The application drives the EL through the Engine API

Calls
  • engine_forkchoiceUpdatedV3, engine_getPayloadV5 and engine_newPayloadV4, plus the pinned EL's extensions for a given transaction list and a byte limit.
  • The proposer builds with the derived header values. Other nodes recompute the header and require newPayload to return VALID.
  • The EL's finalized block is the last checkpoint shown by the anchor.
zk gas and fees
  • zk gas is a separate block budget, recorded in difficulty.
  • While building, a transaction that exceeds the zk budget is discarded whole and pays nothing.
  • Validation never discards. If any listed transaction exceeds the budget, the whole block is invalid.
  • Fees use ordinary EVM gas. All base fees and tips go to the block's beneficiary.

1 · Sequencing and blocks

One envelope per block, private to the consensus network

envelope = 0x06 || rlp([block, anchor, committee, forced])

blockThe EL header and the ordered transactions. Always present.
anchorThe raw L1 header plus Inbox proofs. Present when the anchor moves, and in a generation's first block.
committeeThe committee record, registry proofs and entries. Present only at an epoch's switch block.
forcedThe queue entry's proof and the transaction. Present while the queue has an unconsumed entry.
  • The CometBFT header commits to the envelope through data_hash. It never goes to L1.
  • The anchor witness proves five Inbox slots: the generation, the last checkpoint (two slots), the queue head and tail, and the rules schedule.
  • Decoding is strict and identical for nodes and guests. Any violation makes the proposal invalid.

1 · Sequencing and blocks

Nine validity rules, applied in order

  1. The height is the parent's plus one, and parentHash links.
  2. The anchor witness is present when required, and verifies.
  3. The anchor does not regress and is not before the generation's L1 origin.
  4. The chain id recomputed from extraData's generation matches this chain.
  5. Back-pressure: the height is at most U past the checkpoint the anchor proves.
  6. A committee witness appears only at a switch block.
  7. The header matches field by field; the anchor is fresh.
  8. The forced-inclusion rules hold.
  9. The EL's newPayload returns VALID for the full list.
  • ProcessProposal and FinalizeBlock apply the same rules.
  • The execution block is at most 124,000 bytes uncompressed, so each block fits in one blob.
  • If more than 2/3 of malicious power decides an invalid block, honest nodes halt for safety, and only governance recovery fixes it.
  • These are the rules of the block's ruleset, which its anchor selects.

Today

2 · Anchoring and the bridge

Every block reads L1 through a finalized anchor

  • A block either carries an anchor witness or inherits its parent's anchor.
  • The proposer picks the later of the parent's anchor and its own L1 finalized block.
  • Validators check with their own L1 node that the anchor header is canonical and finalized.
  • Freshness is judged against the candidate block's timestamp: timestamp − anchor.timestamp ≤ maxAnchorAge. A locked block proposed again in a later round stays valid.
  • L1 headers are read by position: only parentHash, stateRoot, number and timestamp. Fields an L1 fork appends are accepted without an upgrade.
  • When the anchor moves, a node compares the checkpoint it proves with its own chain, and rejects a mismatch.
  • No usable anchor, no block. If L1 stops finalizing, L2 pauses until an anchor is fresh enough again.
SPEC.md sections 3.3 and 3.4

2 · Anchoring and the bridge

The bridge after Etna

L1 to L2
  • SignalServiceL2 asks the Anchor for the root. From the fork on, the Anchor reads EIP-4788 by L2 timestamp.
  • A proof sets blockId to an L2 timestamp and rootHash to that block's parentBeaconBlockRoot.
  • An entry stays readable for at least 8,191 s, about 2.3 hours. A newer L1 root proves everything an older one did.
  • No new checkpoints are saved on L2 after the fork.
L2 to L1
  • land writes the height, block hash and state root into the L1 SignalService.
  • Withdrawals use that checkpoint directly, with no extra root, delay or veto.
  • A message therefore waits for a landing. The operating target is one landing every 20 minutes.
  • land is not affected by pause. If both proof systems fail, losses are contained by pausing the SignalService and Bridge.
ANCHORLESS.md sections 4 and 5 · SPEC.md sections 1 and 6.2

2 · Anchoring and the bridge

The anchorless fork has a strict upgrade order

  1. Every execution engine makes the EIP-4788 and EIP-2935 calls identically when building and importing. This ships without a fork.
  2. Deploy EIP-2935, then EIP-4788, on L2. A new network puts both in genesis.
  3. Guests learn to read both layouts of the L2 SignalService.
  4. One DAO proposal trusts the new guest images and upgrades the L2 Anchor and SignalService in one batch.
  5. Relayers and the bridge UI switch to proofs keyed by L2 timestamp.
  6. The switch itself.
  • The anchorV4 gate is required. The golden touch key is public, so without the gate anyone could save a forged checkpoint in the first anchorless block.
  • SignalServiceL2 uses a new storage namespace. Old L2 checkpoints and cached signals become unreadable, and must never be revived by a rollback.
  • If EIP-4788 has no code at the fork, uncached L1 to L2 proofs fail closed.

3 · Staking and committees

The staking registry lives on L1

  • register(publicKey, amount, popSig) needs at least minStake. The key is a 33-byte compressed secp256k1 key.
  • The proof of possession binds the L1 chain id, the registry and the sender. A key can be registered once, ever.
  • The owner is the sender and cannot change. Keys cannot be rotated in place: exit, withdraw, register again.
  • The registry fixes the Inbox address at deployment.
  • There are 4,096 slots. Bond ids count up and are never reused.
  • A registration takes the slot with the smallest balance and must stake more than it. A bond already there is displaced: it loses the slot and exits, but keeps its funds until withdrawal.
  • Top-ups are owner-only and delayed. One may be pending at a time.
  • Every L1 block that changes a slot ends with a checkpoint of the entries root. Nodes verify snapshots against it.

3 · Staking and committees

One selection rule, driven only by L1 state

  1. Verify the complete entries and root of the latest registry checkpoint at the snapshot.
  2. Keep entries that are active, not exited, and hold at least max(s_min, vp_unit).
  3. Sort by stake, largest first, with a fixed key hash as tie-break. Take the first n_max.
  4. Voting power is stake divided by vp_unit, rounded down. The total must fit CometBFT's cap.

The same rule selects committee 0, every rotation and every recovery.

Rotation
  • An epoch is L blocks. Epoch t starts at height H(t) = 1 + t·L. The suggested L is 900.
  • The switch block is H(t) − 2. It carries the committee witness, and its FinalizeBlock returns the updates.
  • CometBFT applies updates two heights later, so the new committee signs from H(t).
  • The snapshot is the later of two L1 blocks: the anchor of D(t) = H(t) − 3 and the generation's origin block. When D(t) ≤ S it is the origin block alone.
  • There is no limit on power change per rotation and no automatic eviction for being offline.

3 · Staking and committees

Double signing is slashed on L1, by anyone

slashDoubleSign(bondId, voteA, voteB)
  • Valid evidence is two votes of the same type, height, round and generation for different block ids.
  • The registry recomputes the chain id from its own deployment values, rebuilds CometBFT's sign-bytes, and requires both signatures to recover the bond's key.
  • The caller cannot choose a chain id or an Inbox.
  • Committee membership need not be proven. Only the key holder can produce the signatures.
Consequences and limits
  • The whole principal is slashed. The reporter receives a bounty (suggested 10%) and the rest goes to a sink.
  • Evidence from past generations stays admissible until withdrawal.
  • Only same-round double signing is covered. Conflicting votes across rounds are not.
  • A slashed member keeps its voting power until a committee that excludes it takes effect.
SPEC.md sections 4.1 and 12

3 · Staking and committees

Offline is a governance matter, and nobody is paid to stake

DAO responsibility forfeiture
  • Going offline or withholding signatures is not slashed automatically.
  • The DAO may call forfeit on a bond. It deducts a fixed share of the remaining principal, once per key, and forces an exit.
  • The registry checks authority, identity and expiry. It does not check that the attribution is right.
  • There is no waiting or appeal period, and an unexecuted authorization cannot be revoked before it expires.
Money flows
  • There is no PoS issuance. A proposer earns the base fees and tips of its own blocks.
  • Forced-inclusion fees stay in the Inbox. Anyone can sweep them to the DAO treasury.
  • Landing earns nothing. Proving and landing costs are paid from DAO operating funds.
  • The minimum total stake comes from a capital target that is not pinned yet.

4 · Settlement

There are now two kinds of final

Committed CometBFT commit · about 4 s

Final while Byzantine voting power stays below 1/3. Consensus never rolls it back. The one exception is governance recovery, which discards blocks above the latest checkpoint.

Landed L1 checkpoint · two proofs

Nothing at or below a checkpoint can be rolled back, except by a DAO upgrade after a verifier failure.

  • Funds on L1 recognize only landed checkpoints. Even a fully malicious committee cannot take funds on L1.
  • The spec's advice: exchanges and bridges should rely on checkpoints.
  • Today there is one notion. Order is fixed by L1 inclusion and finalized by prove.

4 · Settlement

Settlement is one permissionless call: land

  • Anyone can call it. It pays no protocol reward; landers are funded by the DAO.
  • The proposer bond, liveness bond and proving window of today's Inbox are gone.
  • Two proofs, at least one of them ZK. This is the same ZkRequiredVerifier rule as today.
  • One to six blobs carry every execution block in the range.
  • Landings end only on a grid of every K blocks, with K between 1 and 6.
SPEC.md sections 6.1 to 6.3

4 · Settlement

What land checks, in order

  1. Range and grid. The origin p is at or below the checkpoint c, c is below h, and both ends are grid points.
  2. Origin. p has a retained landing record in the current generation.
  3. Leaves. One per grid point inside the range. If c is above p, the leaf at c equals the one from c's record.
  4. Queue head. It only advances, never past the tail, and by at most h − c.
  5. Reference and blobs. The reference block's hash is readable on chain; one to six blobs.
  6. Proofs. Compute the cut hash, build the statement, verify both proofs.
  7. Update. Checkpoint, active committee snapshot, queue head, landing record and SignalService, atomically.
  • All checks come before any state change. The leaf checks come before proof verification.
  • If c has already reached h, the call reverts as already settled.
  • The new landing record's parent is the actual c, never the proof origin p.
  • The reference hash comes from blockhash (256 blocks) or EIP-2935 (8,191 blocks).
  • On a switching network, the first landing also requires Unzen's own proof of the start block.
SPEC.md section 6.1, reference Solidity

4 · Settlement

Why landings end only at grid points

Why check c at all
  • A proof may start from an older p while c advances through other landings.
  • If more than 1/3 of the power double-signs, one height can have two valid blocks.
  • Without checking that the proof's chain at c is the block L1 recorded, L1 could settle one fork and then attach the other. The bridge could be double-spent.
  • Requiring p = c would avoid the check, but every competing landing would force a new proof.
Why a grid, and how wide
  • A proof is made without knowing c, so it must commit to every possible c. On a grid that list is short enough to carry in full.
  • The contract does one hash and one indexed comparison. The guest builds no Merkle tree.
  • A grid segment must always fit one transaction. A block fits one blob and a transaction carries six, so K is at most 6.
  • A 300-block batch at K = 6 carries 49 leaves, 1,568 bytes of calldata.
SPEC.md section 6.3

4 · Settlement

Consensus moves inside the proof

Today the guests prove derivation from L1 data plus execution. In Etna they must also prove that the committee decided each block.

  • Each commit carries more than 2/3 of the voting power of the right committee, under this generation's chain id.
  • That committee is derived from the L1 registry through storage proofs. The prover does not supply it.
  • CometBFT headers link from the origin to the terminal block, and each validator-set hash matches the schedule.
  • Each envelope matches its header, and its witnesses satisfy the block rules.
  • Execution runs from the origin's hash to the terminal hash and state root. An over-limit block is never shortened to a provable prefix.
  • The execution part equals the blob payload byte for byte, and the blobs match the transaction's blob hashes.
  • Forced inclusions are consumed exactly and in order.
  • Every L1 anchor lies on a header chain ending at the reference block.

4 · Settlement

Only execution blocks are published

Today all block data is in L1 blobs before a block is canonical.

Public, in blobs at landing
  • 0x06 || zlib(rlp([executionBlock, …])), where each block is its EL header and transactions.
  • One to six blobs per batch, with Unzen's blob encoding.
  • With a sound proof and a finalized checkpoint, blobs plus the starting state rebuild the landed EL chain.
Private, never on L1
  • CometBFT headers, envelopes, commits and signatures, witnesses, registry entries, and the raw bytes of a skipped forced transaction.
  • They are proof inputs. The guest ties each envelope to its header, then to the blob.
  • Unlanded blocks, proving, replay and double-sign evidence all depend on archives of this history.
  • Blobs alone cannot bootstrap CometBFT.

4 · Settlement

Back-pressure caps the unsettled chain at U blocks

about 900 in normal operation
about 2,700 of margin, roughly 3 hours

U = 3,600 unsettled blocks at the target deployment, about 4 hours at 4 s per block.

  • The rule: a block's height is at most U above the checkpoint its anchor proves.
  • U is a circuit breaker for settlement failure, not the pace of settlement. It also caps what a recovery can discard.
  • Inclusion on L1 does not release the pause. The landing must finalize and be adopted by a new anchor.
  • The 900 comes from three 20-minute legs: the gap between landings, proving and inclusion, then finality and anchor adoption.
  • At one landing every 20 minutes, a batch covers about 300 blocks.
  • Landers should prove continuously. One producible height left is an alarm, not a start signal.
  • These figures are targets that still await acceptance testing.

5 · Forced inclusion

Forced inclusion is enforced by the proof

Today
  • Proposers must process due entries from the Inbox's queue.
  • If an entry gets too old, proposing becomes permissionless. L1 is the escape hatch.
Etna
  • There is no permissionless proposing.
  • saveForcedInclusion(tx) accepts at most 8,192 bytes. The fee is fee × (threshold + pending) / threshold.
  • The Inbox stores only the hash, the L1 timestamp and the L1 block. The raw bytes are in the event.
  • The fee buys a place in the queue, not execution. It is never refunded and never paid to a lander.
  • A due entry at the head of the queue must be included or legally skipped. Otherwise the block is invalid and cannot be proven.

5 · Forced inclusion

How a block consumes the queue

Each block may consume one entry, the one at the cursor. An entry is due when anchor.timestamp ≥ entry.timestamp + forcedInclusionDelay.

CaseResult
Transaction 0 is the entryIncluded, cursor + 1, whether due or not. An ordinary revert still counts as inclusion.
Not included, not dueCursor unchanged.
Not included, due, bytes not eligibleSkipped, cursor + 1. No EL run is needed.
Not included, due, bytes eligibleSkippable only if a complete build of that transaction alone, on the parent, yields an empty block.
  • Eligible means exactly one canonical, non-blob transaction for this chain, with a valid signature and gas within the block limit.
  • Entries never expire. Any valid block with a timestamp at least forcedInclusionDelay + maxAnchorAge after the entry sees it as due.
  • That bound is in block time. There is no wall-clock deadline.

6 · Halts, recovery and upgrades

A pause loses nothing; a halt needs a person

Today the chain advances whenever L1 includes a proposal.

Liveness pause
  • The process keeps running, CometBFT keeps rounding, and production resumes by itself. No blocks are lost.
  • Causes: an anchor that is not final or too old, back-pressure, missing witness data, a ruleset the node does not implement, or a lagging L1 node.
  • To make this work with stock CometBFT, the application never returns an error. It proposes an empty placeholder that validators reject.
Safety halt
  • The process exits and needs investigation.
  • Causes: a decided block that breaks the rules or contradicts local state or the EL, fork evidence, or unverifiable data from the node's own L1 or EL.
  • If 1/3 or more of the power is offline, consensus halts. Members return, or the DAO recovers.
  • A settlement stall lets L2 produce at most U more blocks.
SPEC.md section 8

6 · Halts, recovery and upgrades

Governance recovery, step by step

recover(expectedGeneration, expectedC, expectedRecoveryNonce, validUntil, exclusions, fiToClear, rules)

  1. Validate every list and the expected state. One transaction, all or nothing.
  2. Exclusions: listed bonds are forced to exit. Recovery itself does not slash.
  3. Blanking: listed forced-inclusion entries that cannot be proven are emptied.
  4. The generation increments and a fixed origin is recorded: the checkpoint c and the L1 block R that ran the call.
  5. Nodes rebuild the EL at c and select the committee from the registry at R.
  6. Only the unsettled blocks above c are discarded. Users resubmit those transactions.
  • Only the DAO can call it. It is for a long landing stall, a structural upgrade, or replacing a ruleset. Slow progress is never a reason.
  • The expected checkpoint is fixed at authorization, so any landing in between voids the call.
  • Before authorizing, landers settle up to the last provable grid point.
  • There is no recovery queue or timer. Timing is the DAO's own process.

6 · Halts, recovery and upgrades

Each recovery starts a new generation

chain_id = "etna-" + base64url(keccak256(abi.encode(bytes32("ETNA_COMET_DOMAIN_V1"), l1ChainId, l2ChainId, inbox, generation))), 48 ASCII bytes

  • The generation is part of the chain id, so every vote is bound to it. Old votes cannot authorize the new chain.
  • Signing the same height in two generations is not a double sign.
  • The new CometBFT genesis has initial_height = c + 1, genesis_time = R.timestamp, and an app_hash equal to the EL hash at c.
  • Its validators are selected from the registry at R. Pending updates from the old generation are dropped.
  • The first block carries a finalized anchor no earlier than R.
  • The origin record is written once per generation. A proof cannot cross generations.
  • The signer keeps separate anti-double-sign state for each chain id, and never resets it.
  • A validator signs for the new generation only after its own finalized L1 view authenticates the recovery. It then refuses the old one.
SPEC.md sections 3.1, 8.2 and 8.4

6 · Halts, recovery and upgrades

A verifier failure takes a different path

Both proofs accepting a wrong result is outside the threat model. If it happens, recover cannot repair it.

Contain, then roll back
  • First pause the L1 SignalService and the Bridge, and rely on quota limits. land and the registry are not pausable.
  • One DAO upgrade replaces the verifier and restores the checkpoint, queue head and active committee snapshot to the last trusted landing.
  • It voids later landing records and the SignalService checkpoints they wrote.
Side effects the upgrade must handle
  • Signals cached, and bridge messages left retriable, since the first bad landing become unusable until proven again.
  • The registry checks every exit confirmation again against the restored snapshot.
  • The recovery nonce increments, so old recovery authorizations die.
  • Bridge payments or stake already withdrawn on a bad checkpoint cannot be recovered.
SPEC.md sections 1 and 8

6 · Halts, recovery and upgrades

Two kinds of protocol upgrade

Rule upgrade: no stop
  • The DAO calls scheduleRules(rules, time). One Inbox slot holds the active ruleset, the next one and its start time.
  • A block uses the next ruleset once its timestamp reaches that time, read at the block's own anchor.
  • The time must be at least maxAnchorAge ahead, so every later block's anchor already shows it.
  • A node without the ruleset pauses instead of forking. A guest image proves only rulesets it implements.
Structural upgrade: stop and recover
  • Needed for anything L1 checks or stores: the statement, land, K, U, the registry. Also the envelope framing, the block size bound, CometBFT's version and the chain id.
  • scheduleStop(time, grid) ends production at a grid point. Landers settle up to it.
  • One DAO transaction upgrades the contracts and calls recover with the new ruleset.
  • Registering a new guest image alone is not an upgrade.
SPEC.md section 10.1

7 · Nodes

L1 is the trust anchor, and signing waits for it

  • L1 replaces a weak-subjectivity checkpoint. Every node start, and every signer session, begins untrusted.
  • A node becomes trusted once it reaches the Inbox's latest checkpoint, seen in its own finalized L1 view, with matching EL hash, CometBFT hash and validator-state hash.
  • Missing data keeps the node untrusted and retrying. A contradiction halts it for safety.
  • The EL treats the last checkpoint as finalized, so a history forged with old keys can run at most U blocks past its fork point.
  • Every signature, nil votes included, needs the application to confirm the node is trusted.
  • The key sits in an external signer with its own anti-double-sign state, outside CometBFT's home directory.
  • A refusing signer answers with an explicit error. A supervisor restarts CometBFT automatically once trust returns.
  • Exchanges, bridges and public RPC must read the application's trust status, not CometBFT's catching_up.
SPEC.md section 9

7 · Nodes

Three ways to start a node

Replay from the fixed genesis

Replay the current generation from its origin. Always available, and the only way to check every block yourself. It needs the archived consensus history.

Checkpoint import

A validator or full node starts at a landed checkpoint without executing earlier blocks. It authenticates the checkpoint from its own L1, verifies a bounded window of blocks and commits, installs the landed validator sets, then syncs from the next height.

EL-only snapshot sync

An EL starts from a public snapshot at a settled checkpoint and imports only landed blocks. It serves data up to its last matched checkpoint and never signs.

  • Signer state is never imported. Finishing an import grants no signing authority.
  • An imported node has not executed the earlier blocks, so it cannot detect a bad landing at or below its starting point.
  • Operators must keep a public snapshot path, the genesis state and the generation's origin state available.
SPEC.md sections 5.3, 5.4 and 8.4

8 · Reference

What Etna buys, and what it costs

Gains
  • Finality in seconds, without a preconfirmation layer.
  • Simpler derivation: no proposal manifests, no anchor transaction, no golden touch key.
  • No proposer bonds, proving windows or liveness-bond settlement.
  • Stock CometBFT, and an EL whose only Taiko-specific execution rule is header validation.
Costs
  • Ordering and liveness no longer come from L1. They need an honest, online supermajority.
  • Censorship resistance has no wall-clock bound and no permissionless proposing.
  • The DAO is the only way out of a stalled committee, and recovery discards unsettled blocks.
  • Landing earns nothing, so operations depend on DAO funding.
  • Consensus history is private and must be archived.
  • The target is Stage 0. Stage 1 is not a goal for now.

No inclusion deadline

Forced inclusion has no wall-clock bound.

Offline quorum

Only DAO recovery replaces members who stay offline.

Narrow slashing

Only double signing in the same round is slashed by evidence.

Rotation

No limit on how much voting power can change at a rotation.

New key type

secp256k1eth arrived in CometBFT v0.40.0 and is less tested than Ed25519.

Unpinned values

K, the capital target and the forfeiture rate are not fixed. Latency figures await acceptance tests.

Upgrades

They depend on the DAO and on validators upgrading in time.

Switch origin

A multisig writes the Etna start. A wrong value stops Etna but cannot reach funds.

The one-time switch from Unzen

  1. One DAO proposal upgrades the Unzen Inbox, the L1 SignalService and the L2 contracts, and trusts the new guest images.
  2. The Unzen Inbox stops accepting proposals shortly before ETNA_FORK_TIME. Its last block is S.
  3. Once L1 has finalized past the fork time, a multisig writes S, its hash and its state root, once.
  4. Nodes build the CometBFT genesis and produce S + 1. Etna does not wait for Unzen's final proofs.
  5. The first landing requires the Unzen Inbox to have finalized through S with the same hash.

The outage runs from step 2 until the first Etna block in step 4.
