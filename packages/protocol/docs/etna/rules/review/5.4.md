## Q5.4-1

**Which app bootstrap implementation and store layout implement the window import and offline installation?**

**Text.** DATA-5.4-2 through DATA-5.4-5 require a bounded window, installation of the landed validator state, a precise post-s state and durable offline bootstrap of stock v0.40.0 stores.

**Why it matters.** Beyond the public EL verifier tracked in [Q5.3-1](5.3.md#q53-1), app bootstrap needs a concrete window importer and pinned app/Comet/evidence-store layouts, with EL canonical indexes, historical state, contradiction handling and durable cross-store installation. These are separate from verifying a public EL snapshot or syncing finalized execution blocks.

**Would close it.** Name the implementation and versions, publish verification/import commands and demonstrate ACCEPTANCE.md section 7, including H+2, evidence, interrupted installation and window import resource measurements against declared deployment budgets.

## Q5.4-2

**Which operators and endpoints provide the complete app-import path?**

**Text.** DATA-5.4-8 requires an available authenticated current-generation package and all data needed to reach the latest finalized checkpoint; 9.1 retains the consensus archive separately from public blobs.

**Why it matters.** A joining app node needs discoverable access to an import package and its window, and a rotation/outage runbook; the full current-generation consensus history stays archived so fixed-genesis replay remains possible. Public EL snapshots alone do not satisfy this dependency.

**Would close it.** Publish supported packages, consensus archive endpoints/access, responsible operators and the tested rotation/repair procedure.
