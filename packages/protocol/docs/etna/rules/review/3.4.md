## Q3.4-1

**"Same deterministic rules" includes checks that depend on each node's L1 view**

**Text.** "ProcessProposal and FinalizeBlock apply the same deterministic rules, in order:" and, in 3.3, "In ProcessProposal, a validator checks with its own L1 node that the anchor header is canonical and finalized". Section 9 adds that during cold sync FinalizeBlock "likewise first checks with its own L1 node".

**Why it matters.** Rule 2 incorporates 3.3's own-L1-node anchor check, and rule 3 reads the generation's fixed origin, so parts of the rule list depend on L1 facts rather than on the block alone. Two honest nodes with different L1 heads can reach different outcomes for the same block, so "deterministic" cannot mean "same result on every node". The text also names the own-L1-node check in ProcessProposal (3.3) and in cold-sync FinalizeBlock (section 9), but not in live FinalizeBlock, so it is unclear whether the check is repeated there and what happens when the two paths disagree.

**Would close it.** separate block-local deterministic rules from node-local L1 checks, state which checks each ABCI path performs, and state whether a disagreement between an accepted proposal and a node's own L1 view is a pause or a safety halt.

## Q3.4-2

**Order of the chain_id and Inbox-generation checks**

**Text.** "Generation: recompute `chain_id` per appendix A from `extraData`'s uint48 generation and this deployment's parameters; it must exactly match the current chain and CometBFT header. ... If the Inbox's generation is larger, this chain has been superseded (section 8); if it is smaller, reject the block."

**Why it matters.** A `chain_id` mismatch fails rule 4, so the block is invalid like any other failure of rules 1–9. What the text leaves open is the order of the two checks, which matters only when both fail: the block is then either rejected for the mismatch or treated as carrying a superseded-generation anchor (section 8).

**Would close it.** state the order of the two checks, or that the superseded-generation outcome takes precedence.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q3.4-3

**The recovery-initial committee has no stated witness case**

**Text.** "Committee witness: required at switch block S(t), forbidden elsewhere; its registry proofs are verified under the stateRoot of S(t)'s own anchor (4.3). Recovery establishes its authenticated starting committee under section 8 without re-emitting an old pending update. If the first recovered block is S(t), normal switch derivation still applies."

**Why it matters.** Section 8.4 says genesis validators for a new generation are selected on the R snapshot, and the first block uses stock genesis's empty LastBlockID/LastCommit. But 3.4 says a committee witness is required at S(t) and forbidden elsewhere, without saying whether the first block of a recovered generation carries one. The sentence "Recovery establishes its authenticated starting committee under section 8" suggests another authentication path, but it is not described here. An implementer cannot tell whether the first recovered block must carry a committee witness.

**Would close it.** enumerate the witness-presence cases for generation start, recovery start, and S(t), and say how the recovery-initial committee is authenticated in the block itself.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q3.4-4

**"Header matches 3.2 field by field" versus beneficiary "not checked"**

**Text.** Rule 7: "The header matches 3.2 field by field". The 3.2 preamble: "Every field except `beneficiary` is determined by the committed parent ..."; the beneficiary row says "any fee recipient the proposer chooses, as in Ethereum; not checked."

**Why it matters.** Rule 7 does not repeat the beneficiary exception. A literal reading compares every field, including beneficiary, which would make a proposer's free choice fail the field-by-field check. The 3.2 preamble and row exclude it, but the validity rule is where an implementer looks for the check, and the two sections are in different places.

**Would close it.** state in rule 7 that the comparison excludes beneficiary (or list the checked fields), and keep the exception in one place.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q3.4-5

**What the 124,000-byte bound measures, and why only this rule has a halt**

**Text.** "the envelope's block item (the payload's `executionBlock`, including its RLP list header, with every transaction, legacy included, counted as an RLP byte string of its EIP-2718 encoding) is at most 124,000 bytes long" and "If more than 2/3 of malicious voting power decides a block that violates this rule, honest nodes halt for safety in FinalizeBlock, and only governance recovery can fix that."

**Why it matters.** Appendix A defines `block = [elHeader, [tx, ...]]` inside the envelope and `payload = 0x06 || zlib(rlp([rlp([elHeader, [tx, ...]]), ...]))`; the sentence says "the envelope's block item (the payload's executionBlock ...)" without saying whether the two encodings are identical. It is unclear whether the 124,000 bytes are the RLP encoding of the executionBlock list, the item as carried in the envelope, or the bytes before compression. The second problem is consistency: section 8 says a decided block that violates the validity rules is a safety halt, but this rule is the only one in 3.4 that states that consequence. A reader cannot tell whether a decided block violating, say, rule 4 (generation) also halts or is merely rejected.

**Would close it.** define the measured byte string exactly (which RLP object, and whether the list header counts), and state the general rule for a decided block that violates any 3.4 rule, with this case as an instance or an exception.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q3.4-7

**The checkpoint check is described only for a changing anchor**

**Text.** "when the anchor changes, nodes check the anchor's proven `lastCheckpoint`: its height is at most the parent height, and its hash equals the EL block hash at that height on the authenticated local chain."

**Why it matters.** Most blocks inherit their parent's anchor and carry no witness, so this check does not visibly run for them. The inherited checkpoint data was checked when the anchor was carried, but a node that cold-syncs or whose local chain has moved may need the check again. The text also does not say whether the inherited anchor's `lastCheckpoint` is re-authenticated per block or trusted from the carrying block. That affects whether a checkpoint conflict can be detected after the fact, and whether the guests' storage-proof-only role covers inherited anchors.

**Would close it.** state whether the check is performed only at anchor-change blocks (and inherited anchors are trusted from the block that carried them), or per block, and how a cold-syncing node re-checks it.

Raised by: DeepSeek-V4.1-Flash (dantaik)
