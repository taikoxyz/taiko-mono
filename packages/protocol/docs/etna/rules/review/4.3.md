## Q4.3-6

**What if no members list matches the stored `snapshotHash`?**

**Text.** COMM-4.3-3: "Nodes and guests read `snapshotHeight`, `snapshotTotalStake` and `snapshotHash` from H's post-state (appendix B) and take as the candidate's members the `SeatMember` list that `snapshotHash` commits to (appendix A)." The 4.3 details: "a bug or a faulty upgrade must not hand CometBFT an invalid set, which would stop the nodes."

**Why it matters.** The validity conditions (COMM-4.3-4, COMM-4.3-8) are the backstop against a faulty staking contract, but they apply to a members list that nodes must first obtain, for example from `snapshot()` or from seat storage, and match against `snapshotHash`. A faulty contract can store a hash that no list a node can obtain matches, or return from `snapshot()` a list that does not match it. The text does not say whether such a candidate is unusable, so that the fallback key set signs H + 2, or whether H + 2 then has no defined set. A guest takes the list as input and can only check it against the hash; it cannot show that no matching list exists, so a rule that makes such a candidate unusable on nodes would also need a way for guests to reach the same answer.

**Would close it.** State where nodes and guests obtain the members list, and what follows when it cannot be matched to `snapshotHash`: an unusable candidate with a way for guests to establish that, or a halt that the contract's correctness must prevent.
