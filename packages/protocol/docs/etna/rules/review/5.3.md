# 5.3 — review notes

**Non-normative.** Nothing here can be conformed to or failed against. This is what decomposing [SPEC.md](../../SPEC.md) section 5.3 into citable statements turned up. Each item says what would close it. Only the spec owner decides.

## Normativity boundary

Every sentence in 5.3 carries an ID (DATA-5.3-1 ... DATA-5.3-9). The two prose sentences are split by markers DATA-5.3-1 and DATA-5.3-2; the three bullets are split into the starting material, the reconstruction steps and the archive rule. There are no un-numbered sentences in the section body, so no boundary table is needed.

## Q5.3-1

**Which program satisfies "a source-available reconstruction program"?**

**Text.** DATA-5.3-2: "A source-available reconstruction program and these public inputs are required:"

**Why it matters.** "Source-available" is not defined (source code? a specific licence? a reproducible build?), and the program is not named or versioned. A requirement that cannot be checked is guidance. The public-reconstruction guarantee is only meaningful if anyone can obtain the same program and get the same result; otherwise the requirement is satisfied by an unnamed internal tool.

**Would close it.** Name the program or repository, pin a version or content hash, and state the source-availability test (for example, a licence in the deployment manifest).

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q5.3-2

**What are the "content hashes", and where is the starting material published?**

**Text.** DATA-5.3-3: "Starting material includes downloadable complete genesis allocation/state and code, content hashes, EL rule version, L1/L2 chain ids, contract addresses, L1_0, genesis hash and stateRoot."

**Why it matters.** "Content hashes" has no referent: hashes of the genesis allocation files, the code, the program, the blobs, or the L1 headers? "Downloadable" does not say from where, and "complete genesis allocation/state and code" does not say in which encoding. Two reconstructors can use different artifacts and disagree at the first block, which defeats the recompute-and-match rule in DATA-5.3-4.

**Would close it.** Enumerate each artifact with its encoding, hash and publication location, or point to a manifest that lists exactly those fields.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q5.3-3

**How long must historical blobs remain retrievable, and who archives them?**

**Text.** DATA-5.3-9: "Historical blobs must remain retrievable and archive contents must be authenticated against L1 commitments."

**Why it matters.** L1 nodes prune EIP-4844 blobs; section 6.3 relies on a reference-header window of about 131,072 headers (about 18 days), and section 5.2 speaks of "archived blobs". "Must remain retrievable" therefore requires an archive, but the text does not say who must archive, for how long, or what happens if the archive is unavailable. It also does not say whether reconstruction reads blobs from L1 when they are still available or always from the archive. This is a DA/liveness assumption presented as a requirement.

**Would close it.** State the archive obligation (operator, retention at least as long as reconstruction may be needed) and the failure mode when the archive is missing.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q5.3-4

**Which "versions" can be unsupported?**

**Text.** DATA-5.3-8: "Reject missing original material, unsupported versions or hash mismatches".

**Why it matters.** "Versions" could mean the EL rule version, the payload/envelope encoding version, the blob encoding version, the guest image version, or the protocol `APP_VERSION`. The program needs a supported-version set to reject against; the text does not say where that set comes from or whether an unsupported version is a hard reject or an upgrade prompt. This matters most during the section 10.1 upgrade boundaries, when old and new rules coexist.

**Would close it.** Enumerate the versioned artifacts and say how the supported set is pinned (for example, the deployment manifest or config hash).
