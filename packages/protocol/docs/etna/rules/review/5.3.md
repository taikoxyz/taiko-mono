# 5.3 — review notes

**Non-normative.** Nothing here can be conformed to or failed against. These questions track deployment details of the snapshot/sync requirement and optional reconstruction mode. Only the spec owner decides; no answer is asserted here.

## Normativity boundary

The section body uses DATA-5.3-1a, DATA-5.3-2a, DATA-5.3-3 through DATA-5.3-8 and DATA-5.3-9a. DATA-5.3-1, DATA-5.3-2 and DATA-5.3-9 are retired: app import is admitted by 5.4 and full-blob-replay/full-archive obligations were withdrawn. The four remaining questions retain their attribution; no owner decision is asserted here.

## Q5.3-1

**Which public EL-only verifier and checkpoint-sync program is supplied?**

**Text.** DATA-5.3-2a: "Provide source-available snapshot-verification and checkpoint-sync tooling and the public inputs below, plus the app-import tooling required by 5.4."

**Why it matters.** The public EL-only path needs a concrete state/storage/code verifier and finalized-checkpoint sync program, with pinned versions and source-availability criteria. This question covers the public EL-only tooling; stock app/Comet/evidence-store reconstruction and offline installation are tracked separately in [Q5.4-1](5.4.md#q54-1).

**Would close it.** Name the program/repository, pin a version or content hash, and state the source-availability test and verification command in the deployment manifest.

## Q5.3-2

**Which snapshot artifact encodings and publication layout are supported?**

**Text.** DATA-5.3-3 requires complete downloadable state/code, hashes of published files, snapshot format/version, chain identities and starting checkpoint information.

**Why it matters.** File hashes and publication fields now have stated roles, but a deployment still needs an exact mapping from its database/export format to complete account, storage and code verification. Derived indexes need verification or rebuilding before use under DATA-5.3-4.

**Would close it.** Publish the concrete artifact manifest, encoding and supported client/tool revisions, with a reproducible import-and-state-verification procedure.

## Q5.3-3

**Which deployment endpoints and repair runbook implement the mandated public paths?**

**Text.** DATA-5.3-9a fixes the continuous snapshot-to-latest path, permanent public genesis material and public recoverability of the current generation origin. Those guarantees are no longer open design choices.

**Why it matters.** A deployment still needs concrete publication endpoints, supported snapshot formats/ages, responsibility assignments and an outage/repair procedure. These operational details must implement the fixed guarantees, including origin recovery during snapshot rotation; they cannot waive them.

**Would close it.** Publish the concrete rotation/repair runbook and supported snapshot/data-source inventory, then exercise it under ACCEPTANCE.md section 7.

## Q5.3-4

**Which versions can be unsupported?**

**Text.** DATA-5.3-8: "Reject incomplete starting state, missing required ancestor or subsequent-sync material, unsupported versions, an unauthenticated checkpoint/FI cursor, or hash/stateRoot mismatches; never skip required checks or replace authentication with RPC state."

**Why it matters.** DATA-5.3-3 requires snapshot-format and EL-rule versions, while optional blob replay also consumes versioned encodings. The supported set and its relationship to a 10.1 upgrade need a deployment-level definition; a matching checkpoint does not establish that an importer understands the database format or execution rules. DATA-5.3-3a settles the ruleset part (10.1); the snapshot-format and encoding versions remain open.

**Would close it.** Enumerate the versioned artifacts and supported combinations in the deployment manifest, including how an operator obtains a compatible verifier/importer.
