## Q10-1

**Proxy owner, deployment order and the past genesisCutoff are not tied together**

**Text.** "Deploy the Inbox proxy (not yet initialized; only its owner can initialize it), then deploy the registry with that proxy address fixed; validators sign the registration digest (appendix A) with their consensus keys, register and wait for activation and finality." and "Pick a past `genesisCutoff`".

**Why it matters.** Three unstated things interact. First, the owner is never named (DAO, timelock, deployer EOA), yet 4.1 makes the registry's copy of the Inbox address unchangeable, so the wrong owner or address is unrecoverable except through the migration in START-10-16. Second, committee 0 is selected at `genesisCutoff` — a block in the past — while validators register in step 1 and wait for `activationDelay`; if registration happens after the cutoff, no validator can be in committee 0, and the flow has no stated ordering that prevents that. Third, "wait for activation and finality" gives no bound and no check.

**Would close it.** state the owner, make the registration-before-cutoff ordering explicit (or explain how a past cutoff can include validators registering now), and say whether the two deployments are atomic or how a partial deployment is recovered.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q10-2

**Installing the EIP-4788 and EIP-2935 predeploys is not verified anywhere**

**Text.** "Install EIP-4788 and EIP-2935 in the L2 genesis".

**Why it matters.** 3.2 makes `parentBeaconBlockRoot` the anchor's L1 stateRoot and says the EL writes it into the EIP-4788 contract, and L2 contracts verify L1 storage proofs against it. A genesis that omits either predeploy satisfies every numbered step but cannot support the anchor model. The section says "deployment, nodes and guests check the same configuration" (START-10-14) without saying that the genesis configuration is part of it, and the genesis details list consensus params, not predeploys.

**Would close it.** state where the genesis configuration (including the predeploys) is checked — an acceptance test, a block-validity rule, or an InitChain check — and the failure mode.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q10-3

**The initialization field list does not cover the parameters §11 calls "Inbox immutable"**

**Text.** "initialize the Inbox ... with L, genesisCutoff, committee-0/config hashes, forcedInclusionDelay and maxAnchorAge" and §11's row "maxBatchBlocks, forced inclusion fee and doubling threshold, verifier, `protocolFeeRecipient` — Inbox immutable".

**Why it matters.** U, maxBatchBlocks, the FI fee and doubling threshold, the verifier and `protocolFeeRecipient` are immutable Inbox values, but step 5 mentions only `protocolFeeRecipient`. A reader cannot tell which of them are constructor arguments, which are initializer arguments, and which are read from the config hash. This matters at deployment time (the wrong split produces an uninitializable contract) and at audit time (an immutable not covered by the config hash is not authenticated by it).

**Would close it.** give the complete construction and initialization parameter lists, and say which are committed in the config hash and which are checked at initialization.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q10-5

**Some configuration fields cannot be compared on-chain, and the trust assumption is unstated**

**Text.** "The generator writes an empty parameter-update authority. CometBFT v0.40.0 passes that value to InitChain inside the genesis consensus params but only bounds its length and stores it, leaving its meaning to the application, and the application never changes consensus params (3.1), so a different value has no effect and InitChain need not compare it." and START-10-14: "deployment, nodes and guests check the same configuration".

**Why it matters.** The text names one field that InitChain need not compare. Which fields are committed in the config hash and compared, and which are trusted from the deployment manifest? A deployment whose manifest differs in a field nobody compares would pass every rule, yet two nodes could disagree about what was deployed. "Deployment, nodes and guests check the same configuration" is not a mechanism.

**Would close it.** enumerate the fields compared by InitChain and by guests, name the fields that are only manifest-trusted, and state the consequence of a mismatch.

## Q10-6

**"Old signing state is not reset" is undefined once chain_id changes**

**Text.** "Old signing state is not reset." and START-10-16a: "Incorrect parameters in the deployment core (10.1) still require a new Inbox/genesis".

**Why it matters.** A new Inbox proxy address changes `chainDomain` and therefore `chain_id` (3.1 and appendix A). 8.2 requires separate HRS state per full `chain_id` and forbids resetting or rolling it back. If the new deployment has a new `chain_id`, the old state is a different domain: keeping it is harmless but cannot be reused, and "not reset" may be satisfied by leaving a file nobody reads. If the deployment somehow keeps the old `chain_id`, reusing the state is mandatory. The sentence does not say which case applies, yet a fresh deployment is exactly where state gets wiped.

**Would close it.** state what "signing state" covers, whether a migration changes `chain_id`, and what an operator must do (and must not do) with the old state.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q10-7

**The switching L1 range-checks only the Unzen Inbox's checkpoints**

**Text.** "its `saveCheckpoint` accepts calls only from the Unzen Inbox, accepts any height before the start write, rejects heights above S once the start is written" (START-10-5).

**Why it matters.** `saveCheckpoint` overwrites an existing checkpoint without a range check of its own, which is why the Inbox's forwarder rejects Unzen Inbox checkpoints above S. Nothing rejects an Inbox landing checkpoint at or below S: only `land`'s own range check (c < h with c at or above S) keeps the Inbox above S, so a defect in the Inbox or in a later Inbox upgrade could silently overwrite a checkpoint that Unzen withdrawals and the first-landing check (LAND-6.1-8a) depend on. The mirror rule would cost one comparison. The SignalService has one syncer, so it cannot tell the two paths apart; both checks would sit in the Inbox. The text does not say whether the asymmetry is intended.

**Would close it.** either add the mirror rule (the Inbox's landing writes reject heights at or below S once the start is written, and say how a START-10-5c rewrite of S interacts with it), or state why `land`'s range check is considered enough.

Raised by: Claude Fable 5.2 (davidtaikocha)

Raised by: Claude Opus 5.5 (davidtaikocha), amending the text above for the single-syncer SignalService

## Q10-8

**The only bound on maxAnchorAge that can be checked is one the text says is too low on Ethereum**

**Text.** "forcedInclusionDelay>0 and maxAnchorAge≥1152 s" (START-10-9) and PARAM-11-5: "plus the allowance the deployment makes for slots missed at an epoch boundary and for nodes' delay in importing that finalization" … "On Ethereum 1152 s itself therefore does not satisfy this constraint."

**Why it matters.** Both constraints apply, and on Ethereum the second one binds: every value from 1152 s up to 1152 s plus the allowance fails it. The allowance, though, has no stated value, minimum or derivation; it is whatever the deployment chooses. The 1152 s floor is therefore the only bound that a deployment check, a node or a guest can compare a configured value with (START-10-14), and a deployment at or just above the floor passes that comparison while it does not meet PARAM-11-5. Only an acceptance measurement of the finalized block's peak age would show the difference.

**Would close it.** Either state the allowance, as a number or as a formula over L1's parameters, and raise the floor in START-10-9 to match on Ethereum, or state that the allowance is settled at acceptance and that START-10-9 is only a lower sanity bound.

Raised by: Claude Fable 5.2 (davidtaikocha)

## Q10-9

**The evidence limits of 900 blocks and 1 h are not derived or measured**

**Text.** START-10-21: "evidence limits of 900 blocks, 1 h and 1 MiB", with "a node no longer sends it to a peer whose height is more than 900 blocks above the evidence's, whatever its age in time".

**Why it matters.** The limits set the 5.4 import window (DATA-5.4-2) and the history every node keeps for evidence, so smaller values make import and storage cheaper. The spec gives no lower bound for them. CometBFT v0.40.0 treats evidence as expired only when it is older than both limits, stops sending it to a peer once the peer is more than the block limit past it, uses the limits to prune its evidence pool, and applies them to light-client-attack evidence as well as to duplicate votes; whether any of those, or the tooling that gathers conflicting votes for `slashDoubleSign` (SYNC-9.1-7), needs a longer window has not been checked against a running network. The values are fixed for a generation (consensus params are never updated), so a wrong choice is corrected only at a generation boundary.

**Would close it.** state what the limits must cover (for example the longest interval in which a node can still usefully gossip CometBFT evidence), derive or measure the values against it, and add the check to ACCEPTANCE.md.

Raised by: Claude Fable 5.2 (davidtaikocha)

## Q10-10

**Nodes that reject a decided block for expired evidence stay out until a landing covers it**

**Text.** START-10-21: "a block carrying such an item is valid for a node that still holds it as pending and invalid for a node that does not" and "the node continues by a 5.4 import at a landed checkpoint at or above the block".

**Why it matters.** In CometBFT v0.40.0, `CheckEvidence` (`evidence/pool.go`) verifies a duplicate-vote item only when it is not already pending, `PendingEvidence` hands a proposer every pending item without an expiry check, and `Update` prunes the pending pool only past the height and time the previous pruning returned. A proposer can therefore carry an item that has just expired, honestly or on purpose, and a party that delivers the item to some nodes shortly before it expires chooses which nodes will hold it. Nodes without it prevote nil; if more than 2/3 of the voting power holds it the block is decided, and the others stop in `finalizeCommit` ("+2/3 committed an invalid block"), while a block-syncing node drops the peers that served the block and stalls. The text gives the way back, an import at a landed checkpoint at or above the block. Until a landing ends there, an affected validator does not sign; replay from the fixed genesis stops at that block for good (DATA-5.4-8); and a node that imports has not executed the blocks up to its checkpoint itself (DATA-5.3-9a). Two things are undecided: whether the app should prevent the case, and whether there is a cheaper way back. The item's bytes are in the block itself, and `broadcast_evidence` (`rpc/core/evidence.go`) adds an item to the pending pool while the node's own state still finds it unexpired, so a replaying node could be given the item before it reaches that point; the spec defines no such procedure, and it has not been tried.

**Would close it.** decide whether the app rejects a proposal whose misbehaviour list holds an item older than both limits, so that honest nodes agree whatever their pending pools hold, or whether the import is the accepted remedy; in the second case, bound how long affected validators can be out and say whether giving a replaying node the item is allowed.

Raised by: Claude Fable 5.2 (davidtaikocha)
