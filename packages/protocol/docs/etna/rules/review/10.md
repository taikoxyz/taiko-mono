## Q10-1

**Proxy owner, deployment order and the past genesisCutoff are not tied together**

**Text.** "Deploy the Inbox proxy (not yet initialized; only its owner can initialize it), then deploy the registry with that proxy address fixed; validators sign the registration digest (appendix A) with their consensus keys, register and wait for activation and finality." and "Pick a past `genesisCutoff`".

**Why it matters.** Three unstated things interact. First, the owner is never named (DAO, timelock, deployer EOA), yet 4.1 makes the registry's copy of the Inbox address unchangeable, so the wrong owner or address is unrecoverable except through the migration in START-10-16. Second, committee 0 is selected at `genesisCutoff` — a block in the past — while validators register in step 1 and wait for `activationDelay`; if registration happens after the cutoff, no validator can be in committee 0, and the flow has no stated ordering that prevents that. Third, "wait for activation and finality" gives no bound and no check.

**Would close it.** state the owner, make the registration-before-cutoff ordering explicit (or explain how a past cutoff can include validators registering now), and say whether the two deployments are atomic or how a partial deployment is recovered.

## Q10-2

**Installing the EIP-4788 and EIP-2935 predeploys is not verified anywhere**

**Text.** "Install EIP-4788 and EIP-2935 in the L2 genesis".

**Why it matters.** 3.2 makes `parentBeaconBlockRoot` the anchor's L1 stateRoot and says the EL writes it into the EIP-4788 contract, and L2 contracts verify L1 storage proofs against it. A genesis that omits either predeploy satisfies every numbered step but cannot support the anchor model. The section says "deployment, nodes and guests check the same configuration" (START-10-14) without saying that the genesis configuration is part of it, and the genesis details list consensus params, not predeploys.

**Would close it.** state where the genesis configuration (including the predeploys) is checked — an acceptance test, a block-validity rule, or an InitChain check — and the failure mode.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q10-3

**The initialization field list does not cover the parameters §11 calls "Inbox immutable"**

**Text.** "initialize the Inbox ... with L, genesisCutoff, committee-0/config hashes, forcedInclusionDelay and maxAnchorAge" and §11's row "maxBatchBlocks, forced inclusion fee and doubling threshold, verifier, `protocolFeeRecipient` — Inbox immutable".

**Why it matters.** U, maxBatchBlocks, the FI fee and doubling threshold, the verifier and `protocolFeeRecipient` are immutable Inbox values, but step 5 mentions only `protocolFeeRecipient`. A reader cannot tell which of them are constructor arguments, which are initializer arguments, and which are read from the config hash. This matters at deployment time (the wrong split produces an uninitializable contract) and at audit time (an immutable not covered by the config hash is not authenticated by it).

**Would close it.** give the complete construction and initialization parameter lists, and say which are committed in the config hash and which are checked at initialization.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q10-5

**Some configuration fields cannot be compared on-chain, and the trust assumption is unstated**

**Text.** "The generator writes an empty parameter-update authority. CometBFT v0.40.0 passes that value to InitChain inside the genesis consensus params but only bounds its length and stores it, leaving its meaning to the application, and the application never changes consensus params (3.1), so a different value has no effect and InitChain need not compare it." and START-10-14: "deployment, nodes and guests check the same configuration".

**Why it matters.** The text names one field that InitChain need not compare. Which fields are committed in the config hash and compared, and which are trusted from the deployment manifest? A deployment whose manifest differs in a field nobody compares would pass every rule, yet two nodes could disagree about what was deployed. "Deployment, nodes and guests check the same configuration" is not a mechanism.

**Would close it.** enumerate the fields compared by InitChain and by guests, name the fields that are only manifest-trusted, and state the consequence of a mismatch.

## Q10-6

**"Old signing state is not reset" is undefined once chain_id changes**

**Text.** "Old signing state is not reset." and START-10-16a: "Incorrect parameters in the deployment core (10.1) still require a new Inbox/genesis".

**Why it matters.** A new Inbox proxy address changes `chainDomain` and therefore `chain_id` (3.1 and appendix A). 8.2 requires separate HRS state per full `chain_id` and forbids resetting or rolling it back. If the new deployment has a new `chain_id`, the old state is a different domain: keeping it is harmless but cannot be reused, and "not reset" may be satisfied by leaving a file nobody reads. If the deployment somehow keeps the old `chain_id`, reusing the state is mandatory. The sentence does not say which case applies, yet a fresh deployment is exactly where state gets wiped.

**Would close it.** state what "signing state" covers, whether a migration changes `chain_id`, and what an operator must do (and must not do) with the old state.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q10-7

**The upgraded L1 SignalService range-checks only one of its two syncers**

**Text.** "it accepts checkpoints from both the Unzen Inbox and the Inbox, rejects Unzen Inbox checkpoints above S once the start is written" (START-10-5).

**Why it matters.** `saveCheckpoint` overwrites an existing checkpoint without a range check of its own, which is why the upgrade rejects Unzen Inbox checkpoints above S. Nothing rejects an Inbox checkpoint at or below S: today only `land`'s own range check (c < h with c at or above S) keeps the Inbox above S, so a defect in the Inbox or in a later Inbox upgrade could silently overwrite a checkpoint that Unzen withdrawals and the first-landing check (LAND-6.1-8a) depend on. The mirror rule would cost one comparison. The text does not say whether the asymmetry is intended.

**Would close it.** either add the mirror rule (the SignalService rejects Inbox checkpoints at or below S once the start is written, and say how a START-10-5c rewrite of S interacts with it), or state why the Inbox's own check is considered enough.
