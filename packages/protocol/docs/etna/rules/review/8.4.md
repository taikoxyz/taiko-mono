## Q8.4-1

**"A missing record is rejected" — by which component, and how?**

**Text.** "A missing record is rejected; mapping defaults or the latest checkpoint are not substitutes."

**Why it matters.** A slot-290 record is read by at least three parties: `land` (6.1 step 2, which reverts on a missing origin), a node at startup and while proving, and a guest. "Rejected" means a revert for the first, a proposal rejection or halt for the second, and a failed proof for the third. The text does not distinguish them, and the consequence differs for each.

**Would close it.** Name the checkers and what each does on a missing record.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q8.4-2

**What is generation 0's origin record used for?**

**Text.** "generation 0's is (S, L1_0, L1_0's timestamp, the `fallbackKeysHash` in slot 278 at the start write), written by the start write (START-10-5b), and describes the Etna start, not a recovery."

**Why it matters.** "Not a recovery" excludes it from being a recovery origin, and its `fallbackKeysHash` fixes the keys that sign S + 1 and S + 2 (COMM-4.3-9). But the record is also the source for 3.4 rule 3's "current generation's L1 origin" (which is `L1_0` for generation 0) and for `generationStartHeight`. A reader cannot tell whether generation 0's record is used by those checks or only describes the start.

**Would close it.** List the uses of generation 0's record (anchor floor, start height, first two signing sets) and say whether it is exempt from the recover-time rules.

Raised by: DeepSeek-V4.1-Flash (dantaik)
Raised by: Claude Opus 5.5 (davidtaikocha) (amended: the record's fourth word now fixes the first two signing sets)

## Q8.4-3

**The orphan generation's record is retained, and reads may expose it**

**Text.** "Each record is written once and never overwritten or deleted." Together with the verifier-failure rollback, which does not change the generation, and 8.3's "generation never decreases."

**Why it matters.** A recovery that ran at a c above the restored one leaves a permanently written origin record for a generation that cannot land. `generationStartHeight` and every other reader of the record read slot 290 directly; nothing says which generation they read or what they return when asked about the abandoned one. A node or guest can read the orphan record and treat it as live.

**Would close it.** State that the abandoned generation is not authenticated or signed, and that reads are always for the current generation only.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q8.4-5

**How does InitChain obtain c's EL hash and stateRoot?**

**Text.** "chain_id uses the new generation, initial_height=c+1, genesis_time=R.timestamp, and InitChain returns the appHash of ELHash(c) and the genesis validator state (CONS-3.1-8). … EL state must match c's authenticated EL hash and stateRoot."

**Why it matters.** InitChain receives the genesis document. For a recovery generation, that document must carry c's authenticated EL hash and stateRoot so the app can compare the EL state and return `app_hash`. Section 10's initial-deployment genesis carries the L1 header and Inbox proof; 8.4 does not say what the recovery genesis carries or how InitChain authenticates those values. Without that, "EL state must match" has no stated source of truth.

**Would close it.** State the recovery genesis parameters and the authentication path (the retained c record, the Inbox proof, and the reference to the origin record).

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q8.4-7

**May the first block's anchor be later than R?**

**Text.** "The first block must carry a finalized anchor witness no earlier than R and does not use c's anchor."

**Why it matters.** "No earlier than R" allows any finalized anchor at or after R, including one much later. The sets that sign c + 1 and c + 2 come from the origin record whatever the anchor (COMM-4.3-9), but c + 1's anchor proves the `minTotalStake` and `fallbackKeysHash` that decide the set that signs c + 3 (COMM-4.3-3a). The first block could be built with an anchor R+100 if that block is finalized, and that anchor can carry a `setMinTotalStake` or `setFallbackKeys` executed after R. That is consistent with the words, but it means the first block's witness proves a different L1 state than the one that authenticated the recovery. Whether that is intended affects what a joining node must verify first.

**Would close it.** State whether any finalized anchor at or after R is acceptable, and whether a DAO change made between R and that anchor may decide the set that signs c + 3.

Raised by: DeepSeek-V4.1-Flash (dantaik)
Raised by: Claude Opus 5.5 (davidtaikocha) (amended: the first two sets come from the origin record; the anchor now decides the set that signs c + 3)
