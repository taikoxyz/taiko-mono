## Q4.2-1

**Which epoch contains block 0?**

**Text.** STAKE-4.2-2: "Epoch t starts at block `H(t) = 1 + t·L`; block h belongs to epoch `floor((h − 1) / L)`."

**Why it matters.** For `h = 0` the formula yields `floor(-1 / L) = -1`, which is not a valid epoch index under `t >= 0`. Either block 0 is outside the epoch system (a genesis special case), or the formula is meant only for `h >= 1` and block 0 belongs to epoch 0. The difference matters for committee 0 (`targetEpoch = 0`) and for any tool that maps a height to an epoch.

**Would close it.** State the epoch of block 0, or restrict the formula to `h >= 1` and say that block 0 is the Etna start rather than an epoch member.

## Q4.2-2

**May L or `L1_0` change on an Inbox replacement or a new generation?**

**Text.** STAKE-4.2-1: "L = `epochLenL2`, the number of L2 blocks per epoch, and `L1_0` is the L1 block in which the Inbox was initialized; both are fixed at initialization."

**Why it matters.** "Fixed at initialization" can mean fixed for the life of one Inbox, or fixed for the protocol. Section 10 permits a new Inbox and a new registry; section 10.1 treats some deployment parameters as new-genesis migrations. It is not stated whether a replacement Inbox may initialize a different L or `L1_0`, or whether a governance recovery re-initializes them (it does not create a new Inbox). The answer controls whether historical epoch numbering is comparable across deployments.

**Would close it.** State whether L and `L1_0` are immutable for a chain identity, and whether a replacement Inbox starts a new epoch history.
