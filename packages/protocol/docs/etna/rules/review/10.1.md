## Q10.1-8

**How the EL learns which ruleset to execute for a block**

**Text.** START-10.1-14a: "Nodes compute each block's ruleset and stop as above in PrepareProposal, ProcessProposal and FinalizeBlock." START-10.1-3a: a ruleset defines "what nodes and guests check and execute for each block".

**Why it matters.** Execution rules live in the EL, which does not read L1 state. The block header already binds the anchor (`extraData` and `parentBeaconBlockRoot`), and through it slot 293, so the block hash commits to the ruleset and no header field is needed for determinism. But the application must still tell the EL which ruleset to run for each payload it builds, validates or replays, and the text names no interface for that. Two client implementations could pass it differently (an Engine API field, a per-block EL configuration call, or a fork schedule pushed ahead of time), which matters for cold sync and for building a block exactly at `rulesTime`.

**Would close it.** name the interface that carries the block's ruleset to the EL (for example a ruleset field in the build and `newPayload` calls), or state that it is an implementation interface outside this specification, with shared vectors covering a block at `rulesTime − 1` and at `rulesTime`.
