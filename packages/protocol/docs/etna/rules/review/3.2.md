## Q3.2-1

**The floor and unit of "BFT time" are undefined**

**Text.** "`timestamp` | max(parent.timestamp + 1, ⌊BFT time⌋, anchor.timestamp)".

**Why it matters.** Ethereum timestamps are integer Unix seconds. CometBFT's BFT time is a `time.Time` with sub-second precision, and "⌊BFT time⌋" does not say whether it is floored to seconds, truncated toward zero, or converted to a Unix timestamp first. Two nodes with the same BFT time but different conversion can compute different header timestamps at a second boundary, and the header is compared "field by field" by other nodes.

**Would close it.** define the representation (for example "BFT time as Unix seconds, floored, i.e. `uint64(t.Unix())`") and state whether a proposal whose timestamp differs by one second is invalid.

## Q3.2-2

**The EIP-4396 adjustment is named but not written**

**Text.** "`baseFeePerGas` | fixed at 0.025 gwei for block 1; afterwards adjusted by EIP-4396 from the parent's gas usage and block interval (parent minus grandparent timestamp), clamped between the chain's minimum base fee (0.01 gwei for chain id 167000, 0.005 gwei otherwise) and 1 gwei".

**Why it matters.** The base fee determines which transactions are valid in a block and what the beneficiary receives, so every node must compute the same value. EIP-4396 has an exact integer formula with parameters (gas target, elasticity, max change denominator); the text names two inputs and the clamps but not the formula. Section 3.1 says "EIP-4396 parameters are published with that pinned EL version", but that sentence is a publication requirement, not a normative formula, and it does not say where a node finds the values.

**Would close it.** include the exact formula (or pin it by content hash with the EL release) and state the parameter values for each chain id, including the block-1 exception.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q3.2-3

**The "Unzen formula" for mixHash is external and unpinned**

**Text.** "`mixHash` | computed from parent.difficulty and height with the Unzen formula".

**Why it matters.** `mixHash` is a header field; if nodes recompute and compare it field by field, the formula is consensus-critical. SPEC.md does not contain it, does not link to it, and does not pin a version. "Unzen" appears only here and in the not-yet-designed switch (section 12, item 9), so a future Unzen change could silently change this field.

**Would close it.** include the formula, or cite a pinned document/revision and say whether a mismatch invalidates the block.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q3.2-4

**"Block-start system processing still follows 3.2" is self-referential**

**Text.** "Block-start system processing still follows 3.2 and is not rolled back with an aborted transaction."

**Why it matters.** The sentence is in 3.2, so "follows 3.2" cannot mean the section it sits in without circularity. It may mean a different section number, a protocol rule (for example the EIP-4788 system call), or that system processing uses the same header fields. The second clause ("not rolled back") is clear; the first is not, and it is the only sentence that ties block-start processing to the block-validity rules.

**Would close it.** name the processing (for example the EIP-4788 beacon-root write or EIP-2935 history write), state its ordering relative to transactions, and correct the cross-reference.
