# 8.2 — review notes

**Non-normative.** Nothing here can be conformed to or failed against. This is what decomposing [SPEC.md](../../SPEC.md) section 8.2 into citable rules turned up: questions the text does not settle, and sentences whose normative status was ambiguous. Each item says what would close it. Only the spec owner decides.

## Q8.2-1

**HRS state and key-copy rules are unverifiable from outside the signer**

**Text.** "The signer keeps separate stock HRS state for each full `chain_id` (which includes the generation), persists each signature before returning it, and never resets or rolls that state back; no copy of the key may sign outside that state."

**Why it matters.** These are the rules that make same-domain double signing impossible, and none of them is observable by the chain, a guest, or a peer. A conforming deployment and a deployment that violates every clause can produce identical votes until the moment one double-signs. The section also says the state lives outside the Comet home/mount, so even an operator inspecting the node cannot see it. The rule is binding (it has an ID) but has no conformance test stated anywhere.

**Would close it.** State the evidence a deployment must provide (HSM/KMS policy, attestation, independent audit) and, if none is required, say that conformance rests on operator assertion.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q8.2-2

**No stated path back to service after HRS state loss**

**Text.** "If the state is lost or its latest value is uncertain, stop signing; deleting state cannot restore service."

**Why it matters.** The prohibition is clear, but the permitted remedy is not. Can the validator re-register a new key and bond? Can the state be restored from a backup if the operator can prove no signature was made from the lost state? Does the entry remain registered but unable to sign forever? The phrase "deleting state cannot restore service" rules one option out without naming the one that works, and the answer determines whether the operator's capital is stranded.

**Would close it.** Name the recovery path (re-registration, key rotation, backup restoration with a stated proof) or state that the entry cannot sign again.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q8.2-3

**Ordering of the authentication checks before the first new-generation signature**

**Text.** "Sign for a new generation only after the node's own finalized L1 view authenticates the recovery execution (new generation, origin c, R's registry snapshot and the committee reselected under 4.3) and both the 8.4 origin-record and genesis checks and section 9 checkpoint trust pass."

**Why it matters.** Several checks are joined by "and": the recovery execution, the 8.4 origin record, the 8.4 genesis check, and section 9's checkpoint trust. They can pass at different times — for example, the origin record is readable as soon as `recover` executes, while checkpoint trust needs the latest checkpoint to be reachable in the node's own view. The text does not say whether signing waits for all of them (it says it does) or what a node does when one cannot be completed but the others pass, which is the practical case after a long halt.

**Would close it.** State that all checks are required, whether they are evaluated once at session start or continuously, and what the node does when one cannot be evaluated.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q8.2-4

**"Operational practice" leaves same-domain double signing without a protocol requirement**

**Text.** "Failover, fencing and similar protections against same-domain double signing are operational practice."

**Why it matters.** Read on its own (it sits inside RECOV-8.2-6), the sentence lets a deployment can conform to 8.2 while running two signers with the same key and no fencing. Section 4.1 can slash the resulting double sign after the fact, and section 1's finality argument assumes it does not happen, so the safety case depends on a practice the spec explicitly does not require. That is a defensible split, but it should be an explicit residual risk rather than an un-numbered aside.

**Would close it.** State that fencing is a deployment requirement checked at acceptance, or record it as an accepted residual risk in section 12 and say how it is monitored.

Raised by: DeepSeek-V4.1-Flash (dantaik)
