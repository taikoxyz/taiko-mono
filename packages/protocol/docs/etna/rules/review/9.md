## Q9-1

**Trust is established at one checkpoint and not re-earned when a newer one lands**

**Text.** "every app startup and signer session starts untrusted, authenticates the Inbox's latest checkpoint in its own L1 finalized view, and becomes trusted only after reaching that height with an exact match of both the EL hash and the CometBFT hash in the slot 285 record ...; after that, every anchor change checks the new lastCheckpoint per 3.4."

**Why it matters.** The trust target is fixed at session start, but a landing can advance the checkpoint between anchor changes. While the node remains "trusted" at the old height it can sign blocks the network will discard if a newer checkpoint already covers a different chain. The text also decides, without discussion, that there is "no age limit on the starting point": a node is untrusted until its own L1 view reaches the target, so a long L1-finality stall keeps every signer untrusted and the chain halted. That is a liveness consequence of a trust rule, and it is not stated as one.

**Would close it.** state whether trust is re-evaluated per signature or per anchor against the latest authenticated checkpoint, and what a signer does when a newer checkpoint lands while its trust target is older.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q9-2

**A failed check is not assigned to a halt category, and "halts it" names no component**

**Text.** SYNC-9-1 requires a cold-sync check of the anchor and `lastCheckpoint`; SYNC-9-3 says a non-descending history "is rejected by the EL (`-38002`), and the node halts for safety"; SYNC-9-7 says a contradiction "halts it for safety"; SYNC-9-8 says a parse failure "only means the node needs an upgrade".

**Why it matters.** The section says what is checked but not, for the cold-sync case, what happens when the check fails: reject the block and keep syncing, exit the process, or become untrusted and retry. The three observable behaviours differ, and the surrounding sentences support each of them. "Halts it for safety" also does not say whether the app, the signer or the supervisor exits — §8 defines a safety halt as the process exiting and needing manual investigation, but that is a different section.

**Would close it.** classify every failed check in 9 (sync witness, anchor age, `lastCheckpoint` mismatch, EL `-38002`, parse failure) as a liveness pause or a safety halt, and name the halting component.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q9-3

**The L1-node requirements are unbounded and their failure mode is unstated**

**Text.** "the own L1 node must return headers by number back to `L1_0` and serve the `eth_getProof` the trust check needs; a validator also needs historical `eth_getProof` and `debug_getRawHeader`".

**Why it matters.** `L1_0` is the Inbox's initialization block, so "back to `L1_0`" is an unbounded retention requirement for every node, and "historical" for validator proofs has no depth at all. There is also no failure classification: a node whose L1 provider has pruned state cannot satisfy the duty, but the text does not say whether it becomes untrusted (retry forever), pauses (section 8), or must use an archive provider. This is the kind of requirement that silently excludes commodity L1 nodes.

**Would close it.** state the required depth (or that an archive-mode L1 node is mandatory) and the failure class when the data is not available.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q9-4

**The sync modes listed may not be exhaustive**

**Text.** "during cold sync (replay or blocksync)".

**Why it matters.** State sync is a standard third way to obtain a chain and skips execution entirely. If a node can become trusted through state sync, the cold-sync revalidation in SYNC-9-1 never runs; if it cannot, the spec should say state sync is unsupported. The parenthetical reads as an exhaustive list but might be illustrative, and a reader cannot tell which.

**Would close it.** state whether state sync (or any other non-replay acquisition) is supported and, if so, what revalidation and trust steps replace replay/blocksync.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q9-5

**The supervisor cannot distinguish the refusal reasons it is required to distinguish**

**Text.** "After a signing request is refused for lack of trust or a timeout, the supervisor must therefore restart CometBFT automatically once trust returns ... safety halts (section 8), requests for an old generation and refusals at a 10.1 upgrade boundary do not trigger it."

**Why it matters.** The supervisor must restart for one class of refusal and never for two others, but the signer's refusal signal is not specified and "trust returns" is an app-internal state. If the supervisor restarts on a boundary refusal it defeats the upgrade gate; if it fails to restart on a trust refusal the height stalls, which the same paragraph says stalls indefinitely. Full nodes have no signer, so the rule's scope is also unclear.

**Would close it.** define the refusal reason the signer exposes and the supervisor's trigger, and say that the restart rule applies only to deployments with a signer.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q9-6

**"The app's trust status" has no defined representation**

**Text.** "Exchanges, bridges and public RPC must read the app's trust status, not raw CometBFT/EL sync progress or `catching_up`."

**Why it matters.** A consumer is told what not to read, but not what to read. There is no field, endpoint, or semantics for "trust status", so two apps can expose different things and both conform, and an exchange cannot integrate. Given SYNC-9-4/5 the natural content is the target height and both hashes, but that is an inference.

**Would close it.** specify the status fields and how they are queried (ABCI query, HTTP endpoint, metric), and whether the status is per generation.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q9-7

**The checkpoint fence is enforced through an EL error code that is not pinned**

**Text.** "a history that does not descend from that checkpoint is rejected by the EL (`-38002`), and the node halts for safety."

**Why it matters.** The observable trigger of the fence is an Engine API error, not a property the node checks itself. The spec pins "a pinned alethia-reth version" (3.1) but does not require that version to return `-38002` for this case, and does not say what a node does if the EL accepts the history. A node that copies the wording but connects to an EL that does not produce the error would satisfy the sentence while losing the fence.

**Would close it.** require the node to verify descent itself (and treat the EL error as a second line of defence), or pin the EL behaviour by version and acceptance test.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q9-8

**Which JSON-RPC block tags map to which Etna status**

**Text.** SYNC-9-3: "FinalizeBlock passes the `lastCheckpoint.hash` proven by the anchor to the EL's forkchoice as `finalized`". SYNC-9-15: "Exchanges, bridges and public RPC must read the app's trust status, not raw CometBFT/EL sync progress or `catching_up`." Section 1, Finality: "a CometBFT commit is final" while Byzantine voting power stays below 1/3, and "exchanges and bridges should rely on checkpoints".

**Why it matters.** Wallets, indexers, bridge relayers and RPC gateways read the standard `latest`, `safe` and `finalized` block tags, not the app's trust status. SYNC-9-3 fixes `finalized` to the anchor-proven checkpoint, which per the 6.4 latency arithmetic trails the committed head by about 900 blocks in normal operation. Nothing states what `safe` is, or whether `latest` can ever be a block that has not been committed. Two conforming nodes can serve different `safe` heads, and consumers cannot tell which status a tag carries.

**Would close it.** State the mapping for `latest`, `safe` and `finalized` on a trusted node (for example `latest` = `safe` = the last CometBFT-committed block, `finalized` = the anchor-proven `lastCheckpoint`), and what an untrusted node returns for each tag.

Raised by: Karim (kimo-ice)

## Q9-9

**A shared L1-client bug becomes a network-wide safety halt**

**Text.** COMP-2-1: a validator runs "its own L1 node". SYNC-9-7: "malformed or unverifiable data from its own L1 node or EL, halts it for safety, because the node cannot tell that apart from forgery". RECOV-8-13 lists "malformed or unverifiable data from the node's own L1 node or EL" as a cause of a safety halt.

**Why it matters.** The rule is right for one node, but nothing makes validators' L1 nodes independent: nothing prevents most of them from running the same L1 client implementation. A client bug that returns a wrong `eth_getProof` result or header would halt every validator on that client at once. If they hold 1/3 or more of the voting power, consensus stops (RECOV-8-20), and each node needs manual investigation (RECOV-8-12). ACCEPTANCE §4 bounds stake concentration per controller but not per L1 client implementation. The single pinned EL (CONS-3.1-11) carries the same correlated exposure by design, and that is not stated either.

**Would close it.** Either add a launch and monitoring requirement that no single L1 client implementation backs 1/3 or more of committee voting power, or list the correlated-halt risk (L1 clients and the single EL) in section 12 as an accepted limitation.

Raised by: Karim (kimo-ice)
