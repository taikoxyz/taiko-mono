## Q4.1-1

**Consequence of violating a registry requirement that names no outcome**

**Text.** STAKE-4.1-15 says "`topUp(bondId, amount)` is owner-only. Require an unreleased entry, current L1 block ≥ activeFromL1, effStake > 0, no exit set, no pending top-up, and amount > 0." STAKE-4.1-4 says a key "can be registered only once, ever". STAKE-4.1-36 says "Every L1 block that changes the entry in a slot ends with one checkpoint (l1Block, count, entriesRoot)".

**Why it matters.** The section names an outcome for some requirements — `requestExit` "reverts", `confirmExit`/`slashDoubleSign`/`forfeit` "fail" before initialization, "[a]ny failure rejects the entire registration" — but not for the owner-only rule, the second registration of a key, or a missing checkpoint. A violation could be a reverting call, a silent no-op, a proof-side rejection, or an off-chain refusal, and each is observationally different. Until this is settled, the vectors say "violates STAKE-4.1-X" rather than naming an outcome.

**Would close it.** State once whether every unmet condition in 4.1 makes the call revert with an error, and whether a missing or wrong checkpoint is a landing/validity failure or only a proof-side mismatch. Add the consequence to the specific rules that differ.

## Q4.1-2

**What is `activeFromL1`, and when does registration activation happen?**

**Text.** STAKE-4.1-2: "Activation occurs after activationDelay L1 blocks". STAKE-4.1-15 requires "current L1 block ≥ activeFromL1". STAKE-4.1-23 computes the exit effect at "max(current block + `exitDelay`, activeFromL1 + `exitDelay`)".

**Why it matters.** `activeFromL1` is used as an eligibility bound and as the origin of the exit delay, but it is never defined. If it is the registration block, `exitDelay` can expire before the entry is active; if it is the activation block, it cannot. "After activationDelay L1 blocks" also leaves the boundary block open (`b + d` or `b + d + 1`), and the text does not say whether activation is automatic or requires a call. These choices change when an entry can be selected and when its owner can exit.

**Would close it.** Define `activeFromL1` explicitly (for example, registration block + `activationDelay`), state that activation is automatic at that block with no separate call, and say whether the boundary is inclusive.

## Q4.1-3

**Is the 4096-slot cap a protocol rule or a deployment parameter?**

**Text.** STAKE-4.1-13a: "There are 4096 slots, numbered 0 to 4095." Section 12 item 11 repeats the capacity.

**Why it matters.** The registry is an upgradeable proxy and section 10 allows a new deployment with a new registry. If 4096 is a protocol rule, a 4097th slot is a violation; if it is a deployment parameter, a replacement may choose another number. The text states neither a consequence nor whether the cap is immutable, so an implementation cannot tell which changes are conforming.

**Would close it.** Mark 4096 as a consensus rule, an implementation constant, or a deployment parameter, and say whether an upgrade may change it.

## Q4.1-4

**How far does "registered only once, ever" reach?**

**Text.** STAKE-4.1-4: "Each key can be registered only once, ever, keyed by `ckAddr` and never released after withdrawal"

**Why it matters.** A replacement registry deployment starts with empty state. Does "ever" bind across deployments, or only within one registry's lifetime? If only within, the same key can be registered again in a new deployment, which changes the lifetime-uniqueness claim and the reach of the `entryKey` forfeiture flag in 4.4. The text does not say whether key identity is protocol-wide or deployment-local.

**Would close it.** Scope "ever" to a named registry deployment, or state that key identities persist across deployments and how a new registry would learn them.

## Q4.1-5

**What counts as "a block that changes the entry in a slot", and how many checkpoints?**

**Text.** STAKE-4.1-36: "Every L1 block that changes the entry in a slot ends with one checkpoint (l1Block, count, entriesRoot); changes to a bond that holds no slot write no checkpoint."

**Why it matters.** The text does not enumerate the operations that count as changing the entry in a slot (registration, top-up, activation, `requestExit`, `confirmExit`, `withdraw`, slashing, forfeiture, an exclusion-list forced exit), nor say whether a block that changes two entries writes one checkpoint or one per entry. The meaning of `count` — entries changed or total entries — is also unstated. These choices determine the witness layout and what a snapshot proof must show.

**Would close it.** List the operations that change the entry in a slot, state that one checkpoint is written per block regardless of how many entries change, and define `count`.

## Q4.1-7

**The bound that keeps the registry from filling depends on a supply figure and on where slashed tokens go**

**Text.** STAKE-4.1-14a: "Deployment requires 4096 × minStake > 10^27 base units, TAIKO's fixed total supply (4.3), so bonds that still hold the stake they registered with can never hold every slot". LIMIT-12-11: "Every slot can therefore be held only if tokens that double-sign slashing or forfeiture took from bonds still holding slots return to circulation and are staked again".

**Why it matters.** Three things follow from the bound and none has an owner decision yet. First, the admission threshold is at least 244,140.625 TAIKO per validator, which limits who can register; whether that is acceptable is a product decision, not a consequence the text can settle. Second, the bound is exact only while 10^27 is the whole supply the token contract can ever hold on L1; the spec cites 4.3 for the figure but states no check of the token contract at deployment. Third, a slashed or forfeited bond keeps its slot until it is withdrawn, and its tokens go to `slashSink` and the reporter, so the registry can still fill if those tokens are staked again. LIMIT-12-11 discloses this, but nothing bounds how many slots it can take or says whether `slashSink` may be an address that can re-stake. The cost of that case is highest while the chain is halted: an exit that took effect after activeCommitteeSnapshot cannot be confirmed without a landing, so even a zero-balance bond keeps its slot, only its owner can withdraw a bond that keeps a balance after forfeiture, and a governance recovery that needs new members can admit none unless the DAO upgrades the registry.

**Would close it.** confirm the threshold, state the deployment check that ties `minStake` to the token's actual maximum supply, and choose among: constraining `slashSink` (for example to an address that cannot stake) and raising the bound to 4096 × minStake × (10000 − `slashBountyBps`) > 10^27 × 10000, which makes a full registry impossible; letting a bond that can no longer be selected release its slot while it keeps its principal and its liability; letting anyone withdraw a zero-balance bond without a confirmed exit; or accepting the disclosed residual case explicitly.
