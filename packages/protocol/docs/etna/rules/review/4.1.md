## Q4.1-1

**Consequence of violating a registry requirement that names no outcome**

**Text.** STAKE-4.1-15 says "`topUp(bondId, amount)` is owner-only. Require an unreleased entry, current L1 block ≥ activeFromL1, effStake > 0, no exit set, no pending top-up, and amount > 0." STAKE-4.1-4 says a key "can be registered only once, ever". STAKE-4.1-36 says "Every L1 block that changes an entry ends with one checkpoint (l1Block, count, entriesRoot)."

**Why it matters.** The section names an outcome for some requirements — `requestExit` "reverts", `confirmExit`/`slashDoubleSign`/`forfeit` "fail" before initialization, "[a]ny failure rejects the entire registration" — but not for the owner-only rule, the second registration of a key, or a missing checkpoint. A violation could be a reverting call, a silent no-op, a proof-side rejection, or an off-chain refusal, and each is observationally different. Until this is settled, the vectors say "violates STAKE-4.1-X" rather than naming an outcome.

**Would close it.** State once whether every unmet condition in 4.1 makes the call revert with an error, and whether a missing or wrong checkpoint is a landing/validity failure or only a proof-side mismatch. Add the consequence to the specific rules that differ.

## Q4.1-2

**What is `activeFromL1`, and when does registration activation happen?**

**Text.** STAKE-4.1-2: "Activation occurs after activationDelay L1 blocks". STAKE-4.1-15 requires "current L1 block ≥ activeFromL1". STAKE-4.1-23 computes the exit effect at "max(current block + `exitDelay`, activeFromL1 + `exitDelay`)".

**Why it matters.** `activeFromL1` is used as an eligibility bound and as the origin of the exit delay, but it is never defined. If it is the registration block, `exitDelay` can expire before the entry is active; if it is the activation block, it cannot. "After activationDelay L1 blocks" also leaves the boundary block open (`b + d` or `b + d + 1`), and the text does not say whether activation is automatic or requires a call. These choices change when an entry can be selected and when its owner can exit.

**Would close it.** Define `activeFromL1` explicitly (for example, registration block + `activationDelay`), state that activation is automatic at that block with no separate call, and say whether the boundary is inclusive.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q4.1-3

**Is the 4096-slot cap a protocol rule or a deployment parameter?**

**Text.** STAKE-4.1-13: "There are 4096 slots in total, and the bond id is the slot." Section 11 repeats the capacity as "4096 × `minStake`".

**Why it matters.** The registry is an upgradeable proxy and section 10 allows a new deployment with a new registry. If 4096 is a protocol rule, a 4097th slot is a violation; if it is a deployment parameter, a replacement may choose another number. The text states neither a consequence nor whether the cap is immutable, so an implementation cannot tell which changes are conforming.

**Would close it.** Mark 4096 as a consensus rule, an implementation constant, or a deployment parameter, and say whether an upgrade may change it.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q4.1-4

**How far does "registered only once, ever" reach?**

**Text.** STAKE-4.1-4: "Each key can be registered only once, ever, keyed by `ckAddr` and never released after withdrawal."

**Why it matters.** A replacement registry deployment starts with empty state. Does "ever" bind across deployments, or only within one registry's lifetime? If only within, the same key can be registered again in a new deployment, which changes the lifetime-uniqueness claim and the reach of the `entryKey` forfeiture flag in 4.4. The text does not say whether key identity is protocol-wide or deployment-local.

**Would close it.** Scope "ever" to a named registry deployment, or state that key identities persist across deployments and how a new registry would learn them.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q4.1-5

**What counts as "a block that changes an entry", and how many checkpoints?**

**Text.** STAKE-4.1-36: "Every L1 block that changes an entry ends with one checkpoint (l1Block, count, entriesRoot)."

**Why it matters.** The text does not enumerate the operations that count as changing an entry (registration, top-up, activation, `requestExit`, `confirmExit`, `withdraw`, slashing, forfeiture, an exclusion-list forced exit), nor say whether a block that changes two entries writes one checkpoint or one per entry. The meaning of `count` — entries changed or total entries — is also unstated. These choices determine the witness layout and what a snapshot proof must show.

**Would close it.** List the operations that change an entry, state that one checkpoint is written per block regardless of how many entries change, and define `count`.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q4.1-6

**Are slot identifiers 0-based or 1-based?**

**Text.** STAKE-4.1-13: "There are 4096 slots in total, and the bond id is the slot."

**Why it matters.** The bond id is an external ABI value used by `topUp`, `activateTopUp`, `requestExit`, `confirmExit`, `withdraw`, `slashDoubleSign` and `forfeit`. If slots are numbered 0 ... 4095, the first bond id is 0; if they are numbered 1 ... 4096, it is 1. The text gives the count but not the base, and a client that guesses wrong addresses the wrong entry (or an empty slot) for every call.

**Would close it.** State the slot numbering base and the valid bond-id range.
