## Q4.1-1

**Consequence of violating a staking contract requirement that names no outcome**

**Text.** STAKE-4.1-15 says "`topUp(bondId, amount)` is owner-only. Require an issued, unwithdrawn bond with no exit set, and amount > 0." STAKE-4.1-4 says a key "can be registered only once, ever". STAKE-4.1-5 says "The staking contract stores only `ckPrefix = publicKey[0]` and the following 32-byte `ckX`".

**Why it matters.** The section names an outcome for some requirements — `requestExit` "reverts", an operation naming an unissued id "reverts without writing any state", the call that would give a bond a seat when none is empty "reverts", "[a]ny failure rejects the entire registration" — but not for the owner-only rule, the second registration of a key, or a storage requirement such as STAKE-4.1-5. A violation could be a reverting call, a silent no-op or an off-chain refusal, and each is observationally different. Until this is settled, the vectors say "violates STAKE-4.1-X" rather than naming an outcome.

**Would close it.** State once whether every unmet condition in 4.1 makes the call revert with an error, and say what a contract state that breaks a storage requirement means. Add the consequence to the specific rules that differ.

## Q4.1-4

**How far does "registered only once, ever" reach?**

**Text.** STAKE-4.1-4: "Each key can be registered only once, ever, keyed by `ckAddr` and never released after withdrawal"

**Why it matters.** An upgrade of the staking contract proxy keeps its state, but a replacement deployment at a new address starts with empty state. Does "ever" bind across deployments, or only within one staking contract's lifetime? If only within, the same key can be registered again in a new deployment, which changes the lifetime-uniqueness claim. The text does not say whether key identity is protocol-wide or deployment-local.

**Would close it.** Scope "ever" to a named staking contract deployment, or state that key identities persist across deployments and how a new deployment would learn them.
