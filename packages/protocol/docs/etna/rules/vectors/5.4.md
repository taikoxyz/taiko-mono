# 5.4 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). These vectors specify authenticated app checkpoint import from a landed validator state and a bounded window, without pre-s EL execution, followed by stock CometBFT continuation. Deployment details are in [review/5.4.md](../review/5.4.md).

Operational labels `retry`, `reject candidate` and `safety halt` name the expected failure-handling outcome. The other `accept`/`reject` labels identify positive/negative conformance cases; they do not by themselves mean that an import succeeds or a candidate is rejected. The Expected column states the required behavior.

## DATA-5.4-1

| Vector     | Setup                                                                                                                                     | Expected                             |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| 1.a accept | s > current origin; own finalized L1 authenticates generation, EL state, same-generation Comet hash and the record's validator-state hash | conforms to DATA-5.4-1               |
| 1.b accept | s equals recovery origin; existing fixed-genesis path uses its old Comet hash only as proving boundary                                    | conforms to DATA-5.4-1               |
| 1.c reject | checkpoint from another generation is used as this generation’s Comet state                                                               | violates DATA-5.4-1                  |
| 1.d reject | same-domain InitialHeight is reset to s+1                                                                                                 | violates DATA-5.4-1 and RECOV-8.4-15 |
| 1.e accept | the generation has years of history below s; the node imports at s without reading any Comet block below the DATA-5.4-2 window            | conforms to DATA-5.4-1               |

## DATA-5.4-3

| Vector     | Setup                                                                                                                                                                                                                  | Expected                                                    |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| 3.a accept | the preimage hashes to s's landed validator-state hash, its s + 1 set matches header(s)'s next_validators_hash, and both sets match a full replay's members, powers, proposer priorities and stored proposers          | conforms to DATA-5.4-3                                      |
| 3.b reject | validator hashes match but the proposer priorities or stored proposer of the s + 1 or s + 2 set come from an unverified database or an RPC answer                                                                      | violates DATA-5.4-3                                         |
| 3.c reject | missing window validator/parameter history makes an otherwise valid post-s evidence item unverifiable                                                                                                                  | violates DATA-5.4-3                                         |
| 3.d reject | previously committed evidence inside the window is accepted again because committed-evidence markers were not rebuilt                                                                                                  | violates DATA-5.4-3                                         |
| 3.e accept | import derives metadata without any pre-s EVM execution, FI trial, normal FinalizeBlock or block below the window                                                                                                      | conforms to DATA-5.4-3                                      |
| 3.f reject | the app's pending committee for s + 2 differs from the keys and powers of the preimage's s + 2 set                                                                                                                     | violates DATA-5.4-3; safety halt and alert under DATA-5.4-5 |
| 3.g accept | proposer priorities stored for window heights at or below s differ from a full replay's, while the s + 1 and s + 2 sets match                                                                                          | conforms to DATA-5.4-3 ("not consensus inputs")             |
| 3.h reject | s = S(t); the importer sets the stored proposer of the s + 2 set to its lowest-priority member, a newly added one that differs from CometBFT's stored proposer, as stock state sync would, instead of the landed index | violates DATA-5.4-3                                         |
| 3.i accept | the FI cursor is taken from s's slot 285 record                                                                                                                                                                        | conforms to DATA-5.4-3                                      |
| 3.j reject | the window holds a validator-set checkpoint height that stock storage expects a full set at, but the importer stores only a pointer there, so CometBFT's lookup fails for a later window height                        | violates DATA-5.4-3                                         |
