# 8.2 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). This file states only what the text states: each vector either follows from an enumerated condition, or reports that a requirement was violated. Where the text states a requirement but **not the consequence of violating it**, the vector says "violates <ID>" and does not name an outcome. Anything undetermined has no vector; it is listed under "Not covered" and raised in [review/8.2.md](../review/8.2.md).

`accept` means the described signer configuration or signing decision satisfies the rules cited. These rules bind the signer, not the chain, so most violations have no on-chain rejection; the consequence is the review question cited.

## RECOV-8.2-1

| Vector     | Setup                                                                                                                           | Expected             |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| 1.a accept | separate HRS state per full `chain_id`; each signature persisted before it is returned; the state is never reset or rolled back | conforms             |
| 1.b reject | one HRS state shared across chain ids                                                                                           | violates RECOV-8.2-1 |
| 1.c reject | a signature is returned before it is persisted                                                                                  | violates RECOV-8.2-1 |
| 1.d reject | the HRS state is rolled back after a restart                                                                                    | violates RECOV-8.2-1 |

## RECOV-8.2-2

| Vector     | Setup                                                     | Expected             |
| ---------- | --------------------------------------------------------- | -------------------- |
| 2.a accept | the key exists only in the signer that owns the HRS state | conforms             |
| 2.b reject | a copy of the key signs outside that state                | violates RECOV-8.2-2 |

## RECOV-8.2-3

| Vector     | Setup                                                             | Expected                                                       |
| ---------- | ----------------------------------------------------------------- | -------------------------------------------------------------- |
| 3.a accept | the HRS state is lost, or its latest value is uncertain           | stop signing                                                   |
| 3.b reject | the state is deleted and signing resumes                          | violates RECOV-8.2-3 ("deleting state cannot restore service") |
| 3.c accept | an operator restores service by a means other than deleting state | consistent with the stated prohibition                         |

## RECOV-8.2-4

| Vector     | Setup                                                                                                                                                            | Expected             |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| 4.a accept | signing for a new generation starts only after the own finalized L1 view authenticates the recovery, both 8.4 checks pass, and section 9 checkpoint trust passes | conforms             |
| 4.b reject | a new-generation signature is produced before the L1 view authenticates the recovery                                                                             | violates RECOV-8.2-4 |
| 4.c reject | signing starts while the 8.4 origin-record or genesis check fails                                                                                                | violates RECOV-8.2-4 |

## RECOV-8.2-5

| Vector     | Setup                                                                                                             | Expected             |
| ---------- | ----------------------------------------------------------------------------------------------------------------- | -------------------- |
| 5.a accept | the new generation's HRS state starts at c + 1; after authentication, old-generation signing requests are refused | conforms             |
| 5.b reject | old-generation signing continues after authentication                                                             | violates RECOV-8.2-5 |
| 5.c reject | the new generation's HRS state starts at a height other than c + 1                                                | violates RECOV-8.2-5 |

## RECOV-8.2-6

| Vector     | Setup                                                        | Expected             |
| ---------- | ------------------------------------------------------------ | -------------------- |
| 6.a accept | the same height is signed in two different generations       | not a double sign    |
| 6.b reject | cross-generation votes are submitted as double-sign evidence | violates RECOV-8.2-6 |
