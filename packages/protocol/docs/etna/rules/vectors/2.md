# 2 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). Section 2 is a component table, so a vector describes a deployment's component and asks whether it matches its row. `accept` means it does; `reject` means the row is contradicted. No block is accepted or rejected by these vectors, and no enforcement consequence is implied where the text states none. Gaps are in [review/2.md](../review/2.md).

## COMP-2-1

| Vector     | Setup                                                                                                                                                                                                                                           | Expected                                                                          |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 1.a accept | a validator stakes TAIKO, registers a secp256k1eth consensus key with a key-holder signature, and runs stock CometBFT, the ABCI application, alethia-reth and its own L1 node, plus the external FilePV signer behind the checkpoint-trust gate | matches the Validator row                                                         |
| 1.b reject | the same validator registers without a key-holder signature                                                                                                                                                                                     | violates COMP-2-1 ("with a key-holder signature")                                 |
| 1.c reject | the registered signing key or the anti-double-sign state is stored inside the Comet home/mount                                                                                                                                                  | violates COMP-2-1 ("stay outside the Comet home/mount")                           |
| 1.d reject | a signature is produced without the app's checkpoint-trust authorization                                                                                                                                                                        | violates COMP-2-1 ("signatures require the app's checkpoint-trust authorization") |
| 1.e accept | the proposer receives all base fees and tips of the blocks it produces                                                                                                                                                                          | conforms to COMP-2-1                                                              |

_Whether every clause of the row is mandatory for a validator, or only descriptive of a reference implementation: no vector — [Q2-1](../review/2.md#q2-1)._

## COMP-2-2

**Retired.** The unconditional every-block execution obligation is replaced by COMP-2-2b, which admits authenticated checkpoint import.

## COMP-2-2a

| Vector      | Setup                                                                                                                                                 | Expected                          |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| 2a.a accept | an EL-only backend imports finalized-landed execution blocks and serves chain/state data no higher than its last locally matched finalized checkpoint | conforms to COMP-2-2a             |
| 2a.b reject | the EL-only backend imports an unlanded execution block                                                                                               | violates COMP-2-2a                |
| 2a.c reject | the backend serves chain/state data above its last locally matched finalized checkpoint                                                               | violates COMP-2-2a                |
| 2a.d reject | EL-only synchronization progress is used to grant app checkpoint trust or signing authority                                                           | violates COMP-2-2a and DATA-5.3-7 |

## COMP-2-2b

| Vector      | Setup                                                                                                                             | Expected              |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------- | --------------------- |
| 2b.a accept | full node runs the required stack, has no registered signing key, replays from fixed genesis and validates each block             | conforms to COMP-2-2b |
| 2b.b accept | full node imports a verified 5.4 prefix then independently validates every subsequent block and applies the checkpoint-trust gate | conforms to COMP-2-2b |
| 2b.c reject | full node trusts an arbitrary publisher state or skips validation above its authenticated starting point                          | violates COMP-2-2b    |
| 2b.d reject | full node grants trust without the checkpoint-trust gate or votes using a registered signing key                                  | violates COMP-2-2b    |

## COMP-2-3

| Vector     | Setup                                                                                                          | Expected                                       |
| ---------- | -------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| 3.a accept | anyone reads decided blocks/commits, builds batches, obtains two proofs and calls `land` in a blob transaction | matches the Lander row                         |
| 3.b reject | landing is restricted to an allowlisted set of addresses                                                       | violates COMP-2-3 ("Permissionless")           |
| 3.c reject | a lander receives a protocol reward                                                                            | violates COMP-2-3 ("earns no protocol reward") |
| 3.d accept | a lander earns nothing from the protocol for a successful landing                                              | conforms                                       |

_Whether "earns no protocol reward" is a present economic fact or a rule that a future reward must not change: no vector — [Q2-4](../review/2.md#q2-4)._

## COMP-2-6

| Vector     | Setup                                                                                                                                                                                                                                  | Expected                                                                                 |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 6.a accept | the registry handles stake and delayed top-ups, exits, withdrawals, double-sign slashing, DAO responsibility forfeiture and exclusion-list forced exits, and writes one checkpoint for every L1 block that changes the entry in a slot | matches the EtnaStakingRegistry row                                                      |
| 6.b reject | an L1 block changes the entry in a slot and no checkpoint is written                                                                                                                                                                   | violates COMP-2-6 ("one checkpoint for every L1 block that changes the entry in a slot") |
| 6.c reject | one L1 block that changes the entry in a slot writes two checkpoints                                                                                                                                                                   | violates COMP-2-6 ("one checkpoint for every L1 block")                                  |
| 6.d reject | an exclusion-list forced exit is not available through the registry                                                                                                                                                                    | violates COMP-2-6 ("exclusion-list forced exits")                                        |
| 6.e accept | an L1 block only slashes a displaced bond and writes no checkpoint                                                                                                                                                                     | no slot entry changes; conforms to COMP-2-6 and STAKE-4.1-36                             |

_Whether "one checkpoint" is one per changing block or one per changed entry: no vector — [Q2-4](../review/2.md#q2-4)._
