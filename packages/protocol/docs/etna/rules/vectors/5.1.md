# 5.1 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). Each vector follows from the stated envelope format or commitment rule, or reports that a requirement was violated. Where the text states a requirement but not the consequence of violating it, the vector says "violates <ID>". Gaps are in [review/5.1.md](../review/5.1.md).

`accept` means the described CometBFT block or envelope satisfies the rule cited. `reject` means a stated requirement is violated.

## DATA-5.1-1

| Vector     | Setup                                                                                                                                                                      | Expected                                        |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| 1.a accept | the block's single transaction is the `0x06` prefix followed by `rlp([block, anchor, committee, forced])`; anchor, committee and forced are each empty or exactly one item | conforms to DATA-5.1-1                          |
| 1.b accept | anchor, committee and forced are all empty lists                                                                                                                           | conforms                                        |
| 1.c accept | each of the three holds exactly one item                                                                                                                                   | conforms                                        |
| 1.d reject | the prefix is not `0x06`, or the item after it is not one RLP list                                                                                                         | violates DATA-5.1-1                             |
| 1.e reject | anchor, committee or forced holds two or more items                                                                                                                        | violates "empty list or exactly one item"       |
| 1.f reject | the block carries two transactions, or none                                                                                                                                | violates "the single tx in each CometBFT block" |

_Whether a pause placeholder or a zero-execution-transaction block still carries the envelope: no vector — [Q5.1-2](../review/5.1.md#q51-2)._

## DATA-5.1-2

| Vector     | Setup                                                                                | Expected               |
| ---------- | ------------------------------------------------------------------------------------ | ---------------------- |
| 2.a accept | the CometBFT header's `data_hash` commits to the envelope transaction                | conforms to DATA-5.1-2 |
| 2.b reject | the header commits to different bytes, or the envelope is not covered by `data_hash` | violates DATA-5.1-2    |

## DATA-5.1-3

| Vector     | Setup                                                                    | Expected                                                                                                |
| ---------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| 3.a accept | the envelope propagates on the consensus network and is absent from L1   | conforms to DATA-5.1-3                                                                                  |
| 3.b reject | the envelope or its private witnesses are published in an L1 transaction | violates "never goes to L1"; whether this is a rule or a design fact — [Q5.1-1](../review/5.1.md#q51-1) |
