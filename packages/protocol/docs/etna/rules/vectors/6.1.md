# 6.1 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). This file states only what the text states: each vector either follows directly from an enumerated condition, or reports that a requirement was violated together with the outcome the text gives for it. Where the text states a requirement but **not the consequence of violating it**, the vector says "violates <ID>" and does not name an outcome — inventing one would lock in an interpretation nobody decided. Anything you cannot determine has no vector; it is listed under "Not covered" and raised in [review/6.1.md](../review/6.1.md).

`accept` means the described landing satisfies the rules cited. `reject` means a stated requirement is violated. LAND-6.1-10 makes the checks in the reference Solidity normative, and that listing writes each check as a `require`, rejects an already settled target "without mutation" and states "any failure reverts everything"; so a landing that fails a check reads `violates <ID>; land reverts (LAND-6.1-10)`, and it changes no state (LAND-6.1-11). A reject that describes an implementation departing from the rules (omitting or reordering a check, gating the call, writing partial state) has no landing to reject and reads only "violates <ID>". Notation used throughout: `K` is the grid interval, `p` the proof origin, `c` the latest checkpoint height at execution and `h` the terminal height of the landing.

## LAND-6.1-1

| Vector     | Setup                                                                    | Expected                                                                                              |
| ---------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| 1.a accept | a fresh EOA with no role, bond or allowlist sends a valid landing        | accepted — permissionless                                                                             |
| 1.b accept | the same transaction is sent by the current checkpoint's previous lander | accepted — no privileged submitter                                                                    |
| 1.c reject | the call is gated behind an allowlist, bond or role                      | violates LAND-6.1-1 ("permissionless")                                                                |
| 1.d reject | the call carries nonzero `msg.value`                                     | violates LAND-6.1-1 ("nonpayable"); land reverts (LAND-6.1-10): the reference `land` is not `payable` |

| Vector     | Setup                                                                     | Expected                                                                               |

| 5.a accept | `p=300`, `h=309`, `K=3`                                                   | accepted; both are grid points                                                         |

## LAND-6.1-6

The enumeration is a statement about which checks exist, so its vectors are conformance checks on an implementation rather than on a landing.

| Vector     | Setup                                                                                                                                            | Expected                                                |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------- |
| 6.a accept | a landing that passes every enumerated group: range, grid and origin record; leaves; FI head; reference block and blobs; cutHash and both proofs | accepted                                                |
| 6.b reject | a landing is accepted without verifying both proofs                                                                                              | violates LAND-6.1-6 (proof verification is in the list) |
| 6.c reject | a landing is accepted without the FI-head advance check                                                                                          | violates LAND-6.1-6                                     |
| 6.d reject | the leaf set is accepted without checking the leaf at `c`                                                                                        | violates LAND-6.1-6 (and LAND-6.1-8)                    |

| 8.c reject          | `c`'s height and EL hash match but the Comet hash differs                             | violates LAND-6.1-8; land reverts (LAND-6.1-10), before proof verification (LAND-6.1-12) |

## LAND-6.1-10

This rule is about the specification's own text: it fixes where the checks are listed and gives them force. Its vectors are therefore about an implementation matching the toggle.

| Vector      | Setup                                                                                                | Expected                                                                                                                            |
| ----------- | ---------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 10.a accept | the implementation performs every check in the toggle, with the same outcomes                        | conforms                                                                                                                            |
| 10.b reject | the implementation omits a check that appears only in the toggle (for example the `h < 2**48` bound) | violates LAND-6.1-10 ("the checks are normative"); how that sits with the code-block convention is [Q6.1-1](../review/6.1.md#q61-1) |
| 10.c reject | the implementation performs a check that the toggle does not list                                    | violates LAND-6.1-10 ("lists every check land performs")                                                                            |

## LAND-6.1-13

| Vector      | Setup                                                                                      | Expected                                                                                         |
| ----------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| 13.a accept | `land(LandInput, leaves, proof)` with the eight named fields and no others                 | conforms                                                                                         |
| 13.b reject | a ninth field is added to `LandInput`                                                      | violates LAND-6.1-13 ("eight fields")                                                            |
| 13.c reject | `cutLeaf` or `cutHash` is encoded differently from appendix A                              | violates LAND-6.1-13 (the encodings are the interface)                                           |
| 13.d reject | the leaves and cutHash are computed with a different `K` from the one the deployment fixed | violates LAND-6.1-13 (`K` is part of the interface, so both sides must use the deployment's `K`) |

`K`'s value is a deployment choice under section 11 ("Not fixed yet"); "part of the interface" means the guest, the Inbox and the lander must agree on the same `K` for a deployment, not that one value is global.
