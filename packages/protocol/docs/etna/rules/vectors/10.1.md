# 10.1 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md); canonical plan, proof-routing and migration definitions are in [UPGRADES.md](../../UPGRADES.md). Vectors exercise the owner-requested timestamp/checkpoint distinction and its stated checks. `reject` names an explicit rejection where specified; otherwise it reports a violated requirement.

## START-10.1-1

| Vector     | Setup                                                                                   | Expected                 |
| ---------- | --------------------------------------------------------------------------------------- | ------------------------ |
| 1.a accept | an ordinary EL fork uses each block timestamp without stopping or settling exactly at T | conforms                 |
| 1.b accept | a structural upgrade settles exactly through H and activates H+1 afterward              | conforms                 |
| 1.c reject | a structural upgrade signs new-rule H+1 before H settlement/activation                  | violates START-10.1-1    |
| 1.d accept | either upgrade incurs downtime when required material is unavailable                    | no zero-downtime promise |

## START-10.1-2

| Vector     | Setup                                                                                           | Expected              |
| ---------- | ----------------------------------------------------------------------------------------------- | --------------------- |
| 2.a accept | an operational restart retains identical rule/structure/statement commitments and all HRS state | conforms              |
| 2.b reject | a binary change alters validity but is labelled only an operational restart                     | violates START-10.1-2 |
| 2.c reject | same-domain signed state is discarded during restart                                            | violates START-10.1-2 |

## START-10.1-3

| Vector     | Setup                                                                                        | Expected                                          |
| ---------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| 3.a accept | a deployment-immutable/domain/Comet-genesis change uses a separately authenticated migration | conforms                                          |
| 3.b reject | a timestamp plan changes K, signing domain or fixed Comet consensus params                   | violates START-10.1-3 and ordinary classification |
| 3.c reject | a structural plan is used to bypass an immutable parameter                                   | violates START-10.1-3                             |

## START-10.1-4

| Vector     | Setup                                                                              | Expected                                             |
| ---------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 4.a accept | canonical plan binds all declared fields, manifest and exact verifier/image policy | conforms                                             |
| 4.b reject | an ordinary plan changes structure, adapter or K                                   | installation reverts under the normative plan checks |
| 4.c reject | structural H is not divisible by both oldK and newK                                | installation reverts                                 |
| 4.d accept | H satisfies both grids and the unchanged U/maxBatch constraints                    | conforms                                             |
| 4.e reject | plan ABI has trailing bytes or a truncated field                                   | installation reverts                                 |

## START-10.1-5

| Vector     | Setup                                                                                                           | Expected                                   |
| ---------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| 5.a accept | the actual owner installs a plan with matching nonce/head/generation and authenticated manifest/code identities | conforms                                   |
| 5.b reject | only an off-chain manifest or operator agreement authorizes the fork                                            | violates START-10.1-5                      |
| 5.c reject | caller, expected nonce/head/generation or manifest commitment mismatches                                        | installation reverts                       |
| 5.d reject | T equals installation timestamp plus maxAnchorAge                                                               | installation reverts; inequality is strict |
| 5.e accept | T is one second above the lead bound and all other checks pass                                                  | eligible for installation                  |
| 5.f reject | H is below c+U or checked arithmetic overflows                                                                  | installation reverts                       |
| 5.g accept | H equals c+U and both K grids and all bounds pass                                                               | eligible for preparation                   |
| 5.h reject | a later T precedes an inherited future timestamp trigger                                                        | installation reverts                       |
| 5.i reject | another plan is installed while a structural plan is pending                                                    | installation reverts                       |

## START-10.1-6

| Vector     | Setup                                                                    | Expected                      |

## START-10.1-7

## START-10.1-8

| Vector     | Setup                                                                                                         | Expected                                |

| 8.b reject | c<H, c>H, a hash mismatches or the plan is cancelled/stale                                                    | activation reverts                      |
| 8.c reject | a migration call or exact staticcall assertion fails                                                          | the entire governance operation reverts |

| 8.f reject | migration changes protected checkpoint/genesis/FI/committee invariants                                        | activation reverts                      |

## Not covered

No unresolved design question is recorded here after this amendment. Required runtime implementation, real-proof capacity and deployment evidence remain subject to [upgrade acceptance](../../ACCEPTANCE.md#upgrade-activation-spec-101); these prose vectors do not establish that acceptance.
