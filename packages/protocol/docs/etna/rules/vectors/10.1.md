# 10.1 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). `accept` means the setup satisfies the cited requirement; `reject` identifies its violation, without inventing an unstated runtime consequence. These are written vectors, not executed client, contract or guest tests.

The height-only rules START-10.1-1, -4, -7, -8, -11 and -12 are retired in [INDEX.md](../INDEX.md); their suffix replacements below govern timestamp activation.

## START-10.1-1a

| Vector      | Setup                                                                                     | Expected                                                             |
| ----------- | ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 1a.a accept | A compatible rule upgrade is prepared and production/settlement continue across T         | requirement satisfied; no mandatory stop or pre-T settlement barrier |
| 1a.b accept | Operators choose downtime while preserving the plan                                       | no zero-downtime guarantee is violated                               |
| 1a.c reject | The protocol makes settlement of the pre-T prefix a prerequisite for timestamp activation | violates START-10.1-1a                                               |

## START-10.1-8a

| Vector      | Setup                                                                                                                       | Expected                                                                                                                         |
| ----------- | --------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 8a.a accept | Block timestamp is T-1; proof/submission happen after T                                                                     | V1 applies                                                                                                                       |
| 8a.b accept | Block timestamp is exactly T                                                                                                | V2 applies                                                                                                                       |
| 8a.c accept | Parent timestamp is T-2 and child timestamp is T+3; no block exists at T                                                    | V2 applies to the child; prescribed transition runs once before its ordinary execution                                           |
| 8a.d reject | The guest accepts a V1-valid but V2-invalid post-T block because either revision may pass                                   | block invalid under V2; ProcessProposal rejects and neither guest may accept it                                                  |
| 8a.e reject | L1 inclusion time, local wall clock or proof creation time selects the revision                                             | violates START-10.1-8a                                                                                                           |
| 8a.f accept | First V2 block has a V1 parent and an FI singleton trial                                                                    | V2 block rules/context apply after the same block-start transition on independent copies of the actual parent state              |
| 8a.g reject | The first V2 FI trial instead uses V1 rules because its parent is V1                                                        | violates START-10.1-8a                                                                                                           |
| 8a.h reject | A later V2 block repeats the transition already applied by the first V2 block                                               | violates START-10.1-8a                                                                                                           |
| 8a.i reject | A transition funds the FI sender, but the singleton trial uses the pre-transition insufficient balance and justifies a skip | violates START-10.1-8a; if the completed post-transition singleton contains the transaction, the skip is invalid under FI-7.2-10 |
| 8a.j reject | A transition changes the FI sender's nonce, but the singleton trial uses the old nonce                                      | violates START-10.1-8a                                                                                                           |
| 8a.k reject | A transition replaces system-contract code, but the singleton trial executes the old code                                   | violates START-10.1-8a                                                                                                           |
| 8a.l reject | A singleton trial mutates the committed parent or a second trial reapplies the transition to its already transitioned state | violates START-10.1-8a                                                                                                           |
| 8a.m reject | Nodes and guests use different transition ordering or gas/zk-gas accounting                                                 | violates START-10.1-8a                                                                                                           |

## START-10.1-9a

| Vector      | Setup                                                                                                      | Expected                                                                 |
| ----------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 9a.a accept | The node supports V2 but its L1 node has not yet exposed finalized preparation; a post-T proposal arrives  | ProcessProposal returns REJECT; a checkpoint-trusted nil vote is allowed |
| 9a.b accept | The same otherwise valid block is decided while local preparation evidence remains unavailable             | FinalizeBlock waits and retries; no safety halt from absence alone       |
| 9a.c accept | Preparation becomes authenticated and all ordinary block checks pass                                       | FinalizeBlock completes without reclassifying the block                  |
| 9a.d reject | A missing preparation record is classified as a deterministic invalid-block error                          | violates START-10.1-9a                                                   |
| 9a.e reject | An anchor witness is treated as proof of preparation without the separate authorized evidence              | violates START-10.1-9a                                                   |
| 9a.f accept | Both guests enforce the same authorized upgrade schedule; two nodes observe preparation at different times | local readiness differences do not change the guests' validity result    |
| 9a.g reject | A node signs a nil vote without checkpoint trust                                                           | violates SYNC-9-10 and SYNC-9-11; readiness does not bypass trust        |
| 9a.h accept | Required preparation is absent or unfinalized when preparing a post-T proposal                             | PrepareProposal uses section 8's pause behavior                          |
