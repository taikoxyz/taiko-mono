# 10.1 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). `accept` means the setup satisfies the cited requirement; `reject` identifies its violation, without inventing an unstated runtime consequence. These are written vectors, not executed client, contract or guest tests.

The height-only rules START-10.1-1, -4, -7, -8, -11 and -12 are retired in [INDEX.md](../INDEX.md); their suffix replacements below govern timestamp activation.

## START-10.1-1a

| Vector      | Setup                                                                                     | Expected                                                             |
| ----------- | ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 1a.a accept | A compatible rule upgrade is prepared and production/settlement continue across T         | requirement satisfied; no mandatory stop or pre-T settlement barrier |
| 1a.b accept | Operators choose downtime while preserving the plan                                       | no zero-downtime guarantee is violated                               |
| 1a.c reject | The protocol makes settlement of the pre-T prefix a prerequisite for timestamp activation | violates START-10.1-1a                                               |

## START-10.1-2

| Vector     | Setup                                                                                                      | Expected              |
| ---------- | ---------------------------------------------------------------------------------------------------------- | --------------------- |
| 2.a accept | A restart preserves the authenticated schedule, all validity rules and same-domain HRS                     | requirement satisfied |
| 2.b reject | A restart deletes HRS                                                                                      | violates START-10.1-2 |
| 2.c reject | A replacement changes a future activation or a validity rule but is treated only as an operational restart | violates START-10.1-2 |

| 3.b reject | The timestamp plan changes K and relies only on dual-version guests                                        | violates START-10.1-3 |
| 3.c reject | The timestamp plan changes an initialization-only parameter or fixed CometBFT consensus parameter          | violates START-10.1-3 |

| 5.a accept | The actual DAO/timelock authorizes a schedule bound by accepted images or an authenticated commitment enforced by L1 | requirement satisfied |

## START-10.1-7a

## START-10.1-8a

| Vector      | Setup                                                                                     | Expected                                                                               |
| ----------- | ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 8a.a accept | Block timestamp is T-1; proof/submission happen after T                                   | V1 applies                                                                             |
| 8a.b accept | Block timestamp is exactly T                                                              | V2 applies                                                                             |
| 8a.c accept | Parent timestamp is T-2 and child timestamp is T+3; no block exists at T                  | V2 applies to the child; prescribed transition runs once before its ordinary execution |
| 8a.d reject | The guest accepts a V1-valid but V2-invalid post-T block because either revision may pass | block invalid under V2; ProcessProposal rejects and neither guest may accept it        |
| 8a.e reject | L1 inclusion time, local wall clock or proof creation time selects the revision           | violates START-10.1-8a                                                                 |
| 8a.f accept | First V2 block has a V1 parent and an FI singleton trial                                  | V2 block rules/context apply on the actual parent state                                |
| 8a.g reject | The first V2 FI trial instead uses V1 rules because its parent is V1                      | violates START-10.1-8a                                                                 |
| 8a.h reject | A later V2 block repeats the transition already applied by the first V2 block             | violates START-10.1-8a                                                                 |

## START-10.1-9

| Vector     | Setup                                                                                                                                 | Expected              |

| 9.a accept | L1 preparation is finalized and authenticated before post-T signing; both subproofs in every allowed combination enforce the schedule | requirement satisfied |

## START-10.1-10

| Vector      | Setup                                                                                                       | Expected               |
| ----------- | ----------------------------------------------------------------------------------------------------------- | ---------------------- |
| 10.a accept | An unready node stops unsupported signing, preserves HRS and repairs software without changing the schedule | requirement satisfied  |
| 10.b reject | A signed post-T block is reclassified as V1 by moving T                                                     | violates START-10.1-10 |
| 10.c reject | A software rollback restores V1-only behavior after T or rewinds signer state                               | violates START-10.1-10 |

| Vector       | Setup                                                                                                                   | Expected                                                            |

## START-10.1-14

| Vector      | Setup                                                                                                   | Expected                                          |
| ----------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| 14.a accept | A pre-T historical block is replayed after T                                                            | its original V1 rules still apply                 |
| 14.b reject | A new image executes pre-T history under V2 because replay occurs after T                               | violates START-10.1-14                            |
| 14.c accept | Recovery authenticates the inherited schedule for the new generation and produces a block at or after T | V2 applies; settled-prefix rules remain unchanged |

| 14.e reject | Recovery-origin state already reflects the transition but the transition runs again                     | violates START-10.1-14                            |

## START-10.1-15

| Vector      | Setup                                                                                                                                                      | Expected               |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------- |
