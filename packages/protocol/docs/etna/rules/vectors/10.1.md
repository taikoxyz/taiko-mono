# 10.1 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md); canonical plan, proof-routing and migration definitions are in [UPGRADES.md](../../UPGRADES.md). Vectors exercise the timestamp/checkpoint distinction and its stated checks. `reject` names an explicit rejection where specified; otherwise it reports a violated requirement.

## START-10.1-1

| Vector     | Setup                                                                                                    | Expected                                                                                      |
| ---------- | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 1.a accept | an ordinary EL fork uses each block timestamp without stopping or settling exactly at T                  | conforms                                                                                      |
| 1.b accept | a structural upgrade settles exactly through H and activates H+1 afterward                               | conforms                                                                                      |
| 1.c reject | a structural upgrade signs H+1 while its same-generation fence is authenticated live at the cited anchor | signature refused; ProcessProposal rejects; a decided violation safety-halts (START-10.1-7/8) |
| 1.d accept | either upgrade incurs downtime when required material is unavailable                                     | no zero-downtime promise                                                                      |

## START-10.1-5

| Vector     | Setup                                                                                                           | Expected                                                        |
| ---------- | --------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| 5.a accept | the actual owner installs a plan with matching nonce/head/generation and authenticated manifest/code identities | conforms                                                        |
| 5.b reject | only an off-chain manifest or operator agreement authorizes the fork                                            | violates START-10.1-5                                           |
| 5.c reject | caller, expected nonce/head/generation or manifest commitment mismatches                                        | installation reverts                                            |
| 5.d reject | T equals installation timestamp plus maxAnchorAge                                                               | installation reverts; inequality is strict                      |
| 5.e accept | T = now+maxAnchorAge+1, T<=now+maxTimestampLead and all other checks pass                                       | eligible for installation                                       |
| 5.f reject | H is below c+U or checked arithmetic overflows                                                                  | installation reverts                                            |
| 5.g accept | H=highestCheckpoint[g]+U is within current c+maxStructuralLead, both grids and all bounds                       | eligible installation (START-10.1-5)                            |
| 5.h reject | a timestamp plan is installed while another timestamp remains pending                                           | installation reverts (START-10.1-5)                             |
| 5.i reject | another validity-changing plan is installed while a structural plan is pending                                  | installation reverts (START-10.1-5)                             |
| 5.j reject | T exceeds now+maxTimestampLead (including a milliseconds-as-seconds value outside that bound)                   | installation reverts (START-10.1-5)                             |
| 5.k accept | T equals now+maxTimestampLead and exceeds the lower bound                                                       | eligible (START-10.1-5)                                         |
| 5.l accept | maintenance replaces a policy while a validity plan is pending                                                  | allowed with unchanged rules (START-10.1-5)                     |
| 5.m reject | a structural plan is installed while a timestamp remains pending                                                | installation reverts                                            |
| 5.n reject | H>current c+maxStructuralLead, or lower/upper sum overflows                                                     | installation reverts                                            |
| 5.o accept | first policy/image revocation changes false to true; the same key is revoked again                              | count increments once; repeated revocation is idempotent        |
| 5.p accept | rollback changed c_bad to c_good but highestCheckpoint[g]=c_bad                                                 | new H must be >=c_bad+U; old anchors cannot cross the new fence |

## Not covered

Deployment acceptance remains separate from these vectors. Required runtime implementation, real-proof capacity and deployment evidence remain subject to [upgrade acceptance](../../ACCEPTANCE.md#upgrade-activation-spec-101); these prose vectors do not establish that acceptance.
