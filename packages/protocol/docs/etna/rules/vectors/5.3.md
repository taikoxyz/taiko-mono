# 5.3 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). Vectors distinguish EL-only snapshot startup from validator/full-node fixed-origin replay. A stated rejection uses the rule's rejection consequence; other failures say "violates <ID>". Deployment questions remain in [review/5.3.md](../review/5.3.md).

## DATA-5.3-1

| Vector     | Setup                                                                                                                                                          | Expected                                                                                              |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 1.a accept | an EL without the ABCI application starts from a public authenticated checkpoint snapshot                                                                      | conforms to DATA-5.3-1                                                                                |
| 1.b accept | a newly started EL-only backend uses verified snapshot startup long after launch                                                                               | conforms to DATA-5.3-1; no launch-only restriction                                                    |
| 1.c accept | an EL-only backend instead starts from complete genesis material                                                                                               | conforms to DATA-5.3-1                                                                                |
| 1.d reject | EL-only snapshot authentication requires validator-private history or a running L2 RPC                                                                         | violates DATA-5.3-1                                                                                   |
| 1.e reject | later EL-only snapshot admission is refused solely because the launch period ended                                                                             | violates DATA-5.3-1                                                                                   |
| 1.f accept | an app node obtains state at its authenticated fixed generation origin from a snapshot, then replays every subsequent block and matches both checkpoint hashes | conforms to DATA-5.3-1 and RECOV-8.4-14                                                               |
| 1.g reject | a validator/full node imports a later checkpoint snapshot and skips earlier FinalizeBlock calls in the same generation                                         | violates DATA-5.3-1 and RECOV-8.4-14                                                                  |
| 1.h reject | an app node uses a snapshot to bypass a required FI singleton replay because the parent state is missing                                                       | violates DATA-5.3-1; RECOV-8-13 requires a safety halt for the stated non-retryable cold-sync failure |

| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------- |

| 3.b accept | s=0 uses complete genesis material, the initialized FI cursor and the genesis header                                                                                                 | conforms to DATA-5.3-3/4                                                      |

## DATA-5.3-4

| Vector     | Setup                                                                                                                                                      | Expected                                            |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| 4.a accept | the own finalized L1 authenticates s's retained record and FI cursor; header/ancestor hashes and actual state/code verify; indexes are verified or rebuilt | conforms to DATA-5.3-4                              |
| 4.b accept | proof-checked state sync establishes the same complete account/storage/code commitment as local recomputation                                              | conforms to DATA-5.3-4                              |
| 4.c reject | matching supplied headers or metadata are accepted without actual state verification                                                                       | violates DATA-5.3-4                                 |
| 4.d reject | a changed balance, nonce, storage slot or code has a recomputed matching file checksum                                                                     | reject the stateRoot/code mismatch under DATA-5.3-8 |
| 4.e reject | derived database indexes are used without verification or rebuilding                                                                                       | violates DATA-5.3-4                                 |
| 4.f reject | the checkpoint is supported only by a publisher claim or an unfinalized L1 block                                                                           | reject under DATA-5.3-4                             |
| 4.g reject | a required ancestor hash fails its link to the authenticated starting header                                                                               | reject under DATA-5.3-8                             |
| 4.h accept | the first post-s block computes base fee and BLOCKHASH using authenticated ancestors without pre-s state execution                                         | conforms to DATA-5.3-3/4                            |
| 4.i reject | s is an unlanded height with no retained slot 285 record                                                                                                   | reject under DATA-5.3-4                             |
| 4.j reject | s is a grid point inside a landed batch but has no landing record of its own                                                                               | reject under DATA-5.3-4                             |

## DATA-5.3-5

| Vector     | Setup                                                                                                              | Expected                                                                    |
| ---------- | ------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| 5.a accept | optional blob replay verifies full (p,h] inputs in canonical L1 landing order, with p/c from authenticated records | conforms to DATA-5.3-5                                                      |

## DATA-5.3-9a

| Vector      | Setup                                                                                                                                      | Expected                                                     |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------ |
| 9a.a accept | at least one verifiable public snapshot and all authenticated public data needed to reach the latest finalized checkpoint remain available | conforms to DATA-5.3-9a                                      |
| 9a.b reject | only a launch snapshot remains and L1 blob pruning removes the only suffix data before any replacement is provided                         | violates DATA-5.3-9a                                         |
| 9a.c accept | an old supported snapshot path is removed only after its replacement snapshot and complete suffix are available                            | conforms to DATA-5.3-9a                                      |
| 9a.d reject | rotation removes the last complete public snapshot-to-latest path                                                                          | violates DATA-5.3-9a                                         |
| 9a.e reject | an archive input used for sync is not authenticated against L1 commitments                                                                 | violates DATA-5.3-9a                                         |
| 9a.f reject | EL snapshot import is treated as committee/proving-history authentication or replacement signer state                                      | violates DATA-5.3-9a and the referenced 8.2/9.1 requirements |
| 9a.g accept | independent pre-s bad-landing checks use app nodes that validated and retained the history, rather than a copied snapshot                  | conforms to DATA-5.3-9a                                      |
| 9a.h reject | a snapshot-only EL is counted as independent execution/history evidence for a bad landing at or below s                                    | violates DATA-5.3-9a                                         |
