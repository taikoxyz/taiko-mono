# 8.1 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). This file states only what the text states: each vector either follows from an enumerated condition, or reports that a requirement was violated. Where the text states a requirement but **not the consequence of violating it**, the vector says "violates <ID>" and does not name an outcome. Anything undetermined has no vector; it is listed under "Not covered" and raised in [review/8.1.md](../review/8.1.md).

`accept` means the described governance action or state satisfies the rules cited. `reject` means a stated requirement is violated; these are governance-process rules, so a violation usually has no on-chain rejection — the consequence is the review question cited.

## RECOV-8.1-1

| Vector     | Setup                                                               | Expected             |
| ---------- | ------------------------------------------------------------------- | -------------------- |
| 1.a accept | the DAO (Inbox owner) authorizes recovery, exclusion or FI blanking | authorized           |
| 1.b reject | ordinary on-call or pause authority executes recovery               | violates RECOV-8.1-1 |
| 1.c reject | ordinary on-call authority blanks an FI entry                       | violates RECOV-8.1-1 |

| Vector     | Setup                                                                                                                    | Expected                                      |

## RECOV-8.1-4

| Vector     | Setup                                                                                     | Expected                                                                             |
| ---------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 4.a accept | `expectedC` equals the current c at authorization and no landing happens afterwards       | executable                                                                           |
| 4.b accept | a landing advances c after authorization                                                  | the call can no longer execute (`expectedC` mismatch); fresh authorization is needed |

## RECOV-8.1-6

| Vector              | Setup                                                                           | Expected                                                                                                                                           |
| ------------------- | ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 6.a accept          | landers settle up to the last provable grid point; `expectedC` is set to that c | only blocks that truly cannot be settled are discarded, plus at most K − 1 provable blocks short of a grid segment                                 |
| 6.b reject          | authorization uses a c below the last provable grid point                       | violates RECOV-8.1-6                                                                                                                               |
| 6.c accept boundary | the last provable grid point is c itself                                        | only the blocks above c are discarded: those that cannot be settled, plus at most K − 1 provable blocks short of the next grid point (RECOV-8.1-6) |
