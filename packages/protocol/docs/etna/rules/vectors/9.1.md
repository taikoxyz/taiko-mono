# 9.1 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). This file states only what the text states. Where the text states a requirement but **not the consequence of violating it**, the vector says "violates <ID>" and does not name an outcome. Anything undetermined has no vector; it is listed under "Not covered" and raised in [review/9.1.md](../review/9.1.md).

`accept` means the described archive, node or submission satisfies the rule cited. `reject` means a stated requirement is violated.

## SYNC-9.1-1

| Vector     | Setup                                                                                                                                                                                                                       | Expected                                                                           |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 1.a accept | an archive holds original blocks/envelopes, headers, commits/LastCommit, the `fallbackKeys` lists that anchors and origin records commit, FI data/logs, relevant L1 headers/proofs, genesis parameters and recovery records | complete CometBFT recovery and proving are possible from the retained material     |
| 1.b reject | the archive lacks one listed category, for example commits/LastCommit                                                                                                                                                       | incomplete for complete CometBFT recovery/proving; violates SYNC-9.1-1 ("require") |
| 1.c accept | the archive holds every listed category, reconstructed from original sources rather than a running node                                                                                                                     | requirement satisfied                                                              |
| 1.d accept | a node that serves a 5.4 import package also holds the validator-state preimage for that package's checkpoint                                                                                                               | conforms (DATA-5.4-3)                                                              |
| 1.e reject | the archive holds every other listed category but not a `fallbackKeys` list that an old anchor commits and that the Inbox has since replaced                                                                                | incomplete for proving blocks under that anchor; violates SYNC-9.1-1 ("require")   |

_Whether "require" obliges anyone to retain, and for how long: no vector — [Q9.1-2](../review/9.1.md#q91-2)._

## SYNC-9.1-4

| Vector     | Setup                                                                                                                                                                                                                             | Expected                               |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| 4.a accept | recovery authenticates the current generation's fixed origin record and c's EL/Comet hashes from the node's own finalized L1 view; the genesis validators are the keys of the list whose hash the record holds, each with power 1 | conforms to SYNC-9.1-4 and RECOV-8.4-9 |
| 4.b reject | the node builds the new generation's genesis validator set before it has authenticated the origin record                                                                                                                          | violates SYNC-9.1-4                    |
| 4.c reject | the origin record or c's hashes are taken from a peer or an unsigned file rather than the node's own finalized L1 view                                                                                                            | violates SYNC-9.1-4                    |
| 4.d reject | the DAO changed the fallback key list after R; the node takes the genesis validators from the Inbox's current list                                                                                                                | violates SYNC-9.1-4 and RECOV-8.4-9    |

## SYNC-9.1-5

| Vector            | Setup                                                                                                                                            | Expected                                          |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------- |
| 5.a accept        | from c + 1 on, the node derives the set that signs each H + 2 under 4.3 from its rebuilt L2 state at H and H's anchor, which it authenticated    | conforms to SYNC-9.1-5                            |
| 5.b reject        | the node takes the set that signs H + 2 from a peer's validator-set answer instead of deriving it under 4.3                                      | violates SYNC-9.1-5                               |
| 5.c not-inclusion | the sets that sign c + 1 and c + 2, which the origin record's fallback key set gives                                                             | not "later"; SYNC-9.1-4 governs them (COMM-4.3-9) |
| 5.d accept        | an imported node derives the proposer priorities of the s + 1 and s + 2 sets from the validator-state preimage that header(s)'s app_hash commits | conforms to SYNC-9.1-5 and DATA-5.4-3             |
| 5.e reject        | an imported node takes those proposer priorities from a peer's database because its validator-set hashes match                                   | violates SYNC-9.1-5 and DATA-5.4-3                |

## SYNC-9.1-6

| 6.a accept | material needed for authentication is missing      | node stays untrusted                        |

## SYNC-9.1-7

| Vector            | Setup                                                                                                                                                                    | Expected                                                            |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------- |
| 7.a accept        | anyone collects two same-round conflicting votes from different peers that pass STAKE-4.1-32 and STAKE-4.1-33 and submits them to `slashDoubleSign` in an L2 transaction | permitted; Comet evidence inclusion is not required                 |
| 7.b accept        | the two votes are at the same height, round and vote type with different block ids                                                                                       | same-round conflict                                                 |
| 7.c not-inclusion | the two votes are at different rounds                                                                                                                                    | not "same-round"; SYNC-9.1-10 applies                               |
| 7.d accept        | the submitting party is neither the voter nor a validator                                                                                                                | permitted ("anyone may collect")                                    |
| 7.e accept        | proposers leave the reporter's transaction out, and the reporter submits it through forced inclusion                                                                     | permitted ("directly or through forced inclusion")                  |
| 7.f accept        | the reporter takes the bond id from `bondForKey` for the address both votes recover to                                                                                   | conforms to SYNC-9.1-7 ("needs only the two votes and the bond id") |

_The rule grants a permission, so there is no reject case; a submission whose votes fail 4.1's checks is covered by STAKE-4.1-32 and STAKE-4.1-33._

## SYNC-9.1-8

| Vector            | Setup                                                                                                                                         | Expected                                                                                                      |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 8.a accept        | evidence is retained and submitted after the local pool's age limits (START-10-21) have passed                                                | consistent with independence                                                                                  |
| 8.b reject        | a node discards evidence solely because the local pool limit expired                                                                          | violates SYNC-9.1-8 ("independent of the local pool's ... limits")                                            |
| 8.c not-inclusion | the local pool's own eviction behaviour                                                                                                       | not governed by this rule; it is independent                                                                  |
| 8.d accept        | a bond's exit is set in block X; a node keeps evidence against its key until the bond is withdrawn, at the earliest at X + `withdrawalDelay`  | conforms to SYNC-9.1-8                                                                                        |
| 8.e accept        | a recovery from c discards the block above c in which the bond was withdrawn; the node kept the evidence and submits it in the new generation | possible: the withdrawal is void (RECOV-8-59) and the old generation's votes remain admissible (STAKE-4.1-32) |

_The accompanying "should track the withdrawal delay" is guidance, not a rule, so there is no reject case for it — see [review/9.1.md](../review/9.1.md#normativity-boundary)._

## SYNC-9.1-9
