# 9 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). This file states only what the text states: each vector either follows directly from an enumerated condition, or reports that a requirement was violated. Where the text states a requirement but **not the consequence of violating it**, the vector says "violates <ID>" and does not name an outcome — inventing one would lock in an interpretation nobody decided. Anything undetermined has no vector; it is listed under "Not covered" and raised in [review/9.md](../review/9.md).

`accept` means the described node or block behaviour satisfies the rule cited. `reject` means a stated requirement is violated (the enforcement consequence is a separate question — see [Q9-2](../review/9.md#q9-2)).

## SYNC-9-1

| Vector            | Setup                                                                                                                                                                                                                        | Expected                                                                                                                      |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 1.a accept        | cold sync (replay or blocksync) of a block the node did not judge live, carrying an anchor witness; its own L1 node reports the anchor header canonical and finalized, and the witness's `lastCheckpoint` checks out per 3.4 | the cold-sync revalidation is performed and passes                                                                            |
| 1.b reject        | same block; the own L1 node reports the anchor header not canonical or not finalized                                                                                                                                         | violates SYNC-9-1 ("checks ... that the anchor header is canonical and finalized"); consequence — [Q9-2](../review/9.md#q9-2) |
| 1.c reject        | same block; the witness's `lastCheckpoint` fails the 3.4 check against local history                                                                                                                                         | violates SYNC-9-1 ("checks the witness's lastCheckpoint per 3.4"); consequence — [Q9-2](../review/9.md#q9-2)                  |
| 1.d not-inclusion | cold sync of a block without an anchor witness (it inherits its parent's anchor)                                                                                                                                             | the bullet's condition "carries an anchor witness" is not met; no cold-sync witness check required                            |
| 1.e not-inclusion | a block judged live by the node at consensus time                                                                                                                                                                            | not "a block it did not judge live"; its checks are the live path, not this rule                                              |

_What a failed cold-sync check does (reject, halt, or leave the node untrusted): no vector — [Q9-2](../review/9.md#q9-2)._

## SYNC-9-2

| Vector     | Setup                                                           | Expected                                           |
| ---------- | --------------------------------------------------------------- | -------------------------------------------------- |
| 2.a accept | own L1 node lags behind the anchor's finality                   | the node waits and retries; no halt                |
| 2.b accept | own L1 node is unreachable                                      | the node waits and retries; no halt                |
| 2.c accept | a request to the own L1 node times out                          | the node waits and retries; no halt                |
| 2.d accept | own L1 node returns contradictory evidence                      | the node halts for safety (stated)                 |
| 2.e reject | the node halts because its own L1 node merely lags or times out | violates SYNC-9-2 ("only makes it wait and retry") |

_What evidence counts as "contradictory": no vector — [Q9-2](../review/9.md#q9-2)._

## SYNC-9-3

| Vector     | Setup                                                                                                                                         | Expected                                                                      |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 3.a accept | FinalizeBlock passes the `lastCheckpoint.hash` proven by the anchor to the EL's forkchoice as `finalized`; the local history descends from it | requirement satisfied                                                         |
| 3.b reject | FinalizeBlock passes some other hash as `finalized`                                                                                           | violates SYNC-9-3 ("passes the `lastCheckpoint.hash` proven by the anchor")   |
| 3.c reject | the history does not descend from the checkpoint, and the node does not treat the EL rejection as a safety halt                               | violates SYNC-9-3 ("is rejected by the EL ... and the node halts for safety") |
| 3.d accept | the history descends from the checkpoint                                                                                                      | no rejection, no halt                                                         |

_The rule names EL error `-38002`; whether the pinned EL version is required to produce it, and what a node does if the EL accepts a non-descending history: no vector — [Q9-7](../review/9.md#q9-7)._

## SYNC-9-4

| Vector              | Setup                                                                                                              | Expected                                                        |
| ------------------- | ------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------- |
| 4.a accept          | app startup begins with no trust; it reads the Inbox's latest checkpoint from the node's own finalized L1 view     | requirement satisfied                                           |
| 4.b reject          | app startup begins by trusting the local EL head without authenticating the Inbox's latest checkpoint              | violates SYNC-9-4                                               |

## SYNC-9-7

| Vector     | Setup                                                     | Expected                                                    |
| ---------- | --------------------------------------------------------- | ----------------------------------------------------------- |
| 7.a accept | the latest checkpoint cannot be obtained yet              | node stays untrusted and retries                            |
| 7.b accept | an authenticated contradiction from the own L1 node or EL | safety halt                                                 |
| 7.c accept | malformed or unverifiable data from the own L1 node or EL | safety halt                                                 |
| 7.d reject | the node becomes trusted on unverifiable data             | violates SYNC-9-7                                           |
| 7.e reject | the node halts merely because data is missing             | violates SYNC-9-7 ("keeps the node untrusted and retrying") |

_Which component halts, and whether "halt" here is the section 8 safety halt: no vector — [Q9-2](../review/9.md#q9-2)._

## SYNC-9-8

| Vector            | Setup                                                                                        | Expected                                            |
