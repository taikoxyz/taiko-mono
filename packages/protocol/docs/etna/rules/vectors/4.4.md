# 4.4 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). Section 4.4 is a governance power, so these vectors describe what the staking contract permits and what it refuses; they do not judge whether an attribution is correct. Each vector follows from the stated checks, or reports that a requirement was violated. Where the text states a requirement but not the consequence of violating it, the vector says "violates <ID>". Gaps are in [review/4.4.md](../review/4.4.md).

`accept` means the described call or state satisfies the rule cited. `reject` means a stated check fails; where the text says a call fails or reverts, the vector says so. The attribution itself is a governance responsibility, not a vector — see [Q4.4-2](../review/4.4.md#q44-2).

## FORF-4.4-1

| Vector     | Setup                                                                                                             | Expected                                                              |
| ---------- | ----------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| 1.a accept | an L1 → L2 governance message has the staking contract's owner, the DAO's execution address on L2, call `forfeit` | call is permitted                                                     |
| 1.c reject | any other caller invokes `forfeit`                                                                                | violates FORF-4.4-1 ("callable only by")                              |
| 1.e reject | an address that is not the staking contract's owner calls `forfeit`, even if it is a DAO address on L1 or L2      | violates FORF-4.4-1 ("callable only by the staking contract's owner") |

## FORF-4.4-2

| Vector     | Setup                                                                                                                               | Expected                                                            |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 2.a accept | the DAO verifies that the targeted bond id and consensus key match the intended registration in the L2 state at a landed checkpoint | conforms to FORF-4.4-2                                              |
| 2.b reject | the DAO authorizes a predicted but unissued id                                                                                      | violates FORF-4.4-2                                                 |
| 2.c reject | the DAO verifies the bond only against L2 state above the latest landed checkpoint                                                  | violates FORF-4.4-2 ("against the L2 state at a landed checkpoint") |

## FORF-4.4-3

| Vector     | Setup                                                                                              | Expected                                                                                                          |
| ---------- | -------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 3.a accept | the DAO authorization binds the deployment, the full call parameters and the published attribution | conforms to FORF-4.4-3                                                                                            |
| 3.b reject | an authorization not bound to the deployment or the published attribution is executed              | violates FORF-4.4-3; how this is verified — [Q4.4-2](../review/4.4.md#q44-2)                                      |
| 3.c accept | the same incident names two bonds with two separate calls                                          | allowed ("the same incident may name multiple bonds")                                                             |
| 3.d reject | the staking contract refuses the second bond because it deduplicated the incident id               | violates FORF-4.4-3 ("no ... global incident-id deduplication state")                                             |
| 3.e accept | the same incident id is used for a later, unrelated attribution                                    | the staking contract has no dedup state to reject it; whether that is intended — [Q4.4-3](../review/4.4.md#q44-3) |

## FORF-4.4-4

| Vector     | Setup                                                                                         | Expected                                                   |
| ---------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 4.a accept | issued and unwithdrawn, flag false, `block.timestamp <= validUntil`, `balance = effStake > 0` | execution checks pass                                      |
| 4.b reject | the bond has been withdrawn                                                                   | reverts (FORF-4.4-4, FORF-4.4-19)                          |
| 4.c reject | the call names an unissued id                                                                 | the call reverts without writing any state (STAKE-4.1-13a) |
| 4.d reject | `forfeited[bondId] == true`                                                                   | violates FORF-4.4-4                                        |
| 4.e reject | `block.timestamp > validUntil`                                                                | violates FORF-4.4-4 (expired)                              |
| 4.f reject | `balance == 0`                                                                                | violates FORF-4.4-4 ("`balance = effStake > 0`")           |

## FORF-4.4-12

| Vector      | Setup                                                                         | Expected                                                                 |
| ----------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------ |

## FORF-4.4-15

| Vector      | Setup                                                                                                                  | Expected                                                                                       |
| ----------- | ---------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 15.a accept | valid double-sign evidence arrives after forfeiture; it takes the remaining principal                                  | conforms to FORF-4.4-15                                                                        |
| 15.b accept | double signing empties the bond first; forfeiture then fails on zero balance; the bond can still be withdrawn normally | conforms (both outcomes stated)                                                                |
| 15.c reject | forfeiture succeeds on zero balance after double signing emptied the bond                                              | violates "forfeit fails on zero balance"                                                       |
| 15.d reject | an empty bond blocks normal withdrawal                                                                                 | violates "without blocking normal withdrawal"                                                  |
| 15.e accept | B = 10,000, slashBountyBps = 1000, forfeitBps = 9500, owner receives the bounty on valid evidence first                | self-report costs 9000, below the 9500 forfeiture on B. Forfeiture then fails on zero balance  |
| 15.f accept | same rates, B = 1, owner self-reports first                                                                            | net loss and forfeiture on the same balance both round to 1                                    |
| 15.g accept | same rates and B = 10,000, DAO forfeits before the owner's valid self-report                                           | 9500 goes to the sink first, then 500 is slashed with bounty 50. The owner loses 9950 in total |

| Vector      | Setup                                                                                                                             | Expected                                                                      |

## FORF-4.4-19

| Vector      | Setup                                                                                                                                  | Expected                                     |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |

## FORF-4.4-20

| Vector      | Setup                                                                                          | Expected                                    |
| ----------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------- |
| 20.a accept | forfeiture executes before a lawful withdrawal; the penalty is taken from the bond             | conforms to FORF-4.4-20                     |
| 20.b accept | the withdrawal already executed; forfeiture finds no balance and cannot recover the paid funds | conforms ("cannot recover withdrawn funds") |
| 20.c reject | forfeiture recovers funds already paid by a lawful withdrawal                                  | violates FORF-4.4-20                        |
| 20.d accept | a recovery is planned; the DAO executes the forfeitures in the new generation                  | conforms to FORF-4.4-20                     |

_Whether "Execute before lawful withdrawal" is a protocol rule or operational advice to the DAO, and who can enforce ordering: no vector — [Q4.4-4](../review/4.4.md#q44-4)._

## FORF-4.4-21

| Vector      | Setup                                                                     | Expected                                                                                                                                          |
| ----------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 21.a accept | a bond has been forfeited                                                 | it never holds a seat again: its exit stays set (STAKE-4.1-24) and no top-up is allowed after an exit (STAKE-4.1-20)                              |
| 21.b accept | the operator withdraws and registers a new key as a new bond              | the new bond can take a seat and can itself be forfeited                                                                                          |
