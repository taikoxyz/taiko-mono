# Recovery authorization when settlement is intermittent

This operational procedure uses the existing dedicated Etna verifier controls. It does not add a landing freeze to `recover`, relax `expectedC`, establish when a stall merits recovery or bound the DAO's response time. The recovery conditions in [SPEC.md section 8.1](SPEC.md#81-recovery-authority-and-user-visible-boundaries) still apply. A missed landing target or slow but valid settlement is not a recovery trigger. Repeated invalidation alone does not justify the emergency authorization path.

`land` is unaffected by the Inbox's ordinary pause. A committee can therefore let a valid landing advance c while an authorization is queued, even if it had previously stopped producing blocks. That authorization must fail: executing it at another checkpoint would apply lists approved for a different settled prefix. Asking landers to stop, or scheduling a production stop, does not disable previously provable landings.

For an independently justified recovery that needs a stable checkpoint during authorization, use two governance stages:

1. **Settle and prepare the revocation batch.** Have landers settle up to the last provable block, as RECOV-8.1-6 requires. Identify the deployed Etna composition and its dedicated RISC0 and SP1 verifier addresses from the deployment manifest. Verify the actual composition requires at least one of these ZK lanes in every accepted combination. Reconstruct the complete sets of trusted block and aggregation images/programs from the manifest and trust-update history, then check their current flags. Verify the DAO controls both verifiers and neither has a pending ownership transfer. Record the addresses, code hashes and complete trust inventory with the batch. An incomplete inventory cannot establish that settlement is disabled.
2. **Execute revocation on both ZK lanes.** Set every trusted Etna RISC0 block/aggregation image to false with `setImageIdTrusted`, and every trusted Etna SP1 block/aggregation program to false with `setProgramTrusted`. Keep both lanes disabled. Revocation is checked when a proof is verified, so proof bytes generated before the batch also fail. Disabling only RISC0 still permits SGX + SP1; disabling only SP1 still permits SGX + RISC0. Do not modify the separate Unzen verifier instances.
3. **Wait for revocation finality, then authorize the tuple.** Confirm the whole revocation batch is finalized and both lanes remain disabled. Only now read `(recoveryGeneration, lastCheckpoint.height, recoveryNonce)` from the finalized Inbox state, verify c's landing and the intended committee under 8.1, and authorize `recover` with that exact tuple, approved lists/rules and fixed `validUntil`. A landing ordered before revocation is included in this read. The revocation batch cannot itself pin an earlier c for a later authorization.
4. **Execute and finalize recovery before restoring trust.** Keep both lanes disabled through the recovery transaction and its finality. Recheck ownership, trust flags, tuple, deadline and committee before execution. A changed tuple or expired deadline requires fresh authorization. If a ZK lane has been re-enabled early, re-establish revocation and its finality before reading a new tuple. Never tolerate a stale `expectedC` to rescue an old proposal.
5. **Restore intended trust.** Once recovery is finalized and the new generation's software is ready, restore only the image/program trust intended for that generation. Then complete recovery acceptance through the first real two-proof landing becoming finalized. If recovery is cancelled or expires, restoring trust is a separate reviewed governance action; its execution can advance c and invalidate pending authorizations, which must be rechecked.

This procedure depends on complete trust inventory, DAO control and inclusion/finality of its transactions. It deliberately interrupts settlement while authorization is pending. It provides no new recovery guarantee against a DAO that cannot execute these controls, a composition with another accepted lane, unknown trusted images, or verifier failure. Ordinary recovery cannot repair a bad checkpoint; the verifier-failure rollback in spec section 8 applies first.

`EtnaRecoverySettlementFreeze.t.sol` checks the current `ZkRequiredVerifier` policy and real RISC0/SP1 trust checks for all three accepted combinations. Its remote cryptographic verifiers are test stubs. It establishes the contract control behavior, and does not replace the joint real-proof recovery acceptance in [ACCEPTANCE.md section 2](ACCEPTANCE.md#2-recovery-acceptance-spec-section-8).
