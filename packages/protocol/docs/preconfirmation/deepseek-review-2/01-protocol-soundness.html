Protocol Soundness — Does the Design Work?

Aspect 1 of the DeepSeek independent adversarial review of the permissionless based-preconfirmation redesign (PR #22034; branch claude/taiko-preconfirmation-redesign-i0c4ls; normative doc redesign-proposal.md v14). Review date 2026-08-21. Companions: index · attacks · auction sims · L2 vs L1 timestamps · economics · doc consistency · model checker.

Frank verdict: as a mechanism design, the v14 design is logically coherent and largely works: the epoch state machine is sound, the single-decision structure is consistent, the liveness story (degradation ladder + cancellation floor) survives adversarial proving outages in the bounded model check, and the fourteen rounds of dispositions are real and mostly correct — I verified the checker myself (1,408,548 states, 0 violations, 24/24 mutants caught). As an implementable protocol, it does not yet exist: the PR is documentation-only and the doc itself lists 19 structural items, 15 of them Phase-A-blocking (plus 4 Phase-B). Beyond those, this review finds three load-bearing mechanisms that are specified in prose but have no L1-evaluable implementation named (S2–S4), one consensus-exactness gap (S5 — the timestamp decoupling, detailed in aspect 4), and one economic deterrence claim that only holds at watchtower probability 1 (S7). Nothing found is an unfixable contradiction; two things would break the chain if implemented as literally written (§6.8's default-anchor binding, §9.2's anchor eligibility check) and must be pinned before any code.

S2. The default-anchor L1 binding is unspecified — and it is load-bearing (new finding)

HIGH — would break I3/I6 if implemented naively

§6.8 defines the default anchor F(N) = "the highest canonical L1 execution block whose slot is ≤ slot(T_N) − D_anchor", and the DEFAULT-mode seal circuit must verify the forced-only block sequence against F(N)'s state root. But an L1 contract cannot map a past slot to a block number: it only sees the current block. If the seal transaction claims "F(N) = (number n, hash h)", nothing named in the doc lets the contract check that n is the deepest block ≤ slot(T_N) − D_anchor, or even that h is authentic. There is a viable path — the same machinery §5.2 already adds: an EIP-4788 beacon-root SSZ proof of the execution payload (or latest_execution_payload_header in beacon state) at the relevant slot, recorded in the spine while the 8191-slot root buffer is still fresh (a seal can land up to S·E + tolling later, but a cancellation re-resolution can land ~10 days later, long past the buffer — so the record must be made at decision time, not at seal time). The design names none of this: §13-S.18 pins the "decision-record" for mode selection but not the anchor-binding record. Consequences of the gap: (a) a forced-only/DEFAULT seal is unconstructible on-chain → holderless epochs stall → I3/I6 violated; (b) or an implementation accepts a caller-claimed anchor → first-landed sealer gets a retrospective anchor option — exactly the r10H-1 hole §6.8 was written to close. This is the single most important implementation-blocking gap this review found.

S3. The anarchy-proposal anchor eligibility check has no named L1 mechanism (new finding)

HIGH — Phase-A-blocking only if W_a > 0 at launch; otherwise Phase-B per §13-S.19 (round-3 corrected phase tag)

§9.2 requires an anarchy proposal's committed anchor to satisfy §6.6's depth/freshness/advancement "measured against N's own schedule — epoch-relative, never landing-relative". But the proposal lands up to W_a·E (≈25.6 min) after D_N. The L1 contract at landing time can only compare the claimed anchor block number against the landing block — which enforces depth-at-landing (trivially true) and cannot enforce "≥ D_anchor deep at D_N" or "not older than T_N − freshness_ceiling" without historical block-number/timestamp lookup that L1 does not have. For owned epochs the check works because the EBC is accepted within κ of the deadline (acceptance-time block.number is the reference). For anarchy proposals the design needs one of: an EIP-4788-based anchor record (S2's machinery), a spine record of blockAt(slot(D_N)) made at each decision, or a circuit-side L1 header proof — none is named. Same family as S2; both are "works in prose, needs a mechanism" gaps.

S4. The fill-reward trigger is not L1-evaluable as written (new finding)

MEDIUM — incentive element silently unimplementable

§5.2: "A fill reward exists only when the holder failed to make its own referenced data available, funded from the failing holder's working tranche." But blob KZG commitments are content-addressed: the availability certificate proves commitment inclusion, not who posted it. A holder's own slice and a filler's identical re-post are the same commitment — "the holder failed to post" is not a computable L1 predicate unless the EBC additionally binds the holder's own blob-transaction hashes (or equivalent per-sender registration), which the design does not specify. §13-S.12 fixes the payee binding (bytes vs hash) but not the trigger. If unimplementable, the r4b-H2 fix silently degrades to v4's zero-fill reward, and the successor-self-protection argument must carry the availability incentive alone. Recommend: state the trigger-binding (holder's own slice-post registration in the EBC) or explicitly drop the fill reward.

S5. Timestamp/anchor decoupling: consensus-exactness gaps

Summarized here; full analysis in aspect 4: (a) +383 s forward-stamp freedom with no pinned client-acceptance rule (future-block rejection); (b) T_N's origin undefined; (c) anchor-staleness ratchet bounded only by a governance-set ceiling with a lower-but-no-upper setter bound; (d) slot-mapping rounding rules unspecified. All four are Phase-A consensus-exactness items.

S6. Availability-certificate censorship residual — correctly priced, one sharp edge

LOW — admitted, correctly keyed; re-checked in round 2

The AC is small, sender-free, fee-bumpable; suppressing it for R=16 slots requires a builder/proposer coalition against every possible sender; the successor keys its hard-preconf upgrade on the contract-legible materialization, so an AC-suppressed CONTENT→EMPTY flip orphans only soft preconfs (never slashable). This is well-designed. Round-2 re-check retracted an earlier version of this note: the R window (≈3.2 min) does not sit on the recovery path — it closes long before the seal deadline (S·E = 4 epochs), so §6.7's "resolves within ~κ of the deadline" is accurate as written. The only place the materialization lag binds is the earliest possible early seal (no seal before the decision materializes) and the successor's soft→hard upgrade — both as designed.

S7. Equivocation deterrence holds only at watchtower probability 1

MEDIUM (economic) — quantified

No clawback of stolen MEV exists (restitution out of scope): the equivocator keeps the gain and loses L_safety only if caught. Expected profit = Λ·MEV − p·L_safety; the design sizes L_safety ≥ Λ·MEV, which deters only at p = 1. For the double-EBC variant p→1 mechanically (self-materializing L1 evidence — good), but for preconf-vs-record, p is the probability a watchtower acts within the challenge horizon: at p = 0.5 the bond must be 2× the stated size, at p = 0.1 ten-fold (simulation table in economics §5.3). The doc admits watchtower-dependence (r11-N2) but the sizing claim silently assumes p = 1. Moreover "Λ × per-epoch MEV" requires an ETH-denominated MEV estimate set by governance with no oracle (I9) — the deterrence guarantee is as good as a governance guess, with the spike residual already admitted. See economics §5.3.
