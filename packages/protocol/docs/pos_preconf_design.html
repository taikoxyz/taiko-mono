Taiko protocol · design draft for discussion · 2026-10-05

PoS Preconfirmation: a CometBFT Committee on Top of Etna

Remove the preconfirmation whitelist, address preconfirmation fair exchange, and keep the on-chain result ZK-provable, with the smallest set of protocol changes.

Summary. Add an open-stake CometBFT committee on top of Etna. Every validator votes on each 2-second block and only votes for blocks that include the transactions in the inclusion lists (ILs) that the leader placed in the block. Each proposal carries the commit of its last block, and clients and raiko2 accept it only if the commit verifies. Submitting to L1 rotates among validators per epoch as a duty with no separate reward. Etna's L1 anchor rules, the bridge and L2 execution do not change. The Inbox only swaps its implementation: forced inclusion is enforced by derivation instead of being inserted at landing.

Terms

seat
A fixed-size stake unit in the registry. Voting power, leader turns and lander turns are all counted in seats.
leader
The CometBFT proposer for a height. It rotates every block by CometBFT's weighted round robin.
lander
The validator allowed to call Inbox.propose during one 384 s epoch. It only posts committed blocks.
IL
Inclusion list: transactions a validator has witnessed and requires the next block to include, FOCIL-style.
FI
Forced inclusion: a transaction submitted to the L1 forced inclusion store.
commit
CometBFT's certificate for a block: precommit signatures from more than 2/3 of the voting power.

1. Changes

1.1 L1: PreconfWhitelist becomes a staking registry; the Inbox swaps its implementation

  • Open entry with a fixed bond per seat. The registry freezes a committeeRoot (a commitment to validator keys and seat counts) once per epoch and exposes entry points for double-sign slashing and for removing absent validators.
  • Landing rights rotate per epoch. Reuse the existing per-epoch operator selection, drawing uniformly from active seats. The last part of each epoch is open to every active validator as a fallback (see Lander).
  • No new Inbox is needed for the registry: _proposerChecker is immutable but points at the PreconfWhitelist proxy, so swapping the proxy implementation is enough.
  • The Inbox swaps its implementation (same proxy):
    • propose no longer dequeues FIs or inserts FI blocks. The UnprocessedForcedInclusionIsDue check is removed and numForcedInclusions is no longer used. The FI store keeps accepting submissions.
    • The FI queue head advances by proven progress. prove also takes the proven end block's L2 header, checks its hash against the proven end block hash, and reads its anchor block number from extraData bytes 7–12. An FI whose enqueue block plus 48 (576 s) is at or below that number has been checked and can be dequeued; the FI store records the enqueue block number for this. A proposal that derives to zero blocks does not move the end block, so it does not move the queue. Advancing by landing time would be wrong: zero-block landings are finalized too, so unchecked FIs would be dequeued, and a committee could halt, wait for the FI to leave the queue, then resume without it. Never dequeuing is not an option either: the pending count would only grow, and the "fee doubles at 50 pending" rule would keep doubling the FI fee.
    • The "permissionless proposing after long-overdue FIs" path (mainnet multiplier 160, about 25.6 h) stays disabled. It is disabled in today's code; enabling it would let anyone act as a lander.
    • prove finds proposals that derived to zero blocks (end block hash equal to the previous one), records a miss for the lander and pays a small fine to the prover.
    • propose takes the expected hash of the previous proposal (the Inbox already computes parentProposalHash) and reverts on a mismatch. Racing fallback landings, and transactions re-included after an L1 reorg, then fail instead of deriving to zero blocks.

1.2 Nodes: a CometBFT consensus layer

  • CometBFT v0.40 drives the existing execution clients through the Engine API, the same structure as Berachain's BeaconKit. v1.0.1 has had no release since 2025-02, while v0.38, v0.39 and v0.40 are maintained.
  • The Taiko ABCI app (Go) runs in-process with CometBFT as a standalone component and is the only writer of the EL head, through the Engine API. Either taiko-client or taiko-client-rs pairs with it for L1 derivation, L1Origin and landing, over RPC only: committed blocks and commits come from CometBFT's /block and /commit. When L1 derivation disagrees with the committed chain, the client tells the app to halt and resync; it never writes the head itself.
  • Block cadence: v0.40 has no next_block_delay. The field is missing from v0.40.0's ResponseFinalizeBlock; it arrived with ADR-115 in v1.x. The gap between blocks comes from timeout_commit, the wait after a commit before the next height. Setting it to 2 s minus one consensus round gives about one block every 2 s, without alignment to a wall-clock grid, so block intervals jitter. A failed round makes that block longer. Exact alignment would need a CometBFT patch.
  • CometBFT's own mempool is disabled (nop). That requires producing empty blocks, so there is a block every 2 s even when idle. Etna's empty blocks carry no transactions and are cheap to prove.
  • The ILs ride on the vote extensions, and ProcessProposal only checks data that is inside the block. The check is therefore deterministic, as CometBFT requires, and an honest leader is never rejected because some IL arrived late.

1.3 Derivation and proving: one fork on top of Etna

The base rules are the Etna section of PR #22189. Only additions and changes are listed here; the table at the end of this section lists every consensus change.

  • What a proposal carries. Per-block manifests do not change. Each proposal adds three items for its last block:
    • The commit: CometBFT's Commit, one CommitSig per validator (address, timestamp and a 65-byte secp256k1eth signature, about 100 B each). Each validator signs a CanonicalVote that includes its own timestamp, so the messages differ and the signatures are verified one by one. The lander includes just over 2/3 of the signatures and marks the rest absent. The commit for block T is not inside block T; the lander takes it from its own node.
    • The CometBFT header, about 0.4 KB. A CometBFT block is a header plus Data (transactions), LastCommit and Evidence. The header commits to the rest through hashes such as DataHash, and the block_id.hash that validators sign is the header hash.
    • Two Merkle siblings (64 bytes). Data holds tx0 = EVM block hash, tx1 = payload and tx2 = ILs. The siblings let the proof go from DataHash to the last EVM block hash without re-serializing the payload.
  • Why only the last block. EVM parent hashes chain the segment. If the replayed segment ends in the EVM block hash the commit certifies, the whole segment matches what was committed. CometBFT's own last_block_id chain is not needed. The segment start is fixed by the previous proposal's proof; a segment that does not connect cannot produce the same last hash.
  • New checks. Client derivation and the raiko2 guest use the same rules.
    • Committee: the guest takes the L1 header for originBlockHash, gets its state root, and reads the registry's committeeRoot[epoch] with an MPT storage proof. Clients read L1 directly. The validator list in the witness (keys, seat counts) must hash to committeeRoot and must also produce the header's ValidatorsHash under CometBFT's encoding. A proposal stays inside one committee epoch.
    • Commit: the recomputed header hash equals commit.block_id.hash, and chain id and height match. Each CanonicalVote is rebuilt and hashed with Keccak-256, and its signer is recovered with k256. The signing seats must exceed 2/3. Header hashing can reuse tendermint-rs; if it lacks secp256k1eth verification, write that part directly. k256 0.13 is the version both raiko2 guests already accelerate.
    • Link to EVM: a DataHash Merkle path proves that tx0 equals the derived last EVM block hash.
    • Cost (estimate, to be measured): at most about 67 signature checks, comparable to recovering 67 more transaction senders. SHA-256 is accelerated and the MPT proof is about 1 M cycles. The total is a few percent of the per-proposal fixed cost (about 512 M cycles in raiko2's RISC0 model).
  • Public inputs do not change. The committee is read from originBlockHash, which the proposal already contains. The commit and header sit in the blob, which existing blob checks cover. The L1 verifier does not change, and the Inbox does not change for the commit.
  • No landing-dependent fields. Derived blocks must equal committed blocks byte for byte. Etna's 13-byte extraData layout [basefeeSharingPctg(1) | proposalId(6) | anchorBlockNumber(6)] stays, but bytes 1–6 change from the proposalId the Inbox assigns at landing to the CometBFT height. The EL only checks the layout, and bytes 7–12 keep the anchor number. Code that decodes proposalId from extraData must take it from derivation records or L1 events instead: Go's DecodeShastaProposalID (driver/preconf_blocks/api.go, driver/state/l1_current.go, pkg/rpc/methods.go) and Rust's decode_shasta_proposal_id (proposer/src/proposer.rs). Byte 0, basefeeSharingPctg, also comes from the proposal at landing (an Inbox setting) and sets the base fee split, so an Inbox upgrade that changed it would make committed blocks underivable. It becomes a fork constant that only a hard fork changes.
  • Zero blocks on failed validation. If the lander's own segment fails validation, it derives to zero blocks instead of Etna's default source, which would produce an empty block with the lander as coinbase. Failures include an invalid or malformed commit, a committee mismatch, and blocks failing Etna's checks, for example an anchor whose L1 block was reorged out. The proof must produce this zero-block result instead of failing. Otherwise one bad commit would make the proposal unprovable and block every later proof. Only invalid proposal content derives to zero blocks: bad encoding, too few signatures, a header or DataHash path that does not match, blocks outside the windows, or a missing due FI. If the witness from the host fails authentication, the guest must refuse to prove. That covers an L1 header chain that does not reach originBlockHash, a storage proof that does not match the state root, a validator list that does not hash to committeeRoot, and an FI blob that fails KZG. Otherwise a malicious prover could feed a bad witness, prove a valid proposal as zero blocks and finalize it, forking the L1 chain away from the committed chain and collecting the invalid-landing fine.
  • Forced inclusion is checked by derivation. Each FI is checked once, at the block whose anchor passes the FI's due time (enqueue time plus 576 s). Its transactions must already be on chain or be invalid in the current state. Otherwise the proposal's own segment derives to zero blocks. A committee that refuses due FIs can only halt the chain. The guest reads the FI queue with storage proofs against Etna's anchorStateRoot and takes FI transactions from the FI blob, which it already verifies with KZG. A lander therefore cannot insert any block, and an invalid landing at most wastes a turn.

Consensus changes to derivation. Derivation is consensus: clients and raiko2 must derive the same chain. Relative to the Etna rules in #22189, these must change:

1.4 Transaction entry

Wallets and RPC endpoints do not change. Transactions reach validators through public L2 transaction gossip, so validator execution clients must join the public network with gossip on (behind sentry nodes is fine). Inclusion takes about the gossip latency plus 250 ms plus at most one block, unless blocks are full (see Fair exchange in section 4).

2. Lander: a rotating duty

  • Role. The lander on duty packs the blocks committed since the last landing into one proposal and submits it to the Inbox. It cannot change the content, because coinbase and transactions are locked by the commit.
  • Incentive: a duty with no separate reward. Fees go to the leaders that built the blocks. The lander cannot be paid inside the blocks either, because who lands a block is unknown when the block is committed.
    • Stake per seat is fixed, landers are drawn uniformly per seat, and leaders rotate by seat weight. Each validator's share of landing cost therefore matches its share of block revenue.
    • A miss (no landing during one's epoch) is recorded, not fined. It only counts when the epochs before and after had landings, so halts do not trigger it. Repeated misses remove the seat from the active set. A landing that derives to zero blocks also counts as a miss and pays a small fine, about the cost of proving one proposal, to the prover that proves it. L1 sees it at prove time: the commitment already lists each proposal's proposer and end block hash, and an end hash equal to the previous one means zero blocks, so no extra storage is needed. Zero blocks must be the lander's fault for this to be fair: propose binds the previous proposal hash, so a transaction re-included after a reorg reverts; ProposeInput.deadline carries the segment's deadline, so a transaction that waits in the mempool past it reverts; landers only land segments whose anchors are finalized; and the guest produces zero blocks only for invalid proposal content. What remains is a committee that itself signed an invalid block, and by then the chain has halted.
    • Cost: about 75k gas plus one blob per landing. At about 225 landings per day and market tips, roughly 0.005–0.014 ETH per day (estimate), or 20–60% of current L2 revenue.
  • Timing.
    • Land once within the first three quarters of one's 384 s epoch, with 2–3 L1 slots of margin, and retry within that time if the transaction does not land.
    • Deadline on L1: every landing sets ProposeInput.deadline (an existing Inbox field) to the earlier of the segment's earliest block timestamp plus 6144 s and the time of its earliest anchor L1 block plus 6144 s. A transaction that waits in the mempool past it reverts instead of landing as zero blocks. L1 has at most one block per 12 s slot, so meeting this time deadline keeps L1 within 511 blocks of the anchor, and the 512-block anchor window holds without a new field. The Inbox does not check that the deadline is right; it protects the lander, and a wrong value is the lander's own fault. This deadline is conservative and only protects the lander; it is not the point at which blocks expire.
    • Landers only land segments whose anchors are finalized, so an anchor reorg never turns a landing into zero blocks (see L1 anchor depth in section 4).
    • Fallback: the last quarter of the epoch is open to every active validator. Each one first runs derivation itself to confirm that the lander on duty did not land or landed something invalid, then lands; anything left over goes to the next lander. Without this, about 16 consecutive epochs without a valid landing (the 6144 s window) would push committed but unlanded blocks out of the window and reorg up to about 1.7 h of blocks. Landers are drawn per seat at random, so a coalition holding half the seats would hit such a streak about once a year.
    • The only hard deadline comes from Etna's derivation windows (timestamp 6144 s, anchor 512 L1 blocks, about 1.7 h).
    • Segment boundaries follow lander epochs. Committee epochs are a multiple of 384 s.
  • Data. Per-block manifests are unchanged (timestamp, coinbase, anchorBlockNumber, gasLimit, transactions). A proposal adds the commit (secp256k1eth, about 100 B per validator, 7–10 KB for 100 validators), the CometBFT header (about 0.4 KB) and two Merkle siblings (64 bytes). A proposal is about 4 KB today and about 15 KB with these additions, still one blob. The commit is not verified on L1, so L1 cost stays about the same.

3. Unchanged

The main propose and prove flow (apart from the changes in 1.1), FI store submission and its 576 s due time, Etna's L1 anchor rules (parentBeaconBlockRoot holds the anchor state root and extraData bytes 7–12 hold the anchor number), SignalService and the bridge, L2 execution, and the 2 s block time.

4. Rules

  • Committee. All active seats vote; there is no sampling. Voting power is counted in seats, and a commit needs more than 2/3. The number of seats is capped (about 100), and new seats queue for free slots.
  • Launch threshold. CometBFT requires signed power strictly greater than total power × 2 / 3 with integer division. Switching from the whitelist requires at least 4 active addresses (preferably 7) and no address above 1/3 of the seats. Addresses of the same entity cannot be told apart on chain, so the threshold is approximate. One entity with 1/3 of the seats or more can halt the chain alone, and one above 2/3 can forge commits and censor alone. If exits push the set below the threshold after launch, CometBFT keeps producing with lower fault tolerance. The switch happens at one fork height: the whitelist operator stops there, CometBFT starts from that L2 head, and the two never produce blocks in parallel.

  • Keys. CometBFT v0.40's secp256k1eth validator keys: signatures over the Keccak-256 hash, 65 bytes [R‖S‖V], with Ethereum addresses. L1 checks double-sign evidence directly with ecrecover, and both raiko2 guests already accelerate k256.
  • What a preconfirmation means. The transaction is in a block that has a commit. Inclusion is guaranteed; the execution result is not. Four states must be exposed separately: committed (about 2 s), on L1, proven, and L1-finalized. The bridge and withdrawals only trust proven checkpoints.
  • Fair exchange. The tip is paid inside the transaction, so payment happens only on inclusion and the exchange is atomic. The ILs a leader puts into a block must total more than 2/3 of the voting power, so it can leave out less than 1/3. A transaction in the ILs of honest validators holding at least 1/3 therefore always has at least one IL in the block, so it cannot be left out unless the block is full (gas or zk gas) or the transaction is no longer valid (its nonce or balance changed within the block). Normally the delay is at most about one block (about 2 s); a leader that stuffs its block can delay it further (see Block stuffing in the open questions).
  • Slashing. Only CometBFT double signing is slashed: one validator signing two different BlockIDs (nil counts as one) for the same height, round and vote type (prevote or precommit). Prevoting a block and then precommitting nil is legitimate and is not double signing. Anyone can submit the two votes to the L1 registry. After verifying them, the contract slashes the seat's bond, removes the seat from the set, and pays part of the slashed bond to the submitter. Section 5 covers the other kinds of misbehavior.
  • Absence. No fine. An absent validator is only removed from the active set and can queue to rejoin.
    • Fully offline. The lander miss rule covers it, with a miss limit of 1–2. A missed landing is visible on L1 and hard for others to fake. With the seats full, a seat is drawn about every 10.7 h, so an offline validator is removed within half a day to a day on average.
    • Online but not voting. A validator that never votes can never double-sign, yet still earns revenue as leader, so it needs its own count, modeled on Cosmos SDK's x/slashing. The ABCI app counts the blocks each validator signed from decided_last_commit in FinalizeBlock. The first block of each committee epoch must start with a leader transaction that writes the previous epoch's counts to an L2 contract, and ProcessProposal rejects the block if the counts are wrong. The contract emits a hash of the record through SignalService. Once that segment is proven and finalized, anyone can submit the counts with the signal proof to the registry, using the same verification as bridge withdrawals, and validators below the threshold are removed at the next freeze. raiko2, the L1 verifier, the derivation rules and the execution client do not change.
    • Resisting manipulation. Holders of 1/3 or more can refuse to vote for honest leaders' blocks so that only their own blocks commit, then leave a target's votes out of LastCommit to record it as absent. So the threshold is low and the window long (for example, signing under 10% of blocks over a day), and an epoch does not count when more than a set share of its heights (for example, 20%) committed only at round > 0. In a counted epoch, as long as an honest validator's votes arrive in time, an attacker holding x cannot push its signing rate below 1 − x − that share. With the threshold and the share summing to at most 1/3, getting it below the threshold takes more than 2/3.
    • A performance rule, not a framing guarantee. The bound above has a premise. CometBFT ignores precommits for the previous height that arrive after the commit timeout, so a validator on a slow or DoS-ed network can have a low recorded rate even though it always signs. With no fine and the option to rejoin, a wrong removal costs little. Validators should use sentries and redundant links so their votes arrive in time.
    • Once absent validators reach 1/3, the chain has already halted; see Loss of quorum below.
  • Loss of quorum. The chain halts. There is no based fallback and no rollback of committed blocks, except for expired blocks (next item).
  • Expired committed blocks. Back-pressure stops new blocks but cannot stop existing commits from aging. If L1 censors or stalls, or landers keep failing, past the derivation windows (6144 s, 512 L1 blocks, about 1.7 h), committed but unlanded blocks can never be landed. They are dropped, and so are their preconfirmations. Recovery works in generations, and each recovery starts the next one:
    • Etna's real failure condition, on finalized L1. Let P be the last derived block and B its child on the committed chain. B's failure point, the cutoff F, is the first L1 block that meets either condition: its time is past B's timestamp plus 6144 s, or its number minus 1 (its value as an origin) is more than B's anchor block number plus 512. Both conditions only get worse over time, so from F on no proposal can include B. B counts as expired only once F is finalized; until then validators only stop producing. The lander's time-based deadline is too conservative for this: with missed L1 slots, 512 blocks take longer than 6144 s, so B may still land legally after that deadline, and a malicious lander that sets a later deadline could land part of the old chain after the recovery scan. Unfinalized L1 is not enough either: after a reorg, B may turn out to have landed in time.
    • Recovery parameters come from F. Process every Inbox proposal up to F to get the last derived block P_F. The new generation's chain_id is the base chain_id plus the generation number, its validator set is the committee the registry froze at F, and its initial height is P_F's height plus 1. Honest validators share the committed chain and the finalized L1, so they compute the same parameters and restart on their own without manual coordination. Different chain_ids keep votes from different generations from counting as double signing.
    • Signer state per generation. CometBFT's FilePV checks the last signed height, round and step before it puts the chain_id into the sign bytes. After the old chain signed higher heights, restarting at P_F's height plus 1 therefore fails with a height regression, and a new chain_id does not avoid it. Signer state is kept per generation (chain_id): the old generation's record is kept and frozen, and the old chain_id is never signed again. The switch is atomic: once finalized L1 fixes the recovery parameters, the signer first marks the old generation closed, then creates the new generation's state, then starts the new CometBFT, so a crash in between never returns to the old generation. Remote signers such as tmkms and Horcrux already keep state per chain_id but need the same closed-generation rule.
    • Derivation checks the same rules. The new generation's first proposal must carry the expiry evidence from the old generation: B's CometBFT header and commit, the Merkle path from DataHash to tx0 (two siblings), and B's EVM header, whose hash must equal tx0. The CometBFT header alone is not enough: its last_block_id links CometBFT headers, not the EVM parent hash, and it does not give B's timestamp or anchor. Client derivation and the raiko2 guest check that the commit verifies against the committeeRoot of its epoch, that the EVM header's parent hash is the derived tip P_F, and that B has failed under the conditions above, using the EVM header's timestamp and its anchor number in extraData bytes 7–12 together with this proposal's L1 time and origin block number. Only then are commits under the new chain_id accepted, and the old generation's commits are no longer accepted. Without this evidence the committee could switch generations at will and drop committed blocks that had not expired, and the new chain_id would keep that from counting as double signing.
    • This fork could also widen the derivation windows to make expiry less likely.
  • Epoch handoff. The registry freezes the next epoch's set in advance. The app returns validator updates from FinalizeBlock two heights before the boundary (CometBFT applies them at H+2), so the first block of the new epoch already carries the new ValidatorsHash. If the new set is not ready, the chain stops at the boundary instead of skipping the handoff.
  • L1 anchor depth. Validators only vote for blocks whose anchor is far enough behind the L1 head. If the referenced L1 block is reorged out, those committed blocks can never be landed; once their deadline passes they are dropped by the recovery above, along with their preconfirmations. Landers only land segments whose anchors are finalized, so they are never fined for this; the users of those preconfirmations bear the loss. Anchoring to finalized L1 blocks removes the risk entirely but delays L1→L2 messages by about 13 minutes; this needs a trade-off.
  • Data retention. Validators must have the full payload before voting and keep it until the corresponding proposal is finalized on L1. Landing, and re-landing after an L1 reorg, depend on it. For dropped blocks, B's CometBFT header, commit, DataHash-to-tx0 Merkle path and EVM header are kept until the next generation's first proposal lands.
  • Alignment with Etna derivation. Production stops when unlanded committed blocks approach the derivation windows (timestamp 6144 s, anchor 512 L1 blocks), because blocks past the windows can never be landed. A source holds at most 768 blocks (from Unzen). One epoch's segment is about 192 blocks, so one missed landing still fits; a larger backlog is split into several proposals. A proposal never spans committee epochs.
  • Forced inclusion. The FI store stays as the L1 backstop and is enforced as described in 1.3. Normally validators add FI transactions to their ILs and they are included within seconds. In the worst case a malicious majority lags anchors to the edge of the window and delays an FI by about 1.7 h; after that it must include it or halt.
  • Exit. For each generation a validator served, one of these must hold: the blocks it served are proven and finalized on L1, or the generation was abandoned at a finalized cutoff F. A double-sign evidence window then runs from that finalization or from F, and double-sign evidence under the old generation's chain_id can still be submitted during it.

5. Misbehavior: detection and consequences

MisbehaviorHow it is detectedConsequence
Double signing: two different BlockIDs signed for the same height, round and vote type CometBFT spots the conflicting votes in consensus messages and puts DuplicateVoteEvidence into a later block; the app receives it in the misbehavior field of FinalizeBlock. Anyone holding the two votes can also build the evidence. Anyone submits the two votes to the L1 registry. The contract applies CometBFT's VerifyDuplicateVote conditions. It rebuilds both CanonicalVotes, hashes them with Keccak-256 and recovers the same registered address with ecrecover, and that validator must be in the committee of the epoch at that height. Height, round and type must match and the BlockIDs must differ; both votes must carry the same Taiko chain_id; the evidence window must still be open. It then slashes the seat's bond, removes the seat and pays part of the bond to the submitter.
A leader leaves out IL transactions or proposes an invalid block ProcessProposal is deterministic, so every honest validator rejects the block. The round fails and the next leader takes over; the leader loses this block's revenue. No fine.
A lander on duty does not land Visible on L1: no propose during its epoch. A miss is recorded; repeated misses remove the seat from the active set. No fine.
A lander submits an invalid commit or wrong data It derives to zero blocks. At prove time its end block hash equals the previous proposal's, so L1 sees it directly. A miss plus a small fine (about one proposal's proving cost) paid to the prover. No reorg: a fallback lander or the next lander lands the blocks again.
More than 2/3 collude to censor an FI Derivation rule: a due FI must be included. Proposals that skip a due FI derive to zero blocks, so the chain can only halt; it cannot keep producing blocks while censoring.
A validator fills its IL with junk ILs are capped at 8 KiB, and the append test excuses invalid transactions. Harmless; not punished.
A validator stops voting for a long time Fully offline: it misses its landing, which is visible on L1. Online but not voting: the ABCI app counts signed blocks from decided_last_commit, writes the counts to L2 each epoch, and they reach L1 through a signal. Removed from the active set at the next freeze, with no fine; it can rejoin. See Absence in section 4 for the rule and the limits against manipulation.
More than 2/3 sign an invalid block together The hash computed by derivation does not match the commit. The segment derives to zero blocks and the chain halts. State cannot be tampered with, but the signers are not punished today; see open questions.

6. Out of scope for now

Prepaid timely-fair-exchange tickets (pay only on timely delivery, otherwise refund), a shared base fee pool, an encrypted mempool, a based fallback, sampled committees, and signed per-transaction receipts.

7. Open questions

  • Economics. Measured L2 revenue was about 0.0225 ETH per day (2026-09-23 to 09-29), which cannot support meaningful stake from fees alone. The stake asset (ETH or TAIKO) and any subsidy need to be decided first.
  • Block stuffing to evade ILs. After Proposal0026 executes, the whole base fee goes to the block's coinbase. A leader could then fill its own block cheaply and use the "block is full" exemption to skip IL transactions; a full 46M-gas block at today's 0.01 gwei base fee is about 0.00046 ETH. Leaders rotate every block, so this delays a transaction by one block per malicious leader slot. Measure the cost, and add a shared base fee pool if needed.
  • No penalty for signing invalid blocks. When more than 2/3 sign an invalid block together, the chain only halts and the signers are not punished. A mismatch between the commit and derivation is not enough to punish them: a lander could pair a valid commit with wrong data, derivation would mismatch the same way, and honest signers would be framed. Punishing them needs fault attribution. The proof would walk the CometBFT headers' last_block_id chain to check that every block's data was signed (about 0.4 KB of header per block). Only when the data matches and derivation still rejects it are the signers at fault, and the proof would then have to expose that result, which changes the verifier. Assets are safe either way, so halting alone is acceptable for now.

8. Minimal implementation checklist

Decide first

  • The stake asset (ETH or TAIKO) and where any subsidy comes from.
  • Registry parameters: seat bond, seat cap (about 100), epoch length, miss limit (1–2 suggested), evidence window, launch threshold, the fine for an invalid landing, and the fallback window (for example, the last quarter of an epoch).
  • Absence rule: signing threshold, window, and uncounted share (threshold plus share at most 1/3).

Prerequisite: Etna (in progress)

  • Derivation rules in #22189; clients in alethia-reth #248, the Go client #22207 and the Rust client #22263; Etna support in raiko2.

Contracts (taiko-mono/protocol)

  • New PreconfWhitelist implementation: stake per seat with a queue when full; freeze committeeRoot per epoch and draw landers uniformly per seat; checkProposer admits only the lander on duty early in the epoch and any active validator in the fallback window, and records misses; double-sign slashing that checks secp256k1eth signatures with ecrecover under CometBFT's VerifyDuplicateVote conditions (same height, round and type, different BlockIDs) and pays part of the slashed bond to the submitter; absence removal that verifies the L2 count contract's signal proof and removes validators below the threshold; exit locks; the launch threshold.
  • New Inbox implementation: propose no longer dequeues FIs or inserts blocks, and the due check is removed; at prove time the FI queue head advances by the proven end block's anchor (the end header is checked against the proven hash, and the FI store records enqueue block numbers); the "permissionless proposing after long-overdue FIs" path stays disabled; propose takes the expected hash of the previous proposal and reverts on a mismatch; prove finds proposals whose end block hash equals the previous one, records a miss for the proposer and pays a small fine to the prover.
  • L2 count contract: accepts only the first record for each committee epoch, and only during the next epoch; emits the record's hash through SignalService.

Consensus node (new code, the largest piece)

  • The Taiko ABCI app (Go, in-process with CometBFT v0.40): ExtendVote builds the IL; VerifyVoteExtension checks format only; PrepareProposal injects the ILs, builds the block and lays out tx0, tx1 and tx2; ProcessProposal verifies IL signatures and runs the append test, including zk gas, skipping it when the previous height has no vote extensions; FinalizeBlock returns validator updates at epoch boundaries and stores the commit; timeout_commit is tuned for about 2 s blocks.
  • Absence counting: from decided_last_commit, accumulate each validator's signed blocks and the heights committed only at round > 0; put the count transaction first in the first block of each committee epoch and check it in ProcessProposal.
  • Node rules: sync each epoch's set from the L1 registry; anchor depth; back-pressure near the derivation windows; add FI transactions to ILs automatically; keep payloads until L1 finality; secp256k1eth keys with a signer that persists its state across restarts to avoid double signing; public transaction gossip on the execution client; when committed blocks expire, waiting for the failure point F to finalize on L1 and then starting the next generation by the fixed procedure, with signer state kept per generation and no more signing for a closed generation.
  • Lander: on duty (the first three quarters of its epoch), fetch committed blocks and the last commit from CometBFT's /block and /commit, pack them into a blob and call propose, reusing the existing proposers' blob building in both clients. In the fallback window, each validator first derives the duty lander's proposal and lands only if it is missing or invalid. Every landing sets ProposeInput.deadline to the segment's deadline and covers only segments whose anchors are finalized.

Execution client (alethia-reth)

  • An interface for the append test: whether a transaction is valid against the post-block state and fits the remaining gas and zk gas. zk gas must be exact; otherwise every validator rejects an honest block the same way and the chain stalls.
  • extraData bytes 1–6 change meaning: fork-gate the BatchToLastBlock write in forkchoiceUpdated, and rebuild the RPC lookup fallback from L1 instead of scanning headers.

Derivation (spec and both clients)

  • Add the rules on top of #22189, as listed in the consensus-change table in 1.3: a new manifest version carries the last block's commit, header and two Merkle siblings; verify the commit and committee; a failed proposal derives to zero blocks; forced inclusion is checked by anchor time; extraData bytes 1–6 hold the CometBFT height and byte 0 becomes a fork constant; coinbase always comes from the manifest; the new rules apply by the proposal's L1 landing time; after expiry, recovery by generation with the expiry evidence checked (B's CometBFT header, commit, Merkle path and EVM header).
  • Implement them in taiko-client and taiko-client-rs. Committed blocks are already in the execution client, so derivation only checks hashes and fills in L1Origin. proposalId comes from derivation records (three Go call sites, one Rust). When L1 derivation disagrees with the committed chain, the client tells the ABCI app to halt and resync and never writes the head itself. Retire the whitelist preconfirmation P2P path.

Proving (raiko2)

  • Implement the derivation rules in the guest: read committeeRoot and the FI queue with storage proofs; verify commit signatures one by one (Keccak-256 and k256 recovery); produce zero blocks when the proposal content is invalid instead of panicking, but refuse to prove when the witness fails authentication. The host prepares the witness: validator list, storage proofs, FI blobs.

Launch

  • Devnet with at least 4 validators: measure the 2 s cadence, ExtendVote latency, IL propagation, landing cost, and the accuracy of the zk gas append test.
  • Audits: contracts, the ABCI app, the guest.
  • DAO proposal: upgrade the PreconfWhitelist and Inbox implementations and set the fork height. The whitelist stops at that height and CometBFT continues from it.
