PoS Preconfirmation: a CometBFT Committee on Top of Etna

Remove the preconfirmation whitelist, address preconfirmation fair exchange, and keep the on-chain result ZK-provable, with the smallest set of protocol changes.

Summary. Add an open-stake CometBFT committee on top of Etna. Every validator votes on each 2-second block and only votes for blocks that include the transactions in the inclusion lists (ILs) that the leader placed in the block. Each proposal carries the commit of its last block, and clients and raiko2 accept it only if the commit verifies. Submitting to L1 rotates among validators per epoch as a duty with no separate reward. Etna's L1 anchor rules, the bridge and L2 execution do not change. The Inbox only swaps its implementation: forced inclusion is enforced by derivation instead of being inserted at landing.

Terms

seat
A fixed-size stake unit in the registry. Voting power, leader turns and lander turns are all counted in seats.
leader
The CometBFT proposer for a height. It rotates every block by CometBFT's weighted round robin.
lander
The validator allowed to call Inbox.propose during one 384 s epoch. It only posts committed blocks.
IL
Inclusion list: transactions a validator has witnessed and requires the next block to include, FOCIL-style.
FI
Forced inclusion: a transaction submitted to the L1 forced inclusion store.
commit
CometBFT's certificate for a block: precommit signatures from more than 2/3 of the voting power.

1. Changes

1.1 L1: PreconfWhitelist becomes a staking registry; the Inbox swaps its implementation

  • Open entry with a fixed bond per seat. The registry freezes a committeeRoot (a commitment to validator keys and seat counts) once per epoch and exposes a double-sign slashing entry point.
  • Landing rights rotate per epoch. Reuse the existing per-epoch operator selection, drawing uniformly from active seats (see Lander).
  • No new Inbox is needed for the registry: _proposerChecker is immutable but points at the PreconfWhitelist proxy, so swapping the proxy implementation is enough.
  • The Inbox swaps its implementation (same proxy) for forced inclusion only:
    • propose no longer dequeues FIs or inserts FI blocks. The UnprocessedForcedInclusionIsDue check is removed and numForcedInclusions is no longer used. The FI store keeps accepting submissions.
    • The FI queue head advances at finalization by time. An FI older than its due time plus the anchor window, relative to a finalized landing, has already been checked and can be dequeued. Without this the pending count only grows, and the "fee doubles at 50 pending" rule would keep doubling the FI fee.
    • The "permissionless proposing after long-overdue FIs" path (mainnet multiplier 160, about 25.6 h) stays disabled. It is disabled in today's code; enabling it would let anyone act as a lander.

1.2 Nodes: a CometBFT consensus layer

  • CometBFT v0.40 drives the existing execution clients through the Engine API, the same structure as Berachain's BeaconKit. v1.0.1 has had no release since 2025-02, while v0.38, v0.39 and v0.40 are maintained.
  • The Taiko ABCI app (Go) runs in-process with CometBFT as a standalone component and is the only writer of the EL head, through the Engine API. Either taiko-client or taiko-client-rs pairs with it for L1 derivation, L1Origin and landing, over RPC only: committed blocks and commits come from CometBFT's /block and /commit. When L1 derivation disagrees with the committed chain, the client tells the app to halt and resync; it never writes the head itself.
  • Block cadence: the app returns next_block_delay from FinalizeBlock, computed from wall-clock time so blocks align to a 2 s grid (supported from v0.40; nodes need synchronized clocks). A failed round makes that block longer.
  • CometBFT's own mempool is disabled (nop). That requires producing empty blocks, so there is a block every 2 s even when idle. Etna's empty blocks carry no transactions and are cheap to prove.
  • The ILs ride on the vote extensions, and ProcessProposal only checks data that is inside the block. The check is therefore deterministic, as CometBFT requires, and an honest leader is never rejected because some IL arrived late.

1.3 Derivation and proving: one fork on top of Etna

The base rules are the Etna section of PR #22189. Only additions and changes are listed here.

  • What a proposal carries. Per-block manifests do not change. Each proposal adds three items for its last block:
    • The commit: CometBFT's Commit, one CommitSig per validator (address, timestamp and a 65-byte secp256k1eth signature, about 100 B each). Each validator signs a CanonicalVote that includes its own timestamp, so the messages differ and the signatures are verified one by one. The lander includes just over 2/3 of the signatures and marks the rest absent. The commit for block T is not inside block T; the lander takes it from its own node.
    • The CometBFT header, about 0.4 KB. A CometBFT block is a header plus Data (transactions), LastCommit and Evidence. The header commits to the rest through hashes such as DataHash, and the block_id.hash that validators sign is the header hash.
    • Two Merkle siblings (64 bytes). Data holds tx0 = EVM block hash, tx1 = payload and tx2 = ILs. The siblings let the proof go from DataHash to the last EVM block hash without re-serializing the payload.
  • Why only the last block. EVM parent hashes chain the segment. If the replayed segment ends in the EVM block hash the commit certifies, the whole segment matches what was committed. CometBFT's own last_block_id chain is not needed. The segment start is fixed by the previous proposal's proof; a segment that does not connect cannot produce the same last hash.
  • New checks. Client derivation and the raiko2 guest use the same rules.
    • Committee: the guest takes the L1 header for originBlockHash, gets its state root, and reads the registry's committeeRoot[epoch] with an MPT storage proof. Clients read L1 directly. The validator list in the witness (keys, seat counts) must hash to committeeRoot and must also produce the header's ValidatorsHash under CometBFT's encoding. A proposal stays inside one committee epoch.
    • Commit: the recomputed header hash equals commit.block_id.hash, and chain id and height match. Each CanonicalVote is rebuilt and hashed with Keccak-256, and its signer is recovered with k256. The signing seats must exceed 2/3. Header hashing can reuse tendermint-rs; if it lacks secp256k1eth verification, write that part directly. k256 0.13 is the version both raiko2 guests already accelerate.
    • Link to EVM: a DataHash Merkle path proves that tx0 equals the derived last EVM block hash.
    • Cost (estimate, to be measured): at most about 67 signature checks, comparable to recovering 67 more transaction senders. SHA-256 is accelerated and the MPT proof is about 1 M cycles. The total is a few percent of the per-proposal fixed cost (about 512 M cycles in raiko2's RISC0 model).
  • Public inputs do not change. The committee is read from originBlockHash, which the proposal already contains. The commit and header sit in the blob, which existing blob checks cover. The L1 verifier does not change, and the Inbox does not change for the commit.
  • No landing-dependent fields. Derived blocks must equal committed blocks byte for byte. Etna's 13-byte extraData layout [basefeeSharingPctg(1) | proposalId(6) | anchorBlockNumber(6)] stays, but bytes 1–6 change from the proposalId the Inbox assigns at landing to the CometBFT height. The EL only checks the layout, and bytes 7–12 keep the anchor number. Code that decodes proposalId from extraData must take it from derivation records or L1 events instead: Go's DecodeShastaProposalID (driver/preconf_blocks/api.go, driver/state/l1_current.go, pkg/rpc/methods.go) and Rust's decode_shasta_proposal_id (proposer/src/proposer.rs).
  • Zero blocks on failed validation. If the lander's own segment fails validation, it derives to zero blocks instead of Etna's default source, which would produce an empty block with the lander as coinbase. Failures include an invalid or malformed commit, a committee mismatch, and blocks failing Etna's checks, for example an anchor whose L1 block was reorged out. The proof must produce this zero-block result instead of failing. Otherwise one bad commit would make the proposal unprovable and block every later proof.
  • Forced inclusion is checked by derivation. Each FI is checked once, at the block whose anchor passes the FI's due time (enqueue time plus 576 s). Its transactions must already be on chain or be invalid in the current state. Otherwise the proposal's own segment derives to zero blocks. A committee that refuses due FIs can only halt the chain. The guest reads the FI queue with storage proofs against Etna's anchorStateRoot and takes FI transactions from the FI blob, which it already verifies with KZG. A lander therefore cannot insert any block, and an invalid landing at most wastes a turn.

1.4 Transaction entry

Wallets and RPC endpoints do not change. Transactions reach validators through public L2 transaction gossip, so validator execution clients must join the public network with gossip on (behind sentry nodes is fine). Inclusion takes about the gossip latency plus 250 ms plus at most one block.

2. Lander: a rotating duty

  • Role. The lander on duty packs the blocks committed since the last landing into one proposal and submits it to the Inbox. It cannot change the content, because coinbase and transactions are locked by the commit.
  • Incentive: a duty with no separate reward. Fees go to the leaders that built the blocks. The lander cannot be paid inside the blocks either, because who lands a block is unknown when the block is committed.
    • Stake per seat is fixed, landers are drawn uniformly per seat, and leaders rotate by seat weight. Each validator's share of landing cost therefore matches its share of block revenue.
    • A miss (no landing during one's epoch) is recorded, not fined. It only counts when the epochs before and after had landings, so halts do not trigger it. Repeated misses remove the seat from the active set. An invalid landing derives to zero blocks and has the same effect as a miss. Detecting it on chain would need the Inbox to store each proposal's last block hash.
    • Cost: about 75k gas plus one blob per landing. At about 225 landings per day and market tips, roughly 0.005–0.014 ETH per day (estimate), or 20–60% of current L2 revenue.
  • Timing.
    • Land once near the end of one's 384 s epoch, with 2–3 L1 slots of margin. Retry within the epoch if the transaction does not land. Anything left over is landed by the next lander.
    • The only hard deadline comes from Etna's derivation windows (timestamp 6144 s, anchor 512 L1 blocks, about 1.7 h).
    • Segment boundaries follow lander epochs. Committee epochs are a multiple of 384 s.
  • Data. Per-block manifests are unchanged (timestamp, coinbase, anchorBlockNumber, gasLimit, transactions). A proposal adds the commit (secp256k1eth, about 100 B per validator, 7–10 KB for 100 validators), the CometBFT header (about 0.4 KB) and two Merkle siblings (64 bytes). A proposal is about 4 KB today and about 15 KB with these additions, still one blob. The commit is not verified on L1, so L1 cost stays about the same.

3. Unchanged

The propose and prove flow (apart from FI), FI store submission and its 576 s due time, Etna's L1 anchor rules (parentBeaconBlockRoot holds the anchor state root and extraData bytes 7–12 hold the anchor number), SignalService and the bridge, L2 execution, and the 2 s block time.

4. Rules

  • Committee. All active seats vote; there is no sampling. Voting power is counted in seats, and a commit needs more than 2/3. The number of seats is capped (about 100), and new seats queue for free slots.
  • Launch threshold. CometBFT requires signed power strictly greater than total power × 2 / 3 with integer division. Switching from the whitelist requires at least 4 active addresses (preferably 7) and no address above 1/3 of the seats. Addresses of the same entity cannot be told apart on chain, so the threshold is approximate. One entity with 1/3 of the seats or more can halt the chain alone, and one above 2/3 can forge commits and censor alone. If exits push the set below the threshold after launch, CometBFT keeps producing with lower fault tolerance. The switch happens at one fork height: the whitelist operator stops there, CometBFT starts from that L2 head, and the two never produce blocks in parallel.

  • Keys. CometBFT v0.40's secp256k1eth validator keys: signatures over the Keccak-256 hash, 65 bytes [R‖S‖V], with Ethereum addresses. L1 checks double-sign evidence directly with ecrecover, and both raiko2 guests already accelerate k256.
  • What a preconfirmation means. The transaction is in a block that has a commit. Inclusion is guaranteed; the execution result is not. Four states must be exposed separately: committed (about 2 s), on L1, proven, and L1-finalized. The bridge and withdrawals only trust proven checkpoints.
  • Fair exchange. The tip is paid inside the transaction, so payment happens only on inclusion and the exchange is atomic. The ILs a leader puts into a block must total more than 2/3 of the voting power, so it can leave out less than 1/3. A transaction in the ILs of honest validators holding at least 1/3 therefore always has at least one IL in the block and cannot be left out. The worst case is a delay of about one block (about 2 s).
  • Slashing. Only CometBFT double signing (duplicate votes) is slashed. Withholding and lateness are not slashed; they only cost the leader the commit and the block's revenue.
  • Loss of quorum. The chain halts. There is no based fallback and no rollback of committed blocks.
  • Epoch handoff. The registry freezes the next epoch's set in advance. The app returns validator updates from FinalizeBlock two heights before the boundary (CometBFT applies them at H+2), so the first block of the new epoch already carries the new ValidatorsHash. If the new set is not ready, the chain stops at the boundary instead of skipping the handoff.
  • L1 anchor depth. Validators only vote for blocks whose anchor is far enough behind the L1 head. If the referenced L1 block is reorged out, committed blocks become invalid at derivation. Anchoring to finalized L1 blocks is safest but delays L1→L2 messages by about 13 minutes; this needs a trade-off.
  • Data retention. Validators must have the full payload before voting and keep it until the corresponding proposal is finalized on L1. Landing, and re-landing after an L1 reorg, depend on it.
  • Alignment with Etna derivation. Production stops when unlanded committed blocks approach the derivation windows (timestamp 6144 s, anchor 512 L1 blocks), so they are never derived as default blocks. A source holds at most 768 blocks (from Unzen). One epoch's segment is about 192 blocks, so one missed landing still fits; a larger backlog is split into several proposals. A proposal never spans committee epochs.
  • Forced inclusion. The FI store stays as the L1 backstop and is enforced as described in 1.3. Normally validators add FI transactions to their ILs and they are included within seconds. In the worst case a malicious majority lags anchors to the edge of the window and delays an FI by about 1.7 h; after that it must include it or halt.
  • Exit. Stake stays locked until the blocks it served are proven and finalized on L1, plus a double-sign evidence window.

5. Out of scope for now

Prepaid timely-fair-exchange tickets (pay only on timely delivery, otherwise refund), a shared base fee pool, an encrypted mempool, a based fallback, sampled committees, and signed per-transaction receipts.

6. Open questions

  • Economics. Measured L2 revenue was about 0.0225 ETH per day (2026-09-23 to 09-29), which cannot support meaningful stake from fees alone. The stake asset (ETH or TAIKO) and any subsidy need to be decided first.
  • Block stuffing to evade ILs. After Proposal0026 executes, the whole base fee goes to the block's coinbase. A leader could then fill its own block cheaply and use the "block is full" exemption to skip IL transactions; a full 46M-gas block at today's 0.01 gwei base fee is about 0.00046 ETH. Leaders rotate every block, so this delays a transaction by one block per malicious leader slot. Measure the cost, and add a shared base fee pool if needed.

7. Minimal implementation checklist

Decide first

  • The stake asset (ETH or TAIKO) and where any subsidy comes from.
  • Registry parameters: seat bond, seat cap (about 100), epoch length, miss limit, evidence window, launch threshold.

Prerequisite: Etna (in progress)

  • Derivation rules in #22189; clients in alethia-reth #248, the Go client #22207 and the Rust client #22263; Etna support in raiko2.

Contracts (taiko-mono/protocol)

  • New PreconfWhitelist implementation: stake per seat with a queue when full; freeze committeeRoot per epoch and draw landers uniformly per seat; checkProposer admits only the lander on duty and records misses; double-sign slashing that checks secp256k1eth signatures with ecrecover; exit locks; the launch threshold.
  • New Inbox implementation, forced inclusion only: propose no longer dequeues FIs or inserts blocks, and the due check is removed; the FI queue head advances at finalization by time; the "permissionless proposing after long-overdue FIs" path stays disabled.

Consensus node (new code, the largest piece)

  • The Taiko ABCI app (Go, in-process with CometBFT v0.40): ExtendVote builds the IL; VerifyVoteExtension checks format only; PrepareProposal injects the ILs, builds the block and lays out tx0, tx1 and tx2; ProcessProposal verifies IL signatures and runs the append test, including zk gas; FinalizeBlock aligns next_block_delay to 2 s, returns validator updates at epoch boundaries and stores the commit.
  • Node rules: sync each epoch's set from the L1 registry; anchor depth; back-pressure near the derivation windows; add FI transactions to ILs automatically; keep payloads until L1 finality; secp256k1eth keys with a signer that persists its state across restarts to avoid double signing; public transaction gossip on the execution client.
  • Lander: at the end of its epoch, fetch committed blocks and the last commit from CometBFT's /block and /commit, pack them into a blob and call propose, reusing the existing proposers' blob building in both clients.

Execution client (alethia-reth)

  • An interface for the append test: whether a transaction is valid against the post-block state and fits the remaining gas and zk gas. zk gas must be exact; otherwise every validator rejects an honest block the same way and the chain stalls.
  • extraData bytes 1–6 change meaning: fork-gate the BatchToLastBlock write in forkchoiceUpdated, and rebuild the RPC lookup fallback from L1 instead of scanning headers.

Derivation (spec and both clients)

  • Add the rules on top of #22189: proposals carry the last block's commit, header and two Merkle siblings; verify the commit and committee; extraData bytes 1–6 hold the CometBFT height; a segment that fails validation derives to zero blocks; forced inclusion is checked by anchor time.
  • Implement them in taiko-client and taiko-client-rs. Committed blocks are already in the execution client, so derivation only checks hashes and fills in L1Origin. proposalId comes from derivation records (three Go call sites, one Rust). When L1 derivation disagrees with the committed chain, the client tells the ABCI app to halt and resync and never writes the head itself. Retire the whitelist preconfirmation P2P path.

Proving (raiko2)

  • Implement the derivation rules in the guest: read committeeRoot and the FI queue with storage proofs; verify commit signatures one by one (Keccak-256 and k256 recovery); produce zero blocks on failure instead of panicking. The host prepares the witness: validator list, storage proofs, FI blobs.

Launch

  • Devnet with at least 4 validators: measure the 2 s cadence, ExtendVote latency, IL propagation, landing cost, and the accuracy of the zk gas append test.
  • Audits: contracts, the ABCI app, the guest.
  • DAO proposal: upgrade the PreconfWhitelist and Inbox implementations and set the fork height. The whitelist stops at that height and CometBFT continues from it.
