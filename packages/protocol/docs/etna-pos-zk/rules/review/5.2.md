# 5.2 — review notes

**Non-normative.** Nothing here can be conformed to or failed against. This is what decomposing [SPEC.md](../../SPEC.md) section 5.2 into citable statements turned up. Each item says what would close it. Only the spec owner decides.

## Normativity boundary

Under the convention in [../README.md](../README.md), a statement with an ID is normative. These sentences in 5.2 are not independent rules, deliberately:

| Sentence | Why it has no independent ID | Verdict proposed |
|---|---|---|
| "The acceptance rules use fixed limits that operator settings cannot change:" | a lead-in to the three sub-bullets, each of which has its own ID; it adds the fixed-limit scope but no separate testable condition | keep un-numbered; or fold "operator settings cannot change" into DATA-5.2-5 |
| "This is not the same as bootstrapping CometBFT from L1 alone; unlanded blocks still need the full consensus history." | a limitation of the DA recovery claim, not a requirement; section 12 item 15 repeats it | keep un-numbered |

## Q5.2-1

**"Unzen's blob encoding" is referenced but not defined or pinned**

**Text.** DATA-5.2-2: "with Unzen's blob encoding: each blob decodes to at most 130,044 bytes, every non-final blob is full, and all padding bits are 0."

**Why it matters.** The three properties do not define the encoding: field-element packing, bit order, length delimiter and the treatment of the final partial field element are all unstated. Two guests can implement the three properties and still disagree on the same bytes. The spec gives a size (130,044) but not the algorithm, and it names no version of Unzen or of the encoding. This is the "rule depends on something the spec does not fix" shape.

**Would close it.** Pin the encoding by version or content hash alongside the EL rule version, or move the full encoding into appendix A.

## Q5.2-2

**What is an "item" in the 22,020,096-byte limit?**

**Text.** DATA-5.2-5: "Exactly one complete zlib stream, with no preset dictionary and no trailing bytes; at most 64 MiB decompressed, and each item at most 22,020,096 bytes."

**Why it matters.** "Item" is undefined in 5.2. It could be each RLP item in the decompressed payload, each `executionBlock`, each transaction, or each blob. The number matches CometBFT's `block.max_bytes` in section 10, which points to `executionBlock`, but that is an inference. A payload with one large transaction or one large list header could be accepted by one reading and rejected by another.

**Would close it.** Define "item" (for example, each `executionBlock` in the payload list) and state how its size is measured (raw RLP bytes, before decompression).

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q5.2-3

**Does "re-encode byte for byte" apply to the zlib stream?**

**Text.** DATA-5.2-6: "All encodings are canonical and re-encode byte for byte."

**Why it matters.** RLP has a canonical form, so re-encoding is well defined. zlib does not: different compression levels, strategies or library versions produce different streams that decompress to the same bytes. If "all encodings" includes the zlib stream, the producer's encoder settings become consensus, but no encoder, level or version is pinned. If the sentence applies only to RLP, the text should say so. The two readings differ on every batch whose producer used a different zlib setting.

**Would close it.** Scope the sentence to the canonical encodings (RLP and any other fixed encoding) and state that the zlib stream is accepted if it decompresses correctly, or pin the exact zlib settings/implementation.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q5.2-4

**Is "Not published" a disclosure rule or a description?**

**Text.** DATA-5.2-8: "Not published: CometBFT headers, original envelopes, anchor/committee/forced witnesses, registry entries, the raw forced transaction of a skip, evidence, commits and signatures."

**Why it matters.** The sentence says what is not published, not that it must not be published. Read as a rule, it needs an actor and a consequence (what happens to a node or lander that publishes an envelope?); read as a description, a public archive of envelopes does not violate 5.2, although it changes the privacy and DA assumptions. Section 5.3's separation of private history supports the descriptive reading, but the heading "Envelope (private)" suggests the normative one.

**Would close it.** State whether publication is prohibited (and by whom, with what consequence) or whether the list merely describes the public data set.
