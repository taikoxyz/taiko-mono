## Q4.3-1

**Which ordinary rotation follows a recovery when `c + 1` is mid-epoch?**

**Text.** COMM-4.3-15: "Set targetEpoch=floor(c/L), effective immediately at c+1. Discard every pending update from the old generation; ... The next S(t) actually occurring in the new generation performs ordinary rotation; this also applies if the recovery's first block is S(t)."

**Why it matters.** `targetEpoch = floor(c/L)` names the epoch containing `c + 1`, but that epoch's switch point `S(t) = H(t) - 2` may lie at or before `c + 1`. If it does, is the recovery's initial committee the committee for the rest of that epoch (so the first ordinary rotation is the next epoch's `S(t)`), or does an `S(t)` after `c + 1` still trigger a rotation? The phrase "next S(t) actually occurring" suggests the former, but the text does not say how a partial epoch is named or when the next rotation is due. This changes committee membership timing immediately after every recovery.

**Would close it.** State the first height at which ordinary rotation re-derives after a recovery, given that `c` is a grid point but not necessarily an epoch boundary, and say whether `targetEpoch = floor(c/L)` identifies a full epoch or a partial one.

## Q4.3-2

**What is a "standby candidate", and which delay does it skip?**

**Text.** COMM-4.3-17: "`activationDelay` delays new registrations and top-up increments; already active stake and standby candidates need not wait again."

**Why it matters.** "Standby candidate" is used only here. It could mean an entry that is active but not selected in the current committee, an entry that has never been selected, or a candidate carried over from an earlier snapshot. "Need not wait again" also does not say which waiting is skipped: the registration delay, the top-up readiness block, or some other admission step. The answer changes whether a previously active entry can re-enter a committee immediately after an absence.

**Would close it.** Define "standby candidate" and list the waits that do not apply to it (and the ones that still do).

## Q4.3-3

**The set-key prose and appendix A disagree on the hashed preimage**

**Text.** COMM-4.3-6: "A key's set key is a fixed sort value: the keccak256 of the L2 chain id and the key's compressed public key (`ckPrefix ‖ ckX`), with the formula in appendix A." Appendix A: `setKey(ck) = keccak256(abi.encode("ETNA_SET_KEY_V1", l2ChainId, ckPrefix, ckX))`.

**Why it matters.** The prose summary omits the `ETNA_SET_KEY_V1` domain tag and the ABI encoding. A reader who implements the summary computes a different sort key from a reader who follows appendix A, so the same registry can produce two different committee orders. The phrase "with the formula in appendix A" resolves it for a careful reader, but a citable rule should not require resolving a conflict between its summary and its normative formula.

**Would close it.** Make the prose say "as encoded in appendix A" without restating a partial preimage, or restate the exact formula including the domain tag.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q4.3-4

**"The latest registry checkpoint at that snapshot" when no checkpoint has that exact l1Block**

**Text.** COMM-4.3-2: "Verify the complete entries and root of the latest registry checkpoint at that snapshot." COMM-4.3-12: "The proof must show the latest registry checkpoint at the selected snapshot."

**Why it matters.** A registry checkpoint is written only in L1 blocks that change an entry, so most snapshots have no checkpoint with `l1Block == snapshot`. The intended meaning is presumably the greatest checkpoint with `l1Block <= snapshot`, but "at that snapshot" can also be read as equality. The failure mode when no checkpoint exists at or before the snapshot is not stated (deployment rules out `genesisCutoff` before the first checkpoint, but a later snapshot could still precede any checkpoint if no entry has changed).

**Would close it.** Define the phrase as the latest checkpoint with `l1Block <= snapshot`, and state the outcome if none exists.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q4.3-5

**Does a duplicate eligible key reject the derivation or collapse the duplicate?**

**Text.** COMM-4.3-4: "Consensus keys are lifetime-unique; a state in which two eligible entries share a key is invalid, not extra voting power."

**Why it matters.** "A state ... is invalid" reads as a rejection of the derivation, while "not extra voting power" reads as a collapsing rule that keeps one entry and drops the other. The two readings differ observably: one halts the switch (and may persistently halt production under section 8), the other silently changes membership. The text does not say which entry would be kept if it collapses.

**Would close it.** State whether the derivation rejects, or one duplicate is dropped; if it drops, name the deterministic survivor.
