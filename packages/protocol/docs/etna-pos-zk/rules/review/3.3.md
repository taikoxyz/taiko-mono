## Q3.3-1

**max(parent's anchor, local finalized) can be an anchor the validator has not finalized**

**Text.** "The proposer picks max(parent's anchor, local L1 `finalized`)." and "In ProcessProposal, a validator checks with its own L1 node that the anchor header is canonical and finalized".

**Why it matters.** If the parent's anchor is newer than the proposer's local finalized head (for example after a reorg or while the proposer's node lags), the max selects that newer anchor, but the validator is required to reject any anchor its own L1 node does not see as finalized. The proposer then has no anchor that satisfies both rules from its own view, and the two clauses point in opposite directions. Section 3.4's "No usable anchor, no block" says L2 pauses until a usable finalized anchor exists, which suggests the proposer's set is finalized anchors only, but this sentence does not say so.

**Would close it.** state the admissible set for the proposer (for example "max over finalized anchors, including the parent's anchor only if it is still finalized") and what a validator does when its own finalized view is behind.

## Q3.3-2

**"Retained proposal" is undefined**

**Text.** "A retained proposal keeps its original anchor." Section 3.4 adds "a locked block re-proposed unchanged in a later round might never gather more than 2/3 of the voting power".

**Why it matters.** The rule changes which anchor a proposal may carry, but the spec never defines when a proposal is "retained" or "locked": is it the same block hash re-proposed in a later round, a proposal the proposer has locked on, or any proposal not yet decided? It also does not say whether the retained proposal may change its timestamp, beneficiary, or other BFT-time-dependent fields while keeping the anchor. A validator cannot tell when the exception applies, and an implementer cannot tell when the max rule resumes.

**Would close it.** define "retained proposal" (and its relationship to CometBFT's lock/unlock) and state which fields must remain byte-identical while the anchor is retained.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q3.3-3

**The 4,096-byte bound does not say what is measured**

**Text.** "`rawL1Header` must be an RLP list of at most 4,096 bytes with at least 12 items."

**Why it matters.** `rawL1Header` is carried as an RLP byte string holding the L1 header's raw RLP. "An RLP list of at most 4,096 bytes" could mean the raw header bytes (the byte string's content), the list payload excluding its own prefix, or the re-encoded list. The boundary is testable and consensus-relevant: a header just over the limit is accepted under one reading and rejected under another, and the witness is byte-authenticated by `keccak256(rawL1Header)`.

**Would close it.** state that the bound is the length in bytes of `rawL1Header` (or of its RLP payload), and whether the list prefix counts.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q3.3-4

**The "matches but cannot be parsed" branch conflicts with accepting appended fields**

**Text.** "Every other item need only be a well-formed RLP item and is not interpreted, so fields an L1 fork appends at the end (for example Glamsterdam's EIP-7928 `block_access_list_hash`) are accepted without an upgrade. ... if they match but the header cannot be parsed under this rule, L1 has changed the header format and the node needs an upgrade, which is a liveness pause (section 8), not a safety halt."

**Why it matters.** Under the stated decoding rule, the failure modes are fewer than 12 items, a wrong-length field 0 or 3, a non-canonical integer in field 8 or 11, or an over-long list. Those describe a removed, resized or reordered header field, not an appended one, and the text explicitly accepts appended items. So either the parse-failure branch is unreachable (and the pause rule is dead), or it is meant to cover a different failure (for example the raw bytes not being an RLP list at all). The branch decides pause versus safety halt, so the two readings have different operational consequences.

**Would close it.** give at least one concrete canonical-header parse failure that implies "L1 has changed the header format", and reconcile it with the rule that unknown appended items are accepted.

Raised by: DeepSeek-V4.1-Flash (dantaik)
