## Q3.1-1

**"Stock" and "not forked" are not observable**

**Text.** "Stock CometBFT v0.40.0 in its own process, driving the application over an ABCI++ socket. Proposer selection, timeouts, locking and BlockID all use stock behavior; the engine is not forked."

**Why it matters.** Only the version string is pinned. A build with local patches can still report v0.40.0, and "stock behavior" has no test: the four listed mechanisms are exactly where a fork would be invisible from the outside until a producer and a validator disagree. Two nodes claiming conformance can implement different locking or timeout rules and both point at this sentence.

**Would close it.** pin the build (release hash or image) and the non-default flags, or define the observable behavior that "stock" means and where it is checked (startup, acceptance, or a cross-implementation vector).

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q3.1-2

**`app_hash` names no hash function or object**

**Text.** "`app_hash` is the hash of the executed EL block (InitChain returns the genesis hash for the initial deployment and `ELHash(c)` for governance recovery under 8.4)".

**Why it matters.** "The hash of the executed EL block" could be the EL block hash, the stateRoot, or a hash over the header. `ELHash(c)` is used in 8.4 without a definition. ABCI compares `app_hash` across nodes and persists it as the application hash, so an implementation that chooses a different object can agree on execution and still produce a different app hash; a light client or snapshot check would then accept or reject the wrong chain.

**Would close it.** define the value algebraically (for example "the EL block hash at that height") and define `ELHash(c)` in the same place, citing the encoding section.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q3.1-3

**"at height 0 Info" does not match the ABCI call shape**

**Text.** "at height 0 Info returns the app version in this generation's genesis consensus params".

**Why it matters.** ABCI's `Info` request carries a version string and block version, not a height; there is no "Info at height 0" call. The sentence may mean "before the first block", "the app version in the genesis consensus params", or "the version reported by the first Info call". The app version also feeds CometBFT's compatibility check, so an implementer needs to know which response field is meant.

**Would close it.** restate the requirement in ABCI terms (which request, which response field, what value) or move the app-version rule to the startup section where the handshake is described.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q3.1-4

**The external ZK Gas spec is adopted by reference, without a complete pin**

**Text.** "adopt the [ZK Gas spec] ([pinned revision]) for metering, transaction intrinsic cost, opcode/precompile multipliers, CALL/CREATE spawn estimates, uint64 overflow handling and whole-transaction discard ... Publish the enabled revision, parameters and shared vectors with the pinned EL/guest versions; later main-branch changes do not automatically change consensus."

**Why it matters.** The rule adopts an external document by reference and enumerates six topics with "for", but the external document also contains definitions, limits and its own skip rule (which is expressly not adopted). A reader cannot tell which of its remaining clauses bind. The pin is a git commit URL, not a content hash, and "publish" has no location or format, so two deployments can claim the same revision while using different parameters or vectors.

**Would close it.** enumerate the adopted sections/parameters and the ones excluded, pin a content hash in the deployment manifest, and state where the revision, parameters and vectors are published and who checks them.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q3.1-5

**"Remembered overflows" is undefined**

**Text.** "the recommended policy skips that transaction and its sender's later nonces ... This policy applies only to pool candidates; an FI transaction the proposer places at position 0 is executed against the actual pre-block state and is never skipped because of remembered overflows."

**Why it matters.** The guarantee for a forced transaction turns on what is remembered: which component remembers an overflow, for which sender/nonce, for how long (within the block, across blocks, across restarts), and whether it survives a reorg. The text says the pool policy is not a consensus rule, yet the FI clause uses the policy's memory as a premise. Two proposers can both claim conformance while one skips an FI transaction that the other includes.

**Would close it.** define "remembered overflow" (state, scope, lifetime) or restate the FI guarantee without referring to build policy — for example "the FI transaction at position 0 is always executed against the pre-block state, regardless of any prior trial".

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q3.1-6

**EVM OOG and zk metering overflow are not ordered**

**Text.** "a transaction exceeding the zk budget or overflowing metering arithmetic is fully discarded ... An ordinary EVM revert/OOG remains an included transaction when it fits the zk budget and is charged normally."

**Why it matters.** zk gas is metered from execution (opcodes, CALL/CREATE spawn estimates). An EVM OOG stops execution at a different point than a completed transaction, so whether it "fits the zk budget" depends on whether metering runs alongside EVM execution, stops at OOG, or is computed from the final trace. The two rules can both apply to one transaction, and the outcomes differ: included with charged gas, or discarded with no fee and no difficulty contribution.

**Would close it.** state the order and the boundary — for example "metering runs during execution; an EVM OOG stops both execution and metering and the transaction is included; only exceeding the zk budget or uint64 metering overflow discards it".

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q3.1-7

**`eth_call` / `eth_estimateGas` is an API rule inside a consensus section**

**Text.** "`eth_call`/`eth_estimateGas` use the same rules version with the full block zk budget for standalone simulation; report explicit zk-limit errors rather than a successful empty result after discarding the call."

**Why it matters.** These are node RPC methods, not block properties; no other node can observe whether a given RPC used the full budget or returned the right error. Numbering it as a rule makes it citable, but its enforcement point and consequence are unstated, and an implementer may reasonably treat it as client guidance. The contrast with the surrounding consensus rules makes the section's boundary unclear.

**Would close it.** state whether this is a normative node-API requirement (and where it is tested) or guidance, and if normative, name the error shape and the request fields that select the full block budget.

Raised by: DeepSeek-V4.1-Flash (dantaik)
