## Q8.4-1

**"A missing record is rejected" — by which component, and how?**

**Text.** "A missing record is rejected; mapping defaults or the latest checkpoint are not substitutes."

**Why it matters.** A slot-290 record is read by at least three parties: `land` (6.1 step 2, which reverts on a missing origin), a node at startup and while proving, and a guest. "Rejected" means a revert for the first, a proposal rejection or halt for the second, and a failed proof for the third. The text does not distinguish them, and the consequence differs for each.

**Would close it.** Name the checkers and what each does on a missing record.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q8.4-2

**What is generation 0's origin record used for?**

**Text.** "generation 0 is (0, L1_0, the initialization transaction's L1 timestamp) and only describes genesis."

**Why it matters.** "Only describes genesis" excludes it from being a recovery origin, but the record is also the source for 3.4 rule 3's "current generation's L1 origin" (which is `L1_0` for generation 0) and for `generationStartHeight`. A reader cannot tell whether generation 0's record is used by those checks or is purely documentary.

**Would close it.** List the uses of generation 0's record (anchor floor, start height) and say whether it is exempt from the recover-time rules.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q8.4-3

**The orphan generation's record is retained, and reads may expose it**

**Text.** "Each record is written once and never overwritten or deleted." Together with the verifier-failure rollback, which does not change the generation, and 8.3's "generation never decreases."

**Why it matters.** A recovery that ran at a c above the restored one leaves a permanently written origin record for a generation that cannot land. `generationStartHeight` and `recoverySnapshot` read slot 290 directly; nothing says which generation they read or what they return when asked about the abandoned one. A node or guest can read the orphan record and treat it as live.

**Would close it.** State that the abandoned generation is not authenticated or signed, and that reads are always for the current generation only.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q8.4-4

**Who writes generation 0's record at initialization?**

**Text.** "generation 0 is (0, L1_0, the initialization transaction's L1 timestamp)". Section 10 item 5 says initialization sets "generation 0's origin under 8.4".

**Why it matters.** "Each record is written once" needs a first writer. If initialization writes generation 0's record, then the write-once rule applies from initialization; if the record is virtual (derived from `L1_0`), the storage layout in appendix B slot 290 is inconsistent with the text. The initialization timestamp is also only known from the transaction's L1 block, which the Inbox can read.

**Would close it.** State that Inbox initialization writes generation 0's record in the same transaction, and confirm that the write-once rule then applies.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q8.4-5

**How does InitChain obtain c's EL hash and stateRoot?**

**Text.** "`chain_id` uses the new generation, `initial_height=c+1`, `genesis_time=R.timestamp`, and InitChain returns `app_hash=ELHash(c)`; EL state must match c's authenticated EL hash and stateRoot."

**Why it matters.** InitChain receives the genesis document. For a recovery generation, that document must carry c's authenticated EL hash and stateRoot so the app can compare the EL state and return `app_hash`. Section 10's initial-deployment genesis carries the L1 header and Inbox proof; 8.4 does not say what the recovery genesis carries or how InitChain authenticates those values. Without that, "EL state must match" has no stated source of truth.

**Would close it.** State the recovery genesis parameters and the authentication path (the retained c record, the Inbox proof, and the reference to the origin record).

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q8.4-7

**May the first block's anchor be later than R?**

**Text.** "The first block must carry a finalized anchor witness no earlier than R and does not use c's anchor."

**Why it matters.** "No earlier than R" allows any finalized anchor at or after R, including one much later. But the committee is selected from R's snapshot, and the origin record is R; the first block could be built with an anchor R+100 if that block is finalized. That is consistent with the words, but it means the first block's witness proves a different L1 state than the one that authenticated the recovery. Whether that is intended affects what a joining node must verify first.

**Would close it.** State whether any finalized anchor at or after R is acceptable, and confirm that the committee remains the one selected on R regardless of the first block's anchor.

Raised by: DeepSeek-V4.1-Flash (dantaik)
