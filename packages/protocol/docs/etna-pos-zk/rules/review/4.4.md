# 4.4 — review notes

**Non-normative.** Nothing here can be conformed to or failed against. This is what decomposing [SPEC.md](../../SPEC.md) section 4.4 into citable statements turned up: questions the text does not settle, and the boundary between a protocol rule and a governance responsibility. Each item says what would close it. Only the spec owner decides.

## Normativity boundary

Under the convention in [../README.md](../README.md), a statement with an ID is normative. These sentences in 4.4 are not independent rules, deliberately:

| Sentence                                                                                                                                                                 | Why it has no independent ID                 | Verdict proposed                                               |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------- | -------------------------------------------------------------- |
| "Before execution the DAO assesses replacement availability, online quorum and concentration, since normal-operation forced exits may stall a later rotation."           | governance diligence, not a registry check   | keep un-numbered; operational guidance                         |
| "This version has a single-entry API."                                                                                                                                   | a description of the current interface       | keep un-numbered; a limitation, not a rule                     |
| "Execute entries independently when failures must not affect each other; do not couple forfeiture to a potentially stale recover in an all-or-nothing governance batch." | operational advice to the DAO about batching | keep un-numbered; see Q4.4-4 for the related ordering sentence |

## Q4.4-1

**Is `forfeit` callable by the registry owner, the DAO, or both?**

**Text.** FORF-4.4-1: "`forfeit(bondId, entryKey, incidentId, validUntil)` is callable only by the registry owner, the DAO's actual execution address (the Controller where used), and only after Inbox initialization."

**Why it matters.** The comma list can be read as two authorized callers (the registry owner, plus the DAO's execution address) or as one appositive (the registry owner is the DAO's actual execution address). If it is two, a registry owner that is not the DAO can forfeit unilaterally, which contradicts section 1's statement that only the DAO authorizes forfeiture. If it is one, the registry owner must be the DAO/Controller, and the sentence should say so. The authority model is the core of this governance power.

Appendix A's interface sketch adds a third statement that bears directly on the reading: `// forfeit is registry-owner-only, once per lifetime entryKey; no forfeiture nonce or revocation.` (ENC-A-55, with the interface at ENC-A-54). It supports the **one-caller** reading, but it does not say _who_ the registry owner is: if the registry owner is not the DAO's execution address, the appendix confirms exactly the unilateral case this question is about. It also adds two requirements the normative section does not state - **once per lifetime entryKey** and **no revocation** - while FORF-4.4-1's `validUntil` expiry is not reconciled with either.

**Would close it.** Say whether the registry owner and the DAO's execution address are the same address, and if not, whether both may call independently or only the DAO's execution address may.

## Q4.4-2

**What does "the DAO authorization binds the deployment, full call parameters and published attribution" mean on-chain?**

**Text.** FORF-4.4-3: "The DAO authorization binds the deployment, full call parameters and published attribution." The call itself is `forfeit(bondId, entryKey, incidentId, validUntil)`. Section 1 adds: "It checks authority, entry identity, amount and authorization expiry, not the correctness of attribution."

**Why it matters.** The registry call carries no deployment id, no hash of the authorization, and no attribution payload; there is no on-chain authorization object to compare. So "binds" cannot be an on-chain check — it must be a governance-process requirement enforced by the DAO's execution path. The text does not say where the authorization and attribution are published, how a caller demonstrates they match, or what happens if the Controller executes a call that does not match. This is the line between a protocol rule and a governance responsibility, and it is currently on the governance side without being labelled as such.

**Would close it.** State explicitly that the binding is enforced off-chain by the DAO's execution path (and where the attribution is published), or add the binding fields and an on-chain check.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q4.4-3

**Is `incidentId` a unique incident identifier or an opaque label?**

**Text.** FORF-4.4-3: "`incidentId` identifies that attribution; the same incident may name multiple entries. The registry keeps no incident case or global incident-id deduplication state."

**Why it matters.** "Identifies" suggests uniqueness, but the registry keeps no dedup state, so the same `incidentId` can be reused for an unrelated later attribution, and only the per-entry `entryKey` flag prevents a second forfeiture on the same entry. If an off-chain indexer treats `incidentId` as a key, a reused id merges two incidents. If it is an opaque label, the text should not say it "identifies" an attribution without saying who guarantees the mapping.

**Would close it.** State that `incidentId` is an opaque label with no uniqueness guarantee, or define the off-chain registry/indexer that gives it meaning and the uniqueness rule.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q4.4-4

**Is "Execute before lawful withdrawal" a protocol rule or operational advice?**

**Text.** FORF-4.4-20: "Execute before lawful withdrawal; this mechanism cannot recover withdrawn funds." The same bullet also says "Before execution the DAO assesses replacement availability, online quorum and concentration".

**Why it matters.** The registry cannot order two transactions across a block. If a lawful withdrawal executes first, forfeiture finds `balance == 0` and fails under FORF-4.4-4; the second clause says exactly that. So "Execute before" is either an operational instruction to the DAO (the only actor who can sequence the calls) or a normative ordering duty with no stated enforcement mechanism. Treating it as a rule would require an ordering primitive the text does not provide.

**Would close it.** State whether this is a normative ordering duty (and who enforces it) or operational guidance that follows from the balance check. If it is guidance, move it next to the other DAO diligence sentences.
