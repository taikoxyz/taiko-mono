## Q2-1

**Is the component table normative?**

**Text.** Each row describes a component in the present tense, for example: "Validator | Stakes TAIKO in the registry and registers a secp256k1eth consensus key ... runs stock CometBFT ..."; "Full node | Runs CometBFT ... independently validates every block ...".

**Why it matters.** The rows contain requirements without a requirement verb: "independently validates", "has no registered signing key", "earns no protocol reward". If the table is descriptive, a deployment that runs a different stack conforms to every actual rule in the spec. If it is normative, the enforcement point and the consequence are unstated. The two readings change what a "validator" is for sections 4, 9 and 10.

**Would close it.** state whether the table is normative, and for each row either add a rule with an observable obligation or mark the row descriptive.

## Q2-2

**Which validator-stack clauses are mandatory?**

**Text.** "runs stock CometBFT, the ABCI application, alethia-reth and its own L1 node, plus the external FilePV signer behind the checkpoint-trust gate."

**Why it matters.** A validator could satisfy the consensus rules while using a different EL, a remote L1 node, or an HSM signer instead of FilePV. The row reads as a deployment checklist, but it is not stated which items are protocol requirements and which are an example implementation. The distinction matters for audits and for the signer requirements in sections 8.2 and 9.

**Would close it.** split the row into mandatory components (with the rule that requires each) and descriptive ones, or say explicitly that the row is a reference configuration.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q2-3

**What is a "full node", and is independent validation required?**

**Text.** "Runs CometBFT, the ABCI application and alethia-reth with its own L1 view, independently validates every block and applies the same checkpoint-trust gate. It has no registered signing key".

**Why it matters.** The spec uses "full node" only here. A public RPC service that follows the chain without validating would satisfy "has no registered signing key" but not "independently validates every block". Since no rule elsewhere imposes validation on non-validators, this row is the only candidate source of that obligation, and it has no consequence.

**Would close it.** define the classes of node the protocol recognises and state which are required to validate and apply the trust gate.

Raised by: DeepSeek-V4.1-Flash (dantaik)

## Q2-4

**Two row clauses carry unstated scope**

**Text.** "Lander | Permissionless ...; earns no protocol reward (appendix C)" and "one checkpoint for every L1 block that changes an entry".

**Why it matters.** "Earns no protocol reward" could be a statement about the current design or a rule that a future reward mechanism would violate; appendix C treats landing as DAO-funded, so the economic assumption and the component row may diverge. Separately, "one checkpoint for every L1 block that changes an entry" does not say whether a block changing several entries writes one checkpoint or one per entry; section 4.1 repeats the phrase, so the ambiguity propagates.

**Would close it.** say whether the no-reward clause is a rule or an economic fact, and state the checkpoint cardinality for a block that changes multiple entries.
