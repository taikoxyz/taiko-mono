## Q6.4-2

**Which anchor's checkpoint the bound uses**

**Text.** "L2 height cannot exceed the anchor-proven lastCheckpoint.height + U" … "An anchor is a finalized L1 block, and checkpoints only advance, so anchor-based accounting never undercounts unsettled blocks".

**Why it matters.** A node can hold several anchors — newly carried, inherited, older than `maxAnchorAge`, or not yet adopted — and the bound is computed from one of them. A stale or older anchor lowers the bound and pauses earlier; a newer one raises it. "Anchor-proven" and "finalized L1 block" narrow the field but do not say which of several finalized anchors is authoritative, or what a node does while its newest anchor is older than `maxAnchorAge`. 6.2's inherited anchor is a different object again.

**Would close it.** define the accounting anchor (latest adopted finalized anchor, with a tie-break) and the behaviour while no anchor is fresh enough.

## Q6.4-3

**How the chain binds `U`**

**Text.** "U is an integer parameter committed directly in the config hash" … "U is fixed at deployment and cannot be overridden by local node configuration."

**Why it matters.** Section 11 lists `U` under "config hash", but 6.2's statement names only `committeeConfigHash`, and 6.4 does not say that `U` is part of the value the statement authenticates. If `U` is not authenticated by the statement, two nodes with different `U` can follow the same chain and disagree about when to pause — the exact node-splitting failure section 11 says its parameter principle exists to prevent. It is also unstated what a node does when it sees a config hash carrying a different `U`: reject the block, the chain, or the pause only.

**Would close it.** say which hash contains `U`, that the statement (or another authenticated value) commits to it, and what a mismatch causes.

## Q6.4-4

**The latency-budget toggle mixes targets with rules**

**Text.** "Exceeding the allowance causes a normal pause, never a bypass of U" … "settlement throughput must keep pace without a growing unsettled backlog" … "The 20 min finality/adoption component neither bounds L1 finality nor relaxes maxAnchorAge."

**Why it matters.** The paragraph opens by calling the interval an operating target and disclaims any SLA, yet in between it uses "must", "never", and a statement that does not relax `maxAnchorAge` — all rule-shaped. Because it sits in a details toggle, a reader cannot tell which sentences are binding. The "normal pause" sentence names the consequence of exceeding the allowance inside that toggle; the binding statements are 3.4 rule 5 (a block above the bound is invalid) and section 8's back-pressure liveness pause.

**Would close it.** split the arithmetic from the rules (or mark the normative sentences and give them IDs), and state the pause consequence in the main paragraph.

## Q6.4-5

**The Acceptance paragraph has no clear status, and "resource limits" is undefined**

**Text.** "**Acceptance**: before using the target configuration, pass the resource and latency acceptance in [Etna Acceptance and Launch Checklist](../../ACCEPTANCE.md); until then, do not claim deployment readiness or target attainment. Do not omit latest-checkpoint checks, use non-finalized anchors, remove a proof, locally loosen U or silently expand resource limits."

**Why it matters.** This reads as a launch-gate policy, but it is placed in the section as if it were a protocol rule, and "silently expand resource limits" has no referent: which limits, what counts as silent, and who observes the expansion. A chain cannot enforce "do not claim readiness", so the paragraph's owner and enforcement point are unstated. The same applies to "Publish the selected L and its nominal epoch duration" in the previous paragraph — published where, and to whom?

**Would close it.** classify the paragraph (normative deployment requirement with an owner, or guidance), define "resource limits", and name the publication venue for `L`.
