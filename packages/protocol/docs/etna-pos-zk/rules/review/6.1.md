# 6.1 — review notes

**Non-normative.** Nothing here can be conformed to or failed against. This is what decomposing [SPEC.md](../../SPEC.md) section 6.1 into citable rules turned up: questions the text does not settle, and sentences whose normative status was ambiguous. Each item says what would close it.

## Normativity boundary

Under the convention in [../README.md](../README.md), a statement with an ID is normative and everything else is not. These sentences in 6.1 carry no ID, deliberately — confirming each is a judgement call worth an explicit decision:

| Sentence                                           | Why it has no ID                                                                | Verdict proposed     |
| -------------------------------------------------- | ------------------------------------------------------------------------------- | -------------------- |
| the fenced `land` listing and its `<summary>` line | code is never normative under the convention, and an ID must not sit in a fence | see [Q6.1-1](#q61-1) |

## Q6.1-1

**The reference Solidity toggle carries checks the prose never states**

**Text.** "The reference Solidity in the toggle below lists every check land performs; the checks are normative." … "Local names and helper bodies are illustrative: helper results are defined in appendix A and the comments".

**Why it matters.** The convention says a code block is never normative, but this sentence makes the toggle's _checks_ normative while leaving its bodies illustrative — and several checks exist nowhere else: the generation rule for the origin record and its generation-origin exception, `h - p <= maxBatchBlocks`, `h < 2**48`, `headAfter <= fiTail` and `headAfter - fiHead <= h - c`, the 1–6 blob count, the readable-hash window for the reference block, the leaf-count predicate, and the landing record's parent. An implementation that follows only the prose would omit most of these and still believe it conforms. This is the "normative content lives where the convention says it cannot" shape, and it is the largest single ambiguity in 6.1.

**Would close it.** restate each check in prose (or move the normative content into appendix A outside a fence), leaving the toggle as a worked example; or explicitly incorporate the toggle by reference as normative text and record that the "code is never normative" rule does not apply to it.

## Q6.1-3

**Which fields "the current checkpoint record" covers in the leaf-at-c check**

**Text.** "the leaves are exactly those of the grid points in (p,h) and the leaf at c matches the current checkpoint record".

**Why it matters.** "Checkpoint record" could mean `lastCheckpoint` (height and EL block hash) alone, or the slot 285 landing record (EL hash, Comet hash, FI cursor). The appendix A leaf contains all of those words. The prose also does not say that the FI cursor in `c`'s record must equal the current FI head; that requirement is stated only in the fence. Two implementations that both cite LAND-6.1-8 can therefore accept different leaves, and only one of them is consistent with the leaf encoding.

**Would close it.** enumerate the compared fields (height, EL hash, Comet hash, FI cursor) and say explicitly whether the FI-cursor equality is part of this check or of the FI-head check.

## Q6.1-4

**The slot 285 record's parent is specified only in the fence**

**Text.** "Once all pass, land atomically updates the checkpoint, snapshot, FI head, slot 285 record and SignalService."

**Why it matters.** The prose says a record is written, not what its parent is. The fence stores actual `c`, never proof origin `p` — and that choice is load-bearing: 6.3 lets a later proof start from "an authenticated, retained historical checkpoint p", and 6.1's origin check reads the record's generation. An implementation that stores `p` still passes the origin check, so no vector in 6.1 or 6.3 detects it, yet the landing graph no longer describes how checkpoints were reached.

**Would close it.** state the record's parent field (actual `c`) and whether `p` is stored anywhere at all.

## Q6.1-5

**"The checks are, in order" versus "the remaining order is illustrative"**

**Text.** "The checks are, in order: range, grid and origin record; the leaves are exactly those of the grid points in (p,h) and the leaf at c matches the current checkpoint record; FI head advance; reference block and blobs; computing cutHash and verifying both proofs." … "the remaining order is illustrative."

**Why it matters.** The two sentences can be read as (a) the enumerated order is binding and only the internal order within a check group is illustrative, or (b) only two ordering constraints bind — all checks before any state change, and the leaf checks before proof verification — while the enumeration is presentation. The readings differ observably: under (a), verifying proofs before the range check does not conform; under (b) it does. A vector cannot settle it, because the difference is in what a conformance test may assert.

**Would close it.** say which ordering constraints are normative, or delete "in order" and keep only the two explicit ordering rules.
