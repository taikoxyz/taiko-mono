# 3.3 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). This file asserts only what the text says: each vector follows from the cited anchor rule, or reports that it is contradicted. Where the text states a requirement but **not the consequence of violating it**, the row says "violates <ID>" and names no outcome. Undetermined items are under "Not covered" and in [review/3.3.md](../review/3.3.md).

`accept` means the described block satisfies the cited statement. `reject` means it does not; only CONS-3.3-7 states an outcome for one of its failures, and that outcome is quoted.

## CONS-3.3-1

| Vector     | Setup                                                                                          | Expected            |
| ---------- | ---------------------------------------------------------------------------------------------- | ------------------- |
| 1.a accept | a block carries an anchor witness: the raw L1 header plus the Inbox account and storage proofs | conforms            |
| 1.b accept | a block carries no witness and inherits its parent's anchor                                    | conforms            |
| 1.c reject | a block has neither a witness nor an inherited anchor                                          | violates CONS-3.3-1 |
| 1.d accept | the anchor is the L1 block whose state the block reads, identified by the witness's header     | conforms            |

## CONS-3.3-2

| Vector     | Setup                                                     | Expected                                                         |
| ---------- | --------------------------------------------------------- | ---------------------------------------------------------------- |
| 2.a accept | the first block of a generation carries an anchor witness | conforms                                                         |
| 2.b accept | a block moves the anchor and carries a witness            | conforms                                                         |
| 2.c accept | a block keeps the anchor and carries no witness           | conforms                                                         |
| 2.d reject | the first block of a generation carries no witness        | violates "The first block of each generation ... must carry one" |
| 2.e reject | a block moves the anchor but inherits without a witness   | violates "any block that moves the anchor must carry one"        |
| 2.f reject | a block keeps the anchor but carries a witness            | violates "a block that keeps the anchor must not"                |

## CONS-3.3-3

| Vector     | Setup                                                                                                                                   | Expected                                 |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| 3.a accept | the witness proves the Inbox's `recoveryGeneration`, `lastCheckpoint` (height and hash), and the forced inclusion queue's head and tail | conforms                                 |
| 3.b reject | the witness omits `recoveryGeneration`                                                                                                  | violates CONS-3.3-3                      |
| 3.c reject | the witness proves `lastCheckpoint`'s height but not its hash                                                                           | violates "lastCheckpoint (height, hash)" |
| 3.d reject | the witness omits the forced inclusion queue's head or tail                                                                             | violates CONS-3.3-3                      |

## CONS-3.3-4

| Vector     | Setup                                                                          | Expected                                                 |
| ---------- | ------------------------------------------------------------------------------ | -------------------------------------------------------- |
| 4.a accept | the proposer picks max(parent's anchor, local L1 `finalized`)                  | conforms                                                 |
| 4.b reject | the proposer picks an anchor older than the parent's anchor                    | violates "max(parent's anchor, ...)"                     |
| 4.c reject | the proposer picks an anchor older than local L1 `finalized`                   | violates the max                                         |
| 4.d accept | a retained proposal keeps its original anchor after local `finalized` advances | conforms                                                 |
| 4.e reject | a retained proposal is re-anchored to a newer L1 block                         | violates "A retained proposal keeps its original anchor" |

_What "retained proposal" means, and what happens when the parent's anchor is newer than local `finalized`: no vector — [Q3.3-1](../review/3.3.md#q33-1)._

## CONS-3.3-5

| Vector     | Setup                                                                                                                                                                      | Expected                                                                             |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 5.a accept | in ProcessProposal the validator checks with its own L1 node that the anchor header is canonical and finalized, and checks its age against the candidate block's timestamp | conforms                                                                             |
| 5.b reject | the validator accepts an anchor header that its L1 node does not see as canonical                                                                                          | violates "canonical"                                                                 |
| 5.c reject | the validator accepts an anchor header that is not finalized                                                                                                               | violates "finalized"                                                                 |
| 5.d reject | the validator rejects a proposal solely because its local finalized head advanced, with no age violation                                                                   | violates "advancing the local finalized head alone cannot make that proposal expire" |
| 5.e accept | local `finalized` advances while a retained proposal keeps its original anchor; the proposal is not expired by that alone                                                  | conforms                                                                             |

## CONS-3.3-6

| Vector     | Setup                                                                                      | Expected                         |
| ---------- | ------------------------------------------------------------------------------------------ | -------------------------------- |
| 6.a accept | `rawL1Header` is an RLP list of 4,096 bytes with 12 items; fields 0, 3, 8 and 11 are valid | conforms                         |
| 6.b reject | `rawL1Header` is an RLP list of 4,097 bytes                                                | violates "at most 4,096 bytes"   |
| 6.c reject | `rawL1Header` has 11 items                                                                 | violates "at least 12 items"     |
| 6.d accept | a later L1 fork appends a 13th well-formed RLP item (for example a block-access-list hash) | accepted and not interpreted     |
| 6.e reject | field 0 `parentHash` is 31 bytes                                                           | violates "32 bytes each"         |
| 6.f reject | field 8 `number` has a leading zero                                                        | violates "without leading zeros" |
| 6.g reject | field 11 `timestamp` is 9 bytes                                                            | violates "at most 8 bytes"       |

_Whether the 4,096-byte bound is over the raw header bytes or the RLP payload: no vector — [Q3.3-3](../review/3.3.md#q33-3)._

## CONS-3.3-7

| Vector     | Setup                                                                                                        | Expected                                    |
| ---------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------- |
| 7.a accept | a header's identity is `keccak256(rawL1Header)` over the raw bytes; it is never decoded and re-encoded       | conforms                                    |
| 7.b reject | the node decodes and re-encodes the header before hashing                                                    | violates "never decoded and re-encoded"     |
| 7.c reject | the node fetches the canonical hash for the anchor block number and it differs from `keccak256(rawL1Header)` | the witness is invalid (stated)             |
| 7.d accept | the canonical hashes match, but the header cannot be parsed under this rule                                  | liveness pause, not a safety halt (stated)  |
| 7.e reject | a canonical-but-unparsable header is treated as a safety halt                                                | violates "not a safety halt"                |
| 7.f accept | a node reads another header from its own L1 node using only the four fields and ignores unknown items        | conforms                                    |
| 7.g reject | a node interprets an unknown item in another L1 header                                                       | violates "relies only on these four fields" |

_How a canonical header can fail parsing when unknown trailing items are accepted: no vector — [Q3.3-4](../review/3.3.md#q33-4)._
