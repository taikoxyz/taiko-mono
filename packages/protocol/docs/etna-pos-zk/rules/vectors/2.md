# 2 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). Section 2 is a component table, so a vector describes a deployment's component and asks whether it matches its row. `accept` means it does; `reject` means the row is contradicted. No block is accepted or rejected by these vectors, and no enforcement consequence is implied where the text states none. Gaps are in [review/2.md](../review/2.md).

## COMP-2-1

| Vector | Setup | Expected |
|---|---|---|
| 1.a accept | a validator stakes TAIKO, registers a secp256k1eth consensus key with a key-holder signature, and runs stock CometBFT, the ABCI application, alethia-reth and its own L1 node, plus the external FilePV signer behind the checkpoint-trust gate | matches the Validator row |
| 1.b reject | the same validator registers without a key-holder signature | violates COMP-2-1 ("with a key-holder signature") |
| 1.c reject | the registered signing key or the anti-double-sign state is stored inside the Comet home/mount | violates COMP-2-1 ("stay outside the Comet home/mount") |
| 1.d reject | a signature is produced without the app's checkpoint-trust authorization | violates COMP-2-1 ("signatures require the app's checkpoint-trust authorization") |
| 1.e accept | the proposer receives all base fees and tips of the blocks it produces | conforms to COMP-2-1 |

*Whether every clause of the row is mandatory for a validator, or only descriptive of a reference implementation: no vector — [Q2-1](../review/2.md#q2-1).*

## COMP-2-2

| Vector | Setup | Expected |
|---|---|---|
| 2.a accept | a full node runs CometBFT, the ABCI application and alethia-reth with its own L1 view, independently validates every block, and applies the checkpoint-trust gate; it has no registered signing key | matches the Full node row |
| 2.b reject | the full node has a registered signing key and its local identity participates in validator voting | violates COMP-2-2 ("It has no registered signing key") |
| 2.c reject | the full node trusts the proposer's state instead of validating every block | violates COMP-2-2 ("independently validates every block") |
| 2.d reject | the full node omits the checkpoint-trust gate | violates COMP-2-2 ("applies the same checkpoint-trust gate") |

*What distinguishes a "full node" from an RPC node that does not validate: no vector — [Q2-3](../review/2.md#q2-3).*

## COMP-2-3

| Vector | Setup | Expected |
|---|---|---|
| 3.a accept | anyone reads decided blocks/commits, builds batches, obtains two proofs and calls `land` in a blob transaction | matches the Lander row |
| 3.b reject | landing is restricted to an allowlisted set of addresses | violates COMP-2-3 ("Permissionless") |
| 3.c reject | a lander receives a protocol reward | violates COMP-2-3 ("earns no protocol reward") |
| 3.d accept | a lander earns nothing from the protocol for a successful landing | conforms |

*Whether "earns no protocol reward" is a present economic fact or a rule that a future reward must not change: no vector — [Q2-4](../review/2.md#q2-4).*

## COMP-2-6

| Vector | Setup | Expected |
|---|---|---|
| 6.a accept | the registry handles stake and delayed top-ups, exits, withdrawals, double-sign slashing, DAO responsibility forfeiture and exclusion-list forced exits, and writes one checkpoint for every L1 block that changes an entry | matches the EtnaStakingRegistry row |
| 6.b reject | an L1 block changes an entry and no checkpoint is written | violates COMP-2-6 ("one checkpoint for every L1 block that changes an entry") |
| 6.c reject | one L1 block that changes an entry writes two checkpoints | violates COMP-2-6 ("one checkpoint for every L1 block") |
| 6.d reject | an exclusion-list forced exit is not available through the registry | violates COMP-2-6 ("exclusion-list forced exits") |

*Whether "one checkpoint" is one per changing block or one per changed entry: no vector — [Q2-4](../review/2.md#q2-4).*
