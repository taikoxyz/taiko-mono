# 3.4 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). This file asserts only what the text says: each vector follows from the cited validity rule, or reports that it is contradicted. The text states explicit outcomes for some rules ("reject the block", "whole block is invalid", "halt for safety"); those are quoted. Where it states none, the row says "violates <ID>" and names no outcome. Undetermined items are under "Not covered" and in [review/3.4.md](../review/3.4.md).

`accept` means the described block satisfies the cited rule. `reject` means a stated validity condition fails; the consequence is quoted only where the text gives one.

## CONS-3.4-1

| Vector | Setup | Expected |
|---|---|---|
| 1.a accept | ProcessProposal and FinalizeBlock apply the same nine deterministic rules in the listed order | conforms |
| 1.b reject | FinalizeBlock omits rule 4 (generation) while ProcessProposal applies it | violates CONS-3.4-1 |
| 1.c reject | the two paths apply the rules in a different order | violates "in order" |
| 1.d reject | a rule produces one outcome in ProcessProposal and a different outcome in FinalizeBlock on the same input | violates "the same deterministic rules" |

*Whether L1-node-dependent checks (anchor canonical/finalized, checkpoint ancestry) can be "deterministic" across nodes with different views: no vector — [Q3.4-1](../review/3.4.md#q34-1).*
