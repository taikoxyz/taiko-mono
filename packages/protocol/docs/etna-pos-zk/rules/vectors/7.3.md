# 7.3 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). This file states only what the text states: each vector either follows from an enumerated requirement, or reports that a requirement was violated. Where the text states a requirement but **not the consequence of violating it**, the vector says "violates <ID>" and does not name an outcome. Anything undetermined has no vector; it is listed under "Not covered" and raised in [review/7.3.md](../review/7.3.md).

`accept` means the described block or accounting satisfies the rules cited. `reject` means a stated requirement is violated; the consequence, where the text does not name one, is the review question cited.

## FI-7.3-1

| Vector | Setup | Expected |
|---|---|---|
| 1.a accept | queue-head entry due; included at position 0 | included under FI-7.2-5 |
| 1.b accept | queue-head entry due; a legal skip under FI-7.2-8 | skipped |
| 1.c reject | queue-head entry due; neither included nor legally skipped | the block is invalid (FI-7.2-10 states it) |
| 1.d accept | entry submitted a year ago, still queued, not at the head | retained; there is no age-only deletion |
| 1.e reject | an entry removed solely because of its age | violates FI-7.3-1; no actor and no consequence stated — [Q7.3-4](../review/7.3.md#q73-4) |

## FI-7.3-2

| Vector | Setup | Expected |
|---|---|---|
| 2.a accept boundary | `block.timestamp = entry.timestamp + forcedInclusionDelay + maxAnchorAge`, with the anchor at the 3.4 rule 7 freshness bound | the entry is due under FI-7.2-3 (`≥`, not `>`) |
| 2.b accept | `block.timestamp` one second above the sum | the entry is due |
| 2.c accept (rule not triggered) | `block.timestamp` below the sum | the implication does not apply; FI-7.2-3 decides on the anchor timestamp |
| 2.d accept | an old-but-fresh anchor at the bound and a block at the bound | still due; the implication is about the block timestamp, not the anchor's own age in wall-clock time |

## FI-7.3-3

| Vector | Setup | Expected |
|---|---|---|
| 3.a accept boundary | sender balance equals `gasLimit × maxFeePerGas` | requirement satisfied |
| 3.b accept | sender balance above the product | requirement satisfied |
| 3.c reject | sender balance below the product | violates FI-7.3-3; the transaction is still eligible under FI-7.2-4 and its empty singleton build is a legal skip — [Q7.3-2](../review/7.3.md#q73-2) |

## FI-7.3-4

| Vector | Setup | Expected |
|---|---|---|
| 4.a accept | N consecutive blocks, each consuming one queue entry | at most one entry consumed per block |
| 4.b accept | a block consumes no entry because the head is not due | permitted (FI-7.2-6) |
| 4.c reject | one block consumes two entries | violates FI-7.3-4 (also FI-7.2-1) |
| 4.d accept | `threshold = 32`; `pending = 0` charges `fee`, `pending = 32` charges `2 × fee` | the charge is linear in the queue length |
| 4.e reject | `pending = 32` charges `3 × fee` | violates the stated linearity |

## FI-7.3-5

| Vector | Setup | Expected |
|---|---|---|
| 5.a accept | attacker pays F in admission fees; its entries are landed; no landing pays the attacker anything | the attacker has not recovered F by consuming the entries |
| 5.b accept | the attacker also pays L1 submission gas, proving and blob costs | these are accounted separately; recovery of F is still impossible |
| 5.c reject | a landing pays the enqueue caller an amount equal to F | violates FI-7.3-5 |
