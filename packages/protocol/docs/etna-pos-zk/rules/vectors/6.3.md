# 6.3 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). This file states only what the text states: each vector either follows directly from an enumerated condition, or reports that a requirement was violated. Where the text states a requirement but **not the consequence of violating it**, the vector says "violates <ID>" and does not name an outcome. Anything you cannot determine has no vector; it is listed under "Not covered" and raised in [review/6.3.md](../review/6.3.md).

6.3 constrains how batches are cut and reused; it does not itself define landing mechanics, so several vectors here cite 6.1 conditions. `K` is the grid interval, `p` the proof origin, `c` the checkpoint at execution and `h` the terminal height.

## BATCH-6.3-1

| Vector | Setup | Expected |
|---|---|---|
| 1.a accept | `p=300`, `h=309`, `K=3`, batch crosses an epoch boundary | accepted |
| 1.b accept | `p=300`, `h=303`, entire batch inside one epoch | accepted |
| 1.c reject | batch ends at `h=304` with `K=3` | violates BATCH-6.3-1 (batch cut is not a grid point; also LAND-6.1-5) |
| 1.d reject | batch starts at `p=301` with `K=3` | violates BATCH-6.3-1 |

## BATCH-6.3-2

| Vector | Setup | Expected |
|---|---|---|
| 2.a accept | a handover height 305 (not a grid point) falls inside the batch `(300,309]` | accepted; no extra cut |
| 2.b accept | a handover falls exactly on grid point 306 | accepted; the batch is cut at 306 |
| 2.c accept | a cancelled old activation height falls inside the batch | accepted |
| 2.d accept | a recovery start `R` (a checkpoint) used as a cut | accepted; `R` is a grid point |
| 2.e reject | a rule forbids cutting a batch at a height that is also a handover | violates BATCH-6.3-2 (handover heights are unrelated to the grid) |

## BATCH-6.3-3

| Vector | Setup | Expected |
|---|---|---|
| 3.a accept | a batch crossing a handover applies the actual schedule block by block | conforms |
| 3.b reject | the batch cut is moved off a grid point to avoid a handover height | violates BATCH-6.3-3 (and BATCH-6.3-1) |
| 3.c reject | a "problematic" cut is skipped and a non-grid cut used instead | violates BATCH-6.3-3 |

## BATCH-6.3-4

| Vector | Setup | Expected |
|---|---|---|
| 4.a accept | `l1ReferenceBlockNumber = block.number - 1` | accepted |
| 4.b accept | the reference is any recent L1 block inside the readable window | accepted |
| 4.c reject | a rule requires the reference block to be a checkpoint height or a landing's block | violates BATCH-6.3-4 ("any recent L1 block") |

## BATCH-6.3-5

| Vector | Setup | Expected |
|---|---|---|
| 5.a accept | after a long outage, the old suffix is proven from an old `p`, and the anchors it used are authenticated within the ancestry/proving budget | conforms |
| 5.b reject | the old suffix is proven with anchors that are not authenticated, justified only by choosing a recent reference | violates BATCH-6.3-5 ("does not remove that requirement") |
| 5.c reject | a proof is accepted because the reference is recent, although an old anchor is unauthenticated | violates BATCH-6.3-5 |

## BATCH-6.3-6

The value 131,072 headers is written as a "reference value"; whether it is a fixed protocol constant is [Q6.3-1](../review/6.3.md#q63-1).

| Vector | Setup | Expected |
|---|---|---|
| 6.a accept | the reference-header chain needed is exactly 131,072 headers | within the reference bound |
| 6.b accept | the chain needed is fewer than 131,072 headers | within the reference bound |
| 6.c reject | the chain needed is 131,073 headers | beyond the bound: cannot be landed the ordinary way — BATCH-6.3-7 |

## BATCH-6.3-7

| Vector | Setup | Expected |
|---|---|---|
| 7.a accept | a suffix beyond the reference-header bound is discarded by governance recovery, at most U blocks, restarting from `R` | conforms |
| 7.b not-a-result | a suffix beyond the bound is proven and landed the ordinary way | not possible: "cannot be landed the ordinary way" |
| 7.c reject | governance recovery discards more than U blocks | violates BATCH-6.3-7 ("at most U blocks") |
| 7.d reject | recovery restarts from a point other than `R` | violates BATCH-6.3-7 |
| 7.e accept | an outage before `R` is excluded from the header bound | conforms per (8.4); accounting is [Q6.3-3](../review/6.3.md#q63-3) |

## BATCH-6.3-8

| Vector | Setup | Expected |
|---|---|---|
| 8.a accept | `p` is the latest authenticated checkpoint whose slot 285 record is retained | accepted |

## BATCH-6.3-9

| Vector | Setup | Expected |
|---|---|---|
| 9.a accept | `p =` the generation's starting height | accepted (boundary is inclusive) |
| 9.b reject | `p` is one grid segment before the generation's starting height | violates BATCH-6.3-9 |

## BATCH-6.3-10

| Vector | Setup | Expected |
|---|---|---|
| 10.a accept | a competitor advances `c` to 303 with `p ≤ c < h`; the original transaction (two proofs, blobs, leaves) executes | valid unchanged; settles `(303,309]`; no reproving |
| 10.b accept | a competitor advances `c` to 306 | valid unchanged; settles `(306,309]` |
| 10.c reject | an implementation demands reaggregation or new parameters because `c` changed | violates BATCH-6.3-10 |
| 10.d reject | the transaction is re-signed with a new `p` to avoid the competitor | violates BATCH-6.3-10 and BATCH-6.3-13 |

## BATCH-6.3-11

| Vector | Setup | Expected |
|---|---|---|
| 11.a accept | `c = h` before execution | the target is already settled; the work can be cancelled |
| 11.b accept | `c > h` | the target is already settled; the work can be cancelled |
| 11.c | a landing with `c ≥ h` is submitted anyway | not a 6.3-11 case: 6.1's range check rejects it (LAND-6.1-6) |

## BATCH-6.3-12

| Vector | Setup | Expected |
|---|---|---|
| 12.a accept | the reference expires between proving and landing; the job is rebuilt with a new reference | conforms (the job was invalidated) |
| 12.b accept | a rule or image change invalidates the job | conforms |
| 12.c accept | a generation transition invalidates the job | conforms |
| 12.d reject | a deployment treats a reference-expired job as still valid without rebuilding | violates BATCH-6.3-12 |

## BATCH-6.3-13

"Signed job" is not defined in 6.3 — [Q6.3-2](../review/6.3.md#q63-2).

| Vector | Setup | Expected |
|---|---|---|
| 13.a accept | a signed job whose boundary changed is abandoned and re-issued | conforms |
| 13.b reject | a signed job is edited to use a different `p` or reference so the boundary check no longer fails | violates BATCH-6.3-13 |
| 13.c reject | a signed job's proven content is changed while keeping its signature | violates BATCH-6.3-13 |

## BATCH-6.3-14

| Vector | Setup | Expected |
|---|---|---|
| 14.a accept | a copier resubmits the same transaction; the proven content is unchanged | conforms; settlement is identical |
| 14.b accept | the submitter is neither the proposer nor the prover | conforms (landing carries no reward) |
| 14.c reject | a copier changes leaves or blobs and the result still settles as if unchanged | violates BATCH-6.3-14 ("cannot change any proven content") |
