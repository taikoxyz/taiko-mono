# 1 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). This file states only what the text states: each vector either follows directly from a citable statement or reports that it was contradicted. Where the text states a requirement but **not the consequence of violating it**, the vector says "violates <ID>" and does not name an outcome. Anything undetermined has no vector; it is listed under "Not covered" and raised in [review/1.md](../review/1.md).

`accept` means the described configuration satisfies the cited statement. `reject` means the statement is contradicted (the enforcement consequence is a separate question). Statements in section 1 are security-model claims as well as rules; a `reject` therefore means the claim is falsified, not that a block was rejected.

## MODEL-1-1

| Vector | Setup | Expected |
|---|---|---|
| 1.a accept | a block valid under this spec, within the EL gas and zk-gas limits and the 3.4 block size bound; at least one valid proof combination exists for it | completeness requirement satisfied |
| 1.b reject | the same block has no valid proof combination | violates MODEL-1-1 ("must be provable by at least one valid proof combination") |
| 1.c reject | the guest resource limit is below the EL limits, so a valid block cannot be proven | violates MODEL-1-1 (stated: "a guest resource limit below the EL limits ... violates it") |
| 1.d reject | the EL and the guests implement different rules, so a block valid under one is not valid under the other | violates MODEL-1-1 (stated: "a mismatch between the EL and the guests ... violates it") |
| 1.e accept boundary | a block exactly at the EL gas/zk-gas limits and at the 124,000-byte bound | still "within the EL limits ... and the 3.4 block size bound" |

*What happens when a valid non-forced block has no proof combination: no vector — [Q1-2](../review/1.md#q1-2).*

## MODEL-1-2
