# 7.1 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). This file states only what the text states: each vector either follows from an enumerated requirement, or reports that a requirement was violated. Where the text states a requirement but **not the consequence of violating it**, the vector says "violates <ID>" and does not name an outcome — inventing one would lock in an interpretation nobody decided. Anything undetermined has no vector; it is listed under "Not covered" and raised in [review/7.1.md](../review/7.1.md).

`accept` means the described submission or sweep satisfies the rules cited. `reject` means a stated requirement is violated; the enforcement consequence, where the text does not name one, is the review question cited.

## FI-7.1-1

| Vector | Setup | Expected |
|---|---|---|
| 1.a accept boundary | `tx` is exactly 8,192 bytes; `pending = 0` | admitted; charge is `fee` gwei |
| 1.b reject | `tx` is 8,193 bytes | violates FI-7.1-1 (the 8,192-byte cap); consequence not stated — [Q7.1-2](../review/7.1.md#q71-2) |
| 1.c accept | `threshold = 32`, `pending = 8`, deployment fee 1 gwei | charge is `1 × (32 + 8) / 32` = 1.25 gwei; integer conversion — [Q7.1-1](../review/7.1.md#q71-1) |
| 1.d accept | `head = 10`, `tail = 14`, and L2 has already consumed two of those entries while settlement lags | `pending = 4`: the text defines it as `tail − head` |
| 1.e accept | caller sends one wei more than the computed charge | overpayment refunded in the same transaction |
| 1.f accept boundary | `pending = 0`, `threshold = 32` | charge is exactly `fee` gwei |

## FI-7.1-2

| Vector | Setup | Expected |
|---|---|---|
| 2.a accept | enqueue of `tx` | entry stores `keccak256(tx)`, the L1 timestamp and the L1 block number, and nothing else |
| 2.b reject | the entry also stores the raw `tx` bytes on L1 | violates FI-7.1-2 ("stores only") |
| 2.c accept | two entries enqueued in the same L1 block | both records carry that block's number and timestamp |

## FI-7.1-3

| Vector | Setup | Expected |
|---|---|---|
| 3.a accept | enqueue with overpayment | the event records the fee actually charged in wei, not the amount sent |
| 3.b accept | `tx` is two concatenated RLP transactions | still enqueued and charged: encoding is not checked at submission (the entry is ineligible at consumption, FI-7.2-4) |
| 3.c reject | the event records the charge in gwei | violates FI-7.1-3 ("in wei") |
| 3.d accept | second entry in the same L1 block | the event records the entry index and the raw transaction bytes |

## FI-7.1-4

| Vector | Setup | Expected |
|---|---|---|
| 4.a accept | enqueue succeeds | the charged fee becomes protocol revenue and remains in the Inbox |
| 4.b reject | the charged fee is paid out to the lander at consumption | violates FI-7.1-4 |
| 4.c accept | enqueue, then `sweepProtocolFees()` | the fee leaves the Inbox only through the sweep (FI-7.1-10) |

## FI-7.1-5

| Vector | Setup | Expected |
|---|---|---|
| 5.a accept | entry included at position 0 | no refund, no recharge, no payment to a lander |
| 5.b accept | entry legally skipped under FI-7.2-8 | no refund, no recharge, no lander payment |
| 5.c accept | entry blanked by governance step 3 | no refund, no recharge, no lander payment |
| 5.d accept | entry replayed after a settlement rollback | no refund, no recharge, no lander payment |
| 5.e reject | a lander is paid the entry's fee | violates FI-7.1-5 |

## FI-7.1-6

| Vector | Setup | Expected |
|---|---|---|
| 6.a accept | consumption reads only the queue head and tail | consistent: enqueue events are not consulted |
| 6.b reject | recovery derives refunds from historical enqueue events | violates FI-7.1-6 ("not used as consumption or recovery inputs") |
| 6.c accept | the verifier-failure rollback ignores per-entry charges | consistent |

## FI-7.1-7

| Vector | Setup | Expected |
|---|---|---|
| 7.a accept | the submission transaction reverts (for example the fee transfer fails) | no entry is appended and no fee is taken |
| 7.b reject | a reverted submission still appends an entry | violates FI-7.1-7 |
| 7.c reject | a reverted submission still takes the fee | violates FI-7.1-7 |

## FI-7.1-8

| Vector | Setup | Expected |
|---|---|---|
| 8.a accept | deployment sets a nonzero `protocolFeeRecipient` equal to the DAO treasury and publishes it in the deployment manifest | conforms |
| 8.b reject | `protocolFeeRecipient` is the zero address | violates FI-7.1-8 ("nonzero"); consequence not stated — [Q7.1-5](../review/7.1.md#q71-5) |
| 8.c reject | `protocolFeeRecipient` is changed after deployment | violates FI-7.1-8 ("an Inbox immutable") |

## FI-7.1-9

| Vector | Setup | Expected |
|---|---|---|
| 9.a accept | `saveForcedInclusion` called with value above the charge | accepted; the overpayment is refunded in the same transaction |
| 9.b reject | another Inbox entry point accepts ETH | violates FI-7.1-9 |
| 9.c accept | ETH is force-sent to the Inbox | not a violation; the text excepts force-sent ETH from its balance statement |
| 9.d accept | Inbox balance equals unswept FI fees plus force-sent ETH | consistent with the stated balance |

## FI-7.1-10

| Vector | Setup | Expected |
|---|---|---|
| 10.a accept | any caller invokes `sweepProtocolFees()` | the entire Inbox ETH balance is transferred to `protocolFeeRecipient` |
| 10.b accept | the recipient reverts on receipt | the sweep reverts |
| 10.c reject | the sweep transfers only part of the balance | violates FI-7.1-10 ("entire ETH balance") |
| 10.d accept boundary | Inbox balance is zero | the call sweeps nothing; no other outcome is stated |

## FI-7.1-11

| Vector | Setup | Expected |
|---|---|---|
| 11.a accept | 1 ETH force-sent, then a sweep | the 1 ETH is included in the sweep |
| 11.b reject | the sweep leaves force-sent ETH in the Inbox | violates FI-7.1-11 |

## FI-7.1-12

| Vector | Setup | Expected |
|---|---|---|
| 12.a accept | `saveForcedInclusion` or `land` executes | no transfer to the treasury |
| 12.b accept | the treasury would reject a transfer, but only a sweep calls it | enqueue and land are unaffected |
| 12.c reject | `land` pays a share to the treasury | violates FI-7.1-12 |

## FI-7.1-13

| Vector | Setup | Expected |
|---|---|---|
| 13.a accept | sweep with `head = tail = 7` | head, tail and every entry are unchanged |
| 13.b accept | sweep before any landing | permitted; sweeping does not depend on landing |
| 13.c reject | the sweep edits an FI entry or moves the head | violates FI-7.1-13 |
| 13.d accept | two sweeps in a row | the second transfers an empty balance; queue progress still unchanged |
