# 4.2 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). Each vector follows from the stated epoch arithmetic, or reports that a requirement was violated. Where the text states a requirement but not the consequence of violating it, the vector says "violates <ID>"; any consequence is a separate question. Gaps are in [review/4.2.md](../review/4.2.md).

`accept` means the described epoch assignment satisfies the rule cited. `reject` means the stated arithmetic or fixed-at-initialization requirement is contradicted.

## STAKE-4.2-1

| Vector     | Setup                                                                              | Expected                                         |
| ---------- | ---------------------------------------------------------------------------------- | ------------------------------------------------ |
| 1.a accept | Inbox initialized with `L = 900` and `L1_0 = b`; later epochs use the same values  | conforms to STAKE-4.2-1                          |
| 1.b reject | an upgrade or configuration change replaces `L` without a new Inbox initialization | violates STAKE-4.2-1 ("fixed at initialization") |
| 1.c reject | `L1_0` is reassigned after initialization                                          | violates STAKE-4.2-1                             |
| 1.d accept | `L` is the number of L2 blocks in an epoch                                         | epoch length is `L` L2 blocks                    |

_Whether a replacement Inbox or a new generation may initialize a different L or L1_0: no vector — [Q4.2-2](../review/4.2.md#q42-2)._

## STAKE-4.2-2

| Vector     | Setup                                                                   | Expected                                |
| ---------- | ----------------------------------------------------------------------- | --------------------------------------- |
| 2.a accept | `L = 900`: `H(0) = 1`, `H(1) = 901`, `H(2) = 1801`                      | conforms to STAKE-4.2-2                 |
| 2.b accept | block 1 is in epoch 0; block 900 is in epoch 0; block 901 is in epoch 1 | `floor((h - 1) / L)` gives those epochs |
| 2.c reject | block 901 is assigned to epoch 0                                        | violates STAKE-4.2-2                    |
| 2.d reject | epoch t is said to start at block `t * L` rather than `1 + t * L`       | violates STAKE-4.2-2                    |

## STAKE-4.2-3

| Vector     | Setup                                                                                                          | Expected                                                                       |
| ---------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 3.a accept | L1 stops advancing for many L2 blocks; epoch membership is unchanged                                           | conforms to STAKE-4.2-3 ("defined by L2 height alone")                         |
| 3.b reject | an epoch or committee boundary is keyed to L1 progress                                                         | violates STAKE-4.2-3 ("not tied to L1 progress")                               |
| 3.c reject | an anchor-age bound other than 3.4's `maxAnchorAge` is applied by 4.2                                          | violates STAKE-4.2-3 ("only maxAnchorAge ... bounds how old an anchor may be") |
| 3.d accept | an anchor older than `maxAnchorAge` is handled by 3.4's anchor-freshness rule, with no epoch-specific age rule | conforms; the bound belongs to 3.4                                             |
