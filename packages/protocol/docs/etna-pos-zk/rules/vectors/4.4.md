# 4.4 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). Section 4.4 is a governance power, so these vectors describe what the registry permits and what it refuses; they do not judge whether an attribution is correct. Each vector follows from the stated checks, or reports that a requirement was violated. Where the text states a requirement but not the consequence of violating it, the vector says "violates <ID>". Gaps are in [review/4.4.md](../review/4.4.md).

`accept` means the described call or state satisfies the rule cited. `reject` means a stated check fails; where the text says a call fails or reverts, the vector says so. The attribution itself is a governance responsibility, not a vector — see [Q4.4-2](../review/4.4.md#q44-2).

## FORF-4.4-1

| Vector | Setup | Expected |
|---|---|---|
| 1.a accept | the registry owner calls `forfeit` after Inbox initialization | call is permitted |
| 1.b accept | the DAO's execution address calls after initialization | call is permitted |
| 1.c reject | any other caller invokes `forfeit` | violates FORF-4.4-1 ("callable only by") |
| 1.d reject | `forfeit` is called before Inbox initialization | violates FORF-4.4-1 ("only after Inbox initialization") |

*Whether "the registry owner" and "the DAO's actual execution address" are one authority or two: no vector — [Q4.4-1](../review/4.4.md#q44-1).*

## FORF-4.4-2

| Vector | Setup | Expected |
|---|---|---|
| 2.a accept | `entryKey == keccak256(abi.encode(ckPrefix, ckX))` for the entry's key | conforms to FORF-4.4-2 |
| 2.b reject | `entryKey` is the bond id, the slot number, or a hash of the compressed key | violates FORF-4.4-2 |

## FORF-4.4-3

| Vector | Setup | Expected |
|---|---|---|
| 3.a accept | the DAO authorization binds the deployment, the full call parameters and the published attribution | conforms to FORF-4.4-3 |
| 3.b reject | an authorization not bound to the deployment or the published attribution is executed | violates FORF-4.4-3; how this is verified — [Q4.4-2](../review/4.4.md#q44-2) |
| 3.c accept | the same incident names two entries with two separate calls | allowed ("the same incident may name multiple entries") |
| 3.d reject | the registry refuses the second entry because it deduplicated the incident id | violates FORF-4.4-3 ("no ... global incident-id deduplication state") |
| 3.e accept | the same incident id is used for a later, unrelated attribution | the registry has no dedup state to reject it; whether that is intended — [Q4.4-3](../review/4.4.md#q44-3) |

## FORF-4.4-4

| Vector | Setup | Expected |
|---|---|---|
| 4.a accept | unreleased, matches `entryKey`, flag false, `block.timestamp <= validUntil`, `balance > 0` | execution checks pass |
| 4.b reject | the entry has been released by withdrawal | violates FORF-4.4-4 ("unreleased") |
| 4.c reject | the argument `entryKey` no longer matches the entry | violates FORF-4.4-4 |
| 4.d reject | `forfeited[entryKey] == true` | violates FORF-4.4-4 |
| 4.e reject | `block.timestamp > validUntil` | violates FORF-4.4-4 (expired) |
| 4.f reject | `balance == 0` | violates FORF-4.4-4 ("must be positive") |

## FORF-4.4-5

## FORF-4.4-20
