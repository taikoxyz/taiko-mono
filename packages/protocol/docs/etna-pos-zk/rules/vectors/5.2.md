# 5.2 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). Each vector follows from a stated blob-payload rule, or reports that a requirement was violated. Where the text states a requirement but not the consequence of violating it, the vector says "violates <ID>". Gaps are in [review/5.2.md](../review/5.2.md).

`accept` means the described batch or payload satisfies the rule cited. `reject` means a stated acceptance rule is contradicted.

## DATA-5.2-1

| Vector              | Setup                           | Expected               |
| ------------------- | ------------------------------- | ---------------------- |
| 1.a accept          | a batch uses 1 blob             | conforms to DATA-5.2-1 |
| 1.b accept boundary | a batch uses 6 blobs            | conforms               |
| 1.c reject          | a batch uses 0 blobs or 7 blobs | violates "1–6 blobs"   |

## DATA-5.2-2

| Vector     | Setup                                                                                             | Expected                                |
| ---------- | ------------------------------------------------------------------------------------------------- | --------------------------------------- |
| 2.a accept | every blob decodes to at most 130,044 bytes; every non-final blob is full; every padding bit is 0 | conforms to DATA-5.2-2                  |
| 2.b reject | a non-final blob decodes to fewer than 130,044 bytes                                              | violates "every non-final blob is full" |
| 2.c reject | a blob decodes to more than 130,044 bytes                                                         | violates the decode limit               |
| 2.d reject | a padding bit is 1                                                                                | violates "all padding bits are 0"       |

_The full Unzen encoding is defined outside this document: no vector can settle which implementation is pinned — [Q5.2-1](../review/5.2.md#q52-1)._

## DATA-5.2-3

| Vector     | Setup                                                                                                                                            | Expected               |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------- |
| 3.a accept | payload is the `0x06` prefix followed by `zlib(rlp([executionBlock, ...]))`; `executionBlock == rlp([EL header, ordered EIP-2718 transactions])` | conforms to DATA-5.2-3 |
| 3.b reject | payload omits the `0x06` prefix or is not a zlib stream                                                                                          | violates DATA-5.2-3    |
| 3.c reject | `executionBlock` is not an RLP list of EL header followed by transactions, or the transactions are reordered                                     | violates DATA-5.2-3    |

## DATA-5.2-4

| Vector     | Setup                                                                                   | Expected                   |
| ---------- | --------------------------------------------------------------------------------------- | -------------------------- |
| 4.a accept | every transaction, legacy included, is an RLP byte string holding its EIP-2718 encoding | conforms to DATA-5.2-4     |
| 4.b reject | a transaction is encoded as a raw RLP list rather than an RLP byte string               | violates "RLP byte string" |
| 4.c reject | a legacy transaction is not wrapped in its EIP-2718 encoding                            | violates "legacy included" |

## DATA-5.2-5

| Vector     | Setup                                                                                                                                      | Expected                                     |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------- |
| 5.a accept | exactly one complete zlib stream, no preset dictionary, no trailing bytes; at most 64 MiB decompressed; each item at most 22,020,096 bytes | conforms to DATA-5.2-5                       |
| 5.b reject | two concatenated zlib streams, or bytes after the stream ends                                                                              | violates "exactly one ... no trailing bytes" |
| 5.c reject | the stream uses a preset dictionary                                                                                                        | violates "no preset dictionary"              |
| 5.d reject | decompressed size exceeds 64 MiB                                                                                                           | violates the stated limit                    |
| 5.e reject | one item exceeds 22,020,096 bytes                                                                                                          | violates the stated per-item limit           |

_What counts as an "item" for the 22,020,096-byte limit: no vector — [Q5.2-2](../review/5.2.md#q52-2)._

## DATA-5.2-6

| Vector     | Setup                                                                                         | Expected                                         |
| ---------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 6.a accept | every encoding is canonical and re-encodes byte for byte                                      | conforms to DATA-5.2-6                           |
| 6.b reject | an RLP integer has leading zeros, an RLP length prefix is non-minimal, or re-encoding differs | violates "canonical and re-encode byte for byte" |

## DATA-5.2-7

| Vector     | Setup                                                                                                                                                                                                                          | Expected                            |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------- |
| 7.a accept | exactly `lastHeight - parentHeight` blocks at heights `parentHeight + 1 ... lastHeight`; every EL `parentHash` link holds; first parent equals `parentHash`; last hash and stateRoot equal `lastBlockHash` and `lastStateRoot` | conforms to DATA-5.2-7              |
| 7.b reject | a block is missing, extra, or out of order                                                                                                                                                                                     | violates the block count or heights |
| 7.c reject | a block's `parentHash` does not link to the previous block                                                                                                                                                                     | violates "links block by block"     |
| 7.d reject | the first block's parent is not `parentHash`                                                                                                                                                                                   | violates the stated link            |
| 7.e reject | the last block's hash or stateRoot differs from the input                                                                                                                                                                      | violates the stated equality        |

## DATA-5.2-8

| Vector     | Setup                                                                                                                                                              | Expected                                                                         |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| 8.a accept | the listed items are not published; the guest authenticates each original envelope against `data_hash` and proves the execution part equals the blob byte for byte | conforms to DATA-5.2-8                                                           |
| 8.b reject | the guest skips envelope authentication, or proves a different execution part                                                                                      | violates DATA-5.2-8                                                              |
| 8.c reject | a published item includes a private witness or signature as public payload                                                                                         | violates "Not published" (status of the list — [Q5.2-4](../review/5.2.md#q52-4)) |

## DATA-5.2-9

| Vector     | Setup                                                                                                                                                                                     | Expected                                                   |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 9.a accept | a sound proof and a finalized L1 checkpoint plus archived blobs and the starting state rebuild the landed EL chain and check the last hash and stateRoot, without witnesses or signatures | conforms to DATA-5.2-9                                     |
| 9.b reject | reconstruction requires witnesses, signatures or a validator-private database                                                                                                             | violates "without witnesses or signatures"                 |
| 9.c accept | unlanded blocks still require the full consensus history                                                                                                                                  | conforms; this is the stated limitation, not a DA recovery |
