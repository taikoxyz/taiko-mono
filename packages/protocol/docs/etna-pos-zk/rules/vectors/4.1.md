# 4.1 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). This file states only what the text states: each vector either follows from an enumerated condition, or reports that a requirement was violated together with the outcome the text gives for it. Where the text states a requirement but **not the consequence of violating it**, the vector says "violates <ID>" and does not name an outcome — inventing one would lock in an interpretation nobody decided. Anything that cannot be determined has no vector; it is listed under "Not covered" and raised in [review/4.1.md](../review/4.1.md).

`accept` means the described registry state or call satisfies the rules cited. `reject` means a stated requirement is violated, and the vector names the outcome wherever the text gives one:

- a failed registration check: "Any failure rejects the entire registration without creating an entry or consuming the key identity" (STAKE-4.1-9), written `violates <ID>; registration rejected, no entry created (STAKE-4.1-9)`;
- a condition the text places on a named call ("owner-only", "callable only by", "requires", "must", "provided") is a precondition of that call, and in Solidity terms a failed precondition reverts it, written `violates <ID>; the call reverts`;
- where the text itself says a call reverts, fails or is rejected, the vector quotes it.

A reject that describes registry state or an implementation departing from the rules has no call to reject and reads only "violates <ID>"; where the text gives no consequence for such a state (STAKE-4.1-5, STAKE-4.1-36), that is [Q4.1-1](../review/4.1.md#q41-1).
