# 10.1 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). This file states only what the text states. Where the text states a requirement but **not the consequence of violating it**, the vector says "violates <ID>" and does not name an outcome. Anything undetermined has no vector; it is listed under "Not covered" and raised in [review/10.1.md](../review/10.1.md).

`accept` means the described upgrade satisfies the rule cited. `reject` means a stated requirement is violated.

## START-10.1-1

| Vector | Setup | Expected |
|---|---|---|
| 1.a accept | production stops and state settles before the rules switch | requirement satisfied |
| 1.b reject | new rules activate while production continues, or before settlement | violates START-10.1-1 |
| 1.c not-a-result | the upgrade causes downtime | not a violation ("without a zero-downtime promise") |

*What "settle" means as a predicate: no vector — [Q10.1-3](../review/10.1.md#q101-3).*

## START-10.1-2

| Vector | Setup | Expected |
|---|---|---|
| 2.a accept | an operational restart that preserves the validity rules; all same-domain signer state is retained | requirement satisfied |
| 2.b reject | a restart discards same-domain signer state (for example HRS state) | violates START-10.1-2 |

*When a change still counts as "preserving validity rules": no vector — [Q10.1-4](../review/10.1.md#q101-4).*

## START-10.1-3

| Vector | Setup | Expected |
|---|---|---|
| 3.a accept | a section 10 deployment-immutable parameter is changed only through a new-Inbox/new-genesis migration | requirement satisfied |
| 3.b reject | a 10.1 upgrade changes a section 10 deployment-immutable parameter | violates START-10.1-3 |
| 3.c reject | this section is invoked as authority to bypass immutability | violates START-10.1-3 ("cannot bypass immutability") |

## START-10.1-4

| Vector | Setup | Expected |
|---|---|---|
| 4.a accept | the plan binds deployment, generation, boundary height H, old/new client and EL rules, guest images and verifier acceptance ranges; H is a grid point | requirement satisfied |
| 4.b reject | the plan omits the generation or the verifier acceptance ranges | violates START-10.1-4 |
| 4.c reject | H is not a grid point | violates START-10.1-4 |
| 4.d reject | the upgrade changes K and H is not a multiple of both the old and the new K | violates START-10.1-4 |
| 4.e accept | the upgrade changes K and H is a multiple of both | requirement satisfied |

*Who checks the H/K condition and what happens if it fails: no vector — [Q10.1-2](../review/10.1.md#q101-2).*

## START-10.1-5

| Vector | Setup | Expected |
|---|---|---|
| 5.a accept | the plan is authenticated through the actual DAO/timelock authority and enforced in nodes and L1 verification | requirement satisfied |
| 5.b reject | the plan is enforced only by an off-chain manifest | violates START-10.1-5 ("insufficient") |
| 5.c reject | the plan is enforced only by operator agreement | violates START-10.1-5 |
| 5.d reject | the plan is not enforced in L1 verification | violates START-10.1-5 ("in both nodes and L1 verification") |

*What artifact encodes the plan and how L1 enforces it: no vector — [Q10.1-1](../review/10.1.md#q101-1).*
