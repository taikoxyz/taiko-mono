# 9.1 — accept/reject vectors

**Non-normative.** Rule text lives in [SPEC.md](../../SPEC.md). This file states only what the text states. Where the text states a requirement but **not the consequence of violating it**, the vector says "violates <ID>" and does not name an outcome. Anything undetermined has no vector; it is listed under "Not covered" and raised in [review/9.1.md](../review/9.1.md).

`accept` means the described archive, node or submission satisfies the rule cited. `reject` means a stated requirement is violated.

## SYNC-9.1-1

| Vector     | Setup                                                                                                                                                                                            | Expected                                                                           |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| 1.a accept | an archive holds original blocks/envelopes, headers, commits/LastCommit, registry snapshots/entries/witnesses, FI data/logs, relevant L1 headers/proofs, genesis parameters and recovery records | complete CometBFT recovery and proving are possible from the retained material     |
| 1.b reject | the archive lacks one listed category, for example commits/LastCommit                                                                                                                            | incomplete for complete CometBFT recovery/proving; violates SYNC-9.1-1 ("require") |
| 1.c accept | the archive holds every listed category, reconstructed from original sources rather than a running node                                                                                          | requirement satisfied                                                              |

_Whether "require" obliges anyone to retain, and for how long: no vector — [Q9.1-2](../review/9.1.md#q91-2)._

## SYNC-9.1-2

| Vector     | Setup                                                                 | Expected                                                        |
| ---------- | --------------------------------------------------------------------- | --------------------------------------------------------------- |
| 2.a accept | the archive retains the dependencies listed in SYNC-9.1-1             | requirement satisfied                                           |
| 2.b reject | the archive retains only public blobs                                 | violates SYNC-9.1-2 ("public blobs ... alone are insufficient") |
| 2.c reject | the archive retains only an EL snapshot                               | violates SYNC-9.1-2 ("an EL snapshot alone [is] insufficient")  |
| 2.d accept | blobs and an EL snapshot are retained in addition to the dependencies | consistent with SYNC-9.1-2                                      |

## SYNC-9.1-3

| Vector     | Setup                                                                              | Expected                                                             |
| ---------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 3.a reject | an archive plan treats private keys as required historical material to be retained | violates SYNC-9.1-3 ("private keys are not historical archive data") |
| 3.b accept | signing state is handled under 8.2 and is not treated as archive material          | requirement satisfied                                                |
| 3.c reject | signing state is restored from an archive snapshot rather than following 8.2       | violates SYNC-9.1-3                                                  |

## SYNC-9.1-4

| Vector     | Setup                                                                                                                                                                       | Expected              |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------- |
| 4.a accept | recovery authenticates the current generation's fixed origin, c's EL/Comet hashes and R's registry snapshot from the node's own finalized L1 view, then reselects under 4.3 | requirement satisfied |
| 4.b reject | reselection happens before the origin, c hashes and R snapshot are authenticated                                                                                            | violates SYNC-9.1-4   |
| 4.c reject | R's registry snapshot is taken from a peer or an unsigned file rather than the node's own finalized L1 view                                                                 | violates SYNC-9.1-4   |
| 4.d accept | after authentication the committee is reselected under 4.3                                                                                                                  | requirement satisfied |

## SYNC-9.1-5

| Vector            | Setup                                                                                                 | Expected                                |
| ----------------- | ----------------------------------------------------------------------------------------------------- | --------------------------------------- |
| 5.a accept        | after the initial recovery set, a current or pending committee change follows an authenticated switch | requirement satisfied                   |
| 5.b reject        | a pending committee is activated without authenticated switch evidence                                | violates SYNC-9.1-5                     |
| 5.c not-inclusion | the initial recovery committee itself is selected at R under 4.3                                      | not "subsequent"; SYNC-9.1-4 governs it |

## SYNC-9.1-6

| Vector     | Setup                                              | Expected                                    |
| ---------- | -------------------------------------------------- | ------------------------------------------- |
| 6.a accept | material needed for authentication is missing      | node stays untrusted                        |
| 6.b accept | authenticated material contradicts                 | node halts under section 9                  |
| 6.c reject | the node becomes trusted despite missing material  | violates SYNC-9.1-6                         |
| 6.d reject | the node keeps operating on contradictory material | violates SYNC-9.1-6 ("contradictions halt") |

## SYNC-9.1-7

| Vector            | Setup                                                                                                            | Expected                                            |
| ----------------- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| 7.a accept        | anyone collects two verifiable same-round conflicting votes from different peers and submits them directly to L1 | permitted; Comet evidence inclusion is not required |
| 7.b accept        | the two votes are at the same height, round and vote type with different block ids                               | same-round conflict                                 |
| 7.c not-inclusion | the two votes are at different rounds                                                                            | not "same-round"; SYNC-9.1-10 applies               |
| 7.d accept        | the submitting party is neither the voter nor a validator                                                        | permitted ("anyone may collect")                    |

_The rule grants a permission, so there is no reject case; what "verifiable" requires is undetermined — [Q9.1-1](../review/9.1.md#q91-1)._

## SYNC-9.1-8

| Vector            | Setup                                                                                             | Expected                                                           |
| ----------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 8.a accept        | evidence is retained and submitted after the local pool's 100,000-block/48-hour limit has expired | consistent with independence                                       |
| 8.b reject        | a node discards evidence solely because the local pool limit expired                              | violates SYNC-9.1-8 ("independent of the local pool's ... limits") |
| 8.c not-inclusion | the local pool's own eviction behaviour                                                           | not governed by this rule; it is independent                       |

_The accompanying "should track confirmExit and withdrawal boundaries" is guidance, not a rule; no vector — see [review/9.1.md](../review/9.1.md#normativity-boundary)._

## SYNC-9.1-9

_Typed `limitation`: the sentence states what evidence retention does not guarantee, so nothing conforms or fails against it and it has no accept/reject rows. See [Q9.1-5](../review/9.1.md#q91-5)._

## SYNC-9.1-10

| Vector            | Setup                                                                     | Expected                                          |
| ----------------- | ------------------------------------------------------------------------- | ------------------------------------------------- |
| 10.a not-a-result | two votes at the same height with different block ids in different rounds | not automatically double signing                  |
