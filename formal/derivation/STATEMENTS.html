Unzen derivation: statements in words and Lean

This page explains what the four headline theorems establish, which premises they use, and where to read their definitions. The English explanation sits beside the exact Lean declaration; the Lean source is authoritative.

The subject is an executable model of the Unzen derivation rules implemented by taiko-client and taiko-client-rs. The theorems prove properties of that model, not equivalence of the production clients.

Scope and notation

The intended setting is one proposal that lands on L1 at or after UNZEN_FORK_TIME, on top of an Unzen parent block. The model uses the 768-block limit for every source. On a Shasta parent at the activation boundary, all claims still describe the modeled fields except the conclusion that every derived block is Unzen. The pre-Unzen 192-block branch, early parent-anchor calldata recovery, and Etna are outside scope.

The propositions quantify over model inputs. They do not authenticate those inputs, enforce a real chain configuration, or establish machine-integer equivalence.

c — chain parameters
Fork times and the allowed timestamp and anchor offsets.
ctx — proposal context
The proposer, landed L1 timestamp, and origin block number (the L1 block before the proposal).
p — initial parent
The L2 parent number, timestamp, header gas limit, and recorded anchor number.
sources — ordered derivation inputs
Each source has a forced-inclusion flag, blob presence, offset, and optional decoded-blob bytes. deriveSources extracts, validates, defaults when needed, and numbers their blocks.

1. Derivation safety

In words

For any model chain parameters, proposal context, and parent:

  1. Source cardinality. Each source contributes 1–768 blocks. A forced-inclusion source contributes exactly one, including when it defaults.
  2. Source isolation. Deriving a prefix and then the rest gives the same result as deriving their concatenation. Appending later sources cannot change any block already derived from the prefix.
  3. Sequence. Block numbers advance by one from the parent; timestamps strictly increase; anchor numbers never decrease.
  4. Timestamp drift. For zero-based block index i:
    timestamp[i] ≤ max(proposal timestamp, parent timestamp, Shasta fork time) + i + 1
    Accepted sources stay at or before the proposal timestamp. Default blocks may pass it when the timestamp window is exhausted.
  5. Conditional bounds. If the initial parent's anchor is not after the proposal origin, derived anchors stay at or below that origin. If its effective gas is in the protocol range, derived manifest gas stays in the same 10M–45M range.

The initial bounds are needed only for the last clause. Cardinality, isolation, sequence, and drift do not require InitialParentBounds.

For an extracted proposer manifest, successful finalization returns exactly that original block list. Metadata and ordered transaction candidates are preserved, rather than only satisfying the bounds above.

Initial parent bounds, in Lean 
structure InitialParentBounds (ctx : ProposalCtx) (p : Parent) : Prop where
  /-- The parent's anchor does not lie beyond this proposal's L1 origin. -/
  anchorNotAfterOrigin : p.anchorBlockNumber ≤ ctx.originBlockNumber
  /-- The parent's effective (manifest) gas is at least the protocol minimum. -/
  gasMinimum : MIN_BLOCK_GAS_LIMIT ≤ effectiveGasLimit p
  /-- The parent's effective (manifest) gas is at most the protocol maximum. -/
  gasMaximum : effectiveGasLimit p ≤ MAX_BLOCK_GAS_LIMIT

def DerivationSafety : Prop :=
  ∀ (c : ChainParams) (ctx : ProposalCtx) (p : Parent),
    (∀ src payload,
      1 ≤ (sourceBlocks c ctx p src payload).length ∧
      (sourceBlocks c ctx p src payload).length ≤ UNZEN_DERIVATION_SOURCE_MAX_BLOCKS ∧
      (src.isForcedInclusion = true → (sourceBlocks c ctx p src payload).length = 1)) ∧
    (∀ xs ys,
      deriveSources c ctx p (xs ++ ys) =
        deriveSources c ctx p xs ++ deriveSources c ctx (parentAfter c ctx p xs) ys ∧
      (deriveSources c ctx p (xs ++ ys)).take (deriveSources c ctx p xs).length =
        deriveSources c ctx p xs) ∧
    (∀ sources,
      Chain (fun a b => b = a + 1) p.number ((deriveSources c ctx p sources).map (·.number)) ∧
      Chain (· < ·) p.timestamp ((deriveSources c ctx p sources).map (·.timestamp)) ∧
      (∀ i (hi : i < (deriveSources c ctx p sources).length),
        (deriveSources c ctx p sources)[i].timestamp ≤
          max ctx.timestamp (max p.timestamp c.shastaForkTime) + i + 1) ∧
      Chain (· ≤ ·) p.anchorBlockNumber
        ((deriveSources c ctx p sources).map (·.anchorBlockNumber))) ∧
    (InitialParentBounds ctx p → ∀ sources, ∀ b ∈ deriveSources c ctx p sources,
      b.anchorBlockNumber ≤ ctx.originBlockNumber ∧
      MIN_BLOCK_GAS_LIMIT ≤ b.gasLimit ∧ b.gasLimit ≤ MAX_BLOCK_GAS_LIMIT) ∧
    (∀ (src : Source) (m : Option (List BlockManifest)) (bs : List BlockManifest),
      src.isForcedInclusion = false →
      (finalizeSource c ctx p src m = .accepted bs ↔
        m = some bs ∧ validate c ctx p false bs = true))

2. Header safety and the next parent

In words

For any header context (base-fee sharing percentage and proposal ID), building header plans preserves exactly the derived block sequence. Every plan has:

  • Header gas equal to manifest gas plus the 1M anchor reserve.
  • Exactly seven bytes of extraData: one sharing-percentage byte, followed by the low six bytes of the proposal ID, big-endian. Real Proposed.id values are uint48, so they fit without truncation.
  • A system anchor for that block's own anchor number first, followed by the manifest's candidate transactions in their original order.

The Anchor contract is trusted to execute successfully and record the running maximum of checkpoint numbers. Since derived anchors never decrease, its recorded anchor after each block equals that block's anchor. Rebuilding the next parent from the last header and that recorded anchor gives exactly the parent that derivation continues from.

If the initial parent timestamp is at or after Unzen, every derived block is also at or after Unzen. These are header plans; preserving candidate transactions is not a claim that execution includes them all.

The Unzen header layout, in Lean 
def UnzenHeader (hc : HeaderContext) (h : HeaderPlan) : Prop :=
  h.gasLimit = h.block.gasLimit + ANCHOR_GAS_LIMIT ∧
  h.extraData.length = 7 ∧
  h.extraData.head? = some hc.baseFeeSharing ∧
  decodeExtraDataProposal h.extraData = some (hc.proposalId % uint48Limit) ∧
  h.transactions =
    .anchor h.block.anchorBlockNumber :: h.block.transactions.map TransactionPlanEntry.manifest

def HeaderSafety : Prop :=
  ∀ (c : ChainParams) (ctx : ProposalCtx) (hc : HeaderContext) (p : Parent)
    (sources : List (Source × Option ByteArray)),

3. Forced-inclusion acceptance and fallback

In words

Given an extracted, one-block manifest for a forced-inclusion source, the model overwrites its metadata with inherited values before validation. It accepts that source if and only if all of these conditions hold:

  1. The computed minimum timestamp is no later than the proposal timestamp.
  2. The inherited parent anchor is at least origin − maxAnchorOffset (subtraction truncates at zero), and no later than the origin.
  3. The parent's effective gas is within its own gasBounds. This condition always holds when that gas is in the 10M–45M range.

Otherwise it becomes exactly one default block: the computed minimum timestamp, the proposer as coinbase, the parent's anchor and effective gas, and no manifest transactions. A missing manifest also produces that default block.

On acceptance, the result is exactly the inherited block with the submitted manifest's original ordered transaction-candidate list. This equality is part of the headline claim; it does not assert that the execution engine includes those candidates.

Later sources cannot change the earlier prefix. The Inbox's placement of forced sources before the proposer connects that prefix property to forced inclusions.

Forced inclusion can default. A stale inherited anchor or an exhausted timestamp window can discard its candidates. No inclusion deadline, eventual-inclusion guarantee, or transaction-execution result is proved.

The acceptance condition, in Lean 
def ForcedAcceptance (c : ChainParams) (ctx : ProposalCtx) (p : Parent) : Prop :=
  lowerBound c ctx p.timestamp ≤ ctx.timestamp ∧
  ctx.originBlockNumber - c.maxAnchorOffset ≤ p.anchorBlockNumber ∧
  p.anchorBlockNumber ≤ ctx.originBlockNumber ∧
  (gasBounds (effectiveGasLimit p)).1 ≤ effectiveGasLimit p ∧
  effectiveGasLimit p ≤ (gasBounds (effectiveGasLimit p)).2

def ForcedInclusionSafety : Prop :=
  ∀ (c : ChainParams) (ctx : ProposalCtx) (p : Parent),
    (∀ (src : Source) (b : BlockManifest), src.isForcedInclusion = true →
      ((finalizeSource c ctx p src (some [b])).isAccepted = true ↔ ForcedAcceptance c ctx p) ∧
      (finalizeSource c ctx p src (some [b]) =
          .accepted [{ defaultBlock c ctx p with transactions := b.transactions }] ↔
        ForcedAcceptance c ctx p) ∧
      (finalizeSource c ctx p src (some [b]) = .defaulted (defaultBlock c ctx p) ↔
        ¬ ForcedAcceptance c ctx p)) ∧
    (∀ src, finalizeSource c ctx p src none = .defaulted (defaultBlock c ctx p)) ∧
    (∀ xs ys,
      (deriveSources c ctx p (xs ++ ys)).take (deriveSources c ctx p xs).length =
        deriveSources c ctx p xs)

9. Forced inclusions

forced_inclusion_accepted_iff

A forced inclusion whose manifest is one block has an accepted outcome exactly when (a) the timestamp window is not used up, (b) the parent's anchor is at most MAX_ANCHOR_OFFSET behind the origin block and not past it, and (c) the parent's gas limit is within its own bounds. Exact preservation of its transaction candidates is stated separately in forced_inclusion_preserves_transactions_iff. Otherwise it becomes the default block: forced inclusions *can* be dropped, unlike what Derivation.md states.

Evidence and limits

What is checked

The package gate builds the libraries, audits the exact headline types and their dependencies, checks the initial-premise fields, and replays all five library roots with leanchecker. Owned declarations may depend only on propext, Classical.choice, and Quot.sound.

The shared manifest corpus is executable conformance evidence. Compilation-time #guard checks and JSON vector runs are tests, not kernel proofs. The original 136 decoding vectors are joined by 151 shared boundary cases for extraction, metadata, source sequences, header plans and next parents. Each adapter rejects deliberately corrupted expected outputs. The local formal gate runs Lean and fixture checks; CI also runs Go and Rust adapters on drafts. These comparisons do not prove that the clients implement the model.

The named boundary matrix records the covered cases. Go uses production decoding, metadata and shared header helpers; Rust uses production decoding and payload/anchor construction. External RPC/signing or execution boundaries are substituted in tests. Anchor state is still trusted as a running maximum. See the corpus README for the comparison boundary.

Concrete witnesses demonstrate satisfiable bounds, accepted sources, stale-anchor fallback, and a two-source proposal with header plans. They do not prove completeness of the assumptions.

Differences from specification prose

  • A version word below 264 is accepted when its low 32 bits equal 1.
  • The size word uses only its low 64 bits before checking the payload bounds.
  • Proposer anchor 0 is validated normally; it does not request parent inheritance.
  • A proposer source defaults unless one of its blocks raises the anchor above the parent's; the prose names this penalty only where it exempts forced sources.
  • Forced sources can default after inheritance when validation fails.
  • A default block takes the timestamp lower bound without validation, so it can be later than the proposal timestamp; the drift bound above covers it.
  • Zlib, canonical RLP, and transaction grammar add explicit decoding detail.

The model follows the reviewed client behavior in these cases. spec-coverage.json pins the specification's revision and hash; that traceability is not a claim of complete coverage. The README records the additional out-of-domain proposal-ID, parent-gas arithmetic and empty-source-list differences.

Trusted or outside scope

  • Anchor execution. Every anchor transaction is assumed to succeed and record the running maximum of checkpoint numbers.
  • Input authenticity and availability. L1 events, parent reads, chain configuration, blob field-element decoding, data availability, and the split between retried fetch failures and defaulted sources.
  • Execution. Sender authentication, execution filtering, zk gas, base fee, mixHash, and execution results.
  • Unmodeled header and transaction details. Anchor L1 hash and state root, signed anchor encoding, Engine API serialization, and engine-set fields such as parentBeaconBlockRoot, blob gas, requestsHash, and difficulty.
  • Other guarantees. Decoder resource bounds, bridge verification, proof/bond settlement, consensus security, eventual inclusion, and whole-client equivalence.

The source and audit gates have bounded mechanical checks. They cannot decide whether an English explanation is faithful, whether a premise is logically necessary, or whether a model matches production. Those remain review questions.
