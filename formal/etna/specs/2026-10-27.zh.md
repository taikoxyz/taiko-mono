## 1. 定位与安全模型

- <b>定位</b>：PoS-sequenced validity rollup，不是 based rollup。交易顺序由 L2 PoS 决定；Ethereum 不排序，只提供 DA（blob）、证明验证、结算和桥的锚点。
- <b>资金</b>：L1 只认已 land 的 checkpoint，每次 land 要两份证明、至少一份 ZK（6.2）。committee 全体作恶也拿不走 L1 上的资金。
- <b>终局</b>：拜占庭投票权少于 1/3 时，CometBFT commit 即终局，共识不会回滚已 commit 的块；唯一的例外是治理恢复会丢弃最新 checkpoint 之上的块（第 8 节）。checkpoint 及以下只有 verifier 失效后的 DAO 升级才能回滚（第 8 节），交易所和桥应以 checkpoint 为准。
- <b>活性</b>：需要超过 2/3 的投票权在线、L1 持续 finalize、landing 不断（6.4）。
- <b>抗审查</b>：forced inclusion 由证明强制，到期的队头 entry 只能被包含或合法跳过，否则块无效；不能仅因 entry 太旧而删除它，唯一的例外是第 8 节治理恢复可以显式置空指定 entry。推进依赖共识、L1 finality、队列消费和 settlement，不提供墙钟上的 inclusion deadline（第 7 节、3.4）。
- <b>升级与信任</b>：<code>EtnaInbox</code>、registry 和 L1 <code>SignalService</code> 都是可升级 proxy，owner 应为 DAO（经 timelock），升级即可绕过本 spec 的任何规则。verifier 的可靠性，包括 SGX instance 和 RISC0/SP1 image 的管理，是另一个前提。证明的完备性也是前提：凡是按本 spec 有效、且不超过 EL 限额（gas、zk gas）和 3.4 块大小上限的块，都必须能由至少一个合法证明组合证出来；任意一个网格段（K 个连续的这类块，6.1）都必须能在一次 landing 的双证明里一起证出来，最坏情形按每块再加一次 7.2 跳过判定的单笔构建试执行计算（最多再用满一块的 zk 预算）。EL 与 guest 行为不一致，或 guest 的资源上限低于 EL 限额，都会违反这一前提；经 forced inclusion 强制包含的这类交易按第 8 节治理恢复第 3 步处理。<code>land</code>、<code>saveForcedInclusion</code> 和 registry 都不受 pause 影响；两个证明系统同时出错时，只能靠 <code>SignalService</code>、Bridge 的 pause 和 QuotaManager 限额止损，结算随更换 verifier 的 Inbox 升级回退（第 8 节）。
- <b>不在范围</b>：PoS 增发奖励、只凭 L1 启动 CometBFT。Slashing 只罚同 round 双签（4.1）；下线不罚没，治理恢复的排除名单只强制退出（第 8 节第 2 步）；从 Unzen 切换到 Etna 暂不考虑，之后再补。

## 3. 共识与区块

### 3.1 共识引擎

- stock CometBFT v0.40.0，独立进程，经 ABCI++ socket 驱动应用。proposer 选择、超时、lock 和 BlockID 全用 stock 行为，不 fork 引擎。

<toggle>
细节：secp256k1eth 签名格式与 chain\_id 的构造

- Consensus key 是 CometBFT v0.40.0 的 <code>secp256k1eth</code>：对 sign bytes 做 keccak256（无前缀）后签名，签名是 65 字节 <code>R‖S‖V</code>（<code>V ∈ {0, 1}</code>，要求 low-s）；公钥是 33 字节压缩 SEC1；validator 地址就是以太坊地址 <code>keccak256(未压缩公钥去掉首字节)[12:]</code>。因此 L1 能直接用 <code>ecrecover</code> 验证任意一张投票（4.1 双签罚没）。CometBFT 对这种 key 不做批量验签。每届与恢复起始 committee 均按 4.3 取 voting power = ⌊effStake / <code>vp_unit</code>⌋，总和不超过 CometBFT 上限 <code>(2^63 − 1) / 8</code>。
- <code>chain_id = "etna-" + base64url_no_padding(chainDomain)</code>，共 48 个 ASCII 字节；<code>chainDomain</code> 是绑定版本、完整 L1/L2 chain id、Inbox proxy 地址和 generation 的 256 位 keccak256 摘要（附录 A），不截断。节点、signer、guest 和 registry 都重算同一个值。旧 generation 的票不能授权新 generation，其他部署的票不能用于本部署的 commit 或罚没；同一个 key 在不同域签同一高度不构成双签。仍使用 stock CometBFT VoteSignBytes，不改变投票编码。
</toggle>

- mempool 设为 <code>nop</code>：用户交易走 EL devp2p，proposer 的 EL 从自己的 txpool 选交易。
- CometBFT height 等于 EL 块号，共识从 Etna 起点的下一块开始（文中起点暂记为 block 0）。每个 CometBFT 块的 <code>Data.Txs</code> 恰好一项：envelope（5.1）。

<toggle>
细节：ABCI 响应约束

- ABCI 响应：<code>app_hash</code> 是已执行 EL 块的 hash（初始部署的 InitChain 返回 genesis hash；治理恢复的 InitChain 返回 ELHash(c)，见 8.4）；每个交易结果（ExecTxResult）固定为 code 0、空 data、gas\_wanted 和 gas\_used 为 0，这四项都进入 LastResultsHash；Info 在高度 0 时返回本 generation genesis 的 consensus params 中的 app 版本，同一 generation 内 header 的 app 版本不变，各高度适用的规则版本由升级计划决定、不由 Info 决定；不更新 consensus params。本文规则的 <code>APP_VERSION</code> 为 1（各编码版本见附录 A）；checkpoint-trust 元数据只属于本地节点，不进入 <code>app_hash</code> 或区块字节。
</toggle>

- 出块间隔由 <code>timeout_commit</code> 决定，是运行参数，不是有效性规则（目标约 4 s，前提是 n ≲ 128）。
- CometBFT 的 evidence 照常进块，但应用不据此处罚：罚没只在 L1 执行（4.1 的 <code>slashDoubleSign</code>），任何人都能把 gossip 中看到的两张冲突投票交给 registry。

<toggle>
细节：EL 的驱动方式、zk gas 计量与执行收费

- EL 是固定版本的 alethia-reth（支持 Etna）：没有 anchor 交易，支持按给定交易列表构建，basefee 分成比例读 <code>extraData[0]</code>，zk gas 记在 <code>difficulty</code>。EIP-4396 参数随固定 EL 版本发布。应用用 <code>engine_forkchoiceUpdatedV3</code>、<code>engine_getPayloadV5</code>、<code>engine_newPayloadV4</code> 驱动它。
- <b>zk gas</b>：计量、交易 intrinsic、opcode/precompile 乘数、CALL/CREATE spawn 估算、uint64 溢出处理及超限交易的整笔撤销直接采用 [ZK Gas spec](https://github.com/taikoxyz/taiko-mono/blob/main/packages/protocol/docs/zk_gas_spec.md)（[固定修订](https://github.com/taikoxyz/taiko-mono/blob/5dbbf4551c2f89bb94b5d96bf6f9ed3133b4c8df/packages/protocol/docs/zk_gas_spec.md)）。该规范中超限后“跳过其余交易”的截断不是本 spec 的共识规则：构建时如何继续选交易见下文“执行与费用”，验证已提交块见 3.4 第 9 条。所有实际预编译调用都须计量，包括交易直接调用预编译地址；直接调用不虚构 CALL，也不加 CALL spawn 费用。该规范的 <code>BLOCK_ZK_GAS_LIMIT</code> 对应本 spec 的 <code>L2_BLOCK_ZK_GAS_LIMIT</code>，是独立于 EVM gas 的块预算。启用的规范修订、参数和共享 vectors 随固定 EL/guest 版本发布，main 后续修改不自动改变共识；文档中的 100M 为占位值，部署值须按第 11 节固定并通过 Etna 验收与上线清单 中的验收。
- <b>执行与费用</b>：构建候选交易列表时，zk gas 超限或计量溢出的交易按共用规范整笔撤销，退回该交易开始前的状态。撤销包括 nonce、授权、余额转移、日志、receipt 和费用；被撤销和未选入的交易不进入最终块，也不收费。撤销后是否继续尝试其他候选交易属于 proposer 的构建策略，不是共识规则；建议跳过该交易及同一 sender 的后续 nonce，继续选其他交易，并限制超限试执行（含首次和重复）的总工作量。该策略只作用于 txpool 候选；proposer 放在第 0 位的 FI 交易须在实际块前状态上执行，不得因记住的超限记录而跳过。给定列表的单笔构建（7.2）只有 <code>[tx]</code> 一个候选，结果与此无关。验证或导入已提交块时，不撤销块中列出的任何交易：任一列出交易 zk 超限/溢出即整块无效（3.4 第 9 条）；7.2 跳过判定中的单笔构建仍按上述规则撤销 <code>tx</code>。正常 EVM revert/OOG 在 zk 预算允许时仍是已包含交易，按普通 EVM 规则收费。交易 gas、退款、basefee 和小费均采用普通 EVM 规则，zk gas 不折成计费 gas；块的 gasUsed 为最终包含交易的 EVM gasUsed 之和，EIP-4396 使用该值。<code>eth_call</code>/<code>eth_estimateGas</code> 使用相同规则版本、以完整块 zk 预算做独立模拟；zk 超限须返回明确错误，不能把丢弃后的空结果报告为成功。
</toggle>

### 3.2 区块头

除 <code>beneficiary</code> 外，每个字段都由已提交的 parent（及其 parent 的时间戳）、本块 anchor、BFT time 和链常数确定。proposer 按它构建，其他节点重算后逐字段比较。

| 字段 | 取值 |
| --- | --- |
| <code>number</code> / <code>parentHash</code> | height / 已提交 parent 的 hash |
| <code>timestamp</code> | max(parent.timestamp + 1, ⌊BFT time⌋, anchor.timestamp) |
| <code>beneficiary</code> | proposer 自定的收款地址，同以太坊的 fee recipient，不校验；该块的 basefee 和小费全部在 L2 执行时付给它，不依赖 L1 结算，proposer 在自己块里发的交易因此不付净手续费 |
| <code>extraData</code> | 13 字节 <code>[100 \| generation (uint48) \| anchor 块号 (uint48)]</code>；首字节是 basefee 分成比例，恒为 100，即全部 basefee 付给 beneficiary |
| <code>parentBeaconBlockRoot</code> | anchor 的 L1 stateRoot。EL 把它写进 EIP-4788 合约（以 L2 块时间戳为 key），L2 合约据此验证 L1 storage proof |
| <code>gasLimit</code> | 链常数 <code>L2_BLOCK_GAS_LIMIT</code> |
| <code>baseFeePerGas</code> | block 1 固定为 0.025 gwei；之后按 EIP-4396 由 parent 的 gas 用量和出块间隔（parent 与 grandparent 的时间差）调整，限定在链的最低 basefee（chain id 167000 为 0.01 gwei，其余 0.005 gwei）与 1 gwei 之间 |
| <code>mixHash</code> | 沿用 Unzen 的公式，由 parent.difficulty 和 height 算出 |
| 其他 | withdrawals 为空，blob gas 为 0，requests 为空，ommers 为空，nonce 为 0 |

stateRoot、receipts、gasUsed（最终包含交易的 EVM gasUsed 之和）和 <code>difficulty</code> 里的 zk gas 由 EL <code>newPayload</code> 校验。<code>difficulty</code> 只累计最终包含交易的 zk gas（含正常 EVM revert/OOG 的已包含交易），不计已撤销的超限试执行或未选入的交易；块首系统处理仍按 3.2 执行，不因交易撤销而回滚。

### 3.3 Anchor

- 每个块有一个 anchor，即它读取 L1 状态所用的 L1 块。块要么带 anchor witness（L1 header 原文加 Inbox 的 account/storage proof），要么沿用 parent 的 anchor。每个 generation 的首块和 anchor 变化时必须带，不变时不得带。Witness 证明 Inbox 的 <code>recoveryGeneration</code>、<code>lastCheckpoint</code>（height, hash）和 forced inclusion 队列的 head/tail。
- Proposer 选 max(parent 的 anchor, 本地 L1 <code>finalized</code>)。跨 round 保留的 proposal 沿用原 anchor。Validator 在 ProcessProposal 里用自己的 L1 节点确认 anchor header 是 canonical 且已 finalize，并按候选块的时间戳检查 anchor 年龄（3.4）；不能仅因本地 finalized 高度继续前进就让该 proposal 过期。

<toggle>
细节：L1 header 的解码

- <b>L1 header 的解码</b>：<code>rawL1Header</code> 必须是不超过 4,096 字节的 RLP list，至少 12 项。节点和 guest 只按下标读四个字段：0 <code>parentHash</code>、3 <code>stateRoot</code>（各 32 字节），8 <code>number</code>、11 <code>timestamp</code>（各为不超过 8 字节、无前导零的整数）；其余各项只要求是合法的 RLP item，不解释内容。L1 分叉在尾部新增的字段（例如 Glamsterdam 的 EIP-7928 <code>block_access_list_hash</code>）因此不需要升级就能接受。Header 的身份始终是对原始字节计算的 keccak256(rawL1Header)，不得解码后重编码。节点用 <code>extraData</code> 里的 anchor 块号向自己的 L1 节点取 canonical hash，与 keccak256(rawL1Header) 比较：不相等时 witness 无效；相等但按本条解析不了，说明 L1 改了 header 格式、本节点需要升级，按第 8 节的 liveness 暂停处理，不是 safety 停机。节点从自己的 L1 节点读取其他 header（信任检查、冷同步）时同样只依赖这四个字段，忽略未知字段。
</toggle>

### 3.4 区块有效性

ProcessProposal 和 FinalizeBlock 用同一套确定性规则，按序检查：

1. height = parent + 1，<code>parentHash</code> 衔接。
2. anchor witness 的有无符合 3.3，witness 通过验证。
3. Anchor 不倒退：不低于 parent 的 anchor 和当前 generation 的 L1 起点，即固定起点记录（8.4）的 l1BlockNumber：generation 0 为 <code>L1_0</code>，治理恢复后为 R。
4. Generation：以 <code>extraData</code> 中的 generation 和本部署参数按附录 A 重算 <code>chain_id</code>，必须与当前链及 CometBFT header 完全一致；generation 取 uint48，不从摘要字符串反解析。Inbox 的 generation 更大时本链已被取代（第 8 节）；更小时拒绝。
5. Back-pressure：height − anchor 证明的 <code>lastCheckpoint.height</code> ≤ U，即未结算块数不超过 U。U 是直接进入 config hash 的未结算块数上限，约束见 6.4。
6. Committee witness：switch 块 S(t) 必须带，其他块不得带；其 registry proof 在 S(t) 本块 anchor 的 stateRoot 下验证（4.3）。恢复按第 8 节建立已认证的起始 committee，不重发旧 pending update；恢复首块若恰为 S(t)，仍按正常 switch 规则推导。
7. 区块头按 3.2 逐字段相等；anchor 新鲜度：timestamp − anchor.timestamp ≤ <code>maxAnchorAge</code>。
8. Forced inclusion 规则（第 7 节）。
9. EL <code>newPayload</code> 返回 VALID。超限交易的撤销只用于候选列表构建（3.1）：最终 EL block body、envelope 和 blob payload 必须恰好包含被保留的交易，交易 root、receipts、stateRoot、gasUsed 与 difficulty 均匹配。验证已提交块时必须完整执行其列出的每笔交易；若其中任一交易触发 zk 超限/溢出，整块无效，不能静默删减或截断已被 Comet 签署的块中的交易后返回 VALID。

新鲜度只由候选块和已提交 parent 确定：应用不能仅因本地 L1 finalized 高度继续前进而拒绝同一个 proposal，否则跨 round 原样重发的已锁定块可能永远凑不到超过 2/3 的投票权。不启用 PBTS。BFT time 与真实时间的关系依赖拜占庭投票权少于 1/3、诚实节点时钟合理同步，以及共识持续推进；超过这一门槛的合谋方可以操纵块时间。

以下规则说明 proposal 接受和活性行为：

- <b>块大小上限</b>：envelope 中 block 项（即 payload 里的 executionBlock，含 RLP list 头）的字节长度不超过 124,000。规则只看未压缩长度，各实现结果相同，ProcessProposal 和 FinalizeBlock 都检查；proposer 构建时必须满足：alethia 的构建接口带字节上限，按 gas 选交易时一并守住，位置 0 的 FI 交易总是保留。这一上限保证每块都能单独装进一个 blob，一次 6-blob landing 装得下 6 个最大块，所以只要 K ≤ 6，任意一个网格段（6.1）总能用一笔交易 land。超过 2/3 的恶意投票权若决出违反这条规则的块，诚实节点在 FinalizeBlock 按 safety 停机，只能靠治理恢复。

<toggle>
细节：124,000 字节上限的来历与单 blob 打包

上限的来历：1 个 blob 可用 125,948 字节（130,044 减 4 KiB 帧开销），减去 1,024 字节的帧开销余量，再减去 zlib 不压缩（stored）输出的最大开销（每 65,535 字节 5 字节，另加 6 字节，此处不超过 16 字节），向下取整。Lander 单块打包时若压缩后的 payload 超过 125,948 字节，改用每块 65,535 字节（末块可更短）的 stored 输出，所以任何已决块都能单独装进一个 blob；同样的 stored 输出也让最多 6 个最大块组成的网格段装得进 6 个 blob。
</toggle>

- <b>没有可用的 anchor 就不出块</b>：若没有可用的 finalized anchor 满足相对候选块时间戳的确定性年龄上限，L2 暂停，直到出现可用 anchor。这不是独立的墙钟计时器，其时间行为依赖上述 BFT time 前提。
- <b>不采纳与本地链冲突的最新 checkpoint</b>：anchor 变化时，节点核对 anchor 证明的 <code>lastCheckpoint</code>：高度不超过 parent 高度，hash 等于本地已认证链上该高度的 EL 块 hash；不一致则拒绝并报警，可沿用仍有效的 parent anchor。Guest 只验证 witness 的 storage proof，与本地链的比对由节点完成。这一检查只约束区块祖先，不认证 landing 的其他元数据（FI head、snapshot、stateRoot 等）；这些由链下监控核对，不宣称监控能阻止桥或 registry 的付款。

## 4. Staking 与 committee

### 4.1 Registry

- register(bytes publicKey,amount,popSig)：amount ≥ minStake；activationDelay 个 L1 块后激活，registry 记录 msg.sender 为 owner。exitEffectiveL1 初始为 2\^48 − 1，表示未设定退出；requestExit 算出的生效块须小于该值，否则 revert。
  - 每个 key 一生只能注册一次（按 <code>ckAddr</code> 记录，提款后也不释放）。registry 只存 <code>ckPrefix = publicKey[0]</code> 与后 32 字节的 <code>ckX</code>，不另存 publicKey；<code>ckY</code> 仅在内部导出。

<toggle>
细节：公钥格式、解压与 PoP 校验

- <code>publicKey</code> 是恰好 33 字节的 canonical SEC1 压缩 secp256k1 公钥：<code>ckPrefix ‖ ckX</code>，prefix 只能为 0x02 或 0x03，后 32 字节为保留前导零的大端 X。注册工具可接受用户已有的 hex/Base64 公钥并转成这 33 个原始字节；用户无需提供或拆分 X、Y。合约不接受文本编码、64/65 字节未压缩形式、hybrid 编码或尾随字节。
- Registry 在内部按附录 A 解压并校验公钥：X 不得模 p 归约，须满足 X \< p；必须得到有限的合法 secp256k1 点，Y 的奇偶与 prefix 相符，重新压缩后逐字节等于输入。解压或校验失败则整笔注册拒绝，不产生 entry 或占用 key 身份。
- Registry 用解出的两个 32 字节坐标计算 <code>ckAddr = keccak256(ckX ‖ ckY)[12:]</code>，不对压缩公钥直接取 hash。要求 <code>popSig</code> 恰好 65 字节、<code>V ∈ {0,1}</code>、<code>0 < r < n</code>、<code>0 < s ≤ n/2</code>，并按附录 A 的注册摘要恢复出非零且等于 ckAddr 的地址。摘要继续绑定 L1 chain id、registry 和 <code>msg.sender</code>；有效签名必须对应传入的这把公钥，不能只检查任意地址验签成功。复制交易不能改变 owner。
</toggle>

- 共 4096 个 slot，bond id 就是 slot。提款后 slot 进 free list，新注册优先复用。
- <code>requestExit(bondId)</code>：只有该 entry 的 owner 能调用。退出在 max(当前块 + <code>exitDelay</code>, activeFromL1 + <code>exitDelay</code>) 生效。只能对尚未设置退出的 entry 调用；<code>exitEffectiveL1</code> 设定后只会提前（罚没、排除名单），不会推后。
- <b>退出确认与提款</b>：<code>exitEffectiveL1</code> 只决定选人资格，不启动取证倒计时。任何人可调用 <code>confirmExit(bondId)</code>：entry 必须已设定退出（requestExit、罚没或排除名单）、尚未提款，且 Inbox 的 <code>activeCommitteeSnapshot ≥ exitEffectiveL1</code>。首次满足时，registry 记录当前 L1 块号 <code>exitConfirmedAtL1</code>。重复调用是幂等的，不得延后倒计时。
- <code>withdraw(bondId, to)</code>：要求已确认退出，且当前块号 ≥ <code>exitConfirmedAtL1 + withdrawalDelay</code>。<code>effStake > 0</code> 时只有 owner 能调用，把本金转给 to；<code>effStake = 0</code>（已被罚没）时任何人都可调用，只释放 slot、不付款。提款将 entry 清零、释放 slot 并清空其确认记录。确认要求已 land 的 committee 不再包含该 stake，因此完整取证期从那之后才开始，长期停链不会提前耗尽它。<code>activeCommitteeSnapshot</code> 只增不减（唯一例外是第 8 节 verifier 失效回退，它同时按恢复后的 snapshot 复核全部退出确认），因此提款时无需复查。
- Owner 注册后不可更改；运营方若可能更换托管方，应由合约（如多签）调用 register，使其成为 owner。Consensus key 不能原地轮换：换 key 须先 requestExit，提款后用新 key 重新注册。key 泄露时 owner 应立即 requestExit；退出完成前，泄露的 key 仍可能被用来双签并罚没该 entry。
- <code>slashDoubleSign(bondId, voteA, voteB)</code>：任何人可调用。每张投票给出 type、height、round、block id（hash 与 part set header；nil 票全部为零）、timestamp、uint48 generation 和 65 字节签名；不接受调用者选择 Inbox、chain id 或部署 tag。

<toggle>
细节：双签证据的校验与罚没

- 两票的 type 相同且为 prevote（1）或 precommit（2），height、round、generation 相同，block id 不同。generation 不得超过 Inbox 当前的 recoveryGeneration；历史 generation 的有效证据继续接受，不因恢复换代而豁免；未来 generation 或其他部署的票不接受。
- Registry 从该 bond 存储的 <code>ckPrefix ‖ ckX</code> 按注册时相同的 canonical 解压规则内部导出 <code>ckY</code>，调用者不传坐标或替代公钥。再用本部署完整 L1/L2 chain id、registry 固定的 Inbox proxy 地址和两票共有 generation，按附录 A 重算 chainDomain、chain\_id 和两票 sign bytes。两次 <code>ecrecover(keccak256(signBytes))</code> 都须非零且等于该存储公钥的 <code>keccak256(ckX ‖ ckY)[12:]</code>。投票输入不能覆盖这些部署值。
- 该 entry 须尚未提款且 <code>effStake > 0</code>。成功时罚没全部本金：effStake 清零，<code>exitEffectiveL1</code> 改为 min(原值, 当前块)；罚没额的 <code>slashBountyBps</code> 付给调用者，其余转给 <code>slashSink</code>。
- 不要求证明该 key 当时在 committee 里：签名只有持钥人能产生；<code>chain_id</code> 带部署标识和 generation，重新部署或治理恢复后重签较低高度不会被当成双签。
</toggle>

- 每个改动 entry 的 L1 块结束时写一个 checkpoint（l1Block、count、entriesRoot）。节点按历史 checkpoint 验证 snapshot，slot 复用不影响推导。
- <b>Inbox 地址</b>：registry 部署时固定 Inbox proxy 地址，之后不可更改；Inbox 初始化时校验 registry 固定的地址等于 Inbox 自身地址、registry 的 <code>l2ChainId</code> 与自己一致。Inbox 初始化完成前（registry 检查 Inbox 的初始化状态），confirmExit 和 slashDoubleSign 一律失败，因此也无法提款；注册不受影响。Inbox 还可以在第 8 节排除名单恢复时，把名单中 entry 的 <code>exitEffectiveL1</code> 提前到 <code>recoverySnapshot</code>。

### 4.2 Epoch

- L = <code>epochLenL2</code>，即每个 epoch 的 L2 块数；<code>L1_0</code> 是 Inbox 初始化所在的 L1 块。两者在初始化时固定。
- Epoch t 的首块 <code>H(t) = 1 + t·L</code>；块 h 属于 epoch ⌊(h − 1) / L⌋。
- Epoch 只按 L2 高度划分，与 L1 进度无关；anchor 有多新只由 3.4 的 <code>maxAnchorAge</code> 约束。

### 4.3 Committee 推导

- <b>统一选人规则</b>：committee 0、正常换届和治理恢复均在各自认证的 registry snapshot 上执行下列同一规则，不依赖上一届的成员权重或参与历史。
  1. 验证该 snapshot 处最新 registry checkpoint 的完整 entries 与 root。
  2. 合格 entry 满足 activeFromL1 ≤ snapshot \< exitEffectiveL1，且 effStake ≥ max(s\_min, vp\_unit)。共识 key 终身唯一；合格 entry 之间出现重复 key 时状态无效，不能用重复 entry 增加投票权。已释放的 slot 全为零、不合格，不参与这项检查。
  3. 按 effStake 降序、平手按 set key 升序，取前 n\_max 名；不足时全取。每个成员 assignedPower = floor(effStake / vp\_unit)。
  4. 入选成员按 set key 升序编码；totalPower 是 assignedPower 之和。结果必须非空、每个 power 为正且适合 u64、总量不超过 MAX = floor((2\^63 − 1) / 8)；不满足时拒绝该推导，不能截断整数或由节点自行缩放。

<toggle>
细节：power 为什么不会溢出

- <b>Power 不会溢出</b>：TAIKO 总供应量固定为 10\^27 base unit，部署要求 vp\_unit ≥ ⌈10\^27 / MAX⌉ = 867,361,738，因此全部 entry 的 power 之和都不超过 MAX，注册无法触发溢出；第 4 步的检查只是兜底。TAIKO 若增发，须先按新总量选定 vp\_unit 并部署新配置。
</toggle>

- <b>Committee 0</b>：snapshot = genesisCutoff；targetEpoch=0。Inbox 存其 record hash，使用相同选人和 power 规则。

<toggle>
正常换届：snapshot 取值、proof 所在 root 与 H+2 生效（细节）

- <b>正常换届</b>：S(t)=H(t)−2，D(t)=H(t)−3。Snapshot 取 max(D(t) 的已提交 anchor 块号, 当前 generation 固定起点记录的 l1BlockNumber)，候选块自己的新 anchor 不参与选人。Registry account/storage proof 一律在 S(t) 本块 anchor（新带的或沿用的）的 stateRoot 下验证，即 S(t) header 的 parentBeaconBlockRoot；该 root 必然不早于 snapshot，proof 须证明取到该 snapshot 处最新 checkpoint。不得改用 D(t) 或其他 anchor 的 root，否则 proof 字节不唯一。通常 snapshot 就是 D(t) 的 anchor；恢复后 D(t) 可能属于旧 generation，max 保证不退回恢复前 snapshot。S(t) 的 FinalizeBlock 返回更新，在 H(t) 按 CometBFT 的 H+2 规则生效；S(t) 与 S(t)+1 仍由原 active committee 签署。Record.targetEpoch=t。
</toggle>

- <b>治理恢复</b>：在第 8 节认证的执行块 R 上重新运行同一选人规则，包含所有当时合格的候选；targetEpoch=floor(c/L)，从 c+1 起生效。旧 generation 的全部 pending update 作废；起始集合只由 R 的 snapshot 决定，不沿用此前 committee 的成员或 power。新 generation 中下一次实际出现的 S(t) 再按正常规则更新；恢复首块恰为 S(t) 时也执行该规则。
- <b>保证边界</b>：选人和权重由认证的 L1 状态唯一决定。协议不限制单届权重变化，不提供自动离线淘汰或墙钟接管预警；activationDelay 只延迟新注册，已激活候补无须重新等待。每届实际 committee 仍须满足第 1 节的投票权假设；DAO 持续监控在线率和集中度。

## 5. 数据格式与 DA

### 5.1 Envelope（私有）

每个 CometBFT 块唯一的 tx：<code>0x06 || rlp([block, anchor, committee, forced])</code>（后三项各为空 list 或恰好一项），CometBFT header 的 <code>data_hash</code> 承诺它（编码见附录 A）。它只在共识网络里传播，不上 L1。

### 5.2 Blob payload（公开）

- 每个 batch 用 1–6 个 blob（EIP-7594 每个 tx 的上限），沿用 Unzen 的 blob 编码：每个 blob 解出不超过 130,044 字节，非末个写满，填充位全为 0。
- 内容：<code>0x06 || zlib(rlp([executionBlock, …]))</code>，<code>executionBlock</code> 是 <code>rlp([EL header, 有序的 EIP-2718 交易])</code>。

<toggle>
细节：blob payload 的接受规则

- 接受规则用固定上限，不受运营配置影响：
  - 恰好一个完整的 zlib stream，没有预置字典和尾随字节；解压后不超过 64 MiB，单项不超过 22,020,096 字节。
  - 所有编码都是 canonical，重编码逐字节相同。
  - 恰好 <code>lastHeight − parentHeight</code> 个块，高度依次为 <code>parentHeight + 1 … lastHeight</code>；EL <code>parentHash</code> 逐块相连，首块的 parent 等于 <code>parentHash</code>，末块的 hash 和 stateRoot 等于 <code>lastBlockHash</code>、<code>lastStateRoot</code>。
</toggle>

- 不发布：CometBFT header、原始 envelope、anchor/committee/forced witness、registry entries、跳过时的 forced 交易原文、evidence、commit 和签名。它们是证明的私有输入：guest 用 <code>data_hash</code> 认证原始 envelope，再证明其执行部分与 blob 逐字节相同。
- <b>从 DA 恢复</b>：证明可靠且 L1 checkpoint 已 finalize 时，归档的 blob 加起点状态就能重建已 land 的 EL 链并核对末块 hash 和 stateRoot，不需要 witness 和签名。这不等于只凭 L1 启动 CometBFT；未 land 的块仍需完整的共识历史。

<toggle heading="h3">
5.3 公开 EL 状态重建

公开重建只依赖起点状态、canonical L1 交易/事件/header 和对应 blob，不依赖 validator 私有数据库、完整 envelope、witness、签名或运行中的 L2 RPC。必须提供源码可用的重建程序和以下公开输入：

- 起点资料包含可下载的完整 genesis allocation/状态与代码、内容 hash、EL 规则版本、L1/L2 chain id、合约地址、L1\_0、genesis hash 和 stateRoot；程序本地重算并匹配 L1 认证的起点，不能只信任未认证 snapshot。
- 按 canonical L1 landing 顺序验证 versioned hashes 和完整 (p,h\] 的 blob；p 从证明输入读取，实际 c 从认证事件/记录读取。重叠前缀核对已重建的 EL hash 和链链接，只从认证 c 的 EL 状态重执行 (c,h\]，核对 h 的 hash/stateRoot 和 FI cursor。按认证 generation 和固定恢复起点选择历史。缺原始材料、版本不受支持或 hash 不匹配时拒绝，不能重复执行前缀、静默跳过或用 RPC 状态代替认证。
- 历史 blob 必须可获取，并从 L1 承诺验证归档内容。完整 CometBFT/proving 所需私有历史另见 9.1；仅重建 EL 不需要它们。
</toggle>

## 6. Landing 与结算

### 6.1 land

land 无许可、nonpayable。证明和 blob 覆盖完整 (p,h\]，即从证明起点 p 到末点 h；执行时原子读取最新 checkpoint 高度 c，只结算新后缀 (c,h\]，其他 lander 先推进了 c 也不影响同一笔交易。Landing 只在网格点结束：高度（从 Etna 起点 0 计）是 K 的倍数，所以 p、c、h 都是网格点（原因见 6.3，K 的取值见第 11 节）。检查依次为：范围、网格与起点记录；叶子恰为 (p,h) 内全部网格点的叶子，且 c 处叶子与当前 checkpoint 记录一致；FI head 推进；reference 块与 blob；计算 cutHash 并验证双证明。全部通过后原子更新 checkpoint、snapshot、FI head、slot 285 记录和 SignalService。

下面折叠的参考 Solidity 列出 land 的全部检查，这些检查是规范；所有检查先于状态修改，叶子检查先于证明验证，其余顺序只是示意。land 的签名、LandInput 的八个字段、K 以及 cutLeaf 和 cutHash 的编码（附录 A）是接口。局部变量名和辅助函数的写法只是示意：辅助函数的结果以附录 A 和注释为准，存储变量对应附录 B 的规范布局。

<toggle>
参考 Solidity：land 的检查与状态更新

```solidity
// 存储（附录 B）：recoveryGeneration 268、lastCheckpoint 270/271、fiHead/fiTail 281、
// activeCommitteeSnapshot 284、landings 285；generationStartHeight() 读 290

struct LandInput {
    uint256 parentHeight;            // 证明起点 p
    uint256 lastHeight;              // 末点 h
    bytes32 lastBlockHash;           // h 的 EL block hash
    bytes32 lastCometHash;           // h 的 CometBFT block hash
    bytes32 lastStateRoot;           // h 的 EL stateRoot
    uint256 l1ReferenceBlockNumber;  // reference 块
    uint256 forcedInclusionHead;     // 结算后的 FI head
    uint256 activeCommitteeSnapshot; // 实际签署 h 的 committee 的选人 snapshot
}

// 截点：每个高度的 EL block hash、CometBFT block hash 和 FI cursor，对应叶子
// cutLeaf(x) = keccak256(abi.encode(x, blockHash, cometHash, forcedHead))（附录 A）。
// Landing 只在网格点结束：高度（从 Etna 起点 0 计）是 K 的倍数，所以每个 checkpoint 高度都是网格点。
// 两份证明认证 (p, h) 内全部网格点叶子的哈希 cutHash（附录 A），land 把这些叶子全部带上（原因见 6.3）。
// K：网格间隔，协议常量，1 ≤ K ≤ 6，具体取值待定（第 11 节）

function land(
    LandInput calldata input,
    bytes32[] calldata leaves,    // (p, h) 内网格点 p+K, p+2K, ..., h-K 的叶子，按高度排序
    bytes calldata proof          // 双证明（6.2）
) external nonReentrant {          // 无许可、nonpayable；与 recover 共用重入锁（8.3）
    uint256 p = input.parentHeight;
    uint256 h = input.lastHeight;
    uint256 c = lastCheckpoint.height;          // 执行时原子读取；必是网格点

    // 1. 范围与网格。c >= h 表示目标已结算：拒绝且不改变状态。
    require(generationStartHeight() <= p && p <= c && c < h && h < 2**48);
    require(p % K == 0 && h % K == 0 && h - p <= maxBatchBlocks);

    // 2. 起点 p 须有保留的 slot 285 记录且属于当前 generation，缺失则拒绝；
    //    唯一例外是当前 generation 的起点，它可沿用更早 generation 的记录。证明不能跨 generation。
    Landing memory origin = landings[p];
    require(origin.elHash != 0);   // 写入过的记录 EL hash 不为 0（block 0 存 genesis hash，其 Comet hash 为 0）
    require(origin.generation == recoveryGeneration || p == generationStartHeight());

    // 3. leaves 恰为 (p, h) 内全部网格点的叶子。c > p 时，c 处的叶子须等于合约按 c 的 slot 285 记录
    //    算出的叶子：高度、EL hash、Comet hash 和 FI cursor 逐项相同（不能只比较高度或 stateRoot）；
    //    c = p 时，起点记录已由第 2 步和 statement 绑定。c 处记录的 FI cursor 还须等于当前 FI head。
    //    这些都在验证证明之前检查。其余叶子只用于计算 cutHash，不符时第 6 步证明验证失败。
    require(leaves.length == (h - p) / K - 1);
    Landing memory cur = landings[c];
    require(cur.head == fiHead);
    if (c > p) {
        require(leaves[(c - p) / K - 1] == keccak256(abi.encode(c, cur.elHash, cur.cometHash, uint256(cur.head))));
    }

    // 4. FI head 只从执行前的值推进到 forcedInclusionHead：不超过 tail，新增消费不超过 h - c。
    //    证明认证从 p 开始的全部消费，链上只应用新后缀，不重新消费前缀。
    uint256 headAfter = input.forcedInclusionHead;
    require(fiHead <= headAfter && headAfter <= fiTail && headAfter - fiHead <= h - c);

    // 5. reference 块在过去且 hash 可读（blockhash 的 256 块或 EIP-2935 的 8191 块窗口）。
    //    本交易带 1-6 个 blob，绑定完整 (p, h]，不能换成只含后缀的 blob。
    require(input.l1ReferenceBlockNumber < block.number);
    bytes32 refHash = l1BlockHash(input.l1ReferenceBlockNumber);
    require(refHash != 0);
    bytes32[] memory blobs = txBlobHashes();   // 按 index 顺序
    require(blobs.length >= 1 && blobs.length <= 6);

    // 6. 由 leaves 计算 cutHash，构造 statement 并验证双证明（编码见附录 A）；leaves 不符时证明验证失败。
    //    parentHash、parentCometHash 和 headBefore 取自起点 p；statement 的其余字为部署常量与
    //    committeeConfigHash（slot 269）。activeCommitteeSnapshot 由证明认证为实际签署 h 的 committee 的
    //    选人 snapshot，且不超过 reference 块。
    bytes32 cutHash = keccak256(abi.encode(bytes32("ETNA_LAND_CUTS_V1"), recoveryGeneration, p, h,
                                           keccak256(abi.encodePacked(leaves))));
    bytes32 st = statement(recoveryGeneration, input, origin, refHash, keccak256(abi.encodePacked(blobs)), cutHash);
    verifier.verifyProof(st, proof);   // 两份证明都通过才不 revert

    // 7. 原子更新，任一步失败整体回滚；不转出 FI 费。landing 记录的 parent 始终是实际 c，
    //    不是证明起点 p。前沿推进后，绑定旧 c 的恢复授权都不可执行（8.3）。
    lastCheckpoint = Checkpoint(h, input.lastBlockHash);
    activeCommitteeSnapshot = input.activeCommitteeSnapshot;
    fiHead = headAfter;
    landings[h] = Landing({parentHeight: c, generation: recoveryGeneration, head: headAfter,
                           elHash: input.lastBlockHash, cometHash: input.lastCometHash}); // slot 285
    signalService.saveCheckpoint(h, input.lastBlockHash, input.lastStateRoot);
    emit Landed(p, c, h, cutHash, input.activeCommitteeSnapshot, VERSION);
}
```

### 6.2 证明

- Verifier 是 Inbox 的 immutable。合约只调用它的 <code>verifyProof</code> 接口，不检查具体实现；生产部署必须使用与现网（Unzen）相同的 <code>ZkRequiredVerifier</code>：恰好两份子证明、至少一份 ZK（SGX + RISC0/SP1，或 RISC0 + SP1），需要两套 guest。Verifier 地址、code hash 和接受的 image 集合写进部署清单，作为 Etna 验收与上线清单 中的上线门槛核对。单个后端故障可以换组合；凑不齐任何合法组合时 settlement 停止。
- 提款直接用 land 写进 SignalService 的 checkpoint，没有额外的 withdrawal root、延迟或 veto。
- 本节 parentHeight/parentHash 和 headBefore 取自证明起点 p。每份子证明都认证同一个 statement，包括 cutHash；不接受一份只证明执行、另一份才证明截点的拆分。执行时 p 已不是最新 checkpoint 也不构成失效，实际 c 由 6.1 原子选择。

### 6.3 Batch

- Batch 只在网格点切分（6.1），可以跨 epoch。换届高度、被取消的旧生效高度及下一正常交接与网格无关，可以落在 batch 内部，也可以恰在网格点上；恢复起点是某个 checkpoint，因而总是网格点。这些都按实际 schedule 处理，不能靠避开切点维持正确性。<code>l1ReferenceBlockNumber</code> 可以选最近的 L1 块，避免仅因 reference hash 过期而失败。长期停摆后不经治理恢复、直接证明并 land c 以上的旧后缀时，这些块用到的旧 anchor 仍须在支持的 ancestry/proving 预算内认证，选择近期 reference 不会消除这一要求。Lander 和 prover 须给 reference header 链长度设资源上限（参考值 131,072 个，按 12 s 约 18 天的 L1 块）；超出上限的旧后缀无法按常规方式 land，只能按第 8 节治理恢复丢弃（最多 U 块）并从 R 重启，R 之前的停摆不计入这一上限（8.4）。
- Batch 从一个已认证、保留的历史 checkpoint p 起证，通常选择准备时的最新 checkpoint；p 不得低于当前 generation 的起点，证明不可跨 generation。其他 lander 先推进到 c 时，只要 p ≤ c \< h，原交易（双证明、blob 和叶子）原样有效，执行时自动结算 (c, h\]，无需重证、重聚合或改动任何参数。若 c ≥ h，目标已结算，可取消任务。Reference 过期、规则/image 版本变化或 generation 切换仍可能使任务失效；不能改写已签任务绕过这些边界。复制交易不改变任何证明内容；landing 不带报酬，由谁提交不影响结算结果。

<toggle>
细节：为什么只在网格点结算

- <b>为什么要核对 c</b>：证明可以从早于 c 的 p 起证，c 则由别的 landing 推进。超过 1/3 的投票权双签时，同一高度可能有两个都合法的块；不核对证明的链在 c 处就是 L1 记下的块，L1 就可能先结算一条分叉、再接上另一条，bridge 可被双花。要求 p = c 就不必核对，但每次被别人抢先 land 都得重新证明。
- <b>为什么用网格</b>：证明生成时不知道执行时的 c，只能承诺所有可能的 c。若每个高度都可能是 c，就要用 Merkle 树加窗口和兄弟节点，由 lander 签名时猜 c 会落在哪，猜错就 revert。规定 landing 只在网格点结束后，c 也只能是网格点，候选表短到可以整张带上：c 落在 (p,h) 内任何网格点，同一笔交易都有效，lander 不用猜，对手也无法靠抢先 land 让诚实提交失败（第 12 节第 16 项）。合约只做一次哈希和一次下标比对，guest 也不用建 Merkle 树。
- <b>K 怎么取</b>：一个网格段最多 K 个块，必须总能用一笔交易 land。3.4 的块大小上限让每块能单独装进一个 blob，一笔交易最多 6 个 blob，所以 K ≤ 6。K 越大叶子越少，但等待、停链时多丢的块和每次 landing 的证明量都随之变大（见下条）。具体取值待定，按验收中最坏情形的证明能力确定（第 11 节）。
- <b>代价</b>：lander 最多多等 K − 1 块凑到网格点；叶子随 batch 线性增长，B 块的 batch 带 B/K − 1 个、每个 32 字节（例如 300 块时，K = 3 为 99 个、3,168 字节，K = 6 为 49 个、1,568 字节）；任意一个网格段都须能在一次 landing 的双证明里证出（第 1 节）；链停在两个网格点之间时，治理恢复最多多丢弃 K − 1 个可证的已决块（8.1）。
</toggle>

- Lander 可在链外协调当前任务，监控 checkpoint 并取消过时工作；只复用能重新认证且与目标版本兼容的输入或子证明。协调不授予独占权限，不能绕过 6.4 的 U 上限。废弃证明及重试费用由 DAO 的运营资金承担（附录 C）。
- 正常 batching 与提交按 6.4 的主动调度执行；只剩一个可出块高度时必须报警并立即提交可用 batch，不应等到这一刻才开始证明。

### 6.4 Back-pressure

L2 高度不得超过 anchor 证明的 lastCheckpoint.height + U，U 是直接进入 config hash 的整数参数，要求 <code>K ≤ U ≤ 65,536</code> 且 U 是 K 的倍数，使暂停点正好是网格点。U 是结算故障的断路器，不是日常结算的节拍：只有证明或 landing 长时间停摆、或某个已决块证不出来时才应触发暂停，以封顶治理恢复可能丢弃的块数。目标部署采用 <b>U = 3,600</b>（约 4 s 出块时约 4 h）；约 4 s 出块和相邻成功 landing 的 L1 入块间隔不超过 20 min 是运行目标，不是区块有效性规则。U 与 epoch 长度 L 互不约束：未结算后缀可以跨越多个 epoch，L 按换届需要单独选定（第 11 节）。Landing 停摆后最多再出 U 块；landing 入 L1 还不足以解除暂停，其状态须 finalize 并被新的 anchor 采纳。

<toggle>
细节：时延预算与未结算块数的算术

出块间隔约 4 s 是运行目标，不是最小间隔或持续出块保证。L 是块数，名义 epoch 时长为 L × 目标块间隔，实际可长可短。端到端结算时延包含 batching、排队/证明、重试、L1 入块/finality 和 anchor 采纳；判断是否会触发 back-pressure 要直接看 <code>height − anchor.lastCheckpoint.height</code>，不能只用平均块间隔换算。U=3,600 在持续 4 s 出块时对应 4 h；这不是墙钟停摆承诺。正常运行时未结算块数约为“相邻 landing 入块间隔 + 前一 batch 末块产生到其 landing 入块的耗时 + 下一 landing 的 finality 与 anchor 采纳耗时”，两份证明按实际关键路径计时；按 20 + 20 + 20 min 约 900 块，留给证明或 landing 故障的余量约 3 h。这一时延预算是运维目标，未达到时不暂停，只是余量变小。持续 4 s 出块约为 15 块/min；结算吞吐必须跟得上，不能让未结算积压持续增长。若按每 20 min 一个 batch 运行，平均须覆盖约 300 块；maxBatchBlocks、六 blob 容量或 proving 能力装不下时，必须更频繁地结算或补足能力，不能仅靠增大 U 延后停链；故障恢复后，证明能力须高于出块速率才能追平积压。20 min finality/采纳项既不是 L1 finality 上界，也不放宽 maxAnchorAge。超过额度时正常暂停，不得绕过 U；本文不据此声称任何实测暂停比例或不停链 SLA。
</toggle>

持续运行时，U 应大于一次 landing 往返期间的出块数。Lander 应从最新 checkpoint 持续准备与提交 batch，按实际未结算块数和剩余证明/finality 时间提前提交；20 min 不是必须等满的 batching 定时器，也不授予独占 landing 权限。“只剩一个可出块高度”是紧急信号，不是开始证明的时机。4 s 仍是目标，不能把临时降低出块速率后的结果算作达到该目标。

U 在部署时固定，节点不能通过本地配置覆盖它。Anchor 是 finalized L1 块，checkpoint 只前进，按 anchor 计数不会少算未结算块；唯一例外是第 8 节 verifier 失效回退，回退后的计数规则随该次升级发布。L1 finality 滞后只会提前触发暂停，不允许超出 U。提高 U 增大了第 8 节治理恢复可能丢弃的块数上限；恢复前先结算到最后一个可证的网格点（8.1），实际丢弃的只是确实无法结算的块，最多再加 K − 1 个可证但凑不满网格段的块。按选定的 L 公布名义 epoch 时长 L × 4 s（建议值 L = 900 时为 60 min），不把它当作墙钟保证。

<b>验收</b>：采用目标配置前，须通过 Etna 验收与上线清单 中的资源与时延验收；未通过前不能称可部署或达到目标。不得省略最新 checkpoint 检查、使用未 finalized anchor、少一份证明、单节点放宽 U 或静默扩大资源上限。

## 7. Forced inclusion

### 7.1 提交

<code>saveForcedInclusion(bytes tx)</code>：不超过 8,192 字节，付费 <code>fee × (threshold + pending) / threshold</code> gwei，pending 是 L1 上尚未被 land 消费的 entry 数（<code>tail − head</code>；结算滞后时也包括 L2 已消费、尚未 land 的 entry），超付部分退回。Entry 只存 <code>keccak256(tx)</code>、L1 时间戳和 L1 块号；入队事件记录 entry 下标、交易原文和本次实收费用（wei，不含超付退款），提交时不检查编码。成功入队时，按公式计算并收取的费用即归协议，留在 Inbox 中。此费用购买队列准入，不以成功执行为退款条件：包含、合法跳过、治理置空及结算回退后的重放均不退还、不重复收取、不支付给 lander。历史收费明细只由入队事件留档，不作为消费或恢复的输入；提交交易整体 revert 则不入队、不计费。

<toggle>
细节：协议费用转出

<b>协议费用转出</b>：部署时固定非零 DAO treasury 地址 <code>protocolFeeRecipient</code>（Inbox immutable），并在部署清单中公布。Inbox 只有 <code>saveForcedInclusion</code> 接收 ETH（超付在同一交易内退回），其他入口都不接收 ETH，因此除强制转入的 ETH 外，Inbox 余额就是尚未转出的 FI 费。任何人都可调用 <code>sweepProtocolFees()</code>，把 Inbox 的全部 ETH 余额转给该地址，转账失败则整体回滚；强制转入的 ETH 一并转出。<code>saveForcedInclusion</code> 和 <code>land</code> 内不向 treasury 转账，因此 treasury 收款失败只影响转出。转出不依赖 queue head 或 landing，也不修改 FI entry 或队列进度。
</toggle>

### 7.2 消费规则

- L2 状态维护 cursor c（已消费数，初始为 0）。每块至多消费一个 entry，且只能是第 c 个。Land 之后 Inbox 的 head 等于 checkpoint 处的 c。
- 每块用自己的 anchor A：若 <code>c ≥ tail(A)</code>，不带 forced witness；否则必须带 entry c 的 witness，即在 A 的 stateRoot 下的 storage proof。
- <b>到期</b>：<code>A.timestamp ≥ entry.timestamp + forcedInclusionDelay</code>，按不溢出的算术计算。Entry 永不过期。

<toggle>
合格交易：原文恰好是一个 canonical EIP-2718 交易（判定细则）

- <b>合格交易</b>：原文恰好是一个 canonical EIP-2718 交易。Canonical 只看原文、不读状态，节点和 guest 按同一组共享的接受/拒绝 vectors 实现，不依赖某个库的解码器：解码用尽输入、重编码逐字节相同；类型是固定 EL 版本接受的非 blob 类型（type 3 和未知类型都不合格）；typed 交易的 chain\_id 等于 L2 chain id、y\_parity ∈ \{0, 1\}，legacy 交易的 v ∈ \{27, 28, 2·l2ChainId + 35, 2·l2ChainId + 36\}；nonce 和 gas 小于 2\^64，各费用字段小于 2\^128，value 小于 2\^256；签名的 r、s 在 \[1, n − 1\] 内（n 为 secp256k1 的阶）、s ≤ n/2，且能恢复出 sender；gas 不超过 <code>L2_BLOCK_GAS_LIMIT</code>。这些检查只针对交易本身的字段和签名：type 4 的 authorization 元组只要求 EIP-7702 规定的字段宽度，元组签名或 chain id 无效时由 EL 跳过该元组，不影响合格判定。合格判定不看费用：<code>maxFeePerGas</code>（type 0/1 交易为 <code>gasPrice</code>）低于该块 basefee 的交易，单笔构建为空，可以合法跳过。Proposer 能零成本把 basefee 推到 1 gwei 上限（3.2），因此 FI 交易应把 <code>maxFeePerGas</code> 设为不低于 1 gwei，才能确保不因费用被跳过。
</toggle>

<toggle>
细节：给定列表构建（判定能否合法跳过）

- <b>给定列表构建</b>：构建必须完成 <code>[tx]</code> 的确定性构建判定才返回，结果只有两种：含该交易的块，或空块；不得返回构建完成前的占位块。合格交易因 nonce、余额、intrinsic gas 等任何交易级原因不能执行时，结果都是空块，不得报错。超时、连接中断、newPayload 返回 SYNCING 等暂时性的基础设施故障不是构建结果：ProcessProposal 和 FinalizeBlock 都等待并重试到得出结果为止，不得因此拒绝 proposal、判块无效或跳过；等待期间该节点不处理新的共识消息。EL 确定无法在该 parent 上构建（例如缺少已被裁剪的历史状态）时，按第 8 节 safety 停机，补齐后重启。合格交易的 gas 不超过一个块的上限，所以单次构建的工作量有上界。 这里的单笔构建从该 parent 和相同 attributes 开始，候选列表仅为 <code>[tx]</code>，给足完整 EVM gas/zk gas 块预算，不得用普通交易先占预算。依共用规范因 zk 超限/计量溢出完整撤销 <code>tx</code> 后返回的空块，是可复现的确定性空结果；正常 EVM revert/OOG 且仍被包含则不是空块。节点和 guest 均按同一规则完整判定；主机超时、prover 资源耗尽或本地较小预算均不能作为跳过证据。
</toggle>

- 到期后既不包含也不合法跳过的块无效。只有第 0 位算包含：同 sender、同 nonce 的替代交易，或把该交易放在后面，都不算。

<toggle>
细节：witness 里的原文与取原文

- Witness 里的原文可以为空；非空时 hash 必须与 entry 相同。跳过时必须带原文，空原文只能证明提交的本来就是空字节。包含时 guest 直接认证执行块的第 0 笔交易，proposer 因此留空以节省数据。
- Proposer 用 <code>eth_getLogs</code> 在 entry 的 L1 块取原文并核对 hash。到期前取不到可以先出普通块；到期后取不到就不能出块。
</toggle>

- <b>置空的 entry</b>：entry 提交后，<code>txHash</code> 只会被第 8 节治理恢复第 3 步改写为空字节的 hash <code>keccak256("")</code>。在看到这个值的 anchor 下，原文就是空字节，不需要 <code>eth_getLogs</code>；这样的 entry 不可能被包含，到期后按原文不合格的情形跳过，不需要 EL。

### 7.3 保证与界限

- 到期的队头 entry 必须按 7.2 包含或合法跳过，没有仅因年龄删除的路径。对于当前队头 entry，任何满足 <code>block.timestamp ≥ entry.timestamp + forcedInclusionDelay + maxAnchorAge</code> 的合法块都必然判定它已到期，加法使用防溢出算术。这是基于块时间的推论，不是墙钟 inclusion deadline；墙钟上的推进还依赖 3.4 的 BFT time 前提、L1 finality、队列积压和 settlement。
- 发送方要为 gasLimit × <code>maxFeePerGas</code> 预留余额；队列每块至多消费一个，费用随排队数线性上涨。
- <b>Backlog 成本口径</b>：设攻击者入队实际支付费用总额为 F。费用归协议后，无论攻击者赢得多少 landing，都不能通过消费这些 entry 收回 F；L1 提交 gas、其选择承担的 proving/landing/blob 成本以及实际执行的 L2 gas 另计，其他奖励或收益另行核算。生产费率、threshold、持续攻击下的实际服务率及正常用户成本须另行测算，算例见 Etna 验收与上线清单。

## 8. 停机与恢复

<b>范围</b>：自动重试的 liveness 暂停不丢块；执行治理恢复才丢弃 c 以上的后缀。

- <b>Liveness 暂停</b>：进程不退出，CometBFT 继续轮转，原因消失后自动恢复，不丢块。原因包括 anchor 未 finalize 或超过 <code>maxAnchorAge</code>、back-pressure、committee witness 取不到、到期 forced 交易的原文取不到。本地 L1 节点落后、连不上或超时也属于这一类（第 9 节）。anchor header 的 hash 与 canonical hash 一致但按 3.3 解析不了（L1 改了 header 格式）时也一样：ProcessProposal 拒绝，FinalizeBlock 等待重试，升级节点后自动恢复。

<toggle>
细节：stock CometBFT 下保证暂停不丢块的 ABCI 约束

为使 liveness 暂停在 stock CometBFT v0.40.0 下不丢块：应用对任何连接上的任何 ABCI 方法都不得返回错误或异常（CometBFT 会退出或 panic），Query 和 snapshot 相关方法只返回错误码或空结果；ProcessProposal 只返回 ACCEPT 或 REJECT；PrepareProposal 的结果不超过请求中的 <code>max_tx_bytes</code>，暂停期间或放不下所需 envelope 时返回不含交易的占位提案，它会被 ProcessProposal 拒绝，CometBFT 照常换 round；InitChain 只返回 <code>app_hash</code>，不返回 validators 和 consensus params；Commit 的 <code>retain_height</code> 恒为 0。签名被拒后的自动恢复见第 9 节。
</toggle>

- <b>Safety 停机</b>：进程退出，需要人工排查。原因有三类：已决块违反有效性规则，或与本地状态、EL 矛盾（包括 EL 以 <code>-38002</code> 拒绝）；同步或建立信任时发现分叉证据，或者自己的 L1 节点、EL 返回格式错误或无法验证的数据（第 9 节；hash 一致但按 3.3 解析不了的 L1 header 除外）；冷同步重放 canonical 跳过时，EL 以不可重试的错误拒绝在 parent 上构建，通常是缺少该 parent 的历史状态，需要先补齐再重启。
- <b>Generation 被取代</b>：anchor 里的 <code>recoveryGeneration</code> 大于本链的 generation 后，本链不再前进，节点只能按新 generation 重启。ProcessProposal 遇到这样的 anchor 时拒绝该 proposal 并撤销 checkpoint trust，进程继续运行；已决块带这样的 anchor，或者启动、signer 建立 session 时的信任检查发现 Inbox 的 generation 与本链不同，都按 safety 停机处理。
- <b>Committee 推导失败</b>：4.3 的候选为空或认证/数值约束失败时，S(t) 的 proposal 被拒绝，可能持续停链；不能自行缩放、补成员或跳过换届。可按下文治理恢复从新的 R snapshot 重选，但仍需合格候选。
- <b>超过 1/3 投票权离线</b>：共识停住，不自动换人或降权；成员回来可恢复，否则按下文治理恢复重选。提款仍按 4.1：已确认且等待期满的退出可提款，未确认者等待 settlement 覆盖。
- <b>Settlement 停摆</b>：L2 最多再出 U 块，然后因 back-pressure 停产。
- <b>Verifier 失效</b>：两份证明同时接受错误结果不在威胁模型内（第 1 节）。错误 landing 可能写坏 checkpoint、FI head 或 snapshot，普通治理恢复不能修复。此时先用 <code>SignalService</code>、Bridge 的 pause 和 QuotaManager 限额止损；更换 verifier 本来就要升级 Inbox，结算回退随同一次 DAO 升级（Inbox 与 registry）执行：Inbox 把 lastCheckpoint（slot 270/271）、FI head（281）和 activeCommitteeSnapshot（284）恢复为最后一个可信 landing 写入的值，作废其后的 landing 记录和 SignalService checkpoint。最后一个可信 landing 指第一个错误 landing 之前的最后一个 landing；若没有，则恢复为初始化时的值。registry 按恢复后的 snapshot 复核每个退出确认，只保留 snapshot ≥ 该 entry 的 exitEffectiveL1 的确认，其余清空。复核不按确认所在的 L1 块号判断，因为块号无法给同一块内的交易排序。节点处理回退的规则随升级发布；回退使 c 回到旧值，DAO 须同时取消所有未执行的恢复授权；回退本身不改变 generation。若曾在高于恢复后 c 的位置执行过治理恢复，该 generation 的起点高于恢复后的 c，无法再 land；DAO 须在回退后从恢复后的 c 再执行一次治理恢复。错误 checkpoint 已支付的桥款或已提走的 stake 无法追回；L2 手续费在执行时已付给 proposer，不受影响。
- <b>治理恢复</b>：用于 landing 长期停摆、正常结算无法解除的情形。调用为 recover(expectedGeneration, expectedC, exclusions, fiToClear)，exclusions 是按 bondId 严格递增的 (bondId, entryKey) 列表，fiToClear 为严格递增的 entry 下标。调用条件、防重放与原子性见 8.3，授权时机见 8.1。
  1. 先验证全部名单和状态，再在同一事务内完成以下转换。
  2. 排除名单中的 entry 必须仍对应调用参数中的 entryKey，且未释放或复用，否则整笔拒绝。由 Inbox 调 registry，将 exitEffectiveL1 提前到 min(原值,R)，不罚没；双签证据仍可罚掉全部本金。
  3. fiToClear 中每项必须仍在 \[head,tail)；将 txHash 改为 keccak256("")，保留时间戳和入队块号。仅用于处理证不出来的内容；未列出的 entry 保留并在新链依规则消费。入队费不退款、不重收、不向 lander 付款。
  4. 递增 generation（generation+1 必须适合 uint48），写入 8.4 的固定起点记录并公开执行事件及完整名单。保留 checkpoint c 的 landing 记录和 FI head。activeCommitteeSnapshot 不因恢复抢先更新；只有新 committee 的真实 landing 才推进它。已确认的退出不受影响（4.1）。
  5. 节点从认证的 c 重建 EL；在执行块 R 的 registry snapshot 上按 4.3 重选 committee，不沿用旧 generation 的 power。已被排除的 entry 不合格；其他当时已激活的候选可入选。旧 generation 全部 pending 作废，按全局高度继续正常 switch/H+2；按 8.2 认证完成前不为新 generation 签名。节点和 guest 独立认证 R 的最终 snapshot，不信任治理给出的名单权重。
  6. 只丢弃 c 以上未结算后缀，用户需重发交易，这些块里的手续费随块一起作废；不回滚已结算前缀。

### 8.1 恢复授权与用户边界

- 恢复、名单排除和 FI 置空只由 DAO 授权；普通值班或 pause 权限没有这些能力。Bridge/SignalService 暂停只能限制后续暴露，不能追回已支付的桥款或 stake。
- <b>时机</b>：recover 没有独立的时间门槛，实际最短停摆取决于 DAO 授权路径的延迟。expectedC 取授权时的 c 并随授权固定，之后只要有一次 landing 就无法执行，因此经否决期和 timelock 的标准路径执行的恢复，意味着这段时间内没有任何 landing。不经否决期的紧急路径只应在 landing 确实长期停摆、正常结算无法解除时使用，其名单可能到执行时才公开，没有事先通知。进度慢、TPS 低、FI 超过墙钟期限或 20 min landing 目标未达都不是恢复理由。
- <b>授权前</b>：DAO 先让 lander 结算到最后一个可证的网格点，expectedC 取结算后的 c；只丢弃确实无法结算的块，最多再加 K − 1 个可证但凑不满网格段的块；排队和执行前复核拟选集合非空、超过 2/3 power 在线、单方低于 1/3、历史和 signer 可用，并确认 c 的 landing 与诚实节点本地链一致：slot 285 记录中的 EL hash、Comet hash 和 FI head，c 处的 SignalService checkpoint，以及 slot 284（签署 c 的 committee 的选人 snapshot）。不一致说明 verifier 已失效，须先按第 8 节 Verifier 失效回退，再授权恢复。

<toggle heading="h3">
8.2 Recovery signer

- 签名器按完整 <code>chain_id</code>（含 generation）分别保存 stock HRS 状态，签名先持久化再返回，任何时候都不重置或回退；同一 key 不得有可绕开该状态独立签名的副本。状态丢失或无法确定最新状态时停签，不能靠删除状态恢复服务。
- 只有自己的 finalized L1 视图认证了恢复执行（新 generation、起点 c、R 的 registry snapshot 及按 4.3 重选的 committee），且 8.4 bootstrap 和第 9 节 checkpoint trust 都通过后，才为新 generation 签名；新 generation 从 c + 1 起使用独立的 HRS 状态，此后旧 generation 的签名请求一律拒绝。跨 generation 的票签名域不同，不构成双签。主备切换、fencing 等防止同域双签的手段属于运营实践。
</toggle>

<toggle heading="h3">
8.3 recover 的执行时检查

- <b>调用者与条件</b>：recover 只能由 Inbox owner（DAO）调用，执行时 expectedGeneration、expectedC 必须与当前状态相等。Inbox 不维护恢复队列或调度状态，也不区分 DAO 的授权路径；授权或排队不冻结 landing。
- <b>防重放与作废</b>：新 landing 改变 c，恢复改变 generation。generation 永不减少；c 只增不减，唯一例外是 verifier 失效后的升级回退（见上文 Verifier 失效）。先 land 则旧授权失败，先恢复则旧 generation 的证明失败；成功执行后同一授权不能再执行，失败的调用重试时须再次通过全部检查。修改名单须由 DAO 重新授权，无需在 Inbox 中逐个取消旧授权。
- <b>原子性</b>：名单校验、registry forceExit、FI 置空、计数器更新和起点记录都在 recover 内一笔完成，任何一步失败都整体回滚，不留部分退出、FI 改写或新 generation。排除和置空只在 recover 内执行，不另设任何入口（含仅 owner 可调的入口），也不能先在另一笔交易里做。执行期间拒绝能改变 checkpoint、generation、恢复名单或提款条件的跨函数重入，包括 land、recover 和 registry 提款。
</toggle>

<toggle heading="h3">
8.4 确定性 recovery bootstrap 与验收

恢复沿用 stock CometBFT v0.40.0，不增加授权者或可信 snapshot 服务。c 为固定恢复起点，R 为执行交易的 canonical L1 块，均从自己的 finalized L1 视图认证。

- <b>唯一元数据</b>：slot 290 为每个 generation 保存 (startHeight,l1BlockNumber,l1Timestamp)，分别为 c、R.number、R.timestamp。Generation 0 初始化为 (0,L1\_0,初始化交易所在 L1 时间戳)，只描述创世，不授权恢复。每条记录只写一次，之后恢复和 landing 都不覆盖或删除；缺失记录必须拒绝，不能用 mapping 默认值或最新 checkpoint 代替。generationStartHeight 和 recoverySnapshot 分别读取 startHeight 与 l1BlockNumber，不另存缓存。节点/guest 在不早于 R 的认证 L1 root 下验证当前 generation 的记录、保留的 c 记录和 R 的 registry snapshot，不依赖事件或可信运营者。此前同一 c 的恢复记录保留供审计；committee 只按当前 generation 的 R 重选。Generation 0 的 committee 仍取 genesisCutoff，不在 L1\_0 重选；本节 R 重选用于 generation>0。
- <b>唯一 genesis</b>：chain\_id 使用新 generation，initial\_height=c+1，genesis\_time=R.timestamp；EL 状态须匹配 c 的认证 EL hash 和其 header 的 stateRoot，InitChain 返回 app\_hash=ELHash(c)。Genesis validators 由 R snapshot 的统一规则选出，record.targetEpoch=floor(c/L)、cutoffL1Block=R。所有旧 pending 作废，后续 switch 按全局 L2 高度和 H+2 继续。
- <b>共识衔接</b>：首块使用 stock genesis 的空 LastBlockID/LastCommit；c 的旧 Comet hash 单独保留为证明边界，不填入首块 LastBlockID。初始 FI cursor 来自认证的起点 head；首块必须带不早于 R 的 finalized anchor witness（3.3、3.4 第 3 条）。新 generation 不使用 c 的 anchor，证明只用不早于 R 的 L1 root，因此 R 之前的停摆不计入 ancestry 上限；新 generation 只从自己的 anchor（均不早于 R）起受该上限约束（6.3）。R.timestamp 固定 Comet genesis 时间，EL 时间仍按 3.2；不能使用运营者启动时间。
- <b>Bundle 与签名</b>：包包含固定起点、当前 generation/R 的证明、R registry entries/checkpoint、所需 EL/Comet 历史和从 R 起的 L1 ancestry。新加入节点用固定 genesis 重放到自己的 finalized L1 最新 checkpoint，并匹配 EL/Comet hash 才可信；不能把最新 checkpoint 当同域新 genesis。签名按 8.2：缺数据拒签、认证矛盾停机，不能删除 signer state。
- <b>历史保留</b>：slot 285 的历史 checkpoint 和实际 parent 链服务旧 p 的重叠证明和公开重建，不裁剪。各 generation 起点、registry 历史 checkpoint 及证明所需的原始材料继续归档。按 R 直接重选 committee 不减少对历史数据和弱主观性认证的需求。

<b>启用前验收</b>：见 Etna 验收与上线清单；文档修改、mock/host 通过或恢复后出块都不能替代首次真实双证明 landing 被 finalize。
</toggle>

## 9. 同步与弱主观性

- <b>重放与现场同规则</b>：冷同步（重放或 blocksync）时，对没有现场判断过、且带 anchor witness 的块，FinalizeBlock 同样先用自己的 L1 节点确认 anchor header 是 canonical 且已 finalize，并按 3.4 核对 witness 里的 lastCheckpoint。本地 L1 落后、连不上或超时只等待重试；只有自己的 L1 节点给出矛盾证据时才 safety 停机。
- <b>Checkpoint 栅栏</b>：FinalizeBlock 把 anchor 证明的 <code>lastCheckpoint.hash</code> 作为 <code>finalized</code> 传给 EL 的 forkchoice，不以它为祖先的历史会被 EL 拒绝（<code>-38002</code>），节点 safety 停机。旧 key 伪造的历史因此最多比分叉点多出 U 块，但分叉点可能很旧；伪造 checkpoint 之上的块需要治理这些高度的 committee 超过 2/3 的 key，而这些 stake 在 checkpoint 覆盖其退出之前不能提款。
- <b>弱主观性由 L1 解决</b>：每次 app 启动和 signer 建立 session 时，节点都从未信任开始，在自己的 L1 finalized 视图里认证 Inbox 的最新 checkpoint，追到该高度、且 EL hash 和 slot 285 记录里的 CometBFT hash 都精确匹配后才可信（block 0 的记录 Comet hash 为 0；恢复起点 c 的记录保留其原 generation 的 Comet hash）；之后每次 anchor 变化都按 3.4 核对新的 lastCheckpoint。伪造的历史要么停在目标以下、始终不被信任，要么在目标处被拒绝，因此不需要弱主观性 checkpoint，也不需要给起点设年龄上限。认证所需的数据暂缺时保持未信任并重试；遇到已认证事实的矛盾，或者自己的 L1 节点、EL 返回格式错误或无法验证的数据时 safety 停机，因为节点无法把它与伪造区分开。hash 与 canonical hash 一致的 L1 header 不在此列：它的来源已经认证，解析不了只说明节点需要升级（3.3）。 恢复 generation 的固定 genesis 起点与此处最新信任目标可能不同，必须按 8.4 区分并重放，不能随最新 checkpoint 重建同域 genesis。

<toggle>
可信才签名、可信才对外（签名门槛与自动重启细则）

- <b>可信才签名、可信才对外</b>：validator 的每一次签名（包括 nil 和保留块）都要经应用确认节点可信；未信任、超时或 generation 被取代时一律不签，也不能退回本地签名。CometBFT v0.40.0 对被拒或超时的签名请求不重试，至少 1/3 的投票权在同一步被拒签就会让该高度一直停住。因此签名请求因未信任或超时被拒后，supervisor 必须在 trust 恢复后自动重启 CometBFT：signer 先完成新 session 的 trust 检查，再连接 CometBFT 的 <code>priv_validator_laddr</code>，WAL 重放随后对被拒的那一步重新发起签名请求。签名器按 stock 规则拒绝更低的 height/round/step、对同一位置返回原签名，且签名先落盘再广播，所以不会双签。重启不需要人工，也不重置任何签名状态；第 8 节的 safety 停机、旧 generation 的签名请求和 10.1 升级边界处的拒签都不触发重启。交易所、桥和公共 RPC 要看应用的 trust 状态，不能只看 CometBFT/EL 的同步进度或 <code>catching_up</code>。
</toggle>

<toggle>
细节：节点要求

- <b>节点要求</b>：自己的 L1 节点要能按块号返回 <code>L1_0</code> 以来的 header，并提供信任检查所需的 <code>eth_getProof</code>；validator 还需要历史 <code>eth_getProof</code> 和 <code>debug_getRawHeader</code>，proposer 还要能查到未消费 forced inclusion entry 的历史 log。
</toggle>

<toggle heading="h3">
9.1 共识历史与双签证据

- 完整 CometBFT 恢复和 proving 需要原始 blocks/envelopes、headers、commits/LastCommit、registry snapshot/entries/witness、FI 原文/日志及所需 L1 headers/proofs、创世参数和恢复记录。归档须保留这些依赖；仅有公开 blob 或 EL snapshot 不够。私钥不属于历史归档，签名状态另按 8.2 保存。
- 文件 hash 只能检错，不能认证 committee。恢复从自己的 finalized L1 认证当前 generation 的固定起点、c 的 EL/Comet hash 和 R 的 registry snapshot，并按 4.3 重选；随后按已认证 switch 历史验证当前/pending committee。EL snapshot 的 app\_hash 不认证额外 committee 元数据。缺材料保持未信任，认证矛盾按第 9 节停机。
- 任何人可从不同 peers 收集可验证的同 round 冲突票，并直接向 L1 提交；不以 Comet evidence 入块为前提。证据保留/提交不受本地 evidence pool 的 100,000 块/48 h 限制，应跟踪 confirmExit 和提款边界。抵押提款已 finalize 前仍可能需要历史证据；保存历史不能保证观察到所有冲突票，也不把跨 round 不同 BlockID 自动视为双签。
</toggle>

## 10. 启动与部署

下面先按从起点 block 0 启动来写；补上 Unzen 到 Etna 的切换后，这一节随之调整。

1. 部署 Inbox proxy（暂不初始化，仅其 owner 可初始化），再部署 registry 并固定该 proxy 地址；validator 用 consensus key 签注册摘要（附录 A）后注册，等激活并 finalize。
2. 选一个过去的 <code>genesisCutoff</code>，算出 committee 0 的 record hash 和 config hash。
3. 在 L2 genesis 中安装 EIP-4788、EIP-2935，basefee 分成比例为 100。
4. 用 EL 算出 block 0 的 hash 和 stateRoot。
5. 部署 SignalService 并初始化 Inbox（按 4.1 校验 registry），写入 genesis hash/stateRoot、L、genesisCutoff、committee 0/config hash、forcedInclusionDelay、maxAnchorAge，并保存 block 0 checkpoint。固定非零 DAO treasury 为 protocolFeeRecipient；recoveryGeneration 初始为 0，activeCommitteeSnapshot 初始为 genesisCutoff；初始化 8.4 的 generation 0 起点记录；recover 只允许 owner 调用。
6. 等 L1 finalize 后从 L1 读出创世记录并生成 CometBFT genesis。先启动 EL 和 ABCI app，再启动 guarded signer 与配置了 <code>priv_validator_laddr</code> 的 stock CometBFT；trust 关闭时 PubKey/Ping 仍允许握手。Signer 在 Comet home/mount 之外持有已有的已注册 key 和防双签 state。使用受支持的 supervisor/启动配置，不得靠重置签名 state 或启用本地 FilePV 回退绕过 readiness。Full node 使用未注册身份。

<toggle>
细节：部署约束

<b>部署约束</b>：L≥3，L+1\<2\^48；cutoff 在过去且不早于 registry 首个 checkpoint；forcedInclusionDelay>0，maxAnchorAge≥1152 s；K≤U≤65,536 且 U 是 K 的倍数（目标部署 U=3,600，对 1 ≤ K ≤ 6 都满足），L1\_0\<2\^48，1≤n\_max≤4096，vp\_unit≥867,361,738（4.3），s\_min≥vp\_unit；注册/退出延迟取正数；部署、节点和 guest 核对同一配置。chain\_id 按附录 A 为 48 个 ASCII 字节。不可变参数错误仍须新 Inbox/new genesis；registry 固定了旧 Inbox 地址，须由 DAO 升级改指新 Inbox 或重新部署 registry；不重置旧签名状态。
</toggle>

U 取 3,600，L 独立选定（建议 900），约 4 s 出块、20 min landing 为运行目标；固定 maxBatchBlocks≥K（至少一个网格段）。上线门槛（含 committee 0 的最低总 stake 与集中度要求）及全部验收见 Etna 验收与上线清单；未通过前不能称可部署，也不把未实测恢复时长当服务承诺。

<toggle>
细节：初始部署的 CometBFT genesis 参数

<b>初始部署的 CometBFT genesis</b>（治理恢复的起点、时间、validator 与 app\_hash 按 8.4；InitChain 校验 ABCI 能表示的字段）：<code>chain_id</code> 按附录 A 由完整 L1/L2 chain id、Inbox proxy 地址和 Inbox 的 <code>recoveryGeneration</code> 生成；<code>initial_height</code> = 1；<code>genesis_time</code> = <code>L1_0</code> 块的时间戳；validators 恰好是 committee 0（key 和 power）；<code>app_state</code> 带 <code>L1_0</code> 的 header、Inbox proof 和 committee 0 witness。Consensus params 固定：<code>block.max_bytes</code> 22,020,096、<code>max_gas</code> −1；evidence 100,000 块、48 h、1 MiB；只允许 secp256k1eth；<code>APP_VERSION = 1</code>；不开 vote extension；没有参数更新权限。初始状态：anchor 为 <code>L1_0</code>，forced cursor 为 0，checkpoint 为 (0, genesis hash)。 Generator 写入空的参数更新 authority；当前 typed InitChain 请求不暴露这个字段，所以 InitChain 无法独立比较它。不支持从其他 app/config 版本原地迁移（包括已有 entry 的 registry），不能靠删除保留状态绕过版本检查。
</toggle>

<toggle heading="h3">
10.1 协议升级边界

- 协议升级先停链、结清再切换规则；不承诺无停机升级。普通运维重启若不改变有效性规则，保留同域全部 signer state。改变第 10 节部署后不可变参数的操作仍属于新 Inbox/新 genesis 的独立迁移，不能用本节绕过不可变性。
- 协议升级方案必须绑定部署、generation、边界高度 H（须为网格点，因为 landing 只在网格点结束，6.1；改 K 的升级，H 须同时是新旧 K 的倍数，否则升级后找不到新网格上的起点）、旧/新客户端与 EL 规则、guest image 和 verifier 接受范围。方案须由实际 DAO/timelock 权限认证，并由节点及 L1 验证路径强制执行；只有链外 manifest 或运营者口头约定不够。这套激活机制尚未完整设计，之后再补；不得仅注册新 image 就宣称协议已升级。
- 边界前协调 signer 不再签 H 以上，保留全部 HRS 状态；先用旧规则结算到 H，并认证其 EL/CometBFT checkpoint，再启用 H + 1 的新规则。计划必须在签名跨过边界之前生效；若已有 H 以上签名或未结算块，不能删除状态或把边界倒退来强行执行，须重新规划，无法结清则按第 8 节另行处置。
- 在途任务按部署、generation、statement/config/image 版本和高度区间隔离；batch 不跨 H。旧任务须在切换前合法结清或明确作废，不得改写为新版本。历史重放保留旧规则/镜像资料，但 L1 对 H 以上的结算不能再接受只验证旧规则的 image；新 image 也不能隐式改变 H 及以下历史。须定义并测试确切的链上接受范围、切换交易及失败回退方案。
- 升级激活机制之后再补，本节不构成可用的恢复兜底。L1 硬分叉的外部期限另见第 12 节第 10 项。
</toggle>

## 12. 已知限制与未决

1. <b>不提供墙钟 FI deadline。</b> <code>maxAnchorAge</code> 只限制 anchor 相对块时间的年龄；墙钟上的推进还依赖 3.4 的 BFT time 前提、队列积压、L1 finality 和 settlement（7.3）。
2. <b>离线 quorum 依赖 DAO 恢复。</b> 链停住后不自动换人；成员回来可恢复，否则由 DAO 在 R 上重选并按授权排除（第 8 节）。新合格候补可直接加入，但在线率和运营方集中度仍由 DAO 判断，不保证恢复成功；L1 不 finalize、证明不完备或历史缺失时也可能无法恢复。普通恢复丢弃 c 以上后缀，耗时包括 DAO 授权延迟、finality、重建、签名迁移和首次结算；没有治理之外的 escape hatch。
3. <b>双签只罚同 round。</b> 跨 round amnesia 不覆盖，gossip 也可能漏掉证据；离线不罚没（4.1、第 8 节）。
4. <b>运营依赖 DAO 资金。</b> Landing 没有协议收入，结算活性依赖 DAO 资助的 lander 以及 validator 为避免 back-pressure 停链而自行 land；预算和真实 proving/landing 成本仍须实测（附录 C）。
5. <b>依赖 L1 finality。</b> 没有满足 <code>maxAnchorAge</code> 的 finalized anchor 时停止出块（3.4）。
6. <b>空 committee。</b> 没有合格候选时正常 switch 停住；恢复也不能凭空制造 quorum，须先补足合格 stake（4.3、第 8 节）。
7. <b>不限制换届权重变化。</b> 每届直接按 stake 选前 n\_max，不承诺接管下界或 DAO 可反应的时间窗；须持续检查实际 committee 少于 1/3 拜占庭权重的假设（4.3）。
8. <b>退款依赖结算及确认后的取证期。</b> 退出须先被已 land 的 committee 覆盖，再确认并等满 withdrawalDelay。Inbox 无法恢复或必须替换时，解除阻塞仍需治理升级（4.1）。
9. <b>Unzen 切换暂未纳入。</b> 为了精简和便于讨论，本 spec 刻意先不处理从 Unzen 切换到 Etna，之后再补；第 10 节的启动流程和文中的起点（block 0、committee 0 及 6.1 的网格原点）届时随之调整。桥的接线也随切换一起补：L2→L1 已能用 SignalService checkpoint，但现有 Bridge、vault 和 L2 SignalService 怎样接入（包括 L2 SignalService 改从 EIP-4788 读 L1 状态）还没有规定。
10. <b>升级激活机制尚未完整设计。</b> 10.1 已限定先停链并结清到 H、H + 1 切规则、在途任务隔离和历史重放边界；但认证升级计划、按高度约束 image 的链上接受范围及切换/失败路径仍待设计，之后再补，不能当作可用兜底。L1 的硬分叉是另一类外部期限：只在 header 尾部新增字段的分叉由 3.3 的解码规则自动兼容；改动已有字段或状态承诺的分叉（例如 EIP-7864 的 binary trie 会让所有 MPT witness 失效），必须在该分叉于 L1 激活前完成客户端与 guest 升级并注册新 image，期限按 L1 的时间而不是 L2 高度算。
11. <b>Registry 容量。</b> 共 4096 个 slot，占满需要锁定 4096 × <code>minStake</code> 并支付 L1 交易成本，占满期间新注册被挡住。注册在激活前就占用 slot；未入选的 entry 也会一直占位到退出并提款完成。因此，占位者无需控制 committee 投票权，就可能挡住 stake 更高的新成员。竞争式或有期限的准入仍待设计；任何回收机制都必须保留历史 snapshot proof，并遵守抵押金提款的 settlement 条件。
12. <b>不自动处理逐步离线。</b> 协议不按参与率降权，离线成员可持续占据 stake 排名；依赖 owner 退出、其他合格 stake 替换或停摆后的治理恢复。
13. <b>secp256k1eth 较新。</b> 该 key 类型在 CometBFT v0.40.0 才加入，期间还修正过一次签名格式，实战检验少于 Ed25519；外部 signer、HSM/KMS 的支持要单独确认。CometBFT 对它不做批量验签；Etna 验收与上线清单 要求固定版本、跨实现 vectors、signer/HSM/KMS 兼容性和 n = 128 的实测，不能在测试前断言成本影响很小。
14. <b>注册准入边界。</b> vp\_unit 下界只保证 power 不溢出（4.3）；入选仍受 4096 registry slot、stake 排名和资格约束，不保证每个注册者入选。
15. <b>私有共识历史可用性。</b> 公开 blob 只够重建已结算的 EL；普通证明、Comet 重放、签名证据和 L1 ancestry 都依赖 9.1 的归档，不能以未认证 snapshot 替代。
16. <b>短区间 landing 防护由重叠证明承担，待验收。</b> 网格规则见 6.1 和 6.3。对手先 land 到 (p,h) 内任何网格点，都不会让诚实提交失败；只有对手结算到 h 或更高时，诚实提交才会因目标已结算而 revert，这时对手已替它推进了结算，触发不了 back-pressure，诚实 lander 最多白付这笔交易的 blob gas 和 calldata。不宣称在超过 1/3 合谋、证明/数据不可用或 L1 不 finalize 时保证吞吐或恢复。
17. <b>资源与时延数字待验证。</b> U=3,600、约 4 s 出块、20 min landing、正常约 900 块未结算和约 3 h 故障余量都是算例，不是实测，须通过 Etna 验收与上线清单。anchor 只核对最新 checkpoint，不取消历史保留，也不解决 L1 无限期不 finalize；未结算后缀仍是治理回滚暴露。
18. <b>停链门槛的总 stake 下限尚无具体数值。</b> 超过 1/3 投票权不签名即可让链停住；下线不罚没，被排除的 entry 在新 generation 首次 landing 后即可确认退出，等满 withdrawalDelay 后全额取回（4.1、第 8 节），停链者的代价主要是资金锁定期间的时间价值。主要防线是 Etna 验收与上线清单 第 4 节的上线门槛 S\_MIN\_TOTAL，但它只写了“按取得超过 1/3 投票权所需的资本选定”，而这笔资本本身由 committee 的总 stake 决定，因此定不出具体数值。还需选定一个与现有质押无关的外部目标并据此给出 S\_MIN\_TOTAL，并进一步核对上线时、定期复核时和每次恢复授权前的实际 committee 是否满足，包括恢复期间新激活、可能进入 R committee 的 stake。

<toggle heading="h2">
附录 A：编码

<b>版本</b>：APP\_VERSION=1，所有带版本号的域标签均为 V1；外层 envelope/payload 前缀为 0x06。Config 为七字/224 字节；CommitteeRecord 为五字段。Slot 285 为三字（附录 B）。真实 guest image/verifier 的接受范围须与 config 绑定；升级机制完整设计前，不能只换客户端或注册 image 就激活新规则。

<b>共享 vectors</b>：所有编码、接口、存储布局和边界条件都须有节点、合约和两套 guest 共用的接受/拒绝 vectors，清单见 Etna 验收与上线清单。

协议 hash 用 keccak256 over <code>abi.encode</code>，域标签是右补零的 <code>bytes32</code> ASCII；例外是 <code>entriesRoot</code> 的内部节点直接拼接、blob hash 列表和截点叶子列表用 <code>abi.encodePacked</code>。


附录 C：运营资金与成本假设

本附录是运营要求，不是有效性规则。

- <b>运营资金由 DAO 承担</b>：覆盖 validator、proving、landing、历史数据和值守，包括低/零交易负载、FI 消费、重复 DA、竞争导致的废弃证明和重试。Landing 没有协议收入（basefee 和小费归 proposer，FI 费归协议），landing 与 proving 成本全部由这笔运营资金承担。
- <b>资助方式</b>：资助不授予独占 land 权限。Lander 不领取 FI 费，资助也不按消费的 FI 条目数或 FI 费金额发放，因此攻击者不能借资助收回入队费（7.3）。land 不绑定收款方，公开的 blob 交易可被复制，因此 DAO 资助不能是按提交地址发放的逐次 landing 赏金，应资助指定运营方或在链下认定工作量。
- <b>按持续最坏负载落实预算</b>：按约 4 s 出块、相邻成功 landing 的 L1 入块间隔不超过 20 min 的运行目标（6.4）测量并落实预算，仅有成本估算不能作为资助已落实的证据。Proposer 在自己块里的任何负载都不付净手续费（3.2），包括 zk 密集负载和大数据负载；这类负载照常只受每块 gas、zk gas 和 124,000 字节（3.4）上限约束。zk gas 不折成计费 gas，zk 密集但 EVM gas 较低的有效负载可能几乎用满每块的 zk gas 上限。数据的最坏情形是每块都填满不可压缩数据：一次 landing 最多带 6 个 blob、装 6 块，又只能在网格点结束，所以每次覆盖 m 块（m 为不超过 6 的最大 K 倍数），约每小时 900/m 次：K 整除 6 时 m = 6，约 150 次；K = 4 时约 225 次；K = 5 时约 180 次。无论 K 取多少，都是每个 L1 slot 3 个 blob。DAO 须按这种持续最坏负载落实证明、blob 与 landing 预算。
