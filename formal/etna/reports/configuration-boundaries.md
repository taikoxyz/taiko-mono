## Current committee and epoch limits

The production core bounds `n_max` above by 4096, the registry's leaf capacity, and no longer bounds the epoch length beyond the uint48 first-height check. `ChainParams::validate` retains its original order: strict positive unsettled cap, nonzero voting-power unit, nonzero committee size, then the upper committee-size bound before later checks. The extracted upper-bound predicate deliberately returns true for zero; the wrapper's earlier `ZeroNMax` guard rejects it.

The V7 limit `L <= 429496` bounded per-member proposer scores packed in `uint32` by the L1 reward pool. V8 removes that pool, so the limit, its `EpochTooLong` error, the score-budget theorem and the epoch-end batch cut are removed from the core, the proofs and the corpus. `COM-uint48_controls` now binds `uint48_priority`, where `L=max48-1` is accepted again because its first height still fits uint48. `COM-removed_epoch_cap_boundaries` shows `L=429497` accepted with priority controls. The committee-size boundary examples and corpus pin 4096 accepted and 4097 rejected. All primary FI/committee history, cut, authentication and activation contracts are unchanged.

The 4096 bound is a configuration policy. It does not establish CometBFT performance, commit-certificate size or guest proving cost for a committee of that size; those remain deployment parameters.
